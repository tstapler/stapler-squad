# Pre-mortem: terminal-resize-fit-loop
**Date**: 2026-07-27

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The imperative `fit()` entry point (`XtermTerminal.tsx:615`, `useImperativeHandle`, called by `TerminalOutput.tsx`'s visibility-change and `visualViewport.resize` handlers) is never wrapped with `shouldFit` — only the `ResizeObserver` call site gets the AC2 gate — yet AC1/AC7's own repro is "tab background/resume **or** window resize," and the plan's ADR explicitly names this path as an accepted residual risk rather than something the fix touches. | Manual QA (Epic 5.2) — or a user report post-ship — shows CPU pegging/freeze still reproduces specifically via tab background/resume, while the window-resize trigger looks fixed. | Extend the same `shouldFit`-gated pattern to the imperative `fit()` path in `XtermTerminal.tsx:615`, or, at minimum, split Epic 5.2's manual checklist into two independently-verified sub-cases (window-resize-only vs. tab-background/resume-only) so a partial fix can't silently pass as "AC7 verified." | P1 |
| 2 | `shouldAbandonWebgl`'s 3-recurrences-in-2000ms threshold only catches oscillations with a same-value recurrence period below ~666ms; a real-world wobble that repeats every ~1000-2000ms (still a genuine, unbounded `shouldFit`/`shouldSendResize`-passing loop, since each recurrence is a "real" value change relative to the *other* alternating value) never accumulates 3 hits inside any rolling 2000ms window and the WebGL fallback never trips. | Post-ship, some sessions show low-frequency-but-nonzero periodic `fit()`/RPC activity that never fully idles (violates AC1's "settles to zero"), at a rate subtle enough to not register as "frozen" and get dismissed as fixed. | Add a test case for a persistent slow A/B alternation at ~1-1.5s period asserting the plan's known detection boundary, and either widen the window / lower the threshold, or explicitly document the numeric boundary (recurrence period must be `< windowMs/threshold` ≈ 666ms to trip) as an accepted residual risk in ADR-018, with a note in the manual QA checklist to watch for slow residual churn, not just total freeze. | P2 |
| 3 | The WebGL→default-renderer fallback is session-scoped, not persisted (an explicit, deliberate decision), and the Observability Plan has "None" for metrics — any user whose GPU/DPI combination reliably reproduces the glyph-metric mismatch re-runs the identical 3-recurrence oscillation-then-fallback cycle on every new session, with zero way for the team to measure how often this fires across the user base. | No crash or freeze — just an unmeasured, indefinitely-recurring silent WebGL→DOM-renderer downgrade per affected user per session; nothing in any dashboard or log aggregation surfaces it, so it can't be prioritized as a real fix later. | Add a minimal observability signal beyond a bare `console.warn` (e.g., a distinctly-tagged log line intended for later log-aggregation pickup, or a lightweight sessionStorage/localStorage counter), and reconsider making the fallback sticky per-origin so a repeat-affected user doesn't relearn-then-refallback every session — currently resolved by fiat in "Unresolved Questions" without weighing this cost. | P2 |
| 4 | All AC5 test coverage exercises the pure gate functions against synthetic, hand-toggled `proposeDimensions()` values in a JSDOM harness that has no real WebGL/canvas layout engine — it can prove `shouldFit`/`shouldSendResize`/`shouldAbandonWebgl` are internally correct, but cannot prove real xterm.js + real WebGL in a browser actually produces the assumed value sequence, timing, or convergence. The one-time, informal, PR-description-only manual QA pass (Epic 5.2) is the sole check against reality. | `make ci` and all Jest suites pass, PR merges, but the original bug reporter (or another user with a similar GPU/DPI) reopens the ticket because the CPU pegging/freeze still reproduces in an actual browser. | Treat Epic 5.2 as a hard merge gate, not just a PR-description checklist item; reproduce it specifically on hardware/browser matching the original report's `Actual pixels per column: 8.45px vs Expected: 8.33px` evidence (not "any available dev machine"), and record the actual observed pixels-per-column numbers (not just pass/fail) so a future regression has a quantitative baseline to compare against. | P1 |
| 5 | The new gates make the steady-state console output dominated by "Skipping fit()" / "Resize skipped" / oscillation-backstop log lines (some of which, e.g. `shouldFit`'s skip log, don't even include the compared values), so a future, genuinely different resize bug (new feature, new addon interaction) becomes harder to distinguish from "gate correctly suppressing," since the expected noise floor is now much higher than pre-fix. | A later, unrelated resize regression takes longer than it should to triage because engineers scanning the console can't quickly tell "gate working as intended" from "gate silently swallowing a real bug" without manually re-deriving expected cols/rows at each site. | Include the compared proposed/current (or next/lastSent) values inline in every skip-path log message, consistently across all three gates, and add a short note to `.claude/docs/` (or inline comment) that a future resize-bug triage should start by reading the *values* in these log lines, not just their presence/absence. | P3 |

## P1 Items (address before implementation)
- [ ] #1 — Extend `shouldFit` gating (or an equivalent check) to the imperative `fit()` path (`XtermTerminal.tsx:615`) used by `TerminalOutput.tsx`'s visibility/`visualViewport.resize` handlers, since AC1/AC7's repro explicitly includes tab background/resume and the current plan leaves that exact path ungated; failing that, split Epic 5.2's manual checklist so the tab-background/resume trigger is verified independently of window-resize and cannot pass by proxy.
- [ ] #4 — Upgrade Epic 5.2's manual verification from a PR-description-only checklist to a hard pre-merge gate, performed on hardware reproducing the original `8.45px vs 8.33px` glyph-metric evidence, with the actual observed numbers recorded — since no automated test in this plan can exercise real WebGL glyph-metric divergence at all.
