# Adversarial Review: session-search-fts5

**Date**: 2026-08-02
**Verdict**: BLOCKED → **RESOLVED** (2026-08-02, post-Phase-4 validation pass — see resolution notes on each item below; `plan.md` now reflects all four fixes)

All findings below were verified against the actual `main`-tree source (not just the plan's own citations) — file:line references point at code read directly during this review.

## Blockers

- [x] **RESOLVED** — see Epic 1.5's "Correction" note in `plan.md`: `isAutomationSession` now filters on `Instance.Hidden`, matching this finding's own recommendation. ADR-002 updated to match. **Automation-session exclusion filters on the wrong field.** `isAutomationSession`/`filterAutomationSessions` (Task 1.5.1a) check `Instance.AutonomousMode` (`session/instance.go:163-166`), which is the user-facing "Fix Autonomously (Beta)" opt-in toggle (`server/services/session_service.go:1221-1769`, `.claude/rules/session-creation-registry.md`'s `autonomous` mode), not a background/system-session marker. The field that actually means "hide this from user-facing session surfaces" is `Instance.Hidden` (`session/instance.go:220-223`, comment: "excludes this session from the default session list and review queue"), already wired into `ListSessions` filtering with an `include_hidden` request flag (`server/services/session_service.go:1089,1129`; `proto/session/v1/session.proto:444-446`). Backlog-triage/background-review sessions are created via `CreateDirectorySession(..., hidden bool)` passing `hidden=true` (`server/services/backlog_service.go:30`; call sites at `backlog_service_triage.go:2439-2440`, `session_service.go:827`) — they do **not** set `AutonomousMode`. Shipping Story 1.5.1 as specified will (a) fail to exclude the actual background/triage sessions it's meant to hide, and (b) incorrectly exclude legitimate human-initiated "Fix Autonomously" sessions the user deliberately created. `research/architecture.md` §6 itself traced `Session.hidden` in its lineage read (citing `types.proto:189-192`) but then concluded "The only origin signal that exists anywhere in the repo is `session.Instance.AutonomousMode`" — contradicting its own earlier finding — and ADR-002 inherited that error uncritically. — **Recommendation**: swap the signal to `Instance.Hidden` in `isAutomationSession`; keep the best-effort framing (Hidden has the same live-`Instance`-only lifetime limit as AutonomousMode — see Concern below); consider renaming `exclude_automation_sessions` to something that reflects "hidden/background sessions" to match the existing `include_hidden` convention on `ListSessions`.

- [x] **RESOLVED** — see Task 1.2.1b in `plan.md`: the raw engine fetch is now oversampled (`requestedLimit * 5`, capped at 100) whenever post-processing is requested, and truncation to the caller's `limit` happens only after dedup/filtering. Story 1.2.1's third GWT now exercises exactly the busy-session-vs-5-distinct-sessions scenario this finding calls out. **Dedup and automation-filter run after the engine's limit/offset truncation, not before.** `SearchEngine.Search()` (`session/search/engine.go:191-259`) computes `TotalMatches` as a message-level count across *all* sessions, then slices `Results` down to `opts.Limit` (message-level) before returning (`engine.go:225-233`). The handler then runs `filterAutomationSessions` → `groupResultsBySession` → `contextWindowAndBookends` (Tasks 1.5.1b, 1.2.1b, 1.3.1c) on that already-truncated slice. With the triage panel's fixed `limit=5` (`RelatedWorkQuery`, Task 2.2.1b), if the top-5 highest-scored *messages* happen to cluster in 1–2 sessions, `group_by_session=true` returns only 1–2 session rows even though many more relevant sessions exist just below the message-level score cutoff — the opposite of what "discovery" is for. `exclude_automation_sessions=true` can shrink the already-small truncated set further, silently returning fewer than `limit` results when other qualifying sessions exist. `more_matches_in_session_count` undercounts, since it only tallies duplicates within the pre-truncated top-N messages, not a session's true match count. `HasMore` (`searchResults.TotalMatches > offset+len(protoResults)`) compares a pre-filter, message-level total against a post-filter/dedup count, so it can report "more" when there isn't (or vice versa). Story 1.2.1's own Given/When/Then example only holds because its total message count is below the applied limit — it doesn't exercise the realistic default (`limit=5`) case at all. No task addresses over-fetching from the engine (e.g., requesting `limit * K` messages, or making the engine itself session-count-aware) before applying dedup/filtering. — **Recommendation**: either request a materially larger `Limit` from `SearchEngine.Search` when `group_by_session`/`exclude_automation_sessions` is set (then truncate to the requested session-level limit *after* grouping/filtering), or teach the engine a session-aware result cap directly.

- [x] **RESOLVED** — see new Story 2.2.3 in `plan.md` (Epic 2.2): `SessionHitCard` now wires `onClick` to open the session's history page in a new tab via `?sessionId=&messageIndex=`, and Task 2.2.3b confirms/adds `anchor_index`-based centering in `history/page.tsx`, with an explicit fallback (default view) if that page-level plumbing isn't ready at implementation time. **Scroll mode has no frontend consumer anywhere in the plan.** `anchor_index` is added to the proto and backend (Tasks 1.1.1a, 1.4.1a/b) but is never referenced in Phase 2 — `useHistoryFullTextSearch`'s extended `SearchOptions`/`SearchResultItem` (Epic 2.1) and `TriageRelatedWorkSection`/`SessionHitCard` (Epic 2.2) only thread `groupBySession`/`includeContext`/`excludeAutomationSessions`. `requirements.md` lists scroll mode as explicitly **In Scope** and as a **Success Metric** ("A user can page through a session's messages around a hit... without re-issuing the FTS query — currently impossible"). As planned, no user or UI can ever invoke `anchor_index` — it's backend-only work that doesn't satisfy the requirement it exists for. This gap is not acknowledged anywhere in the plan's "Unresolved Questions" or Story 2.2.1's explicit out-of-scope note (which only calls out the PASS/FAIL outcome-badge cross-reference as a deferred fast-follow). — **Recommendation**: add a Phase 2 story wiring anchor-based "load more before/after" into `SessionHitCard`'s context window (the natural UI for it), or explicitly document scroll-mode UI as deferred and why.

- [x] **RESOLVED** — see Epic 1.6 (`filterByProject`) in `plan.md`, further hardened by the Phase-4 pre-mortem's P1 finding: the post-fetch filter now resolves worktree session paths to their main repo via live `Instance.MainRepoPath` before comparing against `item.RepoPath`, rather than naive string equality (which would have silently returned zero results for any worktree-run session). **`SearchClaudeHistory` never applies the `project` filter the plan's frontend relies on.** `SearchClaudeHistoryRequest.project` (`proto/session/v1/session.proto:958-973`, `optional string project = 2`) is read by `ListClaudeHistory` (`server/services/search_service.go:256-257`, a different handler) but is never referenced anywhere in `SearchClaudeHistory` (`search_service.go:459-598`), and `search.SearchOptions` (`session/search/engine.go:23-30`) has no project field — the BM25 engine has no concept of project scoping at all. Yet `RelatedWorkQuery` (Domain Glossary; Task 2.2.1b) explicitly sends `project: repoPath` on every triage search, implying results are scoped to the backlog item's own repo. In reality this field is silently dropped server-side, so the "Find related past work" box will return matches from every project in the user's entire history, not just the current repo — undermining relevance for anyone with more than one active project, and contradicting the plan's own stated intent. No Phase 1 task adds project filtering to the handler or engine.

## Concerns

- [ ] **`IncrementalSync`'s exclusive lock gets a new high-frequency, potentially-automated call site.** `pitfalls.md` §2/`architecture.md` §4 already document that `IncrementalSync` (`session/search/engine.go:399-496`) holds an exclusive `e.mu.Lock()` across a full directory scan + possible reindex-save on *every* `SearchClaudeHistory` call, blocking all concurrent `Search()` readers. The plan adds a second, 300ms-debounced, auto-searching entry point (`TriageRelatedWorkSection`, mounted per backlog item and re-searching on every query edit) without resolving the question research explicitly deferred to planning ("worth deciding per-RPC whether a full sync is actually needed"). `requirements.md` describes "the triage agent" as a primary consumer — plausibly an automated process triaging many items back-to-back — which would multiply exclusive-lock/full-scan cycles under exactly the bulk-automated usage this app is built around. No throttling/caching/"already synced this cycle" mitigation is proposed anywhere in the plan.
- [ ] **`include_context=true` (always-on for triage) reads the entire conversation file per retained hit.** Task 1.3.1c calls `hist.GetMessagesFromConversationFile(r.SessionId, 0)` — a full-file read — per retained hit, just to slice out an ~11-message window; `RelatedWorkQuery` always sets `includeContext: true`. For long sessions (hundreds/thousands of messages) this is O(session size) synchronous disk I/O per hit, uncached across the panel's own debounced re-searches. `requirements.md`'s NFR requires confirming no latency regression, and `architecture.md` §2 flagged this exact cost as "worth a latency check in Phase 4 validation" — but no `validation.md`/Phase 4 artifact exists yet for this project, and no task in this plan benchmarks context-window latency against realistic session sizes before shipping.
- [ ] **Out-of-bounds `anchor_index` silently returns the whole conversation instead of an empty/clamped page.** Existing offset-slicing in `GetClaudeHistoryMessages` (`search_service.go:435-440`) only applies `messages[offset:]` when `0 < offset < len(messages)`; if `offset >= len(messages)`, the guard is false and the full unsliced list is returned. This latent bug becomes far easier to trigger via `anchor_index` (Task 1.4.1a: `offset = anchor - limit/2`) — a client-supplied anchor from a stale/cached search result is much more likely to fall outside a session's current bounds than the existing offset-only callers, which typically derive their offset from a `totalCount` fetched in the same request cycle. Task 1.4.1b's only test covers a valid mid-session anchor, not an out-of-range one.
- [ ] **Fixing the field-selection bug (Blocker 1) does not fix the durability gap.** Whichever field is used (`Hidden` or `AutonomousMode`), it only reflects sessions still tracked in the live `Instance` store — anything whose `Instance` record was deleted is silently un-filterable. This is already documented in ADR-002 for `AutonomousMode` and applies identically to `Hidden`; flagging so the Blocker-1 fix isn't assumed to also close this gap.

## Minors

- `filterAutomationSessions`'s `out := results[:0]` in-place-filter idiom (Task 1.5.1a) is correct but has no comment explaining the aliasing — a future edit could break it (e.g. by holding a reference to the pre-filter slice expecting it untouched) without realizing the intent.
- Task 3.1.1b's example registry JSON hardcodes `"lastModified": "2026-08-02T00:00:00Z"` — obviously needs the real implementation date; a copy-paste risk only if followed literally.
- Story 2.2.2's reassuring empty-state copy ("this looks like new territory") isn't derived from any explicit requirements.md AC — harmless, well-justified scope addition serving the stated triage-operator need, not flagged as a problem, just noted for completeness.
