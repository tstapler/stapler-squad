**Date**: 2026-08-02

## Blockers

- [x] **RESOLVED** — see Task 1.2.1b's oversampling fix (`rawLimit = requestedLimit * 5`, capped at 100, truncation deferred until after dedup/filtering), matching this finding's own remediation exactly. **Story 1.2.1 / Story 1.5.1 / Epic 2.2's `RelatedWorkQuery` (`limit=5`)** — `group_by_session` dedup and `exclude_automation_sessions` filtering run *after* the search engine has already truncated results to `req.Msg.Limit` message-level hits. In `server/services/search_service.go:514-521`, `searchOpts := search.SearchOptions{Limit: limit, Offset: offset}` is passed straight to `ss.searchEngine.Search(...)`; in `session/search/engine.go:222-233`, `totalMatches := len(scoredDocs)` is captured *before* the `if opts.Limit > 0 && opts.Limit < len(scoredDocs) { scoredDocs = scoredDocs[:opts.Limit] }` slice, but the returned `Results` slice itself is already cut to `opts.Limit`. `groupResultsBySession` (Task 1.2.1b) and `filterAutomationSessions` (Task 1.5.1b) then operate on that already-truncated slice. `TriageRelatedWorkSection`'s default query (Story 2.2.1) sets `limit=5` — meaning at most the top 5 *raw message* hits are ever fetched before dedup/filtering gets a chance to collapse duplicates or drop automation sessions. If those 5 top-scored messages cluster in 1-2 busy sessions (precisely the scenario Story 1.2.1 exists to fix) or include an automation session, the operator sees 1-2 or zero results even when 5+ genuinely relevant human sessions exist just past the unexpanded top-5 window. None of Stories 1.2.1/1.3.1/1.5.1's GWT fixtures (4 total messages across 2 sessions) exceed the default engine limit, so this is untested by the plan as written.
  **Remediation**: when `group_by_session` or `exclude_automation_sessions` is set, request an oversampled raw limit from the engine (e.g. `max(limit*5, 50)`, capped at the existing 100 ceiling), then filter → dedup → truncate to the caller's requested `limit` of *sessions* before returning. Add a test fixture where 5+ distinct sessions exist in the raw top-50 but the raw top-5 hits collapse to 1-2 sessions, to lock in the fix.

- [x] **RESOLVED** — see new Story 2.2.3 (`SessionHitCard` click-through wiring `anchor_index`/`messageIndex` through to `history/page.tsx`, with a documented fallback if the page doesn't yet parse the param), matching this finding's own remediation. **Story 1.4.1 (Scroll Mode / `anchor_index`) has no consumer anywhere in this plan.** The backend field is fully specified (Epic 1.4), but Phase 2 (Epic 2.1's `SearchOptions` extension, Epic 2.2's `TriageRelatedWorkSection`) never adds `anchorIndex` to any frontend type and never calls `GetClaudeHistoryMessages` with it. The "N more matches in this session" affordance in Task 2.2.1c is described as static text with no click/paging handler. requirements.md's Success Metric #3 ("A user can page through a session's messages around a hit... currently impossible") and its In-Scope item ("Scroll mode: ... page forward/backward within a session without re-running the search") are therefore not delivered end-to-end — the plan ships an RPC field with zero reachable callers, and this gap isn't called out in plan.md's Unresolved Questions or Out-of-Scope notes (which only defer the outcome-badge join).
  **Remediation**: either add a Phase 2 story that wires `anchor_index` into an actual paging UI (e.g. a "show more context" affordance on `SessionHitCard` that calls `GetClaudeHistoryMessages` centered on the hit), or explicitly move Story 1.4.1 to Out-of-Scope/fast-follow in both requirements.md and plan.md rather than leaving it looking shipped.

## Concerns

- [ ] **Task 1.4.1a — `anchor_index` vs. `tail` is documented as mutually exclusive but never enforced.** The new field's proto comment says "Mutually exclusive with tail"; the existing `tail` field's comment already makes the same unenforced claim about `offset`. A request with `Tail: true, Offset: 0, Limit: N, AnchorIndex: &M` computes `fileLimit=N` (so `GetMessagesFromConversationFile` returns only the tail slice), then applies `offset = anchor - limit/2` against that already-truncated slice — silently returning the wrong window instead of an error. Given Blocker #2, no planned caller reaches this combination in v1, but it's still public RPC surface. **Recommendation**: return `CodeInvalidArgument` when more than one of `offset`/`tail`/`anchor_index` is meaningfully set, or explicitly document and test the resolution order — worth closing both the new and pre-existing ambiguity while this code is being touched anyway.

- [ ] **Task 1.3.1c — N+1 file reads when `include_context=true` and `group_by_session=false`.** This is a legal, additive combination under the chosen API design (nothing requires the two flags together). The context-enrichment loop calls `hist.GetMessagesFromConversationFile(r.SessionId, 0)` once per retained *message* hit; when dedup is off, a session with N matching messages triggers N redundant full-JSONL reads/parses within one request. Not exercised by `TriageRelatedWorkSection` (which always sets `group_by_session=true`), but reachable by any other caller of the now-additive fields, and undercuts the plan's own NFR ("don't regress" the sub-100ms typical latency). **Recommendation**: memoize by `SessionId` in a request-local map inside the enrichment loop — a few lines, closes the gap regardless of who calls it.

- [ ] **`total_matches`/`has_more` on `SearchClaudeHistoryResponse` become session-count/message-count-ambiguous under `group_by_session=true`.** Both are derived from `search.SearchResults.TotalMatches`, which is a raw message-level count computed before dedup/filtering (Epic 1.2/1.5). Under `group_by_session=true`, `has_more` can read `true` with zero additional *sessions* actually available, and `total_matches` no longer matches "count of rows in `results`." Not consumed by `TriageRelatedWorkSection` (no pagination there), but any future caller of these additive fields inherits mismatched semantics with no doc note. **Recommendation**: add a proto comment clarifying these are message-level counts regardless of `group_by_session`, or surface the session-level count in the response — the plan's own Observability Plan already computes `search.sessions_returned` as a span attribute, so exposing the same number as a response field costs little beyond field-numbering.
