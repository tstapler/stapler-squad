# Pre-mortem: session-search-fts5
**Date**: 2026-08-02

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `filterByProject` (Task 1.6.1a) does exact-string equality between `entry.Project` (the session's live JSONL working directory, which is a per-session git worktree path — see `session/instance.go`'s distinct `MainRepoPath`/`ClonedRepoPath` vs `Path` fields, and `backlog_service_diff_test.go`'s `repoPath` vs `worktreePath` params) and `item.RepoPath` (the canonical repo path). Because `RelatedWorkQuery` (the triage panel's *default* query bundle) always sends `project: repoPath`, and sessions created via worktrees never have `entry.Project == item.RepoPath`, the filter can silently exclude every real match. | The "Find related past work" box always shows "No related past sessions found — this looks like new territory" for every backlog item, even ones with obviously relevant prior sessions — because the reassuring empty-state copy (Story 2.2.2) masks a filtering bug as a legitimate negative result. | Before merging, test against a real (not hand-seeded-to-match) backlog item created from an actual worktree session, and confirm `filterByProject` needs to compare against the worktree's main/cloned repo path (or resolve worktree→repo) rather than raw string equality. Add an explicit AC/test where `entry.Project` is a worktree path distinct from `item.RepoPath`, not just the "different repos" case Story 1.6.1's GWT currently covers. | P1 |
| 2 | The best-effort `isAutomationSession`/`Instance.Hidden` filter (Epic 1.5) relies on a *live*, in-memory `Instance` record via `ss.getInstances()`. Background/triage automation sessions are typically short-lived (spun up, do triage work, exit, worktree cleaned up) — by the time a human triages a *different* item later, the very automation sessions this filter targets are the most likely to already have had their `Instance` deleted (`Storage.DeleteInstance`), leaving them un-excludable. | `excludeAutomationSessions: true` is set by default on every triage search, yet automation/background session transcripts keep appearing in results days or weeks after they ran — the filter appears broken even though it is working exactly as ADR-002 describes ("best-effort," not exhaustive). | Validate with a session whose `Instance` has actually been deleted (not one created moments before the test), not just the "no live Instance match → kept" unit test already planned (Story 1.5.1's second GWT covers the mechanism but not the realistic timing). Consider noting in the UI copy that automation-filtering coverage degrades quickly rather than implying it's a general-purpose filter. | P2 |
| 3 | The oversampling fix (Task 1.2.1b, `rawLimit = requestedLimit * 5`, capped at 100) raises the starvation threshold but does not eliminate it: if more than ~5 sessions score above a genuinely relevant 6th+ session within the raw top-100 window, dedup still collapses the busy sessions and the raw fetch never contained the relevant one to begin with. | For a common search term, the triage panel's 5 result slots are consistently filled by the same few frequently-touched sessions, and a real, relevant, less-busy session never surfaces — with no error or indication that results are incomplete. | Add a test case with >5 busy/duplicate sessions ahead of a relevant one exceeding the 100-row raw ceiling (extending Story 1.2.1's third AC beyond its single-busy-session example), and document in the proto comment that oversampling is bounded (raises but does not remove the starvation threshold). | P2 |
| 4 | Task 1.3.1c calls `hist.GetMessagesFromConversationFile(r.SessionId, 0)` for context windows. Per the function's own doc comment (`session/history.go:552-568`), `limit == 0` takes the `readAllMessagesFromFile` path — loading the *entire* conversation file — rather than the "efficient reverse-read" path used when `limit > 0`. This runs once per retained result (up to `requestedLimit`, e.g. 5) on every debounced (300ms) keystroke in the triage search box. | Triage panel search becomes noticeably slow specifically for backlog items whose title matches long-running sessions (multi-day sessions, large embedded tool output), while short sessions stay fast — an item-specific slowdown that's easy to write off as unrelated. | Add a benchmark/perf test with a synthetic large conversation file (thousands of messages) asserting context-window extraction stays within the NFR's stated SLO ("same order of magnitude...sub-100ms"). Consider whether `contextWindowAndBookends` can be served by a bounded read (e.g., forward/backward seek from `hitIndex`) instead of `limit=0`'s full-file read. | P2 |
| 5 | ADR-002's title, Decision, and Alternatives sections all describe the filter signal as `Instance.AutonomousMode`, but plan.md's Epic 1.5 explicitly documents a "Correction" — the actual code (Task 1.5.1a, `isAutomationSession`) filters on `Instance.Hidden` instead, for the reasons plan.md gives (`AutonomousMode` is a human opt-in, not a background-session marker). The ADR file itself was never updated to reflect this. | A future engineer or automated tool treats ADR-002 as ground truth, sees `AutonomousMode`, and "fixes" `isAutomationSession` back to `AutonomousMode` — silently reintroducing the exact bug plan.md's correction note exists to prevent (excluding legitimate human "Fix Autonomously" sessions, failing to exclude real background sessions). | Update ADR-002's title, Decision, and Alternatives Considered sections to say `Instance.Hidden`, matching plan.md's Epic 1.5 text and the actual implementation, before Phase 5 implementation begins. | P2 |

## P1 Items (address before implementation)
- [x] #1 — **RESOLVED** (2026-08-02): `plan.md` Task 1.6.1a now implements `resolvedProject`, cross-referencing a session's live `Instance.MainRepoPath` before comparing against `item.RepoPath`, exactly mirroring Epic 1.5's `Instance.Hidden` cross-reference pattern. Story 1.6.1's acceptance criteria now include the worktree-path-vs-repoPath GWT and a "no live Instance" fallback case, plus new tests `TestFilterByProject_ResolvesWorktreePathViaLiveInstanceMainRepoPath` and `TestFilterByProject_KeepsWorktreeSessionWithNoLiveInstance`. The remaining real-instance validation step (test against an actual worktree-created backlog item, not just a hand-seeded unit test) is retained as an explicit pre-Phase-5 checklist item in Task 1.6.1c — do not skip it even though the code-level fix is now specified.
