# Pitfalls & Risks: session-search-fts5

Research conducted against the current `main` tree. All claims below are VERIFIED by reading the cited files unless marked INFERRED.

## 1. Session dedup / response-shape risk to existing consumers

**`useHistoryFullTextSearch.ts` and `HistorySearchResults.tsx` are structurally coupled to "one row per message."**

- `useHistoryFullTextSearch.ts:121-144` (`convertResult`) maps `SearchResult` 1:1 from the proto with no grouping logic — one `SearchResultItem` per proto `SearchResult`.
- `HistorySearchResults.tsx:222-228` keys the results list as `` `${result.sessionId}-${result.messageIndex}-${index}` `` — assumes each row is a distinct `(session, messageIndex)` pair, i.e. per-message granularity.
- `HistorySearchResults.tsx:248`: `` `${totalMatches - results.length} more` `` on the "Load More" button — this arithmetic is only correct if `totalMatches` and `results.length` are counted in the *same unit* (currently both message-count). **If session dedup changes `SearchClaudeHistoryResponse.total_matches` to mean "matching sessions" while `results` stays "rows returned," this counter silently goes wrong** (e.g. shows a negative or nonsensical "more" count) without any type error, since both fields are plain `int32`/`number` — TypeScript can't catch a semantic mismatch.
- Because ConnectRPC binary encoding tolerates unknown/added fields, adding *new* optional fields to `SearchResult`/`SearchClaudeHistoryResponse` is safe for these two consumers (they just won't read the new fields). The unsafe move is **repurposing `total_matches` or collapsing `results` from per-message to per-session** in the existing RPC — this is exactly what the requirements doc already flags as a "Rabbit Hole" (`requirements.md` — "Session grouping response shape") and what the **Constraints** section requires be additive/versioned. Confirms the requirements doc's own risk assessment is correct; the concrete failure mode above is the reason why.
- **Mitigation already implied by requirements**: land session-grouped discovery as a new field (e.g. `repeated SessionGroup grouped_results`) or a new RPC (e.g. `DiscoverSessions`), and leave `results`/`total_matches` untouched. Do not touch `HistorySearchResults.tsx`/`useHistoryFullTextSearch.ts` unless intentionally migrating them too, as a separate, explicit change.

## 2. BM25 engine concurrency: full write-lock held across disk I/O, on every search request

- `session/search/engine.go:399-496` (`IncrementalSync`) takes `e.mu.Lock()` (exclusive, `sync.RWMutex`) at the top (`engine.go:403-404`) and holds it for the **entire** sync: change computation, re-indexing every added/updated session (which calls `history.GetMessagesFromConversationFile`, i.e. disk reads, `engine.go:433/456/537-541`), and — if changes were found — `e.indexStore.Save(...)` (`engine.go:485-491`), which is itself a full index serialize-to-disk. All of this happens under one exclusive lock.
- `search_service.go:479-495`: `SearchClaudeHistory` calls `IncrementalSync` **synchronously on every single request**, before `Search()`. So every search call currently pays for an exclusive lock + a full directory scan against `history.GetAll()` (`engine.go:505` inside `computeChangesLocked`) even when nothing changed.
- `Search()` itself only takes `e.mu.RLock()` (`engine.go:194-195`), so concurrent searches don't block each other — **except** that any `IncrementalSync` call anywhere blocks *all* concurrent `Search()` calls (RLock blocks behind a pending/active Lock) until the sync (including its disk write) completes.
- **Direct implication for this project**: a new Scroll-mode or Discover RPC that follows the same pattern used by `SearchClaudeHistory` (call `IncrementalSync` at the top of the handler) will not add new lock hazards on its own, but it **multiplies contention** — every scroll-page fetch, every triage-panel search, every existing history search now all serialize through the same exclusive lock + disk-save path. In a triage flow where the operator scrolls through a session's context window message-by-message, each `Next page` scroll call re-running a full `IncrementalSync` is wasted work (nothing changed) but still pays the write-lock cost.
  - **Recommended, low-risk mitigation** (not currently implemented anywhere in the engine): a new Scroll/context-window RPC that only reads already-indexed data (message content by session+index) does not need to call `IncrementalSync` at all if the initiating search already synced the index in the same UI flow — scroll is a "look at what we already have" operation, not a fresh search. Confirm this in planning rather than reflexively copying the sync-then-search pattern onto every new RPC.
- No test currently exercises concurrent `Search()` + `IncrementalSync()` (INFERRED from skimming `engine_test.go`'s test names — this needs an explicit concurrent-access test if new code paths increase concurrent call volume, e.g. a triage panel and a session-detail page both querying at once).

## 3. Memory growth: `DocumentStore` retains full message content forever, no eviction

- `session/search/document_store.go:9-22` (`Document`): stores the **full `Content` string** of every indexed message, forever, in an in-memory `map[int32]*Document` (`document_store.go:28`). There is no LRU, TTL, or size cap anywhere in `document_store.go`, `inverted_index.go`, or `engine.go`.
- `RemoveSession`/`removeSessionLocked` only fires when `IncrementalSync`'s `computeChangesLocked` (`engine.go:498-533`) detects a session was deleted from `history.jsonl` — i.e. memory is only freed if the user deletes history, not on any capacity/age basis.
- This is a known, accepted risk per the requirements doc ("history volume is single-user/local, same as today" — Non-functional Requirements). **Not a blocker**, but worth being explicit for the new context-window/bookend feature: adding "±5 messages + first 3/last 3 bookends" per hit does not by itself increase steady-state memory (the messages are already indexed if they have ≥1 token — see §4 below for the exception), but if the design goes further and pre-fetches/caches windows across many hits (e.g. eagerly computing context for all N session-groups in a discovery response rather than lazily on click-through), that's a new, avoidable memory multiplier worth flagging in the plan.

## 4. Context window / bookend messages: the index has gaps — cannot be reconstructed from `DocumentStore` alone

- `session/search/tokenizer.go`: `Tokenize()` drops any word with `len(word) < 2` (`tokenizer.go:71`) and filters stopwords (`tokenizer.go:121,135`). A message that tokenizes to **zero** tokens (e.g. "ok", "yes", "👍", a bare code fence, a stopword-only reply) is **skipped entirely** during indexing:
  - `engine.go:106-109` (`BuildIndex`): `if len(tokens) == 0 { continue }`
  - `engine.go:156-159` (`IndexMessage`): same guard
  - `engine.go:545-548` (`indexSessionLocked`): same guard
- Consequence: `DocumentStore.SessionIndex[sessionID]` (`document_store.go:30`) is **not** a complete, gap-free list of a session's messages in order — it's the subset that had ≥1 indexable token. A "±5 message context window" or "first 3 / last 3 bookend" feature built by walking `GetDocIDsBySession` / `Document.MessageIndex` will silently skip real messages that exist in the conversation but never got indexed (short acks, pure-emoji replies, etc.), producing an incomplete or index-shifted context window.
- **Concrete recommendation for planning**: context-window and bookend message fetching must go through `history.GetMessagesFromConversationFile(sessionID, 0)` (already used elsewhere, e.g. `search_service.go:426`, `session_service.go` for `GetClaudeHistoryMessages`) — the raw JSONL reader — not through the search index/`DocumentStore`, which is a lossy, search-only projection of the conversation.

## 5. Pagination: reinventing vs. reusing `historyCursor` for scroll mode

- `search_service.go:29-58` defines an opaque, base64url-encoded `historyCursor{UpdatedAtNs, ID}` used by `ListClaudeHistory`'s cursor pagination (`search_service.go:245-333`). It resumes by scanning `entries` for a matching `(UpdatedAt, ID)` pair (`search_service.go:283-299`) — an O(n) linear scan through the full in-memory history list per page, tolerable because history entries (not messages) number in the low thousands at most for a single-user history.
- This cursor shape is **specific to `ClaudeHistoryEntry` pagination** (session-level: keyed on `UpdatedAt` + session `ID`). A Scroll-mode RPC anchored on a **message ID within a single session** (per `requirements.md` Open Question #3) needs a different cursor: `(sessionID, messageIndex, direction)`, not `(UpdatedAt, ID)`. Reusing the exact `historyCursor` struct/encode/decode functions as-is won't fit — but the **pattern** (opaque base64url JSON token, decode-or-empty-start semantics, `next_page_token` empty-string-means-last-page convention) should be reused for consistency with `ListClaudeHistoryResponse` (`session.proto:862-870`) rather than inventing a third pagination convention (e.g. raw integer offsets, or a differently-shaped token) for the new RPC.
- Cheapest-signal pitfall: `GetClaudeHistoryMessages` (`search_service.go:404-456`, proto `session.proto:924-943`) already has `limit`/`offset`/`tail` — a message-level offset-based fetch, not an anchor+direction scroll. Scroll mode could extend this RPC with an `anchor_message_index` + `direction` field rather than adding a wholly new RPC, but that changes `GetClaudeHistoryMessagesRequest`'s semantics (mixing offset-mode and anchor-mode in one message) — needs an explicit decision in Phase 3 planning, not a default.

## 6. `source=tool` / background-session filtering: the signal requirements.md assumes does not exist on history entries

- The Go struct `session.ClaudeHistoryEntry` (`session/history.go:18-33`) — the JSONL-backed struct search operates on — has **no** source/origin/hidden field at all. Fields are: `ID, Name, Project, CreatedAt, UpdatedAt, Model, MessageCount`. Confirms **Open Question #1** and **Feasibility Risk #2** in `requirements.md` are correct: this signal does not exist yet on history entries.
- A visually similar field **does** exist, but on a different, non-overlapping data source: `Session.hidden` (proto `types.proto:189-192`, "used for system/background sessions (e.g. triage, validation) that should not pollute the user-facing session viewer") — but this is populated from `session.Instance`, the **live, in-memory** session/tmux tracker, not from `history.jsonl`. `search_service.go:154-167` (`liveSessionStatus`) shows the existing pattern for cross-referencing a JSONL history entry against live instances: it iterates `ss.getInstances()` and matches by `inst.GetConversationUUID()`.
- **Pitfall for a naive implementation**: pattern-matching `liveSessionStatus`'s cross-reference approach to derive a "hidden"/tool-sourced signal for history search results only works for sessions that are **currently tracked live** (in `getInstances()`). A background/triage session from last week that has since exited has no live `Instance` to check `hidden` against — the signal is unavailable for the majority of historical entries, not just edge cases. **This means either**: (a) a new persistent field must be written into `history.jsonl` at session-creation/completion time (touches `history_watcher.go`/history-writing code — the requirements doc explicitly scopes JSONL format changes as risky/out-of-scope-unless-needed), or (b) some other durable heuristic must be found (e.g. project path pattern, workflow_id presence — `ClaudeHistoryEntry` has no `workflow_id` field either, only `Session` proto does). This is a real open design question, not a small implementation detail — it should be resolved explicitly in Phase 3 planning, and the "cheapest reliable signal" language in the requirements' Open Question #1 should not be assumed to be a quick metadata read.

## 7. Proto/codegen drift risk

- Both generated-code trees are **committed to git**, not gitignored: `web-app/src/gen/session/v1/*.ts` (VERIFIED via `git ls-files`) and `gen/proto/go/session/v1/*.go` (VERIFIED via `git ls-files` on `gen/proto/go/session/v1/backlog.pb.go` etc.). This means:
  - Backend drift is compile-time caught: if `.proto` changes without `make proto-gen`, `server/services/search_service.go` won't compile against the stale `sessionv1` package (assuming new fields are referenced) — `go build` fails loudly.
  - **Frontend drift is not caught automatically.** If a developer edits `session.proto`, forgets `make proto-gen`, and then edits `useHistoryFullTextSearch.ts`/a new hook to reference a new response field, TypeScript will fail to compile (field doesn't exist on the stale generated type) **only if** the new field is actually referenced in `.ts` code. If the PR only changes the backend and leaves the frontend untouched "for now," the committed `session_pb.ts` silently doesn't match the `.proto` source of truth — reviewable (diff shows `.proto` changed, `_pb.ts`/`.pb.go` didn't) but easy to miss in a large PR, especially since `make build`/`make test` (which both depend on the `proto-gen` Makefile target — `Makefile:132,436`) will regenerate and overwrite any stale committed file the next time either runs, potentially producing an unexpected extra diff in an unrelated later commit.
  - Per CLAUDE.md's own root-level guidance: run `make proto-gen` immediately after any `.proto` edit, before writing consumer code in either language, and commit the regenerated files in the same commit as the `.proto` change — not as a follow-up.

## 8. Repo-convention risks specific to this change

- **Feature registry** (`.claude/rules/feature-registry.md`): `docs/registry/features/backend/history/search.json` and `docs/registry/features/frontend/ui/history-search.json` already exist for the current `SearchClaudeHistory` RPC and history-search UI (VERIFIED — read both files). Any **new** RPC (e.g. a `DiscoverSessions`/scroll RPC) needs its own new per-feature JSON file under `docs/registry/features/backend/`; extending the *existing* `SearchClaudeHistory` RPC in place (new request/response fields) means updating `search.json`'s `lastModified` and `testIds`, not creating a new file. The triage-panel UI surface is a **new** frontend feature (`TriageReviewPanel.tsx` doesn't currently have a search box — VERIFIED, no search-related state in the file) and needs its own new `docs/registry/features/frontend/*.json` entry, separate from `history-search.json`.
- **E2E conventions** (`.claude/rules/e2e-test-conventions.md`): the existing `tests/e2e/history-search.spec.ts` is the reference pattern (`// @feature history-search` header, references `FEATURE_CATALOG['history-search']`). A new triage-panel search e2e test must follow the same four hard rules: feature-annotation header, no `waitForTimeout`, `data-testid`/ARIA-only locators, and any new page-interaction helpers go in `tests/e2e/pages/` rather than inlined in the spec.
- **Session-creation-registry / omnibar registries do not apply** — this feature doesn't touch session creation modes or the omnibar's `OmnibarAction`/`DetectorRegistry`, so `.claude/rules/session-creation-registry.md` and `.claude/rules/feature-testing-registry.md` are out of scope; no action needed there, but worth confirming in planning so no one over-applies those checklists to a feature that isn't an omnibar/session-creation change.
- **"New API Endpoints" playbook** (root `CLAUDE.md`): if planning lands a new RPC rather than extending `SearchClaudeHistory` in place, the standard sequence applies — define RPC in `proto/session/v1/session.proto` → `make proto-gen` → implement handler in `server/services/search_service.go` (already the home of the other Claude-history RPCs, register alongside them) → wire into `server/server.go` if a new service registration is needed (likely not, since `SearchService` is presumably already registered — confirm in Phase 3, not verified in this pass).

## Summary of Highest-Leverage Risks (for Phase 3 planning to resolve explicitly)

1. Response-shape change must be additive (new field or new RPC) — confirmed by reading the two frontend consumers; the specific failure mode is the `totalMatches - results.length` "N more" counter in `HistorySearchResults.tsx:248` going semantically wrong if `total_matches` is repurposed.
2. Context window / bookend messages must be sourced from `GetMessagesFromConversationFile` (raw JSONL), not `DocumentStore` — the search index has real gaps from zero-token message filtering.
3. `source=tool`/background-session filtering has no existing durable signal on `ClaudeHistoryEntry` — this is a real design decision (write a new field into history at session-write-time vs. find a different heuristic vs. accept the limitation only applies to currently-live sessions), not a quick lookup.
4. Scroll mode needs its own cursor shape (anchor = sessionID + messageIndex, not the existing `historyCursor`'s UpdatedAt+ID) but should reuse the existing opaque-token/`next_page_token` *convention* for consistency.
5. Any new RPC that copies `SearchClaudeHistory`'s "call `IncrementalSync` synchronously at the top of every request" pattern adds to exclusive-lock contention across the whole engine — worth deciding per-RPC whether a full sync is actually needed (e.g. scroll/context-window reads of already-fetched data likely don't).
