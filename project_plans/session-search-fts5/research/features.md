# Research: Comparable Features & Open Questions

## 1. Existing patterns a new triage search box should follow

Read: `web-app/src/components/history/HistorySearchInput.tsx`, `HistorySearchResults.tsx`, `web-app/src/lib/hooks/useHistoryFullTextSearch.ts`, `useSessionSearch.ts`, `useDebounce.ts`, `web-app/src/components/backlog/TriageReviewPanel.tsx` + siblings (`TriageDiffSection.tsx`, `TriageErrorBanner.tsx`, `TriageLoadingIndicator.tsx`).

**`useHistoryFullTextSearch.ts` (`web-app/src/lib/hooks/useHistoryFullTextSearch.ts:95`)** is the reference hook shape for the new "Find related past work" box — reuse this pattern rather than inventing a new one:

- Debounce via the shared `useDebounce` hook (`web-app/src/lib/hooks/useDebounce.ts:9`), default 300ms, configurable via `debounceMs` option.
- `AbortController` stored in a ref; a new search aborts the in-flight one before firing (`useHistoryFullTextSearch.ts:163-166`). Abort errors are swallowed via a 4-layer detection cascade (native `AbortError`, `DOMException`, `ConnectError` with `Code.Canceled`/`Code.Aborted`, and a message-substring fallback) — worth copying verbatim rather than re-deriving, it's already hardened against ConnectRPC's inconsistent abort surfaces.
- `SearchState` shape: `{ results, totalMatches, queryTimeMs, hasMore, loading, error }` — loading/error/empty are all first-class states threaded through to the results component.
- Pagination is offset-based with an `append` flag (`loadMore()` calls `search({ offset: results.length, append: true })`); results replace vs. append based on that flag (`useHistoryFullTextSearch.ts:187`). `SearchClaudeHistory` returns `hasMore` + `totalMatches` directly, no cursor needed for this RPC (contrast with `ListClaudeHistory`, which does use `page_token`/`page_size` cursor pagination per requirements.md's baseline section).
- Auto-search fires only when `autoSearch: true` and `debouncedQuery` is non-empty; empty query synchronously clears results without a network call (`useHistoryFullTextSearch.ts:253-264`).

**`HistorySearchResults.tsx`** establishes the 4-state render order the triage box should mirror: **(1) empty query** → prompt/hint copy, **(2) loading with zero results** → spinner, **(3) error** → inline error text (no retry button currently — component just shows `error.message`), **(4) zero results for a non-empty query** → "No results found" + hint to try different keywords. Only after all four is the actual result list rendered, with a result count/query-time header and a "Load More" button gated on `hasMore`.

**`HistorySearchInput.tsx`** additionally layers a local-storage-backed recent-searches dropdown (`useSearchHistory` hook, key `stapler-squad-history-search`, max 15 entries) with arrow-key navigation. This is probably more than the triage box needs (its query is pre-populated from the backlog item title, not typed fresh each time), but the core input shell — search icon that swaps to a spinner while `loading`, clear button when `value` is non-empty — is the right minimal pattern to reuse.

**`useSessionSearch.ts`** is a *different* pattern — client-side Fuse.js fuzzy search over already-loaded Redux session state, not a server round-trip. Not directly reusable for history discovery (which requires the BM25 index on the backend), but confirms the repo's convention of keeping search hooks side-effect-free and returning a plain result array from `useMemo`.

**`TriageReviewPanel.tsx` conventions to match:**
- `"use client"` directive, colocated `.css.ts` (vanilla-extract per ADR-009 / `.claude/rules/css-architecture.md` — a new search box here must NOT be a `.module.css` file).
- Every interactive control has a `data-testid` (`triage-apply-button`, `triage-dismiss-button`, `triage-refine-textarea`, etc.) — the new search input/results need the same, since `.claude/rules/e2e-test-conventions.md` mandates `data-testid`/ARIA-only locators for e2e specs.
- Async actions follow a 3-state local status enum (`"idle" | "applying" | "error"` for apply, `"idle" | "submitting" | "error"` for refine) with a paired `xError` message state and an inline `TriageErrorBanner` on failure (`onReload` resets state, `onSkip` dismisses) — the same shape should back the new search box's loading/error handling instead of inventing a third pattern.
- The panel already supports a `readOnly` variant (discriminated union `TriageReviewPanelReadOnlyProps | TriageReviewPanelWriteProps`) for headless/historical-record rendering — a new "Find related past work" box embedded in this panel or a sibling panel needs to decide up front whether it appears in `readOnly` mode too (a historical record arguably still benefits from it, unlike Apply/Skip which are correctly omitted there).

## 2. `source=tool` / background-automation signal — answers Open Question 1

**No field exists on `ClaudeHistoryEntry` or in the search index that flags a session/message as background/automation/reviewer-originated.** Verified by reading:

- `session/history.go:18` — `ClaudeHistoryEntry{ID, Name, Project, CreatedAt, UpdatedAt, Model, MessageCount}`. No role/source/tag field. This struct is parsed straight from Claude Code's own `~/.claude/history.jsonl`/project JSONL files — it has no awareness of stapler-squad's backlog automation at all.
- `session/search/document_store.go:9` — `Document{SessionID, MessageIndex, MessageRole, Content, WordCount, Timestamp}`. `MessageRole` is `"user"`/`"assistant"` only (see next point) — there is no session-origin field to filter on here either.
- `server/services/search_service.go:585` — `MatchSource: "message_content"` on `SearchResultMetadata` describes *what field matched* (title vs. body), not *who/what produced the session*. Easy to misread as the signal requirements.md's Notes section assumes exists (Hermes's `source=tool` tag) — it is not that.

**Message-level `source=tool` filtering is already a non-issue** — it's done upstream of indexing, not something to add: `extractMsgContent` (`session/history.go:388`) only accepts `raw.Type == "user"` or `raw.Type == "assistant"`; tool-use/tool-result/metadata JSONL entries are dropped before they ever reach `ClaudeConversationMessage`, and `CanonicalTurn.Validate()` (`session/canonical.go:112`) rejects any role other than `RoleUser`/`RoleAssistant`. So individual tool-call messages never enter the BM25 index in the first place — the real gap is **session-level** origin, not per-message role.

**A real signal for session-level origin does exist, but only inside stapler-squad's own ent DB, in a different ID namespace, and only for currently-known sessions:**

- `session/backlog.go:49-53` defines `SessionRoleWork = "work"`, `SessionRoleTriage = "triage"`, `SessionRoleReview = "review"` — stored on the `ItemSession` ent entity (`session/ent/schema/item_session.go:25`, field `session_role`, comment `"One of: work, triage, review"`).
- `session/backlog.go:84-88` — `CategoryBacklog = "Backlog"` is the `Session.Category` value stamped onto every session BacklogService spawns (work, revision, review-gate, re-review), plus tag constants `TagBacklogWork`, `TagBacklogRevision`, `TagAutonomous` (`session/backlog.go:78-82`).
- The catch: `ItemSession.session_uuid` (`session/ent/schema/item_session.go:23`, `"Loose FK to Session; not an ent edge"`) is populated from `inst.UUID` — stapler-squad's own `Instance` UUID (confirmed via `SessionUUID: inst.UUID` in `server/services/autonomous_orchestration_service_test.go`) — **not** Claude's conversation UUID that `ClaudeHistoryEntry.ID` uses. The two are linked only transiently, in-memory, by `HistoryLinker` (`session/history_linker.go`) via `Instance.claudeSession.ConversationUUID`, which is **not persisted anywhere in ent** (`session/ent/schema/session.go` fields list has no `conversation_uuid` column). So today, joining "this Claude history entry" → "was this a work/triage/review session" only works for instances still tracked in memory (or requires re-deriving via `HistoryLinker`'s live detection, which won't work for a session whose process/tmux pane is long gone).

**Conclusion for planning**: there is no cheap existing field to filter on directly from `ClaudeHistoryEntry`. The two real options are (a) persist `conversation_uuid` on the `Session` ent schema so historical sessions retain the join key, or (b) since triage sessions run as bounded one-shot headless subprocesses with a synthesized `headless-triage-` UUID prefix (`server/services/backlog_service_triage.go:283`, `headlessTriageUUIDPrefix = "headless-triage-"`) — that string prefix is already a cheap, no-schema-change signal for excluding at least triage sessions specifically, if that prefix ends up embedded anywhere the history index can see it (needs confirming whether it appears in the Claude conversation ID itself or only in stapler-squad's own `SessionUUID`). This is squarely a Phase 3 planning decision, not something research can resolve further without picking one of these paths.

**Bonus finding relevant to Open Question 3**: `GetClaudeHistoryMessages` (`proto/session/v1/session.proto:924`, handler `server/services/search_service.go:405`) already exists and already supports `limit`/`offset`/`tail` against a specific conversation ID, reading via `hist.GetMessagesFromConversationFile` (`session/history.go:558`, which reads the whole JSONL or just the tail via `readLastNMessagesFromFile`/`readAllMessagesFromFile`). Scroll mode's "anchor forward/backward without re-running the query" requirement maps naturally onto **extending this existing RPC** with an anchor/offset parameter (messages only have positional index, not stable per-message IDs, so "anchor on message ID" in practice means "anchor on message index," which `offset` already models) — not a new RPC. This directly resolves Open Question 3 in favor of "extend `GetClaudeHistoryMessages`."

## 3. Edge cases / failure modes

- **Empty backlog item title**: `BacklogItem.title` (`web-app/src/lib/hooks/useBacklogService.ts:94`) is typed as required `string`, but nothing prevents it being `""` in practice (e.g., a draft item never given a title). `useHistoryFullTextSearch`'s `search()` already no-ops on `!searchOptions.query.trim()` (`useHistoryFullTextSearch.ts:150-160`) and clears state — so pre-populating with an empty title will correctly show the hook's default "empty query" state rather than erroring, but the triage UI needs to decide whether to show the box at all, or show it with an explicit "add a title to search" hint, since silently showing an inert search box with no explanation is a UX gap `HistorySearchResults`'s existing empty-state copy ("Search across all your Claude conversations") doesn't cover for this specific pre-populated-but-empty case.
- **No matches found**: already handled generically by `HistorySearchResults`'s zero-results branch (`HistorySearchResults.tsx:190-206`) — reusable as-is, though its copy ("Try different keywords or check your spelling") is written for a human typing, not an agent auto-searching a backlog title; triage-specific copy (e.g. "No related past work found") is a small but real UX delta.
- **A session with only tool-sourced messages**: per finding #2 above, this can't actually happen post-parse — `extractMsgContent` drops non-user/assistant entries before a `ClaudeConversationMessage` is ever created, so a session that is 100% tool calls produces zero indexable messages and simply never appears in search results at all (rather than appearing with empty snippets). Dedup/context-window/bookend logic therefore never has to special-case a session with 0 eligible messages from a message-filtering perspective — but a session-level automation exclusion (question 2) can and will filter out sessions that *do* have real user/assistant turns from a headless `claude -p` triage/review run, and that's a different, separate scenario in-scope for exclusion.
- **Huge message counts / bookend on a 2-message session**: `Document.MessageIndex` (`session/search/document_store.go:13`) is stored per-message, so a ±5 window and first-3/last-3 bookends are index-arithmetic against `ClaudeHistoryEntry.MessageCount` (already tracked per session, `session/history.go:32`) — but the bookend/context-window implementation must clamp both ends (`max(0, idx-5)` .. `min(len-1, idx+5)`) and de-duplicate the overlap when a session has ≤ ~11 messages total (first-3 + hit-window + last-3 can trivially overlap or exceed total message count on a short session). No existing code in `snippet.go` or `document_store.go` does this windowing today — it needs to be net-new logic, and the ≤11-message overlap case is the concrete pitfall to write a unit test for per the requirements' own "Unit tests: session dedup, snippet/context-window extraction" scope item.
- **Concurrent search + live session updates**: `getOrRefreshHistoryCache` (`server/services/search_service.go:172`) already re-syncs the in-memory `ClaudeSessionHistory` and calls `IncrementalSync` on every request per requirements.md's baseline — so a search mid-flight against a session that's actively being written to will simply get whatever was on disk when that request's sync ran; there's no transactional guarantee across a scroll-mode's sequence of anchor requests against the same session if new messages land between them (e.g., page 2 offset shifting because page 1 was computed against an older message count). This is the same class of staleness the existing `offset`/`limit` pagination on `GetClaudeHistoryMessages` already has today (not new), but scroll mode's premise of "page forward/backward without re-running the query" makes staleness more visible to a user scrolling through a session that's still receiving new turns — worth a product decision (freeze message count at scroll-session start? re-check on each page?) rather than an oversight to silently inherit.

## 4. Unstated need: filter by project path

**Yes — worth adding, and cheap.** `SearchClaudeHistoryRequest`/`SearchOptions` already has a `project` filter field end-to-end (`web-app/src/lib/hooks/useHistoryFullTextSearch.ts:19` `SearchOptions.project`, threaded straight into the RPC call at `useHistoryFullTextSearch.ts:175`), and `BacklogItem` already carries `repoPath?: string` (`web-app/src/lib/hooks/useBacklogService.ts:99`). A triage item almost always maps to exactly one project/repo, so the "Find related past work" box can default `project: item.repoPath` on the search call with zero backend changes — this narrows results to the item's own repo by default (likely the more useful default than global search, since "related past work" usually means "past work in this repo"), while still leaving the field clearable/overridable in the UI if the operator wants to search across all projects. This wasn't called out in requirements.md's Scope section and should be flagged to Phase 3 planning as a low-cost, high-value addition to the triage search box's default query — not a new RPC field, just a default value + optional UI toggle.
