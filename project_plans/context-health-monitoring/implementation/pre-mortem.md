# Pre-mortem: context-health-monitoring
**Date**: 2026-08-02

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The loop heuristic (`MaxConsecutiveRepeats` on an exact `ToolCallFingerprint`) fires on ordinary iterative dev workflows — running the identical `npm test` / `go build && go test` / lint command 3+ times in a row while fixing a bug is normal Claude Code behavior, not confusion — so amber/red badges appear constantly on healthy sessions and users stop trusting the signal within days. | Transition-log reviewer (Phase 6 manual review, the only planned detection mechanism) sees `[ContextHealth] level transition` lines correlating with routine test-fix-retest cycles rather than actual degradation; users start filing "badge is wrong again" complaints or just stop looking at it. | Before Phase 6 sign-off, run `extractContextHealthSignals`/`EvaluateContextHealth` against a sample of real `~/.claude/projects/**/*.jsonl` transcripts (not just unit fixtures) and specifically check the rate of `MaxConsecutiveRepeats >= LoopRepeatThreshold` on sessions a human would call healthy. If identical-retry-until-pass is common, either (a) require the repeats to be interspersed with no state-changing progress (e.g. exclude runs where a `git diff`/file-write happened between repeats), or (b) raise the default `LoopRepeatThreshold` / require a longer streak, and record the finding as a validation.md test case, not just an "implementer will eyeball it in Phase 6" checkbox. | P1 |
| 2 | "No badge" is rendered identically for `HealthGreen` (verified healthy) and `HealthUnknown` (insufficient samples — `ToolCallsInWindow < MinToolCallSamples`, or the `TokenStore` hasn't parsed the transcript yet) per Pattern Decisions' "Badge suppression" row and Task 3.1.1b — so a user reasonably reads "no badge" as "this session is fine" for a session that has simply not accumulated enough data to be judged, undermining the very problem statement (users currently must notice degradation themselves) by teaching them to trust an absence that sometimes means "unknown," not "safe." | A session in its first few turns (or one whose JSONL just started being watched after a restart) shows no badge at all, identical in appearance to a 200-turn healthy session; a user who was burned by trusting a green tick elsewhere in the UI generalizes that trust here and stops re-checking scrollback for young/recently-restarted sessions specifically. | Distinguish the two states observably even while keeping both "quiet" per `research/ux.md`'s no-noise mandate — e.g., a single low-emphasis "gathering data" affordance (not a full badge, maybe a subtle dot or `title` on the card itself) for `HealthUnknown` distinct from true `HealthGreen`'s total silence, or at minimum document in the tooltip contract that "no badge" is not a stated guarantee of health and add a validation.md test asserting `getContextHealthInfo(UNSPECIFIED)` and `getContextHealthInfo(GREEN)` are visually distinguishable somewhere in the DOM even if both are `null` from the badge itself (e.g. a card-level `data-context-health-state` attribute consumed only by tests/tooling, not shown to the user, so this distinction is at least auditable). | P1 |
| 3 | The badge, fixed as the *last* element in an already-multi-badge row (`SubStatusChip` → memory badge → … → `ContextHealthBadge`) on a board showing a dozen+ concurrent sessions, gets scanned past or wraps off-card at typical widths — users habituate to ignoring the tail of the badge row the same way they may already tune out `SubStatusChip`, and since there's no action attached to it yet (handoff/restart is explicitly out of scope), there's no reason to develop a habit of looking there. | Usage/telemetry-free signal: in practice, this shows up as users only noticing degradation after being told about it out-of-band (e.g., in conversation) rather than from the board, and reviewers of the Phase 6 manual review find sessions that were red for a long transition-log window before anyone acted on them. | Add a lightweight, low-cost UX validation before ship: a `design-review`/`ux:review` pass (or a quick five-minute look at the card at realistic board density, e.g. 12+ session cards) specifically checking badge-row overflow/wrapping behavior and whether the health badge remains visible without hover/scroll at common viewport widths. If it collides or wraps, consider promoting position (e.g., ahead of the memory badge, or a border/accent on the card itself for RED) rather than accepting "last position" as sufficient distinctiveness by fiat. | P2 |
| 4 | The confusion-language patterns (`"I apologize"`, `"my mistake"`, `"let me try again"`) are Claude-Code-phrasing assumptions that may not match how current/future Claude models actually phrase self-correction (models increasingly self-correct silently or with phrasing like "Ah, that's the issue" / "Right, let me adjust" without apologizing) — so the confusion signal rarely fires in real transcripts, leaving `ContextHealthRed` reachable almost exclusively via the loop signal, which is itself the noisiest heuristic (see #1). | Phase 6 manual review of transition logs shows `ConfusionPhraseCount` rarely if ever crosses `ConfusionPhraseThreshold` across a real transcript sample, while `MaxConsecutiveRepeats` crossings dominate every level-transition log line — i.e., one of the two "initial heuristics" the requirements promised is effectively dead weight in production. | Validate `matchConfusionPatterns` hit-rate against a real transcript sample (same sampling exercise as #1) before or immediately after ship, and track the ratio of loop-triggered vs. confusion-triggered transitions in the Phase 6 review. If confusion essentially never fires, either expand the pattern set based on real observed phrasing or explicitly document that v1's practical signal is loop-detection only, resetting user/stakeholder expectations set by requirements.md's "two initial heuristics" framing. | P2 |
| 5 | `publishContextHealth`'s full-live-instance-scan-per-notification (accepted CONCERN) compounds with `TokenStore`'s unbounded cache (accepted CONCERN) as a user accumulates weeks of archived transcripts under their history directory — each `notify()` from ordinary usage re-sweeps every live instance, and cache entries for long-closed sessions are never evicted, so both CPU-per-notification and steady-state memory creep upward with no metric or alert to catch it (Observability Plan explicitly adds none). | No log line or dashboard signal at all — the first visible symptom is informal: the server feels slower to update the board, or `journalctl --user -u stapler-squad` shows increasing time between fsnotify events and `session_updated` publishes, discovered only if someone happens to profile it (`.claude/docs/profiling.md`) rather than via any built-in signal. | Before or shortly after ship, take one baseline pprof/heap snapshot (`--profile --trace`) against a `~/.stapler-squad` history directory with a realistic multi-week transcript count, and record the live-instance-scan cost and `TokenStore` cache size as a number, not an assumption — turning the adversarial review's "likely fine at current scale, unmeasured" into an actual measurement. If the numbers are non-trivial, this becomes the seed for a follow-on cache-eviction story rather than a silent surprise a month in. | P3 |

## P1 Items (address before implementation)
- [ ] Failure #1 (loop-heuristic false positives on routine test-fix-retest cycles) — plan.md's Epic 1.2/1.3 needs a validation step against real transcript samples (not just synthetic fixtures) before Phase 6 sign-off is treated as sufficient; add either a state-change exclusion rule to the loop heuristic or raise the default threshold based on that sample, and capture the finding as a concrete validation.md test case rather than an unowned Phase-6 checkbox.
- [ ] Failure #2 (green vs. unknown both render `null`, teaching users that "no badge" means "safe") — add an observable (even if test-only / non-user-facing) distinction between `HealthGreen` and `HealthUnknown` so the ambiguity this plan currently ships by design is at least auditable, and note in the tooltip/UX copy that badge absence is not a stated health guarantee.

## Summary
5 failure modes identified: 2 P1, 2 P2, 1 P3.

Top failure mode: the loop-detection heuristic (exact `ToolCallFingerprint` repeats ≥3) is highly likely to fire on ordinary "run the same test/build command until it passes" workflows that are normal, healthy Claude Code usage rather than degradation — the plan's only planned defense (an unowned Phase-6 manual-review checkbox) is not validated against real transcripts anywhere in the plan, so this ships as an unverified assumption about the single riskiest part of the whole feature.
