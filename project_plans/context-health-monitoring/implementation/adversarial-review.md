# Adversarial Review: context-health-monitoring

**Date**: 2026-08-02
**Verdict**: CONCERNS

## Blockers

- [ ] **`publishContextHealth`'s subscriber goroutine (Task 2.2.3a, `server/dependencies.go`) has no panic guard, unlike every comparable long-lived background loop in the same file.** This file already establishes the convention of wrapping process-lifetime goroutines in `defer func() { if r := recover(); r != nil { log.ErrorLog.Printf(...) } }()` — see `server/dependencies.go:594-599` and `:914` (verified via `grep -n "recover()" server/dependencies.go`), plus the same idiom in `session/external_tmux_streamer.go:485`, `session/review_queue_poller.go:361`, `session/external_approval.go:283`, `session/backlog_lifecycle.go:1415`. Task 2.2.3a's `for range tokenStore.Subscribe()` loop iterates every live instance on every notification (`inst.Snapshot()`, `EvaluateContextHealth`, string formatting) with no recover wrapper specified. One panic anywhere in that body — a future refactor bug, a nil `Instance`, an edge case in reason-string formatting — silently kills the goroutine for the rest of the process's life: no more `ContextHealth` updates for any session, no restart, no log line beyond whatever unhandled-panic output the runtime produces. Given how many sibling goroutines in this exact file already treat this as mandatory, its absence here reads as an oversight rather than a decision. **Recommendation**: add the identical `defer/recover` wrapper to Task 2.2.3a before implementation.

- [ ] **The plan contradicts itself on when `publishContextHealth` logs/publishes — "level changed" vs. "verdict changed."** The Observability Plan section states the log line is "emitted from `publishContextHealth` **only when the level actually changes**" (plan.md line 83), and Story 2.2.3's own title says "Only genuine level transitions are logged and published." But Task 2.2.3a's actual algorithm compares `inst.Snapshot().ContextHealth.Level` **and** `Reason`, continuing only "if unchanged in both" — and ADR-002 independently confirms this by design ("an unchanged **verdict** publishes no event"). Since `Reason` interpolates live counts (the plan's own example: `"Repeated the same Bash call 3 times in a row"`), any count increment (3→4→5 repeats, all still under the red threshold, still `HealthAmber`) changes `Reason` and therefore *will* log+publish under Task 2.2.3a's literal algorithm — directly contradicting the Observability Plan's "only when the level actually changes" and the Story title. This isn't a stylistic nit: it changes how noisy the transition log is (the log's whole purpose is being the false-positive/negative review substrate per requirements.md), and Story 2.2.3's acceptance-criteria Given/When/Then only tests the *same-reason* no-op case, leaving the *same-level-different-reason* case — the actual point of disagreement — unspecified and untested. **Recommendation**: pick one rule explicitly (level-only vs. verdict-including-reason) and fix the Observability Plan prose, the Story 2.2.3 title, and add a test for the disambiguating case before coding starts.

## Concerns

- [ ] **`normalizeToolInput` does not canonicalize JSON key order, so semantically-identical tool calls with differently-ordered keys will fingerprint differently — a real false-negative gap the plan's own tests don't cover.** Task 1.2.1b normalizes via `strings.ToLower(strings.TrimSpace(string(raw)))` on the *raw serialized bytes*, not a parsed-and-resorted structure. Two `tool_use` blocks with the same semantic arguments but different key order (plausible for MCP tools with optional/variable key sets, or any tool call assembled by a code path that doesn't guarantee stable field order) hash to different `ToolCallFingerprint` values, so a real stuck loop could silently evade `MaxConsecutiveRepeats` counting. Task 1.2.1's own acceptance criteria and Task 1.2.1e's test list cover whitespace/case invariance only — key-order invariance is neither implemented nor tested, so this is a known-but-silent gap, not a documented limitation. **Recommendation**: either explicitly document the limitation (Claude's tool_use blocks are likely stable-ordered per tool schema from the Anthropic API, which somewhat mitigates real-world risk) with a one-line rationale in the Pattern Decisions table, or canonicalize via unmarshal-to-map + sorted re-marshal and weigh that against the `<5ms` NFR.

- [ ] **`publishContextHealth`'s full-instance-scan-per-notification design doesn't actually mirror `artifactExtractor.OnScanComplete`, contrary to the Domain Glossary's claim ("Mirrors `artifactExtractor.OnScanComplete` exactly").** Verified in `session/tokens/store.go`: `TokenStore.Subscribe()` returns a channel of bare `struct{}` (no changed-file or UUID payload — `notify()` just broadcasts to all subscribers non-blockingly), unlike `OnScanComplete`, which the code shows is called with a specific `title` for the one instance that actually changed (`server/dependencies.go:1114`). This forces Task 2.2.3a's handler to snapshot *every* live instance and re-evaluate all of them on *every single* file-parse completion, anywhere in the history directory — not just the session whose transcript changed. During the startup `walkAndEnqueue` burst (verified in `store.go:225-255`, which enqueues every `.jsonl` under `historyDir` with no batching), a history directory with hundreds of archived transcripts produces hundreds of `notify()` calls in quick succession, each triggering a full live-instance sweep. Per-instance work is cheap (map read + pure function), so this is likely fine at current session-count scale, but it is a real architectural difference from the cited precedent, not an "exactly" match, and the burst cost during startup is asserted-fine rather than measured. **Recommendation**: correct the Domain Glossary's comparison and note the O(files re-parsed × live instances) startup burst explicitly, even if the conclusion (acceptable) doesn't change.

- [ ] **No task in this plan performs (or even schedules a concrete mechanism for) the false-positive-rate review requirements.md's own Success Metrics defer to "Phase 6."** requirements.md explicitly ships this heuristic with "no ground-truth labeled dataset exists yet," and `research/pitfalls.md` §2 independently notes that the existing per-binary idle/active pattern sets required an ongoing 30+-test regression suite (`session/detection/bug_regression_test.go`) to keep false positives/negatives in check over time — implying confusion-phrase tuning should expect comparable ongoing investment, not a one-shot regex. Yet this plan's only acknowledgment is a checkbox in "Unresolved Questions" ("owner: implementer at Phase 6") with no task, no log-analysis tool, and no seeded regression-test file analogous to `bug_regression_test.go`. Given Risk Control ships this default-enabled to real terminals, shipping with zero built-in tooling to observe the promised false-positive rate — beyond a human manually grepping `[ContextHealth] level transition` lines — is a real gap for a feature whose primary stated risk is noise. **Recommendation**: add a concrete task (even a minimal one: a `rtk`/log-grep recipe, or an explicit handoff instruction to `sdd:6-verify`) rather than leaving the promised review as an unowned checkbox.

- [ ] **The Migration Plan's claim that "`TokenStore.walkAndEnqueue` re-parses every transcript, so health recomputes naturally" is asserted, not verified, for the two edge cases the requirements/research explicitly flagged as open questions.** Verified in `session/tokens/parser.go`: `ParseReader` always scans a JSONL file from byte 0 via `bufio.Scanner` — there is no incremental/tail-only parse path, so every single append to a long-running session's transcript triggers a full re-parse of the *entire* file from the start, not just the trailing `healthWindowTurns` window ContextHealth actually needs. This is pre-existing `session/tokens` behavior (not introduced here), but the task explicitly asked whether the plan verified — rather than assumed — that this scales for (a) a very long transcript (hours of turns, megabytes of JSONL) re-parsed on every restart and on every append, and (b) it doesn't cite a benchmark or measurement against the `<5ms`-per-chunk NFR for either case. **Recommendation**: run one benchmark against a real large `~/.claude/projects/**/*.jsonl` file before shipping, or explicitly note this is an accepted pre-existing risk inherited from `session/tokens`, not a new one.

## Minors

- `MinToolCallSamples` is a third user-tunable threshold the plan adds beyond requirements.md's literal scope line ("Configurable thresholds for the two initial heuristics (loop count, apology-message count)"). It's well-justified by `research/ux.md` §4's "no false green on a 3-turn-old session," but the plan doesn't call out that it's an addition beyond the stated Success Metrics/Scope wording — worth a one-line note tying it back explicitly.
- `TokenStore.cache`/`byUUID` (verified in `store.go`) has no eviction path for JSONL files deleted or archived after a session ends — entries persist in memory indefinitely once created. This is a pre-existing `session/tokens` limitation, not introduced by this plan, but `ContextHealth` now depends on that same unbounded cache; worth a one-line acknowledgment.
- Task 2.2.3a calls `inst.Snapshot()` (an actor round-trip per the `sendSyncErr` pattern) for every live instance on every notification just to compare against the previous verdict. Likely negligible at "dozens of sessions" scale, but is more actor round-trips per tick than the NFR's "no new per-session lock contention" framing might suggest to a reader; worth a one-line note if session concurrency ever grows substantially.
- `matchConfusionPatterns` returns only the first matching pattern name in priority order (apology > self-correction > retry); a text block matching two categories silently reports only one. This is a reasonable simplification and is already implicit in the priority-ordered list, but Task 1.2.2b's test list has no case locking this precedence in — worth one additional test.
