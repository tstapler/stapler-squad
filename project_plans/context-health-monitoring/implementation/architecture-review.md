## Concerns

- [ ] **Story 2.2.3 (`publishContextHealth` wiring)** — the acceptance criteria specify three distinct, testable branches (condition-change gating, skip-when-no-UUID, transition logging+publish), but Task 2.2.3a implements all three inline in an anonymous goroutine closure in `server/dependencies.go`, and Task 2.2.3b's only verification is `make test` (which adds no new coverage for this closure) plus a manual grep of a second instance's logs. This mirrors the existing `artifactExtractor.OnScanComplete` closure (also inline in `dependencies.go`, also untested — confirmed via `grep -n "func Test" server/dependencies_test.go`, which covers only `BuildServiceDeps`/`BuildRuntimeDeps`, nothing touching `OnScanComplete`), but repeating an existing testability gap for a second feature compounds it rather than fixing it. **Remediation**: extract the per-instance decision as a small pure function, e.g. `func nextContextHealthPublish(prev, next tokens.ContextHealthVerdict, hasTranscript bool) (verdict tokens.ContextHealthVerdict, shouldPublish bool)`, and table-test it directly (skip-no-uuid, skip-unchanged, publish-on-change) without needing a running server. The goroutine in `dependencies.go` then becomes a thin loop calling this function — restores per-lens-1-item-4 testability without changing the push design ADR-002 settled on.

- [ ] **`ContextHealthVerdict` invariant is enforced by convention, not by the type** (Lens 2, item 6) — `EvaluateContextHealth`'s acceptance criteria correctly specify that `HealthUnknown` always pairs with `Reason == ""` and `HealthAmber`/`HealthRed` always pair with a non-empty `Reason`, and the one production constructor (`EvaluateContextHealth`) happens to uphold this. But `ContextHealthVerdict{Level ContextHealthLevel; Reason string; Signals ContextHealthSignals}` is a plain exported struct with exported fields — nothing stops a future caller (or a second producer added per ADR-001's own stated extension path, e.g. a PostToolUse-hook-based signal source) from constructing `ContextHealthVerdict{Level: HealthRed, Reason: ""}` directly, which `getContextHealthInfo`/`ContextHealthBadge` would then render as a red badge with a blank tooltip. **Remediation**: keep `Level`/`Reason` exported for readability but add a single doc-commented invariant note plus a `func (v ContextHealthVerdict) Valid() bool` (or a table-driven test asserting the invariant over the four `Level` values) that Phase 4 validation or a future second-producer story is expected to call/assert — cheap now, and it's exactly the kind of "no fix without root cause" tripwire ADR-001's own "Mitigation / exit path" section is implicitly counting on a second producer to respect.

- [ ] **`session/tokens` accumulates a third architectural role** (Lens 1, item 2) — this plan adds both a `config` import (policy thresholds) and a `gen/proto/go/session/v1` import (`proto_mapping.go`, Task 2.2.1a) to a package whose `doc.go` describes it as a JSONL parser/cache. The proto-mapping-in-the-same-package pattern is not new — `session/detection/proto_mapping.go` already does exactly this (verified: `sessionv1` imported directly in the `detection` package) — so this is propagating an existing repo convention, not introducing a novel violation, and blocking on it here would be inconsistent given the precedent was already accepted. Still worth naming: `session/tokens` now spans JSONL parsing (infrastructure), token/skill aggregation (domain-ish), threshold evaluation (policy, via the new `config` import), and proto conversion (transport adapter) all in one package. **Remediation**: none required for this plan (matching existing convention is the pragmatic choice), but worth a one-line note in a future `.claude/rules/` entry that `proto_mapping.go` files are the accepted seam for proto conversion inside otherwise-domain packages, so it doesn't get re-litigated per-package.

- [ ] **Proto contract for the deferred "richer introspection" follow-on** (Lens 3, item 10) — the plan's choice of `enum ContextHealth context_health = 72; string context_health_reason = 73;` over a nested `ContextHealthState` message is well-justified for v1 (mirrors `detected_status`/`detected_context` exactly, and the reason string already encodes the one number the UX needs). The `Session` message is already at field 71 before this change, i.e. an already-large flat message. The plan's own Unresolved Questions note a future "richer debug surface (which heuristic, streak length, first-occurrence)" follow-on but doesn't say where that follow-on's fields should land. **Remediation**: add one sentence to the plan or a future ADR stating the follow-on's boundary explicitly — e.g. "if richer introspection needs more than one additional field, it goes in a new nested message or a separate debug RPC, not more flat fields on `Session`" — so the next author doesn't default to `context_health_debug_streak = 74`, `context_health_first_seen = 75`, etc. and continue the flat-field-per-feature pattern.

## Nitpicks

- Task 1.2.3a's description ("in the existing `tool_use` branch also append …; add a new `else if c.Type == "text"` branch") doesn't match the actual code shape at `session/tokens/parser.go` — the current loop is a guard-clause (`if c.Type != "tool_use" || c.Name == "" { continue }`), not an if/else chain, so there's no existing "branch" to extend as described; the implementer will need to restructure the loop into an if/else-if. Low risk (a few minutes), but worth fixing the task wording so it doesn't cause confusion mid-implementation.
- `session/tokens/doc.go`'s package-level "Privacy guarantee" comment (enumerating what `ParseResult` and derived types may carry) isn't updated by any task to mention the new `ContextHealthSignals` fields (tool-call fingerprints, confusion pattern *names*). The new fields are consistent with the existing guarantee (hash instead of raw args, pattern name instead of raw text), but the authoritative doc comment should say so explicitly for future readers rather than leaving it implicit.
- `Instance` and `Session` are both already large aggregates (`Instance` already carries `Artifacts`, rate-limit state, workspace metadata, etc.; `Session` proto is at 73 fields after this change) and this plan adds one more field to each, following existing precedent exactly. Not a new problem this plan created, but each additional field makes a later "is this aggregate doing too much" cleanup larger — noted for awareness only, no action requested here.
