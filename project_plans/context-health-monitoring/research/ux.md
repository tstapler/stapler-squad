# UX Research: context-health-monitoring

Phase 2, Research Agent 5 (UX). Scope: the health badge, its tooltip, and how it composes with existing session-card status indicators. Explicitly out of scope per requirements.md: "restart with summary" handoff flow, any modal/notification beyond the badge.

## 1. Comparable UX patterns — "needs attention" without being annoying

The dominant pattern across mature dev tools is **ambient, glanceable signal + on-demand detail**, never an interrupt:

- **VS Code Problems badge** (bottom status bar, editor tab dots): a small colored count badge that sits passively in a fixed location; clicking/hovering reveals detail in the Problems panel. It never pops a dialog for a new lint warning. Severity is color + numeral count, never color alone (there's always a number or icon).
- **GitHub PR / CI status dots**: a single colored dot (● yellow pending / ✕ red failed / ✓ green passed) inline next to the commit, with the full check list revealed only on click. The dot never auto-expands or interrupts the page.
- **git status indicators** (VS Code SCM badge, gitgutter): color + glyph (M/A/D letters, +/- gutter marks) — always paired with a letter or symbol, never bare color, and always co-located with the item it describes (the file, not a global toast).

What works: (a) the indicator is *always present but low-contrast until something's wrong* — it doesn't appear/disappear and cause layout shift; (b) escalation is through **information density on hover**, not modality — nothing steals focus; (c) the signal is **co-located with the object it describes** (the file row, the PR row), not aggregated into a separate notification tray the user has to remember to check.

What fails (anti-patterns to avoid): toast/snackbar per event (alert fatigue — exactly the CI-flakiness problem this repo already has opinions about, see `.claude/rules/tmux-keep-server-on-restart.md`'s tone of "don't surprise the user"), modal dialogs for non-blocking advisory information, and re-triggering an animation/pulse on every re-render (call it "pull-to-refresh anxiety" — pulsing badges on a list of a dozen concurrent sessions become visual noise, not signal).

**Recommendation**: a small static badge on the session card (matching `StatusBadge`/`SubStatusChip`'s existing visual weight — pill/chip, not a raised alert), silent by default at green, using Radix `Tooltip` (already imported in `SessionCard.tsx:5` for pause-reason and creation-failure disclosure) for the "why" on hover/focus. No sound, no toast, no auto-opening panel. This matches the requirements doc's own scope decision to explicitly defer "restart with summary" and any red-alert modal/notification (requirements.md "Out of Scope").

## 2. Mental model: how health should relate to (not collide with) existing status

`web-app/src/components/sessions/SessionCard.tsx` already renders, left-to-right in the `badges` row: external-source badge → GitHub PR badge → review-queue badge → **primary status badge** (`status` + `getStatusColor`/`getStatusText`, from `SessionStatus` proto enum: Active/Ready/Paused/Loading/NeedsApproval/Creating/Stopped/Hibernated) → rate-limit badge → `StatusBadge` (detected status, terminal-pattern-derived) → `SubStatusChip` (fine-grained live activity: Processing/NeedsApproval/InputRequired/Error/TestsFailing/RateLimited/Idle/Ready/Success, from `session/detection/dtypes/dtypes.go`'s categories) → memory-pressure badge → autonomous-mode badge → workflow badge → pending-program-change badge.

Two existing signal families already answer two different questions:
- **`SessionStatus`** (the pill labeled Active/Ready/Paused/etc.) = "is the *process* alive and what lifecycle state is it in" — infrastructure-level.
- **`SubStatusChip`/`StatusBadge`** (Thinking…/Approve Tool Use/Your Input Needed/Error/Tests Failing) = "what is the agent *doing right now*" — moment-to-moment activity, sourced from the same detection pipeline this project's health signal will extend.

A new **Context Health** indicator answers a third, orthogonal question: "is the agent's *reasoning quality* degrading over time" — a trend/quality judgment, not a point-in-time activity state. Users monitoring several concurrent sessions in list/board view need these to be visually distinguishable at a glance, or "Error" (SubStatus, transient — one bad command) gets confused with "Red health" (Context Health, cumulative — repeated looping/confusion across many turns). Concretely:

- **Never reuse the same shape/style as `SubStatusChip`** (rounded rectangular chip with icon+label text, e.g. "✖ Error"). If Context Health used an identical chip, a user scanning a dozen cards has no fast way to tell a one-off tool error from a sustained degradation pattern — they read the same visually.
- **Use a distinct, smaller form factor**: a compact dot/icon-only badge (think: a small circle or shield glyph, ~8-10px, similar footprint to the GitHub-check-conclusion dot pattern already partially used via `githubCheckConclusion`) placed at a *fixed* position — e.g. always the last item in the `badges` row, or pinned to the card's top-right corner outside the badge flow — so its position alone signals "this is a different kind of thing" independent of color. Fixed position also solves scan-ability: a user learns "top-right corner = health" once and doesn't need to re-parse the whole badge row per card.
- **Label it explicitly "Context Health" in the tooltip/aria-label**, never just "Warning" or "Error" — the word "health" needs to appear so it doesn't get mentally merged with "status." SubStatusChip and StatusBadge already use plain-English tooltips (`title="Waiting for your approval on a tool request"`); Context Health's tooltip should open with the same clarity: e.g. `title="Context health: Amber — 3 repeated tool calls detected"`.
- **Suppress at green** (or render a minimal "all clear" tick, not absent) — matching the existing convention that `SubStatusChip` returns `null` for low-signal states (IDLE/READY are filtered by the caller, see the chip's own doc comment) and `memoryBadge` only renders `if (mb <= 0) return null`. A hard rule: don't invent a fourth color-only "gray/unknown" pill that competes for attention with the real green/amber/red — see section 4 for the "not enough data" case, which should look visually distinct from "confirmed green," not just another color on the same 3-way scale.

## 3. Accessibility — color cannot be the only channel

WCAG 2.1 SC 1.4.1 (Use of Color) directly prohibits green/amber/red as the *sole* differentiator — roughly 8% of men have some form of red-green color vision deficiency, which is exactly the pair this feature's default palette uses. The codebase already gets this right everywhere else and this feature must follow suit — **every existing status/chip component in this repo pairs color with an icon glyph and a text label**, never color alone:

- `SubStatusChip.tsx`: every case has a unicode glyph (⏳ ✖ ⚠ ⌨ ●) *and* a text label ("Thinking…", "✖ Error"), plus `role="status"` + `aria-label`.
- `StatusBadge.tsx`: same pattern — `icon` + `label` pair per `StatusInfo`, rendered together (`{info.icon} {info.label}`).
- `GitHubBadge`/autonomous/workflow badges: same — glyph + word, never a bare colored dot.

**Recommendation for Context Health**: follow this exact convention — pair each of the three states with both a distinct icon *shape* (not just color) and a text label:
- Green → ✓ (check) — "Healthy" (or suppressed/minimal per section 2)
- Amber → ⚠ (triangle warning, already used by `chipTestsFailing`/`chipNeedsApproval`) — "Degrading" or "Watch"
- Red → ✖ or a distinct alert glyph (not the same ⚠ triangle as amber, to keep amber/red distinguishable by shape alone, not just hue) — "Needs Attention"

Using different *shapes* for amber vs. red (not just two different colors of the same triangle) is the detail most implementations skip — a colorblind user can still distinguish ⚠ from ✖ from ✓ even if the color rendering is indistinguishable. Always include `role="status"`, `aria-label` with the full sentence (not just the label word), and `title` for the mouse-hover tooltip — matching every sibling component's existing accessibility scaffolding exactly.

**CSS architecture constraints** (`.claude/rules/css-architecture.md`): the badge is a new component — it must be `.css.ts` (vanilla-extract), not a `.module.css` file, colocated as e.g. `ContextHealthBadge.tsx` + `ContextHealthBadge.css.ts` (matching `StatusBadge.tsx`/`StatusBadge.css.ts`'s existing pattern). Colors must reference `vars.color.*` tokens from `web-app/src/styles/theme.css.ts` (backed by `theme-contract.css.ts`) — never hardcoded hex. The existing `statusNeedsApproval`/`chipError`/`chipTestsFailing` style variants in `SessionCard.css.ts`/`SubStatusChip.css.ts` are the reference for what token-based amber/red styling already looks like in this codebase; new health-badge variants should reuse those same semantic tokens (e.g. whatever `--warning`/`--error`/`--success` map to in the vanilla-extract contract) rather than inventing new ones. If a z-index is needed for the badge or its tooltip layering, use a named slot from `zIndex` in `theme-contract.css.ts:195` — never a magic number (Radix `Tooltip` already handles its own portal z-index via `Tooltip.css.ts`, so this likely only matters if the badge itself needs positioning above sibling badges).

## 4. Error/edge-case UX

- **New session, insufficient data**: do not show green. Green implies "confirmed healthy," but a session three turns old hasn't accumulated enough signal to rule out looping/confusion — showing green is a false-confidence claim the badge can't back up. Instead, suppress the badge entirely (consistent with the existing convention of returning `null` for low-signal states — `StatusBadge`'s `UNKNOWN`/`UUNSPECIFIED` returns `null`, `SubStatusChip`'s `UNSPECIFIED` returns `null`, `memoryBadge` hides at `mb <= 0`). If product wants an explicit "not enough data yet" affordance instead of pure absence, use a neutral/muted style distinct from all three health colors (e.g. a dotted-outline or gray "—" glyph) so it can never be confused with "confirmed green" — but default to suppression unless research turns up a reason users need to see "pending."
- **Paused session — freeze, don't misfire**: per the requirements doc's own pitfalls concern (loop/apology counters must not accumulate or decay while a session is paused, since no new output is being produced to evaluate), the badge must **freeze at its last computed state** while `session.status === SessionStatus.PAUSED`, not reset to "no data" and not continue climbing toward red from stale counters. Visually, this likely means composing with the existing `isPaused` styling (`cardPaused` class, already applied to the whole card per `SessionCard.tsx:401`) — the health badge should render its last known state but the card's overall paused dimming/treatterment already signals "this isn't live right now," which naturally contextualizes a frozen health badge as "this was the state when it paused," not "this is degrading right now." Consider adding "(paused)" to the tooltip text when in this state so a user doesn't read a red badge on a paused card as an active emergency requiring immediate action.
- **Underlying data source errors** (e.g. the health computation itself fails, detector pipeline throws, or the ConnectRPC field is simply absent on an older server build during a rolling deploy): treat identically to "insufficient data" — suppress rather than show a broken/red state. A badge that goes red because *its own plumbing* failed (not because the agent is actually degrading) is worse than no signal: it trains the user to distrust the badge (directly undermining the stated success metric "false-positive rate ... low enough that health badges are trusted"). This mirrors `SubStatusChip`'s existing forward-compatibility guard (`default:` case logs a warning and returns `null` rather than throwing on an unrecognized wire value) — the same defensive-null convention should extend to a missing/errored `ContextHealth` field.

## 5. Jobs-to-be-done

- **Functional job**: "Tell me, at a glance across a board of concurrent sessions, whether this one needs a closer look — without me having to read its scrollback." The badge exists to replace active terminal-watching with passive scanning.
- **Emotional job**: "Stop me from worrying that I'm quietly burning tokens/time on a session that's stuck looping or confused, several turns before I'd otherwise notice." This is a reassurance/trust job as much as an alerting one — the badge's silence (green/suppressed) needs to be as trustworthy as its alarm (red), or the user reverts to manually re-checking scrollback anyway, defeating the point. This is why sections 3-4 push hard on "don't show a false green" and "don't let plumbing failures manifest as red" — a badge that cries wolf or lies quiet loses the trust that is the entire point of building it.
- **Social job**: minimal — this is a single-user tool (per requirements.md's Users/Consumers list: interactive user, backlog automation, rules engine; no team/sharing dimension mentioned). No social signaling job (e.g. "look how many sessions I'm running") is in scope, and the badge should not be designed to invite that reading — kept small, muted, and functional rather than a dashboard/gamification element.

## Summary of concrete recommendations for Phase 3 planning

1. New component `ContextHealthBadge.tsx` + `ContextHealthBadge.css.ts` (vanilla-extract, token-based colors), separate files from `StatusBadge`/`SubStatusChip`, following their exact accessibility scaffolding (`role="status"`, icon+label pair, `aria-label`, `title`).
2. Distinct shape/position from `SubStatusChip` (different form factor and/or fixed position) so "session status" and "context health" are never visually conflated; explicit "Context Health" wording in tooltip/aria-label.
3. Three states use three distinct icon *shapes* (not just three hues of the same shape): ✓ green, ⚠ amber, ✖ red (or equivalent), each with an explicit text label.
4. Suppress the badge (render `null`) for: no data yet (new session), and any computation/data-source error — never render a colored guess in either case.
5. Freeze (don't recompute/reset) the badge's last state while the session is paused; note "(paused)" in the tooltip so a frozen red doesn't read as an active emergency.
6. Tooltip via the existing Radix `Tooltip` component (`web-app/src/components/ui/Tooltip.tsx`) — no modal, no toast, consistent with the requirements doc's explicit exclusion of alert modals this iteration.
