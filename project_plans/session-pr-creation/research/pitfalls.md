## 1. Documented past bugs in this exact code path (`pushAndCreatePR`)

`session/backlog_lifecycle.go:3585` (`pushAndCreatePR`) and its sibling
`shipViaAgentOrFallback` (~line 3520) carry inline doc comments naming the
specific incidents that shaped the current defensive code. The new mechanical
RPC this feature adds is a **second caller of the same primitives**
(`GitWorktree.CreatePR`/`findExistingPR`, `EnablePRAutoMerge`), so each of
these lessons is a real risk for the new path too, not just historical
trivia.

| Bug | What happened | Where | Must the new RPC replicate the fix? |
|---|---|---|---|
| **BUG-040** | A failure persisting `PrURL`/`PrNumber` to storage after `CreatePR` succeeded was only logged, and the code proceeded to `resolveToPRPending` anyway — landing the item in `pr_pending` with `pr_number=0`/`pr_url=""`, permanently invisible to every downstream reconciler's `PrNumberGT(0)` filter, with nothing left to retry. Fixed by treating a persist failure exactly like a push/PR-creation failure (`backlog_lifecycle.go:3663-3684`). | `pushAndCreatePR` | **Yes, by analogy.** The new RPC's session isn't a backlog item, so there's no `pr_pending` reconciler risk directly, but the equivalent failure mode is: `CreatePR` succeeds, then `SaveInstances`/whatever persists `GitHubPrUrl` on the session fails silently. `RunOneShot`'s existing code (`session_service.go:3691-3696`) already does this wrong today — it only `log.Warn`s on a `SaveInstances` failure and returns success regardless (no error surfaced to the caller). The new RPC must **not** copy that pattern: a post-creation persist failure should be returned as an error (or at minimum a `partialFailure` response field) since acceptance criterion 6 requires surfacing specific errors, and a PR that was created but never recorded is exactly the kind of state a re-click would then try to recreate/duplicate.
| **BUG-063 (a)**: `prNumber<=0` (unparseable PR reference) must not fall through to an unconditional success/transition path — treat it the same as a real failure, don't silently retry and risk a duplicate. | `shipViaAgentOrFallback` (~3537-3556) | **Yes.** `CreatePR` (`worktree_git.go:329`) already guards this at the source: it parses the PR number from the URL via regex first (see next row) and only falls back to a second `gh pr view` call if that fails. The new RPC handler should still treat `prNumber == 0` (both parse paths failed) as an error, not a silent "success with number 0" response — mirror BUG-040/BUG-063's rule: never persist/report success with a zero/empty PR reference.
| **BUG-063 (b)**: a branch with zero commits ahead of the base has genuinely nothing to ship; `gh pr create` fails with a `"No commits between X and Y"` error that is **not** a retryable push/PR failure — it needs its own detection (`HasCommitsAheadOfMain`, `worktree_git.go:428`) and a distinct handling path (`fallbackToDone`, not `stayInReviewAndNotify`). | `pushAndCreatePR:3628-3643` | **Yes, and this is explicitly named in acceptance criterion 6** ("no commits ahead" is listed as an example failure the modal must surface specifically). The new RPC should call `HasCommitsAheadOfMain` (or reuse the session's existing "commits ahead" gating already implied by AC1: "at least one commit ahead of its base branch") as a pre-flight and return a distinguishable error/response state — not a generic `gh pr create` stderr passthrough — when there's nothing to ship. Note `HasCommitsAheadOfMain`'s own doc comment: on an inconclusive check (repo-open error, branch not existing locally) it returns `true` (proceed) by design, so a broken check never blocks a legitimate PR attempt — the new RPC should preserve that fail-open behavior rather than fail-closed.
| **PR number parsing from URL vs. a second `gh` call that silently failed** | The original code called `gh pr view --json number --jq .number --head <branch>` as the *only* way to get the PR number; that call occasionally returned empty/erroring output with the error silently swallowed, leaving `prNumber` at 0 even though `prURL` had resolved correctly — the resulting "PR #0" was passed to `EnablePRAutoMerge`, which failed with "no pull requests found," so auto-merge silently never got enabled. Fixed by parsing the number directly out of the URL string first (`prNumberFromURLRe`) and only falling back to the `gh pr view` subprocess call if the regex parse fails. | `CreatePR`, `worktree_git.go:365-389` | **Already fixed at the shared call site** — `CreatePR` is the function the new RPC will call directly, so this fix is inherited for free. No new code needed here, but worth asserting in a test that the new RPC handler doesn't re-derive `prNumber` via its own separate `gh` call (which would reintroduce the exact bug in a new location).
| **Persist-failure-vs-transition-failure distinction generally** (BUG-030/040/041/046/048, referenced at `backlog_lifecycle.go:699`) | Recurring shape across this codebase: a mutating side effect (PR created, commit pushed, item transitioned) succeeds, but persisting the *record* of that side effect fails, and the code either silently ignores it or treats it as if nothing happened — leaving state permanently drifted with no automatic retry path. | Multiple sites, `notifyTransitionFailed` helper | **Design principle to carry into the new RPC**: any failure *after* `CreatePR` returns a real URL (e.g. failing to write `GitHubPrUrl` onto the session, failing to publish the SSE/event-bus update) must be surfaced to the frontend as a partial-success/error state distinct from "nothing happened," not swallowed as a warning log. The modal's error surface (AC6) should be able to show "PR #123 was created (https://github.com/.../pull/123) but couldn't be saved to the session — refresh to check" rather than a generic failure.

## 2. Rule conflicts / clarifications

- **`.claude/rules/prefer-go-git-over-subshells.md`**: `GitWorktree.CreatePR` and `findExistingPR` shell out to `gh` via `safeexec.CommandContext`, not go-git. This is **not a violation** — the rule's own "when a subshell is still fine" exception explicitly covers "any operation needing a credential helper for push/fetch against a real remote," and PR creation is a GitHub-API operation (not a local git operation) that go-git has no support for at all — there is no go-git equivalent to `gh pr create`. `PushBranch` (`worktree_git.go:315`) also shells out (`git push`) for the same credential-helper reason already named as acceptable in the rule. **No action needed**; this is worth stating explicitly in the plan doc so a reviewer doesn't flag it as a rule violation during `sdd:6-verify`.
- **`.claude/rules/gh-pr-merge-repo-flag.md`**: covers `gh pr merge`, not `gh pr create`/`gh pr list` — not directly applicable, but the underlying mechanism (worktree-vs-`gh`-CLI ambiguity about which repo it's targeting) is the same class of risk. `CreatePR`/`findExistingPR`/`HasCommitsAheadOfMain` all set `cmd.Dir = g.worktreePath` before invoking `gh`, which is the correct mitigation (matches how the rule's fix works, just via cwd instead of `--repo`) — confirm the new RPC path reuses `GitWorktree` (and thus this cwd-scoping) rather than introducing a fresh `gh` invocation that could default to the wrong remote.

## 3. Race conditions

- **No per-session/per-branch lock exists today** anywhere in this call path. `GitWorktree.CreatePR` has no mutex (confirmed: no `sync.Mutex`/`Lock()` in `session/git/worktree_git.go`), and `server/services/session_service.go` has no per-session serialization mechanism for mutating RPCs (`findInstance` just looks up the in-memory instance; no lock map found in `session_service.go`/`session/instance.go`).
- **Two near-simultaneous "Create PR" clicks (same session, e.g. two browser tabs or a double-click that beats the frontend's `isRunningOneShot` disable)**: both RPC calls could pass `findExistingPR`'s pre-check (returns "no existing PR" for both, since neither has created one yet) and both invoke `gh pr create` concurrentlyy. `CreatePR`'s existing retry-on-failure logic (`worktree_git.go:350-354`: "A race: PR was created between our check and now. Re-check once.") already handles this at the `gh` level — the loser's `gh pr create` fails, it re-checks `findExistingPR`, finds the winner's PR, and returns that instead of erroring. **This existing mitigation is sufficient for the `gh pr create` call itself** and the new RPC inherits it for free by calling `CreatePR` directly. However, two other steps are *not* covered by this mitigation: (1) `CommitChanges`/`PushBranch` (if the mechanical flow also handles committing dirty state, per `pushAndCreatePR`'s pattern) — two concurrent `git push` calls to the same branch are not guaranteed to both fail-and-recover cleanly (one may succeed, the other may hit a non-fast-forward rejection that then needs its own error message, not a generic "push failed"); (2) whichever step persists `GitHubPrUrl`/`GitHubPrNumber` onto the session record — two concurrent writers doing read-modify-write on `s.allInstances()`/`SaveInstances` is a classic lost-update race unless that path already serializes (needs verification during planning/implementation, not assumed safe by inspection alone).
- **Recommendation**: either (a) add a lightweight per-session in-flight guard in the new RPC handler (a `sync.Map[sessionID]bool` or similar, returning a clear "PR creation already in progress for this session" error on a concurrent second call — cheapest, most explicit fix), or (b) rely on frontend-only prevention (disable button + optimistic state) and accept the `CreatePR`-level race mitigation as the safety net, explicitly documenting that a lost-update on the persisted PR fields is a known, low-probability edge case. Given AC6 wants specific error surfacing, (a) is cheap and directly serves that requirement.
- **Race with the (to-be-removed) `RunOneShot` agentic path, if not fully removed**: AC7 requires removing/demoting the old button, but until that ships, a user could trigger the agentic `RunOneShot("Create a pull request...")` path on one tab and the new mechanical modal on another for the same session. The agentic path runs a full `claude -p` turn that itself may commit/push/run `gh pr create` — colliding with the mechanical path's own commit/push/CreatePR sequence, with no coordination between them (different code paths, `RunOneShot` in `session_service.go:3616` vs. the new RPC). This is exactly the "two confusing entry points" AC7 is designed to prevent — treat AC7 as a correctness requirement, not just a UX cleanup: shipping the new modal *without* removing/demoting the old button reintroduces a real concurrent-mutation race, not just user confusion.

## 4. Auth / security

- **`checkGHCLI()` (`session/git/util.go:46`)** is the only auth gate today: checks `gh` is on `PATH` and `gh auth status` succeeds. It's called at the top of `CreatePR` (`worktree_git.go:330`), so the new RPC inherits this check for free and will surface `"GitHub CLI is not configured. Please run 'gh auth login' first"` as a plain error — AC6 requires this be shown as a specific error in the modal, which it already will be verbatim if the RPC just propagates `CreatePR`'s returned error.
- **`gh auth status` is process-wide/machine-wide**, not per-request-user-scoped — this is a single-operator local tool (stapler-squad runs as the operator's own systemd user service), so there's no multi-tenant auth boundary to enforce at the RPC layer beyond what already exists for every other session-mutating RPC (i.e., none — anyone who can reach the web UI on `localhost:8543`/Tailscale can already create sessions, run one-shots, etc.). **No new authorization check is needed** beyond what every other mutating RPC in this service already has (or doesn't have) — flagging a new auth layer specifically for PR creation would be inconsistent with the rest of the RPC surface and out of scope per the requirements doc's non-functional section (it doesn't mention auth).
- **Do note**: `gh pr create --title ... --body ...` executes with whatever `gh` scopes/permissions the authenticated identity has — if that identity has push access to protected branches or admin-merge rights, `EnablePRAutoMerge`/`RequestCopilotReview` (already existing, not new to this feature per the "explicitly out of scope" section) could act with more privilege than the clicking user intends. This is pre-existing behavior inherited from the backlog path, not a new risk introduced by this feature — no action needed, but worth naming so it isn't mistaken for a gap in the new code.

## 5. Frontend pitfalls

- **Stale diff in the modal vs. actual worktree state at submit time**: AC1 says the modal is pre-filled with a body "generated via the existing `headless.DraftPRDescription` call against the session's diff" at the time the modal opens. If the session is a live agent session (not just a finished backlog session) that keeps writing to the worktree while the modal is open — plausible per this repo's architecture (`session/` manages long-running tmux-backed Claude Code sessions, and `GetSessionDiff` (`server/services/session_service.go:2649`) reads the live worktree state) — the diff shown/summarized in the modal can go stale between "open modal" and "click confirm." `DraftPRDescription` (`session/headless/features.go:280`) explicitly rejects an empty diff (`"DraftPRDescription: empty diff, nothing to describe"`), so if the agent's further writes somehow *reduce* the diff to nothing between preview and submit (unlikely but not impossible — e.g. an agent reverting its own changes), a naive implementation that re-derives the diff at submit time could hit that error unexpectedly, or a naive implementation that reuses the *modal-open-time* diff for the actual PR body could describe a body that doesn't match what actually gets pushed.
  - **Recommendation**: title/body edited by the user should be sent as-is (they're free text, no re-derivation needed — user intent wins). But the actual `git push`/`CreatePR` step must operate on the worktree's state *at submit time*, not a cached snapshot — this is already how `pushAndCreatePR` behaves (it re-reads worktree state fresh on each invocation) so no extra design is needed there, but the modal UI/UX should probably show a lightweight "diff last generated N seconds ago" or a refresh affordance if the session is still actively running when the modal opens, per the mobile+desktop UX standing instruction to consider live/changing state. This is a UX nicety, not a correctness requirement in the acceptance criteria — flag as a suggestion for `sdd:3-plan`, not a blocking gap.
- **Button state duplication (AC7)**: `SessionActionsOverflow.tsx` already tracks local `isRunningOneShot`/`oneShotResult` component state (lines 117-118) that resets on remount/navigation — if the new modal reuses this same local-state pattern rather than deriving "PR already created" from the persisted `session.githubPrUrl` field (already exposed per requirements.md's baseline section), a user who closes/reopens the panel or switches sessions and back will lose the "✅ PR Created" indicator even though the session-level field is still set. The existing baseline already partially has this problem (`oneShotResult` is local, `githubPrUrl` is persisted) — the new implementation should prefer deriving button/modal state from the persisted field, not reintroduce a parallel local-only status flag.
