# Pre-mortem: session-pr-creation
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The Post-Review Revisions fix for the diff-scope blocker made `DraftPullRequest`'s shared `ensureCommitted` step run a real `wt.CommitChanges` **inside the "read-only" preview RPC**, so simply opening the modal now commits whatever is in the working tree — including partial edits from a still-running agent, since AC1 scopes this to "active worktree" sessions, which can mean the agent process is still writing files in that same worktree at the moment the user peeks at the modal. This directly contradicts the plan's own Step 0.5 rationale for choosing two RPCs over a `dry_run` flag ("the preview step can never have a side effect"). | A user opens the Create PR modal to check status, closes it without confirming, and later finds an unexpected `[stapler-squad] work complete ... (pre-PR)` commit on their branch — or, worse, an actively-running agent's in-progress file writes get interleaved with the background commit, producing a commit containing syntactically broken/half-written code. | Move `ensureCommitted` so it runs only inside `CreatePullRequest` (immediately before push, as originally scoped), and have `DraftPullRequest` preview from the working-tree-inclusive diff `GetSessionDiff`/`GitWorktree.Diff()` already uses instead of committing to match it — restoring true read-only semantics. Add a test asserting `DraftPullRequest` never calls `wt.CommitChanges`. | P1 |
| 2 | AC7 fully removes the old `RunOneShot`-driven "Create PR" button with no feature flag or staged rollout ("Risk Control" explicitly rules both out), so any production bug in the new mechanical flow — including #1 above, or an untested `gh` CLI edge case — leaves users with zero UI path to create a PR until a full `git revert` + redeploy ships. | Within days of shipping, multiple sessions' "Create PR" clicks start failing or producing bad commits/PRs, and there is no fallback button to route around it — reported as "PR creation is just broken." | Keep the old overflow-menu entry point in place (even demoted/labeled) until the new flow has run in production through at least one full review cycle, or explicitly rehearse and time the git-revert rollback before merging Epic 2.5's removal so the recovery path isn't being exercised for the first time under incident pressure. | P2 |
| 3 | `GitVCSReader.ResolveDefaultBranch` resolves a single default branch with no remote disambiguation, but this repo itself has two remotes (`origin` fork, `upstream-fanatics` canonical — see `CLAUDE.md`'s Git Remotes table and the existing `.claude/rules/gh-pr-merge-repo-flag.md` documenting prior remote-confusion pain in this exact codebase). The modal's base-branch field is a plain text input (Pattern Decisions row), so a wrong default is easy to miss before confirming. | A PR is published against the wrong remote/branch (e.g. targets `origin/main` when the user meant `upstream-fanatics/main`) — discovered only after the PR is live, when it shows up on the wrong repo or diffs oddly against the wrong base. | Add a Go test exercising the base-branch resolution against a repo configured with two remotes matching this project's own `origin`/`upstream-fanatics` shape, and document in plan.md which remote wins so the behavior is explicit rather than incidental. | P3 |
| 4 | `DraftPullRequest`'s existing-PR short-circuit (Task 1.3.1b) is permanent — once `inst.GitHubPrUrl` is ever set, the modal shows "View PR" forever, with no check of whether that PR was later merged or closed. A session/branch reused for follow-up commits after its PR merges has no path back to the editable create form through this UI. | A user pushes new commits to a session whose earlier PR already merged, clicks "Create PR" expecting a fresh PR, and instead sees a permanent "View PR #512" link pointing at a now-closed/merged PR with no way to create a new one from the modal. | Have `DraftPullRequest`'s short-circuit check live PR status (e.g. via the existing `GetPRStatus` RPC) before deciding to short-circuit; fall through to the normal draft/edit flow when the cached PR is merged or closed. Add `TestDraftPullRequest_should_ShowEditableForm_When_ExistingPRIsMergedOrClosed`. | P2 |
| 5 | The Observability Plan explicitly adds no new logs/metrics beyond existing warning-level lines. When `headlessPool` is nil or `DraftPRDescription` fails/times out, `DraftPullRequest` silently falls back to a generic placeholder body ("_No diff description available._") with no way for anyone to notice this is happening at scale — directly undermining AC1's actual value (a genuinely drafted, useful PR body). | Weeks after shipping, someone manually reading several recently-created PRs notices many of them share the identical generic fallback body text, with no alert or dashboard signal that would have surfaced this sooner. | Add a counted log line distinguishing "LLM draft succeeded" vs. "fell back to placeholder" (even without new metrics infra, a `grep`-able log line is enough for a spot-check), and/or surface the fallback in the modal UI itself (a small "AI draft unavailable — using template" note) so degradation is visible without server-side monitoring. | P2 |
