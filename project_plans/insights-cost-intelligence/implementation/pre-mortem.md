# Pre-mortem: insights-cost-intelligence
**Date**: 2026-09-03

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Every detector abstains ("unpriced model") for every session because the operator's actual models aren't in `PricingTable` — the findings panel renders "No waste patterns detected," visually identical to a genuinely clean dashboard, exactly the conflation Story 1.1.6's design goal says to avoid. | Findings panel shows "No waste patterns detected" every day, including during a week where the Daily Spend chart clearly shows a cost spike. | Add a 4th panel state distinct from "clean": when a non-trivial share of in-range sessions have non-empty `unpricedModels`, surface "N sessions could not be evaluated (unpriced model)" instead of/alongside the clean message. Add a fixture test in Story 1.1.6 asserting this state renders when all sessions are unpriced. |
| 2 | The four detector thresholds (0.40 cache floor, 2M token ceiling, 30K context floor) are fiat numbers never run against Tyler's actual ~600-session distribution — they either fire on nearly every session (alert fatigue, panel ignored) or almost never (feature perceived as broken). | The findings panel shows the same 1-2 low-value findings every day, or floods with 15+ findings per load, and gets stopped being opened. | Before/during implementation, run the 4 detectors as a one-off script over the real local JSONL corpus and record the resulting finding-rate distribution in validation.md; tune constants so the top findings are actually differentiated rather than shipping thresholds as pure guesses with "tune later" as the only plan. |
| 3 | Both success metrics ("find the driver fast," "findings get acted on and spend drops") are validated only by "Tyler's own usage post-ship" with zero instrumentation — the project can ship fully working code and there is still no way to answer "did this work" weeks later. | A month post-ship, nobody can point to a log line, count, or before/after number showing the findings panel was ever opened or acted on. | Add one cheap `slog.Info` line (e.g. "finding_clicked" / "findings_panel_viewed") to validation.md's observability section — no metrics/alerting infra, just a grep-able log line — so the requirement's own success-metric language is checkable after the fact. |
| 4 | ADR-002's non-summability of `DollarImpact`/`WasteScore` is a review convention only (Go can't enforce it); once findings, per-tool cost, and activity cost are all on the same dashboard, a natural next feature ("total estimated waste: $X") sums double-counted or non-additive figures, producing an inflated number that looks authoritative. | A "Total waste" or "Total tool cost" figure appears somewhere that doesn't reconcile with the session's actual billed cost when spot-checked. | Add an explicit non-summability comment at the top of `findings.go`/`FindingsPanel.tsx` plus a review-checklist line in validation.md's verification pass ("no `Σ DollarImpactUsd` or `Σ CostUsd` outside the documented formulas") so a reviewer has a named thing to check, not just tribal knowledge in ADR-002. |
| 5 | The `WatchInsights` fix (Epic 1.5) makes every file-change/reparse event trigger a full `buildSessionSummary` (4 detectors + tool-cost attribution + activity classification + cache ROI) synchronously inside `watchInsights`, turning a "dead but harmless" path into a "live but expensive" one during an actively streaming session with frequent JSONL appends. | The Insights tab feels laggy or the browser's network panel shows a burst of large `WatchInsights` messages during rapid tool-call turns in an active session. | Add a Story 1.5.3 acceptance criterion benchmarking `buildSessionSummary`'s cost under realistic rapid-reparse frequency against the NFR's latency budget, and consider debouncing/coalescing successive `notify()` calls for the same session before invoking it, rather than computing it per raw file-write event. |

## P1 Items (address before implementation)
- [x] Failure #1 — **Resolved in plan.md/ux.md**: Story 1.1.6 and Task 1.1.6b now specify a 4th distinct "N sessions could not be evaluated (unpriced model)" panel state, separate from computed-empty; Task 1.1.6d requires a fixture test asserting the two render different text; `design/ux.md`'s B1 section updated to the same 4-state model.
- [x] Failure #2 — **Resolved in validation.md**: new "Threshold Calibration (blocking)" section added, naming the exact hardcoded constants (`cacheHitFloor = 0.40`, `sessionTokenCeiling = 2_000_000`, `oversizedContextFloor = 30_000`) and a 6-step procedure to run the detectors over the real ~600-session local corpus and tune before Story 1.1.6 ships.
