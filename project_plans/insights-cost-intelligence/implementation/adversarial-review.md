## Concerns

- [ ] **No perf/load test validates the NFR it claims to satisfy.** `requirements.md`'s NFR requires findings/cost computation not to "visibly regress" `GetInsightsSummary` latency, targeting "no more than low-hundreds-of-ms added" at ~600 sessions. The plan's Observability Plan asserts this is "microseconds of CPU — not worth instrumenting a latency histogram for," but no task in Epic 1.1/1.2 adds a benchmark or a 600-session-scale test to substantiate that claim before merge. **Recommendation**: add one `go test -bench` or a table test with a synthetic 600-session store to `insights_service_test.go`, asserting a wall-clock ceiling.
- [ ] **ADR-002's non-summability guardrail is pure convention with zero mechanical enforcement.** The plan is candid that "Go cannot forbid `+` on a numeric newtype," but stops at a doc-comment convention. This repo's own `quality:reflect-and-fix` philosophy (compile → lint → test → checklist, cheapest enforcement wins) is cited elsewhere in this codebase's conventions; settling for the checklist tier here, with no discussion of why a cheap grep-based CI check or a struct-wrapper-with-no-arithmetic-method was rejected, is a gap for a plan this rigorous everywhere else.
- [ ] **Task 1.1.3d's panic-isolation test is inconsistent with Task 1.1.3b's stated guard.** 1.1.3b says `detectOversizedStartContext` should "skip if `len(r.TurnTimeline) == 0`" — but 1.1.3d proposes proving panic isolation by "feeding a 0-turn `ParseResult` that would otherwise divide-by-zero in `detectOversizedStartContext`'s indexing." If the guard from 1.1.3b is implemented as specified, that input can never reach the panicking code path, so this test would pass for the wrong reason (or not exercise `recover()` at all). The AC doesn't commit to the fallback option ("inject a detector stub that panics via a package-level test hook") as the actual mechanism, leaving the aggregator's core safety property effectively untested.
- [ ] **No e2e coverage for either headline user-facing deliverable.** `tests/e2e/` and this repo's `e2e-test-conventions` skill exist specifically for flows like this, yet no task in Epic 1.1 (findings panel) or Epic 1.4 (deep-linkable route) adds a Playwright spec — only React unit/component tests are specified. A bookmarkable route that "renders correctly with no dependency on the dashboard's in-memory state" (Story 1.4.3's own AC) is exactly the kind of claim a component test can't fully verify (it doesn't exercise cold navigation in a real browser).
- [ ] **Two proto field additions skip the provenance check the rest of the plan uses.** Every other field addition in this plan states "next free field number after X" backed by a grep (`findings = 14` after `unpriced_models = 13`; `cache_roi_usd = 18` after `unpriced_models = 17`). Task 1.2.2a (`TopToolEntry.cost_usd = 4`/`cost_may_double_count = 5`) and Task 1.4.1a (`GetInsightsSummaryRequest.conversation_id_filter = 6`) assert field numbers with no such citation — a real collision risk if either message already uses those numbers.
- [ ] **WasteScore's weighting (40/30/30 split) is asserted, not calibrated.** Task 1.1.4a picks a blend of hit-rate/ceiling/context penalties with no validation against any known-good or known-bad session before it ships as the sortable, user-facing waste-score column — the exact kind of "precise-looking number with no operational meaning" the plan itself warns against elsewhere (Pattern Decisions row on per-tool cost attribution, rejecting even-split for the same reason).
- [ ] **Story 1.4.2b bundles an unrelated a11y bug fix into the route-extraction story.** Fixing the modal's pre-existing missing focus-trap is good practice, but it's not something `requirements.md` asked for in Epic 1.4's scope — it enlarges that story's diff and review surface beyond "extract shared component," and risks being the actual cause if that PR needs to be reverted for an unrelated route regression.

## Minors

- Only `detectCacheHitFloorBreach` documents a `clamped ≥ 0` note on its dollar-impact math; `detectModelSwitchCacheBust`/`detectSessionTokenCeiling` don't state the same guarantee, even though negative dollar impacts would be equally nonsensical there.
- `FindingsPanel`'s interim wiring to `onSessionClick` (Task 1.1.6b, pending Epic 1.4) is reasonable sequencing, but if Epic 1.4 becomes the workstream cut under the Large-appetite "cut one entirely" allowance, this interim link becomes permanent with only a code comment as a trace of the intent — no backlog/follow-up task captures that contingency explicitly the way the deferred detectors do (Unresolved Questions section).
- `TokenStore.Subscribe`'s non-blocking `select`/`default` drop-on-slow-consumer behavior is unchanged by this project, but the payload it can now drop is a real `*ParseResult` rather than an empty signal — a dropped per-session update now has no fallback trigger until the next `parse_complete`. Worth a one-line acknowledgment in the plan, not a redesign.
