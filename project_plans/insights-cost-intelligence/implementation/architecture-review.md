## Resolved

- [x] **Epic 1.1 Task 1.1.1a (`WasteFinding.finding_type`/`severity`), Epic 1.2 Tasks 1.2.3a/1.2.4a (`SessionTokenSummary.activity_type`, `ActivityCostBreakdown.activity_type`)** — previously specced as plain proto3 `string`, contradicting this repo's 20+ existing enum precedents. **Verified fixed**: Task 1.1.1a (plan.md:175-180) now defines `enum Severity`, `enum FindingType`, and `enum ActivityType` together in `proto/session/v1/insights.proto`, all three following this repo's exact naming convention confirmed by inspection of `proto/session/v1/types.proto` (`ENUM_NAME_VALUE_UNSPECIFIED = 0` prefixing, e.g. `SESSION_STATUS_UNSPECIFIED`, `PRIORITY_UNSPECIFIED`) — `SEVERITY_UNSPECIFIED = 0`, `FINDING_TYPE_UNSPECIFIED = 0`, `ACTIVITY_TYPE_UNSPECIFIED = 0` all match. The Go alias pattern is applied consistently: `session/tokens/finding_types.go` (Task 1.1.1b, plan.md:183) and `session/tokens/activity.go` (Task 1.2.3a, plan.md:369-370) both define `type FindingType = sessionv1.FindingType` / `type Severity = sessionv1.Severity` / `type ActivityType = sessionv1.ActivityType` as Go type aliases of the generated proto enums plus package-level constant aliases (e.g. `FindingCacheHitFloorBreach`, `SeverityCritical`, `ActivityDebugging`), explicitly citing the same precedent the original blocker named (`proto/session/v1/types.proto:423`, "Maps to session.Status enum in Go" — confirmed present at that file's `SessionStatus` enum doc comment). Every downstream task that touches these fields was checked and none regresses to a string: Task 1.1.5a (`SessionTokenSummary.activity_type` field, plan.md:265) and Task 1.2.4a (`ActivityCostBreakdown.activity_type`, plan.md:389) both explicitly call out "not a plain `string`"; Task 1.1.5b (plan.md:269) and Task 1.2.3c (plan.md:378) both state the enum copies across "with no string conversion" at the domain→proto boundary in `insights_service.go`; the frontend tasks (1.1.6b at plan.md:290, 1.2.5c at plan.md:415) map the generated TS enum value through a lookup table to a UI label/Badge intent rather than a raw string compare; and the acceptance-criteria examples throughout (Stories 1.1.1, 1.2.4) construct fixtures using `sessionv1.FindingType_...`/`sessionv1.Severity_...`/`sessionv1.ActivityType_...` enum values, not string literals. No plain-`string` reference to any of these four fields remains anywhere in plan.md (grep-verified). The fix does not introduce a new problem: enum naming is consistent across all three new enums and with the 20+ pre-existing ones, and the alias pattern is applied uniformly rather than ad hoc per file.

## Concerns

- [ ] **Story 1.1.3, Task 1.1.3c (`ComputeFindings`)** — the Pattern Decisions table calls the detector set a "Strategy" pipeline, but Task 1.1.3c's actual instructions hardcode 4 sequential detector calls, each individually wrapped in its own `recover()` closure, rather than iterating a `[]detector` slice. This undercuts the claimed OCP/Strategy benefit (a 5th/6th detector — already flagged as deferred follow-up work — means copy-pasting the boilerplate again, not appending to a list) and risks tripping this repo's enforced `dupl` new-code gate (`make ready-complexity-gate`) on 4 near-identical panic-recovery closures.
  **Remediation**: `type findingDetector struct { name string; fn func(*ParseResult, *PricingTable) *Finding }`; build `var findingDetectors = []findingDetector{...}`; have `ComputeFindings` loop over it with one shared recover-wrapping helper instead of 4 inline copies.

- [ ] **Story 1.1.3, Task 1.1.3d (fixture tests for panic isolation)** — one of the two acceptance-criteria-sanctioned test approaches ("inject a detector stub that panics via a package-level test hook") would require production code in `findings.go` to expose a mutable package-level detector list as a test seam, introducing test-only global state into non-test code.
  **Remediation**: make the task's other listed option ("feed a 0-turn `ParseResult` that would otherwise divide-by-zero in `detectOversizedStartContext`'s indexing") the mandated approach rather than an alternative, so no exported/mutable test hook gets added; if a future detector can't be made to panic naturally on any constructible fixture, prefer an internal `_test.go`-only variable override over an exported seam.

- [ ] **`insights_service.go`'s per-session loop across Epics 1.1–1.3** — the plan's own Step 0.5 already names this risk ("`GetInsightsSummaryResponse` keeps growing into a kitchen-sink message") and accepts it deliberately, but by the end of this project the per-session loop in `GetInsightsSummary`/`ListSessionTokens` inlines: association/filtering, cost, cache-hit-rate, top-tools+cost, findings, waste-score, activity classification, cache-ROI, daily rollup, model breakdown, and skill/tool aggregation — a Transaction Script (PoEAA) outgrowing Fowler's stated sweet spot ("simple procedural logic; simple CRUD... migrate to Domain Model when complexity grows"). `buildSessionSummary` (Story 1.5.2) extracts the single-session-shaping half; the cross-session accumulation half (`activityMap`, `modelMap`, `dailyMap`, findings cap/sort) stays inline in the loop and keeps growing across epics.
  **Remediation**: after 1.5.2 lands, also extract the accumulation side into a small helper (e.g. an `insightsAccumulator` struct with named `AddDaily`/`AddModel`/`AddActivity`/`AddFinding` methods) — cheap now, considerably more expensive once three more epics' worth of inline map-mutation has piled into one function.

- [ ] **Story 1.1.6, Task 1.1.6b (`FindingsPanel`'s interim click-through)** — the task wires a finding card's action to the existing `onSessionClick` prop, but that prop's confirmed signature is `(session: SessionTokenSummary) => void` (`web-app/src/app/insights/SessionsTable.tsx:37`, used at `InsightsDashboard.tsx:247`) — it needs the full session object, not just the `session_id`/`conversation_id` a `WasteFinding` carries. The task doesn't specify how `FindingsPanel` resolves a finding's IDs to the matching `SessionTokenSummary` before calling `onSessionClick`.
  **Remediation**: pass `summary?.sessions` into `FindingsPanel` alongside `findings` so it can look up `finding.sessionId || finding.conversationId` against that array before invoking `onSessionClick`; state this explicitly in Task 1.1.6b/1.1.6c rather than leaving the lookup implicit.

## Nitpicks

- `FindingType`/`Severity`/`ActivityType` are specced as Go "string-enum consts," not a sealed sum type (interface + unexported marker method, per `type-driven-design`'s Technique 3) — lower priority than the (now-resolved) proto Blocker above since these values are only ever produced by the package's own detector/classifier functions today, but any future `switch` over these types elsewhere in the package won't get an exhaustiveness warning if a value is added later without also updating every switch.
- ADR-001/ADR-002's "review-convention, not compiler-enforced" caveats for `DollarImpact`/`WasteScore` non-summability and `cost_may_double_count` are honestly stated, but neither the ADRs nor the plan propose any mechanical enforcement (e.g., an `ast-grep`/gritql CI check forbidding `+`/`+=` on these types outside `findings.go`/`pricing.go`) — this repo already invests in ast-grep tooling elsewhere (`code-ast-grep`, `code-gritql` skills), so a cheap follow-up exists if the convention-only guardrail proves insufficient in practice.
- The three-state "Not evaluated" / "—" / numeric cell-text pattern (Story 1.3.3) and the two-state unpriced-badge pattern (existing Cost column, reused by Story 1.3.1's Cache ROI) are each specified ad hoc per column in `SessionsTable.tsx` rather than through one shared "missing value" formatting helper — minor, since ADR-003 already documents the precedent being followed column-by-column rather than introducing new drift.

## Lens Notes (not separately actionable — recorded for completeness)

- **SOLID/Clean Architecture**: `session/tokens` (domain) stays free of proto/RPC dependencies throughout; `server/services/insights_service.go` (adapter/service layer) is the only place domain→proto translation happens — this hexagonal boundary is respected consistently across all five epics. `TokenStoreReader.Subscribe()`'s signature change (Epic 1.5) is a breaking interface change, but verified via `grep -rn "\.Subscribe()" --include="*.go"` that `InsightsService` is the interface's only real caller (`capacity_monitor.go`, `quota_gate.go`, `backlog_service.go`, `session_summary_service.go` hold a `TokenStoreReader` but never call `.Subscribe()`), so the blast radius the plan assumes is accurate.
- **DDD**: no aggregate-boundary issues — this is a read-mostly reporting slice over an existing `ParseResult`/`SessionTokenSummary` shape; `DollarImpact`/`WasteScore` as newtypes and `CacheROI`'s `(value, ok bool)` / `WasteScore`'s `*WasteScore` "abstain rather than guess" returns are good Value-Object and illegal-states-unrepresentable design, better than what many of the reference tools this project cites actually do.
- **Build-vs-buy consistency (finding #11)**: verified against `research/build-vs-buy.md` — the plan's hand-written Go heuristic-function approach (no rules-engine library) matches that document's explicit "Not recommended" verdict on Grule/RuleGo/ZEN and its reasoning (externalized/user-authored rule capability this project's Non-Goals exclude). No inconsistency found.
- **PoEAA/pattern fit elsewhere**: Facade (existing `InsightsService`), Observer (channel-based `WatchInsights`), and Extract Function (`buildSessionSummary`, `SessionDetailContent`) are all appropriate reuses of already-established patterns in this codebase, not new pattern debt.
