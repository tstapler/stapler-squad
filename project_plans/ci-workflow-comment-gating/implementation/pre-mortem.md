# Pre-mortem: ci-workflow-comment-gating
**Date**: 2026-08-12

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The sticky comment is today the *only* visibility channel for these non-blocking checks (Lighthouse, all 3 benchmark jobs, coverage); if a gate's `isActionable`/`hasRegression` logic has a false-negative bug, the comment silently never posts, the job stays green (advisory-only by design), and nothing else surfaces the miss — the plan swaps "always-visible but noisy" for "silent when wrong," which is worse than the problem it fixes. | A real Lighthouse drop, benchmark regression, or coverage decline ships to `main` with no PR comment and a fully green Actions run; discovered later only via unrelated investigation, not via CI. | Require architecture-review's remediation (extract each gate's pure decision logic — `hasRegression`, `isActionable`, `previousCoveragePct` parsing — into small standalone modules with unit tests against literal captured fixtures) as a merge-blocking task in Phases 1–3, not an optional "Concern"; add it explicitly to plan.md's task list. | P1 |
| 2 | Plan.md's Risk Control section and Pattern Decisions table both claim Task "4.1.1d" adds a `concurrency:` block to `e2e-video.yml` resolving adversarial-review Blocker 1, but Phase 4's actual task list (Epic 4.1 / Story 4.1.1) only contains Tasks 4.1.1a–4.1.1c — no concurrency-block task exists anywhere in the concrete task breakdown. `e2e-video.yml` ships delete-on-clean (Task 4.1.1b) with zero race protection. | On a PR with two rapid pushes, a stale/slow run's late-finishing job deletes (or fails to show) the anomaly comment a newer run correctly posted or cleared — the exact silent-deletion race adversarial-review Blocker 1 already named, now unmitigated for this workflow specifically. | Add the missing concurrency-block task to Phase 4 explicitly (identical shape to Task 2.1.1e, scoped to `e2e-video.yml`'s PR number) before implementation starts; add a Phase 6 verification task that greps the merged diff for `concurrency:` in `e2e-video.yml` to catch a repeat of this doc/task-list mismatch. | P1 |
| 3 | ADR-002 sets go-tier1's advisory threshold at 20%, but the same ADR (citing `build.yml`) documents 15-25% *natural variance* for these benchmarks on shared runners — the threshold sits inside its own noise band, so a clean PR can randomly exceed 20% on some fraction of runs from jitter alone, producing an advisory comment that clears itself on the next push with no code change. | A developer reports "the benchmark bot flagged a regression that wasn't real" after re-running/re-pushing an unchanged PR and watching the comment disappear. | Before Phase 1 merges, empirically run go-tier1's benchmark 10-20x against unchanged code to measure the false-positive rate at the 20% cutoff; if non-trivial, either raise the threshold or require 2 consecutive regressed runs before commenting (debounce), rather than treating the 20% number as validated by inheritance from `build.yml`'s blocking gate alone. | P2 |
| 4 | `deleteComment`'s permission behavior under `pull-requests: write` is explicitly INFERRED (ADR-001), never exercised in this repo before, and gated on a single one-time manual dry-run (Task 6.1.1a) with no ongoing re-check; `continue-on-error: true` means a later 403 (token scope tightening, org policy change) fails silently and the job stays green. | Users notice a stale "regression detected" or "Lighthouse below 70" comment that never clears even though several subsequent pushes are visibly clean — discovered by manual inspection, not by any CI signal. | Add an explicit `core.warning()` (or equivalent loggable line) on `deleteComment` failure so it's greppable in Actions logs despite the job staying green; add a small periodic canary (e.g. monthly scheduled workflow that creates-then-deletes a throwaway comment) to catch permission drift proactively instead of relying on user-noticed staleness. | P2 |
| 5 | Go-tier1's regression gate is a single `grep -E` regex over raw `benchstat -delta-test=utest` text with zero unit-test coverage (confirmed by architecture-review: testable only via a live PR push) — pitfalls.md independently names a silently-matching-nothing regex gate as the single highest-risk failure mode in this whole item; a future benchstat version change, an unpinned tool version, or an unanticipated output edge case (boundary-exact delta, unusual unit suffix) can silently break the match with no error. | A deliberately-introduced regression during Phase 6's own scratch-PR validation (Task 6.1.1a) fails to produce a comment, or a real regression ships and is only found by someone reading raw benchstat text directly from Actions logs. | Pin benchstat's install to a specific version/commit in `benchmark.yml` (verify it isn't already floating on `@latest`); implement architecture-review's remediation — extract the regex/threshold logic into a small standalone module with unit tests against literal captured benchstat fixtures (including `~`-marked insignificant deltas, an exactly-at-threshold delta, and a missing-baseline case) — before Phase 1 merges. | P1 |
