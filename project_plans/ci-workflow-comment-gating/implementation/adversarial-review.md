# Adversarial Review: ci-workflow-comment-gating

**Date**: 2026-08-12
**Verdict**: BLOCKED → **RESOLVED 2026-08-12** (both blockers patched into plan.md during
Phase 4 validation; see checkboxes below and `pre-mortem.md` Failure #2 for the specific gap
this validation pass caught in the first patch attempt)

## Blockers

- [x] **RESOLVED** (patched 2026-08-12 during Phase 4 validation) — **Delete-on-clean races with out-of-order runs on 3 of 4 target workflows — a superseded run can silently delete a still-valid comment.** `ux-analysis.yml` got its `concurrency:` block (Task 2.1.1e) and `build.yml` got its recency guard (Task 3.1.1d) when this plan was first drafted, but `e2e-video.yml`'s fix was only ever *referenced* as "Task 4.1.1d" in this doc and in Pattern Decisions — the concrete task never existed in Phase 4's task list. Phase 4 validation's pre-mortem (Failure #2) caught the doc/task-list mismatch directly against the plan; Task 4.1.1d now exists for real, adding the same `concurrency:` block shape to `e2e-video.yml`. Task 6.1.2b (new) greps the merged diff for all three fixes so this class of gap can't silently recur. `ux-analysis.yml`, `build.yml`, and `e2e-video.yml` have **no `concurrency:` block** at all (verified: `grep -n concurrency .github/workflows/{ux-analysis,build,e2e-video}.yml` — zero hits outside an unrelated `benchmark-gate` job in `build.yml` that doesn't touch the comment step). `benchmark.yml`, by contrast, already has `concurrency: { group: baseline-push-${{ github.ref }}, cancel-in-progress: ... }`, which serializes/cancels stale runs on the same PR ref. Today, without `deleteComment`, an out-of-order race between two pushes on the same PR only risks a comment briefly showing slightly stale text (self-healing on the next push). ADR-001's `deleteComment` call changes the failure mode: if push #2 (which has a real regression/Axe failure/anomaly) finishes *before* push #1's now-stale, still-running job (which computed `isActionable=false` against older data), push #1's late-finishing run deletes the comment push #2 correctly created — making a genuinely current, actionable problem invisible with no error, no log a reviewer would see on the PR itself, and no re-trigger to fix it until the next push. This is exactly the "read a mutation back before claiming it happened" failure class: `deleteComment` returns 200 either way, so nothing signals the wrong comment was removed. Neither `plan.md`'s Risk Control section nor ADR-001's Consequences section mention this. — **Recommendation**: add a `concurrency: { group: <workflow>-comment-${{ github.event.pull_request.number }}, cancel-in-progress: true }` block to each of the 3 workflows (or reuse `benchmark.yml`'s existing group shape) before landing delete-on-clean, so a stale run is cancelled rather than allowed to race the comment API.

- [x] **RESOLVED** (ADR-002 amended 2026-08-12) — **The 20% advisory threshold is calibrated for a statistically-tested benchmark path and then silently transplanted onto two single-sample paths with no significance testing at all.** ADR-002 was amended to split the threshold: go-tier1 (significance-tested, `count=8` + `-delta-test=utest`) keeps 20%; `frontend-throughput`/`e2e-latency` (single-sample, no significance test) use an explicitly-unvalidated coarser "2x swing" placeholder instead (plan.md Tasks 1.2.1a/1.3.1a), documented in ADR-002's Consequences as a deliberate sensitivity/false-positive tradeoff pending a possible repeated-trials follow-up — not treated as a calibrated number. Pre-mortem.md Failure #3 (P2, not P1) separately flags that go-tier1's 20% itself sits inside its own cited 15-25% variance band and recommends an empirical false-positive check before Phase 1 merges — an residual, lower-severity risk, not a plan gap. ADR-002 justifies 20% by citing `build.yml`'s `benchmark-gate` job, which uses `count=5` repeated trials + `-delta-test=utest` for statistical significance, and go-tier1 (which uses `count=8` + the same `utest` flag — confirmed at `.github/workflows/benchmark.yml`'s "Run Tier 1 benchmarks" step). But `frontend-throughput` and `e2e-latency` (confirmed by reading their "Compare against baseline" steps, `.github/workflows/benchmark.yml` lines ~310-325 and ~524-539) each run **exactly one** Playwright measurement and diff it against **one** cached baseline value — no repeated sampling, no significance test, no variance/noise floor established anywhere in the file (`grep -in "varia\|noise\|flak"` over `benchmark.yml` returns nothing relevant to these two jobs). Browser-driven E2E measurements on shared GitHub runners are typically far noisier than a repeated, statistically-filtered Go micro-benchmark; nothing in the plan or ADR-002 establishes that a single Playwright sample's 20% swing is actually a "real regression" rather than runner jitter for these two jobs specifically. This is the core mechanism the whole feature depends on — get it wrong and either (a) the gate fires on noise, reproducing the exact spam problem this item exists to fix (undermining Kano "basic expectation"), or (b) real regressions under 20% go unflagged with no visibility at all now that the raw dump is gated away. ADR-002's "Alternatives Considered" only discusses a *different* threshold value for all three jobs together — it never separately questions whether the single-sample jobs need repeated trials, a wider threshold, or a different mechanism (e.g. `median-of-N`) before any percentage threshold is trustworthy. — **Recommendation**: before merging Phases 1.2/1.3, either (a) add repeated sampling to the frontend-throughput/e2e-latency Playwright runs so a significance test is possible, or (b) explicitly document an empirically-observed noise floor for these two jobs and pick a threshold above it, or (c) if 20% ships as a placeholder, say so explicitly in ADR-002 and treat it as unvalidated (same caveat already correctly applied to go-tier1's number in Unresolved Question #3, but that caveat currently reads as covering all three jobs when it only has evidence for one).

## Concerns

- [ ] **`e2e-video.yml`'s gate reduces visibility for partial-shard failures below today's baseline.** The job's matrix is a fixed `strategy.matrix.shard: [1, 2]` (confirmed at `.github/workflows/e2e-video.yml:61-62`), so "2 expected artifacts" is a known constant — but `videoAnomaly` is defined as `videoArtifacts.length === 0`, which only catches total failure. Today, a partial failure (e.g. shard 2 times out and never uploads, shard 1 succeeds) still produces a comment reading "**1 shard(s)** recorded feature flows," which at least surfaces the discrepancy to a human skimming the PR. After this plan lands, that same partial-failure case has `videoArtifacts.length === 1` (not 0), so `videoAnomaly` is `false` and **no comment posts at all** — the partial failure becomes silently invisible, which is a regression in visibility, not a neutral gating change. Requirements AC #5's "genuine anomaly" framing arguably should cover `videoArtifacts.length < matrix.shard.length` (a real, known constant), not just `=== 0`. — **Recommendation**: change the anomaly condition to compare against the known expected shard count (e.g. `videoArtifacts.length < 2`) rather than hardcoding the zero case, or explicitly note in the plan why partial failure is deliberately treated as non-actionable.

- [ ] **ADR-001's `deleteComment` dry-run gate is a manual, one-time human observation step (Task 6.1.1a), not a re-checkable mechanism** — if the dry run passes once during Phase 1's scratch-PR validation but a later GitHub API/permission change (e.g. a token scope tightening, an org policy change) causes `deleteComment` to start 403-ing, there is nothing in this plan that would catch the regression going forward; `continue-on-error: true` on the comment step means the failure is silently swallowed and the workflow shows green while stale comments silently stop being cleaned up. This is a lower-stakes version of Blocker #1 (silent failure of a mutation with no readback) but for a different cause (permission drift over time rather than a race). — **Recommendation**: at minimum, note this as an accepted residual risk in ADR-001 rather than leaving it implicitly resolved by a single historical dry run; consider a periodic canary or an explicit `core.warning()` log line on delete failure so a future investigator has something to grep for.

## Minors

- Story 3.1.1's illustrative example ("existing sticky comment body contains `...tested (42.0%)`") doesn't match `tools/coverage/feature-coverage.ts:47`'s actual output, which computes `Math.round(...)` and formats as a plain integer (e.g. `(42%)`, no decimal). Functionally harmless — the regex `\((\d+(?:\.\d+)?)%\)` matches both forms — but worth fixing for plan-reader accuracy.
- Phase 5's SHA-pinning drive-by is legitimate scope expansion beyond the requirements' stated ACs (touches 3 `uses:` lines with no functional connection to comment gating). It's correctly isolated as its own commit per the repo's collateral-debt convention, so this is a process note rather than a real objection.
- No automated test/lint exists anywhere in this repo for `github-script` blocks embedded in workflow YAML (confirmed by the plan's own Risk Control section, which relies entirely on live scratch-PR runs). This is a pre-existing repo-wide gap, not something this plan introduces, but it means every gate site in this plan (6 total) has zero regression protection once merged beyond human review of future diffs.
