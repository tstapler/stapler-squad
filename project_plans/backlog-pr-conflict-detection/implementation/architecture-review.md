# Architecture Review: backlog-pr-conflict-detection
**Date**: 2026-07-12
**Verdict**: CONCERNS

## Blockers

None.

## Concerns

- [ ] **Story 1.1.1 / Task 1.1.1d (Lens 2, Q6 — illegal states)** — `PRStatus{CIFailing, HasBlockingReviews, HasConflicts, FeedbackText}` stores the three booleans and their rendered text as independently-settable fields with no type-level link between them. The type allows constructing (or, via a future edit to `parsePRStatusPayload`, silently producing) `HasConflicts=true` with no `"## Merge conflict"` substring in `FeedbackText`, or vice versa — an illegal state the compiler does not reject. The plan's own answer to this risk is Story 1.3.1/1.3.3's hand-written substring assertions, i.e. tests guarding an invariant the type itself doesn't enforce, and only for the specific cases those tests cover. This is pre-existing debt (the same gap already exists for `CIFailing`/`HasBlockingReviews` today) — this project is the first time the codebase has *test coverage* for that gap, but it doesn't close it. **Remediation**: since `parsePRStatusPayload` is being introduced as a pure function boundary anyway, derive `FeedbackText` via an unexported `render()` method computed from small structured fields captured during evaluation (e.g. `failedChecks []string`, `blockingReview *reviewInfo`, `conflict *conflictInfo`) rather than accumulating into a `strings.Builder` interleaved with the bool-setting. `FeedbackText` becomes `status.render()` at the end — a derived value, always consistent by construction, rather than a field that can independently drift from the booleans. This is in scope for Task 1.1.1c/1.1.1d without expanding the file count or violating the Medium appetite — it's a reshape of the same function, not new production surface.

- [ ] **Story 2.1.2 / Task 2.1.2b (Lens 3, Q9 — untested acceptance criterion)** — the AC for Story 2.1.2 specifies an exact expected log string (`"... (CI=false, reviews=false, conflict=true)"`), but no task in Epic 2.2 verifies it. `log.InfoLog` is a swappable `*log.Logger` (see `log/log_test.go:186`, `NewDummyLogger`), so capturing and asserting on this line is feasible in this codebase, but the plan doesn't do it. The specific risk this leaves open: the log line is three positional `%v` args (`CI=%v, reviews=%v, conflict=%v`) mapped to `prStatus.CIFailing, prStatus.HasBlockingReviews, prStatus.HasConflicts` purely by argument order — nothing in the type system (or in the currently-planned tests) would catch a transposition (e.g. `conflict=%v` accidentally wired to `HasBlockingReviews`). Given this project's explicit purpose is hardening a previously-zero-coverage reconciliation loop, the one line whose entire job is operator-facing signal attribution should have a test. **Remediation**: add one assertion task to Story 2.2.2 (or a new small task) that captures `log.InfoLog` output during `TestReconcilePRPending_SpawnsFixSession_WhenHasConflictsTrue_Alone` and asserts the rendered line contains `conflict=true` (and, in the CI/review regression tests of Story 2.2.3, that it correctly reads `false` for the signals that didn't fire). Low cost, closes the one AC in this plan with no corresponding verification.

## Nitpicks

- **Lens 1, Q4 (testability seam)** — `newPRPendingChecker` is a mutable package-level `var`, consistent with the existing `timeNow` precedent (`session/instance_workspace.go:581`) and therefore not a new pattern, but it does mean tests using this seam cannot safely run under `t.Parallel()` without additional isolation (a second parallel test overriding the same var would race). The plan's `t.Cleanup`-based restore (Task 2.2.2a) handles serial correctness but doesn't call this out. Worth a one-line comment on the var or in the test file noting "not safe for `t.Parallel()`" so a future contributor doesn't add it and get a flaky/racy test.

- **Lens 2, Q5 (primitive obsession, endorsed but incomplete)** — the Pattern Decisions table's rejection of a `TriggerReason` enum is sound (the three signals are independently true, so a single-valued sum type would force a lossy choice). The plan doesn't consider the middle ground — a small `PRStatus.Signals` value object (still a set, not a sum type) wrapping the three bools as named fields with a `Reasons() []string` accessor — but given only three signals, all with identical downstream handling, and an explicit Medium appetite, extending the existing flat-bool shape is consistent with the codebase's established convention (`CIFailing`/`HasBlockingReviews` already flat bools) and correctly avoids introducing new abstraction weight for three fields. No action needed; noted for completeness since the plan's own reasoning didn't explicitly rule out this alternative.

- **Lens 2, Q7 (parse-at-boundary, partial application)** — `parsePRStatusPayload` correctly separates I/O (the `gh pr view` call, left in `GetPRStatus`) from parsing, which is the stated goal and is achieved: the function is directly unit-testable with raw JSON bytes and no `gh` fake is needed (confirmed — no `FakeGHRunner`-style helper exists in `session/git/*_test.go` today, unlike what `build-vs-buy.md` speculated). However the function itself still conflates three concerns — JSON unmarshalling, business-rule evaluation (what counts as a terminal CI failure, what counts as a blocking review, what counts as a conflict), and presentation (Markdown section rendering) — in one function body. Not a blocker: the stated testability goal is met, and splitting further would add indirection without new coverage. Flagged only because a future signal (the plan's own "go-git audit" follow-up, or a Phase-3 fourth trigger) will make this function progressively harder to table-test cleanly if the split isn't made before it grows further.

- **Lens 3, Q10 (interface stability)** — `prPendingChecker`'s two methods (`IsPRMerged(int) (bool, error)`, `GetPRStatus(int) (*git.PRStatus, error)`) mirror `*git.GitWorktree`'s real signatures exactly (verified: `worktree_git.go:459`, `worktree_git.go:338`), so no adapter/translation layer is needed and the interface is stable against the current implementation. The only way a consumer would need to change is if `GetPRStatus`'s return type itself changes shape (e.g. the Concern above, if `PRStatus` gains a `render()`-based accessor instead of a public `FeedbackText` field) — in which case `prPendingChecker`'s second method signature is unaffected either way since it returns `*git.PRStatus` by pointer, not by field. No finding.

## Confirmations (no finding, stated for completeness)

- **Lens 3, Q8** — `ReconcilePRPending` as Transaction Script over a flat `PRStatus` struct is the right level of complexity; nothing here warrants a Domain Model.
- **Lens 3, Q9 (core question)** — rejecting Strategy/Chain-of-Responsibility for the 3-way gate is correct per the design-patterns skill's own guidance ("Avoid when: 2–3 states, simple switch is clearer"); the concrete near-term cost isn't the gate shape itself but the untested log-line wiring flagged above.
- **Lens 3, Q11** — plan matches `build-vs-buy.md`'s recommendation exactly: extend the existing `gh`-CLI pipeline (add `mergeable`/`mergeStateStatus` to the existing `--json` flag list), no new library, no webhook. Confirmed yes.
- **Lens 1, Q2 (layer coupling)** — `prPendingChecker` is correctly defined in the consumer package (`session/backlog_lifecycle.go`), not in `session/git`, per `interface-pollution-checklist.md`; `*git.GitWorktree` satisfies it with zero changes to package `git`. No inappropriate dependency introduced.
