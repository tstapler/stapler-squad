# Pre-mortem: backlog-pr-conflict-detection
**Date**: 2026-07-12

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The only safety net against an autonomous rebase silently corrupting or dropping code is prose guidance inside `FeedbackText` (`--force-with-lease`, `.gitignore` suspicion, "leave markers and stop") — nothing verifies the spawned agent actually followed it, and a force-pushed rebase resets the PR's GitHub diff/review state, so a human reviewer is more likely to skim "looks rebased" than re-diff the full changeset from scratch. | A conflict-fix session force-pushes a rebased branch; the PR's diff view resets and prior review comments lose their anchor; the reviewer approves based on "CI green, rebased" without re-diffing, and a truncated `.gitignore` or silently-wrong hunk resolution merges — the exact incident (cli/cli-adjacent `.gitignore` corruption) that motivated this project, now automated instead of manual. | Add an automated post-rebase sanity gate before the fix session is allowed to push: e.g. a diff-size/line-count delta check against the pre-rebase branch for files matched by a small suspicious-file list (`.gitignore`, lockfiles, config), or require the fix session to post a summary diff stat as part of its final message so `render()`'s guidance has a verifiable artifact, not just an instruction. At minimum, document in plan.md that this PR type must never be auto-merged and must always land back in a human-reviewed state (not just `pr_pending`→closed). | P1 |
| 2 | `parsePRStatusPayload`'s table tests validate hand-authored JSON fixtures against assumed `gh pr view` field names/casing (`MERGEABLE`/`CONFLICTING`/`DIRTY`/etc.), but nothing in Phase 1 re-verifies those fixtures against a live `gh pr view --json mergeable,mergeStateStatus` call before merge — if the assumption is subtly wrong (casing, a renamed field, a `gh` version skew), every unit test passes while production `HasConflicts` stays permanently `false`. | Real conflicting PRs keep sitting in `pr_pending` indefinitely with no `HasConflicts=true` log line ever appearing, even though a manual `gh pr view --json mergeable,mergeStateStatus` on the same PR shows `CONFLICTING`/`DIRTY` — the original bug persists, just now with tests that claim it's fixed. | Add one task to Phase 1: before merging, run `gh pr view <a currently-known-conflicting or previously-conflicting PR#> --json mergeable,mergeStateStatus` once and paste the literal raw JSON into a fixture/comment, confirming the exact field names and enum casing this project assumes. This is a one-time verification task, not ongoing test infra. | P2 |
| 3 | `maxAutoReworkIterations` is shared across all three trigger types by construction (Pattern Decisions table) — a PR that already burned 2 attempts on `CIFailing`/`HasBlockingReviews` has only 1 (or 0) attempts left when a conflict later appears, and nothing in the log line or `PRStatus` distinguishes "gate stayed open because of a fresh trigger" from "gate is about to hit the shared cap for unrelated reasons." | An item logs `conflict=true` once, a fix session spawns and fails to fully resolve, and the item then silently stops getting further attempts and sits in `pr_pending` — operator has no way to tell from logs that CI/review fixes already spent most of the shared budget before the conflict ever showed up. | Add a log field for `workCount`/remaining attempts alongside the existing `CI=%v, reviews=%v, conflict=%v` line (e.g. `attempt=%d/%d`) so an operator can distinguish "capped out" from "gate never opened." Cheap addition to the same Task 2.1.2b log-line change already planned. | P2 |
| 4 | GitHub computes `mergeable`/`mergeStateStatus` asynchronously; after a fix session successfully rebases and pushes, `mergeStateStatus` can still transiently read `DIRTY` for one or more subsequent poll cycles before GitHub's recomputation catches up — this is the mirror image of the already-handled stale-`mergeable` case, but for the *resolved* side rather than the *unresolved* side, and the plan's belt-and-suspenders OR does not distinguish "still actually conflicting" from "GitHub hasn't recomputed yet." | The same item spawns 2-3 fix sessions in rapid succession for what was actually a single already-resolved conflict, hits `maxAutoReworkIterations` within one or two polling intervals, and lands permanently in `pr_pending` even though the first fix worked. | Debounce the conflict trigger: after a conflict-triggered spawn completes, skip re-evaluating `HasConflicts` for that item for at least one full polling interval, or require two consecutive `HasConflicts=true` polls before spawning again for the same item. Cheap guard to add to Epic 2.1's gate logic. | P2 |
| 5 | Observability Requirements explicitly rule out new metrics/alerting ("standard logging is sufficient at this scale"); if the new `gh pr view` call or `parsePRStatusPayload` starts erroring (auth expiry, rate limit, unexpected JSON shape from a future `gh` version), the failure is only visible in logs nobody is watching — silently reverting `ReconcilePRPending` to the exact "no signal, sits forever" failure mode this project exists to fix, now for all three triggers at once, not just conflicts. | `pr_pending` items across the board (CI, review, and conflict triggers) stop receiving any autonomous fix attempts; the only trace is a warning/error buried in `~/.stapler-squad/logs/stapler-squad.log` that nobody greps proactively; discovered weeks later when someone notices a stack of untouched `pr_pending` items. | Not a scope change to this project's Medium appetite, but record a follow-up: add a simple staleness check (e.g. a periodic log line or lightweight assertion if any `pr_pending` item has had zero `ReconcilePRPending` successful evaluations in N days) as a fast-follow, and confirm `GetPRStatus`'s error path already returns a non-nil error that surfaces as `log.WarningLog` (not swallowed) before shipping. | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — Addressed in plan.md: Story 1.2.1 now requires the fix session's guidance to instruct a mandatory `git diff --stat` callout (against the pre-rebase base) in its final report/PR description, flagging disproportionate `.gitignore`/config/lockfile deltas (Task 1.2.1a, tested by Task 1.3.1b). Epic 2.1's Goal and Story 2.1.2 now document that conflict-triggered fixes go through the identical `in_progress → review → review-gate → pr_pending` human-review cycle as CI/review fixes — no auto-merge shortcut exists for any trigger type. A residual gap (`EnablePRAutoMerge` not distinguishing rebase-reset diffs from incremental ones) is honestly recorded as a follow-up in Unresolved Questions rather than falsely resolved.
