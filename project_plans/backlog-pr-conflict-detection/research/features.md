# Research: Features — Similar "Detect a Stuck PR and Auto-Fix It" Systems

Agent 2 (Features), SDD research phase for `backlog-pr-conflict-detection`.

## 1. How the two existing triggers work today (exact mechanics)

### The gate: `ReconcilePRPending` — `session/backlog_lifecycle.go:530-585`

Polls every `pr_pending` backlog item (`FindPRPendingItems`, line 531) and for each:

1. **Merge check** (lines 546-560): `g.IsPRMerged(item.PrNumber)` → `gh pr view --json state --jq .state` (`session/git/worktree_git.go:459-472`). If merged, transitions to `done` and `continue`s — this branch never reaches the fix path.
2. **Status fetch** (lines 562-567): `g.GetPRStatus(item.PrNumber)` (`worktree_git.go:338-438`). A single `gh pr view --json statusCheckRollup,reviews,comments` call (line 345-346) — note `mergeable`/`mergeStateStatus` are **not** in the `--json` field list today.
3. **The gate itself** (line 568): `if !prStatus.CIFailing && !prStatus.HasBlockingReviews { continue }`. This is a pure OR — either signal alone is sufficient to proceed to step 4. There is no signal-specific branching after this point; both trigger the exact same downstream call.
4. **Spawn** (lines 572-583): builds one `fixCtx` string via `fmt.Sprintf("PR #%d (%s) needs fixes:\n\n%s", item.PrNumber, item.PrURL, prStatus.FeedbackText)` — `prStatus.FeedbackText` is a single combined string that **already interleaves CI-failure and review-changes-requested content** (built in `GetPRStatus`, `worktree_git.go:382-434`: failing-checks section written first if any, then `CHANGES_REQUESTED` review section(s), then general PR comments — see below). Then calls `fixSpawner.AutoReopenForPRFix(ctx, item.ID.String(), fixCtx)`.

**Key existing precedent for the "both signals present" edge case**: `PRStatus.FeedbackText` (`worktree_git.go:333`, built at 382-436) is already a single string that both signals write into, unconditionally, in a fixed order — CI failures section (409-415) before review section (417-426) before general comments (429-434). Neither signal short-circuits or overwrites the other. **This is the existing pattern the new conflict signal should follow**: append a third section rather than choosing one winner.

### `PRStatus` struct — `worktree_git.go:326-334`

```go
type PRStatus struct {
    CIFailing          bool
    HasBlockingReviews bool
    FeedbackText       string
}
```
Exactly two booleans plus one combined text blob. No field distinguishes *which* signal(s) fired once you're past the gate — the log line at `backlog_lifecycle.go:579-580` is the only place that records `CI=%v, reviews=%v` distinctly; `FeedbackText` itself is unlabeled as to origin beyond its own markdown headers.

### The spawn: `AutoReopenForPRFix` — `server/services/backlog_service_triage.go:435-513`

1. Loads item, asserts it's `pr_pending` (438-449) — **type-checked precondition**, not itself gated on which signal fired.
2. **Iteration cap** (451-465): counts `ItemSession`s with `Role == session.SessionRoleWork` across the item's entire history and compares to `maxAutoReworkIterations = 3` (`backlog_service_triage.go:37`). This counter is **shared** with `AutoReopenAfterFailedReview` (lines 389-405) — both count the same `SessionRoleWork` sessions for the item, not a per-trigger-type count. This directly answers the requirements.md open question about cap-sharing: **today, review-rework and PR-fix rework already share one undifferentiated cap**, so a conflict-triggered spawn reusing this same counting logic would naturally share it too, consistent with existing behavior (not a new decision so much as "the pattern already does this").
3. Transitions `pr_pending` → `in_progress` with an optimistic-concurrency precondition (`ExpectedUpdatedAt`, 467-475) — guards against a race with e.g. a concurrent manual reopen.
4. **Context injection is a temporary notes mutation** (477-501): prepends `[PR Fix context - PR #%d (%s)]\n%s` to `item.Notes`, calls `SpawnSessionFromItem` (which reads `item.Notes` into the prompt via `WriteBacklogContextFile` → `BuildSessionInitialPrompt`, `session/backlog_commands.go:118-140`), then **restores the original notes unconditionally** afterward (497-501), regardless of spawn success. This means the fix context is transient — it exists only in the spawned session's initial prompt snapshot, not persisted on the item.
5. On spawn failure, rolls back to `pr_pending` (505-509) "so the reconciler can retry" — i.e., failure to spawn is not itself a terminal state; the next poll cycle will re-attempt from step 2 of `ReconcilePRPending`, re-deriving `fixCtx` fresh from a new `GetPRStatus` call.

### Sibling pattern for comparison: `AutoReopenAfterFailedReview` — `backlog_service_triage.go:378-433`

Nearly identical shape (load → cap check → transition → spawn → rollback-on-failure) but has **no notes-injection step** — review feedback there comes from the review verdict itself, not a prepended context string. This confirms `AutoReopenForPRFix` is the correct integration point per requirements.md's constraint (reuse, don't build parallel), since it's already the one of the two spawn paths that carries an injectable free-text context blob.

## 2. Edge cases the two existing triggers don't obviously cover

**A. PR has both a conflict AND failing CI simultaneously.**
The existing `FeedbackText` pattern (worktree_git.go:382-436) already answers this by precedent: append, don't choose. A conflict section should be added to the same `sb.WriteString` sequence in `GetPRStatus`, and `ReconcilePRPending`'s gate (line 568) should become a three-way OR (`!CIFailing && !HasBlockingReviews && !HasConflict`). The log line at 579-580 should grow a third `%v` so operators can see all three signals per spawn, per the Observability Requirement in requirements.md. Section ordering matters for the fix agent's reading order: conflicts should likely come **first** in `FeedbackText`, since a PR that can't even be rebased makes CI/review feedback moot until the branch is mergeable again — the agent needs to resolve the conflict before it can even evaluate whether CI failures are still reproducing post-rebase.

**B. A conflict reappears immediately after a fix attempt (main moved again mid-fix).**
Nothing in the current architecture detects "did my fix actually work" versus "was overtaken by events." The flow is blind re-poll: `ReconcilePRPending` calls `GetPRStatus` fresh every cycle with no memory of the prior attempt's outcome beyond the `SessionRoleWork` count used for the cap. This is actually **fine and consistent with existing CI-failure behavior** — a flaky CI failure that recurs after a fix session pushes a new commit is handled identically today (poll again, spawn again if still failing, up to the cap). The conflict case is symmetric: if `mergeable` is still `CONFLICTING` on the next poll, it just spawns again (cap permitting). The one thing worth flagging for Phase 3: because rebase-based fixes force-push (implied by "resolve conflicts and push" in the fixCtx), a fast-moving `main` could cause **thrashing** — 3 attempts burned entirely on repeatedly falling behind rather than on genuine resolution difficulty. Nothing currently distinguishes "cap exhausted because resolution is hard" from "cap exhausted because main outpaced 3 rebase cycles." This is worth a log-line distinction (e.g. include the base-branch SHA seen at each attempt) but is out of scope for this project per requirements.md's "no new metrics/alerting infrastructure" NFR — a log detail, not new logic.

**C. Fix session can't push because its own conflict resolution is wrong.**
This is the requirements.md "Rabbit Hole" (conflict resolution confidence). Today, `PushChanges`/`PushBranch` (`worktree_git.go:40`, `242`) would simply fail/error if the local resolution is bad (e.g., unresolved markers left in files causing a bad commit, or a force-push rejected). That failure is invisible to `ReconcilePRPending` — the loop has no notion of "the last work session pushed a broken commit," it only re-reads `GetPRStatus` next cycle. If the bad resolution still results in `mergeable: MERGEABLE` (e.g., conflict markers got committed as literal text, which is syntactically not a git conflict anymore), **the reconciler would consider the conflict "fixed" and move on** — a false negative that's arguably worse than doing nothing, since it ships broken content silently. This is exactly the scenario the operator hit 3 times today with `.gitignore` corruption. The industry research (below) directly informs the mitigation: none of the surveyed tools attempt semantic hunk resolution: the safe design posture per the Rabbit Hole in requirements.md is to give the fix-session prompt explicit "if you can't confidently resolve a conflict, leave markers/stop and say so in your final message rather than guess" guidance — but *detecting* that outcome mechanically (vs. a clean resolution) is flagged as a Phase 3 open question, since nothing in the current `ReconcilePRPending`/`AutoReopenForPRFix` pipeline inspects session *output content*, only backlog item state transitions.

**D. Transient `mergeable: UNKNOWN`.**
Already called out in requirements.md's Rabbit Holes — GitHub computes this asynchronously. The existing pollers offer no precedent for handling it since none of the three pollers (`PRStatusPoller`, `WorktreePRPoller`, and `GetPRStatus` itself) currently request `mergeable` at all. The closest existing precedent for "treat an ambiguous poll result as non-actionable rather than erroring" is `ReconcilePRPending`'s own error handling at lines 549 and 565: both `IsPRMerged` and `GetPRStatus` errors just `log.DebugLog` and `continue` — i.e., **the existing convention for "can't get a clean signal this cycle" is silently skip and retry next poll**, not error loudly or treat ambiguity as the worst case. Treating `UNKNOWN` the same way (skip this cycle, don't treat as conflict) would be consistent with that convention.

## 3. Industry precedent: what happens when an auto-rebase produces a conflict a bot can't resolve

Researched: Mergify, Dependabot, Renovate, GitHub's native auto-merge/"Update branch."

- **Mergify** (merge queue): doesn't resolve conflicts, it *sequences around them* — when two queued PRs conflict, it merges one and dequeues the other with a notification. Visibility is configurable PR comments (`queue.comment`: `"all"` or `"outcomes"`) plus queue-membership labels. No retry cap specific to conflicts — a dequeued PR waits for a human to fix and re-queue. [docs.mergify.com/merge-queue/rules](https://docs.mergify.com/merge-queue/rules/)
- **Dependabot**: auto-rebases by regenerating its own PR from scratch (not textual conflict resolution), stops after 30 days of no merge or once a human pushes an extra commit to the branch. If regeneration can't cleanly apply, it just leaves the PR conflicted with GitHub's native "This branch has conflicts" banner — no dedicated bot comment. [docs.github.com/dependabot/managing-pull-requests](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/managing-pull-requests-for-dependency-updates)
- **Renovate**: sidesteps the problem structurally — its "rebase" reapplies its own previously-authored update commit on the new base rather than doing a real 3-way merge, which only works because it owns 100% of the diff. Docs explicitly state a user should never need to manually resolve Renovate conflicts, precisely because it never merges foreign (human-authored) changes. Does not generalize to a human/agent-authored PR conflicting with `main` — stapler-squad's problem is structurally the harder case none of these tools actually solve. [docs.renovatebot.com/updating-rebasing](https://docs.renovatebot.com/updating-rebasing/)
- **GitHub auto-merge / "Update branch"**: halts on a real conflict, no retry, no resolution attempt — shows the standard "can't automatically merge" banner. Third-party wrappers around it expose only two postures: fail a status check, or silently ignore. Auto-merge is also disabled outright if a non-write-permission user pushes or the base changes underneath it. [docs.github.com/automatically-merging-a-pull-request](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request)

**Synthesis**: none of the four tools attempt semantic conflict resolution (rewriting a genuinely conflicting hunk of someone else's content). They either regenerate a diff they themselves fully own (Dependabot, Renovate — not applicable here, since stapler-squad's PRs are agent-authored and the *base* moved, not a bot-owned diff), or they detect-and-escalate via a visible signal (comment/label/banner/status check) and wait for a human (Mergify, GitHub native). **There is no industry precedent for an automated system guessing at a 3-way merge of substantive conflicting content.** This directly supports the Rabbit Hole's proposed mitigation in requirements.md: the fix-session prompt should tell the agent to flag and stop on a non-trivial conflict rather than guess, since even the most mature ecosystem tools don't attempt this — they either avoid needing to (own the whole diff) or bail to a human.

## 4. Unstated user needs — what would make the operator trust an autonomous conflict-fixer

Context: the operator manually rebased 3 PRs today (#147, #148, #150's predecessor) specifically because of this gap, including resolving `.gitignore`-corruption conflicts by hand. That's the direct evidence base for what "trust" requires here — not a hypothetical.

- **A diff-shaped receipt, not just a status change.** The existing pattern already gives partial visibility: `AutoReopenForPRFix`'s notes-injection (`backlog_service_triage.go:479-489`) puts the fix context into the spawned session's prompt, and the observability requirement asks for a log line distinguishing which signal triggered the spawn. But neither surfaces *what actually changed* during conflict resolution specifically. Given the operator's actual pain point was `.gitignore` corruption — a case where "the merge succeeded" doesn't mean "the merge is correct" — the highest-trust addition (worth flagging for Phase 3 scope, likely beyond this project's stated scope of just detection+spawn) is: the fix session's own PR update/commit message should explicitly call out "resolved N conflicting files: [list]" so a human skimming PR history sees a receipt, the same way CI-failure fixes are implicitly self-documenting (the diff shows what got fixed to pass CI).
- **A clear distinction between "trivial rebase-forward" and "resolved a real conflict."** Per the industry synthesis above, no tool trusts an agent to silently resolve substantive conflicts — the operator's trust bar is likely the same: they'd trust an autonomous fix for a clean fast-forward-style rebase (no actual conflicting hunks, just replaying commits past a moved base) far more than one that rewrote a conflicting hunk. The requirements.md Rabbit Hole's "leave markers and stop" guidance is the mechanism for this, but the trust signal only lands if the *log/notes* clearly say which case occurred ("rebased cleanly, no conflicts" vs. "resolved N conflicting hunks — review recommended").
- **The same "it already gave up gracefully" reassurance the CI/review path already provides.** `AutoReopenForPRFix`'s cap-exhaustion behavior (`backlog_service_triage.go:462-465`) already leaves the item in `pr_pending` for manual action after 3 attempts, with an `InfoLog` line — this is a known, trusted failure mode for the existing two triggers. Extending the exact same behavior to conflicts (rather than, say, looping silently or auto-force-pushing without limit) is itself the primary trust-builder: the operator already trusts this fallback for CI/review, so the biggest risk to trust is if conflict-handling *deviates* from it (e.g., a more aggressive auto-push policy) rather than matching it.
