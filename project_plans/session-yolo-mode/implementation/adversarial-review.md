# Adversarial Review: session-yolo-mode

**Date**: 2026-08-06
**Verdict**: CONCERNS

## Blockers
- [ ] The plan (Risk Control, ADR-001 Consequences) accepts as harmless that a session can end up with both `--permission-mode bypassPermissions` (from pre-existing `AutoYes`, common via Profiles/Aliases/DirectoryRules presets) and `--dangerously-skip-permissions` (new `AutoApprove`) on the same Claude command line — but this is asserted, not verified. If the Claude CLI actually rejects or mis-parses that combination, every preset-created session (`auto_yes=true`) where a user also flips the new toggle fails to launch/restart, which is a directly reachable path once this ships. Recommendation: before writing code, run `claude --permission-mode bypassPermissions --dangerously-skip-permissions --help` (or equivalent) once and confirm the CLI accepts both flags without error; if it doesn't, `buildLaunchCommand` needs to skip appending the new flag when `AutoYes`/`PermissionMode` already produces an equivalent bypass.

## Concerns
- [ ] `SetAutoApprove` (Task 3.2.1) persists the new value *before* calling `Restart(true)`, mirroring `SwitchProgram`'s pattern exactly — but `SwitchProgram` has a named regression test for the resulting partial-failure state (`TestSwitchProgram_RestartError_PersistAlreadyRan` in `session/instance_program_test.go`), and `UpdateSession`'s handler (Task 3.3.1) returns a bare `CodeInternal` error with no session object when restart fails, after the persist already succeeded. The client has no way to reconcile — it sees only an error, while the DB/instance already reflect the new value, so the UI can silently desync until the next full reload. Recommendation: add the equivalent `TestSetAutoApprove_RestartError_PersistAlreadyRan` test, and have `UpdateSession` return the actual current session state (or at least a distinguishable error) so the client can reconcile rather than assume the write failed outright.
- [ ] Aider support hinges entirely on the `--yes-always` literal in `yoloFlagByAgent`, justified only by an in-code comment ("verified against aider.chat/docs") with no link and no automated coverage beyond a unit test asserting the map returns that exact string (`TestYoloFlagFor_should_ReturnYesAlways_When_ProgramIsAider`). Story 7.2's e2e spec only exercises Claude and an unsupported program — Aider is never actually launched end-to-end. If the flag name is wrong or diverges from the installed Aider version, every Aider auto-approve session fails to launch, silently defeating the "not hardcoded to one agent" success criterion for the one other agent named in scope. Recommendation: verify the flag against the actually-installed/bundled Aider version (not just docs), and add at least one integration test that spawns Aider with the flag and confirms it doesn't error, or explicitly document why that's infeasible in CI.
- [ ] The badge cannot represent two real "this session is unguarded" populations, both undermining the literal success criterion ("...so a user scanning the session list can immediately tell which sessions are unguarded"): (a) sessions where a user hand-typed `--dangerously-skip-permissions` into a custom command — the exact scenario the Problem Statement cites as the feature's motivation — get no badge while Active (since `session.autoApprove` stays `false`), and can show a permanently-stuck "pending" badge while Paused/Stopped, because `autoApprove` can never become `true` without an explicit toggle; (b) backlog automation's headless review sessions (`session/backlog_review.go:419`, `PermissionMode: PermissionModeBypassPermissions`), which the plan itself names as a known, unfixed gap. For (b) specifically, a cheap partial fix exists: `permissionMode` is already exposed on `Session` (`proto/session/v1/types.proto:1051` → `web-app/src/gen/session/v1/types_pb.ts:1962`), so the badge predicate could also check `session.permissionMode === "bypassPermissions"` at near-zero extra cost instead of deferring it to an unscheduled future change.
- [ ] No migration/backfill for existing sessions whose persisted `launchCommand` already contains a hand-typed bypass flag. The Migration Plan section only covers the ent column's schema-level default (`false` for every existing row); on rollout, the population of sessions this feature is meant to make visible starts out invisible until each is manually re-toggled. Worth at least a one-line acknowledgment alongside the Migration Plan (it's currently only implied by the badge-logic gap above, not stated as a migration concern).
- [ ] Frontend/backend agent-support checks disagree in scope: `isAutoApproveSupported` (frontend, Task 4.1.2) checks only the first whitespace token's basename (`program.split(/\s+/)[0]`), while `yoloFlagFor` (backend, Task 2.1.1) scans *every* token's basename, deliberately mirroring `isClaude`'s existing convention (confirmed in `session/instance_tmux.go:74-80`). A program string where the agent name appears in a later token would show the checkbox disabled (frontend) while the backend would still inject the flag if enabled another way — and the post-creation toggle path (Story 6.2's overflow menu item) has no `AutoApproveSupported` gate at all, so a user can flip it on for a program the create-time UI would have refused. Not mentioned anywhere in the plan.

## Minors
- `yoloFlagFor`'s any-token basename match can false-positive on an unrelated program whose *argument value* happens to equal `claude` or `aider` (e.g. `python train.py --model claude`), silently appending a permission-bypass flag to an unrelated command line. This mirrors the pre-existing, already-accepted `isClaude` classification pattern, but this is the first use of that pattern to inject a security-relevant flag rather than just pick an internal code branch — worth a code comment acknowledging the tradeoff explicitly rather than only citing it as "mirroring isClaude."
- The post-creation toggle ships two independent ways to disable auto-approve (clicking the session-card badge directly, and the overflow-menu item) for what requirements.md scopes as a single "explicit session action" — doubles the surface to keep in sync and test. Low risk since both only ever *disable* without confirmation (the safe direction), but it's scope beyond the literal ask.
- Unresolved Question 1 (MCP `create_session` not getting `auto_approve`) and the Risk Control backlog-automation callout describe the same underlying gap (headless/automation-created sessions have no path to the new field) in two different sections without cross-referencing each other — worth linking them so a future reader doesn't treat them as unrelated.
