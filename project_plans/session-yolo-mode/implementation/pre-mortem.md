# Pre-mortem: session-yolo-mode
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `auto_approve` and `auto_yes` ship as two visually adjacent but semantically distinct "skip prompts" checkboxes, and the badge is gated on `session.autoApprove` alone — so a session made unguarded via the pre-existing `auto_yes`/`PermissionMode` path (e.g. a Profile/Alias/DirectoryRules preset with `auto_yes=true`) shows no "⚡ Auto" badge at all, even though it is functionally running with `--permission-mode bypassPermissions`. | User scans the session list, sees no badge on a session that was created from an `auto_yes=true` preset, and assumes it prompts for every tool call — then discovers (via a surprising unattended file edit) that it does not. | Compute the badge condition from *observed effect*, not just the new field: `session.autoApprove || (session.launchCommand contains "--permission-mode bypassPermissions" or "--dangerously-skip-permissions")` — i.e. reuse the same `AUTO_APPROVE_FLAG_LITERALS`-style detection already planned for `hasPendingAutoApproveChange` as the *positive* badge condition too, not only the pending-diff condition. Document in plan.md that the badge's contract is "this session's launch command bypasses prompts," not "this session's `auto_approve` field is true." | P2 |
| 2 | `yoloFlagFor` silently no-ops for any agent not in `yoloFlagByAgent`, and only the **create-time** Omnibar checkbox is gated by `isAutoApproveSupported` (Task 4.1.2) — the **post-creation** overflow-menu toggle (Task 6.2.1) has no equivalent `AutoApproveSupported(program)` guard, so a user can enable auto-approve on an already-running session with an unsupported agent (e.g. Codex), triggering a full restart that appends no flag at all. | User enables "Auto-approve" from the session overflow menu on a non-Claude/non-Aider session; the session restarts (visible pane flicker/context loss) but tool-approval prompts continue exactly as before, with no error surfaced anywhere except a Debug-level log line the user will never see. | Add the same `AutoApproveSupported(program)`/`isAutoApproveSupported` gate to the overflow-menu toggle item (disable it, or show the same "Not supported for X" hint used in the Omnibar), and add Task acceptance criteria in plan.md exercising "toggle auto-approve on an unsupported-agent *existing* session via the overflow menu" — the current acceptance criteria in Story 6.2 only test the supported (`claude`) case. | P2 |
| 3 | `SetAutoApprove` restarts an `Active` session unconditionally on *both* enable and disable (`if i.Status == Active { return i.Restart(true) }`), but the plan's asymmetric-friction confirm dialog (Story 6.2) only warns before *enabling* — disabling fires `onToggleAutoApprove(session.id, false)` immediately with zero confirmation, even though it is exactly as disruptive (kills and respawns the tmux/agent process, discarding any in-flight conversational context that isn't part of tmux scrollback). | User clicks "Disable auto-approve" on a session mid-task to tighten safety, and the agent process is killed and respawned instead of just changing a flag for next time — the user loses whatever context the agent had built up in that turn, with no warning it was about to happen. | Split the two concerns explicitly in plan.md: the confirm dialog's copy is about *risk of enabling unguarded mode*, not about *the restart itself*. Add a second, generic "this will restart the session now" notice (or a lightweight toast) on **both** enable and disable when `session.status === Active`, independent of the auto-approve-specific risk copy — mirroring how `SwitchProgram` communicates its own restart-on-change behavior elsewhere in the UI, not `SetAutonomousMode`'s bare-flip precedent this plan borrowed the dialog shape from. | P1 |
| 4 | The steady-state badge (`session.autoApprove && !pendingAutoApproveChange`) trusts the persisted boolean directly for any `Active` session — `hasPendingAutoApproveChange` (Task 5.2.1) only ever evaluates for `Paused`/`Stopped` statuses. Combined with failure #2 (no support-gate on the post-creation toggle), an `Active` session with an unsupported agent and `auto_approve=true` displays "⚸ Auto" / "this session skips permission prompts" in its `aria-label` even though the flag was never injected into the launch command. | An unsupported-agent session shows the auto-approve badge (asserting to the user, in the badge's own `aria-label`, that it "skips permission prompts") while the agent is in fact still prompting normally — the badge becomes untrustworthy in the false-positive direction the first time this combination occurs, undermining the entire feature's stated purpose ("visually distinguishable... immediately tell which sessions are unguarded"). | Badge logic should also consult `AutoApproveSupported(session.program)` (already computed server-side; expose it on `Session` or compute client-side via the same agent-basename list) — render the badge only when `autoApprove && flagActuallyInjectable(program)`, and add an acceptance criterion in plan.md's Story 5.2 for "Active session, unsupported agent, autoApprove=true → no badge, or a distinct 'not applying' badge state" (a case the current acceptance criteria never enumerate). | P1 |
| 5 | Requirements.md and the plan's own Risk Control section name backlog automation's headless review sessions (`session/backlog_review.go:418-419`, which set `PermissionMode: PermissionModeBypassPermissions` directly) as permanently invisible to this feature's badge — by design, not oversight — yet requirements.md's Success Criteria promises the badge lets a user "immediately tell which sessions are unguarded" with no carve-out. | A backlog-automation review session runs unattended with prompts fully bypassed, makes an unwanted change, and the user — having trained themselves to trust "no badge = guarded" from using this feature elsewhere — never suspects that session as the unguarded one, because it never had the chance to show a badge. | Either (a) narrow the shipped Success Criteria/UI copy to state explicitly "auto-approve toggle and badge apply to user-created interactive sessions only; backlog automation sessions bypass prompts independently and are not represented here" (visible in-product, not just in a planning doc), or (b) extend the badge's detection (per fix #1/#4's "observed effect" approach) to also flag `PermissionMode == PermissionModeBypassPermissions` regardless of how it got set, which would cover backlog sessions for free since it's the same underlying signal. Track whichever is deferred as its own backlog item now, not just as an "Unresolved Question" that can be silently dropped. | P1 |

## P1 Items (address before implementation)
- [ ] #3 — Add a restart-is-imminent notice/confirmation to the **disable** path of the post-creation auto-approve toggle (Story 6.2), not just the enable path; the current asymmetric-friction dialog only guards against enabling unguarded mode, not against the unconditional process restart `SetAutoApprove` performs on any Active-session toggle in either direction.
- [ ] #4 — Gate the steady-state badge (Task 5.2.1) on `AutoApproveSupported(program)` in addition to `session.autoApprove`, and add an explicit acceptance criterion for "Active session + unsupported agent + autoApprove=true" so the badge cannot assert prompt-skipping is happening when `yoloFlagFor` actually returned `""`.
- [ ] #5 — Resolve Unresolved Question #3 (backlog review sessions' invisibility to the badge) as an explicit product decision before shipping — either scope the Success Criteria copy to exclude headless/automation sessions in-product, or extend badge detection to cover `PermissionMode == PermissionModeBypassPermissions` regardless of source, rather than leaving it as a silently-deferred footnote.
