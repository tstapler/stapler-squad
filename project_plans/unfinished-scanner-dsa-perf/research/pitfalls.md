## 1. Shared-cache correctness across linked worktrees

What is truly shared vs per-worktree (VERIFIED: gvr:1990-2045 `gitCommonDir`/per-worktree gitdir; `gogitstore/open.go:48-49`, `design/pluggable-gitstore.md:46-54`):
objects, packs, packed-refs, `refs/heads|tags|remotes`, config, `shallow` (commondir `shallow` file), `info/exclude`, `info/attributes` live in the common dir (git-wise). Per worktree: HEAD, index, `refs/bisect`, `refs/worktree`, `info/sparse-checkout`, and `config.worktree`. NOTE: the gogitstore design doc lists `shallow` as *per-worktree* storage via `WorktreeStorer` (`pluggable-gitstore.md:54,129`), i.e. go-git's `ShallowStorage` writes in the dotFs, not commondir. Whether that matches git semantics for linked worktrees is UNVERIFIED; treat shallow as per-worktree in this code base until checked.

Pitfalls to design against:
1. **Key boundary too wide: shallow vs full.** The current code keys `reachableSetCache` by worktree path *on purpose* (gvr:527-533): "a shallow clone and its full-clone origin (same base hash, different reachable set)" must not share a set. Moving to `(commondir, baseHash)` is safe only if the commondir is the same repository, since a shallow clone has its own commondir. Linked worktrees of one shallow repo share the truncated set, which is correct. Residual: a shallow repo deepened in place (`git fetch --deepen`) keeps its truncated set (known limit, gvr:1388-1389). A shared key makes this worse: one stale set now serves W worktrees. Mitigation: include a cheap shallow-file fingerprint (size+mtime of `<commondir>/shallow`, and per-worktree shallow storer content hash) in the key, or the commit-graph/packs fingerprint below. INFERRED.
2. **Key must be canonical.** `gitCommonDir` reads the `commondir` file and may return a non-cleaned/relative-joined path (gvr:2038-2043). Symlinked home dirs, `/private/var` vs `/var` on macOS, trailing slashes, and case-insensitive APFS will split or, worse, alias keys. Canonicalise with `filepath.EvalSymlinks`+`Clean` once per worktree open and memoise. Two distinct repos must never collide: use the resolved path, never a basename. INFERRED.
3. **Linked worktrees through the `gitdir`/`commondir` indirection can dangle.** If a worktree's `.git` file points at a pruned `worktrees/<name>` dir, `gitCommonDir` falls back (gvr:2013 comment). A fallback to `<path>/.git` creates a *different* key than the real repo; the cache then silently duplicates, not corrupts. Acceptable but should be counted (hit/miss metrics). INFERRED.
4. **What is NOT safe to share:** HEAD tree hash and `headTreeCache` (gvr:329-334) are per-HEAD, so key by tree hash (content-addressed, safe to share across worktrees *if* same objects store), not by worktree. The gitignore matcher is NOT safe repo-wide: it depends on the worktree's directory contents (`.gitignore` files in the checked-out tree), per-worktree `info/exclude` if present, and core.excludesFile (global). Only share the layer built from commondir `info/exclude` + global excludes; keep per-worktree `.gitignore` stacks per worktree. Existing tests: `gogit_vcs_reader_gitignore_invalidation_test.go`, `..._matchercache_test.go` encode current invalidation; extend them before sharing. INFERRED from structure; matcher internals not read in full.
5. **Stale after base moves / force-push.** A reachable set keyed by `(commondir, baseHash)` is immutable (content-addressed), so a moved base simply produces a new key; force-push cannot make an old key wrong. The pitfall is *unbounded accumulation of old keys* (see section 3) and the "baseHash-validated single entry per worktree" bound being lost (gvr:531-532 says a moved base replaces the entry, bounding to one per worktree). A repo-wide map needs its own bound: LRU by bytes. VERIFIED that the current bound is one entry per path.
6. **Stale after gc / repack / prune.** Hash-keyed immutable data stays correct after gc (objects are the same). Danger is only for caches of *positions*: pack indexes, mmap offsets, commit-graph files. `gogitstore` already handles this via `mmapwatch.go` fsnotify + `Registry.Prune` TTL (`gogitstore/registry.go:16-21, 236-290`, `mmapwatch.go:34-52`); if fsnotify is unavailable it only recovers on the 30 min TTL (`mmapwatch.go:52`). Any new commit-graph or parent-index cache keyed to file offsets must hook the same invalidation or be validated by (path, size, mtime, or trailer hash). INFERRED.
7. **Ref-derived cache keys.** `AheadBehind` caches by `worktreePath\x00base` with a head/base hash re-validation after TTL (gvr:1247-1290). That revalidation is the correct pattern; a repo-wide `(baseHash, mergeBase)`-keyed `behind` count (AGENTS.md lever) is immutable under the same reasoning, but the result is *capped* at `mergeBaseBFSLimit` (gvr:2189), so the key must include the cap, or a test lowering the cap (it is a var, gvr:2189) will see cross-test contamination. INFERRED.
8. **Missing objects.** `parentMemo.get` treats objects missing from shallow clone or pack as "skip" (gvr:2244). A shared parent memo that stores "missing" as an empty parent list would poison it after a later fetch. Never cache negative results, or cache them with a pack-set fingerprint. INFERRED.
9. **Alternates (`objects/info/alternates`, `clone --shared`) are not supported by gogitstore** (`gogitstore/storer.go:127-132`, `pluggable-gitstore.md:345,400`). Repos with alternates fall back to go-git's own filesystem storage in non-shared path, so keys for them must not be assumed to share an object store with siblings. VERIFIED (doc text); fallback behaviour UNVERIFIED.

## 2. Concurrency hazards: existing mitigations and gaps

Existing mitigations (VERIFIED):
- `sfDo` wraps singleflight with panic capture (gvr:760-763); four SF groups (gvr:544-552).
- `guardInvalidation` generation counter re-evicts a result computed across an `InvalidateWorktree` (gvr:1437-1449). The guard defers *after* the cache check to keep hits alloc-free (gvr:1255).
- `entry.mu` is held only around go-git access in `cachedReachableSet` (gvr:1399-1401), per AGENTS.md rules.
- `gogitstore` Registry never evicts a store with refcount>0 (`registry.go:246-249`).
- sync.Map values are stored by value and not mutated after Store (gvr:515); `reachableSet` map is returned shared and "must not be mutated" (gvr:1391), enforced only by comment.

Gaps / hazards to design against:
1. **Cache stampede in `cachedReachableSet` (gvr:1392-1407).** No singleflight: two callers with different SF keys (`CommitMessages` keys by `path\0base\0max`, gvr:1314, so different `max` values or concurrent worktrees of the same repo) both miss and both run the O(R) walk, each holding `entry.mu` in turn. With repo-wide keys this becomes the *main* hazard: W workers wake on one base move and all compute the same 50k-commit set. Fix: singleflight keyed `(commondir, baseHash)`; store the result once. INFERRED (code reading; no run).
2. **Lock held across a long walk in `CommitMessages` Phase 3 (gvr:1358-1376):** `entry.mu` is held for the whole `Log` walk including message decode. AGENTS.md says hold only around object access; the walk *is* object access, so it conforms, but it blocks every other op on that worktree (`AheadBehind` holds `entry.mu` through the whole BFS, gvr:1263-1264). With a repo-wide cache, do NOT serialise on a repo-wide mutex across the walk: the requirement "no scan may hold a repo-wide lock across a stat walk" (requirements.md:42) also implies not across a commit walk. Use the shared `SharedObjectStore` lock only for index lookups (it is already a coarse `mu`, `gogitstore/index.go:32,190`); verify its hold time under load. INFERRED.
3. **Per-worktree `entry.mu` does not protect shared state.** A shared repo-wide structure (parent memo, reachable-set LRU) needs its own synchronisation; the per-worktree `entry.mu` is a different lock for each worktree, so two worktrees' walks run in parallel against the shared maps. `parentMemo` is explicitly "not safe for concurrent use" (gvr:2194). Promoting it to repo-wide needs either per-repo `RWMutex`, a COW snapshot, or sharded maps; mixing the two lock domains risks lock-order inversion (entry.mu -> repo.mu vs. the reverse). Fix: define a lock order in AGENTS.md (entry.mu outer, shared-cache lock inner, never I/O while holding the inner lock). INFERRED.
4. **atomic.Pointer COW misuse.** If the shared parent memo is published as `atomic.Pointer[map]` snapshots: (a) racing writers each copy-on-write and lose each other's inserts (last writer wins) unless CAS-looped; (b) copying a growing 50k-entry map per insert is O(n^2); (c) readers must never mutate. Prefer one writer via singleflight and publish a finished immutable map once (the reachable set already follows that shape). Existing global `currentReader atomic.Pointer[GoGitVCSReader]` (gvr:670) is a simple pointer swap and fine. INFERRED.
5. **Torn read hazard in aheadBehind TTL refresh** (gvr:1284-1288): Load then Store of a modified copy is fine for value-typed entries (no shared mutation), VERIFIED. But Load-then-Store across two keys (a repo-wide key plus a per-worktree key) is not atomic; keep one key writer per computation.
6. **Invalidation granularity mismatch.** `InvalidateWorktree` deliberately leaves `reachableSetCache` alone (gvr:1409-1412). A repo-wide cache must define who evicts it: `ForgetWorktree` today drops the worktree's set (gvr:1453-1457); with sharing, forgetting one worktree must NOT drop the set other worktrees use. Use refcounts or pure LRU/TTL; do not tie eviction to a single worktree's lifecycle. `Scanner.invalidateRepo` already fans out per worktree (`scanner.go:1267-1279`) and reads `repoWorktrees` sync.Maps; note that fan-out is W calls each doing a `Range` over two sync.Maps with prefix matching (gvr:1418-1430), which is O(W x entries) per `.git` event. Prefix-scan eviction on sync.Map is itself a cost to watch. INFERRED.
7. **Goroutine leaks.** The fsnotify watcher and `mmapwatch.go` start goroutines; `gogitstore/closeall_hang_repro_test.go` exists, indicating a prior `CloseAll` hang (name only; contents not read, UNVERIFIED). New debounce/coalescing timers (`watcher.go`) must be stopped on `Close`; use `time.AfterFunc` with `Stop` and test with goleak-style checks (`golang-testing` skill). Avoid `time.Sleep` tests (notimesleeptest analyzer, section 7).
8. **Watcher-driven dirty tracking** (in scope): fsnotify can drop events on overflow (macOS FSEvents coalescing; Linux `IN_Q_OVERFLOW`). Required design: an overflow or error event forces full-walk fallback, plus a periodic full-walk safety net bounded by TTL. INFERRED from fsnotify behaviour; fsnotify's overflow error surface in `watcher.go` not checked.

## 3. Memory risks of repo-wide caches

1. **Size estimate.** `map[plumbing.Hash]bool` at 50k entries: key 20 B + bool, Go swiss/bucket overhead gives roughly 2-4 MB per set (gvr:2148-2151 comment says "a few MB"; INFERRED, not measured here). Per-worktree today = one set per worktree; repo-wide keyed by `(commondir, baseHash)` without eviction would accumulate one set per base-hash the repo ever sees (base moves with every merge to main), a monotonic leak. Needs budgeted eviction (requirements.md:52) with a bytes estimate, and ideally replace-on-newer-base for the same `(commondir, baseRef)`.
2. **A single global map under GC mark.** Large `map[Hash]bool` and `map[Hash][]Hash` have pointer-bearing values (slices) that the GC must scan on every cycle; the profile already shows GC mark at about 28% of CPU (requirements.md:12). Cheaper structures: a sorted `[]Hash` plus binary search or a `[]uint64` open-addressing table (pointer-free, so the GC skips scanning the backing array), a `map[Hash]struct{}` instead of `bool`, and parents stored as indices into a flat `[]Hash` instead of `[]Hash` slices per commit. INFERRED; validate with the alloc benchmark.
3. **`sync.Pool` retaining big buffers.** No `sync.Pool` in `session/unfinished` today (grep in the first call returned an error for the include glob; the later Grep-equivalent in the same command printed none; re-verify with Grep before relying on this: UNVERIFIED). If pooling decode buffers or `bytes.Buffer` for the header-only reader: a pool that holds buffers grown for one huge commit message (megabytes) retains them until two GC cycles pass. Cap pooled capacity (drop buffers over e.g. 64 KiB on Put), reset to len 0, and never pool anything the caller may retain (parent `[]Hash` returned to the memo must be a fresh copy, not a slice of the pooled buffer). Pool contents also drain at GC, so pools help allocs/op but not steady-state RSS.
4. **`weak`/`unique` pitfalls (Go 1.24+).** `unique.Handle[Hash]` interns forever until unreferenced, but its table is global and its lookup cost is a hash+map access, so it is slower than a plain `[20]byte` compare for 20-byte keys and saves memory only when many duplicates are held (hashes in parents lists duplicate commit keys, so some saving is plausible but measure). `weak.Pointer` caches need a nil check on every `Value()` and give no memory *budget* (eviction at GC's whim, which at load 100+ is unpredictable); they do not satisfy the "budgeted eviction" requirement. Prefer explicit LRU by estimated bytes. INFERRED.
5. **Memory-limit interaction with existing caches.** `blobCache` and `headTreeCache` live in `cachedRepo` and die with its eviction (gvr:324-340, 501-512; evictions counter exists), repo cache ceiling `repoCacheMaxEntries=100`, TTL 30 min (gvr:215-224). The `gogitstore` Registry has its own byte-ish budget and TTL (`registry.go:16-24`). A third, repo-wide cache layer must have its own budget or it silently adds to the total; expose bytes via `metrics.go` as required (requirements.md:81).
6. **Hit path must stay allocation-free** (requirements.md:37, AGENTS.md:52). Key construction via `fmt.Sprintf`/string concat (gvr:1247, 1314) allocates *before* the hit check; `CommitMessages` hit path currently does `fmt.Sprintf` on every call (gvr:1314), so it is NOT alloc-free despite the comment at gvr:1255/1321. A struct key `{commondir string; hash Hash; max int}` in a typed map avoids this. VERIFIED line 1314.

## 4. Benchmark validity at load above 100

1. **Wall-clock is meaningless.** At load 110-160 on the owner's machine, `ns/op` varies run to run by large factors from scheduler preemption. Gate on `allocs/op` and `B/op` (deterministic for deterministic input), plus CPU-time. Use `-benchtime=Nx` (fixed iteration counts, e.g. `-benchtime=200x`) rather than time-based so runs are comparable, and `-count>=8` with `benchstat` (CI already does count=8 and benchstat with alpha 0.05: `.github/workflows/benchmark.yml:92-117`, VERIFIED). Local runs while loaded should compare only `allocs/op`, `B/op`.
2. **CPU-time, not wall-time.** `testing.B` reports wall time; capture user+sys via `getrusage` (`syscall.Getrusage`) in a custom `b.ReportMetric` ("cpu-ns/op") so preemption does not inflate it. Even CPU-time inflates under load from cache and SMT contention (INFERRED); treat as +-20 percent noise, use for large wins only.
3. **GC distorts allocation benchmarks.** `B/op` and `allocs/op` are accurate; timing includes GC assist cost billed to whichever goroutine allocates (requirements.md:8). Set `GOGC=off` or `debug.SetGCPercent(-1)` in micro-benchmarks that must isolate algorithm cost, but run one variant with GC on to see the real effect, since the whole point is reducing GC pressure.
4. **Tier 1 gate coverage.** The bench regex in `benchmark.yml:98` includes `BenchmarkDiffShortstat`, `BenchmarkCountCommitsNotAncestorOf`, `BenchmarkTrackedFileStat`, `BenchmarkUntrackedWalk`, `BenchmarkWorktreeIsDirty_FastVsGoGit`, but nothing that matches `findMergeBase`/`reachableSet`/multi-worktree sharing. New benchmarks must be added to that regex or they will not be gated. The comparison step only writes to the step summary (`|| true`, no failure threshold: `benchmark.yml:112-117`), so it is *advisory*, not a gate; "benchmarks in CI Tier 1" (requirements.md:53) means a regression test (decode-count assertion) is the real gate. VERIFIED.
5. **Existing precedent for deterministic regression tests:** `gogit_vcs_reader_mergebase_test.go` counts decodes (scales with distance, not depth). Prefer decode-count/`testing.AllocsPerRun` assertions over time thresholds. A multi-worktree test must count decodes across at least 3 worktrees of one repo (requirements.md:24).
6. **Pyroscope window comparability.** The 30-min merged profile is dominated by workload phase (a scan burst after a restart, user activity, a build storm) so two windows are not the same workload. Compare same wall-clock-of-day windows or, better, normalise by scanner work units (scans completed, from `metrics.go`) so "CPU per scan" is compared, not raw share. Share-of-process CPU (39.3 percent to 15 percent target) moves if *other* components change, so also report absolute CPU-seconds. Restart resets caches: compare only after a full warm period (repo cache TTL 30 min, gvr:224; Registry 30 min). INFERRED.
7. **Live-binary-may-predate-branch.** Baseline came from a process up about 24h; branch commits `c46c69faf` and `150168a4c` (fsnotify filter, debounce) may not be in it (requirements.md:11, 89). Check before re-profiling: compare the binary's build info (`go version -m ~/.stapler-squad/.../stapler-squad` or the `/actuator` build/vcs.revision field if exposed; UNVERIFIED which endpoint) against `git merge-base --is-ancestor <commit> <vcs.revision>` done via go-git, or just compare the revision to `git log`. Do this read-only; do not run `make install-service` to find out (it restarts the live service and kills tmux unless `--tmux-keep-server`, CLAUDE.md).
8. **Fresh baseline needs a manual instance**, not the live one: `:62871` with a private tmux socket per CLAUDE.md, with a fixed set of repos/worktrees so before/after run on the same corpus.

## 5. Fork maintenance burden

VERIFIED facts: `go.mod:231` `replace github.com/go-git/go-git/v5 => github.com/tstapler/go-git/v5 v5.19.3-ssq.1`; `require` pinned at upstream v5.19.3 (`go.mod:30`). Fork tag `v5.19.3-ssq.1` "carries no source patches" (`docs/how-to/roll-back-go-git-fork.md` Verified section). ADR-002: replace directive, tags `vX.Y.Z-ssq.N`, rollback = delete the line, Dependabot will not bump through a replace, rebase cadence manual (runbook story 6.3, ADR-002 Consequences). ADR files present: ADR-001 (fork v5 not v6), 002, 003 (meaning of no-git and permanent lock compatibility), 004 (per-operation backend seam and cohort switch), 005, 006 (repo capability preflight): `project_plans/go-git-fork-full-git-replacement/decisions/`. ADR-003 to 006 bodies were NOT read in this pass; their constraints on this work are UNVERIFIED (read before the plan phase, especially 003 and 004).

Pitfalls:
1. **Rollback breaks if the app calls a new fork-only symbol.** The rollback doc says a fork tag adding an exported symbol the app calls, *without a build-tag fallback to stock go-git*, fails rollback and must not be adopted (`roll-back-go-git-fork.md`, "Fork tags must stay rollbackable"). So a header-only commit-parents reader added to the fork cannot simply be called from `session/unfinished`; it needs a wrapper with a build-tagged or runtime fallback to the stock `object.GetCommit` path (e.g. a small interface in this package satisfied by fork function or stock implementation). This is the largest design constraint on the fork lever and contradicts "just add a function". VERIFIED text; design implication INFERRED.
2. **Additive-only is not enough for upstream rebases.** A new function in `plumbing/object` is cheap to rebase, but a patch that touches the shared `Commit.Decode` path or `storage/filesystem` object reading conflicts on every upstream merge. Keep patches in new files (`commit_header.go`), no edits to existing functions; touching `filesystem.ObjectStorage` is the highest-conflict area (also what `gogitstore` replaces, so prefer solving it in `gogitstore`, in this repo, over the fork).
3. **Each patch = tag + fork CI + replace bump + `make ci`** (AGENTS.md:21-26; requirements.md:31). That is a wall-clock blocker per patch; batch fork changes into the fewest tags. Patch + app change cannot land atomically; bump `replace` in the same PR as the first call site, never earlier (a dangling replace to a missing tag breaks `go mod verify`/builds for everyone).
4. **Type identity** is preserved only because the module path is unchanged (ADR-002); do not export new types from the fork across package boundaries used by other importers. INFERRED.
5. **Rebase cadence:** upstream v5 is maintenance-mode (INFERRED; ADR-001 chose v5 not v6, rationale not re-read). Rebase risk is low-frequency, but security fixes upstream need a manual rebase; record the upstream base version in each tag's notes.
6. **Do not upstream** (out of scope, requirements.md:59), so patches need not be generalised; but keep them clean enough to rebase.

## 6. Known go-git bugs and limits relevant here

(Web not browsed; sources are repo docs and local code.)
1. **Commit decode cost**: `object.DecodeCommit` is 51.9 percent of alloc_space (requirements.md:13); it parses the full message and gpgsig (continuation handling `continuationCont` 9.2 percent). A header-only reader is the identified fix. VERIFIED (requirements text).
2. **Commit-graph:** the fork ships `plumbing/format/commitgraph` (v1) and `commitgraph/v2` (VERIFIED: `~/go/pkg/mod/github.com/tstapler/go-git/v5@v5.19.3-ssq.1/plumbing/format/commitgraph/` listing shows `commitgraph.go`, `file.go`, `memory.go`, `encoder.go`, `v2/`). A grep of `storage/filesystem/*.go` for `commitgraph` in that module version returned no matches, so the filesystem storer does not appear to serve a commit-graph index (INFERRED: one empty grep; verify before planning). Consequence: the `object` package's commit-graph-aware walkers (`NewCommitNodeIndex`) get a memory index only if the caller builds it; shipping it means reading `.git/objects/info/commit-graph` ourselves, handling v1/v2 (chain files under `commit-graphs/`), and handling a *stale* graph (commits newer than the file are absent: must fall back to decode). Whether the owner's repos have a commit-graph is UNVERIFIED (open question, requirements.md:88): `git gc`/fetch with `fetch.writeCommitGraph` produce it, but nothing guarantees it; a fallback path is mandatory, and keeping an in-memory parent index built once per `(commondir, packfile-set)` may beat file parsing.
3. **Shallow:** `parentMemo.get` tolerates missing parents from shallow clones (gvr:2244); `repo.Log` on shallow repos stops at the boundary; `reachableSet` stays truncated if deepened in place (gvr:1388). `shallow` file is handled by `ShallowStorage` per worktree (`pluggable-gitstore.md:54,103`; the doc notes unexported `dir` fields forcing wrappers).
4. **Alternates not supported by gogitstore** (`storer.go:127-132`): falls back; do not assume sharing.
5. **mmap pack-index pins and truncation:** `gogitstore/mmapwatch.go:111-143` documents a leak if "pins still held (leaked Entries() iterator?)" at eviction; mmap tests `mmap_truncation_test.go`, `trunc_fault_signal_test.go`, `crash_subprocess_test.go` imply SIGBUS risk when a pack is truncated/replaced under an mapping (names only; behaviour UNVERIFIED). A repo-wide cache that holds hashes (not mmap-backed slices) avoids this; do not hold byte slices from mmap past the pin.
6. **go-git `Log` order/limit semantics:** `repo.Log` walks in committer-time order (priority), not BFS; lockstep BFS in `findMergeBase` differs, so merge-base results can differ from git's for criss-cross merges (existing behaviour; any replacement needs a parity corpus per requirements.md:27, 66). INFERRED.
7. **Diff algorithm parity:** current shortstat is LCS DP guarded by `maxLCSLines` (AGENTS.md:41). Myers gives *a* minimal edit script but insertions/deletions counts for a given pair can differ from LCS ties only if the LCS is non-unique in size: minimal edit distance equals `n+m-2*LCS`, so counts of ins+del are equal; the split into ins vs del is also fixed (`del = n - LCS`, `ins = m - LCS`). So counts are parity-safe if both are exact; INFERRED from the identity, run the oracle (`walkers_oracle_test.go` exists) to confirm. Heuristics (patience/histogram, or Myers with cutoff) are NOT parity-safe.

## Cross-cutting design-against checklist

1. Singleflight every repo-wide compute; key `(canonical commondir, hash, cap)`; never cache negatives/missing-object results.
2. Byte-budgeted LRU for repo-wide caches with refcount-free eviction (do not drop on one worktree's `ForgetWorktree`); metrics for hit/miss/evict/bytes.
3. Pointer-free compact structures for large sets/parent indexes; cap any pooled buffer capacity.
4. Header-only reader behind an interface with stock-go-git fallback (rollback requirement), plus a mandatory fallback when commit-graph is absent or stale.
5. Parity corpus (ahead/behind, shortstat counts) and decode/alloc-count regression tests, not wall-clock thresholds; add new benchmarks to the Tier 1 regex.
6. Fix the baseline problem first: confirm the live binary's revision before comparing Pyroscope windows; compare per-scan CPU, not share.
7. Define lock order and keep `entry.mu` out of the shared-cache critical sections; no I/O under any repo-wide lock.
