# ADR-001: Isolate per-repo derived state behind a `repostate` seam, attached to the shared object store through a generic extension slot

**Status**: Accepted (plan phase, 2026-10-15; amended in repair iterations 1-3 and the Phase 4 patch) · **Plan**: `../implementation/plan.md` Epic 1.1, Story 2.1.2

## Context
Derived data (reachable set, ahead/behind, messages, HEAD tree map, parent memo) is keyed by worktree path, so W worktrees of one repo recompute identical commit-derived data (`gogit_vcs_reader.go:1247,1314,1393,333`; research/architecture.md §0). The object layer is already shared by `gogitstore.Registry`, keyed by `EvalSymlinks`+`Clean` of the common dir (`gogitstore/open.go:118`, `registry.go:159`). `gitCommonDir` (`G:2021`) does not resolve symlinks. `gogit_vcs_reader.go` is 2,311 lines (hotspot). `AheadBehind` holds a non-reentrant `entry.mu` across its whole closure (`G:1263`, VERIFIED).

## Decision
1. **Package and purity.** `session/unfinished/repostate` (sibling of `gogitstore`) holds only immutable or epoch-keyed commit-derived data; no import of `unfinished` or `gogitstore`, no `*git.Repository`; commits are read through an injected `ParentsSource`, pressure through an injected `PressureFunc`, time through an injected clock. Mutable, event-driven scanner state (`RefSnapshot`, `ScanSignature`, `DirtyGen`, `FullWalkFallback`) lives in `unfinished` (`scanstate.go`).
2. **Lifecycle rides the store.** `RepoState` is attached to the `SharedObjectStore` through a generic opaque slot (`Extension(newFn) Extension`, `Extension{Bytes() int64; Close()}`), so refcount, idle TTL, LRU trim and budget accounting are the store's own, and there is no second refcount to leak or diverge (architecture-review C1). `gogitstore` stays ignorant of scanner types. The key is the one the store already holds (`CommonDirKey()`); `openRepoEntry` must not recompute it via `resolveGitFilesystems`/`gitCommonDir`.
3. **Lock chain (normative; amended by ADR-009).** `entry.mu` is taken in phase 1 of `AheadBehind`/`CommitMessages` (ref resolution + `ShallowStamp` stat) and released before any graph work. repostate has **no mutex on its read and fill paths** (ADR-009: chunked arena, per-row atomic state, generation pointer). The only repostate-side locks are leaves: `xsync.Map` per-bucket locks (held while a non-blocking compute function runs), `singleflight.Group`'s internal mutex, and, until Story 2.3.1, the `repoCache` LRU mutex; each is held only to publish, never across a storer read, never while taking `entry.mu`. `SharedObjectStore.mu` (`gogitstore/store.go:83`, held across file IO by design) is the innermost leaf, reached only through `SharedObjectStore.EncodedObject`. The `GraphSource` adapter takes **no** `entry.mu`. Chain: `entry.mu` (phase 1, released) .. repostate leaves .. `SharedObjectStore.mu`; no edge points back up. The legacy (flag-off) path keeps today's behaviour (phase 2 under `entry.mu`).
   - **One sanctioned `entry.mu` -> repostate edge (architecture-review N2).** `resolveHeadTreeHashes` runs inside `diffShortstatUncached` while holding the caller's own `entry.mu` (`headTreeCache` is `entry.mu`-guarded, `G:333`). The tree-map lookup (Story 3.1.1) may therefore be called with `entry.mu` held. It cannot cycle: a `TreeMap` build or flight leader takes no `entry.mu` and reads objects only through `SharedObjectStore.EncodedObject`, so the chain `entry.mu -> repostate leaf -> SharedObjectStore.mu` still has no edge pointing back up. The phase-1/phase-2 "released before graph work" rule applies to the commit graph and its products, not to this tree-map call.
   - **Callback contract (architecture-review N3).** `Extension.Close()` and `Extension.Bytes()` run under `Registry.mu` (`pruneLocked`, `approxBytesPerStore`) and must not call back into the registry, the store, `ExtensionsDo` or any repostate path that takes a lock; they only read atomics / sum sizes and release memory. `ExtensionsDo` callbacks run outside `Registry.mu` (Story 1.1.1). A test with a deadline-bounded call (channel `select`, no sleep) registers an extension whose `Close`/`Bytes` call `Registry.RefCounts()` and asserts the harness detects it (negative test) and that `RepoState` itself does not.
4. Call sites migrate one at a time behind flags; `ForgetWorktree` never evicts shared data. Disposition for the hotspot: pure-move split first (Story 0.0.2, no logic change), then isolate via the seam, then delete the path-keyed legacy caches and flag branches after soak (Story 5.3.1). The lockstep walk is **not** deleted: it stays in production as `plainWalk`, the permanent fallback for `ErrGraphFull`, `ErrPressure`, a closed storer and an over-cap restart (Phase 4 patch, pre-mortem P1 #2).

## Alternatives rejected
- Scanner types or algorithms inside `gogitstore.SharedObjectStore`: couples object storage to scanner code (the generic slot gives the lifecycle without it).
- A separate `RepoState` registry with its own refcount: duplicates `Registry.acquire`'s lifecycle and the duplicate-open-loser release logic.
- Refactor `gogit_vcs_reader.go` first as a rewrite: stalls the work; only the behaviour-neutral move is done first.
- Keep `gitCommonDir` as key: splits one repo into two caches on macOS (`/var` vs `/private/var`).
- Adapter that locks `entry.mu` around each storer read from inside the walk: certain self-deadlock once `AheadBehind` holds it (review B2/B7).

## Consequences
New lifecycle to keep within the memory budget (ADR-007); a written lock chain enforced by a deadlock test (Story 2.1.2); one more package; one new extension API on `gogitstore`; path-keyed legacy caches retained until Story 5.3.1 (`plainWalk` retained permanently).
