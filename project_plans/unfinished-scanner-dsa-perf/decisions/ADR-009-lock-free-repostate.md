# ADR-009: Lock-free read and fill paths for `repostate` (chunked arena, per-row atomic state, generation pointer; CLOCK and atomic bitset words conditional)

**Status**: Accepted (owner request, repair iteration 2; accepted in the Phase 4 patch so the dependent ADR-001/002/007 amendments and Stories 2.1.x are no longer provisional; stories remain scheduling-gated by row SG2 and the conditional pieces by row SG6 of the plan's Task 0.1.1d table) · **Plan**: Stories 2.1.1, 2.1.2, 2.1.4, 2.2.1, Epic 2.3, Task 0.1.1e · **Amends**: ADR-001 item 3, ADR-002 items 1 and 3, ADR-007

## Context
- ADR-002 as first written published rows as "immutable snapshots" over shared slice backing arrays while lazy fill wrote `Pending -> Filled` and `Truncated -> Pending` below the published length. Readers holding an old snapshot read the same memory, so that is a Go data race (architecture-review N1, VERIFIED by reading the design, not by running code). The owner asked for a mechanism, not a patch.
- Evidence on lock contention (INFERRED, relayed by the coordinator, not re-run by the repair worker): live mutex profile at process age 1h56m shows the top own-package mutex delay in `session/tmux` (`runGatedWith` 31.7% cum, `listSessionsRaw` 17.5%, `DoesSessionExist` 12.8%, `GetPanePID` 11.8%) and **no `session/unfinished` frame in the top 14**. Lock-free is therefore justified by (a) the lazy-fill correctness problem and (b) removing writer-mutex serialization on cold fills, **not** by measured scanner lock contention. Task 0.1.1e captures mutex and block profiles on the S1 control binary so this is measured, not assumed.
- Constraints that stay: pointer-free hot structures (GC mark is about 28% of CPU, requirements.md:12), no storer read under any repostate lock, go-git only.

## Decision
1. **Chunked append-only arena (replaces snapshots).** Rows live in fixed-size segments (initially 4,096 rows) that are never reallocated or moved. `Options.MaxGraphCommits` fixes the segment-directory length at construction (`[]atomic.Pointer[segment]`, allocated once), so the directory never grows. A row id comes from a bounded CAS increment on a 64-bit `next` that checks the cap first (`ErrGraphFull` at the cap; no overshoot, no wrap); a missing segment is installed by CAS from nil (the loser discards its copy). A segment is pointer-free: `hash [N]plumbing.Hash`, `parents [N][2]uint32`, `state [N]atomic.Uint32`. Octopus parents beyond two go to a second pointer-free chunked side arena addressed by index from `parents[i][1]`. Readers hold no snapshot: they read `state` first and the payload only if the state says it is published.
2. **Per-row atomic state with CAS transitions.** `state` packs a 2-bit state (`Pending`, `Filling`, `Filled`, `Truncated`) and a 30-bit `stampOrd` (an ordinal of the `ShallowStamp` the row was observed under). Transitions: `Pending -> Filling` (CAS; the winner owns the payload), `Filling -> Filled` (store, after the parents payload is written), `Filling -> Truncated(stampOrd)` (store, payload unwritten), `Truncated(old) -> Filling` (CAS, only when `old != currentStampOrd`). **The payload is written exactly once per row per epoch, by the claim holder, before the publishing store; it is never rewritten after `Filled`.** Readers read the payload only after an atomic load observes `Filled`. This relies on `sync/atomic` operations being sequentially consistent and creating happens-before edges in the Go memory model; the race detector models them, so a violation shows up in `-race` runs. A stamp change is one `stampOrd` bump, not a bulk write: a `Truncated` row with a stale ordinal is treated as `Pending` lazily at the next read. This removes the `Truncated -> Pending` mass reset entirely. **Rollback**: the claim holder installs a `defer` at claim time that stores `Filling -> Pending` on error, cancellation, panic or closed storer (the payload is unpublished, so no reader saw it), so a failed fill never strands a row in `Filling`; waiters that see `Pending` claim it themselves. **Stamp ordinal**: phase 1 captures the ordinal before any object read and installs it in one atomic step; a `Truncated` row records the ordinal captured at its own walk's phase 1, never one read at publish time (a mid-walk deepen must not stamp a pre-deepen observation as current). A `Filled` row's parent list is a property of the commit object and never changes on a deepen.
3. **Idempotent fill, lost CAS wastes work but cannot corrupt.** The same commit always yields the same parents, so if the claim is lost the loser may (a) wait a bounded number of `runtime.Gosched` rounds and re-read, then (b) read the parents itself without publishing. Every lost claim increments `fill_lost_cas_total`; a loser that then decodes locally also increments `fill_lost_decode_total`, and each stale-`Truncated` re-probe increments `reprobe_total`. A waiting loser decodes nothing, so `DecodeCount == distinct + fill_lost_cas_total` would fail spuriously; the gate (G2b) is `distinct <= DecodeCount <= distinct + fill_lost_decode_total + reprobe_total`, not an exact count under a racing schedule. Lock-free here is **not wait-free**: a claim holder that is descheduled delays only waiters' bounded spin, never correctness.
   **Decision on the waiter (triad patch, pre-mortem P2 #9)**: keep the bounded `runtime.Gosched` spin, then decode locally without publishing. A per-row wait channel is not adopted up front because a row is pointer-free by design (item 1) and a per-row channel or `sync.Cond` adds a pointer and an allocation per filling row, against the GC-mark goal. **Measured switch trigger**: Story 2.1.4's contended benchmark, case (b) with the claim held for 10x the spin bound, and the Story 5.2.1 soak, both report `fill_lost_decode_total / fill_lost_cas_total`; a ratio above **0.2** switches to a per-row wait whose channel lives in a side table of in-flight rows only (created by the claim holder, closed on publish or rollback, waiters bounded by a context deadline), keeping rows pointer-free. The numeric 0.2 is the pre-mortem's proposed bound, not a measured one; the owner may adjust it.
4. **hash -> id on `xsync.Map`.** Reads (`Load`) are lock-free. Writes take a per-bucket lock inside the library, held while the compute function runs (VERIFIED `xsync/v4@v4.5.0/map.go`, doc comments on `Compute`/`LoadOrCompute`: "locks a hash table bucket while the compute function executes"). So "lock-free" is claimed for readers and for the absence of any repo-wide writer mutex, not for the library's bucket locks. The compute function passed to `LoadOrCompute` does only `next.Add`, the hash-column store and `state.Store(Pending)`; it never calls the storer, never takes another lock, never blocks. Per-commit fill dedup is the `Filling` claim of item 2. Per-`(RepoKey, hash)` or per-key `singleflight` stays for the **expensive** products (ahead/behind, reach, message list), whose results are worth coalescing; `singleflight.Group`'s internal mutex is a leaf.
5. **Generation pointer replaces "epoch bump plus purge".** `RepoState` holds `gen atomic.Pointer[generation]`; a `generation` bundles `{graph arena, directory, id-relative caches (reach, tree maps), epoch}`. Every operation loads `gen` once and uses that generation throughout, so a reader never mixes ids from two assignments. Dropping the graph (pressure, over-cap rebuild) is one CAS installing a fresh generation, which is the atomic step ADR-007 required. The `GraphEpoch` field stays in id-relative **keys** as defense in depth for any value that escapes the generation (for example a returned bitset). ABA is avoided because slots are never reused within an epoch (ids are monotonic) and the old generation is never mutated after replacement.
6. **Reachable sets.** A completed `ReachBitset` is immutable after publication and stored behind `atomic.Pointer` in its cache entry; an incremental rebuild copies the ancestor's words and then sets bits, never mutating a published set. A single flight builder owns its bitset exclusively until it publishes, so **plain words are sufficient and faster**; atomic `Or`/CAS words (Story 2.3.2) are needed only if a parallel builder is adopted, and that story is conditional on a measured benefit.
7. **Byte-budget eviction as CLOCK (conditional, Story 2.3.1).** Entries carry an atomic reference bit; a hand (`atomic.Uint64`) sweeps the entry ring, clearing bits and evicting an entry whose bit is already clear by CAS-ing its state to `Evicted`. No list under a mutex. Removing an evicted key from the `xsync` index is compare-and-delete (never deletes a re-inserted fresh entry), bytes are subtracted exactly once by the winner of the `Evicted` CAS, and the hand's CAS acts on the per-entry state, not the ring slot. Until Story 2.3.1 lands (or if its gate closes), Story 1.1.2's mutex-guarded LRU stays; that mutex is a leaf and is never held across a storer read.
8. **Reclamation is the Go garbage collector's job.** There are no hazard pointers, epoch-based reclamation or free lists for graph rows: a reader holding a pointer to an evicted entry or a replaced generation keeps it alive, and reads valid memory. That is the property the non-GC lock-free literature spends hazard pointers on; here it is free, and must not be re-implemented.
9. **What deliberately stays locked:** `gogitstore.Registry.mu` (refcounts, prune) and `SharedObjectStore.mu` (file IO). They guard IO and lifetimes, run off the hot read path, and are not contended per the mutex profile above. Also `entry.mu` in phase 1 of `AheadBehind`/`CommitMessages` (ADR-001).

## Scope rule (profile-driven)
- **Unconditional once the S1 profile gate for the graph stories passes** (Story 2.1.1 gate): the arena, per-row CAS state, generation pointer and immutable-after-publish bitsets, because they fix the lazy-fill race.
- **Conditional on Task 0.1.1e**: CLOCK eviction and atomic-word bitsets. Entry gate (proposed fraction, owner may adjust): scanner frames (`session/unfinished/...`, including `gogitstore` and `repostate` callers) account for **>= 5%** of total mutex-profile delay on the S1 control under the Story 0.1.5 workload; below that, both stay unbuilt and the mutex-guarded LRU remains. The measured fraction is recorded in `baseline.md`.

## Caveats the design must respect (lock-free literature)
Lock-free is not wait-free and not automatically faster. CAS retries and cache-line bouncing under contention can lose to a short mutex. False sharing: hot atomics (`next`, the CLOCK hand, `stampOrd`, stats counters) are padded to a cache line (`cpu.CacheLinePad` from `golang.org/x/sys/cpu`, `go.mod:61`; Apple silicon lines are 128 bytes). Correctness is established by linearizability-style history checks against a sequential reference, `-race`, and a randomized-interleaving stress test (Story 2.1.4), not by reasoning alone. The contended benchmark against a mutex reference is advisory (wall-clock is meaningless at load 110-160); `cas_retries_total` and `fill_lost_cas_total` are exported so contention is visible.

## Alternatives rejected
- Snapshots over shared slices with a writer mutex (N1: data race on in-place state change). Copy-on-write overlay merged at compaction (more moving parts than per-row atomics for no read-path gain). Per-row `atomic.Uint64` packing state and parents (cannot carry two 32-bit parent ids plus a 2-bit state plus stamp ordinal without shrinking the id space; the state-then-payload protocol keeps rows at 4+8 B plus the hash column). Hazard pointers / EBR (GC makes them unnecessary). A lock-free LRU list (CLOCK gets the same eviction quality with one atomic bit per entry).

## Consequences
Graph read and cold-fill paths have no mutex of ours; the library's bucket locks remain on first insert only. A new concurrency test story (2.1.4) gates the arena. If the S1 profile shows the commit-walk bucket is already negligible, the graph stories (and with them most of this ADR) are deferred by their scheduling gate, and the N1 race never ships.

## Addendum 2026-10-16: item 3 amended, claim losers wait on a striped wake channel (Story 2.1.2)
**Measured trigger fired.** With the bounded spin of 8 `Gosched` rounds, three racing `AheadBehind` calls on one repo (G2b racing test, 2,517 distinct rows) produced `fill_lost_cas_total = 4823` and `fill_lost_decode_total = 4791`, so `DecodeCount = 7308` against `distinct = 2517`: a ratio of 0.99, far above the 0.2 threshold, which defeated the W-fold sharing the graph exists for (a loser gave up after microseconds, long before a storer read finishes). The wait is now `Generation.awaitPublish`: the loser registers one of 64 striped channels, re-checks the row state, and blocks; the holder stores the new state and then closes its stripe's channel (`wake`, after `Filled`, `Truncated` and rollback). Registering before the re-check and storing before the wake means one of the two orders always wins, so no wakeup is missed; a stripe wake is spurious for other rows, which re-check and wait again. The wait is bounded by `Options.ClaimWait` (default 200 ms) and `ctx`; on timeout the loser decodes locally without publishing, exactly as before, so a stalled holder delays but never blocks correctness. The claim itself stays a lock-free CAS; the wait is the only blocking step. After the change the same racing test reports `DecodeCount = distinct = 2517`, `fill_lost_cas_total = 2327`, `fill_lost_decode_total = 0`. Tests: `TestFill_ShouldDecodeOnce_WhenLosersWaitForSlowHolder`, `TestFill_ShouldDecodeLocally_WhenHolderOutlastsClaimWait`, and the G2b gates in `aheadbehind_gate_test.go`.
Other implementation notes: the arena gained a `when` column (committer unix seconds, 8 B/row, written before the publishing store) because paint-down-to-common is the only walk and orders by time; there is still no generation column. `Generation.Bytes()` reports 0 for an empty generation so `ClearCache` returns a RepoState to zero bytes. Scratch for the walks lives in a bounded lock-free pool (`Swap` to take, `CompareAndSwap` into an empty slot to return), not a mutex-guarded free list.

## Addendum: cancellation and singleflight

`AheadBehind`, `CommitMessages` and `AheadBehindResolved` take a `ctx` from the scan worker down to the repostate walks.
Singleflight shares the leader's computation, so one caller's cancel must not fail or poison the others
(`repostate.FlightCtx`, used by `RepoCache` and the reader's `sfDoCtx`):

- every caller waits on its own ctx; a follower leaves at once when it ends;
- a leader's fn runs under the leader's ctx and the leader waits for a started fn (it uses the caller's Walk, which the caller closes on return);
- a follower whose ctx is live and whose leader was cancelled retries as leader rather than inherit the context error;
- a failed fn never reaches `Put`, so a cancelled flight caches nothing.

`Walk.read` samples ctx every 64 visits and returns the bare ctx error, never `ErrFallback` (a fallback would rerun the walk on the legacy path).
Rejected: a detached flight context refcounted by waiters. It would keep shared work alive for the others but needs the same bookkeeping at both flight layers and a cancel path into each walk; the retry wastes one walk only when a leader is cancelled. The legacy plain walks and `HasUncommitted`/`DiffShortstat` still ignore ctx.
