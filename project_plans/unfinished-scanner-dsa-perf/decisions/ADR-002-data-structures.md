# ADR-002: Interned `uint32` commit ids (lazily filled, epoch-scoped), `[]uint64` bitsets, in-process graph as baseline, commit-graph file optional

**Status**: Accepted (plan phase; amended in repair iterations 1-3 and the Phase 4 patch; items 1, 3 and 4 superseded in mechanism by ADR-009) · **Plan**: Epics 2.1, 2.2, Story 5.2.3

## Context
Reachable sets today are `map[plumbing.Hash]bool` (~40-50 B/commit, INFERRED, per worktree); parent memo is `map[Hash][]Hash` rebuilt per miss (`G:2195`); GC mark is ~28% of CPU (requirements.md:12). Only 1 of 10 owner repos has a commit-graph (v1, written Oct 8, so stale) and go-git never loads it (VERIFIED research/stack.md §2). No roaring/bitset dependency exists in `go.mod`; `xsync/v4` is a direct dependency (`go.mod:40`).

## Decision
1. Intern commit hashes to `CommitID uint32` per `RepoState`. Rows live in a **chunked, append-only, pointer-free arena** (fixed-size segments, never reallocated; ADR-009 item 1): `hash`, parents `[2]uint32` (+ octopus side arena) and an atomic `state` word (`Pending | Filling | Filled | Truncated` plus a stamp ordinal) with CAS transitions. There are no snapshots: a reader reads `state` first and the payload only after observing `Filled`. The hash->id index is `xsync.Map` (never a plain map beside lock-free readers).
2. **The graph is filled lazily, per visited commit**, by the same lockstep/count walks that need it — cold cost is O(visited), not O(R) per restart. A fill that would exceed `Options.MaxGraphCommits`, or that runs under severe pressure, returns an error and the caller runs the legacy walk for that call. No generation column in the baseline (parents-first order cannot be guaranteed lazily); `PaintDownBest` computes it on demand.
3. **Id stability invariant**: ids are stable for the life of one `GraphEpoch` and are never reused within it. A row's payload is written exactly once per epoch, by the goroutine that won the `Pending -> Filling` (or stale-`Truncated -> Filling`) CAS, before the publishing `state` store; it is never rewritten after `Filled` (this is the mechanism that resolves architecture-review N1: no in-place payload write is ever visible to a reader that did not observe `Filled`). A `ShallowStamp` change bumps one ordinal; stale `Truncated` rows are re-probed lazily at read time instead of being bulk-reset. `GraphEpoch` is bumped whenever the graph is dropped or rebuilt (pressure, over-cap rebuild; each is a `generation` swap). There is no delta segment and no compaction in the baseline design (the earlier "delta compaction that would renumber" wording is removed: rows are never renumbered within an epoch, and only Story 5.2.3's optional commit-graph base segment, if ever built, adds a read-only base). **Every id-relative product key carries the epoch** (`ReachBitset`: `{repo, base, cap, shallow, epoch}`; `TreeMap` via `PathEpoch`). Hash-keyed products (ahead/behind, behind, message list, per-commit first-line memo) survive an epoch change. Dropping the graph and its id-relative products is one atomic step: a CAS installing a fresh `generation` object that bundles the arena, directory and id-relative caches (ADR-009 item 5); readers load the generation pointer once per operation.
4. `ShallowStamp` (`<commondir>/shallow` fingerprint, repo-level) is part of every product key whose result depends on parent availability (reach, ahead/behind, behind, message list). A shallow boundary is a `Truncated` row recorded with its stamp, never a negative cache entry for the absent hash; a stamp change is one `stampOrd` bump, and a `Truncated` row whose recorded ordinal is stale reads as `Pending` and is re-probed lazily by CAS (`Truncated(old) -> Filling`); **no bulk reset of rows is ever written** (ADR-009 item 2, which supersedes the earlier "resets `Truncated` rows to `Pending`" mechanism that wrote below the published length). Reach bitsets are built incrementally from an ancestor set only when that set is not cap-truncated; otherwise rebuilt from scratch.
5. Reachable sets are `[]uint64` bitsets (~6.1 KB at R=50,000). No roaring, no `bits-and-blooms/bitset`.
6. The in-process graph is the baseline and must work with no commit-graph file. git's commit-graph is an optional zero-heap base segment (Story 5.2.3), built only if the Phase-5 gate shows decode cost still dominates.
7. The `PathID` interner is budgeted and epoch-scoped (`PathEpoch`); over budget it is rebuilt and tree maps are purged with it.
8. The per-commit message memo uses a full decode once per commit (the first line needs the message), not the header-only parents reader; the "parents reader" stories do not cover messages.
9. The index's GC cost is gated (Gate G7: bytes per row; objects-per-row ceiling in Story 2.1.3, which cites this item as "ADR-002 item 9"; an earlier plan text cited item 4 by mistake). If the ceiling is exceeded, replace the `xsync.Map` hash->id index by an **immutable sorted `[]Hash` base plus binary search, with the `xsync.Map` kept only for the delta of rows interned since the base was built** (a rebuild folds the delta into a fresh base published by pointer swap, never renumbering ids). A plain sorted array alone cannot be appended to lock-free, so a bare switch would reintroduce a writer mutex or the snapshot race of architecture-review N1; the delta-plus-base shape keeps readers lock-free (ADR-009 item 4).

## Alternatives rejected
roaring (new dep, no gain at 50k, license UNVERIFIED); commit-graph-first (unreliable presence/staleness; writing into `.git` is a side effect); `unique`/`weak` handles (no byte budget, unpredictable eviction at load > 100); eager ancestor closure per Burst (O(R) per repo per restart, over-cap truncation leaves tips unindexed); copy-on-publish hash map (O(n^2)).

## Consequences
We own ~250 lines of bitset/arena/CAS code, covered by fuzz tests against the map reference, an evict-and-reingest-in-different-order property test, and the linearizability/stress suite of Story 2.1.4 under `-race`. Revisit roaring only if a repo exceeds ~2M interned commits (INFERRED; outside stated scale, requirements.md:42).
