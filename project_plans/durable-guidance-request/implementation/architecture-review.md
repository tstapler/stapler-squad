# Architecture Review: durable-guidance-request
**Date**: 2026-09-12
**Verdict**: CONCERNS

## Constitution Violations
`docs/adr/ADR-000-architecture-constitution.md` does not exist in this repo — no constitution check applies. (Verified: `test -f` on that path returned MISSING.)

## Blockers

- [x] **Task 2.1.2a / AC6 / Pattern Decisions "Ownership check" row** — RESOLVED: plan.md adds new Task 2.1.2a-pre ("Extract `resolveItemLink`'s ownership logic into a package-neutral helper," plan.md:266-270), which introduces `session.ResolveItemLink(ctx, storage, callerUUID, itemID) (ItemSessionSummary, ItemLinkError)` (new file `session/item_link.go`) carrying the storage lookup, not-found-vs-permission-denied disambiguation, and remediation text verbatim out of `resolveItemLink`. `resolveItemLink` (`server/mcp/tools_backlog.go`) is rewritten to a thin adapter over this helper (plan.md:269), and the rewritten Task 2.1.2a (plan.md:272-273) has the new RPC handler in `server/services/guidance_request_service.go` call the SAME `session.ResolveItemLink` helper, translating `ItemLinkError` into a `connect.Error` — explicitly "not a hand-rolled reimplementation." This is a genuine structural extraction (named type `ItemLinkError`, named function `session.ResolveItemLink`, both call sites reduced to thin protocol-specific adapters), matching the remediation asked for — one implementation, not two. — "Reuse `resolveItemLink` verbatim" is not what the task actually does; it re-implements the ownership check. The task text says: *"the RPC path doesn't go through the MCP handler package, so extract or call a shared ownership-check function — reuse `h.storage.GetItemSessionBySessionAndItem` directly, matching `resolveItemLink`'s own logic"*. That is duplication, not reuse: `resolveItemLink` (`server/mcp/tools_backlog.go:585-617`, verified) contains non-trivial logic beyond the raw storage call — disambiguating `ErrNotFound` on the link query from a genuinely-missing item (a second `GetBacklogItem` call), and building context-specific remediation text (including the "linked to a different item" branch at line 611). AC6's own acceptance criterion requires the RPC path be "rejected identically to how `resolveItemLink` rejects every other mutating backlog MCP tool" — but Task 2.1.2a's plan is to hand-roll a second copy of this disambiguation in `server/services/guidance_request_service.go`, in a different package, translated to `connect.Error` instead of `mcpgo.CallToolResult`. Two independently-maintained copies of the same subtle ownership/error-shape logic will drift — this is the exact "uniform-looking API, forked implementation" anti-pattern ADR-002 explicitly rejected for the event-delivery path (its Rationale section: *"Design (A)'s 'uniform-looking API, forked implementation' is exactly the shape... warn against"*). The plan applies the correct principle to one axis of the design and violates it on another.
  - **Remediation**: extract the pure ownership-resolution logic (storage lookup + not-found-vs-permission-denied disambiguation + remediation-text construction) out of `resolveItemLink` into a package-neutral helper — e.g. `session.ResolveItemLink(ctx, storage, callerUUID, itemID) (ItemSessionSummary, ItemLinkError)` returning a small sum-typed result (`ItemLinkOK` / `ItemLinkNotFound` / `ItemLinkPermissionDenied`, each carrying the remediation text) with zero MCP or ConnectRPC dependency. Keep `resolveItemLink` in `server/mcp` as a thin adapter that calls the shared helper and wraps the result in `mcpgo.CallToolResult`; add an equally thin adapter in `server/services/guidance_request_service.go` that calls the same helper and wraps the result in `connect.Error`. This gives both paths the literal-same rejection logic (AC6 as actually written) instead of a parallel reimplementation, at the cost of one small extraction — not a new interface, not new abstraction layers.

- [x] **ADR-001 edge design / Phase 8 Self-Heal Sweep — hard-delete cascade silently destroys durable records, contradicting AC1's durability guarantee.** — RESOLVED: Task 1.1.1b (plan.md:165) now explicitly says "Do NOT add `.Annotations(entsql.OnDelete(entsql.Cascade))` on this edge" and leaves the `item_id` FK to go stale on hard delete instead. Task 8.1.1a's self-heal sweep (plan.md:557) now treats BOTH "item found but archived" and "`GetBacklogItem` returns `ErrNotFound`" (hard-deleted) as cancel-worthy for the `backlog-item` scope, calling `CancelGuidanceRequest` in either case, and plan.md:564 adds a dedicated test case for the hard-delete path. ADR-001's Consequences section (line 24) now documents the decision and rationale ("the `item_id` edge deliberately does NOT cascade-delete... The FK is left to go stale on a hard delete instead, and the self-heal sweep... treats 'item not found' as cancel-worthy, same as 'item archived'"). All three remediation asks (schema, sweep, ADR) are satisfied. `BacklogItem` supports genuine hard deletion, not just archival — confirmed via `session/ent_repository_backlog.go:1306` (`DeleteBacklogItem`) and `:1353` (`r.client.BacklogItem.DeleteOneID(parsedID).Exec(ctx)`), with a dedicated test (`TestDeleteBacklogItem_should_publishRemovedNotUpdated_When_ExistingItemIsDeleted`, `session/ent_repository_backlog_events_test.go:455`). The plan's `item` edge from `GuidanceRequest` back to `BacklogItem` uses `OnDelete(Cascade)` (Task 1.1.1b), matching the existing convention (`backlog_item.go:199-227` and others use the same annotation) — but for `BacklogItem`, that convention was established for genuinely-owned child rows (stages, transitions) where cascade-on-delete is correct. For `GuidanceRequest`, a hard delete of the parent item will silently `DELETE` any pending *or even already-answered-but-not-yet-delivered* `GuidanceRequest` row with **no trace, no cancellation event, no audit** — directly contradicting AC1's stated bar ("no answer is ever silently lost, only its live-delivery timing is delayed", Story 3.2.2) and pitfalls.md's own "never an in-memory dedup map that resets on restart" durability philosophy applied one layer up. Phase 8's Self-Heal Sweep (Task 8.1.1a) cannot catch this: it iterates open `GuidanceRequest` rows and calls `GetBacklogItem` to check for `archived` status — but a cascade-deleted `GuidanceRequest` row is already gone by the time the sweep runs; there is nothing left to reconcile. This is precisely the orphaning risk the review brief asked to check the Self-Heal Sweep's coverage against, and it does not cover it.
  - **Remediation**: do not cascade-delete `GuidanceRequest` from `BacklogItem`'s hard-delete path. Either (a) drop `OnDelete(Cascade)` on this specific edge and let the FK go stale (the row already tolerates a stale/orphaned `item_id` conceptually, since `session`/`standalone` scopes have no item at all) — the existing self-heal sweep's archived-check can be extended to also treat "item not found" as cancel-worthy, same code path; or (b) if cascade-delete is kept for referential-integrity reasons, add an explicit pre-delete step in `DeleteBacklogItem` that resolves+cancels any open `GuidanceRequest` for the item before the delete executes, so the cancellation is recorded durably (a row with `cancelled_at` set) rather than the row vanishing. (a) is simpler and more consistent with how `session`/`standalone` scopes already have no cascade at all.

## Concerns

- [ ] **Task 8.1.1a — Self-Heal Sweep only covers `scope="backlog-item"`; `session`-scoped and `standalone`-scoped requests have no reconciliation path at all.** The task's own description: *"for each open `GuidanceRequest` with `scope="backlog-item"`, check whether the item is archived/removed... if so, call `CancelGuidanceRequest`"* — there is no equivalent for a `session`-scoped request whose owning session is deleted/archived (the `session_uuid` field is explicitly a "loose string FK, NOT an ent edge" per Task 1.1.1a, so there's no cascade to fall back on either). A `session`-scoped `GuidanceRequest` whose session is torn down while pending will sit `pending` forever with no owner ever able to answer it usefully (the answer would have nowhere to be delivered) and no automated path ever cancels it — the exact "indefinite, indistinguishable-from-live limbo" pitfalls.md warns about, for two of the three scopes.
  - **Recommendation**: extend Task 8.1.1a's sweep to also check `session`-scoped open requests against session liveness/existence (whatever the codebase's equivalent of "does this `ItemSession`/session UUID still exist" check is — grep `GetItemSessionBySessionUUID`'s not-found handling for the shape) and cancel accordingly. `standalone` scope has no owning entity to check against by design, so it's reasonable to leave it uncancelled — say so explicitly in the plan rather than by omission, so a reviewer doesn't have to infer it was a deliberate choice.

- [ ] **Task 1.1.1b's composite unique dedup index does not actually dedup `standalone`-scope requests.** The chosen key is `index.Fields("scope", "item_id", "session_uuid", "question_text").Unique()`. For `standalone` scope, both `item_id` and `session_uuid` are `NULL` by construction (Task 1.1.1a). The plan's own doc comment for this index correctly notes "SQLite treats NULL as distinct" as the reason `item_id`/`session_uuid` alone can't carry the key — but doesn't carry that reasoning through to its logical conclusion for `standalone`: since *both* nullable columns are always NULL for that scope, SQLite's unique-index NULL semantics mean **no two `standalone`-scope rows ever collide**, regardless of `question_text` — the `OnConflictColumns(...).Ignore()` upsert in Task 1.1.3a will never fire for standalone, so AC5's dedup guarantee ("two near-simultaneous creates resolve to exactly one open row") silently does not hold for the one scope where there's no `resolveItemLink`-style caller-side gate at all. This project's codebase has no existing partial/filtered-unique-index precedent (confirmed via grep of `session/ent/schema/*.go`), so this isn't a copy-paste-and-move-on fix.
  - **Recommendation**: either (a) use a sentinel non-NULL placeholder value (e.g. empty string `""` instead of a NULL `session_uuid`/a zero UUID instead of NULL `item_id`) for the two scope-inapplicable columns so the composite index's NULL-distinctness problem disappears, matching how the fields are compared in queries; or (b) add a partial/filtered index (`entsql.IndexWhere` if this ent version supports it — confirm during Task 1.1.1b) scoped to `WHERE scope = 'standalone'` over just `(scope, question_text)`; or (c) explicitly accept and document that `standalone`-scope concurrent-duplicate creation is unguarded by the DB and rely purely on the in-transaction cap check (which does still work, since cap-check's `COUNT` doesn't depend on the unique index) — but that's a materially different dedup guarantee than AC5 claims for the other two scopes, and should be called out as such rather than left implicit.

- [ ] **Story 1.1.2 / Task 1.1.3a — the parse-at-boundary validation call site for `RequestScope`/`QuestionType` is never explicitly wired into the plan's task list.** Task 1.1.2a defines `IsValid()` on both types; Story 1.1.2's AC says "the repository validates it... without touching the database" — but Task 1.1.3a's bullet-by-bullet description of `CreateGuidanceRequest` (begin tx → cap-check `COUNT` → `OnConflictColumns` upsert → commit) never mentions calling `domain.RequestScope(req.Scope).IsValid()`/`domain.QuestionType(...).IsValid()` before any of that. Contrast this with how precisely the plan specifies the upsert's exact `WHERE`/`OnConflictColumns` shape elsewhere — the validation checkpoint is the one boundary-parsing step left to implementer discretion, which is exactly the kind of gap that produces an invalid `scope` value reaching the DB (or, worse, silently passing an SQL `COUNT`/upsert with a value nothing downstream expects) if it's implemented after the cap-check rather than before it, or forgotten to be called from the RPC/MCP handlers entirely.
  - **Recommendation**: add an explicit sub-bullet to Task 1.1.3a: "validate `scope`/`question_type` via `IsValid()` as the FIRST statement in `CreateGuidanceRequest`, before opening the transaction" — and add the same explicit call-out to Task 2.1.2a/2.2.1a's handler descriptions (validate before calling the repository), so the parse-at-boundary intent from Story 1.1.2 has one unambiguous, plan-specified location rather than three call sites where an implementer might each independently decide whether to validate.

- [ ] **Story 5.1.2 / Task 5.1.2a — `TriageRespawner.AutoRespawnTriage`'s signature is being *modified*, not extended, which is an OCP-violating touch on a shared interface for a single new consumer's benefit.** Confirmed: `session/backlog_lifecycle_triage.go:25-30` defines `AutoRespawnTriage(ctx context.Context, itemID string) error` with at least two existing call sites (`reconcileOrphanedTriageItems`'s shutdown-respawn branch at line 261, `retryOrphanedTriageWithBackoffGate` at line 397) plus a test fake (`fakeTriageRespawner`, `session/backlog_lifecycle_stuck_test.go:1835`). Task 5.1.2a's plan to add a `seedNote string` parameter to this interface method means editing the interface, every concrete implementation, the test fake, and (per the task's own text) explicitly setting `""` at both pre-existing call sites purely to preserve their current behavior — three call sites touched to serve a fourth, new one.
  - **Recommendation**: add a new interface method instead of widening the existing one — e.g. `AutoRespawnTriageWithContext(ctx context.Context, itemID, seedNote string) error` — with the existing `AutoRespawnTriage` staying untouched (optionally becoming a one-line wrapper calling the new method with `""`, if a single implementation body is desired). This is Open/Closed in the literal sense: the two pre-existing call sites and the test fake's existing method need zero changes, and only `GuidanceRequestDeliveryService` (the one new consumer) needs the new method. Low cost either way, but the additive form is strictly safer for a shared interface with existing production call sites.

- [ ] **Story 5.1.3 / Task 5.1.3a — extending an already-complexity-suppressed function.** `reconcileOrphanedTriageItems` (`session/backlog_lifecycle_triage.go:172-327`, confirmed) already carries `//nolint:gocognit,gocyclo` with a doc comment acknowledging "pre-existing complexity relocated verbatim by the backlog_lifecycle.go split... not introduced by that split" — i.e., this function is a known, already-tolerated complexity hotspot, not a clean extension point. The plan's own "Tech Debt Disposition" table classifies this as "Extend as-is: add one new early-exit branch, not a refactor," and per this review brief's placement-check, the new branch does land as a single early `continue` positioned before the existing shape-1/2/3 branching (not nested inside any of the three shapes) — so it does not compound the *specific* branching the nolint already covers. That said, it does add a new DB call (`ListPendingGuidanceRequests`) inside a loop that already does one DB call per item (`ListItemSessions`) for every item in `idea`/`queued` status on every tick, and it adds a new upstream dependency (`GuidanceRequest` repository) to a function whose doc comment is already effectively a maintenance-hazard notice. "Extend as-is" is a defensible call per this skill's own three-option framework (refactor-first / isolate-via-seam / extend-as-is) given the change is genuinely small and doesn't deepen the *same* violation — but it is exactly the kind of "extend as-is" that should be stated explicitly as a deliberate choice in the PR description when implemented, not left implicit, since a future reviewer without this review's context could easily read "one more branch in a `nolint:gocognit` function" as scope creep.
  - **Recommendation**: no structural change required; when Task 5.1.3a lands, its commit/PR description should explicitly note "extend-as-is per architecture-review.md, not a refactor" so the choice reads as deliberate rather than accidental to whoever reviews that specific diff.

## Nitpicks

- The `RequestStatus` "derived, not stored" design (pending/answered/cancelled from `answered_at`/`cancelled_at` nullability) is sound and correctly guarded at the two write paths (`AnswerGuidanceRequest`'s `WHERE answered_at IS NULL AND cancelled_at IS NULL`, `CancelGuidanceRequest`'s mirror-image guard) — verified against the `MarkStuck`/`ResolveStuck` precedent's exact shape (`session/ent_repository_backlog.go:1901-1990`). The residual risk is that ent's generated client still exposes ungated `SetAnsweredAt`/`SetCancelledAt` setters to any future caller who bypasses these two repository methods, so the "illegal state" (both timestamps set) is unrepresentable only by convention, not by the type system. Not worth a sum type or typestate wrapper for a single-package-internal entity with exactly two guarded writers today — but worth a one-line doc comment on the ent schema fields themselves ("never set directly — use `AnswerGuidanceRequest`/`CancelGuidanceRequest`") so a future direct `.Update().SetAnsweredAt(...)` call site is a deliberate violation, not an accidental one.
- The `GuidanceRequestDeliveryService` 3-way switch decision (Step 0.5 / Pattern Decisions "Delivery/resume branching" row) is sound: `SessionWriter` and `TriageRespawner` are narrow, single/dual-consumer interfaces (the latter reusing the existing `TriageRespawner` type verbatim rather than inventing a new one), and 3 closed, unlikely-to-grow cases don't justify a `Resumer` interface with one implementation apiece — no finding here, noted only because the review brief specifically asked the question.
- Config/feature-flag plumbing (`TymuxFeatureFlag`/`EffectiveTymuxEnabled`/`GetFeatureFlagWithDefault`, `config/config.go:462-505`) and the `knownFeatureFlags` registration point (`server/services/feature_flag_service.go`) both exist exactly as the plan assumes — verified, no gap.
