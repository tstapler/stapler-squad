# Validation Plan: durable-guidance-request

**Date**: 2026-09-12

## Happy Path Scenario

Given a headless triage session for backlog item `b608ab1e-b86e-4130-8879-7328cd363063` has created a `GuidanceRequest` (`scope=backlog-item`, `question_type=yes-no`) and exited, leaving it `pending`, when the human operator answers it "yes" via the `GuidanceRequestCard` in the triage panel, then `AnswerGuidanceRequest` persists the answer, publishes `GuidanceRequestEventPayload` on the bus, `GuidanceRequestDeliveryService` calls `MarkGuidanceRequestNotified` and respawns a fresh triage session via `TriageRespawner.AutoRespawnTriageWithContext` seeded with the answer, the `GuidanceRequestNavBadge` count drops within 5 seconds, and a `NOTIFICATION_TYPE_STATUS_CHANGE` entry naming item `b608ab1e-...` appears in `get_notification_history`.

### Repair-loop regression tests (the 5 blockers)

These are structural-enforcement tests per `quality:reflect-and-fix`'s philosophy — each guards exactly one blocker the adversarial/architecture review caught in planning, so it can never silently regress during implementation.

| Blocker | Test File | Test Name | Type | Scenario |
|---|---|---|---|---|
| 1a. `MarkGuidanceRequestNotified` called on success (Task 3.2.1c) | `server/services/guidance_request_delivery_service_test.go` | `TestGuidanceRequestDeliveryService_should_CallMarkGuidanceRequestNotified_When_WriteToSessionSucceeds` | Unit | Spy repository asserts `MarkGuidanceRequestNotified(ctx, payload.ID)` is called exactly once immediately after a successful `write_to_session` resume |
| 1b. Self-heal sweep does not re-deliver an already-notified answered request (Task 8.1.1a's corrected condition) | `session/backlog_lifecycle_guidance_test.go` | `TestReconcileGuidanceRequests_should_NotRedeliverAnswer_When_RequestAlreadyNotifiedOnSecondSweepTick` | Integration | Answer + notify a row, run the sweep tick twice; asserts the retry-delivery path (`write_to_session`/respawn) fires zero times on either tick, proving the sweep's `answered_at set AND notified_at nil` condition is not satisfied once notified is set on the happy path |
| 2a. | 3. `session.ResolveItemLink` produces identical rejection whether called from MCP or RPC path (Task 2.1.2a-pre) | `session/item_link_test.go` | `TestResolveItemLink_should_ProduceIdenticalErrorShape_When_CalledWithSameFixtureFromBothCallers` | Unit | Table-driven: the same `(callerUUID, itemID)` fixtures run through the raw `session.ResolveItemLink` helper once; a second parity test below re-verifies both adapters translate it the same way |
| 3 (parity across adapters) | `server/services/guidance_request_ownership_parity_test.go` | `TestResolveItemLinkAdapters_should_ReturnIdenticalErrorCodeAndRemediationText_When_MCPAndRPCPathsGivenSameFixture` | Integration | Calls `server/mcp`'s `resolveItemLink` and `server/services`'s `GuidanceRequestService` ownership check with identical not-linked / not-found fixtures, diffs error code + remediation text — this is the regression test for the "two independently-maintained copies" architecture-review blocker; it fails if either adapter's translation drifts from the shared helper |

| 4b. **Step 5 categorization call**: `TestGuidanceRequest_should_SurviveHardDeleteOfOwningBacklogItem_When_NoCascadeConfigured` is labeled **Migration**, not Integration, because it verifies a schema-level property of the new ent DDL itself (the deliberate absence of `entsql.OnDelete(Cascade)` on the `item_id` edge) rather than application business logic — it is the closest thing this feature has to "prove the migration is safe," standing in for the standard `migration_should_be_reversible` test that doesn't apply here (no hand-written migration exists; `Schema.Create()` auto-migrates). `TestReconcileGuidanceRequests_should_SetCancelledAt_When_OwningItemHardDeleted` (4b) stays **Integration** because it exercises the self-heal sweep's reconciliation logic, not the schema itself — 4a proves the row survives at the DB level, 4b proves the application-level backstop that makes that surviving row actionable.

## Test Stack

- **Unit**: Go `testing` + this repo's existing table-driven convention (`go test ./... -short`), run via `gotestsum` per `make test`; no mocking library beyond hand-written fakes (`fakeTriageRespawner`-style), matching existing `session`/`server/services` test conventions. Frontend unit tests: Jest + React Testing Library, colocated `*.test.tsx` files, run via `cd web-app && npx jest --no-coverage`.
- **Integration**: Go tests using a real (temp-file or in-memory) SQLite-backed `EntRepository`, a real `events.EventBus`, and — where a second package's adapter must be proven byte-identical to the first (blocker 3) — both adapters invoked directly in the same test process. Run via `make test-integration` / `go test ./server/services -timeout=20m`. Frontend cross-component integration: a Jest test importing all 3 host components with a mocked RTK Query server.
- **E2E / UX**: Playwright + Allure under `tests/e2e/`, isolated per-run server per `tests/e2e/global-setup.ts` (dynamic port, `--test-mode --test-dir`), following `e2e-test-conventions` (no `waitForTimeout`, `data-testid`/ARIA locators only, `// @feature` annotation naming the guidance-request feature IDs). Manual steps (contrast check, error-table doc conformance) recorded in this table rather than automated, per ux.md's own guidance for the two rows that aren't runtime-observable.
