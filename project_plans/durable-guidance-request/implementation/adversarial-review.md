## Blockers

- [x] **`GuidanceRequestDeliveryService` never marks a `GuidanceRequest` as notified on success, so the self-heal sweep re-delivers every answer forever.** RESOLVED: new Task 3.2.1c ("Mark the request notified immediately after a successful resume, in every scope branch," plan.md lines 350-354) now calls `MarkGuidanceRequestNotified` in each of the 3 scope branches — after a successful `WriteToSession` for `session`, after a successful `AutoRespawnTriageWithContext` for `backlog-item`, and unconditionally for `standalone` (nothing to resume) — and explicitly leaves `notified_at` nil on a resume error so Task 8.1.1a's sweep-retry condition (`answered_at` set, `notified_at` nil) now only matches genuine delivery failures, not every answered row forever. Story 3.2.1's AC now also states this explicitly ("has `notified_at` set immediately, so the self-heal sweep never re-delivers it," plan.md line 338-339).

- [x] **Cap-check runs before dedup, and Story 1.1.4's own test is ambiguous about which behavior it exercises.** RESOLVED: Task 1.1.3a (plan.md lines 193-202) now reorders to dedup-first — it attempts the `OnConflictColumns(...).Ignore()` upsert first, determines whether that call created a genuinely new row, and runs the cap `COUNT` (in the same transaction, rolling back on over-cap) *only* if a new row was created; a dedup hit skips the cap check entirely and returns the existing row. Re-derived the logic by hand: (a) a re-ask of an identical open question at/over cap → dedup hit at step 2 → step 4 returns the existing row without touching the cap check → correctly not rejected; (b) a genuinely new, distinct question at the boundary → step 3's `count > cap` (not `>= cap`) correctly allows the row that brings the count exactly to the cap and rejects the next one. Both directions check out. Story 1.1.4's test spec (lines 216-223) now explicitly requires distinct `question_text` per goroutine for the cap test ("Question 0".."Question 9", explaining why identical text would collapse via dedup and never exercise the cap path), and adds a separate, dedicated dedup-collision test (Task 1.1.4c, lines 233-235: 10 goroutines, identical `question_text`, cap 4, asserts exactly 1 row and zero `ErrPendingCapExceeded`). Minor new wrinkle in the fix's own vicinity, not a blocker: Task 1.1.3a's step 2 leaves the exact "did this call create a new row" detection mechanism unconfirmed ("confirm the exact detection mechanism against this ent version's `OnConflictColumns` semantics before finalizing") — the *logic* is sound and testable, but the implementer still has an open mechanical question to settle before writing the code.

- [x] **Story 3.2.3's resolution path rests on a factually wrong premise about the notification pipeline.** RESOLVED: the plan's "Resolved decision" under Story 3.2.3 (plan.md lines 374-378) now names a specific, real, already-existing enum value — `NOTIFICATION_TYPE_STATUS_CHANGE` — and states no proto change is needed. Verified directly by reading `proto/session/v1/types.proto` lines 940-966: `NotificationType` is indeed a closed enum, and `NOTIFICATION_TYPE_STATUS_CHANGE = 12` exists at line 961 with doc comment "Session status changed," exactly as the plan cites. The enum count claim ("15 fixed values... `NOTIFICATION_TYPE_UNSPECIFIED` (0) through `NOTIFICATION_TYPE_AUTO_APPROVED` (13) plus `NOTIFICATION_TYPE_CUSTOM` (100)") is also correct (14 sequential values 0-13 + 100 = 15). The item is removed from Unresolved Questions — the section's closing sentence now lists the Story 3.2.3 notification-type choice among things "resolved explicitly." Non-blocking observation: `NOTIFICATION_TYPE_STATUS_CHANGE`'s doc comment says "Session status changed," which is a mild semantic stretch when reused for the `backlog-item`-scope "triage resumed" case (no session involved) — the plan acknowledges this is "the best existing fit" rather than a perfect one, which is a reasonable judgment call, not a factual error.

## Concerns

- [x] **`TriageRespawner.AutoRespawnTriage`'s signature change is under-scoped and describes something Go can't express.** RESOLVED: Task 5.1.2a (plan.md lines 429-432) no longer proposes changing `AutoRespawnTriage`'s signature. It now adds a NEW, additive interface method, `AutoRespawnTriageWithContext(ctx, itemID, seedNote string) error`, implemented on every concrete `TriageRespawner` (`BacklogService`, `fakeTriageRespawner`), leaving the existing `AutoRespawnTriage` method, its signature, and all of its existing call sites (`reconcileOrphanedTriageItems`'s shutdown-respawn branch, `retryOrphanedTriageWithBackoffGate`, the direct test call sites in `backlog_service_triage_test.go`) untouched. This is a real interface-extension decision (a new method, not a signature change, an options struct, or variadic args), directly addressing the OCP violation flagged originally, and Task 5.1.2b then calls the new method from the delivery service.

- [x] **Self-heal sweep didn't cover the `session`-scope teardown case (flagged in architecture-review.md's Concern 1, referenced from this plan).** RESOLVED: Task 8.1.1a (plan.md lines 555-561) now explicitly adds a `session`-scope branch to the sweep — for each open `session`-scoped `GuidanceRequest`, it checks whether the owning session UUID still exists and calls `CancelGuidanceRequest` if not, with the task text itself noting "this closes the gap architecture-review.md's Concern 1 flagged." Story 8.1.1's AC (lines 546-552) and Task 8.1.1b's test list now both include a dedicated torn-down-session case alongside the archived-item and hard-deleted-item cases. Not verified against architecture-review.md directly in this pass (out of scope — that document belongs to a separate review track), but the plan text is internally consistent and the fix is concrete and testable.

- [ ] **`GuidanceRequestDeliveryService`'s core branching logic has no unit-test task, only an integration test that skips it entirely.** Task 3.2.1a's `SessionWriter`/`TriageRespawner` narrow interfaces are unit-testable in principle (mirroring the existing `fakeTriageRespawner` pattern), but Story 3.2.2's only test (Task 3.2.2a) explicitly runs with the delivery service *not running*, to test durable read-back — it never exercises the scope-switch at all. No task anywhere in Phase 3 unit-tests the switch's three branches or its success/failure handling. Given the missing-`MarkGuidanceRequestNotified` blocker above, a unit test over the switch would likely have caught it; as planned, the whole delivery service is effectively integration-test-only by omission, not by necessity.

- [ ] **Failed delivery has no user-visible signal until the next self-heal tick, and Story 3.2.3 doesn't cover it.** If `write_to_session` fails (dead tmux pane — a real TOCTOU window between whatever liveness check precedes it and the actual write) or `AutoRespawnTriage` errors for a non-graceful reason, the plan's only stated recovery is Task 8.1.1a's periodic self-heal sweep (same cadence as `reconcileOrphanedTriageItems`, on the order of minutes) — no story logs or surfaces this failure immediately, and Story 3.2.3's "resumed" notification (the mechanism meant to close exactly the "did my answer land" gap) never fires for a failed attempt. Story 3.2.2's "no answer is ever silently lost" claim is true for the *data* (durable read-back) but not for the *resume signal*, and nothing in the plan says so explicitly.

- [ ] **The cap-check's race-safety silently depends on an app-wide invariant the plan never names.** Pattern Decisions frames the cap-check as race-safe via "atomic transaction," and repeatedly says it "mirrors `MarkStuck`'s exact shape" — but `MarkStuck`'s own doc comment (`session/ent_repository_backlog.go:1897-1899`) states plainly that its concurrency safety comes *only* from the single upsert statement and explicitly has "no read-then-write." The guidance-request cap-check is a COUNT-then-write, a materially different shape that would be a genuine TOCTOU race under normal multi-connection SQLite semantics. It is currently safe only because `session/ent_repository.go:161` sets `db.SetMaxOpenConns(1)`, serializing all DB access (reads and writes) through one physical connection app-wide. That's real and true today, but it's load-bearing for this feature in a way no task states — a future perf change that raises `MaxOpenConns` would silently reopen this race, and Story 1.1.4's concurrency test would keep passing (it only proves correctness under the current constraint) with nothing to catch the regression. Recommend a comment at the cap-check call site naming this dependency explicitly.

- [ ] **`pkg/events` vs. `server/events` alias package isn't updated.** `BacklogItemEventPublisher` (Task 3.1.1b's explicit mirror target) imports `server/events`, a hand-maintained forwarding/alias package (`server/events/forward.go`) that re-exports selected `pkg/events` symbols. Task 3.1.1a adds the new event type/payload/constructor only to `pkg/events/types.go`; no task updates `server/events/forward.go`'s alias lists. If the new publisher file follows the mirrored idiom and imports `server/events`, it won't compile until someone notices the missing alias and adds it — trivial to fix, but an omitted step in a plan that otherwise itemizes every file touched per task.

Not re-checked this pass (out of scope — see header note); listed as-is from the original review, with two references updated below now that Blocker 3 is resolved.
