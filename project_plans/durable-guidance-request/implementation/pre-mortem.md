# Pre-mortem: durable-guidance-request
**Date**: 2026-09-12

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | An item with 2+ simultaneously-open `GuidanceRequest`s (explicitly allowed by the dedup-key design — Task 1.1.1b: "an item can have more than one different open question") gets an independent `AutoRespawnTriageWithContext` call per answer, spawning concurrent triage sessions/worktrees on the same item and branch with no coordination between them. | Two headless triage sessions land on the same item's branch around the same time, producing a git worktree conflict, a duplicate/contradictory `submit_triage_result` call, or a `headless.Pool` collision error in the logs with no obvious cause. | Add an explicit Phase 5 task: before respawning, check whether the item already has another *open* `GuidanceRequest` (respawn only once all of an item's open requests are answered) or whether a triage session for the item is already running/was just spawned (debounce/idempotency check via `headless.Pool`). Add a test with 2 open requests answered near-simultaneously asserting exactly one respawn. | P1 |
| 2 | The self-heal sweep — the plan's sole correctness backstop for archived-item, hard-deleted-item, and torn-down-session cancellation — silently stops running or throws partway through a tick, and nothing detects it, because the Observability Plan explicitly specifies zero new metrics/alerts for this feature. | A user notices a `GuidanceRequestCard` still shown as "pending" for an item archived or deleted days earlier, or the nav badge count doesn't match reality — discovered by chance, not by any operational signal. | Add per-row error isolation to the sweep (one bad row must not abort the rest of the pass) plus a completion log line with counts (checked/cancelled/notify-retried), and add a validation.md test asserting the sweep continues past a row that errors. | P2 |
| 3 | `GuidanceRequestDeliveryService`'s 3-way scope switch has no unit test (adversarial-review.md Concern, left unresolved) — its only exercise is an integration test that explicitly runs the delivery service NOT running (Task 3.2.2a). A latent bug in the switch (wrong scope match, `notified_at` set on failure, or never set on success) ships unnoticed. | The first real production halt-and-answer either double-delivers (duplicate `write_to_session` injection into a live terminal) or never resumes (item shows "answered" forever, triage never respawns) — discovered only when the operator wonders why nothing moved. | Add explicit unit-test tasks for the switch using mock `SessionWriter`/`TriageRespawner`: success path per scope, error path per scope (assert `notified_at` stays nil), and an unrecognized-scope case. Require this coverage before Phase 5's respawn integration is considered done. | P1 |
| 4 | `triage_guidance_halt` defaults OFF and there is no consumer of `create_guidance_request` other than the flag-gated triage path — so the entire pipeline (create → cap-check → notify → deliver → self-heal) can ship and sit completely unexercised in production for weeks, until someone finally flips the flag and hits every latent bug (including #1 and #3) at once, with no recent context on expected behavior. | Weeks post-merge, zero real (non-test) `GuidanceRequest` rows exist in production, and/or no feature-flag-flip log entry for `triage_guidance_halt` exists. | Add a required post-ship validation step (not just a merge gate): flip the flag on one real ambiguous item within N days of shipping and manually verify the full halt→answer→respawn→resume loop once in production before Phase 5 is considered "done," not just "merged." | P2 |
| 5 | The dedup key requires byte-identical `question_text`; an LLM-driven triage agent that rephrases its question across retries (or gets seeded and re-asks a slightly different way) bypasses dedup, burns the cap of 4 on near-duplicates, and then legitimately-different new questions get rejected with `ErrPendingCapExceeded` — the cap protects against exact-repeat spam, not the rephrasing spam that's actually likely from an LLM asker. Separately (architecture-review.md Concern, unresolved), `standalone` scope's dedup key is always `(scope, NULL, NULL, question_text)`, and SQLite's NULL-distinctness means the unique index never fires for that scope at all — AC5's "exactly one open row" guarantee silently doesn't hold there. | The operator sees an item's card stack with 3-4 near-identical reworded pending questions from one triage session's retries, with the 4th/5th genuinely-different question rejected — visible cap confusion in the UI. | Normalize/canonicalize `question_text` before the dedup comparison (trim/casefold at minimum), or cap "concurrent asks per triage halt occurrence" independent of exact text; separately fix the `standalone` NULL-index gap per architecture-review.md's own recommendation (sentinel non-NULL values or a partial index) instead of leaving it as an implicit, undocumented gap. | P2 |

## P1 Items (address before implementation)
- [x] #1 — RESOLVED: Story 5.1.4 (Tasks 5.1.4a-c) added — respawn is deferred while sibling open requests remain on the item, batches all answered-but-not-notified requests into one seed note, and adds an `IsLive(itemID)` debounce guard backed by the existing `BacklogService.IsTriageLive`. Concurrency test (5.1.4c) asserts exactly one respawn for 2 near-simultaneous answers.
- [x] #3 — RESOLVED: Story 3.2.4 (Tasks 3.2.4a-d) added — unit tests for `GuidanceRequestDeliveryService`'s scope switch (success/error per scope + unrecognized-scope, mock `SessionWriter`/`TriageRespawner`, explicit `notified_at`-stays-nil-on-error assertion). Task 3.2.1a amended to extract the switch into a testable `handleAnswered` method. Plan notes this coverage as a required dependency of Story 5.1.2/5.1.4.
