# Adversarial Review: omnibar-modal-scroll
**Date**: 2026-07-28
**Verdict**: CONCERNS

## Blockers
(none)

## Concerns

- **pitfalls.md's one substantive finding (residual "fixed chrome eats 80vh" edge case) was never carried into plan.md.** pitfalls.md §2 explicitly flags: on a very short viewport, with `pathDisplay`/`createRepoNotice`/existing-worktree-error visible *and* Advanced Options expanded, the fixed (non-scrolling) chrome around `.body` — `inputContainer` + `detectionInfo` + `pathDisplay`/`createRepoNotice` + `error` + `footer` + `shortcuts` — could itself approach `80vh`, leaving `.body` little/no room to scroll into. pitfalls.md calls this "not a blocker" but "worth a manual check." I grepped plan.md for `pathDisplay`, `createRepoNotice`, `residual`, `edge case`, `known limitation` — zero hits. Task 1.1.1d's manual verification only exercises "700px viewport + Advanced Options expanded" — it never triggers `pathDisplay`/`createRepoNotice` simultaneously, so the plan's verification doesn't actually cover the one scenario the research called out as the fix's real residual risk. AC2/AC3 are phrased broadly ("footer/input bar stay reachable... regardless of viewport/Advanced Options"), which overstates what's actually being verified.
  - **Recommendation**: either (a) add the compound case (short viewport + a visible notice + Advanced Options expanded) to Task 1.1.1d's manual verification checklist, or (b) if that's judged acceptable-but-unverified, add one sentence to plan.md's Risk Control or the story's acceptance criteria explicitly naming it as a known, accepted limitation inherited from the `ResumeSessionModal` pattern (whose `header` has the same "outside the scroll region" property) — don't just let the research finding silently evaporate between pitfalls.md and plan.md.

- **No CI-enforced regression test for a concrete, previously user-reported bug.** AC2 and AC3 are already written in exactly the shape of a Playwright assertion (`getBoundingClientRect()`, `scrollHeight`/`clientHeight`, computed `maxHeight`) — the plan essentially drafted the test and then declined to write it. Task 1.1.1d does the verification once, by hand (or once via Playwright MCP), during implementation, and explicitly declines to add a permanent spec file, citing NFR1/out-of-scope. That citation over-reaches: NFR1 ("No edits to `Omnibar.tsx`... CSS-only... only `Omnibar.css.ts`") governs the *production code* change, not test coverage — adding `tests/e2e/omnibar-modal-scroll.spec.ts` touches neither `.tsx` files nor any other modal's CSS and would not violate NFR1. Given this is explicitly a real user-reported clipping bug (not a hypothetical), and the assertions are cheap (bounding-rect/computed-style checks, no new page objects needed), a manual-only check leaves the fix regressable the next time someone touches `Omnibar.css.ts` or refactors the modal shell — CI would stay green while the bug silently returns.
  - **Recommendation**: add a small permanent Playwright spec asserting (1) `.modal` computed height ≤ 80vh at a short (e.g. 700px) viewport with Advanced Options expanded, (2) the Create Session button's bounding rect is fully within the viewport, (3) a `click()` on it succeeds without prior scroll. This is a few lines given AC2/AC3 already specify the exact assertions.

- **NFR2's "reuse the exact pattern already proven" / plan.md's "identical shell already shipped in production" claim is not literally accurate.** I read `ResumeSessionModal.css.ts` and `WorkspaceSwitchModal.css.ts` directly: neither's scrollable body (`ResumeSessionModal` `.body` lines 59-63; `WorkspaceSwitchModal` `.content` lines 75-79) has `minHeight: 0`. The plan's FR3/Task 1.1.1b adds `minHeight: 0` to `.body` — which is correct CSS (flex items default to `min-height: auto`, which prevents shrinking below content size, which is exactly what's needed here) — but it is not actually copied from either cited reference. Grepping the whole `web-app/src` tree for `.css.ts` files containing `minHeight` near a `body`/`content`/scroll-flex export turns up nothing that matches this pattern anywhere in the codebase. So the fix is *better* than its own cited precedents (arguably the two reference modals have a latent, currently-masked version of the same flex-shrink issue, papered over because their body content happens to be small or self-scrolling), but the plan's "zero-risk, exact copy" framing — used to justify skipping a feature flag and skipping automated tests — isn't quite true. It's a novel (if trivial and well-understood) CSS addition, not a copy-paste.
  - **Recommendation**: reword the Pattern Decisions table / NFR2 to say "closely modeled on... refined with `minHeight: 0`, which neither reference implementation has but which is required per the CSS flex-shrink spec for a body whose content can exceed the capped height" rather than claiming an identical, already-shipped pattern. Doesn't change the fix; changes the plan's confidence framing to match reality.

- **requirements.md's factual citation list is wrong, which undercuts the "already proven convention" argument the whole plan leans on.** The Problem section names four modals as evidence of an existing convention: `ui/Modal.css.ts`, `ResumeSessionModal.css.ts`, `WorkspaceSwitchModal.css.ts`, `ImportRulesModal.css.ts`.
  - `ImportRulesModal.css.ts` does not exist anywhere in the repo (`find`/`grep -ri importrules` across `web-app/src` returns nothing).
  - `ui/Modal.css.ts` does not actually follow the described "maxHeight + flex column + separate flex:1 scrollable body + pinned footer" pattern at all — its `.content` export is a single fixed/centered box with `maxHeight: 85vh` + `overflowY: "auto"` on the *whole* box, and `.footer` is just a child inside that same scrolling box (`marginTop`), not a sibling pinned outside the scroll region. So `ui/Modal`'s footer is not "always reachable" the way this fix intends `Omnibar`'s footer to be — it's cited as supporting evidence for a claim it doesn't demonstrate.
  - Net: only 2 of the 4 cited modals (`ResumeSessionModal`, `WorkspaceSwitchModal`) actually match the pattern being copied. This doesn't invalidate the fix, but it's an easily-checked factual error a reviewer will trip over, and it's the kind of inaccuracy that erodes trust in the rest of the "no risk, proven pattern" argument.
  - **Recommendation**: fix requirements.md's Problem section to cite only `ResumeSessionModal.css.ts` and `WorkspaceSwitchModal.css.ts`, or verify/replace the other two citations before this ships.

## Minors

- Plan.md's citation of `ResumeSessionModal.css.ts`'s `.body` as "lines 50-54" (Pattern Decisions table) is stale — in the current file `.body` is at lines 59-63. Doesn't affect the actual edit instructions (which correctly cite `Omnibar.css.ts`'s own `.modal` at 42-58 and `.body` at 116-121, both verified accurate against the current file), just a drifted reference to someone else's file.
- Task 1.1.1c's lint instruction ("Run the project's frontend lint (per `.claude/rules/css-architecture.md` — `lint:css` step)") is misleading: `npm run lint:css` runs `stylelint 'src/**/*.css'`, which only globs plain `.css` files and does not touch `.css.ts` files at all — it provides zero verification for this change. The check that actually matters for a vanilla-extract `.css.ts` file is `next lint` / `tsc --noEmit` (both already separately listed in the same task), not stylelint. Worth dropping the `lint:css` framing so the implementer doesn't think it validates anything here.
- No architecture risk, no new dependency, and no scope drift were found: Task 1.1.1a/b touch only `.modal`/`.body` in `Omnibar.css.ts` as required by NFR1; Task 1.1.1d's optional visual-regression snapshot update doesn't add a new spec file and is correctly scoped. All 5 requirements.md ACs have a corresponding Given/When/Then in plan.md's Story 1.1.1 (the coverage gap is depth/enforcement of the verification, covered above, not presence of a mapping).
- The project's `docs/registry/features/` has no existing entry for Omnibar/session-creation, so the "update the feature registry" rule in `.claude/rules/feature-registry.md` doesn't apply here (no add/rename of a proto RPC, no new component, no `// +api:`/`// +feature:` marker) — confirmed not a gap, just noting it was checked.
