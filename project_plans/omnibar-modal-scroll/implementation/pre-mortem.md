# Pre-mortem: omnibar-modal-scroll
**Date**: 2026-07-28

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The "known accepted limitation" (fixed chrome eating 80vh) bites at ordinary viewport heights, not just extreme ones. `.modal`'s fixed siblings outside `.body` are `inputContainer`, conditional `detectionInfo`, conditional `error`, conditional `shortcuts`, and `footer` — that's more fixed chrome than the single `header` `ResumeSessionModal` cites as precedent. At the plan's own test viewport (700px tall) with Advanced Options expanded *and* an error/detection notice also showing (an everyday state — e.g. user typed an invalid path), fixed chrome could already consume most of the 560px cap, leaving `.body` almost nothing to scroll into. The new Playwright test only covers the happy path (Directory + valid `/tmp`, no error banner), so it won't catch this. | User on a normal 13" laptop with a browser window not maximized (700-800px viewport height) hits an invalid/unusual path, expands Advanced Options, and the Create button is still unreachable — same bug, narrower repro. | Add a second AC/test case to validation.md: 700px viewport + Advanced Options expanded + an error state visible (e.g. a path that fails validation) simultaneously, asserting the Create button is still `toBeInViewport()`. If it fails, the "known limitation" note must be upgraded from "accepted edge case" to "must fix" (e.g. by moving `error`/`shortcuts` inside the scroll region). | P2 |
| 2 | The plan pre-authorizes `--update-snapshots` as an "expected/approved" outcome if the visual-regression spec (`omnibar-open` case, `maxDiffPixelRatio: 0.01`) trips in CI. That removes the friction that would otherwise force a human to look at the diff. If the diff is actually caused by something other than the intended reflow — e.g. a scrollbar-gutter reservation subtly shifting `.body`'s content width, or an unrelated concurrent change — it gets baked into the new baseline unexamined. | Next PR's unrelated visual-regression failure turns out to be against an already-wrong baseline that was rubber-stamp-updated during this fix. | Add an explicit instruction to plan.md Task 1.1.1d: if snapshots need updating, the diff image (old vs. new) must be visually inspected and the specific pixel-changed region named in the PR description before running `--update-snapshots` — not just "CI failed, so update." | P2 |
| 3 | The new permanent Playwright test (1.1.1e) chains several async-dependent steps — open omnibar, select radio, type into path field (submit-enablement may be debounced/validated), click "Advanced Options" (which triggers `OmnibarCreationPanel.css.ts`'s `maxHeight: 600` collapse-expand transition) — then immediately asserts `toBeInViewport()`. If the assertion runs before the expand transition/path validation settles, it's flaky on slower CI runners, and a flaky "regression guard" test tends to get skipped/quarantined rather than fixed, silently losing the coverage it was added for. | Test passes locally, flakes intermittently in CI, gets `test.skip`'d or retried away within a few weeks. | In the test, explicitly wait on state rather than sequencing raw actions: `await expect(createButton).toBeEnabled()` before the viewport assertion, and either assert on the expanded content being present (e.g. an Advanced Options-only field visible) or disable animations for this spec, before asserting `toBeInViewport()`. | P2 |
| 4 | `.body` only gets `overflowY: "auto"` (not `scroll`), so a scrollbar only appears/reserves width once content actually overflows — i.e. exactly when Advanced Options is expanded. On platforms with non-overlay scrollbars (Linux, Windows, most CI runners), this reserves scrollbar-gutter width at that instant, causing fields inside `.body` to reflow/narrow slightly right when Advanced Options opens. No AC covers this (all four ACs are about height/reachability, not horizontal stability), so it could ship as a small but real jitter that nobody explicitly tested for. | User expands Advanced Options and sees the form fields visibly shift/narrow by a few pixels at the moment of expansion. | Note in plan.md as an explicitly-accepted secondary tradeoff (matching the existing "Known Accepted Limitation" section's tone), or set `scrollbarGutter: "stable"` on `.body` alongside `overflowY: "auto"` to reserve the width up front and avoid the jump — cheap one-line addition if chosen. | P3 |
| 5 | Task 1.1.1e adds a new spec file (`tests/e2e/omnibar-modal-scroll.spec.ts`) reusing the existing `session:create` feature marker rather than registering a new one, per the plan's own note ("no new registry entry needed"). This assumption isn't verified against what `make registry-generate` / `coverage-gaps.json` actually do with a new spec file under an existing feature id — if the generator expects a 1:1 file-to-feature mapping or flags orphan spec files, `make registry-diff` could show unexpected drift that gets noticed only at PR-review time, not during implementation. | `make registry-diff` (or CI's registry check) shows an unexpected change/warning when the new spec file is added, unrelated to the CSS fix itself. | Add a task step: after adding the spec file, run `make registry-diff` and confirm it's clean (or the delta is limited to `lastModified`/`testIds` on the existing `session:create` entry) before considering Task 1.1.1e done. | P3 |
