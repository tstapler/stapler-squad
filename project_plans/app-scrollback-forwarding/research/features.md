# Research: Feature Landscape — App-Managed Scrollback Forwarding

**Project**: app-scrollback-forwarding
**Agent**: Phase 2, Agent 2 (Features Research)
**Date**: 2026-09-14

## 1. Summary of key findings

1. **The exact mechanism this feature needs already exists industry-wide, generically, as a terminal-level protocol** — DECSET mode 1007 ("Alternate Scroll Mode"): when an app switches to the alt screen, the *terminal* (not the app) translates mouse-wheel scroll into `PageUp`/`PageDown` or cursor-key (`\x1b[A`/`\x1b[B`) byte sequences and writes them to the PTY as ordinary input, exactly like a keypress. xterm, iTerm2, VS Code's integrated terminal, and GNOME Terminal all implement this. It requires no per-app knowledge — only "is the pane in alt-screen" — because the app itself is expected to interpret arrow/page keys as its own scroll command if it wants to. This is a strictly more general (and simpler) foundation than the per-adapter approach sketched in `requirements.md`'s Scope section.
2. **Claude Code confirms the feasibility risk for the flagship target**: its fullscreen TUI natively scrolls its own conversation transcript on `PageUp`/`PageDown` keys and (via alt-scroll-mode) mouse wheel — this is documented, current behavior ([code.claude.com/docs/en/fullscreen](https://code.claude.com/docs/en/fullscreen)), not something stapler-squad would need to invent. `Ctrl+O` additionally opens a separate full transcript viewer. Antigravity CLI (`agy`) is confirmed to use the alt-screen when its render mode is `"always"`, "providing an immersive, page-based interface with mouse support and scrollbars" ([antigravity.google/docs/cli/settings](https://antigravity.google/docs/cli/settings/)) — consistent with the same PageUp/PageDown-over-PTY mechanism, though this research did not find an explicit keybinding table to confirm the exact key sent. `pi` remains unconfirmed — no public documentation was found describing its rendering mode or scrollback keybindings; this should be a fast, cheap first implementation step (run `pi`, send PageUp, observe) rather than a web-research question.
3. **The repo's `session/*_adapter.go` files are a false lead for "detect the foreground app" — they implement `HistoryAdapter` (transcript Import/Export for checkpoint/fork and program-switch, `session/history_adapter.go:7-16`), not process-lifecycle or terminal-rendering knowledge.** What the requirement actually needs already exists as a *different* mechanism in the same package: `Instance.Program` / `GetProgram()` (`session/instance_terminal.go:47`, lock-free via `Snapshot()` per `.claude/rules/instance-lock-free-reads.md`) plus the `isClaude(program)` / `isPi(program)` basename-matching helpers (`session/instance_tmux.go:148-169`). These answer "what program did stapler-squad launch this session with," which is a usable but imperfect proxy for "what program currently owns the foreground of this pane" — see Edge Cases §5.1.

## 2. Baseline: what's already shipped and how it works

`ScrollbackRequest` → `handleScrollbackRequest` (`server/services/connectrpc_websocket.go:3104-3144`) → `Instance.GetScrollbackHistory` (`session/instance_tmux.go:1063-1069`) → `tmux capture-pane -S/-E` over a line-number range computed from `FromSequence`. This is a **pull-based, line-numbered pagination model**: the client tracks `oldestSequenceReceivedRef` and asks for the next `limit` lines further back (`web-app/src/components/sessions/TerminalOutput.tsx:1047-1062`, `requestScrollback(oldestSequenceReceivedRef.current, 500)`), and the server slices tmux's native scrollback ring buffer by offset. It only has content to return when tmux's own scrollback ring buffer holds it — which, per tmux's documented behavior, only happens for the **primary screen** in **normal-mode** panes. A pane in the alternate screen (`smcup`/`rmcup`, `ESC[?1049h`) writes into a screen tmux does not add to that ring buffer at all (this is xterm-spec-driven behavior tmux, Zellij, and every other multiplexer surveyed below follow identically) — so `capture-pane -S <negative>` genuinely has nothing further back to return; it isn't a bug in stapler-squad's pagination, it's a structural gap in what tmux tracks.

Related, already-shipped prior art for "the pane is in an app-drawn full-screen state" exists in this codebase already, independent of this feature: `rePositionCodes` in `server/services/connectrpc_websocket.go:129-135` (duplicated in `session/streamhub/snapshot_prepare.go:18-24`, both matching `ESC[?1049h`/`l` among other private-mode codes) is used to strip stateful escapes before replaying a `capture-pane` snapshot into a fresh xterm.js instance — i.e., the repo already parses PTY output for alt-screen-toggle escapes for a *different* purpose (full-resync snapshot sanitization). That regex, or a live-tracking variant of it, is the natural building block for "is this pane currently in alt-screen" detection rather than adding new escape-sequence parsing from scratch.

## 3. Industry landscape: how others handle "scroll passthrough" to full-screen TUI apps

### 3.1 The generic mechanism: DECSET 1007 (Alternate Scroll Mode)
This is the load-bearing finding for the whole feature. Per xterm's own manual and corroborated by iTerm2's and VS Code's issue trackers:

- By default, mouse wheel events scroll the **terminal's own scrollback**.
- When the terminal emulator detects the active screen buffer has **no scrollback** (i.e., alt-screen) *and* the mouse-wheel-as-arrow-keys mode is engaged, it instead synthesizes and sends `\x1b[A`/`\x1b[B` (cursor up/down) or, with DECCKM/application-cursor-mode active, the SS3 variants — as literal PTY input, indistinguishable from a real keypress.
- This is purely a **terminal-emulator-side heuristic based on alt-screen state**, not something the foreground app opts into or is even aware is happening — the app just receives what looks like arrow-key presses and is free to interpret them as "scroll my own view" (most curses/TUI apps already do, since arrow keys are the conventional pager navigation).
- iTerm2 exposes this as *Settings → Advanced → "Scroll wheel sends arrow keys when in alternate screen mode"*, gated on *"Disable save/restore alternate screen"* being off. tmux (via `tmux-mighty-scroll` and similar plugins) and VS Code's integrated terminal implement the same translation, though multiple VS Code issues (#42254, #32552) document that it's imperfect for apps like `less` that don't natively bind arrow keys to scroll (`less` scrolls on arrow keys itself only in some configurations — it's the app's own keybinding table that ultimately decides, the terminal only sends the bytes).
- **Implication for this feature**: stapler-squad does not need bespoke per-adapter "send this special escape sequence" logic if the target CLI already treats PageUp/PageDown/arrow keys as scroll (Claude Code confirms this). The adapter-specific work shrinks to: (a) confirm which literal key sequence each CLI's scroll binding expects (arrows vs PageUp/PageDown vs something custom), (b) decide the gesture-to-keystroke mapping (e.g., wheel delta → N arrow-key repeats, or scroll-to-top → repeated PageUp), not "invent a forwarding protocol."

### 3.2 tmux's own copy-mode vs. apps with their own pager
tmux's copy-mode (`prefix+[`) operates on tmux's **own** scrollback buffer for the **primary screen only**. It has no awareness of, and does not interact with, an app's internal pager state:
- `less`, and `git log`/`git diff` (which pipe through `less` by default via `core.pager`), run **inside the alternate screen** exactly like a full TUI app. tmux copy-mode entered from inside such a pane scrolls tmux's (empty, for alt-screen) buffer — it does not talk to `less`'s own line-based scroll. Confirmed by tmux's own issue tracker (`tmux/tmux#4725`, on copy-mode/alt-screen scrollbar interaction) and third-party mouse-mode plugin issues (`NHDaly/tmux-better-mouse-mode#27`, specifically calling out `git log`'s pager not responding to the plugin's emulated scroll — `git log`'s default pager invocation disables mouse reporting, so even the DECSET-1007 arrow-key translation described in §3.1 doesn't reach it consistently).
- This is the **same class of problem** as this feature: the multiplexer's scrollback and the app's internal pager scrollback are two disjoint buffers, and "which one does the user's scroll gesture apply to" is decided per-app, not centrally. It reinforces that a generic, blanket alt-screen-detection approach (§3.1) will work for *most* apps that follow the arrow/PageUp convention, but will silently no-op for apps (like `less` in some default configs, or any app that grabs raw mouse reporting without binding wheel-generated arrow keys to scroll) that don't. This is directly relevant to the Rabbit Hole "some agent CLIs may expose no scroll-back keybinding via terminal input at all" — it is a *real, observed-in-the-wild failure mode*, not a hypothetical.
- **Explicitly out of scope per requirements.md** ("Generic passthrough for arbitrary non-agent TUI apps... vim, less, htop") — but worth noting for design: if the detection mechanism ends up being alt-screen-based rather than per-adapter Program-string-based, it will *technically* also fire for `less`/`vim`/`htop` unless explicitly gated to only the known adapter set. The gating therefore has to be an intersection (`in alt-screen` AND `i.Program resolves to a known adapter`), not alt-screen alone — see §5.1 for why `i.Program` alone is also insufficient.

### 3.3 Zellij
Zellij's design is the most directly analogous prior art, because it is also a modern, actively-developed multiplexer wrestling with exactly this problem, in the exact same use case (AI coding CLI agents in a multiplexed pane):
- Zellij deliberately does **not** build scrollback from alt-screen content at all ("Zellij intentionally disabled scrollback in alternate screen to follow the xterm spec strictly") — stricter than tmux, which at least offers a config knob (`alternate-screen off`) to disable the alt-screen switch itself and keep everything in the primary/scrollback-tracked buffer.
- The `openai/codex` project (a very close analog to this feature — an AI coding CLI run inside a multiplexer) hit this exact issue repeatedly against Zellij: `zellij-org/zellij#4780` ("Codex Scrollback Bug"), `openai/codex#2836` ("mouse/scroll in zellij doesn't let me view earlier TUI conversation"), `openai/codex#10331`, `#23651`, `#11847`. Their fix, landed as `openai/codex#8555`, added a `tui.alternate_screen` config option and a `--no-alt-screen` CLI flag to Codex itself — i.e., **the fix lived in the agent CLI, not the multiplexer**: make the CLI render inline (never switch to alt-screen) so the multiplexer's native scrollback captures everything, sidestepping the whole forwarding problem.
- Even with `--no-alt-screen`, `openai/codex#10331` reports the bug persists in some cases ("full-screen redraw in main buffer") — because some renderers still do in-place cursor-repositioning redraws in the primary buffer, which a multiplexer's scrollback treats as "the same lines being overwritten," not new history to page through. This is a durable failure mode worth carrying into Design/Pre-mortem: **even a "confirmed" scroll-forwarding mechanism can produce a redraw that looks identical or garbled if the app's TUI framework repaints via cursor-repositioning instead of a clean full-screen clear+redraw per page** — directly matches this project's own Rabbit Hole ("What 'the resulting redraw' looks like varies by terminal size and app render behavior").
- **Notable non-analog but relevant contrast**: `sst/opencode#3020` reports the *inverse* symptom in Zellij — OpenCode's scrollback works, Codex's doesn't, in the same multiplexer, which corroborates that this is fundamentally a **per-app rendering-mode property**, not a multiplexer bug to fix once centrally. That is direct evidence that stapler-squad's requirements.md is right to scope this per-adapter rather than hoping for one universal fix.

### 3.4 VS Code integrated terminal / iTerm2 / GNOME Terminal
Covered in §3.1 — all three implement the same DECSET-1007-driven wheel→key translation, with VS Code's implementation documented (via its own issue tracker, #42254/#32552) as the least complete of the three (works for mouse-reporting-aware apps like `vim`, not consistently for `less`). No product surveyed implements anything conceptually different from "translate scroll gesture into a keystroke and let the app's own handler do the rest" — there is no widely-shipped design that captures the app's *redraw* and re-paginates it centrally the way this project's requirements.md Scope section describes ("capture the resulting redraw, streaming it back as the page of content"). That specific design — forward a synthetic keystroke, then diff/capture the resulting screen state as a servable "page" — appears to be a genuinely novel combination for this project, not something to copy from an existing implementation. The novelty is worth flagging to the planning phase: there's no reference implementation to validate against; it will need first-party testing against each target CLI's actual redraw behavior.

### 3.5 Warp
Warp sidesteps the entire problem category by not using a traditional PTY-scrollback model at all — it structures terminal history into discrete, app-aware "blocks" per command/agent-run and lets its own UI layer manage block-level scroll/collapse, rather than reading raw ANSI/alt-screen state. Not directly reusable (stapler-squad is explicitly a thin client over tmux+xterm.js, not a from-scratch terminal renderer), but validates the underlying product insight: once an app's own agentic output stops fitting the "flat scrollback of characters" model, the multiplexer/terminal has to gain some structured, app-aware concept of history to keep scrolling useful. This is directional support for treating "app has its own scrollback" as a first-class session concept (matching this project's proposed per-adapter detection) rather than trying to force everything through the primary-screen scrollback model.

## 4. What the adapter pattern actually offers (and doesn't)

`session/history_adapter.go:7-16` defines:
```go
type HistoryAdapter interface {
    Name() string
    CanHandle(program string) bool
    Import(ctx context.Context, inst *Instance) ([]CanonicalTurn, error)
    Export(ctx context.Context, turns []CanonicalTurn, inst *Instance) error
}
```
`resolveHistoryAdapter` (`session/history_adapter.go:21-29`) is called from `session/instance_checkpoint.go:53` (checkpoint/fork) and `session/instance_program.go:80-84` (mid-session program switch) — its job is entirely **conversation-transcript portability** (reading/writing each CLI's own on-disk JSONL/session-log format so history survives a checkpoint fork or a `claude` → `agy` switch). `ClaudeAdapter.CanHandle` (`session/claude_adapter.go:27-29`) and `AgyAdapter.CanHandle` (`session/agy_adapter.go:29`) both do simple substring/basename matching against the `program` string — they do **not** touch the PTY, terminal state, or process tree at all. `pi_adapter.go` does not implement `HistoryAdapter` at all (no `CanHandle`); it's a JSONL event-stream reader/writer for `pi`'s own conversation format only (`PiEventReader`, `session/pi_adapter.go:167-245`), referenced independently of the adapter-resolution path.

What *is* directly reusable, and is the actual answer to the requirement's open question "Can the current foreground process be identified as one of these adapters without new app-specific process sniffing?":
- `Instance.GetProgram()` (`session/instance_terminal.go:47`) — lock-free read of `i.Program` via `Snapshot()`, per this repo's own `.claude/rules/instance-lock-free-reads.md`.
- `isClaude(program)` / `isPi(program)` (`session/instance_tmux.go:148-169`) — whitespace-token + `filepath.Base` matching, already hardened against `env -u VAR claude`-style wrapper false positives and `claude-squad`/`mypi` lookalike false positives.
- No equivalent `isAgy`/`isAntigravity` helper was found by name; `AgyAdapter.CanHandle` (`session/agy_adapter.go:29`) is the closest existing check and should be read directly before this project reuses it, since `session/instance_program_test.go:202-211`'s comment flags a known historical drift bug between the "family gate" and `AgyAdapter.CanHandle` (`"gemini" treated as portable by AgyAdapter.CanHandle` when it shouldn't have been) — i.e., **this exact matching logic has already had at least one correctness bug in production**, worth a defensive test in this project's own detection code rather than assuming `CanHandle` is authoritative today.

## 5. Edge cases and failure modes

### 5.1 `i.Program` is a launch-time label, not a live foreground-process fact
`i.Program` records what stapler-squad was told to launch the session with (set via `SwitchProgram`/`SetProgram`, `session/instance_actor_setters.go:309-310`) — it is **not** derived from live inspection of the pane's actual foreground process (no `tmux display -p '#{pane_current_command}'` or `/proc/<pid>/comm` sniffing was found anywhere in `session/` or `server/`). Consequences the design must handle:
- If the user drops to a shell *inside* the Claude Code session (e.g., Claude Code exits or the user backgrounds it with `Ctrl+Z` / runs a sub-shell it spawned), `i.Program` still says `"claude"`, but the actual foreground process is now `bash`/`zsh` with real tmux-native scrollback available. Forwarding a scroll gesture as if it were still Claude Code's own scroll command would send garbage keystrokes (e.g., PageUp) into an interactive shell, at best a no-op, at worst triggering shell-specific PageUp behavior (some shell configs bind PageUp to reverse-history-search) — a real regression versus today's "silently does nothing."
- This means the "is this pane self-managing scrollback right now" signal needs to be **live**, not just launch-config-derived — most simply, `i.Program` matches a known adapter **AND** the pane is currently in alt-screen (reusing/generalizing the existing `rePositionCodes`-style detection from §2, tracked as live per-pane state rather than only at snapshot time). Matches the requirement's own Rabbit Hole framing ("may need per-adapter state tracking beyond simple alt-screen detection") — research confirms *both* signals are individually insufficient and the combination is the minimum viable detector.

### 5.2 Concurrent live output vs. user-initiated scroll (requirement's own Rabbit Hole)
Once a scroll-forwarding keystroke is sent, the app's own redraw is asynchronous — there is no synchronous request/response the PTY protocol gives you. If the agent CLI is actively streaming new output (e.g., Claude Code mid-response) at the same moment the user scrolls up, the "page" captured after sending PageUp may be a mix of the scrolled-back view and freshly streamed content, or may capture a transient partial-redraw frame. Every terminal-scroll product surveyed in §3 sidesteps this because their translation is a dumb one-way keystroke injection with no capture step — this project's added capture-the-redraw step is the genuinely novel part (see §3.4) and is exactly where this race lives. Needs either: debounce/settle detection (this repo already has `resizeSettling *atomic.Bool` precedent at `server/services/connectrpc_websocket.go:3167-3168` for a structurally similar "wait for the pane to stop actively changing before capturing" problem around resize) or an explicit app-quiescence check via the existing idle/busy `detection` package (`session/detection/idle.go`) before treating a captured frame as a valid scrollback "page."

### 5.3 Redraw viewport doesn't map to a stable "page" concept
`ScrollbackRequest`'s existing contract is line-range-addressable (`FromSequence`/`limit`, tmux `-S`/`-E`) — a stable, re-fetchable offset into an append-only buffer. A forwarded-keystroke capture is fundamentally different: it's "whatever the app chose to redraw in response to one keypress," which is not addressable by line offset, may not be idempotent (repeating the same forward-scroll request might scroll further rather than return the same content, since there's no absolute position, only relative deltas), and has no natural "end of history" signal (some CLIs virtualize their transcript and may just stop redrawing at the top with no boundary marker). The client-side pagination model (`prependScrollbackBatch`, sequence tracking) will not directly fit; this needs its own response shape/semantics, not a reuse of `ScrollbackResponse`'s offset-based contract as-is. Flag for Phase 3 (architecture): decide whether this is a new RPC/message type or a variant field on the existing one.

### 5.4 Terminal resize interaction
This repo already treats resize as a state that must "settle" before other pane operations proceed safely (`resizeSettling`, §5.2). An app's own scrollback redraw is very likely tied to the current terminal dimensions (virtualized transcript renderers typically re-flow to viewport size) — a resize event arriving concurrently with, or shortly before, a forwarded scroll request risks capturing a redraw mid-reflow. Should share the same settle-gate as `CurrentPaneRequest` (`server/services/connectrpc_websocket.go:3151-3168`) rather than inventing a second one.

### 5.5 Mobile/touch scroll gesture granularity
Per this project's own memory (`mobile + desktop UX requirement`), both form factors must be considered. Wheel-delta-to-keystroke-count mapping (§3.1) is naturally built for discrete wheel ticks; mobile touch-scroll is continuous and typically over-fires small deltas. A literal 1:1 gesture-pixel-to-PageUp mapping would spam the PTY with keystrokes on mobile; needs the same kind of gesture-coalescing/debounce the existing scroll-triggered `requestScrollback` call likely already has some version of (`web-app/src/components/sessions/TerminalOutput.tsx:1047-1062` — worth Agent 1/3's review of the existing debounce, if any, to confirm reuse vs. new logic).

## 6. Unstated needs beyond the explicit requirements

- **Visual mode indicator** (the requirement's own Open Question — "Should the client UI indicate 'you're now viewing the app's own scrollback'?"): research strongly suggests **yes, this is not optional polish**. Every failure mode in §5 (redraw doesn't match expectations, garbled partial frame, hit an undetectable top-of-history with no boundary signal) is far more confusing to a user if they don't know they've left "real tmux history" semantics. Precedent for stapler-squad's own visual-affordance pattern for a similar backend/UI split exists in `docs/reference/tag-organization.md`'s grouping-strategy indicators and this project's own recent `fork-pressure hysteresis + system status banner` work (`0ce32e531`) — a small persistent banner/badge is the idiomatic mechanism this codebase already reaches for, not a new pattern.
- **Graceful degradation signal for "no scroll command found"**: for `pi` (unconfirmed) or any future adapter where feasibility research finds no forwardable scroll command, the client needs to distinguish "still returning tmux history (works)" vs. "app-managed, no forwarding available (silently stuck, same as today)" vs. "app-managed, forwarding attempted but produced nothing new (hit top of app's own history)." These are three different UX states; requirements.md's Success Metric ("0% silent-no-op") implies at minimum the third state must be surfaced, not silently absorbed the way today's empty-`ScrollbackResponse` is.
- **A per-adapter feasibility record, not just a boolean**: since this is genuinely unproven territory (§3.4 — no reference implementation exists to copy), the research this project's own Scope calls for ("does the app expose a keybinding... and can it be sent over the PTY the same way regular input is?") should produce a durable, checked-in finding (e.g., an ADR or a table in the adapter file's doc comment) per adapter — keystroke used, confirmed CLI version, and known failure modes (e.g., "breaks mid-stream," "no top-of-history signal") — both so Phase 3/5 can build against confirmed facts instead of assumptions, and so a future CLI version bump that silently changes scroll behavior (as already happened to Claude Code itself across the v2.1.150 → v2.1.172 issue trail in §3.1) has something to diff against.
