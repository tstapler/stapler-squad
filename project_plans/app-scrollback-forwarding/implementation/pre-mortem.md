# Pre-mortem: app-scrollback-forwarding
**Date**: 2026-09-14

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Claude Code ships a version that changes or removes the confirmed scroll keybinding/redraw behavior (`VerifiedAgainstVersion: "2.1.270"`), and the only detector (`scrollForwardKeybindingCanary`) is a live-traffic heuristic gated at 3+ warnings/hour before it pages — sparse per-session scroll usage means the volume threshold may never trip even as the feature silently regresses to the exact no-op it was built to fix. | A trickle of user complaints that "scrolling up does nothing" or "reached the top instantly" on Claude Code sessions, with no corresponding alert firing (canary log lines exist but stay under the 1-hour/3-line threshold). | Add a scheduled/synthetic probe (not just organic-traffic canary) that periodically drives the confirmed keystroke against a real Claude Code session and diffs against the golden fixture from Task 1.2.1a, or trigger an immediate (not volume-gated) warning the first time a session's installed Claude Code version differs from `ScrollForwardCapability.VerifiedAgainstVersion`. | P1 |
| 2 | `ScrollBlockedReasonUnspecified` falls back to the `MULTIPLE_VIEWERS` toast copy ("another viewer is connected"), which is factually false when the real cause is a client/server eligibility race (e.g. `DetectedStatus` flips idle→executing between the client's decision to attempt and the server's `AppScrollGate` evaluation) — a narrower recurrence of the exact defect adversarial review already filed as a BLOCKER once. | Solo users occasionally see "another viewer is connected" and file confused reports, echoing the bug class the plan already fixed twice for the legacy-path and multi-client cases. | Change Task 1.4.3a's `UNSPECIFIED` fallback to a generic "Scroll-forwarding is unavailable right now" string instead of reusing the `MULTIPLE_VIEWERS` copy, per the adversarial review's own explicit recommendation, before Epic 1.4 implementation starts. | P2 |
| 3 | The mid-forward PTY-write/error path (Task 1.3.1c) has no dedicated test proving `scrollLease.release()` and `StreamHub`'s attach-barrier release actually fire on every error branch; if the `defer` ordering has a subtle bug, an error leaves the lease held or the barrier mutex locked, permanently disabling scroll-forwarding for that session or hanging every future `AttachSubscriber` call (a new client trying to view that session). | A single transient PTY hiccup (e.g. tmux pane blip) causes scroll-forwarding to silently stop responding for that session going forward, and/or a second client opening the same session hangs while connecting, with no error surfaced to either. | Add the explicit test case adversarial review flagged as missing: force an error mid-`SendInputViaControlMode` and mid-`waitForRedrawQuiescence`, then assert both a subsequent `ForwardScroll` call and a subsequent `AttachSubscriber` call proceed normally afterward — not just that the code reads correctly. | P1 |
| 4 | Claude Code's own transcript view may be a bounded/virtualized window rather than indefinite history (`requirements.md`'s own Feasibility Risks section), so forwarded scroll quickly hits `AtTop` on long-running sessions — the feature reports success (no error, no silent no-op) while still failing the actual user need ("review content the app scrolled past") for exactly the long sessions most likely to need it. | Users on long-running sessions (hours of agent activity) hit "No more history available" after only a page or two of scroll-up and report they still can't find something from earlier in the session, even though the feature is "working" per its own success metric. | During Story 1.2.1's spike, measure and record how much history depth is actually recoverable via the chosen strategy on a long-running session (not just "does content visibly differ"), and document the measured limit in `ScrollForwardCapability.KnownFailureModes`; if `NativeDumpFallbackStrategy` recovers materially more depth than `GestureForwardStrategy`, prefer it even if gesture-forwarding "works" in the narrow diff-test sense. | P2 |
| 5 | The multi-client block gates on raw `hub.SubscriberCount()`/`connection_count` (confirmed: `session/streamhub/hub.go:251-252`, `proto/session/v1/events.proto:166-171` — no per-user identity dedup exists), so the *same person* viewing one session from two devices — a pattern this project's own `mobile + desktop UX requirement` memory treats as a first-class use case — always sees `subscriberCount >= 2` and gets permanently `Blocked` with `MULTIPLE_VIEWERS`, never the feature this project built. | Users who habitually keep a session open on both laptop and phone (or two browser tabs) find scroll-forwarding "never works," always showing the "another viewer is connected" toast, for the exact power-user pattern most likely to want scrollback review. | Before implementation, explicitly decide (and record in validation.md) whether `AppScrollGate`'s viewer-count check should key on distinct authenticated users rather than raw connections; add a Phase-1 test scenario for "same user, two devices/tabs, one scrolls" and either relax the gate or explicitly accept this as a known, named limitation rather than an unnoticed gap in the Unresolved Questions list. | P1 |
| 6 | A single redraw containing an unwrapped line genuinely longer than the negotiated pane width can still lose content past the visible pane: tmux keeps zero scrollback in the alternate screen (confirmed via `man tmux`'s `capture-pane -S -N -E -` docs and a live reproduction — widening the capture range is structurally inert once alt-screen content has scrolled off), so `captureViaRedrawQuiescence`'s plain `CapturePaneContentPriority` capture cannot recover it. Related to, but distinct from, `requirements.md`'s Feasibility Risks note about an app's *own* virtualized scrollback — this is tmux's terminal emulation, not app-level windowing. | An extremely wide/long single line in a redraw (wider than the negotiated pane) truncates in the captured content with no error and no indication anything was lost. | Accepted as a known Phase-1 limitation — no fix shipped this round. A real fix would need either temporarily growing the pane during capture (new latency/race surface, no precedent in this codebase, deliberately not pursued) or client-side frame accumulation for self-echo matching (a related but separate robustness improvement). | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — Resolved 2026-09-14: added Story 1.5.3 (`scrollForwardVersionMismatchCheck`, Tasks 1.5.3a–c) to `plan.md` Epic 1.5 — an immediate, non-volume-gated `claude --version` check against `ScrollForwardCapability.VerifiedAgainstVersion`, modeled on `session/tmux/version_check.go`'s existing precedent.
- [x] Failure #3 — Resolved 2026-09-14: added the mid-forward error-path test to Story 1.3.1's acceptance criteria and Task 1.3.1d in `plan.md` (forced `SendInputViaControlMode`/`waitForRedrawQuiescence` errors, asserting lease + attach-barrier release), plus REQ-5 rows in `validation.md`.
- [x] Failure #5 — Resolved 2026-09-14: `plan.md`'s Risk Control section now has an explicit "Decision — per-connection, not per-user identity" subsection, grounded in reading `server/middleware/auth.go`/`session/streamhub/subscriber.go`/`server/auth/webauthn.go` (no per-user identity plumbing exists) — accepted as a documented Phase-1 limitation, with a same-user-two-devices test scenario (REQ-3b) added to `validation.md` asserting the accepted behavior.
