# Validation Plan: app-scrollback-forwarding

**Date**: 2026-09-14

## Happy Path Scenario
Given a Claude Code session whose pane is alt-screen-active and idle with exactly one connected client, when the user scrolls up (wheel, trackpad, or touch drag) past the point where xterm's own scrollback is empty, then the client forwards the gesture, receives a `DELIVERED` `AppScrollbackResponse` containing Claude Code's own scrolled transcript, and renders it under a `ScrollSourceIndicator` banner reading "Viewing Claude Code's own history" — instead of today's silent no-op.

Every other scenario below is a variation on this core sequence: a different `ScrollForwardOutcome` (`AT_TOP`, `BLOCKED`, `NO_CAPABILITY`), a different `AppScrollGate` failure that prevents it from starting, or a concurrency edge around the `ScrollLease`/`ScrollForwardAttachBarrier` that protects it.

### Golden Fixture Strategy (REQ-4 — the core hard-to-test mechanism)

Forwarding a keystroke to a live external CLI and capturing its redraw is inherently nondeterministic to unit-test: no real `claude` process runs in CI. The plan's own answer (Task 1.2.1a) is a **committed before/after pane-content fixture pair** — `session/testdata/scroll_forward_claude_before.txt` / `scroll_forward_claude_after.txt` — captured once, manually, against a real `claude 2.1.270` session, and checked in as data (not investigation narrative, so it's exempt from this repo's comment-proportionality convention).

Every test that would otherwise need a live CLI is built against this fixture instead:
- `waitForRedrawQuiescence`'s poll-and-compare logic is exercised with a fake `paneContent func() (string, error)` closure that returns the fixture's `_before.txt` content on early polls and `_after.txt` on later ones — deterministic, fast, no PTY.
- `scrollForwardKeybindingCanary` (REQ-4, REQ-14) is regression-tested directly against the fixture pair: does the *committed* real transition still read as "scrolled" to the canary's heuristic? This is what "re-verifies the byte-sequence-to-behavior claim after the initial spike" (adversarial-review's own phrasing) means concretely — a version-drift or heuristic-drift bug shows up as this specific test starting to fail, not as a silent production regression.
- The end-to-end `ForwardScroll` integration test (`TestClaudeScrollAdapter_ForwardScroll_should_ReturnDeliveredOutcome_When_GoldenBeforeAfterFixtureAppliedThroughFakePaneSource`) wires the fixture through the *entire* pipeline (gate → lease → send via a no-op fake PTY writer → quiescence → outcome computation) without touching tmux or a real CLI at all.
- **What this deliberately does not cover**: whether `\x1b[5~` (or `Ctrl+O`+`[`) still produces this exact transition against a *future* Claude Code version. That's an explicitly accepted gap (plan's Task 1.2.1a: "manual spike + committed fixture + production canary, no live-CLI CI") — the production canary (REQ-14) is the actual detector for that drift, not CI.
- The UX/E2E layer (Step 2 below) reuses the same fixture pattern via a scripted fake program rather than a live `claude` binary, for the same reason.

## UX Acceptance Tests

All twelve criteria (UX-AC-1 through UX-AC-12) are from `design/ux.md`. Implementation model: the `ui-playwright` skill, following this repo's existing `tests/e2e/` conventions — `// @feature` header tag, `data-testid`/ARIA-role locators only, no `waitForTimeout` (poll via `expect(locator).toHaveText(...)`/`waitForSelector` instead), page objects under `tests/e2e/pages/`.

Per the same "no live CLI in CI" constraint as REQ-4, every scenario below runs against a scripted **fixture program** (`tests/e2e/fixtures/alt-screen-scroll-fixture.sh`, started as the session's `program` the same way existing e2e specs already launch a scripted `pi` session via `SessionsPage.createPiSession`) that reproduces the committed golden before/after pane content on `PageUp`/`Ctrl+O`+`[` input, rather than a real `claude` process — deterministic and CI-safe, and directly reuses REQ-4's fixture bytes so the e2e assertions and the Go-level canary test can't silently diverge on what "a correct redraw" looks like.

## Test Stack
- **Unit (Go)**: standard `testing` package + `gotestsum` (this repo's convention, `make test`) for readable per-test pass/fail output; table-driven tests per `session/detection/detector_test.go`'s existing style; no new assertion library introduced.
- **Unit (TypeScript)**: Jest + React Testing Library, matching the existing `*.test.tsx` files under `web-app/src/components/sessions/`; `npx jest --no-coverage` for fast local iteration, matching `CLAUDE.md`'s documented frontend test command.
- **Integration (Go)**: same `testing`/`gotestsum` stack, no separate framework — "integration" here means crossing a package boundary (`session` ↔ `session/streamhub`, `session` ↔ `session/detection`) or exercising `go test -race`, not a different tool. Test doubles only: a fake `ScrollAdapter`, a fake `paneContent` closure, and this repo's existing `session/streamhub` test helpers for a real (non-mocked) `StreamHub` — never a live tmux pane or a real `claude` process, per the Golden Fixture Strategy above.
- **E2E / UX**: Playwright, following `tests/e2e/`'s existing conventions (`global-setup.ts`'s auto-managed isolated server instance, `@feature` header tags, `data-testid`/ARIA-role locators, no `waitForTimeout`) and the `ui-playwright` skill as the implementation model. The alt-screen CLI itself is a scripted fixture program (`tests/e2e/fixtures/alt-screen-scroll-fixture.sh`), not a live `claude` binary, mirroring the existing `createPiSession`-style scripted-program precedent already used in this test suite.
