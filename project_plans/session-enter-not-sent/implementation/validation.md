## Go/No-Go Gate Precision Check

Story 1.3.4 / Task 1.3.4a (plan.md lines 222-231) sets the gate between Phase 1 and Phase 2.

**PASS criteria — precise enough to execute.** "*When* all three showed `success: true` with `read_session_output`-confirmed real submission and no unresolved `SUBMIT_NOT_CONFIRMED`, *then* the verdict is PASS" ties directly to observable tool-call fields (a specific return value, a specific absent error code) plus a pane-content check each story's own Task-c already spells out concretely (e.g. Task 1.3.3b's unique marker-string echo). The only soft spot — Task 1.3.1c's "shows Claude Code actively processing... (e.g., visible progress/response text)" — is a judgment call on pane content, not a numeric threshold, but it's the same kind of check `tests/e2e/backlog-session-steer.spec.ts` already makes against real tmux output, so it's executable by a human or an agent reading the pane, not vague in a way that blocks execution.

**FAIL *detection* criteria — precise.** "*if* any tool showed a swallowed submission (input sat unprocessed) or an unresolved `SUBMIT_NOT_CONFIRMED` after the built-in retry" names exactly the two observable failure shapes (unprocessed input; a specific named error after the documented retry-once behavior at `session/pane_submit.go:168-181`).

**FAIL *action* — still underspecified.** The action on FAIL — "Phase 2 is skipped, and a new, narrowly-scoped follow-up bug is filed instead" — names no artifact, no tool, and no task, unlike the PASS branch's fully broken-down Task 2.2.1a→2.2.1c sequence. This is exactly adversarial-review.md's Concern (bullet 4, "The go/no-go gate's FAIL branch (Story 1.3.4) is underspecified relative to every other step in the plan"), which recommended "a concrete Task 1.3.4b... naming the exact artifact/tool for the FAIL path." **Confirmed still open**: `grep -n "1.3.4b"` and a full read of Story 1.3.4 (plan.md lines 222-231) show no such task was added — the Concern's checkbox in adversarial-review.md is unchecked (`- [ ]`), and the plan.md text matches what the review critiqued verbatim. This is a genuine, currently-unresolved gap, not one this validation pass is silently accepting as closed.

## Verification Method (in place of a Test Stack)

- **Live MCP tool calls**: `create_session`, `read_session_output`, `write_to_session`, `steer_session`, `run_command` (Phase 1, against the manual instance on port 62871 only — registered via `claude mcp add --transport http ssq-manual-smoke http://localhost:62871/mcp`, never the live `:8543` registration); `get_backlog_item`, `report_duplicate` (Phase 2, against whichever backend the operator's default MCP client resolves to — this is the live backlog store, since the item being closed lives there).
- **Shell-level checks**: `curl -sf http://localhost:62871/` / `:8543/` to confirm instance reachability and that the live instance was never restarted (Task 1.1.1a-c); `tmux list-sessions` before (Task 1.1.1d baseline) and after (Task 1.4.1d) teardown, diffed by name and count — the only check that actually confirms the *shared* tmux server's production sessions were untouched, since an HTTP-port probe says nothing about the tmux layer; `git fetch`/`git merge-base --is-ancestor`/`git push origin --delete` for the stale-branch cleanup (Epic 2.3).
- **Read-back verification discipline**: Task 1.1.1c reads `~/.stapler-squad/instances/claude-manual-test/config.json` back rather than trusting the start command succeeded silently; Tasks 1.3.1c/1.3.2c/1.3.3b each call `read_session_output` after a write rather than trusting the tool's `success: true` return value (this is the load-bearing check for the entire smoke test — a tool returning `success: true` while the Enter got swallowed is exactly BUG-047/BUG-031's failure shape); Task 2.2.1c calls `get_backlog_item` again after `report_duplicate` rather than trusting its return value — though see the Concern above: it currently checks a field (`VerificationNotes`) the expected code path may not write, which itself needs fixing before this read-back is trustworthy.
