## Concerns

- [ ] **Task 2.2.1c's read-back verification checks a field the expected code path never writes.** `reportDuplicateUnclaimed` (the path Pattern Decision row 3 expects to fire, given the item's likely idea/refining/ready/queued status) records its note via `recordStatusEvent` into `BacklogStatusEvent` (`session/ent_repository_backlog.go:1369-1378`), not via `UpdateItemSessionVerificationNotes` — that call only happens on the separate linked-work-role path (`tools_backlog.go:2296`). Task 2.2.1c's acceptance criterion ("`VerificationNotes` contains `duplicate_ref=...`") will find nothing if the unclaimed-archive path is the one that actually executes, risking a false "the mutation didn't take" conclusion after a real success. — **Recommendation**: verify via the item's status-history/status-event record (whatever `get_backlog_item` surfaces for it) when the unclaimed-archive path is used, not `VerificationNotes`.
- [ ] **Item #819's own backlog-item status is never checked or closed.** requirements.md establishes that #819's underlying symptom is fixed by PR #837, but neither requirements.md nor plan.md includes a task to check or close backlog item #819 itself — only `f7201b49`. If #819 is still open in the live backlog store, this plan leaves it permanently stuck despite its fix having already shipped, with nothing in either document reconciling that. — **Recommendation**: add a Phase 2 task to `get_backlog_item` on #819 and, if still open, close it (citing PR #837) or explicitly record why that's deliberately left for a separate pass.
- [ ] **Task 1.2.2a's `create_session` call is missing a required parameter and a precondition.** `title` is required (`server/mcp/tools_lifecycle.go:137-139`, rejected with `ErrInvalidArgument` if empty) — the task never specifies one. `path` must already exist on disk (`os.Stat` check at `tools_lifecycle.go:144-146`, rejected with `ErrInvalidPath` otherwise) — the task references `/tmp/ssq-smoke-test-repo` as the working directory with no `mkdir -p` step beforehand. As literally written, this task fails on the first call. — **Recommendation**: add `title` to the call and an explicit `mkdir -p /tmp/ssq-smoke-test-repo` task before Task 1.2.2a.
- [ ] **The go/no-go gate's FAIL branch (Story 1.3.4) is underspecified relative to every other step in the plan.** "file a new, narrowly-scoped follow-up bug" names no mechanism (a `docs/bugs/open/*.md` file per this repo's own convention? a backlog item via some creation tool?) and no task breakdown, unlike the PASS branch's fully spelled-out Phase 2. — **Recommendation**: add a concrete Task 1.3.4b (or short follow-up epic) naming the exact artifact/tool for the FAIL path.
- [ ] **Story 1.3.2 doesn't confirm `steer_session` actually exercises the fix under test.** `steerSession` branches on `inst.OneShot && uuid != "" && GetEffectiveStatus() == Stopped` into an entirely different `RunWithResume` subprocess path (`tools_terminal.go:690-706`) that never calls `session.SubmitContentWithEnter` — the fix this whole smoke test exists to verify. Nothing in the plan asserts the target session is non-OneShot/non-Stopped at call time, so the smoke test could "pass" while silently exercising the unrelated resume-subprocess branch instead. `SteerSessionResult.Method` (`"send_keys"` vs `"resume_subprocess"`) already distinguishes this. — **Recommendation**: require `Method == "send_keys"` as part of Task 1.3.2's PASS criteria, not just `success: true`.
