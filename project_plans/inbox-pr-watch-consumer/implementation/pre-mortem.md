# Pre-mortem: inbox-pr-watch-consumer
**Date**: 2026-10-22

Premise: the consumer shipped, was enabled, and failed within a month. Each failure below
is tied to code that was read (VERIFIED) or to a stated inference (INFERRED); see
"Verification of plan assumptions" for the file:line evidence.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Hostile PR text still steers the agent. The fixed template blocks bodies, but (a) `actor` is still attacker text after a login-regex check (a 39-char login such as `ignore-prior-rules-and-run-curl` is a legal GitHub login), (b) `action` and `repository` come straight from the payload and are not validated by the plan, (c) any stranger who comments on a public-repo PR wakes an unattended agent whose first instruction is `gh pr view`, so the attacker text reaches the model through the session's own tool call, and (d) every edit or new comment is a distinct fingerprint, so a commenter can trigger a pane write about every 60 s indefinitely. | A session on a public repo starts turns nobody asked for, shortly after a comment from an unknown account; token spend rises with no operator activity. | Build the message only from values the session owns (its own `owner/repo`, PR number) plus an allowlisted `kind` enum; drop `actor` and `action` from the pane text entirely (log them). Add an actor gate before any steer: operator login, configured allowlist, or the repo's collaborators (an extra `gh api` check), and ack-drop everything else with a counter. Add a per-session/per-PR steer cooldown (for example 5 min) with ack-all-covered after one steer, so spam collapses to one steer. Add a test where `actor`, `action` and `repository` are hostile strings, not only `summary`/`details`. | P1 |
| 2 | The feature silently never fires for most sessions. (a) The inbox only gets events for repos with a gh-signal webhook: `~/.config/gh-signal/config.d/95-webhooks.toml` lists exactly two repos (`tstapler/gh-signal`, `tstapler/stapler-squad`). (b) The inbox does not replay, and Squad learns a hand-opened PR's number only when `PRStatusPoller` finds it by branch: a 60 s tick, plus a 5 min `NoPRBackoff` if the branch had no PR at the previous tick, so the first CI result and early reviews can arrive before the subscription exists. (c) Fork sessions are skipped by the poller and get no CI events from gh-signal. (d) Squad has no way to tell "subscribed, covered, quiet" from "subscribed, no hook, will never hear anything". | The operator opens a PR from an ad-hoc session on any other repo, CI fails, and nothing happens; `GET /v1/subscriptions` shows `last_activity` null forever; success metric 1 passes only in the two hooked repos. | Add a catch-up step on first subscribe: read current CI conclusion and unresolved review state through the existing GitHub client (the poller already fetches `PRInfo.CheckConclusion`, `ChangesRequestedCount`) and steer once if already failing or changes requested. Resolve open question 1 before building: add the gh-signal HTTP `watch` (returns `coverage`) or have Squad refuse and surface "no webhook for owner/repo" in the UI and logs when `coverage` is unavailable. Subscribe on PR discovery, not on a timer, and log time-from-PR-creation-to-subscription. Restrict v1 to `GitHubHost == ""` and non-fork sessions. Add an e2e test for "event arrives before subscribe". | P1 |
| 3 | Event storm and self-echo loop. One failed CI run produces `check_run` (one per job), `check_suite` and `workflow_run` events, each with its own fingerprint, so one failure is N events; the plan steers per event. `kind: pull_request` fires on every push, label and assignment. The agent's own `gh pr comment`, review replies and pushes arrive as events from the operator's own login, so the agent steers itself: comment, steer, comment, steer. Edits (`action: edited`) and deletions of comments also create new events (body digest is in the fingerprint). | The pane receives several steers per CI failure; a session in a loop posting and re-reading its own comments; `inbox pending` count high while steers/min is also high. | Replace the plan's "each `kind`" table with an explicit allowlist of `(kind, action)`: `comment/created`, `review/submitted` (state not `approved`), `review_comment/created`, and `ci` only for `check_suite` or `workflow_run` completed with a failing conclusion (`failure`, `timed_out`, `startup_failure`, `action_required`); never steer on `pull_request` except to unsubscribe on `closed`. Drop events whose actor equals the operator's own GitHub login (resolve once at start). Coalesce per `(PR, head_sha, ci)` and per `(PR, kind)` within the cooldown, acking the covered items. Test with a recorded fixture of one failed run with three jobs. | P1 |
| 4 | Duplicate or unsafe writes because the plan names the wrong steer path and an incomplete D4. (a) The plan says to call `IsReadyForSteer` then `SteerActiveSession`; that method is documented unguarded, skips the nudge guard, the in-flight claim and the pane-ownership check, and has a check-then-write gap. The guard (`sessionNudgeGuard`) is unexported and only reachable through `SteerSessionGuarded`. (b) D4 names `FindPRPendingItems`, which is an `EntRepository` method that returns only `pr_pending` items with `PrNumber>0`, so a backlog work session whose item is in `review` or `in_progress` is both unsteered by #645 and (if not excluded) steered here, while a `pr_pending` match costs a `git remote` call per item. The poller populates PR fields on backlog work sessions too, so this overlap is the normal case, not an edge. (c) Two steers inside the 60 s duplicate window come back as `SteerDuplicate`; if the consumer acks on that, the event is lost. | A backlog-tracked PR gets two steers (one from #645, one from prwatch); or a comment is acked and never steered; or a steer lands in the wrong tmux pane after a name collision. | Define the prwatch `Steerer` port as `SteerGuarded(ctx, uuid, sig, msg) (Outcome, error)` with its own outcome enum, and have the server adapter call `SessionService.SteerSessionGuarded`; do not use `SteerActiveSession`. Treat `SteerGuardBusy`/`SteerDuplicate`/`SteerCoolingDown`/`SteerBusy`/`SteerNoStatusSource` as "leave pending", and ack only on `SteerDelivered` or a deliberate drop. Build D4 in the server adapter from `Storage.ListItemSessionsBySessionUUIDs` (session UUID to item link, one batched query, no git calls) and decide explicitly whether the exclusion is "any backlog link" or "item status is `pr_pending`". Reuse `githubpkg.LinkKey` plus the canonical reason names in `guardSignature` so the guard also dedups against #645. Consider the wake path's fresh-capture dialog check (`wakes.WriteIfIdle`) because the cached idle status is blank for 6 to 9 s after a keypress. | P2 |
| 5 | The one-consumer-per-session design (D2) leaks and cannot clean up. The inbox has no list-all-consumers call, and pending items for active subscriptions are never pruned, so a subscription left behind by a Squad crash, a deleted session or a hibernated session accumulates items forever; commenters on a public PR can grow the backlog and there is no per-subscription cap. Paused or hibernated sessions force a choice between dropping events (unsubscribe) and unbounded pending (stay subscribed). Also, `GET /v1/events` returns the oldest 200, so a wedged head of line starves newer items. D2's stated reason (a single ack would cover every session) is wrong: acks are per inbox item, and items are per subscription. | `gh-signal inbox pending` shows hundreds of items for consumers `squad:<uuid>` of sessions that no longer exist; the loop's per-tick request count grows with sessions; SQLite file growth. | Use one host consumer (`squad:<host>`) and route by `(repository, pull_request)`: one `GET /v1/events` per tick (this also satisfies the requirements' NFR, which D2 as written contradicts), `GET /v1/subscriptions` to diff against live sessions at every reconcile so orphans self-heal, and unsubscribe only when the PR is terminal or the session is archived (not on pause). Two sessions on one PR share one item; route to every matching live session and ack when all are delivered or dropped. Cap how many items a tick will process per PR and ack-drop beyond the cap. Residual (repair 3): a hostname change orphans the subscriptions under the old `squad:<oldhostname>` consumer ID, which the inbox cannot list for us; the operator doc gives the cleanup commands (plan task 2.3, item g). | P2 |

## Verification of plan assumptions

### (a) Does a hand-opened PR populate the session's PR fields? VERIFIED: partly, late, and not the URL
- `report_pr_created` does not write Instance fields: `SetGitHubPR`/`SetGitHubPRNumber` callers outside the poller are `server/services/pr_creation_service.go:305` (Squad's own PR creation), `server/services/session_service_lifecycle.go:826` (RunOneShot output scrape), `server/dependencies.go:1771` (ArtifactExtractor from JSONL history), `session/session_driver.go:891` (`scanAndLinkPRURL`, only for driver-run sessions, and requires `GitHubOwner != ""`), and `server/services/session_service_create.go:896-897` (session created from a PR URL).
- A hand-opened PR gets `GitHubPRNumber` from `PRStatusPoller.fetchAndUpdatePRStatus` (`session/pr_status_poller.go:420`, `SetGitHubPRNumber`): number only, not `GitHubPRURL`. Poll interval 60 s and `NoPRBackoff` 5 min (`session/pr_status_poller.go:63,67`); a no-PR result arms the backoff (`:478-485`).
- `GitHubOwner`/`GitHubRepo` come from worktree detection (`session/instance_actor_setters.go:991-996`) or the GitHub-URL create path. The poller skips `GitHubIsFork` sessions (`session/pr_status_poller.go:323-326`) and sessions with `GitHubPRStatusTerminal` (`:319`).
- Consequence: the consumer must build `owner/repo` from `GitHubOwner`/`GitHubRepo` (not from `GitHubPRURL`, which may be empty), must handle `GitHubHost != ""`, and for fork sessions an owner/repo plus an upstream PR number would address the wrong repo.
- The poller also fills PR fields on backlog work sessions, so D4 overlap is the common case.

### (b) How is a backlog-tracked PR identified? VERIFIED
- `FindPRPendingItems` is `(*EntRepository).FindPRPendingItems` at `session/storage_backlog.go:1133`; it returns items with `status = pr_pending` and `PrNumber > 0` only. Matching to a repo needs `github.GetOwnerRepoFromRemote(item.RepoPath, ...)` per item (`session/backlog_lifecycle_pr.go:1804-1825`, `findPRPendingItemForEvent`).
- #645 acts only on `pr_pending` items (`ReconcilePRPending`, `session/backlog_lifecycle_pr.go:1789-1797`; webhook path via `TriggerPRFixForEvent`).
- A prwatch port can get the same answer without importing `server/services`: `(*Storage).ListItemSessionsBySessionUUIDs` (`session/storage.go:1391`, backed by `session/storage_backlog.go:404`) returns each session's newest `ItemSession` (with item id) in one query; a server-side adapter (like `server/wakes_adapters.go`) can wrap it. Implementable: yes. The choice between "any backlog link" and "item is `pr_pending`" was a plan decision unmade at the time of this pre-mortem; plan D4 now decides it (repair 3, from the code above): only a link to an item in `pr_pending` excludes, because #645 acts only on `pr_pending` items; a session linked to an `in_progress`, `review`, `done` or other item is steered by nothing else and is watched here (the batched query returns only each session's newest link and carries no item status, so the adapter also reads the item's status, `session.BacklogStatusPRPending` at `session/backlog.go:23`). Residuals: the BUG-058 window (PR fields before `pr_pending`) and an item reopened out of `pr_pending` by #645, bounded by the shared guard signature and a catch-up skip after a `pr_pending` exclusion.

### (c) What does `sessionNudgeGuard` dedup on, and is it reusable? VERIFIED
- It dedups on `(session stable ID, signature)`: `TryBegin(id, sig)` (`server/services/session_nudge_guard.go:95-122`): in-flight per session, 60 s duplicate window for a delivered signature, 10 s cooldown after a failed one, 10 min TTL, 1024 records, in memory only (lost on restart). Signature is `string(LinkKey) + "|" + sorted reason names` (`:44-62`), so it dedups by PR plus problem set, not by event id.
- Type and field are unexported: `guardedSteerState.guard` at `server/services/session_service_guarded_steer.go:78`. It is reachable only through `SessionService.SteerInstanceGuarded` (`:121`) and `SteerSessionGuarded` (`:187`), which are also on the `SessionSteerer` interface (`server/services/backlog_service.go:115-119`). The plan's interface list (`SessionProgram`, `IsHiddenSession`, `IsReadyForSteer`, `SteerActiveSession`) omits `SteerSessionGuarded`.
- Outcomes (`SteerOutcome`, `session_service_guarded_steer.go:27-48`): delivered, guard_busy, duplicate, cooling_down, busy, no_status_source, not_tracked, failed. Only delivered is an ack.

### (d) Mid-turn sessions; is `SteerActiveSession` unguarded? VERIFIED
- `IsReadyForSteer` (`server/services/session_service_liveness.go:86`) calls `instanceReadyForSteer` (`session_service_guarded_steer.go:86-106`): false without a status manager or active controller, with queued or current commands, or unless `IsSafeSteerStatus` (`session/idle_status_gate.go:29`: `StatusIdle` plus one of three Claude idle prompt contexts). A mid-turn agent is not ready, so a steer is never written and never queued: `SteerSessionGuarded` returns `SteerBusy` and writes nothing. The item stays pending in the inbox, and nothing retries except the next poll.
- `SteerActiveSession` (`session_service_liveness.go:94`) is unguarded, as its port comment says ("writes message to the session unguarded (verdict steering)", `backlog_service.go:113`): it only resolves the live instance and calls `steerInternal` (`server/services/steer_authorization.go:154`), which takes the write lease and writes. It does not check readiness, hiddenness, the nudge guard, or pane ownership (`SteerInstanceGuarded` comment: pane ownership is verified there "because steerInternal does not do it itself"). For autonomous-mode sessions it uses `SendCommandImmediate` (`steer_authorization.go:190`).
- The guards the new consumer must apply itself if it ever used `SteerActiveSession`: `IsHiddenSession`, `IsReadyForSteer`, per-session in-flight claim, duplicate window, pane-ownership verification. The simpler path is `SteerSessionGuarded` (guard, idle gate, pane-ownership verify, write), plus `IsHiddenSession` before it. The wake path adds a fresh-capture dialog check (`server/wakes/pane.go:38-64`) because the cached status is "blank for 6-9 s after a keypress".

### (e) Where do background services start and stop? VERIFIED: plan location is wrong
- `server/dependencies.go` builds services (`BuildRuntimeDeps`); it does not own goroutine lifecycles. Background loops are started in `wireDepsIntoServer` in `server/server.go` through `srv.goBackground(func(){ ... Start(serverCtx) })` (`server/server.go:174-177`; example hibernation sweeper at `:1351-1358`) or a `Start*(serverCtx, ..., &srv.backgroundTasksWG)` helper, joined by `Shutdown()` (`server/server.go:75`). `server/shutdown_join_test.go:104-135` fails the build on a bare `go` in `wireDepsIntoServer`.
- The wake dispatcher is the precedent for a flag-gated service: `startWakes(serverCtx, srv, deps, ...)` at `server/server.go:772`, `wakeLifecycle` in `server/wakes_module.go` (live-settable flag, started and stopped by the existing 60 s `ReconcileStuck` ticker; ADR-006 rule 6 says no new ticker). The plan's 5 s loop is a new ticker, so it needs its own justification or must ride the wake lifecycle's pattern.
- The wiring test the plan cites exists: `server/dependencies_test.go:270` (`TestBuildRuntimeDeps_should_WireSessionSteererAndSessionStopper_When_ServerBoots`); the steerer wiring line is `server/dependencies.go:1513`.
- No `pr_event_webhooks` constant exists; it is only documented in the `GetFeatureFlag` comment (`config/config.go:1896`). Wake flags have a constants file (`config/wake_flags.go`).

### (f) The other side (gh-signal at `0bab1f6`)
- Key for the CI conclusion: `details.conclusion` (VERIFIED, `crates/gh-signal-core/src/inbox/normalize.rs:377-399`): lowercased token matching `[A-Za-z0-9_-]{1,40}` or `null`. Siblings: `details.status`, `details.ci_kind` (`check_run`|`check_suite`|`workflow_run`), `details.name`, `details.resource_id`. `head_sha` is top-level. `conclusion` is null for in-progress runs.
- `action` is any payload string truncated to 200 chars (`normalize.rs:262-263`), not enum-checked; `actor` is `sender.login` truncated to 200, optional (`:149-153`); `repository` is validated by `is_valid_repository` (`:69`); `kind` is server-assigned. The event `id` is `evt_` plus the first 24 hex chars of the semantic fingerprint (`:426`), so it is stable across redelivery; a redelivered body after ack becomes `duplicate_semantic_event` and creates no new item (`store.rs:ingest`).
- Event multiplicity: CI events are normalized for `check_run`, `check_suite` and `workflow_run` (`normalize.rs:25-26`), so a single failure yields several events with different fingerprints. A check spanning PRs yields one per PR (up to 20). `pull_request` events fire for every action. Comment and review bodies are in the fingerprint, so an edit is a new event.
- Pending growth: unbounded per the doc ("Pending items are never pruned ... A per-subscription pending cap is a planned follow-up", `docs/agent-inbox.md:173-177`). Pruning exempts active-subscription pending items (`docs/agent-inbox.md:186-190`). There is no list-all-consumers route (`routes.rs:93-114`; `GET /v1/subscriptions` requires `consumer_id`), so Squad cannot garbage-collect orphan consumer IDs it no longer remembers. Inactive subscription rows persist.
- Events between PR creation and subscription: lost. `ingest` writes nothing unless an active subscription matches (`store.rs:274-300`, outcome `ignored_unsubscribed`), and the doc says "subscribing after an event does not replay it" (`docs/agent-inbox.md:158-160`). Squad downtime is safe (the subscription stays active and items stay pending); unsubscribing and re-subscribing drops pending items (`store.rs:174-225`, reactivation acks them).
- Subscribe is idempotent for an active subscription (`INSERT OR IGNORE`, `UNIQUE(consumer_id, repository, pull_request)`), repository matching is case-insensitive (`migrations/0004_agent_inbox.sql`, `COLLATE NOCASE`), and acks are per inbox item (`store.rs:444-467`), not per consumer.
- Coverage: the inbox cannot tell a subscriber that no hook exists; only `gh-signal inbox watch` reports `coverage`. Webhook-registered repos on this machine (names only; secrets not read): `tstapler/gh-signal`, `tstapler/stapler-squad` (`~/.config/gh-signal/config.d/95-webhooks.toml`). The inbox is up (`GET http://127.0.0.1:8789/v1/health` returned `ready`) and `~/.local/state/gh-signal/inbox.token` exists with mode 0600. Fork PRs get no CI events (`docs/agent-inbox.md:80-83`).
- INFERRED: with two Squad servers on one machine (the wake code has a leader lock, `server/wakes_module.go:wakeLeaderLockName`), a host-level consumer needs the same leader guard to avoid double steering; per-session consumers do not collide because session UUIDs differ.

### Existing path caveat (context, not a plan error)
- #645 writes GitHub comment text verbatim into the pane (`server/services/backlog_service_pr_fix_steer.go:338` comment "fixContext is unauthenticated GitHub PR/review content written verbatim into the PTY"; `buildSteerMessage` at `:244`). This plan's fixed template is stricter, but the stricter rule does not neutralize the agent re-reading the PR through `gh`.
