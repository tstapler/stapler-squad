## Concerns
- [ ] Story 1.1.1/1.1.2 (Approach B rejection, plan.md Pattern Decisions table) — The plan's rejection of a shared `submitAndClose` wrapper only evaluates a "fat" version (one function that also knows about payload-building and side effects). It doesn't consider — or explicitly reject — a "thin" control-flow-only wrapper, e.g. `async function withSubmitState(fn: () => Promise<void>)` that does *only* `setIsSubmitting(true); setError(null); try { await fn(); } catch(e) { setError(...) } finally { setIsSubmitting(false); }`, leaving each branch's actual logic (session-data building, `addRecentShellCommand`, R2 recovery, `onClose()`) as the passed closure. That thin wrapper would apply uniformly to all 4 same-shaped call sites in this file after the fix — SpawnShell (`:1016-1025`), Alias (`:1061-1069`), default (`:1073-1169`), and the already-correct path-confirmation retry handler (`:1550-1559`, verified — it already has an identical `try/catch/finally` shape and was not called out in the plan's inventory) — without touching the branch-specific bodies the plan correctly says shouldn't be unified. Combined with the plan's own Story 3.1.1 finding that `SessionWizard.tsx:238-253` has the *identical* missing-`finally` antipattern, this exact shape has now recurred independently at least 5 times across the codebase with no compiler/lint enforcement against a 6th/7th recurrence — only hand-copied convention. Not a blocker for this minimal, low-risk bug fix (the duplicated boilerplate is ~4 lines, and the diff-minimization rationale in requirements.md is reasonable), but worth a documented decision either way. **Remediation**: either (a) explicitly note in the Pattern Decisions table that the thin-wrapper alternative was considered and still rejected (state why — e.g. "not worth a fifth abstraction for a bug fix"), or (b) add a lightweight enforcement artifact matching this repo's own precedent (`.claude/rules/go-double-checked-locking.md` codifies an analogous recurring-shape rule for Go) — a short comment at the top of `handleSubmit` stating the convention ("every branch that calls `setIsSubmitting(true)` must reset it in a `finally`") is sufficient; a full helper extraction is not required.

## Nitpicks
- The `try` blocks in the SpawnShell and Alias branches wrap not just `onCreateSession(...)` but also a post-success step (`addRecentShellCommand(shellCommand)` in SpawnShell, `onClose()` in both) inside the same `catch`. If either of those throws *after* `onCreateSession` has already resolved successfully, the user sees "Failed to create session" even though the session was created — misattributing a post-success side-effect failure as a creation failure. This is pre-existing behavior, not introduced or worsened by this plan, and the plan already lists the correct fix as a Follow-Up Suggestion ("surfacing post-success side-effect failures... via the `NotificationContext`/`addNotification` toast system"). No action needed now; flagging only so the follow-up description can cite the exact trigger (`addRecentShellCommand` inside the `try`, after `onCreateSession` but before/around `onClose()`) when it's eventually picked up.
- Task 1.1.3a's reset effect fix and the branch-level `finally` fixes both reset `isSubmitting` on two independent triggers (a settling promise vs. an `isOpen` transition). This is intentional, well-labeled defense-in-depth (matches precedent commit `80f80da22` per pitfalls.md) rather than duplication smell — no change needed, noting only that a future reader should not "clean up" one of the two resets thinking it's redundant dead code; a comment at one of the two sites cross-referencing the other would cheaply prevent that.
