## Concerns
- [ ] The state-leak explanation (`isSubmitting` never resets, so the *next* open shows a stuck button) explains a different observable than the literal bug report. Requirements.md's Problem section says the modal "never dismissed" during the reported session, backed by a live mobile screenshot matching the session's `created_at`, implying continuous observation. `pitfalls.md:45-48` itself hedges this: "the stuck state the user saw may have been the next open, not the same one, which is easy to misreport." That's a plausible reinterpretation of the user's account, not a verified one — nothing in the plan checks session timestamps, screenshot metadata, or asks the reporter to confirm whether they reopened the omnibar before seeing the stuck state. Declaring victory on AC6 without closing this gap compounds the Blocker above. — **Recommendation**: at minimum, note in the plan (not just research) that the "next open" reinterpretation of the report is itself unverified, so a reviewer doesn't read "Unresolved Questions: None" as "we confirmed what the user actually saw."
- [ ] Phase 3 (Story 3.1.1, filing a `SessionWizard.tsx:238-253` follow-up bug) expands scope beyond requirements.md, which never mentions that file — it's a discovery from research (features.md), not an in-scope ask. It's low-cost (tracking only, no code) and arguably justified by this repo's `fix-collateral-debt` convention, but the plan should say so explicitly rather than treating it as if requirements.md authorized it. Also worth noting: `SessionWizard.tsx`'s success path relies on the parent unmounting the component on success ("The parent component will handle navigation," `SessionWizard.tsx:243-244`), which is a structurally different mitigation than Omnibar's long-lived-instance problem — the filed follow-up should say whether that makes it a real bug or a false-positive pattern match, not just cite it as "the SAME anti-pattern."
- [ ] No mention of the `onCreateSession` never-resolving case (hung request, dead network) — under that failure mode `isSubmitting` stays `true` forever and neither the `finally` fix nor the reset-on-close effect helps, since the effect only fires on `isOpen` transitioning to `false`, and nothing drives that transition if the promise never settles and the user doesn't manually dismiss. This is arguably out of scope (requirements.md's ACs only cover resolve/reject), but the plan should say so explicitly instead of silently omitting it, especially since AC6's spirit is "don't leave a real failure mode as an unstated assumption."

## Minors

Not discussed in the plan; low severity given the component's already-intentional long-lived-instance design, but worth a one-line acknowledgment.
