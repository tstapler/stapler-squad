| 4 | Task 1.1.1a's `try` block wraps `onClose()` (and, in the SpawnShell branch, `addRecentShellCommand(shellCommand)`) *after* the awaited `onCreateSession` call. If either of those post-success calls throws for any reason (e.g. a future `addRecentShellCommand` change that touches `localStorage` and hits a quota/serialization error, or a future `onClose`/`close()` implementation that isn't the current trivial `setIsOpen(false)`), the shared `catch` block sets `setError("Failed to create session")` even though the session was already created successfully server-side — actively telling the user creation failed when it didn't, which is a more confusing regression than today's silent stuck spinner. | A user sees an explicit "Failed to create session" error toast/message immediately after a session was in fact created (visible in the session list), and — trusting the error — retries, creating a duplicate session. | Narrow the `try` block (or add a nested try/catch) so only `onCreateSession` failures reach the "Failed to create session" message; treat a post-success `addRecentShellCommand`/`onClose` exception as a separate, non-blocking failure (log it, don't show the creation-failed message) — this is the same gap the plan's own Follow-Up Suggestions section names for `NotificationContext` surfacing but doesn't schedule as a task in this pass. | P3 |
