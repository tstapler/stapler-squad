# Architecture Review: server-services-home-env-race
**Date**: 2026-10-13
**Verdict**: CONCERNS

Scope: test-helper design in `server/services/home_env_test_helper_test.go` (`homeEnvMu`/`stateEnvMu`, `acquireEnvLock` re-entrancy, lock order) and the commit split. Reviewed from plan.md, requirements.md and the helper file; kibitzer not used (test-only change, no package-level structure at stake).

## Constitution Violations
None. `docs/adr/ADR-000-architecture-constitution.md` does not exist in this repo (checked).

## Blockers
None.

## Concerns

- [ ] **Story 1.1.2 / Task 1.1.2a, R3 (lock order)** - The plan's R3 says "VERIFIED no current violation if Task 1.1.2a's grep is clean". It is not clean. `server/services/session_service_create_settings_env_test.go:41-42` calls `withIsolatedStateDir(t)` then `withFakeHome(t)`, i.e. state-then-home, the inverse of the documented order (helper file `:85-86`). Found by scanning the 5 files that call both helpers; this is the only inversion. Remediation: (a) swap the two lines in that test (inside C2); (b) stop relying on a grep audit and enforce the order in `acquireEnvLock`: when acquiring `homeEnvMu`, call `t.Fatalf` if `stateHolders.heldBy(t.Name())` is true and `homeHolders.heldBy(t.Name())` is false. Cost is ~5 lines and it is deterministic, so a future inversion fails at its first run instead of deadlocking under load.

- [ ] **`acquireEnvLock(t, mu, holders)` signature** - `mu` and `holders` are parallel arguments that must be passed as a matched pair; `acquireEnvLock(t, &homeEnvMu, stateHolders)` compiles and silently breaks re-entrancy. Remediation: one type, e.g. `type envLock struct { mu sync.Mutex; holder envLockHolders }` with `func (l *envLock) acquire(t *testing.T)`, and `var homeEnvMu, stateEnvMu envLock`. The AC-mandated names `homeEnvMu`/`stateEnvMu` are preserved; `homeHolders`/`stateHolders` globals disappear (2 fewer package-level vars). Note this must land before C2 since the helper is in that commit.

- [ ] **Re-entrancy by `t.Name()` prefix** - Sound for the current call patterns (verified by reading: holder name is set only after Lock by the owning test; cleanup clears it before Unlock; the `name+"/"` prefix cannot match an unrelated top-level test; `-count=N` reruns are sequential). Two edge cases are not covered by any test and should be documented or tested: (1) if a subtest `A/x` acquires first and parent `A` later calls the helper, `heldBy("A")` is false so `A` takes `Lock()` while `A/x`'s cleanup has already run - fine today only because subtests finish before the parent continues; (2) a `t.Parallel()` subtest cannot call `t.Setenv`, so the pass-through for subtests is only valid for serial subtests. Remediation: add one sentence to the `acquireEnvLock` doc stating "serial subtests only", and add a subtest-first-then-parent case to `TestEnvLock_Reentrant...`.

- [ ] **Doc contradiction on `withIsolatedStateDir`** - Its comment says "at most once per *testing.T" (`:92-93`) but the new re-entrancy supports, and `TestEnvLock_ReentrantWithinOneTestAndSubtests` exercises, multiple calls per `t`. The comment predates re-entrancy. Remediation: reword to "may be called more than once per test; the last call wins and `t.Setenv` restores LIFO".

- [ ] **Task 1.1.2a / R2 and R4 - helper provides no demonstrated protection** - The plan itself concedes (R1, R2) that Go never overlaps two serial top-level tests and `t.Setenv` panics in parallel tests, so the mutexes serialize operations that cannot overlap; the real writer-vs-reader race is a leaked goroutine the locks do not cover. The helper therefore adds ~40 lines of re-entrant locking with nonzero deadlock risk (the inversion above) and zero demonstrated benefit. The requirements fix the scope, so this is not a blocker, but the plan should (a) fix the misleading header comment `:19-26` now rather than leave it to owner approval, since a comment that asserts an impossible interleaving is the next reader's wrong mental model, and (b) make the PR body state "serialization is defensive; root cause is reader-side, tracked by 1.6b". Also R4: `withFakeHome` calls `t.TempDir()` before `acquireEnvLock`, so the directory's `RemoveAll` runs after unlock and after HOME is restored - the exact window in which AC6's "directory not empty" failure occurs. Cheap fix with real effect on that window: in `withFakeHome`/`withIsolatedStateDir`, acquire the lock first, then create the temp dir, so removal runs under the lock (LIFO). Recommend doing it in C2; it is one reorder in two functions.

- [ ] **No regression guard against the next bare `t.Setenv("HOME"|"STAPLER_SQUAD_TEST_DIR")`** - AC1/AC3 are one-time greps; the plan's Story 1.1.1/1.1.3 only re-run them. `NewIsolatedStateDir`'s doc comment is the sole guard, and it is a comment in a non-test package (`envtest`) naming an unexported test helper of a single consumer (`server/services`), a reverse knowledge dependency. Remediation: add a ~30-line `go/parser` test in `server/services` (or an analyzer under `tools/lint/`, matching the `norawghrequest`/`noarchivedrevival` precedent in `.claude/rules/`) failing on `t.Setenv("HOME"`, `t.Setenv("STAPLER_SQUAD_TEST_DIR"` and `envtest.NewIsolatedStateDir(` outside the helper file, with the search-index exception allow-listed by test name. Add as a Story in Epic 1.1 and put it in C2. If declined, drop the envtest doc comment's reference to `stateEnvMu` (internal detail) and keep only "use `withIsolatedStateDir` in server/services".

- [ ] **Commit split C2 (57 files, one commit)** - Needed as one commit for build-green only in part. The helper (`stateEnvMu`, `acquireEnvLock`, exports, 3 new tests) can land alone and compiles, because nothing calls it yet. Splitting gives independently reviewable and revertible pieces: C2a helper + its tests + `envtest` doc; C2b HOME migration (41 sites); C2c state-dir migration (115 + 25 sites). Reviewers then read the helper as design and the rest as mechanical. Remediation: split C2 into C2a/C2b/C2c, staging by explicit file lists generated from `git diff -U0` pattern membership; any file touching both patterns goes in C2c (note the 5 dual-use files, which must also have the order fix).

- [ ] **Per-commit proof is weaker than the claim** - Story 3.1.1's loop runs `go build ./...` and `go vet` only, but the stated goal is "each green on its own". C1 was introduced first specifically so later commits pass `-race`, yet no commit is ever tested. Remediation: in the scratch-worktree loop add `go test ./session/ -race -run TestToInstanceData -count=1` for C1 and `go test ./server/services/ -race -count=1 -run 'WithIsolatedStateDir|WithFakeHome|EnvLock'` for the C2 commits; keep the full `-count=5` only once, on HEAD.

## Nitpicks
- `WithFakeHome`/`WithIsolatedStateDir` exports omit the `Path` and `AsFile` variants; fine today (two external-package files), but state that in the comment so the next external caller extends rather than copies.
- `withFakeHomeAsFile` registers `os.Remove(name)` after `acquireEnvLock`'s cleanup, so removal runs before unlock; this is the correct order and is the pattern the other two helpers should follow (see R4 concern).
- C3 message `chore(sdd): ...` is correct per the Conventional Commits table (hidden from changelog); PR title `fix:` is correct only if the PR is merged as a squash. If merge-commit style is used, release-please sees C1's `fix(session)` and C2's `test(...)` and the title is irrelevant; no action needed, just confirm.
- `go.sum` revert sequencing (Task 2.1.1a) is correct and independent of the helper design; no finding.
