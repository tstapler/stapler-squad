# Adversarial Review: threat-pattern-scan
**Date**: 2026-08-06
**Verdict**: BLOCKED

## Blockers

- [ ] **Automated (non-interactive) callers of `TriggerTriage`/`SpawnSessionFromItem` silently swallow the new threat-scan block — a false-positive item can get permanently stuck with zero visibility.** The plan wires the block as a plain `error` → `connect.CodeInvalidArgument` at `BacklogService.initialPromptFor`/`triagePromptFor`/`reviewPromptFor` (Epic 3.1), reasoning in ADR-001 that "each has exactly one call site of its own... the ripple is contained." Verified against the actual code that this framing undercounts the blast radius: `TriggerTriage` and `SpawnSessionFromItem` are each invoked by *multiple further upstream automated callers*, none of which surface the new error visibly:
  - `MaybeTriggerTriage` (`server/services/backlog_service_triage.go:2110-2124`, called automatically from `backlog_service_sync.go:262`, `backlog_service_lifecycle.go:209`, and `server/mcp/tools_backlog.go:1111,1174` — i.e. on every item creation/sync, not a user click) does `log.WarningLog.Printf(...)` and `return false` on error — no item-state change, no stuck marker, no notification. A legitimate item whose title/description happens to trip a pattern (pitfalls.md §2's own worked example: a bug report *about* "ignore previous instructions" is the highest-fidelity trigger for this exact scanner) simply never gets auto-triaged again, silently, forever.
  - `AutoReopenForPRFix` (`backlog_service_triage.go:~1836`) rolls the item back to `pr_pending` "so the reconciler can retry" on `spawnErr != nil` — for a permanent false positive this is an infinite silent-retry loop (WarningLog spam each cycle), never surfacing a distinct blocked state.
  - `TriggerTriage`'s own `AutoSpawnSession` opt-in branch (`~line 2431`) does `log.WarningLog.Printf(...)` on `spawnErr != nil` and continues — the auto-spawn intent is silently dropped.
  - Contrast with `ReviewGateRunner.Run` (Epic 3.3), which correctly reuses the proven `RunPreGateSecurityCheck` pattern: FAIL verdict recorded, notifier fired, fed into `AutoReopenAfterFailedReview`/`notifyReworkCapHit` — a real, visible unblock path. The other three sites get none of this.
  - This is precisely the failure mode research/pitfalls.md §4 flagged and asked to be resolved *explicitly* in the plan phase ("does the item just never get a session created — i.e., does it silently vanish from the actionable queue with only a log line?"). The plan's Pattern Decisions table and Unresolved Questions section never revisit this question — it was asked and never answered.
  - **Recommendation**: either (a) route the triage/initial-prompt block through the same stuck-item/notification machinery the review-gate path uses (e.g. mark the item with a distinct `StuckReason` your reconciler already understands, per `.claude/rules`/memory on the backlog stuck-review investigation), or (b) at minimum have `MaybeTriggerTriage` and the other silent-swallow sites promote a threat-scan-specific error to a stuck/notify path instead of a bare `WarningLog.Printf`. Either way, this needs to be an explicit decision, not an implicit consequence of "the ripple is 1 call site."

- [ ] **No enforcement stops a future direct caller of the 4 `Build*` functions from silently bypassing scanning entirely.** ADR-001 deliberately leaves `BuildSessionInitialPrompt`, `BuildHeadlessReviewPrompt`, `BuildHeadlessTriagePrompt`, `BuildHeadlessRetriagePrompt` with unchanged plain-`string` signatures — verified none of them currently carries any doc-comment warning (`session/backlog_context.go:123`, `session/backlog_review.go:307`, `session/backlog_triage.go:53-55` all have plain descriptive doc comments only). research/pitfalls.md §3 explicitly named this exact risk and its own fix: *"If chosen [call-site scanning over builder-internal scanning], the plan needs a grep-based or lint-based check (a test asserting every `Build*Prompt(` call site in the repo is preceded by a `threatscan.Scan` call) so a missed site fails CI instead of shipping silently unscanned."* The plan's task list has no such test, and Task 3.4.2a's doc-comment addition lands only on the *new* `session/threat_scan.go` file — not on the `Build*` functions themselves, which is where a future contributor adding a new call site would actually be looking. Today's 6-site coverage is grep-verified accurate (confirmed independently), but nothing stops tomorrow's regression.
  - **Recommendation**: add a `// SECURITY:` doc-comment line to each of the 4 `Build*` functions pointing at `session.ScanItemForThreats` and the 6 existing call sites, and add the grep/ast-based CI guard test pitfalls.md §3 explicitly asked for (even a simple test enumerating known-good call sites and failing if a new non-test `Build*Prompt(` call site appears elsewhere would close this).

## Concerns

- [ ] **The "1 call site each" framing in ADR-001's Pattern Decisions table undersells the actual blast radius.** As detailed in the blocker above, `TriggerTriage`/`SpawnSessionFromItem` (the sites `initialPromptFor`/`triagePromptFor`/`reviewPromptFor` feed) are themselves each called from 3-5 further automated sites with heterogeneous, mostly silent error handling. The signature-change ripple is compiler-contained (1 call site), but the *behavioral* ripple — what happens when that 1 call site starts returning a new kind of error — is not, and isn't traced in the plan.
- [ ] **AC2's "no false positive on legitimate AGENTS.md-style content" test doesn't use the repo's actual `AGENTS.md`.** This repo has a real root-level `AGENTS.md` file (verified: `/home/tstapler/Programming/stapler-squad/AGENTS.md`, a copy of `CLAUDE.md`'s content). Task 1.2.1d instead uses paraphrased `sddInitialPromptTemplate` and `.claude/rules/fix-flaky-tests-dont-defer.md` prose. Those are reasonable proxies, but a literal read-and-scan of the real `AGENTS.md` (or a representative excerpt of it, e.g. its "WARNING: `make install-service` restarts..." imperative-heavy section) is a stronger, more literal fixture that's sitting right there and costs nothing extra to add.
- [ ] **Pathological-unicode input isn't tested.** Task 1.2.1e tests the 65,536-char truncation bound but not truncation mid-multi-byte-rune (`s[:maxScanChars]` on a byte-length string can split a UTF-8 rune) or invalid-UTF-8/zero-width/RTL-override input generally. Go's `regexp` (RE2) doesn't panic on invalid UTF-8, so there's no crash risk, but there's no test asserting the truncation-boundary behavior is what's intended, and no test exercising the "known gap" (Unicode confusables) the package doc comment claims to disclaim — worth at least one smoke test proving `Scan` doesn't panic on adversarial unicode, even though full confusable-normalization is correctly out of scope.
- [ ] **Requirements.md's explicit design fork (pitfalls.md §4, second bullet) is unresolved: is `strict` scope even the right scope for backlog fields?** Hermes's `strict` scope assumes curated content (memory writes, skill installs); this repo's backlog items are filed by whoever discovers a bug, including bug reports that quote injection payloads for documentation. The plan silently proceeds with `strict` scope for all 6 sites without recording a decision on this trade-off (the Unresolved Questions section covers back-testing against real data, which is adjacent but not the same as this scope-choice question).
