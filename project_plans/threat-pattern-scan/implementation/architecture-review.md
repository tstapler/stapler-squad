# Architecture Review: threat-pattern-scan
**Date**: 2026-08-06
**Verdict**: BLOCKED

## Constitution Check

`docs/adr/ADR-000-architecture-constitution.md` does not exist in this repo (verified: `test -f` returns not found). No constitution-derived BLOCKERs apply; skipping that section.

## Blockers

- [ ] **Epic 3.4 / ADR-001 coverage claim** — The plan's central claim ("every real caller of the four `Build*` functions funnels through exactly one of six orchestrator/wrapper functions," and Epic 3.4's stated goal of proving 100% custom-pipeline-mode coverage) is **false**. `session/pipeline_engine.go:70-72` — the `PipelineEngine` interface itself, the exact interface the plan audited — lists `SlashCommandSet(item *BacklogItemData) (map[string]string, error)` as a method, documented in its own doc comment as producing "the filename→rendered-content map that `WriteSlashCommands` writes to `.claude/commands/backlog/`." `CachingPipelineEngine.SlashCommandSet` (`session/pipeline_engine.go:336-375`), on any non-default `PipelineMode`, renders `item.Title`/`item.Description` (via `itemPlaceholders`, line 353) **and AC criterion text** (`c.Text`, unsanitized, line 368) into `DoneCommandTemplate`/`FailCommandTemplate`/etc. — content that later becomes a slash-command file the agent reads and can be invoked as instructions (`/backlog/done-N`, `/backlog/status`, etc.). This is squarely "content injected into agent context," the exact hazard requirements.md's item #4 names. None of the plan's 6 call sites scan before this path executes:
  - `server/services/backlog_service_sync.go:94` — `AttachSessionToItem` calls `session.WriteSlashCommands(s.pipelineEngine, item, worktreePath)` **directly**, with no prior call to `ScanItemForThreats`/`initialPromptFor`/any scanned wrapper anywhere in that RPC handler (verified: `grep -n "WriteSlashCommands\|WriteBacklogContextFile\|initialPromptFor\|ScanItemForThreats" backlog_service_sync.go` shows only the two `Write*` calls, no scan). `WriteBacklogContextFile` runs *after* `WriteSlashCommands` in this function (line 98, after line 94) and per the plan gets a scan added inside it (Task 3.2.2a) — but by then the poisoned slash-command files are already written to disk, and a later error from `WriteBacklogContextFile` does not delete them.
  - `server/services/backlog_service_triage.go:1382-1389` (`writeSessionFiles`, called from `spawnSessionAfterGates` at line 783) also calls `WriteSlashCommands` then `WriteBacklogContextFile` — in this path the earlier `initialPromptFor` scan at line 759 does run first and would block before `writeSessionFiles` is reached, so `SpawnSessionFromItem`'s path is *not* exploitable. Only the `AttachSessionToItem` path is a live gap.
  
  **Remediation**: Add a 7th wiring point — either (a) call `session.ScanItemForThreats(item)` at the top of `AttachSessionToItem` before its `WriteSlashCommands`/`WriteBacklogContextFile` calls (matching the guard-clause style used elsewhere), or (b) better, add the scan inside `WriteSlashCommands` itself (`session/backlog_commands.go:31`), mirroring Task 3.2.2a's placement inside `WriteBacklogContextFile` — this covers both callers (`AttachSessionToItem` and `writeSessionFiles`) from one place and needs no signature change (the function already returns `error`). Either way, Epic 3.4's "proves — not just asserts — 100% coverage" integration test (Story 3.4.1) must also exercise `SlashCommandSet`/`WriteSlashCommands`, not just `triagePromptFor`, or the proof itself is incomplete.

- [ ] **ADR-001's "no change ripples into `pipeline_engine.go`'s methods" framing is the root cause of the above gap, not just its symptom** — ADR-001 explicitly chose guard-clause scanning at 6 hand-enumerated call sites over touching `PipelineEngine`'s interface, reasoning "no change ripples into `pipeline_engine.go`'s five `PipelineEngine` methods" (the interface in fact has 6: `SlashCommandSet`, `TriagePromptFor`, `ReviewPromptFor`, `InteractiveReviewPromptFor`, `InitialPromptFor`, `ContentHashFor` — the ADR's own count is off by one, a small but telling sign the interface wasn't fully enumerated during the decision). research/pitfalls.md §3 (per plan.md's own citation) already identified "fan-out risk" as the reason to avoid scanning inside the 4 `Build*` functions or their ~15 call sites — but the same fan-out risk reappears one layer up: 6 manually-enumerated wrapper call sites is still a hand-maintained list that can (and did) miss a site, exactly the failure mode the plan was designed to avoid. A GoF Decorator wrapping `PipelineEngine` (`type scanningPipelineEngine struct { next PipelineEngine }`, one method per interface method, each scanning `item` before delegating to `next`) would have made the guarantee structural — every current *and future* `PipelineEngine` method is covered by construction, with a compile error if a new interface method is added and the decorator isn't updated to implement it. This is the PoEAA/GoF pattern this ADR's problem shape actually calls for, and the plan's Pattern Decisions table does not consider it as an alternative (only "scan inside builders" (A) vs. "scan at every grep-found call site" (B) are listed) — see Lens 3 discussion below.

## Concerns

- [ ] **Story 3.4.2 doc-comment claim would be inaccurate as specified** — Task 3.4.2a's planned doc-comment text ("Because every strict-scope call site here scans *before* delegating to `PipelineEngine`'s `*PromptFor` methods, a custom `PipelineMode`'s `renderTemplate`/`itemPlaceholders` path... is covered") asserts complete coverage while omitting `SlashCommandSet`, which uses the same `itemPlaceholders`/`renderTemplate` machinery but is not one of the "`*PromptFor` methods" the sentence names. If the Blocker above is fixed, this doc comment must be updated to explicitly include `SlashCommandSet`/`WriteSlashCommands` in its coverage claim, or it will overclaim exactly the kind of "no completion claim without proof" gap this repo's own engineering discipline flags.
- [ ] **`Result.Scope` field naming is ambiguous** — Task 1.1.1e's `Scan` implementation sets `Result.Scope = p.minScope` (the *pattern's* activation threshold), not the scope the caller passed to `Scan`. A reader of `Result.Scope` at a call site (e.g. in a log line) would reasonably assume it reflects "the scope this scan ran at," not "the narrowest scope this specific pattern requires." Not a functional bug, but worth a one-line doc comment on `Result.Scope` clarifying which of the two it is, since both are legitimate interpretations of the field name.
- [ ] **Story 3.1.3 / `reviewPromptFor` scans `verificationNotes` but the custom-mode template branch never renders it** — `CachingPipelineEngine.ReviewPromptFor`/`InteractiveReviewPromptFor` (`session/pipeline_engine.go:402-445`) only pass `itemPlaceholders(item)` plus `criteria_count` to `renderTemplate` on the custom-mode branch — `verificationNotes` is never substituted into a custom template today. Scanning it anyway (as planned) is harmless (a strict superset scan, no false negatives introduced) but means the doc/comment should not claim "`verificationNotes` is scanned because it reaches the custom-mode prompt" — it doesn't, for custom modes. Purely a documentation-precision nitpick, not a functional gap, but worth getting right given the "no completion claim without proof" discipline this review is graded against.

## Nitpicks

- Pattern Decisions table's "Package API shape" row (plain function over interface) and the "Shared registry with `session.secretPatterns`" row (explicitly not merging with `pkg/threatscan`) both correctly apply `.claude/rules/interface-pollution-checklist.md` — no speculative interface, no premature generic. Good discipline, no changes needed.
- `pkg/threatscan`'s zero-import, pure-function design (Task 1.1.1a-e) correctly respects the `pkg/` vs `session/` vs `server/` layering — `pkg/threatscan` has no `session`/`server` imports, `session.ScanItemForThreats` is the sole `session`-layer consumer, and `server/services` calls into `session`, never the reverse. No layer-coupling violation.
- The plan's own Pattern Decisions table already flags and defends against the "half-adopted, fan-out miss" risk pattern (row: "Where to run the strict-scope scan") — the irony that the same risk reappeared at the wrapper layer (see Blockers above) is worth feeding back into `research/pitfalls.md`-style thinking for future items: enumerating call sites by reading one interface's declared method set is more reliable than enumerating them by reading call-site source files, since the interface is the actual contract surface.
