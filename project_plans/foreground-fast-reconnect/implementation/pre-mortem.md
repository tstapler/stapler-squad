# Pre-mortem: foreground-fast-reconnect
**Date**: 2026-08-09

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The `foreground` false→true transition resets `terminalBackoffRef`'s internal attempt counter and `foregroundConnectAttemptRef`, but does **not** touch or reschedule the already-pending `reconnectTimerRef` timeout (the backoff-delay wait computed *before* the user switched to this terminal). A user who selects a terminal that is currently sitting out an old, long backoff delay (computed while it was backgrounded — up to `BackoffState`'s 30s cap) still has to wait out that stale delay before `connect()` is even called; the fast 1200ms connect-timeout only bounds the attempt once it starts, not the wait beforehand. This is the exact scenario the feature exists for (user switches to a stalled terminal and stares at it) and it is not covered by the plan's "snapshot-at-schedule-time" Pattern Decision, which only discusses an in-flight *connect attempt*, not a pending *wait-to-reconnect* timer. | A user selects a session that was disconnected while backgrounded and sees the terminal sit idle/blank for several seconds (up to ~30s) with no visible reconnect activity, then finally reconnects fast once the attempt starts — logs show a large gap between the `foreground=true` transition and the first `connect()` call for that instance. | In the transition effect (`useTerminalStream.ts`, the new `useEffect([foreground])`), when flipping false→true, also clear any pending `reconnectTimerRef` and immediately invoke `connectRef.current()` (or reschedule it with a 0ms delay) instead of only resetting the counters for the *next* delay computation. Add a unit test: schedule a long pending `reconnectTimerRef` while `foreground=false`, flip to `true`, and assert `connect()` is invoked well before the original delay would have elapsed. | P1 |
| 2 | `1200` is an unvalidated guess — the plan's own Domain Glossary admits herdr-web's real `TERMINAL_FOREGROUND_CONNECT_TIMEOUT_MS` "isn't inspectable" and the value was "re-derived directly from the AC's own numbers," not measured against real connection-establishment latency (VPN, corporate proxy, remote dev over higher-RTT links). If real first-message latency for a healthy connection regularly exceeds 1200ms on such networks, every foreground reconnect attempt 1-2 gets aborted and retried needlessly, producing *more* churn and handshake overhead for foreground terminals — exactly the terminals a user is watching — than the pre-feature single-3500ms baseline. The Observability Plan explicitly adds no metrics ("none added... out of scope"), so this regression would be invisible in production; the only signal is the very `console.warn` line the plan adds, which nobody monitors. | Users on VPN/remote-dev connections report reconnects feeling "flappier" or terminals repeatedly flashing disconnected/reconnected after this ships with the flag on, with no dashboard or log-based way to confirm the cause without manually grepping browser consoles. | Before enabling `NEXT_PUBLIC_RECONNECT_V2` broadly, validate `FOREGROUND_CONNECT_TIMEOUT_MS` against real p95/p99 connect-to-first-message latency (e.g. a temporary counter of `trigger=connect-timeout foreground=true` log lines, or a one-time manual test over a VPN/high-RTT link) rather than shipping the AC's lower-bound number unmeasured. At minimum, note in the PR description that 1200ms is a starting guess subject to tuning, and file a follow-up to add a lightweight success/failure counter for connect-timeout-triggered aborts. | P1 |
| 3 | A `setTimeout`-based connect-timeout races the async message-delivery path: if the first stream message arrives in the same tick window the timer fires (plausible right around the 1200ms boundary for marginal-but-healthy connections), `attemptController.abort()` can fire concurrently with — or a beat before — the `firstMessage` block's `clearTimeout`, producing a connect-then-immediately-disconnect flicker instead of a clean connection. This disproportionately affects the population closest to the 1200ms cutoff: users whose connections are *just barely* fast enough to succeed under the old 3500ms budget but not comfortably under the new fast one. | Intermittent, hard-to-reproduce single-cycle disconnect/reconnect flashes immediately after a session is selected, worse on marginal-latency connections, that a user can't correlate to any action they took. | Add an explicit ordering guard: in the connect-timeout callback, check whether `firstMessage` is still `true` (i.e. re-read the same flag the success path checks) immediately before calling `attemptController.abort()`, so a message that already landed (even if `clearTimeout` hasn't run yet due to scheduling order) short-circuits the abort. Add a regression test that pushes the first message and fires the timer in the same `act()` batch to lock in "message wins the race." | P2 |
| 4 | This feature ships entirely inert: the whole mechanism only activates inside `NEXT_PUBLIC_RECONNECT_V2 === "true"` branches, and that flag defaults off (`web-app/.env.local.example:1`). The plan's Risk Control section treats "ships dark by default" as a safety feature but the plan has no activation plan, owner, or timeline for actually turning it on for real users — nothing forces anyone to revisit it. The GitHub issue this traces to can be closed as "done" while zero production users ever experience the fast reconnect, and the underlying UX complaint remains unfixed indefinitely. | A month post-merge, `grep NEXT_PUBLIC_RECONNECT_V2` in the deployed build config still shows it unset/off, and the original issue reporter says the terminal still reconnects slowly when they switch sessions. | Add an explicit rollout step to `plan.md`'s Risk Control or a follow-up backlog item: name who/when decides to flip `NEXT_PUBLIC_RECONNECT_V2` on (even just "dogfood on personal deployment for N days, then flip for all"), so shipping this code isn't silently conflated with shipping the fix. | P2 |
| 5 | Test coverage (Epic 4.1/4.2) only exercises the synthetic `makePushStream` mock's cooperative `AbortSignal` handling under controlled, single-step `jest.advanceTimersByTime` calls — it never exercises React 18 double-invoked effects (dev StrictMode mount/cleanup/remount) or rapid, same-tick `foreground` prop churn (e.g. fast keyboard-driven session switching flipping `foreground` true→false→true before a single microtask flush). If the real `connectTimeoutRef`/`attemptController` capture has a subtle ordering bug only StrictMode's extra mount/unmount cycle or rapid re-renders expose, it ships undetected because nothing in Phase 4 targets that shape of interaction. | Occasional, non-reproducible-in-manual-testing reports of a terminal getting "stuck" briefly in `CONNECTING` or double-connecting right after very fast session-switching (e.g. rapid arrow-key navigation through a session list), that don't reproduce under the existing single-attempt-at-a-time test suite. | Add one test that renders under `<React.StrictMode>` (or manually double-invokes the mount effect, per RTL's documented pattern) and one that flips `foreground` twice within the same `act()` call before any timer advances, asserting exactly one live `connectTimeoutRef`/`abortControllerRef` pair exists afterward. | P3 |

## P1 Items (address before implementation)
- [x] Failure #1 — Addressed in `plan.md` (Task 2.2.1b, AC3): the foreground false→true transition effect now also clears any pending `reconnectTimerRef` and invokes `connect()` immediately (guarded by `shouldReconnectRef`/not-already-connecting/not-already-connected), instead of only resetting the attempt counters. Task 4.2.1f adds the regression test proving a stale backoff wait does not survive the transition.
- [x] Failure #2 — Addressed in `plan.md`'s Risk Control section: `1200`ms is now explicitly documented as an unvalidated starting guess (not a measured value), with a required pre-broad-rollout validation step (measure real p95/p99 connect-to-first-message latency on VPN/high-RTT links) and a named follow-up (lightweight connect-timeout-abort counter) if dogfooding surfaces flappiness.

## P2 items addressed during triad review (not required to be P1-blocking, fixed anyway)
- [x] Failure #3 — Addressed in `plan.md` Task 2.3.1b: the connect-timeout callback now re-checks `firstMessage` before calling `attemptController.abort()`, so a message landing at the timeout boundary wins the race. Task 2.3.1e adds the regression test.
- [x] Failure #4 — Addressed in `plan.md` Risk Control: named activation owner (`tstapler`, sole active maintainer) and an explicit dogfood-or-file-follow-up requirement, so the flag-flip doesn't silently fall off the radar.
