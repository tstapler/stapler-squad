# Validation Plan: foreground-fast-reconnect

**Date**: 2026-08-09

## Happy Path Scenario
Given a session terminal that is the one currently selected/displayed (`foreground` transitions `false → true`) and whose reconnect attempt stalls with no first message received, when `connect()` schedules the attempt's connect-timeout via `connectTimeoutMs(foregroundRef.current, foregroundConnectAttemptRef.current)`, then the attempt is abandoned after `FOREGROUND_CONNECT_TIMEOUT_MS` (1200ms) rather than `CONNECT_TIMEOUT_MS` (3500ms), `attemptController.abort()` fires, and the existing `terminalBackoffRef`-driven retry path reconnects — so the terminal the user is actually looking at recovers roughly 3x faster than a backgrounded one would.

## Test Stack
- **Unit**: Jest + `@testing-library/react` (`renderHook`, `act`, `waitFor`), `jest.useFakeTimers()` for timer-driven assertions — matches the existing conventions in `web-app/src/lib/hooks/__tests__/useTerminalStream.test.ts` and `web-app/src/lib/utils/backoff.test.ts`.
- **Integration**: Same Jest/RTL stack; "integration" here means multi-boundary hook-level tests that exercise the full `connect()` → timer → abort → backoff → retry → mocked-`streamTerminal` cycle (or a component render pulling `TerminalOutput` → `useTerminalStream`), as opposed to isolated pure-function or single-effect unit tests. No real network/WebSocket or backend process is involved — `streamTerminal` is mocked via `mockStreamTerminal.mockImplementation(...)` and `makePushStream`'s extended `AbortSignal` support (Epic 4.1).
- **E2E / UX**: N/A — no new UI affordance (see requirements.md Non-goals: "does not add a UI affordance/indicator for 'fast reconnecting'"); no `design/ux.md` exists for this project.
