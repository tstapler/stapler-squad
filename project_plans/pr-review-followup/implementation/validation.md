# Validation Plan: pr-review-followup

**Date**: 2026-08-02

## Happy Path Scenario

Given a `pr_pending` backlog item whose PR has green CI, no conflicts, and no prior
`PrFeedbackAddressedAt` watermark, when GitHub Copilot leaves a substantive
`COMMENTED`-state review on it and `ReconcilePRPending`'s next 60s tick runs, then
`hasNewFeedback` evaluates true, `remediatePRFixWithBackoffGate` dispatches the same
`AutoReopenForPRFix` fix-session path used for `CHANGES_REQUESTED` reviews today, and
`PrFeedbackAddressedAt` is persisted to the review's `submittedAt` so the identical
feedback does not re-trigger a fix session on the next tick.

## Test Stack

- **Unit**: Go `testing` package + table-driven tests — this repo's existing convention in `worktree_git_test.go` (`TestParsePRStatusPayload_*`) and `backlog_stuck_rpc_test.go` (`TestToProtoStuckReason_*`).
- **Integration**: Go `testing` + ent test fixtures — `session/ent_repository_backlog_test.go` pattern (real SQLite/test-DB-backed round trips, not mocked), plus `backlog_lifecycle_test.go`'s mock-`prCreator`-backed `ReconcilePRPending`/`pushAndCreatePR` tests (these count as integration in this repo's existing test taxonomy since they exercise the storage layer + multi-method control flow, not a single pure function).
- **E2E / UX**: manual checklist only. No Playwright test is required for this backend-focused change — the only user-visible surface touched is a `Record` map keyed by a TS enum (`stuckReason.ts`), which the TypeScript compiler exhaustiveness-checks at build time; the one genuinely dynamic behavior (a `pr_needs_fix` item actually appearing on `/unfinished` with a working "Retry now" button) is covered by the manual acceptance check above, not an automated E2E spec, because provoking a real `pr_needs_fix` stuck state end-to-end would require a live GitHub PR with a live Copilot review — out of proportion for this Small-appetite extension.

## Coverage Targets and How to Measure

| Stack | Coverage command | Target |
|---|---|---|
| Go | `go test ./session/... ./server/... -coverprofile=coverage.out && go tool cover -func=coverage.out` | ≥80% line coverage on touched packages (`session/git`, `session`, `server/services`); 100% branch coverage on the new `hasNewFeedback` gate and `isSubstantiveFeedback` predicate specifically, since both are single-line boolean expressions where an untested branch is cheap to close |
| Frontend (compile-only gate) | `cd web-app && npx tsc --noEmit && npx jest --no-coverage --testPathPatterns="stuckReason"` | No numeric coverage target — the `Record<StuckReason, T>` type is the enforcement mechanism; the pass/fail signal is "compiles" + "existing exhaustiveness test still passes with the new enum member added to `ALL_REASONS`" |

- All public/exported surfaces touched by this plan — `PRStatus.HasReviewFeedback`, `PRStatus.LatestFeedbackAt`, `(*GitWorktree).RequestCopilotReview`, `toProtoStuckReason`/`fromProtoStuckReason` — have both a happy path and an error/negative path covered above.
- The one external integration this plan adds (`gh pr edit --add-reviewer`) has both a unit test with a mocked `prCreator` AND the mandatory real, non-sandboxed dry-run (Story 5.1.2) — the plan explicitly calls out that the research sandbox's stub response for this exact call was suspicious and must not be trusted as evidence.
- Migration test: **N/A** — additive nullable ent column (`pr_feedback_addressed_at`), no backfill, no reversible-migration section in plan.md requiring one. The ent round-trip integration test above (`TestEntRepositoryBacklog_PrFeedbackAddressedAt_should_RoundTrip`) incidentally exercises the auto-migration path (fresh test-DB schema creation includes the new column) but is not itself a dedicated migration test.
