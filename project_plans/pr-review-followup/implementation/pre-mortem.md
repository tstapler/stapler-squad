# Pre-mortem: pr-review-followup
**Date**: 2026-08-02

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Coarse-grain watermark dedup: a batch tick with N feedback items (e.g. Copilot review at T1 + human comment at T2) spawns one fix session; if it only addresses a subset, the watermark still advances to `LatestFeedbackAt` (max of all N) after dispatch, so the unaddressed remainder is never re-detected — GitHub never clears `COMMENTED` reviews/plain comments, and nothing downstream re-checks per-item resolution. | A PR sits merged-pending with a visibly unaddressed review comment thread on GitHub, but the backlog item shows no stuck reason (`resolveStuckLogged` already fired) — an operator has to notice the stale comment manually, exactly the failure requirements.md was written to eliminate. | Already known (ADR-001/adversarial-review). Elevate adversarial-review's Concern-1 recommendation (b) from optional to required: log "N items included in this dispatch's context" (item IDs/authors) whenever `hasNewFeedback` triggers a spawn covering >1 substantive item, and add an acceptance test asserting the log fires for a 2-item batch. This doesn't fix the miss but makes it discoverable in logs instead of silent, and gives an operator a lead when a PR looks stuck. | P1 |
| 2 | `copilot-pull-request-reviewer[bot]` literal login used by `RequestCopilotReview` turns out not to be a valid/functioning reviewer login in the deployment org (stack.md flagged this as UNVERIFIED end-to-end — the sandboxed research environment's `gh pr edit` returned an "ok edited"-shaped response without demonstrably touching `reviewRequests`). Because the call is wired best-effort (log+notify, non-fatal per Pattern Decisions), it fails silently on every PR forever. | Every ship-flow PR logs a `RequestCopilotReview failed` warning (Task 5.1.1c's pattern), and no PR ever accrues a `COMMENTED` review from `copilot-pull-request-reviewer[bot]` going forward — the entire comment-feedback signal this project adds has nothing to detect for Copilot specifically, undermining the project's own motivating example. | Story 5.1.2's dry-run (Task 5.1.2a/b) must be a blocking pre-ship gate, not an informational check with an "not expected, but this is the check" fallback. Add a named contingency to Story 5.1.2: if the literal login doesn't add Copilot as a reviewer, fall back to the raw `gh api` reviewer-request REST endpoint (already identified as an alternative in requirements.md's Rabbit Holes) before this phase is marked done. | P2 |
| 3 | The shared `effectiveReworkCap = 3` budget is consumed by comment-feedback-driven fix sessions (nits, style suggestions) before a genuine CI-driven fix ever gets its 3rd attempt — pitfalls.md §3 named this explicitly; adversarial-review logged it as an accepted trade-off with no test, not a plan defect. | An item flips to `StuckReasonReworkCap` shortly after a run of `feedback=true` dispatch log lines, with the actual CI failure never having been retried 3 times — visible only by cross-referencing the dispatch log's `(CI=%v, reviews=%v, conflict=%v, feedback=%v)` line history, not from the stuck-reason UI alone. | Add the log-line cross-reference as a first-class debugging aid: when `AutoReopenForPRFix`'s rework-cap gate denies a spawn, log which trigger type(s) consumed the prior attempts (derivable from the existing per-tick log line if attempts are tagged). This was flagged as a "one-line note" nit in adversarial-review's Minors — this pre-mortem elevates it to a required Observability Plan addition given it directly obscures the root cause of a `StuckReasonReworkCap` item. | P2 |
| 4 | `PrFeedbackAddressedAt`'s watermark write (Task 3.1.2c) is a separate `UpdateBacklogItem` call after `remediatePRFixWithBackoffGate` confirms dispatch, not atomic with the attempt-recording write (architecture-review Concern 3). A crash/restart landing between the two loses the watermark advance while the rework-budget attempt is already consumed. | After an unplanned service restart, the same `feedback=true` content re-triggers a fix session on the next backoff-due tick for a PR whose feedback was already addressed in a prior attempt — visible as two dispatch log lines with an identical `LatestFeedbackAt` value bracketing a service restart timestamp in `journalctl --user -u stapler-squad`. | Document as an accepted residual risk in the plan (architecture-review's own recommendation) rather than leaving Story 3.1.2's acceptance criteria silent on it. If cheap, fold the watermark write into the same transaction/call `remediatePRFixWithBackoffGate` uses for `RecordRemediationAttempt` rather than a follow-on `UpdateBacklogItem`. | P3 |
| 5 | `isSubstantiveFeedback`'s length-only filter (`>= 10` runes) has no author check — `generalComments` captures every PR comment unconditionally regardless of author, so a long-enough automated bot comment (coverage bots, CodeQL, Dependabot, e2e report bots — none excluded anywhere in the plan) counts as "substantive feedback" and can independently trigger `hasNewFeedback` on every push that bot re-comments, burning rework-cap slots on non-actionable text. Not identified in either existing review. | Fix sessions spawn repeatedly with `feedback=true` on PRs where the only new "feedback" since the last watermark is a recurring automated bot comment (e.g. "Coverage decreased (-0.1%) to 95.3%") that a competent fix agent cannot meaningfully act on, consuming `maxAutoReworkIterations` without addressing the actual CI/review signal. | Add an author-based exclusion (or explicit allowlist of "human or Copilot" logins) to the substantiveness check before Phase 1 ships — extend `isSubstantiveFeedback` or add a sibling predicate checked at the same call site in Task 1.1.2d/1.1.2e. Add a regression test with a synthetic known-bot comment author (e.g. `github-actions[bot]`, `codecov[bot]`) asserting it does not set `HasReviewFeedback`. | P2 |
