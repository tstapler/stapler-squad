# Adversarial Review: pr-review-followup
**Date**: 2026-08-02
**Verdict**: CONCERNS (was BLOCKED; sole blocker resolved 2026-08-02 during triage — see resolution note below)

## Blockers

None remaining.

### Resolved

- [x] **Task 1.1.2d's zero-value timestamp fallback creates a silent, permanent dedup blind spot for exactly the class of feedback this project exists to catch.** Resolved by patching `plan.md` Task 1.1.2d to use recommendation (b): on parse error, log a warning and fall back to `at: time.Now()` instead of the zero value — `time.Now()` can only push `LatestFeedbackAt` later, never mask a real later item under an already-persisted watermark. Added a new required test (`TestReconcilePRPending_HasNewFeedback_UnparseableTimestampStillAdvancesWatermark`) to Story 1.1.4's acceptance criteria proving the compound scenario (parse failure + pre-existing non-zero watermark) still sets `hasNewFeedback == true`. Trace: if `time.Parse(time.RFC3339, r.SubmittedAt)` fails, the plan says "log+skip the timestamp on parse error... but still append with a zero `at`." Task 1.1.3a's max-timestamp computation (`LatestFeedbackAt = max over substantive commentReviews/generalComments`) means a zero-value `at` only "wins" the max if it's the *only* substantive item present. Once the watermark (`item.PrFeedbackAddressedAt`) already reflects a **later, real** timestamp from prior addressed feedback, any *new* substantive comment/review whose timestamp also fails to parse contributes `at = zero` to this tick's max — which never exceeds the already-real, already-persisted watermark. Result: `LatestFeedbackAt` doesn't advance, `.After()` is false, `hasNewFeedback` stays false, and the item takes the *healthy* branch (`resolveStuckLogged`) — **the new feedback is silently never detected as a trigger**, even though `render()`/`FeedbackText` includes its body unconditionally (so it's visible to a fix agent only if some *other* reason happens to spawn a session, and otherwise invisible forever). This is the "stuck forever, ignoring genuine feedback" failure mode requirements.md names as the project's single highest risk — just the inverse direction (silent miss, not infinite respawn) from the risk ADR-001 explicitly reasoned about. It is also self-contradictory on its face: Task 1.1.2d's own text claims to match "the 'fail loudly, don't silently zero-value' concern from stack.md/pitfalls.md §4" while describing the literal opposite (log + skip + silently zero-value). Pitfalls.md §4 is explicit: "any new fields parsed from that payload should fail loudly (return an error from `parsePRStatusPayload`) rather than silently zero-valuing" — this task does not do that.
  **Recommendation**: On parse failure, either (a) return an error from `parsePRStatusPayload` per pitfalls.md §4's explicit guidance (loudest, matches documented codebase convention for `gh` payload brittleness), or (b) if degrading gracefully is preferred, fall back to `time.Now()` (a local timestamp that is guaranteed to be *later* than any prior GitHub-issued watermark, so the item is never silently excluded from the max) rather than the zero value — with a clear code comment on why `time.Now()` is safe here specifically (it can only ever push `LatestFeedbackAt` later, never mask it). Either way, add a test proving a second, later substantive item with an unparseable timestamp still causes `hasNewFeedback` to go true when the watermark already reflects earlier feedback — the plan currently has no test for this compound scenario (only `TestParsePRStatusPayload_HasReviewFeedback_*` in isolation, none combining a parse failure with a pre-existing non-zero watermark).

## Concerns

- [ ] **Approach 1's documented coarse-grain gap plausibly violates requirements.md's explicit dedup constraint, not just ADR-001's own risk tolerance.** Concrete trace requested by this review: Copilot posts review A ("fix X") at T1; a human posts comment "fix Y" at T2 > T1, same polling tick, before any fix session runs. `LatestFeedbackAt = T2`. One fix session spawns (Story 3.1.1's gate fires once). If it only addresses "fix X" — because that's what the prompt emphasized, or it ran out of budget/turns — the watermark still advances to T2 post-dispatch (Task 3.1.2c). Next tick: `commentReviews`/`generalComments` still contain both A and B (GitHub never clears `COMMENTED` reviews/plain comments), so `LatestFeedbackAt` recomputes to the same T2, `.After()` on the now-equal watermark is false, and the item resolves to healthy — `resolveStuckLogged` fires, `StuckReasonPRNeedsFix` clears. "Fix Y" is never re-surfaced by anything short of a *new* GitHub comment with a timestamp > T2 (i.e., a human manually noticing and re-posting). ADR-001's Consequences section names this exact grain problem and accepts it, reasoning that `FeedbackText` puts both items in the same fix session's context so "a competent fix session addresses the batch together." That's an assumption about agent behavior, not a guarantee, and requirements.md's Constraints section states the mechanism "must distinguish 'new/unaddressed' comment-only feedback from feedback already factored into a prior fix attempt" — this design never actually verifies anything was factored in; it assumes a spawned session covers everything with a timestamp at or before dispatch time. The distinction is between "attempted to address" and "verified addressed," and the design implements the former while the requirement's language implies the latter.
  **Recommendation**: This is a legitimate, plan-documented trade-off (not a silent gap) and the appetite (Small, 1-3 days) argues against building per-comment ID tracking now — so CONCERN rather than BLOCKER. But the plan should either (a) tighten the requirements-vs-ADR language mismatch explicitly in the plan doc (state plainly that "factored into" means "included in context," not "confirmed addressed"), or (b) add a cheap mitigating signal: e.g. log a warning distinguishing "N items included in this dispatch's context" so an operator scanning logs for a stuck-looking PR has a lead on partial coverage, even without full per-ID dedup.

- [ ] **No dedicated regression test verifies the new trigger inherits the `closeIfSupersededByMain` (BUG-032/036) protection.** Pitfalls.md §4 flags this as a load-bearing trap: the superseded-PR guard runs upstream of the fix-spawn call and is trigger-agnostic *only if* the new trigger flows through the same shared `if` gate rather than an early-return/parallel branch. The plan's implementation (Task 3.1.1b: extend the existing `if !CIFailing && !HasBlockingReviews && !HasConflicts` condition with `&& !hasNewFeedback`) is structurally correct — it's the same single gate, not a new branch — so the protection is very likely inherited by construction. But nothing in Phase 3 or Phase 6 adds a test that actually exercises "hasNewFeedback=true AND PR is superseded by main" to confirm `closeIfSupersededByMain` still fires and no fix session spawns against a stale diff. Given how explicitly pitfalls.md called this out as a "don't break it" trap, its absence from the test list is a real coverage gap, not a hypothetical one.
  **Recommendation**: Add one test alongside Story 3.1.1/3.1.3's tests: a `pr_pending` item with `hasNewFeedback=true` whose PR is also superseded by main — assert `closeIfSupersededByMain`'s existing behavior (PR closed, item routed off the feedback-fix path) takes precedence over the new trigger, exactly as it does today for CI/reviews/conflicts.

- [ ] **Story 5.1.2's "real dry-run verification" task has no defined fallback or merge-blocking gate if the literal Copilot bot login turns out not to work.** stack.md flagged that the sandboxed research environment's `gh pr edit --add-reviewer` call returned a suspicious "ok edited"-shaped response without demonstrably touching `reviewRequests` — i.e., the entire assumption that `copilot-pull-request-reviewer[bot]` is a valid, functioning reviewer login is UNVERIFIED end-to-end as of plan-writing time. Story 5.1.2 exists (Tasks 5.1.2a/5.1.2b) and correctly identifies the need to verify against a real PR, but its acceptance criteria only says to "capture the exact `gh` error text" and Task 5.1.2b says a fix "may produce a follow-up task ... not expected, but this is the check" — there is no defined action if verification fails (e.g., fall back to `gh api` reviewer-request REST endpoint directly, or the `@copilot` alias with version detection previously rejected in Pattern Decisions). Since `RequestCopilotReview` is wired best-effort (log+notify, doesn't fail PR creation), the blast radius of shipping a broken literal login is bounded — worst case, the feature silently never requests a review and only a warning log/notification signals it — but the plan should not treat "verify it" as equivalent to "and if it's broken, do X."
  **Recommendation**: Add an explicit contingency line to Story 5.1.2 or the Pattern Decisions table: if the dry-run shows the literal login doesn't add Copilot as a reviewer, the fallback is [named alternative], not an open-ended "follow-up task."

- [ ] **Requirements.md's explicitly named Rabbit Hole — Copilot review-request idempotency when Copilot is already a reviewer or has already completed a review — has no corresponding acceptance criteria or test in Phase 5.** Story 5.1.1's acceptance criteria cover exactly two cases: Copilot code review enabled (success) and not enabled for the org (non-zero exit, wrapped error, non-fatal). Neither covers the specific idempotency scenario requirements.md called out by name: what happens if Copilot is already configured as a required reviewer at the repo/org level (a scenario the requirements' own Problem Statement raises) and `--add-reviewer` is called again — does `gh pr edit` error, no-op, or duplicate-request? Since `pushAndCreatePR` calls this exactly once per PR (not per-tick), the blast radius is small, but it's still a named-and-then-dropped requirement.
  **Recommendation**: Either add a third acceptance-criteria case (Copilot already a reviewer → best-effort call still doesn't error the ship flow) with the corresponding test, or explicitly note in the plan that this was investigated and found to be a non-issue (e.g., `gh pr edit --add-reviewer` on an existing reviewer is a documented no-op) with a citation — currently it's neither tested nor explicitly waived.
