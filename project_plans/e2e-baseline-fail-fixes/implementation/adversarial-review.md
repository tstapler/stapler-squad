## Concerns

- [ ] **"open terminal here" Phase 1 assumption has no fallback task** — Task 1.1.3 classifies this test as fixed by the keychain stub and marks it as "Expected: test passes." But the root cause is explicitly INFERRED in the research ("Root cause hypothesis"), not VERIFIED. The fix path in the features research doc also says "If `SessionType.DIRECTORY` creation has an additional dependency, that must also be stubbed." If Task 1.1.3 fails (session creation fails for a non-keychain reason — tmux socket, git worktree init, missing binary, etc.), there is no fallback task: Story 3.1 investigates only the symlink test, not open-terminal. Task 3.2.1 then unconditionally marks all 4 local-file-browser entries as `"class": "pass"`, which would corrupt the baseline and create a new gate failure. Recommend: add an explicit investigation sub-task to Story 3.1 that covers the "open terminal here" test if Task 1.1.3 does not confirm a pass, with a concrete fallback (assertion update matching actual nav, or identify the additional stub needed).

- [ ] **AC-5 accepts "pass or skip" but the plan produces a third outcome** — AC-5 requires the 2 route-focus skip-link rows to "transition to pass or skip." The plan removes them from the baseline (Task 3.2.2) so they classify as `removedFromRun` (severity "report") rather than "pass" or "skip." The pitfalls research confirms this is not a gate failure, so it is functionally acceptable — but it technically violates AC-5's acceptance criterion as written. If the compare script's behavior ever changes, or if AC-5 is audited strictly, this will be flagged as an unmet criterion. Recommend: either add a `test.skip(...)` guard to any remaining skip-link test code (in case the test was partially deleted), or update AC-5's wording to accept `removedFromRun` as a valid terminal state.

- [ ] **AC-02 and AC-05 investigations have no concrete fallback if the tests fail unexpectedly** — Story 2.2 runs the two tests and says "if either fails, diagnose from trace and fix locator." The pitfalls research identifies a timing risk for AC-02 (the success toast may fire and clear before the `expect` assertion, causing `saveAlias()` to throw under slow CI). The features research says "No label mismatch" for both tests — but that is not the same as "these tests will pass." If AC-02 or AC-05 fail for a timing or state-transition reason (not a locator mismatch), there is no pre-planned fix path. The plan would stall at Task 2.2.1. Recommend: explicitly record the timing risk in Task 2.2.1's failure scenario and add a concrete conditional fix (e.g., add `waitFor` after save, or switch to polling assertion) to avoid open-ended debugging during implementation.

- [ ] **Features research identifies lines 65 and 130 of the route-focus spec as needing `isBunBuild` guards, but the plan omits this fix entirely** — `research/features.md` section 3 states both tests ("the announcer is role=status..." at line 65 and "/history: duplicate main#main-content..." at line 130) fail in the Bun build because `useFocusOnNavigate` is a no-op without Next's router. The baseline JSON (18 entries for this spec) has these tests under "(Bun only)" prefixed titles with class "skipped" — meaning they were skipped in the Next build when the baseline was captured. Under the current spec structure (no "(Bun only)" describe prefix), if these tests now run with new names, the comparator cannot match them against the "(Bun only)" baseline entries and they will be treated as new tests with no baseline protection. If they fail in Bun CI, that is a gate failure not addressed anywhere in this plan. Recommend: either add a Story to apply `test.skip(isBunBuild, ...)` to lines 65 and 130, or verify (by checking baseline entry counts before and after CI) that the comparator still maps them correctly and classifies them as excluded.

## Minors

- **Locator strategy inconsistency between research and plan for the Advanced checkbox** — `research/features.md` says the fix for the Advanced checkbox should be `page.getByRole("checkbox", { name: "Advanced" }).check()`. The plan (Task 2.1.1) instead uses `page.getByLabel("Advanced").check()`. Playwright resolves `getByLabel` via the wrapping `<label>` element, so both work, but they test slightly different DOM relationships and diverge from the explicit recommendation in the research document without explanation. If the label becomes explicit (`aria-label="Advanced"`) and the wrapping `<label>` is removed, `getByRole` is more robust.

- **mockProvider thread-safety is assumed, not guaranteed** — The pitfalls research says the mock store is safe "in practice" because no e2e test calls `SetJulesAPIKey` through the UI. This is a brittle assumption: a future e2e test touching Jules settings could trigger a concurrent `Set`/`Delete` without singleflight serialization, causing a data race. The plan notes the assumption but takes no action on it. Acceptable for now, but should be documented as a constraint on future Jules e2e tests.

- **Task 3.2.1 specifies a Python mutation approach without providing the script** — "use `python3 -I -c '...'` to load the JSON, mutate the class fields for matching entries, and write back" is an implementation note with no actual script. The JSON has 357 "fail" entries across many specs; matching by `{spec, project, title}` is non-trivial. A missing or incorrect match silently skips an entry, leaving a stale "fail" that blocks CI. Provide the full Python invocation or switch to a jq command that can be copy-pasted directly.

- **Baseline skip-link entry title in the plan does not match the actual JSON value** — The plan describes the entries as `"skip link: Tab reaches it, Enter activates it"` but the actual baseline JSON title is `"skip link: Tab reaches it, Enter keeps the path and sets the hash"`. This discrepancy won't cause implementation failure (the removal can search by partial match), but it indicates the plan was not verified against the actual JSON value before writing, which slightly undermines confidence in other count claims.

- **Baseline entry counts in Task 3.2.1 are stated, not verified** — The plan says "10 entries (5 tests × chromium + chromium-dom)" for jules-dispatch and "6 entries (AC-02, AC-04, AC-05 × 2 projects)" for alias-settings. These are plausible but have not been confirmed by a grep/count against the actual baseline JSON. If the counts are off by one (e.g., a test exists only in chromium and not chromium-dom), the edit script will produce a baseline that doesn't match what CI actually sees. Recommend running `grep -c '"jules-dispatch.spec.ts"' next-e2e-baseline.json` before writing the edit script.
