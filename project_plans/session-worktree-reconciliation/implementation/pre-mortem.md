# Pre-mortem: session-worktree-reconciliation
**Date**: 2026-09-23

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Flag ships default-`false` (per plan's Risk Control) with no owner or deadline to flip it — Epic A's code exists but never runs, so the reported PR #625 problem is never actually solved, only "made fixable in principle." | Weeks after ship, `logs/staplersquad.log` has zero `worktree_consistency_sweep` lines and `get_notification_history` has zero matching entries; a new PR #625-shaped incident recurs and a human again fixes the DB by hand. | Make "flag flipped to `true` after a defined burn-in window" an explicit exit criterion of the project, not just "code merged." Add a dated follow-up task/backlog item at ship time (owner + date) to flip the default, mirroring how `feedback_rollout_flags_live_settable_no_env_vars.md` expects flags to be live-managed, not "set once and forgotten." | P1 |
| 2 | `classifyIssues`'s `IssueMissingWorktreeRow` branch only fires when a live `git.ListWorktrees` entry exists to match against (Story 1.2.2, task 1.2.2a); if the on-disk worktree is *also* gone by the time the sweep runs — the plan's own Epic-A-alternatives text concedes PR #625's row "was already missing by the time anyone looked" — `Worktree == nil` and zero live entries means **no issue kind fires at all** (the repo_path/base_commit_sha checks in 1.2.2b/1.2.2c both key off `candidate.Worktree.*`, which doesn't exist when `Worktree == nil`). The regression test in Epic 1.4 only reproduces the easier variant (row missing, disk worktree present), so this gap ships un-caught. | A session in the exact "row and directory both gone" state produces zero `WorktreeConsistencyFinding`s, tick after tick, forever — silently indistinguishable from a healthy session in the sweep's logs. | Add a 4th detection branch: `Worktree == nil AND ExpectsWorktree(data) AND matchLiveWorktree` returns 0 candidates → emit `IssueMissingWorktreeRow` with `Resolution = ResolutionFlagged` (nothing to repair from) instead of silently skipping. Add a second Epic 1.4 regression fixture for the double-missing case, since it's the harder and more historically accurate reproduction of the reported incident. | P1 |
| 3 | The 15-minute sweep's candidate query, `ListInstanceDataWithWorktree` → `EntRepository.ListWithOptions`, is a genuine full unfiltered table scan (confirmed: `session/ent_repository.go:1494-1496`'s `//nolint:entfullscan` comment — "the base list all sessions query genuinely needs every row") with no status/archived filter and no time bound — every session ever created stays in the scan set forever, and `classifyIssues`'s base-commit-sha check calls `git.CommitInfo` → `OpenRepo` (`session/git/ops.go:481`, `git.PlainOpenWithOptions`) fresh per candidate, un-cached, un-pooled across repos or ticks. Cost grows monotonically with total historical session count, not "current live sessions," and the plan has no per-tick time budget, no overlap guard, and "Metrics: none new." | Sweep tick duration (visible only via the one per-tick summary log line, if anyone looks) grows quarter over quarter; eventually two ticks overlap or a tick starves other git operations on a shared repo during a 15-minute window. | Filter candidates by status (exclude terminal/archived sessions, which have no live-tracking need) before the git-truth pass; add a per-tick duration + candidate-count log as an operational signal (already planned for candidate/issue counts — extend it to duration); add a single-flight/overlap guard so a slow tick can't stack with the next. | P2 |
| 4 | Repair is gated by *two* independent conditions — the feature flag AND `config.IsIsolatedInstance()` (Story 1.3.3) — but the plan's Risk Control section describes them as one linear "flip the flag, watch, then default it on" rollout story. An operator who flips the flag on a manual/isolated dev instance to "try out" repair behavior will only ever see `ResolutionFlagged` outcomes and reasonably conclude repair is broken; an operator who flips it on the primary instance to "just see what it finds" gets live `Worktree` table writes on the very first tick with no dry-run step in between. | Operator files a bug ("flag doesn't repair anything") against working-as-designed isolated-instance behavior, or is surprised by an unplanned DB write on the primary instance during a "let's just look" trial. | Document the flag+instance-isolation interaction explicitly next to the flag (config description/tooltip) and in Risk Control; consider a separate dry-run/detect-only toggle so "turn on the sweep" and "let it start writing" are two distinct, deliberate steps — this also gives the staged-rollout narrative already in the plan an actual mechanism to burn in notifications before any writes occur. | P2 |
| 5 | Epic B's fix for `cleanupItemWorktreesExcept` is exactly one more `NOTIFICATION_TYPE_WARNING` + `log.Warn` into the same generic panel/history this codebase has already documented as easy to miss (`project_backlog_stuck_review_investigation.md`'s "non-durable notify-once state" root cause for a prior, structurally identical problem) — and it fires during item *archival*, i.e. after the user's attention has already moved on. No on-disk cleanup is attempted ("there is no known path to remove without the row," task 2.1.1b), and there's no durable, actionable record beyond the notification log — no `MarkStuck`-equivalent, since the item is already terminal. | Worktree directories keep leaking on disk at the same rate as before the fix; the only difference from the pre-fix state is an ignorable WARNING sitting in `get_notification_history` that nobody queries. | Tag this notification distinctly (a filterable category) so it can be swept in bulk later, or — since Epic A's `ExpectsWorktree` + full-table-scan candidate listing (Failure #3) would otherwise already re-examine this same archived session — route the leaked-directory signal into Epic A's sweep instead of a one-shot notification, so it's periodically re-surfaced rather than fired once and forgotten. | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — **Severity corrected to P1 during the Product Triad Review pass** (originally shipped with no Severity value in the table — a table-formatting gap, not a deliberate P2 classification; the Product lens independently flagged this exact risk as a blocker: a project that ships every acceptance criterion while the reported PR #625 problem remains completely unprotected in practice, because nothing ever flips the flag, does not actually solve what it was built for). **Resolved during the triad repair pass**: plan.md's Risk Control section now states a concrete, dated flip-on decision rule instead of "consider flipping the default."
- [x] Failure #2 — Add a 4th `classifyIssues` branch for "`Worktree == nil` and zero live git-worktree matches," emitting a flagged (not silently-skipped) finding, and add a corresponding double-missing regression fixture to Epic 1.4 alongside the existing single-missing one. Without this, the plan's own regression test (Story 1.4.1) proves detection of an easier case than the one PR #625 actually presented. **Resolved during Phase 4**: plan.md's Story 1.2.2 AC + Task 1.2.2a now specify the zero-match → `ResolutionFlagged` branch explicitly, and new Story 1.4.2 (Tasks 1.4.2a/b) adds the double-missing regression fixture.

## Summary
2 P1, 3 P2, 0 P3 (Failure #1's severity was corrected from an unfilled table cell to P1 during the Product Triad Review pass — see "P1 Items" above). Top failure mode: `classifyIssues`'s missing-row detection requires a live `git.ListWorktrees` match to fire at all, so the harder, more historically accurate PR #625 shape — DB row **and** on-disk worktree both already gone by the time the sweep runs — produces zero findings and ships completely undetected, while Epic 1.4's regression test only proves the easier variant. Both P1s are now resolved in plan.md.
