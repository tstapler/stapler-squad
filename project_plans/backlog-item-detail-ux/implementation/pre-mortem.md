# Pre-mortem: backlog-item-detail-ux
**Date**: 2026-07-21

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `DescriptionSection` defaulting to collapsed treats the item's description as "secondary," but for a solo user re-orienting on an item he hasn't looked at in hours/days, the description is often the *first* thing he needs — collapsing it by default turns "glance at the panel" into "click Description, then glance," a net increase in clicks for the single field checked on nearly every open, undermining the plan's own "fewer clicks" premise for exactly the field it's most true for. | Tyler notices he expands `DescriptionSection` on almost every item he opens within the first few days, i.e. the "collapsed by default" state is never actually the steady state for that section. | Before merging Story 3.1.3, spend one real day dogfooding item opens and count how often Description gets expanded; if it's near-100%, flip its default to expanded (treat it as primary content like `ActionsSection`/`PlanningSection`, not secondary) rather than assuming collapsed-by-default is correct for every section uniformly. |
| 2 | `useShowMore`'s caps (5 sessions / 8 workflow events / 8 progress notes) are **not** persisted (plain `useState`, re-collapses on every mount per Task 3.1.4c2) and were sized without measuring real stuck-item session counts — but the items Tyler most needs full history for are exactly the heavily-cycled, stuck ones (the `df0d5872` example itself has 11 linked sessions). Every time he re-opens a problem item to check on it — which for a stuck item happens repeatedly over days — he re-pays the "Show N more" click, on the exact section this project exists to make inspectable. | Tyler notices he clicks "Show N more" on the same handful of chronically-stuck items every single time he re-checks them, not just once. | Persist the show-more expansion state the same way `useSectionExpandState` already persists collapse state (`localStorage`, keyed by `itemId` + section), or auto-set `showAll=true` for items already flagged by `useStuckBacklogItems()` (they're precisely the ones where full history is the point) instead of applying a flat cap universally. |
| 3 | `classifySessionKind()` is a hardcoded, closed set of prefix-string checks with a **silent fallthrough**: anything not matching `headless-`/`review-blocked-`/`diff-error-`/`manual-review-` and `role === "review"` classifies as ordinary `"review"` (rendered as a live clickable `<a href="/?session=...">`). This project fixes today's two known dead-link prefixes, but the classifier has no defensive default — a *new* synthetic-session prefix introduced later (this codebase adds new session-lifecycle constructs roughly every 1-2 months per the session-creation-registry's changelog) will silently fall through to the clickable branch and reproduce the exact dead-link bug Story 1.1.3 was built to fix, with no test failing because the new prefix by definition isn't in `sessionKind.test.ts` yet. | Tyler clicks a session row that looks like a normal review session, and it opens to a blank/broken terminal view because there's no backing `session.Instance` — the same failure this project shipped to eliminate, just for a session kind that didn't exist yet when the plan was written. | Instead of (or in addition to) the adversarial review's "shared constant" fix, make the fallback fail *safe*, not fail *open*: if a `LinkedSession` has `role === "review"` or `"triage"` but its `sessionId` doesn't match a known real-session ID shape (i.e. doesn't look like a plain session UUID) AND it carries `reviewVerdict`/`triageResult` with no session ever having started, classify it as a generic synthetic/diagnostic kind (routed to `BlockedNotice` with "Unrecognized session type — showing recorded verdict") rather than defaulting to the clickable `"work"`/`"review"` branch. Add a test asserting an unrecognized prefix never resolves to a clickable link. |
| 4 | Task 1.1.1's acceptance criterion that collapsed content is **removed from the DOM, not just hidden**, combined with `ReviewingSection` (containing `GateVerdictBox`'s live Approve/Reopen/Override/Skip Gate/Re-review buttons) being wrapped in the shared `CollapsibleGroup`/`Accordion.Root`, creates a real interaction hazard the test suite won't catch: the existing 5-second poll (`BacklogItemDetail.tsx:243-249`) only suspends for `editMode`/`showManualReview` (Task 3.1.3c) — not for an in-flight action inside `ReviewingSection` (e.g. clicking Approve). If a poll-triggered re-render recomputes `defaultExpanded` while an Approve/Override request is in flight, the section (and its pending-state spinner/disabled button) can unmount mid-request, leaving Tyler unsure whether the click registered — a plausible trigger for an accidental double-submit of a verdict action with real backend side effects (re-running review, consuming rework-cap budget). jsdom unit tests won't reproduce this because they don't model a real network round-trip racing a real poll interval. | During a normal review-approval click, the panel visually flickers/collapses and Tyler is unsure if his Approve/Override actually went through, so he clicks again — and later notices the item shows two review-verdict events for one click, or a rework-cap decrement he didn't expect. | Extend the same polling-suspend pattern Task 3.1.3c adds for `showManualReview` to also cover any pending action inside a `Collapsible`-wrapped section with a live mutation (i.e. suspend polling whenever `actionLoading` is true, not only whenever a form is open), and add a regression test: given `actionLoading === true` for a `ReviewingSection` action, when a poll tick fires, then the section stays mounted/expanded and the pending button state is preserved. |
| 5 | Story 5.1.0's new status label plus Story 5.1.1's compact `BlockerChip` are each individually justified, but stacked together on `BacklogItemCard` — already carrying title, priority badge, AC summary, and an action button — they add two more always-on text elements to a card whose entire value is fast visual triage across many cards at once. The new status label is frequently near-redundant with the existing action-button text (e.g. status "Review" sitting next to a button reading "View Review"), so it reads as line-noise more often than as new information, working against the requirement's own "no duplicated or contradictory indicators between the two" framing by introducing a *new* on-card duplication (label vs. button) while fixing the old detail-view one. | Tyler notices scanning `/backlog/board` takes a beat longer than before — every card now looks similarly "busy," so the one item that actually needs attention doesn't stand out at a glance the way it used to. | Before shipping Story 5.1.0 unconditionally, render a card for each status side-by-side (mock or screenshot) and check whether the new status label is ever a near-duplicate of the action-button text; if so, suppress the separate status label for those statuses (the button text already carries the information) rather than always rendering both, keeping the card's added-text budget to one new element (`BlockerChip`), not two. |

## P1 Items (address before implementation)
- [x] #2 — Resolved in plan.md: Task 3.1.4c2's `useShowMore` is now `localStorage`-persisted (key `backlog-detail-showmore-${itemId}-${sectionKey}`), same convention as `useSectionExpandState`.
- [x] #4 — Resolved in plan.md: Task 3.1.3c now extends the polling-suspend condition to `actionLoading !== null` (not just `editMode`/`showManualReview`), with a regression test covering `ReviewingSection` staying mounted during an in-flight action.

## Summary
2 P1, 3 P2, 0 P3. Top failure mode: `useShowMore`'s non-persisted 5/8-item caps re-collapse on every re-open, so the chronically-stuck, multi-session items this project was built to make inspectable are exactly the ones where Tyler pays a "Show N more" click every single time he checks on them — a direct regression against the project's own stated success metric for its hardest cases.
