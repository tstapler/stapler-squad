# Research: Feature Landscape — backlog-item-detail-ux

## 1. Existing "progressive disclosure over a complex entity" patterns in this codebase

Three distinct patterns already exist and are usable as precedent — no need to invent a fourth:

### Pattern A: native `<details>/<summary>` (lightest weight, built-in a11y)
- `web-app/src/components/sessions/GoalPanel.tsx:120-154` — the whole panel is a `<details>` with a `<summary>` row containing a status chip + label. Body (goal text + task tree) only renders visibly when expanded; browser handles `aria-expanded`/keyboard for free. Also does **text truncation with a "more/less" toggle** for a long `goalText` (`MAX_GOAL_DISPLAY_LENGTH = 120`, lines 106-110, 129-140) — directly relevant to "very long description/plan text" edge case.
- Also used in `SuggestedRuleCard.tsx:201` and `ErrorState.tsx:68` for secondary/debug info (stack traces, source commands) that's rarely needed.
- **Best fit for**: single self-contained panels where the summary line alone (chip + label) is enough to convey state, and body content doesn't need imperative open/close control from a parent.

### Pattern B: click-to-expand card + separate detail component (accordion, imperative state)
- `web-app/src/components/backlog-stuck/StuckItem.tsx` (card, `isExpanded`/`onToggleExpand` props owned by parent) + `StuckItemDetail.tsx` (body, rendered only `{isExpanded && ...}`). Card is `role="button"` + `tabIndex={0}` + `aria-expanded` with full keyboard handling (Enter/Space to toggle, Escape to collapse, lines 136-147) and **focus restoration to the toggle control on collapse** (lines 126-134, "AC 29" comment) — a real a11y detail worth reusing verbatim.
- `web-app/src/components/unfinished/UnfinishedItemDetail.tsx` is an explicit sibling ("mirrors UnfinishedItem.tsx" per `StuckItemDetail.tsx:24` docstring) — same accordion shape for worktree/session detail.
- **Best fit for**: list contexts where the parent needs to track which of several items is expanded (e.g. accordion-of-sections within one detail view, only one open at a time), or where expand state must be driven by something other than the DOM (e.g. deep-linking to an open section).

### Pattern C: hover-media-query-gated inline controls
- `StuckItem.tsx:77-96` (`useHoverUnavailable`) — detects `(hover: none), (pointer: coarse)` to switch always-visible-icon-button vs. hover-reveal controls. Relevant to the mobile requirement (per `feedback_mobile_desktop_ux` memory) since `BacklogItemDetail` currently has no touch-vs-hover affordance handling at all.

### Layout precedent for the detail panel itself
- `web-app/src/app/backlog/page.tsx:594-603` renders `BacklogItemDetail` inside a **resizable `<aside>`** (`detailPane`), not a modal — `web-app/src/app/backlog/backlog.css.ts:206-221` sets `minWidth: 240px`, `maxWidth: 800px` on desktop, and flips to a `position: fixed; inset: 0` full-screen overlay at `max-width: 768px`. Any redesign must read well as narrow as 240px on desktop and as a full-screen mobile sheet — the "at a glance" summary can't assume wide layout.

## 2. Concretely duplicated fields in BacklogItemDetail.tsx (file:line citations)

File: `web-app/src/components/backlog/BacklogItemDetail.tsx` (1577 lines, 12 unconditional/conditional sections rendered in the `scrollArea` div, lines 756-1573).

### D1 — Lifecycle status
- Header badge: `item.status` → `getStatusLabel`/`getStatusClass`, **line 710-714**.
- Card-level action button label is entirely status-derived (`getActionSpec` switch in `BacklogItemCard.tsx:24-51`) but the **card itself never shows the status label/badge** — only an action-button microcopy proxy for it. This is the flip side of the duplication problem: the *detail* view repeats status 3+ times while the *card* doesn't show it clearly at all, so board and detail are inconsistent in the opposite direction (see Scope: "Board/list cards show status consistent with the detail view").
- Implicitly re-derived via section visibility conditionals scattered through the file (`item.status === "review"` **line 828**, `item.status === "pr_pending"` **line 922**, `item.status === "idea"` **line 772/784**, etc.) — the reader has to mentally reconstruct "what state am I in" by scanning which of ~6 conditionally-rendered blocks fired, rather than reading it once.
- `item.statusEvents` (Workflow timeline, **line 1476-1496**) — the *last* entry's `toStatus` is redundant with the header badge; the whole timeline is effectively "how did status get to what the header already says," but there's no visual link between the header value and the timeline's terminal node.

### D2 — Acceptance criteria (pass/fail)
- `AcCriteriaList` component fed `item.acCriteria`, "Acceptance Criteria (`done`/`total`)" section, **line 975-980**.
- `GateVerdictBox`'s `criteria` prop fed `item.gateCriteria` (pass/fail per criterion, **line 882-893**; rendered as `<ul className={criteriaList}>` in `GateVerdictBox.tsx:256-262`), shown only when `item.status === "review"`. `gateCriteria` and `acCriteria` are two separately-fetched/typed fields (`AcCriterion[]` vs `{label,passed}[]`) describing overlapping information — the same criteria, evaluated by two different mechanisms (manual AC tracking vs. automated gate verdict), rendered in two different visual styles with no cross-reference.
- The "Acceptance Criteria (done/total)" heading count (**line 977**) is a third independent tally of "how much is done" alongside the gate verdict's own pass/fail count.

### D3 — Work/review session identity + links
- "Reviewing" section (only when `status === "review"`) computes and links `workSession` and `activeReviewSession` inline, **lines 828-868** (recomputed via `[...item.linkedSessions].reverse().find(...)`).
- "Sessions" section, **lines 1312-1442**, re-renders *every* linked session including the same work/review sessions already surfaced above, with fuller metadata (branch, date, cost, pipeline mode, verdict detail).
- The "Actions" section's `in_progress` case independently recomputes "the current work session" a third time to build a "View Session" link, **line 1074**: `[...item.linkedSessions].reverse().find(s => s.role === "work") ?? item.linkedSessions[...]`.
- `latestWorkSession` (module-level derived state, **line 190**) is a *fourth* independent computation of "the current work session," used for `ReviewChangesModal`/`BacklogFileBrowserModal`/`VcsWidget`'s `worktreePath` (**line 907, 1303**).
- Net: "which session is the current one" is computed independently at least 4 times in slightly different ways (some exclude `headless-`/`review-blocked-` synthetic IDs, some don't — see edge cases below), with no single source of truth.

### D4 — PR / pull-request info
- "Pull Request" section (`status === "pr_pending"` only), shows `item.prUrl`, `item.prNumber`, **lines 922-960**.
- `VcsWidget` (Version Control section, `mode="full"`, **lines 1296-1305**) independently renders PR/CI/review info via `fromShipStatus`/`fromSessionVcs` adapters (`web-app/src/lib/vcs/adapters.ts:135-168`), which includes its own PR URL, check conclusion, approved/changes-requested counts — overlapping with the "Pull Request" section's `item.prUrl`/`item.prNumber` but sourced from a different field path (`shipStatus` vs. `item.prUrl` directly) and only shown for non-`pr_pending` statuses in practice (since VCS falls back through `vcsStatus`→`shipStatus`).
- "Ship PR" action button (Actions section, `status === "review"`, **lines 1094-1110**) references PR creation without linking to either of the above once one exists.

### D5 — Session cost
- Per-session `s.estimatedCostUsd` shown inline per row, **lines 1345-1346 / 1368-1369**.
- `item.totalEstimatedCostUsd` shown as an aggregate directly below the session list, **lines 1443-1447**. (Not a bug — aggregate + line items is reasonable — but worth folding into a single "cost" affordance in the redesign rather than two separately-styled elements.)

### D6 — Pipeline mode
- Rendered per-session inside the Sessions section, **lines 1406-1423** (`resolvePipelineModeDisplay`, defined **lines 89-124**) — this is the *only* place pipeline mode appears, so not duplicated today, but it's nested three levels deep (Sessions → each row → pipeline sub-block) despite being fairly important "what ran" context per the Epic 3.4 comment at **line 89-101**. Worth flagging as a candidate for promotion to a more visible location rather than a literal duplicate.

### Not found (checked, absent)
- `item.notes` and `item.description` are each rendered exactly once (Description **963-972**, Notes **1524-1572**) — no duplication there.
- `item.triageResult` appears in exactly one of two mutually-exclusive branches depending on status (`TriageReviewPanel` while `status === "idea"`, **786-797**; read-only "Planning" summary otherwise, **800-818**) — not simultaneous duplication, but the same underlying data rendered by two different components depending on a status check, which is itself a source of "where do I look for this" confusion.

## 3. Edge cases and failure modes to handle

1. **Zero linked sessions** — `item.linkedSessions.length > 0` gates the entire Sessions section (**line 1312**); for `idea`/`refining`/newly-`ready` items with no sessions yet, there is currently no explicit "no sessions yet" affordance — the section just doesn't render, which is fine, but the redesign's at-a-glance summary must have a valid empty state (not just "blocker: none" but "not started").
2. **Only a triage session exists, no work session** — `latestWorkSession` (**line 190**) resolves to `undefined`; anything depending on it (`ReviewChangesModal`'s `sessionId`, `VcsWidget`'s `worktreePath`) silently gets `undefined`. Need to confirm downstream components degrade gracefully (they appear to via optional chaining) but the summary view needs an explicit "triage only, work not started" state distinct from "no sessions."
3. **Synthetic `headless-`/`review-blocked-` session IDs** — confirmed **not real backing tmux sessions**: `session/backlog_lifecycle.go:1744` (`headlessTriageSessionUUIDPrefix`), `server/services/backlog_service_triage.go:204-205` (`headlessTriageUUIDPrefix`, `headlessReReviewUUIDPrefix`), and `session/review_gate.go:229` (`"review-blocked-"+uuid.New().String()`) — these are literally synthesized ID strings for bookkeeping, not sessions with tmux panes/scrollback. Three separate call sites in `BacklogItemDetail.tsx` special-case-exclude them from "active session" lookups (**lines 830, 1333, 1462**) but the *rendering* branch at **line 1333-1351** still gives them a non-interactive `<span>` (correctly, since there's no session to open) — this is exactly the "read-only viewer" gap named in the requirements' Rabbit Holes. A new read-only viewer must handle the case where there is genuinely nothing to view (a `review-blocked-` ID may have zero output, just a stored verdict) vs. a `headless-` ID that does have real captured output.
4. **Very long description/plan text** — `Description` section (**963-972**) renders full markdown with no truncation; `Planning` section's `item.triageResult.summary` (**803**) likewise unbounded. `GoalPanel.tsx`'s `MAX_GOAL_DISPLAY_LENGTH`/expand-toggle pattern (lines 64, 106-140) is the direct precedent to reuse for both.
5. **Long-stuck items with many progress-history entries** — `Progress History` section (**1499-1521**) maps `item.progressNotes` with no cap/virtualization/collapse; `Workflow` timeline (**1476-1496**) same for `item.statusEvents`. An item that has bounced `in_progress ↔ review` many times (per `backlog-stuck-item-visibility` requirements, item `df0d5872` had "6 triage + 3 review + 2 work sessions over 4 days") would render a very long, un-collapsed Sessions list (each with its own pipeline/verdict sub-block) plus a very long timeline plus a very long progress-note list, compounding the "everything expanded" problem this project is meant to fix. Progressive disclosure must include a hard collapse/"show N more" for these three specifically, not just top-level section collapsing.
6. **Item genuinely stuck (per `backlog-stuck-item-visibility` reason taxonomy)** — `BacklogItemDetail.tsx` has **zero integration** with the stuck-item detection system. `StuckReason`/`StuckBacklogItem` (`@/gen/session/v1/backlog_pb`) and the whole `web-app/src/components/backlog-stuck/` tree (`StuckItem.tsx`, `StuckItemDetail.tsx`, `StuckItemsSection.tsx`) are rendered only from `web-app/src/app/unfinished/UnfinishedTab.tsx` — a page this project's requirements explicitly mark out of scope. This means a user can see an item flagged stuck on `/unfinished` but get no signal at all when opening the same item's detail panel from `/backlog` — directly undermining the stated success metric ("identify current lifecycle state and blocker without expanding anything"). Reconciling this is flagged in the requirements' own Rabbit Holes ("reconcile UI lifecycle model with... derived stuck-state logic") and is the single biggest gap between current code and the stated goal.
7. **Manual review form left open across status transitions** — `showManualReview` (**line 178**) is local component state gated to `item.status === "review"` (**line 1150**); if an external event (poll/websocket) flips status away from `review` mid-edit (e.g. another process auto-reviews it), the form's visibility condition disappears but there's no explicit reset/warn-on-navigate-away for in-progress typed input — worth a defensive check during redesign since progressive disclosure will likely restructure how this form's section visibility is computed.
8. **Session with `endedAt` unset but role doesn't match current status ("orphan")** — already handled today via `isOrphan` (**lines 1317-1324**, `statusToRole` map) with an "ended" badge, but this logic is duplicated a third time at **line 1454-1462** for `SessionMonitor` gating — same `statusToRole` map re-declared inline twice (**1319-1323** and **1454-1458**) rather than hoisted, a latent staleness risk if one copy is edited and not the other.
9. **Pipeline mode "unrecognized"/"drifted"** — already handled (`resolvePipelineModeDisplay`, **107-124**) but only surfaced deep in the per-session Sessions list; if the redesign promotes an at-a-glance summary, a drifted/unrecognized pipeline mode is exactly the kind of "why is this behaving oddly" signal that belongs in the glance view, not buried three levels deep.
10. **Mobile full-screen overlay + very narrow desktop panel (240px min)** — per `backlog.css.ts:206-221`; any redesigned header/summary must degrade to both extremes. No current mobile-specific behavior exists in `BacklogItemDetail.tsx` itself (no `useHoverUnavailable`-style gating, unlike `StuckItem.tsx`) — action buttons are always-visible today which is actually mobile-safe, but a redesign that adds hover-reveal affordances must not regress that.

## 4. Tyler's unstated needs (beyond explicit requirements)

Drawing on `project_plans/backlog-ux/requirements.md`, `project_plans/backlog-stuck-item-visibility/requirements.md`, and repo-wide memory/rules:

- **He's the only user, on a self-hosted instance he restarts constantly** (`backlog-stuck-item-visibility` requirements: "15+ times observed on a single day"). Any redesign that adds local component state to represent "what's expanded/collapsed" should default to sensible auto-expand rules driven by *data* (e.g. auto-expand the section relevant to the current blocker) rather than requiring him to re-expand the same sections every time he reopens an item after a service restart — he does not want to re-teach the UI his preferences every session.
- **He already asked for board/list status consistency once and didn't fully get it**: `backlog-ux/requirements.md` US-3 ("Backlog status/progress on session cards") is scoped to *session* cards in the session view, not backlog item cards on the board — and per section 2 above, `BacklogItemCard.tsx` still doesn't show a status label today. The current requirements' scope item "Board/list cards show status consistent with the detail view" is effectively finishing that earlier, still-incomplete thread — worth calling out explicitly in planning so it isn't treated as brand new scope.
- **He wants stuck-reason visibility to actually reach him, not live in a corner he has to remember to check** (`backlog-stuck-item-visibility`'s entire premise: toasts get missed, in-memory notify-once state resets on restart). Given `/unfinished` (where stuck reasons currently render) is out of scope here, the unstated need is a **lightweight cross-reference** — even just a link/badge "also flagged stuck — see /unfinished" — so this redesign doesn't accidentally regress the one place stuck-reason context existed, and ideally starts closing the gap identified in edge case #6 above without taking on the full `/unfinished` migration.
- **He cares about not re-deriving the same fact different ways in different places** — the `stapler-squad-bk-ux` branch name and this project's own "Consolidate duplicated info" scope item echo a pattern visible across `.claude/rules/` (e.g. the double-checked-locking rule's insistence on a single source of truth, the interface-pollution checklist's dislike of forwarding-only wrappers). Section 2's D3 finding (4 independent re-derivations of "the current work session") is the sharpest concrete instance of this in the file and should get a shared helper/memo rather than 4 inline `[...].reverse().find(...)` call sites — this is very much in the spirit of "consolidate duplicative information," not just a cosmetic issue.
- **Solo-dev velocity matters more than enterprise-grade polish** — per `pm-product-management`-style solo-PM framing implicit across this repo's SDD artifacts (small `project_plans/` entries, fast iteration, `Complexity: 3` self-rating in this project's own requirements.md) — the redesign should favor the cheapest pattern that solves progressive disclosure (native `<details>`, per Pattern A above) over building new generic accordion infrastructure, unless multiple sections genuinely need coordinated/exclusive expand state (Pattern B) or deep-linkable open state.
- **Mobile is a first-class usage mode for him** (`feedback_mobile_desktop_ux` memory: "always consider both form factors"), and this specific component already has real mobile behavior baked into its container (`backlog.css.ts` full-screen overlay at ≤768px) — the redesign needs to be validated on that breakpoint, not just assumed to reflow correctly, since the current file has zero mobile-specific logic despite living inside a component that already gets a completely different layout mode on phones.
- **He wants to trust the read-only session viewer to actually show something useful**, not a dead end — since `headless-`/`review-blocked-` IDs are synthetic (edge case #3), the new viewer needs a clear empty/explanatory state for the `review-blocked-` case (verdict-only, no captured output) distinct from the `headless-` case (has real captured output) rather than a generic "nothing here" — matching his stated pattern elsewhere in this repo of preferring specific, named failure modes over generic fallbacks (see `.claude/rules/prefer-go-git-over-subshells.md`'s insistence on naming the specific failure a fallback exists for).
