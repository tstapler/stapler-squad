# Pre-mortem: quota-aware-backlog-gating
**Date**: 2026-08-10

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `AssumedWindowTokenBudget` ships at `0` (ADR-001's safe default) and the operator never calibrates it, so the soft/proactive signal stays `Valid=false` forever — backlog is only ever paused reactively, after a session has already been rate-limited, never before | `status_detail`/notifications only ever cite the hard-override wording ("a session hit the usage limit"), never a headroom-threshold reason; individual backlog sessions still occasionally get rate-limited despite the feature showing "on" | Surface the reactive-only mode in the UI itself (e.g. a `status_detail` line "soft signal disabled — reactive-only mode" whenever `Enabled=true && AssumedWindowTokenBudget==0`) instead of leaving calibration as a prose note in Unresolved Questions; add a Phase 4 task that logs observed peak 5h usage for a week so the operator has a real number to plug in | P1 |
| 2 | The hard/reactive signal depends entirely on `session/detection/ratelimit`'s regex-based message matching; a wording variant Anthropic ships later goes undetected, so `onRateLimitDetected` never fires and `RateLimitAggregate` never updates — since this is the *only* signal active by default (per Failure #1), the feature silently provides zero protection while still reporting "Backlog: On" | Terminal scrollback visibly shows a rate-limit/usage-limit message but no "Backlog Automation Paused" notification appears and Settings still shows "Backlog: On" — only detectable by manually comparing scrollback against the absence of a notification | Add a canary/validation check that logs a warning whenever session output contains generic quota keywords ("limit", "quota", "usage") the configured detector regex does *not* match, so a drift in wording is caught structurally instead of relying on a static pattern set with no drift detection | P1 |
| 3 | `QuotaGate`/`TokenStore`/`RateLimitAggregate` are in-memory, per-process state (Migration Plan: "no schema or persisted-data changes... all `QuotaGate` state is in-memory-only"), but CLAUDE.md's own documented manual-testing workflow instructs running a second `stapler-squad` instance against the same Claude Code account/quota — that instance's rate-limit events are invisible to the "live" instance's `QuotaGate`, so the live instance keeps dispatching backlog work while the shared account is already rate-limited elsewhere | Backlog sessions in the live instance start getting individually rate-limited even though its own Settings page shows "Backlog: On, healthy" | Document this as an explicit scope limitation (single-instance quota visibility only) in plan.md's Risk Control, and/or persist the hard-signal's last-event timestamp to a shared file outside any instance's isolated state dir so co-located instances on the same host/account can share at least the reactive hard signal | P2 |
| 4 | `foregroundSessionActive`'s `Category != CategoryBacklog` predicate assumes every backlog-spawned session (including headless/Hidden triage and one-shot PR-fix sessions) reliably sets `Category = CategoryBacklog` — Task 2.3.1c itself flags this as unverified ("hasn't been independently confirmed for every backlog-spawned session type"); if any backlog-spawned session type leaves `Category` unset, it's misclassified as foreground and backlog perpetually throttles itself via its own spawned sessions | Backlog shows "Backlog: On" (not paused-by-quota) but never creates new sessions; `StatusDetail`/logs show "Throttled — foreground session active" continuously with no human at the keyboard | Promote Task 2.3.1c from a "grep and eyeball, file a fast-follow if a gap is found" checklist item to a blocking acceptance criterion with an integration test asserting every backlog session-creation call site produces `Category == CategoryBacklog`, before Epic 2.3 is considered done | P2 |
| 5 | Task 2.1.2b resets `consecutiveBelow`/`consecutiveAbove` to `0` on any tick that doesn't match the current direction, with no dead-band on the pause side; a headroom estimate that's genuinely trending down but noisy near `PauseBelowHeadroomPct` (realistic for a 5h rolling window recomputed every 60s) can perpetually fail to reach `ConsecutiveTicksToPause` consecutive ticks, so the proactive pause never fires — and conversely a single noisy dip after resuming re-resets the resume streak, unpredictably extending downtime | Headroom hovers just under threshold for extended periods with no pause notification ever firing, or backlog stays disabled far longer than expected after usage clearly dropped, prompting the operator to give up and flip the manual override | Add a symmetric dead-band/margin on the pause side (not just resume), and add a unit test with a synthetic noisy-but-trending series — Story 2.1.2/2.1.3's GWT cases are all clean step functions today, none exercise oscillation near the threshold | P3 |

## P1 Items (address before implementation)
- [x] Failure #1 — Addressed in plan.md: Task 3.2.2a's `StatusDetail()` now returns a
  "Reactive-only mode — proactive quota threshold not calibrated" line whenever
  `Enabled && AssumedWindowTokenBudget<=0`, and new Task 3.2.2d logs observed 5h peak token usage
  hourly while uncalibrated, giving the operator real numbers to set a budget.
- [x] Failure #2 — Addressed in plan.md: new Task 1.3.2d adds a canary `log.Warn` in
  `session/detection/ratelimit/manager.go` when session output contains generic quota/limit
  keywords the configured regex set doesn't match, surfacing detector-wording drift instead of
  silently defeating the feature's only active-by-default signal.
