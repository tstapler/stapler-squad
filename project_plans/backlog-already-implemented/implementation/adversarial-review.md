**Note**: Re-reviewed after a repair pass. See "Repair Pass Re-Review" section below for what changed.

## Repair Pass Re-Review

- **Original Blocker 1** — RESOLVED: The dependency graph and prose are now internally consistent and unambiguous. Task 1.1.1a is explicitly the "true Phase 1 gate" with "HARD BLOCKS: nothing below may start until this is green" printed directly on the graph. Epic 1.1's header states plainly "This epic is a hard blocking prerequisite for Epic 2.2, not a de-risking nice-to-have," and ADR-001's Repair Pass Addendum echoes the same language ("now hard-blocks the *start* of Epic 2.2... hard-blocks Epic 2.2.2/2.2.3 being marked *done*"). No remaining "de-risks but doesn't block" phrasing survives anywhere in plan.md or the ADR. The former self-contradiction the architecture review flagged (Task 1.1.1b depending on `CallOptions` fields that don't exist until Phase 2) is fixed by resequencing that test to Task 2.1.1e, placed immediately after Story 2.1.1 lands its fields — and it is still explicitly re-affirmed as a hard blocker in its new location. The new Task 1.1.1b (production-CLI-parity check) is concrete enough to be verifiable, not aspirational prose: it names the exact test names to re-run (`TestPool_RealClaude_WorkDirOnly_GrantsReadAccess`, `TestPool_RealClaude_WorkDirWithToolFlags_GrantsReadAccess`), the exact commands (`claude --version`, `systemctl --user show stapler-squad -p Environment`, `go test -race -tags integration ...`), and what to record (CLI version, pass/fail, environment delta). One residual gap worth noting (not enough to keep this unresolved): enforcement of Task 1.1.1b is procedural — a checked-off line in the Post-Implementation Checklist — not an automated CI gate. Nothing in the codebase actually prevents a PR from merging Epic 2.2.2/2.2.3 without this step having been performed; it depends on a human following the checklist honestly. That's a process-rigor gap, not a design gap, and doesn't undermine the sequencing fix itself.

- **Original Blocker 2** — PARTIALLY RESOLVED: The degradation path is now real and concrete, not unspecified. `CodebaseReadCallTimeout` (150s, vs. the shared 900s `DefaultCallTimeout`) cleanly closes the "hangs" failure mode — a stuck codebase-read call now fails fast into `UNVERIFIABLE` instead of blocking the review gate for up to 15–30 minutes, with Story 2.2.4's Given-When-Then ACs and Task 2.2.4a's literal `DegradeIfUnverified` pseudocode making this genuinely implementable as written (this also answers the "are the GWT acceptance criteria specific enough" question affirmatively for Story 2.2.4 — the JSON fixtures, exact field names, and exact `ReviewVerdictUnverifiable`/`path=` values leave little room for ambiguous implementation). The `tool_reads` heuristic reasonably addresses the specific failure mode the original blocker named — "the model can't actually read files but doesn't realize it" — because in that scenario the model genuinely has no tool results to list, so an honest self-report legitimately comes back empty. **The gap**: this heuristic is entirely self-attested by the same LLM call that produces the verdict, parsed out of the same JSON blob the model authors — it is not cross-checked against any independent, out-of-band signal of what tools actually ran (e.g., `claude -p --output-format stream-json`'s own `tool_use`/`tool_result` events, which the CLI itself emits independently of what the model chooses to claim in its final answer). A model that is willing or able to hallucinate a confident PASS with fabricated file:line "evidence" can, by the same failure mode, just as easily populate `tool_reads` with a plausible-looking list of file paths it never opened — nothing in `DegradeIfUnverified` or the system prompt makes that harder to fabricate than the `evidence` field it's meant to police. So the fix closes the "silent/accidental tool-grant failure" half of Blocker 2 well, but does not close the "model hallucinates a confident PASS and doesn't even know it's ungrounded" half as fully as the plan's own framing claims — a sufficiently-confabulating model defeats the checkable heuristic by extending the same confabulation one field further. This is a real narrowing of the original blocker's risk (a strict improvement over "no degradation path" at all) rather than a full close, and is not a regression — it does not make the anti-gaming problem worse than before this feature existed, since the pre-feature baseline (UNVERIFIABLE-on-empty-diff) is still the floor for both a timeout and an empty `tool_reads` list.

- **New issues introduced by the fix itself**:
  - **(Concern, not blocker) Disproportionate blast radius of the `Pool.CallBlocking` consolidation.** The original review's Concern B (not a Blocker) objected to a *proposed 4th* near-duplicate method and offered two remedies: fold cost into a single parameterized call path, or explicitly flag the M×N growth as accepted debt. The repair pass instead chose full consolidation of all three existing methods into one, which — per the plan's own verified inventory — touches 12 call sites across `session/headless/features.go`, `session/review_gate.go`, `server/services/approval_handler.go`, `server/services/backlog_service_triage.go`, `server/services/session_service.go`, and `session/autonomous_driver.go`; 3 narrow consumer-defined interfaces that must change in lockstep; and 6 test files' worth of fakes/mocks. Several of those call sites (`approval_handler.go`, `session_service.go`, `autonomous_driver.go`) have nothing to do with the empty-diff review feature this plan exists to ship. For a plan whose own requirements.md sets "Complexity: 2 — focused feature" and "Appetite: Medium," this is a materially larger and more diffuse change than either original blocker demanded — it's a breaking signature change to a shared package's public API rasterized across unrelated subsystems, done inside the same PR/pass as two anti-gaming-critical fixes. Each individual site's edit is mechanical and the plan does specify tests for the consolidated method and its call sites (Task 2.1.2d/e), so this isn't assessed as introducing *correctness* risk — but it is a scope/proportionality overcorrection worth a second look: splitting the `Pool.CallBlocking` consolidation into its own separate PR, decoupled from the Blocker-1/Blocker-2 fixes, would reduce the review surface of the safety-critical changes and make it easier to bisect a regression to one or the other if something breaks post-merge.
  - No blocker-level issue was introduced. The self-attestation gap noted under Blocker 2 above is the closest candidate, but it narrows an existing risk rather than creating a new one, and the plan's own "Residual risk" section already establishes the precedent of documenting-but-not-fully-closing an adjacent risk (a false PASS with genuinely-grounded evidence shipping silently) — the `tool_reads`-fabrication case is a natural extension of that same already-acknowledged residual-risk category, not a fresh, unacknowledged one.

## Blockers

None. Both original blockers show genuine engineering progress; the residual gap in Blocker 2 (self-attested `tool_reads` versus an independent tool-invocation signal) is tracked as a concern below rather than a blocker, consistent with how the plan's own Residual Risk section treats the adjacent "grounded-but-wrong PASS" risk — documented, accepted, not gating.

## Concerns

- [ ] **New (this repair pass) — `tool_reads` is self-attested, not independently verified against actual tool invocations.** See "Original Blocker 2" analysis above. A model capable of hallucinating a confident, ungrounded PASS/FAIL with fabricated `evidence` can equally fabricate a plausible-looking non-empty `tool_reads` list, which sails through `DegradeIfUnverified` unchallenged. The mechanism is a strong defense against *unintentional* silent tool-access failure (the literal scenario Blocker 2 named) but not against a genuinely confabulating model. **Recommendation**: If/when `Pool`'s underlying `claude -p` invocation supports `--output-format stream-json` (or equivalent), consider deriving the "did a tool actually run" signal from the CLI's own out-of-band tool-use events rather than a model-authored JSON field, so the check is adversarially robust rather than an extension of the same trust boundary it's meant to police. Not required to ship this feature — the current heuristic is a real improvement over the pre-repair-pass "no degradation path at all" — but should be tracked as a known limitation, ideally in the plan's Unresolved Questions or Residual Risk section, which currently doesn't mention this specific fabrication vector.
- [ ] **New (this repair pass) — `Pool.CallBlocking` consolidation is disproportionate in scope to the two blockers it's justified by.** See "New issues introduced by the fix itself" above. Recommend splitting into its own PR to reduce blast radius on the anti-gaming-critical changes, even though no correctness risk was identified in the mechanical edits themselves.
- [ ] **Duplicated branching logic across two call sites is dismissed as a footnote, not addressed.** Story 2.2.3 explicitly documents that the WorkDir/AllowedTools/system-prompt branching logic is "duplicated by hand across two call sites in two different files/packages" (`session/review_gate.go` and `server/services/backlog_service_triage.go`) with no shared helper. For a feature whose core value is exactly this branching logic (deciding when/how to grant codebase access and which prompt to use), duplicating it doubles the chance the two paths drift — e.g., one call site gets a security/timeout fix and the other doesn't, silently reopening the anti-gaming gap in just the `TriggerReReview` path while the primary review-gate path is fixed. This is a correctness risk, not just a style nit, given how central this exact logic is to the anti-gaming guarantee. **Recommendation**: Extract a single `resolveEmptyDiffCallOptions(codebaseWorkDir string) (headless.CallOptions, systemPrompt string)`-shaped helper before merging Epic 2.2, even if it costs a small amount of the "focused feature" appetite — this is the single highest-leverage place in the whole plan to prevent silent divergence.
- [ ] **`CallBlockingWithCostAndOptions` as a 4th similarly-named method risks becoming an API surface the codebase already flags as an anti-pattern in its own rules.** The repo's `.claude/rules/interface-pollution-checklist.md` explicitly calls out "forwarding-only wrapper" methods that just call straight through with no added behavior as a smell to catch before merge. Plan's own text: "thin wrapper combining `CallWithOptions` + `drainChannelWithCost`" — by its own description this is exactly that smell. `Pool` now has `CallBlocking`, `CallBlockingWithCost`, `CallBlockingWithOptions`, `CallBlockingWithCostAndOptions` — four near-identical methods differing only in which of {cost-tracking, options} they support, an M×N combinatorial-explosion pattern that will keep growing every time a 5th cross-cutting concern (e.g., streaming callback, retry policy) needs plumbing through. For a "complexity 2 — focused feature," this is scope creep in the `headless` package's public API that outlives this one feature. **Recommendation**: Either (a) fold cost-tracking into `CallOptions`/`CallWithOptions` as the single parameterized call path and deprecate the narrower methods over time, or (b) at minimum, flag this explicitly as intentional accepted debt in the plan rather than silently adding a 4th method with no naming/consolidation strategy noted.
- [ ] **Anti-gaming test coverage is a single fixture for the feature's own stated "core point."** Epic 2.3 is the only test in the entire plan that (a) is adversarial/negative rather than positive, and (b) makes a real, non-mocked LLM call to validate the anti-gaming guarantee. Requirements.md calls this "THE ANTI-GAMING REQUIREMENT — the core point of the feature." One fixture (a missing `auth/login.go` claim) covers exactly one shape of lie — a citation to a file/function that flatly doesn't exist. It does not cover: a citation to a real file/function that exists but doesn't actually satisfy the criterion (harder to catch — requires the model to read and *understand* the code, not just confirm existence); a criterion satisfied by a *different*, unstated file than the one cited (model must independently search, not just verify the claim); or multiple AC where some notes are true and one is subtly false (partial-gaming, arguably the most realistic gaming pattern from a rework-fatigued agent). A single real-LLM adversarial test is also inherently flaky/non-deterministic pre-merge-gate material — CI will either need to tolerate occasional false failures or the test becomes ignored/skipped over time, which quietly erodes the only regression coverage this feature's central promise has. **Recommendation**: Add at least 2-3 more adversarial fixtures covering the failure shapes above, and treat this test suite as a first-class, monitored regression gate (not just a nice-to-have integration test) given it is the sole technical enforcement of the feature's namesake requirement.
- [ ] **No test or design decision for the "partially already implemented" mixed-criteria case.** Requirements/research reportedly flagged this edge case (some criteria satisfied without a diff, others requiring one, same review) but the plan has no story addressing it explicitly. The branching in Story 2.2.2 is a binary `diff == ""` check at the whole-review level — it says nothing about what happens when diff is non-empty (so the codebase-read path is *not* taken) but one specific criterion's Note claims "already implemented, unrelated to this diff" for something the diff doesn't touch. In that case the reviewer gets only the diff-based system prompt (not the falsification-framing one) and only sees `c.Note` text (Story 1.2.1) with no tool access to verify it — i.e., the anti-gaming check that Epic 2.2 built specifically does not apply to the mixed case, even though the Note-rendering change (Story 1.2.1) is unconditional across all reviews including this one. This is a real gap: the feature makes it *easier* for an agent to make an "already implemented" claim in the Note field for any criterion in any review (not just empty-diff ones), while only building an anti-gaming verification path for the all-criteria-empty-diff review as a whole. **Recommendation**: Explicitly scope Story 1.2.1 and note in the plan whether per-criterion "already implemented" claims in a partially-non-empty-diff review get the same tool-verification treatment, or explicitly document as accepted risk that they don't (and why that's acceptable) — right now the plan is silent, which reads as an oversight rather than a decision.

## Minors

- The Risk Control section's own words — "a false PASS via the codebase-verification path ships silently... makes the anti-gaming prompt design the ONLY backstop once a review reaches PASS via this path" — is an accurate and honest risk statement, but pairing zero notification/audit trail on the PASS path with zero feature flag (justified only by "complexity 2, no flag needed" from requirements.md) is an inconsistent risk posture: the requirements' own complexity rubric predates the discovery (during planning) that this feature's blast radius includes bypassing the diff-based safety net entirely for some reviews. Worth a second look at whether "no feature flag" still holds given what Phase 3 planning uncovered, even without reopening the full requirements phase.
- Story 2.1.1's `toolAccessArgs() []string` helper and `WithToolAccess` builder method on `ProcessRunner` are introduced without a corresponding unit test explicitly named in the plan (only implied by "Epic 2.1... tests pure Go logic... flag-arg construction" in the Epic 2.3 comparison) — confirm this is actually enumerated as a task, not just assumed to exist.
- `Epic 2.4`'s advisory-only tool-description change is honestly scoped as unenforceable, which is good, but its stated mechanism ("the reviewer will independently check that citation") depends entirely on Epic 2.2's codebase-read path actually working (see Blocker 1/2 history above) — if that path degrades silently, Epic 2.4's sentence becomes a false promise to the implementation agent with no code-level check that it was kept.
