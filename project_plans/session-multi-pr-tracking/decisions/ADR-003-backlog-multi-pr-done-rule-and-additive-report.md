# ADR-003: Backlog done rule for multi-PR items and additive `report_pr_created`

**Status**: Accepted for the done rule (owner decision 2026-11-03: done when at least one PR is merged and none are open; cleanup and retention need all PRs terminal). PROPOSED, pending owner confirmation (plan Owner confirmations pending): the worktree-cleanup gate scope, archival staying ungated, the ungated explicit removals (force-reset, MCP pause/destroy), the iteration-3 round and tombstone behavior changes, the live-work hold and the issue-close offer. — **Project**: session-multi-pr-tracking

## Context
`setPRAndTransition` (`session/storage.go:1240-1271`) rejects a second PR on a `pr_pending` item unless a reassignment guard passes, and refuses any change once the current PR is merged. `ReconcilePRPending` and `reconcileBouncingItems` complete an item when "the" PR merges. `FindPRPendingItems` filters on `PrNumberGT(0)`.

## Decision
- Item PR set = distinct `PullRequestState` ids from links with the item's id UNION links of the item's current round (its latest `work`-role `ItemSession` by `created_at`; an earlier work session is used only while every later one has NEVER linked, i.e. has no link and no session tombstone, so a newly created session does not hide a live PR before discovery links its own, while a detached link, which leaves a tombstone, does not let an earlier round's PR re-enter; tie-break `id`, deterministic not semantic), minus states tombstoned for the ITEM (a session tombstone does not subtract a PR another live contributor still holds), derived at read time through the `PRSetReader` seam (ADR-001). There are no mirror links and no `abandoned` flag: a superseded round simply stops being the latest work session, and its PRs do not count for the verdict (they stay linked, polled, and hold that session's worktree). The legacy fallback synthesizes one `unknown`-state PR from `pr_number`, never a terminal one. An `unknown` PR (persistent poll failure) blocks done until it is detached; an exhausted unverified-terminal row is read as `unknown` (held) by the verdict and as terminal only by the gate and sweeper.
- `pr_pending -> done` iff at least one PR is merged and none are open. This narrows the earlier wording "all tracked PRs" (requirements Success Metrics, now aligned): a PR that reached the item only through a superseded round's session link is outside the verdict; item-direct PRs always count. Closed-unmerged PRs are allowed if another merged; if none merged the item falls to the existing superseded/closed handling.
- Every backlog-driven path that removes a worktree requires every PR tied to it to be terminal, through ONE predicate `PRCleanupGate.Blocked(sessions)` called at the single choke point `cleanupItemWorktreesExcept` (the archive RPC, reopen, orphan-tombstone, inline transition, `WorktreeCleaner` hook and the 60s safety net all reach it; VERIFIED), plus the retention sweeper (which reads `InstanceData` through a bulk link query and ALSO the item-direct links of the session's item, fail closed). The gate looks at the removed work sessions' own links and the item's direct links, fails closed (open, `unknown`, legacy number with no link, or a lookup error all block) and is not flag-gated. A block withholds ALL worktree removal of that call (sessions share a worktree path across rework rounds). Session archival and tmux-pane kill are not worktree removal and stay ungated (OOM leak, 2026-07-29); `CleanupTerminalItem` therefore runs archival regardless and returns a `CleanupOutcome` so a blocked item is not settled. Explicit user and agent-requested destroy/pause, and the operator force-reset / backward-to-ready session stop (`stopLiveWorkAndReviewSessions`), are intentionally ungated but warn about open PRs.
- Cleanup re-runs when the last PR goes terminal: the poller notifies the lifecycle listener, and the 60s safety net re-evaluates blocked items without settling them.
- A PR may be attached to an item or session that is already `done`; it does not reopen the item and holds cleanup until terminal.
- `report_pr_created` (flag on) with a PR number different from the current one attaches an additional PR (role `followup`), keeping head-branch verification. The existing correction path stays behind a new `replaces_pr_number` parameter with the unchanged guard (override reason, current PR not merged, author verified).
- The MCP handler verifies that the calling session is linked to the item server-side; `--allowedTools` is client-side only.
- `item.pr_url` / `pr_number` remain a mirror of the active PR, written in the same atomic UPDATE as the status (no reader may see `pr_pending` with `pr_number=0`); it is also recomputed at the end of each `ReconcilePRPending` pass for session-link changes and an empty set never zeroes it (T5.2.3).
- Live-work hold (Phase 4 pre-mortem #4, proposed): a `Done` verdict is held as `pr_pending` (reason `merged, session still active`) and the cleanup gate blocks worktree removal while the item's current-round work session is unended and active within `liveWorkIdleWindow` (default 10 minutes), so PR A merging before PR B exists does not archive the session that is about to open B. It is a hold in the verdict consumer, not part of `ItemPRVerdict`; archival stays ungated by open PRs, except that a live session itself is skipped (RULE L, plan T5.4.6); the 60 s sessions sweep leaves such an item unsettled so the session is archived on the first pass after it idles or ends, not after the 10-minute settle TTL.
- Issue close on re-import (owner request 2026-11-03): when `ImportGitHubIssue` finds an existing item that is FINISHED (status `done`, and for items with PRs the done rule holds; archived and duplicate items never) while the GitHub issue is still open, the response carries an offer and the user confirms with one click; the close reuses the forward-sync close action and comment, is decided server-side, is limited to github.com issues with a token (GHE reported, not closed) and is behind scope `reader:backlog`. Never silent.
- `backlog_lifecycle_pr.go` is isolated behind the seam, not restructured.

## Alternatives rejected
- Done when the primary PR merges: today's behavior; strands follow-ups.
- Done when all PRs merged: a closed duplicate blocks forever.
- Always reassignment for a second PR: needs an override for the normal follow-up case.

## Consequences
An old merged PR no longer decides state; a new open PR keeps the item `pr_pending`. The per-path cleanup tests and the sweeper tests are written before the `reader:backlog` flip because they are the data-loss sites.

## Owner confirmation
The PROPOSED parts (cleanup-gate scope, ungated explicit removals) are item #1 of plan.md "Owner confirmations pending", with the recommended default (accept as written). The live-work hold and its new maximum hold (`liveWorkMaxHold`, 1 hour) are item #2 there and do not change the done rule. Triad iteration 2 adds RULE L to item #2: terminal-item cleanup and the 60 s session sweep skip archiving and pane-killing a live current-round work session (verified: before it, `CleanupTerminalItem` archived and killed the pane at the maximum hold, so the worktree hold was unreachable), and `reconcileBouncingItems` honors the same hold.
