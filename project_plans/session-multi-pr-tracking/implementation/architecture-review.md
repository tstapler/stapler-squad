## Concerns

- [ ] **C1. `RunPRStartupMaintenance` in `BuildCoreDeps` also runs in the stdio MCP subprocess, so "only the service runs it" is false (T1.5.1, Migration Plan lines 153-156, Glossary "State writer", ADR-001, Story 1.5 line 409).** VERIFIED: the call site the plan names (`server/dependencies.go:425`, `storage := sessionService.GetStorage()`) is inside `BuildCoreDepsWithOptions`, and `BuildCoreDeps()` is a thin wrapper over it (`dependencies.go:413-451`). `buildMCPDeps` (`main.go:1871`) calls `server.BuildCoreDeps()`; per its own comments (`main.go:~160-165`) that process is a short-lived stdio subprocess per agent session, used when the thin-client proxy is unavailable (`main.go:150-155`). Each such subprocess would run the backfill and `ResetVerifyCounters`, and a transient SQLite busy would fail `mcp: init deps`. The ordering claim is otherwise correct (VERIFIED: `BuildServiceDeps` builds the poller at `dependencies.go:479`, `LoadInstances` runs in `BuildRuntimeDeps` at `:739`, and the service path is `main.go:384`), and the effect is in the safe direction (rows stay non-terminal), but the invariant text and the Story 1.5 ordering AC cite a path that does not exist. The window is real: a service restart is exactly when proxy fallbacks happen, so several maintenance runs can race the service's own. Remediation: add a `BuildOptions` field (for example `RunPRMaintenance bool`), set true only at `main.go:384`, and have `BuildCoreDepsWithOptions` honor it; or move the call to a service-only phase. Add an AC that `buildMCPDeps` does not run it, and correct the Glossary, Migration Plan and ADR-001 wording ("hook, CLI and MCP-fallback processes").
