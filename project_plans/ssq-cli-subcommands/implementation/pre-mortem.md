# Pre-mortem: ssq-cli-subcommands
**Date**: 2026-10-18

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | CI pipelines omit `--wait`, then immediately call `steer` or `get-diff` on a session still in `SESSION_STATUS_CREATING`, getting spurious failures or acting on a session that never became active | `steer` exits non-zero with "not found" or "failed precondition" intermittently in CI logs; operators assume the server is flaky | Add a `--wait`-by-default option or a CI-usage warning to `--help` text; document the async contract explicitly in the README examples (plan.md §4.1 must include a CI-pattern anti-example alongside the create example) | P1 |
| 2 | `ssq steer` on a non-autonomous session returns exit 0 but the message is silently dropped — the server accepts `UpdateSession.steer_message` on any session but only the autonomous driver reads it | `steer` exits 0, no error output, but the running session's behaviour is unchanged; operators assume steering worked and wait indefinitely for an effect that never comes | Before shipping, verify actual server behaviour when `steer_message` is sent to a non-autonomous session; if the server returns 200 with no side effect, the CLI must detect `autonomous_mode=false` from `GetSession` and return an error before calling `UpdateSession`, rather than relying on a `CodeFailedPrecondition` that may never arrive | P1 |
| 3 | Scripts written against `get-session --json` (integer enums via `encoding/json`) break when ported to `list-sessions --json` (string enums via `protojson`) because status comparisons like `jq '.status == 2'` silently evaluate to false | Shell conditionals on session status pass or fail incorrectly; no error is raised — the comparison simply returns false, so downstream steps are skipped without any log message | Resolve the unresolved question in plan.md §Unresolved Questions §1 now: migrate `get-session --json` to `protojson` in Phase 2 as part of the port fix, document the one-time breaking change in `--help` and README, and ship both changes together so the enum format is consistent from day one | P2 |
| 4 | `--wait` times out after the 60 s default on legitimate slow environments (large repo initial clone, slow network mount, constrained CI runner), causing `create-session --wait` to exit 1 even though the session eventually becomes active | CI jobs reliably fail with "timed out waiting for session to become active" on certain repositories; `ssq get-session` run a few minutes later shows `SESSION_STATUS_ACTIVE` — the job just needed more time | Lower the polling interval from 2 s to 1 s (halves perceived latency at negligible cost), add a stderr progress line every 10 s during the wait (e.g., `# waiting for session... 20s elapsed`) so operators can tell the command is alive, and document the `--wait-timeout` flag prominently in README CI examples with a recommended value for large repos | P2 |
| 5 | Operators or incident runbooks migrate from `ssq list` (reads SQLite directly, works without a running server) to `ssq list-sessions` (requires a live server), then discover their diagnostic tool also fails during the exact incident they need it for | During a server outage, `ssq list-sessions` returns "server unreachable" and reveals no session state; `ssq list` still works but the operator no longer knows it exists because the README now prominently features `list-sessions` | Add a callout in README §CLI reference and in `ssq list-sessions --help` that explicitly names `ssq list` as the offline/offline-diagnosis fallback — "requires a running server; use `ssq list` to read SQLite directly when the server is down"; ensure `ssq list` remains registered and undeprecated | P3 |

## P1 Items (address before implementation)

- [ ] Failure #1 — Add a CI anti-pattern callout to plan.md §4.1 and the README: every `create-session` example in CI context must show `--wait`; add a note to `create-session --help` Long description: "In CI, use `--wait` to block until the session is active before proceeding."
- [ ] Failure #2 — Add an acceptance criterion to Story 3.3 (`steer`) that verifies actual server behavior when `steer_message` is sent to a non-autonomous session; if the RPC returns 200 with no effect, the CLI must pre-flight with `GetSession` and reject the call with a clear error rather than silently succeeding.
