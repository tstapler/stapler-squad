# CLI Subcommands — Build vs. Buy Research

Sources: `go.mod`, `main.go`, `cmd/commands/get_session.go`,
`config/config.go` (lines 212–215, 784), `server/services/notification_service.go` (line 384).

---

## 1. Proto JSON marshaling — use `protojson`, not `encoding/json`

**Verdict: use `protojson` (no new dependency — already transitively available).**

`google.golang.org/protobuf/encoding/protojson` is part of the
`google.golang.org/protobuf v1.36.12` module already in `go.mod` (line 64). No new
dependency is needed.

The existing `get_session.go` (line 37) uses `encoding/json` on a proto message:

```go
jsonData, err := json.MarshalIndent(resp.Msg.Session, "", "  ")
```

This is wrong for two reasons:
- Proto field names come out as Go struct names (`SessionId`, `CreatedAt`), not proto
  JSON names (`session_id`, `created_at`). Tools that consume JSON expecting the wire
  format will fail or silently misread fields.
- Enum values are rendered as integers, not their string names (`0` vs `"STATUS_STOPPED"`).
- `google.golang.org/protobuf/encoding/protojson` handles all of this correctly,
  including `google.protobuf.Timestamp` → RFC 3339 string conversion.

**Correct pattern:**

```go
import "google.golang.org/protobuf/encoding/protojson"

m := protojson.MarshalOptions{Multiline: true, Indent: "  ", EmitUnpopulated: false}
out, err := m.Marshal(resp.Msg.Session)
fmt.Println(string(out))
```

The `notification_service.go` comment at line 384 shows the codebase is aware of
`protojson` (refers to it by name when describing a concurrency concern), but no file
currently imports it — the first importer will need to add the import path
`google.golang.org/protobuf/encoding/protojson`.

## 2. Output formatting — stdlib `text/tabwriter` is the established pattern

**Verdict: build with `text/tabwriter` (stdlib, already used).**

No third-party table-writer (`github.com/olekukonko/tablewriter`, `github.com/jedib0t/go-pretty`,
etc.) appears in `go.mod`. The codebase uses `text/tabwriter` from the standard library
directly, as seen in `main.go`'s `formatKnownHosts` helper (lines 1900–1908):

```go
w := tabwriter.NewWriter(out, 0, 4, 2, ' ', 0)
fmt.Fprintln(w, "HOST ID\tADVERTISED ADDRESS(ES)\tLAST SEEN")
for _, entry := range entries {
    fmt.Fprintf(w, "%s\t%s\t%s\n", ...)
}
_ = w.Flush()
```

`tabwriter.NewWriter(out, minWidth, tabWidth, padding, padchar, flags)` with
`(0, 4, 2, ' ', 0)` is the pattern to replicate for `list` output. No third-party
library is warranted unless richer color/sort/filter output becomes a requirement.

## 3. Server address auto-discovery — read `config.ListenAddress`

**Verdict: build a thin resolver that reads `config.LoadConfig()`, with `--server` flag
override. No new dependency.**

`config.Config.ListenAddress` (line 215 of `config/config.go`) is the server's bind
address (`"localhost:8543"` by default, line 784) and is a `json:"listen_address"` field
in `config.json` — it is persisted to disk, so `config.LoadConfig()` can read it without
a running server. The server also respects a `PORT` env var override.

Recommended discovery order for CLI commands:
1. `--server` flag (explicit override, user-supplied full URL or host:port)
2. `STAPLER_SQUAD_SERVER_URL` env var (for scripting)
3. `config.LoadConfig().ListenAddress` → prepend `http://` and append `/api` path

This mirrors how `gh` (`~/.config/gh/hosts.yml`), `kubectl` (`~/.kube/config`), and
`flyctl` (`~/.fly/config.yml`) handle local daemon address resolution: config-file first,
flag second.

No third-party service-discovery library (consul, etcd client, etc.) is warranted — this
is a single-instance local daemon, not a distributed service. The config file is the
source of truth.

## 4. ConnectRPC buf-gen patterns — no generated CLI client; use typed Go client

**Verdict: use the existing generated `sessionv1connect` Go client. `buf curl` is for
manual inspection only.**

The `github.com/bufbuild/buf v1.57.2` CLI is in `go.mod` as a direct dependency
(line 24), which means `buf curl` is available for ad hoc HTTP/2 inspection. It is
not suited for scripted CLI use: it requires the proto schema to be available on disk
(or via BSR), does not integrate with cobra flags, and returns untyped JSON.

The right approach for scriptable subcommands is the generated typed Go client already
used in `cmd/commands/get_session.go`:

```go
sessionv1connect.NewSessionServiceClient(httpClient, baseURL)
```

`sessionv1connect` is generated by `make build` (via `make proto-gen`) into
`gen/proto/go/session/v1/sessionv1connect/` — not committed, but always available after
a build step. There is no buf-ecosystem "CLI generator" that produces cobra commands from
proto definitions; the closest upstream project (`buf-cli-gen`) is experimental and not
compatible with ConnectRPC.

## 5. Comparable CLI designs

**Pattern: thin cobra wrapper → typed ConnectRPC client → `protojson` output.**

| Tool | Daemon discovery | Output |
|---|---|---|
| `kubectl` | `~/.kube/config` → `--kubeconfig` / `KUBECONFIG` override | `go-printers` table or `--output json` |
| `gh` | `~/.config/gh/hosts.yml` → `GH_HOST` env | `--json` flag + `--jq` filter |
| `flyctl` | `~/.fly/config.yml` → `FLY_API_TOKEN` | always-JSON or pretty-print per command |
| `docker` | `/var/run/docker.sock` → `DOCKER_HOST` | custom formatter per command |

The closest match for `ssq` is `gh`: config-file-first address resolution, `--server`
flag override, machine-readable JSON by default for piped use. The difference is that
`gh` adds `--json field,field,...` and `--jq` support for field selection — that is a
useful future addition but not required for V1.

One concrete lesson from `gh`'s design: expose `--json` as a flag (not always-on JSON)
so human-facing commands like `list` can default to a tabwriter table while still
supporting `ssq list --json | jq '.[] | .id'` in scripts. The existing `get-session`
always-JSON model is fine for single-object commands.

## Summary

| Question | Decision | Rationale |
|---|---|---|
| Proto JSON marshaling | `protojson` (`google.golang.org/protobuf/encoding/protojson`) | Correct field names and enum strings; no new dep |
| Output formatting | `text/tabwriter` (stdlib) | Already used in `main.go`; no new dep |
| Server discovery | Read `config.LoadConfig().ListenAddress`, `--server` flag override | Config is on-disk; mirrors `gh`/`kubectl` pattern |
| ConnectRPC buf-gen | Use generated `sessionv1connect` typed client | `buf curl` is for inspection only; no proto→cobra generator exists |
| `--json` flag | Add to human-facing commands (`list`); always-JSON is fine for single-object commands (`get-session`, `get-diff`) | Matches `gh` model; tabwriter table for humans, JSON for scripts |

**No new library dependencies are required.** The entire feature can be built with
`text/tabwriter` (stdlib), `protojson` (already in `go.mod` via `google.golang.org/protobuf`),
`connectrpc.com/connect` (already in `go.mod`), and `config.LoadConfig()` (in-repo).
