# Pre-mortem: review-session-notification-cleanup
**Date**: 2026-07-25

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The plan only patches 2 of the ~15 `events.NewNotificationEvent` call sites in the codebase. `wireRateLimitCallbacks` (`server/services/session_service.go:3851-3894`) is wired unconditionally for every instance via `wireCallbacks`/`WireInstanceCallbacks` — including `SpawnReviewSession`'s `Hidden=true` sessions, since `CreateDirectorySession` → `wireCallbacks` has no `Hidden` branch anywhere. Its two closures (`onDetected`/`onRecovery`) publish "Session X rate limited" / "resumed after rate limit" notifications with no `Hidden` gate and no `item_id`/`session_scoped` metadata, so a Hidden review/triage session that hits an API rate limit mid-review still produces the exact dead-link Notifications-page entry this project exists to eliminate. This confirms the requirements' "Current State" section (itself a point-in-time code inspection) missed at least one live producer — proven by grepping all `NewNotificationEvent(` call sites, which the plan's own producer inventory (Epic 2 + Epic 3) never enumerates or cross-checks against. | Users still see noisy "Session X rate limited"/"resumed" cards with dead View-Session links after shipping, clustering specifically around periods of heavy API rate-limiting — exactly when many Hidden review/autonomous sessions run concurrently, i.e. right when the fix is needed most. | Before closing this item, grep every `events.NewNotificationEvent(` call site (not just the two Epic 2/3 targets) and classify each as item-scoped (already safe, e.g. `backlog_service_triage.go`'s notifiers) vs. session-scoped-and-unguarded (`wireRateLimitCallbacks`'s two closures at minimum). Add an `inst.Hidden` gate + `events.SessionScopedMetadata` call to every unguarded session-scoped producer, and add one test per producer to the regression suite — reusing the adversarial review's already-flagged "no structural guard against a 4th producer" concern, but pointed at a concretely identified miss instead of a hypothetical future one. | P1 |
| 2 | Every `NotificationRecord` persisted **before** this deploy decodes with `SessionScoped` defaulting to its Go zero value (`false`) per the plan's own Migration Plan. `PruneOrphaned`'s eligibility check requires `SessionScoped == true`, so the entire pre-existing pile of stale "TASK COMPLETE"/"Session idle" entries — the exact clutter the backlog item complains about — is permanently ineligible for the new pruning logic. It only disappears via the unrelated, pre-existing 7-day age-based `enforceRetention` trim. | Immediately after deploy, a user opens the Notifications page expecting the reported clutter to be gone and sees no visible change — only newly created notifications behave correctly; the perceived bug looks unfixed for up to a week. | Document this explicitly as an accepted limitation in plan.md/validation.md ("no backfill; pre-existing entries age out via the pre-existing 7-day retention, not the new orphan sweep") so it isn't discovered as a surprise post-ship; optionally add a one-time startup migration pass that infers `SessionScoped` for legacy records via the same title/UUID heuristic already used for `ListInstanceData` matching (safe as a one-time pass, unlike the rejected per-record predicate that runs on every `Append`). | P2 |
| 3 | Design Decision 1 makes Hidden-suppression unconditional on `Reason` specifically so `ReasonErrorState`/`ReasonTestsFailing` are also suppressed, reasoning "notify for conditions on a one-shot ephemeral process nobody is watching anyway." But if a Hidden review session crashes or errors before it ever calls `submit_review_verdict`, the backlog item is left waiting on a verdict that will never arrive, and this repo's own history (`project_backlog_stuck_review_investigation` memory: "root causes: auto-merge disabled, silent rework cap, non-durable notify-once state") shows this exact stuck-and-silent failure class has already burned this project once. The plan removes the review-queue notification as a signal for this case without verifying any other durable surface (e.g. a `MarkStuck`/`BacklogStuckState`-style mechanism, per `notifyReworkCapHit`'s pattern) actually covers `ReasonErrorState` specifically for `Hidden` review sessions. | A backlog item silently sits "in review" indefinitely; the only way to notice is scanning the backlog list for items that haven't moved in a while, since the one mechanism that used to page an operator for this exact session is now gone precisely because it's Hidden. | Before closing this item, verify (via test or a traced code path) that some durable stuck-detector already fires for a Hidden review session hitting `ReasonErrorState`/`ReasonTestsFailing`. If none exists, narrow Design Decision 1's suppression to only `ReasonTaskComplete`/`ReasonIdle`/`ReasonStale` (the requirement's literal three reasons) and leave error-class reasons notifying for Hidden sessions as a safety net — even though this contradicts the plan's current "unconditional on reason" choice. | P1 |
| 4 | `pruneOrphanedMinUptime`/`orphanPruneInterval` are explicitly flagged in the plan's own "Unresolved Questions" as "not derived from measured behavior." The wired closure calls `storage.ListInstanceData()` — the same full ent query (eager-loading `Worktree`/`Tags`/`Project`/`ClaudeSession+Metadata` per instance) the adversarial review already flagged as expensive per-record — once per minute, synchronously, while `NotificationHistoryStore.mu` (a write lock blocking all concurrent `Append`/read calls) is held. As this long-lived personal tool accumulates instance history over months, this once-a-minute call's cost is untested at the record counts it will eventually reach. | Intermittent, once-a-minute stalls on Notifications-page loads or other RPCs sharing the eventBus/notification path, worsening slowly over months — hard to correlate back to this specific change long after it shipped, especially since the Observability Plan deliberately logs nothing on no-op prune passes and never logs fetch latency, only non-zero prune counts. | Add a benchmark/test asserting `ListInstanceData()`'s cost at a realistic future instance count (e.g. 1,000+) stays under a fixed budget (e.g. 50ms) so a regression is caught before it becomes a production surprise; consider, as a documented follow-up, moving the batch fetch outside the write-lock-held section of `enforceRetention()`. | P3 |
| 5 | AC4 asks for a regression test confirming "a headless review session completing/going stale does not produce a Notifications-page entry" — but every test the plan adds is a unit test of one already-patched function in isolation (`Determine()` called directly with a hand-built `Instance`; `StartupScanner.Scan` called directly; `OnItemAdded` called directly with a hand-built `ReviewItem`). No test exercises the real end-to-end pipeline (poller tick → `checkSession` → `Determine()` → `queue.Add()` → `OnItemAdded` observer callback → `EventBus.Publish` → `eventToRecord` → `NotificationHistoryStore.Append` → persisted `notifications.json`) for a genuinely Hidden review session. Each layer's fix could be individually correct while a wiring assumption between layers (e.g. what `checkSession` actually passes to `Determine()`, or how the real subscriber reads back `session_scoped` metadata) silently doesn't hold. | All new unit tests and CI go green, but a headless review session in the actual running server still produces a Notifications-page entry — discovered only via later manual testing or a fresh user report, not by the test suite this plan asked for. | Add one true integration-level test (or as close to it as the test harness allows) that spins up a real `ReviewQueuePoller` + `ReactiveQueueManager` + `EventBus` + `NotificationHistoryStore` together, drives a genuinely `Hidden` instance to `TASK_COMPLETE`/`Idle`/`Stale` through the poller's own tick/check path (not a hand-called `OnItemAdded`), and asserts the resulting notification store gains zero new records — closing the gap between "each patched function is correct in isolation" and "the notification that used to appear no longer appears in practice." | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — **Resolved in plan.md.** Confirmed real by reading `server/services/session_service.go:3848-3898`'s `wireRateLimitCallbacks` (wired unconditionally for every instance, including `Hidden=true` review sessions). Added **Epic 5** (Stories 5.1/5.2) gating both closures on `inst.Hidden` and threading `item_id`/`session_scoped` metadata via `events.SessionScopedMetadata`. Two further unguarded producers (`CapacityMonitor.handleTransitionTrigger`, `SessionService.UpdateSession`'s steer-message notice) were found and explicitly documented as an out-of-scope follow-up rather than silently left uncovered.
- [x] Failure #3 — **Resolved in plan.md.** Investigated `session/backlog_lifecycle.go`'s `StuckReasonAbandonedReview`/`FindStuckReviewItems`/`FindZombieReviewItems` machinery: it durably covers a Hidden review session that crashes/exits before `submit_review_verdict`, but does **not** cover one still alive and stuck in `ReasonErrorState`/`ReasonTestsFailing`. Design Decision 1 was narrowed accordingly: suppression now applies only to `ReasonTaskComplete`/`ReasonIdle`/`ReasonStale`; error-class reasons still notify even for `Hidden` sessions as a safety net. Propagated through `Determine()`'s gate (now reason-scoped, not a first-statement early-return), `StartupScanner.Scan` (belt-and-suspenders change reverted, since it would otherwise bypass the reason-scoping), `OnItemAdded`'s guard, and new test cases (Task 1.1.1b's `ReasonErrorState` case, Task 2.3.1d).
