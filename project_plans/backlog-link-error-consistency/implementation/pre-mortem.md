# Pre-mortem: backlog-link-error-consistency
**Date**: 2026-08-16

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | A future 6th mutating backlog tool (or a silently-skipped story during implementation) reintroduces the raw `errors.Is(linkErr, session.ErrNotFound) → PERMISSION_DENIED` pattern, and nothing catches it because the table-driven test only enumerates the 5 known handlers by name — the structural grep guard `pitfalls.md` §3 recommended was never added to the plan's task list, a gap the adversarial review already flagged and the plan was not updated for. | A session hits the new tool's link check on a deleted item and gets `PERMISSION_DENIED` instead of `ITEM_NOT_FOUND` — the exact original bug recurring, invisible to CI. | Add a CI-enforced grep/ast-grep guard (e.g. `! grep -n 'errors.Is(linkErr, session.ErrNotFound)' server/mcp/tools_backlog.go` shows no matches outside `resolveItemLink` itself) to Task 2.1.1c or 4.1.1a, not just a manual "confirm 5 call sites" note. | P2 |
| 2 | `submitReviewVerdict` and `submitTriageResult` have zero pre-existing tests for their role-mismatch `PERMISSION_DENIED` branch (confirmed by the adversarial review's grep), and Epic 2.1's new table-driven test only covers the not-linked/not-found cases — so a transcription error in Tasks 1.2.3a/1.2.5a while hand-editing the surrounding role-check block could silently break or bypass role enforcement for these two handlers, and `make test` would still report green. | A wrong-role session (e.g. a "work" session calling `submit_review_verdict`) is either wrongly accepted (authorization bypass) or a correctly-roled session is wrongly rejected, discovered only in production or via manual QA, not CI. | Add one minimal role-mismatch test case per handler to Epic 2.1's table before implementation starts (mirroring `TestReportPRCreated_should_RejectCall_When_CallerRoleNotWork`), per the adversarial review's Concern #1 — do not ship on the unverified claim that role-mismatch behavior is "unchanged from today." | P1 |
| 3 | The `GetBacklogItem` fallback query, paid only on the not-found path, adds a second serialized query on the single `SetMaxOpenConns(1)` SQLite connection for every not-linked/not-found request — if that path becomes frequent (concurrent startup-race hits, or agents retrying per failure #4), it measurably worsens the already-documented `list_sessions`/`get_session`/`get_session_goal` connection-pool contention this same investigation flagged but explicitly declined to fix. | Timeout frequency for `list_sessions`/`get_session`/`get_session_goal` increases and correlates with backlog-tool error-path traffic after this fix ships, where before it was flat. | Capture (or explicitly estimate) expected not-found-path call volume before shipping, and note in the Observability Plan that a spike in `resolveItemLink`'s disambiguation-path log line should be treated as a leading indicator for connection-pool contention, not just a link-hygiene metric. | P3 |
| 4 | The improved `PERMISSION_DENIED` message tells the caller to "wait a few seconds and retry" for the startup-race window, but research confirmed there is no working `report_blocked` or other escalation tool anywhere in this codebase — so an LLM agent session whose link is *permanently* severed (e.g. item hard-deleted mid-session) has no way to distinguish "transient, retry" from "permanent, stop," and no exit ramp even if it correctly infers the latter. It retries indefinitely until it exhausts its turn/token budget. | Logs show a single session calling the same mutating tool many times in a row against the same item id, all returning `PERMISSION_DENIED`, with no successful call and no other tool activity in between — a runaway retry loop, not a transient race. | Change the remediation text to bound the retry (e.g. "retry once after ~10s; if it fails again, stop calling this tool and report this session UUID + item ID in your final summary") instead of open-ended "retry," and treat filing the `report_blocked` follow-up (already listed in Unresolved Questions) as a near-term prerequisite rather than an optional human decision, since this fix's own message actively encourages retry behavior with no defined exit condition today. | P1 |
| 5 | This fix is explicitly scoped (per its own non-goals) to make the error code correct, not to add a guard to `DeleteBacklogItem` against deleting an item with an active session — the actual trigger research identified for the reported incident. The bug class (a live session's item/link vanishing out from under it) will keep recurring at the same rate, just with a clearer error message, and the PR shipping may be mistaken for "the incident is closed" rather than "the incident is now legible." | Within the first month, an operator deletes a backlog item from the web UI while a session is actively working it; the session gets a well-labeled `PERMISSION_DENIED`/`ITEM_NOT_FOUND` response but is still permanently stuck with no way to recover its in-flight work — a repeat orphaned-session incident, now correctly diagnosed but not prevented. | Convert the plan's "Unresolved Questions" `DeleteBacklogItem` guard item from an optional human decision into a backlog item filed at ship time (make Task 3.1.1a require filing it, not just documenting it), so the fix's legibility improvement isn't mistaken for closing the incident class in the PR description or in any operator's mental model. | P2 |

## P1 Items (address before implementation)
- [x] Failure #2 — **Patched into plan.md**: added Task 2.1.1d (role-mismatch tests for `submitReviewVerdict`/`submitTriageResult`), added acceptance criterion (d) to Story 2.1.1, and corrected Stories 1.2.3/1.2.5's acceptance criteria to stop claiming "unchanged from today" as a verified baseline.
- [x] Failure #4 — **Patched into plan.md**: revised the `resolveItemLink` remediation string in Task 1.1.1a to bound the retry to one attempt with a concrete duration ("~10 seconds") and an explicit stop condition, and elevated the `report_blocked` follow-up in Unresolved Questions from optional to a near-term filed item.
