# Validation Plan: backlog-scaffolding-gitignore

**Date**: 2026-08-10

## Happy Path Scenario

Given a backlog work session running in the primary (linked, `git worktree add`) topology with only scaffolding files (`.backlog-context.md`, `.claude/commands/backlog/*`) written into it, when `addWorktreeExcludes` resolves `$GIT_COMMON_DIR` correctly and writes `ScaffoldingExcludePatterns` there, then `IsWorktreeDirty`/`GetWorktreeDirtyPaths` report the worktree clean and `request_review` neither rejects the call nor tells the agent to `git add -A` the scaffolding.

## Gaps Found

- **G1 — Story 1.3.2 AC 2 had no corresponding task/test in plan.md.** The plan's Epic 1.3 task list (1.3.1a/b, 1.3.2a/b/c) only covers `GetWorktreeDirtyPaths`'s general parsing correctness (dirty repo, clean repo, rename) and the pure message formatter — none of the three coded tests (`TestGetWorktreeDirtyPaths_ReturnsPathsForDirtyWorktree`, `_EmptyForCleanWorktree`, `_HandlesRenamedFile`) touch a linked worktree or scaffolding patterns at all. The specific claim in Story 1.3.2's acceptance criteria — "a worktree containing only scaffolding files ... `GetWorktreeDirtyPaths` returns `[]`" — is exactly the coupling this item's Scope section calls out as load-bearing ("shipping the message improvement without fixing `addWorktreeExcludes` first would make things worse"), yet nothing in the plan's task list would fail if that coupling broke. Closed above by adding `TestGetWorktreeDirtyPaths_EmptyForScaffoldingOnlyLinkedWorktree`, an integration test combining the Epic 1.1 linked-worktree fixture with `GetWorktreeDirtyPaths`.

- **G2 — Success Metric 4 (`IsWorktreeDirty` must keep shelling to `git status --porcelain`, not switch to go-git) has no automated check anywhere in the plan.** This is enforced only by the fact that Story 1.3.1's tasks don't touch `IsWorktreeDirty`'s implementation, verified by `go build ./...` plus a diff review showing `review_gate.go`/`backlog_review.go`'s existing function body is untouched. There is no test (and no obvious idiomatic Go test — this would need something like an AST/grep-based lint check, not a runtime assertion) that would fail if a future change swapped `IsWorktreeDirty` to go-git's `Worktree.Status()`. Acceptable to leave uncovered for this Complexity-2 item, but flagged rather than silently treated as tested — a future regression here would resurrect the exact bug class this item fixes (per the Alternatives Considered section of requirements.md).

- **G3 — The Epic 1.3-must-land-after-Epic-1.2 sequencing constraint has no automated enforcement beyond the new G1 test's incidental coverage.** Per the task brief's specific question: this ordering is purely a task-execution-order convention (see plan.md's Dependency Visualization diagram and the "Sequencing constraint" note at the top of Epic 1.3) — nothing prevents a future edit from regressing `addWorktreeExcludes` while leaving `GetWorktreeDirtyPaths`/the message wiring in place. The new `TestGetWorktreeDirtyPaths_EmptyForScaffoldingOnlyLinkedWorktree` test (G1) does incidentally act as a regression guard for the *outcome* (it would fail if the exclude fix regressed, since scaffolding paths would reappear in the dirty list), but it does not — and cannot — verify "ordering" as a process property. This is an acceptable gap for a Complexity-2 item per the task brief, noted rather than silently folded into "complete."

- **G4 — Story 1.2.1 AC 3 ("no behavior change for plain, non-worktree repos") is asserted only via "existing tests still pass," not a dedicated new assertion.** No test in the plan explicitly checks that `--git-common-dir` and `--git-dir` resolve to the same path for a plain `git init` repo (the mechanism by which the fix claims to be a no-op there) — the plan relies entirely on pre-existing `TestWriteSlashCommands_*`/`TestWriteBacklogContextFile_*`/`TestUntrackTrackedScaffolding_*` tests (which predate this change and were never written to detect this specific fix) continuing to pass. This is a reasonable/low-risk gap to accept for a one-line flag change with a well-precedented pattern (`session/git/util.go:148-161` already relies on the same equivalence), but it is not a dedicated regression test and should be named as such rather than counted as "covered."
