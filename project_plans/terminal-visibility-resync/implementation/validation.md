# Validation Plan: terminal-visibility-resync

**Date**: 2026-07-24

## Happy Path Scenario
Given a user with an active, connected terminal session whose backgrounded browser tab has silently render-desynced (coalesced/dropped tmux control-mode deltas while hidden), when the user refocuses the tab (`visibilitychange`→`'visible'` and/or `window focus` fire), then the client debounces the transition, sends exactly one `requestFullResync(true)` (`CurrentPaneRequest`), and the server's `clearAndHome + content` response repaints the pane cleanly within one debounce+RPC round-trip, with no keyboard focus stolen and no manual reconnect click required.

## Test Stack
- **Unit**: Jest (via `npx jest`) + `@testing-library/react` (`renderHook`/`act`), `jest.useFakeTimers()`/`advanceTimersByTime` for debounce and watchdog timing. All `useVisibilityResync` and `useDebouncedCallback` tests are pure-hook tests with mocked collaborators (`requestFullResync`, `connect`, `disconnect`, etc. as `jest.fn()`), no DOM component mount beyond `document`/`window` event dispatch and a single sibling `<input>` for the focus test.
- **Integration**: real (non-mocked) `@xterm/xterm` `Terminal` + real `TerminalStreamManager` for AC7 — explicitly forbids `jest.mock('@xterm/xterm', ...)` in that file (Task 3.1.1a) so the test exercises actual ANSI escape-sequence parsing, not an assumption about it.
- **E2E / UX**: manual repro for AC0 (Task 4.1.1a), recorded as a screen recording/screenshot pair in the PR description; no automated E2E harness is added or needed for this fix (see Risk Control: "no cohort/percentage rollout mechanism exists in this frontend").

## Cross-check notes (plan.md tasks read in full, not just the summary table)

- **Naming convention**: all 18 test names found across the three new test files consistently follow `methodName_should_ExpectedBehavior_When_Condition` (e.g. `useVisibilityResync_should_forceDisconnectThenConnect_When_resyncStallsPastWatchdogTimeout`). No deviations found — Step 3's flag-any-violation check comes back clean.
- **AC1's "call pair" language**: requirements.md AC1 asks for "exactly one full-resync call pair... paired with marking/clearing the pending-resync state," but Tasks 2.1.1d/e/f only assert the `requestFullResync` call count — they do not themselves assert the marking/clearing half of the pair. That half is separately covered by the AC5-associated tests (2.1.3a/b/d, 2.1.5d), which do assert `pendingResyncCompletionRef`'s set/clear behavior via its observable effects (`markResyncComplete`/`markPaneResponseReceived`/watchdog firing or not). Net: AC1's full "call pair" requirement is covered, but only by reading AC1's and AC5's test groups together — worth flagging so a reviewer doesn't look at 2.1.1d alone and conclude the pairing is untested.
- **AC7 test body is thinner than the AC1-AC5 tests**: unlike every `useVisibilityResync` test (each given as a literal, complete code block), Task 3.1.1b does *not* provide a literal test body — it says "Write the test body per the Given-When-Then in Story 3.1.1's Acceptance Criteria above" and leaves the implementation to prose description (seed stale content, write `clearAndHome + fresh`, assert via `getLine().translateToString()`, scan for absence of `"STALE"`/`"CORRUPTED"`). The Given/When/Then in the Acceptance Criteria is specific enough to implement unambiguously (exact API calls, exact assertions named), so this isn't a coverage gap, but it is a lower level of prescriptiveness than the rest of the plan and the one test in the suite without a name explicitly given in plan.md — flagged as a minor thinness note, not a blocker.
- **AC4's `LOADING` variant** (Task 2.1.2c) is described only as "add a second variant" without an explicit test name in plan.md, unlike its `CONNECTING` sibling which is fully named. Implementer should name it consistently, e.g. `useVisibilityResync_should_notCallConnect_When_visibilityFiresWhileTerminalStateIsLoading`, to keep the naming convention audit clean.
- **File-existence check**: confirmed via `test -f` that none of `useVisibilityResync.ts`, `useVisibilityResync.test.ts`, `useDebounce.test.ts`, or `TerminalStreamManager.resync.test.ts` exist yet in the working tree — consistent with this being the pre-implementation validation phase (Phase 4 of SDD, before Phase 5 implementation).
- **No thin/missing coverage found for AC0, AC2, AC3, AC6** — each has either a complete literal test body (AC2, AC3) or an appropriately non-code verification procedure (AC0 manual repro, AC6 scoped diff) fully specified in plan.md.
