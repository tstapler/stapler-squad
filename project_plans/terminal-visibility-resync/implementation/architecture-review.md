## Concerns

1. **Story 2.1.6's session-switch cleanup closes the "already-armed watchdog" race but not the "debounce still in flight" race — it moves part of the problem rather than closing it.** The cleanup effect (Task 2.1.6a) clears `resyncStallTimerRef` and `pendingResyncCompletionRef` on `[sessionId]` change, which correctly handles the case where a resync has already fired and is awaiting its response. But the debounce timer that coalesces `visibilitychange`/`focus` events lives *inside* `useDebouncedCallback`'s own `timeoutIdRef`, cleared only by that hook's internal cleanup effect, which has an **empty** dependency array (Task 1.2.1b: `useEffect(() => { return () => { if (timeoutIdRef.current) clearTimeout(...) } }, [])`) — i.e. it only cancels on full unmount, never on a prop/session change. Since `useVisibilityResync` (and therefore its one `useDebouncedCallback` instance) is called unconditionally from `TerminalOutput.tsx`'s render body and that component is stated to be reused across session switches without remounting (Story 2.1.6's own "Given" clause, corroborated by the real `[sessionId]`-keyed effect at `TerminalOutput.tsx:927-992` which resets state in place rather than remounting), a debounce timer scheduled while viewing session A that has *not yet fired* when the user switches to session B is never cancelled. When it fires ~300ms later, it invokes `handleVisibilityOrFocusResyncInner` — whose `console.info`/`console.warn` calls still say `sessionId=<A>` (closed over per-render) but whose actual `isConnectedRef`/`terminalStateRef`/`connectRef`/`requestFullResyncRef` reads are the shared refs already mirrored to session B's live values by that point. Net effect: a visibility/focus event that happened while viewing session A can force a resync (if B is connected) or a `connect()` attempt (if B is disconnected and not already `CONNECTING`/`LOADING`) against session B, mislabeled in the logs as belonging to A. Bounded/self-healing (worst case one extra `CurrentPaneRequest` or one gated `connect()` call, not corruption), so not a blocker, but it is a real, untested gap: Task 2.1.6b's regression test only exercises the case where the resync has *already fired* before the session switch (it advances 300ms, confirms `requestFullResync` was called, *then* switches `sessionId`), never the case where the switch happens *during* the debounce window. Recommend either (a) exposing a `cancel()` from `useDebouncedCallback` and calling it from the `[sessionId]` cleanup effect, or (b) guarding `handleVisibilityOrFocusResyncInner`'s body with a ref that's updated to the current `sessionId` and comparing it against the `sessionId` captured at schedule time, and documenting/testing whichever is chosen.

2. **`UseVisibilityResyncParams.terminalState` is typed `string` instead of the already-exported `TerminalState` union.** `useTerminalStream.ts:28` exports `export type TerminalState = 'DISCONNECTED' | 'CONNECTING' | 'LOADING' | 'STABLE' | 'RESIZING' | 'FETCHING_SCROLLBACK';`, but Task 2.1.1a's `UseVisibilityResyncParams` interface declares `terminalState: string;` rather than importing and reusing `TerminalState`. The disconnected-branch gate that Story 2.1.2/Risk Control leans on for closing the `connect()` in-flight race (`terminalStateRef.current === 'CONNECTING' || terminalStateRef.current === 'LOADING'`) is exactly the kind of comparison this widening silently defeats compile-time checking for — a future rename or typo of one of these state literals anywhere in the chain would not be caught by `tsc --noEmit` (the very check Task 2.1.7a relies on to prove the watchdog chain is sound). Low effort to fix: `import type { TerminalState } from '@/lib/hooks/useTerminalStream'` and use it in place of `string`.

## Nitpicks

- Risk Control's framing ("a background tab auto-connects, user refocuses within ~1s before the first message arrives") is slightly inaccurate: `TerminalOutput.tsx:439` passes `autoConnect: false` to `useTerminalStream`, so there is no hook-level auto-connect. The actual `connect()` call that makes the in-flight race reachable comes from `TerminalOutput.tsx`'s own mount/session-switch effects (e.g. `TerminalOutput.tsx:960`, `:980`, `:1004`), not from `useTerminalStream`'s `autoConnect` option. Doesn't change the validity of the `CONNECTING`/`LOADING` gate (Task 2.1.2b/c) or its test coverage — it's a documentation-accuracy nit in the plan prose, not a code issue.
