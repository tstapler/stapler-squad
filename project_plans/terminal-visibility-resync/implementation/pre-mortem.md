# Pre-mortem: terminal-visibility-resync
**Date**: 2026-07-24

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | All N pooled terminal sessions in one tab fire simultaneous `CurrentPaneRequest` RPCs off a single `visibilitychange` event (by design, per requirements) — no jitter/stagger, no client- or server-side concurrency cap — risking a synchronized server-side latency spike when a user with many sessions refocuses the tab. | Users with 10+ open sessions notice the whole web UI briefly freeze/lag exactly on tab refocus, correlated with a burst of `[resync] sessionId=...` log lines and a momentary CPU/lock-contention spike server-side. | Add small per-session random jitter (0-250ms) to the resync trigger, or a pool-level cap on concurrent in-flight `CurrentPaneRequest`s; load-test with 10-20 simulated sessions firing `visibilitychange` simultaneously and record server latency before merging. | P2 |
| 2 | The plan's tests and watchdog math model a merely-backgrounded tab (fake timers, `document.hidden` toggling), not a genuinely suspended machine (lid closed for hours). On wake, the WebSocket can be half-open with `isConnected` still `true`; the 4000ms watchdog assumes `disconnect()`/`connect()` settle promptly, but neither `useTerminalStream.ts`'s `disconnect()` nor the browser's `WebSocket.close()` is guaranteed to resolve quickly against a truly dead TCP path — the "self-heals in ~4s" promise has no enforced upper bound for the exact real-world trigger (long suspend/sleep) this bug report is about. | Bug reports of "terminal still stale 10-30+ seconds after waking my laptop" that don't reproduce with simple tab-backgrounding — only with actual OS suspend/long network loss — and therefore don't match anything in the automated test suite. | Add a manual repro step covering actual OS-level suspend/resume (not just `document.hidden` toggling) before shipping; consider a secondary hard client-side timeout that force-drops the stale WebSocket reference even if `close()` hasn't resolved, bounding user-visible recovery time independent of underlying socket/OS behavior. | P2 |
| 3 | AC7's integration test proves `terminal.buffer.active` state is correct after `clearAndHome + content`, but never calls `terminal.open()` or renders a frame — it structurally cannot detect a visible flash/flicker between the clear and the repaint, which is exactly the risk the plan's own UX research says to avoid. The only other check is one manual repro performed once by the implementer, who is primed to see the fix working. | User reports (or an unnoticed regression) of a visible blink-to-blank-then-repaint on every tab refocus, undermining the "silent" UX goal recorded in the Pattern Decisions table. | Extend the manual repro (Task 4.1.1a) to explicitly watch for and narrate flash/flicker, not just "content is now correct," ideally via a frame-by-frame screen recording; consider an additional rendered (DOM/canvas, `terminal.open()`'d) smoke check that intermediate paint state isn't visually blank for more than one frame. | P3 |
| 4 | `notifyResyncOutputReceived()`'s no-correlation-ID heuristic clears `pendingResyncCompletionRef` on the *first* output chunk received after a resync is requested. If a large pane/scrollback's `CurrentPaneRequest` response is ever split across more than one `TerminalData_Output` message (or an unrelated small chunk races in first), the watchdog is disarmed before the real repaint has fully arrived — silently defeating the fix precisely for the large-pane/heavy-TUI cases most likely to need it. | Reports that the resync "usually works but sometimes still shows a partial/corrupted repaint," disproportionately from large terminal panes — doesn't reproduce against the small fixed fixtures in Story 2.1.5's tests. | Confirm server-side whether large-pane `CurrentPaneRequest` responses can ever span multiple messages; if so, correlate on content (detect the `clearAndHome` prefix marker) rather than "any output arrived," or extend the watchdog to require a trailing quiet period after the marker before disarming. | P2 |
| 5 | The plan itself documents as an accepted residual risk that the pre-existing V2 listener (200ms debounce, disconnect-only) and this feature's new listener (300ms debounce, connected-and-disconnected) fire off the same `visibilitychange`/`focus` events with no shared coordination beyond an incidental timing gap. Combined with shipping unconditionally to 100% of traffic (no feature flag per Risk Control), any emergent interaction under real, irregular tab-switching (not the clean back-to-back-in-one-tick scenarios the tests cover) can only be mitigated by a full revert, not a flag flip. | A rise in reconnect-related log noise or duplicate-connect warnings within the first weeks in production, visible only under real rapid/irregular alt-tabbing patterns the test suite's single-shot fake-timer scenarios don't model. | Add a lightweight feature flag (env var or localStorage) gating the new listener before full rollout so a production issue can be disabled instantly; add a fuzz-style test dispatching many random-interval visibilitychange/focus events over a simulated multi-second window to probe state-thrashing interactions the current isolated-scenario test matrix doesn't cover. | P2 |

## P1 Items (address before implementation)

None of the five failure modes above rise to P1 (likely-and-catastrophic) — all are either P2 (likely but recoverable/self-healing) or P3 (unlikely, cosmetic). The plan's existing watchdog/self-healing design bounds the blast radius of #1, #2, #4, and #5 to "degraded/delayed recovery," not data loss or crash. Recommended before implementation, in priority order (not blocking, but cheap and worth doing given no P1s exist):

- [ ] #1 — add per-session jitter or a concurrency cap to `useVisibilityResync`'s trigger before merge, and load-test with 10-20 simulated sessions.
- [ ] #5 — add a simple feature flag gating the new listener, given the plan's own Risk Control section already flags the dual-listener interaction as an untested, accepted race.
- [ ] #2 — extend the manual repro (Task 4.1.1a) to include an actual OS-suspend/resume cycle, not just tab-backgrounding.
