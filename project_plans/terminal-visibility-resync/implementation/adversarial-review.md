## Prior Findings Resolution

- **Blocker 1 — no cleanup of pending resync/watchdog state on session switch** — PARTIALLY RESOLVED — Story 2.1.6 / Task 2.1.6a adds a `[sessionId]`-keyed cleanup effect that clears `resyncStallTimerRef` (via `clearTimeout`) and resets `pendingResyncCompletionRef`. This **does** eliminate the literal failure mode originally described ("a stale watchdog from session A could force-reconnect session B") — `clearTimeout` on the stall timer is unconditional and doesn't depend on ref content, so the 4000ms watchdog armed for session A can no longer fire `disconnect()/connect()` against session B. However, the *broader* class of "session-A-triggered async work leaking into session B" is not fully closed: the 300ms **debounce timer** inside `useDebouncedCallback` (Epic 1.2, reused as-is) is never cancelled on a session switch — its own cleanup effect has an intentionally empty `[]` dependency array (Task 1.2.1b: "runs once on unmount... matches the ref-mirror idiom") and `useVisibilityResync`'s single persistent hook instance never unmounts across a session switch (confirmed: `TerminalOutput.tsx` "reuses one long-lived component instance across session switches, never remounting," per Story 2.1.6's own acceptance-criteria text). See new Concern #1 below for the concrete reachable scenario this leaves open.
- **Blocker 2 — `connect()` has no in-flight guard / toothless test** — RESOLVED — Story 2.1.2 gates the disconnected branch on `terminalState !== 'CONNECTING' && terminalState !== 'LOADING'` in addition to `!isConnected` (implemented in Task 2.1.1b's `else` branch), and Task 2.1.2c replaces the original non-asserting test with one that asserts `connect` is called **zero** times while `terminalState === 'CONNECTING'` (and a `'LOADING'` variant). Verified against the actual code: `connect()`'s only guard is `isConnectedRef.current || !sessionId` (`useTerminalStream.ts:155`), and `setTerminalState('CONNECTING')` is set **synchronously** at `useTerminalStream.ts:172`, before any `await` — so the new hook's ref-mirrored `terminalStateRef.current` will reliably reflect `CONNECTING` well before a 300ms-debounced check runs, closing the specific reachable race named in the original Blocker (background-tab autoConnect + refocus-within-~1s). See new Concerns #2/#3 below for adjacent, not-fully-closed variants of the same underlying `connect()` guard gap.
- **Concern (a) — disconnected-branch not special-casing in-flight CONNECTING state** — RESOLVED — same fix as Blocker 2 (Story 2.1.2).
- **Concern (b) — `requestFullResync` not wrapped in try/catch, stall timer not armed unconditionally** — RESOLVED — Task 2.1.1b wraps the call in `try { ... } catch (err) { ... } finally { clearStallTimer(); resyncStallTimerRef.current = setTimeout(...); }` — the timer is armed in `finally`, so a synchronous throw is treated the same as a stall. Task 2.1.3c adds a regression test for this exact case.
- **Concern (c) — rapid visibility flapping re-arms the watchdog / duplicates resyncs** — RESOLVED — Task 2.1.1b's connected branch now no-ops (`if (pendingResyncCompletionRef.current) return;`) when a resync is already pending. Task 2.1.3e adds a regression test.
- **Concern (d) — AC1 test could pass for the wrong reason** — RESOLVED — Task 2.1.1e adds a focus-only test (no `visibilitychange`), Task 2.1.1f adds a >300ms-apart-produces-two-calls test.
- **Concern (e) — no test for the "any output clears the pending flag" false-positive risk** — RESOLVED — Task 2.1.3d adds `useVisibilityResync_should_notFireWatchdog_When_unrelatedOutputArrivesMidWindow`, locking in the accepted heuristic as executable behavior.
- **Concern (f) — TerminalOutput.tsx bloat / no hook extraction considered** — RESOLVED — Step 0.5's "Post-review refinement" + Epic 2.1 extract all new logic into a standalone `web-app/src/components/sessions/useVisibilityResync.ts`, unit-testable via `renderHook` without mounting `TerminalOutput`.
- **Concern (g) — Phase 5 aria-live scope drift** — RESOLVED — "Phase 5 — dropped" section removes it entirely from this plan and redirects it to a separate follow-up ticket.

## Concerns

- **Session-switch cleanup narrows the cross-session window but does not close it: a pending (not-yet-fired) debounce timer from session A fires 300ms later against session B's live `connect`/`disconnect`/`requestFullResync`.** Concrete sequence: a `visibilitychange`/`focus` event fires while session A is displayed → `debouncedResync()` (session A's `useDebouncedCallback`-wrapped closure) schedules a real `setTimeout` 300ms out, internal to `useDebounce.ts`'s `timeoutIdRef`. Within that 300ms window the user switches to session B (`sessionId` prop changes on the persistent `useVisibilityResync` instance). Story 2.1.6's cleanup effect (Task 2.1.6a) clears `resyncStallTimerRef`/`pendingResyncCompletionRef` but has no way to reach into `useDebouncedCallback`'s internal `timeoutIdRef` — `useDebouncedCallback` exposes no `cancel()`, and its own cleanup effect only fires on unmount (`[]` deps, Task 1.2.1b), which never happens here since `TerminalOutput`/`useVisibilityResync` persist across the switch. When the stale timer fires, it calls `handleVisibilityOrFocusResyncInner` — whose body reads `isConnectedRef.current`, `terminalStateRef.current`, `requestFullResyncRef.current`, `connectRef.current`, etc., all of which the no-deps ref-mirror effect (Task 2.1.1a) has *already* updated to session B's values by the time the switch's render committed. Net effect: an event that occurred while viewing session A ends up firing `requestFullResync(true)` (if B is connected) or `connect()` + `setShowReconnectButton(true)` (if B is disconnected and not mid-handshake) against session B, ~300ms after a visibility change the user made while looking at a different session. Blast radius is bounded (existing guards — `isConnectedRef` check inside `connect()`, the `terminalState` gate, the `pendingResyncCompletionRef` re-entrancy check — still apply, so this can't itself duplicate a stream or corrupt state), which is why this is graded a Concern rather than a Blocker, but it is a real, reachable instance of exactly the "stale trigger crosses into the wrong session" class of bug the original Blocker 1 was written to eliminate, via a mechanism (the debounce timer) Story 2.1.6 doesn't touch. **Recommendation**: give `useDebouncedCallback` an optional returned `cancel()` (or have `useVisibilityResync` own its debounce timer directly via a ref it controls, rather than delegating to `useDebouncedCallback`, for this specific call site), and call it from Story 2.1.6's session-switch cleanup effect alongside `clearStallTimer()`.

- **The new hook's `terminalState` gate is local to itself and doesn't coordinate with the pre-existing `NEXT_PUBLIC_RECONNECT_V2` listener, which shares the same `connect()`-guard gap and now has a second, uncoordinated trigger racing against it.** Confirmed in code: the V2 listener (`useTerminalStream.ts:420-446`) independently calls `connectRef.current()` after its own 200ms debounce on `visibilitychange`/`online`, gated only on `shouldReconnectRef.current && !isConnectedRef.current && !isDisconnectingRef.current` — it does **not** check `terminalState` at all, so it carries the exact same "no in-flight guard beyond `isConnectedRef`" weakness the plan's Blocker 2 fix addresses only for its own new caller. In the ordinary case (V2 enabled, a `visibilitychange`-while-disconnected event), V2's 200ms debounce fires first and flips `terminalState` to `CONNECTING` well before the new hook's 300ms debounce elapses, so the new hook's gate correctly no-ops — but this protection is **incidental to `200 < 300`**, not enforced or tested anywhere, and would silently stop working if `RESYNC_DEBOUNCE_MS` were ever tuned below V2's debounce in a future change. More importantly, the new hook also listens to a bare `window focus` event (e.g. alt-tabbing between two already-visible windows, multi-monitor OS focus changes) that V2 **never** observes (V2 is `visibilitychange`/`online` only) — so for that class of event, the new hook is now the sole trigger, and it can race against `connect()` calls from *other*, pre-existing `TerminalOutput.tsx` call sites (the 5s safety-timeout connect, the post-disconnect pending-connect effect) that also have no guard beyond `isConnectedRef`. This is a legitimate coverage improvement per requirements.md, but it does modestly widen the reachable surface for the still-open, explicitly-accepted-as-residual `connect()` gap — the Risk Control section's framing ("not made worse by it") undersells that a genuinely new trigger source (focus-without-visibilitychange) is being added where none existed before. **Recommendation**: at minimum, a code comment at the disconnected-branch gate noting the incidental V2-timing dependency; consider a regression test for "focus fires while a non-visibility-triggered connect() is already in flight" since that combination didn't exist pre-change.

- **The stall watchdog's own recovery path reopens a narrow window for a second, overlapping `connect()`/`disconnect()` chain.** When the watchdog fires (Task 2.1.1b), it sets `pendingResyncCompletionRef.current = false` (disarming the re-entrancy guard) *before* calling `disconnectRef.current().then(() => connectRef.current())`. `disconnect()` (`useTerminalStream.ts:359-401`) can take up to ~1000ms to resolve — it arms a fixed 1-second forced-abort timeout with no early-resolve signal when still connected — and `terminalState` only actually settles back to `DISCONNECTED` once the aborted stream's async loop unwinds and hits `connect()`'s own `finally` block, which doesn't happen instantly. A `visibilitychange`/`focus` event landing in this up-to-1-second window can read `isConnectedRef.current` as still `true` (routing to the connected branch, firing another `requestFullResync` at a socket already mid-teardown) or read a stale `terminalState` that isn't `CONNECTING`/`LOADING` yet (routing to the disconnected branch, calling `connect()` a second time in parallel with the watchdog's own pending `connect()`). This is a second-order instance of the same class of race Blocker 2 closed for the mount/autoConnect path, now reachable via the watchdog's self-triggered recovery instead. Narrow and low-probability (requires a user-visible transition to land inside a sub-second window that itself only opens after a 4-second stall), but not addressed or tested anywhere in the plan. **Recommendation**: hold `pendingResyncCompletionRef.current = true` (or an equivalent "recovery in flight" guard) for the duration of the watchdog's own `disconnect()`→`connect()` chain, clearing it only once `connect()` resolves, rather than clearing it immediately when the watchdog fires.

## Minors

- Story 2.1.6's cleanup effect correctness (reading `markResyncCompleteRef.current`/`markPaneResponseReceivedRef.current` inside the `[sessionId]` cleanup and getting the *previous* session's functions, not the new session's) depends on React's two-pass effect-commit model — all of a commit's effect **cleanups** run before any of its effect **setups**, so the no-deps ref-mirror effect's reassignment to session B's values happens strictly after the `[sessionId]` effect's cleanup has already read session A's values. This is correct as designed, but non-obvious and easy to silently break (e.g. by reordering the two effects, or "simplifying" the ref-mirror effect to have a cleanup of its own). Task 2.1.6b's test is the only thing that would catch a regression here — worth a one-line comment at the cleanup site calling out the ordering dependency explicitly, since the source code alone doesn't make it apparent.
- Every mounted pool `TerminalOutput` (up to 8, per the session pool in `SessionDetailView.tsx`) gets its own `useVisibilityResync` instance and independently reacts to the same document-level `visibilitychange`/`focus` event. A single tab refocus after being backgrounded can now fire up to 8 simultaneous `CurrentPaneRequest` RPCs, one per pooled session, rather than one for the actively-viewed session only. The plan's Observability Plan explicitly accepts this "by design," so not a defect, but the resulting simultaneous-burst server load was never quantified anywhere in Risk Control — worth a sentence confirming this is acceptable.
- The disconnected-branch gate's `terminalState === 'LOADING'` check (Task 2.1.1b) is effectively dead code: per `useTerminalStream.ts:210-217`, `isConnected` and `terminalState === 'LOADING'` are set together in the same statement block, so the `else` branch (only reached when `isConnectedRef.current` is `false`) can never actually observe `terminalState === 'LOADING'`. Harmless belt-and-suspenders, but worth a comment noting it's defensive/currently-unreachable so a future reader doesn't assume it's exercised by a real scenario (or write a test asserting it is).
