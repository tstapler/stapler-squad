# Adversarial Review: vscode-extension

**Date**: 2026-08-06
**Verdict**: CONCERNS

## Blockers

None. The prior blocker is resolved — Task 3.3.1e ("Register the tree view in extension.ts and wire disposal", `project_plans/vscode-extension/implementation/plan.md:354-356`) now:

1. Calls `vscode.window.createTreeView("staplerSquadSessions", { treeDataProvider: sessionTreeDataProvider })` in `activate()`, wiring `sessionTreeDataProvider` to the `staplerSquadSessions` view declared in Task 3.3.1c.
2. Adds a `dispose()` method to `SessionTreeDataProvider` that disposes its internal `EventEmitter` (the one created in Task 3.3.1b), and pushes both the returned `treeView` and `sessionTreeDataProvider` into `context.subscriptions`.

Sequencing is correct: Task 3.3.1e comes after the provider is created (3.3.1b) and the view is declared in `package.json` (3.3.1c), and within the same `activate()` wiring point used by every other subsystem (status bar, poll scheduler). A repo-wide check for `createTreeView`/`registerTreeDataProvider` in the plan turns up exactly this one call site — no duplicate or conflicting registration elsewhere. The task's own rationale text explicitly names the two failures this closes ("no provider is ever attached to it, so AC-3/AC-4 render nothing, and the `EventEmitter`... leaks on deactivate"), confirming the fix targets both original findings (missing registration and missing disposal).

## Concerns

- [ ] **Cross-window thundering-herd risk is named by research and left unmitigated by the plan's own admission.** `research/pitfalls.md` states plainly that "multiple VS Code windows (one per worktree, a common stapler-squad workflow) each independently polling... is a real thundering-herd risk against a single local Go process" and recommends `WatchSessions`/`WatchReviewQueue` streaming specifically to avoid it. The plan's Step 0.5 creative pass rejects streaming as "disproportionate lift... for a P3 backlog item," and its only mitigation — Task 3.3.1d, sharing one poll between the status bar and tree view — explicitly hedges "mitigates... at least within a single window," i.e. it does not touch the exact multi-window case research flagged as real. No jitter, no shared-lock/leader-election, no backoff-under-load, and no explicit written risk-acceptance exists for the case a developer has 5-10 worktree windows open simultaneously (a documented common workflow per this same research doc). — Recommendation: either add per-window poll-interval jitter (cheap, ~1 line) or add an explicit sentence in Risk Control accepting the risk with a concrete threshold (e.g. "N windows @ 8s interval = X req/s, acceptable because...").
- [ ] **"New Session in Current Folder" has no failure path.** Task 5.1.2b's spec is "calls `createSession(...)`, shows a confirmation `showInformationMessage` on success" — no mention of what happens when `createSession` rejects (duplicate title, invalid path, RPC/network error). Contrast with Approve/Deny (Task 4.2.2c), which gets explicit revert + `showErrorMessage` + "Retry" wiring, and with this repo's own instinct ("document AI decisions in edge cases" — never fail silently on a state-changing action). A user invoking this command over a dropped connection or invalid folder gets no feedback at all as currently scoped. — Recommendation: add a task mirroring 4.2.2c's failure-path pattern to Story 5.1.2.
- [ ] **No cancellation/disposed-guard for in-flight RPCs on deactivate/reload.** If a poll tick or an approve/deny RPC is in flight when the extension deactivates (window close, F5 reload during dev, Marketplace auto-update), its `.then`/`.catch` continuation fires after `context.subscriptions` has already disposed `StatusBarItem`/`TreeDataProvider`/`EventEmitter`, and will attempt to mutate disposed VS Code objects. `PollScheduler.dispose()` (Task 1.3.4a) only clears the interval timer — it doesn't cancel or ignore an already-in-flight tick's eventual resolution. No `AbortController` threading or `isDisposed` guard appears anywhere in the plan. — Recommendation: add an `isDisposed` check (or `AbortController` per Node's `connect-node` transport support) before any post-await UI mutation in `PollScheduler`'s tick handler and the approve/deny command handlers.
- [ ] **No content-drift detection between the two `buf.gen.yaml` TypeScript outputs.** ADR-001 explicitly accepts "two TypeScript copies of the same generated types" (`web-app/src/gen/` and `extensions/vscode/src/gen/`) as the tradeoff for not introducing a pnpm workspace. The only staleness guard (Task 1.2.1e, `Makefile:398-413`) checks *file existence* (`[ ! -f .../session_pb.ts ]`), not content parity — confirmed by reading the actual `Makefile` clause. In the ordinary path (`make proto-gen` running one `buf generate` call that writes both outputs together) this is low-risk, but nothing in the plan guards against a future partial regen, hand-edit, or CI workflow change silently diverging the two copies — and no CI step in this plan (or referenced from it) does a `git diff --exit-code` sanity check on either generated tree. — Recommendation: either note this is already covered by an existing web-app generated-code CI check (verify and cite it) or add one that also covers `extensions/vscode/src/gen`.
- [ ] **The documented "second manual instance on a different port" scenario has no task or test.** `research/pitfalls.md` and `CLAUDE.md`'s own "Manual/interactive testing" section both call out that a developer commonly runs a second instance on a non-default port (`PORT=8999`, or the e2e suite's `:8544`) and would need to repoint `staplerSquad.serverUrl` per-workspace. Task 5.2.1a declares the four settings but never specifies or verifies a configuration `scope` that permits per-workspace override (VS Code's default `"window"` scope does allow this, but the plan neither states this explicitly nor tests it), and no test in Phase 6 exercises a non-default `serverUrl`. — Recommendation: add one line to Task 5.2.1a confirming/declaring scope, and one test case pointing `getConfig()`/the transport at a non-8543 URL.
- [ ] **`extension.ts` accumulates every epic's wiring inline with no composition-root checkpoint.** Tasks 2.1.2c, 2.1.3a, 3.3.1d, 3.3.2b, 4.2.2c, 4.3.1b, plus three command registrations in Phase 5 all add directly to `activate()`. By the end of Phase 5, one function is coordinating the poll scheduler, status bar, tree provider registration (once Blocker #1 is fixed), three commands, approve/deny optimistic-update wiring, notify de-dup, and config-change listening — with no task anywhere that extracts this into a composition/controller layer once it grows. This is exactly the God-function risk the task description asked to check for in Phases 2-5, and the plan's own `interface-pollution-checklist.md`-style discipline (applied elsewhere in this plan to reject wrapper classes) isn't applied here to prevent the opposite failure mode — too little structure concentrated in one growing function. — Recommendation: not necessarily a new abstraction (would risk over-engineering per the plan's own stated principles), but at minimum flag this in the plan as a known risk with a stated size/complexity threshold (e.g. "if `activate()` exceeds N lines, extract an `ExtensionController`").

## Minors

- `CurrentWorkspaceMatch` (Epic 3.2) and the non-localhost `serverUrl` warning guard (Story 5.2.2) are both reasonable, research-grounded additions but map to no literal AC — worth one sentence in the plan explicitly flagging them as deliberate scope additions rather than leaving a reviewer to wonder whether they're scope creep.
- Task 8.1.1c's "never called from a poll tick" invariant is enforced only via "a documented invariant in the test's comment" — weaker than a real lint/import-boundary rule, and it's Phase-8 stretch work least likely to get review scrutiny if it silently regresses later.
- Unresolved Question 2 (`engines.node`/VS Code version pin) is already correctly flagged as open in the plan — no new finding, just confirming it's still unresolved as of this review.
