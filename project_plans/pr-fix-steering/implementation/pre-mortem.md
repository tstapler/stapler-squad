# Pre-mortem: pr-fix-steering
**Date**: 2026-08-26

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The entire `AutoReopenForPRFix` call — spawn **and** the new steer branch — is gated by `remediatePRFixWithBackoffGate`/`RemediationDue` (`session/backlog_lifecycle_pr.go:1182-1229`, `session/backlog_remediation.go`), a shared 30m→2h→8h→24h→72h exponential backoff keyed on `StuckReasonPRNeedsFix`. The first tick fires immediately, but nothing in `notifyActiveSessionSteered`'s success path resolves the `StuckReasonPRNeedsFix` row, so once one steer is delivered, the *next* opportunity to steer — even for a genuinely changed reason (Success Metric #2, conflict resolved → CI now failing) — is not "due" again for up to 30 minutes, then 2h/8h/24h/72h if the item stays stuck. All of Phase 2/3's reasonSignature/cooldown/debounce machinery only ever gets exercised in production on this rare cadence, not every ~60s tick as the plan and both reviews assume throughout. | An item's active session gets exactly one steer on first detection, then no follow-up steer for a changed CI/conflict/review reason for tens of minutes to days, even though the plan's dedup logic would allow a re-steer within 5 minutes if it were ever called. | Either (a) resolve/reset `StuckReasonPRNeedsFix`'s backoff row on a successful steer so RemediationDue treats the next distinct problem as a fresh "attempt 1," or (b) pull the steer branch out from behind `remediatePRFixWithBackoffGate` entirely — call `steerActiveSessionForPRFix` unconditionally on every tick regardless of `due`, since it already has its own 5-minute cooldown + reason-signature dedup and doesn't need the spawn-storm protection this gate exists for. Add an integration test at the `session` package level (not just `server/services`) that drives `remediatePRFixWithBackoffGate` across multiple ticks with a changing reason and an active session, asserting more than one steer fires inside the backoff window. (Positive side-finding: this same gate means a "steer storm" from a stale-then-refreshed GitHub status is *not* a realistic risk — the gate over-throttles rather than under-throttles.) | P1 |
| 2 | `session/backlog_lifecycle_pr.go:1240`'s `reconcilePRPendingItem` is the single shared body for both the 60s-tick loop (`ReconcilePRPending`, sequential, one goroutine) **and** `TriggerPRFixForEvent` (`:1599`). `TriggerPRFixForEvent` itself is invoked synchronously from the GitHub webhook handler (`server/services/github_webhook_pr_fix.go:302`) on every `check_run`/`workflow_run`/`pull_request_review`/`issue_comment` event — a feature that just shipped (PR #628, `15702ae95`) — but verified against the current source, it dispatches the actual `reconcilePRPendingItem` call onto a background goroutine (`go func() { l.reconcilePRPendingItem(...) }()`, `:1609-1611`) rather than running it inline with the HTTP response, so it's that dispatched goroutine — not the HTTP handler's own goroutine — that runs concurrently with the ticker. This makes the adversarial review's "not atomic across two overlapping reconcile ticks" concern a routine occurrence, not a rare timing coincidence: any actively-CI-churning PR (exactly this feature's target population) will regularly have a webhook-dispatched goroutine land mid-tick. | `BlockerChip` shows both `StuckReasonSteerFailed` and `StuckReasonRespawnBlockedActive` open at once, flickering between which one renders — reported as a confusing, hard-to-reproduce UI bug because it needs webhook+tick overlap to occur. | Extend `steerInFlight` (or an equivalent per-item lock) to wrap `steerActiveSessionForPRFix`'s entire body, including the degrade branches' `resolveSteerFailedLogged`/`notifyRespawnBlockedByActiveSession` calls, not just the delivery path in Task 4.2.1c — closing the exact gap the adversarial review flagged, using a ticker-goroutine-vs-webhook-goroutine race as the regression test's concrete scenario instead of two synthetic goroutines. | P2 |
| 3 | `buildSteerMessage` (Task 3.1.1b) builds `msg := fixContext + prShipSuffix` and truncates from the *tail* when over `session.MaxSteerMessageLength` (10000 bytes, `session/instance.go:139`). `PRStatus.render()`'s conflict block alone is ~1500 bytes of instructions, and `blockingReviews`/`generalComments` append reviewer comment bodies (`br.body`) verbatim with no cap — an ordinary combination (a couple of failing checks plus one substantive review comment) can push `fixContext` past 9700 bytes. Because the `/github:pr-ship` suffix is appended *after* `fixContext` and truncation cuts from the end, the one instruction telling a Claude Code session what action to take is exactly the part most likely to be silently dropped, while the diagnostic dump (which survives) gives no next step. Story 3.1.1's tests only exercise a synthetic oversized `fixContext` in isolation, never a realistic composed message, so this never surfaces in the plan's own test matrix. | A steered session receives a long, truncated problem description with no visible instruction and either stalls, asks the user what to do, or improvises something other than `/github:pr-ship`. | Reserve space for the suffix before truncating: compute the truncation budget as `MaxSteerMessageLength - len(prShipSuffix) - len(truncationPointer)` against `fixContext` alone, then append the suffix after, so the actionable instruction is never a truncation casualty. Add a test with a realistic long `fixContext` (multi-check failure + a long review comment) asserting the suffix survives. | P2 |
| 4 | Epic 2.3's two-tick debounce protects only against GitHub *over*-reporting a conflict (mergeStateStatus staleness, cli/cli#9583) — `GetPRStatus` (`session/git/worktree_git.go:499-560`) is a single unretried `gh pr view` snapshot with no equivalent guard in the other direction. If GitHub transiently *under*-reports (a real conflict or CI failure not yet reflected — GitHub's mergeStateStatus computation is itself asynchronous on their backend), the reconciler sees a "clean" PR and takes no action at all: not spawn, not steer, not even a stuck-state row, because `CIFailing`/`HasConflicts` never go true for that tick. Nothing in the reconciler or this plan watches for "PR has been stuck in a healthy-looking state for suspiciously long while the session is still active and not shipping." | A PR silently sits broken with an active session that never gets steered and never spawns a fresh fix, with no `StuckReason` row at all to alert on — worse than the "known and notified" respawn-blocked case, because there's no signal to notice. | Out of this project's stated scope to fully close, but at minimum: note the asymmetry explicitly in the plan/ADR (only one staleness direction is defended), and consider a follow-up watchdog: if an item has sat in `pr_pending` with an active session for N reconcile ticks with zero `CIFailing`/`HasBlockingReviews`/`HasConflicts` ever observed true, yet the PR also never reaches merged/closed, flag it — a distinct signal from today's `StuckReasonPRReadyUnmerged`. | P3 |
| 5 | `backlogSvc.SetSessionSteerer(sessionService)` (Task 1.2.2b, one new line in `server/dependencies.go`) has no test coverage that would fail if it's omitted or misplaced during implementation. Every existing and planned test (`grep SetSessionStopper` across `server/services/*_test.go`) constructs a `BacklogService` directly and wires the mock steerer by hand — none exercises `BuildCoreDepsWithOptions`/the real wiring path. Because the nil-safe degrade path (`s.sessionSteerer == nil`) is *by design* externally indistinguishable from today's shipped behavior (falls back to `notifyRespawnBlockedByActiveSession`, unchanged), a forgotten or misplaced wiring line compiles, passes `make ci`, and ships with the entire feature silently inert. | Nothing — that's the point. No error, no failing test, no distinct log line (the degrade path logs the same message the pre-project code already logged). Only discoverable by an operator noticing an active session was never steered despite a CI failure sitting for a long time, or by someone reading the `dependencies.go` diff line-by-line. | Add one integration/smoke test asserting `sessionSteerer` (and, while at it, `sessionStopper`) is non-nil after `BuildCoreDepsWithOptions` runs — mirroring the kind of wiring-assertion test this repo already uses for other required setters — so a missing `SetSessionSteerer` call fails CI instead of shipping silently. | P2 |

- [x] #1 — Addressed in plan.md's Story 4.2.2 (`session/backlog_lifecycle_pr.go`, `server/services/backlog_service_triage.go`): chose prevention (b), moving the active-session check (new `PRFixSpawner.HasActiveWorkSession`) ahead of `RemediationDue` in `remediatePRFixWithBackoffGate`, so `AutoReopenForPRFix`'s steer branch is reached on every tick regardless of the 30m→72h backoff, while the spawn branch remains fully gated.
