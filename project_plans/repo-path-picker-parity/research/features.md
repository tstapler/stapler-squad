## Quirks / edge cases per consumer

- **BacklogItemForm**: This is the only consumer combining `error` + `detectGitHubUrl` + `disabled`. Validation (`validate()`, line 290) runs only inside `handleSubmit`, not on every keystroke or blur — so `errors.repoPath` stays unset while the user types, and RepoPathInput's `aria-invalid`/error styling only appears after a failed submit attempt. `disabled={busy}` freezes the field (and implicitly closes/prevents interaction with the dropdown, since `RepoPathInput`'s own `disabled` prop passes straight through to the `<input>`) during an in-flight submit. `isCloningRepo` (`useMemo(() => isGitHubRef(repoPath), [repoPath])`, line 436) is derived independently in the parent for its own conditional UI, duplicating (by design) the same GitHub-ref detection `RepoPathInput` does internally for its own hint.
- **NewShellDialog**: Simplest consumer — no `error`, no `required`, no `detectGitHubUrl`. Field is genuinely optional (placeholder "Defaults to session directory"), so there is no validation-timing concern at all.
- **WorkflowForm**: `required` is set but there is no `error` prop wired — required-field violations must be caught elsewhere (submit-button disable or backend validation), not surfaced inline on this field. No GitHub-URL detection either, even though a workflow's target directory could conceivably be a repo.
- **LocalFileBrowser**: The only consumer using `onSelect` for behavior beyond filling the text value — selecting a dropdown entry triggers `navigate(entry.path)` immediately, same action as submitting the form (`handlePathSubmit` also calls `navigate(pathInput.trim() || "/")`). This is the closest existing analog to "pick from history → go" UX, relevant to R2/AC2 for the two Omnibar fields.

## Target fields in OmnibarCreationPanel.tsx (current state)

Both are **plain `<input type="text">`**, not `RepoPathInput`, with no field-level `error` prop wired to either — `OmnibarCreationPanel` only surfaces one **global** `error: string | null` (line 819, rendered once at the bottom of the whole panel) and gates the submit button via a single `canSubmit: boolean` (line 830, `disabled={!canSubmit || isSubmitting}`). Neither of the two target fields has ever had its own per-field error message — unlike `BacklogItemForm`, there is no `errors.parentDir` / `errors.existingWorktree` object to plug a `error` prop into today. Introducing `RepoPathInput`'s `error` prop for these two fields (if desired) would be new plumbing, not a swap of an existing per-field error.

1. **Parent Directory** (`omnibar-parent-dir`, lines 488-501, New Project mode): `value={parentDir}`, `onChange={(e) => setFormField("parentDir", e.target.value)}`, static hint "Directory where the new project folder will be created". No `required` attribute is currently set on the raw `<input>` despite the label showing `*`.
2. **Existing Worktree Path fallback** (`omnibar-existing-worktree`, lines 651-660, Existing Branch mode, only rendered when `worktrees.length === 0` and not loading): `value={existingWorktree}`, `onChange={(e) => setFormField("existingWorktree", e.target.value)}`. Same `id` (`omnibar-existing-worktree`) is shared with the `<select>` variant shown when worktrees *are* found — the two are mutually exclusive renders of the same field, so swapping only the fallback branch is a like-for-like conditional-render replacement.

## Edge cases specific to the two Omnibar fields (not faced by the other 4 consumers)

- **Parent Directory doesn't need to exist yet, and isn't a git repo at all.** New Project mode creates a *new* project folder (`${parentDir}/${projectName}`) — unlike every other `RepoPathInput` consumer, the value typed here is expected to often be a location that does not yet contain the target directory (only the *parent* must exist). `usePathCompletions` (filesystem completion, `directoriesOnly: true`) will legitimately return zero completions for a brand-new nested path, which is correct behavior, but there's no "this path doesn't exist" affordance today (none of the 4 consumers need one, since they all point at an existing repo). Session-history suggestions (`useSessionRepoPaths`) are still meaningful here — a user picking a *parent* directory would plausibly want to reuse a directory they've used before as a container for a repo/session, even though the sessions in history point at leaf repo paths, not container directories.
- **Existing Worktree Path fallback arguably SHOULD resolve to a real git worktree**, unlike Parent Directory. This is the opposite failure mode: `RepoPathInput` has no "verify this is actually a git worktree" capability anywhere in the codebase today (none of the 4 consumers validate git-repo-ness client-side either — `BacklogItemForm`'s `detectGitHubUrl` only detects GitHub *URLs*, not local git validity). The requirements doc explicitly scopes this out of R1-R6 (validation of worktree-ness is not called for in any AC), but it's worth flagging: this field only renders as a fallback when worktree *discovery* already failed/returned nothing (`worktreesError` or empty `worktrees`), so the session-history list (`useSessionRepoPaths`) — sourced from *all* known session root paths, not specifically git-worktree paths — may suggest paths that aren't valid worktrees for the currently-selected repo. This is a pre-existing imprecision in `useSessionRepoPaths` (it has no per-repo filtering at all, in any consumer), not something newly introduced by this feature, so it's silent scope creep to fix without an AC covering it — flag as a known limitation, not a blocker.
- **No existing per-field `error` state to attach.** Both fields currently rely solely on the panel-level `canSubmit`/`error` gate. If `RepoPathInput`'s `error` prop should show something (e.g., a required-field violation), new local error-derivation logic would need to be added to `OmnibarCreationPanel` — this doesn't exist for either field today and isn't strictly required by the ACs (R1-R6 don't mention field-level errors), so treat it as optional/deferred rather than in-scope, consistent with `WorkflowForm`'s precedent of `required` + no wired `error`.
- **The Escape-key-inside-a-keydown-capturing-modal hazard (R6/AC6)** is unique to the Omnibar embedding — none of the 4 existing consumers render `RepoPathInput` inside an ancestor that itself listens for Escape at the container/document level with `stopImmediatePropagation()` guards for its *own* dropdown-closing logic (`Omnibar.tsx` lines 748, 772, 820, 839 all show this pattern already exists for the omnibar's own internal dropdowns — it just isn't applied inside `RepoPathInput.tsx`'s own handler at line 134-137 today). This is the one true "porting existing pattern" fix needed, not new design.
- **`useSessionRepoPaths` recency-ordering gap (R3/AC3)** applies identically to all 6 eventual consumers (the existing 4 plus these 2 new ones) — it's not specific to the Omnibar fields, but the Omnibar fields are what surfaced it as user-visible (per the backlog item's stated motivation). Fixing `selectActiveSessionsSortedByUpdatedAt`'s missing tiebreak benefits every consumer transparently since they all go through the same `useSessionRepoPaths` hook.

## Unstated user needs implied by the backlog item description

The backlog item's stated goal — "recency-based… more easily select what they want more quickly" — implies more than literal parity with the 4 existing consumers:

1. **Speed of repeated task**: Users creating a New Project or resuming an Existing Worktree session are very likely doing so as a *repeated* workflow against a small set of parent directories / worktree roots (e.g. always `~/Projects` or always `~/.stapler-squad/repos/<org>/<repo>`). The value of recency ordering is disproportionately high for *this* entry point vs. e.g. `NewShellDialog`, where working directory is often left blank/defaulted. This argues for treating R3 (tiebreak fix) as high-priority, not a nice-to-have side effect.
2. **Trust that the suggestion list won't fight manual entry** (R4/AC4 already captures this explicitly) — implied because New Project's Parent Directory is exactly the case where the "correct" value (a brand-new subdirectory) will *never* appear in history or filesystem completions, so the UI must not make free typing feel broken or unsupported when nothing matches.
3. **Consistent muscle memory across the whole app** — a user who has learned RepoPathInput's keyboard/mouse interaction model (arrow keys, Enter to select, click-outside-to-close, Escape-to-dismiss) in `BacklogItemForm` or `LocalFileBrowser` should get identical behavior in the Omnibar without having to relearn a second, subtly different path-entry widget — this is the core "parity" ask, and is the direct justification for R1 (reuse, no new component) rather than building bespoke suggestion logic for these two fields.
4. **Mobile usability** is not explicitly called out in the backlog item text but is implied by R5/AC5's phone-viewport (390×844) requirement — the two target fields are used during session-creation flows the user is likely to trigger from a phone (per the project's standing mobile+desktop UX requirement), so dropdown tap-target sizing matters more here than it might for a desktop-only power-user flow like `WorkflowForm`.
