| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Epic 1.2's `selectActiveSessionsSortedByUpdatedAt` tiebreak change silently reorders the main Omnibar search box's "recent sessions" fallback list — a feature `requirements.md` explicitly puts out of scope — because `Omnibar.tsx:391` (`activeSortedSessions`, feeding the empty-query `sessionResults` at line 395) consumes the *same* selector `useSessionRepoPaths` is being switched to. Plan.md never mentions re-running `Omnibar.discovery.test.tsx`/`Omnibar.alias.test.tsx` or eyeballing that list after the change. | A user opens the Omnibar with an empty search box and the "recent sessions" quick-pick list shows sessions in an unfamiliar order (most sharply for sessions with identical/zero `updatedAt`, e.g. bulk backlog-created sessions, where the new final tiebreak — ascending UUID string — is not a meaningful recency signal, just a different arbitrary-but-stable one). No test fails; it just looks different in production. | Add an explicit Phase 3 task: run `Omnibar.discovery.test.tsx` and `Omnibar.alias.test.tsx` after Task 1.2.1a lands and confirm no assertion relies on incidental pre-fix ordering; add one test asserting `activeSortedSessions`' empty-query fallback order is unaffected/acceptable post-tiebreak. | P2 |
| 2 | The plan claims the Escape/`stopImmediatePropagation` fix also benefits `NewShellDialog.tsx`'s already-shipping identical bug (unconditional `document.addEventListener("keydown", ...)` → `onCancel()`, confirmed at `NewShellDialog.tsx:31-38`), but no test in the plan exercises that scenario. Task 1.1.1c's test wraps `RepoPathInput` in a React `<div onKeyDown={parentKeyDown}>`, which is a different propagation path than a real `document`-level native listener several DOM levels up (matching neither `NewShellDialog`'s nor `Omnibar`'s actual topology precisely) — the only test that hits a real `document`-level listener is the Omnibar-specific e2e in Task 3.1.1e, which says nothing about `NewShellDialog`. | `NewShellDialog`'s Escape-to-cancel either still swallows dropdown-open Escapes forever (bug not actually fixed for that site despite the plan claiming it is) or, worse, an existing `NewShellDialog.test.tsx` case starts behaving differently in some edge state nobody anticipated — surfaced only when a user reports "Escape doesn't close the new-shell dialog anymore" weeks later. | Add one unit or e2e test that mounts `RepoPathInput` inside `NewShellDialog` (or a minimal harness using a real `document.addEventListener` listener, not a React `onKeyDown` prop) with the dropdown open, and asserts `onCancel` is NOT called — proving the claimed cross-component fix actually holds for the second hazard site the plan explicitly cites as a beneficiary. | P2 |
| 3 | Epic 1.1's shared-component changes (Escape gating, `role="combobox"`/`aria-haspopup`/`aria-expanded` triad) apply to all 6 `RepoPathInput` consumers, but Phase 3's verification (Epic 3.1) only re-runs the two Omnibar e2e specs — `BacklogItemForm.test.tsx`, `WorkflowForm.test.tsx`, `LocalFileBrowser.test.tsx`, and `NewShellDialog.test.tsx` (plus their e2e coverage, e.g. `local-file-browser.spec.ts`) are never listed as regression-verification steps for the shared-component change itself. | One of the other 4 consumers' existing unit/e2e suite goes red in CI after merge (e.g. an a11y snapshot or role-based query elsewhere assumes the input's implicit `role="textbox"`), or — more likely — nothing fails locally but the PR's Axe Core CI gate (which runs on any PR touching `web-app/src/`) flags a new WCAG issue on one of the untouched 4 consumers because `aria-expanded`/`role="combobox"` interacts with other ARIA attributes already present there in a way `RepoPathInput.test.tsx`'s isolated tests don't catch. | Add a Phase 3 task: run the full `cd web-app && npx jest --no-coverage` suite (not just `RepoPathInput.test.tsx` and the 2 new consumer files) before considering Phase 1/2 done, specifically calling out the other 4 consumers' test files by name as must-pass. | P2 |
| 4 | Task 3.1.1f-contingency (open-upward dropdown fallback) is discovered reactively at the tail end of implementation, is itself a `RepoPathInput.tsx`/`.css.ts` change affecting all 6 consumers (same blast radius as #3, compounded), and its own "done" bar is just re-running the two original bounding-rect assertions — no dedicated test for the upward-opening dropdown overlapping the field's own label/hint text above it, no dark-mode check, no check against the other 5 consumers' layouts (e.g. `LocalFileBrowser`, which may have a different container shape than the Omnibar modal). | If triggered: the 390×844 e2e check goes green, but a user on a different consumer (e.g. `WorkflowForm` in a narrower panel, or `BacklogItemForm`) sees the dropdown open upward and cover the field's own label, or open upward when there was no need to (viewport-detection heuristic firing based on the Omnibar modal's specific geometry, not the actual consumer's). | If Task 3.1.1f fails and the contingency triggers, add explicit sub-tasks: (a) a screenshot/visual check that the upward-opened dropdown does not overlap the label/hint, (b) at minimum a manual smoke check in `NewShellDialog` and one other consumer, not just re-running the Omnibar-specific bounding-rect assertions. | P3 |
| 5 | Task 3.2.1a's feature-registry JSON is hand-authored with `"tested": true` and free-text `testIds`, but `make registry-generate`'s frontend step (`tools/scanner/frontend/src/main.ts`) scans `web-app/src` for `// +feature: <id>` marker comments to (re)generate entries — the plan never adds a `// +feature: repo-path-picker-parity` marker to `OmnibarCreationPanel.tsx`, and the backend scanner is already known to prune stale/unmatched per-feature files (`prune-stale-backend.sh`). If the frontend scanner has equivalent unmatched-entry pruning or simply never marks the hand-written entry as scanner-confirmed, `.claude/rules/feature-registry.md`'s own rule that `testIds` must exactly match `describe > test` names is also unmet by the plan's mixed spec-filename/describe-string values. | `make registry-generate` (required by `make ci`) either silently drops/overwrites `docs/registry/features/frontend/ui/repo-path-picker-parity.json`'s hand-set fields, or `coverage-gaps.json` doesn't actually reflect this feature as covered despite AC7's requirement — discovered only when `make ci` is run for real during Task 3.2.1b, potentially after the PR is otherwise considered done. | Add a `// +feature: repo-path-picker-parity` marker comment near the top of `OmnibarCreationPanel.tsx` (or wherever the scanner's convention requires it) as part of Task 3.2.1a, and correct `testIds` to the exact `describe`/`test` name strings the new e2e/unit tests actually use, per `.claude/rules/feature-registry.md`. Run `make registry-generate` once during planning/early implementation (not only as the final task) to confirm the hand-written file survives regeneration unchanged in the fields that matter. | P2 |
