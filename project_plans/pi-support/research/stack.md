# Research: Stack — pi integration

Agent 1 (Stack), SDD phase 2, project pi-support.

## pi itself — version and stability

- **Package**: `@earendil-works/pi-coding-agent`, npm dist-tags: `latest` = **0.84.4** as of 2026-09-02 (also a `legacy-node20` tag at 0.74.2 for Node <22). VERIFIED via `https://registry.npmjs.org/@earendil-works/pi-coding-agent`.
- **Node requirement**: `engines.node >= 22.19.0` on recent versions (was `>=20.6.0` around 0.74.0 — bumped since). If stapler-squad ever needs to invoke pi's TS build tooling itself (it shouldn't — see below), Node 22+ must be available; if it only shells out to the installed `pi` binary, this only constrains what Node the *user's* environment provides.
- **Package shape**: `"type":"module"`, `main: dist/index.js`, `bin: {pi: dist/cli.js}`, `types: dist/index.d.ts`. Built with `tsgo` (TypeScript's Go-based compiler front end) + `vitest`, not relevant to stapler-squad's own build.
- **API stability**: No formal semver/stability guarantee found anywhere in `pi.dev/docs/latest` (extensions, json, rpc pages) — no "stable API" language, no deprecation policy. Treat the extension API, JSON event schema, and RPC message shapes as **unversioned and subject to breaking change on any pi upgrade** (confirms the risk already flagged in requirements.md's Feasibility Risks). The JSON stream does carry a per-session `"version":3` field in its header line — that's the one explicit versioning hook available; stapler-squad's parser should read and log it, and can gate/warn on unexpected values rather than silently misparsing.
- **Recommendation**: pin nothing in stapler-squad itself (it doesn't depend on the npm package), but record the tested-against pi version (0.84.4) in a comment near the parser/extension code, and treat a pi version mismatch as a "verify against docs again" trigger, not an assumption of continued compatibility.

## Go side — invoking pi and parsing its event stream

### Detecting pi commands (mirror `ClaudeCommandBuilder`)

`session/claude_command_builder.go` (94 lines) is the exact shape to replicate:
- `isClaudeCommand()` does `strings.Fields(baseProgram)[0]`, strips any path via `strings.Split(name, "/")` and basename, lowercases, compares to `"claude"`.
- `Build()` short-circuits to the raw `baseProgram` unless there's session data with a non-empty, UUID-validated session ID, then appends `--resume <uuid>`.

For pi: `isPiCommand()` is the same basename-match against `"pi"`. Resume flag differs per requirements.md: pi's docs show `--session <id>` (and possibly a `-c`/continue-last shorthand) rather than `--resume`. **Action for planning phase**: confirm the exact flag name/format against `pi.dev/docs/latest/sessions` and `session-format` (not yet fetched in this research pass — the four pages fetched were `extensions`, `json`, `rpc`, and the top-level `latest` page; `sessions` and `session-format` should be re-checked before implementation since they define the resume-flag contract and the on-disk JSONL session file pi reads back). Given pi has no documented stability guarantee, this builder should be a small, isolated type (`PiCommandBuilder`) analogous to `ClaudeCommandBuilder` rather than a shared abstraction — keeps a future breaking change contained to one file, and matches the existing per-agent-CLI pattern already used in `cmd/ssq-hooks/main.go` (separate `installClaude`/`installGemini`/`installAgy`/`installOpenCode` functions, separate `writeHookDecision`/`writeGeminiHookDecision`/`writeAntigravityHookDecision`/`writeOpenCodeHookDecision` — one function per agent, no shared interface forced across them).

### Parsing `--mode json` (JSONL over stdout)

Format, confirmed from `pi.dev/docs/latest/json`:
- stdout, one JSON object per line (JSONL), first line is always a session header: `{"type":"session","version":3,"id":"...","timestamp":"...","cwd":"..."}`.
- Lifecycle pairs: `agent_start`/`agent_end`, `turn_start`/`turn_end`, `message_start`/`message_update`/`message_end`.
- Tool events: `tool_execution_start`/`tool_execution_update`(`partialResult`)/`tool_execution_end`(`result`,`isError`), each carrying `toolCallId`, `toolName`, `args`.
- `message_update` is delta-only (no cumulative snapshot) — use `contentIndex`+`delta` to reconstruct live text if a live transcript is needed; `message_end` has the authoritative final message. Idle/waiting-for-input is NOT an explicit event (confirmed in requirements.md's Rabbit Holes) — must be inferred as "no activity for N seconds after the last `agent_end`."

Go pattern to use: this is structurally identical to what a `bufio.Scanner` + per-line `json.Unmarshal` into a tagged union does — the same shape already used in this repo for hook payload parsing (`cmd/ssq-hooks/main.go`'s `parseGeminiPayload`/`parseOpenCodePayload` do `json.NewDecoder(os.Stdin).Decode(&payload)` and `json.Unmarshal(raw, &p)` against typed structs). For a growing stdout stream from a long-running subprocess (not a single stdin decode), prefer:
- `exec.Command(...).StdoutPipe()` + `bufio.NewScanner(pipe)` (raise `scanner.Buffer(...)` above the default 64KB token limit — `message_update` deltas can be large; the default `bufio.MaxScanTokenSize` is 64KB and pi transcripts can exceed a single line's default budget) — read line-by-line, `json.Unmarshal` each line first into a minimal `{Type string \`json:"type"\`}` struct to dispatch, then unmarshal again into the concrete event type (`AgentStartEvent`, `ToolExecutionEndEvent`, etc.) — the same "peek discriminator field, then re-decode into a typed struct" pattern already implicit in this repo's hook-payload structs (`classifier.PermissionRequestPayload`).
- No external streaming-JSON library is needed — stdlib `encoding/json` + `bufio.Scanner` is the idiomatic and sufficient choice for line-delimited JSON at this volume (single agent session, human-scale event rate). Do not reach for a SAX-style streaming JSON decoder (e.g. `jsoniter`) — it solves a different problem (partial/huge single documents), not JSONL framing.
- Existing `slog`-based logging pipeline (already required by requirements.md's Observability section) is the natural sink for "session status changed to X" transitions derived from this parser — no new logging library needed.

### RPC mode caveat (important for the approval-parity requirement)

`pi.dev/docs/latest/rpc` confirms the Rabbit Hole flagged in requirements.md: RPC mode's stdin/stdout protocol (commands/responses/events) does **not** itself expose a tool-call approval gate to the external process. The only approval-shaped signal that crosses the RPC boundary is `extension_ui_request`/`extension_ui_response`, and only when an **in-process extension** calls `ctx.ui.confirm()`/`ctx.ui.select()` — i.e., the approval must originate inside the pi process via the extension calling into the UI bridge, then RPC mode surfaces that as a UI round-trip the Go side can answer over stdin. This means: running pi in RPC mode alone (for status) gives no tool-call visibility/gating on its own — the extension is required regardless of which mode is used for status, and stapler-squad's Go side must handle `extension_ui_request` messages (matching `id`, replying via `extension_ui_response` on stdin) as its enforcement path if RPC mode is chosen. If `--mode json` is chosen instead of RPC for status (simpler, no bidirectional protocol), the extension still independently calls stapler-squad's HTTP approval endpoint directly (see below) — decoupled from whatever mode drives status. **Recommendation for planning**: prefer `--mode json` (one-way, simpler Go-side parsing, matches the read-only nature of "status for the session list") and have the extension call the existing approval HTTP endpoint directly over the network rather than round-tripping through RPC — avoids the "careful protocol sequencing to avoid deadlock" risk called out in requirements.md, and reuses a mechanism (HTTP callback from a hook/extension) already proven for Claude.

## TypeScript side — authoring the pi extension

### No build step needed for the shipped extension file

`pi.dev/docs/latest/extensions` confirms: "Extensions are loaded via jiti... so TypeScript works without compilation." jiti is a runtime TS loader (comparable to `tsx`/on-the-fly esbuild transforms) built into pi itself — pi loads raw `.ts` files directly from `.pi/extensions/*.ts` at startup. This is a materially different distribution model than Claude's `.claude/settings.json` hook (a JSON config block naming a shell command) or Gemini/Antigravity/OpenCode's flat-JSON hook patches in `cmd/ssq-hooks/main.go` (`patchBeforeToolHook`, `patchAntigravityHooks`, `patchOpenCodeHooks`) — those all point at the **already-compiled `ssq-hooks` Go binary**. For pi, stapler-squad ships a **source `.ts` file** as the artifact itself; there is no separate compile/bundle stage to run before injection, and no `tsc`/webpack/esbuild dependency needs to enter stapler-squad's own build. This significantly simplifies distribution: the extension can be a Go `//go:embed`-ed template string (or embedded file), rendered with the runtime approval-endpoint URL substituted in, and written verbatim to `.pi/extensions/ssq-approval.ts` — analogous to how `cmd/ssq-hooks/main.go`'s `openCodePluginContent(ssqHooksPath)` (line ~1229) builds a small JS/TS plugin file as a Go string template and writes it out, except pi's case doesn't even need `ssqHooksPath` since it's not calling out to `ssq-hooks` at all — pure TS calling `fetch()`.

### Extension shape (confirmed from docs)

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
export default function (pi: ExtensionAPI) {
  pi.on("tool_call", async (event, ctx) => {
    // classify via HTTP call to stapler-squad's existing approval endpoint
    // block via returning a deny/blocked result, or via ctx.ui.confirm() round-trip
  });
}
```
- Default export is a factory function taking `ExtensionAPI` (can be async; pi awaits it before `session_start` etc.).
- Relevant events for approval-parity: `tool_call` is explicitly documented as **blockable** (the event stapler-squad's extension must hook), `tool_result` is documented as modifiable. Other lifecycle events (`session_start`, `agent_start/end`, `turn_start/end`) are the same ones useful for status, meaning a single extension file *could* in principle emit status too — but per the RPC-mode caveat above, simplest is to keep status derivation in Go via `--mode json` and keep the extension scoped to `tool_call` gating only, per requirements.md's explicit non-goal of building general extension-management tooling.
- **Trust gating** (the Rabbit Hole in requirements.md): confirmed — "Project-local `.pi/extensions` entries load only after the project is trusted." A `project_trust` event exists for *global/user or CLI extensions* to decide trust programmatically, but the project-local extension itself is simply not loaded pre-trust; there's no documented way for a project-local extension to bypass or auto-answer this from inside itself. **Implication for the health-signal requirement**: stapler-squad cannot fully guarantee the approval extension is active just by writing the file — it must also verify (or surface) whether the target `.pi` project directory is trusted, otherwise "extension installed" and "extension enforcing" are different states and the observability requirement (per-session health signal) needs to check for both — e.g. by having the extension itself emit a one-time `notify`/status-set call on `session_start` that the Go side can watch for, and treating "no such signal within N seconds of session start" as the failure mode (trust-gated or otherwise not loaded), not by inspecting pi's trust state file directly (undocumented format/location — safer to observe via the extension's own successful-load signal, since that's confirmed to be inside our control).

### Interop patterns already in this repo worth reusing

- **Per-agent-CLI variant functions with no forced shared interface** (`cmd/ssq-hooks/main.go`): `installClaude`/`installGemini`/`installAgy`/`installOpenCode`, and `writeHookDecision`/`writeGeminiHookDecision`/`writeAntigravityHookDecision`/`writeOpenCodeHookDecision` — each agent gets its own small, explicit function rather than a generalized abstraction, because each CLI's hook contract genuinely differs (JSON stdout vs exit codes vs settings-file shape). Follow this for pi: a `writePiApprovalDecision`-shaped concept doesn't even apply the same way (the decision travels over HTTP from the extension, not back through ssq-hooks' stdout/exit-code contract) — which itself validates keeping pi's path structurally separate rather than jammed into the existing `handleCheck`/hook-decision dispatch in `cmd/ssq-hooks/main.go`.
- **Atomic file writes with idempotency checks** (`patchBeforeToolHook`, `copyBinary` in `cmd/ssq-hooks/main.go`; `InjectHooksConfig`/`InjectHookConfig` in `server/services/hook_injector.go`): write to `path+".tmp"`, then `os.Rename` for atomicity; check for "already present, nothing to do" before rewriting. The pi extension injector should follow the same shape when writing `.pi/extensions/ssq-approval.ts` — but note the *content* comparison for idempotency needs to account for the embedded approval-URL and any session-specific templating, not just byte-for-byte staleness against a fixed string like the Claude/Gemini hook JSON.
- **The webhook endpoint the extension should call**: `server/services/hook_injector.go`'s `hookEndpoints(baseURLFn)` map (keyed by `HookName`, e.g. `HookPermissionApproval` → `base + "/api/hooks/permission-request"`) is the single source of truth for hook URLs, already used by `InjectHookConfig`'s curl-based Claude hook (`server/services/hook_injector.go:807-843`ish: builds a `curl -s --max-time N -X POST '<url>' -H 'Content-Type: application/json' -H 'X-CS-Session-ID: <id>' -d @-` command string injected into `.claude/settings.local.json`). The pi extension's `tool_call` handler should call this **same** `/api/hooks/permission-request` endpoint (via `fetch()` from TS, not `curl`) with an equivalent JSON body and the same `X-CS-Session-ID` header — this directly answers the Open Question in requirements.md ("same webhook or new endpoint") in favor of reusing the existing endpoint: `HookPermissionApproval`'s URL is already agent-agnostic (a plain HTTP POST + JSON body), and `ApprovalHandler.HandlePermissionRequest` (`server/services/approval_handler.go:231`) is generic HTTP handling, not curl/Claude-specific. The classifier backend it calls into (`RulesService`, `rules_service.go`) is Claude-settings-shaped in *rule sourcing* (per requirements.md's Rabbit Holes) but the *request/response contract* at the HTTP boundary is already agent-neutral — the new work is translating pi's `tool_call` event payload (`toolName`, `args`) into the same `classifier.PermissionRequestPayload` shape the endpoint expects, analogous to what `parseGeminiPayload`/`parseOpenCodePayload` already do in Go for their respective agents, just done in TS inside the extension instead of in `ssq-hooks`.
- No existing web-app-side session-creation preset registry or `SessionStatus` enum was found under `session/` or `web-app/src` via targeted grep in this pass (`SessionStatus` hits were unrelated: `instance_adapter.go`, `search_service.go`, `telemetry/attributes.go`, `session/workspace/*`, `session/detection/ratelimit/*` — none is the enum requirements.md's Open Questions ask about). **Flag for planning/UI research agent**: the actual status-model and session-creation-preset locations need a dedicated look (likely `session/detection/` package and `web-app/src` session-creation components / `docs/reference/session-creation-registry.md`'s 7 touchpoints) — out of this Stack-research agent's scope but a direct dependency for the "status/output parsing" and "UI preset" in-scope items.

## Summary of concrete recommendations

1. Add `session/pi_command_builder.go` mirroring `ClaudeCommandBuilder`'s exact shape (basename match on `"pi"`, UUID-validated resume flag) — but confirm the actual resume-flag name against `pi.dev/docs/latest/sessions`/`session-format` before implementation (not yet verified in this pass).
2. Parse `--mode json` output with `exec.Command` + `bufio.Scanner` (raised buffer size) + discriminator-field `json.Unmarshal` into typed event structs — no new dependency needed. Avoid RPC mode for status; it adds a bidirectional-protocol deadlock risk for no benefit over one-way JSON mode.
3. Ship the approval extension as a Go `//go:embed` TS template rendered with the target approval URL, written atomically to `.pi/extensions/ssq-approval.ts` — no TS build tooling needed in stapler-squad itself, because pi loads raw `.ts` via its own jiti runtime loader.
4. Point the extension's `tool_call` handler at the existing `/api/hooks/permission-request` endpoint (`server/services/hook_injector.go`'s `HookPermissionApproval`) via `fetch()`, translating pi's tool-call shape into the same JSON body Claude's curl-based hook already sends — reuse, not a new endpoint.
5. Treat pi's project-trust gate as a real failure mode for the health-signal requirement: have the extension emit an explicit "I loaded and I'm active" signal on `session_start` rather than assuming file-presence implies enforcement.
6. Record pi 0.84.4 as the version this research was verified against; re-verify extension/JSON/RPC docs against the actually-installed CLI version before implementation, since no stability guarantee exists.
