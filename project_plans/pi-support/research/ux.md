# Research: UX — pi as a peer program to Claude Code

Agent 5 (UX Research), SDD Phase 2, project `pi-support`.

## 1. Comparable UX patterns

**How stapler-squad presents "program" today** (`web-app/src/components/sessions/OmnibarCreationPanel.tsx:916-934`, `web-app/src/lib/constants/programs.ts`):

- "Program" is a single `<select>`/combobox (`#omnibar-program`) backed by a flat list, `PROGRAMS: ProgramOption[]` — `{ value, label, description }`. Claude Code is just one entry (`{ value: "claude", label: "Claude Code", description: "Anthropic's CLI assistant" }`) alongside a Claude-proxy variant, Aider (plain + Ollama-model variant), OpenCode, Gemini CLI, Antigravity, and a raw "Terminal" (`bash`) escape hatch. There is **no visual tiering** — Claude Code gets no icon, badge, or special placement; it's differentiated from other agents only by being `DEFAULT_PROGRAM` and the "System default" placeholder entry resolving to it.
- The dropdown is backed by `useAvailablePrograms()` at runtime (`OmnibarCreationPanel.tsx:313`), which presumably probes `PATH`/config rather than trusting the static list blindly — `isProgramRecognized` (`:330`) flags free-text programs not in that list with a warning (`preset-program-warning`, `presetListStyles.programWarning`) rather than blocking submission. So the picker already supports "typed anything, warn if unknown" as a fallback — pi already works today exactly this way (per the requirements' Baseline), just with the warning and none of the parity features.
- **Presets** (`OmnibarPresetList`, collapsible section, `presetsOpen` state) are a separate, higher-level layer: a preset carries an `argv` array; selecting one derefs `argv[0]` into `program` and can also set `workingDir` (`:385-389`). This is the natural slot for a "pi" preset — a labeled, iconified shortcut that pre-fills `program: "pi"` — distinct from the raw Program dropdown entry that the session-creation-registry doc's touchpoint list doesn't even need to touch (adding a `PROGRAMS` entry + a preset entry is not one of the 7 session-creation-mode touchpoints; those are for `SessionType`, not for `program` string values — pi does not need a new `SessionType`).
- **Feature-gating per program is precedented**, not novel: `isAutoApproveSupported()` (`web-app/src/lib/sessions/autoApprove.ts:4,12-16`) hardcodes `AUTO_APPROVE_SUPPORTED_AGENTS = ["claude", "aider"]`, matched against `program`'s basename. The auto-approve checkbox in `OmnibarCreationPanel.tsx:972-980` disables itself and shows `Not supported for "${program}" yet.` when unsupported, and there's a `useEffect` (`Omnibar.tsx:233-240`) that force-unchecks auto-approve if the program changes to an unsupported one mid-edit. **This is the exact mechanism pi's approval-extension parity should reuse**: add `"pi"` to an equivalent allow-list (or a richer per-program capability map, since pi's mechanism is a shipped extension rather than a CLI flag) once the extension exists, and reuse the same disabled+tooltip UX for "approval rules apply" until it does.
- Program recognition also feeds `getProgramDisplay()`/`isKnownProgram()` (`programs.ts:55-65`) used elsewhere (session cards, headers) to render a human label instead of the raw command string — pi needs an entry here too or it displays as the raw string `"pi"`, which is actually fine/acceptable but loses the icon/branding requirement.

**External comparables (multi-agent CLI orchestration tools):** I did not have live web access in this pass to survey e.g. OpenHands, Aider's own multi-model UX, or newer multi-agent orchestrators (Devin, Cursor's agent picker, Zed's agent panel) — flagging as a gap rather than inventing citations. The in-repo pattern (flat select + capability-gated checkboxes + preset shortcuts) is a reasonable, low-risk baseline; if a follow-up pass has web access, compare against Zed's and Cursor's model/agent switchers specifically, since both already solve "different backends, same conversation-shaped UI."

## 2. User mental model

Given the existing architecture, a user's expectation for pi as a "peer" (not a second-class free-text hack) is:

- **Same picker, ranked visually with Claude Code**, not appended at the bottom of an alphabetical-ish list — `PROGRAMS` is currently ordered by rough popularity/recency (Claude first, then its proxy variant, then Aider, OpenCode, Gemini, Antigravity, bash). Inserting pi near the top (after Claude Code, before Aider) signals "second first-class agent" rather than "one more CLI someone glued in."
- **An icon/description consistent with the others.** All existing entries have a one-line `description`. pi's should name what makes it distinct in the same voice, e.g. `{ value: "pi", label: "pi", description: "@earendil-works/pi-coding-agent — TypeScript-extensible CLI" }`.
- **Resume works the same way it does for Claude — silently.** Per requirements, resuming a Claude session already reinjects a resume flag with no user action; a user picking pi and expecting the "same peer status" would be surprised if resuming a pi session dropped conversation context. This is already captured as an In-Scope item (`ClaudeCommandBuilder`-equivalent for pi), but worth stating as the *mental-model* consequence: **feature parity is table stakes for "peer," not a nice-to-have** — a picker entry that looks identical but silently behaves worse than Claude's on resume/status/approval would violate the affordance it presents.
- **Status indicators behave identically.** `SessionCard.tsx` renders one `getStatusColor`/`getStatusText`-driven glyph regardless of `program` (`:658-660`) — status is a property of the *session*, not the *program*, in the current model. That's good: it means pi doesn't need a parallel status UI, only a parallel status *source* (pi's `--mode json`/RPC stream feeding the same `SessionStatus` enum Claude's polling/hooks feed today). The open question in requirements.md ("is there an existing `SessionStatus`-like enum to extend") should resolve to: **extend the existing enum's value set if pi's states don't map 1:1 onto Claude's**, don't introduce a second status field — the mental model a user has is one indicator per session card, and any per-program branching there breaks that.
- **Approval-rules coverage should be silently assumed, not something the user has to remember to check per program.** Because rules apply automatically today for Claude, a user switching their default agent to pi (with the opt-in flag on) will assume the same safety net is in effect — which is exactly the gap requirements.md flags (extension load/health signal) and is addressed in §4 below.

## 3. Accessibility

No WCAG/ARIA guidance specific to the program picker exists yet as a written rule beyond what's already implemented; the closest sources are `docs/reference/feature-testing-registry.md` (registries, not a11y) and the CI note in the top-level `CLAUDE.md`: **"UX analysis CI runs on PRs touching `web-app/src/`: Axe Core (blocks on WCAG AA violations), Lighthouse CI (warns if score < 70)."** That means any new pi-related markup is automatically gated — no separate manual a11y checklist item needed, but the existing patterns below are the bar to match:

- **Program `<select>`** (`OmnibarCreationPanel.tsx:918-927`): has a `<label htmlFor="omnibar-program">` / matching `id` pair — a new pi option added to the same `<select>` needs no extra ARIA work, it inherits the label association for free. If pi instead gets a distinct "preset button" UI (per the Multi-agent-in-one-session UX item), that control needs the same labeled-control treatment, not a bare clickable `<div>`.
- **Program-unrecognized warning** (`:931-934`) is a plain `<span data-testid="preset-program-warning">`, not `role="alert"` or `aria-live` — screen-reader users get no announcement when their typed program is flagged unknown. This is a pre-existing gap (not introduced by pi) but worth noting since a parallel "pi extension failed to load" indicator (§4) should **not** repeat it — that one is more safety-relevant and should use `role="alert"`/`aria-live="polite"` at minimum, matching the pattern already used for `inline-error-${session.id}` (`SessionCard.tsx:586`, `role="alert"`) rather than the silent warning span.
- **Session status glyph** (`SessionCard.tsx:658-660`) is exemplary and should be the template for any new pi-specific indicator: `role="img"` + `aria-label={`Session status: ${getStatusText(session.status)}`}` — the visual glyph is decorative, the label carries the actual semantics. A new "extension health" badge (§4) should follow the identical `role="img"` + descriptive `aria-label` shape, not a bare emoji/icon with no label (as seen, less ideally, at `:607-623` for the external-session and remote-host badges, which do at least set `aria-label` on the wrapping element).
- **Keyboard**: the whole creation panel is native form controls (`<select>`, `<input>`, checkboxes) — no custom keyboard handling required for a new dropdown entry or a new checkbox-style capability toggle. If the "multi-agent-in-one-session" design introduces a custom widget (e.g., a per-turn agent switcher inside an active session), it needs its own keyboard/focus-management pass; that's new surface area, not something inherited for free the way the picker entry is.

## 4. Error states — pi extension injection/health failure

Requirements' Observability section calls for "an extension install/health metric: per-session signal indicating whether the pi approval-hook extension was successfully injected and loaded." From a UX standpoint this needs to surface in **at least two places**, mirroring existing failure-state patterns already in `SessionCard.tsx`:

- **Session list / card level** — `SessionCard.tsx` already has a taxonomy of failure-shaped statuses (`statusCrashed`, `statusCreationFailed`, `statusNeedsApproval`, `statusUnknown`, all mapped from `SessionStatus` at `:279-304`) and a documented rule that only two statuses are visually similar enough to need a distinguishing glyph (comment at `:309-311`). Extension-load failure is **not** a session-lifecycle failure (the pi process itself is running fine) — it should **not** be folded into `SessionStatus`. Instead it needs its own small badge/indicator analogous to the external-session (`🔗`) and remote-host (`🖥️`) badges at `:607-623`: an icon (e.g. a shield/warning glyph) with `role="img"` + `aria-label="pi approval extension: not loaded — tool calls are unenforced"` shown only when the flag is on, the program is pi, and health is unhealthy. This keeps the primary status glyph meaning "is the agent responsive" and a secondary badge meaning "is the safety net attached" — matching the existing separation of concerns (lifecycle status vs. metadata badges) rather than overloading one glyph with two meanings.
- **Explicit failure vs. silent absence**: the requirement explicitly worries about a "silent injection failure" disabling enforcement unnoticed. The UI's job is to make "unknown/not-yet-checked" visually distinct from "confirmed failed" and both distinct from "confirmed healthy" — a three-state badge (loaded/failed/unknown), not a binary. Precedent: `getProgramDisplay`/`isKnownProgram` already distinguish "recognized" vs not; the health badge should similarly never default to "assume healthy" — default to "unknown" until a positive signal arrives, so a stale UI can't read as "protected" when it isn't.
- **Session-creation time**: if the extension fails to inject *before* the session ever starts (e.g., trust-gate blocks it — a named Rabbit Hole in requirements.md), the creation flow should surface this the same way the "program not recognized" warning does today (`preset-program-warning` pattern) but with `role="alert"` per §3 — since here the stakes are "tool calls are unenforced," not just "typo in a command," it warrants an actual alert, not a passive hint.
- **Detail/analytics view**: `ApprovalAnalyticsPanel.tsx` already exists as a home for approval-rule audit data for Claude hooks — the natural place to also show pi's per-decision audit log (from the extension's webhook calls) and a persistent health-history view, rather than inventing a new panel.

## 5. Jobs-to-be-done

- **Functional job**: run a second, differently-capable coding agent (pi's TypeScript-extensible tool ecosystem) on the same project/worktree infrastructure stapler-squad already manages, without giving up the safety and continuity features that made Claude Code sessions trustworthy to leave running unattended — specifically resumability across restarts and rule-based approval gating on risky tool calls.
- **Emotional job**: confidence that switching or adding an agent doesn't mean stepping back onto a less-safe, less-familiar tool. The user (Tyler) is already running approval rules as a safety net for autonomous Claude sessions; the emotional payoff of pi parity is *not worrying* that a pi session left running overnight did something a Claude session would have been blocked from doing. A picker entry that looks first-class but isn't functionally at parity would produce the opposite feeling — false confidence — which is arguably worse than an obviously-second-class free-text entry.
- **Social/identity job** (weaker signal, but present given "pi" is a comparatively niche/new agent): being able to evaluate and adopt an interesting new agent-CLI inside an already-invested-in orchestration tool, without a fork-lift migration or a second, disconnected tool for babysitting it — i.e., stapler-squad continuing to be "the one place I manage all my agent sessions" rather than "the place I manage Claude sessions, plus a separate ad hoc process for anything else." This is the underlying reason "multi-agent-in-one-session UX" and "approval-rules parity" are both in scope rather than deferred: partial parity would undermine the tool's core value proposition (single pane of glass) for exactly the users likely to want a second agent in the first place.
