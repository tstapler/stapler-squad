# Architecture Review: pi-support
**Date**: 2026-09-02
**Verdict**: CONCERNS

## Constitution Check
`docs/adr/ADR-000-architecture-constitution.md` does not exist in this repository (`ls docs/adr/` shows ADR-001 through ADR-027 plus numbered non-ADR docs, no ADR-000). No constitution constraints apply — skipping the Constitution Violations section.

## Blockers
None. The plan is unusually disciplined for a pre-code review: it defers every unverified third-party fact (resume-flag syntax, event names, trust-gate behavior) to a Phase 1 spike rather than hand-coding from docs; ADR-001/002/003 each show verified evidence (file:line citations against this repo) for their decisions rather than assumption; and the fail-closed/three-state-health design directly targets the exact silent-failure mode (PITFALL-1) that would otherwise make this security-relevant feature dangerous. No correctness- or security-breaking structural issue was found.

## Concerns

- [ ] **Pattern Decisions table — "Status derivation for pi" / Epic 5.2.2 (`session/instance_status.go`)** — Adding a second parallel `piSources *xsync.Map[string, *PiStatusSource]` alongside `controllers *xsync.Map[string, *ClaudeController]`, with `GetStatus()` branching between them, is a genuine Open/Closed violation, not just a judgment call: every future status-source type requires *modifying* `GetStatus()` again (a third map, a third `if`), rather than extending it. It also adds a second and (per Story 5.3.1) third responsibility to `InstanceStatusManager` — it now must know about two structurally different status-holding types *and* reconcile against `ExternalApprovalMonitor`. The plan's stated reason for rejecting a shared interface ("would require stub/dummy implementations of Claude-only concepts") is a straw man: `ClaudeController.GetStatusAndIdleInfo()` already has the exact signature `(detection.DetectedStatus, string, detection.IdleStateInfo, int)` (verified: `session/claude_controller.go:1105`), which is precisely the 4-tuple `InstanceStatusInfo` needs from a non-active-command source — no PTY/command-queue methods need to be forced onto anything. **Remediation**: define a narrow `statusProvider` interface with just that method (plus `IsStarted() bool`, already on `ClaudeController`); `*ClaudeController` satisfies it with zero changes; `PiStatusSource` implements it via a thin wrapper around its own `CurrentStatus()` that fills unused fields with zero values (`detection.IdleStateInfo{}`, `0`) — exactly what the plan already does today via the "leave QueuedCommands/SubagentCount/LastCommandStatus at zero value" note in Task 5.2.2b, just moved behind an interface instead of a second lookup. Replace both maps with one `providers *xsync.Map[string, statusProvider]`. Extract Story 5.3.1's approval-reconciliation override into a decorator (`approvalAwareProvider` wrapping any `statusProvider`) rather than inlining it as a third branch in `GetStatus()`. This costs about the same code the plan already writes and avoids a guaranteed second rewrite the next time a status-source type is added.

- [ ] **Task 5.2.1c (`session/pi_status_source.go`)** — The chosen architecture (Alternative 3: an independent second `pi --mode json` subprocess for status, separate from the tmux-interactive `pi` process) rests on an unconfirmed assumption — that pi supports two concurrent invocations against the same session without state divergence or doubled cost/API calls — that the task itself flags only as a code-comment-level "confirm during implementation," not a spike gate. Alternative 2 (RPC-mode-everything) was explicitly rejected to avoid one kind of protocol risk, but this alternative reintroduces a different one (dual-process divergence) that is currently unverified until Phase 5, deep into implementation. **Remediation**: add this as an explicit Story 1.1.5 acceptance criterion in Phase 1 (alongside 1.1.1–1.1.4) — confirm whether launching a second `--mode json` pi process against an in-progress interactive session is supported and side-effect-free — before any Phase 5 story starts, not discovered mid-Epic-5.2.

- [ ] **Story 4.1.1 / Task 4.1.1d + Story 6.2.1 (`cmd/ssq-hooks/main.go`, `tests/e2e/pi-session.spec.ts`)** — The only verification that the generated `.pi/extensions/ssq-approval.ts` actually loads and blocks in a real pi process is a one-time manual step (Task 4.1.1d), recorded as a comment. Story 6.2.1's e2e spec only asserts UI-level preset selection, not that the real extension loads/enforces. requirements.md's own Feasibility Risks section names exactly this gap: "a pi upgrade could change or break the injected extension's contract with no warning" — but nothing in the plan re-runs that check automatically. **Remediation**: either add a periodic/CI smoke-test job that installs the pinned pi version and verifies the real extension loads and blocks a probe tool call, or explicitly document in Story 6.2.2's how-to doc that bumping the pinned pi version requires re-running Task 4.1.1d's manual verification before merging.

- [ ] **`PermissionRequestPayload.Source` (`pkg/classifier/classifier.go`, Story 4.3.1)** — A raw `string` field with two implied legal values (`"claude"`, `"pi"`) plus an empty-string default. Low priority today since nothing branches logic on it (display/analytics only), but a typo'd value (`"clade"`) would silently become its own unlabeled bucket with no compiler check. **Remediation**: `type ApprovalSource string` with `SourceClaude`/`SourcePi` constants costs nothing extra at this field's current usage and prevents that failure mode if the field's role ever grows beyond a display label.

## Nitpicks
- Pattern Decisions table labels `PiExtensionHealthTracker` "Observer/health-check pattern (GoF-adjacent)" — it's a timeout-tracked map with no subscribe/notify, not an Observer. Harmless, but worth a one-word correction ("health-check pattern" alone) so a future reader doesn't go looking for a GoF Observer structure that isn't there.
- `research/build-vs-buy.md`'s recommendation ("Hand-write the TS approval extension... conditioned on reusing ssq-hooks's existing exit-code/timeout contract") is superseded by ADR-001's direct-`fetch()` decision, but the research doc itself isn't annotated as superseded — a future reader skimming `research/` before `decisions/` could be misled. Add a one-line "superseded by ADR-001" pointer.
