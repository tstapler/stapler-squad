# Pre-mortem: pi-support
**Date**: 2026-09-02

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Story 1.1.2's go/no-go spike finds that none of `{block:true}`/`ctx.ui.confirm()`/a thrown exception actually stops pi's tool execution — plausible given ADR-003's own framing that "pi ships no built-in permission system at all" and the docs' `tool_call` vs `tool_execution_*` naming inconsistency (PITFALL-3) — and approval-rules parity, the requirement's core ask, becomes undeliverable for the installed pi version, with no pre-drafted fallback scope to fall back to. | During Phase 1, the probe extension logs the intercepted tool call to stderr but the tool executes anyway regardless of the returned/thrown value. | Pre-draft a "status-only" scope-cut variant of the plan (Phases 2/3/5 without Phase 4) *now*, so a go/no-go trip converts into an immediate, already-scoped decision instead of an open-ended escalation that burns the 3–6 week appetite waiting on "the user/requirements owner has chosen a path." | P1 |
| 2 | The re-ping interval (Story 4.2.3) and grace window (Story 4.2.1) are both explicitly "tune during implementation" placeholders validated only by a single synthetic unit test (4.2.3c); in production, ordinary network/Node-event-loop jitter causes the health badge to flap between Loaded/Failed/Unknown, training the user to ignore it — silently reproducing PITFALL-1's "looks installed but you can't trust the signal" concern one layer up, in the very mechanism built to prevent it. | The pi-extension health badge intermittently flips to "Failed"/"Unknown" on sessions that are actually fine, with no correlated server outage or crash. | Require the interval/grace-window pair to be validated against a real multi-hour captured pi session transcript (not just the synthetic restart test), document the ratio as an explicit constant relationship (e.g. grace ≥ 3× interval) in one place, and add a "badge flap rate" metric so drift is caught rather than inferred from user complaints. | P2 |
| 3 | The "single-user, not applicable" scalability framing ignores that each pi session now costs *two* OS processes (interactive tmux pi + a second `pi --mode json` status process) plus a bounded relaunch-with-backoff loop (Story 5.2.3); stapler-squad exists specifically to run many concurrent agent sessions, so a power user with a dozen-plus pi sessions doubles pi process count, and a single shared trigger (machine sleep/wake, a service restart — already a documented class of bug per `docs/explanation/service-restart-orphan-process.md`) can suspend/kill many status subprocesses at once, causing every affected `PiStatusSource` to independently enter its retry-backoff loop simultaneously. | After a laptop sleep/wake or service restart, a CPU spike coincides with several pi sessions' status badges flickering between Executing/Unavailable/Idle at the same time. | Add per-session jitter to the relaunch backoff (Story 5.2.3b) so retries don't synchronize across sessions, and add a process-wide (not per-session) cap on concurrent relaunch attempts, explicitly citing the orphan-process doc's precedent in that story rather than treating each `PiStatusSource` as isolated. | P2 |
| 4 | ADR-002's global install (`~/.pi/agent/extensions/ssq-approval.ts`) gates *every* pi invocation on the machine, including ones started entirely outside stapler-squad — but nothing in the plan ties the extension's presence to the `pi-support` Config flag's live state. A user who enables the feature, then disables it, is left with all pi usage (in or out of stapler-squad) still fail-closed (ADR-003) against a server that may not even be running, with the feature they explicitly turned off still fully in effect. | User disables `pi-support` in settings, later runs `pi` directly from a terminal for unrelated work, and every tool call hangs or is denied — with no obvious link back to a stapler-squad setting they think they turned off. | Add an explicit story: toggling `pi-support` to `false` triggers (or clearly prompts the user to run) `ssq-hooks install pi --uninstall`, so the flag's lifecycle actually controls the globally-installed artifact, not just stapler-squad's own UI surfaces. | P1 |
| 5 | pi is a fast-moving, independently-versioned third-party CLI with "no public API stability guarantee" (Feasibility Risks), mitigated only by a one-time Phase-1 spike against whatever version is installed on 2026-09-02. A later, stapler-squad-unrelated `pi` self-update changes the extension-loader contract or `tool_call` shape; because the extension is installed globally (finding #4), a load-time break isn't just a silent enforcement gap — it can prevent pi from starting at all, for every invocation on the machine, with zero stapler-squad code changed. | Weeks after shipping, `pi` fails to start (or logs an extension-load error) after a routine, unrelated `pi` self-update; the health badge flips to Failed, but the user's own direct pi usage surfaces the breakage first and is hard to correlate back to the injected extension. | Add a version guard at the top of `ssqApprovalExtensionTemplate` that logs-and-skips (fails safe on load, not silently incompatible) when the running pi's reported version falls outside a known-good range, and surface that mismatch through the same health signal rather than assuming forward compatibility indefinitely. | P3 |
