# Adversarial Review: omnibar-backlog-button

**Date**: 2026-10-17
**Verdict**: BLOCKED

Code claims were checked against `web-app/src/components/sessions/Omnibar.tsx`, `OmnibarCreationPanel.tsx`, `OmnibarModeBadge.tsx`, `OmnibarResultList.tsx`, `Omnibar.css.ts`, the compose test file, and a fresh `pnpm run lint:duplicates` run (VERIFIED: 15 clones, 0.14%).

Plan claims confirmed by reading: Tab swallowed in creation mode (`Omnibar.tsx:1217-1224`, no `e.target` check, handler on the modal wrapper at `:1799`); plain Enter falls through to `handleSubmitRef.current()` (`:1241-1247`); `isAtDropdownVisible = isDiscoveryMode && isAtCommand` (`:616`) hides the result list (`:2066`); `openBacklogCompose` is passed at both sites; the cancel path restores `input` and refocuses (`:1283-1287`, `:1765-1768`); `footer` has no `flexWrap` and `.modal` has `overflowX:hidden`.

## Blockers
- [ ] **The Tab guard does not make the footer button keyboard-reachable; Story 1.1.2 and AC2's keyboard claim are unachievable as designed.** The guard (Task 2a) only lets Tab through when `e.target` is already a `<button>`. Focus starts in the main input (or another form field), whose Tab is still swallowed by session-type cycling at `:1217`. Nothing moves focus onto the footer button except a mouse click. The unit and e2e tests (Task 3/4) would put focus on the button directly (`.focus()`), so they pass while a real keyboard user still cannot reach it. Recommendation: pick one and write it into the plan. (a) Narrow the story to "Enter/Tab on an already-focused button is not hijacked" and drop every "keyboard reachable" claim, with the AC2 row saying keyboard access in creation mode is not delivered. (b) Add a real path: a dedicated shortcut (for example Cmd/Ctrl+Shift+B, registered in the global handler and shown in the shortcuts bar), or let Tab leave the input once past the last form field. Either way, make the e2e test reach the button by key presses, not `.focus()`.

## Concerns
- [ ] **The guard changes behavior for every `HTMLButtonElement` in the modal, not only footer buttons.** This includes the "Open as" `role="radio"` buttons (`OmnibarCreationPanel.tsx:672`), the mode-badge buttons, the Create Session button in the shortcuts bar (`Omnibar.tsx:2213`), and the "More" toggle. Today Enter on any of them also calls `handleSubmit` and Tab cycles session type; after the guard Enter only clicks and Tab moves focus natively. This is arguably a fix, but the plan names only Cancel and the mode badge. Recommendation: list all affected buttons, add one unit assertion that Tab/Enter from the input still behaves as before (already in Story 1.1.2), and flag the radio-button Enter change in the commit message.
- [ ] **Guard placement is ambiguous relative to the alias, `@`, and path-dropdown branches.** The plan says "top of `handleKeyDown`", which preempts those branches for button targets (for example Enter on a button while the `@` dropdown is open no longer completes it). That is correct for buttons but untested. Recommendation: state the placement explicitly and add one test with a dropdown open and focus on a button.
- [ ] **Decision c (the `@` fallback) is an inconsistent UI.** The button is added to the discovery shortcuts bar (`Omnibar.tsx:2223-2232`), whose `.shortcuts` container is 12px text with a `marginLeft:auto` `createButton` convention. The plan reuses the 14px `buttonClass` styling with no layout spec. It also appears only in the `@` state, where the list row is hidden, so the button is conditionally present in a bar that otherwise has no actions. It is also scope creep beyond "footer action row". Recommendation: either drop the `@` fallback (the `@` state is a command-entry mode, not a card state needing the action) or specify its styling and add a layout check. Keep the owner flag.
- [ ] **AC1 in discovery mode is "not applicable", which is a stated downgrade.** The requirement says "visible in discovery (list row) and creation (footer)", so this is consistent. Still, the plan's AC table marks AC1 as verified only for creation mode; make it explicit in the traceability table that AC1 relies on the requirements' own discovery carve-out.
- [ ] **jscpd headroom is zero and the check is a rounded percentage.** The run shows 0.14% against a 0.14 threshold with `minLines 20 / minTokens 200`. New tests added to the existing file do not clone `jest.mock` blocks, and non-cloned lines dilute the ratio, so the risk is low; the plan's "no new test file" rule is correct. However, the new `OmnibarBacklogButton.tsx` plus the near-duplicate `@`-fallback and footer JSX could form a clone only if they reach 20 lines, which they will not. Recommendation: run `lint:duplicates` after Task 1 and after Task 3 (not only at Task 5) so a regression is attributed to one task.
- [ ] **Task 3 `@`-state tests depend on an unspecified fixture override.** `mockUseAtCommandSuggestionsModule` returns a fresh `jest.fn` with `isAtCommand: false` (`omnibarTestFixtures.tsx:~105`); the plan says "check how the fixture exposes the mock". The test file also mocks `OmnibarResultList` with its own row, so "list row present when input is `fix login`" would assert the mock, not the real component. Recommendation: spec the override (`jest.requireMock(...).useAtCommandSuggestions.mockReturnValue(...)`) and assert the real-row case in the e2e spec instead.
- [ ] **Narrow-width layout claim is unmeasured.** `flexWrap:"wrap"` plus `marginRight:"auto"` on the backlog button: when the row wraps, the auto margin puts the backlog button alone on the first line and Cancel/Create Session on the second, which is acceptable but not stated. The e2e check `x + width <= viewport` passes even if buttons overlap vertically. Recommendation: add a no-overlap assertion (distinct `y` or non-intersecting boxes) or accept and document wrapped layout.

## Minors

- The `OmnibarBacklogButton` extraction is justified by two call sites; if the `@` fallback is dropped (see Concerns) it becomes a single-use component and the extraction is optional.
- `Omnibar.tsx:1129` `Escape` handling and Cmd/Ctrl+Enter are correctly left alone; no issue.
- Touch-target size (T) is flagged but untested; acceptable for complexity 1.
- Duplicate "Create Session" button in the shortcuts bar (pre-existing) remains; fine to leave.
- The e2e Enter assertion (compose visible, focused) cannot detect an accidental session creation; the plan already delegates that to the unit test.
