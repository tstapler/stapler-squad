# Pre-mortem: go-auto-instrumentation
**Date**: 2026-08-21

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Spike B's go/no-go gate PASSes on a false premise: its only functional check is one read-only ent query (`session-list`/`ListSessions`, Story 1.3.2) and one `curl` to `/` (Task 1.3.1b) — CGO/SQLite weaving bugs (`pitfalls.md` #624/#736) more commonly surface under concurrent writes or transactions, which Spike B never exercises. | Weeks later, a real write-heavy workload (session create, backlog update) run against `stapler-squad-otel` hits a SQLite lock/DSN error or crash that Spike B's recorded PASS gave no warning of. | Spike B (Story 1.3.2, plan.md:304-323; Task 1.3.1b, plan.md:296-298) tests read-only paths only. Add a write-path acceptance criterion to Story 1.3.2 (e.g. drive a session-create RPC, not just `ListSessions`) before the gate is recorded PASS. | P2 |
| 2 | The project ships a correct, documented, opt-in `make build-otel-auto` that nobody runs again after Phase 6 — adoption is fully deferred to a "follow-on decision" (requirements.md Out of Scope, line 54) with no mechanism in the plan that creates adoption pressure, and the Isolation Guard (Story 2.1.3) that protects the default build *also* guarantees CI never exercises the target, so its own bit-rot has zero automatic detection. | Six months on, `otelc` has moved past the version Story 1.1.1 recorded, `make build-otel-auto` fails on first re-run, and nobody notices because it was never in CI and nobody had reason to run it — the observability gap requirements.md opened with is exactly as unaddressed as before this project existed. | Story 6.1.1 (plan.md:841-854) writes a recommendation but names no re-visitation trigger. Add an explicit "revisit-by" precondition to `adoption-recommendation.md` (e.g. a backlog item scheduled for N months out, or a periodic — not CI-wired — run of `scripts/otel-auto-smoke.sh` to catch drift) so the deliverable includes a mechanism for staying current, not just a point-in-time verdict. | P1 |
| 3 | The Isolation Guard (Story 2.1.3) only text-greps `make -n <target>` output for the literal strings `otelc`/`stapler-squad-otel`. `make -n` prints each target's recipe *lines* but does not recurse into the contents of any script those lines invoke — so a future edit that adds a call to some other script (not `scripts/otel-auto-*.sh`) which itself conditionally shells out to `otelc` deep inside its own logic would never match the grep, because the string never appears on the printed `make -n` recipe line. | `make ci` starts silently depending on `otelc` being on `PATH` (breaking CI runners that lack it) — or worse, silently succeeds and produces a woven artifact where `stapler-squad` was expected — with the Isolation Guard reporting all-PASS the whole time. | Story 2.1.3's guard (plan.md:482-509, Task 2.1.3a plan.md:496-499) is a single-layer text match over dry-run output. Add a second check: `grep -rl otelc scripts/` (or all first-party scripts referenced anywhere in the five targets' `make -n` output) to confirm none besides `scripts/otel-auto-*.sh` itself contains the string — closing the "otelc reached through a script's own logic" gap the top-level dry-run grep cannot see. | P2 |
| 4 | Phase 3's Overhead Report (Story 3.1.1–3.1.5) benchmarks exactly four previously-profiled hot paths (`GetStatus`, `ReviewQueuePoller.checkSession`, `CircularBuffer`, `GitWorktree.IsDirty` — plan.md:63,699) inherited from unrelated prior perf projects (mutex hotspots, circular buffers) — none of which is an ent/`database/sql` query path, even though ent's `database/sql` driver is requirements.md's *named flagship target* for weaving (line 21) and the layer `pitfalls.md` flags as highest-risk for CGO overhead. The Overhead Report's headline could read "acceptable overhead" while the one path this whole project exists to instrument was never benchmarked for cost, only checked once for correctness (Spike B). | A developer running `stapler-squad-otel` under a DB-heavy workload (e.g. backlog polling) sees materially worse latency than the Overhead Report implied was "the" acceptable bound. | Story 3.1.3's acceptance criteria (plan.md:698-701) name only the four legacy hot paths. Add an ent/`database/sql` query-throughput benchmark as a fifth named hot path in Story 3.1.1/3.1.3, and require Story 3.1.5's headline (plan.md:727-738) to explicitly scope what was and wasn't measured — the same "no claim stronger than evidence" discipline Story 2.3.3 already applies to the Parity Report. | P2 |
| 5 | `otelc` is explicitly "an external binary install, not a Go module dependency" (Story 4.1.1, plan.md:751) — so nothing in `go.mod`/`go.sum` pins its version. Story 1.1.1 records the version *once*, at project start, but no later story re-checks it before consuming its own spike-derived assumptions weeks into the 3–6 week appetite. | Phase 3 benchmarks or Phase 5's subprocess hook are quietly run against a different `otelc` version than Spike A/B validated, producing numbers or a "PASS" that don't actually trace back to the tool version the Adoption Verdict cites. | Add an acceptance criterion to Story 6.1.1 (plan.md:841-854) and to the benchmark stories (3.1.1/3.1.2) requiring `otelc version` be re-confirmed against Story 1.1.1's recorded value before each is trusted, with any drift logged as a new spike-verdicts.md entry rather than silently absorbed. | P3 |

## P1 Items (address before implementation)
- [ ] Failure #2 — Add a concrete re-visitation/staleness-detection mechanism to `adoption-recommendation.md`'s deliverable (Story 6.1.1) — e.g. a scheduled backlog item or periodic (non-CI) smoke-test run — since the Isolation Guard that protects the default build also guarantees nothing else will ever notice `make build-otel-auto` silently breaking.
