# Architecture Review: go-auto-instrumentation (iteration 2)
**Date**: 2026-08-21
**Verdict**: CONCERNS

## Re-reviewed items

- **A1 — Isolation Guard wiring: RESOLVED.** Story 2.1.3 (`project_plans/go-auto-instrumentation/implementation/plan.md:482-509`) now makes `otel-auto-isolation-guard` an explicit prerequisite of `ci` (Task 2.1.3c) and requires an implementer to *prove* it fires: append the target to `ci`'s prerequisite list, confirm `make -n ci | grep -c -e otelc -e stapler-squad-otel` is `0`, then temporarily add `build-otel-auto` to `ci` and confirm the guard trips and names `ci` as the offender before reverting. ADR-003's "Neutral" section (`project_plans/go-auto-instrumentation/decisions/ADR-003-structural-opt-in-separate-binary.md:46-50`) replaces the old aspirational claim with a corrected argument: the guard dry-runs (`make -n`) rather than invokes, so wiring it into `ci` adds no dependency on the weaving toolchain — this is the distinction the iteration-1 BLOCKER said was being conflated, and it is now stated explicitly and correctly.
  - Verified independently, not just asserted by the plan: `grep -n "^ci:" Makefile` → line 785, `grep -n "^ready:" Makefile` → line 794 — both match the plan's and ADR-003's citations exactly. `Makefile:627/650/652` (the `lint`/`lint-shell`/`SHELL_SCRIPTS` false-positive source Task 2.1.3a warns about) also checked out exactly.
  - The regex self-match claim ("0 matches against the three otel-auto filenames") is correct by inspection: the guard matches only the literals `otelc` and `stapler-squad-otel`; none of `otel-auto-build.sh`, `otel-auto-isolation-guard.sh`, `otel-auto-smoke.sh`, or the target name `otel-auto-isolation-guard` contains either substring.
  - The `ci` prerequisite runtime-cost tradeoff (five extra `make -n` dry-run + grep invocations) is stated as an accepted Negative consequence in ADR-003 rather than glossed over.

- **A2 — Exporter Toggle scoping: RESOLVED.** Story 2.1.1 (`plan.md:429-453`) now opens with an explicit "Scope — build-time concerns only" paragraph and an AC that greps the finished script for `OTEL_ENABLED`/`OTEL_TRACES_EXPORTER`/`OTEL_METRICS_EXPORTER` and treats any `export` of them as a defect (`plan.md:436-438`). A new Story 2.2.2 "Suppression Smoke Test" (`plan.md:556-579`) drives the actual missing coverage: liveness check → truncate (collector kept running) → suppress → assert zero spans → self-test that forces spans on to prove the zero-span assertion isn't vacuous. ADR-004 (`ADR-004-goflags-toolexec-injection.md:28-33`) states the root distinction plainly: `GOFLAGS`/module checksums act on a child process the build script is parent to; `OTEL_ENABLED`/Exporter Toggle are read by a separately-launched process the build script has already exited before — "code here setting those variables would be inert, and worse than inert: it would read as if suppression were handled when nothing had been done."
  - Cross-checked every remaining `OTEL_ENABLED`/`OTEL_TRACES_EXPORTER`/`OTEL_METRICS_EXPORTER` occurrence in `plan.md` (28 hits via grep) — none re-introduce the toggle into `scripts/otel-auto-build.sh`'s scope; every occurrence in that script's own AC/Task text is a prohibition or a "belongs elsewhere, see ADR-004" pointer.
  - The doc's Run Recipe (Story 4.1.1, `plan.md:747-758`) and the Suppression Smoke Test are required to use the *identical* variable set (`plan.md:562`), closing the "doc and test could drift" gap the original design had no mechanism for.

## Concerns (carried over from iteration 1, updated)

- [x] **Story 5.1.2's `go test`-weaving assumption — status updated, PARTIALLY ADDRESSED (was: open concern).** New Story 2.3.1 (`plan.md:591-605`) now settles "is `go test` woven?" with evidence *before* Phase 5 can begin at all — Phase 5's cut policy (`plan.md:774-776`) requires Phases 1–4 complete first, and Epic 2.3 is inside Phase 2, so the answer is known well before Story 5.1.2 is attempted. This removes the risk of Story 5.1.2 being attempted against an unverified assumption. However, Story 5.1.2's AC text itself (`plan.md:801-803`) still reads exactly as before — "*When* `go test ./executor/... ./session/git/...` is run against a woven test build, *Then* all tests pass" — with no explicit cross-reference to Story 2.3.1's finding or fallback language for the `NOT APPLIED` case, unlike Story 3.1.2 which does both (`plan.md:678-680`). Since Phase 5 is first-to-cut and the ordering already de-risks it, this is a documentation-consistency gap, not a re-opened BLOCKER: recommend adding the same one-line cross-reference/fallback Story 3.1.2 has, but it does not block Phase 3 progress.

- [ ] **Pattern Decisions primitive-obsession mitigation for the subprocess hook (unchanged).** The "Type-driven design" row (`plan.md:92`) still cites the `Attr<Concept>`/`<Concept>Attr(...)` attribute-key convention as the mitigation for the hook's own parameter-swap risk, which — as noted in iteration 1 — addresses attribute *keys*, not the hook *function's* own parameter list (command name, argv) that Spike E's rule shape will actually dictate. Not touched by the A1/A2 fix, so it remains open exactly as before: re-check the hook's own signature once Story 5.1.1 (Spike E) resolves its real parameter shape.

## Nitpicks (carried over, unchanged)

- Story 2.1.1's acceptance criteria still describe `scripts/otel-auto-build.sh` as one that "execs the caller-supplied `go build` argv unchanged" (`plan.md:435`), while Story 2.1.4 (Module Mutation Guard, `plan.md:511-522`) requires running the build as a child process instead of `exec`-replacing the shell, so pre/post checksums can be compared once the build finishes (Task 2.1.4a: "since exec replaces the shell, restructure..."). The two stories still describe two different process models for the same script; reword 2.1.1's AC or add a forward-reference to 2.1.4.
- Pattern Decisions table's "Build invocation" row still credits the Decorator choice with "re-using rather than restating the recipe" (`plan.md:85`), while Task 2.1.2a's instruction to mirror `build-embedded`'s shape does restate the same `-tags`/`-ldflags` list a second time in the Makefile — consistent with this repo's existing precedent, not a functional problem, but the phrasing still overclaims what's actually decorated (the environment composition, not the `go build` flag list itself).
