# Validation Plan: go-auto-instrumentation

**Date**: 2026-08-21

## Happy Path Scenario
Given the repo at HEAD with `otelc` installed and `make build-otel-auto` run, when a developer starts `stapler-squad-otel` with `OTEL_ENABLED=true` against a live OTLP collector and drives one session-list request, then the collector receives a span carrying a `db.system` attribute for ent's `database/sql` driver — a path the Baseline Build's manual instrumentation never produces (Story 1.3.2, Story 2.2.1).

## Go Unit Tests (net-new code only — Phase 5's Subprocess Hook)

Phase 5 is explicitly **first-to-cut** — these tests apply only if Spike E (Story 5.1.1) returns "supported" and Story 5.1.2 proceeds. Exact hook function signatures depend on `otelc`'s actual rule shape (Unresolved Question 5.1.1), so names below encode the *behavior* the plan's acceptance criteria demand and should be finalized against the real API once Spike E resolves it.

| Test File | Test Name | Type | Scenario |
|---|---|---|---|
| `telemetry/attributes_test.go` | `SubprocessCommandAttr_should_ReturnAttributeWithCommandNameValue_When_GivenNonEmptyCommand` | Unit | `SubprocessCommandAttr("git")` returns an `attribute.KeyValue` with key `subprocess.command` and value `"git"`, matching the `Attr<Concept>` constant + `<Concept>Attr(...)` constructor convention (`.claude/rules/primitive-obsession-checklist.md`). |
| `telemetry/attributes_test.go` | `SubprocessCommandAttr_should_ReturnEmptyValueAttribute_When_GivenEmptyCommand` | Unit (error/edge) | An empty command string still produces a valid `attribute.KeyValue` (no panic), covering the boundary case Story 5.1.2's AC doesn't explicitly test. |
| `telemetry/attributes_test.go` | `SubprocessArgCountAttr_should_ReturnIntAttribute_When_GivenArgCount` | Unit | `SubprocessArgCountAttr(3)` returns an int-valued attribute keyed `subprocess.arg_count`, not a raw inline `attribute.Int(...)` at the call site. |
| `instrumentation/otelc/safeexec/hook_test.go` | `SubprocessHook_should_StartSpanWithCommandAttribute_When_CommandContextInvoked` | Unit (span recorder, e.g. `go.opentelemetry.io/otel/sdk/trace/tracetest`) | Invoking the hook's entry function with a fake `safeexec.CommandContext` call starts a span carrying `AttrSubprocessCommand`, matching Story 5.1.2's first acceptance criterion without requiring a live collector. |
| `instrumentation/otelc/safeexec/hook_test.go` | `SubprocessHook_should_RecordErrorOnSpan_When_WrappedCommandFails` | Unit (error path) | Simulating a non-zero exit from the wrapped command causes the hook's exit function to record the error on the span (`span.RecordError`) rather than silently closing it. |
| `instrumentation/otelc/safeexec/hook_test.go` | `SubprocessHook_should_EndSpanExactlyOnce_When_CommandCompletesNormally` | Unit | Guards against a double-`span.End()` call, the most common hook-lifecycle bug in entry/exit instrumentation pairs. |

**Integration coverage for the hook** (not a new unit test — an existing-suite regression check per Story 5.1.2's third acceptance criterion): `go test ./executor/... ./session/git/...` run against a woven test build must produce identical pass/fail results to the Baseline Build, proving the hook changes no subprocess *behavior*. This is Type Integration and is already covered by Story 2.3.1's broader woven-suite run.

## UX Acceptance Tests
Omitted — pure infrastructure/build-tooling work, no UI surface (confirmed: no `design/ux.md` exists for this project; plan.md's Pattern Decisions table also confirms "no domain entities, no persistence, no transactions... a Makefile target, two shell scripts, three markdown reports, and (Phase 5 only) one Go hook file").

## Test Stack
- **Unit**: Go stdlib `testing`, matching this repo's existing convention (confirmed via `go.mod`'s `testify` dependency and existing `*_test.go` naming in `executor/safeexec/`). Applies only to Phase 5's net-new attribute constructors and hook lifecycle.
- **Integration**: Plan.md's own shell-script verification suite — `scripts/otel-auto-build.sh`, `scripts/otel-auto-isolation-guard.sh`, `scripts/otel-auto-smoke.sh` (default and `--suppression` modes), plus the manual spike procedures recorded in `spike-verdicts.md` (Spikes A–E) and the woven Go-suite/e2e run in `parity-report.md` (Epic 2.3).
- **E2E / UX**: N/A for UI. The existing Playwright suite is repurposed as a *parity* check (Story 2.3.2) — pointed at `stapler-squad-otel` via an additive `TEST_SERVER_BINARY` override, conditional on Unresolved Question 5 — not a new UX surface being tested.

## Gaps Found (not papered over)

1. **macOS cross-platform build survival is unresolved by any acceptance criterion.** requirements.md's Constraints list "cross-platform builds" (Linux + macOS) as in-scope; plan.md's Unresolved Question 6 acknowledges the `CGO_LDFLAGS`/Info.plist question but defers it to "Story 2.1.2's platform note" with no Given-When-Then verifying it. If macOS support matters for this feature, a Spike A.3 (or equivalent) is missing.
2. **`go test` weaving applicability is a single point of failure for two downstream stories.** Story 2.3.1 settles Unresolved Question 4 once; Story 3.1.2 explicitly reuses that finding rather than re-deriving it. This is by design (plan.md states it), but it means a wrong or stale Story 2.3.1 finding silently invalidates part of the Overhead Report — there's no independent cross-check in Phase 3. Not a missing test per se, but worth flagging as a fragility in the dependency graph.
3. **Playwright e2e parity leg is conditional and may not run at all** (Unresolved Question 5 answered "no"). Story 2.3.2's AC already handles this by requiring the report to say so explicitly rather than silently omit it — this is correctly *not* a gap, just noting it's the one Success Metric leg most likely to end up unverified.
