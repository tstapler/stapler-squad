  **The `ensureBinary()` "silent-rebuild trap" is real and correctly located, but its stated failure mechanism is imprecise.** Verified directly: `tests/e2e/helpers/test-server.ts:144-157`'s `ensureBinary()` stats `this.config.buildPath`; if the file is missing or its mtime is ≥1 hour old, it runs `execPromise('go build -o stapler-squad .', { cwd: projectRoot })` — a **hardcoded** literal output path, unrelated to `this.config.buildPath`, then returns without re-checking anything. `start()` (`test-server.ts:61`) then spawns `this.config.buildPath` regardless. This hardcoded target happens to equal the *default* `buildPath` (`test-server.ts:41`, `path.join(__dirname, '../../../stapler-squad')`) — so the trap is real for the default/unconfigured case, and for that case it is exactly "silent unwoven substitution": if a run forgets to set `TEST_SERVER_BINARY` at all, `ensureBinary()` will silently (re)build the plain, unwoven `stapler-squad` and the suite will "pass" against it while never exercising any woven code, which is exactly the outcome Story 2.3.2's AC (`plan.md:621-622`) warns about. Where the plan's phrasing overstates the mechanism is the "missing or older than an hour" clause *when the override is in effect*: since the rebuild always targets `./stapler-squad`, not `this.config.buildPath` (`stapler-squad-otel`), a stale-but-present override target is left untouched (spawn still runs the old — but still woven — binary, not a silently-substituted unwoven one), and a missing override target causes `spawn()` to fail to find the binary, surfacing as a loud ~90s timeout in `waitForServer()` (`test-server.ts:125-142`), not a silent pass. Net effect: the plan's mitigation (Task 2.3.2c: rebuild `stapler-squad-otel` immediately before the run so its mtime is fresh, and check the run log for the `Building Go binary...` line, `plan.md:621-622`) is still the correct guard and catches the trap regardless of which of these three sub-scenarios actually fires — so nothing needs to change functionally — but the AC's prose ("which would silently substitute an unwoven binary and produce a meaningless pass") should be tightened to distinguish "override unset entirely" (silent unwoven substitution, the sharpest risk) from "override set but stale/missing" (stale-woven reuse or a loud timeout, not a silent unwoven substitution). This is a documentation-precision nit, not a functional gap, and does not change the RESOLVED verdict.
