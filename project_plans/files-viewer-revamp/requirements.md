# Requirements: files-viewer-revamp

**Date**: 2026-10-16
**Type**: feature addition (extends the session Files tab)
**Complexity**: 3 — system design (new RPCs, write path, multiple epics, mobile + desktop)

## Problem Statement
The session Files tab (`web-app/src/components/sessions/FilesTab.tsx`, `FileTree.tsx`, `FileContentViewer.tsx`) is a read-only, single-file, filename-only browser. The owner cannot use it the way they use Vim or VS Code to explore a project: no content search, no multi-file navigation, no editing, and the experience is fragile on phones (the owner's remote-access path via the mobile app/PWA).

## Baseline
Today (VERIFIED by reading source): tree with sort/filter/git-status badges; read-only CodeMirror viewer with `gg`; quick-open palette; recent-files list; resizable tree; two-pane tree/content switching on mobile. `SearchFiles` RPC matches file names only (min 2 chars, cap 500); `GetFileContent` serves 1 MB truncated / rejects >10 MB; there is no write RPC. Workaround: SSH/terminal Vim, or opening the worktree in a desktop IDE.

## Owner decisions (2026-10-16, ADR-036: pluggable range-read and delta-write file transport; ADR-036 is Accepted)
1. **Large-file editing is in scope**: files over 1 MiB up to a proposed 64 MiB (tier T1) are opened in windows and edited by sending only the edits (delta-only), behind the global flags `files:range-read`, `files:delta-write` and `files:edit-large` (all default off, flipped in that order; `files:edit-large` is off by default as decided). Files above 64 MiB up to a proposed 1 GiB are windowed and view-only (T2).
2. **Editor engine**: CodeMirror 6 with a lazy gap-line document behind an `EditorEngine` port (plus `Highlighter`, `MergeSurface` and an engine conformance suite). A custom rope/piece-table editor is built only if CM6 fails the extended S-T3 gate on the owner's phone; it is a contingent epic, costed and counted separately.
3. **All transport adapters are included**: `full` (floor), `connect_unary` (primary), `connect_stream` and `ws_stream` (reads), and a byte-only `http_range` GET adapter, the last only behind the DNS-rebinding guard (the existing `ServeFileRaw` receives the same check). `ApplyFilePatch` is allowed on the remote `:8444` listener subject to Task 0.1.3b; capability negotiation handles either answer and a read-scoped caller is gated by scope if the recon says it can reach writes.
4. **Cost and phasing approved**: A (seam and `full` adapter), then B (range reads and the windowed viewer), then C (delta writes), then D (the optional adapters), included and sequenced last, gated on the spike results S-T1..S-T5 (the results decide default enablement of the stream adapters, not whether they are built).

## Users / Consumers
The owner, on desktop browser and on phone (LAN/Tailscale). Agent sessions concurrently write to the same worktree.

## Success Metrics
- Find-in-project: from any session, locate a string across the worktree and open the hit at the right line in ≤ 3 interactions, on desktop and phone (baseline: impossible without terminal).
  - *Counting protocol*: one interaction = one tap/click or one keyboard chord (typing a query counts as one; each key of a multi-key chord does not). Counted from the Files tab already open on a session, ending when the hit's line is visible in the editor. Measured by a Playwright test at a desktop and a mobile viewport; the owner repeats it once on a real phone at ship.
- Multi-file: ≥ 2 files open simultaneously with tab/back-forward switching without losing scroll/cursor position (baseline: one file at a time).
- Edit: change and save a file from the browser; a save against a changed-on-disk file never silently overwrites (baseline: no editing).
- Mobile: all primary flows (open, search, jump, edit, save) completable one-handed with 44px touch targets and no layout break when the on-screen keyboard opens; verified with Playwright mobile viewport e2e.
- Assistive technology: the active file can be read in full with VoiceOver and TalkBack through a non-virtual, paged Accessible view (CodeMirror 6 virtualizes its DOM, so it is not assumed to be readable); a Phase 0 spike fixes the pass criteria (plan Story 0.1.6) and CodeMirror Edit with a screen reader is documented as supported, best-effort or unsupported from the owner's script (Task 2.5.4b).
- No regression in existing Files-tab e2e/unit tests.
- Large files (ADR-036): from the Files tab on a session, open a 50 MB text file at a search hit's line, scroll and jump within it on the owner's phone, without any response over 1 MiB and within a phone-class memory budget (chunk cache at most 8 MiB of text; the S-T3 sweep measures the document structures); edit one character of a 5 MB file and save it with a request body under 4 KiB (measured by the Playwright test; INFERRED at least two orders of magnitude smaller than a whole-file save), the file on disk equal to a whole-file save of the same text bytewise (golden vectors and fuzz). Baseline: files over 1 MB open truncated and read-only, files over 10 MB cannot be opened.
- Adoption (informational, not a ship gate): after the editing flag is enabled, the owner reports whether they reach for the Files tab instead of terminal Vim/an IDE for quick looks and edits; check in at the 4-week `files:viewer-v2` retirement review (plan Story 2.5.1). **Measured, not only observed**: weekly counts of `files.edit.save{outcome=saved}`, `files.search.run`, `files.edit.enter` and active days from the user analytics system (ADR-035 section 5), shown at `/analytics/files` (plan Story 2.5.3). **Decision rule at the 4-week review (proposed, owner-editable constants; ADR-035 section 5)**, over the trailing 28 days and computed by the endpoint: *inconclusive* below 150 server-side events or 6 active days (extend once by 4 weeks, then decide on the owner's own report; no percentages are shown below the floor, because one user's small counts are noise); *keep v2 and retire the kill switch* at >= 8 active days and >= 20 searches with no rollback; *editing proven* at >= 5 saves; *editing tried but not adopted* at >= 5 Edit entries with < 2 saves (investigate friction); *retire or rework* when volume is met but active days < 4 and searches < 5. **Counting source**: saves and searches are counted from the unthrottled server events `files.server.write{ok}` and `files.server.search`, because the client's 30/min per-event cap, its coalescers and the provider's 200-event drop-oldest queue can only undercount; client events are a lower-bound cross-check and the summed `files.meta.dropped` count is shown beside them. **Sourcing of the thresholds (triad round 3)**: no external benchmark exists for the adoption of a one-user tool and none is claimed; the five constants are the author's judgment (INFERRED: 28 days = four weekly cycles, 6 active days about 1.5 days a week, 150 server events about 25 on each of those days, 8 active days every other working day, 20 searches about one per working day, 5 saves a little over one a week; rationale in ADR-035 section 5), are owner-editable in one Go file, and should be edited before the verdict is read. The comparator for the find metric is the owner's own measured time-to-answer with today's workaround (Task 0.1.5d), not a figure from elsewhere. **Action by verdict**: ADR-035 section 5 maps each verdict to an action; the low-adoption path is to turn `files:editing` off, keep the read-only features and retire the rest only on continued non-use.
- Usage metrics from analytics events (informational; derived queries in ADR-035 section 5, none is a ship gate): find-and-open within <= 3 interactions = share of `files.search.open_hit` with `interactions` <= 3 (client `FindFlowMeter`; the Playwright test stays the gate); save-conflict rate = `save{conflict}` / `save`, plus overwrite-vs-merge-vs-reload choice shares; mobile vs desktop split of search, save and tab-open by the stamped `form` label (touch vs hardware keyboard by `input`); search first-result latency p50/p95 and share <= 2000 ms (`files.perf.search_first_result_ms`, server `files.server.search_first_result`); open latency p50/p95 and share <= 300 ms (`files.perf.open_ms`); agent-race exposure = `files.stale.shown` per active day.

## Constraints
- Go server + React SPA; protobuf/ConnectRPC; pnpm in `web-app/`; vanilla-extract CSS; CodeMirror already in use.
- Must work on both desktop and mobile (touch targets, responsive layout, mobile keyboard). One layout rule decides which: the mobile layout for a container under 768 px or a coarse-pointer device whose short screen side is under 600 px (so a landscape phone keeps the mobile layout and a tablet gets the desktop layout; ux.md section 0).
- **Known limit (accepted, ux.md section 19)**: below a 360 px container (a 320 px phone, split-screen, a large system font) the 3-way merge is unavailable and conflicts are resolved with the 2-way flow (Keep editing / Reload / Overwrite / Copy my version); nothing is lost, but a true merge needs a wider window.
- Rollout gated by live-settable feature flags (no env vars): `files:editing` and `files:viewer-v2` plus, since ADR-036, `files:merge-phone`, `files:range-read`, `files:delta-write` and `files:edit-large`, all global-only (no scopes).
- Transport limits (ADR-036 proposals, confirmed by the S-T2 and Task 1.6.7b benchmarks): `ApplyFilePatch` body 2 MiB, 2,000 edits and 1 MiB inserted text per request (oversized pastes are refused for T1 and fall back to `writeFull` for T0; nothing is split across requests), `writeFull` stays 1.5 MiB, range response 1 MiB and 4,000 lines, 4 concurrent range calls per client and 8 per IP, the editable ceiling (`hash_cap_bytes`) 64 MiB and the read ceiling 1 GiB.
- `make install-service` must not be used to try changes; use an isolated manual instance.

## Non-functional Requirements
- **Performance SLO**: open a typical (<1 MB) file < 300 ms after RPC return; content search over a repo of ~50k files returns first results < 2 s (target, to be validated in research); large files must not freeze the mobile browser. **Since ADR-036 this is met by serving them, not refusing them**: a file over 1 MiB opens from one range read (the first window paints within the same tolerance as the small-file SLO, measured), chunk text in memory stays within the phone budget (8 MiB on `pointer: coarse`, 64 MiB on desktop), a one-character save of a large file sends hundreds of bytes (INFERRED) instead of the whole file, and jump latency and index/hash/splice throughput are benchmarked and recorded (Tasks 0.1.7b, 1.6.7b), not gated.
- **Scalability**: single user; large monorepo worktrees; respect .gitignore by default.
- **Search memory bound**: peak search memory is independent of file count: at most `workers x per-file cap` = 4 x 2 MB = 8 MB of scan buffers per walk, 16 MB across the 2-walk process limit, and under 1 MB of results per search, on a 50,000-file worktree (derived bound; asserted by a heap-sampler test below 64 MB and by `-benchmem` output; plan Story 1.1.1, ADR-030 decision 5).
- **Open streams per origin**: at most 3 concurrent `SearchContent` streams per remote IP (8 in total) so searches in several tabs or devices cannot exhaust the browser's HTTP/1.1 per-origin connection pool (6 assumed) and starve unary RPCs; a fourth stream, or a search queued longer than 20 s, is refused with `ResourceExhausted` `SearchBusy` and the UI shows a Retry message without auto-retry (plan Story 1.1.2, ADR-030 decision 6; the caps are proposed, adjustable constants).
- **CI budget**: the new Go tests must not push the `server/services` race suite past its budget (BUG-067, open): no `createTestStorage`/tmux in new tests, a 5k-file fixture under `-short`, and a measured wall-clock delta of at most 10% of the baseline at every wave gate (proposed threshold); the web-app jscpd ratchet (0.14%) is protected by one shared test-harness factory and a per-wave headroom ledger (plan Story 0.2.4).
- **Security classification**: internal. Write RPC must confine paths to the session worktree (no traversal/symlink escape) and respect session ownership.
- **Data residency**: no special requirements.

## Scope
### In Scope
- **Large files and a pluggable transport (ADR-036)**: range reads with a server sparse line index and a windowed viewer, delta-only saves with layered verification, large-file content search, capability-negotiated adapters (`full`, `connect_unary`, `connect_stream`, `ws_stream`, `http_range`), and the `EditorEngine` port with the CodeMirror 6 gap-line document.
- Project-wide content search (grep-like, regex/case/glob options) with results panel and jump-to-line.
- Multi-file navigation: open tabs/buffers, back/forward history, jump-to-line, symbol/outline navigation.
- Editing and saving: write RPC; optimistic-concurrency check; on conflict, block save and show a diff offering overwrite / reload / keep editing, plus a 3-way merge flow (owner decision 2026-10-16: include 3-way merge via @codemirror/merge; base = the version the buffer was opened from).
- Vim-style and standard keybindings on desktop (Vim mode optional/toggle) plus touch-first controls on mobile.
- Mobile robustness: touch targets, gestures, keyboard-safe layout, large-file handling, reliable pane switching.
- Tests: unit, Go handler, Playwright e2e at desktop and mobile viewports.

### Out of Scope
- Full IDE features: LSP/diagnostics, debugging, terminal embedding, extensions.
- File create/rename/delete/move (unless research shows it is trivial; revisit in planning).
- Real-time collaborative editing (and therefore operational transformation or CRDTs: one human writer, agents overwrite whole files, so reconciliation stays the 3-way merge; ADR-036 decision 9).
- Split view (deferred by the Phase 3 plan; see implementation/plan.md "Deferred / Out of Scope").
- Editing outside a session worktree.

## Rabbit Holes
- Vim emulation fidelity (CodeMirror vim mode vs. mobile soft keyboard; modal editing on touch).
- Content search backend: shelling out to ripgrep vs. go-git/in-process (repo prefers go-git over subprocesses; ripgrep availability and ignore semantics).
- Concurrent agent writes: detecting change (mtime/hash/ETag), and git-index/worktree interactions after a save.
- CodeMirror performance and memory on phones for large files; truncation vs. virtualized/partial loading.
- Binary/CRLF/encoding round-tripping on save.
- Tab state persistence across sessions/reloads.

## Alternatives Considered
- Embed code-server/VS Code web or Monaco: heavier, harder on mobile; CodeMirror is already in the bundle.
- Link out to a desktop IDE / terminal Vim: current workaround, unusable on phone.
- Incrementally extend existing Files tab (preferred starting assumption).
- **Cheaper alternatives for phone editing, considered in triad round 3**: (a) SSH or a terminal app on the phone with tmux and Vim (the current workaround): zero build cost, but typing on a phone terminal is the pain being solved and it has no link to the session worktree, git badges or the agent's concurrent writes, and no conflict check against them; (b) a Tailscale-reachable code-server or openvscode on the worktree: a full editor without building one, but heavy per workspace, not touch-first, and it bypasses the session identity, flags and conflict model this app already has (the plan's rejected alternative B); (c) do nothing for editing and ship only the read-only half (search, tabs, mobile layout, Accessible view), which omits Epics 2.1-2.4, about 29% of the plan's CU after the ADR-036 integration (8.08M of 27.71M including the delta-write Stories 2.1.5, 2.2.5 and 2.3.3; it was 5.63M of 18.04M, about 31%, before it). This scope is chosen because the owner decided on full scope (2026-10-16) and because the Files tab already has the tree, viewer, session binding and mobile access path that (a) and (b) lack; that rationale is the owner's decision and the plan's own comparison, not measured evidence, and alternative (c) is what the low-adoption action above falls back to.

## Feasibility Risks
- Write path adds data-loss risk; needs conflict detection, size/encoding guards, and an audit-friendly log line.
- **Delta writes add a second write path with a silent-mangling failure mode (ADR-036)**: a client encoder bug can produce a valid but wrong edit whose client-side checksums match. Controls: property tests against the full-replace path, shared golden vectors, `FuzzApplyPatch`, layered server verification before rename, periodic reconcile with a forced `writeFull`, explicit Save only, and a kill switch per flag.
- **The editor engine may not support lazy documents on the owner's phone (ADR-036)**: CodeMirror 6's gap-line model is INFERRED from public APIs and gated by the extended S-T3 spike; fallbacks are window swap, the Accessible-view pager for view-only files, and the contingent custom engine.
- ripgrep dependency may not exist on every host; fallback needed.
- iOS Safari keyboard/viewport quirks.
- Unvalidated assumption: the owner will actually edit (not just read and search) on a phone. Mitigation: read-only epics ship first and are independently valuable, editing is last and flag-gated, and the Task 1.5.3c phone smoke test checks the editing ergonomics before the editing epics start.
- Observed pain is asserted, not measured: no log of current phone failures or workaround frequency exists. Mitigation: the Story 0.1.5 phone spike records concrete failures on the owner's device as the regression anchor, and Task 0.1.5d records the owner's current time-to-answer (three timed find-and-reach-the-line trials with today's workaround) as the baseline the find-and-open metric and the 4-week review are compared against.
- **Second unvalidated assumption (named in triad round 3): on desktop the owner prefers editing in the browser Files tab over terminal Vim or an IDE.** The phone-editing assumption above is the strong one; this one is weaker and matters for the cost of the editing epics: if the owner keeps using Vim or an IDE on the desktop, only the phone benefits from editing, and the editing epics (Epics 2.1-2.4, 8.08M of the plan's 27.71M CU, about 29%, recounted from the effort table after the ADR-036 integration; 5.63M of 18.04M, about 31%, before it) buy little. Mitigation: read-only features ship first and stand alone; editing is flag-gated and last; the adoption metrics split search, saves and Edit entries by `form` (mobile vs desktop), so the 4-week review can see whether desktop editing is used at all. **Action if adoption is low at the 4-week review** (decision rule in ADR-035 section 5): flip `files:editing` off, keep the read-only features (search, tabs, mobile read mode, Accessible view), open a follow-up to delete the write path, merge, key bar and draft stores if editing is still unused 8 weeks later, and retire v2 only if search and tabs are also unused.

## Observability Requirements
- Structured slog lines for file write (session, path, bytes, outcome incl. `conflict_rejected`) and content search (query length, duration, result count, truncated); no file contents or query text at info level.
- Counters/latency for SearchContent and WriteFile RPCs via existing metrics; alert not required.
- **Transport observability (ADR-036)**: one slog line per `ReadFileRange` and per `ApplyFilePatch` (session, path, sizes, outcome, adapter, duration; never content) and the closed-enum labels and events of ADR-035 "Transport extension" (`transport`, `fallback_reason`, `payload`, `ops`, `tier`; `files.transport.select|fallback`, `files.read.window`, `files.edit.patch_rejected`, server `files.server.patch`), no paths, offsets, lines or text.
- **User analytics events** through the existing analytics system (`web-app/src/lib/analytics/`, `server/analytics/`, ADR-012/013): a typed `files.*` taxonomy emitted by the viewer (client) and `files.server.write|search|search_first_result` recorded by the server through an injected port, for long-term understanding of adoption, conflicts, mobile vs desktop and latency. Privacy: labels are closed enums, booleans and count/size/length/extension-class buckets plus form factor, input profile and flag state; **never** file paths, file names, file contents, query text, globs, branch names or draft text. Defined in ADR-035; implemented by plan Stories 0.2.5 and 2.5.3; no consent UI (data stays in the local `analytics.db`).

## Risk Control
- ADR-036 flags `files:range-read`, `files:delta-write`, `files:edit-large` (global-only, default off); each is a kill switch (delta-write off routes saves to `writeFull` for T0 and makes T1 buffers read-only with their drafts kept).
- Feature flag (live-settable via the feature-flag RPC/panel, **global only**: per-scope overrides exist only for hidden-session kinds, `server/services/feature_flag_mutation.go:30-36`; amended by Phase 3 review repair): `files:editing` (earlier drafts: `files_editing`) gating the write RPC and editor mode; search/navigation ship behind `files:viewer-v2` (earlier drafts: `files_viewer_v2`); the `area:name` spelling is canonical.
- Rollback: flip the flag off; read-only viewer remains intact. No data migration.
- Staged: read-only epics (search, tabs, mobile) first; editing last.
