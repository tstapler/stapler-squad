# ADR-031: WriteFile atomicity, confinement and optimistic concurrency

**Status**: Proposed (2026-10-16; amended after Phase 3 review)
**Plan**: `implementation/plan.md` Epics 0.2, 2.1; amended by ADR-036 (Stories 0.2.6, 2.1.5)

## Context
No write path exists. Risks (pitfalls.md W1-W15): saving a truncated read destroys the tail; `resolveAndValidatePath` (`file_service.go:106-116`) is lexical-only; `ExistingDir` falls back to the main checkout when a worktree is gone; agents write the same files; CodeMirror normalizes EOL; `.git/hooks` writes are code execution; remote access makes the RPC a network write primitive. go.mod is Go 1.26.6, so `os.Root` is available.

## Decision
- **Confinement**: one `resolveInWorktree` over `os.Root`, used by read, write and search; reject NUL, `..`, absolute, any `.git` component. The `.git` denial is symlink-safe: for writes every intermediate component is `Lstat`ed and any intermediate symlink is rejected (a `linkdir -> .git/hooks` symlink stays inside the root and would pass a lexical check), and the post-resolution path is re-checked; the leaf must not be a symlink. Retrofit to read RPCs as its own commit (closes the existing symlink read hole). Fallback to `EvalSymlinks` + prefix check only if Task 0.1.3a finds a platform gap.
- **Target dir**: writes use `Workspace().ActiveDir` and require `ActiveDir != ""` and `ActiveDir == ExistingDir`; otherwise `FailedPrecondition WorktreeMissing` (the active directory is gone, e.g. after `pause_session`). `WorktreeDir` may be `""`: a directory-mode or existing-worktree session works directly in `RepoRoot` (`session/types.go:325-355`) and stays editable. The hazard (an `ExistingDir` fallback aiming a write at the main checkout) is exactly `ActiveDir != ExistingDir`, so the earlier extra `WorktreeDir != ""` requirement was dropped. Editing the main checkout directly is allowed by default (owner may veto, then add a `NoDedicatedWorktree` reason); because `.git` is then a real directory, the symlink-safe `.git` deny above is mandatory.
- **Token**: `FileVersionToken = v1:<size>:<mtime_ns>:<sha256hex>`; hash `-` for non-editable reads (truncated, binary, over cap). A well-formed `-` token parses and `WriteFile` refuses it as `FailedPrecondition` (`Truncated` by default; `Binary`/`TooLarge` when the live classification says so); only an unparseable token string is `InvalidArgument`. The server **always compares sha256** inside a per-path mutex keyed by `(ActiveDir, ResolvedPath)`. The hash is the identity; size and mtime are hints. A size or mtime mismatch only triggers hashing, never acceptance on its own, and size+mtime equality never accepts without hashing (an agent rewrite of the same size within one timestamp tick is the failure the hash exists for; cost about 1 ms at the 1 MB cap). If the on-disk hash equals the token's hash, the write proceeds even when mtime moved (a `touch`, formatter no-op or `git checkout` of identical bytes is not a conflict) and the response carries the new token; a different hash is `Conflict`. It re-checks immediately before rename by re-hashing under the same rule, so an mtime-only change in that window does not abort the save but a content change does. The `Conflict` response carries `TheirsVersion = FullText{content (LF-normalized, BOM stripped), token} | Unavailable{reason}` (reason is the shared `ReadOnlyReason` enum, which gains `Deleted`, restricted to `Deleted|TooLarge|Binary|NonUtf8|MixedEol|Symlink`): when the current disk file is over 1 MB, binary, non-UTF-8, Mixed EOL, a symlink or deleted, the server sends `Unavailable` and no content (never a truncated `theirs`, which would let a merge or overwrite drop the tail of the agent's file). The client disables Merge and Overwrite for `Unavailable`; a deliberate overwrite of a file the user cannot see stays impossible.
- **Atomicity**: temp file `.<name>.ssq-tmp-<rand>` in the same directory (same-filesystem rename; temps outside the worktree are rejected for that reason), `fsync`, `chmod` to original perms, `rename`, directory `fsync`; cleanup on failure. Precedent: `server/services/settings_file_atomic_write.go`. Accepts inode change (hard links, `tail -f`). Crash residue: a best-effort sweep of `*.ssq-tmp-*` older than 10 minutes in the target directory runs before each write. No `info/exclude` write: the git common-dir is outside the worktree `os.Root` and outside the threat model. Accepted residual: after a crash and until the next save in that directory, a leftover temp could be committed by an agent's `git add -A`.
- **Encoding (single owner: the server)**: UTF-8 only. The client always sends **LF-normalized** text (it normalizes on load and never sets CodeMirror's `lineSeparator` to CRLF), and `WriteFileRequest` has no `line_ending`/`has_bom` fields. The server derives BOM and EOL (`LF`/`CRLF`) from the on-disk file it just token-verified and applies them to the content, so a no-op save of a CRLF+BOM file is byte-identical; content containing `\r` or NUL is rejected `InvalidArgument`. `merge3` works on LF text and does not re-apply EOL. `Mixed` EOL, non-UTF-8, NUL, binary are read-only. Editable cap equals the existing non-truncated read (1 MB) on the `full` adapter and for T0; no relaxed-truncation edit path for `WriteFile`. **Qualified by ADR-036**: files over 1 MiB are edited by `ApplyFilePatch` only (T1, behind `files:edit-large`), never by `WriteFile`; the truncated-read refusal (token hash `-`, Pitfall W1) is kept on the `full` adapter and is solved by construction for deltas because no full content is ever sent.
- **Wire shape**: `WriteFileResponse` is `oneof {Saved, Conflict}`; every refusal is a Connect error with a typed `ReadOnlyReason` detail (`FailedPrecondition` for state-dependent refusals incl. `FlagOff`, `PermissionDenied` for `HiddenSession`/`GitInternal`/escape, `InvalidArgument` for unparseable tokens, NUL or `\r` in content); the client maps it to `Rejected(reason)`.
- **Local-listener guard**: the unauthenticated `:8543` listener enforces POST-only plus the Origin/rebinding verdict only for procedures in `guardedProcedures` (`server/server.go:1879-1888`; `middleware.ProfileRebinding`, `server/middleware/callerguard.go:21-24`). `WriteFile` is registered there beside `UpdateFeatureFlag` and `ReplyToPendingQuestion`, with a Go test over the real map (foreign-Origin POST, rebinding Host and GET rejected; membership asserted) so the registration cannot be dropped. Remote-access tiers are a separate check (Task 0.1.3b).
- **Symlink reads**: in-tree symlinks (including directory links) read normally and are shown read-only with `ReadOnlyReason=Symlink`; links resolving outside the root or into `.git` return `PermissionDenied` with a `Symlink` detail and the link's target string, never bytes. The classes found in the owner's live worktrees are recorded under Spike outcomes (Task 0.2.1d).
- **Gating/audit**: `files:editing` is a **global-only** flag (per-scope overrides exist only for hidden-session kinds, `feature_flag_mutation.go:30-36`, `:94-95`), enforced server-side; hidden-session write guard; slog line (session, path, bytes, outcome) without content. "Respect session ownership" (requirements) is satisfied by the hidden-session guard plus authenticated access: this is a single-user tool with no per-owner model.
- **Structure**: the write path is a separate `FileWriter` with ports `FilesFlags`, `WriteGuard`, `StatusInvalidator`, `WorkspaceProvider`; `FileService` stays read-only.
- **Threat model**: editing makes the Files tab a code-execution primitive for anything an agent later runs (hooks in `.claude/settings*.json`, `Makefile`, CI files). Authorization equals terminal write access (`WriteToSession`), so there is no escalation. `LocalFileBrowser`'s unconfined HTTP model is untouched and not reachable from the editing UI. Remote-access exposure of `/api` write RPCs is established by Task 0.1.3b before the handler is built (see Spike outcomes).
- **Request-size cap (unconditional; triad round 2)**: VERIFIED by grep that `server/` sets no `connect.WithReadMaxBytes` anywhere (the only mention is a comment in `server/services/backlog_service_lifecycle.go:1054` calling the absence "a known, pre-existing, repo-wide gap"), so Connect's default (no limit) applies and the 1 MB editable cap is enforced only after the body is already in memory. `WriteFile` therefore gets a **path-scoped body limit of 1.5 MiB** (1 MiB of content grows to about 1.34 MiB as base64 in the Connect JSON encoding, plus the path, token and framing) implemented as a small `http.MaxBytesReader` middleware in `server/middleware/` (precedent: `server/handlers/telemetry_handler.go:79`, `server/auth/host_advertisement.go:37`), **wrapped around the Connect handler itself, not beside the `guardedProcedures` entry** (triad round 3, VERIFIED in `server/server.go`): `guardedProcedures` is consulted only by `localChainWith` (`LocalWriteGuard`, the `:8543` chain); `remoteChain` (`:8444`) never applies it, so a limit registered there would leave the remote listener unbounded. Both chains share `srv.mux`, and the session handler is built once at `server/server.go:~495-497` (`handler = services.WithRequestHost(handler)` before `RegisterConnectHandler`), so the limit is one wrapper there: `handler = middleware.BodyLimit("/session.v1.SessionService/WriteFile", 1.5<<20)(handler)`, matching the path as the handler sees it (the mux strips `/api`, `http.StripPrefix("/api", handler)`), which covers local and remote listeners with one line. **How the refusal looks**: connect-go v1.20.0 converts an `*http.MaxBytesError` raised while it reads the body into a `CodeResourceExhausted` Connect error (`connectrpc.com/connect@v1.20.0/error.go:452-466`, called from `envelope.go` and `protocol_connect.go`) before any handler or interceptor runs, so the typed `ReadOnlyReason=TooLarge` detail of the refusal table **cannot be attached** to this one refusal; the wire contract is therefore: body over the limit -> `ResourceExhausted`, and the client maps `ResourceExhausted` on `WriteFile` (the only RPC with this limit) to `Rejected(TooLarge)`. A content string over the 1 MiB editable cap but under the body limit still reaches the handler and gets `FailedPrecondition` + `TooLarge` from the validation pipeline. The wrapper is a one-line registration in `server/server.go` so the file-length lint exposure is minimal (plan Story 0.2.4, Task 0.2.4f). The repo-wide gap is not fixed here.
- **ADR-036 amendment (2026-10-16)**: the confinement, atomicity, token (`v1`, unchanged; the `-` form now also covers range reads whose whole-file analysis is pending), encoding-ownership, guard-registration and request-size rules above apply unchanged to every transport adapter and to `ApplyFilePatch`/`PreflightFilePatch`, because all policy lives in `FileOps` (Story 0.2.6) and wire handlers hold none. `WriteFile` keeps its 1.5 MiB body cap and 1 MiB content cap; `ApplyFilePatch` has its own path-scoped 2 MiB body limit (the same `middleware.BodyLimit` wrapper on both listeners), 2,000 edits and 1 MiB of inserted text, and is registered in `guardedProcedures` with `ProfileRebinding` beside `WriteFile`. `FileWriter` is the write-side collaborator of `FileOps` and consumes its policy ports and `FileBackend` (Task 2.1.2b amended). Any GET route that returns file bytes (`ServeFileRaw`, the Phase D `http_range` route) must pass the rebinding verdict or not ship (audit in Task 0.1.3b, guard in Task 2.6.3a). The remote-tier answer for patch-sized write bodies is recorded under Spike outcomes by Task 0.1.3b.


## Consequences
Residual TOCTOU: an agent process can modify the file between the final re-check and `rename`, and can overwrite a saved edit at any time; mutexes cannot serialize against other processes. Documented in the how-to and conflict UX; mitigated by focus/visibility re-stat in the client. Known rename-save limits (accepted, pre-mortem #14/#15): hard links, xattrs/ACLs/SELinux labels and non-owner ownership are not preserved; file watchers see create+rename; a crash leaves `.x.ssq-tmp-*` until the next save in that directory; and the `.git` decision is made on the path before the open, so a directory-to-symlink swap in that window is possible (confined by `os.Root`, no privilege escalation). A UI save can also make a Claude agent's next Edit fail with "modified since read".

## Alternatives rejected
mtime-only token (misses same-tick edits); git blob id (no benefit, needs hashing parity); `renameio` dependency (matches repo precedent instead); in-place write (torn reads); relaxing truncation to edit 1-10 MB files (memory on phones, message size).

## Spike outcomes
*(Task 0.1.3a/b are recorded below, 2026-10-16, Go 1.26.6 on Linux. Task 0.2.1d (symlink classes in the owner's live worktrees) is still pending.)*

**`os.Root` semantics (Task 0.1.3a, VERIFIED: `go test ./server/services -run TestOsRoot -count=1 -v`, 15 subtests PASS, `server/services/os_root_semantics_test.go`).**
- `root.Open("link_out/secret")` (escaping directory symlink), `root.Open("link_out")` (final-component escaping symlink), an absolute-target symlink, `..` paths leaving the root, and absolute paths all fail with `path escapes from parent`. `..` that stays inside the root works.
- `root.Lstat("link_in")` reports `ModeSymlink` (also for the escaping link); `Stat`/`ReadFile` follow an in-tree link.
- `OpenFile(".t", O_WRONLY|O_CREATE|O_EXCL)` works and a second call returns `fs.ErrExist`; `O_EXCL` creation through an escaping directory link is refused and nothing lands outside the root.
- `root.Rename` replaces an existing destination; renaming onto an in-tree symlink replaces the link itself and leaves its target untouched; renaming into or out of an escaping directory link is refused.
- Directory `fsync` works: `root.Open(".")` and `root.Open("sub")` followed by `Sync()` succeed on Linux. macOS was not run here (UNVERIFIED); the test skips directory `Sync` on Windows only.
- `root.Symlink` can create a link that points outside the root; it is unfollowable through the root. `FileWriter` must therefore not treat "a symlink exists" as proof of confinement; the root does that at open time.

**Connect message limit (Task 0.1.3b, VERIFIED: `go test ./server -run TestRecon -count=1`, `server/files_recon_chain_test.go`).** `grep -rn ReadMaxBytes --include='*.go'` finds only two comments (`server/services/backlog_service_lifecycle.go:1054`, `session/instance.go:199`); no `WithReadMaxBytes`/`WithSendMaxBytes` is set. Through the real `ConnectOptions` and `localChain`, a `WriteToSession` body of 1.5 MiB + 1 byte and one of 2 MiB are both accepted and delivered intact to the handler. So Connect imposes no limit today, and Task 2.1.2f's `WriteFile`-scoped body limit must be installed unconditionally, as the plan says.

**Hidden-session guard registration (VERIFIED by reading).** There is no per-RPC registration. The guard is in-handler: `TerminalService.WriteToSession` calls `AccessForUnary(inst, ts.guards).Writer(nil)` (`server/services/terminal_service.go`, `terminal_access.go:59`), governed by the live flag `hidden_session_readonly_guards` (`guards_flag.go`). `AccessForUnary` callers are pinned: `terminal_write_pins_test.go` (`pinnedAccessCallers`) and `terminal_write_callers_test.go` fail if any unlisted function calls it. `WriteFile`/`ApplyFilePatch` must therefore call `AccessForUnary` from the file-write policy and add themselves to `pinnedAccessCallers` (Task 2.1.2d). `AccessForUnary` looks only at `Snapshot().Hidden` and the flag; it does not look at `ArchivedAt`, and no `ArchivedAt` check appears in `terminal_service.go`, `terminal_access.go` or `workspace_service.go` (grep). The archived-session refusal for `WriteFile` is therefore new code: refuse with `FailedPrecondition` when `inst.IsArchived()` (`session/instance_state.go:513`), never revive (`noarchivedrevival`).

**Local-listener guard map (VERIFIED: `server/server.go:1879-1888`, test `TestReconLocalChain_ShouldKeepWriteRPCsOutOfGuardedProcedures`).** `guardedProcedures` holds `ProbeProgram`, `NudgeSessionForPR` (`ProfileProbe`) and `PruneHiddenSessionNotifications`, `UpdateFeatureFlag`, `ReplyToPendingQuestion` (`ProfileRebinding`). Neither `WriteToSession` nor `/api/files/raw` is in it; `WriteFile` and `ApplyFilePatch` must be added with `ProfileRebinding` (enforced by Task 2.1.2d). Two layers exist on the unauthenticated `:8543` chain: `HostGuard` (every method and path, including GET and WebSocket upgrades: loopback or allow-listed Host, and any Origin must be loopback on the request's port or allow-listed) and, only for map members, `LocalWriteGuard` (POST-only plus `RebindingVerdict`). Observed through the real `localChain`: a `WriteToSession` POST with Host `evil.example:8543`, or with Origin `https://evil.example`, returns 403 and never reaches the handler even though the procedure is not in the map, because `HostGuard` already rejects it. What the map adds for `WriteFile` is the POST-only check and the `RebindingVerdict` host rules (verified LAN hostnames and local interface IPs, which `HostGuard` would reject on a wildcard bind). With `s.authMiddleware` set the map is skipped and auth plus `HostGuard` are the boundary.

**Remote-access exposure of write RPCs (VERIFIED: `TestReconRemoteTier_ShouldHaveNoReadScopedTier_And_AcceptPatchSizedWriteBody`).** `remoteChain` is `stampRequest -> Logging -> CORS -> Compress -> middleware.Auth -> mux` (`server.go:1933`); no `ProbeGuard`/`LocalWriteGuard`. `middleware.Auth` has one decision: a valid `cs_auth` cookie or `Authorization: Bearer` token per `ValidateAuthSession(token) bool` (`server/middleware/auth.go`). There are no scopes, tiers or read-only tokens in `server/middleware` or `server/auth` (grep for readonly/read-only/scope finds nothing relevant). Results: an unauthenticated remote `WriteToSession` returns `Unauthenticated`; any authenticated remote caller reaches any `/api` write RPC, including a stand-in write RPC with a 2 MiB body. Consequence for `WriteFile`: **no per-RPC deny is required for a tier, because no weaker tier exists**; remote write authorization equals remote terminal-write authorization, consistent with the threat model above. If a read-only tier is ever introduced, `WriteFile` and `ApplyFilePatch` must be added to its deny list.

**VCS-cache invalidation (VERIFIED by grep).** `vcsStatusCache` is evicted only by `SwitchWorkspace` (`workspace_service.go:447`); entries otherwise expire after `vcsStatusCacheTTL` = 15 s. `Instance` exposes no VCS-status invalidation: its public surface is `UpdateDiffStats()` (forced recompute, `instance_worktree.go:637`) and `RefreshDiffStatsIfStale()`; `GitWorktreeManager.ClearDiffStats()` is reachable only through the unexported `gitManager`. `WorktreeChangeDetector` (`session/git_worktree_watcher.go`) re-fingerprints dirty/HEAD every 15 s and fires `OnChange` (subscribers: `git_worktree_manager.go:234,313`); it never touches `vcsStatusCache`. So Task 2.1.3a adds `InvalidateVCSStatus(workDir)` to `workspace_service.go` (a `vcsStatusCache.Delete`), and a save should also call `inst.UpdateDiffStats()` or accept the 15 s TTL for the diff-stat badge.
