# ADR-036: Pluggable range-read and delta-write file transport

**Status**: **Accepted** (2026-10-16, owner decisions below; integrated into `implementation/plan.md` the same day)
**Plan**: `implementation/plan.md` Stories 0.1.7, 0.1.8 and Tasks 0.1.4c/0.1.4d (spikes), Story 0.2.6, Story 1.2.3, Tasks 0.2.5d, 1.2.1f, 1.2.1g (Phase A), Epic 1.6 (Phase B), Stories 2.1.5, 2.2.5, 2.3.3, 2.5.5 (Phase C), Epic 2.6 (Phase D), contingent Epic 1.7 (custom engine); cost and waves in the plan's "Effort estimate"; the integration is logged under "ADR-036 integration" in the plan's Review repair log.
**Research**: `research/transport.md` (claims labelled VERIFIED / INFERRED / UNVERIFIED there)

## Owner decisions (2026-10-16; this ADR is Accepted on these)
1. **Large-file editing is included.** T1 (1 MiB to `hash_cap_bytes`, delta-only edits) is built under `files:range-read`, `files:delta-write` and `files:edit-large` (all global-only, live-settable, no scopes). Flag defaults are the planner's choice because this ADR was silent on range-read and delta-write: **all three default off**, flipped in the order `files:range-read` (after the Task 1.6.7c owner check), `files:delta-write` (after Gate G2: the Task 2.5.4a dogfood is signed), `files:edit-large` (after Gate G3: the T1 steps of Task 2.5.5b); `files:edit-large` is off by default as decided. The owner may change any default.
2. **Editor engine: CodeMirror 6 with a lazy gap-line document behind the `EditorEngine` port** (plus `Highlighter`, `MergeSurface` and the engine conformance suite, owned by plan Story 1.2.1). A custom rope/piece-table engine is built only if CM6 fails the extended S-T3 gate on the owner's phone; it is a clearly marked contingent epic (plan Epic 1.7), costed separately and excluded from the base total. Decisions 6 and 7 below describe the window-swap model (a1) with one editable window; after this decision a1 is the **fallback** and the default is the gap-line document of decisions 19-20 (several editable regions, one history), so read "one editable window" there as the fallback case.
3. **All adapters are included**: `full` (the floor), `connect_unary` (primary), `connect_stream` and `ws_stream` (reads), and the byte-only `http_range` GET adapter, the last **only** behind the DNS-rebinding guard (the existing `ServeFileRaw` receives the same check). `ApplyFilePatch` is allowed on the remote `:8444` listener, subject to Task 0.1.3b: capability negotiation is designed so either answer works, and if the recon says a read-scoped remote caller can reach write RPCs the plan gates `ApplyFilePatch` by scope.
4. **Cost approved with phasing A then B then C; Phase D (the adapters beyond `connect_unary` and `full`: `connect_stream`, `ws_stream`, `http_range`) is included, sequenced last and gated on the S-T1..S-T5 results.** Interpretation recorded in the plan: the spike results decide the default ladder (stream adapters advertised on or off), not whether the code is built; `http_range` never ships without its guard.

## Context
Today the file wire is whole-file: `GetFileContent` serves at most 1 MB (truncated) and rejects over 10 MB; the planned `WriteFile` sends the full content (about 1.34 MiB base64 for a 1 MB file; 1.5 MiB body cap, ADR-031). Consequences: big files cannot be opened, a truncated read is made non-editable to avoid destroying the tail (pitfall W1), every one-character save ships the whole file over a phone link, and drafts are bounded snapshots (ADR-032). The owner asked for a pluggable transport that sends parts of files for reading and serializes writes to their smallest parts.

## Decision
1. **Two ports, adapters only translate.** Client `FileTransport` (TS) with a `FileTransportRouter`; server `FileOps` (application service holding every policy: `resolveInWorktree`/`os.Root`, `.git` and symlink denial, flags, hidden-session guard, per-path mutex, token check, idempotency, limits, audit) over a `FileBackend` (storage port: `osRootBackend`, in-memory test backend). Wire handlers (Connect unary, Connect server-stream, WS stream, HTTP Range GET) contain no safety logic. ADR-031's confinement, atomicity, token and encoding rules apply unchanged to every adapter.
2. **Adapters.** `full` (today's `GetFileContent`/`WriteFile`; mandatory floor), `connect_unary` (primary: ranges + patch), then optional `connect_stream`, `ws_stream` (reuses the existing `watch-ws-transport.ts`; reads only) and `http_range` (byte-only, `206`, ETag = token, behind the rebinding guard or not shipped). A true bidirectional WS multiplex is not adopted. Per-op routing (read, patch, stat, writeFull resolve independently).
3. **Capability negotiation.** New unary `GetFileTransportCapabilities` returns `protocol_version` (major, breaking only), additive `features`, `ops`, per-listener `wires` (so `:8543` and `:8444` differ truthfully), `limits` and a `caps_epoch` echoed on every response so live flag flips are noticed. `Unimplemented` or a newer server major pins the `full` adapter. Fallback ladder per op: `ws_stream` > `connect_stream` > `connect_unary` > `full`; three consecutive transport-class failures demote one rung for the page lifetime and emit an analytics event; application errors never demote. Rollout flags (live-settable, global booleans): `files:range-read`, `files:delta-write`, `files:edit-large`.
4. **Reads.** `ReadFileRange` by line window (anchor line, direction, `want_lines` default 400 / max 4000, `max_bytes` default 128 KiB / max 1 MiB) or by byte anchor; responses are line-aligned and carry `start_line/end_line/start_byte/end_byte/bof/eof`, `line_count` when known, validator, CRC32C of the served bytes and `torn`. Wire byte offsets are raw-file offsets (BOM never shifts them); text is LF-normalized (ADR-031); byte anchors snap to rune starts; first-chunk 8 KB NUL sniff plus later `contains_nul_at`; lines over 256 KiB switch to read-only byte-window mode. A server **sparse line index** (checkpoint every 4096 lines) plus EOL/NUL/max-line statistics and a whole-file sha256 come from one background `Analyze` pass cached by `(path,size,mtime_ns,inode)`; client-side line discovery is rejected.
5. **Version token unchanged.** `v1:<size>:<mtime_ns>:<sha256|->` stays. Range reads return the `-` form until analysis finishes (then the full token); editing requires `analysis=ready`. Staleness for caches uses size+mtime; write identity is always the sha256 (computed during the streaming pass, so no extra read). Per-response CRC32C guards transport integrity. Merkle/chunk-digest tokens and a `v2` with `ctime_ns`/inode are deferred alternatives.
6. **Size tiers.** T0 up to 1 MiB: whole-file load as today (one round trip when the first range request sets `prefer_full_if_le`), full or delta save. T1 over 1 MiB up to `hash_cap_bytes` (64 MiB, proposed): windowed read; delta-only editing of **one editable window** under `files:edit-large`. T2 above that up to a 1 GiB read ceiling (proposed): windowed view-only (`ReadOnlyReason=TooLarge`).
7. **Client document model.** CM6 has no lazy document, so T1/T2 use a **windowed `EditorState`** (line-offset gutter, edge-triggered window swap via `setState` with an anchor line, external virtual scrollbar from line count), with the Accessible-view pager (500-line pages from `read(lines)`) as the screen-reader path and the T2 fallback. Chunk cache is an LRU by bytes (8 MiB phone, 64 MiB desktop) invalidated on any validator change; prefetch one window ahead/behind, two in scroll direction at speed, at most 2 ranges in flight per buffer; unary calls only so the HTTP/1.1 connection pool is not held. Search-hit jump is one `read(lines, around N)`; hits gain `byte_offset`; `SearchContent`'s 2 MB per-file cap becomes request-scoped (`large_files`).
8. **Deltas.** `ApplyFilePatch` carries ordered, non-overlapping edits in **base-document coordinates** as `{start{line, col_utf16}, end{line, col_utf16}, insert, deleted_crc32c}` (exactly what CM6 `ChangeSet.iterChanges` yields), plus `base_token`, `client_id`, `seq`, `expect_new_size`, optional `expect_result_sha256` (client holds whole doc), per-region `region_crc32c`. The server converts line/col to bytes, owns EOL/BOM, and rejects a column that splits a surrogate pair. Rejected units: whole-doc UTF-16 offsets (impossible when windowed) and byte offsets (client-side CRLF/BOM arithmetic is where corruption lives).
9. **Client sync is not OT.** The client composes a `pending` ChangeSet since the last acknowledged base (undo/redo collapse into the net edit), sends one request at a time (stop-and-wait; `seq` is a check, not a protocol), and builds the next patch on the new token. **OT/CRDT is not adopted**: one human writer, agents overwrite whole files with no op log, so reconciliation is the existing 3-way merge. Save remains explicit (no autosave to disk).
10. **Server write strategy.** T0: in-memory splice then ADR-031 temp+fsync+rename. T1: **streaming splice** into the temp file (read old, write prefix/insert/suffix, hash old and new in the same pass, verify, fsync, rename) with O(1) memory and a disk-space preflight; process-wide semaphore of 1 large rewrite. In-place `pwrite`, append journals and server-held piece tables are rejected (torn reads, stale files for agents, divergent truth).
11. **Verification before rename.** (a) base sha256 == token; (b) per-edit `deleted_crc32c`; (c) resulting size == `expect_new_size`; (d) region CRC32C; (e) T0 `expect_result_sha256`; plus a client-driven reconcile every 20 patches / on blur via `StatFile{want_sha256}`, after which a mismatch marks the buffer `Diverged` and forces `writeFull`. Any failure leaves the original file untouched; new typed reasons `OffsetMismatch`, `ResultMismatch`, `OutOfOrder`, `AnalysisPending`, `PatchTooLarge`.
12. **Idempotency.** Bounded replay store per `(session, path)` keyed by `(client_id, seq)` with payload digest (256 entries, 10 min); same key and digest returns the recorded outcome; same key with a different digest is `InvalidArgument`; `seq` must be `last_acked + 1`. After a server restart the lost-response rule (plan Story 2.2.3) applies; T1 unknown outcomes resolve by Reload (documented limit).
13. **Conflicts.** Base moved gives `Conflict`. T0: ADR-034 unchanged (documents are merged, deltas are not rebased). T1: `theirs = Unavailable{TooLarge}`; Reload keeps the pending ChangeSet as a draft, or `PreflightFilePatch` verifies that each edit's `deleted_crc32c` and touched-line CRC still hold at the same line numbers in the new file (fail closed if lines shifted); no diff-and-guess rebase.
14. **Drafts (ADR-032).** Persist the composed pending ChangeSet (`ChangeSet.toJSON`) keyed `(session, path, baseToken)`; the 256 KB cap now bounds edit volume, not file size; restore rules for equal/changed token are ADR-032's. Undo history is not persisted.
15. **Limits.** `ApplyFilePatch` body 2 MiB (path-scoped `MaxBytesReader`), 2,000 edits, 1 MiB total inserted text (oversize: `writeFull` in T0, else refuse; no splitting across requests because a half-applied logical edit is a corrupt file), 2 patches/s per path; `writeFull` stays 1.5 MiB; range response 1 MiB / 4000 lines; 4 concurrent ranges per client, 8 per IP; index/analysis builds under a semaphore of 1-2.
16. **Security.** `ApplyFilePatch` and `PreflightFilePatch` join `guardedProcedures` (`ProfileRebinding`); `files:editing` enforced in `FileOps`; capabilities omit `PATCH` on `:8444` until Task 0.1.3b decides remote write reachability; any GET route returning file bytes (`http_range`, and an audit of existing `ServeFileRaw`) must pass the rebinding verdict or not ship. slog line per patch without content. ADR-035 gains closed-enum labels `transport`, `fallback_reason`, size/payload/ops buckets and events `files.transport.select|fallback`, `files.read.window`, server `files.server.patch`; no paths, offsets, lines or text.
17. **Testing gate.** An adapter ships only when `runTransportConformance` (TS) and `FileOpsConformance` (Go) pass; shared golden vectors (`testdata/transport/*.json`) feed Go and TS; `FuzzApplyPatch` and fast-check assert `applyPatch == writeFull(applyChanges(base))` bytewise for LF/CRLF/BOM, multibyte and astral text in both T0 and T1 paths; fault-injection and benchmark plan in research section 7.
18. **Phasing (as integrated into the plan).** A: seam + `full` adapter + capability RPC + engine ports (behavior-identical; plan Wave 3, inside Phase 0/Phase 1 of the plan, since the plan has no Wave 0 and the seam wraps the Wave 2 resolver and Wave 3 codec). B: range reads + windowed viewer + gap-line document + large-file search (plan Wave 6, before any editing epic; flag `files:range-read`). C: delta writes (plan Waves 7-9, code starts after Gate G1; `files:delta-write` flips after Gate G2, `files:edit-large` after Gate G3). D: `connect_stream`, `ws_stream`, `http_range` (plan Wave 10, last, gated on the spike results). Five spikes S-T1..S-T5 precede B/C in Phase 0 (compression, hash/splice throughput, CM6 gap-line and window swap on desktop, WebKit and the owner's phone, encoder prototype, connection-pool contention); `S-T5` is re-measured with the real load in Task 1.6.7b.

## Consequences
Positive: large files open, jump and search without full load; one-character saves shrink from about 1.3 MiB to hundreds of bytes (INFERRED); pitfall W1 is solved by construction for deltas; drafts cover big files; transports can be swapped, measured and demoted without touching safety code; the `full` floor keeps today's behavior as the fallback. Negative: a second write path with silent-mangling risk (mitigated by layered verification and a kill switch); the windowed editor is real CM6 work and a visible "edit this window" mode; stale PWA clients and newer servers must interoperate (capabilities and the floor cover it); **about +9.7M CU in the integrated plan (bottom-up task splits, recomputed by script: 63 tasks, 5.95M raw tokens, 27.71M CU total against the base plan's 18.04M; the top-down estimate this ADR first carried was about +6.2M, plus about 1.0M for the engine seam and lazy document, INFERRED)**, with the contingent custom engine (about 4.6M CU, replacing the earlier "about 6M") excluded; more RPC surface to guard, register in the feature registry and keep in `guardedProcedures`.

## Supersedes / reconciles
Supersedes in part: ADR-031 "editable cap equals the 1 MB read; no relaxed-truncation edit path" (kept on `full`/T0; T1 is delta-only behind `files:edit-large`); the plan's truncated-read refusal (kept only on the `full` adapter); ADR-032 snapshot drafts (now ChangeSet drafts). Amends: ADR-030 (request-scoped per-file cap, `byte_offset`, shared limiter), ADR-034 (deltas not rebased; T1 same-position rebase), ADR-035 (labels/events). Unchanged: ADR-031 token format, confinement, atomicity, encoding ownership and the 1.5 MiB `writeFull` cap; ADR-033.

## Alternatives rejected
Byte offsets or whole-document UTF-16 offsets on the wire; OT/CRDT; in-place patching, append journal or server piece table; placeholder-line or custom lazy CM6 document; client-side line discovery; Merkle-root token now (no benefit before the 64 MiB tier, first computation is a full read anyway); sending the full content with compression only (does not fix large files or the truncation hazard); bidirectional WebSocket multiplex (Connect browser clients have no client streaming; unary patch plus unary/streamed reads covers all operations).

### Task 0.1.3b recon (2026-10-16; Go 1.26.6, Linux; tests in `server/files_recon_chain_test.go`, run: `go test ./server -run TestRecon -count=1` PASS)
- **Remote-tier reach of write RPCs (VERIFIED).** There is no read-scoped remote tier: `middleware.Auth` (`server/middleware/auth.go`) decides only "valid cookie or bearer token" vs not, and nothing under `server/middleware` or `server/auth` carries a scope. Through the real `remoteChain(middleware.Auth(...), true)` an unauthenticated `WriteToSession` returns `Unauthenticated`; an authenticated caller reaches it with a body of 2 MiB (the patch cap) and the handler receives all 2,097,152 bytes. Consequence: `ApplyFilePatch` on `:8444` is reachable by every authenticated remote caller, exactly like `WriteFile` and `WriteToSession`, so `PATCH` is advertised on `:8444` to authenticated callers (there is no weaker caller to withhold it from) and Task 2.1.5e needs no scope gate today. If a read-only tier is later added, `ApplyFilePatch`, `WriteFile` and the capability probe must be revisited together. This is a recorded fact; the plan's branch ("if no, PATCH is advertised for write-scoped remote callers") applies with "write-scoped" meaning "authenticated". No owner decision is needed unless the owner wants a new read-only tier (not in scope).
- **`ReadMaxBytes` (VERIFIED).** Not set anywhere in `server/` (only two comments mention it). Real Connect handlers built with `ConnectOptions` accept 1.5 MiB + 1 byte and 2 MiB unary bodies on `localChain` today. `ApplyFilePatch`'s 2 MiB path-scoped body limit must be installed explicitly (`middleware.BodyLimit` wrapper, ADR-031), because Connect will not enforce it.
- **`guardedProcedures` (VERIFIED, `server/server.go:1879-1888`).** Holds `ProbeProgram`, `NudgeSessionForPR`, `PruneHiddenSessionNotifications`, `UpdateFeatureFlag`, `ReplyToPendingQuestion`. Neither `WriteToSession`, `WriteFile`'s future path, `ApplyFilePatch`'s future path nor `/api/files/raw` is a member (`TestReconLocalChain_ShouldKeepWriteRPCsOutOfGuardedProcedures`). `WriteFile`, `ApplyFilePatch` and `PreflightFilePatch` must be added with `ProfileRebinding` (Task 2.1.2d / 2.1.5e). The `localChainWith` map is bypassed when `s.authMiddleware` is set.
- **`ServeFileRaw` GET through the real `localChain` (VERIFIED, `TestReconLocalChain_ShouldRejectForeignOriginAndRebindingHost_For_FileBytesGET`; the route is a stand-in handler on the real mux path `/api/files/raw` because the verdict lives in the chain, not in the handler).** The `GET /api/files/raw` with no Origin and Host `localhost:8543` is served (200); with the same-port loopback Origin it is served; with Origin `https://evil.example` it is rejected 403; with Host `evil.example:8543` it is rejected 403; with another loopback port's Origin (`http://localhost:9999`) it is rejected 403; the handler is not reached in the rejected cases. The rejecting layer is `HostGuard` (`server/middleware/hostguard.go`), which wraps every method and path before the mux, not `LocalWriteGuard`/`ProfileRebinding` (POST-only, applies only to `guardedProcedures` members). So the GET is already protected against DNS rebinding and foreign-Origin fetches on the unauthenticated listener. Residuals: (a) a cross-origin simple `<img>`-style GET carries no Origin header and a loopback Host, so it is served, but the embedding page cannot read the bytes without CORS (none is granted to a foreign origin by `CORSWithOrigins`); (b) `HostGuard` accepts only loopback or allow-listed hosts, stricter than `RebindingVerdict`, so a verified LAN hostname on a wildcard bind is refused on GET but would be accepted by `ProfileRebinding` on a guarded POST. Task 2.6.3a therefore adds no new guard for `ServeFileRaw` itself; it must assert that the new `http_range` GET route is registered on the same mux (so `HostGuard` covers it) and add a regression test equivalent to the one above. No owner decision needed.
- **Metrics registration pattern (VERIFIED, `server/services/session_creation_metrics.go`, `watch_stream_metrics.go:57`).** Package-level instruments created once from `telemetry.GetMeter()` (safe before `telemetry.Initialize`; delegating no-op meter until a provider is installed) via the existing helpers `mustInt64Counter` and `mustFloat64Histogram`, with a closed set of string constants for attribute values and one `Record...` function. Names are dotted with `_ms` units (`session.creation.outcome`, `session.creation.duration_ms`), not the Prometheus-style `files_*_seconds` names written in plan.md. Files metrics should follow the same shape (`files.search.duration_ms`, `files.search.total{outcome}`, `files.range.duration_ms`, ...); the exporter maps names. `server/services/file_metrics.go` does not exist (re-confirmed). Deviation from plan wording only; record the final names when Story 1.1.3 / 2.1.x implement them.
- **Hidden-session/archived policy (see ADR-031).** In-handler `AccessForUnary` (pinned-caller test), no `ArchivedAt` check exists in the current unary guards.

### S-T1 compression and wire cost (Task 0.1.7a; 2026-10-16; Go side only; host AMD Ryzen 9 7900X, loopback)
Tests: `server/services/transport_spike_test.go` (`go test ./server/services -run TestTransportSpike -count=1 -v`, PASS) and `server/files_recon_chain_test.go` (`go test ./server -run TestReconChains -count=1 -v`, PASS). The throwaway handler is a test-file stub of `GetFileContent` mounted with a plain Connect handler under the production `otelhttp -> Logging -> CORS -> Compress` layers; nothing is registered in `server.go`, so there is nothing to delete.
- **Finding: `/api` unary responses are already gzipped, at Connect level, whenever the request carries `Accept-Encoding: gzip`, which every browser sends.** `middleware.Compress` does bypass `/api/` (`gzip.go:155-163`) but connect-go's own handler compresses the unary body and sets `Content-Encoding: gzip`. Through the real `localChain` and `remoteChain` (`TestReconChains_...`), a `GetFileContent` call with `Accept-Encoding: gzip, deflate, br, zstd` returns `content-encoding="gzip"` on both chains. connect-web is created without compression options (`web-app/src/lib/api/transport.ts:34`, JSON format) and the browser decompresses `Content-Encoding` itself, so no client change is needed. Without `Accept-Encoding` the body is identity.
- **Wire sizes, 15 calls each, JSON unary, `DisableCompression` client (median latency is in-process loopback and so includes the server's gzip CPU):**
  | payload | identity wire bytes | gzip wire bytes (ratio) | identity median | gzip median |
  |---|---|---|---|---|
  | 128 KiB real Go source | 140,052 | 38,753 (0.277) | 0.78 ms | 7.36 ms |
  | 1 MiB real Go source | 1,110,024 | 292,029 (0.263) | 4.01 ms | 46.70 ms |
  | 128 KiB repetitive words (best case) | 134,343 | 1,334 (0.010) | 0.57 ms | 0.88 ms |
  | 1 MiB repetitive words (best case) | 1,074,527 | 6,801 (0.006) | 2.35 ms | 6.61 ms |
  Real source compresses to about 26-28 percent of identity; the repetitive samples are a ceiling, not a typical case. Server CPU cost of default gzip is about 40 ms per 1 MiB response on this host (the median gap above), so a 128 KiB window costs about 6.6 ms extra.
- **Decision (evidence-backed, recommended): Connect-level gzip as is.** Range responses need no per-RPC compression setting and the `/api/` bypass in `Compress` stays untouched. Revisit only if a measurement on the phone path shows gzip CPU on the server, not bandwidth, as the bottleneck (then a `connect.WithCompressMinBytes` threshold is the lever).
- **WebSocket path (`StreamingWSBridge`, gorilla/websocket, `connectrpc_websocket.go:94`):** the production `wsUpgrader` does not set `EnableCompression`, so a client offering `permessage-deflate` gets no `Sec-WebSocket-Extensions` header back (test `TestTransportSpike_WebSocket_ShouldReportPermessageDeflateNegotiation`: production `""`, with `EnableCompression: true` `"permessage-deflate; server_no_context_takeover; client_no_context_takeover"`). Library availability is therefore VERIFIED, enablement is a one-field change, and no range traffic rides the WS bridge in the current design (range reads are unary on the Connect adapter), so it stays off.
- **PENDING-OWNER: the phone/LAN/Tailscale leg of S-T1** (response size on the wire and latency from the phone over `:62872`) is not measured here; the Go numbers above predict the same bytes. The jest half (Task 0.1.7a web) is owned by another worker.

### S-T2 index/hash/splice throughput and the 64 MiB scan (Task 0.1.7b; 2026-10-16)
Host: AMD Ryzen 9 7900X (24 threads), 61 GB RAM, Linux 6.6, Go 1.26.6, files on NVMe btrfs (`/home`), page cache warm, 3 iterations per case (`-benchtime 3x`; the timing noise at this count is visible in the 1 MB rows). Command: `TMPDIR=$HOME/.cache/ssq-bench-tmp go test -bench 'BenchmarkTransport|BenchmarkScan64' -run '^$' -benchmem -benchtime 3x ./server/services &` (run in the background and waited on); code `server/services/transport_bench_test.go`, with prototype correctness pinned by `TestTransportSpike_SpliceAndIndex_ShouldMatchInMemoryOracle` (PASS). Files: deterministic seed 42 in three shapes: LF (60-char lines), CRLF (60-char lines), and `long200` (200-char lines). The index is sparse (one offset per 1,024 lines) with a 1 MiB read buffer.

Single-pass index + sha256 (ns/op, MB/s, B/op; allocs/op 6-18):
| shape | 1 MB | 16 MB | 64 MB | 256 MB |
|---|---|---|---|---|
| LF | 1.23 ms, 854 MB/s | 12.4 ms, 1357 MB/s | 53.6 ms, 1252 MB/s | 209 ms, 1283 MB/s |
| CRLF | 1.14 ms, 921 MB/s | 12.0 ms, 1394 MB/s | 48.9 ms, 1372 MB/s | 203 ms, 1323 MB/s |
| long200 | 0.72 ms, 1465 MB/s | 12.3 ms, 1363 MB/s | 47.2 ms, 1422 MB/s | 188 ms, 1429 MB/s |
`B/op` is flat at 1.05-1.18 MB for every size (the read buffer plus the sparse index): memory does not grow with file size.

Streaming splice (read old, write prefix, insert 100 bytes, skip 10, write suffix to a temp file in the same directory, `fsync`, hash old and new in the same pass; `B/op` 1.05-1.06 MB, 20-22 allocs for every size):
| shape | 1 MB | 16 MB | 64 MB | 256 MB |
|---|---|---|---|---|
| LF | 12.3 ms, 85 MB/s | 49.2 ms, 341 MB/s | 193 ms, 348 MB/s | 626 ms, 429 MB/s |
| CRLF | 13.3 ms, 79 MB/s | 47.9 ms, 350 MB/s | 160 ms, 420 MB/s | 661 ms, 406 MB/s |
| long200 | 12.5 ms, 84 MB/s | 49.7 ms, 338 MB/s | 165 ms, 408 MB/s | 619 ms, 434 MB/s |
The 1 MB rows are dominated by the temp-file `fsync` (about 12 ms on this btrfs volume), not by copying or hashing. Temp-file and free-space behavior: the temp file lives in the target's directory and needs free space equal to the new file's size on top of the original (peak about 2x); it is removed on success (rename consumes it) and on any error through `defer os.Remove` (the oracle test finds exactly one directory entry after a splice). ENOSPC mid-splice was not injected here (UNVERIFIED; the conformance suite's in-memory `FileBackend` covers it per validation.md).

|---|---|---|---|

**Constants (confirm / replace):**
- `hash_cap_bytes` = 64 MiB: **confirmed.** Hashing plus indexing 64 MB costs about 50 ms and a 64 MB splice with fsync about 160-190 ms on this host, so neither is binding; the cap is a policy and memory-safety line, not a throughput one. Hash throughput scales with CPU SHA extensions: slower hosts (older laptops, the work macOS machine, a Pi-class host) are UNMEASURED; a 5x slower host would still index+hash 64 MiB in about 0.25 s.
- Read ceiling = 1 GiB: **confirmed as proposed, with an INFERRED cost.** Extrapolating the linear 256 MB rows (about 1.3 GB/s) gives roughly 0.8 s to index a 1 GiB file warm and 2.5 s to splice it, both measured only up to 256 MB. Windowed reads themselves are O(window). Because the analysis pass is paid once per file and then cached by token, 1 GiB stays acceptable, but cold-cache disk throughput is not measured here.
- Scan: **replace the whole-file read with streaming for any file above the old per-file cap.** Reading a 64 MiB file whole costs 64 MiB of heap per worker (67 MB/op; 24 parallel workers could pin 1.6 GB), against 1 MB/op streaming, and streaming is also 2.5x faster here. Proposed scan constants for the Story 1.1 implementation: stream files up to 64 MiB (about 20-45 ms each warm); skip larger files with a counted "too large" outcome unless `IncludeIgnored`-style opt-in is added. UNVERIFIED on a cold cache.
