# ADR-030: In-process streaming content search behind `ContentSearcher`

**Status**: Proposed (2026-10-16)
**Plan**: `implementation/plan.md` Epic 1.1; amended by ADR-036 in Story 1.6.6 (large-file search) and Task 1.6.2c (shared limiter)

## Context
Files tab needs project-wide content search over agent-written, often uncommitted worktrees. Target: first results < 2 s on ~50k files (UNVERIFIED; measured in Story 1.1.3). `rg` exists on the dev host but is not guaranteed elsewhere; repo convention prefers in-process over subprocesses (`prefer-go-git-over-subshells`); go-git `Worktree.Grep` searches tracked content only.

## Decision
1. Define `ContentSearcher` (domain interface). Ship an in-process implementation: `fs.WalkDir` over the `os.Root` filesystem, pruned at `SkipDir`, an incremental, ctx-aware `IgnoreMatcher` that loads each directory's `.gitignore` through the `os.Root` as the walker enters it (go-git `ParsePattern`, same semantics as `SearchFiles`; `collectAllGitignorePatterns` is a full second non-cancellable walk that bypasses `os.Root` and is not reused for search), `doublestar/v4` globs (`go.mod` carries only the v1 line as ent's indirect dependency, so v4 is added with `go get`; `ValidatePattern` rejects malformed globs at the boundary), go-git `ParsePattern`/`NewMatcher` reuse verified against the pinned fork (plan Task 1.1.1e), RE2 `regexp`, 8 KB NUL sniff, 2 MB file cap, a bounded `errgroup` of `min(4, GOMAXPROCS/2)` workers so terminal streaming keeps CPU, ctx checks inside scan loops, UTF-16 column ranges, caps (1000 total, 50 per file, 512-byte line clamp).
2. RPC is server-streaming `SearchContent` with a final stats message, so first results are not blocked by the full walk. Newest search wins **per client** (`SearchKey{SessionID, ClientID}`, one mutex-guarded registry with swap-and-cancel inside the lock), so a phone and a desktop viewing the same session never cancel each other; a process-wide semaphore (limit 2) bounds concurrent walks across sessions; a search waiting on it sends `Queued{ahead}` so the UI shows a cancellable waiting state. Walk with `fs.WalkDir(root.FS(), ".")` so traversal and reads share the one `os.Root`. Search never runs against the repo-root fallback: for a paused or archived session whose worktree is gone (`ActiveDir != ExistingDir`) the handler returns `FailedPrecondition WorktreeMissing` and walks nothing (same wrong-checkout hazard as writes); the UI shows the "Session paused; worktree unavailable" empty state with Resume. `SearchStats` therefore has no `root_is_fallback`.
3. `rg` accelerator is deferred: added only if Story 1.1.3's benchmark misses the 2 s target, behind the same interface with `--no-config`, args array, `--` separator, no `--pre`.
4. **Transport (decided by Story 0.1.1 on the real path)**: `SearchContent` is not a `Watch*` RPC, so it is not served by `StreamingWSBridge` and `TestEveryServerStreamingWatchRPCHasAWebSocketBridge` does not cover it. Default is plain Connect fetch streaming through `getConnectTransport()` (short-lived, abortable, one connection held only while a search runs). The spike measures a throwaway streaming RPC on that exact stack over `:62871`, `:62872` and the phone, plus connection-slot impact. **Suspect order if batches buffer (engineering triad ET-6)**: response compression is *not* the prime suspect: `middleware.Compress` returns the handler untouched for every `/api/` path (VERIFIED `server/middleware/gzip.go:155-163`; `SearchContent` is mounted under `/api`, `server/server.go:497`), and its writer flushes the encoder on `Flush()` regardless (`gzip.go:93-103`). The in-process chain test (Task 0.1.1b, `server/streaming_chain_test.go`) therefore targets, in order, the `otelhttp` wrapper (`server.go:1536`, `:1965`; Flusher preservation via httpsnoop is INFERRED, untested), then off-process hops (the TLS listener's HTTP/2, a LAN/Tailscale proxy, the phone browser's fetch-stream support; UNVERIFIED). `Logging` (VERIFIED flushes), `CORS` and `HostGuard` (VERIFIED no writer wrapping) are cleared by reading. Remedy order: fix the buffering layer in-process first (a Flusher passthrough, or an exempt-path entry if a layer is ever shown to buffer a non-`/api/` streaming route), then exact-path WS-bridge registration with a transport-selector entry (and extending the bridge registration test), then a unary wrapper over the same handler body. **If path (b) is chosen (triad round 3)**: the exact-path WS-bridge registration (beside `watchSessionsPath` etc., `server/server.go:499-509`), the transport-selector entry in `web-app/src/lib/transport/watch-ws-transport.ts` and the extension of `TestEveryServerStreamingWatchRPCHasAWebSocketBridge` are owned by contingency **Task 1.1.2d** (Wave 4, in Story 1.1.2, after the Task 0.1.1b finding and before Task 1.1.2b's delegate registration). It edits `server/server.go` in Wave 4, i.e. **before** the Wave 4 gate that probes `server/server.go`'s length (Story 0.2.4), so the probe measures the file with those lines already added; Task 0.2.4f, if triggered, therefore carves out the bridge registration lines together with `guardedProcedures`. Path (c) needs no `server.go` edit beyond the delegate (its `SearchContentUnary` proto addition rides Task 1.1.1a's commit).
5. **Memory bound (NFR, ET-8)**: scan buffers are at most `workers x per-file cap` = 4 x 2 MB = 8 MB per walk and at most 16 MB across the process-wide 2-walk semaphore (derived, not measured); results are under 1 MB per search (1000 matches x at most 512 B); nothing scales with the 50,000 files because the walk streams and files are read through a pooled buffered reader. A Go test with a heap sampler asserts peak `HeapAlloc` growth below 64 MB (4x the bound) and `BenchmarkContentSearch -benchmem` prints `B/op`.
6. **Open-stream cap (NFR, ET-8)**: a server stream holds one HTTP/1.1 connection of the browser's per-origin pool (6 assumed, shared by all tabs of that browser, UNVERIFIED per browser), and a queued search holds it while waiting. `streamLimiter` caps open `SearchContent` streams at 3 per remote IP and 8 in total (proposed, INFERRED, adjustable constants) and bounds queue wait at 20 s; a refused or timed-out stream ends with `ResourceExhausted` and a `SearchBusy` detail, the client shows a Retry message and never retries automatically, and aborts abandoned streams (panel closed, unmount, document hidden for 30 s). **Key limitation (triad round 2)**: the limiter keys on the connection's remote IP (`http.Request.RemoteAddr` host part; `X-Forwarded-For` and similar headers are ignored because the unauthenticated local listener cannot trust them). Behind a reverse proxy or on the loopback listener every device and tab shares one key, so the 3-per-IP cap becomes a 3-per-proxy cap and one phone's runaway tabs can starve a desktop (the total cap of 8 still bounds the process); devices that reach the server directly (LAN, Tailscale, the TLS remote-access listener) have distinct keys. This is acceptable for a single-user tool and is recorded rather than engineered around; the caps are constants and the key function is a single replaceable seam. Tests: `TestStreamLimiter_ShouldKeyOnRemoteAddr_And_IgnoreForwardedHeaders` drives the limiter with two different `RemoteAddr` values (a third stream from the second IP is accepted while the first IP is saturated) and with identical `RemoteAddr` plus different `X-Forwarded-For` (still one key).
7. **Amendment (ADR-036, 2026-10-16): large-file search, `byte_offset`, shared limiter.** (a) The 2 MB per-file cap of decision 1 is a **policy constant on a streaming scanner**, so it becomes **request-scoped**: `SearchOptions.large_files` (default false, per-device UI toggle) raises it to `hash_cap_bytes` (proposed 64 MiB) under a per-file time budget and a lower worker count (`min(2, GOMAXPROCS/2)`); a file past the cap or the budget is counted in `SearchStats.large_files_skipped`, never silently missed; the memory bound of decision 5 still holds because buffers are `workers x pooled reader`, not file size (the 64 MB heap-sampler test is re-run with the cap raised). The 64 MiB scan cost is measured in S-T2 (Task 0.1.7b) before the cap is set. (b) Each `SearchMatch` gains `byte_offset` (the raw-file offset of the matched line start; not PII, never logged or sent to analytics) so opening a hit is one `ReadFileRange(lines, around N)` that works before the line index exists. (c) The open-stream limiter of decision 6 and the new range limiter (4 concurrent range calls per client, 8 per IP) share one per-IP accounting seam in `content_search_limits.go`; range calls have their own higher cap and a refused range call never cancels a search. Proto fields are added in Task 1.1.1a.


## Consequences
Search and tree agree on ignore semantics; no external dependency; 2 s SLO is a measured gate, not a claim. `hardSkipDirs` hides `build/dist/vendor` unless `IncludeIgnored`; `.git` is always denied.

## Alternatives rejected
Unary-only RPC (cannot become streaming without a new RPC); `rg` first (availability, ignore divergence, subprocess convention); go-git grep (misses untracked files); content index (staleness class, not needed for walk-per-query).

### Task 0.1.1b (server side) and Task 0.1.2 (2026-10-16; host: AMD Ryzen 9 7900X, 24 threads, Linux 6.6, Go 1.26.6)
**Transport decision: path (a), plain Connect fetch streaming through `getConnectTransport()`; no WS-bridge registration and no unary wrapper.** Evidence, all VERIFIED by Go tests (`go test ./server -run TestStreamingChain -count=1 -v` and `go test ./server/services -run TestStreamingSpike -count=1 -v`, all PASS):
- A real Connect server-stream (stand-in on `WatchSessions`'s signature; 4 messages, 100 ms apart, mounted at `/api` with the production `ConnectOptions`) read by the Go Connect client with `Accept-Encoding: gzip, zstd` arrives incrementally through the real `localChain` and `remoteChain`, each wrapped in `otelhttp` with `WithMessageEvents` as in `server.go:1536` and `:1965`. Arrival gaps (first is time to first message): local `[930.841us 100.91911ms 101.80246ms 100.533238ms]`, remote `[2.070647ms 100.883492ms 103.752002ms 101.677793ms]`. The `otelhttp` writer wrapper therefore keeps `http.Flusher` working; it is cleared as a suspect. Compression, `Logging`, `CORS` and `HostGuard` are cleared by the same run.
- The same stream through the production `StartRemote` (real `http.Server.ServeTLS`, self-signed TLS, negotiated `HTTP/2.0`) arrives incrementally: gaps `[132.977us 101.211185ms 101.042589ms 103.636835ms]`. So the `:8444`/`:62872` listener does serve HTTP/2 (previously INFERRED) and does not buffer in-process.
- The test can detect buffering: `TestStreamingChain_ShouldFlagBurstDelivery_When_ALayerBuffersTheResponse` wraps the chain in a layer that holds the response until the handler returns and the incremental check fails as it should. On a real failure the chain test logs a one-layer-removed bisect (otelhttp, logging, cors, compress).
- Abort: closing the client context makes the server handler observe `ctx.Done()` 54.6 microseconds later (`TestStreamingSpike_ShouldCancelServerContext_When_ClientAborts`, limit one second).
- Connection slots: with two streams held open on one HTTP/1.1 origin and a client limited to 6 connections per host, a unary RPC on the same origin completes immediately (`TestStreamingSpike_ShouldCompleteUnaryCall_When_TwoStreamsAreHeldOpenOnOneOrigin`). This models, but is not, a browser's pool.
- NOT done: the throwaway handler was not registered in a running `:62871`/`:62872` binary (that needs a temporary edit of `server/server.go`, a file other workers are building against), so no real-binary, real-network number exists. The in-process real-listener runs above stand in for the laptop leg. **Phone/LAN/Tailscale leg: PENDING-OWNER** (open the stream from the phone against a manual instance and record first-message time and whether batches arrive incrementally; if the phone path buffers, try path (b) then (c)). The jest half (Task 0.1.1a) belongs to another worker.
- The chain test is kept as the regression test (no tmux or storage needed); the stand-in handler lives only in test files, so there is nothing to delete before merge.
