# Validation Plan: session-lifecycle-state-machine

**Date**: 2026-09-06

## Happy Path Scenario

Given the Baseline (`session/tymux/stream.go`'s `readAttachLoop` classifies "should I stop or
continue" via a 3-clause `||` of independently-set flags, with no compile-time exhaustiveness
guarantee), when `openStandingStream`'s teardown-for-reopen path cancels a generation's `ctx`
without setting `s.closing` (incident #2's exact trigger), then `classifyStreamEnd` returns
`lifecycle.ReasonDeliberateSupersede`, `reason.ShouldContinue()` returns `false` so the reader
goroutine exits instead of blocking on reconnect, `teardownStandingStream`'s
`lifecycle.AwaitBounded` wait returns promptly, and `lifecycle.EndGeneration` records
`session_lifecycle_ends_total{subsystem="tymux_stream",reason="deliberate_supersede"}` — proving
the new mechanism makes this class of hang diagnosable from a trace/metric instead of requiring
a live `pprof` goroutine dump (the exact gap incident #2 exposed).

## Test Stack

- **Unit**: Go's standard `testing` package + `github.com/stretchr/testify` (already used throughout `session/tymux`/`session/tmux`, e.g. `require.Eventually`, `assert.Equal`) — run via `gotestsum` per `make test`, or plain `go test` for single-package/-test runs per this repo's convention.
- **Integration**: Same `testing`/`testify` stack, no separate framework — "integration" here means exercising the actual `session/tymux` gRPC-mock stream boundary (`RPC-mock`/`startedSessionWithStream`-style fixtures already in `stream_test.go`) or the actual `session/tmux` control-mode pipe boundary (fake/pipe-backed process fixtures already in `control_mode_test.go`), as opposed to calling `classifyStreamEnd`/`classifyControlModeExit` directly with hand-constructed structs. Observability assertions (both unit and integration) use a test-local OTel SDK `metric.ManualReader`, matching `control_mode_observability_test.go`'s existing pattern.
- No database or network-service boundary exists in this project (Migration Plan: N/A, no schema/config/wire-protocol change) — the two "external call" boundaries in scope are the in-process tymux gRPC stream and the tmux control-mode OS pipe, both already covered above.
