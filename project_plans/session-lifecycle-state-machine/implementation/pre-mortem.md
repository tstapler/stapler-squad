# Pre-mortem: session-lifecycle-state-machine
**Date**: 2026-09-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `telemetry.StartLinkedBackgroundSpan`'s derived `genCtx` is assumed (not proven) to still propagate the parent's cancellation into `classifyStreamEnd`'s `ctx.Err()` check (plan.md Task 2.2.1a); if the assumption is wrong, `ctx.Err()` permanently reads `nil` under the new mechanism, silently reintroducing incident #2's exact `teardownStandingStream` deadlock behind the abstraction built to prevent it. | `teardownStandingStream: old reader goroutine did not exit in time, abandoning it` warnings (or actor-wide wedges) spike again after the migration ships, even though the pre-mortem's own regression tests and the `-race` run both stayed green — because `-race` proves absence of data races, not correct cancellation propagation. | Add a dedicated unit test (in `session/lifecycle` or `session/tymux/stream_test.go`) that starts a generation via `StartGeneration`, cancels the *parent* context, and asserts the returned `genCtx.Done()` fires — direct proof, not inference from an unrelated `-race` run — and gate Task 2.2.1a's merge on it. | P1 |
| 2 | `STAPLER_SQUAD_TMUX_LIFECYCLE_V2` flipping to `true` (Epic 5.3, Task 5.3.2a) is the first time the consolidated `classifyControlModeExit`/`onExitOnce` path runs against real concurrent production sessions on the default backend; the plan's bake-time criterion ("N weeks, no incident report") is left undefined, unowned, and untied to any dashboard, so the flip happens on schedule-optimism rather than evidence, or never happens and the new path silently rots as dead code. | A cluster of new-shape `tmux_control_mode` incidents (missed or duplicated `onExit` callbacks) appears clustered in time with the global env-var flip across every session at once, rather than with any reviewed code change — hard to attribute quickly, and with no canary subset to compare against. | Replace Task 5.3.2a's vague criterion with a concrete, monitored gate: require `session_lifecycle_ends_total{subsystem="tmux_control_mode"}` and `session_lifecycle_active_generations{subsystem="tmux_control_mode"}` to be dashboarded and observed through a staged rollout (a subset of hosts/sessions first, not one global flip) before the `false` branch is deleted. | P1 |
| 3 | Task 2.1.1c adds a second, freestanding `if s.closing.Load()` check inside `ReconnectLoop`, living outside `classifyStreamEnd` — reproducing, inside this migration's own diff, the exact "two independently-maintained checks of the same signal can drift" smell the project exists to eliminate (Architecture Review concern, unresolved). | A future change to what counts as "deliberate close" is added to `classifyStreamEnd` but not mirrored in `reasonForReconnectFailure`, so `session_lifecycle_ends_total{subsystem="tymux_reconnect",reason="reconnect_exhausted"}` fires on a deliberate stop — a false-positive reconnect-exhaustion signal with no matching real exhaustion. | Route Task 2.1.1c's branch through `classifyStreamEnd` itself (or a helper both call), per the architecture review's own remediation suggestion — fix before Phase 2 merges, not deferred to a follow-on. | P2 |
| 4 | `Reason` values have no type-level restriction on which subset each subsystem's classifier may legally return, and subsystem labels (`"tymux_stream"`, `"tmux_control_mode"`, …) are raw repeated string literals across 3+ files with no shared constant (Architecture Review concerns 1 and 3, both unresolved) — a future edit or copy-paste into a 4th subsystem can silently emit a semantically wrong `Reason` or a typo'd label. | A dashboard panel for `tmux_control_mode` shows an unexpected `reason` value (e.g. `clean_exit`, which that subsystem should never produce) or a near-duplicate subsystem string silently fragments `session_lifecycle_ends_total`'s cardinality — caught only by manual reconciliation weeks later, not by any test or alert. | Add the architecture review's suggested per-subsystem "allowed reason subset" test for each classifier, and define subsystem labels as exported constants (or a `type Subsystem string`) in `session/lifecycle` instead of string literals — land both before Phase 3, since Phase 3 is the first place a second classifier exists to drift from Phase 2's. | P2 |
| 5 | The Success Metrics claim that a future incident is "diagnosable from a trace, not a live pprof dump" doesn't survive contact with a real on-call workflow: neither `StartGeneration` call site attaches a session/pane identifier to its span (Adversarial Review concern, unresolved), and `control_mode.go`'s span starts from `context.Background()`, severing it from any request trace. | During a real incident, `session_lifecycle_active_generations{subsystem="tymux_stream"}` correctly shows elevated/leaking, but the on-call engineer can't narrow it to a specific session or pane from the span/metric alone — and falls back to the same pprof-dump workflow incident #2 required, defeating the project's stated diagnosability goal. | Add a `session.id`/`pane.id` span attribute at both `StartGeneration` call sites (Tasks 2.2.1a, 3.2.1a) before claiming the Success Metric is met, and validate it by walking the actual on-call trace-lookup workflow end to end (not just asserting the span exists in a unit test) as part of Phase 2/3 verification. | P2 |
