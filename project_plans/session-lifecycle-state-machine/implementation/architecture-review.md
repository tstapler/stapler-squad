# Architecture Review: session-lifecycle-state-machine
**Date**: 2026-09-06
**Verdict**: CONCERNS
**Note**: Repair-loop iteration 1 — scoped re-review of the single prior blocker (metric double-counting). See git history for the original full review if needed.

## Blockers
None. The original Blocker is resolved.

- **Tasks 3.1.1b/3.1.1c/3.1.1d** (`plan.md` lines 833-868): classification (`t.classifyControlModeExit()`), the `lifecycle.EndGeneration` call, and the conditional `t.onExit(...)` call are now all written **inside** the closure passed to `t.onExitOnce.Do(...)` — confirmed by the literal replacement text: `t.onExitOnce.Do(func() { reason := t.classifyControlModeExit(); lifecycle.EndGeneration(span, "tmux_control_mode", reason); if reason.ShouldFireExitCallback() && t.onExit != nil { t.onExit(...) } })`. Since `sync.Once` guarantees the closure body runs at most once across all 3 call sites, `session_lifecycle_ends_total{subsystem="tmux_control_mode",...}` now increments exactly once per generation regardless of which/how-many of the 3 sites observe the exit — the exact double-count mechanism the original Blocker described is gone. Task 3.1.1c's text explicitly states this supersedes "the prior draft's 'accepted, documented' double-count approximation."
- **Task 3.2.1a** (lines 958-974): the second, latent double-count the fix agent reported (a `defer lifecycle.EndGeneration(...)` at the top of `readControlModeOutput`, independent of the onExitOnce closures) is explicitly absent. The plan states directly: "Deliberately **no** paired `defer ... EndGeneration(...)` here — `span` is captured by the closures Tasks 3.1.1b/c/d pass to `t.onExitOnce.Do`, and one of those ... is the sole place `EndGeneration` is called for this generation. A second, independent `EndGeneration` call here would double-count the very metric Blocker A's fix exists to make single-count." Epic 3.2's own Story 3.2.1 goal and acceptance criteria (lines 925-954) restate the same constraint ("not by a second, independent defer... which would double the counter increment"), so the fix is stated consistently across both the task-level and epic-level text, not just asserted once and left unreinforced elsewhere.
- **Naming**: the call is `lifecycle.EndGeneration`, not `RecordEnd`, at all 3 sites — matches the fix agent's summary. `RecordEnd` is reserved for `ReconnectLoop`'s give-up branches (Task 2.2.1b), which never call `StartGeneration` and so have no gauge slot to release — a deliberate, correctly-justified split (Task 1.3.3b: "`RecordEnd` ... does **not** touch the gauge ... there is nothing for it to decrement").

## Over-correction check (no new blocker, no regression to "never recorded")
- The only path where a generation's end is now *never* recorded is a wedged/abandoned `readControlModeOutput` goroutine that never reaches any of the 3 `onExitOnce`-guarded sites at all. This is explicitly called out as intentional, not a gap: Story 3.2.1's acceptance criteria (lines 951-954) and Story 1.3.3's goal (lines 399-407) both state this is the exact signal `session_lifecycle_active_generations` exists to surface (mirrors the tymux side's `Story 2.2.2`, which has an end-to-end test proving the gauge stays elevated for the known-wedged-reader case). This is correct, not an over-correction — a truly-abandoned generation *should* look different from a cleanly-ended one, and the un-decremented gauge is that difference.
- No remaining double-count path was found: the tymux-side `Task 2.2.1b` `RecordEnd` calls in `ReconnectLoop`'s give-up branches use a *different* subsystem label (`"tymux_reconnect"`) from the enclosing generation's `"tymux_stream"` `EndGeneration` call, so they increment a distinct metric series rather than double-counting the same one.

## Gauge sanity check (Story 1.3.3 / Story 2.2.2)
No double-increment/decrement risk from the same call-site structure:
- Increment lives solely in `StartGeneration` (Task 1.3.3b), called exactly once per generation (once at the top of `readAttachLoop`'s wrapper for tymux; once at the top of `readControlModeOutput`, gated by the flag, for control_mode's Task 3.2.1a).
- Decrement lives solely in `EndGeneration` (Task 1.3.3b), which — per the Blocker fix above — is itself now called exactly once per generation for control_mode (via the shared `onExitOnce` closure) and exactly once for tymux (`readAttachLoop`'s wrapper calls it once, synchronously, after the goroutine function returns — no competing call site exists there since Epic 2.2 doesn't have the same 3-call-site structure that caused the control_mode bug).
- `RecordEnd` (Task 1.3.2c/1.3.3b) is explicitly documented to never touch the gauge, closing off the one other function that writes to `session_lifecycle_ends_total` from also double-touching the gauge.
- Not independently re-verified this iteration: whether `config.TmuxLifecycleV2Enabled()` is cached at process start vs. read live per-call. The plan reads the flag independently at 4 points in `control_mode.go` (once in Task 3.2.1a's entry gate, 3x in Task 3.1.2b's per-call-site branches) — if it's a live, uncached `os.Getenv` read (unconfirmed; the mirrored `STAPLER_SQUAD_USE_CONTROL_MODE` convention this is meant to copy was not found as a distinct helper function in the current codebase to check), a flag value changing between process start and generation end could in theory start the gauge but skip its `EndGeneration`-based decrement. This is speculative, not evidence-based, and out of scope for this iteration's check (env flags in this codebase are conventionally read once at startup, and no evidence was found suggesting otherwise) — flagged as a nitpick, not a blocker.

## Concerns
Carried forward verbatim from the previous review — not re-checked this iteration:
- [ ] Epic 1.1 (`session/lifecycle/reason.go`) + Epic 2.1 (`classifyStreamEnd`) + Epic 3.1 (`classifyControlModeExit`) — the shared `Reason` type spans two subsystems whose classifiers only ever produce disjoint subsets of its 6 constants (`classifyControlModeExit` never legitimately returns `ReasonDeliberateSupersede`, `ReasonCleanExit`, or `ReasonReconnectExhausted`; those are documented "tymux-only" in the Domain Glossary). Nothing in the type system prevents a future edit to `classifyControlModeExit` from returning one of those semantically-inapplicable values. **Remediation**: either (a) add a same-package test per subsystem asserting its classifier's return value is always drawn from an explicitly-named allowed subset, or (b) note explicitly in each classify function's doc comment which subset of `Reason` it may legally return.
- [ ] Epic 2.1, Task 2.1.1c (`session/tymux/stream.go`, `ReconnectLoop`'s `ok=false` branch) — introduces a second, freestanding classification decision (`if s.closing.Load() { ReasonDeliberateClose } else { ReasonReconnectExhausted }`) alongside `classifyStreamEnd`, checking the same `s.closing` signal in a separate function/location. Two independently-maintained "closing-check" sites can drift out of sync as new deliberate-stop causes are added. **Remediation**: route this branch through `classifyStreamEnd` itself, or at minimum add a doc comment on both functions cross-referencing each other.
- [ ] Epic 1.3/2.2/3.2 (`session/lifecycle/observability.go`, `session/tymux/stream.go`, `session/tymux/session.go`, `session/tmux/control_mode.go`) — subsystem labels (`"tymux_stream"`, `"tymux_reconnect"`, `"tmux_control_mode"`) are raw string literals repeated across at least 3 files with no shared constant or newtype. A typo variant would silently fragment the `session_lifecycle_ends_total` metric's cardinality with no compiler or linter catch. **Remediation**: define exported constants (or a small `type Subsystem string`) in `session/lifecycle`.

## Nitpicks
Carried forward verbatim from the previous review, plus one new item from this iteration:
- `session/lifecycle` bundles four only-loosely-related concerns in one package: the `Reason` closed enum, OTel observability plumbing, a generic `AwaitBounded` channel-wait helper, and a generic `IsBenignTimeout` error classifier. Low cost to leave as-is given the total package size (~150-250 LOC per ADR-001), but worth a one-line package doc comment explaining the grouping rationale.
- Pattern Decisions table already considered and rejected an unexported-field-gated `Reason` in favor of matching `DetectedStatus`'s existing plain-`iota` convention. Reasonable, already-justified trade-off — flagging only for visibility: `lifecycle.Reason(999)` remains constructible by any caller.
- Task 2.2.1a's context-derivation through `telemetry.StartLinkedBackgroundSpan` (does the returned `genCtx` still observe the same `ctx.Done()` for `classifyStreamEnd`'s `ctx.Err()` check?) is called out by the plan itself as needing `-race` verification before merging — good self-awareness, just flagging that this should block Phase 2's merge if the assumption doesn't hold.
- The `.golangci.yml` `exhaustive` carve-out mechanism (a growing chain of single-character negative-lookahead path regexes) is pre-existing tech debt, not introduced by this plan — but Task 1.2.1a doubles its length again. Out of scope to fix here, but worth a follow-on note if the pattern recurs a third time.
- **New (this iteration)**: `config.TmuxLifecycleV2Enabled()` is read independently at 4 separate points across `control_mode.go` (Task 3.2.1a's entry gate, plus Task 3.1.2b's 3 per-call-site branches) rather than cached once per generation. If the underlying read is a live, uncached `os.Getenv` (not confirmed — no existing `UseControlMode`-style helper was found in the current codebase to check the convention against), a flag change mid-flight could in theory decouple a `StartGeneration` gauge-increment from its would-be `EndGeneration` decrement. Speculative and likely moot if the flag is cached at startup like other env-var flags in this codebase, but worth a one-line confirmation during implementation review rather than assuming.
