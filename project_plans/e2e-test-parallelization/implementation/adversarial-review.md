## Resolved in repair iteration 1

- [x] **Story 3.1.1's `fullyParallel: true` flip changes `--shard`'s splitting *granularity* from whole-file to individual-test, which the plan treats as a pure within-job no-op.** Confirmed via multiple Playwright community sources (Currents' "Fully Parallel Mode" guide, bug0.com's sharding guide): with `fullyParallel: false` (today's setting, `tests/e2e/playwright.config.ts:59`), `--shard=N/M` assigns whole files to shards, so every test in a file always lands in the same CI job. With `fullyParallel: true`, the shardable unit becomes the individual test, so a single file's tests can be split across *different* shard jobs — i.e., different `TestServer` instances — even though `workers: 1` (`playwright.config.ts:65`) is unchanged. The plan's own Domain Glossary entry and Story 3.1.1's narrative ("a no-op on actual concurrency... it changes `--shard`'s balancing granularity from file-count to test-count") correctly names the mechanism but misjudges its blast radius: the risk isn't in-job concurrency, it's cross-job test redistribution. This directly undercuts `research/architecture.md` §5's own safety argument for the 54 files (28% of the 193-spec suite) that use file-scoped `beforeAll`/`afterAll` — that argument explicitly rests on "safe under worker-per-file assignment, **the same granularity job-level sharding already uses**." Story 3.1.1 removes that premise. Phase 4's triage (Story 4.1.1) then builds its "priority" sample *on top of* this now-shaky "safe" categorization, compounding the risk. Neither Story 3.1.1 nor 3.1.2's acceptance criteria check for new test failures/flakiness from file-splitting — they measure only shard-duration spread.
  **Recommendation**: Before merging Story 3.1.1, add an acceptance criterion comparing the comparator's pass/flaky/fail findings before vs. after the flip (zero new `severity: "fail"` findings allowed — see `scripts/e2e-baseline-compare.ts`), and re-check whether any of the 54 flagged files actually got split across shards post-flip (diffable from the per-shard JSON reports' file/project lists). If splitting does occur and any affected file's `afterAll` assumes all of that file's tests ran in the same process, that file needs `test.describe.configure({ mode: 'serial' })`-equivalent protection or explicit exclusion before the flip ships.
  **RESOLVED**: Story 3.1.2 (`plan.md:216-237`) now carries both fixes as explicit go/no-go gates, not observations. AC3 (`plan.md:223-224`) requires running `scripts/e2e-baseline-compare.ts` (confirmed present at that path on `origin/main`) against the post-flip CI run via `gh run view <new-run-id> --log | grep -A5 "Run the baseline comparator"`, stating "any new `fail`-severity finding is this story's go/no-go blocker, not a follow-up to triage later." AC4 (`plan.md:225-226`) requires re-deriving the 54-file `beforeAll`/`afterAll` pool (count reconfirmed live — `research/architecture.md` §5 states 54/28%, matching the original finding) against the merged per-shard JSON report (`tests/e2e/all-blobs` → `report.json`, confirmed as the real merge path at `build.yml:456-461` on `origin/main`), producing a "file: shard indices observed" table for all 54 files with a mandatory per-file "safe because `<reason>`" or "needs `test.describe.configure({ mode: 'serial' })` / exclusion" verdict for any file that split — "An unreviewed split file blocks the merge; it is not an acceptable known-gap." Both checks feed one shared Rollback trigger (`plan.md:228`: "revert Story 3.1.1's `playwright.config.ts` commit immediately"), and Task 3.1.2a (`plan.md:231-237`) implements both in the same CI-validation pass. This is a real stop/revert gate, not a measured-but-advisory check.

- [x] **Story 3.2.1 (browser-install isolation) will very likely break `e2e-bun`'s own comparator step on the first real CI run — traced end-to-end through the actual comparator source, not inferred.** `tests/e2e/baseline/next-e2e-baseline.json` carries 2 `desktop-firefox`, 2 `desktop-webkit`, and 2 `webkit-mobile` baseline-class-"pass" spec entries (confirmed by direct grep). After Story 3.2.1 ships: the 20 gating shard jobs stop installing Firefox/WebKit, so `webkit-mobile`'s activation gate (`fs.existsSync(webkit.executablePath())`, `playwright.config.ts:9-20`) silently returns `false` there; and the new `e2e-secondary-browsers` job, per Task 3.2.1b's own text, is instructed to run only `desktop-firefox`, `desktop-webkit`, and the *differently-gated* `mobile-webkit` project (`process.env.PW_WEBKIT === '1'`, `playwright.config.ts:160`) — `webkit-mobile` (a distinct, similarly-named project, `testMatch: '**/mobile-webkit.spec.ts'`) is never mentioned anywhere in the plan. Net effect: all 6 of those baseline-tracked specs vanish from both `e2e-next`'s and `e2e-bun`'s merged JSON reports. Tracing `evaluateBaselinePassSpec` in `scripts/e2e-baseline-compare.ts`: for a baseline-"pass" spec with zero attempts in the bun report, `failCount` becomes 1 (an empty attempts array is treated as a failure by `failedOrRetried`); `sharedFlake` then evaluates `ctx.nextAttempts.get(ks)` as `undefined` (also missing), and the ternary's false-branch (`: false`) is taken rather than correctly computing "next is also missing, so this is shared, not Bun-only" — so the code falls through to the final branch and returns `severity: "fail"` ("New Bun-only failure... e2e-next clean"). `exitCode` is 1 whenever any finding has `severity === "fail"`. This is the exact "gate breaks immediately post-merge" failure shape as #1165/#1166 (which this session's own requirements.md explicitly asks the plan to avoid repeating), just via a different code path — the comparator's missing-spec handling, not `DEFAULT_MEMBERS`. Story 3.2.1's own acceptance criterion for "no side-effect dependency is silently dropped" only runs `grep -n "firefox\|webkit" .github/workflows/build.yml` inside the two edited job blocks — a same-file textual check structurally unable to see this cross-file (`playwright.config.ts`'s dynamic project list) and cross-job (baseline JSON / comparator) effect.
  **Recommendation**: Before merging, either (a) have `e2e-secondary-browsers` also run the `webkit-mobile` project and upload a `--reporter=blob` artifact named to match the `e2e-next-blob-*`/`e2e-bun-blob-*` download patterns so all 6 specs' results still reach the merge/comparator pipeline, or (b) deliberately remove those 6 entries from `next-e2e-baseline.json` in the same PR as an explicit, called-out coverage-tracking change. Either way, add an acceptance criterion that runs the comparator (locally or via the PR's own CI) and confirms zero new `fail`-severity findings relative to the pre-change baseline — Story 3.2.2's current criteria check job timing and `DEFAULT_MEMBERS`/`needs:` mechanics only, never the comparator's actual output.

## Concerns

- [ ] Story 3.1.2 / 3.2.2's CI-validation acceptance criteria measure proxies (shard-duration *spread*, install-*step* duration) rather than requirements.md's literal Success Metric: "measured wall-clock for `e2e-next`/`e2e-bun` to reach a final verdict... drops." Neither story records the absolute slowest-shard-to-final-gate-verdict time before/after. — Add that direct before/after measurement to both validation stories, alongside the spread/step-duration numbers already planned.
- [ ] No acceptance criterion anywhere in the plan checks `route-coverage-manifest.ts` for a coverage drop, despite requirements.md naming it explicitly as a guardrail and Story 3.2.1 being the one change most likely to affect it (per the blocker above). — Fold a `route-coverage-manifest.ts` check into whichever remediation is chosen for the browser-install-isolation blocker.
- [ ] The plan asserts rollback is mechanically trivial (`git revert`) but never states the *trigger* for using it — no story says "if the comparator shows N new fail-severity findings vs. the pre-change run, revert," only that reverting is cheap if someone decides to. Given the blocker above shows a concrete, traceable path to a silent-until-the-comparator-exits-1 regression, each Phase 3 story should name its own specific revert trigger, not just the revert mechanism. — Add one line per Phase 3 story: the signal that would make Tyler or a reviewer actually pull the trigger.
- [ ] Phase 4's sample-selection methodology (Story 4.1.1) draws its entire 20-file "priority" sample from the 54-file "file-scoped `beforeAll`/`afterAll`" pool, picking the *largest* files by line count. A large file in that category plausibly correlates with *heavier* backend/session setup (more reason the `beforeAll` exists at all) — which may anti-correlate with "doesn't need a real backend," the opposite of the stated rationale ("more to gain... more to lose"). The plan doesn't acknowledge this competing hypothesis or include any file outside the 54-pool as a counterexample/sanity check. Not a blocker since the output is a reviewed list Tyler signs off on, not an applied conversion — but worth a one-line methodology caveat in the finding note itself.
