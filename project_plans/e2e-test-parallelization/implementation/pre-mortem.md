# Pre-mortem: e2e-test-parallelization
**Date**: 2026-10-25

Scope note: `adversarial-review.md` and `architecture-review.md` already found and the final `plan.md` already fixed the two structural blockers (the `fullyParallel` shard-granularity/beforeAll-split risk, and the browser-install-isolation baseline/comparator drop) plus their follow-on concerns (wall-clock-to-verdict measurement, `route-coverage-manifest.ts`, revert triggers, the sample-bias caveat, the `gh api /user` fallback, the `DEFAULT_MEMBERS` regression test). Those are not repeated below. This pre-mortem covers five different failure modes, concentrated in Phase 2, Phase 4, Phase 5, and the staging/effort-estimate decisions, that neither review's brief was scoped to catch.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Phase 4's 20-file candidate list ships as a static markdown note with no review mechanism attached, so the suite's content question is procedurally "closed" but never actually acted on. | Weeks later, `test-content-triage-sample.md` has zero git history after its creation commit, and no backlog item or follow-up PR references it — Tyler has no reminder it exists. | Task 4.1.1c should create a backlog item (`mcp__stapler-squad__create_backlog_item`) or `schedule_wake` pointing at the finding note, instead of just writing "flag for owner review" prose with no delivery mechanism. | P2 |
| 2 | Story 2.2.1's `bun install` timing comparison runs on a local developer machine (warm/cold disk cache, different CPU, no network-throttled runner), not an actual `ubuntu-latest` GitHub Actions runner, so the go/no-go verdict doesn't necessarily transfer to the CI environment the decision is actually about. | A future story proposing a `bunfig.toml` change gets waved off citing this spike's "no-go" verdict, and nobody checks it was measured on a laptop. | Amend Task 2.2.1a to run the timed comparison inside a real CI job (a `workflow_dispatch` spike run, or piggybacked on one of the Phase 3 branches' own CI run), or explicitly caveat the finding note: "measured locally; CI environment may differ, re-verify before relying on this for a future decision." | P3 |
| 3 | Story 3.1.1 (`fullyParallel: true`) and Story 3.2.1 (chromium-only installs + `--project` filters) are deliberately staged as independent branches/PRs off `origin/main`, each validated alone on its own CI run — but 3.2.1 changes which/how-many tests exist per shard, which directly interacts with 3.1.1's test-count-based shard balancing. The combination is first exercised live on `main`, not in either PR's CI run. | A PR opened after both land shows new shard-duration skew or flakiness that neither individual CI validation predicted; "independently revertible" doesn't mean "independently correct," so reverting one doesn't necessarily fix a combination-only regression. | Add a task requiring one CI run on a branch carrying both diffs stacked (either right before the second PR merges, or as a follow-up check right after) that re-runs the same comparator + shard-duration-spread checks Story 3.1.2/3.2.2 already define — not just each change validated in isolation. | P2 |
| 4 | Phase 5 defers the one lever the plan itself calls "highest-potential-value" (the N-server rearchitecture) to a doc-only artifact with zero forcing function to resume it — no backlog item, no re-review date, no checkpoint tied to whether Phase 3's incremental wins (shard-spread tightening, ~30-45s/shard browser-install savings against a 25-40 min shard) actually move the literal Success Metric ("wall-clock... drops... noticeably faster"). The project can be called "done" by this plan's own criteria while the underlying "CI still feels slow" problem remains essentially unsolved. | Months after this project ships, a contributor still complains `e2e-next`/`e2e-bun` is slow, and nobody connects it back to `docs/explanation/e2e-per-worker-server-seam.md`. | After Phase 3's CI validation data lands, add an explicit go/no-go checkpoint comparing the realized wall-clock delta against requirements.md's Success Metric, and record the decision (new backlog item or ADR amendment) on whether Phase 5's seam gets scheduled next — rather than leaving it a dangling "future implementer" document with no owner or trigger. | P1 |
| 5 | Stories 3.1.2/3.2.2's go/no-go gates check only for new `severity: "fail"` comparator findings. A spec that goes from solid-pass to flaky-but-eventually-passing (now redistributed to a different shard/job, or racing a file-scoped `afterAll` against a different TestServer instance) surfaces as `severity: "flaky"`, which the plan's own acceptance criteria explicitly do not block on. | Within the first month, the comparator's flaky-classification count on `main` creeps up relative to the pre-flip baseline, noticed only incidentally during an unrelated PR — the exact chronic-noisy-gate pattern this session's #1165/#1166 incidents were trying to get away from. | Add an AC to Story 3.1.2 (and 3.2.2) that diffs the comparator's `flaky`-severity count before vs. after, with a numeric threshold (e.g., "no more than N new flaky-classified specs") as part of go/no-go, not just zero-`fail`. | P2 |

## P1 Items (address before implementation)
