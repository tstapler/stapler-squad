# Feature Landscape Research: e2e-test-parallelization

## 1. Industry landscape: per-worker backend isolation for stateful Playwright suites

**Finding: "one full server process per worker" is not the common, proven pattern for a heavy, stateful backend. The proven pattern is one shared backend + per-worker *logical* isolation.**

- **Kibana Scout** (Elastic) is the clearest real-world precedent for a Playwright suite backed by a heavy stateful server (Kibana + Elasticsearch, directly analogous in weight to this repo's Go binary + DB + tmux). Scout runs **one** shared Kibana/Elasticsearch deployment for the whole run and gives each worker an isolated **Kibana Space** via a worker-scoped fixture, torn down when the worker finishes. Scout explicitly does *not* extend this per-worker isolation to API tests — those isolate themselves via unique resource names per worker instead. [Kibana Scout parallelism docs](https://www.elastic.co/docs/extend/kibana/testing/parallelism), [Kibana Scout fixtures](https://www.elastic.co/docs/extend/kibana/testing/fixtures)
- Playwright's own worker-identity primitives exist for exactly this kind of isolation: `testInfo.workerIndex` (monotonically increasing, a restarted worker gets a **new** value — never reused) vs `testInfo.parallelIndex` (stable in `[0, workers)` across restarts). [Playwright `WorkerInfo` docs](https://playwright.dev/docs/api/class-workerinfo)
- Where teams *do* spin up a real per-worker server process via a worker-scoped fixture deriving a port from the worker index (`4000 + workerInfo.workerIndex`, or `8907 + workerInfo.workerIndex * 4` reserving a port range), the backend in every example found is a **lightweight mock/stub** (an Express server, an MSW-style HTTP double) — not a full app server with DB + process-manager state. [qaskills.sh worker-scoped fixture example](https://qaskills.sh/blog/playwright-worker-scoped-fixture-database-per-worker), MCP Playwright `fixtures.ts` example on glama.ai.
- Nobody found runs this at the scale/weight of stapler-squad's backend (Go binary cold boot ~30-45s per `test-server.ts`'s own comment, plus DB seed, plus a private tmux server). The closest adjacent finding (Depot CI engineering blog) is about a **different** axis of the same cost problem: fixed per-job setup cost (checkout, deps, browsers, seed data) multiplying linearly with shard count — directly matching this project's own "fixed per-shard overhead" rabbit hole, not the in-process-worker question. [Depot: accelerating test suites](https://depot.dev/blog/accelerating-test-suites)
- A documented gotcha for anyone using `workerIndex`-derived ports: because it keeps increasing across restarts (e.g. after a retried/crashed worker), a long or flaky run can drift to unexpectedly high port numbers, and a crashed worker's old server process may still be holding its old port. `parallelIndex` is the safer key for a fixed port-range scheme. None of the community examples found actually guard against this.

**Verdict for this repo:** "N full server instances, one per Playwright worker, inside one CI job" is a real but *unproven-at-this-weight* pattern. The better-attested comparable (Kibana Scout) argues for sharing fewer, heavier server instances and isolating *state* per worker (unique session/test-data namespaces against one running server) rather than isolating *processes*. This directly informs the plan-phase go/no-go the requirements ask for — the research should not treat "spin up N TestServer instances" as low-risk just because the env-var/port-indirection mechanics are simple; the mechanics are simple, but running N copies of *this specific* heavy backend concurrently on a shared CI runner is the part with no proven analog.

- [Kibana Scout — fixtures](https://www.elastic.co/docs/extend/kibana/testing/fixtures)

## 2. Edge cases for "N server instances per CI job" — specific to `TestServer`/`global-setup.ts`

Read `tests/e2e/helpers/test-server.ts` and `tests/e2e/global-setup.ts` in full. Findings, in order of how badly each would break with N concurrent instances in one process:

| Resource | Current scoping | N-instance safe? |
|---|---|---|
| Port | `findFreePort()` per instance (OS-assigned ephemeral port, `port: 0` default) | **Yes, already safe.** Each `TestServer.start()` independently asks the OS for a free port. |
| tmux socket | `tmuxSocket()` returns `` `ssq-e2e-${this.config.port}` `` — derived from the port, not a fixed name | **Yes, already safe**, *because* it piggybacks on the already-safe port. This already matches the isolation pattern CLAUDE.md documents for concurrent manual dev instances (unique `STAPLER_SQUAD_TMUX_SOCKET` per instance, port-paired by convention) — see `CLAUDE.md`'s "Manual dev port block." |
| **Test data dir** | `config.testDir \|\| process.env.TEST_SERVER_DIR \|\| \`/tmp/stapler-squad-test-${process.pid}\`` | **No — real collision.** `process.pid` is the *global-setup Node process's* PID, identical for every `TestServer` instance it constructs. N instances spawned from one `global-setup.ts` process would compute the **same** `testDir`, and `start()`'s `cleanupTestDir()` (`rm -rf` the dir, then recreate) would race-delete a sibling instance's live DB/session state mid-run. Needs a `parallelIndex`-style discriminator added to the default, not left as PID-only. |
| **Binary copy dir** (`ensureBinary()`) | `path.join(os.tmpdir(), 'stapler-squad-e2e-bin', String(process.pid))` | **No — same bug class.** Also PID-scoped only; N instances would compute the same `binDir` and race on `fs.promises.copyFile`. |
| **`make stapler-squad` build itself** | `ensureBinary()`'s own comment: *"The Makefile target always writes to the single repo-root path, which every concurrent e2e run / manual instance in this (shared, non-worktree-isolated) checkout would otherwise spawn from directly."* The existing PID-scoped copy-after-build is the mitigation **for separate OS processes** (e.g. two manual instances), not for N instances built serially/concurrently from the *same* `global-setup.ts` process. | **No.** N `TestServer.start()` calls, each independently calling `execPromise('make stapler-squad', ...)`, would race N concurrent rebuilds of the one repo-root binary before each copies its own snapshot out. A per-job build must run **once**, then be copied N times — the current code has no such single-build-then-fan-out step; it assumes exactly one `ensureBinary()` call per process. |
| **Seeding cost** (`seedDemoData`, `seedHiddenSession`, `seedLiveSessions`) | Each shells out to `go run ./tests/demo/seed ...` / `go run ./tests/e2e/seed-hidden ...`; `seedLiveSessions` additionally sleeps a flat 12s waiting for the review-queue poller (2s poll interval, 5s idle threshold) | **Multiplies, doesn't parallelize for free.** This is a fixed per-instance wall-clock tax (the 12s sleep especially) that N instances pay independently — can run concurrently across instances, but doesn't shrink per-instance, so "N servers" buys parallel *test* execution but not a cheaper *startup* critical path if anything serializes the N startups. |
| **Cold-boot budget** (`waitForServer(maxAttempts = 90)`) | Comment: *"on this machine a cold test-mode boot... has been observed taking ~30-45s... right at the old 30s cap."* Already a tight margin **under single-server load**. | **Risk, not a hard break.** N servers cold-booting concurrently on a shared-CPU CI runner (GitHub-hosted public-repo Linux runners are 2-4 vCPU) contend for the same cores; several could plausibly exceed the already-tight 90s budget on first touch, producing a startup-flaky `global-setup`, not a test-content-flaky one. |
| **Singleton server + teardown wiring** | `let globalTestServer: TestServer \| null` (module-level singleton), `getGlobalTestServer()`, `startGlobalTestServer()`, `stopGlobalTestServer()` — all hardcoded to exactly one instance; `global-teardown.ts` calls `stopGlobalTestServer()` unconditionally | **No — structural, not incidental.** This whole module assumes 1:1 (process ↔ server). Supporting N means this singleton becomes a map/array keyed by `parallelIndex`, and teardown must iterate it. Any other call site that imports `getGlobalTestServer()` directly (not checked exhaustively here — flag for the architecture/plan phase to grep for) would also need updating. |
| **Per-worker env propagation** | `global-setup.ts`'s own comment (lines 15-16): *"process.env mutations here are inherited by Playwright worker processes"* — this is a **single** broadcast value (`TEST_SERVER_URL`, `TEST_SERVER_TESTDIR`) seen identically by every worker today. | **No — needs new plumbing.** N servers means N different base URLs/test dirs, but `process.env` set once in `global-setup` can't vary per worker. This requires either a worker-scoped fixture that picks its own server's info keyed by `testInfo.parallelIndex` (reading from a small lookup file/array `global-setup` writes, since `getGlobalTestServer()`'s live singleton is "NOT reachable from worker processes" per the existing comment at `global-setup.ts:20-22`), or moving server startup into a worker-scoped fixture entirely rather than `global-setup`. |
| `remote-workspaces.spec.ts`'s per-run sshd | Deliberately started in a file-scoped `beforeAll`/`afterAll`, *not* in `global-setup`, specifically because a single global sshd shared by multiple projects hitting the *same* server would only show the TOFU host-key dialog to the first project to connect (documented in `global-setup.ts`'s own comment, lines 26-33) | **Already N-aware in spirit.** This spec already had to solve "one shared resource breaks a test that needs fresh per-run state" — it's a precedent *for* per-worker/per-project isolation elsewhere in the suite, and a model to follow (file-scoped lifecycle keyed to the consuming spec) if full per-worker server isolation turns out too costly to do globally. |

**Net read:** port and tmux-socket isolation are free (already correct by construction); test-dir, binary-dir, the build step, and the singleton/env-broadcast wiring are **not** — they were written assuming exactly one instance per process and will silently corrupt/race with N, not fail loudly. This matches the requirements.md "Feasibility Risks" warning to verify, not assume, that per-worker servers are safe.

## 3. Unstated needs beyond "make it faster"

- **CI cost / concurrency-slot pressure, not $ cost.** Public-repo GitHub Actions minutes are free, but the requirements already flag "generous... but not unlimited" Actions concurrency. The real unstated need is: total **concurrent job/runner-slot consumption** stays bounded, since every one of the 20 shard jobs (10×2 for `e2e-next`/`e2e-bun`) each separately repeats Go setup, `bun install`, Playwright browser install, and (for `e2e-bun`) a full `make stapler-squad` build — fixed overhead that scales *linearly* with shard count even though wall-clock plateaus at the slowest shard. More shards past the point of diminishing wall-clock return is pure waste of concurrency slots and queue time for other PRs, which the owner would feel as "my unrelated PR's CI is queued," not as a dollar bill.
- **Reliability — more shards is more failure surface, already bitten once.** The owner's own #1165/#1166 saga this session hit a "chronic-red-gate bug" from shard-membership semantics. This is concrete prior evidence (not speculation) that touching shard count/shape again carries real regression risk independent of wall-clock gains — any further shard-count change should be weighed against this, and validated with the same rigor (multiple full CI cycles) the Risk Control section already calls for.
- **Debuggability — a latent "don't regress this" need.** The requirements' Observability section states today's per-shard-job Actions-UI visibility is "sufficient" — i.e., no current complaint, but also no slack to spend: 10 clean per-shard logs are easier to root-cause than one. If the plan pursues in-process `fullyParallel`/multi-worker inside a single job, worker output interleaves in one log stream by default — a real, concrete regression risk to debuggability that the requirements don't explicitly name but that the "no regression in what the suite verifies" success metric implicitly covers (a failure that's harder to attribute isn't actually verified the same way). Flag this explicitly to the plan phase as a cost of the in-process-parallelism path specifically, separate from the server-isolation risk.
- **Fits the existing isolation mental model.** The owner has invested repeatedly (CLAUDE.md's "Manual dev port block," multiple `project_plans/*` manual-verification sections) in a specific "isolated, nameable, cleanly-torn-down instance" pattern (`STAPLER_SQUAD_INSTANCE`, `STAPLER_SQUAD_TMUX_SOCKET`, numbered port blocks, never touch `:8543`). Whatever lands here should extend that existing vocabulary (e.g., `parallelIndex`-scoped instance names/ports) rather than invent a parallel, one-off isolation scheme just for CI.
- **Explicit validation-cost budgeting, already named but worth restating.** requirements.md's Rabbit Holes section already asks the plan to budget for an iterative, CI-cycle-expensive validation process for the shared-server rearchitecture (mirroring #1165/#1166 and Stories 7.10/7.11). This is itself evidence of an unstated-but-now-stated need: the owner wants that cost acknowledged up front, not rediscovered mid-implementation the way shard-membership bugs were.

## 4. Prior art: `project_plans/isolated-dev-stacks/research/architecture.md` (lines ~130-228)

This is a **different** problem (an opt-in, interactive dev-mode Playwright config that drives a *dual-process* dev stack — Go backend + `next dev` frontend — for live development, not CI throughput), but its conclusions bear directly on this project's "shared-server rearchitecture" question:

- **Orchestration shape it recommends:** a single parent process (Node or Go) that spawns/supervises children, explicitly **modeled on `tests/e2e/helpers/test-server.ts`'s `TestServer` class** (allocate port → spawn child with env → wait-for-ready → own teardown), just extended to supervise two children instead of one. This endorses `TestServer`'s existing shape as the right building block to extend — relevant precedent if this project's plan also extends it to N instances.
- **Explicitly rejected a parameterized single config/global-setup.** It considered, and rejected, branching the *existing* `playwright.config.ts`/`global-setup.ts` on a mode flag to support the dual-process dev stack. Its stated reasoning (quoting the architecture doc directly): `playwright.config.ts`'s `use.baseURL` and `global-setup`'s server lifecycle are **"single-server-shaped by construction"** (one `TestServer` instance; the `baseURL` comment literally says "dynamically assigned by global-setup"); branching all of that inside one file is **"more invasive"** than a second small config; and critically, a separate config keeps the **default `npm test` run's latency and behavior completely unchanged** — serving the requirement that the new mode stay strictly opt-in with zero cost to the default path. It therefore recommended a wholly separate `playwright.dev-mode.config.ts` + `global-setup.dev-mode.ts`.
- **Direct implication for e2e-test-parallelization:** if the plan phase decides to pursue "N servers per job, true in-process `fullyParallel`," this same precedent argues for landing it as a **separate** config/global-setup (not a mode-flag branch inside the existing single-server `global-setup.ts`/`TestServer` singleton) — which also lines up with this project's own Risk Control section ("stage it behind its own PR, separate from... safer wins"). Two independent sources (the isolated-dev-stacks architecture decision, and this project's own risk-control instinct) converge on the same shape: don't make the default single-server path carry a branch for a mode most runs won't use.
- **Reusable sub-finding on env propagation:** isolated-dev-stacks concluded that per-instance config (port, data dir, instance name) should be passed via **env vars injected directly into each child process's environment**, not a shared file both sides parse — "avoids a file-parsing race." This doesn't fully solve the Playwright-specific wrinkle this project has (the consumer of per-instance config is a **worker process** that needs to discover *its own* server's info out of N, keyed by `testInfo.parallelIndex` — not a sibling process that gets one fixed env block), but the "env vars over a shared parsed manifest" principle still applies to however `global-setup` hands each worker its slice of a small, `parallelIndex`-keyed lookup.
- Also notable: isolated-dev-stacks concluded `STAPLER_SQUAD_INSTANCE=<name>`-based data-dir isolation is "already solved" and needed no new Go-side mechanism — confirms the Go side's existing instance/data-dir isolation primitives are reusable building blocks for N-server test-dir scoping too, beyond just the port/tmux-socket pattern already covered in §2.
