# Research: UX for Session Notes

Source requirements: `project_plans/session-notes/requirements.md`

## 1. Comparable UX patterns

| Tool | Placement | Edit affordance | Relevant takeaway |
|---|---|---|---|
| **This repo's own `GoalPanel`** (`web-app/src/components/sessions/GoalPanel.tsx`) | Inline in the detail view's Info tab, below session metadata (`SessionDetailView.tsx:1246-1249`), inside a native `<details>`/`<summary>` disclosure | Read-only (goal is set via MCP `set_session_goal`, not edited in the UI) | Establishes the precedent placement slot for session-scoped "extra context" panels — directly under the info block, not a separate tab. Session Notes should follow this same slot for consistency, not invent a new tab. |
| **This repo's `DescriptionSection`** (`web-app/src/components/backlog/detail/DescriptionSection.tsx`) | Collapsible section (`CollapsibleSection`) | Read-only render via `ReactMarkdown` + `remarkGfm`, editing happens in a separate form (`BacklogItemForm.tsx`, plain `<textarea>`) | Confirms this repo's established pattern for markdown fields: **render and edit are separate UI surfaces**, not a live-preview split pane. Session Notes should follow suit — a read (rendered) mode and a distinct edit (textarea) mode, not both visible simultaneously. |
| **This repo's inline-editable metadata fields** (`SessionDetailView.tsx` — `isEditingProgram`, `isEditingWorkingDir`, `isEditingCategory`, `isEditingTags`, lines 202-226, 889-1005) | Inline, in place | **Explicit edit-mode toggle**: a display span + pencil/click target that swaps to an input on click, swaps back on save/cancel | This is the app's dominant, repeated convention for "click to edit, click away or Save to commit." Session Notes should reuse this exact interaction model (click note body/an "Edit" button → textarea appears → Save/Cancel → back to rendered markdown) rather than introducing a new interaction pattern (e.g. always-editable textarea, or a modal). |
| **Linear** (issue "Description" field) | Inline, top of the issue detail pane, no separate tab | **Always-editable inline** — the rendered markdown *is* the editor; clicking anywhere in the text drops you into edit mode at the cursor position (rich WYSIWYG-over-markdown), no explicit Save button — it autosaves on blur/debounce | Illustrates the "no mode switch" alternative. Not recommended here: this repo has no rich-text/WYSIWYG editor dependency, and every other note-like field in this codebase uses the explicit-toggle model — matching Linear would be inconsistent with the rest of the app and a bigger lift (would need a WYSIWYG markdown editor library, not just `react-markdown` for display). |
| **GitHub Issues sidebar** (no free-text "notes," but the comparable "Notifications"/"Development" sidebar widgets) | Sidebar, not a tab | N/A — mostly structured, not freeform | Less relevant as a direct analog since GitHub doesn't have a per-issue freeform sidebar note; closer analogs are the issue body itself (edit pencil icon top-right → full-width textarea replaces the rendered body, Save/Cancel below) — this is functionally identical to Linear's not-quite-inline pattern but *with* an explicit edit button, closer to this repo's convention. |
| **VS Code** (no native pinned per-file notes; closest analogs are `TODO`/`FIXME` comment highlighting via the "Todo Tree" extension, or the "Comments" API used by GitHub Pull Requests extension) | Gutter icon / inline decoration, opens a small popover editor anchored to the line | Popover with textarea, explicit Save (Ctrl+Enter) / Cancel (Esc) | The gutter-icon-as-indicator-and-entry-point pattern is the closest analog to "SessionCard shows a lightweight indicator" — a small icon that both signals presence and is the click target to open the note. Session Notes should give the `SessionCard` note indicator the same dual role: visible presence signal *and* (if session card click already opens session detail) an affordance that scrolls/expands directly to the note. |
| **herdr-web** (`PaneNote` model, referenced in requirements as the out-of-scope superset) | Per-pane, multiple titled notes, with `expected_revision` optimistic-concurrency guard | Explicit CRUD (create/edit/delete each note) | Confirms the requirements doc's own scoping decision is sound: herdr-web's model solves a harder problem (multi-pane, multi-note, concurrent editors) this single-user tool doesn't have. A single markdown field with last-write-wins is the right-sized subset — no auth/concurrency conflict is possible when only one browser tab is realistically editing a given session's note at a time (still worth a plain "save failed, your local edit is preserved" toast rather than a revision-conflict UI; see §4). |

**Recommendation**: reuse the explicit edit-mode toggle already established by `SessionDetailView.tsx`'s `isEditing*` fields, render with `ReactMarkdown`/`remarkGfm` styled via the existing `markdownBody` vanilla-extract class (`web-app/src/components/backlog/markdownBody.css.ts` — reusable as-is or as a copy-and-adapt base for a session-scoped equivalent), and place the panel in the same Info-tab slot as `GoalPanel`, immediately adjacent to it (`SessionDetailView.tsx:1246-1251`, right before or after `<WorkspacePeersPanel>`).

## 2. User mental model: Notes vs. Goal vs. Description

The repo already has **three** distinct "long text about a session/item" concepts a user could confuse:

1. **`session_goal`** (`SessionGoalSummary`, surfaced via `GoalPanel.tsx`, set via the `set_session_goal`/`get_session_goal` MCP tools) — this is **agent-facing and machine-set**: the *agent* declares what it's working toward, plus a structured task tree (`tasksJson`, `tasksDone`/`tasksTotal`) and a status enum (`idle`/`working`/`blocked`/`done`). It answers "what is the agent currently doing," and a user cannot edit it directly in the UI — it's read-only in `GoalPanel` (confirmed: no `isEditing` state, no textarea, no save handler in `GoalPanel.tsx`).
2. **Backlog item `notes`/`description`** (`session/ent/schema/backlog_item.go:72`, `DescriptionSection.tsx`) — this is **task-planning content tied to a backlog item**, i.e. pre-work scoping, not tied to a live/parked session at all. A backlog item can exist with no session yet, or outlive several sessions that work on it.
3. **New: Session Notes** (this feature) — **user-facing and user-set**: freeform scratch space the *human* attaches to one specific running/parked session instance, e.g. "left this waiting on X," "spike, don't merge." It answers "what do *I* need to remember about this session," independent of what the agent is doing or what the backlog task says.

**Confusion risk and mitigation:**
- The biggest risk is `session_goal` vs. `Notes` — both are freeform-ish text blocks that could sit near each other in the Info tab. Mitigate by:
  - Distinct, unambiguous labels: "Goal & Tasks" (existing, `GoalPanel`'s `summaryLabel`, `GoalPanel.tsx:125`) vs. "Notes" — do not call the new feature "Description" or "Details," which would read as a synonym for Goal.
  - Visual distinction: `GoalPanel` has a status chip (`idle`/`working`/`blocked`/`done`) and task-progress fraction that Notes must NOT mimic — Notes has no status semantics, it's pure freeform text. Keep Notes' rendered body plain (no chip/badge inside the panel itself, other than the SessionCard indicator).
  - Editability as the clearest differentiator: Notes has a visible "Edit" affordance; Goal does not (it's agent-only). Making Notes' edit button prominent signals "this one's yours to write," Goal's absence of one signals "this one's the agent's."
  - Empty-state copy should reinforce the distinction, e.g. "No notes yet — leave yourself a reminder about this session" rather than generic "No content."
- Backlog-item notes vs. session notes are less likely to be confused since they appear in entirely different views (`BacklogItemDetail` vs. `SessionDetailView`), but if a session was created *from* a backlog item, consider whether the backlog item's notes should be visible/linked from the session view for cross-reference — out of scope per requirements' non-goals, but worth flagging: the requirements doc's Problem section already anticipates this distinction explicitly ("that's task-planning notes tied to a backlog item, not a running/parked session"), so no further UI cross-linking is required for v1.

## 3. Accessibility

- **Edit affordance**: follow the existing `isEditingX` pattern's markup shape — a visible, keyboard-focusable `<button>` (not a `<span onClick>` or `<div onClick>`) labeled `Edit note` (or `Edit` if context is clear from a heading), with `aria-label` when the visible label is just an icon. `SessionDetailView.tsx`'s existing edit-triggers already do this correctly (e.g. `onClick={() => { setWorkingDirValue(...); setIsEditingWorkingDir(true); }}` on what should be verified as a real `<button>`, not a clickable span — confirm this at implementation time and use it as the pattern to copy).
- **Textarea labeling**: the edit-mode `<textarea>` needs a programmatic label — `aria-label="Session note (markdown)"` or a visually-associated `<label htmlFor>` — plus `aria-describedby` pointing at a short hint ("Markdown supported") since there's no live preview to signal that otherwise.
- **Rendered markdown heading semantics**: `ReactMarkdown` by default maps `#`/`##`/etc. straight to `<h1>`/`<h2>`, which risks heading-level skips or duplicate `<h1>`s inside a page that already has its own heading hierarchy (session name is likely an `<h1>` or `<h2>` in `SessionDetailView`). Cap or remap heading levels for this specific field via `ReactMarkdown`'s `components` prop, e.g. render `h1`→`h4`, `h2`→`h5`, etc., or simplest: since these are short scratch notes, consider whether heading syntax is even a desired affordance — `remarkGfm` alone (as used by `DescriptionSection.tsx`) is fine, but check the rendered output doesn't produce a stray `<h1>` deep in the DOM tree that breaks the page's heading outline (an axe/Lighthouse a11y check flag per this repo's CI — see CLAUDE.md's "UX analysis CI" section, Axe Core blocks on WCAG AA violations).
- **Focus management on mode switch**: when clicking "Edit," move focus into the newly-rendered `<textarea>` (`ref.current?.focus()` in a `useEffect` keyed on the editing boolean — this repo doesn't currently appear to do this for the other `isEditingX` fields based on the grep, which is worth flagging as a pre-existing gap, not something to silently propagate into new code). When Save/Cancel returns to read mode, return focus to the "Edit" button (or the panel's heading) rather than letting it fall back to `<body>`, so keyboard/screen-reader users don't lose their place.
- **Live region for save feedback**: use `aria-live="polite"` on a small status element ("Saved" / "Save failed") so the async save doesn't require a screen-reader user to go hunting for a toast — see §4 for the failure-mode detail.
- **Contrast/markdown styling**: the existing `markdownBody.css.ts` tokens (`vars.color.textPrimary`, `vars.color.textMuted` for blockquotes, etc.) already come from the theme contract that presumably passes the repo's WCAG AA gate — reuse them rather than introducing new color values, satisfying `.claude/rules/css-architecture.md` and avoiding a fresh contrast audit.

## 4. Error states

- **Save failure feedback**: per the codebase's existing patterns (worth confirming at implementation time whether there's a shared toast/error-banner hook already used by the other `isEditingX` saves in `SessionDetailView.tsx`, and reuse it rather than inventing a new one). Minimum bar: on save failure, (a) do not discard the user's typed text — stay in edit mode with the textarea still populated, (b) show an inline error message adjacent to the textarea (not just a toast that can be missed), (c) mark it with `aria-live="assertive"` since this is an error, not a routine status update (contrast with the `aria-live="polite"` "Saved" case in §3). This directly serves the JTBD in §5 ("external memory") — losing a note on a flaky save is worse than not offering notes at all, since the user believed the memory was externalized and it wasn't.
- **Long-note truncation in the `SessionCard` tooltip**: `SessionCard.tsx` already has an established `Tooltip` component (`web-app/src/components/ui/Tooltip.tsx`) used for `pauseReason` and `creationProgress` (lines 492, 506). Critically, `Tooltip`'s `label` prop is typed `string` (`Tooltip.tsx:13`), **not** `React.ReactNode** — so a note tooltip cannot render markdown or scroll; it can only show a plain-text excerpt. Recommendation: strip markdown syntax (or just take the first N characters of the raw source, accepting occasional visible `#`/`*` characters — matching the precedent of the goal panel's own `MAX_GOAL_DISPLAY_LENGTH = 120`-char plain-text truncation in `GoalPanel.tsx:64`) and truncate to a similar length (~100-120 chars + "…") for the tooltip. Do not attempt scrollable tooltip content — that would require either extending `Tooltip` to accept `ReactNode` (a shared-component change with broader blast radius than this feature) or building a bespoke popover; out of scope for a v1 "lightweight indicator." Clicking the indicator (or the card generally) to open the full session detail view is the actual "read the whole thing" path, consistent with `GoalPanel`'s existing `MAX_GOAL_DISPLAY_LENGTH`+"more/less" toggle pattern for its own long-text case.
- **Empty state**: when `note` is empty/unset, show a muted placeholder + explicit CTA, e.g. `<p className={emptyText}>No notes yet.</p>` plus an "Add note" button — following `DescriptionSection.tsx`'s existing `item.description ? <rendered/> : <p className={styles.emptyText}>No description.</p>` pattern (`DescriptionSection.tsx:25-31`), but with a CTA button added since notes (unlike description) are edited from the same view, not a separate form.
- **`SessionCard` indicator should never render for an empty/whitespace-only note** — trim before checking truthiness (a note that's saved as `"   "` should not show the indicator or count as "non-empty" per acceptance criterion 3).

## 5. Jobs-to-be-done

- **Functional — external memory across sessions.** When juggling many concurrent tmux-backed agent sessions (the core premise of this tool per `CLAUDE.md`'s architecture overview), a user's working memory of "why did I leave this one paused" or "what was I trying with this branch" degrades fast — especially across days, context-switches, or after auto-compaction/summarization events elsewhere in the tool. A note is a durable, session-scoped externalization of that context so the user doesn't have to reconstruct it from scrollback or commit history. This is the primary job and the one acceptance criteria are built around (persist across restarts — AC4 — is exactly what makes it "external memory" rather than a transient UI convenience).
- **Emotional — reduce anxiety when re-entering a parked/background session.** Distinct from the functional job: the *feeling* of confidently clicking back into session #14 of 20 knowing there's a note that says "waiting on CI, don't touch" versus the anxious uncertainty of "did I mean to leave this running, or did I forget about it?" The `SessionCard` indicator (AC3) is what serves this job specifically — it has to be visible in the list/grid view *before* the user commits to opening the session, because the anxiety-reduction value is in triage, not just in the detail view.
- **Social — none.** Confirmed no social/collaborative job exists: this is an explicitly single-user tool (per requirements' own non-goals ruling out optimistic-concurrency revisioning "since single-user model, last-write-wins overwrite is acceptable"), so there's no "notify a teammate" or "leave a note for the next person" dimension the way herdr-web's multi-note/revisioned model might imply in a team context. Notes here are a diary entry to one's own future self, not a communication channel to anyone else.

## Summary of concrete recommendations for the plan phase

1. Reuse the app's explicit edit-toggle convention (`isEditingX` state pattern from `SessionDetailView.tsx`), not an always-editable or WYSIWYG editor.
2. Place the panel in the Info tab, adjacent to `GoalPanel` (`SessionDetailView.tsx:1246-1251`), with a clearly distinct label ("Notes") and no status chip, to avoid confusion with the agent-set Goal panel.
3. Render with `ReactMarkdown` + `remarkGfm`, styled via a session-notes-scoped copy of (or direct reuse of) `markdownBody.css.ts`; consider remapping heading levels to avoid heading-hierarchy a11y violations.
4. `SessionCard` indicator: a small icon/badge following the existing `autonomousBadge`/`workflowBadge` conditional-render convention (`SessionCard.tsx:570-626`), wrapped in the existing `Tooltip` component with a plain-text-truncated (~120 char) excerpt — `Tooltip.label` is `string`-only, so no markdown/scroll in the tooltip itself.
5. Trim-and-check-non-empty before showing the `SessionCard` indicator (AC3's "non-empty note" should mean non-whitespace).
6. Save-failure UX: preserve the user's edit-in-progress text, show an inline `aria-live="assertive"` error, do not silently discard on failure — this is the single highest-leverage a11y/error-state fix given the "external memory" JTBD's reliance on the save actually succeeding.
7. Empty state: muted placeholder text + explicit "Add note" CTA button, following `DescriptionSection.tsx`'s existing empty-state text pattern but adding a CTA since (unlike backlog description) notes are edited in-place.
