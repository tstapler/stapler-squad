# Architecture Review: session-notes
**Date**: 2026-08-06
**Verdict**: CONCERNS

## Constitution Violations
- None — no constitution file found (`docs/adr/ADR-000-architecture-constitution.md` does not exist in this repo).

## Blockers
None. The plan's field placement (ADR-001), pattern selection (Transaction Script, no new GoF pattern), and type choices are well-reasoned and consistent with existing codebase conventions. Verified against the actual code, not just the plan's claims: `session/ent/schema/session_goal.go` confirms `SessionGoal`'s multi-writer/structured shape the ADR distinguishes itself from; `session/instance_snapshot.go`'s doc comment confirms the "keep every mutable-field list in sync" touchpoint pattern the plan's Risk Control table cites; `session/instance_actor_setters.go`'s `SetCategory`/`setCategoryLocked` confirms the exact setter shape Story 1.2 Task 3 says `SetNote` mirrors.

## Concerns

- [ ] **Story 1.3 Task 4 (`server/services/session_service.go` + `session/instance.go`) — the 10,000-char cap is defined independently in three places (ent schema `.MaxLen(10000)`, Go `session.MaxNoteLength` constant, frontend `maxLength={10000}`) with no automated check that they agree, only a code comment.** The plan's stated reason the ent schema and Go constant can't share a literal — an import cycle — is real: I verified `session` (top-level) imports `session/ent` (`ent_repository.go`), and `session/ent/runtime.go` imports `session/ent/schema`, so `session/ent/schema` importing `session` to read `session.MaxNoteLength` would close the cycle `session/ent/schema → session → session/ent → session/ent/schema`. Given that constraint is real, the risk is specifically about **drift**, not about the initial numbers being wrong: if a future edit changes `session.MaxNoteLength` (e.g., to 20,000) without updating the ent schema's `.MaxLen(10000)`, `UpdateSession`'s handler-level check (Task 4's `if len(*req.Msg.Note) > session.MaxNoteLength`) would accept a note the ent layer then rejects on `Create`/`Update` — surfacing as an opaque `connect.CodeInternal` from a deep persistence-layer validation failure instead of the clean `connect.CodeInvalidArgument` Story 1.3's own acceptance criterion promises for over-length notes. Task 1.4.1's planned test (`TestUpdateSession_NoteExceedsMaxLength_ReturnsInvalidArgument`, 10,001 chars) only pins the handler-level constant; it does not prove the ent schema's independent `.MaxLen(10000)` literal still matches it.
  **Remediation**: add one Go test that writes a note of exactly `session.MaxNoteLength` characters through the *ent persistence layer directly* (not through the handler) and asserts it's accepted, and one at `session.MaxNoteLength+1` asserting the ent layer itself rejects it (not the handler's own pre-check). This pins the two Go-side numbers together behaviorally — it will fail loudly the moment they drift, which is the same "test as the sync mechanism" pattern the plan's own Risk Control table already applies to the 8-touchpoint round-trip risk (Task 1.4.2). Cross-reference this in the Risk Control table as a second instance of the same class of problem.

## Nitpicks

- **`session/instance_actor_setters.go`'s planned `SetNote`/`setNoteLocked` (Story 1.2 Task 3) carries no length validation itself** — the cap is enforced only in the RPC handler (`server/services/session_service.go`), not on the setter. Confirmed this matches the codebase's existing convention exactly (`SetCategory`/`setCategoryLocked` also has zero validation, and no field in `session/ent/schema/session.go` currently uses `.MaxLen` at all — this plan introduces the *first* length-capped field in that schema). Not a new defect relative to the rest of the codebase, so not raised as a Concern, but worth naming: any future caller of `instance.SetNote(...)` that doesn't route through `UpdateSession` (an MCP tool, an import/migration path, a checkpoint-restore path) would silently bypass the cap. If this convention is ever revisited repo-wide, `Instance.SetNote` is the reference case to fix first since it's brand new code, not legacy.

- **Story 2.1's empty-state UX ("Add note" button, GoalPanel-style) diverges from `research/build-vs-buy.md` §4's explicit recommendation to adapt `NotesSection.tsx`'s click-to-edit `<p role="button">` interaction pattern**, without the plan calling out or justifying the divergence. The build-vs-buy verdict's *primary* recommendation (plain `<textarea>` for edit + `react-markdown`/`remark-gfm` for render, no new editor dependency) is followed correctly by Story 2.1 Task 2 — that's the load-bearing part of the research doc and it's honored. But build-vs-buy's Option 4 additionally recommended adapting `NotesSection.tsx`'s specific entry-point interaction (keyboard-accessible click-to-edit paragraph), and Pattern Decision 3 / Story 2.1 instead follow `GoalPanel.tsx`'s file-structure precedent (standalone panel, explicit "Add note" button) without reconciling the two. Likely a fine choice — an explicit button is arguably more discoverable and accessible-by-default than a `role="button"` paragraph — but a one-line note in the Pattern Decisions table explaining the choice would close the gap between what the research doc recommended and what the plan implements.

- **`truncateGoal` (`web-app/src/lib/utils/string.ts:5`) is reused for note-tooltip truncation (Story 2.2 Task 2) despite being goal-specific in name only** — confirmed its signature (`truncateGoal(text: string, max: number): string`) is already fully generic (no `Goal`-typed parameter), so the reuse itself is sound, but naming it after its first caller makes call sites like the note badge read as an odd cross-feature dependency. Not worth a rename in this PR's scope, but if a third caller shows up, rename to `truncateText` at that point.
