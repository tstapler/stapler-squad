# Adversarial Review: session-notes

**Date**: 2026-08-06
**Verdict**: CONCERNS

## Blockers

None remaining.

- [x] **RESOLVED — Clearing a note will not persist across a restart, directly violating AC4.** Originally: `session/ent_repository.go`'s Update path guarded every optional string field with `if data.X != "" { sessionUpdate.SetX(data.X) }`, which would have silently dropped intentional note-clears. Verified against the current plan.md: Task 1.2.6(b) (line 242) now specifies `sessionUpdate.SetNote(data.Note)` called **unconditionally**, with an inline comment explaining why `Note` differs from sibling guarded fields ("an empty note is a meaningful, intentionally-reachable state... not an 'unset' sentinel"). Story 1.4 (line 294) adds `TestUpdateSession_NoteCleared_PersistsAsEmptyAcrossReload`, explicitly described as the regression test that "must fail against the guarded... version and pass against the unconditional version."
  - Checked for the follow-on risk this fix could introduce (unconditional writes are only safe if they don't clobber `Note` whenever some *other* field is updated without `Note` present in that particular request): Task 1.3.4 (line 266) parses the request with `if req.Msg.Note != nil { ... instance.SetNote(*req.Msg.Note) }` — `note` is `optional string` in the proto (`session.proto` Task 1.3.2, line 261), so Go generates a `*string`, giving a real nil/empty distinction at the request layer; `instance.SetNote` is only invoked when the field was actually present in the request. Traced how `data` reaches `EntRepository.Update`: `session/storage.go`'s `SaveInstances`/`SaveInstancesSync` (lines 257-285, 472, 485) always build `data` from `instance.ToInstanceData()` — the full current in-memory snapshot — not a per-request diff. Since `Instance.Note` is only ever mutated via `SetNote`, an update to an unrelated field (e.g. `Category`) leaves `Instance.Note` untouched, so `data.Note` at persist time still reflects the last legitimately-set value. The unconditional `SetNote(data.Note)` therefore does not reintroduce a "some other field update wipes the note" bug. Also confirmed Task 1.2.4 (line 240) wires `Note` through both `ToInstanceData()` and `FromInstanceData`, and the plan's own 8-touchpoint round-trip test (Task 1.4.2, line 295) covers this path. No new problems found.

## Concerns

- [ ] **Length-cap unit mismatch between frontend and backend can reject notes the UI itself allowed.** Task 1.3.4 enforces the cap via `len(*req.Msg.Note) > session.MaxNoteLength` — Go's `len()` on a string counts UTF-8 **bytes**. Task 2.1.2's `<textarea maxLength={10000}>` counts UTF-16 **code units** (≈ characters for BMP text). For any non-ASCII note (CJK, accented text, emoji — all plausible in a "free-form" reminder) a user can type well under the frontend's 10,000-character limit yet still get bounced with `InvalidArgument` on save, because the byte count exceeds 10,000 first. This directly contradicts the plan's own Risk Control row ("save failure silently discards the user's typed note... losing a note the user believed was saved is worse than no notes feature") — here the UI doesn't even warn the user they're near the limit before the save fails. — **Recommendation**: enforce the same unit both ends (e.g. `utf8.RuneCountInString` on the backend to match character-oriented UI expectations), or document explicitly that the cap is byte-based and size the frontend limit accordingly.
- [ ] **Duplicated 10,000 constant is justified by an import-cycle claim that doesn't hold.** Task 1.3.4 says the ent-schema `.MaxLen(10000)` and the handler's `session.MaxNoteLength` "must be kept in sync by comment, not by shared constant, since the schema package cannot import the session package (avoiding an import cycle)." Verified against the actual code: `session/ent/schema/session.go` (and every file in `session/ent/schema/`) imports only `entgo.io/ent/*` — nothing from `session` or `session/ent`. The generated `session/ent/runtime.go` already imports `session/ent/schema` directly with no cycle. A `const NoteMaxLength = 10000` defined in package `schema` and referenced from both `.MaxLen(schema.NoteMaxLength)` and `server/services/session_service.go`'s handler check would eliminate the two-place-duplication drift risk entirely — the plan accepts a risk that's avoidable by construction. — **Recommendation**: move the constant into `session/ent/schema` (or another leaf package both sides can import) rather than relying on a cross-file comment to keep two literals in sync.
- [ ] **`SessionCard` note badge deviates from every sibling badge's icon+label+native-tooltip convention, with no mobile fallback for the tooltip.** Every existing badge in the row (`autonomousBadge`'s "Auto-pilot", "Done ✓", "Stuck"; `workflowBadge`'s "⚙ Workflow", "⏳ Pending program change") pairs an `aria-hidden` glyph with a **visible text label**, and most also set a native `title` attribute in addition to relying on hover. Story 2.2's proposed badge (`📝` only, `role="img"`, `aria-label="Has a note"`, wrapped only in the Radix `Tooltip` component) is icon-only with no visible label and no `title` fallback. Two consequences: (1) it will look visually inconsistent sitting next to text-labeled badges in the same row; (2) Radix `Tooltip` is hover/focus-triggered — on touch devices (no hover state) there's no equivalent affordance to see the truncated note preview, which is the exact concern the requirements flag ("consider mobile... touch targets") for precisely this kind of new indicator. — **Recommendation**: match the existing badge shape (icon + short label, e.g. "📝 Note"), and add a `title` fallback or otherwise verify/handle the touch-tooltip case before relying on `Tooltip` alone.
- [ ] **Requirements' own motivating scenario (agents/users juggling many simultaneous sessions) isn't served by the chosen interface.** The Problem statement frames this as a reminder for whoever is juggling sessions — which in this codebase is frequently an agent operating through the `mcp__stapler-squad__update_session`/`get_session` MCP tools, not a human clicking through `SessionDetailView`. The plan scopes `note` editing/reading to the web `NotePanel` only and never touches the MCP tool surface, so a session can't read or leave itself a note through the interface it actually runs in. This may be an intentional v1 scope cut (requirements literally say "editable from the session detail view"), but the plan doesn't call this trade-off out anywhere (its own Unresolved Questions list covers search, checkpoint-fork, and review-queue display, but not MCP exposure) — worth an explicit decision rather than a silent gap.

## Minors

- Task 1.4.2 hedges with "confirm at implementation time, none was found via grep" for which file already tests `SetCategory`-style setters — signals the research pass didn't pin down a concrete home for the `Instance.Note` round-trip test, risking either a stray ad hoc test file or the test quietly not landing.
- No section considers whether free-form user note text (now durably persisted, unbounded across backups/exports) warrants any data-handling note beyond "single-user model, last-write-wins" — likely a non-issue for a personal dev tool, but the plan doesn't explicitly reason about it the way it reasons about every other edge case.
