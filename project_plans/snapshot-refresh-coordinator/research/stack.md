# Research: Stack & Conventions — snapshot-refresh-coordinator

## 1. Existing coordinator/dedup/in-flight-tracking patterns

No `refreshCoordinator`/`coalesce`/`inFlight` utility exists anywhere in `web-app/src/lib` today (`grep -rE "coalesce|debounce|inFlight|refreshCoordinator" web-app/src/lib` finds only unrelated hits). The closest precedents:

- **`web-app/src/lib/hooks/useSessionService.ts`** — `streamGenerationRef` (a `useRef(0)` monotonic counter, declared line 185) is the existing generation-guard idiom: incremented at the start of each stream attempt (`++streamGenerationRef.current`, lines 829/833), then checked at every `await` checkpoint (`streamGenerationRef.current !== myGeneration`, lines 844/869/880/891/914/925/936) before applying a dispatch. This is a hand-rolled, per-hook version of exactly the "stale-response discard" behavior the new coordinator needs to generalize.
- **`web-app/src/lib/hooks/useHistoryFullTextSearch.ts`** (`search`, lines 147-226) — in-flight-cancellation via `AbortController`: aborts the previous controller before issuing a new request (lines 163-166), checks multiple abort/cancel error shapes before treating a rejected promise as a real error (lines 195-214). This is the "cancel-and-replace" flavor rather than "coalesce concurrent callers," so it's adjacent but not the same shape as what's needed (four call sites need to share one in-flight request, not cancel each other).
- **`web-app/src/lib/utils/backoff.ts`** — `BackoffState` class is the style precedent for a small, stateful, framework-free utility class (constructor takes config, exposes a getter + mutating methods, fully unit-testable in isolation). This is the closest structural template for `createRefreshCoordinator<T>()`.
- **`web-app/src/lib/hooks/useDebounce.ts`** — debounce-only (delay + replace-timer), not coalescing/dedup; not directly reusable but shows the project's naming convention for hook-adjacent utility files.

**Conclusion**: there is no existing coordinator to extend — this will be a genuinely new utility file, styled after `backoff.ts`'s "small class + free helper functions" shape, generalizing the ad hoc pattern already proven out in `streamGenerationRef`.

## 2. Test framework & conventions for pure utility functions

- **Framework**: Jest 30 (`"test": "jest"` in `web-app/package.json`), with `jest-environment-jsdom`, `@testing-library/react` v16, `@testing-library/jest-dom`, `@testing-library/user-event` also present for component/hook tests (not needed for a pure utility).
- **File placement**: pure utils live in `web-app/src/lib/utils/<name>.ts` with either a co-located `<name>.test.ts` in the same directory (e.g. `backoff.ts` + `backoff.test.ts`, `string.ts` + `string.test.ts`, `rangeSelect.ts` + `rangeSelect.test.ts`) **or** in a `web-app/src/lib/utils/__tests__/<name>.test.ts` subfolder (e.g. `frecency.test.ts`, `notificationStorage.test.ts`) — both patterns coexist in this directory; co-located is more common for newer single-purpose files, so prefer `web-app/src/lib/utils/refreshCoordinator.ts` + `web-app/src/lib/utils/refreshCoordinator.test.ts`.
- **Test naming convention** (consistent across `backoff.test.ts`, `useSessionService.test.ts`, and the omnibar/detector registries per `.claude/rules/feature-testing-registry.md`): `<methodOrFn>_should_<expectedEffect>_When_<condition>`, e.g. `next_should_incrementAttemptOnEachCall_When_calledMultipleTimes`.
- **Style**: `describe(<UnitName>)` blocks grouping `it(...)` cases; imports the utility directly from its `@/lib/...` path (no mocking needed for pure functions); loop-based property assertions (e.g. running jittered-delay checks 50-100x) are used for utilities with randomness/timing components — likely relevant if the coordinator's "latest-pending-rerun" behavior needs interleaving assertions.
- **Integration-level test** (per the requirements doc's "integration-level test on useSessionService/sessionsSlice simulating out-of-order resolution"): `useSessionService.test.ts` (318 lines) currently only unit-tests `BackoffState`/close-code helpers plus one hook-level `renderHook`-style visibility/online-handler integration test — there's no existing precedent in this file for mocking `clientRef.listSessions` with controllable-resolution-order promises. That harness will need to be built new (e.g. manually resolvable promises passed as the mocked `listSessions` return value, matching how `abortControllerRef`/`clientRef` are already refs assigned in `useEffect`, so tests will need to drive the hook via `renderHook` + `act` and control mock resolution timing explicitly).

## 3. Redux Toolkit version & patterns in sessionsSlice.ts

- **Version**: `@reduxjs/toolkit": "^2.11.2"` (RTK 2.x).
- **Patterns already used**: `createSlice`, `createEntityAdapter<Session, string>` (normalized store keyed by `session.id`), `createSelector` for memoized derived selectors (`selectActiveSessionsSortedByUpdatedAt`). `sessionsSlice.ts` (`web-app/src/lib/store/sessionsSlice.ts`) has **no `createAsyncThunk` usage** anywhere in the codebase (`grep -rl "createAsyncThunk" web-app/src` returns nothing) — all RPC calls are made imperatively inside hooks (`useSessionService.ts`) which then `dispatch()` plain action creators (`setSessions`, `upsertSession`, `setLoading`, `setError`) themselves. This confirms the project's established pattern is "hook owns the RPC + dispatch, slice stays RPC-agnostic" — the new coordinator should wrap the existing `listSessions` RPC call inside the hook, not introduce `createAsyncThunk` (which would be an unrelated architectural shift out of scope per the requirements doc).
- **Relevant to the race**: `setSessions` (line 38) does an unconditional `sessionsAdapter.setAll(state, filtered)` on every dispatch — exactly the "full replace with no sequencing guard" the requirements doc describes. `upsertSession` (line 42) already has its own no-op/staleness guard via `updatedAt` comparison (lines 51-58), but that guard is per-session and doesn't help `setSessions`' bulk replace. The coordinator's job is to prevent a stale `dispatch(setSessions(...))` from ever firing, not to change `sessionsSlice.ts` itself (per requirements: "sessionsSlice.ts per-session merge/dedup logic" is explicitly out of scope).

## 4. Generation-counter / AbortController pattern to mirror

`useSessionService.ts`'s `streamGenerationRef` pattern (lines 185, 829, 833, 844, 869, 880, 891, 914, 925, 936) is the direct stylistic model:
1. A single monotonically-incrementing counter ref, incremented once per new logical operation ("start this refresh").
2. Every async continuation captures its own generation number locally (`const myGeneration = ++ref.current`) at the moment it starts.
3. Before applying any side effect (dispatch), re-check `ref.current === myGeneration` — if another operation has since started, discard.

This is precisely the shape a pure `createRefreshCoordinator<T>()` should encapsulate generically (generation counter + in-flight promise tracking + "latest queued rerun" semantics), so `useSessionService.ts`'s four call sites can delegate to it instead of each hand-rolling comparable checks against `streamGenerationRef`/`clientRef`. Note the existing `streamGenerationRef` is scoped to the *stream* lifecycle (reconnect loop) and is explicitly out of scope per the requirements doc ("WatchSessions stream reconnect/backoff logic has its own generation-counter guard") — the new coordinator targets only the plain `listSessions()` RPC call sites (lines 212, 840, 876, 921), which currently have zero such guard.

## Summary for implementation

- New file: `web-app/src/lib/utils/refreshCoordinator.ts` (+ co-located `refreshCoordinator.test.ts`), styled after `backoff.ts` (small class or factory function, framework-free, fully unit-testable).
- No RTK Query / `createAsyncThunk` — stays consistent with the codebase's "hook dispatches plain actions" convention; do not restructure `sessionsSlice.ts`.
- Mirror `streamGenerationRef`'s generation-counter + late-check-before-dispatch shape, generalized to also coalesce concurrent callers (return the same in-flight promise) and queue at most one "latest pending" rerun — matching the requirements doc's "herdr-web-inspired" description (request coalescing, one-in-flight + latest-pending-rerun, stale-response discard).
- Test naming: `<fn>_should_<effect>_When_<condition>`; integration test on `useSessionService` will need a new manually-resolvable-mock harness (no existing precedent to reuse directly).
