# Adversarial Review: snapshot-refresh-coordinator

**Date**: 2026-08-06
**Verdict**: BLOCKED

## Blockers

- [ ] **No timeout/cancellation on the coordinator's `fetcher`, and the shared single-flight design amplifies the blast radius of a hang.** Today, each of the 4 `listSessions`-triggering call sites fires its RPC independently — a hung/slow request at one site does not block the other three from completing their own. Under the plan's "≤1 in-flight fetch, shared across all 4 sites" design, a hung `fetcher()` call keeps the coordinator's state at `inFlight` indefinitely, so every other call site's `request()` just queues behind it instead of firing its own round-trip — meaning one slow `ListSessions` response now stalls session-list refresh for the whole app (manual refresh, initial stream snapshot, and both resync paths), not just the caller that triggered the slow request. `useSessionService.ts:282` shows this codebase already has a precedent for guarding against exactly this (`{ timeoutMs: CREATE_SESSION_TIMEOUT_MS }` passed to `createSession`), but none of the 4 `listSessions()` call sites — old or new — pass a timeout, and the plan doesn't add one. **Recommendation**: add a timeout/`AbortSignal` to the fetcher (or the coordinator's `run()`), and add a test proving a slow winning fetch doesn't starve queued callers beyond a bounded window — or, if an unbounded RPC is judged acceptable, say so explicitly in the plan with the amplified-blast-radius tradeoff named, not left unaddressed.

- [ ] **Coalescing can skip a stream-guarded fetch's underlying RPC entirely, not just discard its result — this is a real regression against requirements.md's "must not regress the `streamGenerationRef` guard" constraint that the plan's own verification method (Story 2.1.6) can't catch.** Concrete scenario: a stream reconnect resync (site #2/#3, gated on `streamGenerationRef`) is sitting in the coordinator's `pending` slot when a later, ungated site #1 (`listSessions()`) call arrives — per Task 1.1.1b, `pending = { fetcher, onResult, waiters }` is *overwritten*, not appended, so the stream resync's `fetcher` is discarded before it is ever invoked; its network call never goes out. That breaks the documented contract at `useSessionService.ts:813` ("On reconnect, ListSessions is called first to flush any state missed while disconnected") — the flush can now silently not happen at all, with a differently-filtered site #1 response substituting for it with no guarantee it covers the same data (e.g. it may exclude archived/other-category sessions the flush was meant to restore). Story 2.1.6's check ("grep `streamGenerationRef.current`, confirm the boolean condition text is unchanged at 6 checkpoints") cannot detect this, because the code snippet is unchanged — what changes is whether that code path executes *at all* for a superseded caller. Story 2.1.5 only tests the milder, already-anticipated case (a caller loses its own *filter preference* to a later coalesced caller); no task or test exercises "a stream-guarded call's fetcher is discarded before it ever runs because an unguarded call arrived after it." **Recommendation**: add a dedicated regression test proving the reconnect-flush contract still holds (or is safely self-healing via a subsequent `WatchSessions` event) when a differently-sourced call coalesces ahead of a queued stream resync — or explicitly document this as an additional accepted risk in ADR-001's Consequences section, which currently doesn't mention it.

## Concerns

- [ ] **Fusing one user-facing, UI-feedback-bearing call site with three silent internal stream-lifecycle call sites in a single coordinator instance conflates two different reliability contracts.** `page.tsx:363-368` gates the "R" manual-refresh shortcut on `if (!loading)` and fires an analytics event (`sessions_refreshed`) — it's a tracked, deliberate user action, unlike sites #2-#4 which never touch `loading` at all. Under the chosen design (Approach A), a user's `listSessions({status: ...})` call can be silently coalesced behind (and replaced by) an unrelated, differently-filtered background stream resync: `loading` still correctly resolves to `false` (per the Story 1.1.3 settle fix), so no error surfaces, but the data the user explicitly asked for may never be fetched. ADR-001 documents and tests this (Story 2.1.5) but frames it as "loses its own filter," understating that it's specifically a *tracked user action silently no-op'ing with no error and no retry signal*. Recommend lowering the bar ADR-001 sets for escalating to Alternative C (filter-signature keying) specifically for this "user-initiated call coalesced away" case, or adding a lightweight signal (log/telemetry) at site #1 when its own request was coalesced away, so this is diagnosable if a user ever reports "I hit refresh and nothing changed."

- [ ] **No design or test coverage for `onResult` itself throwing.** Task 1.1.1c/1.1.3a specify handling only for `fetcher()` rejecting; the success-path `onResult(result)` callback (e.g. a `dispatch()` that throws) is unaddressed. Depending on exactly where in `run()`'s `try/finally` this executes, a thrown `onResult` could mislabel an RPC *success* as a caller-visible rejection for coalesced waiters, or interact awkwardly with the "drain pending synchronously in `finally`, no `await` between clearing state and checking `pending`" requirement (Task 1.1.1c). Add an explicit test for this case.

- [ ] **Naming/conceptual collision between the coordinator's internal `generation` counter and the pre-existing `streamGenerationRef`.** They are independent (per-fetch vs. per-stream-reconnect-attempt) and the plan's cases handle their interaction correctly where tested, but same-named counters operating at different granularities in the same file — combined with the real structural interaction in Blocker #2 — is an easy area for a future maintainer to misreason about. Recommend renaming the coordinator's field (e.g. `fetchGeneration`) and adding an explicit "these two counters do not synchronize" note to the coordinator's JSDoc.

## Minors

- Risk Control table row 1 states this item "exists to close" a stuck-`loading` bug, but `requirements.md`'s Problem Statement and Success Metrics never mention loading state at all — `research/pitfalls.md` §4 correctly identifies stuck-`loading` as a *new* risk the coordinator's own coalescing design would introduce if built naively, not a pre-existing bug being fixed. The mitigation and test (Task 1.1.3a/b) are implemented correctly; this is a framing overclaim in the plan's prose, not a functional gap.
- The hand-rolled single-flight/promise-coalescing primitive (vs. an existing tested implementation) is reasonably justified by the "Small" appetite and the `BackoffState` precedent, but the reference sketch it's modeled on already had one dangling-promise bug that had to be caught and fixed here (Task 1.1.3a) — a reminder that this class of code is exactly where hand-rolled concurrency logic tends to hide edge cases, reinforcing Concerns 2 and 3 above rather than a standalone issue.
- Sites #2/#3/#3b's new fetcher closures (Tasks 2.1.3a/2.1.4a/2.1.4b) omit `includeArchived` from the `listSessions` request payload — this matches today's code exactly (pre-existing, not introduced by this plan) but is reproduced verbatim with no comment noting it's intentional.
