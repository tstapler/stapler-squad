## Concerns

- [ ] **ADR-001 / Story 2.1.5 (last-caller-wins across all 4 sites)** — The plan's own supporting evidence for rejecting Alternative C (filter-signature-keyed map) is incomplete. `research/ux.md` §3 concludes "no live UI burst pattern today actually mixes filters," but that finding only checked category/status dropdown-driven filtering (confirmed client-side, no RPC). It never checked `web-app/src/components/pane/PaneSplitRenderer.tsx:191` — `onFetchArchivedSessions={(includeArchived) => void listSessions({ includeArchived })}` — which **is** a real, user-triggered, filtered call into site #1 that can arrive at any time relative to the ever-present background watch-stream lifecycle (reconnects, the 30s staleness backstop, backwards-jump resyncs — all filter-homogeneous but *unfiltered relative to `includeArchived`*, since sites #2/#3/#3b never pass `includeArchived`). Under the chosen design, a user clicking "show archived" while a background resync's `request()` call happens to queue after theirs will have their own `onResult` (which would apply the archived-inclusive list) silently discarded in favor of the resync's non-archived result — the UI's "show archived" toggle would appear on while the session list silently reverts to non-archived data, with no error surfaced.
  - **Is this a structural defect or inherent to the requirements?** Traced this through: `requirements.md`'s Success Metric 1 ("No two `ListSessions` RPCs are in flight concurrently ... including listSessions, watch-stream initial snapshot, backwards-jump resync, staleness-backstop-triggered reconnect") is written as a *hard, literal* constraint across all 4 sites. Any design that avoids the filter-loss risk (e.g., a second independent coordinator instance for site #1 alone) would let a site-#1 RPC and a site-#2/3/3b RPC be in flight simultaneously, directly violating that literal metric. So the tension is baked into `requirements.md` itself, not introduced by the plan — Approach A is the correct resolution given the literal requirement, and the plan is right not to force Alternative C's map-based complexity onto a real but narrow, recoverable race (self-corrects on the next toggle click or reconnect).
  - **Remediation**: Not a redesign. (1) Correct `research/ux.md` §3 to name `PaneSplitRenderer.tsx:191`'s `includeArchived` toggle as a known, accepted instance of the ADR-001 tradeoff, rather than leaving the "no burst pattern mixes filters" claim standing unqualified — it's currently cited as evidence against Alternative C and is only true for the dropdown case it checked. (2) Broaden Story 2.1.5's regression test from a synthetic `status: ACTIVE` example to explicitly cover (or at least name in its test comment) the real `includeArchived` toggle scenario, so a future maintainer who hits this in production finds the documented rationale immediately. (3) Optional, non-blocking: consider a dev-only `console.debug` (not a full mitigation) inside the coordinator's coalescing branch when a caller's own `onResult` never fires, to aid future debugging of the exact user report ADR-001 anticipates ("my filtered view briefly showed the wrong sessions").

- [ ] **Task 1.1.1b / Story 1.1.3 (`PendingRequest<T>.waiters` accumulation across repeated overwrites)** — The task text specifies overwriting `pending` on each coalesced `request()` call as `{ fetcher, onResult, waiters: [...existing waiters if any] }`, but no Story's Acceptance Criteria or named unit test actually asserts that **every** intermediate coalesced caller's promise still settles when a *third* caller overwrites the pending slot a *second* time. Story 1.1.1's burst-of-3 AC (`request_should_collapseBurstToLatestCaller_When_NCallsArriveWhileOneInFlight`) only asserts fetcher-invocation counts and which `onResult` fires — not that caller B's (the one whose fetcher never ran and whose slot was itself overwritten by C) returned `Promise<void>` still resolves. Story 1.1.3's tests (`request_should_resolveEveryCoalescedWaiter_When_theCoalescedFetchSucceeds`, `...RejectAllCoalescedWaiters...`) are written against a single-coalesce (A running, B queued) scenario per their own AC text, not the 3-caller chain. This is exactly the class of bug the plan's Risk Control table calls "Was High pre-mitigation" for the reject path — the same risk exists on the "waiters array gets reset to `[]` instead of being carried forward" path, and it isn't covered by name anywhere in the plan.
  - **Remediation**: Add one explicit AC + test to Story 1.1.3 (or as 1.1.1e): *Given* A in flight, B coalesces (pending = B, `pB` pending), then C coalesces and overwrites pending (pending = C, `pC` pending, B's original waiter must be carried into C's `pending.waiters` array), *When* A resolves and C's rerun resolves, *Then* **both** `pB` and `pC` resolve — not just `pC`. Suggested name: `request_should_settleEveryIntermediatelyCoalescedCallersPromise_When_PendingIsOverwrittenMultipleTimesBeforeItRuns`. This is cheap to add (same harness as the existing burst-of-3 test) and closes a real gap between the stated invariant and what's actually tested before implementation starts.

## Nitpicks

- `useSessionService.ts` is already a large, multi-responsibility hook (session CRUD, watch-stream lifecycle, reconnect/backoff, event dispatch) — a pre-existing SRP smell. This plan correctly declines to extract the watch-stream lifecycle into its own hook (out of scope, "Small" appetite), but implementers should be aware they're adding a 5th concern (refresh coordination) to an already-crowded file rather than a clean extraction point. Not a blocker for this item; worth a future follow-up note (already implicitly covered by the Unresolved Questions section's forward-looking mentions of `useStuckBacklogItems.ts`/`useSessionSummary.ts`).
- Task 1.1.3a's control flow (`try`/`catch`/`finally` with a synchronous pending-drain-and-rerun-kickoff inside `finally`, plus a re-throw *after* that drain to propagate the direct caller's own rejection) is inherently fiddly to get right in one pass. The plan already budgets a dedicated task and tests for it (good) — just flagging that implementers should write the "no yielded microtask between clearing state and checking pending" (Pitfall 1b) invariant as an inline code comment in `refreshCoordinator.ts`, not only in the plan doc, since it's easy to accidentally break by inserting an `await` during a future edit.
- `web-app/src/lib/hooks/useRepositorySuggestions.ts:42` calls `client.listSessions({})` directly against the raw ConnectRPC client, bypassing `useSessionService.ts`'s `listSessions()` wrapper entirely — this 5th call site is untouched by (and outside the stated scope of) this plan, which is correct per `requirements.md`'s explicit scope to `useSessionService.ts`'s 4 internal call sites, but worth a one-line acknowledgment in the plan so a future reader doesn't assume "all `listSessions` RPC calls in the app" are now coordinated.

## Positive findings (confirmed, not just asserted)

- **Constitution**: none exists; no violations possible.
- **Type-driven design (point 6)**: `CoordinatorState<T>`'s discriminated union genuinely does make "pending set while not in flight" unrepresentable — verified by tracing `request()`/`run()`'s described transitions; the only gap found is the waiters-accumulation testing gap above, not the union's shape itself.
- **PoEAA (point 8)**: Correctly confirmed N/A — no persistence layer exists in this change; `research/build-vs-buy.md` explicitly rules out RTK Query/TanStack Query for structural reasons (cache-ownership split with the `WatchSessions` push path, and `sessionsSlice.ts`'s existing tombstone/no-op-upsert logic would need bypassing), not just "not needed."
- **Build-vs-buy consistency (point 11)**: Plan matches `research/build-vs-buy.md`'s hand-roll recommendation exactly; the `BackoffState` precedent it cites (`web-app/src/lib/utils/backoff.ts`) was verified — genuinely the same shape (framework-free class, `useRef`-instantiated once per hook instance).
- **API contract (point 10)**: `request(fetcher, onResult): Promise<void>` is stable across all 4 call sites without needing per-site variance; the choice to type the coordinator as `RefreshCoordinator<ListSessionsResponse>` (not `Session[]`) is justified by a concrete need (site #1's `systemMemoryPct` read), not speculative.
- **Interface-pollution checklist**: No speculative interface introduced — `RefreshCoordinator<T>` is used as a concrete class directly, consistent with `.claude/rules/interface-pollution-checklist.md`. The generic `<T>` parameter is justified by a named, if deferred, second use case (`useStuckBacklogItems.ts`, `useSessionSummary.ts` follow-ups in Unresolved Questions), not "generic for its own sake."
- **Testability (point 4)**: Coordinator is fully unit-testable in isolation (no React/Redux/ConnectRPC imports); wiring is covered by integration-level tests against the real hook + Redux store. No component in this design forces integration-only testing.
