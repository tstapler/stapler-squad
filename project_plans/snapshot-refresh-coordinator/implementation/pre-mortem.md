# Pre-mortem: snapshot-refresh-coordinator
**Date**: 2026-08-07

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | An `onResult` callback that throws (e.g. a malformed session payload crashing the `setSessions` reducer) leaves the coordinator's internal state stuck at `inFlight` forever — since only `fetcher()` rejection is handled (adversarial-review Concern 2), the drain-pending logic in `run()`'s `finally` never runs, so every future `request()` call across all 4 sites queues behind a slot that will never clear, permanently freezing session-list refresh app-wide until a full page reload. | User reports "session list stopped updating"; reload fixes it. No error toast appears — the RPC itself succeeded, it's the downstream `dispatch`/reducer that threw, invisible to the coordinator's own error path. | Wrap the `onResult(result)` call itself in try/catch inside the drain step (not just `fetcher()`), so a thrown `onResult` still lets the coordinator return to `idle`/start the next pending rerun. Add `request_should_returnToIdleState_When_onResultThrowsSynchronously` to Story 1.1.3's test set. | P1 |
| 2 | Per Blocker 2 (coalescing can discard a queued stream-reconnect flush fetch before its RPC ever fires): if the subsequent `WatchSessions` stream events do **not** actually self-heal the gap — a possibility the adversarial review explicitly leaves unconfirmed ("or is safely self-healing") — the missing archived/other-category sessions never reappear on their own, indefinitely, not just until the next stream event. | Sporadic, hard-to-reproduce bug reports weeks after ship ("my archived session vanished and won't come back") that don't correlate to any single deploy, get dismissed as flaky because they can't be reproduced on demand — only occurs when an unrelated call happens to coalesce ahead of a queued reconnect resync. | Before marking Blocker 2 resolved, add a test proving (or disproving) self-healing via a subsequent `WatchSessions` upsert event. If it doesn't self-heal, this needs a code-level fix (e.g. never let an ungated caller overwrite a pending stream-guarded `pending.fetcher` slot) — not just a documented risk in ADR-001. | P1 |
| 3 | Both open BLOCKERs get closed the same way Story 2.1.5 closed the filter-heterogeneity Concern — an ADR "Consequences" note plus a regression test that asserts the bad behavior *happens*, rather than a code change that prevents it — so the plan ships two known correctness bugs re-labeled as "accepted tradeoffs" instead of fixed. | The next adversarial-review pass (or a future reviewer) finds the same BLOCKER prose still true, now merely cross-referenced from an ADR, backed by a test named `*_should_discardCallerWhen*` that proves the loss rather than prevents it. | Require plan.md/ADR-001 to carry an explicit code-level fix for each BLOCKER (timeout+abort for #1; a non-destructive pending-slot merge or an "always send the stream flush RPC regardless of coalescing" carve-out for #2) before either checkbox can be marked resolved. Reserve "document as accepted tradeoff" exclusively for Concerns, never for Blockers. | P2 |
| 4 | `page.tsx`'s tracked "R" manual-refresh action (fires a `sessions_refreshed` analytics event) can get coalesced behind an unrelated background stream resync and silently settle with different — or effectively no newly-requested — data. `loading` still correctly clears and no error fires (Story 1.1.3's settle fix works exactly as designed), so the user gets zero signal that their explicit action didn't do what they asked. | Analytics show `sessions_refreshed` firing at a normal rate while support tickets say "I hit refresh and nothing happened" — the two signals disagree because the event fires on any settled request, not on the caller's *own* fetch/data actually being applied. | Add a coalesced-away signal (console.debug or a lightweight counter) specifically for site #1, per adversarial-review Concern 1's recommendation — and/or lower ADR-001's bar for escalating this one tracked, user-initiated caller to filter-signature keying (Alternative C) rather than treating it identically to the 3 silent background sites. | P2 |
| 5 | ADR-001's premise — "mutations always dispatch `upsertSession`/`removeSession` directly, never wait on a follow-up snapshot fetch" — was only verified against `createSession`/`updateSession`/delete inside `useSessionService.ts` itself. If any other code path (bulk archive, import, a future feature) awaits a mutation RPC and then calls `listSessions`/`watchSessions` expecting to observe its own write, that refetch can now be silently coalesced away by an unrelated concurrent caller, reintroducing the exact mutation-vs-stale-snapshot race the plan declares structurally impossible and therefore out of scope. | A newly shipped, unrelated feature (e.g. bulk-archive) appears to "lose" its own change immediately after completing — UI briefly reverts to pre-mutation state — reported as a regression against *that* feature, never traced back to this coordinator. | Before merging, grep the full `web-app/src/` tree (not just `useSessionService.ts`) for every call site that awaits a mutation RPC and then calls `listSessions`/`watchSessions` expecting to observe its own write. Record the audit's scope and result in validation.md rather than asserting it from the 3 sites already checked. | P3 |

## P1 Items (address before implementation)
- [x] #1 — Resolved 2026-08-24: `run()`'s pending-drain is in a `finally` block (not only on `fetcher()` rejection), so a thrown `onResult` still returns the coordinator to `idle` and still kicks off any queued rerun. Test: `refreshCoordinator.test.ts`'s `request_should_returnToIdleState_When_onResultThrowsSynchronously`.
- [x] #2 — Resolved 2026-08-24 with the code-level fix this item called for (not a self-healing-via-WatchSessions investigation, which risked being unverifiable): `request()` gained a `guarded` option, and a non-guarded caller can no longer overwrite an already-queued guarded `pending` fetcher — see ADR-001's Amendment section. Tests: `refreshCoordinator.test.ts`'s `request_should_neverOverwriteAGuardedPendingFetcher_When_ALaterNonGuardedCallerCoalesces` and `useSessionService.test.ts`'s `listSessions_should_neverOverwriteAQueuedGuardedStreamSnapshot_When_ALaterUnguardedListSessionsCoalesces`.
