# Adversarial Review: osc-status-signals

**Date**: 2026-08-06
**Verdict**: RESOLVED (2026-08-07) — see resolution note below. Originally BLOCKED.

## Resolution (2026-08-07)

The blocker below is addressed in `plan.md`: `classifyOSC` now also gates on
`oscStaleThreshold` (5s) compared against `IdleDetector.GetLastActivityNs()` — a liveness
clock already updated on every real PTY read (`rs.SetOnOutput`'s `RecordActivity()` call),
independent of this feature. A crashed/killed process stops producing PTY bytes, so this
clock freezes with it, and `classifyOSC` falls back to `(OSCStatusNone, false)` (text-pattern
detection) once the tail is stale — closing the "stuck at Executing forever" failure mode
without wiring `Stop()`/state-reset into the exit callbacks (smaller diff, reuses existing
state). See plan.md Domain Glossary (`oscStaleThreshold`) and Task 4.1.1a/4.1.1a-test.
This was a documentation/plan fix made during triage, not yet implemented in code —
Task 4.1.1a-test is the regression test that must pass before this is considered closed.

## Blockers (original — see Resolution above)

- [x] **`classifyOSC`'s `cc.IsStarted()` staleness gate does not do what the plan claims, and can produce a new, longer-lived false-Executing bug than the one being fixed.** Task 4.1.1a's doc comment says `classifyOSC` is "gated on the session still being started — an exited process's last-written title could otherwise be misread as current state" and calls this "the single fallback gate" for AC7-style staleness. Verified against the actual code (`session/claude_controller.go`): `cc.started` (`IsStarted()`) is set `false` **only** inside `Stop()`, and `Stop()` is called **only** from deliberate operator/driver actions — `Instance.Destroy()` (`session/instance.go:1266`), `Instance.Restart()` (`session/instance.go:1534`), `KillExternalSession()` (`session/instance_tmux.go:308`), and `handleDriverFailure` (`session/session_driver.go:540`). The unexpected-exit paths — `ResponseStream.OnEOF` → `cc.onEOFCallback` (`session/instance_controller.go:59-74`) and the control-mode exit callback `instanceOnExitCallback` (`session/instance.go:785-824`) — transition the session's `Status` to `Stopped` and fire `EventExited`, but **never call `controller.Stop()`**. So `Instance.Status == Stopped` and `ClaudeController.IsStarted() == true` are simultaneously reachable, non-error states, for an indefinite period after a crash/kill. Because the tail buffer is also frozen at that point (no more PTY output), `GetCurrentStatus`'s content-hash cache will serve the same computed value forever. If the last OSC title before death happened to show the spinner, and the frozen screen text reads as anything in the promotable set (Ready/Unknown/Idle/Processing — a blank shell prompt after a crash is a very plausible case), `applyOSCStatusOverride` will promote it to `StatusExecuting` and it will **stay stuck there forever**, whereas text-pattern-only detection (today's behavior) would have correctly read the blank prompt as Ready/Idle. This is a new failure mode strictly worse than the one this feature exists to fix: the false-idle case self-corrects on the very next real screen update; this false-Executing case does not self-correct at all for a genuinely dead process, because there is no next OSC title coming. Combined with "Risk Control" explicitly choosing no feature flag ("full rollout on merge"), this should be resolved before implementation — either gate on real liveness (e.g. consult `Instance.Status`/the exit callback, not just the `started` flag) or make `classifyOSC`'s doc comment and design honest about the residual risk and add an explicit mitigation (e.g. a max-age check on the cached tail, or wiring `Stop()`/a state reset into the exit callbacks as part of this change).

## Concerns

- [ ] **`applyOSCStatusOverride` (the core decision-matrix function) has no direct unit tests — only 3 of roughly 20 meaningful `(DetectedStatus, OSCStatus)` branch combinations are exercised, and only indirectly via `ClaudeController` integration tests.** Story 4.1.1's Acceptance Criteria cover only `classifyOSC`; no Story/Task in the plan calls for a table-driven unit test of `applyOSCStatusOverride` itself. The explicitly-named "never demote" protected set (`StatusError`, `StatusNeedsApproval`, `StatusInputRequired`, `StatusTestsFailing`, `StatusSuccess`, `StatusWaitingForAgent`) — the whole point of the asymmetric-safety design — has **zero** test coverage proving any of the 6 categories actually resist an OSC override; Task 4.2.1b only proves `StatusExecuting` (the 7th protected category) is safe. Recommend a dedicated table-driven `TestApplyOSCStatusOverride` covering all `DetectedStatus` values against both `OSCStatusExecuting` and `OSCStatusIdle`.
- [ ] **`ApplyOSCStatus`'s `OSCStatusIdle` branch is untested at the `IdleDetector` unit level.** All five planned tests in Task 3.1.2b (`FirstTransitionNeverDebounced`, `BypassesTextDebounceViaShorterWindow`, `BumpsLastActivity`, `NoneIsNoOp`, `RepeatedSameStatusDoesNotChurnClock`) exercise `ApplyOSCStatus(dtypes.OSCStatusExecuting)` only. Neither the debounce-bypass behavior for the idle direction nor the `idleDuration > id.config.IdleThreshold → IdleStateTimeout` branch inside `ApplyOSCStatus`'s `OSCStatusIdle` case gets a unit test — only an indirect, non-debounce-focused integration assertion (Task 4.2.1b). AC6 doesn't distinguish direction; both should be tested symmetrically.
- [ ] **`pkg/ansi/osc.go` is a fourth independent hand-rolled implementation of BEL/ST-terminated OSC scanning in a codebase that has already been bitten by exactly this duplication pattern once (BUG-025, the reason `pkg/ansi` exists at all).** `research/build-vs-buy.md`'s explicit final recommendation was "Do **not** write OSC parsing from scratch a third time... reuse [`pkg/analytics/escape_code_parser.go`'s `parseOSC`] logic." The plan's rejection of that reuse (Pattern Decisions table: `EscapeCodeParser.Parse()` no-ops when `captureLevel == "off"`, the common no-analytics-DB case) is well-reasoned as a coupling concern, but the plan doesn't reuse the *logic* either — it writes a new `findOSCTerminator`/forward-scan implementation from scratch. The result is 4 independent BEL/ST-terminator scanners (`pkg/ansi/csi.go` is CSI-only and not itself a duplicate, but `pkg/analytics/escape_code_parser.go`, `server/terminal/escape_scan.go`, and now `pkg/ansi/osc.go` all independently implement "scan for BEL or ST terminator") with no shared test vectors or cross-reference — a future terminator-parsing bug fix found in one has no mechanism to propagate to the others. At minimum, cross-reference the three in code comments and consider sharing a `findTerminator` helper.
- [ ] **`GetStatusAndIdleInfo` lacks the nil-guard `GetCurrentStatus` has for an uninitialized `statusDetector`, and the new OSC override makes that gap materially worse.** `GetCurrentStatus` returns early (`"status detector not initialized"`) when `cc.statusDetector.Load() == nil`. `GetStatusAndIdleInfo`'s equivalent block (`if sd := cc.statusDetector.Load(); sd != nil { ... }`) has no `else`/early-return — if `sd` is nil, `status` silently stays at its zero value, `StatusUnknown`. Pre-feature this was harmless (Unknown just fell through as "no badge"). Post-feature, `StatusUnknown` is in **both** OSC promotable sets, so an uninitialized-detector call to `GetStatusAndIdleInfo` could now report a confident `StatusExecuting`/`StatusIdle` sourced entirely from OSC rather than surfacing the uninitialized state. Likely unreachable in production if `Start()` always populates `statusDetector` before flipping `started` (not fully confirmed), but cheap to close with a matching guard for defense-in-depth.
- [ ] **The requirements' and Pattern Decisions table's framing of "OSC wins" is narrower than AC5's title suggests, and the supporting precedent for the narrowing isn't cited.** The asymmetric upgrade-only policy is legitimate — AC5 literally says "wins for **at least** the false-idle case" — and excluding `StatusSuccess` from OSC promotion is actually *consistent* with the existing text-pattern priority chain (`session/detection/pattern_set.go:69-141` already ranks `Success` above `Active`/`Executing`, confirmed by its own comment at lines 98-100 explaining why `WaitingForAgent` is checked before `Success`). But neither the plan nor the ADRs cite this existing precedent, so a reviewer reading only the OSC feature docs would have no way to tell the `StatusSuccess` exclusion is principled rather than arbitrary. Recommend citing `pattern_set.go`'s existing Success > Active ordering directly in the Pattern Decisions table row.

## Minors

- `OSCDebounceDelay`'s 150ms default is derived from an *estimated* (not measured) ~80-100ms spinner redraw interval (`research/ux.md`) — only ~1.5x that estimate, so there's real risk it's tuned against a guess rather than real Claude Code CLI behavior. ADR-002 already flags it as revisable; worth capturing actual redraw-interval data during/soon after rollout instead of leaving it as a guess indefinitely.
- `ExtractLastOSC(data string, oscNums ...string)`'s variadic signature constructs a slice at each call site; Task 1.1.2b's zero-alloc test (mirrored from `StripCSI`'s non-variadic precedent) may be more sensitive to Go compiler escape-analysis/inlining behavior than the precedent it's modeled on — confirm it actually holds in CI rather than assuming parity.
- The plan's own Unresolved Questions section already flags that the requirements' `\x1b]4;0` OSC-progress sequence number is likely wrong per the OSC spec (OSC 4 = color-palette-set; the real progress convention is OSC `9;4`) — correctly out of scope for this plan, but worth a loud enough marker that a future contributor doesn't copy the wrong sequence number straight from the original backlog issue.
- `claude_controller.go`'s `statusCacheEntry`/`idleCacheEntry` doc comments describe the cache key as an "FNV-64a hash" but the actual implementation uses murmur3 (`github.com/spaolacci/murmur3`). Pre-existing and unrelated to this feature, but Phase 4 touches this exact code region — worth a drive-by comment fix per this repo's own collateral-debt convention.
