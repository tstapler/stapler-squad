# Requirements: GitHub Issue Cleanup

**Item ID:** 404529d0-3f08-4362-9391-4f628bb7b6de  
**Date:** 2026-11-03  
**Category:** feature

## Problem Statement

When a backlog item is imported from a GitHub issue — either via the plugin sync
(`SourceID` present) or via the `import_github_issue` MCP tool (`ExternalURL`
only, no `SourceID`) — there are two related lifecycle gaps:

1. **Issue not closed for MCP-imported items.** The existing forward-sync
   subscriber (`backlog_github_forward_sync.go`) closes the GitHub issue when
   the backlog item reaches `done`, but it skips any item whose `SourceID` is
   empty (`SourceID == "" || ExternalID == ""` guard at line 141-143). Items
   created via `import_github_issue` have only `ExternalURL`, so their backing
   GitHub issue is never closed automatically.

2. **No PR-to-issue link in GitHub.** When a PR is created for a backlog item
   backed by a GitHub issue, the PR body contains no `Closes #N` / `Fixes #N`
   keyword. GitHub does not natively link the PR to the issue, so the issue
   tracker does not show the relationship and the issue is not auto-closed on
   merge via GitHub's own mechanism.

A secondary deferred item from the original forward-sync implementation: skip
re-closing an issue that is already closed (pre-mortem P2 #5, noted in
`backlog_github_forward_sync.go` lines 115-121).

## Scope

### In scope

- Extend the `done`-transition forward-sync path to cover items with
  `ExternalURL` pointing to a GitHub issue but no `SourceID` — mirroring the
  pattern already in `resolveProgressTarget` (progress sync).
- Inject a `Closes #N` footer into the PR body for items backed by a GitHub
  issue (`ExternalURL` or `ExternalID`) in both the mechanical `pushAndCreatePR`
  path (`buildFallbackPRBody` / `appendBacklogFooter`) and the LLM-drafted path.
- Add a "skip if already closed" check before each forward-sync close attempt —
  one live GET per done-transition (acceptable latency given the event-driven,
  non-latency-sensitive subscriber context).
- Leave a bot comment on the closed issue for MCP-imported items (mirrors the
  existing plugin-sourced behaviour in `forwardSyncCloseCommentFor`).

### Out of scope

- Linear / JIRA issue linking (ADR-002 state-updater path; different interface,
  separate follow-up).
- Webhook-driven issue-close on PR merge (the current approach of closing on
  `done` transition is correct for the app's lifecycle model; "close on PR
  merge" is a separate design question).
- Backlog-item archival when a GitHub issue is externally deleted or transferred
  (not mentioned in the backlog description).

## Functional Requirements

### FR1 — Close GitHub issue on `done` for MCP-imported items

When a backlog item transitions to `done` and has a non-empty `ExternalURL`
that parses as a GitHub issue URL (`github.com/<owner>/<repo>/issues/<N>`) but
has no `SourceID`, the forward-sync subscriber MUST call `CloseIssue` and
`PostIssueComment` using the keychain token for the parsed host, leaving the
same kind of bot comment it leaves for plugin-sourced items.

### FR2 — `Closes #N` in PR body

When a PR body is generated by `buildFallbackPRBody` or `appendBacklogFooter`
for a backlog item whose `ExternalURL` (or derived `ExternalID` + source config)
points to a GitHub issue on the **same repository** as the PR, the generated
body MUST include a `Closes #N` line so GitHub natively links and auto-closes
the issue on merge.

The `Closes #N` line MUST be omitted when the GitHub issue lives on a different
repository than the PR (cross-repo link keywords are not supported by GitHub).

### FR3 — Skip-if-closed guard

Before attempting to close a GitHub issue (both for plugin-sourced and
MCP-imported items), the forward-sync handler MUST issue a GET to read the
issue's current state. If the response indicates `state == "closed"` already,
the close call MUST be skipped and the event logged at DEBUG level. The
watermark MUST still be updated from the GET response's `updated_at` to prevent
re-triggering on the next backward sync.

### FR4 — Idempotency and failure tolerance

All new close/comment paths MUST be best-effort: a failure logs at WARN level
and records via `storage.RecordSourceSyncFailure` without blocking the `done`
transition itself, mirroring the existing forward-sync failure handling.

## Non-Functional Requirements

- No new synchronous RPC overhead on the critical path (subscriber goroutine
  only).
- No schema change required (ExternalURL is already stored; `ExternalID` for
  MCP-imported items can be derived from the parsed URL at runtime).
- Rate-limiting: use the existing `github.HTTPClient()` which honours GitHub's
  rate-limit headers; log at WARN and record sync failure on 429/403.

## Acceptance Criteria

1. Given a backlog item imported via `import_github_issue` with `ExternalURL =
   "https://github.com/owner/repo/issues/42"` and no `SourceID`, when the item
   transitions to `done`, then the GitHub issue #42 is closed and receives the
   bot comment within the subscriber's normal event processing window.

2. Given a backlog item with a GitHub `ExternalURL` whose backing issue is
   already closed before the item reaches `done`, when the item transitions to
   `done`, then no second close is attempted and the already-closed state is
   logged at DEBUG level (not WARN).

3. Given a PR created by `pushAndCreatePR` for a backlog item whose
   `ExternalURL` points to `https://github.com/owner/repo/issues/42` and the PR
   is in the same repo (`owner/repo`), the generated PR body contains
   `Closes #42`.

4. Given a PR created for a backlog item whose `ExternalURL` points to a GitHub
   issue on a different repository than the PR (cross-repo), the generated PR
   body does NOT contain a `Closes #N` line (keyword not supported by GitHub
   cross-repo).

5. Given `forward_sync_enabled = true` on the item's source plugin (existing
   plugin-sourced path), the existing `done`-transition close behaviour is
   unchanged (no regression).

6. Given that CloseIssue fails with a network or auth error for an MCP-imported
   item, the item still reaches `done` status (the subscriber failure is
   best-effort and must not block the transition).

7. All new code paths have unit tests covering the close, skip-if-closed,
   cross-repo exclusion, and failure-is-best-effort behaviours.
