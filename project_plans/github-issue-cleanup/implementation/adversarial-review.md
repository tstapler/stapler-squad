# Adversarial Review: github-issue-cleanup

**Date**: 2026-11-03
**Verdict**: APPROVED (blockers resolved in plan.md)

## Blockers

- [x] **AC-3 / AC-4 violated: plan uses full-URL `Closes` form unconditionally, skipping same-repo detection** — AC-3 says the generated PR body must contain `Closes #42` (bare issue number) when the issue is in the same repo. AC-4 says the `Closes` line must be **omitted entirely** when the issue is on a different repository. Plan.md's Pattern Decisions table instead chooses `Closes <full-url>` for every item, explicitly to avoid the cross-repo `#N` data-corruption hazard. That rationale is internally inconsistent: (a) GitHub's full-URL closing keyword *does* work cross-repo, so emitting `Closes https://github.com/acme/widget/issues/42` in a PR on a different repo **will** auto-close that issue — violating AC-4's "must NOT contain a Closes line" rule; (b) same-repo items receive a full URL where AC-3 requires the bare `#42` form. Neither AC is met. The same-repo check required by FR2 is absent from every task in the plan — `closingKeywordFor` returns a keyword with no repo-comparison logic, and `buildFallbackPRBody` has no access to the PR repo for comparison. Recommendation: either (a) implement the same-repo check in `buildFallbackPRBody` (requires passing the PR's owner/repo — which is known from the item's git remote at `pushAndCreatePR` call time — and comparing it to the parsed `ExternalURL`; emit `Closes #N` on match, nothing on mismatch), or (b) if full-URL form is chosen as a deliberate simplification, revise AC-3 and AC-4 in requirements.md to match, and explicitly document that cross-repo issues **will** be auto-closed by the keyword.

- [x] **FR2 scope gap: `appendBacklogFooter` is explicitly excluded from the plan despite being named in-scope by requirements** — FR2 says: "When a PR body is generated by `buildFallbackPRBody` **or** `appendBacklogFooter`…the generated body MUST include a `Closes #N` line." The requirements Scope section likewise lists both functions. Plan.md's Domain Glossary and Tech Debt Disposition explicitly state "AC-3 does NOT touch this function (keyword goes in `buildFallbackPRBody` only, not in LLM-drafted bodies)" and relies on `BuildSessionInitialPrompt`'s prompt instruction for the LLM-drafted path instead. This creates a non-deterministic gap: if an agent ignores the prompt instruction (a normal LLM behaviour under context pressure or truncation), the LLM-drafted PR body will contain no closing keyword, and no fallback mechanism catches the omission. Direct injection in `appendBacklogFooter` is deterministic; prompt instruction is advisory. Recommendation: modify `appendBacklogFooter` to call `closingKeywordFor(item.ExternalURL)` and append the keyword line before the footer — same guard pattern as `buildFallbackPRBody` — so the closing keyword is present regardless of whether the agent included it. The prompt instruction in `BuildSessionInitialPrompt` is still valuable (it tells the agent to do it natively in its draft), but should not be the sole mechanism.

## Concerns

- [ ] **4-tuple vs 5-tuple inconsistency between Task 1.1.2b and Task 1.1.2c** — Task 1.1.2b's pseudo-code defines `resolveCloseTarget` with a 4-tuple return: `(plugin externalIssueCloser, cfg session.PluginConfig, externalID string, ok bool)`. Task 1.1.2c then says to widen the signature to 5-tuple by adding `closeLabel string`, making it `(plugin, cfg, externalID, closeLabel string, ok bool)`. The dependency graph requires 1.1.2b before 1.1.2c, so an implementer following the plan will write the 4-tuple first, then immediately modify the signature in 1.1.2c. Task 1.1.4a already assumes the 5-tuple (it tests that `closeLabel` is returned from Path A). The plan should update 1.1.2b's pseudo-code to show the final 5-tuple directly — the incremental "widen it in 1.1.2c" instruction serves no design purpose and introduces an unnecessary rewrite step. Recommendation: amend 1.1.2b to show the 5-tuple signature and document that `closeLabel = ""` on Path B; remove the "update the signature" note from 1.1.2c.

- [ ] **Empty `*session.GitHubIssuesPlugin{}` struct assumption is unverified** — Task 1.1.2b's Path B builds `&session.GitHubIssuesPlugin{}` (zero-value struct) and returns it as the closer. The plan asserts "token is resolved by GitHubIssuesPlugin from the keychain at call time," but `GitHubIssuesPlugin` instances obtained via `registry.Get(source.PluginID)` on Path A are populated at startup by the plugin registry (which may inject an HTTP client, keychain reference, or config cache). If `*GitHubIssuesPlugin` relies on any registered state rather than a global keychain singleton, the bare empty struct will silently fail to authenticate — producing a Warn-log skip indistinguishable from a legitimate token-miss. The existing precedent (`resolveProgressTarget`) uses the same bare-struct pattern, which is reassuring, but the plan provides no citation to confirm this is safe. Recommendation: add an explicit cross-reference to `resolveProgressTarget`'s Path B at the equivalent location in production code, and add a unit test that calls `CloseIssue` on a `*GitHubIssuesPlugin{}` with a valid mock HTTP server and config — this is not covered by the existing `ReadIssueState` tests.

## Minors

- **Task 1.1.4c is a verification step, not a task.** It contains no code changes ("Files: none (verification step)") and is effectively a checklist item. Placing it inside a Story Acceptance Criteria block makes the AC count appear higher than it is. Move it to a "Pre-merge gate" note at the bottom of Story 1.1.4 or delete it and rely on the standard `make ci` gate that all PRs run.

- **No production success signal for AC-3/AC-4.** The Observability Plan provides a log-based signal only for AC-1 (`log.Info("closed MCP-imported issue", ...)`). AC-3 and AC-4 (closing keyword in PR body) produce no log line, counter, or metric. A silent regression — e.g., `closingKeywordFor` returning `""` due to a URL format change — would go undetected until a human notices that PRs are not auto-closing issues. Recommendation: add a `log.Debug("backlog_lifecycle_pr: injected closing keyword", "item", item.ID, "keyword", kw, "url", item.ExternalURL)` in `buildFallbackPRBody` to make the injection observable at debug level.

- **Double `storage.GetItemSourceByID` call in the error path.** When `resolveCloseTarget` Path A fails (source not found, or plugin not found, or token decrypt fails), `handleForwardSyncClose` Task 1.1.2c's fallback block re-fetches the same source row via a second `storage.GetItemSourceByID(ctx, current.SourceID)` call for the Linear/JIRA state-updater path. This is at most one extra DB read per done event and not a hot path, but it is a double-fetch of the same row. If the first fetch failed due to a transient DB error, the second may succeed — which is an accidental retry that could mask the error. Recommendation: widen `resolveCloseTarget`'s return to pass the fetched `source` back (or return the error cause), so `handleForwardSyncClose` can reuse it rather than re-fetching.

- **`ClaimingHostID` on Path B MCP-imported items is undocumented.** Task 1.1.2c builds the close comment with `forwardSyncCloseCommentWithPR(current.ClaimingHostID, current.PrURL)`. For MCP-imported items there is no claiming source, so `ClaimingHostID` may be empty. `forwardSyncCloseCommentFor("")` likely omits the host suffix silently. This is probably harmless, but it differs from the SourceID-path comment format. The plan should document the expected comment format for Path B (host suffix absent, PR suffix conditional on `PrURL != ""`), and the test for `TestHandleForwardSyncClose_MCPImport_ClosesIssue` should assert the exact comment string to prevent silent divergence.
