# Pre-mortem: github-issue-cleanup
**Date**: 2026-11-03

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | AC-4 instructs the agent to include `Fixes <url>` in the PR body. When the PR merges, GitHub auto-closes the issue. The item then transitions to `done`, `handleForwardSyncClose` fires, calls `CloseIssue` idempotently (200 OK, no error), and posts a "Closed automatically" comment on an already-closed issue. | External GitHub issue watchers see a redundant "Closed automatically — implemented in: <PR url>" comment appearing *after* the issue was already closed by the merged PR. Visible noise to outside stakeholders on every successfully implemented item. | In `resolveCloseTarget` Path B (or in `handleForwardSyncClose` before the close call), fetch the current issue state via `GetIssue`; if `state == "closed"` skip both `CloseIssue` and `PostIssueComment`. Alternatively, make `PostIssueComment` conditional on the issue transitioning from open → closed in this call. Add a test case: MCP-import path where issue is already closed → neither call fires. | P1 |
| 2 | No kill switch. Any item that acquires a spurious `ExternalURL` (bad import, operator mistake, a future code path that sets the field carelessly) triggers an unintended close of a real GitHub issue when the item transitions to `done`. With no feature flag, the only remediation is a code revert + service redeploy, during which every concurrent `done` transition is silently unhandled. | A GitHub issue that should not have been closed is now closed; the owner has no fast disable path and must redeploy to stop further spurious closes. | Add a `github_issue_mcp_import_close` feature flag (defaulting `false`; flip on after soak). This contradicts the requirements' "no new flag" directive, but the blast radius of a spurious ExternalURL hitting an external issue with no kill switch is the scenario that overrides that preference. At minimum, document the revert runbook in `docs/how-to/` and wire the Warn log to a Grafana alert so the operator knows within minutes, not days. | P1 |
| 3 | `handleForwardSyncClose`'s refactoring (Task 1.1.2c) replaces the existing SourceID early-return and plugin lookup with `resolveCloseTarget`. For GitHub SourceID-linked items `resolveCloseTarget` Path A works. For Linear/JIRA SourceID-linked items `resolveCloseTarget` returns `ok=false` (the type assertion `plugin.(externalIssueCloser)` fails), and the plan specifies a "secondary fallback" for the `externalIssueStateUpdater` path — but requires a *second* source lookup (the source object is not returned when `ok=false`). If this refactoring is done incorrectly or the second lookup uses different error semantics, Linear/JIRA item closes silently stop working. | Linear/JIRA issues remain open after backlog items reach `done`; no error is logged (the fallback returns nil on lookup failure). Only noticed by a user who checks the external tracker. | Add `TestHandleForwardSyncClose_LinearStateUpdater_NoRegression` using a mock `externalIssueStateUpdater` plugin (not `externalIssueCloser`) with a SourceID-linked item; assert `UpdateState(closed)` is called. Without this test, the Linear/JIRA fallback path has zero coverage after the refactoring and can silently break undetected. | P2 |
| 4 | The 30 s `context.WithTimeout` wraps the entire close+comment+watermark sequence. If a network glitch causes `CloseIssue` to succeed server-side but its response arrives just past 30 s, the context is cancelled before `storage.UpdateBacklogItem(ctx, ..., BacklogItemUpdate{GitHubSyncedIssueUpdatedAt: &watermark})` completes. The issue is closed on GitHub; `GitHubSyncedIssueUpdatedAt` is not advanced. The next backward-sync poll sees `updated_at` newer than the stale watermark and re-ingests the now-closed state, potentially creating spurious state-change log noise or a watermark loop. | Backward-sync logs show a re-ingest event for an item already at `done`; in the worst case the item's `GitHubSyncedIssueUpdatedAt` oscillates between the missed watermark and the re-ingested value across consecutive polls. | Perform the watermark write with a fresh background context (not the per-request `ctx` derived from `WithTimeout`). The write is a local DB operation with sub-millisecond latency; it should never be cancelled by a network timeout. Pattern: `storage.UpdateBacklogItem(context.Background(), ...)` with a short dedicated deadline, mirroring the existing watermark advancement on Path A. | P2 |
| 5 | `closingKeywordFor` uses `strings.Contains(url, "/issues/")` to classify URLs. A repo whose name contains the substring `issues` (e.g. `https://github.com/acme/my-issues-tracker/pull/5`) matches the first branch and returns `"Closes"` instead of `"Related:"`. The fallback PR body and agent prompt then emit `Closes <pr-url>` for a PR-backed item — a keyword that GitHub silently ignores for PR-to-PR links but that is semantically incorrect and confusing to reviewers. | A fallback PR body for an item whose `ExternalURL` is a PR in a repo whose name contains `issues` reads `Closes https://github.com/acme/my-issues-tracker/pull/5`. Reviewers see a wrong closing keyword; GitHub does not auto-close anything (it ignores the keyword), so there is no data loss but there is visible noise. | Replace `strings.Contains` classification with `ParseGitHubRefWithHosts` and compare `ref.Type` against `RefTypeIssue` / `RefTypePR`. The parsed type is authoritative and not fooled by repo names. This also centralises the parsing logic (already used in `resolveCloseTarget` Path B) so both uses are consistent. | P3 |
