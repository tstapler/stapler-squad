# Pre-mortem: launcher-presets
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `buildLaunchCommand`'s `plainProgram` path (`session/instance_tmux.go:105-119`) uses `i.Program` verbatim as the shell command base — only the `CLIFlags` and `ExtraArgs` loops call `shellQuote`. A preset's `argv[0]` (hand-authored, or copied from someone else's shared dotfiles per the ADR's own "shareable dotfiles artifact" framing) flows straight into `Program` with only a non-empty check (Task 1.1.1c) — no metacharacter check — so a preset with e.g. `argv: ["true; touch /tmp/pwned"]` runs as two shell commands, not one. | A user selects a preset and the tmux pane runs something other than (or in addition to) the intended program — a second command executes silently, or the pane shows a shell syntax/"command not found" error for what was supposed to be a single program token. | Before Phase 2 is implemented, either (a) shell-quote `i.Program` in the `plainProgram` case of `buildLaunchCommand`, or (b) add load-time validation in `validateLauncherPresets` rejecting `argv[0]` values containing shell metacharacters — and extend Story 2.2.1's ACs to cover a metacharacter-bearing `argv[0]`, not just `ExtraArgs` elements, which is the only carrier the plan currently tests for quoting safety. | P1 |
| 2 | The flagship SSH remote-exec preset (`ssh -t host 'cd ~/repo && exec claude'` — the exact example in the Problem Statement) still goes through the unchanged `directory`/`new_worktree` session-creation path (ADR-001 rules out a new `SessionType`), so the user must still pick a local working directory that has no relationship to the remote host or command before they can submit. | Users select the SSH-style preset, then stall at the still-required working-directory field, or pick an arbitrary local directory that then shows up as the session's "project" in the session list despite the session having nothing to do with that directory. | Resolve this explicitly in plan.md rather than leaving it as the architecture review's nitpick — e.g. default to a `one_off`-style throwaway path when a selected preset's argv looks like a remote-exec form, or make the working-directory field optional/hidden specifically after such a preset is selected. | P2 |
| 3 | Presets can only be authored by hand-editing raw JSON (`~/.stapler-squad/launcher-presets.json`) — requirements.md scopes UI editing explicitly Out of Scope — a materially higher activation barrier than "select from a dropdown" for the average user this feature is meant to help. | One month post-ship, real-world preset counts stay near zero across users; no bug reports, but also no organic adoption — the feature ships working correctly and goes unused. | Ship a minimal "save current form as a preset" affordance (server-side append to the JSON file) alongside the read-only RPC, or explicitly scope a fast-follow story for it in plan.md rather than leaving authoring at hand-edited-only for v1 with no compensating discovery path. | P2 |
| 4 | `handlePresetSelect` (Task 4.2.1a) overwrites `program`, `extraArgs`, and `workingDir` but never touches `profile`, `alias`, `branch`, or `sessionType` — so a preset selected after the user already configured a `new_worktree`/profile combo merges with that leftover state instead of replacing it. | A user mid-way through a `new_worktree` session (branch typed, profile selected) clicks a preset and submits, then gets a session that tries to create a git branch/worktree for a non-git command, or gets a profile's `cli_flags` silently prepended ahead of a preset's `argv` in a combination the preset author never tested. | Add an explicit, tested reset of `profile`/`alias`/`branch` (and re-evaluation of `sessionType` where the preset's shape doesn't fit the current mode) inside `handlePresetSelect`, with a component test asserting preset selection after profile/branch was already set produces a fully preset-consistent form state, not a merge of both. | P2 |
| 5 | `default_path`'s resolution semantics (absolute path? relative to the resolved repo root? relative to CWD?) are never specified in plan.md — the Domain Glossary only says it "prefills `OmnibarFormState.workingDir`" — and nothing validates it at load time. | A preset author sets `default_path: "packages/api"` expecting it to resolve against whatever repo the session ends up rooted in; session creation instead fails with a generic "path does not exist" (or silently resolves against an unrelated CWD), with no signal that `default_path`'s interpretation — not the preset's `argv` — is the cause. | Add one sentence to the Domain Glossary/Pattern Decisions pinning down `default_path`'s exact resolution semantics, add load-time validation rejecting ambiguous forms, and add an acceptance criterion/test exercising a relative `default_path` end-to-end. | P3 |

## P1 Items (address before implementation)
- [x] #1 — `buildLaunchCommand`'s `plainProgram` case must shell-quote `i.Program` (or `validateLauncherPresets` must reject metacharacter-bearing `argv[0]` values) before Phase 2 lands; extend Story 2.2.1's acceptance criteria to explicitly test a metacharacter-bearing `argv[0]`, since the current plan only specs quoting tests for `ExtraArgs` elements, leaving `Program` — the one field every preset always populates — untested for the exact corruption class this feature exists to prevent.
  **Resolved in `implementation/plan.md`**: Story 2.2.1 and Task 2.2.1a now shell-quote the
  `plainProgram` base token (`cmd = shellQuote(p.cmd)`) in addition to `CLIFlags`/`ExtraArgs`,
  with a dedicated metacharacter-injection AC and test case.
