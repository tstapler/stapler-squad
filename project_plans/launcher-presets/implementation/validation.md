# Validation Plan: launcher-presets

**Date**: 2026-08-06

## Happy Path Scenario

Given a user has at least one launcher preset configured in `~/.stapler-squad/launcher-presets.json` and opens the Omnibar, when they click a preset row in the Presets section and then click Create Session (or press Ctrl+Enter), then a new session launches running the preset's `argv`-derived program with its extra arguments and working directory exactly as configured, with no shell-quoting corruption.

## Test Stack

- **Unit**: Go `testing` package, table-driven style (`config/`, `session/`, `server/services/`), matching this repo's existing convention; TypeScript via Jest + React Testing Library (`web-app/`) for hooks, detectors, and components — `getByRole`/`getByTestId` queries only, no CSS-class assertions.
- **Integration**: Go — `server/services/*_test.go` using `t.Setenv("STAPLER_SQUAD_TEST_DIR", t.TempDir())` for real-filesystem, instance-isolated config reads (the existing config-isolation convention); frontend — RTL tests that exercise `OmnibarContext.tsx` + `useSessionService.ts` together with a mocked ConnectRPC client, verifying the full form-state → RPC-body threading path.
- **E2E / UX**: Playwright (`tests/e2e/launcher-presets.spec.ts`), driven against the isolated per-run test server (`tests/e2e/global-setup.ts`), with a `launcher-presets.json` fixture seeded into `STAPLER_SQUAD_TEST_DIR` before server start (verify/extend seeding support per Task 6.2.1a). Locators: `getByTestId`/`getByRole` only; no `waitForTimeout`; feature annotation header `// @feature launcher_presets:get, launcher-presets-list`.

## Coverage Targets and How to Measure

| Stack | Coverage command | Target |
|---|---|---|
| Go | `go test ./... -coverprofile=coverage.out && go tool cover -func=coverage.out` | ≥80% line, with `config/launcher_presets.go`, `server/services/launcher_presets_service.go`, and the `buildLaunchCommand` `ExtraArgs` loop in `session/instance_tmux.go` at 100% (shell-quoting correctness is the feature's core risk) |
| TypeScript/Jest | `npx jest --coverage --coverageThreshold='{"global":{"lines":80}}'` | ≥80% line, with `useLauncherPresets.ts`, `PresetDetector.ts`, and `OmnibarPresetList.tsx` prioritized to near-100% given their direct mapping to UX-visible states |

- All public service methods: happy path + error paths covered — `LoadLauncherPresets`, `GetLauncherPresets`, `buildLaunchCommand`, `CreateSession`'s `ExtraArgs` fold, `useLauncherPresets`, `PresetDetector.detect`.
- All external integrations: unit mocked (Jest mocked ConnectRPC client) + at least one integration test (Go `server/services` tests hitting a real isolated filesystem via `STAPLER_SQUAD_TEST_DIR`; RTL `OmnibarContext` + `useSessionService` integration test).
- UX acceptance criteria: all 16 criteria in `design/ux.md` §9 have a corresponding automated test (Playwright or RTL) or an explicit manual/CI-gate step (contrast via Axe CI, no-CSS-selectors via PR-review grep).
- Migration test: **N/A** — `implementation/plan.md`'s Migration Plan states this is a new, additive JSON config file and a purely-additive proto field; no database schema changes, no `config.json` changes, and existing installs default to zero presets with no `load_error`. That default-empty-state behavior is itself covered by `LoadLauncherPresets_should_ReturnNotExistError_When_FileIsMissing` and `GetLauncherPresets_should_ReturnEmptyPresetsNoError_When_FileIsMissing` above.
