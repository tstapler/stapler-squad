# Pre-mortem: jest-ci
**Date**: 2026-08-02

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Task 1.3.1's `gh issue create` is best-effort/non-blocking (plan.md's own design). If `gh` isn't authenticated for issue creation in whatever environment executes this plan, Task 1.3.2 ships `TODO(#TBD)` in both test files, and nothing in the plan forces a human to circle back — the quarantine (including the real `SessionDetail` a11y regression: missing `tablist`/`tabpanel` roles) becomes permanent. | `grep -rn 'TODO(#TBD)' web-app/src` still matches weeks/months after merge; no linked GitHub issue exists. | Make the issue number a hard requirement before the PR is marked ready (fail the task, don't degrade to `TBD`), OR add a scheduled check that greps for `TODO(#TBD)`/stale `TODO(#N)` older than N days and fails a workflow to force follow-up. | P1 |
| 2 | `.github/workflows/jest.yml`'s exit-code-preserving script (`set +e`/`set -o pipefail`/`PIPESTATUS[0]`/`tee`/ANSI-stripping `sed`/`$GITHUB_STEP_SUMMARY` append) is verified only via Story 2.3's bare local `npx jest` run, never the actual multi-line `run:` block on a real `ubuntu-latest` hosted runner — plan.md's own Unresolved Question #4 admits this gap. | First real PR shows either an empty/missing Summary tab on a run that should have one, or (worse) a red Jest failure whose job status still reports green because the real exit code got masked somewhere in the pipe. | Add a Story 2.4 task: push the branch and let `jest.yml` run for real at least twice (once green, once with a deliberately broken test) before merging, instead of treating "first exercise happens on the shipping PR" as acceptable. | P1 |
| 3 | `--maxWorkers=2` is a guess, explicitly "not derived from this repo's actual `ubuntu-latest` vCPU count (not queried at planning time)" per plan.md. If it's meaningfully slower than local runs, the new check becomes the thing developers wait longest on and start merging around, bypassing, or asking to disable. | `jest.yml` step duration is visibly longer than the local baseline; PR comments/chat complaints about "Jest CI is slow." | Query actual runner core count (GH-hosted `ubuntu-latest` = 4 vCPUs) before pinning, or use `--maxWorkers=50%` instead of a hardcoded absolute; log run duration in the Step Summary so degradation is visible before it's a complaint. | P2 |
| 4 | `--selectProjects web-app` is hardcoded, and `jest.yml`'s `paths:` filter is scoped to `web-app/**` only. `jest.config.js`'s `dev-stack` and `e2e-dev-mode` projects have `roots` at `scripts/dev-stack/**` and `tests/e2e/**` — entirely outside `web-app/`. If either project is later promoted into CI (a change this plan explicitly defers as an open decision), a change to only `scripts/dev-stack/**` or `tests/e2e/**` won't even trigger the workflow, on top of `--selectProjects` still excluding it. | A bug ships in `scripts/dev-stack` or `tests/e2e`'s Jest unit tests (e.g. `global-setup.dev-mode.test.ts`) with zero CI signal — not a false-green, literally no run — discovered only when someone runs `npx jest` locally against `main` and it fails. | `.claude/rules/jest-ci.md` (Story 3.1) should explicitly document that expanding `--selectProjects` also requires adding the corresponding path(s) to `jest.yml`'s `paths:` filter — frame it as a 2-part touchpoint list, mirroring this repo's own `.claude/rules/session-creation-registry.md` pattern, not just prose. | P2 |
| 5 | Turning the CI gate green creates false confidence that "tests are wired up, we're covered," while the two real bugs behind the quarantine (an unhandled-rejection crash and a real a11y regression) sit unfixed indefinitely with no forcing function beyond a single GitHub issue that itself may never get created (see #1). | The a11y regression or crash bug surfaces via a user/support report or a `ux-analysis.yml` Axe failure months later; whoever triages it finds a stale, unassigned, un-prioritized issue open since the jest-ci PR merged. | Link the quarantine issue into an actual tracked/prioritized backlog item (not just a bare `gh issue create`), and add an expiry check (lint rule or scheduled workflow) that flags `// TODO(#N): quarantined` comments older than ~90 days so quarantine can't silently outlive its "temporary" framing. | P2 |

## P1 Items (address before implementation)
- [ ] #1 — Change Task 1.3.1/1.3.2 so a missing real issue number blocks PR completion (or add a scheduled staleness check for `TODO(#TBD)`/aged `TODO(#N)` comments), instead of silently shipping `TODO(#TBD)` as an acceptable terminal state.
- [ ] #2 — Add a Story 2.4 task requiring at least one real green run and one real red run of the actual `jest.yml` workflow (not just bare local `npx jest`) on a pushed branch before the PR is considered mergeable, closing plan.md's own Unresolved Question #4 gap instead of deferring it to the shipping PR.
