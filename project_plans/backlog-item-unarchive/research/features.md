# Research: Similar Features (Agent 2 — Features)

## 1. Session archive/unarchive vs. backlog archive: structural diff

| Aspect | Session (`ArchiveSession`/`UnarchiveSession`) | Backlog (`ArchiveBacklogItem`) |
|---|---|---|
| RPC location | `proto/session/v1/session.proto:396-401` | `proto/session/v1/backlog.proto:739-740` — only `ArchiveBacklogItem` exists, no unarchive RPC |
| Handler | `server/services/session_service.go:4213` (`ArchiveSession`), `:4234` (`UnarchiveSession`) — mirror-image, ~15 lines each | `session/ent_repository_backlog.go:741` (`ArchiveBacklogItem`) — no counterpart |
| State mutation | `inst.SetArchivedAt(&now)` / `inst.SetArchivedAt(nil)` — **only** field touched | `ArchiveBacklogItem` sets **two** fields atomically: `SetArchivedAt(now)` **and** `SetStatus(string(BacklogStatusArchived))`, plus `SetUserModifiedStatusAt(now)` (`session/ent_repository_backlog.go:756-760`) |
| Precondition / CAS | None — plain `FindLiveInstance` + unconditional save, no optimistic concurrency check | None either for `ArchiveBacklogItem` (plain `Get` then `UpdateOneID`) — **but** the sibling `TransitionBacklogItemStatus` (used for every other status change) has a genuine SQL-level CAS via `precondition.ExpectedStatus`/`ExpectedUpdatedAt` folded into the `UPDATE ... WHERE` clause (`session/ent_repository_backlog.go:850-917`), added specifically to close a read-then-write TOCTOU race (see `docs/bugs/fixed/BUG-026-backlog-transition-status-toctou-reopen.md`). `ArchiveBacklogItem` was never migrated to this pattern. |
| Audit trail | None — sessions have no event/history log analogous to `BacklogStatusEvent` | `recordStatusEvent(...)` appends an immutable `BacklogStatusEvent` row on every archive (`ent_repository_backlog.go:768`) and on every `TransitionBacklogItemStatus` call (`:938`). | Status-machine guard | N/A — sessions have no status enum | `session/domain/backlog.go`'s `validTransitions` table already has `BacklogStatusArchived: {BacklogStatusIdea: true}` (line 385-387), i.e. `archived → idea` is the *only* legal transition out of archived. ### Key implication for design

`ArchiveBacklogItem` is a bespoke method that duplicates status-mutation logic already centralized in `TransitionBacklogItemStatus` (it does its own `SetStatus`/`SetUserModifiedStatusAt`/`recordStatusEvent`/`publishItemChanged` sequence rather than calling the shared transition method). An `UnarchiveBacklogItem` has two viable shapes:

1. **Dedicated method mirroring `ArchiveBacklogItem`** (symmetric with sessions' pattern) — sets `status = idea`, clears `archived_at`, records the event, publishes `ChangeItemArchived`-style with `ArchivedAt: nil` (or a new `ChangeItemUnarchived` kind — the frontend's `useWatchBacklogItems.ts` explicitly does *not* fold `itemArchived` into `backlogItemsSlice` per its file-header note 1, so a symmetric `itemUnarchived` case needs the same treatment, not a silent gap).
2. **Fix `TransitionBacklogItemStatus` to clear `archived_at`** whenever the `toStatus` isn't `archived` (a one-line addition: `SetNillableArchivedAt` cleared unless `toStatus == BacklogStatusArchived`), then call it with `toStatus = idea` and a precondition of `ExpectedStatus: "archived"`. This is the only approach that gets the TOCTOU-safe CAS "for free" (unlike a bespoke `UnarchiveBacklogItem` copy of `ArchiveBacklogItem`, which would inherit `ArchiveBacklogItem`'s *lack* of a precondition). Requirements.md (line 55) leaves this choice open for `plan.md`, but the CAS gap is a concrete argument for option 2, or at minimum for adding a precondition to a bespoke option 1.

Either way, `ArchiveBacklogItem` itself has no precondition today (a concurrent double-archive or archive-during-delete race is unguarded) — that's a pre-existing gap the ask explicitly puts out of scope ("Existing `ArchiveBacklogItem` / delete behavior is unchanged"), so it shouldn't be silently fixed as a side effect, but an `UnarchiveBacklogItem` built on `TransitionBacklogItemStatus` should not reintroduce it for the *new* path.

## 2. Edge cases / failure modes for `UnarchiveBacklogItem`

- **Item concurrently deleted while archived.** `DeleteBacklogItem` (`ent_repository_backlog.go:783`) hard-deletes the row and cascades to `ItemSession`/`ReviewVerdict`. If unarchive races a delete, `TransitionBacklogItemStatus`'s `Get` at the top will hit `ent.IsNotFound` → `ErrNotFound`, which is already handled cleanly by the existing method. No new work needed here beyond surfacing `ErrNotFound` as 404 in the RPC handler, same as `ArchiveBacklogItem`'s existing `NotFound` handling.
- **Item's linked sessions/worktrees already cleaned up.** `archiveStaleDoneItems` and the terminal-item-session sweep (`session/backlog_lifecycle.go:1358-1368`, tests at `backlog_lifecycle_stuck_test.go:1575` `TestReconcileTerminalItemSessions_should_ArchiveWorkSession_When_ItemAlreadyArchived`) archive the item's *sessions* (not delete them) when the item reaches done/archived. Unarchiving the item does **not** automatically resurrect those sessions — they stay archived. This is almost certainly correct behavior (matches how `UnarchiveSession` never touches backlog items), but it means "unarchive" only restores the item to the active board, not its historical sessions/worktrees to a live state. Worth an explicit non-goal note in plan.md so nobody assumes symmetric session restoration.
- **Double-archive / double-unarchive races.** Two concurrent `archive` calls, or an unarchive racing a second unarchive, or an unarchive racing an in-flight archive — this is exactly the TOCTOU class `TransitionBacklogItemStatus`'s CAS was built to close (BUG-026). If `UnarchiveBacklogItem` is built as a bespoke method copying `ArchiveBacklogItem`'s unconditional read-then-write, it reintroduces that exact race for the unarchive direction. Building it on `TransitionBacklogItemStatus` with `precondition.ExpectedStatus = "archived"` closes this for free and reports `ErrPreconditionFailed` (mappable to a `FailedPrecondition` Connect error) if the item moved on in the meantime.
- **Restoring to something other than "idea" if business rules change.** The state machine (`validTransitions["archived"]`) hardcodes exactly one legal target (`idea`). If a future business rule wants e.g. `archived → ready` for items that were fully triaged before archiving, that's a `CanTransitionBacklog` table change — explicitly out of scope per requirements.md ("Any change to the `archived -> idea` transition guard rules themselves"). The unarchive RPC/method should hardcode `toStatus = idea` rather than accepting an arbitrary target status, so it can't be used to bypass the guard table; if the guard table changes later, the RPC's fixed target would need a matching update, but that's a deliberate follow-on, not something to build flexibility for speculatively now.
- **Items auto-archived by the stale-done sweep (`archiveStaleDoneItems`, `session/backlog_lifecycle.go:1334-1353`).** This sweep calls `TransitionBacklogItemStatus` (not `ArchiveBacklogItem`!) with `TriggeredBySystem`, running every reconcile tick (`maxDoneAge` constant, `:277`). Two consequences: (a) system-auto-archived items currently do **not** get `archived_at` set at all today — `TransitionBacklogItemStatus` never touches that field, so an item auto-archived by the sweep has `status=archived` but `archived_at=null`, a pre-existing inconsistency the requirements doc's problem statement calls out generally ("`TransitionBacklogItemStatus` never clears `archived_at` on any transition" — the flip side is it also never *sets* it). If `UnarchiveBacklogItem`'s precondition is `ExpectedStatus: "archived"` (not keyed off `archived_at`), auto-archived items are still unarchivable through the new path, which is good — but it's worth confirming in the plan that the fix path (whichever of the two shapes above) also makes `TransitionBacklogItemStatus` *set* `archived_at` when transitioning **into** archived (symmetric with clearing it on the way out), or the "no stale archived timestamp" AC1 language ends up only half-true (no *stale* timestamp, but also no *correct* one for system-archived items). A retriggered sweep tick immediately after a manual unarchive is idempotent by construction (item is back in `idea`/active, not `done`, so `FindDoneItemsOlderThan` won't pick it up) — no race there.
- **Concurrent transition out of archived via a different path.** Since `archived → idea` is the only guarded transition, and no other code path currently calls `TransitionBacklogItemStatus(toStatus=idea)` from `archived` except a hypothetical manual API/future UI action, the practical concurrent-writer set is small (the new unarchive button + any direct API caller). Still, using the CAS precondition removes any ambiguity.
- **archived_at semantics under the CAS-fix option.** If `TransitionBacklogItemStatus` starts unconditionally clearing `archived_at` for every non-archived target status, verify no other status column or feature (e.g. `docs/registry` features, "Show Archived" filter logic in the list view) relies on `archived_at` remaining non-null while `status` briefly diverges (e.g. mid-transition) — the update is a single SQL statement (`SetArchivedAt` + `SetStatus` in the same `Update()` chain), so it's atomic, no torn-read window.

## 3. Unstated user needs

- **Undo-toast instead of (or in addition to) a separate button.** `BacklogItemDetail.tsx` already has a toast mechanism (`showActionToast`, `ACTION_SUCCESS_MESSAGES`, e.g. `archive: "Archived."` at line 70) used for every action's success/error feedback. The archive action's own success toast is a natural place to add an "Undo" affordance (toast action button calling the new unarchive path) — this is the single most common pattern for "casually reversible" actions in web UIs, and the requirements' own AC0 (add a confirmation dialog to archive because it currently reads as irreversible) would be *less* necessary if an undo-toast existed instead of/alongside a confirm() dialog. This isn't in the explicit ask (which asks for a confirm() dialog matching delete's pattern, plus a persistent Unarchive button for later), but is worth flagging to the user/planner as an alternative or complementary UX to the confirm-dialog requirement, since confirm() dialogs are more disruptive than an undo toast for a reversible action.
- **Bulk unarchive from "Show Archived" list view.** Requirements.md explicitly puts this out of scope ("Bulk unarchive / 'Show Archived' list-level restore affordance (single-item action only, matching the ask's scope)"), but it's a predictable near-term follow-up: once single-item unarchive exists, users who archived several items (e.g. a batch caught by `archiveStaleDoneItems`) will want to restore more than one without opening each item's detail view. Worth noting as a natural "Ask #2" for a future backlog item rather than scope-creeping into this one.
- **Visibility into *why* an item is archived (manual vs. auto-swept).** Since `archiveStaleDoneItems` auto-archives items with `TriggeredBySystem` while manual archive uses `TriggeredByUser` (both recorded in `BacklogStatusEvent.TriggeredBy`), a user restoring an item from "Show Archived" may want to see whether it was archived by them or by the stale-done sweep before deciding to restore it — this data already exists in the audit trail (`BacklogStatusEvent`) and could be surfaced in the archived-item card/detail view without new backend work, satisfying AC3's audit-trail requirement doubly (both recording the *new* unarchive event and surfacing the *existing* archive event's provenance).
