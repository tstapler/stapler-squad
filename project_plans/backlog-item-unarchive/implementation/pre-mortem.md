# Pre-mortem: backlog-item-unarchive
**Date**: 2026-08-29

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The gated `ClearArchivedAt()` check reads `current.Status` from a non-atomic pre-write `Get()` (`session/ent_repository_backlog.go:894` per plan), reintroducing the exact TOCTOU race BUG-026 fixed for the write path — but now for the archived_at-clear decision. Most internal callers pass `precondition == nil` (`backlog_service_sync.go:122`, `backlog_lifecycle.go:3163`, `backlog_service_triage.go` ×9, `autonomous_orchestration_service.go:506`), and `ArchiveBacklogItem` (`session/ent_repository_backlog.go:741`) has *no* CAS/precondition at all — confirmed by ADR-001's own rationale #2 — so it can race with any concurrent `TransitionBacklogItemStatus` call and land its `archived_at` write in the gap between that call's `Get()` and `Update()`. | An item shows a non-archived status in the default list, but `GetBacklogItem` (or a DB query) still returns a non-null `archivedAt` — surfaces as a confusing support report, not a test failure, since no test exercises concurrent Archive+Transition. | Call `.ClearArchivedAt()` **unconditionally** on every `TransitionBacklogItemStatus` update (idempotent no-op when already null) instead of gating on a pre-write status snapshot — removes the race entirely. Add a goroutine-based regression test racing `ArchiveBacklogItem` against `TransitionBacklogItemStatus` on the same item, matching the existing BUG-026 test style. | P2 |
| 2 | `CanTransitionBacklog`/`s.engine.CanTransition` is enforced only in `BacklogService.TransitionBacklogItemStatus` (`server/services/backlog_service_lifecycle.go:504`), the one RPC handler. `EntRepository.TransitionBacklogItemStatus` itself — called directly by ~15 other sites (triage sweeps, autonomous orchestration, sync, the MCP tool, the debug-mutate handler) — has no such guard. ADR-001's premise that "archived → idea" is the only way to leave archived holds only for the UI/RPC path, not at the repository layer this feature edits. | An archived item's audit trail shows a `BacklogStatusEvent` with `from_status: archived, to_status: <something other than idea>` — caught by log/DB inspection, not by any test in this plan, since Phase 1's new test only calls the repository method with a valid target. | Add a defense-in-depth check inside `EntRepository.TransitionBacklogItemStatus` (`if !CanTransitionBacklog(...) { return err }`), or at minimum add a plan task to audit all direct-repository callers and confirm none can ever target an archived item with a non-idea status, documenting the finding in ADR-001. | P3 |
| 3 | Epic 2.3's Jest coverage only exercises the happy path (button renders; click calls `transitionStatus`) and the "does not render" case — no test simulates `transitionStatus` rejecting (e.g. `ErrPreconditionFailed`/`CodeAborted` from a raced double-click), so the error-toast/`actionLoading`-reset behavior for this specific action is unverified. | A user double-clicks Unarchive (e.g. slow network); the second click's rejection produces no visible feedback and the button stays disabled — reported as "Unarchive doesn't work," not caught in CI. | Add a Jest case to `BacklogItemDetail.archiveConfirmAndUnarchive.test.tsx`: `transitionStatus.mockRejectedValueOnce(...)` for the unarchive case, asserting an error toast fires and `actionLoading` resets. | P2 |
| 4 | Task 3.2.1a itself flags "verify the exact field casing... before finalizing" as an open TODO rather than a resolved decision — the spec as drafted may not pass on first run. Separately, the e2e seed helpers (`createBacklogItemDirect`/`archiveBacklogItemDirect`) route through `backlog_debug_mutate_handler.go:166`, which calls `storage.TransitionBacklogItemStatus(..., nil, ...)` — a nil-precondition caller of the exact kind implicated in failure #1, so parallel e2e workers touching overlapping state could intermittently hit that race and fail non-deterministically for reasons unrelated to the feature under test. | The new Playwright spec is red or flaky immediately post-merge — either a `TypeError` from a field-casing mismatch, or an intermittent status-mismatch assertion failure under parallel workers. | Resolve the casing question during plan review (grep an existing e2e spec that already asserts on a `GetBacklogItem` JSON response and copy its field-access pattern verbatim) instead of leaving it to implementation time; confirm test isolation (unique IDs, already done via `Date.now()`) is sufficient before merging, or pin `--workers=1` for this spec. | P2 |
| 5 | Task 2.1.1a's diff is a one-line change to `case "archive":`, immediately adjacent to `case "delete":` in the same switch, in a codebase written almost entirely by LLM agents (per this repo's own CLAUDE.md). No test in Epic 2.3 pins delete's confirm *message* text — only that `deleteBacklogItem` is/isn't called — so a copy/paste slip that leaves archive's non-destructive wording ("can be restored later") on the delete case, or vice versa, would pass every test in this plan. | A user deletes an item, sees reassuring "can be restored later" copy, and is surprised the item is actually gone — a silent product/UX regression, undetected because AC4 ("existing delete tests continue to pass") doesn't cover message text. | Add a Jest assertion pinning delete's existing confirm message text as a regression guard in the same new test file that adds the archive message assertion. | P3 |
