# Pre-mortem: backlog-bounce-escalation
**Date**: 2026-08-11

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `multiReasonThreshold = 2` fires on the structurally-paired `bouncing` + `abandoned_review` combination almost every time an item bounces, because `markAbandonedReview` already internally gates its own respawn on the same bouncing remediation gate (`session/backlog_lifecycle_review.go:553`, proven by `TestMarkAbandonedReview_SkipsRespawn_WhenBouncingGateNotDue`, `session/backlog_lifecycle_test.go:1158`) — the two reasons are not independent signals, so "2 simultaneous reasons" degrades from "distinct escalation" to "every bouncing item eventually." | Within days of shipping, most/all currently-bouncing items (not just the 2-3 flagged in requirements.md) carry an open `multiple_reasons` row — the Stuck Items panel's "escalated" group becomes as large as the "bouncing" group instead of a distinguishing subset, silently defeating the requirement's own success metric ("visibly distinguished... from a single-reason stuck item"). | Before implementing Story 1.2.2, query current/historical `backlog_stuck_states` for `bouncing`+`abandoned_review` co-occurrence rate; if high, either exclude `abandoned_review` from the count when it co-occurs with an already-gated `bouncing` row (treat it as a derived consequence, not an independent reason), or raise the threshold for that specific pair. Don't wait for the plan's own "re-check after ~1 week of live data" — this is checkable against existing rows *before* writing code. | P1 |
| 2 | No de-escalation hysteresis (explicitly deferred per Pattern Decisions/Unresolved Questions) combined with notify-once-per-*row* semantics means an item whose open-reason count oscillates around the threshold (e.g. `abandoned_review`'s zombie-session detection flickering tick-to-tick) gets `ResolveStuck`'d and re-`MarkStuck`'d repeatedly, and each re-open resets `NotifiedAt` to nil — so once the new dwell elapses again, a fresh ERROR/URGENT notification fires again for the same underlying condition. | Repeated near-duplicate "Multiple stuck reasons open" notifications (minutes to tens-of-minutes apart) for one item that never actually resolved anything, i.e. notification-fatigue on the exact single-user notification surface the feature was meant to make trustworthy. | Add a minimal cooldown: don't notify again for `StuckReasonMultipleReasons` if the row was resolved and re-opened within e.g. one dwell window of its last `NotifiedAt`. Requires no new column — comparable to how `multiReasonEscalationNotifyReady` already derives from `FirstDetectedAt`; a symmetric "was recently resolved" check can reuse the resolve path's own timestamp. Flag explicitly in Unresolved Questions as a pre-ship, not post-ship, decision. | P2 |
| 3 | **[FIXED — see plan.md Task 2.1.1c / 2.1.3c]** The escalation-reason exclusion (`multiple_reasons`/`bounce_cap_exhausted` must not count themselves or each other) is implemented in the Go backend detector's count (Task 1.2.2a, tested by Story 1.2.4c) but explicitly **not** applied to the frontend — the Domain Glossary states `otherReasonsCount`/`otherReasonLabels` in `StuckItemsSection.tsx` are "Unchanged — the two new reasons flow through this existing computation automatically." | An escalated item's card shows an inflated "+N other reasons" badge that includes the escalation reason(s) themselves (e.g. a `multiple_reasons` card whose own badge lists `bounce_cap_exhausted` as "another reason," or vice versa) — self-referential and confusing exactly where the requirement demanded clarity, and it's the mirror-image of the self-reinforcement bug the backend went out of its way to test for. | Add a task under Story 2.1.1 (or a new subtask) to exclude `StuckReason.MULTIPLE_REASONS`/`StuckReason.BOUNCE_CAP_EXHAUSTED` from `StuckItemsSection.tsx`'s `otherReasonsCount`/`otherReasonLabels` grouping, mirroring the backend's Task 1.2.2a exclusion, plus a render test asserting an item with 2 real reasons + 1 escalation reason shows "+1," not "+2." | P2 |
| 4 | Both new `MarkStuck` call sites (Task 1.2.2a, Task 1.3.1b) are explicitly "best-effort" — errors, including an `expectedStatus` precondition mismatch (`applied=false`), are logged and swallowed, never retried within the tick. Signal 1 self-heals next tick since `reconcileMultiReasonEscalation` re-evaluates from scratch every 60s, but Signal 2's `MarkStuck` fires once, synchronously, inside an event-triggered handler (`handleReviewSessionExited`) with no periodic backstop if that one call's `itemStatus` snapshot is stale relative to a concurrent status write. | An item that hit `MaxRemediationAttempts` while still bouncing (the requirement's own item 2 motivating example) never gets a `bounce_cap_exhausted` row — no error surfaces to the user, only a log line — so the exact "capped while still bouncing" case the feature was built to surface silently doesn't. | Add a reconcile-tick backstop detector (or extend an existing one, e.g. alongside `reconcileBouncingItems`) that re-derives "is this item at-cap while `bouncing` is open but no `bounce_cap_exhausted` row exists" and creates the row if missing — the same self-healing property Signal 1 gets for free from being tick-driven. Add a test that forces `applied=false` on the Signal-2 `MarkStuck` call and asserts the backstop catches it next tick. | P2 |
| 5 | The differentiated ERROR/URGENT notification treatment is wired only into the `bouncing` reason's backoff-gate call site (`session/backlog_lifecycle_review.go:208`); the structurally identical `justParked` pattern in `backlog_lifecycle_pr.go:881,1210` (push-failed gate) and `backlog_lifecycle_stale.go:240` (stale-work gate) keep emitting the old generic WARNING/HIGH "use Reset" copy, per requirements.md's own Baseline listing all four call sites. | A user who has learned "ERROR/URGENT = non-converging retry loop, needs a different approach" from the `bouncing` case will misread the *absence* of that differentiated notification on a similarly-capped `push-failed` or `stale-work` item as "this one's just an ordinary park" — when structurally it's the same cap-exhaustion condition, just on a different reason. | Either extend the same `justParked`-branch treatment to the push-failed and stale-work gates in this same project (small, mechanical — same pattern, ~10-15 min per site per the plan's own task-sizing), or add an explicit line to requirements.md/plan.md scoping this to `bouncing` only and file the other two gates as a named fast-follow, so the inconsistency is a tracked, known gap rather than a surprise found live. | P3 |

## P1 Items (address before implementation)
- [x] Failure #1 — **Addressed in plan.md** (Task 1.2.2a + new Task 1.2.2e regression test):
  the code-level coupling between `abandoned_review` and `bouncing`
  (`markAbandonedReview`/`TestMarkAbandonedReview_SkipsRespawn_WhenBouncingGateNotDue`)

  the non-escalation count when it co-occurs with an open, gate-blocked `bouncing` row,
