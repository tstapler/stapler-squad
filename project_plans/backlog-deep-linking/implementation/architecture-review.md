# Architecture Review: backlog-deep-linking
**Date**: 2026-08-19 (re-review of ADR-002 fix pass)

## Blockers

- [x] **RESOLVED — Story 3.2 / ADR-002 ("Advertisement exchange piggybacked on existing peer polling")**. plan.md itself is internally consistent and no longer asserts piggybacking: Step 0.5's Cross-host registry row (`plan.md:11`) and its "Architecture review finding" callout state a new HTTP transport is built, not an extension of an existing loop; the Pattern Decisions table's Cross-host registry row (`plan.md:37`) cites real, verified citations; Unresolved Question 1 (`plan.md:73`) is marked resolved with the same finding; and Story 3.2 is rewritten around a new endpoint rather than a piggyback spike.

  ADR-002 has now been updated to match: its Decision section item 2 (`ADR-002:47-70`) opens "A minimal new HTTP advertisement transport on the existing `--remote-port` server, not a piggyback," explicitly states "There is no existing inter-host transport to piggyback on, so this ADR corrects its original premise" (`ADR-002:51-52`), and describes advertisement propagation via `POST` calls to a new `/internal/host-advertisement`-style endpoint (`ADR-002:64-70`). The Consequences section's transport bullet (`ADR-002:115-118`) now reads "New minimal HTTP transport: an advertisement-receiving endpoint on the existing `--remote-port` server ... plus a new periodic background task that sends advertisements to known hosts" — the prior "extends existing peer-polling loop" language is gone. A file-wide grep of both ADR-002 and plan.md for "piggyback"/"extend the existing peer" turns up no remaining assertion of piggybacking anywhere in either file — every hit is in corrective context (negating the old premise, e.g. `ADR-002:48,51`, `plan.md:11,37,73,350,358,362`). The two code citations ADR-002 relies on are accurate: `main.go:1055` is `func startRemoteAccess(ctx context.Context, srv *server.Server, localAddr string, cfg *config.Config, remotePort int) error` and `server/auth/handlers.go:22` is `func RegisterRoutes(mux *http.ServeMux, waHandler *Handler, sessions *SessionManager, store *CredentialStore, setup *SetupManager, invites *InviteManager, tlsCAPath, primaryDomain string, remotePort int)` (both confirmed by direct read of the source). ADR-002 and plan.md now describe the same design; a reader who opens either file gets a consistent, correct account.

## Nitpicks

- The `BacklogItemID` type-shape decision (plan.md's Pattern Decisions table, Story 1.1) cites "following `RepoRef`/`AccountRef`" as precedent, but only `RepoRef` (`github/repo_ref.go:11-25`, unexported fields + validating `NewRepoRef` constructor) actually matches the smart-constructor pattern the primitive-obsession checklist wants. `AccountRef` (`github/keychain.go:51-54`) has exported fields and no validating constructor, so it's not really precedent for the pattern being followed. Doesn't change the technical decision (which correctly follows `RepoRef`'s shape) — just fix the citation in ADR-001/plan.md so it doesn't point future readers at the wrong example.
- `resolveBacklogItemLookup(raw string) (lookupKind, error)` and `ParseDeepLink(raw string) (DeepLink, error)` (Stories 1.3, 2.1) are each single-primitive-param functions, so they're clean on the primitive-obsession checklist — noted only because they're exactly the kind of dispatcher function where a second same-typed parameter tends to get added later (e.g. a second string for "expected type"); worth a comment at each site flagging that a second string param should trigger a newtype review rather than being added ad hoc.
- Epic 3's `Advertise(entry)` / `Prune(ttl)` methods on the registry (Story 3.2 task 2) are well-shaped (single struct/duration params, no primitive piles) — no action needed, called out only as a positive contrast to the Blocker above so the transport-layer concern isn't read as a criticism of the registry's own API design, which is fine.
