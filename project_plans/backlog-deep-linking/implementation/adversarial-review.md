# Adversarial Review: backlog-deep-linking

**Date**: 2026-08-19
**Verdict**: CLEAR

## Re-review: Blockers (2026-08-19, post-fix-pass)

Scoped re-check of the 3 previously-BLOCKED items against the patched `implementation/plan.md`. All 3 are RESOLVED; overall verdict is CLEAR. (Concerns and Minors below are carried over unchanged from the prior pass — not re-litigated in this re-review.)

- [x] **RESOLVED — macOS scope cut evidence.** Step 0.5's macOS row (`plan.md:12`) and the Pattern Decisions table's macOS row (`plan.md:38`) now cite a concrete, verifiable mechanism rather than an assertion: `make install-service`'s macOS binary embeds `Info.plist` into the `__TEXT/__info_plist` Mach-O section via `CGO_LDFLAGS="-sectcreate ..."` and is deliberately kept out of a bundle-directory layout — confirmed by reading `.claude/docs/codesigning.md`'s "How it works" section, which states `Info.plist` lives in `macos/` (not alongside the binary) specifically so `codesign` doesn't auto-detect a bundle and seal this repo's 80k+ tracked/untracked files, which would break `codesign --verify` on any untracked-file change. The plan correctly reasons that `CFBundleURLTypes` registration depends on Launch Services (`lsregister`) scanning a real `.app` bundle on disk, which this binary structurally is not, and frames building one as a packaging-model change orthogonal to this feature. Critically, the plan does **not** silently resolve the contradiction: `plan.md:38` and Unresolved Question 3 (`plan.md:75`) both explicitly state this deferral "contradicts requirements.md's Success Metrics/In-Scope wording" and must be "confirmed with the user before this plan is treated as final" rather than being a unilateral rewrite of the requirement. This matches the acceptable resolution shape (flag-for-user-decision, honest about the contradiction).

- [x] **RESOLVED — Piggyback spike for Story 3.2 (Unresolved Question 1).** Story 3.2 now has an explicit Task 0 (`plan.md:239`), marked "do first, before any other Story 3.2 task," requiring enumeration of every existing inter-instance polling/heartbeat loop in `session/`, a committed decision on which one to piggyback on (or an explicit "new poller needed" call), and recording that decision in a code comment at the integration point *before* Task 1 starts. It also adds a caveat that the task list/estimate is contingent on the spike's outcome. This converts the previously-assumed design into a required pre-implementation decision point, closing the "decided mid-implementation" risk for a Large-appetite project's core cross-host mechanism.

- [x] **RESOLVED — Story 1.2/1.4 public_id NULL vs empty-string mismatch.** Story 1.2 Task 3 (`plan.md:131`) now requires verifying the real ent-generated zero-value behavior for an unset `public_id` field (via the generated ent client, not a manual DB insert), explicitly deciding `.Nillable()` vs. plain-string-`""` based on that finding, and recording the decision as a schema-field comment. Story 1.4's given/when/then (`plan.md:153-158`), its Task 1 (`plan.md:161`), and the Migration Plan's backfill step (`plan.md:48`) all now reference "whichever predicate Story 1.2 task 3 determined" (`public_id.IsNil()` vs. `public_id == ""`) instead of asserting `== ""` unconditionally, and Story 1.4 explicitly calls out that assuming `== ""` without verification "risks a silent no-op backfill." The decision and its consumption are now consistent across both stories.

## Concerns

- [ ] **Gossip non-convergence mitigation is detection-only.** The Risk Control table's mitigation for "Gossip registry never converges / silently stuck" is a metric plus a `--list-known-hosts` inspection command — both diagnose the problem but no remediation path (forced re-broadcast, manual reset) exists once it's observed, for a tool with no on-call. — *Recommendation*: add a manual "force re-advertise" escape hatch, or explicitly accept "restart the process" as the documented remediation.
- [x] **RESOLVED — No integrity check on advertisement records.** Raised again independently by the Phase 4 Product Triad Review's Engineering lens (2026-08-19) and fixed in the same pass: ADR-002 now requires each instance to generate an Ed25519 keypair alongside its `HostIdentity`, sign every outgoing advertisement, and TOFU-pin the public key on first observation per `HostIdentity` — a later advertisement claiming the same identity is dropped if its signature doesn't verify against the pinned key. This closes "a compromised/misbehaving peer redirects a clicked link to an attacker-controlled host" for any identity already observed once. First-contact TOFU (the very first advertisement for a brand-new identity) remains unverifiable by construction and is documented in ADR-002's Consequences as an accepted residual risk consistent with the same-LAN/trusted-workspace threat model, not a silently-dropped gap. Propagated into `plan.md` Story 3.1 (tasks 4-5, keypair generation/signing) and Story 3.2 (tasks 2-4, 6: signed advertisement schema, TOFU-pinning in `Advertise`, and dedicated rejection/acceptance test cases).
- [ ] **Dual-ID dispatch coverage is unconfirmed beyond the primary read path.** Story 1.3 wires the UUID-or-`public_id` dispatcher into "the primary `GetBacklogItem`-style read path," but the plan doesn't confirm whether other consumers of a raw ID string (other API routes, notification/reference lookups) get the same treatment — a partial rollout could make the deep-link resolver work while other features silently reject `bl_...` IDs. — *Recommendation*: grep all ~40 call sites and enumerate which ones need the dual-ID branch vs. which are internal-UUID-only by design.
- [ ] **New metrics contradict requirements.md's explicit "No new metrics/alerts."** requirements.md's Observability Requirements state plainly: "No new metrics/alerts — this is a low-volume, non-critical-path feature." The plan's Observability Plan proposes `deep_link_resolve_total` and `host_registry_size` as new counters/gauges. Low-risk, but unrequested scope that directly contradicts a stated requirement. — *Recommendation*: either drop the new metrics or add a line reconciling this against the requirement.
- [ ] **Backfilling `public_id` for old rows sits close to a rejected alternative.** requirements.md's Alternatives Considered explicitly rejects "Full backfill-migration of all existing IDs to the new format... for no user-visible benefit beyond cosmetic consistency." Story 1.4's backfill (minting a fresh `BacklogItemID` as `public_id` for every pre-existing row) is plausibly distinct — it leaves the internal `id` UUID untouched and is needed to satisfy "generate a copyable link for any backlog item" — but the plan never explicitly reconciles the two, leaving ambiguity for a future reader. — *Recommendation*: add a one-line note in the Migration Plan explaining why this backfill isn't the rejected alternative.
- [ ] **Version segment semantics remain undefined**, despite requirements.md's Rabbit Holes explicitly asking the Phase 3 plan to "pin down concretely" what a `v1`→`v2` change would actually mean (URL shape? resolved payload schema?). Story 2.1 only implements rejecting unrecognized versions; it never defines what versioning covers. — *Recommendation*: add one sentence to the Domain Glossary or Story 2.1 defining the versioning contract.
- [ ] **Registry persistence frequency vs. stated low-volume nature is unaddressed.** Story 3.2's registry is "in-memory + persisted" via a flock-guarded JSON file (per the `HostIdentity`/registry pattern decision), while the Observability Plan separately calls advertisement send/receive events "high frequency." No discussion of I/O or lock-contention cost if persistence happens on every gossip cycle, despite requirements.md classifying this feature as low-volume/non-critical-path. — *Recommendation*: clarify whether persistence is throttled/batched rather than per-cycle.

## Minors

- The session-ID stretch goal from requirements.md's Scope ("Apply the same scheme to session IDs if it can be done without disrupting existing consumers") isn't mentioned anywhere in the plan — not picked up, and not explicitly declined with a rationale the way the macOS and schema-tightening cuts were. Should get the same one-line explicit-cut treatment for consistency.
- The no-sudo/no-interactive-credential-prompt constraint (requirements.md Constraints) isn't explicitly verified against Story 4.2's `xdg-mime`/`update-desktop-database` calls — these are typically user-level and sudo-free, but the plan doesn't state this was checked.
- "Registry TTL" is defined conceptually in the Domain Glossary but never given a concrete default value anywhere in the plan.
- Story 3.2's convergence test targets "a 3-node fake topology within N cycles" — `N` is left unpinned, so the actual acceptance bound is undefined until test-writing time.
