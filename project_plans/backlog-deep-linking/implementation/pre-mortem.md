# Pre-mortem: backlog-deep-linking
**Date**: 2026-08-19

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Gossip registry advertises `AdvertisedAddress` values that are unreachable across real-world topologies (NAT'd home/work laptops, VPN-only routes, dynamic IPs) — Story 3.2's tests pass against a fake in-process topology, but the actual "workspace" this ships for is exactly the kind of multi-machine, multi-network setup where `--remote-port` isn't mutually routable without a tunnel already configured. | Cross-host `ssq://` links always resolve to "known but unreachable" or silently never populate the registry with the peer at all, even though both instances are running — user assumes the feature is broken rather than realizing it was never going to work over their network shape. | Add an explicit fake-topology-vs-real-topology distinction to validation.md: require one manual test between two machines on different networks (not same-LAN or same-host processes) before calling Epic 3 done, and document the NAT/VPN limitation in user-facing docs so "not reachable" reads as expected, not broken. | P1 |
| 2 | Dual-ID lookup dispatch (Story 1.3) is verified only on the "primary read path" (`GetBacklogItem`-style), but ~40 call sites parse/compare backlog item IDs as `uuid.UUID` per the plan's own estimate — some secondary path (MCP tool lookups, notification links, workflow item references, search/filter-by-id) never gets the `public_id` branch and 400s/404s or silently mis-routes. | A backlog item created after this ships works fine in the main detail view but returns "not found" or panics when referenced from a different surface (e.g. an MCP tool call, a workflow reference, a Slack-pasted link routed through a different handler). | Before Epic 1 is marked done, grep every `uuid.Parse`/`uuid.UUID` call site touching `BacklogItem` IDs (not just the ones plan.md names) and add each to Story 1.3's task list explicitly, with a regression test per site — don't rely on "the dispatcher is wired into the primary path" as sufficient. | P1 |
| 3 | `oklog/ulid/v2`'s monotonic entropy source is documented as not safe for concurrent use without external synchronization; Story 1.1 says "monotonic entropy source seeded once at process start" with no explicit mutex — if backlog item creation ever happens concurrently (parallel API requests, workflow-driven bulk creation), this either panics or silently produces colliding/non-monotonic IDs that violate the sortability guarantee and possibly the `Unique()` constraint on `public_id`. | An intermittent `public_id` uniqueness-constraint violation on item creation under load, or two backlog items sharing an ID — likely first seen as a flaky test or a rare production error log, easy to misdiagnose as a DB issue rather than the ID generator. | Add an explicit task to Story 1.1 requiring the monotonic entropy source be wrapped in a mutex (or use `ulid.Monotonic` per-goroutine with a shared locked reader, per the library's own documented pattern) and add a concurrent-generation test (N goroutines, assert all IDs unique and monotonic) — not just the same-millisecond single-threaded test currently listed. | P1 |
| 4 | macOS OS-level scheme registration is deferred (ADR-003) but the requirements' Success Metrics literally promise "clickable from Slack/terminal/Notes on macOS and Linux" — if this ships without the deferral being explicitly re-confirmed by the user (it's flagged three times in plan.md but the plan doesn't block on an actual answer), the feature ships perceived as broken on the platform most of Tyler's day-to-day dev happens on (per repo CLAUDE.md, "macOS at work"). | User pastes an `ssq://` link into Slack on their Mac, clicks it, and gets a "no application can open this URL" OS dialog — the core promised behavior from the requirements doc simply doesn't exist there, discovered by hitting it in real use, not by a test failing. | Treat Unresolved Question 3 as a hard gate, not a note: get explicit user sign-off on the macOS scope cut before Phase 4 starts, and if confirmed, update requirements.md's Success Metrics itself to remove/qualify the macOS clickability claim so the shipped feature and the written requirement don't disagree. | P1 |
| 5 | Observability Plan assumes a metrics pipeline exists under `server/` (Unresolved Question 5, unverified) and requirements.md explicitly says "no new metrics" — if no pipeline exists, the counters/gauges meant to detect gossip non-convergence (failure mode #1) quietly become dead code or get cut at implementation time, and the "structured logs alone" fallback isn't actually wired to alert anyone, so a stuck-at-1 registry or resolve-failure spike goes unnoticed for weeks with nobody watching logs proactively. | The gossip registry has been silently non-convergent (see #1) for an extended period and nobody notices until a user reports a specific broken link — no dashboard or alert ever fired because none was ever built, only logs that nobody was tailing. | Resolve Unresolved Question 5 at Epic 1 start (not "at implementation time" as currently scheduled, which is too late to change the observability design) and make `--list-known-hosts` a documented part of a periodic manual/scripted health check if no metrics pipeline exists, rather than leaving detection purely reactive to user reports. | P2 |
