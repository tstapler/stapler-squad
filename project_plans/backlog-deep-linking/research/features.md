# Research: Similar Features, Edge Cases, Unstated Needs (backlog-deep-linking)

Agent 2 (Features) — Phase 2 research. Companion to Agent 1's peer-registry/packaging research; this doc covers industry precedent, failure modes, existing in-repo patterns to reuse, and needs the requirements doc leaves implicit.

## 1. Industry precedent: type+version+id deep-link schemes

| Product | Scheme shape | Type/entity disambiguation | Version handling | Host/workspace disambiguation |
|---|---|---|---|---|
| Slack | `slack://channel?team=T123&id=C456` | Query param per entity kind (`channel`, `user`, `app`) rather than a path segment | None baked into scheme itself — app-side routing versioned server-side | `team=` query param carries workspace ID; app resolves against currently-signed-in workspaces, prompts to switch if not the active one |
| Linear | `linear://issue/ENG-123` (also `https://linear.app/<workspace>/issue/ENG-123`) | Path segment for entity kind | No version segment — issue identifier itself (`ENG-123`) is workspace+sequence, not globally opaque | Workspace slug embedded in the `https` form; `linear://` form relies on single-workspace-signed-in assumption, falls back to picker if ambiguous |
| GitHub Desktop | `x-github-client://openRepo/https://github.com/owner/repo` | Verb-shaped path (`openRepo`, `startOAuth`) rather than noun+id | N/A (action dispatch, not a resolvable resource) | Full HTTPS URL embedded as parameter — host and repo both explicit, no local ambiguity |
| VS Code | `vscode://file/<absolute-path>:<line>:<col>`, `vscode-remote://ssh-remote+<host>/<path>` | Path-authority prefix change (`vscode` vs `vscode-remote`) rather than a segment | None | `vscode-remote://ssh-remote+<host>/...` — the authority itself encodes the remote host, exactly analogous to `ssq://<hostname>/...` |
| Figma | `figma://file/<key>?node-id=<id>` | Path segment for entity kind | None | File key is globally unique (server-assigned), no host segment needed — cloud-hosted, single canonical resolver |
| Notion | `notion://notion.so/<page-slug>-<page-id>` | Slug+ID concatenation, ID is a UUID with dashes stripped | None | Cloud-hosted, single resolver, no host disambiguation needed |

**Takeaways for this design:**
- `ssq://<hostname>/<type>/<version>/<id>` is closest in shape to **VS Code Remote's `vscode-remote://ssh-remote+<host>/`** — putting the host in the authority position (not a query param) is the right call for a scheme whose whole point is multi-instance resolution, and it's the one scheme in this table designed for the same problem (same app, multiple hosts) rather than same app, multiple cloud workspaces.
- Every scheme that supports **actions on an ambiguous/unavailable target** (Slack team switch, VS Code Remote host connect) has a user-visible "connecting to X" or "switch workspace?" affordance rather than a silent failure — reinforcing the requirement's "clear message naming the host" bar, but suggesting the message should optionally offer a one-click action (open the peer's URL directly) rather than just informational text.
- None of these examples put a bare version number as its own path segment the way `ssq://.../backlog/v1/bl_01J...` does — Slack/Linear/GitHub Desktop version their route *shapes* implicitly via app releases, not explicitly in the URL. This isn't a defect in the plan, but it means there's no borrowed convention for what `v1`→`v2` migration actually looks like at the routing layer; Phase 3 will need to invent it from scratch rather than copy a pattern (confirms the requirements doc's own open question — "Rabbit Holes" / "Version segment semantics").
- Type-prefixed sortable IDs: **Stripe (`ch_`, `cus_`, `pi_`...)** and **Linear (`ENG-123` project-prefixed sequence)** are the standard industry precedent for "self-describing at a glance" IDs the requirements doc cites. Stripe's prefixes are the closer analogy to `bl_01J...` — opaque-after-prefix, not human-sequential — and Stripe's IDs are *not* sortable-by-time despite being prefixed; pairing a type prefix with a ULID (which Stripe does not do, but tools like Postmark and some newer Stripe-alikes do) is the specific combination this project is proposing. No known prior art combines a type prefix + ULID + explicit URL version segment + host authority in one scheme — this is a novel combination, not an off-the-shelf pattern, which raises the design's surface area for edge cases below.

## 2. Edge cases and failure modes

Working through the requirements doc's own "never fail silently" bar for each:

1. **Item deleted/archived after link created.** Requirements doc doesn't mention this. The ID resolves (host reachable, ID well-formed) but the backlog service returns not-found. Distinguish from "wrong host" — the message shown should be "this item was deleted/archived" (if soft-delete/archive state is retrievable) vs a bare 404. Check whether `BacklogItem` has an archived flag distinct from hard delete (`session/ent/schema/backlog_item.go` — needs Phase 3 check) so archived-but-resolvable is a materially different UX than gone-forever.
2. **Link opened before the target instance is running.** `ssq://` scheme handler (macOS `.app`/embedded-plist launch, Linux `.desktop` `Exec=`) needs to either (a) launch the binary if not running, then retry resolution once the web server is up, or (b) fail with an actionable "instance not running — start it and click the link again" rather than a connection-refused browser error. This is a real gap in the current requirements/rabbit-holes: they discuss *scheme registration* but not *cold-start race* — the OS hands off to the app before confirming the HTTP server inside it is listening. Needs a retry-with-backoff or a small native shim that polls `localhost:8543/healthz` before redirecting the browser.
3. **Opened by someone without access to that workspace.** stapler-squad is described as single-user/small-team local/dev-machine deployment (per requirements' Data residency note) — no auth model is mentioned in this doc. Worth flagging: if a link is pasted into a *public* Slack channel by mistake, is there anything sensitive in `ssq://hostname/backlog/v1/bl_...`? The requirements doc already addresses this for hostnames ("should not leak anything more sensitive than what's already visible in the running UI") — but doesn't address whether the *web app itself* has any access control today. If it doesn't, this is out of scope for this project but worth a one-line callout in Phase 3's risks so it isn't silently assumed away.
4. **Malformed/truncated `ssq://` URLs** (common failure mode from copy-paste into Slack, which sometimes truncates or auto-links only part of a URL, or a markdown renderer eating characters after `://`). The resolver needs a validation layer that fails closed with a specific "malformed link" message (already called out in Observability Requirements: "malformed ssq:// URL" is one of the three named log cases) — but the requirements doc doesn't specify *where* that validation lives (URL scheme handler vs. web route vs. both). Both entry points (`ssq://` native handler and `https://.../backlog?item=`) need the same parser so behavior doesn't diverge — one shared Go (or TS, if resolution is client-side) function, not two independent parsers.
5. **Old UUID-format link vs. new ULID-format link both resolving.** This is explicitly in scope ("Backward compatibility... continue to work unchanged"). The two ID shapes are trivially distinguishable (UUIDv4 has dashes at fixed positions and no type prefix; `bl_<26-char-ULID>` has an underscore-delimited prefix) — but the resolution *path* differs: today's UUIDs go through `/backlog?item=<uuid>` (query param, no type/host/version info), while new IDs go through `ssq://<host>/<type>/<version>/<id>` (or its `https://` equivalent) with type/version explicit. A `ssq://host/backlog/v1/<uuid>` (someone manually constructs the new URL shape but pastes an old-format ID into it) is a plausible input the parser will see and should accept, not reject — the type+version segments and the ID format are independent axes and old-format IDs should be legal payloads in the new URL shape.
6. **Cross-host handoff when the peer is reachable but stale/wrong data** — e.g., peer's own DB was reset, or the peer is a *different* item with the same ID by coincidence (extremely unlikely with ULID/UUID collision space, but worth a one-line note that ID collision is not a realistic risk to design around).
7. **Multiple browser tabs/windows racing on the same `ssq://` open** — if the OS handoff opens a new tab per click rather than focusing an existing one, repeated clicks on the same Slack-pasted link could spawn tab sprawl. VS Code's own `vscode://` handler focuses the existing window rather than opening a new one; worth matching that convention if the app is already open.
8. **Case sensitivity / URL-encoding of the hostname segment** — hostnames aren't case sensitive by spec but some environments (WSL2, Docker Desktop hostname mapping) produce inconsistent casing; the resolver's host-match-against-current-instance check should normalize case before comparing, or a self-link generated and immediately reopened on the same box could spuriously report "wrong host."

## 3. Existing in-repo patterns worth reusing

- **Workspace peers registry already exists and is richer than the requirements doc assumes might be needed.** `session/workspace_peers.go`'s `WorkspacePeer` struct (`SessionUUID`, `Title`, `Branch`, `Path`, `Status`, `Goal`, `InstanceLive`, `StaleGoal`) and `ListWorkspacePeers`/`ApplyTmuxLiveness` give a **liveness signal** (`InstanceLive`, backed by `LiveTmuxSessionUUIDs` which shells to tmux directly rather than trusting a DB status column) — this answers one of the Phase 2 Open Questions ("does peer registry track liveness") for *sessions*. However, this registry is **scoped to sessions sharing a workspace key (repo identity), not to host/instance identity** — there's no field here for "which hostname/port is this peer's web UI reachable at." For backlog-item cross-host handoff, the registry as it exists today tells you a peer *session* is alive, not that a *given hostname* has a reachable stapler-squad web server. This is a meaningful gap: the deep-link handoff needs host-to-URL resolution, and `WorkspacePeer` has no URL field at all. Recommend Agent 1 (or Phase 3) confirm whether `InstanceData` (the underlying source in `ListInstanceData()`) carries a hostname/port anywhere, since `WorkspacePeer` itself doesn't expose one.
- **No existing "copy link" affordance in the web app.** Grepped `web-app/src/components/**` for share/copy-link UI — none exists for backlog items or sessions specifically. The closest analogs:
  - `web-app/src/app/account/page.tsx:72-77` — `copyUrl` does `navigator.clipboard.writeText(invite.registration_url)` then `setCopied(true)` with a 2-second `setTimeout` revert, driving an inline "Copied!" state (not a toast). This is the most directly reusable pattern for a "Copy link" button + inline confirmation on a backlog item.
  - `web-app/src/app/history/page.tsx:176-179` — `handleCopyId` does the same clipboard write with try/catch and `console.error` on failure, no user-visible error state at all (silent failure on clipboard permission denial — worth *not* copying this part, since backlog-deep-linking's success bar implies the copy action should have visible feedback either way).
  - A dedicated toast system exists (`web-app/src/components/ui/NotificationToast.tsx`, already used elsewhere e.g. `TriageReviewPanel.tsx`, `WorkspaceSwitcher.tsx`) — this is the better-designed option for "copied to clipboard" confirmation than the account page's local `copied` boolean, and is already wired into the app's global notification plumbing. Recommend the new Copy Link button use the toast system rather than reinvent an inline "Copied!" state.
- **No prefixed/typed ID scheme exists yet anywhere in the Go codebase.** Grepped for existing `sess_`/`bl_`-style prefixes and for a ULID library in `go.mod` — neither exists. This confirms the requirements doc's characterization of this as new ground (not a refactor of an existing convention) — there's no precedent to match against for prefix casing, separator choice, or whether the prefix is validated/enforced anywhere at parse time. Session IDs today are plain UUIDv4 strings compared by direct string equality throughout `session/`; if the session-ID stretch goal is picked up, every one of those call sites is a place a bare-string comparison could silently accept a malformed or wrong-type ID.
- **`/backlog?item=<uuid>` today** (`web-app/src/app/backlog/page.tsx:230`, `searchParams.get("item")`) is the only existing "deep link" surface, and it's client-side only — it reads the query param via `useSearchParams()` and presumably scrolls-to/selects the row, with no server-side resolution step at all (unlike the proposed `ssq://` scheme, which needs a server or native-handler resolution hop before the browser even loads the page). Worth confirming in Phase 3 whether the new `https://`-equivalent route reuses this exact query-param mechanism (i.e., the scheme handler just rewrites to `https://host:port/backlog?item=<id>` and lets existing client logic take over) rather than inventing a new path-based route — that would minimize new surface area and automatically inherit whatever selection/scroll UX already exists for `?item=`.

## 4. Unstated needs beyond the explicit requirements

- **Toast/confirmation on copy** — covered above; the requirements doc says "generates a copyable link" but doesn't specify user feedback on the copy action itself. Given the existing toast system, users will expect parity with other copy-to-clipboard actions in the app (e.g., account page's registration URL, though that one lacks a toast too — an argument for standardizing rather than copying either existing pattern verbatim).
- **Extending beyond backlog items to sessions.** Requirements doc explicitly ties this to the ID-format stretch goal ("covered only if... not a hard requirement") — but the deep-link *URL scheme* itself (`ssq://<host>/<type>/<version>/<id>`) is already generic over `<type>`, so once `backlog` works, adding `session` as a second `<type>` value is comparatively cheap *if* the resolver/router is written generically rather than backlog-item-specific. Recommend Phase 3 design the resolution dispatch (native handler → web route → entity lookup) keyed on the `<type>` segment from day one, even though only `backlog` ships now — avoids a second migration when sessions get their own deep links later. This is the single highest-leverage "build it slightly more general now" call in this research, because the alternative (hardcoding `backlog` into the URL parser) is exactly the kind of thing that becomes a breaking `v2` change per the version-segment rabbit hole.
- **"Share view" vs. per-item link.** Requirements doc scopes this tightly to a single backlog item; it doesn't ask for a link to a *filtered/tab* view of the backlog board (e.g., "here's my current filter+sort state, shareable"). `BacklogBoard.tsx` and the board's filter state (see `BacklogBoard.filters.test.tsx`) aren't part of this project's scope per the doc, but it's worth naming explicitly in Phase 3 as a deliberately-excluded adjacent feature (view-state links are a different, larger problem — arbitrary filter serialization vs. a single opaque ID — and conflating them would blow the "Large, 3-6 weeks" appetite).
- **Keyboard/right-click affordance, not just a button.** Not mentioned in requirements; users of Linear/GitHub commonly expect a right-click "Copy link" on a list row in addition to (or instead of) an explicit button inside the detail view — worth a design decision in Phase 3 on where the affordance lives (`BacklogItemDetail.tsx` header vs. a context menu on `BacklogBoard.tsx` rows), since the existing `BacklogItemDetail.tsx` doesn't currently have a header actions area with copy-style buttons (grepped for "Copy"/"link" in that file — no matches), so this is new UI surface either way.
- **Retry/backoff for the cold-start race** (edge case #2 above) is really a UX requirement in disguise — "clickable from outside the browser" implicitly promises the link works even when stapler-squad isn't running yet, which is a meaningfully bigger lift (process launch + health-check polling + a loading state in whatever intermediary page/native shim handles the scheme) than "the web app resolves the route once it's open." The requirements doc's Rabbit Holes section anticipates the *registration* side of this (bundle vs. bare binary) but not the *runtime* cold-start side — flag both for Phase 3 scoping since they compound (a `.desktop`/`Info.plist`-launched cold process also has to bind the same fixed port `:8543` without colliding with anything, and the launched process needs to know which backlog item to navigate to once it's up — i.e., the args/URL need to survive the launch handoff, not just trigger it).

## Summary of research gaps to hand off to Phase 3

- Confirm whether `InstanceData` (backing `ListInstanceData()` in `session/workspace_peers.go`) has any hostname/port field — `WorkspacePeer` itself does not expose one, so today's peer registry cannot answer "what URL do I redirect to for peer X" without this.
- Confirm whether `BacklogItem`'s ent schema has an archived/soft-delete flag distinct from hard delete, to give edge case #1 (deleted item) a materially different message than "unknown ID."
- Decide where malformed-URL validation lives (shared parser used by both the native scheme handler and the `https://` web route) so the two entry points can't drift.
- Explicit design decision (not just "punt to v2"): what launches the app on a cold `ssq://` click, and how does the item ID survive that launch to the eventual browser navigation.
