# Pre-mortem: report-pr-created-branch-mismatch
**Date**: 2026-08-04

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | LLM work sessions reach for `override_reason` reflexively whenever `report_pr_created` rejects a call — supplying a generic, plausible-sounding reason ("tracked branch was polluted") instead of only for genuine branch-pollution recovery — because it's a faster unblock than diagnosing why the branch actually mismatches (e.g. a truly hallucinated PR number, or a PR opened against the wrong item). Nothing in the plan distinguishes "override used correctly" from "override used lazily" — `decideOverridePolicy` only checks non-empty string + open/merged state, never reason *content* or *frequency*. | An item ends up `pr_pending` with the wrong PR attached; nothing crashes at call time — the audit `log.Warn` line fires exactly as designed, so grep-based review is the only detection path, and no one is grepping until something downstream looks wrong (e.g. a stranger's PR referenced during manual review of that item). No metric/alert exists on override-path usage rate or on repeated overrides from the same session/item. | Add a lightweight usage signal beyond the log line: e.g. a periodic count of `override_reason`-path invocations (even just a `grep`-based report) surfaced in an existing reconciliation/health-check pass, or a rule against the override hint text (Task 3.2) telling sessions to first attempt to resolve via a clean re-diagnosis before reaching for `override_reason`, with an explicit example of *not* using it (hallucinated/wrong PR number is never an override case, only branch pollution is). | P2 |
| 2 | Story 6's `verifyPRHeadBranchMatchesTracked` guard fails closed on *any* GitHub lookup error, including a transient outage — indistinguishable in the code from a genuine, permanent branch mismatch. If GitHub has an extended outage exactly while a legitimate (non-override) item is ready to auto-complete, the guard blocks `closeIfSupersededByMain`/the two `IsPRMerged` done-transitions every tick for the outage's duration, with only a `WarningLog` line (not an alert) and no mechanism to distinguish "will resolve itself next tick" from "permanently blocked by an override-linked mismatch." | Items pile up in `pr_pending`/`in_progress` with repeated identical `WarningLog` lines ("skipping auto-close... was this item's PR attached via report_pr_created's override_reason path?") even for items that were never override-linked at all — a human has to read logs to realize it's an outage, not a real mismatch, because the guard's fail-closed contract (Task 6.2) treats a lookup error and a definitive `false` (real mismatch) identically. | Add a task distinguishing transient GitHub errors (network/5xx/rate-limit — safe to silently retry next tick, no log spam beyond a rate-limited warning) from a definitive `Exists && HeadRef != tracked` mismatch (log once per item-transition, not every tick) in `verifyPRHeadBranchMatchesTracked`'s return contract; consider an escalating log level or counter after N consecutive lookup failures for the same item so a genuine multi-day outage is distinguishable from routine noise. | P2 |
| 3 | The plan's validation is entirely mocked (`verifyPRMatchesBranch`/`prByNumberFinder` stubs in Tasks 4.0–4.5, 6.6) — no task in Story 1–6 actually invokes the fixed `report_pr_created` (or a manual equivalent) against the real, confirmed-stuck item `3065ecfb-3fb7-4ee7-9d04-ada6a7f4169d` / PR #326 before shipping. requirements.md explicitly puts "retroactively fixing already-stuck items" out of scope, and the plan appears to have folded "verifying the fix actually works against the real repro" into that same out-of-scope bucket, even though the two are different: confirming the mechanism works against real GitHub data (auth scopes, `base.repo.full_name` shape, actual `head.ref` casing/format) is validation, not retroactive fixing. | The PR merges with all unit/integration tests green, but the first real invocation of the override path against real GitHub data (post-ship, by an actual stuck session) still fails — e.g. `GetOwnerRepoFromRemote` resolves a different owner/repo string than the mocked fixture assumed, or GitHub's real `base.repo.full_name` format doesn't match the defensive check in Task 1.1 exactly as the httptest fixture modeled it. | Add an explicit manual-smoke-test task to validation.md (or as a final Story 4/6 task): after implementation, run `report_pr_created` (or a `curl`/`gh api` equivalent hitting the same REST endpoint `GetPRByNumber` uses) against the real PR #326 and confirm the shape (`head.ref`, `base.repo.full_name`, `state`, `merged`) matches what Task 1.1's parsing expects — a read-only verification, not a write to the stuck item, so it doesn't conflict with the "no retroactive fix" scope decision. | P1 |
| 4 | The plan grew from an original design to 6 stories / 23 tasks across two adversarial-review repair rounds, with Story 6 (and especially Task 6.3a, added in the *second* repair pass) framed throughout the plan and ADR-001 as closing gaps found late rather than being part of the "core" fix. Implementation sessions working task-by-task under time/context pressure are structurally more likely to treat the last-added, most defensively-coded, most call-site-scattered story (6 files touched: `closeIfSupersededByMain`, two `ReconcilePRPending` sites, `reconcileBouncingItems`, plus a new test file) as optional polish and cut or under-test it, especially since Stories 1–4 alone make all the tests in Task 4.0–4.6 pass and look "done." | Code review or `make ci` shows Stories 1–4 fully implemented and green, but Story 6's guard is either missing from one of its three call sites, or Task 6.3a's disclaimer-prepending logic is missing/untested (`session/backlog_lifecycle_pr_branch_guard_test.go`'s `TestReconcilePRPending_should_IncludeUnverifiedDisclaimer_*` tests absent or failing) — and it isn't caught before merge because the PR still "solves the reported bug" from an AC1/AC2/AC3 standpoint. | Make Story 6 (all of 6.1–6.7, explicitly including 6.3a) a hard, named item in validation.md's coverage map and in the shipping checklist (`sdd:6-verify`/`code:is-it-ready`), not merely "lower severity" — call out that Story 6 is the ADR-001-documented mitigation for a review-identified Blocker, so omitting it is a scope regression, not a nice-to-have cut. Consider running `quality:architecture-review` or `code:review` specifically re-diffing Story 6's three guarded call sites against the plan's line-number references before merge. | P1 |
| 5 | `NewPRVerification` (Task 2.1) enforces `Matched ⇒ Exists` by silently coercing `matched=false` and logging via `log.ErrorLog.Printf` rather than failing loudly (no panic, no test hook asserting the invariant path is never hit) — and `decideOverridePolicy` (Task 3.1) returns an internal code that `reportPRCreated` separately maps to the exact AC3 message text, a second, independently-maintained mapping. Both were added during repair rounds after the "core" design (root-cause number-keyed lookup) was settled, and neither has a test that specifically exercises the invariant-violation/coercion path or asserts code→message mapping stays in sync — Task 4.0's table only covers well-formed `PRVerification` values, never the constructed-and-coerced case. | A latent bug in `GetPRByNumber`'s own branch-matching logic (e.g. case sensitivity, trailing-slash/prefix mismatch on `head.ref`) would surface only as an `ErrorLog` line nobody pages on, while the coerced `matched=false` makes behavior look "safe" (defaults to reject) — masking a real defect indefinitely instead of failing a test. Separately, a future edit to `decideOverridePolicy`'s code constants without an equally-updated `reportPRCreated` message-formatting switch would silently produce a wrong AC3 message, only caught if a test asserts the literal string (Task 4.3 does, but only for the specific messages the plan wrote, not exhaustively per code value). | Add one test asserting `NewPRVerification(true, false, ...)` triggers the coercion path (matched forced to false + confirms an `ErrorLog` line, e.g. via a log-capture helper) so the invariant-guard itself has coverage, not just its default-safe side effect; add a table test in `decideOverridePolicy`'s test (Task 4.0) that walks every returned `code` value and asserts `reportPRCreated`'s message-formatting switch has a corresponding case (compile-time exhaustiveness via a `switch` with no `default`, or a reflection-based completeness test), so the two independently-maintained mappings can't silently drift. | P3 |
