## Concerns

- [ ] **`PRVerification{Exists: false, Matched: true}` is representable and only prevented from causing a false-accept by branch *order* in `reportPRCreated`, not by the type.** Per Task 2.1, the real `VerifyPRMatchesBranch` never actually constructs this combination (an `ErrNoPR` result returns `PRVerification{Exists: false}` with `Matched` at its zero value), so it's not reachable through production code today — but nothing enforces that invariant at the type level, and the safety currently depends entirely on Task 3.1's branching checking `!verification.Exists` *before* `!verification.Matched`. A future edit reordering those checks, or a second caller of `PRVerification` that reads `.Matched` without first checking `.Exists`, would silently false-accept. Recommend either a smart constructor (`PRVerification.NotFound()` / `.MatchedBranch(...)` / `.Mismatched(actualBranch, state)`) so the illegal state is unconstructable, or at minimum a unit test that pins "Exists:false always short-circuits regardless of Matched" so a future refactor that breaks this ordering fails a test instead of silently regressing. (Directly relevant given this repo's own `type-driven-design` skill and its "illegal states unrepresentable" framing.)

- [ ] **`GetPRByNumber` doesn't verify the response body's own `owner/repo` against the requested `owner/repo`.** Task 1.1 parses `number`, `head.ref`, `base.ref`, `state`, `merged`, `html_url` but not `base.repo.full_name`/`head.repo.full_name`. Because PR numbers are repo-scoped by the REST URL path (`repos/{owner}/{repo}/pulls/{number}`), this is low-probability in practice (a stale/renamed-repo redirect lands on the *same* repo under its new name, so even that case is benign) — but it's a cheap, one-line defensive check (`resp.Base.Repo.FullName == owner+"/"+repo`) that costs nothing and closes the "does the plan trust the request URL's owner/repo blindly" gap the review brief asked about directly. Recommend adding it to Task 1.1 rather than leaving it purely as inference from URL-path scoping.

- [ ] **No explicit 5xx/network-error test case for `GetPRByNumber`.** Task 1.2 lists three cases (200/404/403); there's no `TestGetPRByNumber_should_ReturnError_When_ServerError` (500) case. The code shape should route a 500 to a generic non-`ErrNoPR` error (mirroring `GetPRForBranch`'s existing status-code branches at `github/client.go:394-401`), which `reportPRCreated` needs in order to correctly surface `ErrInternalError` (retryable) rather than a hard reject — but this is currently asserted by code-shape inference, not pinned by a test. Cheap to add; recommend doing so in Story 4's task list.
