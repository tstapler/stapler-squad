# Pre-mortem: ci-status-diff-viewer
**Date**: 2026-08-02

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The bounded-staleness guard (Task 1.1.2b) is left as an "Implementer TODO" — plan.md explicitly punts on whether `2 * PollInterval` threads the poller's *live* config or hardcodes a disconnected `60s` literal. If hardcoded, the guard silently drifts once the real poll interval is ever changed (config, load-shedding, rate-limit backoff), either trusting genuinely stale "success" for an irreversible auto-approve, or making the guard so aggressive that `ci_passing` rules almost never fire. | A `RequireCIPassing` rule intermittently falls through to Escalate despite the badge showing green CI ("the rule doesn't work"); or, worse, a post-hoc audit finds an auto-approved session whose CI flipped to failing shortly after approval, traced to a stale cached conclusion older than the guard assumed. | Resolve this now in plan.md, not at implementation time: require `ApprovalHandler` to receive the poller's `PollInterval` via constructor injection (same pattern as `storage`), and add a unit test asserting the guard reads the *actual configured* interval rather than a duplicated literal, so a future interval change can't silently desync the two. | P1 |
| 2 | AC5's manual-approve block (Task 2.2.2a) reads raw `data.GitHubCheckConclusion` with **no** staleness bound, while AC6's auto-approve path (Task 1.1.2b) treats the identical field as unknown once `LastPRStatusCheck` exceeds `2 * PollInterval`. The plan's own rationale for the guard ("CI status is inherently async/network-sourced... no fresher local value to fall back to") applies equally to both gates but is only implemented for one. | A reviewer sees "CI is failing on this branch — review before approving" for a session whose CI actually passed a while ago (poller lagging or stopped tracking it); no staleness is disclosed in the block message (only in the badge tooltip elsewhere), so the reviewer can't tell the message is stale and reflexively reaches for "Approve anyway." | Apply the same staleness treatment to Task 2.2.2a's guard: skip the block once `LastPRStatusCheck` exceeds the threshold, and include "last checked Ns ago" text in the `CodeFailedPrecondition` message itself, not just the diff-viewer badge tooltip. | P2 |
| 3 | The diff viewer renders the *local* worktree while the badge reflects the *remote* PR head's CI (Unresolved Question #3, explicitly deferred with "revisit if confusing in practice"). After a force-push/rebase — a routine operation in this repo's session/worktree workflow — the local diff and the badge's CI conclusion can describe two different commits. | A reviewer approves a diff that looks clean with a green badge, but the badge's "success" was computed against a SHA that's since been superseded by a force-push containing new, unreviewed, possibly-failing changes; or conversely a fixed force-pushed branch is permanently shown as "Failing" until the poller happens to refetch. | Promote Unresolved Question #3 from an open-ended "revisit if confusing" to a tracked follow-up with an explicit trigger (e.g., ship a cheap SHA-comparison check comparing the PR's current head SHA — already available to the poller — against the session's local HEAD, and render a distinct "may be stale (branch updated)" badge state when they diverge) rather than leaving it silently deferred. | P2 |
| 4 | The badge's 4-state vocabulary deliberately conflates "genuinely no CI configured" with "fetch failed/rate-limited/errored" (Unresolved Question #1). requirements.md's own Open Question about rate-limit exhaustion across many concurrently-polling sessions is never revisited or resolved anywhere in plan.md. | During a GitHub outage, secondary rate-limit window, or expired token, every session's badge quietly reads "No checks" instead of any error indicator — reviewers conclude no CI exists for any of their branches and silently lose the exact protection (Goal 1) the feature exists to provide, with no visible signal anything is broken. | Reuse the staleness signal already being added elsewhere as a cheap proxy for "poller can't currently refresh this session" and render it as a distinct state from "no checks configured," even without new backend plumbing — this doesn't require the deferred `details_url`/last-error field, just reusing `LastPRStatusCheck` age the same way Task 1.1.2b already does. | P2 |
| 5 | "Approve anyway" (Story 2.2.4) is the only override mechanism for AC5's block, and its sole audit trail is a grep-able log line nobody is assigned to review — the plan sets no threshold or monitoring for override frequency. | Log/analytics show "Approve anyway" clicked on nearly every red-CI approval shortly after rollout — the block becomes a speed bump reviewers click through by habit, reintroducing exactly the failure (approving diffs about to fail CI) the feature was built to prevent, just moved one click over. | Add an explicit success metric to validation.md (e.g., "if >X% of blocked approvals are overridden within the first month, the default/UX needs revisiting") and surface override counts somewhere reviewable (settings page or periodic report), not just an unreviewed log line. | P2 |
