## Concerns

- [ ] **C1. "Clear mode for every non-adopted candidate" is applied uniformly, but the rejection causes are not equivalent.** Plan: Story 3.1.3 ("a candidate rejected by any gate ... mode is cleared"), Task 3.1.3c, Risk Control.
  (a) *Contradiction with the plan's own test.* `no_driver` is both a gate and part of the candidate definition. The "pass runs twice, second starts none because `no_driver` rejects" AC combined with "rejected by any gate -> mode cleared" means the second run clears the mode of the session the first run just adopted (live driver, mode false, LLM auto-approval off at `server/server.go:889-891`). `sync.Once` prevents this in production, but a table test written literally from the AC would assert the bug. Also `startDriverIfAbsent` returning `ErrDriverPresent` is not in the start-failure list (only `ErrNoDriverPool`/`Start` failure), so its handling is unspecified.
  (b) *Transient causes are treated as permanent.* `pane_owned` shells out to `tmux show-environment` with a timeout (`session/nudge_gate.go:123-130`) for every candidate in the boot fan-out; the ItemSession/item lookups can fail with a non-`ErrNotFound` DB error; `pane_alive` can read false while a backend is mid-restore. A timeout or storage error clears the persisted mode (the pass runs once), so the session loses autonomy until a human re-toggles. That equals today's outcome, so it is not a regression, but it defeats the feature's purpose exactly when the machine is busiest (just after boot) and contradicts "default ON is justified by the complete gate list".
  Recommendation: classify gate results as `reject` (definitive: status, archived, paused, retry-pending, ItemSession ended, item moved on, dead pane per `PaneExitInfo`), `skip` (`no_driver`/`ErrDriverPresent`: leave mode untouched, log) and `unknown` (probe timeout, non-NotFound storage error, `Restoring`/`Creating`: do not clear; either retry once after a short delay or leave mode and log loudly). Keep the invariant test but restate it as "no mode true with no driver *except candidates logged `unknown`*". Add table rows for each class.

- [ ] **C2. Boot-cleared candidates get outcome `"stuck"`, which paints a false stuck badge.** Plan: Task 3.1.3c uses `SetAutonomousStopped(cancelled_shutdown)`, which Glossary defines as outcome `"stuck"`. `SessionCard.tsx:888` renders `autonomousOutcome === "stuck"` as a warning badge (confirmed by reading it). `AutonomousOutcome` is not persisted, so after every boot every Hibernated/Paused/archived/ended-ItemSession session that still had persisted `AutonomousMode == true` shows "stuck" until the next restart, with no row and no notification to explain it. The shutdown-callback case (flag OFF) justifiably mirrors today; the boot pass has no such obligation.
  Recommendation: the boot pass clears with outcome `""` (a distinct setter argument or `cancelled_external` semantics), and keep `"stuck"` only for the flag-OFF shutdown branch. One assertion in the readoption table test.

- [ ] **C3. The pass trigger sits before the controllers' settling delay.** Plan: Task 3.1.3c signals (b) "after the Step 7.5 loop". Step 7.6 then sleeps 500 ms explicitly "to allow controllers to initialize their terminal readers" and runs `scanner.Scan` (`server/dependencies.go:1083-1089`). The re-adopted driver's first act is `waitForIdle` with settle 0, which returns immediately if `cc.IsIdle()` is true, then calls the headless LLM with a pane tail (`autonomous_driver.go:289, 335`). INFERRED: an idle detector seeded from a quiet pre-restart timestamp reads idle at once, so the first orchestration turn can run against an unsettled controller. Work-role DONE is already neutralised (`:443-481` leaves the item in progress), but triage DONE advances `idea -> ready`. Also: if the dependency goroutine ever returns before signalling (b), nothing runs the pass and the "no mode true without driver" invariant is silently unenforced.
  Recommendation: signal (b) after Step 7.6 (after the settle sleep and scan), and add a bounded fallback in `maybeReadopt` (e.g. run once a timeout after (a) even if (b) never arrives, in dry-run-clear mode) or assert in a test that every exit of that goroutine signals.

- [ ] **C4. Default ON removes the only gate-validation evidence.** The plan's evidence mechanism is the dry-run (flag OFF) candidate log, but it ships default ON, so the first boot already adopts and the log is read after the fact (wall-clock blocker 3 says so). The plan flags this as the one owner decision and the flag-off semantics are fully defined, so this is a decision, not a defect.
  Recommendation (not a requirement): ship default OFF for the first release and have the owner flip it after reading one `would_adopt` log. Note flag OFF is safe: it clears stale mode at boot, which is today's behaviour. If the owner keeps default ON, keep the always-on candidate log (already planned).

- [ ] **C5. `ErrNudgeSubmitUncertain` -> Resupervise can write into a pane holding unsubmitted text.** `SubmitDriverContent` types the content, then Enter; `ErrSubmitNotConfirmed` and "cancelled before sending Enter" (`session/pane_submit.go:112-142`) mean text may sit in the input box. The table sends this to Resupervise-if-headroom, whose next driver (after idle) injects another orchestrator message, which would append to or garble the pending input. Today's path (break -> stuck -> Respawn) kills the pane, so this exposure is new. Two smaller points on the same row: (i) precedence between the "recovery ctx cancelled" row and the "uncertain" row is only implied by row order; a cancel-after-send matches both. `canRestart` fails on a cancelled ctx so the outcome is right, but state it. (ii) "never Respawn" is correct for a possibly-delivered write; the leave-the-pane branch is fine.
  Recommendation: for `ErrSubmitNotConfirmed` / cancel-after-send choose leave-the-pane (no further writes) rather than Resupervise, or make the re-supervised driver's first turn clear the input line; state the ctx-cancel precedence in the table.

- [ ] **C6. Per-boot cap of 8 clears, rather than defers, the excess, in unspecified order.** The cap is a start-storm bound, but the remainder permanently loses autonomy (and gets C2's badge) and "first 8" depends on `LoadInstances` order, which the plan does not define. With the backlog WIP cap of 2 the cap is rarely reachable, which is why this is a concern and not a blocker.
  Recommendation: stable order (e.g. most recent `LastMeaningfulOutputTime` first) and stagger/queue the excess (start N, then the rest after the first warm-ups) instead of clearing; if clearing stays, log it at Warn with the count.

- [ ] **C7. Risk Control overstates "flag OFF equals today's shutdown".** Facts row 38 says today a graceful shutdown writes an `autonomous_stuck` row, dispatches a respawn and publishes the FAILURE notification. The OFF branch keeps only mode/outcome and drops row, respawn and notification (correct, and listed under "Ungated behaviour changes"), but the sentence "OFF must equal today's graceful-shutdown outcome" will mislead a rollback decision. Reword: OFF restores today's *in-memory mode/outcome*, not the stuck row/respawn/notification; the latter are ungated corrections.

## AC verifiability

- **AC1**: verifiable (grep counts and census command are stated; the doc must say production frequency is unknown).
- **AC2**: verifiable via the stuck-row `context` (`ListStuckBacklogItems`), the single `[AutonomousDriver] stopped` log line (a `captureLogs` helper already exists in `server/services/autonomous_orchestration_service_test.go`) and the in-memory snapshot field. Stops with no row (resupervise, cancelled, shutdown) are log-only, as stated.
- **AC3**: verifiable for driver-stop paths. The stale-work and health-checker restart paths remain a recorded deferral that is still marked "owner sign-off requested"; AC3 should not be reported fully met until the owner signs it.
- **AC4**: verifiable and deterministic (exhaustive decision loop, fake nudger/starter, injected clock, no sleeps). Add two rows from this review: the `no_driver`/`ErrDriverPresent` skip-without-clear case (C1a) and the transient-probe-error case (C1b). The nudge-settle cancellation test is the only one that needs real timing (racing a 1 s timer against a 100 ms cancel); keep it on a fake controller as planned.

## Minors

- M1. `Instance.TmuxAlive()` reads raw `i.Status` (`instance_tmux.go:992`), against `.claude/rules/instance-lock-free-reads.md`; the `paneProbe` seam is the place to use `GetLifecycleStatus()` instead.
- M2. A superseded completion is dropped wholesale, including a real `done` from an older run displaced by `registerDriver` (item stays `in_progress`; the stale detector eventually recovers). Rare; log at Warn with the dropped `StopReason` so it is diagnosable.
- M3. `VerifyNudgeSafeToWrite` ctx pass-through is a (benign) MCP-path behaviour change although the plan says "unchanged"; add one MCP-handler test for a cancelled request ctx and check `writeNudge`'s error classification handles `context.Canceled`.
- M4. The re-adopted driver's first turn can inject into a pane that is quiet but mid-tool-call (idle detection is output-based). This is the existing driver's behaviour, not new, but re-adoption makes it happen at every boot; worth a line in the soak checklist.
- M5. Re-adoption grants a fresh `AutonomousMaxTurnsOrDefault` per restart (logged). Combined with frequent deploys it can exceed the turn budget the `max_turns` row protects; accepted, but note it next to the Resupervise multiplier.
- M6. `cancelled_external` from an unrelated `Stop()` while a `Cancelled` callback is still running can clear mode after a user re-toggled ON (D1 completion clears mode between `SetAutonomousMode(true)` and `registerDriver(D2)`). Pre-existing race, now narrower because supersession usually catches it; guard `SetAutonomousStopped` for `cancelled_external` on "no driver registered under the title".
