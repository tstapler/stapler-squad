## Blockers

- [ ] **Task 1.3.1a's root-cause hypothesis (`position:fixed` without `createPortal`) is inconsistent with the code and is about to be filed into a new backlog item as the "leading hypothesis."** `Omnibar.tsx:1237` is `if (!isOpen) return null;` — a top-level early return, and `OmnibarContext.tsx:275-276` renders `<Omnibar isOpen={isOpen} onClose={close} .../>` unconditionally, with `close = useCallback(() => setIsOpen(false), [])` (`OmnibarContext.tsx:148-150`) being a plain, unguarded state setter. When `onClose()`/`close()` runs, React removes the *entire* modal subtree from the DOM on the next render, regardless of any `position: fixed`/ancestor-transform CSS issue — that class of bug causes a still-mounted overlay to be *mispositioned or visually clipped*, not a mounted-but-invisible element to fail to unmount. So the CSS/portal theory doesn't actually explain "onClose() failing to dismiss the modal" as reported. Filing this specific, unverified mechanism verbatim (title: "migrate per css-architecture.md") risks sending whoever picks up the follow-up into a createPortal migration that fixes nothing, while the real mechanism (most likely: `isOpen` never actually reaches `false` in the mobile repro — e.g. a double-fire event, a race with a subsequent `open()`/`toggle()` call, or some other state-update issue in `OmnibarContext.tsx`) goes uninvestigated. — Recommend: before filing, either spend a few minutes checking `open`/`openInCreationMode`/`toggle` (`OmnibarContext.tsx:130-153`) for a plausible double-invocation/race explanation, or file the item scoped to the *symptom* only ("modal sometimes doesn't dismiss after onClose on mobile — mechanism unconfirmed") with the CSS theory demoted to "one hypothesis to check, not yet corroborated against the `if (!isOpen) return null` guard."

## Concerns

- [ ] **This PR does not fix the full reported symptom, and nothing in the plan states that plainly for reviewers/stakeholders.** The original bug report (`requirements.md:26-30`) describes two symptoms: the modal stayed open, and the button was stuck on "Creating...". This fix only addresses the second (the button becomes clickable again after the `finally` reset). Given the Blocker above, the first symptom's actual cause is still unknown and unfixed after this ships — a user in the exact repro scenario would still see a modal that won't close, just with an interactive button instead of a frozen one. — Recommend stating this partial scope explicitly in the PR description and in the backlog item close-out, so it isn't read as a full fix.
- [ ] **Requirement 4 ("failure path... already works... must not regress") is not actually true for the SpawnShell branch, and the plan's own finding isn't tracked anywhere actionable.** Unresolved Question #2 in the plan documents that SpawnShell's `error` state has zero DOM rendering surface (it only renders via `OmnibarCreationPanel.tsx:839`, which never mounts while SpawnShell keeps the component in discovery mode) — so a SpawnShell `onCreateSession` failure is currently silent to the user, with no visible error at all. This is flagged as "informational," but unlike the Requirement 7 finding it gets no follow-up backlog item — it's just a doc note. Per this repo's own standing convention of tracking/fixing collateral debt found mid-task (see `.claude/rules/fix-flaky-tests-dont-defer.md` and the analogous treatment given to Requirement 7 in Epic 1.3), this should get the same treatment: either file a matching follow-up item for "SpawnShell failures produce no visible error," or explicitly amend Requirement 4 in `requirements.md` to scope out SpawnShell's error visibility instead of asserting something the investigation shows is false.
- [ ] **The unconditional `finally`-based reset, combined with the new `!isOpen` defense-in-depth reset, widens a pre-existing overlapping-submission race with no test coverage.** Scenario: user submits (isSubmitting=true, request A in flight) → modal is closed and reopened while A is still pending → the `!isOpen` effect now force-resets `isSubmitting` to `false` (Story 1.1.3) → user submits again (request B in flight, isSubmitting=true) → request A finally resolves/rejects, and its `finally` unconditionally calls `setIsSubmitting(false)`, clobbering B's in-flight state and re-enabling the Create button while B is still outstanding. This pattern already exists in today's Default branch in isolation, but this PR (a) extends it to two more branches and (b) makes reaching the overlap window *more* likely by adding the very reset (Story 1.1.3) designed to unblock resubmission after a stale close. No task/test in Epic 1.2 exercises overlapping submissions. — Recommend either a lightweight submission-id/ref guard in `finally` ("only reset if this call is still the latest"), or an explicit note accepting this as a known, pre-existing limitation out of scope for a Complexity-1 fix.
