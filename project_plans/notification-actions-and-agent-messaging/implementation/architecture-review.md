## Blockers

- [ ] **Story 4.5 / ADR-007 rules 1, 3, 4 (caller identity, peer authorization, provenance)** — VIOLATION: the plan treats `callerSessionUUID(ctx)` as "derived server-side" and builds cross-pair `FORBIDDEN`, "only the named answerer can `answer_help`", and "from session B" provenance on it. VERIFIED in code that the UUID is client-asserted: `server/server.go:1112-1115` copies the `X-Stapler-Session-UUID` request header into the context with no proof, and `server/mcp/server.go:170-171` reads `STAPLER_SESSION_UUID` from the environment on stdio. `/mcp` is registered on the unauthenticated mux (`server/server.go:1118`). Any dispatched agent or local process can set that header and answer, schedule, or read as another session. The existing role gates (`diagnose_role_gate.go`) are "narrow-only, fail open when unidentified" and were never an authorization boundary. The ADR's consequences ("Peer help cannot be used to spoof ... answer another pair's request") are therefore false as written, and the Story 4.5 ACs only test honest callers. — REMEDIATION: (a) Bind MCP identity to an unforgeable per-session credential. The repo already has the mechanism for hooks: `server/services/hook_proof.go:21` (HMAC-SHA256 over session identity, ADR-010 2g). Mint a per-session MCP token at spawn (next to where `session/instance_tmux.go:637` and `server/mcp/proxy.go:62-68` inject the UUID header), verify it in `mcpWithUUID` before `WithSessionUUID`, and add a task plus AC "forged header without valid proof is rejected for the five new tools". (b) Or, if this is deferred, rewrite ADR-007 and the 4.5 ACs to state the same-user local trust model honestly, drop `FORBIDDEN`/anti-spoofing as security claims, and keep only server-side invariants (self-target, archived, one-shot, caps) that do not depend on identity. Either way, amend ADR-007 before Task 4.5a.

- [ ] **Story 4.1 / 4.3 (`WakeTrigger` state model, `SteerDelivery`)** — VIOLATION: the primary success metric is "wakes survive a service restart" and fire exactly once, but the design marks the row `fired` (guarded transition, 4.1 AC) before delivery, while delivery is an in-memory queue that waits for `IsReadyForSteer` with expiry (Task 4.3c, glossary `SteerDelivery`). A restart or crash between the `fired` commit and the pane write loses the wake permanently, and `fired` rows are "never re-fired" (4.3 AC). The reconcile counters and the missed-wake alert only count `missed`, so the loss is silent. `WakeStatus` (`pending/fired/missed/cancelled/skipped`) has no state that distinguishes "claimed" from "delivered". Story 4.8's `needs_revive` status (AC "rest queue as `needs_revive`") is also not in `WakeStatus`, so the model does not even cover the plan's own tests. — REMEDIATION: split claim from delivery in the schema. Add `delivery_state` (`unclaimed -> claimed -> delivered | expired`), `claimed_at`, `delivered_at` to `wake_triggers` (Task 4.1a/4.1c); `Fire` only claims. The row becomes `fired` (or `delivered`) after the successful pane write confirmed by `IsReadyForSteer` plus write result. Reconcile re-queues `claimed` rows older than the claim lease and applies the expiry rule. Delivery is at-least-once, de-duplicated by the `<wake id=...>` marker in the payload. Add `needs_revive` (or `deferred`) to the enum and glossary. Add ACs: "kill after claim, before write -> restart delivers once" and "delivered row never re-sent". Without this, the 4.8 restart test cannot pass for the busy-session case.

- [ ] **Story 3.3 Task 3.3c (cancel-on-session-end sweep) and Tech Debt Disposition** — VIOLATION: the task says "extend the existing self-heal sweep for cancel-on-session-end" in `session/backlog_lifecycle.go`. VERIFIED no such sweep exists for guidance rows: `CancelGuidanceRequest` has no production caller (only the repository and storage forwarders, `session/ent_repository_guidance.go:338`, `session/storage_guidance.go:32`), and `backlog_lifecycle.go` / `backlog_notifier.go` contain no guidance references. `selfHealStuck` (`backlog_lifecycle.go:2145`) is backlog-item scoped. The target file is the repo's highest-churn hotspot (2441 lines, 81 commits touching it in 90 days, measured with `git log --since=90.days`), and the plan's Tech Debt Disposition has no row for it. Putting session-scope hook-question cleanup in the backlog lifecycle listener also puts a non-backlog entity's lifecycle in a backlog-domain class (SRP/layering). The AC "pending hook-source row whose session is archived -> `cancelled_at` set" is therefore unimplementable as described. — REMEDIATION: re-scope 3.3c as a new small component, e.g. `GuidanceSessionReaper`, wired at the session-end/delete seam that already notifies `PendingQuestionStore` (`server/services/hidden_question_reply.go:241` calls `store.SessionDeleted`) plus a startup pass for rows whose session is archived/stopped/missing. It calls `CancelGuidanceRequest`. Remove `session/backlog_lifecycle.go` from the Story 3.3 Files line. Add a Tech Debt Disposition row stating "do not extend `backlog_lifecycle.go`; isolate via new reaper".

## Concerns

- [ ] **Story 0.8 / ADR-008 (flags)** — Files and design duplicate existing code. `server/features/flags.go` and `server/features/client_event.go` are feature-registry metadata only (28 and 17 lines of `featureregistry.Register`), not flag controllers or a client-event sink. Real flag plumbing is `server/services/feature_flag_service.go` (known-flag table with `scopes`, `FlagAuditPolicy`, `flagScopeReadback`) plus `config/config.go:1915-1945`, where `Config.GetFeatureFlagScoped(name, scope, default)` already implements "scope's explicit value wins, then global, then default" (no production caller yet). A new `ResolveScopedFlag` in `server/features/scoped_flag.go` would be a second resolver. Recommend: Task 0.8b adds callers/tests for `GetFeatureFlagScoped`, no new resolver; register the four flags in `feature_flag_service.go` with `*FlagController` and an audit policy following `replyFlagController` (`hidden_question_reply.go:85`); note loosening flips are audit-fsynced and refused when the sink is down (affects the `background_activity_feed` default ON path). Story 1.5 / S7 check (4) must locate the real client-event RPC handler; `server/features/client_event.go` is the wrong target.

- [ ] **Story 4.2 (scheduler seam)** — `workflows.Scheduler` is workflow-shaped: `Start` loads workflows from `repo` and returns early if `repo == nil` (`scheduler.go:158-162`), and the cron is built with a minute-granularity parser (`scheduler.go:75-79`). robfig/cron v3.0.1 has no clock injection (`option.go` offers only `WithLocation/WithSeconds/WithParser/WithChain/WithLogger`), so the AC "`ScheduleAt('w1', now+2s)` with a fake clock" is not implementable against it. Wakes would also silently stop wherever the workflow scheduler is not constructed (`dependencies.go:1788` area). Recommend: `WakeDispatcher` owns one timer keyed to `min(next_fire_at)` from the durable table (rebuilt on create/cancel/restart) and uses `cron.ParseStandard` only to compute the next time for `cron` triggers. Drop the "second consumer of `workflows.Scheduler`" coupling, or keep the `WakeScheduler` seam but inject a clock into the dispatcher, not into robfig. This also removes the ADR-006 / Debt-table promise "register through the one cron engine", which research flagged as the point.

- [ ] **Story 4.3 / 4.4c / 4.5c (package dependency direction)** — `server/wakes` needs `SessionSteerer` and `BacklogService.Admit` (both in `server/services`), while `server/services/guidance_request_service.go` must call into wakes for `guidance_answered`, and `server/mcp` imports both. Without consumer-defined interfaces this is an import cycle (the repo already solved it in `server/workflows/scheduler.go:28-45` with `AdmissionGate` "defined here, not in server/services"). Add a task or AC: wakes defines `Steerer`, `Admission`, `OwnerLookup` ports; services depends on a tiny `AnswerListener` func type owned by services, set by wiring. Likewise `isOneShot` is unexported in `session/session_driver.go:1171`; the wake guard needs an exported predicate or an `OwnerLookup` method.

- [ ] **Story 4.3d / ADR-007 rule 5 (`noarchivedrevival` coverage)** — the analyzer's scope is a fixed file list (`tools/lint/noarchivedrevival/analyzer.go:40-44`), and `server/wakes/*` is not in it, so the stated guard "revive call site in the `noarchivedrevival` scope" is unenforced; only a spy test covers it. Add a task to add the wake revive file(s) to the analyzer list. Also, "SpawnGate" does not exist as a type (only `spawnSessionAfterGates` and `BacklogService.Admit` at `backlog_service.go:562`), and a revive of an existing stopped session is not a spawn. State exactly which gate applies (`Admit` for WIP cap; rework cap is spawn-only) and name the interface.

- [ ] **Story 3.1 / ADR-003 (aggregate and illegal states)** — `GuidanceRequest` gains about 11 columns across three concerns (question content, peer addressing, answer-delivery lifecycle), stored as strings validated in Go. Illegal combinations are representable: `source=peer` with `answerer_kind=human`, `answerer_session_uuid` set with `answerer_kind=human`, `delivery_state=sent` with `delivery_route=read_only`, `asker_session_uuid != session_uuid` for scope=session. Add a single constructor/parser (`NewGuidanceRequest` with a `Source`-keyed sum type or `Addressee` value object) that enforces these cross-field rules at the repository boundary, plus a guarded transition table for `DeliveryState`. Consider moving delivery tracking to a child `AnswerDelivery` row instead of widening the question aggregate; the requirement forbids a second question store, not a delivery record.

- [ ] **Story 3.3 / 4.5c (answer-path side effects)** — `GuidanceRequestService.Answer` already runs `notifyAnswered` (INPUT_REQUIRED, needs-human class, scope=session; `guidance_request_service.go:68-82`) and `resumeTriageIfHalted` (`:100`, backlog-item scope only). For `source=ask_user_question_hook` rows answered from the pane this emits a second "Your guidance request was answered" notification beside the existing one, and for peer help it notifies the asker as if it were human guidance. Specify per-`source` behavior (suppress `notifyAnswered` for hook-source; peer answers route through the wake/`SteerDelivery` instead), with an AC.

- [ ] **Story 2.7 / ADR-002 decision 4 (reaper "event" claim)** — `ReapResolvedItemNotifications` is a polled, item-scoped pass keyed on `metadata["item_id"]` with an `ItemStateLookup` (`resolved_item_reaper.go:28-62`). Keying it on `question_id`/`approval_id` and making it event-driven (Task 2.7a) is new design, not "the reaper pattern". Re-size 2.7a and name the event source (answer success in the dispatcher publishing a resolve event to the store).

- [ ] **Story 2.2 / 2.8 (descriptor read-time listener identity)** — descriptors must carry `available=false, reason=desktop_only` on `:8444`, but `GetNotificationHistory` is served through `SessionService` -> `NotificationService` (`session_service_delegates.go:269`, `notification_service.go:209`) with no stated way to know the listener. `EvaluateLocalWrite(ctx, peerAddr, profile)` (`local_write_verdict.go:57`) is the only precedent and works on the request peer. - [ ] **Story 4.7b (guard test)** — "matches only the existing prompt strings" understates the allowlist: `ScheduleWakeup` appears in at least `server/mcp/tools_backlog.go` (5 sites), `server/mcp/tools_backlog_test.go`, `tools_backlog_wait_cap_test.go`, `server/services/backlog_service_verdict_steer.go`, `session/backlog_context.go:120`, `session/backlog_commands.go:234`, `session/pipeline_mode_seed.go:170,412`, `session/backlog_post_review_prompt_test.go` (found with `git grep ScheduleWakeup -- '*.go'`). ### Blocker 1 (caller identity, 4.5/4.9): resolved in design, with three wiring concerns
- Verified premise holds: `server/server.go:1112-1115` copies the header unauthenticated; `HookProofs` (`server/services/hook_proof.go:44-110`) has `mac/HeaderValue/Verify` over a domain string, so a second domain `ssq-mcp-v1` is a small addition. Verifying in `mcpWithUUID` (package `server`, which already imports `server/mcp` and `server/services`) creates no import cycle. Fail-closed `identity_unverified` on the five new tools, with the old `WithSessionUUID` unchanged, is correct. ADR-007 rule 0 states the residual same-user limit honestly.
- [ ] CONCERN **Task 4.9b, mint-at-spawn layering.** The plan says "minted at spawn" in `session/instance_tmux.go`, but `HookProofs` lives in `server/services`, which imports `session` (`hook_proof.go:16`); `session` cannot call it. `buildExtraEnv` (`instance_tmux.go:729-740`) and `claudeMCPConfigArgsWithToken` (`:655`) have no such seam. Specify an injected provider in `session` (precedent: the `SetMCPServerURL` func provider) wired from `server`, and a nil-provider behavior (no proof, new tools refuse).
- [ ] CONCERN **Proof leaks via argv by default.** `claudeMCPConfigArgsWithToken` puts headers inline in `--mcp-config` argv unless a local token exists (`:667-669`; the 0600-file path is taken only when `token != ""`). A proof added to `headers` would be visible in `ps` to any same-user process, i.e. any other session's Bash tool, which is cheaper than the `/proc` environment read the ADR cites. Require the proof-bearing config to always use the 0600 file route (or an env-expanded header) and add an AC "proof never appears in argv".
- [ ] CONCERN **Rollout/compat not stated.** Sessions spawned before the upgrade (and `RunStdio` at `server/mcp/server.go:170`, which sets only the unverified UUID) have no proof, so the five new tools return `identity_unverified` for them. Say so in Story 4.9, and note secret rotation (`HookProofs.Rotate`) revokes MCP proofs too.
- Nit: Story 4.9 Files lists `server/mcp/context.go`; it does not exist (`WithSessionUUID` is at `server/mcp/tools_backlog.go:32`). Mark it new, which also keeps the identity code out of the 3235-line hotspot.

### Blocker 2 (wake durability, 4.1/4.3): resolved, with state-model gaps

It lists `pending->claimed`, `claimed->delivered|needs_revive|missed`, `needs_revive->claimed|missed`. ACs also require `pending->missed` (4.1, expired without claim), `claimed->skipped` (4.3 archived/one-shot guards), and `cancelled` from `pending|claimed|needs_revive`. Recurring `cron` rows (`max_fires`, `fire_count`) need a `delivered->pending` re-arm or a successor row; neither is specified.
