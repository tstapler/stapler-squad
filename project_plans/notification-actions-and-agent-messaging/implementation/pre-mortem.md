## P1 Items (address before implementation)

- [ ] **#1 Background `finished` is unsatisfiable** (VERIFIED inputs: plan.md glossary `ActivityKind` and Story 1.2 ACs define `finished` as "stopped AND a non-error history record exists"; ADR-001 Alternatives says producers emit TASK_COMPLETE/STATUS_CHANGE and the gate suppresses them for hidden sessions; requirements show 0 history rows for 11 sessions. INFERRED conclusion: in production no such record will ever exist, so Story 1.2's passing fixture, which adds a `review:abc` history record, tests a state the live system never produces.) Plan change: before Story 1.2 starts, pick and state the production evidence for `finished` from data the tab already has or can cheaply get: the linked backlog item's status/verdict, the session's exit/last-status field in `HiddenSessionSummary`, or one small server-side `outcome` field on the hidden session list. Change Story 1.2 ACs to use that source, add an e2e (Story 1.4) whose seed has no history rows and still yields at least one `finished` row, and add a metric alert if `finished` is 0 while stopped > 0 for a day. Also update ADR-001 decision 3, which still says "all healthy" (VERIFIED: `decisions/ADR-001-...md:15`) while the plan and `design/ux.md` use "no failures reported".

- [ ] **#2 10-minute sampler `stale` blocks late answers** (VERIFIED text: plan.md Story 3.3 AC "after 10 minutes ... the row is `stale`"; Story 3.7 and ADR-010's claim TTL of 30 min show answers are expected later). Plan change in Story 3.3 and Task 3.3f: ending sampling after 10 minutes means "stop polling", not "mark stale"; a row leaves answerable state only when `DialogMatch` fails at write time (already the STALE path) or the session ends. Add an AC: a row open 45 minutes with the dialog still on screen can be answered with one digit and returns APPLIED. Also reconcile with the stated goal "zero new poll loops": document the sampler as the only exception, with the per-pass cap (20 rows), and have it back off to 30 s after the first minute.

- [ ] **#3 Wake write into a live selection/permission dialog** (VERIFIED text: ADR-006 rule 2 gates delivery on `IsReadyForSteer` only; pitfalls section 1 records that cached status is blank 6-9 s after a keypress and that "newest hook wins" was wrong for exactly this reason; ADR-007 rule 4 escapes text but does not stop a leading `1` or Enter-equivalent). Plan change in Task 4.3c: before any `steer_text` write take the `TerminalWriteLease`, run a fresh `tmux capture-pane`, and refuse to write (row stays `claimed`) if any known dialog profile matches or the match is indeterminate; the wake payload always begins with a non-digit, non-whitespace marker (`<wake ...>`) and is written with `SubmitContentWithEnter`, never as a selection key. Add an AC and a fault-injection test: a pane showing the fixture `AskUserQuestion` dialog receives zero bytes from a due wake.

- [ ] **#4 Wake cost controls have no numbers** (VERIFIED text: ADR-007 rule 6 lists "max pending triggers per session, max fires per trigger, global wake budget per window, ... max chain `generation`" with no values; Story 4.3 uses "cap 5" only as a test example; Story 4.2 says cron minute granularity; pitfalls section 4 records the $106.69 idle-wait loop). Plan change: add a "Wake limits" table to plan.md and ADR-006/007 with default and hard ceiling for each: minimum cron interval (for example 5 minutes unless the operator raises it), per-session pending cap, per-owner fires per hour, global fires per hour, default and max `max_fires`, default and max `expires_at` horizon, and max `generation`. A `cap_exceeded` result must be a notified state (already required). Add a Story 4.8 storm test whose assertion is the numeric ceiling (for example, one owner with `* * * * *` yields at most the per-hour limit of deliveries) and a cost-shaped metric `wake_delivered_per_owner_hour`. Owner confirms the numbers once in W0 with the other Epic 4 decisions.
