## Blockers

- [ ] **Caller identity is not server-derived; ADR-007 rules 1-3 rest on a forgeable header.** `server/server.go:1112-1118` sets the MCP caller UUID from the client-supplied `X-Stapler-Session-UUID` header (and `server/mcp/server.go:170` from an env var) on the `/mcp` mux of the `:8543` listener, which the plan's own ADR-004 says has no authentication. `callerSessionUUID(ctx)` therefore returns whatever the caller claims. The plan's "never an argument" mitigation is a distinction without a difference: any session or local process that learns another session's UUID (MCP `list_sessions`/`get_session` expose sessions; not opened to confirm UUID is in the output, INFERRED) can set the header and (a) call `answer_help` as the named answerer, (b) schedule/cancel wakes as another owner, (c) get a hidden `review`/`diagnose` role's allowlist swapped for a work-session's full five-tool allowlist. The registration test (`GetTool` wrapping) proves tools are wrapped, not that the identity is trustworthy. The existing precedent (`withDiagnoseGate`, `diagnose_role_gate.go:42`) shares the same weakness but only restricts; here the identity grants authority. — Add a pre-implementation story and an ADR-007 amendment: bind MCP identity to an unforgeable per-session credential (e.g., reuse the HMAC proof already used for hook attribution in Story 3.3, issued at spawn and verified server-side), or explicitly scope the peer-help/wake authority claims down to "cooperative agents on a trusted host" and drop the "cannot answer another pair's request" acceptance criterion. Make 4.5a's tests forge the header and assert denial.

- [ ] **Hook-sourced AskUserQuestion rows collide with the existing GuidanceRequest coalescing and the pending cap of 4; the plan's dedup design misses both.** VERIFIED `session/ent/schema/guidance_request.go:105` indexes `(scope, scope_key, question_text)` and its comment (lines 92-104) states open-row dedup is enforced in Go inside `upsertGuidanceRequest`; VERIFIED `DefaultGuidanceRequestPendingCap = 4` per `(scope, scope_key)` (`ent_repository_guidance.go:18-25`). For `scope=session`, `scope_key` is the session UUID (schema line 46). Consequences the plan does not address: (1) two distinct `AskUserQuestion` calls in one session with identical text (different `hook_call_id`) coalesce into one row, so the second answer is delivered against the wrong call and a stale dialog; Story 3.1's dedup AC only tests same `hook_call_id`. (2) Questions the operator answers directly in the terminal never produce a Reply, so their rows stay open (Story 3.4e only detects acknowledgement of answers ssq sent); after four, every new question hits `PENDING_CAP_EXCEEDED` and is silently not mirrored, which defeats the Epic 3 goal and the success metric. (3) ADR-003's rationale for "no unique index" cites legacy default values, but the actual constraint is this existing Go-side coalescing and cap, which the ADR never mentions; peer-help rows (`source=peer`) also need a stated `scope`/`scope_key`, since an unspecified choice either exhausts the asker's cap or collides with hook rows. — Amend ADR-003 and Story 3.1: define coalescing as `hook_call_id`-keyed for `source != agent_mcp` (bypassing the `question_text` coalesce), give hook/peer sources a separate cap or exempt them with a bounded TTL, specify peer-help `scope`/`scope_key`, and add a task that auto-cancels a hook row on PostToolUse/dialog-gone regardless of who answered (with an AC: 5 terminal-answered questions then a 6th still mirrors).

- [ ] **Wake revival is claimed to sit under `noarchivedrevival`, but the lint will not cover it.** VERIFIED `tools/lint/noarchivedrevival/analyzer.go:39-45` hard-codes six file suffixes; `server/wakes/*` (Story 4.3d) is not among them. ADR-007 rule 5 says the revive call site is "a guarded function in the `noarchivedrevival` scope", and the plan's only enforcement is a spy test. The rule's own text says this invariant regressed repeatedly (7 sites over 4 review rounds) because it lived outside a mechanical check, and wakes are the highest-volume new auto-revival path (50-trigger storm in Story 4.8). — Add a task in 4.3d to add the dispatcher's revive file to `lifecycleFiles` (with analyzer testdata), or route the revive through a helper in an already-covered file; make "analyzer reports zero findings on `server/wakes`" an AC. Also state which function is the "normal resume path" (Story 4.3 never names it).
