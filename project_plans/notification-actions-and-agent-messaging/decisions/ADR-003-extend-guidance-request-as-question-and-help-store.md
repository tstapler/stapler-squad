# ADR-003: Extend `GuidanceRequest` additively as the single store for live questions and peer help

**Status**: Accepted (2026-10-18, owner defaults accepted at the Phase 5 start gate); prior status: Proposed (2026-10-17); amended 2026-10-17 after review (real coalescing/cap constraints, scope keys, mirror clearing, constructor); triad round 2: this ADR becomes Accepted when the owner-defaults list in plan `Unresolved Questions` is confirmed at the Phase 5 start gate (one explicit accept step for all eight ADRs; until then the stated defaults proceed)
**Project**: notification-actions-and-agent-messaging
**Flags**: `askuserquestion_structured`, `agent_wake_triggers`

## Context

`GuidanceRequest` (`session/ent/schema/guidance_request.go`, `proto/session/v1/guidance_request.proto:44-60`) is shipped, durable, and has a guarded answer path, but is single-question, human-answerer-only, and has no asker/answerer identity. Live Claude `AskUserQuestion` calls are held only in the in-memory `PendingQuestionStore` (256 cap, 30 min TTL, lost on restart). Requirements forbid a parallel question store; Open Question 3 asks whether peer help reuses the entity.

## Decision

Add columns and proto fields **additively, all with defaults** so existing rows stay valid under ent auto-migration:

| Field | Type / default | Purpose |
|---|---|---|
| `source` | string, `agent_mcp` | `agent_mcp` / `ask_user_question_hook` / `peer`. `ask_user_question_hook` means "mirrored from a harness prompt": a Claude `AskUserQuestion` hook, or a terminal-detected dialog of a replyable non-Claude profile (profile name kept in `questions_json.profile`). There is no `terminal_detect` source: a second value would need its own cap class, coalescing key and reaper scope for no behavioral difference. Without a `hook_call_id` (terminal-detected rows never have one) the payload-hash fallback applies |
| `asker_session_uuid` | optional string | who is waiting |
| `answerer_kind` | string, `human` | `human` / `session` |
| `answerer_session_uuid` | optional string | named peer for `answerer_kind=session` |
| `multi_select` | bool, false | checkbox variant |
| `questions_json` | optional string | canonical `QuestionPayload` (1-4 questions, header, options with description, multiSelect); `question_text`/`options` keep carrying question 1 for old readers |
| `delivery_route` / `delivery_state` | string, empty | `live_keystroke`/`hook_reply`/`resume`/`read_only`; `pending`/`sent`/`acknowledged`/`delivery_failed`/`saved_for_later`/`stale` |
| `delivery_attempts` | int, 0 | bounded retry accounting |
| `hook_call_id` | optional string | correlates to the live hook invocation (`tool_use_id`) |

Rules:
1. **Dedup, coalescing and caps for the new sources (corrected rationale).** The reason there is no new unique index is **not** only legacy default values. The actual existing constraints are: (a) `session/ent/schema/guidance_request.go:105` indexes `(scope, scope_key, question_text)` (non-unique) and `upsertGuidanceRequest` (`session/ent_repository_guidance.go:231`) coalesces an **open** row with the same `(scope, scope_key, question_text)` in Go inside the create transaction; (b) `DefaultGuidanceRequestPendingCap = 4` per `(scope, scope_key)` (`session/ent_repository_guidance.go:18-25`) refuses a fifth open row with `PENDING_CAP_EXCEEDED`. Left as is, two distinct `AskUserQuestion` calls in one session with identical text would merge into one row (the second answer would target the wrong call), and four questions answered in the terminal (which never produce a Reply) would leave four open rows and silently block every later mirror. The decision:
   - **Coalescing key for `source != agent_mcp` is `(asker_session_uuid, hook_call_id)` when `hook_call_id` is present, else the canonical payload hash; the `(scope, scope_key, question_text)` coalesce is bypassed for these sources** (the `agent_mcp` path is unchanged). Lookup-then-insert stays inside one transaction on the single-connection SQLite handle; no new database unique index (a nullable column in a SQLite unique key is distinct per row, and a non-null default would collide across legacy rows). A `-race` test asserts exactly one row from N concurrent creates, and a second test asserts two calls with identical text but different `hook_call_id` yield two rows.
   - **Scope keys**: hook-mirrored rows use `scope=session`, `scope_key=<asker session UUID>` (as `agent_mcp` session rows do). Peer-help rows use `scope=session` with `scope_key=<asker session UUID>` and `source=peer`; the **pending cap is counted per `(scope, scope_key, source-class)`** where source-class is `agent_mcp` vs `{ask_user_question_hook}` vs `{peer}`, so hook mirrors and peer help can neither exhaust the 4 slots of agent guidance nor each other. This is a code change, not a property of the current code: `enforceGuidanceRequestPendingCap` (`session/ent_repository_guidance.go:272-292`) filters only on `scope`, `scope_key`, `answered_at IS NULL` and `cancelled_at IS NULL`, with no `source` predicate, so as written hook and peer rows would count against `agent_mcp` guidance. The function gains a `sourceClass` argument and a `source` predicate (legacy rows default to `agent_mcp`, so existing behavior is preserved); tests run in **both directions** (4 open `agent_mcp` rows then a hook create succeeds; 4 open hook rows then an `agent_mcp` create succeeds; likewise peer; each class still refuses its own 5th). Hook and peer sources additionally carry a bounded TTL (hook rows: cancelled by the clearing rules below; peer rows: `expires_at` of 24 h, then `cancelled` with reason `expired`).
   - **Mirror clearing**: a hook-source row is auto-cancelled (reason `answered_in_terminal` or `dialog_gone`) when ssq observes the dialog resolved by any route: the `PostToolUse` event for `AskUserQuestion` (if the Story 3.4e spike shows the injected matcher covers it), else the pane no longer matches `DialogMatch` on two consecutive samples (taken by the `DialogGoneSampler`, Task 3.3f: it polls only sessions that have an open hook-source row, every 3 s per row for the first minute then every 30 s, at most 20 rows per pass; after 10 minutes it **stops polling that row and leaves it open and answerable**. Answerability never depends on the sampler: a row leaves the answerable state only through a failed `DialogMatch` at answer time, a confirmed dialog-gone, a terminal answer or the session ending, so a question the operator answers from a phone 45 minutes later still works. A row the sampler gave up on could otherwise hold a pending-cap slot, so a create that would hit the hook-class cap first re-verifies that session's open hook rows once, on demand, and cancels those whose dialog is gone (reason `dialog_gone`); this is the only extra capture and it is event-driven, not a poll), else the originating session ends (`GuidanceSessionReaper`, Story 3.3). Without this the cap-of-4 starvation above recurs. Acceptance: five terminal-answered questions followed by a sixth still mirrors (Story 3.3).
   - **Reaper scope (round 2).** `GuidanceSessionReaper` cancels only rows whose dialog or peer context dies with the session: `source=ask_user_question_hook` (the dialog is gone with the process) and `source=peer` rows asked by or addressed to the ended session. It never cancels `source=agent_mcp` session-scope guidance (created by `server/mcp/tools_guidance.go`); those follow Story 3.4's delivery states (`saved_for_later` for a stopped session, stored-but-undelivered for an archived one).
   - **Accepted limitation (round 2).** A hook payload with no `hook_call_id` falls back to the canonical payload hash, so two genuinely distinct `AskUserQuestion` calls with identical content in one session coalesce into one row. Accepted: hook payloads normally carry `tool_use_id` (S1 records whether the real payload does), and the consequence is one answer serving two identical questions.
2. `status` stays derived from timestamps; delivery state is a separate fact (answered != delivered).
3. Peer help is the same lifecycle with `source=peer`, `answerer_kind=session`: `AnswerGuidanceRequest` gains an **answerer authorization** step (human RPC answers only `answerer_kind=human` or an explicit operator override; the MCP answer tool only the named answerer session). The current "no ownership check, human-only" behavior is preserved for `human`.
3a. **Per-source answer side effects.** `GuidanceRequestService.Answer` already runs `notifyAnswered` and `resumeTriageIfHalted` (`server/services/guidance_request_service.go:68-100`). For `source=ask_user_question_hook` the answered notification is suppressed (the operator already acted on the pane card; a second "Your guidance request was answered" would duplicate it); for `source=peer` the asker is told through the implicit `guidance_answered` wake and `SteerDelivery`, not through `notifyAnswered`, which is human-guidance copy. `resumeTriageIfHalted` is backlog-item-scope only and does not fire for session-scope rows. Each is an AC in Stories 3.3 and 4.5.
3b. **Illegal states are rejected at the repository boundary.** A single constructor/parser `NewGuidanceRequest` (domain package `session/domain`, new file; note `guidance_request.go` does not exist there, the existing types live in `backlog.go:307,330`) enforces: `source=peer` implies `answerer_kind=session` and a non-empty `answerer_session_uuid`; `answerer_session_uuid` only when `answerer_kind=session`; `delivery_route=read_only` implies `delivery_state` in `{stale, saved_for_later, delivery_failed}`, never `sent`; for `scope=session`, `asker_session_uuid == scope_key`. `DeliveryState` transitions go through a guarded transition table (conditional UPDATEs). Delivery tracking stays on the row (a child `AnswerDelivery` table was considered and rejected: it adds a join for no behavior the guarded transition table does not give).
4. Asker/answerer UUIDs are resolved by UUID, never by title/tmux name (`MatchesID` ambiguity, pitfalls section 1).
5. `PendingQuestionStore` is kept as a verified-proof cache for the keystroke path; the durable row is the source of truth for rendering. After restart the row is re-hydrated and re-verified via `DialogMatch` before any write.

## Consequences

- One table, one answered-at-guarded UPDATE, one notification path; the inline UI and session view share the same entity.
- Extra nullable columns widen the row; acceptable at hundreds of rows.
- `question_text` duplication with `questions_json` is a compatibility cost, retired when old readers are gone.

## Alternatives rejected

- **Separate `AgentMessage`/`PeerHelp` table**: a second durable question store, forbidden by requirements and doubling the answer/guard code.
- **Make `PendingQuestionStore` durable**: it is shaped around the keystroke path (hook proof, claim TTL) and would still not serve MCP-originated or peer questions.
- **Unique index on a new `question_key` column**: fails against legacy rows and nullable-in-unique semantics; the real conflicts are the existing Go-side coalesce and pending cap, see rule 1.
