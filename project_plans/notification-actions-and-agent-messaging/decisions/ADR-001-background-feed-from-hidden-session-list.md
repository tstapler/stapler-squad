# ADR-001: Background activity feed is derived from the hidden-session list; the delivery gate is unchanged

**Status**: Proposed (2026-10-17); amended in the Phase 4 repair (roll-up copy, session role vs state, server-computed outcome as the evidence for `finished`); triad round 2: this ADR becomes Accepted when the owner-defaults list in plan `Unresolved Questions` is confirmed at the Phase 5 start gate (one explicit accept step for all eight ADRs; until then the stated defaults proceed)
**Project**: notification-actions-and-agent-messaging
**Flag**: `background_activity_feed`

## Context

The Background tab is empty because `selectBackgroundRows` (`web-app/src/lib/utils/backgroundActivity.ts:86`) reads only notification history, and the delivery gate drops routine events for hidden sessions before they reach the bus or history (`server/deliverygate/policy.go` `typeClass` / `ShouldDeliver`; `gate.go:201`). Evidence and the live counters are in `research/architecture.md` section 1 (11 hidden sessions, 0 history rows, `suppressed{reason=routine_for_hidden}` counters non-zero). The empty tab is the intended behavior of ADR-001 of the tray plan, not a producer or prune bug.

## Decision

1. Build **activity rows from the hidden-session list the tab already polls** (`useBackgroundSessions`, `ListSessions{hidden_only}` every 30 s). One row per hidden session: title, **role** (`SessionRole`: review/diagnose/triage/other from tags), **state** (`ActivityState`, the chip), last-activity time, link to the linked backlog item when present. "Kind" is no longer used for either.
2. Failure-class and needs-human rows from history stay **pinned first**, joined to the same session rows (one row per session, exception state wins).
3. Never-blank roll-up: "N background sessions, no failures reported. Last activity <t>." when there are no exceptions; "No background work. Review and diagnose sessions will appear here while they run." when there are no hidden sessions. The copy never says "healthy": absence of a failure record is not proof of health. A stopped session is `finished` only with positive evidence (decision 6) and otherwise `stopped_unknown` (chip "Stopped, outcome unknown").
4. **The delivery gate is not modified.** No new RPC *definition*: Story 1.5 posts counts through the existing client-event RPC, and decision 6 adds one additive field to the existing `Session` message returned by `ListSessions{hidden_only}`.
5. A durable server-side `background_activity` lane (written by a gate sink on suppress) is deferred and only built if the session-derived feed proves insufficient (retention/reaping deletes the sessions the feed refers to). This is recorded as a follow-up trigger, not scheduled work.
6. **Evidence for `finished` (added in the Phase 4 repair).** The earlier plan defined `finished` as "stopped AND a non-error history record exists". That is unsatisfiable in production: the gate suppresses the routine records (TASK_COMPLETE, STATUS_CHANGE) for hidden sessions by policy (`server/deliverygate/policy.go` `typeClass`, `ClassRoutine`), so history holds none and every stopped session would read `stopped_unknown` forever. The evidence source is instead a server-computed `Session.background_outcome` (`completed | failed | unknown`, proto field added to `Session`, populated only for `ListSessions{hidden_only}`), derived from state that does exist: `ItemSession` rows (`proto/session/v1/backlog.proto` `ItemSession`, looked up by `GetItemSessionBySessionUUID`, `session/storage_backlog.go:386`) and the session status. `completed` = an `ItemSession` for the session carries a recorded `review_verdict` (review role) or `triage_result` (triage role); `failed` = status `CRASHED`, or an `end_reason` on the **failure allowlist** below; everything else, including the diagnose role (no verdict is recorded for it) and a session with no `ItemSession`, is `unknown`. **Failure allowlist (triad round 2; default is non-failure).** `end_reason` is free text written by several producers, so "non-empty and not `shutdown`" would mislabel benign values as failures. Verified by reading every call of `UpdateItemSessionEndedWithReason` / `UpdateItemSessionEndedWithDetail` at this commit: failure values are `pool_saturated`, `idle`, `timeout`, `claude_not_found`, `subprocess_start_error`, `fanout_ceiling`, `cost_ceiling`, `other` (all from `classifyHeadlessCallError`, `server/services/backlog_service_triage.go`), `parse_error` (`backlog_service_trigger_triage.go`), and the Jules values `dispatch_failed`, `dispatch_incomplete`, `jules_timed_out`, `jules_session_missing`, `jules_failed` (`jules_dispatch_service.go`, `session/jules_session_poller.go`). Explicitly not failures: the empty string, `shutdown` (our own restart), `jules_completed`, `jules_completed_no_pr`. Any other value, including the caller-supplied `reason` of `stopGuardrailSession` (`server/services/session_service_liveness.go:164`) and any value added later, is **not** a failure and leaves the outcome `unknown` until it is added to the allowlist in `session/background_outcome.go`. `orphaned_triage` is a stuck-reason name (`session/backlog_lifecycle.go`), not an `end_reason` value. `completed` is evaluated first, so a recorded verdict wins over a later failure reason. History still contributes only the pinned exceptions. Whether the 11 live stopped sessions actually have verdicts is checked read-only in Spike S7 item (8); if none do, the feed still ships with `stopped_unknown` rows and the metric alert in Story 1.5 reports that `finished` is zero while stopped sessions exist.

## Consequences

- Lowest-risk increment, client-only, flag kill switch restores the old selector.
- The feed shows current state, not history: a reaped session disappears. `departed` for one poll cycle is new selector behavior (Task 1.2c), not existing handling. Accepted.
- Waiting-for-human state for a hidden session still arrives through history (needs-human class passes the gate), so pinned rows remain correct.
- Triad round 1: a permanent `Stopped, outcome unknown` row is retired by a browser-local "Mark reviewed" (no server write), the list is bounded by an "Older (24 h)" collapse and the 100-row cap, new failures are named in a sticky strip rather than a count-only pill, and the tab's accessible name carries only the exception count (`design/ux.md` 1.4; plan Story 1.8). None of this changes the decisions above.

## Alternatives rejected

- **Loosen the gate so routine hidden events enter history**: re-opens the notification flood the gate was built to stop (283 hidden records, 166 from one producer) and breaks `PruneHiddenSessionNotifications` assumptions.
- **New server-side activity lane now**: more moving parts (schema, retention, RPC) for no increment in value over the session list today.
- **Fix producers**: producers are correct; they emit TASK_COMPLETE/STATUS_CHANGE which the gate suppresses by policy.
