# ADR-006: Durable `WakeTrigger` ent table, one dispatcher, startup reconcile from the database

**Status**: Proposed (2026-10-17); amended 2026-10-17 after review (claim/delivery split, dispatcher-owned timer, reconcile predicates); round 2: complete transition table, cron re-arm, stale-claim re-queue scoped; Phase 4 repair: single owner-state decision table (incl. `allow_revive=false`), guards scoped by action kind, wake-write safety, numeric limits; triad round 1: cron timezone/DST (rule 9), duplicate-delivery contract and busy-owner hold (rule 10), reconcile digest (rule 11); triad round 2: this ADR becomes Accepted when the owner-defaults list in plan `Unresolved Questions` is confirmed at the Phase 5 start gate (one explicit accept step for all eight ADRs; until then the stated defaults proceed)
**Project**: notification-actions-and-agent-messaging
**Flag**: `agent_wake_triggers`

## Context

Sessions poll with the client-side `ScheduleWakeup`/`/loop` (ssq#428). The server has no code for it and cannot see, persist or survive-restart a wake. Claude Code's native scheduling is per-conversation, expires recurring tasks after 7 days, has no catch-up and cannot express "session B reaches state X" or "human answer arrives". The `EventBus` is in-process and lossy (`pkg/events/bus.go`). The only cron engine is `server/workflows/scheduler.go` (robfig/cron v3) and it never replay-fires after downtime. Recurring incident classes: in-memory notify-once maps lost on restart (stuck-item-visibility ADR-001), subscribe-after-read gaps (backlog-event-subscribe), wake/nudge storms ($106 headless idle loop), check-then-reserve races (diagnose nudge cap, Jules cap, rework cap).

## Decision

1. New ent entity `WakeTrigger`: `id`, `dedup_key` (**non-null string, unique index**; derived from owner + type + canonical spec; no nullable column in the key), `owner_session_uuid`, `trigger_type` (`at|cron|backlog_event|pr_event|ci_event|session_state|guidance_answered`), `spec_json`, `action_kind` (`steer_text|notify_operator`), `action_payload`, `status` (`pending|claimed|delivered|needs_revive|missed|cancelled|skipped`; `fired` is retired in favor of `delivered`), `claimed_at` (nullable), `delivered_at` (nullable, the idempotency fact), `delivery_attempts` (pane-write attempts), `rate_limit_deferrals` (int, default 0: consecutive claim-time rate-limit deferrals, see "Rate-limit deferral and cron"), `next_fire_at` (nullable, indexed with status), `fire_count`, `max_fires`, `generation`, `allow_revive` (bool, false), `expires_at`, `created_at`. Index `(status, next_fire_at)`, `(trigger_type, status)`.
2. **Claim is separate from delivery.** `Fire` only **claims**: guarded `UPDATE ... SET status='claimed', claimed_at=now WHERE status='pending'`; the loser is a no-op. The row becomes `delivered` (and `delivered_at` is set) only after the pane write succeeded, confirmed by `IsReadyForSteer` immediately before and a nil write result. The in-memory `SteerDelivery` queue is therefore a cache of `claimed` rows, never the source of truth. Delivery is **at-least-once**; the `<wake id=...>` marker in the payload lets a receiver tolerate a duplicate, and a `delivered` row is never re-sent. `needs_revive` holds a claimed wake whose stopped (non-archived, `allow_revive=true`) owner is waiting on `Admit`. Restart reconcile re-queues `claimed` rows older than the claim lease (default 2 min) and `needs_revive` rows, applying `expires_at` (past expiry -> `missed` with notification).
   - **Complete transition table (the repository rejects every other transition; terminal = `delivered`, `missed`, `cancelled`, `skipped`):**

     | From | To | When |
     |---|---|---|
     | `pending` | `claimed` | guarded claim |
     | `pending` | `missed` | `expires_at` passed without a claim |
     | `pending` | `cancelled` | owner or operator cancel |
     | `pending` | `skipped` | claim-time rate limit: the third consecutive deferral of a **one-shot** row (type `at` or an event type), reason `rate_limited`. A `cron` row never takes this transition (see "Rate-limit deferral and cron" below) |
     | `claimed` | `delivered` | confirmed pane write (non-recurring, or last fire) |
     | `claimed` | `pending` | **cron re-arm only**: confirmed write with `fire_count + 1 < max_fires` (and before `expires_at`); same transaction sets `fire_count++`, `delivered_at` (last occurrence), `next_fire_at` = next cron time, clears `claimed_at` |
     | `claimed` | `needs_revive` | stopped, non-archived owner with `allow_revive=true` waiting on `Admit` |
     | `claimed` | `missed` | expired while claimed/undeliverable |
     | `claimed` | `skipped` | archived/one-shot/terminal-item guard fired at claim time |
     | `claimed` | `cancelled` | cancel while queued |
     | `needs_revive` | `claimed` | re-admitted |
     | `needs_revive` | `missed` | expired |
     | `needs_revive` | `skipped` | owner archived while waiting |
     | `needs_revive` | `cancelled` | cancel |

     **Delivery decision table (single source of truth for stopped, archived and busy owners; ADR-007 rule 5 and plan Story 4.3 cite it and must not restate it differently).** Evaluated when a row is claimed. The revival guards apply to `steer_text` only:

     | action_kind | Owner state at claim | `allow_revive` | Result |
     |---|---|---|---|
     | `steer_text` | live and idle | any | wake-write safety check (rule 8), write, then `claimed -> delivered` |
     | `steer_text` | live but busy, or a dialog is showing | any | stays `claimed` in `SteerDelivery`; delivered when idle; past `expires_at` -> `missed` |
     | `steer_text` | stopped, not archived | true | `claimed -> needs_revive` until `Admit` admits it; `reviveStoppedOwner`; then as live; past `expires_at` -> `missed` |
     | `steer_text` | stopped, not archived | false (default) | `claimed -> skipped(reason=owner_stopped)` plus a failure-class operator notification. Never `needs_revive`: nothing can ever re-admit it |
     | `steer_text` | archived, one-shot, backlog item terminal, or deleted | any | `claimed -> skipped(reason=archived or one_shot or item_terminal or owner_missing)` plus notification; no revive call |
     | `notify_operator` | any, including archived, one-shot, terminal item, stopped, deleted | n/a | guards and revival are not applied (nothing is written to the owner). `claimed -> delivered` once the INFO notification is persisted; for a deleted owner the text says "Session no longer exists" |

     A `notify_operator` notification is emitted as a system-level notification with no session binding and the target in `metadata.target_session_uuid`. Reason: `deliverygate.ShouldDeliver` suppresses routine-class events for hidden sessions (`server/deliverygate/policy.go` `typeClass`), so an INFO notification bound to the hidden review session the operator asked to be reminded about would never reach history.

     **Rate-limit deferral and cron.** A claim-time deferral (Wake limits rows `fires_per_owner_hour` and `fires_global_hour`) is not itself a state change: the row stays `pending` and `next_fire_at` moves to when the window frees a slot. Each deferral increments the row's persisted `rate_limit_deferrals` column in the same UPDATE that moves `next_fire_at`; a successful claim (`pending -> claimed`) and a cron occurrence skip both reset it to 0, and because it is a column a restart neither loses nor resets it. When the increment reaches 3 a one-shot row takes `pending -> skipped(reason=rate_limited)`. A `cron` row instead **skips that occurrence**: it stays `pending`, `next_fire_at` advances to the next cron time, `fire_count` is unchanged, and the skip is counted in `wake_limit_hit_total` and the owner digest; rate limiting never makes a recurring row terminal (it ends only by `max_fires` or `expires_at`). The cron floor is **derived in code** from the effective per-owner limit: `effective_floor_minutes = max(5, ceil(60 / effective per-owner fires per hour))`. The default is 10 min (6 per hour), the hard floor 5 min (12 per hour, the per-owner ceiling). Config may set a lower floor, but it is clamped up to the derived value, so lowering the floor to 5 min with the per-owner limit still at 6 leaves the effective floor at 10 min; a 5 min cron needs the per-owner limit raised to 12 as well. Hence a cron at or above the effective floor never defers on its own limit (plan Story 4.3 AC).

     A recurring `cron` trigger is one row that cycles `pending -> claimed -> pending` until `max_fires` (then `delivered`) or `expires_at` (then `missed` if never delivered, `delivered` otherwise); no successor rows. The `<wake id=... n=fire_count>` marker makes each occurrence distinguishable. A `delivered` row is never re-sent; a re-armed row is `pending`, not `delivered`, so the "delivered is never re-sent" invariant is unaffected.
   - **Stale-claim re-queue is startup-only.** Lease-based re-queue of `claimed` rows runs once during startup reconcile, when the in-memory `SteerDelivery` cache is empty by construction. The periodic `ReconcileStuck`-cadence pass (rule 6) never applies the lease: it only handles `needs_revive` re-admission and overdue `pending` rows, and it skips every `claimed` id currently held by the live `SteerDelivery` cache (a legitimately waiting claim for a busy owner with `IsReadyForSteer=false`), so it cannot double-deliver. A `claimed` row that is not in the cache and is older than the lease while the process is running is reported by the stale-claim alert, not silently re-sent.
3. **One dispatcher** (`server/wakes.WakeDispatcher`): a single EventBus consumer (same shape as `StartVerdictSteering`) indexing pending triggers by `(trigger_type, key)` in memory, **subscribed before the initial state read** so there is no gap. **Time triggers are owned by the dispatcher, not by `workflows.Scheduler`.** Verified: `workflows.Scheduler` has no `ScheduleAt`/`ScheduleCron`/`Cancel` and no callback registration (public methods: `Start`, `Stop`, `Reload(wf)`, `Remove`, `FireNow`, `FireTrigger*`), `Start` returns early when `repo == nil` (`scheduler.go:158-162`), its cron uses a minute-granularity parser, and robfig/cron v3.0.1 offers only `WithLocation/WithSeconds/WithParser/WithChain/WithLogger` (no clock injection). So the dispatcher keeps **one timer keyed to `min(next_fire_at)`** over the durable table, rebuilt on create/cancel/restart, with an injected `Clock` interface (real clock in production, fake in tests); `cron.ParseStandard` (already a dependency) is used only to compute the next fire time for `cron` triggers. This is still the single admission path (claims, caps, guards) and not a row-scanning ticker: it sleeps until the next due row. The earlier "register through the one cron engine" promise is withdrawn. Package direction: `server/wakes` defines the ports it needs (`Steerer`, `Admission`, `OwnerLookup`, `Clock`) and `server/services` supplies adapters in wiring; `server/services` depends only on a func type `AnswerListener` it owns (set by wiring), so there is no `wakes <-> services` import cycle (precedent: `AdmissionGate` in `server/workflows/scheduler.go:28-45`).
4. **Startup reconcile** from the database before the dispatcher reports ready: load pending rows; `at`/`cron` overdue rows fire at most once if still within `expires_at` (no catch-up storm, "fire once when idle" like Claude Code) else become `missed` with an operator-visible notification; event-type triggers re-evaluate **current state** (item status, PR state, guidance row answered, peer session state) because replayed events do not exist. **Every supported `(trigger_type, kind, predicate)` must declare a persisted-state predicate used by reconcile**; a kind with no such predicate (a transient edge with nothing to re-evaluate, since `EventBus` drops events per slow subscriber and is in-process) is rejected at `schedule_wake` with the typed error `no_reconcile_predicate`, with a test over the full kind table. The supported table is enumerated in plan Story 4.4 (for example `status_transition` is accepted only as `status_reached(status)`, whose predicate is "item status equals the target", and `verdict_recorded` only with the predicate "item has a recorded verdict"; `item_updated`, `triage_progress_updated` and `activity_note_added` are rejected). Re-delivery checks `delivered_at` first. Overdue fires after a restart are queued and released through the same admission gate, not spawned in bulk.
5. Fire path invariants: coalesce/debounce window per trigger key, hard per-session and global caps under **one short process-wide cap lock** (`capMu`, check-then-reserve of the pending, fires-per-hour and `max_fires` counters; held only for the in-memory check plus one transactional COUNT or insert, never across a tmux call or a revive; the revive path uses a separate revive lock, ADR-007 rule 5, so create and claim checks never wait on a tmux and worktree spawn; the numeric defaults and hard ceilings for every cap, including the minimum cron interval, per-owner and global fires per hour, `max_fires`, `expires_at` horizon, `generation` and the busy-owner hold, are the 12-row "Wake limits" table in `implementation/plan.md`, the single source), `generation` counter incremented when a woken turn schedules another wake, delivery only when `IsReadyForSteer` is true (unknown means do not write; queue with expiry), payload delimited and provenance-labeled.
6. Self-heal piggybacks on the existing reconcile sweep cadence (`ReconcileStuck`); no new ticker.
7. The dispatcher is joined on shutdown with the other background goroutines and holds a single-leader guard against restart overlap (`service-restart-orphan-process`).
8. **Wake-write safety (pre-mortem P1).** Before any `steer_text` write the dispatcher takes the `TerminalWriteLease`, runs a fresh `tmux capture-pane`, and writes only when the capture positively shows the idle composer and no dialog (no `Enter to select` footer, no permission prompt, no unrecognized layout). A dialog, an indeterminate capture or a capture failure leaves the row `claimed` with no byte written. This is a generic "no dialog showing" test (`session.PaneShowsDialog`, plan Task 2.4c, which returns `Absent` only on a positively recognised idle layout): `session.DialogMatch` needs a specific question (`session/pane_reply.go:74`) and cannot serve as the negative check. The cached `IsReadyForSteer` status is not sufficient on its own because it is blank for 6-9 s after a keypress (`research/pitfalls.md` row 1). The payload always begins with the non-digit, non-whitespace marker `<wake ...>` and is written with `SubmitContentWithEnter`, never as a selection key, so even a race that lands inside a dialog cannot be read as an option choice.

9. **Cron timezone and DST.** Times are stored in UTC. A `cron` spec carries an IANA zone through the robfig `CRON_TZ=` prefix (supported by `cron.ParseStandard`, `robfig/cron/v3@v3.0.1/parser.go:95`) and defaults to `UTC` when absent, never to the server's local zone; an unknown zone is `invalid`. The operator sees the zone in the Scheduled prompts row. A wall-clock time inside a spring-forward gap does not exist and is skipped (robfig documents the same, `doc.go:169`), logged `reason=dst_gap`; an ambiguous fall-back time fires once, at the first occurrence; a backward clock jump never re-fires an occurrence already counted in `fire_count`. Tested with the fake `Clock` (plan Task 4.2d).
10. **Duplicate delivery and busy owners.** Every delivered text begins `<wake id=... n=...>` and ends with the standing sentence "If you have already acted on wake id ..., do nothing." so the at-least-once window (crash after the pane write, before `MarkDelivered`) is tolerated by the receiver; `wake_duplicate_delivery_total` counts a second write of one id. A `claimed` `steer_text` row for an owner that never becomes ready is held for the busy-owner hold (30 min, ceiling 2 h, never past `expires_at`; Wake limits row `busy_hold`) and then becomes `missed(reason=owner_busy_timeout)` with a digest entry.
11. **Reconcile digest.** One startup reconcile run raises at most one failure-class digest notification (up to 5 owners listed, a count for the rest), however many rows it marks `missed` or `skipped`; archived-owner `skipped` rows are counted in it rather than notified one by one; per-owner digests are capped at 1 per hour. Re-enabling `agent_wake_triggers` goes through the same admission, debounce and Wake-limits path (no catch-up bypass). `wake_needs_revive_age_seconds` above 3,600 raises a failure-class notification.

12. **Terminal-row retention and the dedup key.** `dedup_key` is unique among live rows only: in the same UPDATE that moves a row to a terminal state (`delivered`, `missed`, `cancelled`, `skipped`) the repository rewrites it to `<key>#<id>` (a tombstone, still non-null and unique), so the same trigger can be created again after it ended while a duplicate of a `pending`, `claimed` or `needs_revive` row still returns the first. A recurring `cron` row is not terminal between fires and keeps its key. Terminal rows are kept 30 days for the Scheduled prompts list and the audit trail, then deleted by a sweep that piggybacks on the existing reconcile cadence (rule 6) and runs once at startup; no new ticker. Task 4.1d.

## Consequences

- Wakes survive restart; missed wakes are visible rather than silent.
- Adds one table and one consumer; no new infrastructure, no new dependency (cron parsing already in robfig).
- Correctness is ours: clock jumps, double-fire and missed-fire are covered by explicit tests (Epic 4 story 4.8).

## Alternatives rejected

- **River/asynq job queue**: adds Postgres/Redis to a single-binary SQLite deployment.
- **Temporal/Inngest**: new infrastructure; model copied (event match + timeout), infra not.
- **Row-scanning ticker goroutine**: a second scheduler, constant DB load, divergent admission behavior.
- **Rely on Claude `CronCreate`/`ScheduleWakeup`**: session-bound, 7-day expiry, Claude-only, no state/human triggers; allowed only as an optional client accelerator.
