# ADR-007: Agent messaging security model: server-side caller identity, named-pair peer help, and no-revival wake policy

**Status**: Proposed (2026-10-17); amended 2026-10-17 after architecture and adversarial review (caller identity now bound to a per-session credential; revival lint scope extended); amended again in round 2 (proof delivered by 0600 file, not argv or env; revive path named); Phase 4 repair: proof minting extends to every harness whose MCP config ssq controls (S5), revival guards scoped by action kind, limits table; triad round 2: this ADR becomes Accepted when the owner-defaults list in plan `Unresolved Questions` is confirmed at the Phase 5 start gate (one explicit accept step for all eight ADRs; until then the stated defaults proceed)
**Project**: notification-actions-and-agent-messaging
**Flag**: `agent_wake_triggers`

## Context

`--allowedTools` is client-side only; Diagnose & Nudge (#880) shipped without a server-side gate and #894 had to add `withDiagnoseGate` around `write_to_session`, `send_control`, `run_command`, `steer_session`, `resume_session` (`server/mcp/diagnose_role_gate.go`). Today `steer_session`/`write_to_session` are unattributed raw injection reachable by any dispatched role, including into hidden sessions. New tools that write into another session's context (peer help, wake) have the same blast radius. `noarchivedrevival` forbids auto-reviving archived sessions, and a one-shot respawn loop (230+ respawns) showed archival alone is not sufficient (item terminal state must also be checked).

## Decision

0. **Trust model (stated honestly).** Today `callerSessionUUID(ctx)` (`server/mcp/tools_backlog.go:49`) returns whatever the client claimed: `server/server.go:1112-1118` copies the unauthenticated `X-Stapler-Session-UUID` header into the context on the `:8543` `/mcp` mux, and `server/mcp/server.go:170` reads `STAPLER_SESSION_UUID` from the environment on stdio. The existing `withDiagnoseGate` is narrow-only (it restricts) and fails open when unidentified, so a forged identity there loses nothing; the new tools **grant authority by identity**, so a forgeable identity is not acceptable for them. Decision: **bind the new tools' caller identity to a per-session credential that cannot be forged by knowing the UUID**, reusing the HMAC machinery of `server/services/hook_proof.go` (`HookProofs`, HMAC-SHA256 over a domain string and the session UUID, secret in the 0600 config-dir file). A new domain string `ssq-mcp-v1` makes an MCP proof non-interchangeable with a hook proof. `mcpWithUUID` (`server/server.go:1112`) sets a **verified** identity on the context (`WithVerifiedSessionUUID`) only when `X-Stapler-Session-Proof` verifies for the claimed UUID; the unverified `WithSessionUUID` remains for the pre-existing tools, unchanged.
   - **Delivery channel (corrected in round 2): files only, never argv, never tmux env.** The proof is delivered through 0600 per-session files in a 0700 directory, following how the local API token already avoids argv (`claudeMCPConfigArgsWithToken`, `session/instance_tmux.go:655-680`, writes `<configDir>/mcp/<uuid>.json` 0600 and passes only the path). Verified by reading the code: `claudeMCPConfigArgsWithToken` passes the whole config as inline `--mcp-config` JSON (visible to any same-user process in `ps`) unless a token exists (`token == ""` returns inline at lines 666-667); and `buildExtraEnv` (`instance_tmux.go:729-739`) injects through `tmux new-session -e`, which `tmux show-environment -t <session>` returns to any process that can reach the tmux socket (the repo already does exactly that: `session/nudge_gate.go:133`, `session/workspace_peers.go:179`) in addition to `/proc/<pid>/environ`. Therefore: (i) the Claude CLI path (`claudeMCPConfigArgsWithToken`) **always** uses the 0600 file route when a proof is present, and the proof-bearing config is never emitted inline; if the file cannot be written the launch omits the proof header (the session then gets `identity_unverified`) rather than falling back to inline; (ii) the stdio-proxy path (`server/mcp/proxy.go` `ProxyHeaders`) reads the proof from the per-session proof file `<configDir>/mcp-proofs/<uuid>` (path derived from `STAPLER_SESSION_UUID`), and there is **no** `STAPLER_SESSION_PROOF` environment variable; (iii) a test asserts the proof string appears in neither the built command line nor `buildExtraEnv()` output.
   - **Layering.** `session` cannot import `server/services` (`server/services/hook_proof.go:16` imports `session`). `session` therefore gets an injected provider (precedent: `SetMCPServerURLProvider`, `session/instance_actor_setters.go:75-81`), `SetMCPProofProvider(func(sessionUUID string) (headerValue string, ok bool))`, wired from `server`; a nil provider or `ok=false` means no proof is emitted and the new tools return `identity_unverified`.
   - **Harness coverage (Phase 4 repair).** A harness that cannot load an MCP config carrying our per-session credential cannot call the five tools at all, so "Claude-family only" is not a policy choice to make but a consequence of what each harness can load. The rule: a proof file and header are minted for **every harness whose per-session MCP config ssq writes and can point at a 0600 file** (Claude via `--mcp-config <path>`; any other harness only where Spike S5's MCP-identity item, Task 0.5e, shows a per-session config path or flag that can carry the header without argv or tmux env). Task 4.9g implements the harnesses S5 passes; the rest stay fail-closed with `identity_unverified`. Global `llm-sync` MCP entries cannot carry a per-session value and do not count. The requirement is worded accordingly: messaging and wake tools are available to sessions on harnesses that support MCP with a verified credential.
   - **Compatibility.** Sessions spawned before the upgrade, sessions whose proof file write failed, and the in-process `RunStdio` path (`server/mcp/server.go:170`, which has no HTTP middleware and sets only the unverified UUID) carry no proof: the five new tools return `identity_unverified` for them. This is documented in `docs/reference/wake-triggers-and-agent-messaging.md`; such sessions regain the feature on their next launch. `HookProofs.Rotate` revokes MCP proofs as well (every session needs a respawn to refresh its config file).
   - **What this defeats**: a dispatched agent or other client that learns another session's UUID (for example through `list_sessions`) and sets the header, and any local process that merely reads `ps` output. **What it does not defeat, stated plainly**: any process running as the same OS user can read `<configDir>/mcp/<uuid>.json`, `mcp-proofs/<uuid>` and the secret file (every session's Bash tool runs as that user), and an agent holding `run_command`, or `steer_session` + `read_session_output`, can make another session print such a file and read it back (those tools are not role-gated for work sessions; ADR-007 rule 7 leaves them unchanged). Keeping the proof out of argv and tmux env removes the cheap routes (`ps`, `tmux show-environment`, `/proc/<pid>/environ`), but a prompt-injected agent told to `cat` another session's MCP config can still obtain it. **Accepted risk (decision; owner confirms in Unresolved Questions):** the guarantee is "an agent cannot act as a session by UUID knowledge alone", not "a hostile or prompt-injected same-user agent is excluded". Best-effort mitigation, explicitly not a security boundary: `read_session_output` and `wait_for_output` redact strings matching the proof header value format (Task 4.9e). **Redaction scope (decision)**: only those two tools; persisted scrollback, Claude transcripts reachable via `search_claude_history`, `get_session` previews, notification snippets and `get_session_diff` are an accepted residual and are not redacted. **Lifetime**: the proof is a deterministic HMAC valid for the session's life (until a global `Rotate`); `mcp/<uuid>.json` and `mcp-proofs/<uuid>` are deleted on session deletion and the five tools require a live session (Task 4.9f). The repo already records the same limit for hook proofs (`server/services/hook_proof.go` header comment). The `:8543` listener remains unauthenticated and no UI or doc copy may claim otherwise (ADR-004).
   - A request without a valid proof is treated as **unidentified**: the five new tools return a typed `identity_unverified` error and perform no write. The error copy must not reuse the existing tools' `ErrPermissionDenied` text "Set STAPLER_SESSION_UUID in your environment"; it says the session has no verified credential and must be relaunched.
1. **Caller identity is derived server-side** from the *verified* identity (rule 0) via `verifiedCallerSessionUUID(ctx)`, never from a caller-supplied `session_id` and never from the unverified `callerSessionUUID(ctx)`. Every new tool (`schedule_wake`, `list_wakes`, `cancel_wake`, `request_help`, `answer_help`) is registered through a single `withCallerIdentityGate(roleAllowlist, handler)` wrapper. A registration test uses `MCPServer.GetTool` (the #894 technique) and fails if any new tool's handler is not wrapped. A second registration test sends each of the five tools a request with a forged `X-Stapler-Session-UUID` and no/invalid proof and asserts `identity_unverified` with zero writes (Story 4.5, Task 4.5d).
2. **Role allowlist**: work sessions may use all five tools; `triage`/`review`/`diagnose` hidden roles may call `request_help` and `list_wakes` only (they already have bespoke reporting tools) - exact list is a table in code with a test. Allowlist changes need an ADR amendment.
3. **Peer help authorization**: `request_help(peer)` requires the peer to be a live or stopped non-archived session in the caller's own workspace/item context (resolved by UUID; `Workspace().RepoRoot`/`WorkspaceKey()` for "same repo", not `ExistingDir`), rejects self-targeting and archived/one-shot/terminal-item peers. `answer_help` is accepted only from the named `answerer_session_uuid` for that request id; a session cannot answer a request addressed to the human or another peer.
4. **Prompt-injection hygiene**: any text delivered into a session (wake payload, help request, help answer) is delimiter-escaped (`lastNudgeText` angle-bracket precedent) and prefixed with provenance ("from session X", "from operator", "wake <id>"). An operator answer given on a stalled peer request ("Answer for {peer}") is delivered with provenance `from=operator on-behalf-of={peer}`, so the asker can tell it from a peer's own answer (triad round 1).
5. **Revival policy**: a wake never revives an archived session, a one-shot session, or a session whose backlog item is terminal. "One-shot" is `isOneShot` (`session/session_driver.go:1171`: tags `backlog:triage`, `backlog:review`), which is unexported; the wake guard reaches it through an exported predicate `session.IsOneShot(inst)` added in Task 4.3d (or an `OwnerLookup` port method) so the rule is not duplicated. For a stopped non-archived owner the revive is the sequence `(*Instance).RecoverFromStopped()` (`session/instance_state.go:533`; it only resets status to `Creating` and clears `started`, it starts nothing) **then `(*Instance).Start(false)`** (the existing warm-restart pairing at `session/instance_claude.go:143-145` and `session/retry_state.go:335`), performed **only inside one function, `reviveStoppedOwner`**, and only when `allow_revive=true` was set at creation **and** `BacklogService.Admit` (`server/services/backlog_service.go:562`, the WIP cap of 2) admits it. `reviveStoppedOwner` re-checks `IsArchived()` itself immediately before the call: the analyzer is lexical (the guard must appear earlier in an enclosing statement list), so a guard only in `guards.go` or a caller does not count and this rule does not lean on the "every in-package caller guarded" exemption. `RecoverFromStopped`'s doc comment reads "Deprecated: prefer transitionTo(ctx, Active)", but `transitionTo` is unexported (`instance_state.go:42`), so a `server/wakes` caller cannot use it; Task 4.3d runs `make lint` and, if staticcheck reports SA1019 for the cross-package call, adds a one-line `//nolint:staticcheck` with a reason (never `//nolint:noarchivedrevival`). **Admission spans the revive, under its own bounded lock**: `Admit` counts items (`in_progress`, plus `review` with an active work session; `countLiveBacklogWorkSessions`, `server/services/backlog_service_triage.go:1314`) and reserves nothing, so a **revive lock** (`reviveMu`, separate from the short cap lock of rule 6) is held from before `Admit` until the revived session is registered as an active work session, the revive failed, or the `revive_lock` budget expires (Wake limits table: default 30 s, hard ceiling 60 s; `RecoverFromStopped` plus `Start(false)` spawns tmux and a worktree, so an unbounded hold could freeze the dispatcher). On expiry the lock is released and the row stays `needs_revive`; the next cycle first re-reads the owner's state and, if the session did come up, treats it as live. Two wakes therefore cannot both pass at cap-1, and only revives ever take `reviveMu`: create-time and claim-time cap checks use the short cap lock and never wait on it. The rework cap is spawn-only and does not apply to revival; "SpawnGate" in earlier text means `Admit` and nothing else. Every other owner state resolves through the single **delivery decision table in ADR-006 rule 2** (for example `allow_revive=false` on a stopped owner is `skipped(owner_stopped)`, not `needs_revive`) and the operator is notified (document automated decisions visibly). **The archived, one-shot, terminal-item and revive guards are scoped to `action_kind=steer_text`**: a `notify_operator` wake writes nothing into the owner and is delivered regardless of owner state, which is what lets an operator "Remind me" about a finished (stopped or archived) review session.
   - **Enforcement is mechanical, not a spy test only**: `tools/lint/noarchivedrevival/analyzer.go` `lifecycleFiles` (lines 38-45, six hard-coded suffixes) gains `server/wakes/revive.go`, `reviveStoppedOwner` is the only function in `server/wakes` allowed to call `RecoverFromStopped`/`Start(false)`, and analyzer testdata under `tools/lint/noarchivedrevival/testdata/src/` gets a fixture proving an unguarded revive in that file is reported and a guarded one is not (Task 4.3f). `//nolint:noarchivedrevival` is not permitted in `server/wakes`: wakes are not an explicit operator action.
6. **Caps (check-then-reserve under the short process-wide cap lock; revives use the separate revive lock of rule 5)**: max pending triggers per session, max fires per trigger, minimum cron interval, per-owner and global fires per hour, `expires_at` horizon, max open peer requests per asker, max chain `generation`, busy-owner hold, revive-lock hold. The numeric defaults and hard ceilings are the 12-row "Wake limits" table in `implementation/plan.md` (single source); the dispatcher enforces each and counts every hit. A refusal is a visible state returned to the agent and notified, never a silent drop.
7. The existing `steer_session`/`write_to_session` tools are not changed by this project; peer delivery uses the attributed `SessionSteerer` path, not those tools.

## Consequences

- Dispatched roles cannot reach the new surface beyond the allowlist even if a client lies about `--allowedTools`, and cannot impersonate another session by UUID knowledge alone (rule 0; a same-user file reader is outside this).
- Peer help cannot be used to spoof the human or answer another pair's request **by an agent that does not read that session's credential files**. A same-user process or prompt-injected agent that can read the proof files or the secret, or make another session print them, is outside this guarantee (rule 0, accepted risk).
- Cost: one new header and a per-session proof file, one `ssq-mcp-v1` proof verification on every request to the five tools, an injected proof provider in `session`, and spawn-path changes in `session/instance_tmux.go` (`claudeMCPConfigArgsWithToken`) and `server/mcp/proxy.go`. Pre-upgrade sessions and the in-process stdio path degrade to `identity_unverified`.
- Wake deliveries to non-revivable targets degrade to visible `missed`, never to a silent write or a revive storm.

## Alternatives rejected

- **Client-side tool allowlists only**: proven insufficient (#894).
- **Allow wakes to auto-revive stopped sessions**: reproduces the respawn-loop and OOM classes.
- **Restate the trust model and drop the identity claims (no credential)**: considered and rejected because the HMAC primitive already exists and the cost is small; if Story 4.5's credential task is ever deferred, the fallback is to delete `FORBIDDEN`/anti-spoofing from the ACs and keep only identity-independent invariants (self-target, archived, one-shot, caps), and this ADR must be amended first.
- **Reuse `steer_session` for peer messages**: unattributed, no refusal for hidden sessions, no rate limit.
