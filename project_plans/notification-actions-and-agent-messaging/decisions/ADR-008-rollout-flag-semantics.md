# ADR-008: Four live-settable rollout flags with explicit global + per-scope precedence

**Status**: Proposed (2026-10-17); amended 2026-10-17 (reuse existing scope resolver; no new `ResolveScopedFlag`); triad round 1 (2026-10-18): the "off" column now means "the decision point resolves false", and a dependency matrix replaces the contradiction between "explicit scoped value wins" and "off disables new writes"; triad round 2: this ADR becomes Accepted when the owner-defaults list in plan `Unresolved Questions` is confirmed at the Phase 5 start gate (one explicit accept step for all eight ADRs; until then the stated defaults proceed)
**Project**: notification-actions-and-agent-messaging

## Context

Rollout flags must be live-settable via the feature-flag RPC/panel, global plus per-scope, never env vars (memory `feedback_rollout_flags_live_settable_no_env_vars`). Existing precedents: `replyFlagController` / `featureFlagSvc.SetFeatureController` (`server/services/hidden_question_reply.go:85-116`) and the delivery gate's `FlagCache` with `kind:*` scopes (`server/deliverygate/flagcache.go`). `server/features/flags.go` (28 lines) and `server/features/client_event.go` (17 lines) are `featureregistry.Register` metadata only, not flag controllers or a client-event sink. Flag plumbing is `server/services/feature_flag_service.go` (known-flag table with `scopes`, `FlagAuditPolicy`, `flagScopeReadback`) and `config/config.go:1913-1945`, where `Config.GetFeatureFlagScopedOverride` and `Config.GetFeatureFlagScoped(name, scope, default)` already implement the precedence below (tested in `config/feature_flag_scopes_test.go`; no production caller yet). The proto `FeatureFlag` already carries `repeated FeatureFlagScopeOverride scopes` and the RPCs are `GetFeatureFlags`/`UpdateFeatureFlag` (`session.proto:505,508`). Explicit-false persisted flags survive default flips (delivery-gate ADR-004). Requirements fix the flag names.

## Decision

| Flag | Default | Scope vocabulary | When a decision point resolves false |
|---|---|---|---|
| `background_activity_feed` | ON | none (global only) | Old history-only selector; no data change |
| `notification_inline_actions` | OFF until e2e + soak, then ON | `channel:remote`, `channel:remote:tierB`, `action:<ActionKind>` | `InvokeNotificationAction` returns `FLAG_OFF` for that action; descriptors reduce to `OPEN`; legacy Approve/Deny UI path stays reachable |
| `askuserquestion_structured` | OFF | `stage:render`, `stage:answer`, `stage:hook_reply` | That stage's *new writes* are refused (`FLAG_OFF`); durable rows already created remain readable |
| `agent_wake_triggers` | OFF | `trigger:<type>`, `tool:<name>` | MCP tools for that scope return a typed `flag_off` error; creating triggers of that type is refused; rows are kept, and `pending` rows of a type whose scope is false are neither fired nor marked `missed` while it is false, with one carve-out: **`expires_at` always wins**, so a row past `expires_at` becomes `missed` (reconcile) even while its scope is false and scope-held rows cannot outlive their horizon |

Precedence rule (**already implemented once and tested once** as `Config.GetFeatureFlagScoped`, `config/config.go:1925`; this project adds production callers and new-flag tests, not a second resolver): **the scope's explicit value wins in either direction, then the explicit global value, then the default**. A scoped `false` under a global `true` is a kill switch for that decision point; a scoped `true` under a global `false` enables exactly that decision point (this is how a single stage or trigger type is released first). "Off" in the table above never means "global false": it means the decision point resolves false. The earlier text said both "explicit scoped value wins" and "off disables new writes" for the same flag; those no longer conflict because the second sentence is now scoped to the decision point.

**Dependency matrix (applied by the caller after the resolver, in this order).** Source of truth: the "Flag precedence and dependency matrix" in `implementation/plan.md`; cells are tested by `TestFlagMatrix_ShouldResolveEveryCell_*` (Task 0.8d). `askuserquestion_structured`: `stage:answer` is effective only when `stage:render` is effective, and `stage:hook_reply` only when `stage:answer` is effective and Spike S1 passed (an answer enabled without its render stage is ignored so no invisible card has live buttons). `notification_inline_actions`: `channel:remote:tierB` is effective only when `channel:remote` is and Spike S6 passed. **`ANSWER_QUESTION` composes three flags** (the one cross-flag cell): `Scoped(action:ANSWER_QUESTION)` AND a route gate that depends on where the write goes. A hidden-session `live_keystroke` write is gated by the existing `hidden_session_reply` (untouched); a visible-session `live_keystroke` write is gated by `askuserquestion_structured` `stage:answer`, which already includes `stage:render`; a durable-record write (`resume`, a stored answer for a stopped session or an `agent_mcp` row, Tier A) is also gated by `stage:answer`; a `hook_reply` write by `stage:hook_reply`. The rows and permutations are in the plan's flag matrix and are enumerated by Task 0.8d. `agent_wake_triggers`: the dispatcher runs when the unscoped value is true or any `trigger:<type>` is explicitly true; `trigger:<type>` and `tool:<name>` are effective only while the dispatcher runs; `schedule_wake` needs both its tool and its type. **The server re-evaluates every write**; the client's flag cache only chooses between the legacy and the new row and can never allow a write, and `FLAG_OFF` has operator copy ("This action is turned off. Open session." with Open). Flags are read at decision time, not cached at pass start. Each flag is registered in `server/services/feature_flag_service.go` with a `*FlagController` and `FlagAuditPolicy` following `replyFlagController` (`server/services/hidden_question_reply.go:85`), publishes `status_detail`, and so a live flip takes effect without restart. Loosening flips are audit-fsynced and refused while the audit sink is down; this applies to the default-ON `background_activity_feed` (a flip to ON after an explicit OFF is a loosening) and is stated in the flag's `status_detail`.

Re-enable semantics for `agent_wake_triggers`: triggers that became overdue while off are handled by the startup reconcile policy (ADR-006 rule 4): fire-once if within `expires_at`, else `missed` with notification. No bulk catch-up.

## Consequences

- Zero new resolvers: four flags use the existing precedence function, with a new table test over (global x scope x dependency) combinations for the new flag names and scope vocabularies.
- Stage 1 of any staged flag ships with global `false` and the stage's scope explicitly `true`; flipping the global to `true` later is the "everything on" step, and an explicit scoped `false` is how a stage is held back after that.
- Staged rollout in the order in the requirements is a sequence of flag flips with no deploy.
- Reply's existing `hidden_session_reply` flag is untouched and stays the hidden-session kill switch; `askuserquestion_structured` `stage:answer` only extends reach to visible sessions.

## Alternatives rejected

- **Env var flags**: forbidden by requirements.
- **A single master flag**: cannot stage render -> answer -> hook reply.
- **Per-scope default-wins-over-explicit**: breaks the operator kill switch.
