# UX Research: Bun Build 7a Baseline Regressions

## R1 — Route Announcer (WCAG/ARIA)

WCAG 2.1 SC 4.1.3 ("Status Messages") and ARIA authoring practices specify that navigation announcements belong in a `role="status"` / `aria-live="polite"` region, not `assertive`. The difference matters in practice: `polite` waits for the screen reader to finish speaking the current utterance before queuing the new page title — the user hears what they already triggered, then the confirmation. `assertive` (`role="alert"`) interrupts immediately, which is correct for errors or time-sensitive warnings but wrong for navigation, where the announcement is confirmatory rather than urgent. The existing `RouteAnnouncer.tsx` already uses the correct combination (`role="status"` + `aria-live="polite"` + `aria-atomic="true"`), mirroring the approach recommended by the A11y Project and opposed to Next.js's own announcer, which uses `assertive` (noted in the component's comment as deliberate divergence from Next). The fix for R1 is therefore to ensure this component is mounted in the Bun build — the ARIA semantics are already correct.

The clear/set-in-separate-task pattern (clear message, increment generation, then re-set after `ANNOUNCE_DELAY_MS`) is the standard workaround so screen readers re-announce an identical title — without it, navigating back to the same route produces silence because the DOM text didn't change.

## R2 — Missing Font Variable Classes

Next.js and the existing Bun build inject a `className` like `__variable_geist_sans` on `<html>` or `<body>` that defines a CSS custom property (`--font-geist-sans: 'Geist', sans-serif`). Component styles reference that custom property (`font-family: var(--font-geist-sans)`). Without the class, the property resolves to `unset`, and the browser falls through to the system default (typically Arial on Windows, Helvetica/SF Pro on macOS, the distro default on Linux). The visual impact is a full typeface substitution: character metrics change (width, x-height, tracking), which can cause reflowed layouts, misaligned buttons, and truncated text labels — a pervasive regression on every page, not just a subtle color shift. The fix must ensure the Bun HTML entry-point injects the same variable class attributes that the Next build did; the font assets themselves loading is not sufficient if the CSS custom property bridge is missing.

## R3 — Not-Found Page UX

Inline not-found pages (the current approach in `NotFound.tsx`) are preferable to silent redirects to `/` for two reasons: the user sees the URL they attempted, which helps them understand what went wrong and self-correct (a mistyped deep link, a stale bookmark), and the browser history entry is preserved so the Back button works predictably. A redirect to `/` destroys both — the user lands on sessions with no feedback that the URL they tried doesn't exist, and hitting Back loops them back to sessions again. The current component already follows best practice: it shows the attempted path in a `<code>` block, offers a primary "Go to Sessions" `<Link>` as the safe exit, and shows "Go back" conditionally only when `history.length > 1` (avoiding a Back button that would leave the app on a fresh tab). The only fix needed for R3 is ensuring `not-found.tsx` is present in the Bun build's routing layer so this component actually renders for unknown URLs instead of the build's fallback behavior.

## R4 & R5 — Scroll Behavior (Tab Switch vs Back Button)

For tab switching (R4), users expect the scroll position of each tab to be independently preserved — the mental model matches native mobile apps, browser tab groups, and most SPA tab implementations where each pane remembers where you left off. Resetting to the top on every tab switch breaks this: a user who scrolled halfway down a long session list in "Up Next" loses their place every time they check another tab, creating repetitive re-scrolling. The correct behavior is to save the scroll offset of the departing tab before unmounting (or hiding) it and restore it when it becomes active again.

For the Back button (R5), the browser's own scroll-restoration contract (`history.scrollRestoration`) should handle this, but SPAs that push history entries programmatically (rather than letting the browser navigate) must either leave `scrollRestoration` as `"auto"` and let the browser do it, or opt into `"manual"` and implement the save/restore themselves. A Bun build that breaks `popstate`-triggered scroll restoration has likely either set `scrollRestoration = "manual"` without implementing the restore side, or replaces the scroll container's DOM node on navigation (which destroys the browser's saved scroll state). The fix must verify that on `popstate` the scroll container scrolls to the position recorded at push time — WCAG SC 3.2.3 ("Consistent Navigation") is the relevant criterion, since unpredictable scroll position after Back is a navigability failure for keyboard-only and low-vision users who rely on spatial orientation.
