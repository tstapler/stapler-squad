# Pre-mortem: worktree-selfheal-test-flake
**Date**: 2026-08-22

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The bounded retry (`worktreeAddRetryAttempts=3`, `worktreeAddRetryDelay=20ms` — 60ms total) is copied verbatim from `getHeadCommitSHA`'s in-process torn-read mitigation (`util.go:283-329`), which waits out a microsecond-scale local file write, not a concurrent `git worktree add` subprocess that — per this plan's own root-cause finding — can run up to `runGitCommand`'s 30s timeout under the exact CI load that produced the original flake. Under real contention the "winner" goroutine's `worktree add -b`/`worktree add` may still be mid-flight well past 60ms, so `branchRefExists`/`findWorktreeForBranch` observes "not yet created" and Ground-Truth Re-Query falls through to the same hard error as today — the fix defeats itself under precisely the load condition it was built to survive. | The same or a near-identical flake reappears in CI weeks after the fix ships, now harder to triage: the failure no longer contains a recognizable error-text clue (the whole point of the fix was to stop depending on `err.Error()`), so the next investigator has to re-derive that it's a timing/sizing bug from scratch. | Do not reuse `headSHARetryAttempts`/`headSHARetryDelay` by analogy alone — size the new retry budget against the actual contended-completion time observed in Story 2.1.1's stress repro (or against a fraction of `runGitCommand`'s 30s ceiling with backoff), and state the sizing rationale in the doc comment instead of just citing the unrelated precedent. Patched into `plan.md` (see below). | P1 |
| 2 | Story 2.1.1/2.1.2's stress repro runs `stress -p $(nproc)` against only the isolated `worktree_ops.test` binary, but the requirements doc's own root-cause framing says the flake fired under "full-suite CI load" (PR #583, an unrelated PR) — i.e. the real trigger is contention from dozens of *other* concurrently-running `session/git` tests (84 `t.Parallel()` sites per pitfalls.md §1) plus the two intentionally-racing goroutines, not amplification of the isolated test alone. An isolated-binary stress run that comes back clean (exit 124) is treated by the plan as valid AC-1 closure either way ("documented either way"), so a repro methodology that structurally can't reach the real trigger condition produces false confidence rather than a null result. | Story 2.1.1 reports "did not reproduce within 90s budget" both pre-fix and (trivially) post-fix, and AC-1 is marked closed on that basis even though the isolated repro never approximated the load shape that actually caused PR #583's failure. | Run the stress command against the full `session/git` package (`go test -race ./session/git -count=N` or `stress` invoked over the whole package binary, not `-test.run=<single test>`) so other package tests contribute real concurrent subprocess load, matching the documented trigger condition. Treat a clean isolated-binary run as inconclusive, not as AC-1 closure. | P2 |
| 3 | Story 1.1.2 makes `setupFromExistingBranch`'s `worktree list --porcelain` + `findWorktreeForBranch` re-query fire unconditionally on *any* `worktree add` failure (not gated by error text anymore), and — per the existing code at `worktree_ops.go:141-157` — adopts whatever path `findWorktreeForBranch` returns with no `os.Stat` liveness check (unlike the sibling `worktreeAlreadyRegisteredForBranch`, which does check). A genuine non-transient failure (disk full, permission denied) that happens to coincide with a stale/prunable `worktree list --porcelain` entry for the same branch name (e.g. left by a previous crashed run git hasn't pruned yet) would be silently "healed" into adopting a broken, nonexistent path instead of surfacing the real disk-full/permission error to the caller. | A session is created against a worktree path that doesn't actually exist on disk, discovered only when a later operation (build, git command) against that path fails with "no such file or directory" — several layers removed from the real root cause (the original disk-full/permission error was swallowed). | Add the same `os.Stat` liveness check `worktreeAlreadyRegisteredForBranch` already uses before adopting a re-queried path in `setupFromExistingBranch`'s failure-recovery branch, so a stale/prunable porcelain entry can't be silently adopted as a live worktree. | P2 |
| 4 | Only `setupNewWorktree`'s re-query (Task 1.1.1a) gets a bounded retry loop; `setupFromExistingBranch`'s re-query (Task 1.1.2a) is specified as a single unconditional check with no retry, per Story 1.1.2's Given/When/Then ("re-check ... *Then* ... adopts that path" — no retry language). This is an asymmetry between the two self-heal layers described as mirroring the same idiom: if the race winner hasn't finished registering its worktree at the instant the loser's own `worktree add` (no `-b`) call fails, the second layer has zero chance to catch up before hard-failing, even though the first layer would tolerate exactly that delay. | The `TestSetupNewWorktree_SelfHeals_...` flake stops recurring (layer 1 fixed) but a structurally identical flake appears at layer 2 instead, tracing to `setupFromExistingBranch` instead of `setupNewWorktree`. | Give `setupFromExistingBranch`'s re-query the same bounded-retry treatment as `setupNewWorktree`'s (reuse `worktreeAddRetryAttempts`/`worktreeAddRetryDelay`), not a single check, so both self-heal layers tolerate the same in-flight-winner window. Patched into `plan.md` (see below). | P1 |
| 5 | Both new regression tests (Stories 2.2.1/2.2.2) script the spy's `runFunc` hook to create the branch/worktree synchronously *before* returning the error, meaning Ground-Truth Re-Query's very first check always succeeds — the retry loop's looping/backoff behavior itself (the actual mechanism meant to close the race under load, and the specific thing Failure #1 above says is undersized) is never exercised. A logic bug in the retry loop (off-by-one on attempt count, sleep in the wrong place, early `return` skipping remaining attempts) would still pass both tests. | CI stays green through the change (both new tests pass), but the original class of flake still recurs later under real load, and the regression suite gives no signal pointing at the retry loop as the cause. | Add at least one regression test where the spy's `runFunc` delays the branch/worktree creation until the *second* (or later) `branchRefExists`/`findWorktreeForBranch` check — e.g. by counting invocations and only creating the branch on the Nth — so the test fails if the retry loop doesn't actually retry the configured number of times. | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — retry budget (60ms) sized by analogy to an unrelated in-process precedent instead of the actual contended `git worktree add` completion time under CI load. Patched Task 1.1.1a in `plan.md` to require sizing justification against Story 2.1.1's stress-repro evidence rather than reusing `headSHARetryAttempts`/`headSHARetryDelay` unexamined.
- [x] Failure #4 — `setupFromExistingBranch`'s re-query (Task 1.1.2a) had no retry loop at all, unlike `setupNewWorktree`'s. Patched Task 1.1.2a in `plan.md` to add the same bounded-retry loop, closing the asymmetry.
