# Requirements: Smart Notification Deduplication & Native Notification Lifecycle

## Problem Statement

Two related notification UX problems:

### Problem 1: Fork Pressure Critical Notification Spamming
The system continues to fire "Fork Pressure: Critical" alerts (both banner toast and system notification) even when:
- The number of zombie processes has not increased since the last alert was shown
- The user has already acknowledged they are in a critical state

Root cause hypothesis: The backend `forkAlertCooldown` (2 min) resets after each window, so the alert re-fires every ~2 minutes for the lifetime of the elevated zombie count — even if no new zombies appeared. The backend does not track "has the severity *worsened* since the last notification the user saw?"

### Problem 2: Native Browser / Mobile Notifications Never Dismiss
Chrome desktop notifications, macOS Notification Center entries, and mobile browser notifications generated by the app persist indefinitely. They never auto-close and accumulate in the OS notification tray.

---

## Scope

Both fixes should apply to **all health/system notifications** (fork pressure, tmux server recovery, memory pressure, etc.), not just fork pressure specifically.

---

## Functional Requirements

### FR-1: Condition-Change Gating for Health Notifications
The system MUST NOT re-emit a notification for a health condition unless the condition has worsened since the last emission.

- "Worsened" for fork pressure = zombie count is higher than the count at last notification, OR pressure level escalated (warning → critical)
- "Worsened" for tmux recovery = a new recovery event (not a repeat of the same one within a window)
- If the condition is unchanged, suppress the re-emission regardless of cooldown timer expiry

### FR-2: Count Baseline After Notification
When a fork pressure alert fires, the backend MUST record the zombie count (and spawn failure count) at the time of emission. The next alert only fires if the current count exceeds that recorded baseline, or if pressure level increases.

### FR-3: Native Notification Auto-Dismiss
All browser native `Notification` objects created by the app MUST have a finite lifetime:
- High/urgent priority: auto-close after 30 seconds
- Medium/low priority: auto-close after 15 seconds
- Actionable notifications (approval_needed, input_required): auto-close after 5 minutes
- Explicit call to `notification.close()` must happen (not just relying on OS behavior)

### FR-4: Native Notification Deduplication
When a new native notification fires for the same `(sessionId, notificationType)` pair, any previously open native notification for that pair MUST be closed before the new one is shown.

### FR-5: Notification Re-arm on Clear
Once a health condition clears (e.g., zombie count drops to zero), the baseline resets so that a future re-occurrence triggers a fresh notification.

### FR-6: Consistent Behavior Across Surfaces
Both the in-app toast AND the native OS notification must follow the same dedup/lifecycle rules. They must not diverge (e.g., toast suppressed but native fires anyway).

---

## Non-Functional Requirements

### NFR-1: No Regressions on Actionable Notifications
`APPROVAL_NEEDED` and `INPUT_REQUIRED` notifications MUST never be suppressed by dedup logic — each one represents a distinct blocking request from Claude.

### NFR-2: No New Persistence Layer
Use in-memory state for the condition baseline tracking (Go side). No new database tables or JSON files required.

### NFR-3: Backward Compatible
Existing notification history, store format, and frontend components remain unchanged.

---

## Out of Scope
- Snooze/remind-later feature (nice to have, not blocking)
- Per-user notification preferences UI
- Push notifications via Service Workers

---

## Acceptance Criteria

1. With zombie count stable at N for >10 minutes, exactly one "Fork Pressure: Critical" toast and one native notification fires — no repeats.
2. If zombie count increases from N to N+5, a new notification fires within the next monitoring window.
3. After zombie count drops to 0, a subsequent re-occurrence triggers a fresh notification.
4. All native notifications visible in Chrome/macOS/mobile close automatically within their respective time limits.
5. A second notification for the same (sessionId, type) closes the first native notification before opening the new one.
6. Approval notifications are never affected by dedup logic.
