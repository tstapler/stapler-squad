# Pre-mortem: tmux-ptmx-race-fix
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `make ptmx-field-guard`'s awk command is hardcoded to scan only `session/tmux/tmux.go`, but Task 1.1.1c's own rationale says the risk is direct field access "anywhere in package tmux (which spans multiple files, e.g. `shell_handle.go`, `fork_metrics.go`)" — the guard cannot catch a violation in any file but the one it greps. | Months later, `-race` failures on `t.ptmx`/`t.attachCmd`/`t.attachCmdWaitOnce` reappear in CI or production (identical signature to the original bug report) after a PR that added a direct field read/write in `shell_handle.go` or `fork_metrics.go` — `make ci` stayed green the whole time because `ptmx-field-guard` never looked at those files. | Change the awk target's `grep`/`awk` input from the single hardcoded path to `session/tmux/*.go` (excluding `_test.go` as appropriate), and add a guard-verification step (mirroring the plan's own "verify the guard actually catches a violation" step in Task 1.1.1c) that plants a violation in a *second* file, not just in `tmux.go`, to prove the expanded glob actually works before merging. | P1 |
| 2 | `go.mod` declares `go 1.26.3`, but `.github/workflows/build.yml` pins `go-version: '1.25.0'` via `actions/setup-go@v5` in 5 separate jobs (verified: `grep -n "go-version: '1.25.0'" .github/workflows/build.yml` → 5 matches), and no `toolchain` directive or `GOTOOLCHAIN` override exists anywhere in the repo. This directly contradicts Task 1.2.2a's own claim that "`testing/synctest` is stable in this repo's Go 1.26.3 (`go.mod`)" — CI does not actually have 1.26.3 pre-installed; it relies on Go's implicit `GOTOOLCHAIN=auto` behavior silently downloading 1.26.3 at build time on every job. | CI build times increase or a job intermittently fails with a toolchain-download error (network hiccup, proxy.golang.org rate limit, or a firewalled/ephemeral runner with restricted egress) — a flake that has nothing to do with the PTY fix itself but blocks merging it, and is confusing to debug because `go build` locally "just works" (developer's local Go is already ≥1.26.3). | Before merging, either (a) bump `go-version` in all 5 `build.yml` jobs to `1.26.3` to match `go.mod` exactly, or (b) add an explicit `toolchain go1.26.3` line to `go.mod` so the auto-download behavior is pinned and reproducible rather than implicit. Confirm with a clean-cache CI run (or `GOFLAGS=-mod=mod GOTOOLCHAIN=local go build ./...` locally against a 1.25.0 toolchain) that the mismatch doesn't break the build outright. | P2 |
| 3 | No `deadlock.Opts` configuration exists anywhere in the repo (verified: `grep -rn "deadlock.Opts\|DeadlockTimeout\|OnPotentialDeadlock"` → zero matches) — `ptmxMu`, like the file's 3 existing `deadlock.Mutex` fields, runs entirely on the `go-deadlock` package's upstream defaults. The plan never audits what those defaults actually do (default timeout value, default action — log-only vs. process-terminating) before adding a *sixth* lock to a file that already has 5, on a field now touched from more call sites (every attach, resize, keystroke, and reattach). | Under real production load — many concurrent sessions, GC pauses, or a CPU-starved host — a goroutine legitimately waiting slightly longer than usual for `ptmxMu` (not truly deadlocked) trips the default `DeadlockTimeout`, producing a "POTENTIAL DEADLOCK" stack dump flood in the logs or, depending on the default `OnPotentialDeadlock` action, an unexpected process abort — a new production failure mode that didn't exist before this fix, triggered by load rather than a bug. | Before implementation, read `go-deadlock`'s actual default `Opts` values (timeout duration and `OnPotentialDeadlock` behavior) and explicitly configure them at package init (matching whatever the other 3 existing `deadlock.Mutex` fields in this file already rely on — if they're also unconfigured, this is pre-existing debt worth surfacing, not just accepting silently for a 4th/5th/6th lock). Add a load test with realistic concurrent session counts, not just `-race` unit tests, before calling this production-ready. | P2 |
| 4 | Tasks 1.2.2a/1.2.2b's determinism argument rests on `synctest.Wait()` correctly recognizing a goroutine blocked on `t.ptmxMu.Lock()` as "durably blocked" — but `ptmxMu` is a `deadlock.Mutex` (a third-party wrapper around `sync.Mutex` with its own bookkeeping, and in some configurations a background watchdog goroutine), not a bare `sync.Mutex`. Nobody in this plan actually ran a spike combining `deadlock.Mutex` + `testing/synctest` + real blocking syscalls (`os.Pipe`, `cmd.Process.Kill()/Wait()` in 1.2.2b) before writing ~80 lines of test code assuming the combination "just works." `synctest` has documented restrictions around goroutines that touch bubble state from outside the bubble. | Task 1.2.2a or 1.2.2b hangs (test times out, or the whole `-race` run wedges) or panics with a `testing/synctest`-specific runtime error the first time it's actually executed during implementation — discovered late, after the "deterministic proof" narrative in the plan has already been treated as settled. | Spike a minimal throwaway test combining `deadlock.Mutex.Lock()` inside a `synctest.Test` bubble with `synctest.Wait()` *first*, before writing the full 1.2.2a/1.2.2b bodies, to confirm the primitive is actually synctest-compatible in this repo's toolchain. If it isn't, fall back to a plain `sync.Mutex`-guarded test double, or a channel-based rendezvous (`ready := make(chan struct{}); ...`), instead of relying on `synctest.Wait()`. | P2 |
| 5 | The plan's Pattern Decisions table justifies releasing `ptmxMu` before I/O by claiming "`os.File`'s own `internal/poll` fdMutex already makes concurrent `Write`/`Close` on a captured local `*os.File` memory-safe" — but `updateWindowSize` (Task 1.2.1c) calls `file.Fd()` to get the raw descriptor number, and `pty.Setsize` internally issues a raw `ioctl()` against that captured fd number. `.Fd()` takes the file out of `internal/poll`'s protected/reference-counted mode; the ioctl no longer benefits from the safety net the plan's own reasoning leans on. | Intermittent, near-impossible-to-reproduce corruption of an *unrelated* file/socket's state (wrong window-size ioctl landing on a freshly-opened PTY from a concurrent `AttachToExisting`/`RestoreWithWorkDir`, or sporadic `EBADF`/`EINVAL` ioctl errors in logs) correlated with rapid resize-during-reattach — very hard to trace back to this code since nothing about it resembles the original `-race` symptom. | Document this as a second, narrower residual risk in `plan.md` alongside the existing write-write TOCTOU one (it is pre-existing, not introduced by this fix, but the plan's safety claim doesn't actually cover this call site). Consider holding `ptmxMu` across the `Fd()`-capture-through-ioctl window specifically in `updateWindowSize` — that window is a fast, non-blocking ioctl, not a `Close()`/`Kill()`/`Wait()` call, so the plan's own "don't hold the lock across blocking I/O" rationale doesn't actually forbid it here. | P3 |
