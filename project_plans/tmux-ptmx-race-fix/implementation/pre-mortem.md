# Pre-mortem: tmux-ptmx-race-fix
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The plan converts `AttachToExisting`'s nil-check (Task 1.1.2a: `if t.lockedPTMX() == nil { ...; t.setPTYTriple(...) }`) and `RestoreWithWorkDir`'s pre-check (Task 1.1.2b: `if t.lockedPTMX() != nil { closePTYAndAttachCmd() }` then `if t.lockedPTMX() == nil { ... }`, tmux.go:1240-1243) into two-step check-then-act sequences where each `lockedPTMX()` call is its own independent lock/unlock cycle. This is exactly the double-checked-locking anti-pattern this repo already has a rule against (`.claude/rules/go-double-checked-locking.md`): a concurrent `Close()` (which, unlike `Detach()`/`DetachSafely()`, never takes `detachMutex` — confirmed at tmux.go:1724-1728), a second `AttachToExisting()`, or another `RestoreWithWorkDir()` can install/clear the triple in the gap between the two checks. Concretely: two concurrent `AttachToExisting()` calls can both observe nil, both spawn a `ptyFactory.Start()` (two attach-session processes + PTYs), and the second `setPTYTriple()` silently overwrites the first — leaking a PTY fd and an unkillable orphaned tmux attach process (never tracked, so `closePTYAndAttachCmd` can never reap it). `RestoreWithWorkDir` can similarly skip installing its own PTY because a *different* generation appeared in the gap, silently returning success while attached to the wrong generation/workDir. | Orphaned `tmux attach-session` processes and leaked PTY fds accumulating under concurrent attach/restore load (visible via `lsof`/process count creep), or a session silently restored against a stale working directory — neither is caught by `go test -race` because every individual field access *is* correctly synchronized; this is a logic race (TOCTOU), not a data race, so AC2/AC3's race-detector-based verification gives false confidence. | Collapse each two-step check-then-act into one compound helper (e.g. `ensurePTYTriple` that locks once, checks, and — if needed — releases only around the blocking `ptyFactory.Start()`/`closePTYAndAttachCmd()` calls, then re-checks-and-installs still inside the same logical critical section using a version/generation counter to detect a concurrent winner) rather than two independent `lockedPTMX()` calls. Add a validation.md test that races `AttachToExisting()` against itself and `RestoreWithWorkDir()` against `Close()`, asserting exactly one PTY/process survives — not just that `go test -race` is silent. | P1 |
| 2 | The `ptmx-field-guard` grep (Task 1.3.1b: `grep -rEn '\bt\.(ptmx|attachCmd|attachCmdWaitOnce)\b' session/tmux/*.go`) matches on the literal receiver-variable name `t` and bare field names, not on the `TmuxSession` type — it is not type-aware. `session/tmux/shell_handle.go`'s unrelated `ShellTmuxHandle` struct already has its own `ptmx *os.File` / `attachCmd *exec.Cmd` fields (lines 40-43) guarded by its own `spawnMu sync.Mutex`, and is safe today only because its receiver happens to be named `h`, not `t`. In the other direction, the plan's own Task 1.2.2a test writes `session.ptmx = r` directly (receiver named `session`) as "pre-test setup" — the guard's pattern cannot see this at all, so any future violation copy-pasted from that exact test idiom (or written with any receiver other than literal `t`) ships silently, undermining AC1's "never read or written outside... anywhere in package tmux." | Either (a) a real future violation using a non-`t` receiver lands and reintroduces a live race that only a lucky `-race` interleave catches, or (b) `make ptmx-field-guard` starts failing on an unrelated PR the day someone renames `ShellTmuxHandle`'s receiver to `t` for style consistency, with an error message pointing at a mutex that struct doesn't even use. | Scope the grep to `session/tmux/tmux.go` only (the PTY-triple invariant doesn't apply to `shell_handle.go` at all) instead of the whole-package glob, and add a self-test that plants a violation using a non-`t` receiver name to prove the guard actually catches the class of bug it claims to. Consider an `ast-grep`/gritql rule scoped to methods on `*TmuxSession` specifically (per this repo's own tool-priority guidance for structural code search) as a more durable alternative to text grep. | P2 |
| 3 | `TestSessionService_CreateThenImmediateDelete_NoDataRace` (Task 1.3.2a) has no explicit synchronization barrier — it calls `CreateSession` then immediately `DeleteSession` and relies entirely on scheduler timing for the async controller-start goroutine to still be inside `GetPTY()` when the delete cleanup goroutine runs `closePTYAndAttachCmd()`. This is structurally the same "incidental timing window" flaw the plan itself criticizes in `TestServer_should_WriteUnchangedHookURL_When_StartedOnExplicitPort` (the test this one is meant to make reliable), just moved one level down — "very likely still in flight" is a probability statement, not a guarantee, unlike Task 1.2.2a's unit test which forces the interleave by holding `ptmxMu` before spawning either goroutine. | The test passes green on every CI run (fast runners, warm caches, low load consistently let the goroutine finish quickly or consistently not finish in time) while providing zero actual regression coverage in either direction — a future change that reintroduces the race is not caught by this test; discovered only when the race resurfaces in production, or the test starts flaking under `-race`'s ~5-10x slowdown once CI hardware or load characteristics shift. | Add an explicit rendezvous the same way Task 1.2.2a does: a test-only hook/channel that blocks the controller-start goroutine at (or just after) its `GetPTY()` call until the test has confirmed `DeleteSession`'s cleanup goroutine has entered `closePTYAndAttachCmd()`, guaranteeing the interleave on every run. Document in validation.md that the test's value depends on that barrier actually firing — assert the barrier was reached, not just that both RPCs returned without error, so a scheduling change can't silently turn this into a no-op test. | P1 |
| 4 | `ptmxMu`'s leaf-lock doc comment (Task 1.1.1a) and requirements.md AC4 only reason about ordering among the 5 locks declared inside `session/tmux/tmux.go` (`detachMutex`, `controlModeSubMu`, `controlModeStartMu`, `cmdSendMu`, `recoveryMu`). But per requirements.md's own race description, `GetPTY()` is reached externally via `TmuxProcessManager.GetPTY()` → `TmuxBackend.GetPTY()` → `Instance.GetPTYReader()` — none of `Instance`'s or the backend layer's own locking is examined for a reverse ordering against `ptmxMu`. The plan's deadlock-freedom argument is local to one file, but the actual call graph (confirmed by the bug report itself) crosses package boundaries. | `deadlock.Mutex`'s detector fires a "POTENTIAL DEADLOCK" panic/log in production or CI under a cross-package interleaving that `go test -race ./session/tmux/...` (AC4's verification command, scoped to the `tmux` package alone) structurally cannot exercise, since it never invokes the `Instance`/backend layers that actually call into `GetPTY`. | Before implementation, read `Instance.GetPTYReader` and any other `Instance`/backend method that calls into the new locked accessors (`GetPTY`, `TapEnter`, `SendKeys`, `SetWindowSize`, etc.) and confirm none holds an `Instance`-level mutex while calling in; if any do, extend the lock-order doc comment and requirements.md AC4 to cover that ordering explicitly instead of implicitly assuming the tmux.go-local analysis is complete. Add this as its own validation.md checklist item, separate from the existing 5-lock table. | P2 |
| 5 | Task 1.2.1d's one-time `ptmxForCopy := t.lockedPTMX()` snapshot pins `Attach()`'s `io.Copy` goroutine to whichever PTY generation was live at `Attach()`-call time — this is unchanged from the pre-fix code (argument evaluation was already a one-time read), so it is a pre-existing property, not a new bug. But `clearPTYTriple()`/`setPTYTriple()` only ever act on the *current* `t.ptmx`, never on a specific stale generation — if a `Restore()` or second `AttachToExisting()` installs a new generation while that goroutine is still blocked reading the old one (now more reachable since `Close()`, which never takes `detachMutex`, races cleanly against a live `Attach()` instead of hitting an unguarded/undefined-behavior data race that might have crashed or masked the interleave before), the old fd is never closed by anything, and the goroutine leaks forever. | An intermittent, hard-to-reproduce hang on `Detach()`/`DetachSafely()` under concurrent attach/restore load: `t.wg.Wait()` (tmux.go:1592-1595 and 1660-1663), held under `detachMutex`, blocks forever waiting for a goroutine that will never see EOF — visible as a goroutine-count leak in `/debug/pprof/goroutine` and a `detachMutex` holder that never releases, likely surfacing weeks after ship since it needs the specific Restore-during-live-Attach interleave. | Since this is genuinely pre-existing and out of non-goals scope ("No behavior change to PTY lifecycle semantics"), plan.md/validation.md should say so explicitly rather than leaving it implicit — state that goroutine-1 generation-pinning is a known, unfixed latent issue, and add (even if deferred to a follow-up item) a regression test that races `Attach()` against a concurrent `Restore()`/second `AttachToExisting()` and asserts goroutine count returns to baseline after `Detach()`, closing the gap between "no new data race" (proven by AC2/AC3) and "no new hang" (currently unproven either way). | P2 |

## P1 Items (address before implementation)
- [x] #1 — **Resolved by explicit descope + follow-up, not by implementing the generation-counter fix in this PR.** Confirmed real via code inspection (`session/instance_tmux.go:87-94`'s `pmMu` only guards lazy-init of the process-manager reference, not calls through it; `TmuxSession.Close()` never takes `detachMutex`), so this is a genuine, not merely theoretical, TOCTOU. But it is a *logic* race requiring a behavioral change (generation-counter CAS + discarding a "loser" goroutine's freshly-started PTY) to fix correctly — out of scope for a PR whose own requirements.md non-goals state "no behavior change to PTY lifecycle semantics" and whose blast-radius reasoning (see requirements.md's "Why not fixed inline") is exactly this kind of scope creep. Filed as backlog item `0f4b1300-d667-437b-b51f-89d81a668693` ("AttachToExisting/RestoreWithWorkDir check-then-act TOCTOU can double-install or leak a PTY under concurrent Close()") instead of silently leaving it implicit. plan.md's Epic 1.1 now carries a matching note and the code itself gets an inline comment at both call sites pointing at the follow-up.
- [x] #3 — **Resolved, with a course-correction found during implementation**: `TestSessionService_CreateThenImmediateDelete_NoDataRace` (Task 1.3.2a) initially raced 8 concurrent create/delete pairs in one test invocation to raise the odds of landing in the real window. That approach was reverted after `go test -race -count=20` empirically showed it introduces a real, unrelated flake: "database is locked" from the session store's SQLite connection under 8-way concurrent writes combined with `-race`'s slowdown exceeding the store's 5s busy_timeout (`session/ent_repository.go`'s `_timeout=5000`). Landed instead on a single sequential create/delete pair per invocation, relying on `-count=20`'s outer repetition (not in-test concurrency) for probabilistic coverage — verified clean across 20 consecutive `-race` runs with zero data races and zero DB-lock failures. Its doc comment states explicitly that it is a best-effort, non-deterministic repro; the *deterministic* proof of correctness is `TestGetPTY_ClosePTYAndAttachCmd_ConcurrentAccessIsSerialized` (Task 1.2.2a), which forces the exact interleave by holding `ptmxMu` before spawning either goroutine. A full production test-hook (blocking the real controller-start goroutine mid-`GetPTY()`) was considered and rejected as disproportionate blast-radius for this PR — noted as a nice-to-have, not filed as a separate item since it's a test-quality improvement, not a product bug.
