## Blockers

- [x] **RESOLVED** — Task 1.2.2a in the final plan already uses a `testing/synctest` bubble with `synctest.Wait()`, and its own prose explicitly explains and rejects the naive "lock-before-spawn" approach this finding warned about (see plan.md Task 1.2.2a's "Why `testing/synctest` and not a manual lock-hold-before-spawn" paragraph). Original finding preserved below for history.
  **Task 1.2.2a / Story 1.2.2 (`TestGetPTY_ClosePTYAndAttachCmd_ConcurrentAccessIsSerialized`)** — The test's "hold `ptmxMu` before spawning both goroutines, unlock after both are launched" pattern does not actually force contention, and the plan's stated reason for rejecting `testing/synctest` in favor of it is factually wrong. Holding the lock before `go func(){...}()` only guarantees blocking *if* a spawned goroutine has already reached its `Lock()` call by the time the parent calls `Unlock()`. Go gives no scheduling guarantee that a newly-spawned goroutine has started running (let alone reached a specific line) before the spawning goroutine continues — `go func(){}()` merely makes the goroutine runnable, not immediately running. If `Unlock()` executes before either child goroutine reaches `t.ptmxMu.Lock()`/`clearPTYTriple()`'s internal lock, the mutex is already free when they do start, and the test degrades to an ordinary uncontrolled race — exactly the "probabilistic, hope-the-scheduler-cooperates" category `research/pitfalls.md` #4 says this test exists to avoid. The task's own justification text claims "both spawned goroutines are guaranteed blocked on `ptmxMu.Lock()` before the test's `Unlock()` runs, since neither can pass that line without the lock" — this conflates "cannot pass the line without the lock" (true) with "has reached the line at all" (not guaranteed). This directly undercuts Story 1.2.2's explicit goal ("deterministically forces the ... interleave ... not just a probabilistic `-count=N` stress run") and the reasoning used to reject `synctest` (which — via `synctest.Wait()`'s durable-blocked-goroutine tracking, covering goroutines blocked on `sync.Mutex.Lock()` — is designed to solve exactly this rendezvous problem).
  - **Remediation**: Add real synchronization that proves both goroutines are durably blocked before calling `Unlock()`. Preferred: wrap the test in a `testing/synctest` bubble and call `synctest.Wait()` before unlocking (Go 1.26.3 in `go.mod` has this stable). If `synctest` is deliberately avoided, use an explicit two-phase barrier instead (e.g., each goroutine closes a "ready" channel immediately before calling into `GetPTY()`/`closePTYAndAttachCmd()`, and the main goroutine waits on both channels — narrows, though does not perfectly close, the race). Either way, correct the code comment's rejection rationale for `synctest` so it doesn't ship a false claim about Go's scheduling guarantees into the test file.

## Concerns

- [x] **RESOLVED** — plan.md Task 1.1.1a's doc comment now correctly states `detachMutex` is held across one or more `ptmxMu` critical sections in both `Detach()` and `DetachSafely()`, matching this finding's remediation verbatim; ADR-001's Alternatives section was corrected too. Task 1.1.1a (`ptmxMu` doc comment) / Pattern Decisions table / ADR-001 — The mandated doc comment ("`detachMutex` → `ptmxMu` is fine (used sequentially by `DetachSafely` → `Restore` → `RestoreWithWorkDir`, never nested)") misstates the actual call graph, verified by reading `session/tmux/tmux.go`. `DetachSafely()` (tmux.go:1553–1603) never calls `Restore()` at all — it calls `closePTYAndAttachCmd()` directly (tmux.go:1572) while holding `detachMutex`. It's the *separate* method `Detach()` (tmux.go:1607–1680) that calls `closePTYAndAttachCmd()` directly (tmux.go:1624) **and then** calls `t.Restore()` → `RestoreWithWorkDir()` (tmux.go:1648), still within the same `detachMutex` hold. So `ptmxMu` is acquired and released two-to-three times *while `detachMutex` is held throughout* — that is genuine nesting, not "never nested." The plan's own research (`research/pitfalls.md` §3) gets this right ("a real (if benign) nesting relationship that didn't exist before... document this explicitly"); the plan's Task 1.1.1a text flattens that correct finding into an inaccurate one before it ships as a permanent code comment. The safety conclusion is still correct (order is consistently `detachMutex`-outer/`ptmxMu`-inner, never reversed, so no deadlock), but a lock-ordering comment whose entire purpose is to keep *future* maintainers from introducing a cycle should describe the real call graph, not a wrong one.
  - **Remediation**: Rewrite the Task 1.1.1a comment along the lines of: "`ptmxMu` is a leaf lock. `detachMutex` is held across one or more `ptmxMu` critical sections in both `Detach()` and `DetachSafely()` (each calls `closePTYAndAttachCmd()` directly; `Detach()` additionally chains into `Restore()`/`RestoreWithWorkDir()` afterward) — this is nested, but safe because `ptmxMu` is always released before returning control to the `detachMutex` holder, and no code path acquires `ptmxMu` first and then attempts to acquire `detachMutex`." Also fix the corresponding claim in the Pattern Decisions table and ADR-001's Alternatives Considered section, which repeat the same wrong "`DetachSafely` holds it, then calls `Restore()`" framing.

- [x] **RESOLVED — `ptmx-field-guard` CI target added** (Task 1.1.1c, expanded package-wide per pre-mortem P1 fix), promoting the grep from a one-time PR check to a standing `make ci`/`quick-check` gate exactly as recommended. Story 1.1.1 / Pattern Decisions "PTY triple storage shape" row — The plan's stated benefit of keeping 3 separate fields plus helper methods — "the same 'can't forget a field' guarantee ... without the rename tax" — only holds for call sites that already go through `lockedPTMX`/`setPTYTriple`/`clearPTYTriple`. Nothing in the design stops a future method (added anywhere in package `tmux` — it already spans multiple files, e.g. `shell_handle.go`, `fork_metrics.go`) from directly reading or writing `t.ptmx`/`t.attachCmd`/`t.attachCmdWaitOnce`, since unexported fields are visible to the whole package, not just `tmux.go`. The design's only enforcement mechanism is the one-time manual grep specified as AC1's verification step (Task 1.1.1a/1.2.2b) — it proves the invariant holds at the moment of this PR, not that it keeps holding afterward. This is a real gap between Story 1.1.1's stated goal ("one obvious, **hard-to-skip** way") and what the chosen design actually enforces: today it is easy to skip — nothing fails the build if a later change bypasses the helpers.
  - **Remediation**: Promote the AC1 grep from a one-time PR-verification step into a standing CI check (a small `ast-grep`/shell script gating `session/tmux/tmux.go`, run in `make lint` or a dedicated CI step) that fails if `t.ptmx`, `t.attachCmd`, or `t.attachCmdWaitOnce` appears outside the three helper method bodies. This moves the guarantee up the enforcement ladder from "checklist" to "lint," consistent with this repo's own `quality:reflect-and-fix` doctrine, and actually delivers on the "hard-to-skip" claim rather than relying on reviewer vigilance indefinitely.

## Nitpicks

- Step 0.5 and ADR-001 cite "30 existing `deadlock.Mutex` uses ... vs 2 plain `sync.Mutex`" as evidence this "matches the file's dominant idiom" — but per `research/stack.md`'s own count, the 30 figure is **package-wide** across `session/` (health.go, pty_discovery.go, instance.go, tmux/fork_metrics.go, etc.), not specific to `tmux.go`. Within `tmux.go` itself there are only 3 `deadlock.Mutex` fields (`detachMutex`, `cmdSendMu`, `recoveryMu`) vs. 2 plain-mutex fields (`controlModeSubMu`, `controlModeStartMu`) — confirmed by direct grep. Separately, `research/build-vs-buy.md`'s "matches 4 existing precedents in this exact file" appears to overcount by one (3 verified). None of this changes the (correct) recommendation to use `deadlock.Mutex`, but the numbers should be corrected before they land verbatim in a comment, ADR, or commit message that a future reader might take at face value.
- Task 1.1.2b's converted `RestoreWithWorkDir` still performs two independent locked reads (`t.lockedPTMX() != nil` ... then later `t.lockedPTMX() == nil`) rather than a single check-and-branch under one lock hold, leaving a narrow TOCTOU window between them where a concurrent write-site call could interleave. This is a preserved pre-existing gap (the original code had the identical unsynchronized two-read pattern), not a regression, and fixing it is out of scope per AC6/non-goals — but a one-line comment noting it's a known, intentionally-preserved gap (not an oversight) would save a future reader from "fixing" it in a way that expands this item's scope.
