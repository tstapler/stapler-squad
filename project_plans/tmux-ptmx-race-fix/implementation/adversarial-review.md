# Adversarial Review: tmux-ptmx-race-fix

**Date**: 2026-08-06
**Verdict**: RESOLVED (re-verified 2026-08-06 against final `implementation/plan.md` during Phase 4 validation)

## Blockers

- [x] **RESOLVED** — Task 1.2.2c (`TestSessionService_CreateThenImmediateDelete_NoDataRace`) implements exactly the recommended fix: calls `DeleteSession` immediately after `CreateSession` returns, skipping `waitForLiveInstance`, looped `-count=N`, landing inside the real repro window. See `plan.md` Story 1.2.2 / Task 1.2.2c. Original finding preserved below for history.
  **AC3's "verified under concurrent load matching the original repro conditions" is not actually exercised by any task in the plan.** Task 1.2.2a is a synthetic, same-package `TmuxSession`-level test (`session.ptmx = r` direct assignment, `GetPTY()` vs `closePTYAndAttachCmd()` only) — it never touches `SessionService.CreateSession`/`DeleteSession`. Task 1.2.2b's only real-path check is rerunning the pre-existing `TestServer_should_WriteUnchangedHookURL_When_StartedOnExplicitPort` 20x. I read that test (`server/server_integration_test.go:373-413`): its `t.Cleanup` fires `DeleteSession` only after `waitForLiveInstance(t, deps, sessionID, 30*time.Second)` has already confirmed the instance is fully live. Per `research/architecture.md` §1, the actual race window is `CreateSession`'s async controller-start goroutine (`session_service.go:1574`) racing `DeleteSession`'s cleanup goroutine (`session_service.go:2062`) — a window that closes once the controller finishes starting, i.e. typically *before* `waitForLiveInstance` returns. So most/all of the 20 reps of this test likely complete their `CreateSession`→live-check→`DeleteSession` sequence entirely outside the narrow window that produced the original flake; rerunning it 20x is much weaker evidence for AC3 than the acceptance criterion's own wording ("under concurrent load matching the original repro conditions") implies.
  - **Recommendation**: add a purpose-built integration test that calls `DeleteSession` immediately after `CreateSession` returns (skip `waitForLiveInstance`), in a `-count=N` loop — `CreateSession` is confirmed to return before its async goroutine starts (`architecture.md` §1), so this directly maximizes the chance of hitting the reported interleave without needing a new synchronization hook. Alternatively, add an explicit test-only hook at the `SessionService` layer (mirroring the deterministic-rendezvous approach already used in Task 1.2.2a at the `TmuxSession` layer) that forces the interleave every time rather than probabilistically.

## Concerns

- [x] **Documented as a Known Residual Risk in `plan.md`, filed as a followup per project convention** — `setPTYTriple` vs `clearPTYTriple` write-write TOCTOU can leak a PTY/process on delete-during-create — fixed for memory safety, not for the underlying lifecycle race. `closePTYAndAttachCmd`'s `clearPTYTriple()` always captures "whatever triple is currently in the field," not "the specific generation the caller observed earlier." Concretely: `CreateSession`'s async goroutine reaches `Instance.Start()` → `i.pm().RestoreWithWorkDir(...)` (confirmed call sites: `session/instance.go:906,930,976,1108,1144,1202,1428`, all outside `i.mu` per `architecture.md` §1) → `RestoreWithWorkDir`'s retry loop calls `t.ptyFactory.StartWithSize(...)` then `t.setPTYTriple(...)`, installing a brand-new generation. If `DeleteSession`'s `Destroy()` → `closePTYAndAttachCmd()` runs to completion *before* that `setPTYTriple` call lands, the freshly-spawned tmux attach-session process and PTY are never torn down by anything — `Destroy()` already ran and won't run again, and nothing else in the codebase watches for a post-delete PTY install. This is a pre-existing race (not introduced by this plan) and legitimately out of scope per requirements.md's "no behavior change to PTY lifecycle semantics" non-goal — but the plan doesn't name it anywhere, and fixing the `-race`-flagged memory race could easily read as "the CreateSession/DeleteSession race is fixed" when only its memory-safety half is.
  - **Recommendation**: add an explicit "known residual risk, out of scope" note to the plan/PR description, and file it as its own backlog item per `.claude/rules/fix-flaky-tests-dont-defer.md`'s "don't just move on, file it" discipline — don't let this get silently reabsorbed into "the race is fixed."

- [x] **RESOLVED — `ptmx-field-guard` Makefile target added** (`plan.md` Task 1.1.1c, expanded package-wide per pre-mortem P1 fix 2026-08-06). No enforcement mechanism prevents a future direct field access or a 7th ad-hoc lock — despite the repo already having the exact tool for this. AC1's verification method (Story 1.1.1) is "grep and confirm zero matches at review time" — a one-time manual check, not a codified guard. The Makefile already has a directly analogous CI guard for the same class of problem: `actor-field-guard` (`Makefile:758-763`, wired into `make ci`) fails the build if direct `Instance` field writes appear outside `session/instance*.go`/`actor.go`. The plan's own AC1 language ("grepping for `t.ptmx`, `t.attachCmd`, or `t.attachCmdWaitOnce` outside the bodies of `lockedPTMX`, `setPTYTriple`, and `clearPTYTriple`") is literally the guard's logic, just not turned into a `make` target.
  - **Recommendation**: add a `ptmx-field-guard` target modeled on `actor-field-guard`, wired into `make ci`/`quick-check`, so a future contributor adding a raw `t.ptmx = ...` or a new unguarded PTY-adjacent field gets a build failure instead of relying on code review to catch it.

- [x] **RESOLVED — Task 1.2.2b adds `TestClosePTYAndAttachCmd_ConcurrentCallersDoNotPanic`**, the dedicated two-concurrent-caller test. Task 1.1.2c's "naturally serialize" claim ships with zero dedicated test coverage. The plan asserts, as an intentional side effect, that concurrent `closePTYAndAttachCmd()` callers now serialize — "only the first caller to acquire `ptmxMu` inside `clearPTYTriple()` gets non-nil locals, so a second concurrent caller is a fast no-op instead of racing on `.Close()`/`.Kill()`." Task 1.2.2a only exercises `GetPTY()` vs `closePTYAndAttachCmd()`; no test exercises two concurrent `closePTYAndAttachCmd()` callers (plausible in practice: `Detach()`/`DetachSafely()` and `Instance.Destroy()` → `Close()` can both reach it). This is very likely a strict improvement — in the *old* unsynchronized code, a second caller reading `t.attachCmd` as non-nil (raced ahead of the first caller's `t.attachCmd = nil`) but then reading `t.attachCmdWaitOnce` *after* the first caller already nil'd it would call `.Do()` on a nil `*sync.Once`, i.e. a nil-pointer panic — a latent bug the atomic triple-capture design incidentally closes. But that's my inference from reading the old code, not something the plan tests or states. AC6 in Story 1.1.2 is scoped to "same suppressed error strings, same `errs` slice" for the *single-caller* path only.
  - **Recommendation**: either add a second deterministic test (two goroutines both calling `closePTYAndAttachCmd()` concurrently, asserting no panic and exactly one does real cleanup work), or soften the plan's prose to not assert a guarantee nothing verifies.

## Minors

- Deadlock-detector false-positive risk (concern raised about `deadlock.Enabled` combined with the diagnostic goroutine at tmux.go:1272-1276) checked out as low-risk: `deadlock.Enabled` is driven by build tags (`race`/`deadlock`/`nodeadlock`), not a runtime flag, and is already active for the file's existing 5 locks in every `-race` run including `make quick-check`'s `test-race` target — adding `ptmxMu` doesn't create a new enablement surface. The package's inconsistent-lock-order detector (`lockorder.go`) only flags genuinely reversed nesting order across goroutines; the one real nesting (`detachMutex` → `ptmxMu` via `Detach`/`DetachSafely` → `Restore` → `RestoreWithWorkDir`) is consistently ordered everywhere it occurs, and `lockedPTMX`/`setPTYTriple`/`clearPTYTriple` never call out to another lock, so no reversal is possible. The diagnostic goroutine never touches `ptmxMu` at all (it closes over local `cmd`/`waitOnce` vars) and shares its `*sync.Once` safely via `sync.Once`'s own guarantee, independent of `ptmxMu`. No action needed.
- The concern about `TapEnter`/`TapDAndEnter`/`SendKeys`'s changed error text breaking a caller checked out clean: grepped every caller of the three methods and every reference to the relevant error strings ("PTY not initialized", "invalid argument") in the repo. Nothing pattern-matches on the old nil-receiver `os.File` error text. `session/session_driver.go:478`'s comment mentioning tmux `"invalid argument"` is descriptive prose only (`attemptBacklogNudge` treats any non-nil `SendKeys` error identically, no string check). Plan's "not a lifecycle behavior change" claim holds.
- `session/tmux/tmux.go` growing to a 6th lock in a 2499-line file is a real ongoing complexity cost, but the plan's design (single leaf lock, 3 narrowly-scoped helpers, documented ordering) is already the right mitigation shape for a bugfix of this size — the actionable follow-up is captured above as the field-guard concern, not a separate ask.
