# Research: Similar Features, Edge Cases & Failure Modes — Escalation Reasoning

## Similar features (existing precedent to reuse/stay consistent with)

- **`ApprovalAnalyticsPanel.tsx`** (`web-app/src/components/sessions/ApprovalAnalyticsPanel.tsx`, backed by `useApprovalAnalytics` hook and `GetApprovalAnalytics` RPC, registry entry `docs/registry/features/backend/approval/get-analytics.json`) is the *direct* precedent for AC4. It already has a selectable time-window control (`windowDays` state, buttons for 7/30/etc — `windowSelector`/`windowBtn`/`windowBtnActive` CSS classes), category badges (`categoryBadge`), and card/table breakdown rendering (`cardAllow`/`cardDeny`/`cardManual`, day-by-day bars). The backend aggregation function `ComputeSummary` (`server/services/analytics_store.go:317`) already buckets `AnalyticsEntry` records by `RuleID`/`Decision`/`Reason` (fields already present, `analytics_store.go:27-29`) — `RecordFromResult` (`analytics_store.go:159`) is already called for **both** classifier escalations (`approval_handler.go:286-288`) and the domain-age escalation path (`approval_handler.go:250-257`, with `RuleID: "new-domain-check"`), so the raw data AC4 needs is already flowing into analytics today; only a new category-bucketing aggregation (grouping by the 5-way taxonomy) plus a UI section (likely inside `ApprovalAnalyticsPanel.tsx`, following its existing patterns) is new work.
- **`BlockedNotice.tsx`** (`web-app/src/components/backlog/detail/BlockedNotice.tsx`) is the closest existing "explain why this couldn't proceed automatically" UX pattern in the codebase — a plain-text explanation keyed by a small taxonomy (`BlockedNoticeKind`: `blocked_guardrail` / `manual_review_marker` / `missing_diagnostic_data`), each with an icon/label/fallback config, rendered as plain text with a documented fallback string when data is missing. Worth mirroring the "always have a non-empty fallback string" discipline even though AC6 specifies plain `itemContext`-class text (no icon/badge component) for this feature.
- **`ReviewQueuePanel.tsx`**'s existing `getReasonLabel` switch (lines ~526-544) and `AttentionReason` taxonomy is the sibling pattern for "why is this item in the queue" at the *item* level; the new escalation reason is one level more specific ("why was *this specific tool call* escalated," only populated when `reason === ReasonApprovalPending`).
- **Industry precedent** (context, not code): CI/lint "explain this failure" UX (e.g., GitHub Actions annotations, ESLint `--explain <ruleId>`) and agent-permission tools (e.g., other Claude Code permission-review UIs) universally separate "what is blocked" from "why," and most surface the *rule id* alongside the plain-language reason for auditability — this codebase already has that pairing (`RuleID` + `Reason` on `ClassificationResult`) so the design should carry both through, not just the prose string, even though AC6 only requires the plain text to render.

## Edge cases

### 1. Multiple domains in one command matching new-domain-age — VERIFIED
`server/services/approval_handler.go:238-263`: `ExtractDomainsFromCommand(cmd)` returns all domains found in the command; the loop checks each in order and on the **first** `isNew` match it logs, records to analytics (`RuleID: "new-domain-check"`), and does `goto createApproval` — which jumps out of the loop entirely. So:
- **Only the first newly-registered domain (in `ExtractDomainsFromCommand`'s extraction order, effectively left-to-right occurrence in the command) produces a reason.** Any additional new domains later in the same command are never checked (the loop is abandoned via `goto`) — their reasons are silently dropped, not just de-prioritized.
- Worse: the computed `reason` string is **currently discarded entirely** — `_ = reason` at line 261, with a comment "will be surfaced when the approval is shown in review queue" that was never implemented. This is the literal bug the requirements describe; the design must plumb this specific `reason` value (not a general "domain-age" label) through to `PendingApproval`.
- Design implication: decide explicitly whether to keep "first match wins" (simplest, matches current analytics recording) or list all new domains — first-match-wins is consistent with what's already recorded in analytics, so extending it (rather than changing loop behavior) is the lower-risk choice unless product wants a fuller enumeration.

### 2. Explicit-rule vs. shell-expansion sentinel precedence — VERIFIED, unambiguous by construction
`pkg/classifier/classifier.go:479-502` (`classifyInternal`): the `pc.HasShellExpansionProgram` check (line 485) returns immediately with `RuleID: "shell-expansion-program"` *before* `classifySingle` (line 502, which evaluates the explicit rule table) is ever called. These are two different early-return branches in the same function — a single classification can produce **at most one** of {explicit-rule, shell-expansion-program, no-match}, never both. No precedence rule is needed in the new design; the mutual exclusivity is already guaranteed at the source. (Also note: the domain-age path (`approval_handler.go`) and the classifier path are themselves mutually exclusive per-request — `goto createApproval` on domain-age skips the classifier call entirely — so domain-age vs. explicit-rule/shell-expansion collisions are likewise impossible today.)

### 3. What happens to the reason on resolution (approve/deny/timeout)? — VERIFIED, gap identified
- **Human approve/deny**: `ApprovalService.ResolveApproval` → `ApprovalStore.Resolve` (`server/services/approval_store.go:160-183`) **deletes** the `PendingApproval` from `s.pending` and re-persists to disk immediately (`s.persistToDiskLocked()` inside the same lock). There is no separate resolved/audit table — once resolved, the in-memory+on-disk record (and thus any reason field stored only on `PendingApproval`) is gone.
- **Timeout**: `approval_handler.go:398-406` calls `h.store.Remove(approvalID)` (same deletion effect) then `h.stampResolved(approvalID, sessionID, "timeout")`.
- **Client disconnect**: `approval_handler.go:409-415`, same `Remove` + `stampResolved(..., "canceled")`.
- `stampResolved` (`approval_handler.go:99-111`) only writes a `"approval_decision"` metadata key (`"timeout"`/`"canceled"`) onto a **notification** record via `notificationStamper.SetMetadata` — it does not carry the escalation reason or `RuleID`.
- **The only durable record that outlives resolution is the `AnalyticsStore` entry** written at classification/escalation time (`RecordFromResult`, called before the human ever sees the item) — it already has `RuleID`+`Reason` fields. That entry is *not* updated with the eventual human decision, so today there is no single row joining "why it was escalated" with "what the human decided." This is out of scope per AC2 (which only requires surviving restart *while pending*), but worth flagging as a known adjacent gap — not something this feature is required to fix, since no existing resolved-approval audit trail exists to extend.
- Conclusion: the reason does **not** need to survive past resolution for AC2's purposes (queue item disappears once resolved, same as today), but should not be assumed to be independently queryable post-resolution — don't design UI that expects to look up "why was this approved 3 days ago" without also wiring a write to `AnalyticsStore` (which is possible since analytics already has the reason at escalation time, just not the final decision).

### 4. Orphaned approvals reloaded from disk — VERIFIED, real risk requiring explicit handling
This is the most concrete failure mode found. The reason data must be threaded through **four** separate structs/functions, and missing any one silently drops it for orphaned entries specifically:
1. `PendingApproval` struct (`approval_store.go:21-39`) — in-memory, needs a new field (e.g. `EscalationReason string`, possibly `EscalationRuleID string`).
2. `PersistedApproval` struct (`approval_store.go:43-53`) — the JSON-on-disk shape; **currently has no reason field**, and `persistToDiskLocked` (`approval_store.go:291-317`) does a field-by-field copy from `PendingApproval` → `PersistedApproval` — a new field on `PendingApproval` alone does *nothing* for persistence unless also added here.
3. `loadFromDisk` (`approval_store.go:342-` ) reconstructs `PendingApproval` from `PersistedApproval` field-by-field (not a struct copy) — again, must explicitly copy the new field or it silently becomes the zero value for every orphaned entry after a restart.
4. `session.ApprovalMetadata` struct (`session/review_queue_poller.go:54-62`, consumed via the `ApprovalMetadataProvider` interface) and `GetApprovalMetadataBySession` (`approval_store.go:137-154`) — the metadata struct currently only carries `ApprovalID`, `ToolName`, `ToolInput`, `Cwd`, `Orphaned`. A new field must be added here too, and to the mapping loop inside `GetApprovalMetadataBySession`, and finally consumed in `review_queue_poller.go:808-820`'s enrichment block (which currently sets only `tool_input_command`/`tool_input_file`/`cwd`/`orphaned` into `item.Metadata`) to add e.g. `item.Metadata["escalation_reason"]`.

Because orphaned approvals are reconstructed purely from the on-disk JSON (there is no live request context to recompute the reason from after restart — `ToolInput`/`Cwd` are the only original signals retained), the reason **must** be computed once at escalation time and persisted as data, not recomputed lazily on read. This directly reinforces AC1's "sourced from the real escalation path" requirement — there is no fallback recomputation path available for orphaned entries.

Also note `GetApprovalMetadataBySession` uses only `approvals[0]` ("most recent/first approval") when enriching a review-queue item (`review_queue_poller.go:809-810`) — if a session somehow has multiple pending approvals, only the first one's reason (like today's command/cwd) will surface; this is pre-existing behavior, not a new edge case to solve, but the reason field should follow the same single-approval assumption for consistency.

### 5. AC7 button intent — VERIFIED current state
The "Create Rule" button (`ReviewQueuePanel.tsx:820-838`) currently always uses `intent="ghost"` for any approval item that has `tool_input_command` metadata (no distinction by escalation category today). AC7 requires switching to `intent="secondary"` specifically for no-match escalations (RuleID==""), which means the button's intent must become conditional on the new reason-category data, not just presence of `tool_input_command`.

## Reviewer's unstated needs

- **Fallback/empty state discipline**: `BlockedNotice.tsx`'s per-kind `fallbackText` config ("No summary recorded.") is a useful pattern to copy — any approval item where the reason can't be computed (e.g., pre-existing orphaned entries persisted *before* this feature ships, which will have no reason in their on-disk JSON) needs a defined fallback string rather than blank space, since `loadFromDisk` will happily unmarshal old JSON without the new field into a zero-value string.
- **RuleID alongside prose**: consistent with `ClassificationResult` always pairing `Reason` (prose) with `RuleID` (machine-checkable category), the design should keep both fields even though AC6 only renders the prose — the `RuleID`/category is what AC4's analytics breakdown and AC7's conditional button intent both key off of, so it can't be dropped even if UI only shows text.
- **Category taxonomy must be computed once, not duplicated**: the taxonomy in the requirements (RuleID=="" + Escalate → no-match; "new-domain-check" → domain-age; "secret-scan" → secret-scan; "shell-expansion-program" → unclassifiable; other non-empty RuleID + Escalate → explicit-rule) should live in one shared helper (Go, and mirrored or exported to TS for AC4's frontend rendering) rather than being reimplemented separately in the analytics aggregation and the queue-item enrichment path — both consume the same `RuleID`/`Decision` inputs.

## `docs/registry/` pattern check

- Backend: existing per-feature files already cover the adjacent surface — `docs/registry/features/backend/approval/get-analytics.json`, `resolve.json`, `list-pending.json`, `generate-suggested-rule.json`, and `docs/registry/features/backend/review-queue/get.json`/`watch.json`. No RPC signature changes are anticipated (the reason rides in `ReviewItem.Metadata`, a `map<string,string>` already used for `tool_input_command` etc., not a new proto field), so likely **no new backend registry file is needed** — existing `review-queue/get.json` and `approval/get-analytics.json` entries just need `lastModified` bumped and `tested`/`testIds` updated once new tests land.
- Frontend: `docs/registry/features/frontend/` is sparse (13 entries total) and currently has **no** entries for `ReviewQueuePanel.tsx`, `SuggestedRuleCard.tsx`, or `ApprovalAnalyticsPanel.tsx` despite those being registered, tested, longstanding features — this repo's frontend registry has a pre-existing coverage gap unrelated to this feature. New work here should still add a proper kebab-case entry (e.g. `docs/registry/features/frontend/escalation-reasoning-display.json` and/or `approval-analytics-reason-breakdown.json`) per `.claude/rules/feature-registry.md`, but should not assume any existing frontend entry needs updating since none currently exist for the surfaces being touched. Run `make registry-generate` after adding.
