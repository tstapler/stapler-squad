## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `EscalationReasonText`'s fallback ("No approval rule matched this request…") fires whenever `Reason == ""` regardless of category — but `Reason` is never validated as required anywhere a rule can be created (manual `UpsertApprovalRule`, YAML import via `ImportRulesModal.tsx`, or an LLM `GenerateSuggestedRule` suggestion accepted with a blanked textarea in `SuggestedRuleCard.tsx:322-329`). An explicit-rule escalation whose matched rule has a blank `Reason` renders a sentence that flatly denies a rule matched at all. | A reviewer sees "No approval rule matched this request" on a card whose `escalation_reason_category` is actually `explicit-rule` (a real, named `RuleID` the reviewer or a teammate authored) — the text contradicts the card's own category/RuleID and the feature's central promise (AC1: "not a generic string"). | Branch `EscalationReasonText` on category, not just `Reason == ""`: for a non-empty `RuleID` with empty `Reason`, return a category-aware fallback ("Rule '<RuleID>' flagged this for review (no reason text was provided)") instead of the no-match sentence. Add a test case: `ClassificationResult{RuleID: "custom-rule", Reason: ""}` → assert the fallback does NOT claim no rule matched. | P1 |
| 2 | The new `default:` arm on the classifier switch (added to close the architecture-review's "missing case" gap) sets `escalation = result` for any unrecognized `ClassificationDecision`, but `result.RuleID` in that branch is almost certainly `""` (no rule lookup occurred) — so `CategorizeEscalationRuleID` buckets a genuine classifier-internal bug as `no-match`, which renders the confident "no rule matched" copy and offers the "✦ Create Rule" CTA for a case that isn't a coverage gap at all. | If `classifier.ClassificationDecision` ever grows a 4th value (or misbehaves), reviewers see a normal-looking no-match card and may create a rule to "fix" what's actually an internal bug — undermining AC1's "grounded in the actual classification outcome, not a generic string" promise in exactly the case that most needs an honest signal. | Give the `default:` arm its own 6th category (e.g. `EscalationUnexpected`) that renders distinct copy ("An internal classification error occurred — review manually") and is excluded from the no-match-only Create Rule gate, instead of silently inheriting `no-match`'s UI treatment. | P3 |
| 3 | `ApprovalStore` serializes every `Create`/`Resolve` behind one `sync.RWMutex`, and `persistToDiskLocked` re-marshals and writes **all** pending approvals to disk on every single mutation, while holding that write lock. This feature adds two more string fields per entry — one of which (`EscalationReason` for explicit-rule/rule-author text) is already flagged elsewhere in this same plan (Task 3.1.1b) as unbounded free text with no length cap. The plan's own Observability Plan states "Metrics: not required." | Under a burst of many near-simultaneous escalations (an autonomous/headless session or a script issuing several disallowed commands back-to-back — the exact workload this tool exists for), hook-response latency and review-queue population lag visibly increase, and nothing in place would surface it as a metric or alert, so it looks like the app is just "slow" with no diagnostic trail. | Add a concurrency test (N goroutines calling `HandlePermissionRequest`/`store.Create` for simultaneous escalations) to Story 5.1.1, and either cap `EscalationReason` length at write time or explicitly benchmark the added marshal/write cost before accepting "no metrics needed" as the final answer. | P2 |
| 4 | The plan's 41 tasks are anchored to specific line numbers (`ReviewQueuePanel.tsx:718`, `:726-743`, `:818`, `:820`; `approval_handler.go:237`, `:280-312`, `:358-369`) in files with demonstrated high churn: `git log` shows PR #148 alone landed a 927-line rewrite of `ReviewQueuePanel.tsx` on `main`, and a scan of sibling worktrees in this same workspace shows 10+ other in-progress backlog branches (e.g. `stapler-squad-launchd-shell-sourcing`, `stapler-squad-terminal-fit-convergence`, `stapler-squad-backlog-github-issue-link`) currently carrying 200-1400 line diffs against these exact files (`approval_handler.go`, `approval_store.go`, `analytics_store.go`, `review_queue_poller.go`, `ReviewQueuePanel.tsx`, `ApprovalAnalyticsPanel.tsx`, `rules_service.go`). | The implementation subagent edits the wrong lines (silently, since the line numbers "compile" against whatever text happens to be there) because another backlog item's PR landed on `main` first and shifted the file; or this branch's PR hits repeated merge conflicts against other concurrently-shipping review-queue/approval PRs, slowing delivery well past the plan's task-level time estimates. | Before Phase 5 (implementation) actually starts, re-diff the plan's cited line ranges against current `main` (not the planning-time snapshot) as a matter of course, and treat this PR as high-conflict-risk — merge/rebase promptly rather than letting it sit alongside other approval/review-queue work in flight. | P2 |
| 5 | Story 3.2.1 hides the "Create Rule" button entirely for `domain-age` escalations, reasoning that "domain-age escalations have no 'prevent this next time' story a pattern rule can express" — but `GenerateSuggestedRule`'s `validateSuggestion` (`rules_service.go:772-773`) explicitly supports `auto_allow`/`allow` decisions, not just deny/escalate patterns. A domain-age false positive (a legitimately new but trusted domain) is exactly the case where a user would want a one-click "always allow this domain" rule — which the button already supports today (it's `tool_input_command`-gated only, not category-gated) and would lose entirely after this ships. | A user who previously used Create Rule to allowlist a trusted-but-new domain after a domain-age escalation finds the button gone with no equivalent one-click path, and has to fall back to manually building a rule in the separate rules panel — a real capability loss, not just a UX-optics question needing sign-off (which is as far as `adversarial-review.md` took this). | Either scope the no-match-only gate to *deny/escalate-pattern* suggestions specifically (keep the button for domain-age, since an allow-suggestion is a valid use), or explicitly confirm with the PR description that domain-age's allow-rule use case is deliberately dropped, not just overlooked because the rationale text only considered "prevent this" and not "always allow this." | P2 |

## P1 Items (address before implementation)
- [x] #1 — RESOLVED in `implementation/plan.md` (commit `d32763dd9`): Task 1.1.1c's
  `EscalationReasonText` now branches on `CategorizeEscalationRuleID(result.RuleID)`, using the
  "No approval rule matched this request…" sentence only for the `no-match` category; a
  category-aware fallback ("Rule %q flagged this for review — no reason text was provided.") is
  used for `explicit-rule`/`domain-age`/`unclassifiable`, and a distinct sentence for the new
  `EscalationUnexpected` category (see finding #2's fix). Story 1.1.1's AC and Task 1.1.1d's test
  list were both updated with this exact case.
