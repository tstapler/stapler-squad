# Pre-mortem: network-hostname-redetect
**Date**: 2026-09-18

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | A subprocess call inside `redetect` (`scutil`/`avahi-resolve`/`hostname`, or `net.LookupHost` in `verifyHostnameOwnership`) hangs during an unstable network transition — precisely the moment it's most likely to, and precisely the moment responsiveness matters most. Since `Run` processes ticks/events/manual triggers serially through one `select` loop with no per-call deadline (only `ctx.Done()` stops `Run` itself, not an in-flight `redetectFn`/`resolveFn`/`detectFn` call), one stuck call freezes the *entire* detector — timer, OS-event, and manual-trigger paths all go dark simultaneously. | After a WiFi switch, no `"hostname-detect: cycle complete"` log line appears at all — not even an error — and the previous network's hostnames stay stuck. Looks like the feature silently died, not that it's mid-cycle. | Wrap every subprocess/DNS call inside a cycle with a bounded `context.WithTimeout` (a few seconds, well under the 5-minute interval) so one hung call can't stall the loop past that bound; add a test with a fake `resolveFn` that blocks forever and assert `redetect` still returns within the timeout. | P1 |
| 2 | `verifyHostnameOwnership` only checks "does this hostname forward-resolve to one of my own non-loopback IPs" — it has no allowlist/domain-suffix restriction. On a network where the DNS server itself is untrusted or attacker-influenced (rogue DHCP handing out a malicious resolver), an attacker-chosen hostname can be made to resolve to the victim's own LAN IP, passing the gate and becoming a *permanently* trusted WebAuthn RPID / TLS SAN for the rest of the process's life (add-only, no expiry, per Scope). | No symptom at the time — the whole danger is silence. Eventually surfaces only if Tyler audits `waHandler.rpIDs` or the debug endpoint's `networks` dump and finds a hostname he never intentionally visited. | Restrict auto-registration to a configured allowlist of domain suffixes (e.g. `*.staplerhome.com`, the known VPN/office domains) rather than "resolves to my IP" alone; anything outside the allowlist gets logged as a candidate but requires a manual trigger/confirmation before `RegisterHostname`/TLS-SAN inclusion. | P3 |
| 3 | The manual-trigger endpoint's send onto `detector.manual` is timeout-guarded (Task 4.2.2a), but the subsequent *receive* of the `redetectCycle` off `respCh` is not — if `Run`'s goroutine is mid-cycle when it dequeues the manual request (or hits Failure #1 right after), the HTTP handler blocks indefinitely with no response, exactly during the manual verification workflow it exists to support. | `POST /api/debug/redetect-hostnames` hangs with no response and no log line, during the one workflow (manual verification without waiting 5 minutes) this endpoint was built for. | Apply the same `time.After(...)`/`r.Context().Done()` guard to the `respCh` receive, not just the `detector.manual` send; add a test that starts a `Run` goroutine whose fake `resolveFn` blocks forever and asserts the HTTP handler still returns (e.g. `504`) within the bound. | P2 |
| 4 | `networks` (and therefore the per-cycle subprocess call count) only grows, never shrinks, for the life of the process — every IP ever seen on every network ever visited gets fully re-resolved every single cycle forever, per Task 2.1.1b's explicit "every currently-detected IP, not just new ones" design. Over weeks/months of uptime (the whole point of no longer needing restarts) this is a slow, unbounded increase in per-cycle subprocess load. | Cycle `duration` in the structured log creeps upward over days/weeks; eventually cycles start taking a non-trivial fraction of the 5-minute interval, or subprocess-spawn overhead becomes noticeable in CPU/process-count spikes every 5 minutes. | Add a soft cap/eviction policy on the *re-resolution target list* only (distinct from the permanent hostname-trust set, which stays add-only per Scope) — e.g. stop re-resolving an IP not seen on the current interface list for N consecutive cycles. Add a long-run synthetic test (many distinct historical IPs) asserting cycle duration/subprocess-call count stays bounded, not linear in total-IPs-ever-seen. | P2 |
| 5 | The OS-level network-change path (`tailscale.com/net/netmon` on macOS) has zero CI coverage (no macOS runner) and its exact API was guessed in the plan pending godoc verification. A bug in event delivery or wiring degrades to "timer-only" behavior that still mostly works (just slower, via the 5-minute fallback) — meaning the bug is masked rather than surfaced, and easy to ship without ever really verifying the event-driven half of the appetite decision. | After switching WiFi on the Mac, the new hostname doesn't appear promptly but does show up ~5 minutes later via the timer — looking like "it worked, just a bit slow," when actually the event trigger never fired at all. | Add an explicit manual QA step to validation.md: unplug/switch WiFi and confirm the log line fires within seconds (not just "eventually"), performed and recorded at ship time, not skipped under time pressure; consider a startup self-check that logs a warning if the process has been up longer than 2 ticker intervals with zero network-change events observed on a machine that's known to roam networks. | P2 |

## P1 Items (address before implementation)
- [ ] #1 — Add per-call `context.WithTimeout` deadlines around every subprocess/DNS call inside `redetect` (including `verifyHostnameOwnership`'s `net.LookupHost`), and add a test proving a stuck fake dependency can't stall `Run`'s entire select loop past the bound. This isn't in the current plan.md at all — add it as a new task under Epic 2.1 or 2.2 before Phase 2 implementation starts.
