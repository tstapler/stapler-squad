# Research: Pitfalls & Risks — network-hostname-redetect

## 1. Subprocess leakage / zombie processes / unbounded goroutine growth

**Existing convention already covers half the risk.** `detectLANIPs`/`resolveLANHostnames` (`main.go:965-1267`) already shell out via `executor/safeexec.CommandContext` (`main.go:1007,1018,1069,1092`), not raw `exec.CommandContext` — `executor/safeexec/safeexec.go:1-37` pre-sets `WaitDelay = 2s` specifically so a killed subprocess's `cmd.Wait()` can't block forever when a grandchild holds stdout/stderr pipes open. A `norawexec` lint rule enforces this repo-wide. **The periodic/event loop must keep using `safeexec` for every re-detection subprocess call** — this is already structurally enforced by lint, but worth stating explicitly since it's easy to reintroduce a raw `exec.Command` in a new code path lint hasn't seen yet.

**What's not yet covered — the loop itself:**
- The periodic ticker/goroutine and the OS-event-listener goroutine both need to be spawned with a `context.Context` derived from server shutdown, and **must select on `ctx.Done()`** in every blocking point (ticker wait, event-channel read, subprocess call). `docs/explanation/concurrency-patterns.md` documents a double-checked-locking gotcha for this codebase but has no existing periodic-loop pattern to mirror — this feature would be the first, so the shutdown-cancellable-loop pattern needs to be designed carefully, not assumed to already exist somewhere to copy.
- If `resolveLANHostnames` is invoked without a bounded per-call timeout distinct from the loop's outer context, a single hung `scutil`/`avahi-resolve` invocation (e.g. against a flaky VPN interface) could pin one goroutine indefinitely; each subprocess call already gets its own child context in `main.go` (e.g. `avahiCtx`, `scutilCtx`) — confirm the periodic caller does the same per-cycle, not one context shared for the process's whole lifetime that only cancels at shutdown (which would make hangs invisible until then).
- **Debounce must not spawn a fresh unbounded goroutine per event.** A naive `go func() { time.Sleep(debounceWindow); redetect() }()` per raw OS network event during a flapping burst (e.g. Wi-Fi association retry loop) creates N in-flight goroutines and N eventual `redetect()` calls — the opposite of debouncing. Use a single coalescing goroutine with a resettable `time.Timer` (drain-and-reset, the standard Go debounce idiom), not a timer-per-event.
- **Test enforcement**: this repo already runs `goleak.VerifyNone` in integration tests (`server/server_integration_test.go:93-94`, plus a "tolerant" wrapper in `server/server_test.go:288-341` for known-noisy cases). Any test that starts the periodic/event loop and doesn't cleanly stop it via context cancellation before the test ends **will fail `goleak`** in CI — this is a real gate, not just a style preference, and should catch a missing-cancellation bug before merge rather than after.

## 2. Race conditions on `Server.hostnames`

`server/server.go:1510-1518` confirmed as described in requirements — `SetHostnames`/`GetHostnames` are plain unsynchronized `[]string` field accessors, no mutex, no atomic:
```go
func (s *Server) SetHostnames(hostnames []string) { s.hostnames = hostnames }
func (s *Server) GetHostnames() []string          { return s.hostnames }
```
Today this is safe only because `SetHostnames` is called exactly once at startup before any reader goroutine exists. Adding a background writer breaks that invariant — `GetHostnames()` will then race with the periodic-detection goroutine's writes, and Go's race detector (`go test -race`, used across this repo's `make test-race`) will catch it.

**Which pattern to apply**: `.claude/rules/instance-lock-free-reads.md` documents this repo's established convention for exactly this shape of problem — `atomic.Pointer[T]` + a `Snapshot()`-style accessor, chosen over `sync.RWMutex` because it's a "publish immutable value, read lock-free" pattern (single writer path — periodic loop; N reader paths — HTTP handlers, WebAuthn, remote-access TLS). That rule is written for `*Instance` specifically but the shape (add-only, append-then-republish, many concurrent readers, one background writer) matches `Server.hostnames` closely enough that the same primitive applies:
```go
type Server struct {
    hostnames atomic.Pointer[[]string] // replace plain []string field
    ...
}
func (s *Server) SetHostnames(hostnames []string) { s.hostnames.Store(&hostnames) }
func (s *Server) GetHostnames() []string {
    if p := s.hostnames.Load(); p != nil { return *p }
    return nil
}
```
A plain `sync.RWMutex` would also be race-free and is simpler to reason about for a rarely-written, occasionally-read `[]string` — either is defensible, but since the repo has already standardized on `atomic.Pointer` + `Snapshot()` for this exact shape elsewhere (`session/instance_snapshot.go`), following that precedent keeps the codebase consistent rather than introducing a second idiom for the same problem. **Note the add-only merge (new hostname list must be the union of old + newly detected, not a wholesale replace)** needs to happen before the `Store()` call, computed from the previously-loaded slice — do the merge, then publish, same as the double-checked-locking gotcha in `concurrency-patterns.md:8-19` ("always return the locally-computed value, not the cache slot") applied to a write path instead of a read path.

## 3. Security risk: hostname spoofing / DNS rebinding feeding WebAuthn RPID trust

This is the highest-stakes risk in the whole feature. Read `server/auth/hostname_guard.go` (negativeHostnameCache, sourceIPLimiter) and `server/auth/webauthn.go`'s `webauthnForHost` in full.

**Existing reactive model and its guard rails**: `webauthnForHost` (`server/auth/webauthn.go:93+`) only calls `hostnameValidator` — which does a real DNS lookup — when an *inbound HTTP request* arrives with an unrecognized `Host` header, and only after passing `negativeHostnameCache.IsNegative` (skip re-validating recently-failed hostnames) and `sourceIPLimiter.Allow` (rate-limit per source IP, `rate.Limit(1)`/burst 3 — `server/auth/hostname_guard.go:16-22`). This means today, an attacker would need to (a) get a request delivered to the server with a spoofed `Host` header pointing at attacker-controlled infrastructure, AND (b) have that hostname's forward DNS lookup actually resolve (to *something* — `hostnameValidator`'s exact check needs confirming, but the comment at `webauthn.go:85` implies it validates the hostname resolves to one of the server's own IPs, not just that DNS answers at all) — and even then it's rate-limited to ~1/sec per source IP, capped at 256 negative entries.

**How periodic/proactive detection changes the threat model:**
- Today, RPID registration for a new hostname is *gated behind an actual attacker-controlled request reaching the server* — an attacker has to actively probe with a crafted Host header to trigger the validator at all. A periodic background loop that calls `detectLANIPs`/`resolveLANHostnames` **on a timer, independent of any inbound request**, moves hostname discovery to a source the attacker doesn't need request access to influence directly: it depends on reverse-DNS (PTR), mDNS/avahi, and `scutil` DNS search-domain answers — i.e., **whatever the network currently tells the box, unauthenticated**, since none of `LookupAddr`/`avahi-resolve`/`scutil --dns` do any TLS/auth validation of the answer.
- **Concrete rebinding-shaped attack**: if the server is on a network an attacker (or attacker-controlled device, e.g. a compromised IoT device, malicious AP, or ARP/mDNS spoofing) can inject a hostname into — e.g. answering `avahi-resolve`/mDNS queries under an attacker-chosen name that happens to reverse-resolve to this host's own current LAN IP, or a rogue DHCP/DNS server on a public/untrusted Wi-Fi network handing out a PTR record — the periodic loop would proactively add that attacker-supplied hostname to `Server.hostnames` and (per requirements' add-only design) potentially into the WebAuthn RPID set and TLS SAN list, **with no request-level rate limiting or negative-cache gating at all**, since those guards live in `webauthnForHost`'s reactive path, not in `detectLANIPs`/`resolveLANHostnames`.
- **This is a materially larger attack surface than today's reactive model** for two reasons: (1) no per-source-IP rate limit exists on the network-answer side — an attacker spoofing mDNS/PTR responses isn't bound by `sourceIPLimiter`, which only throttles HTTP request-driven validation attempts; (2) it's proactive rather than request-gated, so the attacker doesn't need to get a request to the server's HTTP listener at all — poisoning the LAN's name resolution is sufficient.
- **What should be explicitly designed against**: the periodic/event-driven detection path must funnel any newly-discovered hostname through the **same validation the reactive path already trusts** before it's eligible for RPID/TLS SAN registration — specifically, whatever check `hostnameValidator` performs (confirm exactly what: does it verify the hostname resolves back to one of *this host's own* currently-bound IPs, i.e. a round-trip check, not just "DNS answered something"?). If `detectLANIPs`/`resolveLANHostnames`'s own internal fallback chain already performs an equivalent round-trip consistency check (forward-resolve the candidate hostname and confirm it maps back to an IP this host is actually listening on) that's the existing mitigation to lean on and just needs to be preserved end-to-end, not reinvented. If it does *not* perform that check today (i.e. it accepts any PTR/mDNS answer without confirming the forward direction agrees), **that gap predates this feature but this feature is what turns it into an auth-relevant proactive attack surface** — flag this explicitly for Phase 3 planning as a candidate for adding a round-trip verification step before any hostname coming out of the periodic loop is allowed to touch `Server.hostnames`'s WebAuthn/TLS-consuming paths, mirroring `hostnameValidator`'s existing bar rather than a lower one.
- **Rate-limiting the periodic loop itself is not a substitute** for validating what it finds — a slow attacker only needs one accepted false hostname, ever, since the design is explicitly add-only/process-lifetime-persistent (per Scope: "hostnames that stop resolving are not removed"). A single successful spoof during a network flap event is enough to plant a permanently-trusted attacker RPID until the next restart. This raises the bar for the validation step from "nice to have" to "the actual control," since there's no cleanup/expiry safety net to fall back on if a bad hostname slips in.

## 4. Test flakiness pitfalls

Confirmed conventions in this repo:
- `server/server_integration_test.go:93-94` and `server/server_test.go:288-341` show the established `goleak.VerifyNone`/`IgnoreCurrent` pattern (with a documented "tolerant" wrapper for known environment noise) — any new test exercising the periodic/event loop should follow this same pattern to catch goroutine leaks from an improperly-cancelled loop.
- The repo's `fix-flaky-tests-dont-defer` and `deterministic-fast-tests` skills (referenced in this project's CLAUDE.md reference table) establish the house rule: fix flaky tests structurally rather than deferring them, and prefer deterministic constructs (fake clocks, injectable event sources) over real sleeps/timeouts in tests. This is the load-bearing guidance for this feature specifically, since:
  - **Real network events cannot be triggered deterministically in a unit/integration test** — actually changing Wi-Fi networks or bringing an interface up/down in CI is not viable (and CI runs on `ubuntu-latest`/`ubuntu-22.04` exclusively — see §5 — so a macOS-specific `SCDynamicStore` test couldn't run there regardless).
  - **Design the periodic loop and the OS-event listener as injectable dependencies from day one**: a `<-chan time.Time` (or an interface wrapping `time.Ticker`, swappable for a test-controlled channel/fake clock) for the timer path, and a `<-chan struct{}` (or similarly minimal interface) for "a network-change event fired" that the real macOS/Linux shim publishes to in production but a test can push to directly. This mirrors the general Go idiom for testing ticker-driven loops (inject the ticker/channel, not `time.NewTicker` called inline) and is the only way to test debounce-coalescing logic (§1) without a real `time.Sleep` in the test.
  - Avoid any test that asserts on wall-clock timing (e.g. "after 500ms exactly one redetect happened") — assert on sequence/count of events fed through the injected channel instead, so the test runs in milliseconds and is deterministic regardless of machine load.

## 5. macOS vs Linux platform divergence

**CI runs exclusively on `ubuntu-latest`/`ubuntu-22.04`** — confirmed by grepping every `runs-on:` line across all 14 workflow files in `.github/workflows/`; there is no `macos-*` runner anywhere in the CI matrix. This is a significant risk specific to this feature, since:
- The macOS-side OS-event trigger (`SCDynamicStore`/`scutil` reachability callbacks per the requirements' Rabbit Holes section) **can never be exercised by CI at all** — it will only ever be tested by hand on the primary dev machine (macOS, per this repo's environment). Any macOS-specific bug here ships without a CI safety net; the Linux netlink/`operstate`-polling path is the only one CI can verify, and only indirectly (CI containers typically don't have real network interface churn to observe either, so even the Linux path likely needs the injectable-event-source design from §4 to be tested at all in CI).
- This repo already has an established `//go:build` split convention for exactly this kind of OS divergence — e.g. `server/services/exec_unix.go` / `exec_windows.go` (`//go:build !windows` / `//go:build windows`) and the analogous `dup_fd_unix.go`/`dup_fd_windows.go`, `tmuxreap_testmain_unix_test.go`/`_windows_test.go` pairs. The network-change-detection shim should follow the same pattern: `netdetect_darwin.go` (`//go:build darwin`) and `netdetect_linux.go` (`//go:build linux`) implementing a shared interface, rather than runtime `runtime.GOOS` branching inside one file — consistent with how this repo already handles unix/windows divergence elsewhere, and it keeps each platform's `cgo`/exec-shim code out of the other platform's compiled binary.
- Given CI can only build (not functionally exercise) the macOS path, **the injectable-event-source design in §4 becomes doubly important**: it lets the *coalescing/debounce/state-update logic* (the part that actually touches `Server.hostnames` and RPID/TLS registration — the security-relevant part from §3) be fully covered by CI-runnable tests on Linux, even though the *real* macOS event source itself is only manually verified. Don't let "the OS shim can't be tested in CI" become an excuse to also leave the logic downstream of it untested.
- Confirm during Phase 3 planning whether a `go build ./...` (compile-only, no execution) for `GOOS=darwin` is already part of `make ci`/`goreleaser-check.yml` — if cross-compilation isn't currently verified for this repo's Go build (worth checking `goreleaser-check.yml`, not fully read here), a macOS-only build tag file could silently bit-rot without even a compile failure being caught until someone builds on a Mac by hand.

## Summary of explicit design requirements this research surfaces
1. Use `executor/safeexec` for all periodic-loop subprocess calls (already lint-enforced) and give the loop a shutdown-derived `context.Context`, checked at every blocking point.
2. Debounce with a single coalescing timer per-loop, not a goroutine-per-event.
3. Replace `Server.hostnames`'s plain field with `atomic.Pointer[[]string]` + `Snapshot()`-style accessors (per `.claude/rules/instance-lock-free-reads.md`'s established pattern), with add-only merge computed before `Store()`.
4. Any hostname flowing from periodic/event-driven detection into WebAuthn RPID or TLS SAN registration must pass through the same (or equivalent) validation `hostnameValidator` applies today — confirm exactly what that check is and whether `detectLANIPs`/`resolveLANHostnames` already performs a round-trip (forward-resolve-back-to-own-IP) check; if not, flag adding one as a required control, not optional hardening, given the add-only/no-expiry design removes any later cleanup safety net.
5. Design the timer and OS-event source as injectable interfaces/channels from the start so debounce and update logic are covered by fast, deterministic CI tests (goleak-checked) even though the real macOS event source itself can only be manually verified (CI has no macOS runner).
6. Follow the existing `_unix`/`_windows`-style build-tag split (`netdetect_darwin.go` / `netdetect_linux.go`) for the platform-specific event-source shim.
