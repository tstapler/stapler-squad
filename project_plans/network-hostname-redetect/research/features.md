# Research: Feature Landscape — Runtime Hostname Re-detection

Agent 2 (Features), SDD Phase 2, project `network-hostname-redetect`.

## 1. What this codebase already has (and already answers one Open Question)

**`Server.hostnames`** (`server/server.go:60`, `SetHostnames`/`GetHostnames` at `1510-1518`) is a plain unsynchronized `[]string` field — the concrete thing that must become thread-safe. `detectLANIPs()` (`main.go:1249`), `resolveLANHostnames()` (`main.go:967`), `getDNSSearchDomains()` (`main.go:1043`), and `scutilNameservers()` (`main.go:1089`) are the reusable detection primitives named in the requirements.

**The add-only precedent already exists and is well-tested**: `server/auth/webauthn.go`'s `webauthnForHost` (line 93) lazily validates an unrecognized `Host` header via an injected `hostnameValidator` closure (wired from `main.go`'s `startRemoteAccess`, which forward-resolves via `net.LookupHost` + `forwardLookupViaKnownNameservers` and checks the result against `listNonLoopbackIPs()` — i.e., "does this hostname resolve to an IP *this machine owns*"). On success it appends to `h.rpIDs` and registers a new `webauthn.WebAuthn` instance with a matching `RPOrigins` entry (guarded by `h.mu`). This is guarded by two rate-limiting primitives in `server/auth/hostname_guard.go`: `negativeHostnameCache` (256 entries, 5-minute TTL, evict-oldest) and `sourceIPLimiter` (512 IPs, 1 req/s sustained, burst 3, `golang.org/x/time/rate`). **This is the exact concurrency/rate-limit pattern the new periodic/event-driven detector should reuse or plug into**, not reinvent — `webauthn_test.go`'s own regression-test comment (lines 53-61) already frames this as "hostname discovery at server startup... is one-shot."

**Finding that changes scope on a stated Open Question**: requirements.md's Open Questions asks whether the `--remote-access` TLS path supports a dynamically-updated SAN set or is a single static cert. It is *already* the dynamic case, architecturally: `server/tls.go`'s `EnsureNetworkTLSCerts` issues **one leaf cert per network** (keyed by local IP, e.g. `"192.168.1.135"`), each signed by a stable shared CA that's reused as long as it isn't near expiry — so adding a network's cert never forces regeneration of another network's cert or the CA. `GetCertificateByLocalAddr` (`server/tls.go:128`) returns a `tls.Config.GetCertificate` callback that picks the right leaf cert per-connection by inspecting `chi.Conn.LocalAddr()`. This callback is wired in exactly once, in `main.go:1271`'s `startRemoteAccess()`, over a `netCerts map[string]*NetworkCert` captured by closure. **The remaining gap is not "does dynamic SAN support exist" (it does) — it's that `networks`/`netCerts` are built once at `startRemoteAccess()` time and the map is not behind a mutex/atomic**, so a periodic re-detector needs to (a) re-run `EnsureNetworkTLSCerts` with an updated `networks` map when a new LAN IP/hostname appears, and (b) swap the `GetCertificate` closure's underlying map thread-safely (e.g. `atomic.Pointer[map[string]*NetworkCert]`, mirroring the `Instance.snapshot` pattern documented in this repo's `instance-lock-free-reads.md` rule). This substantially de-risks the "TLS cert SAN mutation after issuance" Rabbit Hole in requirements.md — it's a wiring problem, not a design problem.

**Already a dependency**: `go.mod` includes `github.com/shirou/gopsutil/v4` (used elsewhere; confirmed present via `grep go.mod`) — gopsutil's `net.Interfaces()` gives a portable poll-based interface list without new subprocess shelling, useful as a debounce-friendly "did anything change" pre-check before re-running the expensive `scutil`/`avahi-resolve` detection chain. `github.com/fsnotify/fsnotify` is also present but is a filesystem watcher, not applicable to network events directly (ruled out, not a lead).

## 2. Industry landscape

**Tailscale's `tailscale.com/net/netmon`** is the closest existing prior art for exactly this problem and directly answers requirements.md's question "is there a maintained, low-dependency-weight Go library for cross-platform network-change notification?" — with a qualified yes:
- Purpose per its own doc comment: "monitoring network interface and route changes... primarily exists to know when portable devices move between different networks."
- Built-in **debounce/coalescing**: `InjectEvent`/state-change callbacks fire within "a fraction of a second" coalescing window — solves the requirements.md Rabbit Hole about a single network transition firing multiple raw OS events.
- Built-in **sleep/wake detection**: `TimeJumped`/`JumpDuration` detect a wall-clock jump indicating the machine just woke — directly relevant to the "sleep/wake" edge case named in this research question.
- **`IsMajorChangeFrom`** classifies whether a transition is worth tearing down/rebinding — a ready-made signal for "should I re-run detection now."
- Per-OS backends: `netmon_linux.go` (netlink), a macOS implementation over `AF_ROUTE`/routing sockets + `sysctl`, and a generic `polling.go` fallback — i.e., it already solves the exact "no shared Go stdlib API between macOS and Linux" problem requirements.md flags as a Rabbit Hole, with a documented per-platform shim *plus* a polling fallback for anything unsupported.
- **Caveat (real cost, not hypothetical)**: there is no way to import just the `netmon` subpackage without adding `tailscale.com` as a `go.mod` module dependency — the whole module is pulled in at the dependency-declaration level (though Go's linker still dead-code-strips the actual binary). This is a real increase in the dependency graph's surface area (transitive deps of the full `tailscale.com` module, e.g. wireguard-go, dependencies for tailscale's own crypto/logging) that Phase 3 planning should weigh explicitly against a hand-rolled per-OS shim, especially given this repo's existing convention of shelling out to `scutil` directly rather than using cgo/library wrappers for macOS-specific state.

**vishvananda/netlink** and **mdlayher/netlink** are lower-level, Linux-only netlink libraries — usable for a hand-rolled Linux backend if `netmon`'s dependency weight is rejected, but they solve none of the macOS side, coalescing, or sleep/wake pieces `netmon` gets for free.

**macOS `SCDynamicStore`**: the native API (`SCDynamicStoreCreate` + `SCDynamicStoreSetNotificationKeys`), reachable from Go only via cgo — no evidence of a pure-Go wrapper. Community discussion notes it's noted as "confusing to work with" even in ObjC/Swift. This repo already shells out to `scutil` for DNS lookups (`main.go:1089`'s `scutilNameservers`), so a similar shell-out-and-parse approach to `scutil --nc`/reachability could avoid a new cgo dependency, at the cost of no true event-push (would need polling `scutil` output) — this is the "small platform-specific shim" alternative requirements.md's Rabbit Hole names as plausible.

**How self-hosted/local-first peers actually behave in practice** (bearing on user's unstated needs, not just the mechanism):
- **Syncthing** re-broadcasts its local-discovery UDP announcement on a fixed 30-60s interval (cache TTL 90s = 3x interval) and *does* force an immediate re-announce when it discovers a new peer, but — per its own community forum — has **no built-in user-facing command to force a re-discovery after a network/interface change**; the only documented workaround users report is a full restart. This is precisely the baseline behavior this project's requirements.md explicitly rejects as the status quo to fix.
- **Home Assistant's Plex integration** (GDM/mDNS-based discovery) shows the failure mode of *not* handling network/IP change gracefully: numerous open GitHub issues describe the sensor going permanently "unavailable" after an IP change or a restart-during-downtime, requiring the user to delete and re-add the integration (breaking device names/automations in the process) — a cautionary example of what happens when there's no re-detection loop at all, and of how sensitive to fix users are once names/identities (their analogue to this project's RPIDs) get baked to a stale value.
- **Tailscale** (the actual node, not just the `netmon` library) treats a detected "major" network change as a trigger to re-derive its own reachable-address set and re-home connections — the same shape as this project's problem (a host with several possible LAN identities that must track which one currently applies), but Tailscale's own security model tolerates the more aggressive "rebind" behavior because it isn't juggling an add-only trust list the way this project's WebAuthn RPID/TLS-SAN scope decision requires.

## 3. Edge cases and failure modes the design should handle

Beyond what requirements.md already names (flapping, VPN toggle, DHCP renewal, debounce), from cross-referencing the industry patterns above and this codebase's actual detection chain:

- **Sleep/wake without a network change**: `netmon`'s `TimeJumped` distinguishes "the box just wasn't running" from "the network actually changed" — worth using (or replicating the wall-clock-delta heuristic) so a laptop resuming from sleep on the *same* network doesn't trigger a redundant `scutil`/`avahi-resolve` subprocess burst.
- **Multiple simultaneous interfaces (Wi-Fi + Ethernet + VPN tun)**: `detectLANIPs()` already needs to consider all of them (per requirements.md's non-goal note about not rewriting this), but the re-detection *trigger* logic must not fire once per interface event when three interfaces change near-simultaneously (e.g. connecting a VPN also renumbers the Wi-Fi's effective default route) — this is the debounce Rabbit Hole, and `netmon`'s coalescing window is the off-the-shelf answer.
- **DNS resolver cache staleness independent of interface state**: `main.go`'s `hostnameValidator` already works around OS-resolver shadowing by falling back to `forwardLookupViaKnownNameservers` (querying `scutil`-known nameservers directly) rather than trusting `net.LookupHost` alone — the periodic detector should reuse this same double-check, since a stale resolver cache can persist across a network change even after `scutil`'s own state has updated.
- **Negative-cache interaction (named in requirements.md, confirmed in code)**: `negativeHostnameCache`'s TTL is a fixed 5 minutes (`server/auth/hostname_guard.go:21`) — independent of any network-change signal. A hostname that failed lazy validation on the old network and got negatively cached will silently block re-validation for up to 5 minutes even after the new periodic/event-driven detector confirms it's now resolvable, unless the new detection path explicitly clears (or bypasses) matching negative-cache entries when it adds a hostname to `Server.hostnames`. This is a concrete, code-verified version of the interaction risk requirements.md flags abstractly.
- **Subprocess/goroutine leakage under a tight event storm**: requirements.md's Feasibility Risk about `scutil`/`avahi-resolve`/`hostname` being shelled out to per call is real — an event-driven trigger that isn't bounded by `context.Context` cancellation and a debounce/coalesce step could spawn overlapping detection cycles under network flapping. The existing `docs/explanation/concurrency-patterns.md` conventions this repo already follows should govern the timer/event-loop's lifecycle.
- **Race between the periodic timer and the OS-event hook firing at once**: two triggers (timer tick + event) landing concurrently should not run two overlapping detection cycles — needs a single-flight guard (this repo doesn't currently have `golang.org/x/sync/singleflight` in `go.mod`; worth flagging for Phase 3 as either a new small dep or a simple mutex/in-flight-flag).
- **TLS leaf-cert map mutation racing live TLS handshakes**: since `GetCertificateByLocalAddr`'s returned closure is invoked per-incoming-TLS-handshake, any runtime update to the underlying `certs` map must not race a concurrent handshake read — this is the same class of bug this repo's `instance-lock-free-reads.md` rule was written to prevent for `*Instance` fields, and the fix is the same shape (atomic snapshot swap, not a raw map mutation).

## 4. Unstated user needs beyond the explicit requirements

- **Confidence that the fix actually engaged**, not just correctness: the Observability Requirements section already asks for structured logging per cycle, but given the Plex/Home Assistant failure pattern above (silent permanent staleness that users only notice much later, if ever, and then have to manually intervene), the log line for "cycle ran, nothing changed" is as important as "cycle ran, hostname added" — Tyler's own stated baseline symptom ("the only fix today is a full process restart") implies he wants a way to *notice* re-detection working without needing a restart to test it, i.e. logs he can `grep` for confidently, not just DEBUG-level noise.
- **A way to force a cycle without restarting**, for troubleshooting/verification during rollout (not in requirements.md's explicit scope, but implied by the Risk Control section's ask for "trivially disableable" — the symmetric "trivially triggerable" for testing is a very small addition and directly supports the manual verification workflow this repo's own `docs/how-to/*` conventions favor over relying on real timing).
- **Not breaking the existing one-shot `webauthnForHost` lazy-validation path** — the new periodic/proactive detector and the existing per-request lazy detector will now both be capable of adding the same hostname to the trusted set; the design needs one of them to be authoritative (or both converge on the same underlying add-only store) so they don't diverge or duplicate log noise for the same hostname.
- **Minimizing new dependency weight** given this is a single-developer personal tool (per requirements.md's Constraints) — the `netmon` dependency-weight caveat above is directly relevant to an implicit "keep this maintainable solo" need, even though requirements.md doesn't say so explicitly.
