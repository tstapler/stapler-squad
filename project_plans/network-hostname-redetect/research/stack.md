# Stack Research: network-hostname-redetect

## Existing primitives to reuse (confirmed by reading code)

- `detectLANIPs()` (`main.go:1249`) — returns `[]string` of LAN IPs, OS-routing-preferred first.
- `resolveLANHostnames(lanIPStr string) []string` (`main.go:967`) — per-IP hostname resolution (reverse DNS, scoped-nameserver PTR, avahi, `hostname -f`, search-domain + `.local` fallback). Shells out to `scutil`, `avahi-resolve`, `hostname` via `executor/safeexec` with 3-5s timeouts each — dozens of subprocess calls per full cycle across all detected IPs, matching the NFR's "cheap but not free" framing.
- `getDNSSearchDomains()` (`main.go:1043`) and `scutilNameservers()` (`main.go:1089`) — support functions already used by the above; no new signature needed.
- `Server.hostnames []string` (`server/server.go:60`) with `SetHostnames`/`GetHostnames` (`server/server.go:1510-1518`) — **plain field, no mutex, no atomic**. This is the one piece that must change: a background goroutine calling `SetHostnames` concurrently with an HTTP handler calling `GetHostnames` is a data race today. Fix pattern: either wrap with a `sync.RWMutex` (cheapest, matches `negativeHostnameCache`'s style below) or republish via `atomic.Pointer[[]string]` (matches the `session/instance_snapshot.go` "lock-free reader" convention this repo already uses elsewhere — see `.claude/rules/instance-lock-free-reads.md`). Given call frequency here (once per timer tick / event, read on every request), a plain `sync.RWMutex` is proportionate; the atomic-pointer pattern is overkill for a field this infrequently written.
- `webauthnForHost` (`server/auth/webauthn.go:93`) already has an add-only, lazy, on-demand hostname→rpID registration path (`h.webauthn[hostname] = wa`, `h.rpIDs = append(...)`, guarded by `h.mu`). The new periodic/event-driven detector should call into the **same registration path** (or a small exported wrapper around it) rather than re-implementing rpID/origin construction — this keeps "single source of truth for how a hostname becomes a trusted rpID."
- `negativeHostnameCache` (`server/auth/hostname_guard.go:29`) — bounded, **5-minute TTL** (`negativeCacheTTL`), evict-oldest-on-insert. This directly answers the Open Question about interaction with `webauthnForHost`'s negative cache: a hostname that failed lookup on the old network self-expires from the cache after 5 minutes regardless of what triggers revalidation, so the periodic/event-driven redetector doesn't need any special cache-busting — worst case is a hostname stays falsely negative-cached for up to 5 minutes after becoming valid on a new network. If the chosen redetection interval is shorter than 5 minutes, consider whether the redetector should proactively call something like `negativeCache.clear(hostname)` when it (re)confirms a hostname resolves — cheap to add, avoids the residual 5-minute worst case.
- `--remote-access` TLS SANs (`server/tls.go`) are **already dynamic at the connection layer**: `GetCertificateByLocalAddr(certs map[string]*NetworkCert)` (`server/tls.go:128`) returns a `tls.Config.GetCertificate` callback (wired at `main.go:1301`) that picks a cert **per accepted connection** by local IP, out of a `map[string]*NetworkCert` built once by `EnsureNetworkTLSCerts` (`server/tls.go:58`) in `startRemoteAccess`. This resolves the Rabbit Hole/Open Question about SAN mutation: the cert is **not baked in once for the life of the process** in the sense of being read once by `tls.Config.Certificates` — it's read fresh per-handshake from the callback's captured map. Practically, this means live SAN updates are a matter of regenerating the `map[string]*NetworkCert` (via `EnsureNetworkTLSCerts` again with the updated hostname list merged into each network's `sans`) and swapping it under a lock/atomic that `GetCertificateByLocalAddr`'s closure reads — **not** a full listener restart. `EnsureNetworkTLSCerts` already diffs `sanHash(sans)` against a stored hash file and only reissues a leaf cert (reusing the stable CA) when the SAN set actually changed, so calling it again on every redetection cycle is cheap when nothing changed. The remaining wiring gap: `certs` is currently a local variable captured once in `startRemoteAccess`, not a mutable/reloadable reference — Phase 3 needs to make that map swappable (e.g. `atomic.Pointer[map[string]*NetworkCert]` or a small guarded wrapper struct) for `GetCertificateByLocalAddr` to see updates.

## Background goroutine + ticker convention (matches repo style)

Closest existing analog: `session/host_advertiser.go`'s `HostAdvertiser.Run(ctx context.Context)` (lines 75-86):

```go
func (a *HostAdvertiser) Run(ctx context.Context) {
	ticker := time.NewTicker(a.interval)
	defer ticker.Stop()
	for {
		a.BroadcastOnce(ctx)
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
		}
	}
}
```

This is the pattern to copy for the new redetector's timer arm: run once immediately, then loop on `ticker.C`/`ctx.Done()`. Other repo instances of the same shape: `session/hibernation_sweeper.go:216`, `session/backlog_sync.go:75`, `session/orphan_tmux_sweeper.go:75`. All are started via `go x.Run(ctx)` from `main.go` with a `ctx` derived from `signal.NotifyContext` (`main.go:85`), which already cancels on `SIGTERM`/`SIGINT` — the new redetector goroutine should be started the same way so it shuts down cleanly with the rest of the process's background loops, satisfying the Feasibility Risk about goroutine/subprocess leakage on shutdown.

For the OS-event arm, the same `select` needs a third case (an event channel) alongside `ctx.Done()` and `ticker.C`, with a debounce timer (`time.AfterFunc` or a small "reset a timer on every event, fire on quiet period" helper) to satisfy the Debounce/Coalescing Rabbit Hole — no existing repo helper for this exists yet; it's a small addition, not a new dependency.

## OS network-change notification: library options

**No existing dependency in `go.mod` covers this today.** Relevant existing deps: `golang.org/x/net v0.58.0`, `golang.org/x/sys v0.47.0`, `github.com/fsnotify/fsnotify v1.10.1` (used for config-file watching only — `main.go`, `config/claude.go` — not applicable to network interfaces). `github.com/shirou/gopsutil/v4` is already a dependency but only exposes point-in-time stats (`net`, `mem`, `process` subpackages) — no change-notification API; not useful for the event-hook requirement.

**Critical constraint from `go.mod`'s own top-level comment**: this repo deliberately sets `godebug netdns=go` and documents *why* — `CGO_ENABLED=1` (required elsewhere for `go-sqlite3`) switches Darwin's default resolver to the cgo-based `getaddrinfo`, which previously deadlocked a goroutine calling `os/exec` concurrently with a cgo-resolver thread holding a libc lock (see the `TestReviewGateRunner_BranchDrift_...` incident referenced there). This means **any macOS network-change library that relies on cgo bindings into `SCDynamicStore`/`CoreFoundation` (e.g. wrappers around `SCNetworkReachability`) reintroduces exactly the risk this repo already paid down** — a cgo thread holding a lock at the moment a `resolveLANHostnames` subprocess call forks. This is a strong argument for either (a) a pure-Go approach on macOS, or (b) continuing the existing pattern of shelling out to `scutil` rather than linking against `SystemConfiguration.framework` via cgo.

Recommended approach, in order of preference:

1. **macOS: shell out to `scutil` in "watch" mode, or poll.** The codebase already treats `scutil` as an external subprocess (via `executor/safeexec`), not a cgo binding — this is consistent with the `netdns=go` decision. Two concrete options:
   - `scutil -w State:/Network/Global/IPv4` (or similar keys) blocks and prints a line to stdout on every change to that dynamic-store key — trivially wrapped as a long-running `exec.Command` with a `bufio.Scanner` on stdout, feeding lines into the same event channel the ticker arm uses. This needs no new Go dependency at all, just another `safeexec.CommandContext`-style long-running subprocess (new pattern for this repo — existing subprocess calls are all short-lived with a timeout, so this one needs its own restart-on-exit supervision loop, not a straight port of the timeout pattern).
   - Alternative: poll `scutil --dns`/interface list on the same ticker interval as the periodic arm and diff the result — effectively folds the "event" arm into a shorter-interval "timer" arm. Simpler, but drops the "promptly on actual change" appetite requirement in favor of "frequently enough not to matter," which the ideation phase already rejected (Alternatives Considered: "Timer-only, no OS event hook").
   - A pure-Go alternative exists in principle — `golang.org/x/net/route` (pure Go, no cgo, reads `AF_ROUTE`/`PF_ROUTE` socket messages on BSD-family systems including Darwin) can be used to open a routing socket and read `RTM_NEWADDR`/`RTM_DELADDR`/`RTM_IFINFO` messages as they arrive, which is the same underlying primitive `route -n monitor` uses. It's already in the module graph transitively is not guaranteed — **not currently in `go.mod`'s direct requires**, so it would need adding as a new explicit dependency (it's a `golang.org/x/net` subpackage, so no new *module*, just importing an already-present module's subpackage — `go.mod` already requires `golang.org/x/net v0.58.0`, so this needs **no new module addition at all**, only a new import path). This is the lowest-dependency-weight option and avoids both cgo and a new subprocess-supervision pattern. Recommended as the primary macOS approach if the event-loop code is worth writing directly; the `scutil -w` subprocess approach is the fallback if the raw route-socket message parsing proves fiddly.

2. **Linux: netlink route/address change socket.** Two realistic options:
   - Hand-rolled via `golang.org/x/sys/unix` (already a dependency, pure Go, no cgo): open an `AF_NETLINK`/`NETLINK_ROUTE` socket, subscribe to `RTMGRP_LINK|RTMGRP_IPV4_IFADDR|RTMGRP_IPV6_IFADDR`, parse `RTM_NEWLINK`/`RTM_NEWADDR`/`RTM_DELADDR` messages. More code to write and maintain than a library, but zero new dependencies — `golang.org/x/sys` is already required (`v0.47.0`).
   - `github.com/vishvananda/netlink` — the most widely used pure-Go netlink library (used by Docker, Kubernetes CNI plugins, systemd-adjacent tooling); has `LinkSubscribe`/`AddrSubscribe`/`RouteSubscribe` APIs that deliver exactly this kind of change-notification channel with far less boilerplate than hand-rolling netlink parsing. Actively maintained (regular releases tracking recent kernel netlink additions as of 2026). This is a **new dependency** but a small, focused, pure-Go one with no cgo and no transitive dependency bloat (its own deps are just `golang.org/x/sys` and `github.com/vishvananda/netns`) — reasonable fit for "low-dependency-weight" per the Open Question.
   - Recommendation: prefer hand-rolled `golang.org/x/sys/unix` netlink if the parsing surface needed is small (just "something changed, re-run detection" — the payload details don't need to be decoded, just the fact that a `RTM_NEWADDR`/`RTM_DELADDR`/`RTM_NEWLINK` message arrived), since the redetection logic re-derives everything from scratch via `detectLANIPs`/`resolveLANHostnames` anyway and doesn't need the message contents. Reach for `vishvananda/netlink` only if the hand-rolled parsing turns out more fiddly than expected once implementation starts.

3. **Cross-platform unified library**: no actively-maintained one exists that cleanly covers both without cgo on macOS (this is exactly the "no shared Go stdlib API" gap the requirements doc already flags). The realistic shape is a small `network_watch_darwin.go` / `network_watch_linux.go` pair with Go build tags (a pattern this repo already uses — see `session/procinfo/inspector_other.go`, `session/tmux/socket_owner_darwin.go` for existing `_darwin`/`_other` file-suffix build-tag splits), each producing the same `<-chan struct{}` (or similarly minimal) event signal consumed by one shared `Run(ctx, events <-chan struct{})` loop.

## Dependency additions summary

| Need | New module required? | Recommendation |
|---|---|---|
| macOS route-change events | No (subpackage of existing `golang.org/x/net`) | `golang.org/x/net/route` |
| Linux route-change events | No (using existing `golang.org/x/sys/unix`) — or Yes if choosing `vishvananda/netlink` | Prefer hand-rolled via `golang.org/x/sys/unix`; fall back to `github.com/vishvananda/netlink` if netlink parsing proves too fiddly |
| Debounce/ticker/background loop | No — stdlib `time` + existing repo pattern (`session/host_advertiser.go`) | N/A |
| Hostname-set mutex | No — stdlib `sync` | `sync.RWMutex` on `Server.hostnames`, mirroring `negativeHostnameCache`'s existing `sync.Mutex` style |
| Dynamic TLS SAN reload | No new deps — reuse `server/tls.go`'s `EnsureNetworkTLSCerts` + make the `certs` map swappable (`atomic.Pointer` or mutex) for `GetCertificateByLocalAddr`'s closure | N/A |

**Bottom line: this feature needs zero new required `go.mod` entries for the happy path** (macOS via `x/net/route`, Linux via `x/sys/unix` netlink) — everything needed is already either stdlib or an existing direct dependency. `github.com/vishvananda/netlink` is available as a fallback if hand-rolled Linux netlink parsing turns out more complex than expected during implementation, and remains the only "new dependency" scenario in this whole design.

## Testability notes (for Phase 4/5, flagged here since it constrains the API shape)

Per this repo's `deterministic-fast-tests` skill and the Feasibility Risk about real-network-dependent tests: the `Run(ctx, ...)` loop should accept an injectable ticker/clock (mirroring how other pollers in this repo are already structured, e.g. `session/pr_status_poller.go`'s `PollInterval` config field) and an injectable event-source channel (a plain `<-chan struct{}` is enough — tests can just send on a channel they own instead of needing a fake OS network stack), so unit tests can fire both a synthetic tick and a synthetic OS event without any real interface change or `time.Sleep`.
