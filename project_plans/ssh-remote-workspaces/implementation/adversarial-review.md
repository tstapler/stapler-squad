# Adversarial Review: ssh-remote-workspaces

**Date**: 2026-08-06
**Verdict**: RESOLVED (2026-08-06 validation pass — both blockers independently re-verified
against the current plan.md task text, not just trusted from the plan's own "closes Blocker N"
annotations; see pre-mortem.md Failure #3, which named that exact re-verification gap)

## Blockers

- [x] **RESOLVED** — Task 2.1.1f now wraps every blocking SSH call (`Dial`, `Run`/
  `CombinedOutput`, `Start`) in a ctx-bound goroutine with documented per-operation-class
  timeout budgets, **and** (added in this validation pass, closing the gap pre-mortem.md
  Failure #3 found) now also wraps `sshremote.KeyStore.GetIdentity`'s `go-keyring` call, since
  that read happens before `SSHRunner.Dial` even starts and can itself hang on a headless
  `systemd --user` Secret Service unlock prompt. Task 3.2.1d's test now covers the hang case,
  not just the immediate-error case. **`golang.org/x/crypto/ssh` has no native `context.Context`
  support, and no task wires cancellation to it.** `CommandRunner.Run`/`Start` (ADR-002) take a `ctx context.Context`, but `ssh.Session.Run`/`CombinedOutput`/`Start` and `ssh.Dial` are all blocking calls with zero context awareness — cancelling `ctx` does nothing to an in-flight `Session.CombinedOutput()` unless the code explicitly races it against `ctx.Done()` and force-closes the session/client. `research/pitfalls.md` §4 states this as a hard requirement ("a hung SSH connection must not block the dashboard UI thread... Budget timeouts per RPC, not per underlying SSH library call") but no story or task in Phase 2 (`SSHRunner.Run`/`Start`, Task 2.1.1b/c) or Phase 3 (keychain/dial construction, Task 4.2.1c) implements or tests this. Without it, `CreateSession` against an unreachable/half-open remote host can hang the ConnectRPC handler indefinitely instead of failing within a bounded timeout — the exact failure mode pitfalls.md names as unacceptable. — **Recommendation**: add an explicit task to Story 2.1.1 (and to the keychain read path, since `go-keyring`'s Linux Secret Service backend can also block on a D-Bus call with no user session to satisfy an unlock prompt — Task 3.2.1d only tests the case where `go-keyring` *returns* an error, not the case where the call hangs) that wraps every blocking SSH/keychain call in a `select` against `ctx.Done()` with a documented per-operation-class timeout, plus a test proving a hung dial/command is cancelled within that bound.

- [x] **RESOLVED** — Task 4.2.1e/f now implements best-effort compensating cleanup
  (`RemoteWorktreeOps.RemoveWorktree`) when remote tmux setup fails after worktree creation
  succeeds, or the connection drops between the two steps; the plan's Unresolved Questions
  section records the explicit scope decision (full reconciliation-on-connect for orphans from
  other causes is a fast-follow, not v1). **Orphaned remote-worktree / partial-failure cleanup
  is explicitly unresolved yet the plan is marked "Ready for implementation."** The plan's own Unresolved Questions list flags this: "Is orphaned remote-worktree reconciliation... in scope for this feature's v1, or a fast-follow? ... blocks Phase 2/Phase 6 scoping." No story or task in Phase 2 (`RemoteWorktreeOps.CreateWorktree`, Epic 2.2) or Phase 4 (`resolveRemoteTarget`/mode-specific wiring, Epic 4.2) handles the case where `git worktree add` succeeds on the remote host but the subsequent remote `tmux new-session` fails, or where the SSH connection drops between the two steps — both are realistic given Phase 2's own reconnect/backoff work assumes connections *do* drop mid-operation. The result is a silently orphaned worktree directory (and possibly a branch) on the remote host with no detection, no cleanup task, and no UI surface to even see it exists. This is a multi-step remote provisioning flow shipping with a known, named gap in its own failure-recovery story, not a hypothetical. — **Recommendation**: resolve the open question before implementation starts, not during it (it "blocks Phase 2/Phase 6 scoping" by the plan's own admission). At minimum, add a compensating-action task to `resolveRemoteTarget`'s call site — if tmux/session setup fails after worktree creation, attempt best-effort `git worktree remove` on the remote before surfacing the error — even if full reconciliation-on-connect is deferred to a fast-follow.

## Concerns

- [ ] **Per-session `*ssh.Client`, no connection-pooling story, against a stated 10-20-concurrent-sessions success metric.** Task 4.2.1c has each `CreateSession` call dial its own `SSHRunner`/`*ssh.Client` for that session; Epic 6.4's `RemoteHealthProber` opens a further, separate connection per remote for health checks. Neither the plan nor `research/architecture.md`/`stack.md` discusses connection reuse or multiplexing across sessions targeting the same remote. A burst of session creation against one host can produce a burst of concurrent SSH handshakes, which is exactly the shape `sshd`'s default `MaxStartups` (10:30:100) rate-limits — unauthenticated/in-progress connections beyond the threshold get dropped, which would surface as opaque connection failures on exactly the "10-20 concurrent sessions" scenario this feature is built for. — **Recommendation**: explicitly test/measure burst-creation behavior against a real or containerized `sshd` at the target concurrency, and note in the plan whether connection reuse (one `*ssh.Client` multiplexing many sessions' channels, à la `research/stack.md`'s note on `yamux`) is being deferred deliberately or simply not considered.

- [ ] **The connection-status indicator (AC5) reflects the health prober's own connection, not each session's actual data connection.** `RemoteHealthProber` (Epic 6.4) drives `RemoteConnectionState` off its own independent `SSHRunner`/`ssh.ClientConn.Wait()`, separate from the per-session `SSHRunner` each session's `TmuxSession`/`GitWorktree` actually uses (per the concern above, these are different TCP+SSH connections). The two connections can have independent liveness — e.g. the prober's low-traffic connection survives an idle-timeout that an individual session's connection doesn't, or vice versa — so the badge can show "connected" while a specific session's terminal is actually stalled, or "disconnected" while other sessions on the same remote are working fine. This undermines the literal AC5 requirement ("connection status indicator... reflects live SSH connection health") for anything more granular than "is the remote reachable at all." — **Recommendation**: either scope the indicator's claim explicitly to "remote reachability" (not per-session health) in the UI copy, or key the indicator off the union of the prober's connection and the currently-open per-session connections.

- [ ] **ADR-003 ties the approval-relay channel's liveness to the terminal-streaming connection's liveness with no reconnect story for the relay itself.** ADR-003 explicitly frames "an SSH channel drop and a terminal-stream drop share the same underlying liveness signal" as a benefit, but Epic 5.1 has no task re-establishing the `direct-streamlocal@openssh.com` relay channel after the parent `*ssh.Client` reconnects (Story 2.1.2's backoff/redial is scoped to `SSHRunner.Run`/`Start`, not to re-opening dependent channels like the relay). Nor is there any task addressing what happens to an approval request that's in flight (agent blocked on its remote-side socket read) at the exact moment the connection drops and is later re-established — is the pending request lost, does the agent's blocking read need its own retry logic, or does a fresh relay channel resume it transparently? None of this is stated. Given approvals are the mechanism blocking an autonomous agent from taking a potentially destructive action, silently losing one across a network blip is a worse failure mode than a stalled terminal. — **Recommendation**: add a story to Phase 5 explicitly covering relay re-establishment on reconnect and an end-to-end test for "connection drops with a pending approval in flight, then reconnects."

- [ ] **No explicit task implements the `SSHRunner.Start`-backed control-mode reconnection lifecycle itself.** `research/architecture.md` §(1) asserts this is "already true by construction" — that a dead `Start`-channel "just gets an error/EOF... and re-runs the same restore path against a **new** SSH session" — but this is stated as an inferred consequence of existing local-reconnect code, not backed by any story/task that actually implements "detect dead Start-channel → tear down → re-dial SSH → re-run `tmux -C attach` → resubscribe the control-mode consumer" for the remote case. Task 2.1.2b's backoff covers dial-retry, and Task 4.4.1e covers resize-on-reconnect, but the gap between "SSH connection drops mid-terminal-stream" and "a fresh `Start()` call is actually issued and rewired into `streamViaControlMode`" has no task of its own, despite being the core reliability promise of this feature (AC3/requirements.md's "network partition... dashboard should be able to reattach and recover scrollback on reconnect"). — **Recommendation**: make this an explicit story with its own acceptance criteria and integration test (kill the SSH connection mid-stream, assert the client reattaches and recovers scrollback), not an assumed consequence of Phase 1/2 work.

- [ ] **No path to use an existing SSH key — onboarding forces app-generated keys only.** Story 3.2.2 ("Per-remote keypair generation at onboarding") only covers Stapler Squad generating a fresh Ed25519 keypair per remote; there's no story or task for a user who wants to register a remote using a key they already manage (e.g. a host with centrally-managed `authorized_keys`, or a key already scoped via existing infrastructure). Requirements.md AC1's "SSH key reference" wording is ambiguous enough to allow either interpretation, but the plan silently commits to "generate-only" without calling this out as a scope decision. — **Recommendation**: either explicitly scope BYO-key import out of v1 in requirements.md/plan.md (a one-line decision), or add the import path if it's expected to be common for the target "beefier always-on Linux box" use case named in requirements.md's problem statement.

- [ ] **"Fail loudly" on headless keychain unavailability is untested for the actual failure mode `research/pitfalls.md` names.** Task 3.2.1d tests only the case where `go-keyring` *returns* an error ("no backend available"). Pitfalls.md §2 specifically warns that on a headless `systemd --user` Linux service (which is how this app already runs, per `.claude/rules/systemd-user-service.md`), Secret Service D-Bus calls "can silently fail **or block waiting on a keyring unlock prompt that never appears**" — the hang case, not the error case. Combined with the ctx-cancellation blocker above, an unlock-prompt hang on `KeyStore.GetIdentity` during session creation would wedge the request with no timeout and no loud failure. — **Recommendation**: fold this into the ctx-cancellation blocker's fix (timeout-wrap the keychain call), and add a test simulating the hang, not just the immediate-error case.

## Minors

- AC2 names a CLI entry point (`ssq --remote user@host:/path`) as an example interface, but no `ssq` session-creation CLI exists anywhere in this repo today (only `ssq-hooks`/`ssq-mux`, unrelated helper binaries), and the plan implements zero CLI touchpoints for remote targets. This is likely fine — the dashboard path fully satisfies AC2 on its own — but the CLI clause should be explicitly dropped/reworded in requirements.md rather than left as unaddressed text a future reader might mistake for a gap.
- Task 2.2.1a's `base_path` existence check (`test -d`) and Task 2.2.1b's actual `git worktree add` are two separate SSH round-trips with a small TOCTOU window between them (connection drop or directory removal in between). Low probability/impact given the reconnect/backoff work elsewhere in Phase 2, but worth a one-line note that the check is advisory, not atomic, with the real error surfacing from the `git worktree add` call itself if the race is lost.
