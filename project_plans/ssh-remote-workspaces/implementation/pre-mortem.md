# Pre-mortem: ssh-remote-workspaces
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Each `CreateSession` dials its own `*ssh.Client`, and `RemoteHealthProber` (Epic 6.4) opens yet another per remote — a burst of session creation at the stated 10-20-concurrent-session goal produces a burst of concurrent SSH handshakes that collides with sshd's default `MaxStartups` (10:30:100) unauthenticated-connection throttle. No task in Phase 2/4 implements connection reuse or multiplexing (adversarial-review.md Concern 1, still unresolved — it is a Concern, not a Blocker, so nothing in plan.md addresses it). | A user spinning up several sessions in quick succession against the same remote sees some `CreateSession` calls fail with opaque SSH dial/handshake errors instead of succeeding — worse the more sessions are created at once, which is exactly the scenario the feature is built for. | Add an explicit connection-reuse design decision to plan.md before Phase 2 implementation (one `*ssh.Client` per remote, reused across sessions and the health prober, with per-session work opened as SSH channels on that shared connection rather than a new TCP+SSH handshake each time), plus a validation.md load test that creates 15-20 sessions against a test sshd within a short window and asserts zero `MaxStartups`-related failures. | P1 |
| 2 | ADR-003 frames "approval-relay liveness = terminal-stream liveness" as a benefit, but no task re-establishes the `direct-streamlocal@openssh.com` relay channel after the parent `*ssh.Client` reconnects (Story 2.1.2's backoff is scoped to `Run`/`Start`, not to dependent channels), and no task defines what happens to an approval request the remote agent is blocked reading when the connection drops mid-request (adversarial-review.md Concern 3, unaddressed by any Phase 5 task). | An agent's turn silently stalls after a `PermissionRequest` hook fires during a transient network blip: the connection indicator later shows "connected" again, but the session makes no further progress, and the local approval UI never received (or already discarded) the request — there is no error, just silence, until the user notices the agent has been idle far longer than expected. | Add a Phase 5 story implementing relay-channel re-establishment whenever the parent `*ssh.Client` reconnects, plus an explicit "connection drops with a pending approval in flight, then reconnects" integration test — treat this as blocker-severity given it sits on the same path that gates a remote agent from taking destructive actions, not an optional concern. | P1 |
| 3 | adversarial-review.md Blocker 1's recommendation explicitly named **both** the SSH calls and the keychain read path ("Task 3.2.1d only tests the case where go-keyring *returns* an error... not the case where the call hangs") as needing ctx-bounded timeouts, because headless `systemd --user` Secret Service D-Bus calls can hang on an unlock prompt that never appears. Plan.md's remediation (Task 2.1.1f) only wraps `Dial`/`Run`/`Start` — it never touches `sshremote.KeyStore.GetIdentity` (called in Task 4.2.1c, before the SSH dial even starts) — yet the plan's task text asserts this "closes" the blocker, and the review checkbox was never re-verified against the actual task text before being trusted. This is the checkbox/plan mismatch named in the review artifacts made concrete: the self-asserted "closes Blocker N" annotations were not independently re-checked against what the remediation task actually does. | The `CreateSession` RPC for a remote target never returns — the Omnibar's spinner spins indefinitely. `journalctl --user -u stapler-squad` shows the request goroutine stuck after a "resolving identity for remote X" log line with no subsequent dial attempt or error, because execution is blocked inside `go-keyring`'s D-Bus call before `SSHRunner.Dial` (and Task 2.1.1f's timeout wrapper) is ever reached. | Extend Task 2.1.1f's ctx-bound wrapping to explicitly cover `sshremote.KeyStore.GetIdentity`'s `go-keyring` call, and extend Task 3.2.1d's test to cover the hang case (not just the immediate-error case). Separately, before implementation starts: re-run the adversarial/architecture review checklists against the actual current task text and check off each blocker only once independently confirmed resolved — don't carry forward a plan's own "closes Blocker N" claim as verified. | P1 |
| 4 | architecture-review.md Concern 4 flags that "SSH connection drops mid-terminal-stream → a fresh `Start()` is issued and rewired into `streamViaControlMode`" is asserted as "true by construction" from existing local-reconnect code, but no task actually implements or tests this specific remote-path lifecycle — Task 2.1.2b covers dial-retry and Task 4.4.1e covers resize-on-reconnect, but the gap between the two (detect dead remote `Start`-channel → re-dial → re-attach `tmux -C` → resubscribe the consumer) has no owning task. | After a laptop sleep/wake or network blip mid-session, the xterm.js view for a remote session shows a frozen/stale terminal frame that a local session would auto-recover from but this one does not — the user has to manually reload the page or recreate the session to get a working terminal back, contradicting requirements.md's "dashboard should be able to reattach and recover scrollback on reconnect." | Add an explicit story/task implementing "detect dead remote `Start`-channel → tear down → re-dial SSH → re-run `tmux -C attach` → resubscribe the control-mode consumer," with its own acceptance criteria and an integration test that kills the SSH connection mid-stream and asserts the client reattaches and recovers scrollback — don't ship it as an assumed consequence of Phase 1/2 work. | P2 |
| 5 | Task 4.2.1e/f's compensating cleanup only covers the narrow case of a *synchronous* failure during `CreateSession` itself (worktree succeeds, tmux setup fails, or the connection drops between the two — all within one request). The Unresolved Questions section explicitly defers full reconciliation-on-connect (crash, `kill -9`, manual deletion on the remote, local server restart mid-session) to a fast-follow, with **no UI surface to even discover an orphan exists** in v1. | Weeks into using the feature, remote host disk usage climbs unexplained; running `git worktree list`/`git branch` by hand on the remote shows entries with no corresponding session anywhere in the dashboard — the first the user learns of it is by manually inspecting the remote host, not from any in-app signal. | Either explicitly commit to a documented manual-cleanup runbook for v1 (so the gap is a known, communicated trade-off rather than a silent surprise), or add a minimal read-only diagnostic — "list remote worktrees with no matching local session" — short of full reconciliation, so orphans are at least discoverable inside the app rather than invisible. | P2 |

  `*ssh.Client` per remote (Task 2.1.0a `ssh_pool.go`), a Pattern Decisions row, and a
  burst-creation load test (Task 2.1.0b) asserting 15-20 concurrent session creations against
  one remote produce zero `MaxStartups`-class failures.

  `direct-streamlocal` relay channel when the pooled `*ssh.Client` reconnects, with an explicit
  decision point for in-flight-request survival and an integration test for
  "connection drops with a pending approval in flight, then reconnects."

  `sshremote.KeyStore.GetIdentity`'s `go-keyring` call (not just the SSH-side calls), and Task
  3.2.1d now tests the hang case. Re-verification of "closes Blocker N" claims against

  see updated checkboxes in those files.
