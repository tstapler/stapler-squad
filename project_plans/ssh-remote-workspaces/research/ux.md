# Research: UX — SSH Remote Workspaces

Scope: comparable-product patterns, the user's mental model of "remote," accessibility
requirements for a live connection-status indicator, graceful error handling, and
jobs-to-be-done — cross-referenced against the existing Omnibar/SessionCard UI
(`web-app/src/components/sessions/OmnibarCreationPanel.tsx`,
`web-app/src/components/sessions/SessionCard.tsx`) and the SSH stack already chosen
in `project_plans/ssh-remote-workspaces/research/stack.md` (`golang.org/x/crypto/ssh`
+ `knownhosts.New()`, no `InsecureIgnoreHostKey`).

## 1. Comparable UX patterns

| Product | Host selection at creation time | First-time credential/host-key setup | Ongoing connection-health visibility |
|---|---|---|---|
| **VS Code Remote-SSH** | Command palette → pick or type a `Host` entry resolved from `~/.ssh/config`; no in-product host registry beyond that file | **Modal dialog** (not a terminal prompt) shows host + key fingerprint on first connect, "Continue"/cancel; password/passphrase also prompted via modal, not inline form | Remote host name + connection state shown as a permanent segment in the editor's status bar (bottom-left); reconnect happens silently, failures surface as a notification toast |
| **GitHub Codespaces** | "Create codespace" picks repo/branch + machine SKU from a dropdown; no user-managed SSH — Codespaces owns the whole VM lifecycle | N/A — no user SSH keys; auth is GitHub OAuth, host trust is implicit (GitHub-owned infra) | Codespaces list view shows state per codespace (Starting/Available/Stopped) with auto-refresh for transitional states; connection errors are flagged as "transitional — wait and retry" |
| **Coder** | Workspace created from a **template** with typed `coder_parameter` fields (region, CPU/RAM, etc.), increasingly via "Dynamic Parameters" (conditional fields, presets) rather than free-text host entry | Coder Desktop / CLI extension handles auth via the platform's own identity, not raw SSH keys per host; admin pre-provisions the template | Workspace status filter values are literally `connecting` / `connected` / `timeout` / `disconnected`; DERP-relay round-trip latency (ms) is surfaced directly in the dashboard, not just a binary up/down |
| **JetBrains Gateway** | "New Connection" wizard: Host/Port/Username fields or a saved SSH Configuration picked from a list | Auth type is an explicit form field (Password vs. Key pair); the wizard is fully synchronous/blocking — user watches progress inline before the IDE backend even starts | Gateway shows IDE-backend provisioning progress as a linear step list during connect; once connected, status lives in the thin-client titlebar |
| **Emdash** (competitor named in requirements) | **Reusable SSH connection profiles** created once under Settings → Connections (name, Host, Port, Username); a Remote Project then *references* a saved connection instead of re-entering credentials — this is the closest precedent to the requirement's "configured once in settings, reused across session creations" | Three auth methods (Password / SSH Key / Agent) with secrets in **encrypted app storage**, not plaintext; can also import an existing `~/.ssh/config` `Host` alias and lock the resolved fields | Changelog evidence of iterating on this: v1.1.37 shipped "Duplicate SSH connection errors show clearer messages"; v1.1.36 shipped "SSH terminals apply write backpressure on slow connections" and orphaned remote-tmux cleanup on archive; "sessions reconnect on drops" is a stated feature, not just aspirational |
| **cmux** (competitor named in requirements) | CLI/deep-link driven: `cmux ssh user@remote` creates a workspace directly from a host string, reading `~/.ssh/config` for aliases; **no separate "add remote" step** — the connect action *is* the creation action | `--ssh-option`/`host-key-policy` flag (`accept-new`/`ask`/`strict`/`yes`) is explicit and user-settable; deep links (`cmux://ssh?host=...`) show a **confirmation prompt with a command preview** before connecting, specifically because a link can't carry identity files or other sensitive options — the user must explicitly trust the target | `mosh` transport option specifically for surviving Wi-Fi/VPN/sleep network changes; stated design principle: "SSH remains the management lane... Mosh carries only the terminal PTY" — i.e. connection-quality and session-liveness are treated as separate concerns from the interactive stream itself |

**What works well and why:**

- **Emdash's "saved connection, referenced per session" model is the direct precedent for this feature's proposed `remotes` config** — it solves exactly the stated requirement (credentials configured once, reused across creations) and is proven in a tool with the same target use case (agent sessions in git worktrees). Adopt its shape: a named profile with host/port/user/key, selected by name at creation time, not re-entered.
- **VS Code's modal-not-terminal host-key dialog** is the right answer to requirement (4)'s "how does host-key verification work from a background Go server process" — the verification decision belongs in the web UI as an explicit confirm/cancel step, never assumed away with `StrictHostKeyChecking=no` (the stack research already rules this out by mandating `knownhosts.New()`).
- **Coder's granular status values (connecting/connected/timeout/disconnected) plus a numeric latency figure** is a stronger model than a binary up/down badge — it gives the user enough information to distinguish "slow" from "broken" without opening the session.
- **cmux's explicit host-key-policy + pre-connect confirmation for anything not fully interactive** (deep links) is the closest analog to a headless dashboard triggering a connection on the user's behalf — confirms that even a "trust always" fast path should still be an explicit, visible choice, not a silent default.

Sources: [VS Code Remote-SSH docs](https://code.visualstudio.com/docs/remote/ssh), [Remote-SSH fingerprint issue #1525](https://github.com/microsoft/vscode-remote-release/issues/1525), [GitHub Codespaces creation docs](https://docs.github.com/codespaces/developing-in-codespaces/creating-a-codespace), [Codespaces troubleshooting](https://docs.github.com/en/codespaces/troubleshooting/troubleshooting-your-connection-to-github-codespaces), [Coder SSH/networking](https://deepwiki.com/coder/coder/5.3-ssh-and-networking-commands), [Coder Dynamic Parameters](https://coder.com/docs/admin/templates/extending-templates/dynamic-parameters), [Coder workspace presets discussion](https://github.com/coder/coder/discussions/16304), [JetBrains Gateway SSH connection docs](https://www.jetbrains.com/help/idea/remote-development-a.html), [Emdash SSH Connections docs](https://emdash.sh/docs/remote-development/ssh-connections), [Emdash changelog (v1.1.36/37)](https://emdash.sh/), [cmux SSH docs](https://cmux.com/docs/ssh), [cmux FAQ](https://cmux.com/).

## 2. User mental model: transparent vs. explicit

**Recommendation: lean explicit, but only at the edges — treat "remote" as a location attribute layered onto the existing session types, not a parallel universe.**

Reasoning:

- The existing `SESSION_TYPES` radio group (`new_worktree`, `directory`, `existing_worktree`, `one_off`, `new_project`) already encodes a **git-workflow dimension** (isolated branch vs. existing folder vs. scratch space). "Remote" is an orthogonal dimension — *where the process runs*, not *how the git workspace is structured*. A user picking `new_worktree` on a remote host still wants an isolated branch/worktree; the git semantics don't change.
- Precisely because of that, the repo's own conventions already have the right pattern for this: `.claude/rules/session-creation-registry.md` documents the **"autonomous mode" exception** — a mode that "reuses `SESSION_TYPE_DIRECTORY` and uses a separate `bool autonomous_mode` flag instead of a new enum value... when the backend session type is shared but behavior is driven by additional request parameters." Remote should follow the same shape: **not a 6th radio option**, but an orthogonal selector (a "Remote host" dropdown, defaulting to "This machine") that composes with whichever `sessionType` is already selected — exactly like the existing `autonomousMode` checkbox composes with session type in `OmnibarCreationPanel.tsx` (`sessionType !== "one_off"` → show the Autonomous mode checkbox, line ~464).
- That said, the model can't be fully transparent ("happens to run elsewhere, behaves identically") because it verifiably doesn't: connection state is a new failure mode with no local equivalent, latency changes terminal responsiveness, and the requirements explicitly call for a host badge on session cards and a remote-host filter — both are UI concessions to the fact that remote sessions **are** a distinct thing the user needs to reason about (which host, is it up). A purely transparent model would omit those affordances entirely.
- **Concrete recommendation**: default the Omnibar to local (today's behavior, zero new decisions for the common case), surface remote as an explicit opt-in selector that appears once ≥1 remote is configured in Settings, and once selected, the rest of the creation form (session type radio, branch, working dir) stays unchanged — only the target host is different. Post-creation, be explicit: host badge on the card (mirroring the existing `externalBadge` pattern at `SessionCard.tsx:459-469`, which already shows a similarly-scoped "where did this come from" badge for external/mux sessions), and a distinct connection-status affordance (see §3) that a local session never shows at all — don't render a "Connected" badge on local sessions just for consistency, since it's meaningless there and would dilute the signal for sessions where it matters.

## 3. Accessibility: the connection-status indicator

The codebase already has two directly-relevant precedents to extend rather than invent from scratch:

1. **Status badges never rely on color alone.** Every existing status affordance in `SessionCard.tsx` pairs a `role="img"` + `aria-label` with visible text — e.g. the session status badge (`getStatusText`, lines 203–224, rendered with `aria-label={`Session status: ${getStatusText(...)}`}`), the rate-limit badge (line 524–531), the memory badge (line 549–569). The connection-status indicator must follow the identical pattern: icon/color **and** a text label (e.g. "Connected" / "Reconnecting…" / "Disconnected"), never an icon or dot alone. Do not introduce a new "just a colored dot" affordance — it would be the first one in this component.
2. **A live region for state transitions already exists for an analogous case.** `SessionCard.tsx:792` has a persistent `role="status" aria-live="polite"` region dedicated to creation-progress text, with the comment "always in DOM so NVDA announces on content change." The connection-status transition (`connected → reconnecting → disconnected` or back) is the same shape of problem — a state change a screen-reader user needs announced without requiring focus to be on the card — and should reuse this exact pattern: a persistent, empty-when-idle `aria-live` region per session card (or one shared region if status changes are batched/global), updated with a short human sentence ("Connection to prod-box lost, reconnecting…") rather than just the badge text alone, since the announcement needs to carry the *why*, not just the *new state*.

Specific decisions for this feature:

- **Politeness level**: `aria-live="polite"` (not `assertive`) for connected→reconnecting, matching the existing creation-progress region — this is expected, self-healing behavior, not an alarm. Reserve `assertive`/`role="alert"` for a *terminal* failure state the user must act on (e.g. "Disconnected — SSH auth failed, check your key in Settings"), consistent with how `inlineEditError` already uses `role="alert"` for a save failure at `SessionCard.tsx:441`.
- **Icon + label pairing, not color alone**: reuse the `status`/`statusRunning`/`statusReady`/etc. class family in `SessionCard.css.ts` — add `statusConnected` / `statusReconnecting` / `statusDisconnected` variants following the same naming and always render `aria-label` text alongside.
- **Don't overload the existing session-status badge.** Connection state (is the SSH link up) and session state (is the agent process running/paused/needs-approval) are different axes — a session can be `PAUSED` (session state) while its remote connection is `connected` (transport state), or `ACTIVE` while `reconnecting`. Render connection status as its own badge distinct from `getStatusText`'s output, not merged into it, or a screen-reader user loses the ability to distinguish "the agent needs my input" from "the network is flaky."
- **Tooltip pattern**: the existing `Tooltip` component (used for pause-reason and stopped-reason context, `SessionCard.tsx:492`, `:506`) is the right vehicle for the connection badge's detail text (last-connected timestamp, specific error) — keep the badge label terse ("Reconnecting…") and put detail in the tooltip, matching how `pauseReason`/`creationProgress` already work.

Sources: [WCAG 4.1.3 Status Messages](https://dockaccess.org/documentation/wcag-success-criteria/wcag413/), [WCAG color-alone status indicator guidance](https://www.accessibility.chat/articles/when-color-coding-fails-why-status-indicators-need-more-than-pretty-colors), [Accessible loading/error states](https://accessibility.build/blog/accessible-loading-empty-error-states), plus the in-repo precedents cited inline above (`web-app/src/components/sessions/SessionCard.tsx`).

## 4. Error states requiring graceful handling

| Scenario | Recommended handling | Precedent in this codebase or in comparables |
|---|---|---|
| **Remote unreachable during session creation** | Disable/keep the Create button active but attempt connection async with a timeout; on failure, show an **inline form error** (not a toast — the user is still in the creation flow and needs to change something, e.g. pick a different remote or fix the config), matching the existing `error` prop pattern already threaded through `OmnibarCreationPanel` (`error: string | null`, rendered via `errorClass` at the bottom of the form, `OmnibarCreationPanel.tsx:816-817`). Do not let creation silently hang — Codespaces' own guidance ("transitional errors — wait and retry") implies a bounded retry/timeout, not an indefinite spinner. |
| **SSH auth failure (wrong key/passphrase)** | Surface at the point of **remote configuration in Settings**, not deep in session creation, since credentials are configured once and reused (per requirement) — validate the connection when the user saves a `remotes` entry (an explicit "Test connection" affordance, as several comparables effectively require by testing on first connect) so the failure is caught before it can block N future session creations. If it still occurs at creation time (e.g. key rotated remotely), same inline-form-error treatment as above, with the message naming the remote and the specific failure ("Auth failed for prod-box — check the SSH key in Settings → Remotes") so the user knows exactly where to go fix it, not just that something broke. |
| **Mid-session disconnect** | The terminal pane should show a **distinct, in-place state** — not revert to a blank/broken terminal and not silently pretend the session is fine. Follow Emdash's stated behavior ("sessions reconnect on drops") and cmux's mosh-transport rationale (management/control lane separate from the interactive PTY lane): keep the last-rendered terminal frame visible (don't clear scrollback), overlay a "Reconnecting…" state consistent with §3's badge, and only fall back to a hard "Disconnected" empty state after a bounded number of reconnect attempts. This must **not** be conflated with the session being STOPPED/PAUSED — those are session-lifecycle states with their own existing badges (`statusPaused`, `statusPausedDistinct`) and mixing "network is down" into that vocabulary would misrepresent agent state to a user glancing at the card. |
| **First-time host key verification (no interactive terminal)** | Per `stack.md`, the backend uses `knownhosts.New()` (never `InsecureIgnoreHostKey`), so an unknown host key is a real, expected first-connect event, not a rare edge case to special-case away. Modeled on VS Code's modal (not terminal) and cmux's explicit `host-key-policy` + pre-connect confirmation: when a remote's host key isn't yet in the known-hosts store, block the connection attempt and show a **confirmation dialog in the web UI** — host, port, and the key fingerprint (SHA256, matching what OpenSSH/VS Code display), with explicit "Trust and connect" / "Cancel" actions. This must happen at **remote configuration time in Settings** (first "Test connection"), not silently inside a session-creation request, both because the backend is a headless process with no other channel to ask the question, and because trusting a host key is a security decision the user should make once per remote, not once per session. |

## 5. Jobs-to-be-done

- **Functional — offload compute.** The core job: run an agent session on a machine with more CPU/RAM/GPU, or persistent uptime, than the local dev machine, without changing the workflow the user already has (same Omnibar, same session card, same terminal). Success criteria per the stack research: remote worktree creation and PTY streaming should be behaviorally indistinguishable from local except for the host badge and connection status — i.e. the *session-type* semantics (worktree isolation, branch handling) are unaffected by *where* it runs, reinforcing the §2 "orthogonal dimension" recommendation.
- **Emotional — confidence the session won't silently die or lose work while unattended.** This is the dominant emotional job given the requirements' own framing (a connection-status indicator was explicitly requested, and Coder/Emdash/cmux all independently converged on "reconnect on drop" as a named feature, not an afterthought). The design must actively counter the failure mode where a remote session dies quietly and the user only discovers it hours later expecting completed work — this is why §3 mandates a persistent, screen-reader-announced status transition rather than a badge the user has to notice visually, and why §4 requires the terminal pane to distinguish "reconnecting, hang on" from "disconnected, look at this now." A remote session that goes stuck/dead should be at least as visible as the existing `autonomousOutcome === "stuck"` badge (`SessionCard.tsx:604-615`) already is for autonomous-mode sessions — that pattern (a persistent, high-contrast, explicitly-labeled "needs attention" badge) is the right bar to match for "your remote session dropped and needs you."
- **Social — mostly N/A for the current solo-user scope**, but the requirements note a secondary team-sharing scenario. If/when that materializes, the per-remote `ssh_key` credential model already implies per-user credentials (each teammate configures their own key against a shared host), which naturally supports multi-user access to the same remote without a shared-secret anti-pattern — worth confirming this assumption holds if team-sharing is scoped into a later phase, but it does not change anything about the UI proposed here since credentials remain local-per-user in Settings either way.
