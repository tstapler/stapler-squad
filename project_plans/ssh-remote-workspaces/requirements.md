# Requirements: ssh-remote-workspaces

**Date**: 2026-08-06
**Type**: feature addition (new session execution target)
**Complexity**: 4 — system-level (new execution backend, credential storage, network transport, UI surface); Large appetite
**Source**: Backlog item `3461c8dd-a3b5-4543-8055-204c183ae396`, migrated from
`TylerStaplerAtFanatics/stapler-squad#48` (created 2026-04-09)

## Problem Statement

Stapler Squad only runs agent sessions on the machine the server process itself
runs on: worktrees are created on the local filesystem, tmux sessions are
created on the local tmux server, and terminal streaming reads local PTY
scrollback. This caps total concurrent session throughput at whatever a single
machine (typically a laptop) can sustain — practically ~4 concurrent
Claude-Code-class sessions on a Mac before contention becomes noticeable. It
also means there is no way to point the dashboard at a beefier always-on Linux
box, or to share one execution host across a team, while continuing to drive
everything from one local dashboard.

## Baseline

Today, `SessionType` (`session/instance.go`) supports `directory`,
`new_worktree`, `existing_worktree` — all resolved against a local filesystem
path and a local tmux server (`session/tmux/`). Worktrees live under
`~/.stapler-squad/worktrees/`; there is no host/target concept anywhere in
`config.json`, the proto definitions, or the Go session lifecycle code, and no
notion of a non-local session at all.

## Users / Consumers

Solo user (Tyler) operating the stapler-squad dashboard, wanting to offload
compute-heavy agent sessions to a dedicated remote Linux host while keeping
the existing local dashboard as the single pane of glass. Secondary
(explicitly named in the source issue, not a current requirement): small-team
scenarios where multiple people share one remote execution host.

## Success Metrics

- A session can be created with a remote host target (`user@host:/path`) and
  the resulting worktree, tmux session, and agent process all run on that
  remote host, not the local machine.
- Terminal output from the remote session streams into the local xterm.js
  view with the same fidelity (delta protocol, resize, scrollback) as a local
  session — the user cannot tell from the terminal experience alone that the
  session is remote, aside from a host badge.
- Approval requests generated by a remote-running agent reach the local
  dashboard and can be answered from it, round-tripping back to unblock the
  remote agent.
- SSH credentials (key path, host) are configured once per remote and reused
  for every session created against that remote, without re-entering
  credentials per session.
- A session card visibly identifies which host it is running on, and remote
  connection health (connected / reconnecting / disconnected) is visible
  without opening the session.

## Appetite

Large (multi-week). This introduces a new transport layer (SSH), a new
credential-storage subsystem, and touches the session-creation registry (7
touchpoints per `.claude/rules/session-creation-registry.md`), tmux
management, and the terminal streaming pipeline. Not a single-PR change —
expect a phased rollout (see plan.md for phase breakdown).

## Constraints

- Must integrate with the existing session-creation mode registry (7
  touchpoints: proto enum, proto request fields, Go handler, `SessionType`
  constants, `Omnibar.tsx`, `OmnibarCreationPanel.tsx`, `OmnibarContext.tsx` +
  `useSessionService.ts`) — see `.claude/rules/session-creation-registry.md`.
  Remote is a new *target*, not a new *mode*; needs a design decision on
  whether it's an orthogonal dimension (any existing mode + a remote target)
  or a new `SessionType` value.
- New/changed RPCs and frontend features must be reflected in
  `docs/registry/features/` (`make registry-generate`), per
  `.claude/rules/feature-registry.md`.
- All new/modified CSS must use vanilla-extract (`.css.ts`), per
  `.claude/rules/css-architecture.md`.
- Prefer `github.com/go-git/go-git/v5` over shelling out for git operations
  where it can do the job (`.claude/rules/prefer-go-git-over-subshells.md`) —
  does not apply to the SSH transport itself, which has no go-git analog.
- Must work on both mobile and desktop dashboard views (existing project-wide
  UX requirement).
- Per-feature e2e test coverage required for any new UI surface (remote tab,
  host badge, connection status indicator), per
  `.claude/rules/feature-testing-registry.md` where applicable.
- Credential storage must not put private key material or passphrases in
  `config.json` in plaintext — the issue's proposed design says "OS keychain,"
  which needs a concrete Go library decision (see research.md).

## Non-functional Requirements

- **Security**: SSH private keys / passphrases are the primary new secret
  class this feature introduces. No hardcoded credentials, no secrets in
  logs, no secrets in `config.json` in plaintext (trust boundary: local
  dashboard ↔ remote host over network).
- **Reliability**: network partition between local dashboard and remote host
  must degrade gracefully (reconnecting indicator, not data loss) — an agent
  running on the remote host should keep making progress inside its remote
  tmux session even while the local dashboard is disconnected, and the
  dashboard should be able to reattach and recover scrollback on reconnect.
- **Performance**: terminal streaming latency over SSH must remain usable
  interactively; no hard SLO specified by the source issue.
- **Scalability**: explicitly the point of the feature — one remote host
  should support 10-20 concurrent sessions per the issue's stated goal,
  significantly more than local-only throughput.

## Out of Scope (this triage)

- Full team/multi-user access control to a shared remote host (issue
  mentions it as a future scenario, not a current acceptance criterion).
- Non-SSH remote transports (containers, cloud VMs via provider APIs).
- Migrating an already-running local session to a remote host or vice versa.
- A `ssq --remote user@host:/path` CLI entry point. The source issue's proposed
  interface names this, but no `ssq` session-creation CLI exists anywhere in
  this repo today (only `ssq-hooks`/`ssq-mux`, unrelated helper binaries) and
  the dashboard path fully satisfies the underlying need. Explicitly deferred
  to a fast-follow, not v1 scope (validation.md's cross-artifact consistency
  check flagged this as an unimplemented AC2 clause; resolved here by
  descoping rather than adding CLI stories to plan.md).

## Acceptance Criteria (draft, refined further in plan.md / validation.md)

1. A remote host can be registered in configuration with a name, host
   (`user@host`), base path, and SSH key reference, without secrets stored in
   plaintext in `config.json`. Registration verifies the remote's SSH host key
   via trust-on-first-use, with an explicit user confirmation step before the
   remote is saved (anchors Epic 3.3's `KnownHostsStore`/TOFU trust-dialog
   scope, flagged as unanchored by validation.md's cross-artifact consistency
   check).
2. Session creation supports a remote target — selected by referencing a
   pre-registered `RemoteConfig` by name (`remote_name`), not by typing a raw
   `user@host:/path` string per session — via a "Run on" selector in the
   dashboard's session creation flow, composing with any existing session
   type. This results in a worktree and tmux session created on the remote
   host over
   SSH, not locally.
3. Terminal output for a remote session streams to the local xterm.js view
   using the existing delta-update protocol, indistinguishable in behavior
   from a local session's terminal.
4. Approval requests raised by a remote session reach the local dashboard's
   existing approval UI and the response is delivered back to unblock the
   remote agent process.
5. Session cards display a host badge for remote sessions, and a connection
   status indicator (connected / reconnecting / disconnected) reflects live
   SSH connection health.
6. Remote-related registries are kept in sync per repo convention: session
   creation registry (7 touchpoints), feature registry
   (`docs/registry/features/`), and e2e test coverage for new UI surfaces.
