# Pre-mortem: session-list-density
**Date**: 2026-09-24

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The plan calibrates every truncation budget and breakpoint against a "fixed ~280px sidebar" that isn't the only real layout — `SessionList` also renders as a leaf inside the user-resizable pane-split cockpit layout (`web-app/src/components/pane/PaneSplitRenderer.tsx:379-380`, `pane.viewKind === "session-list"`, resized via `ResizeHandle`/`RESIZE_PANE` at `:182-188`, `:49`), so real rendered width is a continuous, user-dragged value, not a binary "280px vs. collapsed-narrow" choice. | A user drags a session-list cockpit pane to ~400-600px and sees paths still hash-collapsed to `…` with acres of unused whitespace (budget too conservative), or drags it to ~220-260px and gets awkward multi-line wrapping the 200px `NARROW` breakpoint never kicks in to soften (budget too aggressive for that width). | Add an explicit note (and ideally a task) confirming `ROW_PATH_MAX_LEN`/`CARD_PATH_MAX_LEN` are sane across the pane-split cockpit's actual resizable range, not only the fixed-280px `app/backlog` layout — e.g. verify visually at 200px, 280px, 450px, 650px in *both* mounting contexts, or (longer-term) drive the budget from a coarse container-query-triggered class rather than one constant used everywhere. | P1 |
| 2 | `HEX_HASH_RE = /^[0-9a-f]{7,40}$/i` (`plan.md:141`) matches any 7-40 character string using only `0-9a-f` — since decimal digits `0-9` are a strict subset of hex digits, a purely numeric segment (a date stamp `20260924`, a ticket number, a PID, a timestamp) of 7+ digits satisfies it too, and gets silently collapsed to `…` as if it were a hash. No fixture in Task 1.1.1c exercises an all-numeric segment. | A session/worktree named with a date or ticket-number scheme (e.g. `backlog-20260924`, `PROJ-8675309`) loses that segment to `…` in the row/card — exactly the "truncation hides information the user needed" failure the whole feature exists to fix, just for a different segment shape than the ones tested. | Add a unit test asserting a purely-decimal 7+ digit segment is intentionally classified per whatever rule is chosen — either explicitly exempt pure-decimal runs from `HEX_HASH_RE` (require at least one `a-f` letter to count as "hex-looking"), or accept the collapse but say so; either way, pin the behavior with a fixture so it isn't discovered by the user first. | P2 |
| 3 | Replacing 38px fixed single-line ellipsis rows with wrap-to-multiple-lines (name wrap + path wrap + optional failure-message line + a newly-added hardcoded `elapsed` second line, Task 1.2.2c) roughly doubles-to-quadruples typical row height. No success metric or acceptance criterion measures rows-visible-per-viewport, even though requirements.md's own Baseline describes the real workload as "dozens" of sessions and the feature is literally named "density." | A month in, the user notices they now see ~5-8 sessions per scroll-page instead of ~15-20, and has to scroll far more to scan the list — the original "can't tell sessions apart at a glance" complaint is replaced by a "can't see enough sessions at a glance" complaint. | Add a success metric or manual-check task that counts visible rows at the sidebar's default height/width before and after the change, and treat a large drop as a real regression to weigh against the legibility win — e.g. consider whether the `elapsed` line and failure-message line can share a line with the path on rows that don't wrap, rather than every row unconditionally growing. | P1 |
| 4 | `estimateSize` is bumped from a uniform `50`→`64` (Task 2.1.3a) as a single scalar "typical" guess, but post-change row height is now a combinatorial function of 4 independent optional line additions (wrapped name: 1-3 lines, wrapped path: 1-2 lines, failure-message line: 0-1, elapsed second line: 0-1) — a far higher-variance distribution than the old fixed-38px rows. Validation is one qualitative manual scroll check (Task 2.1.3b) at one point in time, with no automated jank threshold. | Scrolling through a list containing a cluster of long-path or failed sessions shows visible row-position jump/overlap as `measureElement` corrects the virtualizer's guess — worse than before, since variance (not just the mean) is what drives virtualizer jank, and the mean-only retune doesn't address that. | Either measure the actual distribution of rendered row heights across a real session list (not just eyeball one scroll) and pick `estimateSize` from that, or accept the jank risk explicitly and add a lightweight automated check (e.g. a test asserting `measureElement`-corrected heights stay within some bound of the estimate for a fixture list spanning the combinatorial cases) so a future line addition doesn't silently widen the gap further. | P2 |
| 5 | The container-query "no horizontal scroll / no clipping from 200-400px" acceptance criteria (Story 2.1.2, plan.md:307-313) are verified only via "inspected in devtools" / one manual pass through the dev instance — no Playwright test sweeps container width and asserts `scrollWidth <= clientWidth`. Epic 4.1's e2e audit only checks for *existing* locator breakage, not new width-based regressions. | Some future PR (a new badge, a longer default label, an extra icon) reintroduces clipping or a horizontal scrollbar at narrow widths, and nothing in CI flags it — it's noticed only when someone happens to look at a narrow pane or mobile view. | Add one automated Playwright test that renders `SessionRow`/`SessionCard` at 200px, 280px, and 400px container widths and asserts no horizontal overflow, so this AC has a durable regression gate instead of a one-time manual check. | P2 |

## Summary

5 failure modes found: 2 P1, 3 P2, 0 P3.

Top failure mode: the plan's truncation budgets and "genuinely narrower than the fixed ~280px default" breakpoint reasoning (already re-derived twice during adversarial review) are calibrated against only one of `SessionList`'s two real mounting contexts — it also renders as a leaf in the user-resizable pane-split cockpit layout (`PaneSplitRenderer.tsx`), where width is continuous and user-controlled, not binary; nothing in the plan's verification tasks checks that context.
