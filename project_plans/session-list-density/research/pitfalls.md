# Research: Known Pitfalls — session-list-density

## 1. Performance: virtualization and dynamic measurement

**Both surfaces already virtualize with `@tanstack/react-virtual` (`^3.13.25`), and already do dynamic measurement — this is not a greenfield risk.**

- `SessionList.tsx:643-648` (`rowVirtualizer`) and `BoardColumn.tsx:48-53` (`virtualizer`) both call `useVirtualizer` with `estimateSize` (a *guess*, `50` for rows / `ESTIMATED_CARD_HEIGHT` for cards) and `measureElement: (el) => el.getBoundingClientRect().height`, wired to each row/card via `ref={rowVirtualizer.measureElement}` (`SessionList.tsx:1190`, `BoardColumn.tsx:91`). tanstack-virtual attaches a `ResizeObserver` to any element handed a `measureElement` ref, so **wrapping text that changes an element's real height is already the supported path** — the library re-measures and repositions subsequent items automatically. `BoardColumn.tsx:22`'s own comment confirms this was deliberate: "measureElement reports real sizes — SessionCard's actual height varies with content."
- The actual risk is `estimateSize` drifting further from reality once wrapping is added. A bad estimate doesn't break correctness (measureElement corrects it after mount) but causes a visible **layout jump on first render/fast-scroll** — the scrollbar thumb/track jumps as newly-mounted items get remeasured. Recompute `estimateSize` (or move to a component-specific default per density mode) once the new wrapped-row baseline height is known, rather than leaving the old single-line `50`/`ESTIMATED_CARD_HEIGHT` constants in place.
- **ResizeObserver gotchas to guard against in the new CSS**, since the wiring already exists and any layout change lands directly on an observed element:
  - **Loop warnings**: a `ResizeObserver loop completed with undelivered notifications` fires if the observed element's own resize handler feeds back into that element's size (e.g. a `useEffect` that sets inline `width`/`height` state from the observed box). Container queries and `line-clamp` avoid this because they're pure CSS — no JS feedback loop — but any *new* JS-driven "measure and set state" logic (e.g. for the smart middle-truncation, if implemented by measuring text width in JS rather than CSS) must not write back a style that changes the observed box's size.
  - **Layout thrashing**: reading `getBoundingClientRect()` (what `measureElement` already does) forces a synchronous layout recalc. This is fine at virtualizer-scroll cadence (already proven in production here) but would become a problem if the smart-truncation logic *also* measures DOM nodes per row on every render/scroll tick outside the virtualizer's own batched remeasure — prefer a CSS-only truncation approach (`line-clamp`, `text-overflow`, container queries) over per-row JS measurement to avoid adding a second measurement pass alongside the virtualizer's.
- `overscan: 8` (rows) / `4` (cards) — variable, taller rows raise the pixel range those overscans cover somewhat, but this is a tuning knob, not a correctness risk.

## 2. CSS: container queries and `line-clamp`

**Container queries are already in production use in this codebase with vanilla-extract — no plugin, no workaround needed.** `FilesTab.css.ts:9-10` sets `containerType: "inline-size"` / `containerName: "filesTab"` as plain style properties, and `FilesTab.css.ts:24-30` uses a raw `"@container"` key inside `style()` (`vanilla-extract/css`'s `style()` accepts arbitrary nested at-rules by string key — it doesn't special-case `@container`, so it needs no library version bump or plugin). This directly contradicts the requirements doc's stated risk ("no existing usage confirmed") — reuse `FilesTab.css.ts`'s pattern (`containerType`/`containerName` + `"@container": { "name (max-width: Npx)": {...} }`) rather than researching from scratch.

- **Ancestor `overflow: hidden` interaction**: `containerType: inline-size` on an element makes *that* element a containment context (also implicitly `contain: layout style`), which is generally fine, but the virtualized list/column wrappers already use `overflow: hidden`/`overflow: auto` for scroll clipping. If the container-query container is set on the *scrolling* virtualizer wrapper itself (rather than on the row/card content, as `FilesTab.css.ts` does on an inner `container` div), a `contain: size` or forced containment can interact badly with the virtualizer's absolute-positioned item transforms. Follow `FilesTab.css.ts`'s existing pattern: put `containerType` on the row/card's own root, not on `SessionList`'s/`BoardColumn`'s scroll viewport.
- **Browser support**: Container queries (`@container`, size queries) have been supported in all evergreen browsers since ~2023 (Chrome 105+, Safari 16+, Firefox 110+) — not a realistic compatibility risk for a project with no documented legacy-browser requirement. Style-queries (`@container style(...)`) are far newer/less supported — avoid those specifically if considered.
- **`-webkit-line-clamp`**: still a `-webkit-` prefixed *non-standard* property, but has near-universal support (all major engines, including Firefox since v68) — practically safe to use despite the prefix. Real gotchas:
  - It only works on the element itself when that element is (or is made) a `-webkit-box`/`box-orient: vertical` — applying it to a `display: grid`/`flex` child directly does nothing; needs its own wrapper `span`/`div` with `display: -webkit-box` (conflicts with the row's `display: grid` layout — the clamped text needs to be an isolated child, not the grid cell itself).
  - Interacts with dynamic content height unpredictably when combined with `measureElement`-based virtualization: line-clamp fixes the *rendered* height at N lines regardless of actual text length, so it doesn't itself create height variability — it's `line-clamp: 2-3` name/path *without* clamping (full wrap) that produces the variable heights this feature wants. If both wrapping (unclamped) and clamping (capped) are used in different columns of the same row, the row's height is the max of its children — verify which fields are meant to wrap vs. clamp before implementing, since mixing them changes the row-height calculation the virtualizer measures.
  - No JS truncation-detection API (no reliable "is this element actually clamped" signal) — if an accessible label needs to differ when clamped vs. not, that has to be computed from the *pre-truncation* string length/heuristic, not observed from the clamped DOM.

## 3. Accessibility: smart truncation and tooltip-only data

- **Smart middle-truncation and accessible name drift**: The repo already has a working pattern for this — `SessionRow.tsx:339` renders `<span className={nameStyle} title={displayName}>` (full name in `title`) and `SessionRow.tsx:306`'s row-level `aria-label` interpolates `abbreviatePath(session.existingDir)` for the path (a *different*, abbreviated string, per `aria-label={... path: ${abbreviatePath(session.existingDir)} ...}`). This means the row's accessible name **already** uses an abbreviated path today, not the full path — so "smart" middle-truncation must decide whether the new truncation function should (a) replace `abbreviatePath` entirely as the abbreviation used in both the visual label and the `aria-label`, keeping them in sync structurally by construction (single function, two call sites), or (b) diverge, in which case screen-reader users get a *different* abbreviated path than sighted users, which is the actual failure mode the requirements doc's risk describes. Safest path: make the new middle-truncation function the single source powering both the visible text and the `aria-label`/`title`, exactly as `abbreviatePath` already is for the row-level label — don't introduce a second, independent truncation function for the visual layer only.
- **Tooltip-only data (agent/memory columns) failing keyboard/touch users**: confirmed real risk. `SessionRow.tsx:452-455` (agent) and `SessionRow.tsx:503-508` (memory) currently render *both* a `title` (hover tooltip, pointer-only) *and* an `aria-label` on a `<span>` that has no button/interactive role and is not in the tab sequence. A sighted mouse user gets the hover tooltip; a screen-reader user in "browse" mode may encounter the `aria-label` via linear traversal; but a **keyboard-only sighted user** (not using a screen reader, just avoiding the mouse, or with a screen reader in "app"/focus mode) gets *neither* — the `title` attribute never surfaces without hover, and there's no focusable element to trigger it. If the redesign moves agent/memory fully into a "Columns picker / tooltip only" surface without also adding a focusable trigger (e.g. a `tabIndex={0}` + `onFocus`-shown tooltip, or exposing it in the existing `SessionActionsOverflow`/detail-drawer menu which is already keyboard-reachable), this makes the data *less* accessible than the current default-visible column, not just less visible — it should land in a genuinely keyboard-operable disclosure (button/menu item), not a bare `title` attribute, to avoid a straight accessibility regression.
- Row-level `aria-label` (`SessionRow.tsx:306`) already concatenates several fields into one string (status, program, path, "context: lost"). If agent/memory move off the default grid, decide explicitly whether they should be *added* to this concatenated string (keeps them screen-reader-reachable with zero extra interaction cost) — cheaper and more robust than inventing a new tooltip/focus mechanism, and consistent with how the existing code already surfaces non-visible-by-default context.

## 4. Repo-specific regression risks

**Duplication gates**: `web-app/.jscpd.json` (`minLines: 20`, `minTokens: 200`, `threshold: 0.14`) is the only duplication gate that applies to `web-app/` — the Go `dupl`/gocognit/funlen/revive gates in `.golangci.yml` are Go-only and irrelevant here. jscpd has **no diff-scoping** (`--new-from-rev` is a `dupl`/Go-lint-only feature per this repo's CLAUDE.md) — it gates on an absolute repo-wide percentage, so *any* newly duplicated 20+-line/200+-token block anywhere in `web-app/`, not just in touched files, can trip it. Given `SessionRow.tsx` and `SessionCard.tsx`/`BoardCard.tsx` already implement conceptually similar truncation/column-visibility logic independently (see `visibleColumns.includes(...)` gating in `SessionRow.tsx:450`/`501` and its likely counterpart in `SessionCard.tsx`), copy-pasting a new ~20+-line smart-truncation function or a new container-query narrow-layout block into both files verbatim is a real, concrete risk of tripping the 0.14% threshold — the CLAUDE.md's own baseline note ("Most of the baseline is `jest.mock(...)` ... irreducible") implies the ratchet is currently tight around existing debt, not slack for new duplication. Mitigation: extract the truncation function (and any shared narrow-layout CSS via a shared `.css.ts` recipe/mixin) into a single shared module (e.g. `web-app/src/lib/` or a shared `sessions/shared*.css.ts`) used by both `SessionRow.tsx` and `SessionCard.tsx`/`BoardCard.tsx`, rather than writing it twice.

**Playwright locator risk**: grepped `tests/e2e/` for `SessionRow`/`SessionCard`/session-list references — 30+ spec files touch session list/card content, but nearly all interact via `data-testid` (`session-row`, `session-card`, `session-row-checkbox`, `session-status-*`, `host-badge`, `badge-has-note`, `failure-message`, `cancel-creation-button`, `retry-creation-button`, `creation-live-region`, `more-actions-button`, `category-collapse-toggle`, `mobile-key`) or ARIA (`aria-label`/`getByRole`), not raw text/CSS structure — these are stable across a row-height/wrap change as long as the testids themselves aren't removed or the underlying elements aren't removed from the DOM (only hidden/moved into a picker). The one already-known fragile spot: `tests/e2e/accessibility.spec.ts:513-528` has a comment documenting a **pre-existing bug** where `SessionRow.tsx` doesn't render the `FAILED` status the same way `SessionCard.tsx` does — the comment explicitly flags this as "Fixing the underlying reachability gap ... " being out of scope for whatever change added that comment; worth checking this doesn't get worse if agent/memory-column removal touches the same conditional-rendering logic in `SessionRow.tsx`. `tests/e2e/touch-targets.spec.ts` explicitly measures element bounding boxes (`getBoundingClientRect` via `getByTestId(testId)` — see its `checkMinTouchTarget`-style helper at line 26-29) for `more-actions-button` and others — the "···" 44×44 fix should be validated directly against this spec, and note `SessionCard.css.ts:498-509`'s current `overflowButton` only sets `minHeight: "44px"`, no explicit width/min-width, so width may not already satisfy 44×44 on `pointer: coarse` even though height does — check via this spec, don't assume it already passes.
