# Pre-mortem: monitor-waiting-indicator
**Date**: 2026-09-09

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Claude Code CLI wording drifts again (reversed order, e.g. "1 monitor, 1 shell still running") and the extended regex doesn't fail loudly — it still matches the "shell" fragment alone and silently drops the monitor count. Confirmed empirically: `regexp.MustCompile(shells_still_running)` against that exact reversed string returns `["1 shell still running", "1", ""]` — count 1, not 2. This is the same class of bug this plan is fixing, just triggered by a different word order, and the project has already chased this CLI's wording 3 times (PR #678 + 2 follow-ups per plan.md's precedent section). | UI badge shows "Waiting for 1 Task" while the session actually has 2 outstanding shells/monitors — a silently wrong number, not an absence of detection. | Add the reversed-order case as an explicit regression test documenting today's known-undercount behavior (plan.md currently only mentions it in "Out of Scope" prose, with no test pinning the gap). Add a debug-log canary mirroring the existing `compactingCanary` idiom (`detector.go:349-364`): fire when a line matches a WaitingForAgent pattern but also contains additional unmatched `\d+\s+(?:shells?|monitors?)` tokens, so the *next* wording drift surfaces via logs instead of a user bug report. | P2 |
| 2 | A future Claude Code CLI version adds a third background-work category to this same status line (e.g. "1 shell, 1 monitor, 1 subagent still running"). Confirmed empirically the extended 2-group regex produces **zero matches** against that shape — a full detection regression (line falls through to Idle/Unknown), not merely an undercount. | The "Waiting for N Tasks" badge disappears entirely for sessions running the new CLI version, instead of showing a partial/wrong count — worse than today's bug because there's no visible signal at all. | Same canary-log addition as #1: log when a line contains the turn-completion marker + "running" but matched no WaitingForAgent pattern at all. Without a canary, this class of regression has no detection mechanism for its own future obsolescence — exactly the failure mode `compactingCanary` was built to catch elsewhere in this same file. | P2 |
| 3 | `matchWaitingForAgent`'s generalized sum-all-captured-groups loop has no way to distinguish "count" groups from any other capture group a *custom* `WaitingForAgent` pattern might define. Patterns are loadable at runtime via `LoadPatterns`/`NewStatusDetectorFromFile` (`session/detection/detector.go:141-186`) — a real, exported, YAML-driven customization surface, confirmed to have no current production caller (`grep` found only test usages), i.e. latent but live API surface. A custom pattern with a capture group for something numeric-but-not-a-count (a PID, a timestamp digit run) would get silently added into `SubagentCount` once this generalization ships. | A session using a custom pattern file shows a `SubagentCount` that doesn't correspond to any real outstanding shell/monitor total — hard to attribute back to the regex change. | Document (code comment on `matchWaitingForAgent` and/or a line in plan.md's Pattern Decisions table) that every capture group in a `WaitingForAgent` pattern is now treated as an additive count, so custom-pattern authors know the contract changed from "only group 1 matters" to "every group must be a count." Optionally validate group count/shape at `NewPatternSet` time. | P3 |
| 4 | Task 1.1.1b's zero-count guard (`count <= 0` → treat as no match, continue to next pattern) has no planned unit test exercising the all-zero-groups path, even though it's empirically reachable: `"0 shell, 0 monitor still running"` matches the new regex and produces groups `("0","0")`. The guard is the right defensive move (per Pattern Decisions), but ships unverified. | None observable today — Claude Code never emits a 0-count footer. If a later regex edit or a custom pattern (see #3) ever produces a genuine all-zero match, there is no failing test today that would catch a regression in the guard's fallthrough behavior. | Add the explicit `"0 shell, 0 monitor still running"` case to `pattern_set_test.go` asserting `ok=false`, matching the justification already written in plan.md's Pattern Decisions table for why the guard exists. | P3 |
| 5 | Epic 1.1's new tests (per plan.md Task 1.1.1c) exercise only `PatternSet.MatchLines` / `detectFromLines` — the regex/pattern layer. Epic 1.2 explicitly treats the rest of the pipeline (`InstanceStatusInfo.SubagentCount` → `instance_adapter.go:256` → `SubStatusChip.tsx`) as "verification only, no code," which is reasonable given it's unchanged, but means no test in this plan would catch a bug in an intermediate mapping/caching layer (e.g. a stale cached count not refreshing when the underlying count changes without a status transition). | Unit tests for the regex fix all pass in CI; a real or manual-test session shows a wrong count specifically in the rendered web UI badge, with every backend unit test green. | Either add one thin integration test through `ClaudeController.GetStatusAndIdleInfo` (or an existing equivalent) asserting the corrected count reaches `InstanceStatusInfo.SubagentCount` end-to-end, or explicitly note in validation.md why the existing `SubStatusChip.tsx` tests (which are generic on the count value) make this gap low-risk — right now the plan asserts this by code-tracing (1.2.1a) rather than by a running test. | P3 |

## P1 Items (address before implementation)

None. This is a low-stakes status-badge display bug fix — every plausible failure mode above degrades to "wrong or missing count on a UI chip," never data loss, a security issue, or an outage, so none qualify as "likely AND catastrophic." The two P2 items (#1, #2) are worth addressing before/alongside implementation since they're cheap (one test case + one canary log, mirroring an idiom already in this exact file) and directly hedge against this project's own documented history of three prior CLI-wording chases.
