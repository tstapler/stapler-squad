# Research: Feature Landscape & Prior Art — terminal-redraw-corruption

Date: 2026-08-06

## 1. `docs/tasks/terminal-jank.md` — Story 1/2/3 mechanisms, and does anything there explain THIS bug?

### Story 1 (COMPLETE, 2026-04-20) — ED3 filter + remove clear-screen prefix + xterm 6.0 upgrade
- Mechanism: Claude Code's TUI emits `\x1b[2J\x1b[3J` on every repaint. `EscapeSequenceParser.processChunk()` strips the `\x1b[3J` (erase-scrollback) half of that pair via regex `/\x1b\[2J\x1b\[3J/g` → `\x1b[2J`, applied to the **full reassembled chunk** (partial-sequence buffer prepended first) before any partial-sequence detection. Also removed a redundant `\x1b[2J\x1b[H` clear-screen prefix the server used to prepend to cold-start snapshots (now just `\x1b[H`).
- This is a *literal-text-stripping* fix for a *specific, always-paired, never-split* escape sequence. It does not touch `\x1b[K` (erase-in-line) or any row-addressing sequence, and both `\x1b[2J`/`\x1b[H` still pass through untouched.
- Also upgraded `@xterm/xterm` `^5.5.0 → ^6.0.0` (confirmed live in `web-app/package.json:74`, see §2 below for a related discrepancy) — pulled in xterm.js 6.0's native DEC mode 2026 (synchronized-output) support and alt-buffer scroll fixes.

### Story 2 (COMPLETE, 2026-04-20) — Quiescence detector + snapshot cache
- Mechanism: replaced fixed `time.Sleep(50ms)`/`time.Sleep(200ms)` after the ±1 SIGWINCH nudge with `waitForQuiescence()` — blocks until no `%output` control-mode event arrives for 50ms (or a 500ms hard cap), then runs `tmux capture-pane`. Adds a per-session snapshot cache (`sessionSnapshot{content, capturedAt, dirty}`) so a clean (non-dirty) session skips `capture-pane` entirely on reconnect.
- This only affects the **cold-start / reconnect snapshot path** — a `tmux capture-pane` invocation. It has no effect on the live streaming path once a client is connected and receiving `%output` deltas directly.

### Story 3 (PENDING) — Terminal instance pool
- Mechanism: keeps up to 8 xterm.js instances alive via CSS `visibility:hidden` instead of destroy/recreate on session switch, portalled into `document.body`.
- **"Bug 3: Rapid-Switch Race Condition"** (line ~564): stale WebSocket writes hitting the *wrong* terminal instance during a session switch, guarded by per-entry `sessionId` stamping (Task 3.6). This is a *cross-session* mixup — output from session B landing in session A's buffer. It is not a same-session, same-row overwrite artifact.
- **"Bug 4: tmux capture-pane Alternate Screen Race"** (line ~577): race between the SIGWINCH-triggered redraw starting and `capture-pane` executing before the redraw finishes, so the captured *snapshot* can mix pre- and post-redraw content. Explicitly scoped to the **cold-start/reconnect capture-pane path** ("only affects cold starts... pooled terminals receive live output directly — no capture-pane needed").

### Assessment: could Story 3's open issues (or anything else in the doc) produce THIS symptom?

**No — with moderate-to-high confidence.** Reasoning:

1. **Wrong mechanism class.** Both open Story 3 issues are about *which buffer/session* content lands in (cross-session race) or a *capture-pane snapshot* representing a torn intermediate state (mixing two full-pane captures). The reported symptom — a short new status line drawn over a long old one, with the old line's tail surviving underneath — is a **single-row partial overwrite within one continuously-streamed terminal**, not a cross-session mixup and not an artifact of a single `capture-pane` snapshot (the screenshot fragments `"r Running..."`, `"ss Running..."`, `"x) Running..."`, `"o) Running..."` are four *different* moments stacked as if never cleared between them — that requires multiple live redraws in sequence, which a single snapshot capture cannot produce).
2. **Story 3 hasn't shipped.** Its guards (Task 3.6 stamping, pool eviction) don't exist in the running code yet, so they can't be *causing* anything — but by the same token, they also can't be blamed for regressing a fix that was never deployed. The bug is happening in the **current, pre-pool** architecture (`TerminalOutput.tsx` owns one live `XtermTerminal` per active session, direct WebSocket stream).
3. **Nothing in Story 1/2 addresses erase-in-line.** Story 1's regex only ever strips `\x1b[3J` when paired with `\x1b[2J`. If Claude Code's TUI repositions the cursor (`\x1b[<row>;<col>H` or `\x1b[<n>A`/cursor-up) and writes a shorter string **without** a preceding `\x1b[K` (erase to end of line) or `\x1b[2K` (erase whole line), nothing in the current pipeline — ED3 filter, quiescence detector, or snapshot cache — would clear the trailing glyphs of the previous, longer line. This is architecturally a **gap in the pipeline** (nothing strips or compensates for a missing EL sequence), not a **regression caused by** any Story 1/2/3 change. It is most likely present regardless of those stories' status.
4. **Framing distinction that matters for the fix:** this is not a corruption *introduced by* stapler-squad's transport (unlike the PR #163 CSI-terminator bug, which leaked payload bytes as literal text) — it's Claude Code's TUI *itself* apparently redrawing a line without first erasing it (or emitting an erase sequence that xterm.js's parser is, for some reason, not applying before the shorter overwrite lands). The fix surface is more likely in **how/when chunks are written to xterm.js** (ordering, chunk-boundary splitting, or a missing forced-clear compensation) than in stripping escape codes.

## 3. Prior art — how other web-terminal-over-websocket products handle missing/dropped erase-in-line corruption

- **VS Code integrated terminal (xterm.js-based) — closest direct analog found.** A documented, currently-open-issue-tracked failure mode: users report the **exact trigger** named in this bug's requirements — running **Claude Code** (a full-TUI app that redraws its whole screen on every tool call) inside VS Code's integrated terminal causes garbled/corrupted rendering, attributed to the GPU-accelerated renderer getting stressed under heavy/continuous full-screen redraws. The commonly-cited community workaround is switching VS Code's terminal renderer from GPU (`"terminal.integrated.gpuAcceleration": "on"`) to the DOM renderer (`"off"`) in `settings.json`. *(Source: Sanskar Tiwari, ["My VS Code Terminal Got Completely Garbled Running Claude Code — Here Is the One-Line Fix"](https://www.sanskartiwari.io/articles/fix-garbled-vscode-terminal-claude-code).)* This is independent evidence that **Claude Code's specific TUI redraw pattern is a known trigger for this general class of renderer corruption bug across multiple xterm.js host applications**, not something specific to stapler-squad's transport pipeline — it strengthens the requirements.md hypothesis that the root issue is in how a GPU-accelerated (WebGL) renderer handles rapid partial-row overwrites, and suggests **a WebGL→DOM/canvas renderer fallback is a plausible, previously-validated mitigation**, not just a parser-level escape-sequence fix.
- **xterm.js core team's own framing of the risk class ("Parser Hooks & Terminal Sequences" guide):** screen updates are batched/throttled independently of parser state processing — the renderer decides what to redraw within a time budget, and "it is not possible to conclude whether or when a certain chunk of data will finally appear on the screen" under heavy input; a chunk's terminal-state effects can complete before the corresponding screen redraw happens, and in pathological cases a redraw can be skipped entirely if state has already moved on by the time the renderer runs. This is architecturally consistent with an erase-in-line effect being applied to internal state correctly but the intermediate frame where it would have been visible getting coalesced away — worth testing directly (see edge cases in §5) even though it doesn't fully explain OLD content surviving (that requires the buffer's actual character data, not just a missed frame).
- **DEC private mode 2026 — "Synchronized Output"** (support already present in xterm.js 6.0, per Story 1's changelog notes, and independently confirmed via [xterm.js#3375](https://github.com/xtermjs/xterm.js/issues/3375)): lets an application wrap a full-frame redraw in `\x1b[?2026h` ... `\x1b[?2026l` so the terminal buffers/holds rendering until the closing sequence, guaranteeing the viewer never sees a half-applied frame. This is the standard, purpose-built mitigation for exactly this failure mode (partial-frame visibility) in the terminal ecosystem today. **Caveat**: this requires the *source* application (Claude Code's TUI) to emit the mode-2026 wrapper: if the tmux pane program isn't using it, xterm.js supporting it is necessary-but-not-sufficient. Worth checking (in the planning phase, not this research task) whether Claude Code's Ink/TUI renderer emits `?2026h/l` around its spinner-line redraws.
- **tmux itself / Zed's persistent-terminal design (analogous architecture, not a widget library but structurally identical to this app's tmux-control-mode + capture-pane pattern):** the established pattern for "client's rendered state has diverged from the true PTY state" is a **full-state resnapshot + forced redraw**, not incremental patching — Zed's RFC explicitly does "process every byte through a headless terminal emulator to build the full grid, then serialize the whole grid on reconnect + send SIGWINCH to force full-screen apps to repaint," matching what `useTerminalFlowControl.requestFullResync()` + `CurrentPaneRequest` already does in this codebase (see `terminal-visibility-resync/requirements.md`, already-wired-but-underused primitive). If a per-escape-sequence root-cause fix proves intractable, this repo already has the "give up and force a clean repaint" fallback built — it just isn't triggered by anything mid-session today (only visibility/focus regain and manual reconnect).
- **ttyd / gotty**: no documented erase-in-line-specific corruption fix found; both are thin PTY↔WebSocket relays with no server-side terminal emulation of their own (they trust the client xterm.js/hterm to interpret the byte stream faithfully), so this failure mode would surface identically in them if the underlying TUI omits an erase sequence — no additional mitigation pattern to borrow from either project specifically. One tangential but relevant finding: an unrelated project (`pocketshell`, also tmux-control-mode-based) has an open issue describing terminal corruption ("content misplaced, screen mostly blank, cursor stranded") under heavy/bursty output, which the maintainer attributed to the emulator not keeping up with input rate — another data point for "control-mode/PTY-relay architectures are broadly susceptible to this class of bug under load," reinforcing that a resync/fallback safety net (not just a perfect parser) is the pragmatic mitigation used across this ecosystem.

## 4. Unstated user need this bug violates

- **Trust in the terminal pane as ground truth for triage decisions.** Stapler Squad's core UX loop is a human periodically glancing at a live session's terminal pane to decide "does this need my attention right now" (is Claude stuck, erroring, asking a question, or just working). Garbled/overlapping status-line fragments make that glance unreliable — a user can't tell from a corrupted line whether Claude is still running the *same* tool call or has moved on to several new ones, which directly undermines the "quick glance, then decide whether to intervene" workflow this whole app is built around. This is a more serious violation than "it looks unpolished" — it's a **correctness-of-signal** problem for the exact judgment call the UI exists to support.
- **Copy/paste and log fidelity.** If a user selects and copies visible terminal text (e.g., to paste a Claude Code question elsewhere, or to file a bug), the corrupted row's leftover characters get copied verbatim, producing garbage that has to be manually cleaned up — a small but real friction cost each time it happens mid-corruption.
- **Accessibility / screen-reader angle**: xterm.js's DOM-based accessibility layer (the "accessibility tree" / `TerminalAccessibilityService` used for screen readers, gated behind `screenReaderMode`) reads the *rendered buffer content* — if a row visually contains interleaved fragments of two different lines because an erase-in-line never ran, a screen reader would announce that same garbled concatenation, likely as nonsensical or misleading text, to a user who has no other way to visually cross-check what's actually happening. This repo doesn't appear to currently document `screenReaderMode` usage in `XtermTerminal.tsx` (not verified in this research pass — worth a quick grep in the planning phase), but if it's enabled anywhere, this bug's impact is strictly worse for a screen-reader user than for a sighted one, since a sighted user can often still infer the current state from the *newest* fragment even with stale text underneath, while a linearized screen-reader announcement of a corrupted row has no such visual disambiguation available.

## 5. Edge cases the eventual fix must explicitly handle

1. **Multi-byte UTF-8 split across WebSocket/TCP chunk boundaries.** If a fix involves scanning/patching bytes at the transport or parser layer (rather than relying entirely on xterm.js's own parser), it must not attempt to interpret a chunk boundary that falls mid-UTF-8-sequence as a character boundary — this repo's own `EscapeSequenceParser.ts` already has a "partial sequence" buffering concept (`this.partialSequence`) for exactly this class of problem with escape sequences; equivalent care is needed for raw text bytes if any new logic touches them directly. Existing precedent: PR #163 (`sanitizeUTF8Bytes`) already handles UTF-8 continuation-byte safety for the *sanitization* path — any new logic should reuse/extend that rather than re-implement UTF-8 boundary detection.
2. **Wide (CJK/fullwidth) characters and column math.** `\x1b[K`/`\x1b[nX` (erase characters) and cursor-position math operate on terminal *columns*, not bytes or even Unicode codepoints — a CJK character occupies 2 columns. If the eventual fix does any column-counting to detect "does this row need a forced erase," it must use xterm.js's own wide-character-aware cell/column model (`terminal.buffer.active` line/cell APIs) rather than raw string length, or it will misjudge overwrite length for any row containing wide characters (also relevant to `terminal-robustness/requirements.md`'s R3.5 touch-selection column math, which names the same wide-char risk in a different feature).
3. **Alt-screen vs normal-screen mode.** Claude Code's TUI likely runs in the **alternate screen buffer** (`\x1b[?1049h`) for its interactive picker/status UI — `docs/tasks/terminal-jank.md` Bug 4 already flags that `tmux capture-pane` cannot capture alt-screen content at all, a structurally different limitation from this bug (which is about the *live stream*, not a snapshot) but the fix must confirm which screen mode is active when the corruption is observed, since alt-screen redraws and normal-screen redraws may follow different code paths in Claude Code's TUI (and any erase-compensation logic added to xterm.js's write path must apply correctly to whichever buffer is active — xterm.js maintains cursor/erase state per-buffer).
4. **Reconnect/resume with a fresh xterm.js instance receiving a `capture-pane` snapshot instead of a live stream.** A brand-new xterm.js instance (e.g., after the pool evicts a session, or on a hard page reload) starts from a blank buffer and receives a single `capture-pane` text blob, not the sequence of incremental redraws that produced the corruption in the live-stream case. The bug as screenshotted is inherently a **live-stream-only** artifact (it requires several successive partial redraws layering on top of each other); a fix must be verified against **both** paths — confirm the snapshot/cold-start path doesn't exhibit it (Story 2's quiescence detector already targets getting a *settled* capture, which should avoid a mid-redraw snapshot) and confirm whatever fix is applied to the live-stream write path doesn't regress the snapshot path's simpler one-shot write.
5. **Distinguishing this bug from the already-fixed PR #163 class.** Any diagnostic/repro work should first rule out that the observed corruption isn't actually a residual case of the OSC/DCS/PM/APC/SOS-terminator gap that PR #163 fixed for `stripANSIBytes`/`sanitizeUTF8Bytes` — i.e., confirm the escape sequences in a captured repro are being **correctly parsed and interpreted** (cursor moves, erase runs) rather than **leaking as literal text** before concluding this is a genuinely new "missing erase" bug class, per requirements.md's own framing.
