# ADR-003: Media is never committed, is generated in CI, and staleness fails loudly

**Status**: Accepted (owner-decided input) | **Date**: 2026-11-10

## Context
Committed screenshots/clips date from PR #1051 (2026-10-15). `deploy-website.yml` warns and falls back to them when recording fails (`:138-152`); `features.json` exists in two states (committed vs regenerated with clips); the release-asset hash manifest is legacy. Earlier GIF commits left about 15.6 GB of dead blobs (`demo-publish.yml` header).

## Decision
1. **No binary media in git.** A diff-based guard (Go, `tools/promo/cmd/mediaguard`, git access via go-git, shared code in `tools/promolib/gitbase`) fails PRs that add or modify `png|jpg|jpeg|gif|webp|avif|webm|mp4|mov` outside an allow-list file (logos, favicons, icons, `tests/e2e/tests/snapshots/**`), with a size ceiling backstop. Deletions are always allowed. The guard runs as a step of the path-filter-free `pr-diff-guards` job (job id `guard`; conditional on the Task 1.1.4b0 measurement, otherwise the separate `promo-guards` job, and every mention of `guard`/`pr-diff-guards` here has that condition) in `backlog-scaffolding-guard.yml` so media-only, README-only and docs-only PRs are checked (a `lint.yml` step would be skipped by its `paths:` filter). A PR labelled `allow-media` passes with a notice only when the **latest** `labeled` event for the label was made by an actor of type `User` listed as an individual user in the base CODEOWNERS (checked through the events API; bots never count, teams are not resolved); this is the rollback path when reverting the Phase 5 deletion, and its use is reported. The allow-list is the plan's Task 2.1.1b list (it also covers `website/src/assets/**`, `project_plans/**/design/*.png` and test-fixture icons, not only logos, favicons and snapshots). The guard workflow triggers on PRs targeting `main` only, so stacked-PR bases are not checked until they retarget. If the Task 1.1.4b0 measurement fails the 5-minute gate the guards move to a separate always-reporting `promo-guards` job; a `guardsEnforce` flag is the kill switch. **Gate inputs are read from the base blob** (`gitbase.ReadBlob(HEAD^1, path)`): the flag file, both allow-lists and `.github/CODEOWNERS`, so a PR cannot widen its own gate; the guard code itself is protected by CODEOWNERS entries on `tools/promo/**`, `tools/promolib/**`, the flag file, the allow-lists and the two workflows (requires "require review from code owners" on `main`, verified in Task 2.1.1c). The `allow-media` actor is looked up through the events API (job permissions `contents`, `pull-requests`, `issues` read) and must be listed as a user login in the base CODEOWNERS; teams cannot be resolved with `GITHUB_TOKEN`, so a team-only entry fails closed. New steps skip unrelated `labeled`/`unlabeled` events so label churn does not re-run the backlog-scaffolding checks. The workflow never uses `pull_request_target` (it builds PR code; a test fails if the string appears). **Absent inputs**: a gate input missing from the base blob takes a fixed default (flags absent: `guardsEnforce=true`, others `false`; allow-list absent: empty; CODEOWNERS absent: no override authority), a present but malformed input exits 2, and the inputs merge in an earlier PR than the wiring. **Blocking precondition (chosen over building the guard from the base ref, which needs a second checkout/build and has its own bootstrap problem)**: the steps are wired as blocking only after `.github/CODEOWNERS` exists (absent today, created in Task 2.1.1c) and `branches/main/protection` reports `require_code_owner_reviews: true`. **Residual risk**: an admin override, a code owner approving a harmful change to the guard code, or protection being disabled later each defeat the control; the base-blob rule only protects the data inputs, not the guard binary built from the PR tree, and nothing here detects a protection change after the check.
2. **Media ships in the Pages artifact** (`/clips`, `/shots`), produced by record shards in `deploy-website.yml`; the record job never commits back.
3. **No stale fallback.** `expected-media.json` (generated from sources) is the list of truth; `mediafresh` (`mediatool fresh`, one `mediatool` binary with `fresh`, `shard-plan`, `summary`) fails the build if any expected entry is missing from the merged `media-manifest.json`, its `commit` differs from `$GITHUB_SHA`, its recorded theme is not Grimdark, or any referenced `src/poster/source` is absent from `dist`. Missing clip = red deploy; the previous Pages deployment stays live.
4. `features.json` becomes deterministic: cards reference media by **name** (declared in `website/src/content/feature-media.json`), never by recorded file presence, so the committed file equals the deployed one.
5. README links to `/tours` pages (no release-asset embeds). `demo-publish.yml` and `asset-health-manifest.json` are retired once local-media checks replace them.
6. PRs run a smoke subset (1 clip + 1 shot set) with `TOURS_MEDIA_MODE=smoke`; the full matrix runs on the weekly cron, dispatch and app-affecting pushes to main. Content-only pushes reuse the last-known-good media and check it with `mediatool fresh -reuse-from <commit>` (recorded commit is an ancestor of `GITHUB_SHA` and no recording-input path changed, so strict `commit == GITHUB_SHA` still holds for every full record). Last-known-good is the named artifact `promo-media-lkg` (`retention-days: 35`, found through the newest successful deploy run, `actions: read`; a missing artifact hard-fails; `actions/cache` is not used because of its 7-day eviction). Budgets (per-clip 3 MB, per-image 400 KB, total `dist/` 40 MB, record-job wall clock 30 min, clip duration 60 s) live only in `tools/promo/budgets.json` and are enforced by `mediatool fresh`. A scheduled run where freshness fails deploys the last-known-good media for up to 28 days with a visible notice, then hard-fails; push and PR runs never use last-known-good. Clips ship as WebM plus an H.264 MP4 rendition.
7. Rollout: freshness runs report-only first, beside the old warn-and-fallback step (marked `# REMOVE IN 5.1.2`), controlled by `freshnessEnforce` in the checked-in `.github/promo-flags.json` (reviewable, readable by fork PRs; repo variables rejected). Flipped and the old step removed in Story 5.1.2, only after 10 consecutive green full runs (including 2 weekly cron runs). This supersedes the requirements.md Risk Control sentence that the fallback can be re-enabled by reverting one workflow step: that holds only until Phase 5 deletes the committed media. After Phase 5 deletes the committed PNGs, rollback means redeploying the previous Pages artifact.

## Solo-owner review and admin override
On a solo-owner repo the author cannot approve their own PR, so a PR touching a gated path (`tools/promo/**`, `tools/promolib/**`, the flag file, the allow-lists, the two workflows) cannot satisfy "require review from code owners" and needs an admin override (merge with branch-protection bypass).
- **Expected frequency**: high. Phases 2-5 touch these paths constantly (guard code, allow-lists, `deploy-website.yml`), and autonomous sessions open such PRs, so expect an override on most promo PRs until a second reviewer exists.
- **Override procedure**: (1) the PR states in its description which gated paths it touches and why; (2) the owner reviews the diff of those paths specifically; (3) the owner merges with the admin bypass (`gh pr merge --merge --admin --repo owner/repo`) and notes the override in the PR; (4) a bypass never covers a change that disables the guard or edits `guardsEnforce` without a stated reason. The guard job id must also be a required status check on `main` (Task 2.1.1c), since `main` currently has no required checks.
- **OWNER DECISION (open, not decided here)**: name a second reviewer (a user login in CODEOWNERS) or accept admin override as the standing procedure.

## Alternatives rejected
Git LFS (owner: no binaries in repo; `lfs: true` checkout would also mask the guard); keeping committed screenshots as fallback (the stated failure mode); release-asset hosting for README (camo caching, extra publish workflow).

## Consequences
A Chromium/runner-image change can fail the weekly deploy with no code change; the existing `notify` job opens the issue and the last good deploy stays up. Pixel diffs are not gated; presence, size, dimensions, duration, theme and commit stamp are.
