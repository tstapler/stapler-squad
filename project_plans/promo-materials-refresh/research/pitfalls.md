# Research: Pitfalls — promo-materials-refresh

Builds on `project_plans/stapler-squad-website/research/pitfalls.md` (subpath/base-path bugs, curation link rot, dispatch-only publishing, Lighthouse/GIF cost). Those still hold and are not repeated. Labels: VERIFIED = opened in this repo; INFERRED = general knowledge or reasoning, not run here.

## 1. Naming / IP leak (new constraint: public name is "Grimdark" only)

- VERIFIED: the in-app theme picker label is literally "WH40K" (`web-app/src/components/settings/ThemePicker.tsx:28`, description "Grimdark parchment + gold"). Any screenshot or clip showing Settings > Theme, the theme picker, or a command-bar theme listing leaks the name. Planning must either rename the user-visible label (id `wh40k` and `stapler-theme` storage value can stay) or forbid those scenes.
- VERIFIED: `Warhammer`/`40K`/`wh40k` already appear in published-site sources: `website/src/components/NoThemeSelect.astro`, `website/src/styles/wh40k.css`, `website/src/content/docs/help/add-user-themes.md` (the last is synced from `docs/how-to`, so the fix must happen in the source doc, or `sync-content --check` will fail on drift). File names and CSS identifiers are internal; the `.md` and `.astro` text need review for user-visible strings.
- VERIFIED: the recorder passes `theme = 'wh40k'` (`tests/e2e/website-demos/recorder.ts:27`) and sets it via `localStorage['stapler-theme']`. That is an internal id and fine, but `ClipSpec.theme` values must not flow into captions, `title`, filenames or alt text.
- INFERRED leak channels beyond copy: media filenames (`wh40k-*.png`), `<title>`/`alt`, `aria-label`s, tab titles and tooltip text captured in frames, ffmpeg/PNG metadata, Playwright trace/test names surfaced in the job summary, and page text in the Starlight search index (Pagefind indexes content, so a banned term in help docs becomes searchable).
- Mitigation: a CI scanner over the built `website/dist` (HTML, JSON, search index, file names) plus README and `docs/` sources, case-insensitive, covering `warhammer`, `40k`, `wh40k`, `40,000`, `grim darkness`, `adeptus`, `space marine`, `imperium`, `emperor`, `chaos`. Allowlist internal-identifier paths such as `*.css` selectors. Pixel content cannot be grepped, so also OCR a sample of screenshots, or assert on DOM text at capture time (`page.locator('body').innerText()` run through the same banned-term list before the frame is saved). Imagery matters too: check that theme fonts, icons and flavour text (e.g. in seeded session titles or theme-specific copy) contain no franchise names.

## 2. Deterministic recordings (flaky/nondeterministic)

Existing harness: `tests/e2e/website-demos/recorder.ts`, `clips.ts`, `scripts/record-website-demos.sh` (VERIFIED, read in full).

- Hard-coded `page.waitForTimeout(...)` throughout `clips.ts` and `caption()` conflicts with the repo e2e convention ("no `waitForTimeout`", `e2e-test-conventions` skill). Existing clips are exempt only because they are pacing, not synchronization. Keep pacing sleeps in one helper (`hold(page, ms)`), and wait on locators or `expect` for every state change, or the e2e-conventions CI check will flag the new specs.
- Wall-clock relative data: `tests/demo/helpers.go` uses `time.Now()` when seeding (`helpers.go:158`), so "updated 3m ago" and any date text differ per run and per week (scheduled weekly redeploy). Static screenshots will churn visually and relative-time strings can straddle a bucket boundary mid-recording. Mitigation: seed timestamps at fixed offsets from now and freeze the browser clock with `page.clock.install({ time })` (Playwright clock API; INFERRED applicable to the installed Playwright version, verify) before navigation. A frozen clock also stops spinners and polling-driven timers, so check that SSE/ConnectRPC streaming still delivers under a paused clock (`clock.install` without `runFor` can stall `setTimeout`-driven UI; use `clock.setFixedTime` for display-only freezing instead).
- Live streaming UI: the dashboard polls and streams; seeded sessions with no real agent show stale or `unknown` states and terminal panes may be empty or show tmux noise. Seed deterministic terminal scrollback and statuses rather than relying on real tmux output. `STAPLER_SQUAD_USE_CONTROL_MODE=false` is already set by the script (VERIFIED), which is good.
- Animations and transitions: the captions use CSS transitions; app UI has transitions and a `prefers-reduced-motion` block (`web-app/src/app/globals.css:453`, VERIFIED). For screenshots set `reducedMotion: 'reduce'` in the context so the app settles, and pass `animations: 'disabled'` to `toHaveScreenshot`/`screenshot`. For video clips keep motion on (the point of the clip) and trim by measured readiness, as the harness does.
- Font loading: fonts are self-hosted woff2 with `font-display: swap` (`web-app/src/app/fonts.css`, VERIFIED), so the first frame can render fallback fonts and then reflow. Before capture `await page.evaluate(() => document.fonts.ready)` and assert the named families via `document.fonts.check(...)`; a missing woff2 silently falls back to system fonts, and runner system fonts differ from a dev machine, so a screenshot that "looks fine locally" differs in CI.
- Theme application: the first-paint boot script reads `localStorage['stapler-theme']` and falls back to `clean` if the key is unknown (`web-app/src/styles/theme-boot-script.ts`, VERIFIED). `addInitScript` sets it before navigation (good), but a typo or a renamed id silently yields the Clean theme with no error. Add a capture-time assertion that the `<html>` class equals the expected theme class (or a computed CSS variable such as the background colour), failing the clip otherwise, per the requirement's "check that the captured media really is" the theme. Per-instance server-side theme preference could also override localStorage if the app syncs it; verify before relying on localStorage alone (UNVERIFIED).
- Onboarding/toast noise: the recorder already suppresses tours and quiet mode via localStorage keys (VERIFIED). Each new feature page may add its own onboarding key (the backlog has one); a new feature that adds a key without updating the recorder will put a tour overlay in the footage. Add an assertion that no `[role=dialog]` is open before `clip.ready()`.
- Version/build info on screen: footers or About panels may show the git SHA, version or build time, which differ per run; mask them (`mask:` option) or hide them.
- Flag-gated pages: `FeatureGuard` routes redirect to `/` when the flag is off, producing a screenshot of the wrong page with no error. Enable flags via the feature-flag RPC (per project memory, flags are live-settable, not env vars) before navigation and assert the final URL and a page landmark.
- Failure behaviour: `record-website-demos.sh` exits 3 on partial success and the workflow ships whatever worked, and the deploy job falls back to committed screenshots (VERIFIED, `deploy-website.yml:137-150`). The new requirement forbids silent stale fallback; the freshness gate must fail the deploy (or at least the PR check) when an expected clip is missing, with an explicit expected-clip list as the source of truth (otherwise a deleted spec looks like success).
- Visual-diff noise: Chromium version bumps (`npx playwright install chromium` is cached on `bun.lock` hash) change anti-aliasing. Do not gate on pixel diffs of promo media; gate on presence, size, duration, dimensions and theme assertions.

## 3. Seed data leakage (security classification: public)

- INFERRED: the "Files viewer", history search, and workspace views may read real directories from the runner (checkout path `/home/runner/work/stapler-squad/...`) or the repo's own files; a tour that browses files will show the repo itself, which is public, but will also show untracked build output. Seed a dedicated fixture repo under the temp dir.
- Claude history search reads `~/.claude` on the host. On a local run that exposes real sessions; on CI it is empty, so the tour would be blank. Seed a synthetic history directory and point the server at it (needs a config/env seam; check existing `--test-dir` handling covers it, UNVERIFIED).
- Notifications/Slack/GitHub/Jira integrations: fixtures only. Never record with real tokens present in env; the recording job has `contents: read` only (VERIFIED) which limits blast radius. Add a post-capture grep of the DOM text for the runner username, `/home/`, `/tmp/tmp.`, `ghp_`, `gho_`, `.internal`, `@` email patterns, same mechanism as the Grimdark scanner (section 1).
- Video also records the browser URL bar? No: Playwright video captures page content only, so URLs are not shown, but captions and tab titles inside the page can show `localhost:<port>`; harmless but ugly.

## 4. GitHub Pages artifact size and deploy time

- VERIFIED current state: `website/public` is 2.1 MB; `assets/` is 4.3 MB; the Pages artifact is built from `website/dist` (`deploy-website.yml:221-224`).
- GitHub documented limits (INFERRED from GitHub docs, not re-verified today; re-check at planning): published site up to 1 GB, soft bandwidth 100 GB/month, deployment times out at 10 minutes, the upload-pages-artifact tarball is gzip-compressed (webm and png do not shrink further). Practical risk is not the cap but deploy time and the weekly full rebuild re-uploading all media (no cross-deploy dedupe).
- Budget math to plan with: N feature cards (~19) x clip at 1280x720 webm. Existing pipeline uses `-crf 28 -b:v 0` VP9 (`scripts/demo-post-process.sh`, VERIFIED). Assume 0.5 to 3 MB per 15 to 30 s clip, plus 2 to 5 screenshots per feature at 100 to 400 KB PNG (use WebP or AVIF for screenshots via ffmpeg/`cwebp`, an order of magnitude smaller for UI images with flat colours; PNG-quantize otherwise). 19 clips + 40 tours media + 80 screenshots lands in roughly 40 to 120 MB, well under 1 GB but large enough to slow a git-less artifact upload and every Lighthouse run. Set a per-asset budget (e.g. clip <= 3 MB, image <= 400 KB) and a total `dist` budget enforced in CI, tracked like `.size-limit.json` (project memory warns budgets files drift when stored in two places; keep one source).
- Pages artifact rule: `upload-pages-artifact` forbids symlinks/hardlinks in the artifact and is sensitive to file permissions (INFERRED); recorded files in `$RUNNER_TEMP` copied with `cp -r` are fine, `ln -s` is not.
- Artifact handoff between jobs: `record-clips` uploads via `upload-artifact` with `retention-days: 1` (VERIFIED line 95); with more clips split across a matrix, each shard uploads its own artifact and the build job must merge them (`download-artifact` with `pattern:` and `merge-multiple: true`), otherwise later shards overwrite or the path layout changes (INFERRED, v4+ artifact names must be unique per run).
- Deploy-time health check: `check-asset-health.mjs` verifies Release asset URLs by sha256 against `asset-health-manifest.json` (VERIFIED). The manifest still lists ~23 old `demo-*.gif`/`review-queue-*.gif` hashes keyed to release-asset names. Once media is shipped inside the artifact, that manifest and its "not yet published?" failure mode become dead or misleading; planning should decide whether to retire the manifest, or replace it with a build-time check that every referenced local media file exists in `dist` with non-zero size. Per the project memory ("two-place values"), a hash manifest committed alongside content drifts unless something regenerates it.
- `concurrency: group: pages, cancel-in-progress: false` (VERIFIED) means a long record job queues all later deploys behind it. Weekly cron at Monday 06:17 UTC plus a push to main can stack; with a heavier record matrix, a push to main can wait behind a 45 min job.

## 5. GitHub runner time / cost

- VERIFIED: `record-clips` is a single `ubuntu-22.04` job with `timeout-minutes: 45`; it builds Go + the web UI + the binary, installs Playwright, then records serially. Cost scales linearly with clip count when serial. Public repos get free standard hosted runner minutes, but this repo's Actions budget is still shared and `docs/reference/ci-job-budget.md` (VERIFIED exists) governs growth. A push-triggered deploy that re-records every clip for every website-path change is the main multiplier; today the deploy runs on path-filtered pushes, weekly cron and dispatch (VERIFIED `on:` block). Do not trigger the full recording matrix on PRs; PRs should validate with a small smoke subset (one clip + one screenshot set) and the registry/media-commit/naming gates, which are cheap.
- Sharding: split clips across 2 to 4 matrix jobs, but each shard repeats the expensive Go+web build unless it is built once and passed as an artifact (or served from the existing cached prepare action). INFERRED: a build once then `upload-artifact` binary approach beats 4x rebuilds.
- Recorder single-server concurrency: Playwright runs one project with workers set in `playwright.website-demos.config.ts`; video recording at 1280x720 under parallel workers on a 2-vCPU runner drops frames and gives choppy clips (INFERRED, common Playwright issue). Keep `workers: 1` per server, shard across jobs instead.
- Memory: project memory records an OOM-restart incident from RAM-backed `/tmp` and parallel workers (the 2026-07 notes). On the runner, `/tmp` is disk-backed, but ffmpeg VP9 two-pass or `-row-mt` on many files in parallel can spike memory. Post-process serially or cap parallelism.
- Weekly cron failure is already handled by the `notify` job (VERIFIED), which opens issues; extend it with new check names rather than adding a second notifier.

## 6. ffmpeg / webm / gif size and browser compatibility

- VERIFIED pipeline: `scripts/demo-post-process.sh` re-encodes with VP9 `-crf 28 -b:v 0`, can add a title card, and can export a GIF (first 12 s, 960 px, 10 fps). `--no-gif` is used for website clips.
- Browser compat: WebM/VP9 plays in Chrome, Firefox and Edge, and in Safari 14.1+ on macOS 11.3+ / iOS 17.4+ (INFERRED; older iOS cannot play WebM). The existing `HeroVideo.astro` and `reduced-motion-video.ts` are the place to check for an MP4/H.264 fallback `<source>`; if absent, iOS visitors on older devices see a blank box. Add an H.264 `.mp4` rendition only if the size budget allows (it doubles clip bytes) or keep a poster image as the guaranteed fallback.
- GIF is a poor fit for README: GitHub README renders `<img>` GIFs but not `<video>` from relative paths; user-attached video URLs work only via github.com `user-attachments` links, which cannot be CI-generated (INFERRED). Since no binaries may be committed, README media must be hotlinked to the Pages URL or a Release asset. A rolling Release (`demo-gifs-latest`, `--clobber`) already exists and is the proven pattern (VERIFIED in `demo-publish.yml` header), but Release assets are cached by GitHub CDN/camo: camo caches README images, so a clobbered asset can show stale for hours. Prefer Pages URLs with content-hash filenames or a `?v=<sha>` query.
- GIF size: 10 fps palette-mapped GIFs for a UI clip routinely hit 3 to 10 MB; GitHub README rendering has a per-image size ceiling in practice (INFERRED, ~10 MB). Cap GIF length (the 12 s truncation already does) and keep GIFs only for README.
- Poster frames: extract a poster at a deterministic frame (after `clip.ready()` + N seconds) rather than the first frame, which is often a title card or blank.
- Encoding determinism: ffmpeg VP9 output is not bit-reproducible across ffmpeg versions or thread counts; the runner uses apt ffmpeg on `ubuntu-22.04` (VERIFIED `apt-get install ffmpeg`), version pinned only by the image. The "freshness check: media produced from the deployed commit" must be based on a build-stamp recorded in a sidecar JSON (commit SHA, ffmpeg version, timestamp, per-clip sha256 and size), not on comparing hashes against a previous run. The existing script already prints sha256 per clip (VERIFIED).
- `ubuntu-22.04` runners are scheduled for retirement in GitHub's roadmap (INFERRED; check the GitHub runner-images deprecation notice); all three media workflows pin it, so a migration to 24.04 changes ffmpeg and Chromium font stacks at once, which will shift every image.
- Reduced motion: the site handles it in `website/src/lib/reduced-motion-video.ts` and `HeroVideo.astro` (VERIFIED exist). Every new tour embed must go through the same helper (no autoplay, show poster, user-initiated play), including `loop` and `muted autoplay`; ad-hoc `<video autoplay>` in tour MDX bypasses it and will fail the existing a11y/e2e checks only if those tests cover tour pages (they currently cover the existing pages, so new tour pages need test coverage added). Also give every video a `<track kind="captions">` or an adjacent text transcript: burned-in captions (the recorder overlays them in the DOM, VERIFIED) are not accessible text, and Lighthouse's `video-caption` audit applies. Burned-in captions also disappear below ~12 px on mobile viewports; tour steps in prose are the real accessible content.

## 7. Git history bloat and the media-commit guard

- VERIFIED precedent: `demo-publish.yml` header says 16 runs left about 15.6 GB of dead blobs because GIFs do not delta-compress. Currently committed media: `website/public/features/01..08-*.png`, `website/public/demo.webm`, `assets/demo.gif`, `assets/screenshot.png`, `assets/demo-recording/*.png` (from requirements). Removing them from the tree does not shrink history (out of scope, correct), but the next regeneration must never be committed.
- Guard design pitfalls: (a) a path-only guard (`website/public/**`) is evaded by a new directory; match on extension (`png jpg jpeg gif webp avif webm mp4 mov`) repo-wide, with an allowlist for logos, favicons, icons, and visual-regression snapshot directories (the existing `.png` Playwright snapshot dirs and `web-app` icons must be enumerated, or the first PR fails on legitimate files). (b) Check only files added or modified in the PR diff (`git diff --diff-filter=AM origin/main...HEAD`), not the whole tree, so the 30 legacy files do not block unrelated PRs, and explicitly allow deletion. Per project memory, a stale local merge base makes CI tests against the live base, so use `origin/main` after a fetch. (c) `git lfs` is rejected but `actions/checkout` here has `lfs: true` (VERIFIED line 54); a binary added as an LFS pointer passes an extension-agnostic "is binary" test but still counts; match by name. (d) A binary inside a zip, tarball or base64 in JSON bypasses extension checks; add a size ceiling on any added file (e.g. 500 KB) as a backstop.
- Do not let the record job commit back to main to refresh `features.json`/`asset-health-manifest.json` with hashes; that is how the original GIF bloat happened (INFERRED mechanism, same pattern). `features.json` is checked with `git diff --exit-code` after `build-features.mjs` (VERIFIED), which is deterministic only if media filenames and the clip list come from sources, not from what was recorded; the deploy job regenerates it with the clips present (`deploy-website.yml` "Regenerate features.json"), so the committed version must correspond to the no-clips state, and that is a quiet inconsistency to design away (e.g. media manifest generated entirely at build time, not committed).

## 8. Registry docs-coverage gate (ratchet pitfalls)

- VERIFIED layout: per-feature JSON files in `docs/registry/features/` (the README still describes `backend-features.json` monolith files; the doc has drifted from the per-feature layout described in `CLAUDE.md`; fix the README as part of the schema change).
- Baseline merge conflicts: the requirement's mitigation (per-feature files) only works if the ratchet baseline is also per-feature (e.g. a `docs: {status: "gap-grandfathered"}` field inside each feature file) rather than one `docs-coverage-baseline.json`. One central file conflicts on every concurrent PR that fixes a gap, and per project memory the same class of "two-place value drift" (budgets.json vs .size-limit.json) bit this repo before.
- Baseline drift in both directions: the ratchet must fail when a grandfathered feature gains docs but stays marked as a gap (otherwise the baseline silently overstates debt), or auto-prune by regeneration; and must fail when a new feature is added with `grandfathered: true` by copy-paste. Make "grandfathered" valid only if the feature ID existed on the base branch (`git show origin/main:path`), i.e. the same diff-aware approach as the media guard.
- Mapping robustness (listed as a rabbit hole): naming drift and one-page-many-features. Prefer explicit links (`helpDoc: "<slug>"`, `websitePage: "<path>"`) validated by the gate against the real file set (`web-app/src/lib/docs` loader sources and `website/src/content/docs/**`), not fuzzy matching by ID. Validate anchors (`#section`) too, or a rename passes the file check and breaks the link. Reuse `website/scripts/check-internal-links.mjs` rather than writing a second link checker.
- Existing-gate precedent to copy: `make registry-generate` rewrites feature files and CI diffs them (CLAUDE.md). Adding hand-curated fields to files that a generator rewrites is the classic failure: the generator must preserve unknown or hand-set fields (CLAUDE.md notes `tested` is hand-set and a project memory records it as a CI gotcha). Add a generator test that round-trips a file with `docs` fields.
- "Changed feature" detection is the hardest part: define it concretely (a diff touches the feature file or a source file mapped by the feature's `+feature:` marker) or the gate will either never fire or fire on every refactor. Report-only mode first (stage 3 of the rollout) is right; log how many PRs would have failed before flipping.
- Sync drift: `sync-content --check` already blocks when a curated website doc differs from its source (VERIFIED, `deploy-website.yml`), which means the docs gate and the content sync can disagree (help doc exists in-app but is not in `content-manifest.json`). Treat the manifest as an input to the gate.

## 9. Website build, content and quality gates

- Subpath: the site is served at `/stapler-squad/`; media referenced from tour MDX must go through the base-aware helper (see prior pitfalls doc, section 2c). A tours index with 20 autoplaying or eager videos will fail LCP/total-byte-weight. - Mobile: requirements say both form factors. A 1280x720 clip scaled to a 390 px wide phone makes UI text roughly 30% scale (~4 px) and unreadable; record mobile-viewport variants for the few tours that matter (e.g. 390x844 with `isMobile`/`hasTouch`), rather than relying on CSS scaling, and tag screenshots with a form factor in the manifest. - Do not make the PR workflow depend on the Pages `github-pages` environment: it is restricted to the `main` branch policy (prior doc, VERIFIED then), so PR runs can build and test but not deploy. Preview deploys for tour review would need a separate mechanism (artifact download).

## 9b. Renaming the theme to "Grimdark" in code (id, css, snapshots, persisted setting)

Blast radius, VERIFIED with `git grep -I -i -l wh40k`: 179 tracked files match, but most are noise: ~100 under `web-app/.next/**` (git grep searches tracked files only, so `.next` build output appears to be tracked; confirm with `git ls-files web-app/.next | head` and untrack it rather than renaming inside it), plus `project_plans/*/research` history. Real code sites: `web-app/src/styles/theme.css.ts` and `theme-boot-script.ts` (`THEME_NAMES`), `web-app/src/components/settings/ThemePicker.tsx(.css.ts)`, `web-app/src/lib/contexts/ThemeContext.tsx`, `web-app/src/lib/omnibar/detectors/CommandDetector.ts`, contrast tests (`commandBarContrast.test.ts`, `chipContrast.test.ts`), `server/user_themes.go:37` (`builtinThemeBases` allow-list), `website/src/styles/wh40k.css`, `website/src/components/NoThemeSelect.astro`, `website/tests/unit/wh40k-theme.test.ts`, 7 files under `tests/e2e`, and the tracked snapshot dir `tests/e2e/tests/snapshots/visual-wh40k/` (2 PNGs).

- Stale persisted theme id (the biggest user-facing break). The theme is stored as the raw string `wh40k` in `localStorage['stapler-theme']`; the boot script maps unknown ids to `clean` (`theme-boot-script.ts`, VERIFIED), so every existing user silently loses their theme after the rename. Ship a one-time migration that rewrites `wh40k` to the new id in three places: the boot script (runs before paint, so it must do the alias itself, not wait for React), `ThemeContext` initial read, and any server-side or per-instance stored preference (UNVERIFIED whether one exists; grep `stapler-theme` in Go before assuming localStorage is the only copy). Keep a `LEGACY_THEME_ALIASES = {wh40k: 'grimdark'}` map for at least a release; do not delete it in the same PR. Add a test that boots with `localStorage['stapler-theme']='wh40k'` and asserts the Grimdark class.
- The recorder and the website both set the old id: `recorder.ts` writes `stapler-theme` (VERIFIED) and the website's `wh40k.css`/`NoThemeSelect.astro` use the name. If the recorder is updated but the app alias is not (or vice versa, e.g. recording an older binary), the clip silently records the Clean theme. The capture-time "html class is the expected theme" assertion from section 2 is the safety net; make the expected value come from the same constant the app exports.
- User themes in `~/.stapler-squad/themes/*.json`: each declares a `base` built-in id (`UserTheme.base`, `server/user_themes.go` allow-list `builtinThemeBases`, VERIFIED). Existing files with `"base": "wh40k"` would be rejected or skipped after the rename. Accept the legacy id in `builtinThemeBases` (normalize to the new id on load), log a deprecation, and update `docs/how-to/add-user-themes.md` and its synced website copy (`website/src/content/docs/help/add-user-themes.md`, drift-checked by `sync-content --check`, so the two must change together). The custom-theme cache `stapler-theme-custom` stores `{id, cls, props}` with a precomputed CSS class (`ThemeContext.tsx:40`, VERIFIED): a cached `cls` from the old build points at a class name that no longer exists, so invalidate or version the cache key, or the first paint after upgrade is unstyled.
- FOUC: theme CSS class names are content-hashed vanilla-extract identifiers injected by the boot script from a map extracted at build time (`theme-boot-script.ts` header, VERIFIED). A rename changes the hashes; a cached HTML shell with an old inline script and a new CSS bundle (or reverse, during the service restart window or a CDN/Pages cache) briefly applies a class with no CSS. The build already emits both from the same map, so the risk is browser/proxy caching of `index.html`; verify it is served `no-cache` and keep the old class name resolving for one release if cheap. Also check the website: `website/src/styles/wh40k.css` is loaded by the Astro build, and Starlight dark/light plus `NoThemeSelect` may key off a `data-theme` value; renaming the attribute value without updating the CSS selectors gives an unstyled flash on every page, and the Lighthouse/a11y gates only catch it if contrast collapses.
- Visual-regression baseline churn: `tests/e2e/tests/snapshots/visual-wh40k/` is a Playwright snapshot directory named after the project/theme (VERIFIED, 2 PNGs tracked). Renaming the directory requires renaming the Playwright project or `snapshotPathTemplate`, regenerating or `git mv`-ing the PNGs, and updating CI references. Do it as a pure move in its own commit (`git mv`, no pixel change) so reviewers can confirm the images are byte-identical (`git diff -M --stat` shows a 100% rename). If baselines are regenerated in the same PR as unrelated visual changes, a real regression hides inside the churn. Binaries added to the tree here also trip the new media-commit guard unless snapshot directories are allowlisted (sections 7 and 8): decide the allowlist glob before the rename lands, and note the renamed path must match it (`visual-*` vs `snapshots/**`).
- Order of operations to avoid a broken main: (1) add the new id plus legacy alias and migration, keep the old CSS selectors working; (2) switch the recorder, website and picker label; (3) rename files and snapshot dir; (4) remove the legacy alias in a later release. Doing 1 to 3 in one PR works only if the boot-script migration test passes in CI; the e2e suite and the website unit test (`wh40k-theme.test.ts`) both reference the old name and will fail loudly if missed.
- Public docs and registry: `docs/registry/features/**` and `docs/reference/css-architecture.md` may mention the old id; the trademark scanner (below) deliberately does not cover `docs/` internal pages, so decide whether internal docs may keep the old identifier (requirements: only where it surfaces to users).

### Trademark scanner false positives and scope (grep-based check)

- Hash and lockfile hits (VERIFIED concern, not yet observed here): a case-insensitive scan for `40k` matches random base64/hex in `go.sum`, `bun.lock`, `package-lock`, sha256 manifests (`asset-health-manifest.json`, which is full of 64-hex strings that can contain `40k`... hex has no `k`, but base64 integrity strings in `bun.lock`/`go.sum` do), minified bundles, source maps, SVG path data, `.woff2` binaries, and numbers like `140k`, `40K requests`, `$40k`. Mitigations: scan only published output and public content roots (`website/dist` text files, `website/src/content`, `README.md`, tour sources, media filenames, extracted captured-DOM text), never lockfiles, vendored fonts, or binary media; use word-boundary regexes (`\b40k\b` is still too loose, so prefer the specific tokens `warhammer`, `\bwh40k\b`, `\bwh-40k\b`, `40,000`, `grim ?dark` is allowed) and treat bare `40k` as a warning needing an allowlist rather than a failure.
- The rename itself will legitimately leave the old token in places that must be allowed: the legacy alias map, migration test, `builtinThemeBases` compat entry, and git history. Use an explicit allowlist file of `path:reason` entries (checked in, small, reviewed), not inline `nolint` markers in published content, and fail when an allowlist entry no longer matches anything so it cannot rot.
- Scope the failure to what ships: the scanner runs on `website/dist` after the build, so it catches terms arriving through synced docs, Starlight search index and alt text, not just source. Run it on the generated `features.json`, the sidecar clip manifests and media filenames too. Words inside images need the capture-time DOM-text check; a grep cannot see pixels.
- Avoid self-trigger: the scanner's own term list and its tests contain the banned words; exclude its directory or build the list from encoded fragments, or the check fails on itself and gets disabled.
- Run order: this check is cheap and should run on every PR touching `website/**`, `README.md`, `tests/e2e/website-demos/**`, `docs/**` synced to the site, and the theme files, with the full built-`dist` variant in `deploy-website.yml`'s build job before the Pages upload.

## 10. Top risks ranked for planning

1. Trademark leakage and the code rename: UI label "WH40K" in the theme picker plus mentions in website sources and the synced help doc; the rename to Grimdark must migrate the persisted `stapler-theme` id (else users silently fall back to Clean), accept legacy `base: wh40k` in user themes, move the snapshot dir as a pure rename, and be paired with a published-content scanner (HTML, search index, filenames, captured DOM text) that ignores lockfiles and hashes (section 9b).
2. Silent staleness/fallback: today a failed recording quietly ships old screenshots, and the committed `features.json` and asset-health manifest assume pre-recorded Release assets; the new gate needs an explicit expected-clip list, a sidecar build stamp, and removal of the committed-screenshot fallback in the same change.
3. Determinism and leakage of environment data: wall-clock seed data, hostnames/temp worktree paths on screen, unmocked history/GitHub data, font fallback and flag-gated pages redirecting. Each needs a capture-time assertion (theme class, final URL, banned-text scan, fonts ready), not just a visual review.
4. Media commit guard and ratchet design: must be diff-based against `origin/main`, extension-based with an allowlist, and per-feature for the registry baseline, to avoid legacy-file lockout and merge conflicts.
5. Runner time and artifact growth: shard recording, build the binary once, keep PR runs to a smoke subset, set per-asset and total `dist` budgets, and plan the `concurrency: pages` queueing behind a long record job.
