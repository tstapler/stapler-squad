# Architecture Review: rum-session-diagnostic-bundle
**Date**: 2026-10-16
**Verdict**: BLOCKED

Three compile-stopping method-name mismatches must be fixed in the plan before any code is written. Eight additional concerns flag structural and safety issues that will cause real bugs or painful maintenance if deferred.

---

## Blockers

- [ ] **Story 1.3.1, Task 1.3.1a (step 8)** — `GetSessionArtifacts` takes `title string`, not session UUID — the plan's assembly pipeline treats it as a UUID lookup, but `session/ent_repository.go:1064` is `GetSessionArtifacts(ctx context.Context, title string) (string, error)`. At the call site in `assembleBundle` the types won't match, or silently the wrong session's artifacts will be fetched. Remediation: add a new `GetSessionArtifactsByUUID(ctx, sessionUUID string) (string, error)` method to the `Storage` interface and `EntRepository`, and add it to Story 1.1 as a data-layer extension task alongside `ListAnalyticsBySessionID`.

- [ ] **Story 1.3.1, Task 1.3.1a (step 4, architecture.md §1.6)** — `Storage.GetItemSessionsBySessionUUID` does not exist — the plan references a plural form that returns a slice of backlog linkages, but the real method is `GetItemSessionBySessionUUID` (singular, `session/storage_backlog.go:386`), which returns only the single most-recent `ItemSessionSummary` and raises `ErrNotFound` if none. A session with both a work and a review ItemSession would silently drop the older one. Remediation: decide whether single-latest is acceptable (document it and update the glossary entry for `BacklogLinkage`), or add a `ListItemSessionsBySessionUUID` method that returns all rows. Either way, update every reference in plan.md to the correct method name.

- [ ] **Story 1.3.1, Task 1.3.1a (step 7)** — `ctxHistory.GetSessionSummary` does not exist — the plan's assembly pipeline calls this method, but `session/contexthistory/store.go` exposes `SummarizeSession(ctx, sessionUUID string) (SessionSummary, error)` (line 162) and `Series(ctx, sessionUUID string) ([]Sample, error)` (line 147). No `GetSessionSummary` method exists on `*contexthistory.Store`. Remediation: replace `GetSessionSummary` with `SummarizeSession` in the assembly pipeline description and in every subsequent task that references it.

## Concerns

- [ ] **Story 4.1.1a (unit tests), Story 1.3.1** — ISP violation: `SessionBundleService` depends on `*session.Storage` (fat interface) — the assembler uses at most five methods (`GetSession`, `ListAnalyticsBySessionID`, `GetItemSession[s]BySessionUUID`, `GetSessionArtifactsByUUID`), but the `Storage` interface has well over 100 methods. The plan's unit test instructs creating "a fake in-memory `Storage` implementing `session.Storage` interface" without acknowledging that this requires implementing all of those methods. Recommendation: define a narrow `BundleStorage` interface in `server/services/session_bundle_service.go` containing only the four methods the assembler needs. `*session.Storage` satisfies it structurally; the test fake becomes trivial. This follows the existing `DiagnosticService` pattern of accepting a typed concrete dep rather than the full fat interface — though in this case an interface is the right call.

- [ ] **Story 4.1.1a, Story 1.3.1** — No interface for `*contexthistory.Store` prevents test injection — `contexthistory.Store` is a concrete struct with no exported interface. The plan's nil-guard ("omit section when nil") means context history is never covered by a positive test path — there is no way to inject a fake with known samples. Recommendation: define a narrow `ContextHistoryReader` interface with `SummarizeSession` and `Series`; have `SessionBundleService` depend on that. Unit tests can then inject a fake reader with controlled samples.

- [ ] **Story 1.3.2, Task 1.3.2a** — Full ZIP assembled in memory before streaming; OOM risk not fully mitigated — `assembleBundle` returns `[]byte` (the entire ZIP in memory), which `ExportSessionBundle` then chunks into 64 KB slices. A 50 MB bundle means 50 MB is allocated before the first chunk is sent, defeating the main motivation for choosing streaming over unary. The acceptance criteria cap of 50 MB uncompressed remains a real allocation. Recommendation: document this explicitly in the implementation notes and add a hard pre-flight guard (`if estimatedUncompressedBytes > 50*1024*1024 { return CodeResourceExhausted }`) before calling the ZIP writer, consistent with the disk-space guard already planned for `SaveSessionBundle`.

- [ ] **Story 1.3.3, Task 1.3.3b** — `RunDiagnosticsRetention` called synchronously during `BuildRuntimeDeps` — the task says to call `services.RunDiagnosticsRetention(...)` inside `BuildRuntimeDeps`, which is synchronous startup code. A stale or large diagnostics directory (many files, slow filesystem) would delay server startup. The analogy the plan cites, `contexthistory.Store.Prune`, is launched with a `go` prefix inside `BuildRuntimeDeps` (see the recorder goroutine on line 1363). Remediation: wrap the call in `go func() { ... }()` with its own context, logging errors but not blocking startup.

- [ ] **Story 3.1.1, Task 3.1.1a** — Module-level OTel UUID state races with in-flight RPCs during session navigation — `let activeSessionUUID: string | null = null` is set on mount and cleared on unmount, but React's strict-mode double-invocation and the async nature of streaming RPCs mean that when a user navigates from session A to session B, session A's still-in-flight `ExportSessionBundle` stream's spans could be tagged with session B's UUID. The plan acknowledges the mount/unmount ordering but not the in-flight async overlap. Recommendation: capture the UUID at call-site (i.e., close over it when the RPC starts) rather than reading the mutable global when each span is created.

- [ ] **Story 3.1.2, Task 3.1.2a** — `WebVitalsReporter` coupled to `otel-init.ts` via `getActiveSessionUUID` — the plan wires analytics session labeling through the OTel module (`import { getActiveSessionUUID } from './telemetry/otel-init'`). Analytics and distributed tracing are separate concerns; this cross-module dependency means adding a `sessionId` to analytics events requires importing a tracing module. Recommendation: pass `sessionId` as a prop to `WebVitalsReporter` from `SessionDetailView` (which already has `session.uuid` in scope) rather than reaching into `otel-init.ts`. This eliminates the coupling and makes `WebVitalsReporter` testable without mocking the OTel module.

- [ ] **Story 1.3.3, Task 1.3.3a** — `output_dir` parameter lacks path-traversal validation — when `req.Msg.OutputDir` is non-empty, the plan uses it directly as the write directory without sanitization. A caller supplying `"../../etc"` could write outside `~/.stapler-squad/`. Recommendation: validate that `filepath.Abs(outputDir)` has `strings.HasPrefix(abs, config.GetConfigDir())` before use, and return `connect.CodeInvalidArgument` if the check fails.

- [ ] **Epic 2.1 + Epic 2.2** — `ExportBundleModal` SRP violation: single component handles delivery mode, consent, export progress, and backlog item creation — Story 2.2.1 adds the "Create backlog item" callback, toast, and "View backlog item →" link to the same modal component that already manages radio selection, consent checkbox, streaming progress, and error display. This is four responsibilities in one component. Recommendation: extract backlog hand-off into a child component (e.g., `BundleBacklogHandoff`) rendered conditionally after a successful save, keeping `ExportBundleModal` scoped to delivery-mode selection and export triggering.

## Nitpicks

- **Pattern Decisions table: "Builder pattern (GoF)" label is incorrect** — `assembleBundle` is a sequential pipeline function, not a GoF Builder (which requires a director, a builder interface, and step accumulation via chainable methods). The actual pattern is a Collection Pipeline or Façade. Mislabeled patterns cause confusion when future maintainers look for a `BundleBuilder` type that does not exist. Correct the label to "Collection Pipeline" or "Façade over data-source adapters."

- **Tech Debt Disposition table omits Pitfall #7 (OTel high-cardinality)** — `pitfalls.md` explicitly flags `session.uuid` on all spans as HIGH cardinality risk that could cause unexpected cost spikes. Story 3.1.1 mitigates this ("only attach to session-scoped spans"), but the Disposition table has no row tracking this commitment. Add a row: Area = `web-app/src/lib/telemetry/otel-init.ts`, Issue = "Adding session.uuid to all spans creates high-cardinality attribute at SampleRate=1.0", Disposition = "Scoped to session-context spans only via custom SpanProcessor".

- **Architecture.md §1.4 says cap at 5,000 scrollback lines; plan.md says 500** — the research phase recommended 5,000, the plan reduced it to 500. The reduction is defensible (smaller default bundle size, less PII exposure) but nowhere in the plan is the architectural decision documented. A one-line note in the Migration Plan or Unresolved Questions section would prevent future confusion.
