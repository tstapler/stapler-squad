# Adversarial Review: rum-session-diagnostic-bundle

**Date**: 2026-10-16
**Verdict**: BLOCKED

## Blockers

- [ ] **`Storage.GetItemSessionsBySessionUUID` does not exist** — The domain glossary lists backlog linkage as "Sourced via `Storage.GetItemSessionsBySessionUUID`" and the assembly pipeline (Task 1.3.1a step 4) relies on it, but this method is absent from `session/repository.go` and `session/storage.go`. The only related method is `GetAllItemSessionsWithBacklogInfo()` which returns ALL item sessions globally (no per-session filter). `SessionBundleService`'s constructor `NewSessionBundleService(storage, ctxHistory, scrollback)` also includes no `BacklogService` reference. As written, the backlog linkage section has no viable code path — it will not compile. Resolution: add a new `Storage` interface method `GetItemSessionsBySessionUUID(ctx context.Context, sessionUUID string) ([]ItemSessionBacklogEntry, error)` to `session/repository.go` and implement it in `session/ent_repository_backlog.go`. This is a full new story not in the plan.

- [ ] **Wrong scrollback API for tail — plan will silently bundle the oldest lines, not the newest** — Task 1.3.1a step 5 says "collect scrollback tail, capped at `min(maxScrollbackLines, 500)`" but never names the API. `GetScrollback(sessionID, 0, 500)` — the most obvious call — returns the **oldest** 500 lines (ascending from seq=0). The bundle intent is the tail (most recent). The correct API is `GetRecentLines(sessionID, 500)` (defined at `session/scrollback/manager.go:111`), which returns the last N lines as `[]byte`. After `FlushSession` drains the in-memory buffer, `GetRecentLines` reads only from storage and returns the correct tail. `GetScrollbackBefore` also works but is more complex. Without explicit guidance, an implementor will default to `GetScrollback` and produce a bundle with the wrong content. Resolution: name `GetRecentLines` explicitly in Task 1.3.1a.

- [ ] **Plan calls `ctxHistory.GetSessionSummary` — method does not exist** — Task 1.3.1a step 7 calls `ctxHistory.GetSessionSummary(ctx, sessionUUID)`, but `session/contexthistory/store.go` exports `SummarizeSession(ctx context.Context, sessionUUID string) (SessionSummary, error)`. This will fail to compile. Resolution: replace `GetSessionSummary` with `SummarizeSession` in the task text.

## Concerns

- [ ] **`ListAnalyticsBySessionID` query returns oldest events, not newest (AC contradicts task)** — Story 1.1.1 AC says "at most 2,000 events returned (the most-recent 2,000 by `created_at`)" but Task 1.1.1b specifies `Order(analyticsevent.ByCreatedAt())` which is ascending — returning the **oldest** 2,000. All other analytics queries in `session/ent_repository.go` (lines 1872, 1924, 1941, 1998) use `Order(ent.Desc(...))`. Resolution: change `Order(analyticsevent.ByCreatedAt())` to `Order(ent.Desc(analyticsevent.ByCreatedAt()))` in Task 1.1.1b.

- [ ] **`output_dir` in `SaveSessionBundleRequest` accepts arbitrary paths with no validation** — Task 1.3.3a resolves the output directory from `req.Msg.OutputDir` when non-empty without any path sanitization. An authenticated user can pass `output_dir = "../../etc"` or an absolute path outside the diagnostics directory to write bundles anywhere the server process can write. The existing pattern in `server/services/local_file_service.go:64–65` uses `filepath.IsAbs` + a prefix check against the allowed root. Resolution: validate `output_dir` by cleaning the path and confirming it is either empty (default) or starts with `config.GetConfigDir()` — reject with `connect.CodeInvalidArgument` otherwise.

- [ ] **`syscall.Statfs` will not compile on Windows** — Task 1.3.3a uses `syscall.Statfs` for the disk-space guard. The codebase targets Linux, macOS, and Windows (WSL2 per CLAUDE.md). `syscall.Statfs` is not available on Windows. The codebase already handles this split via `exec_unix.go`/`exec_windows.go` build-tag pairs. Resolution: either move the disk-space check to a `disk_space_unix.go` + `disk_space_windows.go` pair (return 0/nil on Windows) or use `golang.org/x/sys/unix.Statfs_t` under a `!windows` build tag.

- [ ] **DiagnosticsRetention runs only at startup, not periodically** — Task 1.3.3b registers `RunDiagnosticsRetention` in `BuildRuntimeDeps`. A long-running daemon that never restarts will never prune its diagnostics directory. The pitfalls doc (`research/pitfalls.md:4`) explicitly flagged this and said "startup or a periodic timer"; the plan chose startup only. At 10–50 MB per bundle, a daemon that runs for months without restart will accumulate gigabytes. Resolution: schedule `RunDiagnosticsRetention` on a 24-hour ticker in addition to startup, matching the pattern of `analytics/retention.go:EnforceRetention`.

- [ ] **`assembleBundle` assembles the full ZIP into a `[]byte` before streaming — peak allocation is the full bundle size** — Despite using server-streaming for delivery, `ExportSessionBundle` calls `assembleBundle` which constructs the entire zip in memory and returns `[]byte zipBytes` before the first chunk is sent. A 50 MB bundle allocates 50 MB on the heap per export request. With multiple concurrent exports, this multiplies. The streaming approach was chosen to avoid the 4 MB unary ConnectRPC limit (ADR-001), but the plan doesn't eliminate the peak allocation — it only distributes delivery. This needs a comment in the plan documenting it as a known limitation, and a note that concurrent exports should be bounded (e.g., a semaphore of 2–3).

- [ ] **No context cancellation checks inside `assembleBundle`** — `assembleBundle` runs up to 5 seconds across 8 sequential pipeline steps. If the client disconnects mid-assembly (e.g. navigates away), the server holds the request's resources for the full remaining assembly time. The `ctx` passed from the streaming handler is cancelled on client disconnect; none of the 8 steps check `ctx.Err()`. Resolution: add a `ctx.Err()` check between each step (steps 1–8 in Task 1.3.1a), returning early with the context error.

- [ ] **`ScrollbackManager` is a concrete struct — `assembleBundle` is not unit-testable via dependency injection** — Task 4.1.1a describes tests using a "fake in-memory `Storage`" but `SessionBundleService` holds a `*scrollback.ScrollbackManager` (concrete type). Test `TestAssembleBundle_CompletesWithinDeadline` needs to inject 10,000 fake scrollback lines, which requires either a `ScrollbackManager` interface in the new service or constructing a real `ScrollbackManager` with in-memory storage in the test. Neither is in the plan. Resolution: define a `ScrollbackReader` interface (e.g., `GetRecentLines(sessionID string, n int) ([]byte, error)`) in `session_bundle_service.go`, accept it in the constructor, and wire the real `*scrollback.ScrollbackManager` in production. Tests get a simple fake.

- [ ] **`WebVitalsReporter` captures session UUID at event-fire time, not event-start time** — CLS and LCP can fire long after the user has navigated to a different session. `getActiveSessionUUID()` is a module-level variable read at fire time. A CLS event triggered while viewing session A may fire after the user navigated to session B, incorrectly tagging session B's UUID on the event. Resolution: `WebVitalsReporter` should capture the UUID at mount time via a `useRef` snapshot and pass that stable value to each vitals callback's closure, not call `getActiveSessionUUID()` inside the callback.

## Minors

- **PII consent copy is "blocking" but the text is already in the document** — The Unresolved Questions section marks consent copy as blocking Story 2.1.2 (owner: product/design) while the Risk Control section already provides the exact text: `"This bundle may contain raw terminal output including typed credentials. Do not share it with untrusted parties."` The blocker is not actually blocking if the team accepts the text already written. Treat it as a design-review checkpoint, not a hard block.

- **`BundleChunk.final = true` edge case when bundle size is exactly a multiple of 64 KB** — The loop in Task 1.3.2a sends `final=true` on the last non-zero chunk, but if `len(zipBytes)` is exactly N×65536, the last non-empty chunk is already index `N-1`. A following zero-byte "final" chunk would be an off-by-one depending on loop implementation. The client reassembler needs to handle this. Add a test case for exactly-64KB bundles.

- **`window.innerWidth < 640` detects narrow viewport, not mobile device** — `ExportBundleModal` pre-selects "Save on server" on mobile via this heuristic. A narrow desktop window (e.g. split-screen) triggers the same default. This is likely acceptable per the UX research but differs from a device-type check. Document the intent if this behavior is intentional.

- **`SummarizeSession` returns a summary struct, not raw per-turn samples** — The bundle's context history section will contain aggregate statistics (min/max/ceiling fractions) rather than raw per-turn token counts. For debugging a specific conversation the raw `Series(ctx, sessionUUID)` data is more useful. Consider including the raw series as a separate file and the summary as metadata. Minor value-of-data issue, not a correctness bug.

- **Feature registry file `docs/registry/features/rum-bundle.json` must be committed by the implementor** — The file is generated by `make registry-generate` and excluded from `.gitignore`, but the plan states it as "(new, generated)" and says to commit it. CI already enforces the registry is up to date (per CLAUDE.md). This is an operational reminder, not a gap.
