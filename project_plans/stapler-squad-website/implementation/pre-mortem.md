# Pre-mortem: stapler-squad-website
**Date**: 2026-10-14

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The ≥90 Lighthouse gate (Epic 6.1) is only run after all of Phases 3–5 content exists; the autoplay hero `<video>`, the client-side `prefers-reduced-motion` script, and Starlight's Pagefind search index all add JS/network weight that Astro's "zero-JS islands" pitch doesn't actually guarantee for a content-heavy marketing page, so the first real Lighthouse run fails performance and forces late rework across already-"done" phases. | `website/lighthouserc.json`'s CI job fails on `performance` (not `accessibility`) after Phase 6 begins, on a page that every earlier phase treated as finished. | Run a cheap Lighthouse smoke-check at the end of Phase 1 (on the empty scaffold, to get a performance baseline) and again right after Phase 3 lands (hero video + feature grid), not only once in Phase 6; add it as a non-blocking PR check into `website/**` earlier so regressions are visible incrementally instead of as one large Phase 6 surprise. | P2 |
| 2 | `CuratedDoc`s drift from their `SourceDoc`s after launch: `sync-content.mjs` is explicitly "run on-demand, not on every deploy" (per the Domain Glossary), and nothing in the deploy workflow compares a `SourceDoc`'s current content against what was last synced — so a `docs/how-to/*.md` file fixed or changed post-launch never propagates, and the public Troubleshooting page keeps telling users an outdated procedure indefinitely. | A user follows a published troubleshooting step that contradicts the current (already-updated) behavior described in the live `docs/how-to/` source file. | Add a `check-content-freshness` step (extend `sync-content.mjs` with a `--check` mode) that compares each manifest entry's recorded source hash/mtime against the live file and fails the build — or at minimum posts a visible warning — when a `SourceDoc` changed since its last sync, per Task 6.3.1a's "idempotency check" pattern (which only catches an unsynced manifest, not a changed source). | P2 |
| 3 | The hero's value-prop sentence and install command are lifted "verbatim" from `README.md` at authoring time (Story 3.1.1's AC), but `deploy-website.yml`'s path filter (Task 6.3.1a) only covers `website/**`, `docs/how-to/**`, and `docs/features.md` — not `README.md` — so a later README wording/command change (a near-certain event in an actively developed repo) never triggers a redeploy or any re-check, and the two sources silently diverge with no CI signal. | A visitor copies the landing page's install command, it differs from the current README's, and troubleshooting the mismatch burns their first five seconds instead of converting them. | Add `README.md` to the `paths:` filter so a README edit alone triggers a rebuild, and add a small build-time assertion (in `check-internal-links.mjs` or a new script) that re-extracts the tagline/install command from the live `README.md` and fails the build if it no longer matches the hero's hardcoded copy — turning the one-time "lifted verbatim" AC into an ongoing invariant. | P3 |
| 4 | `website-demo-publish.yml` is `workflow_dispatch`-only by design (to avoid the CI-cost problem that got the old cadence disabled), so breakage from e2e fixture drift (`tests/e2e/pages/` changes, UI changes) accumulates silently for however long passes between manual triggers — and when someone finally runs it, either all 5 `FeatureSpec`s fail at once with compounded, hard-to-isolate causes, or worse, it succeeds and silently publishes clips of now-stale/incorrect UI that nobody reviews before they go live as the site's flagship "higher production value" demo media. | A maintainer manually triggers the recording workflow months after launch and gets either a wall of failures across unrelated specs, or clips that visibly show deprecated UI once someone finally looks. | Add a lightweight `schedule:`-triggered dry-run (separate from the publish-triggering `workflow_dispatch`) that runs the 5 `FeatureSpec`s on a monthly cadence and only reports pass/fail (discarding the recording, never publishing/clobbering), so fixture drift is caught within weeks instead of whenever someone happens to need fresh clips. | P2 |
| 5 | `ReleaseAssetRef`'s `website-demo-gifs-latest` tag is overwritten via `gh release upload --clobber`, so a filename's URL is stable but its *content* is not; `AssetHealthCheck` (Epic 2.2) only HEAD-checks for a 2xx/3xx response, which tells it nothing about whether the bytes behind that URL are the new clip, the old clip (during GitHub's CDN propagation window), or a corrupted partial upload from an interrupted `--clobber` run — so the landing page's primary conversion asset can silently show wrong or broken media while every automated check reports green. | The hero or feature-grid video embed shows an outdated/incorrect UI capture, or fails to play at all, despite `check-asset-health.mjs` and the live-verification tasks (5.1.2, 6.3.1b) having passed. | Add a content hash to the verification surface: record each published `DemoClip`'s expected SHA256 (or a short version suffix baked into the filename on publish) in a small checked-in manifest, and have `check-asset-health.mjs` diff actual-vs-expected hash instead of just status code — the one check in the plan explicitly designed to catch "is this asset real" needs to also catch "is this asset the right one," which `--clobber` guarantees will eventually matter. | P1 |

## P1 Items (address before implementation)
- [x] Failure #5 (`--clobber` content-staleness invisible to AssetHealthCheck) — add a content-hash/version-suffix check to `website/scripts/check-asset-health.mjs` and wire the expected-hash manifest into Epic 2.2's Story 2.2.1 acceptance criteria before Task 2.2.1b is implemented, so the health check validates content identity, not just HTTP status. Addressed in `plan.md`: Story 2.2.1 AC + Task 2.2.1b now require a SHA256 hash comparison against a new `AssetHealthManifest` (`website/scripts/asset-health-manifest.json`), written by Story 5.1.1/Task 5.1.1b at publish time.
