## Blockers
- [x] **RESOLVED** (verified via independent re-check agent, 2026-10-14): Story 3.1.1's AC now reads the exact README.md:50 command verbatim (`brew tap tstapler/stapler-squad https://github.com/tstapler/stapler-squad && brew install tstapler/stapler-squad/stapler-squad`), confirmed character-for-character against the live file, with no other stale occurrence of the wrong command anywhere in plan.md. Original finding preserved below for context.
  - **Story 3.1.1 (Hero install CTA, Task 3.1.1a)** — The acceptance criteria's literal clipboard-content string is wrong versus the actual source it claims to lift verbatim. AC says: *"the clipboard contains the exact text `brew tap tstapler/stapler-squad && brew install stapler-squad`"*. The real command, `README.md:50`, is:
  ```
  brew tap tstapler/stapler-squad https://github.com/tstapler/stapler-squad && brew install tstapler/stapler-squad/stapler-squad
  ```
  The AC's string both drops the explicit tap URL and uses the wrong formula path (`brew install stapler-squad` instead of `brew install tstapler/stapler-squad/stapler-squad`). If an implementer treats the AC as ground truth (the norm in this SDD workflow), the single highest-stakes CTA on the entire site — the install command, per `requirements.md`'s own Success Metrics — ships non-functional. This also contradicts the plan's own stated principle (Story 3.1.1: "reuses the README's value prop verbatim, not reworded copy") — the spec itself violates "verbatim" by silently paraphrasing the command it claims to transcribe exactly, which is the parse-don't-validate failure mode: a hand-copied literal should never have been re-derived by eye into a planning doc in the first place.
  **Remediation**: Rewrite Task 3.1.1a's acceptance criteria to say "verbatim copy of the Homebrew line in README.md's Installation section" rather than a hardcoded string, and derive the actual snippet in `InstallCommand.astro` from README at content-authoring time (or, better, factor both README and the site's component to read from one shared plain-text/data source so this class of transcription drift can't recur). Verify the literal command once implemented, by actually running it.

## Concerns
- [ ] **Story 3.2.1 / Story 4.2.1 (FeatureCard data set)** — The plan's own numbers are internally wrong. `docs/features.md` has **18** `## ` sections (`grep -c "^## " docs/features.md` → 18), not the "17" cited throughout (Story 3.2.1, Story 4.2.1, the Domain Glossary's implicit framing). Of those 18, **9** have an existing screenshot (`grep -n "!\[" docs/features.md` → 9 matches, including the broken `09-unfinished.png`), leaving **9** without a screenshot, not the "8" Story 3.3.1 and Story 4.2.1 both state. This means Task 3.2.1a's and 4.2.1a's acceptance criteria are unverifiable as literally written — whichever implementer builds `features.json` will find a count mismatch against the stated AC the moment they walk the real file. — **Remediation**: recount against the live file before implementation starts (trivial — this review already did it), and fix the "17"/"8" references to "18"/"9" throughout Stories 3.2.1, 3.3.1, and 4.2.1.

- [ ] **Epic 5.1 (WebsiteDemoWorkflow) — `FEATURE_SPECS` duplicated across two workflow files with no shared source** — `demo-publish.yml` hardcodes its curated spec list as a literal YAML `env:` block (confirmed: `demo.spec.ts`, `review-queue.spec.ts`, `session-lifecycle.spec.ts`, `history-search.spec.ts`, `workspace-management.spec.ts`). Story 5.1.1's Task 5.1.1a copies this same list, by hand, into a second file (`website-demo-publish.yml`). The AC only checks the two lists match *at write time* ("contains exactly the same five specs"); nothing structurally prevents them from diverging later — if someone edits `demo-publish.yml`'s curated set (adds a newly-stabilized spec, drops a newly-flaky one), `website-demo-publish.yml` has no mechanism to follow, and no test re-checks the two lists stay in sync going forward. This is exactly the primitive-obsession/illegal-state gap type-driven design flags: two free-standing string lists that are supposed to represent one conceptual set, with no single source of truth. — **Remediation**: extract `FEATURE_SPECS` into one shared location both workflows read (a composite action input, a `scripts/feature-specs.json` both `env:` blocks source via a `jq`/`yq` step, or a reusable workflow) rather than a second hand-maintained copy; at minimum, add a CI lint step that diffs the two lists and fails on drift.

- [ ] **ADR-002 / `ReleaseAssetRef`'s `tag` parameter is a bare string, not a closed set** — `releaseAssetUrl({ tag, name, ext })` takes `tag` as a free-form string. The repo now has two superficially similar, easy-to-confuse release tags for the same kind of content: the pre-existing `demo-gifs-latest` (owned by `demo-publish.yml`, feeding README's committed `assets/demo.gif`) and the new `website-demo-gifs-latest` (owned by `website-demo-publish.yml`). ADR-002 and `research/architecture.md` §2 both explicitly call out that these two must never collide — but nothing in the type signature stops a future call site from passing the *wrong* one (a typo, or a lazy copy-paste from an example that used the other tag), silently coupling the site to the wrong release's lifecycle. This is the canonical "primitive obsession where a sum type belongs" case this project's own Pattern Decisions table already applied correctly to `IncludeDecision` — it just wasn't applied here too. — **Remediation**: narrow `tag`'s type to a union of the one (or two, if ever needed) legitimate literals (e.g. `type ReleaseTag = "website-demo-gifs-latest"`) rather than `string`, or default it with no override needed for the common path, making "wrong tag" a compile-time error instead of a runtime 404 `AssetHealthCheck` has to catch.

- [ ] **Epic 1.1 (deploy spike) doesn't validate the single premise ADR-001 rests its override on** — ADR-001's decisive argument for Astro+Starlight over `research/build-vs-buy.md`'s Nextra pick is that zero-JS-by-default is "a direct, mechanical answer" to the ≥90 Lighthouse NFR. That claim is sound in direction (well-established SSG performance behavior) but is not empirically checked against this project's actual scaffold until Phase 6 (Epic 6.1), after Phases 2–5 have built an entire site's worth of content on top of the choice. Compare: the *other* big "works locally, breaks live" risk (Pages/BasePath config) gets exactly this kind of early, live verification in Story 1.1.2 ("Prove the GitHub Pages deploy end-to-end against the live URL... before any content work depends on it") — the plan applies "verify live, don't just reason" rigor to one load-bearing premise but not the other, even though both are named as the two biggest risk classes in `research/pitfalls.md`. If Starlight's defaults (Pagefind's JS payload, the splash template, video embeds) don't actually clear ≥90 in practice, that's discovered only after 4 phases of sunk content work. — **Remediation**: add a minimal Lighthouse smoke-check to Story 1.1.2's acceptance criteria (run Lighthouse CI against the bare scaffold, before any content lands) so the ADR's deciding premise is retired at the same point the deploy-mechanics premise is.

- [ ] **Docs-curation transform pass (ADR-003 / Story 2.1.1) only guards against leaked internal *links*, not leaked internal *content*** — Task 2.1.1b's transform pass strips/rewrites links into out-of-scope paths, and Story 2.1.1's acceptance criteria test only that case (a `project_plans/` link is removed). But "curated subset, not a mirror" (`requirements.md` Scope) is a content-leakage concern, not just a link-leakage one — a dev-facing how-to file can reference internal-only facts (a hostname, an internal tool name, a teammate's name, an unreleased feature) in prose with no hyperlink at all, and nothing in the transform pass or its acceptance criteria would catch that. (This review manually grepped the 11 included files for one known example — internal hostnames like `onyx.staplerhome.internal` — and found none today, but that was a one-time manual check, not a build-time gate; the mechanism doesn't generalize to the next edit of any of these 11 source files.) — **Remediation**: either extend `transform-markdown.mjs` with a small denylist/pattern check (internal hostnames, known internal tool names, `project_plans`/`CLAUDE.md`-adjacent prose mentions even without a link) that fails loudly like the missing-source check already does, or make Task 2.1.2a's file-by-file classification pass include a full-body content read (not just a title/topic judgment) with that risk named explicitly in the manifest's `reason` field for each included file.

- [ ] **No isolation-level tests for the project's only nontrivial custom logic** — `sync-content.mjs`, `transform-markdown.mjs`, `check-asset-health.mjs`, and `check-internal-links.mjs` are each specified only via end-to-end "Given the manifest/built output, When the script runs, Then..." acceptance criteria — i.e. verified by running the real script against real content, not by a fixture-based unit test. This is the testability lens's core question (can each component be tested in isolation?) and the answer as planned is no: `transform-markdown.mjs`'s link-rewrite regex in particular is the single most error-prone piece of logic in the project (string/regex manipulation of arbitrary Markdown) and has no task anywhere allocating a `*.test.mjs` file with input/output fixture pairs. Phase 6 does this correctly for a11y (`website/tests/a11y.spec.ts`) — the same discipline is missing for the scripts phase. — **Remediation**: add a small unit-test task to Story 2.1.1 (feed `transform-markdown.mjs` a handful of fixture Markdown strings, assert the transformed output) and to Story 2.2.1/4.4.1 (feed `release-asset.ts`/`check-internal-links.mjs` known-good and known-bad inputs) rather than relying solely on full-build verification.

- `ContentManifest`'s `slug` field and `astro.config.mjs`'s sidebar config (Task 4.3.1a) are two independently hand-maintained lists of the same logical "11 included slugs" set, with no shared constant and no build-time check that they stay in sync (unlike `AssetHealthCheck`/`BrokenLinkCheck`, which do check adjacent classes of drift). Low current risk given it's a one-time Phase-4 wiring task, but worth a one-line note if the curated set grows later.
- Minor citation drift: Story 3.1.1's AC cites "`README.md:3`" for the hero tagline; the actual text is on `README.md:2`. Inconsequential but worth a find-and-replace pass given this review's broader finding that transcribed source text in this plan has drifted from the source twice already (see the install-command Blocker above).

## Astro vs. Nextra override — verdict
Sound, well-justified override, not an under-justified one. ADR-001 resolves a genuine disagreement between research tracks using the requirement's own explicit, measurable NFR (Lighthouse ≥90) as the tie-breaker — a technically correct, well-established point (Astro's zero-JS islands vs. React-hydration-by-default even for "static" Nextra output) — and corroborates it with a second, independently-reasoned research track (`research/architecture.md`) that arrived at "don't reuse `web-app/`'s toolchain" from unrelated angles (deploy-target mismatch, `web-app/next.config.ts`'s Go-embed-tuned config already doing double duty). The asymmetric-verification critique (Nextra's release health was never `gh api`-checked the way Starlight/VitePress/Docusaurus were) is a legitimate methodological point, not a rationalization. The one real gap: the Lighthouse premise itself isn't empirically checked against this project's actual scaffold until Phase 6, four phases after the choice is irreversibly built on — flagged above as a Concern, not a reason to reverse the decision.

## Summary
**Verdict: CONCERNS** — 0 blockers remaining (1 resolved, see Blockers section), 7 concerns, 3 nitpicks. The Astro-over-Nextra ADR-001 override is sound and well-evidenced; the one blocker is a transcription defect (the install-CTA command string in Story 3.1.1 doesn't match the real README command it claims to copy verbatim) that would ship a non-functional primary CTA if implemented literally. The concerns cluster around three themes: (1) two more factual/count errors in the plan's own acceptance criteria (features.md's 17-vs-18/8-vs-9 section counts), (2) two primitive-obsession gaps the project's own type-driven-design conventions should have caught (`FEATURE_SPECS` duplicated with no shared source; `ReleaseAssetRef.tag` as a bare string instead of a closed set), and (3) two testability/scope gaps (no fixture-based unit tests for the custom scripts; the Lighthouse premise behind ADR-001 isn't checked until Phase 6).
