## Concerns

- [ ] **No runtime fallback for a demo clip that 404s after a successful deploy.** `AssetHealthCheck` (Epic 2.2) only runs at `deploy-website.yml` build time, which is only triggered by pushes to `website/**`, `docs/how-to/**`, or `docs/features.md` — not by a `website-demo-publish.yml` run (Phase 5) that renames or re-clobbers a clip. Between site deploys, a clip rename in the demo-recording workflow can leave a broken embed live with no detection until the next unrelated content push, and only the hero video (Story 3.3.1) gets a `poster` fallback — feature-grid clips embedded via `ReleaseAssetRef` have no `<video onerror>`/poster/fallback-UI path specified for a post-deploy 404. ADR-002 explicitly accepts this as a documented gap for *renames*, but doesn't address the no-runtime-fallback half. — **Recommendation**: add a poster/fallback image to every `ReleaseAssetRef`-backed embed (cheap, consistent with the hero's existing pattern), and consider a lightweight scheduled (e.g. weekly) workflow that runs only `check-asset-health.mjs` against the live site (no rebuild/redeploy) and opens an issue on failure, decoupling detection from "something else happened to touch `website/**` recently."

- [ ] **ADR-003 and the plan's own Task 6.3.1a disagree on whether `sync-content` runs in the deploy workflow.** ADR-003 states: "the sync step deliberately does not run as part of the deploy workflow ... to avoid re-introducing an unreviewed live-mirror." Plan.md's Epic 6.3 / Task 6.3.1a wires `pnpm run sync-content` into `deploy-website.yml`'s build job as a blocking idempotency check ("fails if running it produces a diff"). The *substance* is fine (read-only diff check, not a write-and-commit mirror) and actually gives good automatic protection against the "renamed/deleted source doc" failure mode this review was asked to check — but the ADR's literal text contradicts the plan's task, which will confuse whoever implements or reviews against "the ADR is the source of truth." — **Recommendation**: amend ADR-003's Consequences section to distinguish the sync script's *write* path (on-demand, human/agent-run, committed) from the *read-only idempotency check* now wired into deploy, so the two documents agree.

- [ ] **The demo-recording workflow's `workflow_dispatch`-only trigger discipline is verified once, in prose, not enforced structurally.** Story 5.1.1's AC checks the `on:` block by inspection at implementation time, and `research/pitfalls.md` §4 calls this "a near-mechanical review check" for Phase 6 — but no task in the plan adds an actual CI/lint gate (e.g. a `tools/lint` rule, or even a trivial grep-based test) asserting `website-demo-publish.yml`'s `on:` block never gains a `push`/`pull_request`/`schedule` trigger. This repo has explicit, repeated precedent for converting exactly this class of risk — "a future editor might silently reintroduce an incident" — into a structural check rather than a one-time review (see `.claude/rules/noarchivedrevival.md`, `.claude/rules/norawghrequest.md`, and the `quality:reflect-and-fix` skill's "eliminate the class, not the instance"), and `pitfalls.md` itself names the exact incident this would prevent (the 15.6GB git-bloat history / git-history-growth regression). — **Recommendation**: add a cheap automated check (shell/Go test asserting the workflow YAML's `on:` key is exactly `{workflow_dispatch: {}}`) to Phase 6, not just a comment + one-time AC.

- [ ] **README-sourced landing-page content has no staleness-detection mechanism, unlike `docs/how-to` content.** The hero tagline, install-command block, and `FeatureCard` descriptions reconciled from README's Highlights section (Stories 3.1.1, 3.2.1) are hand-copied into `website/src/content/docs/index.mdx` / `features.json` at write time. `deploy-website.yml`'s path filter (Task 6.3.1a: `website/**`, `docs/how-to/**`, `docs/features.md`) does not include `README.md`, and there is no `ContentManifest`/`sync-content`-equivalent for README-derived snippets. This is exactly the staleness risk ADR-003 built the whole manifest+sync machinery to solve for `docs/how-to/*`, left unaddressed for README content — if the Homebrew tap name or install command in README.md changes later, the site silently drifts out of sync with no build-time signal. — **Recommendation**: at minimum, add `README.md` to the deploy workflow's path filter (forces a rebuild, though not a correctness check) or extend the `ContentManifest` to cover the specific README snippets reused verbatim.

- [ ] **ffmpeg's `drawtext` filter (Task 5.2.1a's title-card stage) needs an explicit `fontfile=` path or a fontconfig-enabled build to resolve any font** — neither is specified in the task. This is a well-known, easy-to-hit ffmpeg/CI footgun (the filter either silently picks a default/missing font or fails outright depending on the runner's ffmpeg build) and the task only says "add the new filter-graph stage," not which font/path to pin. — **Recommendation**: pin an explicit `fontfile=` path (a committed TTF, or confirm `ubuntu-22.04`'s default `ffmpeg` package resolves fontconfig names) as part of Task 5.2.1a, not left to implementation-time discovery.

## Minors

- Starlight is explicitly the least-mature of the three dedicated-SSG candidates per `research/build-vs-buy.md` ("least install-base track record of the three") — ADR-001 discloses this and names VitePress as a same-deploy-mechanics-tier fallback, so this is an accepted, documented risk rather than a gap, but worth a quick revisit if Phase 1's scaffold hits a Starlight-specific limitation (as the plan itself anticipates).
- No retry/backoff guidance is given for a transient `actions/deploy-pages` failure beyond "re-run the workflow manually" (Risk Control's rollback procedure) — acceptable for a low-risk static site per `requirements.md`'s own framing, but a one-line "why no retry logic" comment in the workflow (mirroring this repo's convention of documenting trigger-discipline rationale inline) would be cheap insurance against a future "why doesn't this retry" question.
- The Effort Estimate table's per-story CU figures are INFERRED guesses with no Astro/Starlight-specific historical basis in this repo; the plan already flags this itself ("recalibrate after the first implementer run"), so it's self-aware rather than hidden — noted only for completeness.
