# Pre-mortem: detector-plugins
**Date**: 2026-08-01

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `DetectForProgram` (and everything this plan builds on top of it — `MergedRegistry`, `activeSnapshot`, hot-reload) has zero production call sites; real status detection runs through the separate `getDefaultPatterns()` generic path (`claude_controller.go`, `idle.go`, `command_executor.go`), so a user's override plugin can load, validate, and appear in `DetectorProvenance()` while never once changing what the web UI actually shows. | A user's plugin is confirmed loaded (log line + `DetectorProvenance()` entry + a future `detectors test` match) but their agent's status badge never changes even when the plugin's regex literally appears in the live terminal output. | Before implementation starts, resolve and record in plan.md which is true: (a) a planned follow-up wires `claude_controller.go`/`idle.go`/`command_executor.go` onto `DetectForProgram` via the session's known program name (`session/instance_program.go`), (b) this plan's scope is expanded to do that wiring itself, or (c) ship explicitly labeled as "registry + hot-reload machinery only; not yet wired into production status detection" so acceptance criterion #1 isn't silently claimed as done when it's false for the running app. | P1 |
| 2 | fsnotify degrades silently on WSL2 (inotify doesn't fire across drvfs/9p-backed mounts) and batches/delays on macOS (FSEvents coalescing), so hot-reload either never fires or takes far longer than the "within 2 seconds" acceptance criterion, falling back only to the 60s periodic rescan with no signal to the user that this happened. | The Story 2.3.3 "<2s" hot-reload test is flaky or fails outright on WSL2/macOS CI runners; in production, a user edits a plugin and waits up to 60s wondering if it worked, with no log distinguishing "fsnotify fired" from "periodic tick caught it." | Add a one-time `log.Info`/`log.Debug` line tagging each rebuild's trigger (`reason=fsnotify` vs `reason=periodic`) — this is already planned as a debug log per Task 2.3.3c's design, so promote it to something a user would actually see; document in plan.md/validation.md that the "<2s" bound is only guaranteed on native filesystems with working inotify/FSEvents, and relax or skip the timing assertion for CI runners on non-native filesystems. | P2 |
| 3 | The RE2-only, no-sandbox trust boundary (ADR-004) is a design-time decision with no procedural gate; once the feature is popular, an incremental feature request ("let my plugin run a command", "let my plugin call a webhook") gets implemented by a future contributor as an ordinary code change without re-deriving ADR-004's threat model, quietly reopening the exact code-execution/network-access risk this item explicitly ruled out. | A PR or backlog item proposes a new plugin capability beyond regex matching (e.g. a `filter_regex`/`command`/`webhook` TOML key) and is reviewed as a normal feature addition rather than a security-boundary change. | Add one sentence to ADR-004 (or a short new `.claude/rules/` entry) stating that any future addition to the plugin schema's *capabilities* (not just new status keys) requires an explicit security/trust-boundary re-review before merge — make the gate procedural, not just a hope someone remembers the original ADR. | P3 |
| 4 | The entire "did my plugin work" feedback loop is daemon logs only (no UI, by explicit scope decision; Phase 3's `detectors list`/`test` CLI is optional and likely to be dropped under time pressure per its own "drop it if scope is tight" framing) — so a user who doesn't know to run `journalctl --user -u stapler-squad -f` has no way to self-diagnose a rejected or silently-not-overriding plugin. | A support/backlog item reads "I added a TOML file and nothing happened," filed by a user who never checked the daemon log, with no repro steps because they have no error to report. | Promote the read-only half of Phase 3 (`detectors list` — "what's loaded, what was rejected and why") from optional to a minimum required deliverable of this item, since it's the only zero-log-reading way to close the loop; if schedule pressure still cuts it, say so explicitly in plan.md rather than letting "optional" quietly become "never," given both `research/pitfalls.md` and `research/features.md` already flagged this as the most common real-world failure shape. | P2 |
| 5 | `PluginDir()` resolves through `config.GetConfigDir()`, which is instance-scoped via `STAPLER_SQUAD_INSTANCE`/`STAPLER_SQUAD_TEST_DIR` (confirmed in `config/config.go`) — so "the" plugin directory is not one well-known path. A developer following this repo's own documented manual-test workflow (`STAPLER_SQUAD_INSTANCE=claude-manual-test ./ssq-manual-test`) who edits `~/.stapler-squad/detectors/*.toml` will find it has no effect on that instance, because it resolves to `~/.stapler-squad/instances/claude-manual-test/detectors/` instead. | During exactly the manual-verification step this repo's CLAUDE.md prescribes for trying out in-progress changes, a plugin edited in the "obvious" directory never shows up in the manual test instance's `DetectorProvenance()`. | Add one sentence to plan.md's Domain Glossary entry for "Plugin Directory" calling out instance-scoping explicitly (mirroring the existing `STAPLER_SQUAD_TEST_DIR` note already there), and make sure the planned `log.Info("detector plugins loaded", "dir", dir, ...)` startup line prints the *absolute resolved path* prominently, so a confused dogfooder can immediately see which directory a given process actually read from. | P3 |
