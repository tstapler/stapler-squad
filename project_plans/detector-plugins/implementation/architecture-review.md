## Concerns

- [ ] **Task 2.2.1d / ADR-002 "leave untouched and unused"** — The plan leaves `NewStatusDetectorFromFile`, `StatusDetector.LoadPatterns`, and `validatePatternFilePath` in `detector.go` fully intact, unused outside their own tests (verified: `grep -rn "LoadPatterns\|NewStatusDetectorFromFile" --include="*.go" session/` returns only `detector.go` definitions and `detector_test.go` call sites — zero production call sites, confirming ADR-002's claim). After this change, the package will contain **two independently-invented, structurally-similar hot-swap mechanisms** for the same underlying idea (atomic-pointer-guarded pattern-set replacement): the old `atomic.Pointer[PatternSet]` per-`StatusDetector` swap, and the new `atomic.Pointer[detectorSnapshot]` registry-level swap. A future contributor grepping for "how do I reload patterns at runtime" will find both, with no compiler-enforced or doc-enforced signal steering them to the live one. ADR-002 justifies *not building on* the old machinery (correctly — wrong unit of change, wrong atomicity boundary), but does not address the cost of *leaving it in place* net-new confusion once a second, competing mechanism exists in the same package.
  **Recommendation**: add a short doc comment above `NewStatusDetectorFromFile`/`LoadPatterns` (one-line addition to this plan, e.g. new subtask under 2.2.1d) explicitly marking them "superseded for per-binary detection by `detectorSnapshot`/`InitPlugins`; retained only for [reason X, e.g. any other caller / potential future direct-YAML-load use case]" — or, if no such reason exists, treat their removal as an explicit follow-up decision (not silently deferred) rather than leaving genuinely dead-relative-to-this-feature code unexplained in the same file the new mechanism lives in. This is process, not a blocker: it doesn't have to happen in this change, but the plan should say so on purpose rather than by omission.

- [ ] **Story 2.2.1 / `detectorSnapshot`, `PluginDetector` — primitive-obsession on `provenance map[string]string`** — `detectorSnapshot.provenance` is `map[string]string` where the value is either `""` (built-in) or an absolute file path (user plugin). This is a two-state sum type (`BuiltIn | UserPlugin(path)`) encoded as a primitive string with a magic empty-string sentinel. Nothing stops a future caller from mistaking an empty path for "not yet loaded" vs. "is a built-in," and `DetectorProvenance()`'s doc comment is the only place this convention is recorded (Task 2.2.1c/Task 2.3.2a's acceptance criteria literally assert on the string `""`, baking the sentinel into the test contract too).
  **Recommendation**: not a blocker given the small, internal-only surface (never serialized, never round-tripped through TOML), but consider a small named type — `type detectorSource struct { BuiltIn bool; Path string }` or a two-case sum type — instead of the bare string convention, so the meaning of `""` isn't tribal knowledge encoded only in a doc comment and a handful of test assertions. Low cost to fix now (it's an internal map value, no wire format), rising cost to fix later once `DetectorProvenance()` (an exported function) has callers depending on the string shape.

- [ ] **Story 2.2.2 (`rebuildSnapshot`) / Task 2.2.1a (`snapshotWriteMu`) — mutex-span claim is correct in the design text but worth flagging as a review-time invariant, not just a comment.** The plan (Task 2.2.2a step 1: `snapshotWriteMu.Lock(); defer Unlock()` held across `LoadPluginDir` → `MergedRegistry` → `buildSnapshot` → `Store`) does correctly hold the writer mutex across the *entire* rebuild-then-store sequence, matching the `pipelineModeCache.refresh` precedent verified above (`session/pipeline_engine.go`'s `refresh` holds `writeMu` across the DB read too, not just the `Store`) — so the claim in the plan holds up against its own cited precedent. The one gap: nothing in Phase 2 explicitly requires a `go vet`/lint rule or code comment enforcing that *no future edit to `rebuildSnapshot` moves the `Lock()` past step 2* (a classic regression pattern — someone "optimizing" by narrowing the lock scope around just the `Store` reintroduces exactly the lost-update race ADR-002 documents). The double-checked-locking house rule (`.claude/rules/go-double-checked-locking.md`) is correctly judged inapplicable here per ADR-002's own caveat (no caller consumes a return value from `rebuildSnapshot`), so this is not a violation — it's a durability concern about a correct design.
  **Recommendation**: Task 2.2.2a's doc comment (already planned) should say explicitly "do not narrow this lock's scope to just the Store call" so the invariant survives a future refactor, not just the original author's intent.

- [ ] **Epic 3.1 (Phase 3, optional) / `detectors test` subcommand — scope creep watch, not a violation today.** Phase 3 is explicitly marked optional and correctly scoped (CLI-only, reuses `LoadPluginDir`/`NewPatternSet`/`MatchLines` — no new detection code path). Flagging only because Story 3.1.2's `--input -` (stdin) plus a `--file` pointing at an arbitrary `.toml` outside the plugin directory is a slightly different trust boundary than ADR-004 (which is scoped to `~/.stapler-squad/detectors/*.toml` specifically, with symlink-skip and the plugin-directory constraint). ADR-004 §3 ("only files matching `*.toml` directly inside the plugin directory are loaded") is written for the *hot-reload* path; the CLI debug subcommand in Story 3.1.2 deliberately parses a caller-specified path, which is a reasonable and different use case (a developer testing a draft file before moving it into place) but should be called out as intentionally outside ADR-004's directory constraint, not silently exempted from it.
  **Recommendation**: if Phase 3 is implemented, add one line to Task 3.1.2a noting explicitly that `--file` bypasses the plugin-directory constraint by design (it is a local debug tool operated by the same user who already has filesystem access, not a remote/reload path), so a future reader doesn't read ADR-004 and conclude the CLI subcommand violates it.

## Nitpicks

- **Domain Glossary term `Override` vs. `Upsert` naming** — the glossary defines "Override" as the user-facing concept (a plugin claiming a binary name a built-in also claims) and `Upsert` as the mechanical registry method. This is a clean separation (ubiquitous-language term vs. implementation-level method name) and worth calling out as *done well*, not a problem — noting it so the eventual PR reviewer doesn't second-guess why the method isn't named `Override`.
- **`PluginLoadError.Field` as a bare string path-expression (`patterns[2].regex`)** — this is intentional primitive use for human-readable diagnostics (per Story 1.2.1's acceptance criteria, these strings are asserted on verbatim in tests), not primitive obsession in the type-driven-design sense — a typed field-path value would add ceremony with no behavior gain for a write-only diagnostic string. Correctly left as a plain string; noting only so a reviewer applying the primitive-obsession checklist mechanically doesn't flag it.
- **`statusField`'s table-driven switch vs. reflection** — the plan's explicit rejection of reflection-over-struct-tags (Pattern Decisions table) is the right call and is exactly the kind of "unjustified generic/reflection" smell the interface-pollution checklist warns about; good that the plan pre-empted it rather than an implementer reaching for `reflect` later.
- **`MergedRegistry` always builds a fresh registry rather than mutating in place** — correctly avoids the aliasing bug where a caller's `builtins` registry could be observed mutated (Story 2.1.2's third acceptance criterion tests exactly this). Worth confirming during implementation review that `Upsert`ing `builtins.Names()`/`Lookup` results copies detector *references* (fine, since `BinaryDetector` values are treated as immutable) rather than needing a deep copy — the plan doesn't need to change, just confirm the assumption holds when built.

## Summary of what's structurally sound (not requiring action)

- **SOLID**: `PluginDetector` has one job (adapt a validated TOML file to `dtypes.BinaryDetector`); `LoadPluginDir`/`validatePluginFile`/`parsePluginFile` are cleanly separated by responsibility (parse vs. validate vs. scan); `Upsert` alongside `Register` (rather than weakening `Register`) is correct Open/Closed — new capability added without modifying the tested invariant on the existing method. No ISP/LSP concerns — `PluginDetector` satisfies the existing `dtypes.BinaryDetector` interface with no new interface introduced.
- **DDD aggregate boundaries**: `detectorSnapshot` (aggregate) with `byBinary`/`provenance` as its consistency boundary, swapped atomically as a whole, is the correct grain — matches the actual invariant (a reload is directory-global, not per-file) that the requirements impose (collision detection needs the whole directory in view at once).
- **Parse-Don't-Validate**: `pluginFile`/`patternEntry` DTOs → `validatePluginFile` → `toStatusPatterns` → `*PluginDetector` is a real parse boundary, not validate-then-trust — once a `*PluginDetector` exists, nothing downstream re-checks its regexes or status keys; the DTO never escapes the loader (per the plan's own glossary note), which is exactly the "type as proof" pattern.
- **Registry pattern fit**: right-sized for the complexity — a handful of built-ins, single-digit user files, reload measured in per-minute at most. Rejecting Decorator/Chain-of-Responsibility for override (Pattern Decisions table) is correct: override is total replacement keyed by a map, not layered behavior.
- **Testability**: every listed component (`parsePluginFile`, `validatePluginFile`, `LoadPluginDir`, `MergedRegistry`, `buildSnapshot`, `rebuildSnapshot`) is designed as a pure(ish) function taking explicit inputs (bytes, paths, registries) and returning values/errors — no hidden global state read during the pure phases. The one necessarily-global piece (`activeSnapshot`) is isolated to the smallest possible surface (`lookupBinaryDetector`, `rebuildSnapshot`) and each test resets it in `t.Cleanup`, which the plan calls out explicitly (Task 2.2.2b, 2.3.3d).
- **Task 2.2.1d verified safe**: `grep -rn "builtBinaryDetectors" session/` returns exactly the three lines the plan cites (`detector.go:733,735,754`) and nothing else — the plan's claim that deleting it and repointing to `lookupBinaryDetector` has no other reader is confirmed correct, not just asserted.
- **Build-vs-buy consistency**: go-toml/v2 + stdlib `regexp` + fsnotify are used exactly as `research/build-vs-buy.md` and ADR-001 specify; no undocumented substitution.
