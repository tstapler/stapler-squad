# Adversarial Review: detector-plugins

**Date**: 2026-08-01
**Verdict**: BLOCKED at time of writing; the sole Blocker and 5 of 8 Concerns
are now marked `[x] RESOLVED 2026-08-01` below, via `plan.md`'s Epic 2.4 and
Hardening Addendum (added during the Phase 4 pre-mortem/triad-review pass).
Original per-item verdicts preserved unmodified for record.

## Blockers

- [x] **RESOLVED 2026-08-01** — independently confirmed by the Phase 4
  pre-mortem (P1 #1) and fixed by adding **Epic 2.4** ("Wire plugin-aware
  detection into the live status path") to `plan.md`, taking recommendation
  (b): `ClaudeController.Start` now resolves its `StatusDetector` via
  `lookupBinaryDetector`/a new exported `DetectorForProgram(program)`,
  falling back to `getDefaultPatterns()` only on a miss. Original finding
  preserved below for record.
- [ ] **`DetectForProgram` — the sole consumer of everything this plan builds (registry, `MergedRegistry`, `activeSnapshot`, hot-reload) — has zero production call sites in the current codebase, so the feature may have no observable effect on real session status.** Verified by exhaustive repo-wide search: `grep -rn "DetectForProgram" . --include="*.go"` returns only the function's own definition (`session/detection/detector.go:753`) and its own tests (`snapshot_test.go`, `detector_test.go`). Every real status-detection call site in `session/` — `claude_controller.go:224,668,1021` (`sd.Detect`/`sd.DetectWithContextFromLines`), `session/detection/idle.go:136,168` (`statusDetector.Detect`/`.DetectFromLines`), `session/command_executor.go:359` (`.DetectWithContext`), `session/review_queue_determiner.go:195` (`.DetectWithContextFromLines`) — uses the **generic** path, none of which take a `program`/binary-name argument or ever touch `DefaultRegistry()`, `binaries/*.go`, or the registry the plugin loader upserts into. The generic path is driven entirely by `getDefaultPatterns()` (`detector.go:304`), a hand-maintained, hardcoded union of patterns for Claude/Gemini/OpenCode/agy that is a *separate, parallel* pattern source from `binaries/*.go` — not derived from it. So today, even the five **built-in** per-binary detectors this plan cites as precedent (`binaries/claude.go` etc.) do not appear to influence any status a user actually sees; `DetectForProgram`/`DefaultRegistry` look like a foundation that, like the YAML `StatusDetector.LoadPatterns` path ADR-002 documents as "built and never wired up," was itself never wired up.
  Practical consequence: a user could drop a valid `claude`-overriding plugin TOML, see it load successfully, see `DetectorProvenance()` report it, see the Phase 3 `detectors test` subcommand confirm the regex matches — and their actual Claude session's displayed status in the web UI would never change, because the code path computing that status never calls `DetectForProgram`. Requirement #1 and acceptance criterion #3 would pass at the unit-test level (`DetectForProgram` tests, `MergedRegistry` tests) while being false for the running application.
  — **Recommendation**: before implementation starts, resolve which of these is true and make it explicit in the plan: (a) confirm with a maintainer whether some other in-flight/planned change already wires `claude_controller.go`/`idle.go`/etc. onto `DetectForProgram` (in which case this plan should say so and take a dependency on it), or (b) expand this plan's scope to thread the session's known program/binary name (already tracked — see `session/instance_program.go`) into those call sites so the override mechanism actually activates, or (c) if neither is acceptable right now, ship this explicitly labeled as "the plugin registry and hot-reload machinery are built and tested but not yet wired into production status detection; overriding a built-in has no visible effect until a follow-up item wires the call sites" so stakeholders don't believe requirement #1 is satisfied when it isn't.

## Concerns

- [x] **RESOLVED 2026-08-01** — `plan.md`'s new "Hardening Addendum" adds a
  `maxPluginCompileTime = 500ms` wall-clock budget around the per-file
  compile loop. Original finding preserved below.
- [ ] **The three resource caps (`maxPatternsPerPlugin=50`, `maxRegexLength=4096`) do not bound aggregate compile time, contradicting ADR-004's claim that no additional protection beyond RE2 is warranted.** Empirically verified: a single regex shaped as `(4000-byte-literal){500}` is 4007 bytes — under the 4096-byte cap — and compiles in ~200ms; 50 such patterns in one file (at the pattern-count cap) took **6.1 seconds** to compile in a local test (`regexp.Compile` in a loop, Go 1.x). This is not catastrophic backtracking (RE2 genuinely forecloses that), but it is a concrete, reproducible, cap-compliant way to make `rebuildSnapshot` — which runs **synchronously** inside `InitPlugins` at daemon/web-server startup, and synchronously inside `watchLoop`'s event-handling goroutine on every debounced edit and every 60s periodic tick — take multiple seconds. ADR-004 states "If a future contributor proposes [additional protection], the burden is on them to name a concrete RE2 vector" — this is that vector, named with numbers. It directly conflicts with the non-functional requirement that regex compilation "must not be able to hang the process... in a way that blocks startup indefinitely" (not literally infinite, but a real, avoidable multi-second stall) and is more consequential in this repo specifically because of the existing, documented sensitivity around restarts (`.claude/rules/tmux-keep-server-on-restart.md`) — anything that makes shutdown/restart slower is already a known pain point here.
  — **Recommendation**: add a per-file (or per-rebuild) wall-clock compile budget, or tighten `maxRegexLength`/`maxPatternsPerPlugin` substantially, and add a task that tests compile time at the cap *boundary with adversarially-shaped content* (Task 1.2.2b currently only tests that patterns *above* the cap are rejected — it never tests a cap-compliant-but-expensive file).

- [x] **RESOLVED 2026-08-01** — `plan.md`'s Hardening Addendum makes the
  seed-file-write step in `EnsurePluginDir` log-and-continue instead of
  returning an error. Original finding preserved below.
- [ ] **A transient failure while writing the optional seed file disables the entire feature for the process's lifetime, not just the seeding step.** Task 2.3.2a's `InitPlugins` step 2 says: on any `EnsurePluginDir()` error, `log.Warn` and `return nil` — skipping `rebuildSnapshot` and `StartPluginWatcher` entirely. But `EnsurePluginDir` (Task 2.3.1a) bundles two unrelated operations behind one error return: "create the directory" (essential) and "write the example seed file if absent" (cosmetic/optional per requirement #6's "optionally seeded"). A disk-full condition, or a permissions hiccup, hit exactly while writing the seed file — even if the directory itself exists and is readable, and even if it already contains real user plugin files from a previous run — currently propagates as a fatal `EnsurePluginDir` error and skips scanning those real files and starting the watcher, with no retry path (since `InitPlugins` is called exactly once).
  — **Recommendation**: make the seed-file-write failure non-fatal to `EnsurePluginDir` (log and continue); only a failure to create/access the directory itself should skip the subsequent scan+watch steps.

- [x] **RESOLVED 2026-08-01** — `plan.md`'s Hardening Addendum adds
  `maxPluginFiles = 200` to `LoadPluginDir`. Original finding preserved
  below.
- [ ] **No cap on total plugin file count or total directory size — only per-file caps exist.** The review prompt's "extremely rapid file churn (hundreds of files)" scenario is explicitly unbounded by the plan: `maxPatternsPerPlugin`, `maxRegexLength`, and `maxPluginFileSize` all bound a *single file*, but nothing bounds how many files `LoadPluginDir` will read+parse+validate in one pass. `rebuildSnapshot`'s own doc comment (Task 2.2.2a) justifies rebuilding the whole directory on every reload by asserting "the directory is single-digit sized" — an assumption nothing enforces or tests. The debounce timer (reset-on-event) means continuous churn defers the *debounced* rebuild indefinitely (arguably fine — avoids thrashing), but the 60-second periodic ticker still fires unconditionally regardless of ongoing churn and pays the full O(directory-size) cost every time, compounding with the compile-cost concern above.
  — **Recommendation**: add a `maxPluginFiles` (or total-bytes) cap consistent with the existing three, using the same file/field/why error-reporting shape, and warn-and-skip files beyond it (sorted-order, matching the existing deterministic-winner convention).

- [x] **RESOLVED 2026-08-01** — `plan.md`'s Hardening Addendum threads
  `ctx context.Context` into `rebuildSnapshot` with an early cancellation
  check. Original finding preserved below.
- [ ] **`rebuildSnapshot` takes no `context.Context` and never checks for cancellation.** Task 2.2.2a's signature is `func rebuildSnapshot(dir string) error` — no `ctx` parameter anywhere. `watchLoop` (Task 2.3.3c) calls it synchronously inside its `select` loop; if `ctx.Done()` fires while a rebuild is in flight, the goroutine can't observe it until the current (potentially multi-second, per the compile-cost concern above) rebuild finishes. Combined with the missing directory-size cap, this means a sufficiently large or adversarial plugin directory can measurably delay graceful shutdown — again, notable in a repo with documented restart-sensitivity issues.
  — **Recommendation**: thread `ctx` into `rebuildSnapshot` (or at minimum check it between per-file compiles in `LoadPluginDir`) so a cancelled context can abort a rebuild in progress rather than only being checked between `select` iterations.

- [x] **RESOLVED 2026-08-01** — `plan.md`'s Hardening Addendum wraps
  `InitPlugins` in `sync.Once`. Original finding preserved below.
- [ ] **`InitPlugins` has no re-entrancy guard.** The plan relies entirely on a doc comment ("call exactly once, from `main.go`") rather than a `sync.Once` or equivalent. Today only one call site exists and `main.go`'s `RunE` runs once per process, so this isn't currently exploitable — but nothing in the code would prevent a future "reload plugins" RPC, a test harness, or a refactor from calling `InitPlugins` a second time, which would start a **second** `fsnotify.Watcher` + goroutine + 60s ticker over the same directory (the first `*PluginWatcher` handle isn't retained anywhere to `Stop()` it), doubling event-handling and periodic-rebuild cost for the rest of the process's life with no user-visible symptom beyond wasted CPU.
  — **Recommendation**: add a `sync.Once` (or a package-level "already initialized" guard with a clear error/no-op) inside `InitPlugins` itself, not just a doc comment.

- [ ] **Package-global `activeSnapshot`/`snapshotWriteMu` mutable state makes the whole `session/detection` test suite (not just the new files) load-bearing on manual test-cleanup discipline.** The plan's own tasks (2.2.2b, 2.3.3d) already flag the need for `t.Cleanup` restoration and avoiding `t.Parallel()`. No existing test in the package currently uses `t.Parallel()`, so this doesn't break anything *today*, but it converts "no parallelism" from an incidental style choice into a silent correctness invariant enforced by nothing but comments — exactly the fragility class this repo's own `.claude/rules/go-double-checked-locking.md` and `interface-pollution-checklist.md` exist to catch for other patterns. A single test that panics before its `t.Cleanup` registers, or a copy-pasted test that omits the restore line, leaks a custom snapshot (e.g. a `claude`-overriding `FORKED-BUSY` pattern) into every test that runs afterward in the same package binary — including unrelated pre-existing tests like `bug_regression_test.go` and `snapshot_test.go` — producing confusing, run-order-dependent failures far from the actual bug.
  — **Recommendation**: write one shared test helper (e.g. `withTestSnapshot(t *testing.T, snap *detectorSnapshot)`) that every new test uses to set-and-defer-restore `activeSnapshot`, rather than repeating the pattern by hand in each of Tasks 2.2.2b / 2.3.3d / 2.3.2c.

- [ ] **Subdirectories under the plugin directory are skipped with zero signal, unlike symlinks.** Task 1.2.3c skips directory entries silently; the acceptance criteria for Story 1.2.3 confirm this explicitly ("only the symlink produces a log line"). A user who reasonably organizes plugins into subfolders (`detectors/work/foo.toml`) gets no error, no log line, and no entry in the future `detectors list` CLI (Phase 3) — the file simply never loads with no discoverability path at all. This is inconsistent with requirement #3's "clear, actionable error… which file, which field, why" spirit, and worse than the symlink case the plan already handles.
  — **Recommendation**: add at least a `log.Debug`/`log.Warn` line naming a skipped subdirectory, ideally through the same reporting path as the next item.

- [ ] **Symlink rejection bypasses the `[]PluginLoadError` reporting path used by everything else**, going out via an inline `log.Warn` inside `LoadPluginDir` instead. The Phase 3 `detectors list` subcommand (Task 3.1.1a) explicitly only prints `LoadPluginDir`'s returned `[]PluginLoadError`s — so a symlinked-and-skipped plugin is invisible to the one debugging tool built for exactly this question, visible only in the daemon's log (which a systemd-user-service consumer may not think to check). Combined with the subdirectory gap above, there are now two categories of "file didn't load" that don't flow through the structured error path the rest of the design (and the future CLI) is built around.
  — **Recommendation**: make both the symlink-skip and subdirectory-skip cases produce a `PluginLoadError` (e.g. `Field: "type"`) alongside the log line, so there is exactly one reporting mechanism for every rejection category.

## Minors

- The specific numeric caps (`maxPatternsPerPlugin=50`, `maxRegexLength=4096`, `maxPluginFileSize=256KiB`) are the plan's own invented values — `requirements.md` only suggests the general idea of "a max-pattern-length guard," not these numbers, and nothing in the repo is cited as precedent for them. Sanity-checked against the largest existing built-in detector (`binaries/claude.go`, 26 patterns) — comfortably under the 50-pattern cap — so the count cap is empirically reasonable for real-world-sized files even though it isn't independently justified in the ADR.
- The TOCTOU in `EnsurePluginDir` (`os.Stat` then `os.WriteFile` for the seed file) is real but provably benign under the current single-invocation-per-process design: the only thing that could race the check is another process attempting to write the exact same constant content, so no user-edit-clobbering scenario actually exists today. Worth a one-line code comment acknowledging the race is intentionally left unguarded (and why), so a future reviewer doesn't have to re-derive that conclusion from scratch.
- Phase 3 (CLI debugging subcommands) is clearly and appropriately marked optional/non-blocking ("recommended but not required... drop it if scope is tight") — low risk of unplanned scope creep, well-gated. No action needed.
- ADR-001's choice of `github.com/pelletier/go-toml/v2` is well-justified (actively maintained, MIT license, `DisallowUnknownFields()` is a genuine deciding factor given the typo failure mode) and the swap-surface mitigation (DTO isolation confining the dependency to one function) is credible.
