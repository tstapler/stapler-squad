## 2. `DetectByPath` mechanics (the recovery primitive both Goal 1 and the fallback rely on)

`session/history_detector.go:137-199`:
- Scans `~/.claude/projects/<ClaudeProjectDirName(projectPath)>/` (no live process required).
- Filters to `*.jsonl` files, excludes `agent-*.jsonl`, requires a valid-UUID basename (`isValidUUID`).
- **Picks the single most-recently-modified file** (`sort.Slice` by `modTime`, descending, take `candidates[0]`) — no session-identity check, no "is this the file *this* session wrote" check. This is a pure directory-scan heuristic.
- Returns `nil, nil` (not an error) if the directory doesn't exist or has zero valid candidates.
- `ClaudeProjectDirName` (`history_detector.go:118-129`) does a pure character-class substitution (alnum kept, everything else → `-`) — no symlink resolution, no path normalization (no `filepath.Clean`/`EvalSymlinks`) on the input `projectPath` itself. Contrast: `Detect` (the PID-based sibling) *does* call `filepath.EvalSymlinks` on discovered open-file paths (line 75) before matching, but that's resolving the discovered file, not the *input* project path used to build the directory to scan.

## 3. Edge cases and failure modes to design for

1. **Multiple sessions sharing a directory (confirmed prior-art conflict).** `DetectByPath`'s "most recent wins" heuristic is the *exact* mechanism `session-resume-uuid-fix` (`project_plans/session-resume-uuid-fix/requirements.md`) had to guard against for `HistoryLinker.correlateSession` — it added a `pathFallbackAllowed` gate (`history_linker.go:274-275`) that skips the fallback for already-linked Paused/Hibernated/Stopped sessions with no live PID, specifically because a *second* session's newer JSONL would silently steal a *first*, already-linked session's stored UUID.
   - That prior fix's own **R3** (`project_plans/session-resume-uuid-fix/requirements.md:59-68`) explicitly carves out the case this bug is about: a session with **no stored UUID** must still use the path fallback — R3's scope note calls the multi-session-no-UUID combination "a pre-existing limitation, best effort only" and explicitly out of scope for that fix.
   - So this project inherits that *known, accepted* limitation: if a session has never captured a UUID (or had it cleared) and shares its directory with other sessions that have since run and produced newer JSONL files, `DetectByPath` can and will attach the *wrong* session's conversation. Goal 1's synchronous invocation of the same `DetectByPath` at decision time doesn't fix this — it inherits it. Worth flagging explicitly rather than silently reproducing: the design should decide whether to (a) accept this as inherited scope (matching R3's own stance), or (b) add a stronger match signal (e.g. cross-check `HistoryFilePath` if one was *ever* recorded, even if currently empty, against the JSONL directory listing) as a bonus improvement.
   - Directory-mode sessions (no worktree) are the highest-risk case for this — worktree sessions get a unique path per session by construction; directory-mode sessions can genuinely be re-pointed at the same folder repeatedly.

2. **JSONL exists but is corrupt or empty.** `DetectByPath` only checks the filename (`isValidUUID` on the basename) and mtime — it never opens or parses file contents. An empty or truncated JSONL (e.g. Claude crashed mid-write, or the file was just `touch`ed) will still be selected as a "valid" candidate and its UUID handed to `--resume`. The actual failure mode then shifts downstream to Claude CLI's own `--resume` handling: `instance_claude.go`'s `isStaleResumeExit`/`staleResumePattern` (`"No conversation found with session ID"`) already detects a stale/invalid resume and `recoverFromStaleResume` (`instance_claude.go:78-96`) clears state and restarts fresh. That existing mechanism is the natural fallback for "recovered a UUID that turns out to be unusable" — the new decision-time recovery doesn't need to itself validate JSONL contents, but the design should confirm the corrupt/empty-JSONL → stale-resume-error → `recoverFromStaleResume` loop terminates (doesn't recovery-loop back onto the same bad file) and that it, too, produces the Goal 3 user-visible signal rather than silently retrying.

3. **Session legitimately has no prior conversation** (AC2/AC6: first-time setup, one-off sessions, explicit "start over"). Two structurally different sub-cases:
   - **True first launch**: goes through `startLocked`'s `firstTimeSetup == true` branch (`instance.go:936-980`), which is an entirely separate code path from the cold-restore branch under discussion (`!firstTimeSetup`, `instance.go:878-921`) — it never reaches `HasClaudeSession()`/`tryExtractConversationUUID` at all on the very first start. So true first-time setup is inherently unaffected by this fix, confirming AC6 should be easy to satisfy for that sub-case.
   - **Restart of a session that never got a UUID captured** (e.g. a one-off session whose Claude process died before producing any JSONL, or died before `SetHistoryInfo`/`tryExtractConversationUUID` ever ran) — this *does* hit the `!firstTimeSetup` cold-restore branch with `HasClaudeSession() == false`, same as the buggy case. The distinguishing signal from "lost track of a real conversation" has to be: does `DetectByPath` find *anything* at all in the project dir. AC2 already specifies this: "no JSONL for this path... starts fresh exactly as it does today." The design should double check `ClaudeProjectDirName` encoding is deterministic per path so this negative case (directory doesn't exist) resolves instantly rather than doing wasted I/O loops on repeated restarts of a one-off session with a churning inactivity watchdog (see race edge case below) — `os.ReadDir` on a nonexistent dir returns immediately with an error which `DetectByPath` already treats as "no candidates," so this looks cheap by inspection, but worth confirming under the watchdog's repeated-restart cadence there's no accumulating cost (e.g. logging volume from Goal 3's new signal firing every ~10 min for a one-off session that will *never* have history).

4. **Race between two revives of the same session.** `Instance.Start()` is only entered through `startMu.Lock()` (`instance.go:1027`, in the legacy `start` path) — but note `startLocked` (the actor-routed, production path) explicitly does **not** take `startMu` (see its own doc comment at `instance.go:838-841`: "No startMu.Lock() — the actor goroutine serializes concurrent calls"). Serialization instead comes from the actor's single-goroutine command queue. This matters for the new recovery call: if Goal 1's `DetectByPath` call is added inside `startLocked`, it executes with the same single-actor-goroutine guarantee already relied on elsewhere in that function (e.g. the existing `tryExtractConversationUUID()` call at line 921) — so no *new* race is introduced by adding one more `DetectByPath` call inside the same actor command, as long as it stays inside `startLocked` rather than being hoisted out to an async path. The real race risk is external: the background `HistoryLinker` goroutine (`scanAllSessions`/`ScanAll`) calls `inst.SetHistoryInfo` concurrently with `startLocked` potentially doing the same — both go through `SetHistoryInfo`'s own locking (`instance_claude.go:464-499`, `claudeSessionMu` + nested `i.mu`), which is safe for data-race purposes, but the *last writer wins* on `ConversationUUID`/`HistoryFilePath`, so if `startLocked`'s new recovery call and a concurrent `HistoryLinker` pass both call `DetectByPath` around the same restart, whichever finishes last determines the final resume target — worth a design note even though both would very likely resolve to the same "most recent" file in practice.

5. **Symlinked/renamed working directories change the encoded project-dir path.** `ClaudeProjectDirName` does a pure string transform of `projectPath` with no symlink resolution or canonicalization (§2 above). `GetEffectiveRootDir()` (used as the input at both `instance_claude.go:337` and `instance.go:880`/`:1071`) — if a worktree's path changes representation between the original session start and a later cold restore (e.g. the repo is moved, a symlinked home directory resolves differently after a remount, or `GetEffectiveRootDir()`'s underlying worktree path changes due to git worktree relocation) — the encoded directory name would differ and `DetectByPath` would scan an empty/wrong directory, silently falling into the "no history found" branch (AC2's negative path) even though a real transcript exists under the *old* encoded path. This is effectively unrecoverable by `DetectByPath` alone since it has no fuzzy-match capability — out of scope to fix, but the design should note it as a known limitation of the recovery mechanism (same category as the shared-directory issue) rather than something a decision-time-only fix within `startLocked` can close.

## 4. Precedent for Goal 3's user-visible signal

No generic "session-level toast/notification reaches the frontend" mechanism currently exists outside the backlog subsystem — searched `web-app/src`, `session/*.go`, `server/services/*.go` for "restart.*fresh", "lost.*conversation", "started a new session", "context lost", "could not be resumed": no matches. The only `notify(...)`-style user-facing notification helper (`BacklogLifecycleListener.notify`, `session/backlog_lifecycle.go:731`) is scoped to backlog items specifically (`itemID`, `notificationType`, `priority`) — not applicable to arbitrary sessions.

The mechanism that *does* already generalize to any session is the `LifecycleEvent`/`LifecycleListener` bus (`session/instance.go:69-94`, `session/instance_controller.go:108-144`): `fireLifecycleEvent(event LifecycleEvent, reason string)`. `EventStarted` already carries a free-text `reason` string in production use for exactly this kind of "why did this session (re)start" distinction — `session/review_queue_poller.go:473` fires `EventStarted, "reconcile-session-revived"` and `:497` fires `EventStarted, "reconcile-session-hibernated-but-alive"`. This is the natural precedent to extend: fire `EventStarted` with a reason like `"cold-restore-resumed"` vs `"cold-restore-fresh-lost-history"` (exact strings TBD in planning) from the fixed `startLocked`/`start`, and separately ensure that reason is persisted/surfaced to the frontend (requirements.md Goal 3 says "durable... e.g. a session event/status field the frontend can surface" — today's `LifecycleEvent` listeners are in-process Go callbacks, not automatically durable or wire-visible; the plan phase needs to identify whether an existing listener already forwards `EventStarted`+reason to a persisted/RPC-visible field, or whether one needs to be added — `session_summary_listener.go` and `backlog_lifecycle.go`'s `OnLifecycleEvent` are the two existing listeners and neither currently branches on `reason` string content for anything resume-related).

## 5. Unstated user needs beyond the explicit ACs

- **Manual "start fresh" vs "always try to resume" control.** Requirements.md's Goal 4 / AC6 only requires *not regressing* explicit start-fresh flows — it doesn't ask for a new manual override. No existing UI affordance for "force fresh start on next restart" was found beyond `ClearConversationState()` (`instance_claude.go:278-296`), which is currently only called internally (`recoverFromStaleResume`) — not exposed as a user action. If users want a deliberate "abandon this conversation, start clean" button distinct from the automatic recovery behavior being added here, that's an unstated need worth flagging to the requirements owner before planning — it's plausible but not in scope per the current requirements.md, and adding *more* automatic resume-recovery (this project's whole point) makes an explicit opt-out more valuable than it was before, since users lose the "it'll fix itself eventually by drifting to fresh" implicit escape hatch this bug currently provides.
- **Distinguishing "resumed the right conversation" from "resumed *a* conversation" in the shared-directory edge case (§3.1).** Because `DetectByPath` can silently attach the wrong session's history when directories are shared, a user could get *worse* silent confusion than today's "lost context, started fresh" — namely "resumed, but with someone else's conversation," which looks successful (no warning, no fresh-start signal) but is subtly wrong. Requirements.md's Goal 3 signal is framed around the fresh-start case; the design should consider whether the shared-directory mis-resume case also deserves a signal, since it's arguably a worse UX outcome (silently wrong vs visibly reset) than the case explicitly being fixed.
- **Latency/perf expectation (implicit in AC2: "no added latency that matters")** — `DetectByPath` does a single `os.ReadDir` plus a `sort.Slice` over however many JSONL files exist per project dir; for the common case (no JSONL, one-off/never-started sessions, §3.3) this is one failed `os.ReadDir` call, cheap. No unstated need surfaced here beyond confirming this in the validate/implement phase with a real perf check under the `SessionDriver`'s ~10 min repeated-restart cadence for a never-linked session.
