# Pre-mortem: slack-review-notifications
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The feature ships via `make install-service`, whose Linux restart is documented (`.claude/rules/tmux-keep-server-on-restart.md`) to kill the tmux server and every live session, which then get silently rebuilt — flooding the review queue with "stopped unexpectedly" items at the exact moment Slack notifications go live for the first time. | Immediately after the deploy restart, the user's phone gets a burst of many Slack messages (or several silently-dropped/429'd ones) for sessions that didn't actually fail, before they've opened the dashboard to see what happened. | Add a rollout note to plan.md's Risk Control section: don't let first-ever activation coincide with the deploy restart. Either confirm the Linux `--tmux-keep-server` gap is fixed first, or ship with `NotifyOnQueueItem`/threshold defaulted off and have the user opt in only after confirming a normal (non-restart) queue state. | P1 |
| 2 | `ReactiveQueueManager.OnItemAdded` can be invoked concurrently by multiple sessions completing near-simultaneously (this codebase routinely runs parallel/autonomous sessions), but `MaybeNotifyQueueDepthThreshold` reads `queue.GetStatistics().TotalItems` outside the mutex that only guards `thresholdCrossed` — concurrent callers can each see a stale depth, causing a double-fired digest or a missed crossing. The plan's only latch test (Task 1.5.1e) feeds depths sequentially, never concurrently. | Two "N items pending" digest messages arrive back-to-back for one crossing, or a crossing produces zero digest even though depth is now above threshold. | Snapshot the depth read inside the same critical section as the `thresholdCrossed` check/set (pass it in under lock, or single-flight `OnItemAdded` per queue), and add a concurrency test that calls the method from N goroutines crossing the threshold simultaneously, asserting exactly one digest fires. | P2 |
| 3 | `resolveSlackWebhookURL` decrypts via `cfg.GetOrCreateEncryptionKey()`, which is machine-bound. Restoring `config.json` onto a new or reinstalled host (hardware swap, OS reinstall, disk restore — plausible for a single-user home server) leaves `WebhookURLEncrypted` permanently undecryptable, yet `GetSlackConfig`'s `webhook_configured` only checks that the ciphertext is non-empty, not that it still decrypts — so the settings UI reports "configured" while every send silently fails. | The settings page shows "Webhook: configured" but "Last Slack delivery: failed" persists across every restart, with a generic error that doesn't distinguish "key can't decrypt this ciphertext" from "Slack is down." | Make `webhook_configured` reflect decrypt success, not just ciphertext presence, or surface a distinct delivery-status reason ("decryption failed — re-enter webhook URL") so migration breakage is self-diagnosing instead of looking identical to a transient Slack outage. | P2 |
| 4 | Phase 2's plan hardens the endpoint itself (signature verification, 401 on failure, conditional route registration) but requirements/plan only require *documenting* the public-reachability requirement, not scoping it. Typical ngrok/reverse-proxy quick-starts tunnel the entire local port by default — a user following that doc to enable `ApprovalEnabled` exposes the whole stapler-squad UI (session management, every diff, every other unauthenticated `/api/hooks/*` route) to the public internet, not just the one signed endpoint. | No local symptom — the exposure only shows up externally: unexpected requests in stapler-squad's logs from non-Slack IPs, or the user discovers their session list is reachable from the public ngrok URL. | Add an explicit instruction to the Phase 2 documentation deliverable to scope any tunnel/reverse-proxy to the single path `/api/hooks/slack-interactive` (e.g. ngrok's path-restricted config or a reverse-proxy location block), with a concrete example — not just "document the requirement" in the abstract. | P1 |
| 5 | All of Epic 1.5's automated tests run against `httptest` fakes encoding assumed Slack behavior (status codes, truncation), never against a real Slack webhook. `requirements.md`'s Success Metrics manual verification is the only place real-Slack behavior is checked, and nothing gates Epic 1.5/PR-merge on that manual step having actually been performed. | Epic 1.5's test suite is green and the PR merges, but the first real review item never produces a Slack message — the manual verification step was described but never run. | Add an explicit checklist item to validation.md or the PR description ("Success Metrics manual verification against a real Slack webhook — completed, with evidence") that gates shipping, so the manual step is a required, checked artifact rather than an implied-but-optional aside. | P2 |

## P1 Items (address before implementation)
- [ ] Failure #1 — Add a rollout-sequencing note to plan.md's Risk Control section so first activation of Slack notifications is deliberately decoupled from the deploy restart that ships this feature (either fix the Linux tmux-keep-server restart gap first, or default triggers off until the queue is confirmed steady-state).
- [ ] Failure #4 — Add a concrete path-scoping instruction (with an example) to the Phase 2 documentation task (Story 2.1's public-reachability doc, referenced in requirements.md Scope) so enabling `ApprovalEnabled` doesn't implicitly invite exposing the entire app rather than the one signed endpoint.
