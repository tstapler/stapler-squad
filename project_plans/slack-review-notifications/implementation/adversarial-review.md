# Adversarial Review: slack-review-notifications

**Date**: 2026-08-06
**Verdict**: PASS (re-checked after plan.md patch — see resolutions below)

## Blockers (resolved)

- [x] **RESOLVED** (Task 1.2.1c amended + new Task 1.2.1d test): `postToSlack` now constructs a
  sanitized error on any `httpClient.Do` failure instead of propagating the raw `*url.Error`,
  and Task 1.5.1d's test is required to cover a genuine transport-level failure, not just
  non-2xx. **Webhook URL can leak into logs on the exact failure modes it's supposed to protect against (DNS failure, connection refused, TLS error).** Task 1.2.1c builds `postToSlack` via `http.NewRequestWithContext` + `n.httpClient.Do(req)`, and only describes handling for "non-2xx" responses ("treat non-2xx as an error carrying only the status code, never the URL"). It never addresses the separate case where `httpClient.Do` itself returns an error — which is exactly what happens on DNS failure, connection refused, or TLS error. Go's stdlib wraps *all* such failures in `*url.Error`, whose `Error()` method is literally `fmt.Sprintf("%q: %s", e.URL, e.Err)` — the full webhook URL (a bearer credential per ADR-001's own framing) is embedded in `err.Error()` itself, not just in a developer-written `%s`. If `postToSlack` does anything ordinary with that error (`fmt.Errorf("post to slack: %w", err)`, or just passing it to `log.Warn("...", "err", err)`), the webhook URL leaks into logs on every network-level failure — one of the four failure modes this review was asked to check. Story 1.2.1's own AC explicitly requires "postToSlack never includes the webhook URL in any returned/logged error," so this is a plan self-contradiction, not a missing nice-to-have. Task 1.5.1d's planned test ("captures log output ... during a forced failure") may not catch this if it only exercises a non-2xx `httptest.Server` response rather than a genuine transport-level failure (unreachable host/closed listener) — the two are different code paths in Go. — **Recommendation**: explicitly require `postToSlack` to construct its own sanitized error (status code or a fixed `"network error"` string) rather than wrapping/propagating `err` from `httpClient.Do` at all, and require Task 1.5.1d's test to force a real connection failure (e.g. `httptest.NewServer` then `Close()` before the request), not just a non-2xx response.

- [x] **RESOLVED** (Story 1.2.3's AC amended with an explicit "Ownership" statement + Tasks
  1.2.3a/1.3.1b/1.3.2b's text made consistent: `NotifyReviewQueueItem`/`NotifyApprovalPending`/
  `MaybeNotifyQueueDepthThreshold` self-wrap via `dispatchAsync` internally; Epic 1.3 call sites
  call them directly/synchronously, no external wrapper). **The "must never block the review-queue/approval flow" NFR has no single, unambiguous enforcement mechanism — the plan contradicts itself on where `dispatchAsync` wrapping happens.** Task 1.2.3a states `NotifyReviewQueueItem`/`NotifyApprovalPending` "are the `fn` passed in from the Epic 1.3 call sites — this wrapper is what callers actually invoke, not the raw methods" (i.e., call sites are expected to write `n.dispatchAsync(ctx, func(sendCtx){ n.NotifyReviewQueueItem(...) })`). But Task 1.3.1b's own code sample calls `rqm.slackNotifier.NotifyReviewQueueItem(rqm.baseContext(), cfg, item, dashboardURL)` **directly, with no `dispatchAsync`/`go` wrapper at all** — and the `SlackNotifierWiring` interface signature for that method returns nothing, consistent with a self-wrapping fire-and-forget design, not a synchronous one meant to be externally wrapped. Task 1.3.2b then asserts the opposite for the approval path — a comment claims `NotifyApprovalPending` "itself performs the `dispatchAsync` wrapping internally," which Task 1.2.2d's own description of that method never states. Three places in the plan (1.2.3a, 1.3.1b, 1.3.2b) each imply a different owner for the non-blocking guarantee. If an implementer follows Task 1.3.1b's code literally, `postToSlack`'s HTTP POST (bounded at 5s by the client timeout) executes synchronously inside `OnItemAdded`, which `research/architecture.md` itself documents as "runs inline on the poll/reactive path and must not be held open by a slow webhook" — precisely the incident scenario `research/pitfalls.md` §4 calls "the single most likely way this feature causes an incident." This is exactly the "asserted without a concrete mechanism" trap the review was scoped to catch. — **Recommendation**: pick one owner (strongly prefer: `NotifyReviewQueueItem`/`NotifyApprovalPending` self-wrap via `dispatchAsync` internally, since their interface signatures already imply fire-and-forget) and make every code sample in Epic 1.2/1.3 consistent with it before implementation starts; add an explicit AC/test asserting the call site returns before the HTTP POST completes (not just "eventually recovers from a panic").

- [x] **RESOLVED** (new Task 1.4.3f adds the `dashboard_base_url` field + a soft warning when
  unset and a notify toggle is on; Unresolved Question #1 resolved as "soft gap," per UX-9
  option (b)). **`DashboardBaseURL` is part of the RPC/config contract but has no settings-UI input field anywhere in the plan.** Task 1.4.1a includes `dashboard_base_url` in `SlackConfigProto`/`UpdateSlackConfigRequest`, and the Domain Glossary explicitly names the fallback as "unusable from a phone" when unset. But Story 1.4.3's full task breakdown (1.4.3a scaffold, 1.4.3b webhook URL field, 1.4.3c toggles/threshold, 1.4.3d test button, 1.4.3e delivery-status line) never mentions a `dashboard_base_url` input, and there's no env-var override for it either (only the two secrets get one, per Task 1.1.2b). With no UI path and no env override, `DashboardBaseURL` is permanently empty for every real user, so every Slack message's link falls back to `http://<listen address>` — which is exactly the failure state the plan itself labels "unusable from a phone." `requirements.md`'s Success Metrics explicitly requires verifying the message arrives with "a working link back to the dashboard," and the problem statement's whole motivation is mobile access ("especially from mobile, where the dashboard isn't always convenient to open"). As specified, this feature ships unable to meet its own acceptance test on a fresh install. — **Recommendation**: add a `dashboard_base_url` text input to Story 1.4.3 (with the same masking/validation conventions as the webhook field, minus the secrecy), and resolve the already-flagged Unresolved Question about whether it should be a hard validation gate before this Epic is considered done.

## Concerns

- [ ] **The Pattern Decisions table claims burst protection that no task implements.** Row "Burst handling" (plan line 89) states the chosen design is "Edge-triggered threshold latch ... **+ short internal coalescing window** tuned to Slack's ~1/sec limit," and Epic 1.2's Goal line repeats "coalesces queue-depth [bursts]." But the only burst-handling logic actually specified anywhere in Epic 1.2's Stories/Tasks is `MaybeNotifyQueueDepthThreshold` (Story 1.2.4) — an edge-triggered *digest* latch, not a coalescing window. `NotifyReviewQueueItem` (Task 1.2.2c) has no rate limiting of its own: with `NotifyOnQueueItem=true` and a burst of items arriving below (or with) `QueueDepthThreshold` disabled (`0`), each item fires an immediate, independent Slack POST with nothing throttling the rate — exactly the scenario `research/pitfalls.md` §2 says "a naive 'POST once per item' implementation sends 10 requests in milliseconds — several will 429," and explicitly recommends "a single global rate limiter (token bucket, 1/sec) shared across all Slack sends ... regardless." The Pattern Decisions table's wording will mislead a reviewer or future maintainer into thinking this was built. — **Recommendation**: either add a real coalescing/rate-limiting task to Epic 1.2 (a package-level 1/sec token bucket guarding every `postToSlack` call is the minimum the research called for), or correct the Pattern Decisions table to state plainly that only the digest-threshold latch exists and per-item bursts are an accepted gap.

- [ ] **`resolveSlackWebhookURL`'s core precedence/decrypt logic — the entire point of ADR-001 — has no test anywhere in the plan.** Story 1.1.3's acceptance criteria explicitly defers full verification: "this is asserted at the `config` package level for the override getter, and end-to-end in Task 1.5.1a." But Task 1.5.1a is `TestNotifyReviewQueueItem_TruncatesOversizedDiff` — a diff-truncation test, unrelated to override precedence or decryption. Scanning all of Epic 1.5's tasks (1.5.1a truncation, 1.5.1b dashboard link, 1.5.1c non-blocking, 1.5.1d no-log-URL, 1.5.1e threshold latch), none actually exercises `resolveSlackWebhookURL`'s three branches (env override wins over stored ciphertext; decrypt-when-only-ciphertext-present; clean no-op when neither set) at the `SlackNotifier`/`server/services` level — only the "both empty" no-op case has an AC (Story 1.2.1). Given ADR-001 exists specifically because this secret-resolution path carries "agent-approval authority" blast radius, shipping it with a broken cross-reference to a nonexistent test is a real coverage gap, not just a doc typo. — **Recommendation**: add an explicit `server/services` test (e.g. `TestResolveSlackWebhookURL_EnvOverride_TakesPrecedenceOverDecryptedValue` and `TestResolveSlackWebhookURL_DecryptsStoredCiphertext_WhenNoOverride`) and fix Story 1.1.3's cross-reference.

- [ ] **429 (rate-limited) responses get no differentiated handling, and the plan is silent on accepting that gap.** `research/pitfalls.md` §2 calls out 429 specifically as the worst case to silently drop ("exactly the items where 'many are blocked at once' is arguably the most important moment for the human to be notified"). Task 1.2.1c's `postToSlack` treats all non-2xx uniformly — no distinction for 429, no use of Slack's `Retry-After` header, no note that this is an accepted risk under the Medium appetite. `requirements.md`'s Rabbit Holes already pre-authorizes skipping full backoff, but the plan should say so explicitly for 429 rather than leaving it indistinguishable from every other failure. — **Recommendation**: add one sentence to the Observability Plan or Story 1.2.1 stating 429 is treated identically to other failures by design (appetite tradeoff), so a future reader doesn't mistake the omission for an oversight.

- [ ] **Delivery-failure visibility is passive-only, contradicting research's explicit recommendation and partially undercutting the feature's own premise.** `research/pitfalls.md` summary item 7 and `research/ux.md` §4 both recommend surfacing persistent Slack delivery failure through the *existing* in-app `NotificationService` channel (which still works even when Slack doesn't), not only a settings-page status line the user must think to check. The plan (Story 1.4.3e) only implements the passive settings-page line — there is no proactive in-app notification when Slack delivery starts failing. Since the entire feature exists to convert a pull interface into a push one, a silently-broken Slack integration degrades back to "you have to remember to check the app" — for the specific one failure mode (silent webhook revocation) that `research/ux.md` §2 calls "the single highest-risk UX gap for this feature category." — **Recommendation**: either add a task that fires an in-app notification via the existing channel after N consecutive Slack failures, or explicitly note in the plan that this was considered and rejected as out of Medium-appetite scope.

## Minors

- `server/services/secret_scanner.go` already has a Slack token redaction pattern (`\bxox[boas]-...`), and `research/features.md` explicitly flags that the new `slack_webhook_url` value (a `https://hooks.slack.com/services/...` URL, different shape) should probably be added to that scanner's pattern list so a pasted webhook URL can't leak via captured terminal/scrollback output. No task in the plan touches `secret_scanner.go`. Low severity for a single-user instance, but a named research recommendation with zero plan coverage or explicit rejection.
- Two items are correctly flagged in the plan's own "Unresolved Questions" section (DashboardBaseURL validation requirement; whether digest and per-item notifications are mutually exclusive) but are marked "owner: Tyler" without a gate preventing Epic 1.2/1.3/1.4 work from starting before they're answered — worth converting into an explicit go/no-go checkpoint before implementation begins, not just a footnote.
