# Research: Pitfalls — Slack Outbound Webhooks (Phase 1) + Inbound Interactive Callbacks (Phase 2)

**Project**: slack-review-notifications
**Scope**: Common failure modes when building Slack incoming-webhook notifications and (Phase 2) Slack interactive-component callbacks, mapped to this codebase's existing conventions where relevant.

---

## 1. Secret handling

**The failure**: webhook URL (`https://hooks.slack.com/services/T000/B000/XXXXXXXX`) and, in Phase 2, the signing secret are bearer credentials — anyone who has the webhook URL can post to the channel indefinitely (Slack has no other auth check), and anyone who has the signing secret can forge inbound approve/deny callbacks. Both must be treated as secrets, not config strings.

**Concrete ways this goes wrong**:
- **Logged verbatim.** The most common bug: a `log.Error("failed to post to slack", "url", webhookURL, "err", err)` or an `httptrace`/debug dump that includes the request URL. Slack webhook URLs embed the full bearer credential in the path — logging the URL is equivalent to logging a password. This repo's `notification_service.go` already logs structured fields (`log.Error("[NotificationHistory] failed to list notifications", "err", err)` at `server/services/notification_service.go:169`) — the Slack notifier must audit every log call to confirm the URL/secret never appears as a field value, including in wrapped errors (`fmt.Errorf("post to %s: %w", webhookURL, err)` leaks it into the error string, which then gets logged upstream).
- **Committed to config.json.** `config/config.go` already has precedent for exactly this problem: `AnthropicAPIKey` (`config/config.go:371`) is stored in plaintext in `config.json` and documented as also settable via `ANTHROPIC_API_KEY` env var (`config/config.go:481`). If `config.json` is ever committed (e.g. accidentally added, or backed up to a dotfiles repo) the webhook URL and signing secret leak. The repo does have a real encryption mechanism already — `MachineEncryptionKey` (`config/config.go:299-301`, AES-256-GCM) — currently scoped to "sensitive token data in ItemSource configs." Whether the Slack webhook URL/signing secret should also be encrypted at rest under this key (vs. following the `AnthropicAPIKey` plaintext-with-env-override precedent) is a planning decision — flagging as an inconsistency: this repo has two different precedents for secret-at-rest handling and the plan should explicitly pick one rather than silently doing a third thing.
- **Exposed in error messages returned to the frontend.** If the settings UI's "test webhook" action (see §6) proxies the raw HTTP client error back to the browser, a misconfigured URL or a Slack error response could echo the webhook URL back into a toast/console log visible to anyone with browser devtools open — low risk single-user, but still worth stripping.
- **Exposed in stack traces / panics.** A `panic(fmt.Sprintf("slack post failed: %v", err))` including a wrapped URL, or an unhandled panic captured by whatever crash/telemetry pipeline exists (OpenTelemetry export per `.claude/docs/opentelemetry.md`), can ship the secret to a third-party APM backend.
- **1Password precedent not followed.** CLAUDE.md's own `secrets` Ansible role notes 1Password is the established secret-storage tool elsewhere in the repo tooling (`bootstrap/roles/secrets`). The requirements doc (`project_plans/slack-review-notifications/requirements.md:34`) explicitly calls for following "existing secret-handling conventions (see 1Password usage elsewhere in the repo)" — but 1Password is a *developer/bootstrap-time* tool (`op` CLI, environment injection at provisioning), not something the running Go server process integrates with at runtime for end-user config. Conflating the two would be a planning trap: the actual mechanism here is almost certainly "config field the user pastes into the settings UI," not "fetch from 1Password at runtime" — confirm this interpretation before designing storage, since the two lead to very different implementations (a text input + persisted field vs. an `op read` shell-out with its own credential-availability problem in a systemd user service).

**Mitigation direction**: mask the field in any settings-UI GET response (return `"configured": true` + last-4-chars, never the full value, mirroring how many SaaS admin UIs handle API keys) and grep the diff for `webhookURL`/`signingSecret` appearing in any `log.*`/`fmt.Errorf`/`%v`/`%s` call before merging.

## 2. Rate limits and burst handling

**The facts** (Slack's incoming webhook docs, informal/undocumented exact number but widely observed and referenced by Slack support): roughly **1 request/second per webhook**, burstable briefly, with **HTTP 429** returned on excess along with a `Retry-After` header (in seconds) once the limit is hit. Slack does not guarantee message ordering under retry, and repeated 429s within a short window can trigger longer server-side backoff windows.

**Where this bites this feature specifically**: the requirements doc's own "Rabbit Holes" section (`requirements.md:63`) already flags this — a "queue-depth-threshold burst" (many review-queue items landing at once, e.g. after a batch backlog auto-spawn or a mass session failure) could fire N Slack POSTs in a tight loop, e.g. from `NotificationService.SendNotification` (`server/services/notification_service.go:67`) being called once per item in a fan-out. Concretely:
- If 10 review-queue items appear in the same poll cycle (`session.ReviewQueuePoller`, referenced at `server/services/notification_service.go:56`), a naive "POST once per item" implementation sends 10 requests in milliseconds — several will 429.
- **429 handling that's easy to get wrong**: treating 429 as a normal failure (log and drop) silently loses the notification for exactly the items where "many are blocked at once" is arguably the most important moment for the human to be notified. Treating it as "must retry" without a cap risks a retry storm compounding the burst.
- **Coalescing is cheaper than backoff for this appetite.** Given the "Medium (1-2 weeks)" appetite and the requirements doc explicitly saying "worth at least a de-dupe/coalescing note in planning, not necessarily a full backoff implementation," the simplest correct design is: batch queue-depth-threshold triggers into a single message ("5 new items in review queue") rather than one message per item, and rely on a short debounce/coalescing window (e.g. collect items arriving within a 2-5s window into one Slack Block Kit message) rather than building real retry/backoff machinery. A single global rate limiter (token bucket, 1/sec) shared across all Slack sends is still worth adding regardless, since even the "new item" and "queue depth" triggers together could exceed 1/sec on a bad day.
- **Silent drop is a real risk with fire-and-forget.** The non-functional requirement ("notification delivery is fire-and-forget/best-effort with logging, not a blocking dependency," `requirements.md:33`) is correct for not blocking the approval flow, but "best-effort with logging" must mean the failure is actually visible somewhere (see §6) — a 429 that's swallowed into a log line nobody reads defeats the entire point of the feature during exactly the burst scenario it exists to help with.

## 3. Message / block size limits

**The facts** (Slack Block Kit limits, current as of Slack's published API docs):
- Each `section` block's `text` object: **max 3000 characters** (plain_text or mrkdwn).
- Max **50 blocks per message** (5 for some surfaces like modals/app home, but 50 for standard messages via `chat.postMessage`/incoming webhooks).
- Total request payload: Slack's webhook endpoint is not permissive of arbitrarily large payloads — practically, keep total JSON well under **~40KB** (specific undocumented hard cap, but oversized payloads return a 400/`invalid_blocks` or are silently truncated depending on which limit is hit first).
- Attachment-style fallback `text` field also has bounds but Block Kit is the modern path and what should be used here.

**Where this bites this feature specifically**: `requirements.md:40` calls for the message to include "diff summary if available" — this is the single highest-risk piece of the outbound message. A large agent-generated diff (thousands of lines) pasted directly into a `section.text.text` field will:
- Exceed the 3000-char block limit → Slack returns an API error for the whole message (not a partial success), so if this isn't caught, the *entire notification silently fails to send*, which is exactly the failure mode this feature exists to prevent (worse: it may fail exactly on the noisiest/most-important items, since those tend to have the biggest diffs).
- If naively split across multiple blocks to route around the 3000-char cap, could also blow past the 50-block-per-message limit for a genuinely huge diff.

**Mitigation direction**: hard-truncate the diff summary to a fixed budget (e.g. first N lines / M characters with a "... truncated, see dashboard" suffix and the dashboard link) *before* constructing the Block Kit payload, never pass the raw diff through unbounded. Unit test this specifically per `requirements.md:46` ("Unit tests for the notifier (message formatting, ...)") — this is the one part of message formatting where a test with a large fixture diff is worth the cost, since it's the most likely field to regress silently (someone bumps the diff-summary generator elsewhere in the codebase and it grows past the cap with no compile-time signal).

## 4. Blocking the critical path (non-blocking requirement)

**The explicit constraint**: `requirements.md:33` — "a Slack delivery failure (webhook down, network error, rate limit) must not block or fail the underlying review-queue/approval flow." This is the standard fire-and-forget notification requirement, and the standard way to violate it is subtler than "forgetting to catch the error":

- **No timeout on the outbound HTTP client.** Go's `http.DefaultClient` has no timeout by default — a hung TCP connection to a slow/unreachable Slack endpoint (or a proxy/firewall silently black-holing the connection) can hang **indefinitely**. If the Slack POST is called synchronously inline in the same goroutine as the review-queue poller or `ApprovalHandler.HandlePermissionRequest` request path, a single hung Slack request stalls that poller/handler for as long as the connection hangs — which, without a timeout, can be forever. This is the single most likely way this feature causes an incident, precisely because it's invisible in the happy-path testing (Slack usually responds in <500ms) and only manifests under a real network partial-failure.
- **Fix shape**: (a) always construct the `http.Client` with an explicit short timeout (2-5s is generous for a webhook POST — Slack's own guidance is sub-second typical latency), AND (b) fire the send in its own goroutine so even a client-timeout-respecting call can't add latency to the caller. Both are needed — a timeout alone still adds up-to-N-seconds of latency to the critical path if called synchronously; a goroutine alone without a timeout can still leak an unbounded number of goroutines under sustained Slack unavailability (goroutine leak = slow memory growth, not immediately visible either).
- **Goroutine leak edge case**: fire-and-forget via `go func() { ... }()` without a bounded context can still accumulate live goroutines if Slack degrades to "accepts the TCP connection but never responds" for an extended outage and if many notifications fire during that window without a cap. Use `context.WithTimeout` on the outbound request (not just `http.Client.Timeout`, since the client-level timeout is a decent baseline but per-request context gives an explicit, testable bound) so each goroutine is guaranteed to exit.
- **Panics in the notification goroutine must not crash the process.** A `go func() { ... }()` that panics (e.g. a nil-pointer on a malformed session object passed into message formatting) with no `recover()` will crash the entire stapler-squad process — turning a notification bug into a full outage. Any goroutine spawned for this feature needs a deferred recover that logs and drops, never propagates.
- **Where this plugs in matters.** `requirements.md:43` says "wire the notifier into the existing review-queue poller / `NotificationService` path as an additional sink." `NotificationService.SendNotification` (`server/services/notification_service.go:67`) is the natural insertion point — check whether that method itself already runs off the hot request path (i.e. is it called synchronously from `ApprovalHandler.HandlePermissionRequest`, or already async?) before assuming "adding a sink here" is automatically non-blocking; if `SendNotification` today is called inline and synchronously from the permission-request HTTP handler, adding a slow Slack POST as a new sink inside it would directly slow every approval-request response even before considering network hangs.

## 5. Phase 2 — inbound signature verification pitfalls

Slack interactive components (and slash commands, Events API) all use the same signing scheme: HMAC-SHA256 over `v0:{timestamp}:{raw_body}` using the app's Signing Secret, sent back as `X-Slack-Signature: v0={hex}` alongside `X-Slack-Request-Timestamp`.

**Common implementation mistakes, in likely order of "someone will actually make this mistake":**

1. **Non-constant-time comparison.** Comparing the computed signature to `X-Slack-Signature` with `==` (Go string equality, or `bytes.Equal`) is a textbook timing side-channel — an attacker who can make many requests and measure response-time variance can theoretically recover the secret byte-by-byte. Must use `hmac.Equal(computed, received)` (Go's `crypto/hmac` package provides this specifically for this purpose) — **not** `subtle.ConstantTimeCompare` misused with mismatched slice lengths (a common secondary bug: `ConstantTimeCompare` returns 0, not a panic, on length mismatch, but people sometimes skip the length check and get a spurious pass/fail depending on how the underlying compare is written). `hmac.Equal` handles this correctly internally.
2. **Verifying against the parsed/re-serialized body instead of the raw bytes.** The signature is computed over the exact raw request body bytes Slack sent. If the handler reads `r.Body` into a struct via `json.NewDecoder(r.Body).Decode(...)` (or, for interactive components specifically, Slack sends `application/x-www-form-urlencoded` with a `payload` field containing JSON — so it's actually form-decoded, not raw JSON) *before* computing the HMAC, the raw bytes are already consumed (an `io.Reader` is not rewindable) and/or don't match what was hashed if any re-encoding happened. The fix is standard but easy to get backwards: read the full raw body into a `[]byte` first (`io.ReadAll(r.Body)`), verify the signature against those exact bytes, and *only then* parse/decode into a struct from that buffered `[]byte`. Order matters — this is the single most common Slack-signature-verification bug reported across SDKs/frameworks.
3. **No replay-attack window enforcement.** Slack recommends rejecting requests where `X-Slack-Request-Timestamp` is more than 5 minutes (300s) old, specifically to blunt replay attacks (a captured valid request+signature pair being re-sent later). Skipping this check means a leaked/logged/proxied historical request (e.g. accidentally logged during debugging — see §1's logging pitfalls, which apply symmetrically to inbound request logging too) remains a valid, replayable "approve" or "deny" action forever. This matters unusually much here specifically because — per `requirements.md:29` — "anything that can call `/api/hooks/permission-request`-equivalent effectively has agent-approval authority": a replayed approve-click could authorize an agent action after the human intended to deny it, or vice versa.
4. **Comparing against the wrong secret variable, or trusting a client-supplied identifier.** Slack apps have separate Signing Secret vs Bot/User OAuth tokens — mixing these up (using the OAuth token to "verify" instead of computing HMAC with the actual signing secret) is a category of bug where the code *looks* like it's verifying but isn't checking anything meaningful. Confirm during implementation review that the verification path genuinely fails closed on a tampered payload (write a test that flips one byte of the body and asserts rejection — not just a happy-path test that a valid payload passes).
5. **Timestamp/body available to the handler in the wrong Content-Type.** Interactive component payloads arrive as `application/x-www-form-urlencoded` with a single `payload=<url-encoded-JSON>` field — not as a raw JSON body. Signature verification is still computed over the *entire raw request body* (the urlencoded form string, not the decoded-and-re-extracted JSON), so decoding the form into a `url.Values` map first and only later trying to reconstruct "the body" for verification is another way to accidentally verify against different bytes than what Slack actually signed.
6. **Fail-open on verification errors.** If the HMAC computation itself errors (e.g. secret misconfigured, empty) the handler must reject the request (401/403), not fall through and process the callback anyway — a "verification unavailable, allow by default" bug is worse than not having verification at all because it looks protected in code review.
7. **New unauthenticated public HTTP surface.** The requirements doc already flags this as the highest-risk piece (`requirements.md:61`) — signature verification is necessary but not sufficient; the endpoint also needs standard HTTP hardening (request size limit, since it's now internet-reachable per the ngrok/reverse-proxy requirement; no verbose error bodies that leak internals to an internet-facing caller, unlike the Phase-1-only localhost-scoped surfaces this repo currently has, cf. `validateLocalhostOrigin`/`validateLocalhostAddr` at `server/services/notification_service.go:302,308` which establish a "localhost-only" trust boundary precedent that Phase 2's endpoint explicitly cannot rely on).

## 6. Config/UX pitfalls

- **No way to test the webhook before relying on it.** Without a "send test message" action in the settings UI, the first real signal a misconfigured webhook exists is a review-queue item nobody got notified about — by definition, after it already mattered. `requirements.md:44` calls for a settings UI "following existing settings page conventions" but doesn't explicitly call out a test-send action; this is worth flagging in planning as a near-free addition (one button, reuses the same send path with a canned payload) with outsized value for a single-user system where "did I configure this right" has no other verification path.
- **Silent webhook revocation.** Slack incoming webhooks can be revoked/rotated from the Slack app admin UI at any time, independent of stapler-squad. Once revoked, POSTs to that URL return `404` (not 401/403 — Slack's webhook 404 means "no such webhook," ambiguous with "I typo'd the URL"). Per the non-blocking requirement, failures are logged and swallowed — meaning a revoked webhook produces **zero visible signal in stapler-squad** unless something surfaces persistent failures somewhere the user will actually see it (e.g. an in-app banner/toast via the *existing* `NotificationService` in-app channel — notifying "Slack delivery has failed N times" through the channel that still works is the natural fallback, and avoids needing new infrastructure). Worth an explicit design note: track consecutive-failure count and surface it, rather than only writing to a log file nobody tails.
- **No visibility into delivery success either.** Related to the above — even absent an error, the user has no in-app confirmation "yes, that last notification made it to Slack." For a single-user tool this is lower priority than the failure case but worth at least noting as a known gap rather than silently deciding not to build it.

## 7. Notification fatigue

**The general pattern**: any "notify me on X" feature that starts with good intentions and no volume control degrades into noise the user learns to mute/ignore, at which point the feature has negative value (worse than not having it, because it creates false confidence that "I'll get pinged" while the human has already tuned it out).

**Where this applies here specifically**:
- `requirements.md:41-42` already includes two independent trigger conditions — "new review-queue item arrives" AND "queue depth exceeds threshold N" — which, if both fire without care, double-notify for the same underlying event (a burst of items triggers both "new item" pings *and* a "threshold exceeded" ping).
- No mute/snooze path is in scope per the requirements doc's stated scope (`requirements.md:38-58`) — this is consistent with the "Medium appetite, Phase 1 primary deliverable" framing, but worth naming explicitly as an accepted gap rather than an oversight: a user who gets pinged for every single review item during a heavy backlog-automation day (per `.claude/rules/feature-testing-registry.md`'s existing backlog auto-spawn WIP-limit-of-2 pattern, this could realistically be several items/hour) has no way to say "just tell me if it's been pending >30 min" or "mute for the next 2 hours" without editing config. The `slack_notify_on_queue_item` bool toggle is the only volume control in Phase 1's scope, which is coarse (all-or-nothing) — acceptable for a v1 given the appetite, but the plan should say so explicitly rather than let it surface later as "why am I getting spammed."
- **Threshold tuning has no feedback loop.** The queue-depth threshold N is a single static config number; if set too low it spams, too high it never fires. Since this is single-user, self-hosted, there's no analytics/dashboard proposed to help the user pick N — worth a sane conservative default (e.g. threshold disabled/very high by default, opt-in lower) so the out-of-the-box experience errs toward under-notifying rather than immediately spamming a real Slack channel on first use.

## Summary of concrete design implications for planning

1. **Never let the webhook URL or signing secret reach a log call, wrapped error string, or frontend error response** — grep-able rule, worth a lint/test guard (cf. `.claude/rules/interface-pollution-checklist.md`-style enforcement) rather than just a code-review reminder.
2. **Coalesce, don't fan out** — batch same-poll-cycle items into one Slack message; add a simple global rate limiter (1/sec token bucket) as a backstop, not full retry/backoff machinery, matching the Medium appetite.
3. **Hard-cap the diff summary length before building Block Kit blocks** — this is the one piece of message formatting that needs a large-input unit test.
4. **Timeout + goroutine + recover(), all three, on every outbound Slack POST** — timeout alone still blocks the caller for up to N seconds; goroutine alone can leak; no recover() turns a formatting bug into a process crash.
5. **Phase 2 signature verification**: `hmac.Equal`, verify raw un-decoded body bytes before any parsing, enforce the 5-minute replay window, and write an explicit "tampered payload is rejected" test — don't rely on a happy-path test alone.
6. **Add a "send test message" action** in the settings UI — cheap, reuses the send path, closes the biggest UX gap (no feedback that config is correct).
7. **Surface persistent delivery failure through the existing in-app `NotificationService` channel** rather than only logging — a silently-revoked webhook must eventually become visible somewhere the user will see it.
8. **Name the fatigue gap explicitly** — Phase 1 ships without mute/snooze by design (appetite-appropriate), but the plan should say so rather than let it be discovered as a surprise later.
