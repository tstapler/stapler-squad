# UX Research: slack-review-notifications

Scope: Phase 1 (outbound Slack notifications) per `project_plans/slack-review-notifications/requirements.md`. Phase 2 (inbound interactive buttons) is referenced only where it changes the Phase-1 message design (e.g. leaving room for a future button block).

## 1. Comparable UX patterns — external chat notification for a queue/approval system

Products solving the same job ("something is waiting on you, and you're not looking at the dashboard") converge on a small set of patterns:

- **GitHub/GitLab Slack apps (PR review requests, CI status).** Message = one compact block: actor + action + subject + link, e.g. "Tyler requested your review on `stapler-squad#365`". No wall of diff text in the message body — the message is a *pointer*, not a payload. The repo/PR title is the link itself (clickable text), not a separate "click here" line. This matters directly for our case: `session name` + `tool/summary` should be the message text, and the diff/queue-item is a link, not inlined content past a line or two.
- **PagerDuty.** Alerts carry explicit *severity* and *state* (triggered/acked/resolved) in the message, and Slack messages are **updated in place** (via `chat.update`) as state changes rather than posting a new message per state transition. Directly relevant to our rate-limit/coalescing rabbit hole: if a queue item is approved before the next poll cycle, updating the original message ("✅ Resolved by web UI") avoids a stale "still pending" message sitting in the channel forever. Full update-in-place is arguably Phase 2+ scope (requires tracking the Slack message timestamp per item), but even Phase 1 should store enough (message ts / channel) to make this addable later without a redesign — worth a one-line note in planning, not full implementation given Medium appetite.
- **CI bots (CircleCI, GitHub Actions on Slack).** Color-coded attachment/side-bar (green/red/yellow) + a single primary action button ("Re-run", "View run"). Buttons are *disabled/replaced with a static label* after being clicked once, to prevent double-submission from two people clicking the same message. This is the single most important lesson for a *future* Phase 2 approve/deny button: without idempotency + post-click UI feedback, two clicks (or a click after someone already approved via the web UI) either double-apply an action or silently no-op with no user-visible signal. Phase 1 doesn't have this problem (no buttons yet) but the message should be designed so Phase 2 can slot a Block Kit `actions` block in without restructuring the whole message.
- **Vercel deployment notifications.** Terse, single-line-primary + secondary metadata line (branch, commit, duration), always ends in exactly one link ("Visit Preview"). No threading — each deploy is a new message. This is the right level of ambition for Phase 1: one message per queue item, not a running thread. Threading only pays off once there's a stream of *related* updates to the same item (which is closer to Phase 2's future "update in place" territory).
- **Slack's own "coalescing" convention** (seen in GitHub's Slack app for high-volume repos): when many events fire in a tight window, apps either batch into one digest message ("3 new PRs opened") or drop below a noise threshold and link to a list view instead of posting N separate messages. This maps directly to the requirements' queue-depth-threshold trigger — when N items are already queued, the UX should read as "N items are pending — go to dashboard" rather than firing N separate near-simultaneous messages that will also hit Slack's ~1msg/sec incoming-webhook rate limit. Treat the depth-threshold notification as a **distinct message shape** (a summary/digest), not the same per-item template repeated in a burst.

**Takeaway for message structure (Phase 1):**
1. One message per triggering event (new queue item, or threshold crossed) — no thread nesting needed at this appetite.
2. Primary line: session name + what's being requested (tool/summary), not prose.
3. Secondary line: compact metadata (repo/branch, size of diff if available) — capped, per the rabbit-hole note in requirements (~3000 char Slack block limit).
4. Exactly one link, and it should deep-link to the specific queue item in the dashboard (not just the dashboard root) — "click here" as the CTA text is a known anti-pattern (screen reader users tabbing by link list hear a wall of "click here, click here"); link text should be the session/item name itself.
5. Design the payload as Slack Block Kit blocks (not just `text`) even in Phase 1, so a Phase 2 `actions` block is additive, not a rewrite.

## 2. User mental model: what "notify me on Slack" implies

When a user toggles on a Slack integration, they form three implicit expectations that, if violated, produce silent trust erosion (they stop believing the toggle and go back to manually checking the dashboard — defeating the entire feature):

- **"It works until I'm told otherwise."** A toggle is a promise of an *ongoing* state, not a one-time action. If the webhook silently starts failing (Slack webhook revoked, network error), the user has no signal — they still see the toggle "on" in the UI. This is the single highest-risk UX gap for this feature category (see PagerDuty/GitHub outage postmortems: silently-broken outbound webhooks are a top complaint). The settings UI must surface *last known delivery status*, not just the configured on/off state — see §4.
- **"I want to verify before I trust it."** Every comparable settings UI in this space (Slack's own "Incoming Webhooks" app config, GitHub's webhook settings page, PagerDuty's integration setup) offers a **"Send test message" / "Test webhook" button** immediately adjacent to the URL field, before the user ever saves and walks away. This is not a nice-to-have — it's the way a user closes the loop between "I pasted a URL" and "I believe this will page me." Given the review-queue trigger may not fire for hours, a synchronous test button is the *only* way a user gets confidence at configuration time.
- **"On/off should be legible at a glance, and match reality."** Users expect the toggle state to be the source of truth for "will I get pinged." A toggle that's on but pointing at a dead webhook is worse than no toggle at all, because it creates false confidence — the user believes they'll be notified and stops checking the dashboard manually.

**Implication for Phase 1 settings UI**: three UI elements, not two — (1) webhook URL input, (2) enable toggle(s) for the two trigger types (`slack_notify_on_queue_item`, threshold), and (3) a "Send test message" action that performs a real POST and reports success/failure inline. Optionally a small "last notification sent: <time>" or "last delivery failed: <time>, <reason>" status line once any real notification has fired — this is the ongoing trust signal from bullet 1, distinct from the one-time test in bullet 2.

## 3. Accessibility requirements for the settings form

The repo already has consistent, established a11y conventions for exactly this class of form — no new pattern needs to be invented, just followed:

- **Label association**: every input needs an explicit `<label htmlFor="...">` bound to the input's `id`, per `PushNotificationSettings.tsx` (`web-app/src/components/settings/PushNotificationSettings.tsx:54-62`) — not a wrapping label or placeholder-as-label.
- **Two distinct ARIA politeness levels are already codified** — reuse both, don't invent a third:
  - `role="alert"` / `aria-live="assertive"` for real failures (invalid URL, test-send failed) — see `InlineNotice.tsx`'s doc comment (`web-app/src/components/common/InlineNotice.tsx:4-12`) contrasting it with `InlineError`, and `AliasesManager.tsx:334,414` (`role="alert"` on field errors).
  - `role="status"` / `aria-live="polite"` for non-blocking informational state (e.g. "test message sent", "last delivered 2 minutes ago") — `InlineNotice.tsx:34-35`.
- **Field-level error wiring**: `CronScheduleInput.tsx` (`web-app/src/components/workflows/CronScheduleInput.tsx:170-189`) is the best existing template for a validated single-line input in this codebase — `aria-invalid={showError}` on the input, `aria-describedby` pointing at *both* a persistent explanation region and the conditional error region's `id`, and the error itself rendered in a `role="alert"` div with a `data-testid`. The webhook URL field should mirror this exactly: `aria-describedby` linking to a short "paste your Slack Incoming Webhook URL" hint plus the validation error when present.
- **Secret-like field precedent**: `BacklogSourcesSettings.tsx` already has a `token` field (`web-app/src/components/settings/BacklogSourcesSettings.tsx:101`) for source auth tokens — check its input `type` (masked vs. plain text) and whether it round-trips the value or shows a placeholder like "•••• (saved)" after save, and mirror that for the webhook URL field, since a Slack Incoming Webhook URL is itself a bearer credential (anyone with it can post to the channel) and arguably should not be redisplayed in plaintext after save any more than a token would be.
- **Toggle semantics**: the existing toggle pattern (`PushNotificationSettings.tsx:54-63`) uses a real `<input type="checkbox">` with a bound `<label>`, not a div-based custom switch — keep using native checkboxes for the two notify toggles unless the design system's switch component (if one exists) already handles the ARIA (`role="switch"`, `aria-checked`) correctly. Don't hand-roll a `<div onClick>` toggle.
- **Button/test-action feedback**: the "Send test message" button's result should land in a `role="status"` region adjacent to the button (success) or `role="alert"` (failure) — per the two-tier pattern above — and the button itself should show a disabled/pending state while the test POST is in flight (mirrors `submitting` state already used in `BacklogSourcesSettings.tsx:102`).

## 4. Error states and edge cases

Three distinct failure modes need distinct UX treatment — conflating them (e.g. one generic "error" banner) undersells the difference between "you made a typo" and "this used to work and silently stopped":

| Failure mode | When it's detected | UX treatment |
|---|---|---|
| **Invalid webhook URL format** | Client-side, on blur/submit, before any network call — Slack webhook URLs have a fixed shape (`https://hooks.slack.com/services/...`) | Inline field-level error (`role="alert"`, `aria-invalid`), same tier as `CronScheduleInput`'s error region. Block save, don't just warn. |
| **Test-send fails synchronously** (bad URL that's well-formed but wrong/revoked, network unreachable) | User clicks "Send test message"; the POST returns non-2xx or times out | Inline result under the test button, `role="alert"`. Surface Slack's actual error text if the webhook responds (Slack returns readable bodies like `invalid_token`, `channel_not_found`, `no_service` for common misconfigurations) rather than a generic "failed" — this is diagnostic information the user needs and Slack already hands you for free. |
| **Webhook silently stops working after being revoked in Slack, discovered later** (e.g. someone deletes the Slack app/regenerates the webhook, weeks after setup) | Only detectable server-side, at actual notification-send time, asynchronously from any UI the user is looking at | This is the dangerous one per §2 — there is no user interaction to hang an error on. Requires the backend to persist "last delivery attempt: timestamp, success/failure, error" (small addition to the config/state, not full delivery-log infrastructure) and the settings page to surface it passively next time the user opens Settings — e.g. an `InlineNotice`-style banner: "Last Slack delivery failed 2 hours ago: `channel_not_found`. [Send test message]" This turns an invisible silent failure into something surfaced at the next natural touchpoint, without needing an active alerting channel for the alerting channel itself (avoiding infinite regress). Given fire-and-forget/best-effort delivery is an explicit non-functional requirement (webhook failure must never block the review-queue flow), this status surface is the *only* mechanism the user has to ever learn delivery broke — it is not optional polish, it's the minimum viable closure of the "on/off should match reality" mental model from §2. |

Additional edge cases to design for, lower severity:
- **Empty/unset webhook URL with toggle on**: don't allow enabling the toggle with an empty URL — disable the toggle(s) until a URL is present and (ideally) has passed at least one test send. Prevents a config state that's "on" but structurally can't ever succeed.
- **Rate limiting (Slack ~1 msg/sec)**: not really a settings-UI concern for Phase 1 (per requirements, a full backoff implementation is out of appetite) — but if the backend ever surfaces a 429 from Slack, it should fold into the same "last delivery failed" status line rather than being a distinct UI state, since from the user's perspective it's the same signal ("something's wrong, go check").

## 5. Jobs-to-be-done

For a single self-hosted user (Tyler) running this locally/on a home server:

- **Functional job — "get unblocked faster."** The core job: an agent session is stalled on human input (permission request or review-queue item), and the current interface requires the dashboard to be open to notice. Slack is already an always-open, always-notified surface on the user's phone/desktop — the feature's entire value is converting a *pull* interface (must remember to check) into a *push* one, explicitly named as the problem statement in requirements.md. Success is measured directly by "time from item appearing to item being acted on" shrinking, especially from mobile where opening the dashboard is friction the user currently avoids.
- **Emotional job — "peace of mind, not vigilance."** Without this feature, the user's alternative is either manually polling the dashboard (attention tax) or accepting that agents may sit blocked for hours unnoticed (throughput loss + low-grade anxiety about "is something stuck right now that I don't know about"). The job isn't just "notify me" — it's "let me stop checking," which is why the trust/reliability requirements in §2–4 matter disproportionately to the raw notification-send code: a notification system the user doesn't trust doesn't relieve vigilance, it just adds a second unreliable channel to also worry about. This is why the test-button and delivery-status surfacing aren't scope creep — they're the mechanism that actually delivers the emotional job, not just the functional one.
- **Social job — minimal here, but present.** Single-user, self-hosted (per requirements.md's explicit "Users/Consumers" framing — no multi-tenant/team considerations). The social dimension is narrow: a well-formatted, professional-looking Slack message (clean formatting, working link, no raw JSON or stack-trace-looking text) matters only insofar as this may be a shared/team Slack workspace where other channel members see the message, or the user screenshots it while showing off the tool. Not a primary design driver at this appetite — captured here for completeness, but shouldn't drive scope (e.g. don't add branding/theming work for it).
