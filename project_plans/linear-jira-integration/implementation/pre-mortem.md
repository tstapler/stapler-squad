# Pre-mortem: linear-jira-integration
**Date**: 2026-08-21

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `JiraPlugin.Fetch` (Task 1.3.1c) calls `go-jira/v2/cloud`'s `SearchV2JQL` once per tick and advances the cursor to `max(latest Fields.Updated)` from whatever came back — but that API paginates via `nextPageToken`, not the old `startAt`/`total` model (Atlassian's legacy `/rest/api/3/search` is fully removed and now returns 410 Gone as of 2026; confirmed via web search), and the plan never mentions looping on `nextPageToken`. Any tick where more issues were updated since the last cursor than fit in one page permanently loses everything past page 1, because the cursor advances past their `updated` timestamp before they're ever fetched. | JIRA-sourced backlog items silently stop appearing after a busy project period or a paused sync loop — no error in sync history, `Fetch` "succeeds" every tick, items are just gone for good. | Add an explicit task to Story 1.3.1 requiring `Fetch` to loop on `nextPageToken` (bounded, mirroring GitHub's `maxPreviewFetchPages` pattern) before computing the new cursor from the *fully* fetched result, not just the first page; add a validation.md test case seeding more updates than one page holds in a single tick. | P1 |
| 2 | ADR-002's subscriber refactor renames/rewrites `handleForwardSyncClose` → `handleForwardSync` with a type-switch dispatch, touching the already-shipped, live-used GitHub issue-auto-close path for the sake of two trackers nobody has configured yet. Forward-sync failures are only `log.Warn`/`log.Info`'d (`server/services/backlog_github_forward_sync.go:144-149`), never surfaced as an alert, so a subtle dispatch-ordering or interface-satisfaction bug introduced by the refactor would ship silently. | GitHub-sourced backlog items marked done stop auto-closing their linked GitHub issue and stop getting the "Closed automatically..." comment; only visible in server logs, not any UI banner (the existing Sync-failing banner covers fetch/auth failures, not forward-sync dispatch failures). | Require Story 2.2.1's task list to run the pre-refactor GitHub forward-sync test suite *unmodified* against the post-refactor dispatch code as an explicit regression gate (not "renamed and extended" as currently scoped), and land Epic 2.2 in its own reviewable PR before Epic 2.1's Linear/JIRA-specific tests are added on top. | P1 |
| 3 | Task 1.3.2a's ADF→plaintext walker only handles `paragraph`/`heading`/`text`/`bulletList`/`orderedList`; every other node type is "skipped gracefully" — i.e., silently dropped, not degraded. Real JIRA tickets routinely carry `codeBlock` (stack traces, repro snippets), `table`, `taskList` (checklists), `panel` (warning/info callouts), `mention`, and `inlineCard`/`blockCard` (linked Jira issues or Confluence pages) — exactly the content an agent acting on the imported backlog item would need. | A JIRA-imported backlog item's description reads as a plausible but incomplete paragraph — the code block, checklist, or linked-issue reference that was the actual point of the ticket is just gone, with nothing indicating content was omitted. | Expand Task 1.3.2a/5.1.2d to explicitly enumerate `codeBlock`, `table`, `taskList`, `panel`, `mention`, `inlineCard`/`blockCard` and either render a reasonable plaintext approximation or emit a visible `[unsupported content omitted: <type>]` marker instead of silent removal; add one fixture test per node type before shipping. | P1 |
| 4 | `linear.GetKeychainToken()` (Task 1.1.1a) stores exactly one global API key with no workspace/host key, unlike JIRA's per-base-URL keying (Task 1.1.2a) and GitHub's per-host keying. Linear API keys are scoped to a single workspace. A second `ItemSource` row configured for a different team that lives in a different Linear workspace has no way to carry a second credential. | Configuring a second Linear source for another workspace's team either fails every sync with a confusing "team not found" error, or — if the team ID happens to collide across workspaces — silently imports/forward-syncs against the wrong workspace's data. | Add a `workspace_key`-style field to `linearPluginConfig` and key the keychain token per-workspace the same way `jira.GetKeychainTokenForHost` does per base URL, or explicitly document and enforce (reject with a clear error) the single-workspace limitation in Settings rather than leaving it an unstated assumption. | P2 |
| 5 | Story 3.1.1/3.2.1's MCP one-off import intentionally leaves `BacklogItemData.SourceID` unset ("out of scope, see Unresolved Questions"). The sync loop's dedup lookup is keyed on `(SourceID, ExternalID)` — confirmed at `session/backlog_sync.go:352`, `GetBacklogItemByExternalID(ctx, source.ID.String(), extItem.ExternalID)` — so an item with no `SourceID` is invisible to that dedup check. | The same Linear/JIRA ticket appears twice as separate cards on the backlog board: once from an earlier `import_linear_issue`/`import_jira_issue` one-off call, and again after a polling `ItemSource` is later configured for that same team/project — a very likely adoption sequence ("try one ticket" → "now sync the whole team"). | Pick and specify one fix in plan.md rather than leaving it unresolved: either resolve `SourceID` on MCP import by matching the issue's team/project against any already-configured `ItemSource`, or extend the dedup lookup to also match on `(ExternalID, PluginID)` when `SourceID` is empty. | P2 |

- [x] Failure #2 — Change Story 2.2.1's task list to require the pre-refactor GitHub forward-sync tests pass unmodified against the post-refactor dispatch code, and sequence Epic 2.2 as its own reviewed PR ahead of Epic 2.1's tracker-specific additions. **Patched into plan.md Story 2.2.1 / Task 2.2.1b** (sdd:4-validate readiness-gate pass, 2026-08-21).
