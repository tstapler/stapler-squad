# Pre-mortem: fix-mouse-input-readiness
**Date**: 2026-10-19

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The plan gates `handleTap()` but xterm.js independently emits SGR mouse bytes via `terminal.onData` when `mouseTrackingMode !== "none"` — AC#5 is explicitly excluded in Non-Goals, so desktop clicks and any pointer event that bypasses the gesture layer still produce garbled output. | Clicking inside the terminal on desktop with stale mouse-tracking still generates garbled characters; mobile tap via gesture layer is fixed but the underlying xterm.js path is not. | Move AC#5 out of Non-Goals and implement xterm.js suppression: set `terminal.options.mouseEnabled = false` when `mouseMode === 'none'` instead of filtering `onData`. Validate with a test that attaches a raw `onData` listener and confirms no mouse bytes arrive after `mouseMode` is set to `'none'`. | P1 |
| 2 | `mouseMode` defaults to `'any'` (existing state), so every mobile user with a stale PTY mouse-tracking mode hits garbled output by default and must manually find and click the "Mouse OFF" button — the exact scenario the requirements describe. | Bug reports immediately after ship from users who never touched the Mouse toolbar button; QA test that sets stale mouse mode and opens the terminal without clicking anything shows garbled output. | Change the `mouseMode` default on mobile to `'none'` (gate off by default), letting users opt in via the toolbar button rather than opt out. Alternatively, derive the initial `mouseMode` from `terminal.modes.mouseTrackingMode` so it matches actual PTY state on mount. Add an explicit test for the "user never touches the button" path. | P1 |
| 3 | Epic 4 writes the mouse-disable sequences to `xtermRef.current?.terminal?.write()` inside a `connectionEpoch` useEffect, but during a reconnect the terminal instance is being torn down and rebuilt — `xtermRef.current?.terminal` is `null`, the optional chain silently no-ops, and stale mouse-tracking mode persists into the new connection. | After a network drop and reconnect, mobile users still see garbled output; the issue disappears only on a full page reload (which recreates the xterm.js instance from scratch). | Assert that `xtermRef.current?.terminal` is non-null before relying on the write; alternatively, reset xterm.js mouse mode by calling `terminal.options.mouseEnabled` or clearing `modes` after the terminal is (re)initialized rather than at epoch bump. Add an integration test that simulates disconnect → reconnect and checks `mouseTrackingMode` is `"none"` afterward. | P2 |
| 4 | `connectionEpoch` bumps only on a WebSocket reconnect; a user who navigates to a session that was already connected (or whose session never disconnected) never triggers the epoch useEffect, so stale mouse-tracking mode set by a previous PTY program persists indefinitely across command invocations. | Session where `vim` was run and exited (leaving mouse mode enabled in xterm.js) shows garbled tap output in the next shell prompt, even though the user never disconnected. | Reset xterm.js's mouse-tracking mode on any PTY output that indicates a new prompt (e.g., `StatusIdle` detection) or expose a "Reset mouse mode" toolbar action. At minimum, document this gap prominently so QA knows to test the vim-exit → shell-prompt path, not only the reconnect path. | P2 |
| 5 | Unit tests are written against the gesture hook's `handleTap()` path and confirm the gate works, giving CI a green result — but no test exercises xterm.js's native pointer-event-to-`onData` path, so the P1 failure (xterm.js bypasses the gate) is invisible to CI until a human tests in a real browser. | CI is permanently green; the first bug report arrives from a user after ship. | Add a Playwright or jsdom test that simulates a `pointerdown` event on the xterm.js canvas while `mouseTrackingMode` is set to a non-`"none"` value and `mouseMode` is `'none'`, then asserts that the `onSendData` callback receives no mouse bytes. This covers the xterm.js native path that unit tests cannot reach. | P2 |

## P1 Items (address before implementation)

- [x] Failure #1 — **RESOLVED in plan.md Epic 5 (Story 5.1):** Added suppression of xterm.js's native mouse-event generation via `terminal.options.mouseEnabled = false` when `mouseMode === 'none'`; removed the "No onData filtering" Non-Goal and replaced it with Story 5.1. Validation tests AC5-e and AC5-f added.
- [x] Failure #2 — **RESOLVED in plan.md Epic 5 (Story 5.2):** Clarified that `TerminalOutput.tsx` already has a `useEffect` that auto-sets `mouseMode` to `'none'` on mobile after the first render (before any user interaction). No code change needed; added test AC5-g that confirms the auto-default propagates through `scrollGestureProps` without toolbar interaction.
