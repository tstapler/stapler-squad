# Stack Research: fix-mouse-input-readiness

## 1. xterm.js Version

`web-app/package.json` pins `"@xterm/xterm": "^6.0.0"` (addons are also `@xterm/*`-namespaced, confirming the v6 package layout). The `mouseTracking` field **does not exist** as an `ITerminalOptions` key in xterm.js 6 — this is explicitly noted in two comments in `XtermTerminal.tsx` (lines 294–295 and 557–558):

> "Mouse tracking mode is set at runtime by PTY escape sequences and read via `terminal.modes.mouseTrackingMode`. It is not configurable via prop — the `'mouseTracking'` `ITerminalOptions` field does not exist in xterm.js 6."

The runtime mode lives at `terminal.modes.mouseTrackingMode` (the public `.modes` type omits it, so the codebase casts through `TerminalModesWithMouse` — see `mouseTracking.ts` lines 4–8).

## 2. xterm.js 6 APIs for Controlling/Intercepting Mouse Event Forwarding

xterm.js 6 has **no `ITerminalOptions` flag to disable mouse event forwarding** at construction time, and no per-event hook equivalent to `customKeyEventHandler` for mouse. Once the PTY has set a tracking mode, xterm internally generates and emits encoded mouse escape sequences through `onData`. The only interception point the public API exposes is the `onData` observable itself — callers receive every byte xterm emits (keyboard and mouse alike) and can filter before forwarding to the PTY.

The codebase wires this at `XtermTerminal.tsx` line 891:
```ts
const dataDisposable = terminal.onData((data) => {
  onDataRef.current?.(data);
});
```
A filter inserted here (or in `onDataRef.current`'s implementation) is the **only xterm-native way** to suppress SGR/X10 mouse sequences generated by xterm's own mouse-tracking engine before they reach the PTY. There is no `customMouseEventHandler`, no `disableMouseEvents` option, and no way to force `mouseTrackingMode` back to `"none"` from outside without writing a dedicated escape sequence to the terminal (i.e., sending `\x1b[?1000l` etc. through `terminal.write()`).

## 3. Mouse Tracking Mode Values and Encoding

From `mouseTracking.ts` line 16, the known values are:
```
"none" | "x10" | "vt200" | "drag" | "any"
```

Semantics and typical encoding:
| Mode | Escape to enable | Default encoding | Notes |
|---|---|---|---|
| `none` | — | — | No mouse reporting |
| `x10` | `\x1b[?9h` | X10 (`\x1b[M<btn+32><col+32><row+32>`) | Press-only; limited to col/row ≤ 223 |
| `vt200` | `\x1b[?1000h` | X10 or SGR | Press + release |
| `drag` | `\x1b[?1002h` | X10 or SGR | Press + release + motion while pressed |
| `any` | `\x1b[?1003h` | X10 or SGR | All motion |

SGR encoding (`\x1b[<btn;col;rowM/m`) is enabled separately via `\x1b[?1006h` on top of the tracking mode. When SGR is active, xterm.js emits SGR sequences through `onData`; otherwise it uses X10.

The `handleTap()` function in `useTerminalGestures.ts` (line 641) manually constructs **X10** press+release sequences regardless of whether the current mode is `x10`, `vt200`, `drag`, or `any` — it does not check whether the PTY requested SGR encoding.

## 4. `mouseMode` State in TerminalOutput.tsx — Not Wired to Gestures or xterm

`TerminalOutput.tsx` line 391 declares:
```ts
const [mouseMode, setMouseMode] = useState<'none' | 'any'>('any');
```
It initialises to `'any'` and is set to `'none'` on mobile (`useEffect` at line 393–395). The user can toggle it via the toolbar. **It is used only to set toolbar label/aria text** (lines 1900–1905) and is never passed to `useTerminalGestures` or to `XtermTerminal` as a prop. The hook reads the *actual* xterm.js runtime state (`terminal.modes.mouseTrackingMode`) directly via `isMouseTracking()`, so `mouseMode` and the live xterm state can diverge silently.

## 5. TypeScript Patterns for Passing Options to Gesture Hooks

The codebase uses a prop-bag pattern with a stable `useRef` to avoid re-registering listeners on every render:

- `GestureOptions` (declared in `useTerminalGestures.ts` lines 68–106) is a flat interface holding all hook configuration including callbacks.
- Inside the hook, `const optionsRef = useRef(options)` is updated each render (`optionsRef.current = options`) so event handler closures always read the latest values without being recreated.
- `XtermTerminal` exposes `ScrollGestureProps` (lines 153–173), a subset of `GestureOptions`, forwarded as the `scrollGesture` prop. The component spreads relevant fields into `useTerminalGestures({...})` at lines 353–368.
- To add a new option that gates tap behaviour (e.g. `mouseModeEnabled?: boolean`), the pattern is: add to `GestureOptions` → thread through `ScrollGestureProps` → pass from `TerminalOutput` via the `scrollGesture` prop → read inside `handleTap()` via `optionsRef.current`.

## Fix Strategy (derived from research)

Two independent problems need fixing:

**Problem A — `handleTap()` sends X10 sequences without checking `mouseMode`:**  
Add a `mouseModeEnabled?: boolean` option to `GestureOptions` (defaulting `true` for backwards compat). In `handleTap()`, guard the `else if (t)` branch: only send the X10 sequence when `optionsRef.current.mouseModeEnabled !== false`. Wire `mouseMode` from `TerminalOutput` through `scrollGesture` → `XtermTerminal` → `useTerminalGestures`.

**Problem B — xterm.js native SGR events via `onData` when `mouseTrackingMode != "none"`:**  
Filter the `onData` callback to drop SGR/X10 mouse escape sequences when `mouseMode === 'none'`. SGR mouse sequences match `/^\x1b\[<[\d;]+[Mm]/`; X10 sequences match `/^\x1b\[M/`. Insert the filter in `XtermTerminal.tsx`'s `onData` handler (line 891–893) gated on a `mouseEnabled` prop — or in the `onData` prop implementation in `TerminalOutput`.
