## Concerns

- [ ] **Story 3.3.2's collision-guard call site isn't actually gated by `SessionType`, contradicting the plan's own Risk Control claim.** Risk Control states "Epic 3.3's collision guard is scoped to `SessionTypeNewWorktree` only, so it cannot regress the many legitimate `SessionTypeDirectory` sessions that intentionally share a path." But Story 3.3.2's AC places the guard call "immediately after Story 3.3.1's structural check passes... if `i.preSpawnCollisionGuard != nil`, call `i.preSpawnCollisionGuard(basePath)`" with no `i.SessionType == SessionTypeNewWorktree` condition — and Story 3.3.1's own check is itself only an error-raising condition for `SessionTypeNewWorktree` (for every other type it "passes" trivially, i.e. is a no-op). Read literally, the guard call fires for *any* firstTimeSetup session that resolves `i.gitManager.HasWorktree() == true` — which includes `SessionTypeExistingWorktree` and the worktree sub-branch of `SessionTypeNewProject`, not just `SessionTypeNewWorktree`. It's true this can't affect `SessionTypeDirectory` (which never has a worktree), so the Risk Control claim isn't *dangerously* wrong, but it is factually inconsistent with what Story 3.3.2's AC actually specifies implementing, and an implementer following the AC literally would add broader collision-checking than the plan claims elsewhere. — **Recommendation**: either add an explicit `i.SessionType == SessionTypeNewWorktree` gate to Story 3.3.2's guard-call AC, or correct the Risk Control section's scope claim to say "worktree-bearing session types," and confirm whether `SessionTypeExistingWorktree`/`SessionTypeNewProject` colliding with a live sibling is actually intended to be blocked (it plausibly should be — isolation shouldn't be `SessionTypeNewWorktree`-exclusive — but the plan should say so on purpose, not by omission).

- [ ] **Epic 4.4/4.5's test-seam description mischaracterizes the actual injection mechanism.** The Domain Glossary and Epic 4.4/4.5 both describe swapping in "a test-double `GitWorktreeManager`... per the existing mockable interface, `session/git_worktree_manager.go:511`," implying `Instance.gitManager` can be assigned any type satisfying the `GitManager` interface. Verified by direct read: `Instance.gitManager` is declared `gitManager GitWorktreeManager` (`session/instance.go:592`) — the **concrete struct**, not the `GitManager` interface (`git_worktree_manager.go:511`, confirmed to exist and be satisfied by the struct, but that's not the field's declared type). A value merely satisfying `GitManager` cannot be assigned to a field typed as the concrete struct — this will not compile as described. Existing tests (`session/instance_test.go:42,76`, `session/review_queue_uncommitted_changes_test.go:84,259,324`) all construct `gitManager: GitWorktreeManager{worktree: ...}` directly, confirming the concrete-struct constraint. The achievable mechanism instead is: construct a `*git.GitWorktree` with a chosen path via the existing no-I/O constructor `git.NewGitWorktreeFromStorage(repoPath, worktreePath, sessionName, branchName, baseCommitSHA, opts...)` (`session/git/worktree.go:193`) and call `gitManager.SetWorktree(wt)` — which is capable of producing both Epic 4.4's cases (worktree path == `i.Path`, or a path colliding with another live session's `ActiveDir`) without a real git repo. This isn't a blocker — the tests are genuinely implementable — but the plan's own description of *how* would send an implementer down a dead end (trying to construct an interface-based double) before finding the real seam. — **Recommendation**: correct the Domain Glossary's `GitWorktreeManager` row and Epic 4.4/4.5's task text to name `SetWorktree(git.NewGitWorktreeFromStorage(...))` as the actual mechanism, not an interface-based test double.

- [ ] **Story 1.4.2's fix mechanism is less concretely specified than Epic 3.3.2's, and the "reuses the same lookup" phrasing is imprecise in a way that could produce two different (and non-equivalent) implementations.** `OtherLiveSessionInsideWorktree` (which 3.3.2 reuses as-is) only checks path-liveness overlap — it has no concept of "does that other session already own this conversation UUID." Story 1.4.2's AC requires the finer check ("another live Instance is a more plausible current owner... which already has that same UUID as its own `claudeSession.ConversationUUID`"), which is a genuinely new query (iterate live instances, match both effective path *and* UUID), not a call to the existing function. The plan's own Files list hedges this with "likely reusing or extending `SetPreSpawnCollisionGuard`'s companion port" — language that signals the mechanism wasn't nailed down during repair, unlike 3.3.2's fully-spelled-out closure (exact function, exact call site, exact error string). A coarser implementation (block whenever *any* live sibling shares the effective path, regardless of UUID ownership) would also satisfy the letter of the Given/When/Then but would incorrectly block the legitimate `SessionTypeDirectory` path-sharing case the same AC explicitly says must keep working when the sharing session no longer holds that history. — **Recommendation**: before implementation, write out the new `SessionService`-level method signature explicitly (mirroring `OtherLiveSessionInsideWorktree`'s shape but keyed on UUID+path, not path alone), the way 3.3.2 already did for its own guard.
