| 1 | Epic 3's guards are gated on `i.SessionType == SessionTypeNewWorktree` / `gitManager.HasWorktree()`. | 3 | `startLocked` calls the new `SetPreSpawnCollisionGuard`/`SetConversationOwnershipGuard` closures, which iterate `s.reviewQueuePoller.GetInstances()` and call each other live instance's `IsBackendProcessAlive()`/`GetCurrentWorkingDirectory()`. If `startLocked`'s critical section still holds `i.mu` at that point (per this codebase's actor convention) and those cross-instance calls need the *other* instance's own lock rather than its lock-free `Snapshot()`, two sessions starting concurrently in reversed scan order (A scanning B while B scans A) produce a classic AB-BA lock-order deadlock. This is UNVERIFIED — the plan doesn't state whether `IsBackendProcessAlive`/`GetCurrentWorkingDirectory` are lock-free (likely, given `instance-lock-free-reads.md`'s `Snapshot()` convention) or lock-acquiring. | Two (or more) `CreateSession` calls issued close together intermittently hang forever in a non-terminal status — never reaching `Active` or `Failed`, no error logged — requiring a service restart to clear, matching this repo's own "profile lockups" playbook. | Before implementing Story 3.3.2/1.4.2, explicitly verify and record in plan.md whether `startLocked` holds `i.mu` across the new guard calls, and whether the guard's target-instance accessors are lock-free (`Snapshot()`-based) or lock-acquiring. If lock-acquiring, move the guard calls outside `i.mu`'s critical section (snapshot needed data, release, then check). Add a `go test -race` concurrent-creation test starting two colliding sessions simultaneously to Epic 4. | P3 |
| 4 | Story 1.4.2's `ConversationOwnedByOtherLiveSession` excludes only `selfUUID == inst.UUID`; its AC's only "no regression" test case is "the prior owner is no longer alive." If a restart transiently keeps an old `Instance` object registered as "live" while a new one recovers the same conversation, the new guard could see the old incarnation as an "other" live session already owning that UUID+path and block the legitimate self-recovery — regressing the fix `cold-start-uuid-loss` shipped for, in the same code family this plan touches. | A session restart intermittently fails to reattach to its own prior conversation after this change ships — the user sees an empty/fresh conversation instead of the resumed one, with a new Debug log line naming a spurious "owning session" that is actually the same logical session mid-restart. | Before implementing Story 1.4.2, read and test the actual restart/cold-start-uuid-loss code path end-to-end. Add a Given/When/Then to Story 1.4.2's AC explicitly covering "session restarts and recovers its own UUID via `DetectByPath` while its own prior `Instance` object is still transitioning out of liveness." | P2 |
