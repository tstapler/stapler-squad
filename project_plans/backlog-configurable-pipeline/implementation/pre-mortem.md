# Pre-mortem: backlog-configurable-pipeline
**Date**: 2026-07-15

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The single operator never bothers authoring a second real mode after Phase 4's forced proof exercise — the entire DB-persisted CRUD/cache/snapshot investment (the majority of the "Large, 3-6 week" appetite) becomes permanently dead code because the person who could use the UI is also the person who could just edit Go and redeploy, and redeploying is not meaningfully slower for a solo operator with `make install-service` already wired up. | `pipeline_modes` table has exactly 1 row (the Epic 4.1 "quick" proof mode) weeks after ship, with zero new rows created and zero items ever setting `pipeline_mode` to anything other than that one proof slug or `""`. Because the NFR explicitly waives metrics/alerts ("single-operator tool, no oncall"), nobody is even watching for this signal. | Before Phase 3 (the CRUD UI, the most expensive remaining phase) starts, add a cheap, low-ceremony litmus test: have the operator actually try to define a *second* mode's worth of content using nothing but a text file/API call (bypassing the not-yet-built UI) and time how long it takes vs. editing `WriteSlashCommands` directly. If a raw `curl`/`grpcurl` CRUD call is genuinely faster and less friction than a PR, the UI is justified; if not, descope Phase 3 to the pre-authorized minimal/seed-script fallback (already mentioned in the Appetite section) and add a periodic (even manual, monthly) check of `pipeline_modes` row count / last-used mode as an informal adoption signal despite the "no metrics" NFR. | P1 |
| 2 | The 9-fixed-content-column model (6 command files + 3 prompts, no ability to add/remove a *stage*) turns out too rigid to express what "quick" vs "full" actually means in practice, because `PipelineEngine` is deliberately kept fully separate from `WorkflowEngine`/`Skip*` booleans (Pattern Decisions: "compose, don't subsume") — so a mode can vary prompt *text* but cannot skip the review stage or add a new one; achieving a genuinely "quick" pipeline still requires the operator to separately remember to also toggle `SkipReviewGate`/`SkipPlanning`, two disconnected controls that both have to be set correctly. | Epic 4.1's proof milestone technically passes (2-of-9 fields differ, an Info log line differs) but the operator's actual lived experience of selecting "quick" doesn't feel different — review still runs at full weight, planning still happens — because those are governed by the untouched, unlinked boolean checkboxes, not the mode. | Before Phase 4 is declared done, extend Story 4.1.1's acceptance criteria to require proving the *combination* an operator would actually reach for (mode selection + the relevant `Skip*` boxes together) produces the intended end-to-end reduced pipeline, not just that prompt text differs. Add a `description`/hint field surfaced in the mode selector UI (Epic 3.2) suggesting which `Skip*` boxes a mode's author intends to be paired with it, so the two independent controls don't silently drift apart in the operator's head. |  P2 |
| 3 | Two independent, separately-implemented computations of the "same" content hash — one inside `pipelineModeCache.Load` (`computeContentHash`, used to populate `ItemSessionSummary.PipelineModeSnapshotHash` at session-start) and one inside the `GetPipelineMode`/`ListPipelineModes`/`Create`/`Update` RPC handlers (used as `PipelineMode.content_hash`, the live comparison target for the "what ran" drift UI) — silently diverge after a future edit to one call site (e.g. a 10th content field added to one computation but not the other, or a whitespace/ordering difference), because no test anywhere asserts the two hashes agree for the same underlying row; each is only tested in isolation. | The "what ran" surface (Story 3.4.1) starts showing `"(content since changed)"` on sessions whose mode was never actually edited (false positive), or — worse — fails to flag a session whose mode genuinely was edited (false negative), silently defeating the exact trust guarantee Blocker 1's remediation was built to provide. | Add one integration test (Phase 2, alongside Story 2.2.3's round-trip test) that creates a `PipelineMode`, reads back `content_hash` via `GetPipelineMode`, separately triggers a cache `Load`/`Get` for the same slug, and asserts `cache.Get(slug).ContentHash == getPipelineModeResponse.ContentHash` byte-for-byte — the one place both computations are exercised against the same row and required to agree. Ideally, refactor so both call sites literally call the same exported `computeContentHash` helper on the same 9-field tuple (the plan already says this in prose; make it enforced by having only one production call site, not two independent ones that are merely instructed to match). | P2 |
| 4 | The single-operator threat-model relaxation (ADR-001, ADR-implicit NFR) turns out wrong sooner than assumed, because this repo already has a dual-remote setup (`origin` personal fork, `upstream-fanatics` work canonical per CLAUDE.md) — if stapler-squad is ever run as a shared instance for more than one engineer at Fanatics, `PipelineMode` content becomes a cross-user injection surface (one user's template content driving another user's triage/review LLM calls and file writes) with zero access control, because the entire validation model (`ValidatePipelineModeContent`) was explicitly designed for "self-inflicted breakage," not "protect user B from user A." | A second engineer starts using a shared stapler-squad instance, defines or edits a pipeline mode as a normal part of their workflow, and it silently changes triage/review behavior for backlog items belonging to other engineers with no audit trail beyond a Warn-level log line nobody is watching. | Record an explicit tripwire in ADR-001 (not just the requirements doc): "if stapler-squad is ever deployed for concurrent multi-user access (not just multi-repo/multi-remote for one operator), `PipelineMode` CRUD must gain per-user ownership/authorization before that deployment, not after an incident." This costs nothing to write now and prevents the relaxed threat model from being silently carried forward into a context it was never evaluated against. | P3 |
| 5 | `ItemSessionSummary` gains a precise, hash-verified snapshot for pipeline mode (Epic 1.6) but the 3 pre-existing `SkipReviewGate`/`SkipPlanning`/`AutoSpawnSession` booleans remain un-snapshotted and are read live from the item's current state everywhere, including implicitly by the new "what ran" surface's neighboring UI — so an operator now has high-fidelity historical truth for *one* of the four configuration axes that shape a session's behavior and only current-state-masquerading-as-history for the other three, undermining the very success metric ("the UI surfaces what pipeline/skills ran or will run") this project is scored against. | An operator inspects an old session's "Pipeline" group, sees a clean "Quick Fix, no drift" line, and concludes the session ran under quick-mode-with-review-skipped — but `SkipReviewGate` was toggled after that session ran, so review either did or didn't actually happen contrary to what the current checkbox state implies, and nothing in the UI flags the discrepancy. | Before Epic 3.4 ships, either (a) extend the same snapshot discipline to the 3 booleans (3 more `*Snapshot bool` fields on `ItemSessionSummary`, cheap given Epic 1.6's pattern already exists to copy), or (b) explicitly scope Story 3.4.1's UI copy to disclose the asymmetry ("mode shown reflects what ran; override checkboxes reflect current settings, which may have changed since") so operators aren't misled by omission. Track whichever is chosen as an explicit line item in Phase 1 or Phase 3, not left implicit. | P2 |
