# Validation Plan: backlog-configurable-pipeline

**Date**: 2026-07-15

## Happy Path Scenario

Given a backlog item with no `pipeline_mode` set (the Baseline — every item today runs the fixed hardcoded pipeline), when an operator defines a new `PipelineMode` named "Quick Fix" (slug `quick`) through the `/settings/pipeline-modes` UI, selects it on the item via `BacklogItemForm.tsx`'s pipeline-mode `RadioGroup`, and triggers triage, then `WriteSlashCommands` writes `quick`'s custom slash-command content into the item's worktree, the headless-triage LLM call receives `quick`'s rendered `TriagePromptTemplate` instead of the default `BuildHeadlessTriagePrompt` output, the resulting `ItemSession` records `PipelineModeSnapshot == "quick"` and its content hash, and `BacklogItemDetail.tsx`'s "what ran" surface subsequently shows "Quick Fix" for that session — with no code change or redeploy anywhere in the flow.

## Migration Test

This codebase uses **ent auto-migrate** (`ent.Client.Schema.Create(ctx)` at boot), not up/down `.sql` migration files — confirmed by the absence of a `migrations/` directory alongside `session/ent/schema/` and stated explicitly in `plan.md`'s Migration Plan ("Reversibility: ... no down-migration is required for rollback; reverting the code (not the schema) is sufficient"). The test below adapts "migration reversibility" to what this codebase's rollback story actually is.

**Test**: `TestPipelineModeMigration_should_BeReversible_When_AutoMigrateAppliedAndOldCodePathIgnoresNewColumns`
**File**: `session/ent_pipeline_mode_migration_test.go`
**Type**: Migration (integration-shaped, uses `createTestStorage(t)`)

**Steps**:
1. Point an ent client at a fresh test DB and run `Schema.Create(ctx)` (the same call the server makes at boot).
2. Assert the new `pipeline_modes` table exists with the expected columns and defaults: `slug` unique, `enabled` default `true`, all 9 content-template columns present.
3. Assert `backlog_items` gained a `pipeline_mode` column defaulting to `""`.
4. Assert `item_sessions` gained `pipeline_mode_snapshot` and `pipeline_mode_snapshot_hash` columns, both defaulting to `""`.
5. Insert a `BacklogItem` row the way pre-feature code would (i.e., without ever setting `PipelineMode`) — confirm it reads back with `PipelineMode == ""`, proving pre-existing rows are unaffected and readable (`.claude/rules/ent-schema-generation.md`'s "additive-only" contract holds).
6. Simulate "reverting the code, not the schema": construct a `BacklogItemData`/`ItemSessionSummary` read path that never references `PipelineMode`/`PipelineModeSnapshot*` at all (i.e., exercise the plain pre-feature struct fields only) against the same migrated DB, and confirm no error — the orphaned new columns/table are inert to code that doesn't know about them, which is the concrete meaning of "reversible" in an auto-migrate, additive-only codebase.
7. Assert no destructive DDL occurred anywhere in the migration (no `DROP`/`ALTER ... NOT NULL` without a default) by inspecting the executed statements or by re-running `Schema.Create(ctx)` idempotently against the same DB and confirming no error (ent's auto-migrate is safe to re-run).
