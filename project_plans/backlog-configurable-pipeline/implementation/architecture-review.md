## Blockers (re-checked this pass)

Both previously-filed BLOCKERs are **RESOLVED**. No new blocker-level problem was introduced by the fix pass, including in the 3 independently spot-checked CONCERNS below. Details:

### Blocker 1 — `ItemSessionSummary.PipelineModeSnapshot` content-snapshot gap — **RESOLVED**

The fix adds a second field, `PipelineModeSnapshotHash`, and threads a real content hash through the full stack, not just the schema:

- **Epic 1.6 / Story 1.6.1** (plan.md:461-477): `session/ent/schema/item_session.go` now gains **two** fields — `pipeline_mode_snapshot` (slug) AND `pipeline_mode_snapshot_hash` (SHA-256 hex, truncated to 16 chars, over the 9 raw content-template fields in fixed order). `ItemSessionSummary` gets both fields (plan.md:465). This directly matches the remediation option (a) proposed in the original finding.
- **Hash computation is concrete**, not hand-waved: computed once at cache-load time in `pipelineModeCache.Load` (Task 1.3.2a, plan.md:227-229: "`Load` computes each mode's `ContentHash` via `computeContentHash(...)`"), stored on the unexported `resolvedPipelineMode` snapshot struct (plan.md:28), and surfaced to callers via a new 5th `PipelineEngine` method, `ContentHashFor(mode PipelineMode) (hash string, ok bool)` (Story 1.3.1 acceptance criteria, plan.md:210; implemented in Task 1.3.3c, plan.md:266). `SpawnSessionFromItem`/`TriggerTriage` call `ContentHashFor` at session-start to populate `PipelineModeSnapshotHash` (Story 1.6.2, plan.md:482-484).
- **Exposed on the proto, not just computed and stranded server-side**: Task 1.6.1c (plan.md:475-477) adds `pipeline_mode_snapshot_hash = 17` to the `ItemSession` proto message and wires it into the proto-mapping function — explicitly justified as "Required so Story 3.4.1's 'what ran' UI (a frontend consumer) can actually read these values." The comparison target (`PipelineMode.content_hash`, the *live* mode's current hash) is separately exposed via Story 2.1.1 (plan.md:547), computed on read from the row's current 9 template fields.
- **Story 3.4.1** (plan.md:796-810) confirms the UI actually consumes both: it compares `session.pipelineModeSnapshotHash` against the matching mode's live `content_hash` and appends `" (content since changed)"` on mismatch — with concrete Given/When/Then cases for the unchanged, drifted, and deleted-mode paths. No gap between "hash computed" and "hash used" remains.
- **Migration Plan corrected** (plan.md:73): explicitly lists both new `item_sessions` columns and states "there is no `pipeline_mode_snapshot_version` field — that name was a planning-stage placeholder that never made it into an actual epic and is corrected here" — closing the internal plan-vs-Migration-Plan inconsistency flagged originally.
- **Domain Glossary corrected** (plan.md:41): the `ItemSessionSummary.PipelineModeSnapshot` / `.PipelineModeSnapshotHash` entry now explicitly describes two fields and the case-(a)-vs-case-(b) distinction the original finding said was promised but undelivered.

No gap found. Verified end-to-end: schema → cache computation → engine method → proto exposure (both `ItemSession.pipeline_mode_snapshot_hash` and `PipelineMode.content_hash`) → frontend consumption in Story 3.4.1.

## Concerns

*Unchanged from the previous review round — not re-examined in this targeted pass, except where noted. See git history for the round that originally filed these.*

- [ ] **Lens 3 / GoF pattern appropriateness — `PipelineEngine` as a single-implementation interface** — `PipelineEngine` will ship with exactly one production implementation (`CachingPipelineEngine`) for the foreseeable future (no second implementation is planned anywhere in this plan's 4 phases). Per `.claude/rules/interface-pollution-checklist.md` smell #1, this is a real smell on its face. However, unlike `WorkflowEngine` (see Blockers above), this case has two mitigating factors the checklist itself would accept: (1) it has two genuine cross-package consumers (`server/services.BacklogService`, `session.ReviewGateRunner`), which is the actual Go-idiomatic reason to define an interface rather than expose a concrete type — not "future swappability," but "the consuming packages shouldn't both import a private constructor of a type from a fourth location," and (2) Story 1.5.1d explicitly plans test-double substitution at ~20 test call sites (`session/review_gate_test.go`, `session/review_gate_integration_test.go`), meaning it *will* have fakes, unlike `WorkflowEngine`. Verdict: **defensible, not a violation**, but only because of the two-consumer + test-double facts — the plan should say so explicitly rather than leaning on the (incorrect) `WorkflowEngine` precedent (see Blocker above), because if either of those two facts changes (e.g., `ReviewGateRunner`'s dependency is dropped in a later refactor, leaving only `BacklogService`), the interface should be collapsed back to a concrete type at that point.
- [ ] **Lens 1.1 / `CachingPipelineEngine` — four content-generation responsibilities behind one type** — `CachingPipelineEngine` combines: (a) cache-hit/miss resolution logic, (b) fail-closed fallback + Warn logging, (c) template rendering (`renderTemplate`), and (d) four largely-independent content-generation methods (`SlashCommandSet`, `TriagePromptFor`, `ReviewPromptFor`, `InitialPromptFor`) each delegating to a different default-path free function. This is borderline but net acceptable: (a)+(b)+(c) are genuinely one cohesive "resolve-a-mode-and-render-it" responsibility shared identically across all 4 methods (same cache, same fallback pattern, same renderer) — splitting them apart would mean duplicating the cache-lookup + Warn-fallback boilerplate 4 times, which is worse. The 4 content methods are more debatable — they don't share business logic with each other, only the resolution *mechanism*. This is consistent with `DefaultWorkflowEngine`'s existing shape (3 methods on one type, sharing one backing map) so it's locally idiomatic, but it does mean `CachingPipelineEngine` will keep growing every time a new "which content varies by mode" call site is discovered (this already happened once — `InitialPromptFor` was added mid-planning specifically to avoid the seam being cosmetic for autonomous mode, per the Pattern Decisions table). **Recommendation**: not a blocking issue for Phase 1, but if a 5th or 6th mode-varying call site is discovered later (a real risk flagged in the plan's own Rabbit Holes section re: `autonomous_driver.go`), reconsider extracting the shared resolve+fallback+render mechanism into a small unexported helper (e.g. `resolve[T any](item, cache, renderFn) (T, bool)`) that each of the 4 public methods calls, rather than letting `CachingPipelineEngine` keep accreting near-duplicate method bodies. Track this as a trigger condition, not an immediate refactor. (Note: the plan now has a 5th method, `ContentHashFor`, added to close Blocker 1 — this makes the "growing every time a new call site is discovered" observation more concrete, not less; still not blocking.)
- [ ] **Lens 1.4 / Testability of `atomic.Pointer[map[string]resolvedPipelineMode]`** — Task 1.3.2c's stated race test only asserts "no torn/partial read" under concurrent `Get`+`Invalidate`, which `atomic.Pointer` trivially guarantees by construction (an atomic load of a pointer either gets the whole old map or the whole new map — there's no way to write a test that would fail this if the code is correct, making the acceptance criterion close to untestable-as-stated / tautological). The design's actual hard-to-test failure mode is different and unaddressed: a caller that does `snapshot := cache.Get(slug)` and then, across an `await`/goroutine-yield/long-running LLM call, uses fields off that snapshot — is it guaranteed the snapshot is self-consistent even after 3 subsequent `Invalidate` calls happen concurrently? Yes, by copy-on-write construction (the caller holds its own `resolvedPipelineMode` value, not a pointer into the live map) — but the plan doesn't call this out explicitly as the actual invariant being protected, and the "torn read" framing in Story 1.3.2's acceptance criteria undersells what's really being guaranteed (immutable point-in-time snapshots surviving concurrent invalidation across long-lived callers, e.g. an in-flight LLM call reading `resolvedPipelineMode` fields hundreds of ms after `Get` returned). **Recommendation**: rewrite Task 1.3.2c's test to explicitly assert this scenario — hold a `Get()` result across a simulated `Invalidate()`, then assert the held value's fields are unchanged — rather than the weaker "no `-race` failure" framing, which mostly just verifies `atomic.Pointer` itself works (a stdlib guarantee, not something this design needs to prove). (Note: Task 1.3.2c's current text now includes this exact scenario — "hold a `Get()` result across a simulated concurrent `Invalidate()` call and assert the held value's fields are unchanged afterward" — so this recommendation also appears to have been picked up by the fix pass, though it was not one of the 3 items this round was asked to spot-check; worth confirming in a future pass.)
- [ ] **Lens 2.7 / Parse-at-boundary — validation timing gap between Phase 1 and Phase 2** — Phase 1 (Epic 1.4) wires the `optional string pipeline_mode` field through Create/Update RPC handlers with **presence gating only** (correctly closes the clobbering bug), but **no format/slug validation** — `ValidatePipelineModeContent` doesn't ship until Epic 2.3 (Phase 2, several epics later). Between Phase 1 landing and Phase 2 landing, `BacklogItemData.PipelineMode` is writable via `UpdateBacklogItem` with an arbitrary string (any slug, valid or not) — but per Story 1.7.3, at the end of Phase 1 there's no UI/CRUD surface to create a matching `PipelineMode` row yet, so every non-empty value written during this window is guaranteed to be an unresolved slug, hitting the Warn-fallback path on every read. This is low-risk in practice (single-operator tool, and the fail-closed path handles it correctly) but is worth stating explicitly as an accepted, temporary gap rather than leaving it implicit. (Note: this round's spot-check confirmed Story 2.3.1's *eventual* validation, once it ships in Phase 2, is now concretely specified — see Spot-Checked Concerns above. The underlying Phase-1-to-Phase-2 timing gap itself is unchanged and still worth an explicit callout, though the plan's Unresolved Questions section now does explicitly flag this window as "real but unreachable until Phase 2" — plan.md:91.)
- [ ] **Lens 3.10 / API contract stability — `PipelineModeRepository` returning `*ent.PipelineMode` directly** — the plan explicitly chooses to leak the ent-generated type through the repository interface (Pattern Decisions table, "no current consumer needs decoupling from ent... adding a parallel DTO here would be a forwarding-only wrapper"). This mirrors `WorkflowRepository`'s existing convention, so it's locally consistent, but it does mean every consumer of `PipelineModeRepository` (currently: `CachingPipelineEngine`, and the 5 new RPC handlers in Epic 2.2) is coupled to ent's generated struct shape — a future ent regeneration that renames/retypes a field (e.g. switching a `string` to a custom `field.Enum`-backed type) becomes a breaking change across both the caching engine and every RPC handler simultaneously, with no interface boundary absorbing it. Acceptable given the existing codebase convention, but flagging because this compounds — every new ent-backed repository in this style makes a future "decouple domain from ent" refactor larger. Not a blocker; just don't extend this convention indefinitely without revisiting it.
