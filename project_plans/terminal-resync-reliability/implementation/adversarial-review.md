## Concerns

- [ ] **Exec-gate capacity change ships with no load-characterization task, contradicting `requirements.md`'s own Feasibility Risk.** `requirements.md` states raising exec-gate capacity "need[s] their own before/after load characterization, not just a config bump." Epic 4.2 has no benchmark task analogous to Epic 5.1's Task 5.1.1.2 (compression CPU benchmark); `ResyncFastLaneSlots`' default of 4 is admitted as "a placeholder pending real burst-size telemetry" (Unresolved Question #2) with no task scheduled to produce that telemetry before an operator could flip the flag on. — *Recommendation: add a benchmark/load-test task to Epic 4.2 mirroring Epic 5.1's, gating any default-on recommendation.*

- [ ] **The fast lane's own acquire timeout (5s, inherited from `execGateAcquireTimeout`, `session/tmux/exec_gate.go:70`) is longer than the client's stall watchdog (4s, `RESYNC_STALL_TIMEOUT_MS`, `useVisibilityResync.ts:6`).** Under genuine fast-lane saturation — the scenario Epic 4.2 exists to survive — the server could still be waiting up to 5s for a slot when the client's watchdog already fired at 4s and forced a disconnect/reconnect, meaning the capacity fix can still lose the exact race it's built to win. — *Recommendation: either size the resync fast lane's own gate timeout below 4s, or note explicitly why this ordering is acceptable (e.g., because it's expected to be rare given visibility-scoping/staggering already landed first per the rollout order).*

- [ ] **Interface growth tax is broader than the 8 tasks in Epic 4.2 suggest.** `CapturePaneContentPriority`/`RefreshClientPriority` land on both `ProcessManager` and `panePTY`, interfaces referenced across at least 15 files (`session/native_process_manager.go`, `session/tmux_backend.go`, `session/tmux_process_manager.go`, and several `_test.go` files with their own doubles, per a repo-wide grep). Only `NativeProcessManager` was checked in this review (see Blocker above) — the plan doesn't enumerate whether any test doubles/mocks implementing these interfaces also need the two new methods to keep compiling.

- [ ] **Stagger coordinator (Epic 6.1) has no unmount-cleanup task.** `SessionDetailView.tsx`'s new stagger queue holds `setTimeout`-delayed callbacks referencing terminal instances; no task addresses clearing pending timers when the component (or an individual terminal instance) unmounts mid-queue (e.g., user navigates away with resyncs still staggered). Left as-is, this is a plausible stale-closure/leaked-timer bug the client test (Task 6.1.1.4) as scoped wouldn't catch since it only tests the burst/preemption behavior, not unmount.

- [ ] **Two Observability Requirements bullets are under-covered relative to what's needed to validate their Success Metrics.** (a) Req #3 asks for exec-gate wait time/**queue depth on the `"default"` key** "to characterize contention before and after the capacity fix" — Task 7.1.1.2 only instruments the *new* resync fast lane's own `AcquireResyncExecSlot`, not the pre-existing default gate, so there's no "before" baseline to compare against. (b) Req #5 asks for request-count/byte-count metrics once batching/compression ships, to "demonstrate the round-trip/wire-size reduction claimed in Success Metrics" — no task in Phase 5 or 7 adds this; Task 5.1.1.2 benchmarks CPU only, not wire size. Success Metric #4 (measurable wire-traffic reduction) currently has no instrumentation that would prove it was achieved.

- [ ] **Batching's partial-failure semantics are unspecified.** Task 5.2.1.2 unpacks a `BatchedCurrentPaneRequest` into N calls to the shared helper but doesn't say what happens when one of N fails independently (e.g. a session torn down mid-batch) — does the batch response include a per-item error, or does the whole batch fail? Lower urgency since Epic 5.2 is explicitly go/no-go-gated and may never ship, but should be specified before that decision is made.

## Minors

- Epic 8.3 (banner `role="status"`/`aria-label` accessibility fix) is not requested anywhere in `requirements.md` and is explicitly self-labeled a "drive-by." Small and low-risk, but it is scope beyond what was asked, and its AC mapping ("AC1 GWT, incidental") stretches AC1's definition (visibility-scoped resync) to justify unrelated accessibility work.
- Task 4.1.1.2's proposed log line includes an "elapsed-time-saved estimate" — prefer logging the actually-measured skip duration over a guessed/constant estimate, for a metric that's supposed to validate a real speedup.
- No task addresses cleanup of orphaned `resync_id` refs on WebSocket disconnect/reconnect mid-resync; likely inert (overwritten by the next request) but not explicitly reasoned about.

## Re-review Notes (this pass): Resolution Status of the 7 Original Blockers

1. **Compression scope drift — RESOLVED.** The Creative Pass table and Step 3 Pattern Selection now choose Option B/envelope-scoped `CompressedFlag` (plan.md lines 17, 77); Epic 5.1/Task 5.1.1.1 gzip-compresses and sets `CompressedFlag` only on `CurrentPaneRequest`/`TerminalOutput` payloads above a threshold, leaving `wsUpgrader`/`EnableCompression` untouched (plan.md line 62). 2. **`stale_dimensions` flag mismatch — RESOLVED.** Task 3.1.1.4 (plan.md) now states explicitly: "Set `stale_dimensions` **unconditionally** — it is inert metadata with no consumer until Epic 4.1's skip-logic reads it, so it must NOT be gated behind `terminal:resync-correlation-id`." 3. **Missing `resync_id` threading into `notifyResyncOutputReceived` — RESOLVED.** Task 3.1.1.5 now explicitly changes `useTerminalStream.ts`'s `onOutput` type from `(output: string) => void` to `(output: string, resyncId?: string) => void` and its call site to `onOutput(text, msg.data.value.resyncId)`, and changes `TerminalOutput.tsx`'s `handleOutput` to accept and forward `resyncId` to `notifyResyncOutputReceivedRef.current(resyncId)`.
