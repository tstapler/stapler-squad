# Architecture Review: terminal-resync-reliability
**Date**: 2026-08-13
**Verdict**: CONCERNS

## Blockers

_(re-checked after repair pass — all 3 previously-identified blockers resolved)_

- [x] **Epic 4.2 / Task 4.2.1.4 (`ProcessManager` interface widening)** — RESOLVED. The plan now explicitly scopes `CapturePaneContentPriority()`/`RefreshClientPriority()` to the `TmuxManager` interface only (Task 4.2.1.4: "add ... to the **`TmuxManager`** interface — **not** `ProcessManager`"), reached from `Instance` via the `i.processManager.(*TmuxBackend)` type-assertion idiom (Task 4.2.1.5), with `ProcessManager` itself called out as "**Left unmodified in this project**" in the Domain Glossary (plan.md:41) and Step 3 Pattern Selection (plan.md:73). Verified against real source: `session/process_manager.go`'s `ProcessManager` interface contains no priority methods and is untouched by this plan's approach; `session/tmux_backend.go:21`'s `(b *TmuxBackend) TmuxManager() TmuxManager` already exists as the exported accessor the plan's type-assertion idiom calls into. Compile-sanity re-check: `session/tmux_backend_test.go:22`'s `mockTmuxManager` embeds `TmuxManager` (not a hand-implemented direct satisfier), so widening `TmuxManager` requires no changes there; `session/session_driver_test.go:28`'s `stuckDialogProcessManager` hand-implements `ProcessManager` directly, but since `ProcessManager` is not widened by this plan, it is moot and needs no changes either. Both test files require no edits under the plan's revised approach.

- [x] **Epic 4.1 / Task 4.1.1.1 (stale-dimension skip leaves the actual resize untouched)** — RESOLVED. Task 4.1.1.1's text and Story 4.1.1's GWT now explicitly cover the `ResizePTY` call itself, not just the verify dance: "add an early-skip branch wrapping the **entire** dimension-check-through-verify block (`:1971-2025` — this includes the `ResizePTY` call at `:1989`, not only the SIGWINCH loop at `:1993-2011`) ... falling straight through to the existing `CapturePaneContent()` call at `:2028` with no resize attempted." Story 4.1.1's prose adds an explicit rationale: "This is deliberate, not just a speed optimization: `stale_dimensions=true` means the client's own `target_cols`/`target_rows` may themselves be stale ... so resizing the server-side pane to match them would apply a dimension the client itself doesn't trust." The AC3 GWT was also rewritten to assert `ResizePTY()` is called 0 times (not just `RefreshTmuxClient()`), and Task 4.1.1.3 adds a corresponding test assertion. Verified against real source: `server/services/connectrpc_websocket.go` lines 1971-2025 form exactly one `if currentPaneReq.TargetCols != nil ... { ... }` block (opening at line 1973, dimension check at 1978-1984, `target.ResizePTY(targetCols, targetRows)` at line 1989, the 3x-`RefreshTmuxClient()`+sleep loop at 1993-2011, final sleep + verify at 2011-2022), immediately followed by the unconditional `content, captureErr := target.CapturePaneContent()` at line 2028 — confirming the plan's described skip point and fallback-to-current-dimensions behavior are accurate to the real code. This matches remediation option (a) from the original blocker.

- [x] **Epic 5.1 / ADR-004 (transport-level compression exceeds requirements.md's Out-of-Scope boundary)** — RESOLVED. Epic 5.1's Story 5.1.1 and the Step 0.5 Creative Pass table now select the envelope-scoped `CompressedFlag` approach ("Chosen: **B**"), explicitly rejecting whole-connection `permessage-deflate` for exceeding the Out-of-Scope boundary. `ADR-004-transport-level-compression.md` has Status "Accepted (revised)" with an "Original Decision (superseded)" section documenting the reversal and why, and a "Decision (revised)" section describing the envelope-`CompressedFlag`+gzip approach scoped to `CurrentPaneRequest`-triggered `TerminalOutput` payloads above a size threshold. Task 5.1.1.0 is an explicit prerequisite task fixing the client's hard-throw bug in `parseResponseBody` (`websocket-transport.ts:173-178`) before any server-side `CompressedFlag` use, per the ADR's Consequences section ("Requires a client-side fix (Task 5.1.1.0) ... before any server-side `CompressedFlag` use is safe"). The Domain Glossary's `CompressedFlag`/`EndStreamFlag` and `wsUpgrader` rows both cross-reference this decision and note `wsUpgrader` is "**Left unmodified in this project**." `server/protocol/envelope.go:19`'s `CompressedFlag` bit and `server/middleware/gzip.go`'s pooled-gzip-writer pattern (cited as the precedent for Task 5.1.1.1's implementation) both exist as described.

## Concerns

_(carried forward unchanged from the prior review — out of scope for this pass)_

- [ ] **Epic 6.1 / Task 6.1.1.1 (stagger coordinator co-located in an already-1606-line file)** — `SessionDetailView.tsx` is 1606 lines before this project touches it. The plan explicitly rejects a new file for the stagger queue "per Interface Pollution checklist #4 — a forwarding wrapper here would add no behavior," but a custom hook with real jitter/priority-queue logic (which is what Task 6.1.1.1-6.1.1.3 actually describe) is not a forwarding-only wrapper — checklist item #4 is about wrappers with *no added behavior*, which doesn't apply here. **Recommendation**: extract the stagger queue into its own hook/module (e.g. `web-app/src/components/sessions/useResyncStaggerQueue.ts`), consumed by `SessionDetailView.tsx` at its 4 `isVisible` wiring sites. This keeps the same testability and avoids-global-state properties the plan wanted (Task 6.1.1.4's test can target the hook directly, in isolation, without mounting the surrounding 1606-line component) while not growing an already-oversized file further.

- [ ] **Epic 3.2/4.1/4.2 shared helper accreting positional bools** — `handleCurrentPaneRequest` (Task 3.2.1.2) starts with a `skipStaleDimensionSlowPath bool` parameter (Phase 4.1), then Phase 4.2's Task 4.2.1.7 implies a second bool controlling whether to call the `...Priority()` exec-gate variants, and Phase 7's Task 7.1.1.3 adds a correlation-mismatch-logging branch to the same helper. Three feature flags' worth of same-typed `bool` parameters accreting onto one function signature across three epics is exactly the smell `.claude/rules/primitive-obsession-checklist.md` calls out, just arriving incrementally instead of all at once.
  **Recommendation**: introduce a small options struct now (e.g. `type resyncHandlerOptions struct { SkipStaleDimensionSlowPath, UseFastLaneExecGate bool }`) as part of Task 3.2.1.2, so later epics add a field instead of another positional bool.

- [ ] **Epic 4.2.1.1 (`runGatedFastLane[T any]` duplicates `runGated[T any]`)** — `runGated[T any]` (`session/tmux/exec_gate.go:77-86`) already exists: acquire-with-timeout, run `fn`, deferred release. Task 4.2.1.1's `runGatedFastLane[T any]` is described as "mirroring `AcquireExecSlot`/`runGated`... using `gateDir(serverSocket + "#resync")`" — i.e., the same timeout/defer/release scaffolding, differing only in which `Acquire*ExecSlot` function is called inside. This is copy-pasted generic-function duplication, the same class of issue `.claude/rules/interface-pollution-checklist.md` targets for interfaces, here showing up in a generic helper instead.
  **Recommendation**: factor out `runGatedWith[T any](ctx context.Context, acquire func(context.Context) (func(), error), fn func() (T, error)) (T, error)` holding the shared timeout/defer/release logic; make `runGated` and the new `runGatedFastLane` one-line wrappers passing `AcquireExecSlot`/`AcquireResyncExecSlot` respectively.

- [ ] **ADR-003 / Risk Control — combined exec-gate ceiling not addressed** — `exec_gate.go`'s own doc comment states the gate exists because "tmux's server is single-threaded... and gets measurably slower as concurrent load and client count rise," bounding total concurrent tmux subprocesses per socket at `defaultTmuxExecGateSlots` (8). ADR-003's fast lane adds a *separate* 4-slot pool "never subtracted from the default pool's 8" — meaning the combined worst-case concurrent-subprocess count against the *same single-threaded tmux server process* rises from 8 to 12 whenever both pools saturate simultaneously. `implementation/plan.md`'s Unresolved Question #2 only flags the fast lane's own default size (4) as a placeholder pending telemetry; it never addresses that the fast lane, by design, raises the combined ceiling rather than carving out a reserved share of the existing 8.
  **Recommendation**: either explicitly measure/bound the combined ceiling (e.g. cap `default + resync` at 8 total, trading some default-pool headroom for resync isolation, rather than strictly additive), or explicitly accept and document the raised ceiling as a deliberate trade-off alongside Unresolved Question #2 rather than leaving it unstated.

## Nitpicks

_(carried forward unchanged from the prior review — out of scope for this pass)_

- `resync_id` is a bare `string` in both `useTerminalFlowControl.ts`'s and `useVisibilityResync.ts`'s independently-evolving pending-resync refs (deliberately not unified, per Rabbit Holes). A lightweight branded type (`type ResyncId = string & { readonly __brand: unique symbol }`) would make it unambiguous at a glance which of the many string-typed refs/params in these two files (`sessionId`, `shellId`, `resync_id`) is which, at effectively zero cost given `crypto.randomUUID()` is the only producer.
- ADR-004 overrides `research/build-vs-buy.md` §1a's explicit "Recommended" verdict (wire up the existing envelope `CompressedFlag` + `klauspost/compress/gzip`) without a cross-reference explaining why. The override itself is defensible (the client's hard-throw bug wasn't known to Phase 2 research), but a future reader diffing `research/build-vs-buy.md` against `decisions/ADR-004-*.md` will see an apparent contradiction with no pointer between them.
