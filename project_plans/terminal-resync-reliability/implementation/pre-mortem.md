# Pre-Mortem: terminal-resync-reliability

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---|---|---|---|
| 1 | Epic 4.1's `stale_dimensions` skip conflates "resync was visibility-triggered" with "client dimensions are actually stale." Task 3.1.1.4 sets `stale_dimensions: true` *unconditionally* whenever `useVisibilityResync` triggers the resync — not based on any check that the reported dimensions are wrong. If a genuine resize happens while the tab is backgrounded (OS window resize while minimized, monitor/DPI change, browser zoom, container reflow from an unrelated UI change), the visibility-triggered resync on refocus still sets `stale_dimensions=true`, so Epic 4.1 skips `ResizePTY` entirely and captures at the pane's *old* server-side dimensions instead of the client's new (correct) target. The client renders that mismatched capture into an xterm.js buffer sized for the new dimensions — reintroducing the exact backgrounded-tab buffer-divergence/corruption bug the original feature (and this hardening project's own Constraints) exist to prevent. | User reports garbled/wrapped terminal text on a backgrounded terminal after it was resized-while-hidden then refocused, with `terminal:resync-skip-stale-dimension-slowpath` on; no distinguishing log line exists to tell "genuinely stale" apart from "visibility-triggered but dimensions were actually correct/changed." | Change the signal from "which trigger fired" to "did the dimensions actually change." Compare the client's `target_cols`/`target_rows` against the server's last-known pane dimensions server-side, or have the client compare its own current xterm dimensions against the dimensions it last successfully synced *before* backgrounding, and only set `stale_dimensions=true` when they plausibly diverge for a backgrounding-shaped reason (visibility-triggered AND dimensions unchanged since last successful sync) rather than for every visibility-triggered resync unconditionally. Add a regression test that resizes a backgrounded pane's dimensions server-side, then triggers a visibility-driven resync, and asserts the client ends up with correctly-fitted content (not corrupted) — Epic 4.1's existing Task 4.1.1.3 test only covers "dimensions unchanged," never "dimensions genuinely changed while backgrounded." | P1 |
| 2 | Epic 4.2's fast lane (`AcquireResyncExecSlot`, separate `"<socket>#resync"` gate, +4 slots) assumes the shared 8-slot gate on `serverSocket` exists purely for throughput/backpressure management, so adding an independent slot pool for the same socket is "safe" (never subtracted from the default pool). If the original gate instead exists (even partly) to serialize concurrent tmux CLI invocations against the *same tmux server process* for correctness — a real, documented tmux failure mode under concurrent access to one session — then the fast lane allows up to 8+4=12 simultaneous tmux subprocess calls against one socket, a concurrency level never validated as safe by the original gate's author, for gains that only benefit resync latency while raising correctness risk for *all* tmux traffic on that socket (regular pane capture, resize, refresh — not just resync). | Intermittent tmux-server-level errors/garbled pane content or "server exited unexpectedly"-style log lines correlating with `terminal:resync-exec-gate-fast-lane` being on, appearing on completely unrelated (non-resync) tmux operations sharing the socket — hard to attribute to this change without cross-referencing the flag state. | Before enabling the fast lane by default, confirm via git history/commit message or by asking why `defaultTmuxExecGateSlots` was originally set to 8 (throughput cap vs. correctness serialization) — this determines whether a second concurrent pool is safe at all, independent of the already-flagged missing load-benchmark task. If the reason can't be confirmed, treat the fast lane as adding to *total* concurrent access rather than assuming isolation, and load-test regular (non-resync) tmux operations for corruption/errors while the fast lane is saturated, not just resync latency. | P2 |
| 3 | The stagger coordinator (Epic 6.1) is scoped inside a single `SessionDetailView.tsx` instance — i.e., per *session*, staggering only the terminals mounted within that one session. But `requirements.md`'s own "Users / Consumers" section names the dominant usage pattern as "multiple concurrent Claude Code / Aider **sessions**" per user, each presumably its own mounted `SessionDetailView`. A single `document.visibilitychange`/focus event fires for the whole browser tab at once, so every mounted `SessionDetailView`'s independent stagger coordinator starts its own jittered 0–300ms window at essentially the same real-world instant — recreating the synchronized burst at the *session* level (N sessions × their own internally-staggered terminals, all starting together) instead of eliminating it. If multiple sessions share a tmux server socket, they also share the same 4-slot resync fast lane (Epic 4.2), so this cross-session synchronization can still saturate it just as effectively as the pre-fix single-session burst did. | The Success Metric (stall-watchdog fire rate near-zero) doesn't move for users with several concurrently open sessions in one browser tab/window, even though single-session-with-many-terminals test scenarios (the ones Epic 6.1's own tests exercise) show clean improvement — a gap invisible in per-session testing. | Add a resync-burst coordination layer above the per-session `SessionDetailView` scope — e.g. a module-level (or `AnalyticsContext`-sibling) coordinator shared across all mounted `SessionDetailView` instances in the page, so staggering happens across the *whole* set of terminals visible to the user, not just within one session. At minimum, add an explicit test with 2+ `SessionDetailView`s mounted simultaneously (mirroring real multi-session usage) asserting their combined resync fan-out is still staggered, not just each one's internal fan-out. | P2 |
| 4 | Epic 4.2's priority path is only reachable via `i.processManager.(*TmuxBackend)` (Task 4.2.1.5); any `Instance` whose `processManager` isn't concretely `*TmuxBackend` silently falls back to the plain non-priority `CapturePaneContent`/`RefreshClient` calls — a deliberate, correct fallback for genuinely non-tmux-backed instances, but there's no log/metric distinguishing "fell back because flag is off" from "fell back because the type assertion missed for a tmux-backed instance that should have gotten the fast lane." If any current or future wrapping/decoration of `TmuxBackend` (a test seam, a future feature, an unexpected construction path) breaks the assertion for a nontrivial fraction of real sessions, Epic 4.2's entire fix silently no-ops for those sessions with zero diagnostic trail — the Success Metric would simply fail to improve, and nothing in the Observability Plan explains why. | The exec-gate-wait-time metric (Observability Plan #3) shows the fast lane pool being used far less than expected relative to resync volume, or the stall-watchdog fire rate doesn't improve, with no log line anywhere identifying which resyncs took the non-priority path due to a failed type assertion vs. a deliberately-off flag. | Add a debug-level log/counter at the `i.processManager.(*TmuxBackend)` assertion's failure branch specifically when `terminal:resync-exec-gate-fast-lane` is *on* (i.e., "flag on, but this instance couldn't use the fast lane") — distinct from the flag-off no-op path — so a silent-fallback rate can be measured directly instead of inferred from an unmoved top-line metric. | P2 |
| 5 | Story 3.1.2's cross-hook stall-watchdog reconciliation resets a pending resync's stall watchdog whenever *any* outstanding `resync_id` (not necessarily its own) receives output, treating that as "proof the connection is alive." This correctly avoids false stalls when a sibling resync completes first, but it also means: if a specific resync's own server-side handling silently fails or hangs (an unhandled exception in the shared helper, a dropped response, a bug specific to that request) while an unrelated resync on the same connection succeeds normally, the failed resync's watchdog keeps getting reset by the unrelated traffic and never fires — the client waits indefinitely for a response that will never arrive, with no stall-watchdog protection and no banner, silently regressing to a milder version of the exact "ambient output masks real completion failure" heuristic bug this whole project sets out to fix (just narrowed from "any output" to "any known-outstanding resync's output" rather than eliminated). | A user occasionally reports a terminal that "just never catches up" after a resize/visibility event, with no console warning (no stall-watchdog fire, because it kept getting reset), no error, and no reconnect — indistinguishable from "still loading" until the user manually clicks Reconnect. | Add a per-resync_id maximum lifetime distinct from the shared reset mechanism — e.g. after `resetStallWatchdog()` resets a pending resync's timer because a *different* ID's output arrived, still track how long *that specific* `resync_id` has been outstanding, and independently escalate (retry or surface a banner) if it exceeds a hard ceiling (e.g. 2x the normal watchdog) even though the shared-liveness reset kept deferring the naive timer. Cover this with the test Task 3.1.2.3 already plans, but extend its assertion: after the non-matching ID resets the watchdog, if the still-pending ID's own response *never* arrives, some escalation eventually fires rather than waiting forever. | P2 |
