# Terminal QoS techniques: survey, codebase audit, candidate additions

Scope: the two problems in `../requirements.md` (touch-scroll feel; blank/stale redraw after soft-keyboard open) on Android Chrome over flaky links.
Labels: **VERIFIED** = source fetched this session (URL given) or code grepped in this repo. **INFERRED** = reasoning or background knowledge not checked against a primary source.

## 1. Survey of techniques

| # | Technique | What it is / problem solved | Evidence | Applicability | Cost |
|---|---|---|---|---|---|
| 1 | **Mosh SSP state sync** | Client and server each hold a screen *state*; server-to-client may skip intermediate frames and send the latest. Never fills network buffers, so Ctrl-C stays responsive. Datagrams carry increasing sequence numbers; server adopts the source IP of the newest authentic packet (roaming); heartbeat at least every 3 s. VERIFIED: [mosh.org](https://mosh.org/). Caveat (VERIFIED, same page): only the visible screen is synced, so scrollback is incomplete. | VERIFIED | **Med** as a *principle* (send latest screen, drop stale frames). **Low** as a protocol: we ride ConnectRPC/WebSocket over TCP and need real scrollback. | High to adopt wholesale; Low to borrow "latest wins" for redraw frames |
| 2 | **Mosh predictive local echo** | Client predicts that typed chars echo at the cursor; shown only after server confirmation or when RTT/glitch triggers fire; underlined on bad links; "epochs" make ESC/CR/up-down return to tentative mode. Median keystroke response 503 ms to under 5 ms on EV-DO; 70%+ of keystrokes displayed instantly ([USENIX ATC 2012 page](https://www.usenix.org/conference/atc12/technical-sessions/presentation/winstein), [mosh.org](https://mosh.org/)). Logic: [terminaloverlay.cc](https://raw.githubusercontent.com/mobile-shell/mosh/master/src/frontend/terminaloverlay.cc) (VERIFIED: modes never/always/adaptive/experimental, hysteresis on SRTT triggers, kill_epoch on wrong tentative prediction). Numeric thresholds live in `terminaloverlay.h`, not fetched. | VERIFIED | **Low** for this scope. Our users read output and steer an agent TUI (Claude Code) whose input box redraws asynchronously; prediction is brittle in TUIs and neither problem is about typing latency. Revisit as follow-up if RTT > ~150 ms typing complaints arise. | High (needs cell-level overlay + validation) |
| 3 | **Mosh frame-rate adaptation** | Server send interval tracks RTT (roughly half SRTT, clamped; I recall 20 ms min / 250 ms max, plus a short collection delay to batch). | INFERRED (not fetched; `transportsender.cc` URL 404ed) | **Med**: lets the server lower flush rate on slow links instead of fixed batching. | Med |
| 4 | **Eternal Terminal reconnect** | "Eternal TCP": each side counts bytes (sequence number) and keeps a BackedWriter ring of the last N bytes; on reconnect readers report their count and writers resend only the missing M bytes. Native terminal scrollback preserved because it is a byte pipe ([ET how it works](https://eternalterminal.dev/howitworks/)). | VERIFIED | **High** concept: offset-based resume avoids a full snapshot repaint after every flaky-link drop. We have `requestScrollback(fromSequence, limit)` already, but live stream carries no sequence for gap detection (see audit). | Med (server ring buffer per session + seq in envelope + client last-seq tracking) |
| 5 | **xterm.js write callback + HWM/LWM** | `term.write(chunk, cb)`; track pending bytes, pause above HIGH (guide example 100000) and resume below LOW (10000); keep HIGH <= 500K for keystroke responsiveness (test: `yes`, then Ctrl-C). Buffer capped at 50 MB, overflow discarded. Callback batching variant: attach a callback only every ~100000 bytes, pause above 5 pending callbacks, resume below 2. Over websockets, treat transport as infinite buffer and send custom ACKs; client ACK condition and server accounting must agree or the stream stalls. [Official guide](https://xtermjs.org/docs/guides/flowcontrol/) (XON/XOFF is not covered by that guide). | VERIFIED | **High**, already present client-side; gap is server enforcement (audit). | Low-Med |
| 6 | **VS Code terminal flow control / ack batching** | Pty paused when unacknowledged chars exceed a high watermark (100,000 chars per [vscode#338156](https://github.com/microsoft/vscode/issues/338156)); renderer acks processed chars; also a 5 ms `TerminalDataBufferer` batching delay that adds up to 5 ms to every echo; issue proposes leading-edge flush. The "ack every 5000 chars" constant is from memory, not verified. | VERIFIED (watermark, 5 ms batcher); INFERRED (5000-char ack) | **Med**: leading-edge flush is a cheap input-echo latency win; ack scheme equals #5. | Low |
| 7 | **ttyd / wetty / GoTTY backpressure** | Not independently fetched. Related verified recipe: a reference xterm.js scroll fix ([github/copilot-cli#1805](https://github.com/github/copilot-cli/issues/1805)) uses 128 KB/16 KB watermarks with JSON `{type:'pause'}`/`resume` over the WebSocket; server skips `ws.send` while paused. | VERIFIED for the recipe; INFERRED that ttyd/wetty/GoTTY do likewise | same as #5 | Low |
| 8 | **tmux control mode flow control** | `refresh-client -f pause-after=<secs>`: when a pane's output lags beyond the threshold tmux sends `%pause %<id>` and stops; output uses `%extended-output %<id> <lag-ms> : data` (lag visible). Client resyncs (e.g. `capture-pane`) then `refresh-client -A '%<id>:continue'` and gets `%continue`. `-A '%id:pause'` pauses manually; `-A '%id:off'` lets tmux stop reading a pane. `-f no-output` suppresses `%output`. [tmux wiki](https://github.com/tmux/tmux/wiki/Control-Mode) | VERIFIED | **High** for a *server-to-tmux* backstop: a stalled mobile client otherwise makes our server buffer unboundedly or drop the subscriber. Pairs naturally with snapshot-on-resume. | Med (parser for new notifications; version gating) |
| 9 | **Output coalescing / render-frame throttling** | Coalesce many small chunks into one `term.write` per `requestAnimationFrame`; honor DEC mode 2026 synchronized output so TUI frames render atomically; cap full-screen redraws (~30 fps). Recipe with 80/120 ms wheel throttling and RAF write batching: [copilot-cli#1805](https://github.com/github/copilot-cli/issues/1805). | VERIFIED | **High** for redraw-after-keyboard (fewer intermediate frames) and scroll jank. Partly present (see audit). | Low |
| 10 | **Scrollback replay / snapshot-on-reconnect** | On (re)connect send a full-screen snapshot (clear+home prefix) then stream; optionally history in batches. tmux's own doc says the client must `capture-pane` after a pause (#8). | VERIFIED (tmux) | **High**, present; gap is cost (full repaint every drop) and correctness windows (snapshot vs live race). | n/a |
| 11 | **Reconnect/resume with sequence numbers** | See #4. Also exponential backoff, fast connect timeout, reconnect on `online`/`visibilitychange`. | VERIFIED (#4) | **High** concept; backoff/visibility part already present. | Med |
| 12 | **Input prioritization & keystroke latency budgets** | Keep input path out of the output queue; chunk large pastes; bound HIGH watermark so Ctrl-C works under flood (xterm guide's `yes` test); avoid batching delays on echo (#6). | VERIFIED (guide, vscode#338156) | **Med**: input already chunked (512 B / 10 ms). Scroll-to-TUI will inject wheel/PgUp sequences, so they must not be queued behind chunked paste. | Low |
| 13 | **Latency measurement / RTT indicator** | Ping/pong or timestamped acks to show RTT and to drive adaptive behavior (#3, #2). Mosh heartbeats are the model (VERIFIED, mosh.org). | VERIFIED (model) | **Med**: no RTT signal exists client-side (audit); needed before any adaptive tuning and useful for diagnosing the intermittent redraw bug. | Low-Med |
| 14 | **permessage-deflate / app-level compression** | WebSocket per-message deflate (RFC 7692) or app-level gzip over a size threshold. Terminal text compresses very well; helps on slow links, costs CPU on phone/server. | INFERRED (RFC not fetched) | **Low-Med**: app-level gzip envelope compression already exists server-side (audit). Verify client actually decompresses and threshold is sane; do not add permessage-deflate on top. | Low |
| 15 | **Background-tab / visibility throttling** | Hidden tabs: timers once per second (after 5 min and other conditions, once per minute); `requestAnimationFrame` does not run while hidden, so RAF-batched writers stall and queue ([Chrome timer throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)). Pattern: on `visibilitychange` to visible, drop queued stale output and resync from a snapshot instead of replaying a backlog. | VERIFIED | **High** and the same trigger class as our keyboard problem (visibility/viewport transitions). Exists as `useVisibilityResync`. | Low (tune) |
| 16 | **Mobile: soft-keyboard resize** | Since Chrome 108 on Android, the keyboard resizes only the *visual* viewport, so `window.resize` may not fire; listen to `visualViewport` resize; `interactive-widget=resizes-content` restores old behavior. A WebGL/canvas sized to `visualViewport.height` but positioned at layout 0 can leave uncovered area when `visualViewport.offsetTop` is nonzero ([Chrome blog](https://developer.chrome.com/blog/viewport-resize-behavior), search summary). | VERIFIED (Chrome blog via search summary; not fetched in full) | **High**: direct candidate root cause for problem 2. | Low |
| 17 | **Mobile: WebGL vs canvas vs DOM, IME, battery** | xterm.js: DOM default, WebGL addon fastest with texture atlas, Canvas addon CPU fallback; basic touch support, IME via textarea + composition view ([DeepWiki xterm.js overview](https://deepwiki.com/xtermjs/xterm.js/1-overview), search summary). No source found on mobile battery numbers. | VERIFIED (qualitative); battery = **UNVERIFIED** | **Med**: WebGL context loss / zero-size canvas during viewport transition is a stated candidate in requirements; existing code already has a webgl-to-canvas fallback latch. | Low-Med |
| 18 | **Perceived latency: optimistic scroll, momentum** | Scroll locally and immediately (1:1 with finger), decide on release; momentum is client-only inertia with line-quantized output; for alt-screen/mouse-tracking TUIs emit wheel/PgUp sequences at a rate-limited cadence (reference throttles wheel to ~8/s, caps delta; [copilot-cli#1805](https://github.com/github/copilot-cli/issues/1805)). Throttling that hard conflicts with 1:1 touch feel, so cap per-frame, not per-120 ms. | VERIFIED (recipe) / INFERRED (adaptation) | **High**, it is the project's core ask. | Med |

## 2. Codebase audit (what already exists)

All VERIFIED by grep/read in this worktree unless marked.

- **Client watermark flow control exists**: `web-app/src/lib/terminal/TerminalStreamManager.ts:31-32` `HIGH_WATERMARK=100000`, `LOW_WATERMARK=10000`; `CHUNK_SIZE=16384` (`:33`); `pendingWrites` and write-callback decrement (`:399-415`, `:460-501`). Sends `FlowControl{paused, watermark}` through `sendFlowControl` (`useTerminalFlowControl.ts:442`).
- **Redraw throttler**: `TerminalStreamManager.ts` `RedrawThrottler` coalesces full-screen redraws to max 30 fps, keyed on `ANSI_SNAPSHOT_PREFIX = "\x1b[!p\x1b[2J\x1b[H"` (`:~37-84`).
- **Server ignores client FlowControl on the main WebSocket path (GAP, VERIFIED by grep; relevance INFERRED)**: `FlowControl` is handled only in `server/services/session_service.go:4503-4515` (legacy PTY-reading path: "PTY reading PAUSED/RESUMED"). `server/services/connectrpc_websocket.go` has no reference to `FlowControl`/`Paused` (its dispatchers at `:2334-2343` and `:3075-3090` handle Input, Resize, ScrollbackRequest, CurrentPaneRequest only). So for control-mode-streamed sessions the client's pause signal appears to be a no-op and a slow phone is protected only by the slow-subscriber grace (below). I did not trace which path a given session uses at runtime; confirm before relying on this.
- **Server-side batching**: control-mode updates are drained into `streamhub` with `OnRawOutput` + `TryFlush`, coalescing already-available frames (`connectrpc_websocket.go:522-545`); `coalesceBufPool` (`:53-57`); resize coalescer (`:1295-1410`).
- **Slow-subscriber handling**: `session/tmux/control_mode.go:59-68` closes a subscriber only after a 250 ms grace when its 100-slot channel stays full. Closing = disconnect, i.e. a drop-and-reconnect, not pause-and-resume.
- **tmux flow control not used**: no hits for `pause-after`, `%pause`, `%extended-output` in `session/` or `server/` (grep returned nothing).
- **Snapshots**: `snapshotCache` with dirty tracking and TTL-less refresh (`connectrpc_websocket.go:318, 652-704`); initial snapshot with `ansiSnapshotPrefix` and cursor sync (`:137-210`, `:1098-1138`); authoritative post-resize snapshot after quiescence (`:1263-1417`); initial scrollback batch (`:1146`).
- **Compression**: `server/protocol/compression.go` `CompressEnvelopeIfLarge(payload, threshold)` gzip via klauspost with pooled writers. No permessage-deflate (grep). Client-side decompression and threshold not checked; UNVERIFIED.
- **Reconnect**: `useTerminalStream.ts` has `BackoffState`, fast connect timeout, reconnect on `visibilitychange`/`online` (`:689-715`), manual reconnect after hard failure (`:717`), but all of it behind `NEXT_PUBLIC_RECONNECT_V2 === "true"` (`:211, :332, :553, :691`). Whether the flag is on in the deployed build was not checked.
- **Resync after visibility/resize**: `useTerminalFlowControl.ts` `requestFullResync` (2 s throttle `:165`), correlation-ID flag `terminal:resync-correlation-id` (`:15`), shared outstanding-ID map with `useVisibilityResync.ts`; resize throttle 200 ms with escalating bounce hold 3 s to 15 s (`:321-395`). A 3 s to 15 s hold on a bouncing viewport is a plausible contributor to "stays black after keyboard" (INFERRED; connects to requirements' open question).
- **Input**: paste chunked 512 B every 10 ms (`useTerminalFlowControl.ts:234-286`); `requestScrollback(fromSequence, limit)` exists (`:420`) so a sequence concept exists for history, but the live `TerminalOutput` stream carries no per-message sequence for gap detection (no `lastSeq`/`sequence` hits in `useTerminalStream.ts`).
- **Rendering**: `XtermTerminal.tsx` uses WebGL addon with a one-directional fallback latch to `CanvasAddon` (`:19, :228, :470-478`).
- **Absent**: RTT/latency measurement or indicator (no ping/rtt hits in `useTerminalStream.ts` or `connectrpc_websocket.go`); predictive local echo (no hits); DEC 2026 synchronized-output handling was not searched for and is UNVERIFIED.

### Gaps (summary)
1. Client pause is not honored on the control-mode WebSocket path (needs confirmation).
2. No tmux-level backpressure (`pause-after`); a stuck client means disconnect, then full snapshot.
3. Reconnect/visibility logic gated behind an env flag whose deployed value is unknown.
4. No sequence numbers on the live stream, so every reconnect repaints a full snapshot.
5. No RTT signal; no instrumentation for the intermittent blank-terminal event beyond logs.
6. Resize bounce-hold (3-15 s) can delay the post-keyboard refit/resync far beyond the one-frame success metric.
