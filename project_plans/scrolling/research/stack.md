## 2. Existing touch code (VERIFIED)
- `useTerminalGestures` is mounted at `XtermTerminal.tsx:262-266` with `onSendData` -> `onDataRef` (same path as keystrokes, so it can inject escape sequences).
- State machine IDLE/PENDING/SCROLLING/SELECTING/TAPPING. Listeners: `touchstart` on container (passive:false), `touchmove`/`touchend`/`touchcancel` on `document` (`useTerminalGestures.ts:~360-366`).
- Scroll start: PENDING -> SCROLLING after >15px vertical (`:~228`). Scroll step is rAF-throttled: `lines = Math.round(-moveDy / cachedCellH); terminal.scrollLines(lines)` (`:~239-246`). `lastY = clientY` is updated every frame *before* rounding, so any per-frame movement < half a cell is rounded to 0 and permanently discarded (slow drags lose distance; no remainder accumulation). Also the first 15px dead-zone is dropped. These are not direction-asymmetric by themselves.
- No momentum code exists. No call to `isMouseTracking`/`buffer.active.type` in the SCROLLING branch; scroll is always local `scrollLines`.
- Mouse-tracking check: `web-app/src/lib/terminal/mouseTracking.ts:3-8` reads `terminal.modes.mouseTrackingMode` (cast to any). Tap path already forwards clicks to the PTY using legacy **X10** encoding (`useTerminalGestures.ts:~300-313`: `\x1b[M` + chars), which cannot encode col/row >223 and is ignored by apps that enable only SGR (1006).
- CSS: container `touchAction: "none"` (`XtermTerminal.css.ts:60`) so the browser never claims the drag (no pull-to-refresh/overscroll on that element). `TerminalOutput.css.ts:466` and `XtermTerminal.css.ts:31,131` use `manipulation` for other elements; `:186,197,221` use `none` (scrollbar thumb/handles).
- A separate custom scrollbar thumb also calls `scrollLines` (`XtermTerminal.tsx:~903-957`), computed from `buffer.active.viewportY/length`.
- Toolbar PgUp/PgDn: `TerminalOutput.tsx:1984, 2018` send `\x1b[5~` / `\x1b[6~` via `sendKey` on `onPointerDown`. Modifier maps for them at `:15-42`.

## 3. xterm.js 6 APIs relevant to scroll forwarding (KNOWLEDGE, confirm against typings once `pnpm install` is done)
- `terminal.buffer.active.type`: `'normal' | 'alternate'`; `terminal.buffer.onBufferChange` event. In the alternate buffer scrollback length == rows, so `scrollLines` is a no-op: this is the likely reason a TUI "does not scroll down/up" locally. UNVERIFIED as the actual cause of the reported bug - needs a repro log of `buffer.active.type`, `baseY`, `mouseTrackingMode` during a drag.
- `terminal.modes` (IModes): `mouseTrackingMode: 'none'|'x10'|'vt200'|'drag'|'any'`, `applicationCursorKeysMode`, `bracketedPasteMode`, `sendFocusMode`, etc. The mouse *encoding* (SGR 1006 / UTF8 / default) is NOT exposed, only the tracking mode.
- Wheel handling is internal to xterm: with tracking on it converts wheel to mouse reports in whatever encoding the app requested; in alt screen without tracking it sends Up/Down arrow keys. It only reacts to `WheelEvent`s / `attachCustomWheelEventHandler`; touch drags never generate them, and synthesizing `new WheelEvent('wheel')` on `.xterm-screen` is a viable way to reuse xterm's own encoder (it knows the active encoding and handles `applicationCursorKeysMode`). `attachCustomWheelEventHandler(fn)` lets code veto xterm's default.
- Touch: xterm's own Viewport scroll-by-touch behavior in v6 (VS Code scrollable-element based) is UNVERIFIED; the repo comment at `XtermTerminal.tsx:~256-260` says double handlers caused double-scroll, so check that xterm's built-in touch handling is not competing (`.xterm-viewport` element, `touch-action`).
- `terminal.refresh(start,end)`, `terminal.clearTextureAtlas()` (WebGL/canvas atlas rebuild), `fitAddon.proposeDimensions()`, `terminal.onRender`, `terminal.onResize`, `terminal.scrollToBottom()` exist.

## 4. Forwarding choices (design input)
| Option | Encoding | Pros | Cons |
|---|---|---|---|
| Synthetic `WheelEvent` on xterm screen | xterm picks encoding | Correct for tracking, SGR/X10, alt-screen->arrows, applicationCursor; zero encoding code | Event must be trusted-ish; xterm may ignore `deltaMode`/needs cell-sized deltaY; verify it works in jsdom/test |
| Direct SGR wheel | `\x1b[<64;col;rowM` (up) / `\x1b[<65;col;rowM` (down); +4 shift, +8 meta, +16 ctrl | Explicit, testable via `onSendData` | Only valid if app enabled 1006; X10 fallback `\x1b[M` + chr(32+64)... (wheel btn 64/65 +32), cols capped at 223 |
| PgUp/PgDn `\x1b[5~`/`\x1b[6~` | n/a | Known to work with Claude Code today (user-confirmed in requirements) | Page-sized, not 1:1 with the finger; poor for momentum; in a shell it scrolls nothing/readline history |
| `scrollLines` | local | Right for normal buffer with scrollback | No effect in alt screen |
Decision rule candidate (structural, not threshold-based): `buffer.active.type==='alternate'` or `mouseTrackingMode!=='none'` -> forward; else local `scrollLines`. Open: whether Claude Code responds to wheel (mouse tracking) or only PgUp/PgDn - requires a live test (requirements Open Question 3).

## 5. Keyboard / viewport redraw path (VERIFIED code, KNOWLEDGE for browser behavior)
- `ViewportProvider.tsx:34-55`: listens to `visualViewport` `resize`+`scroll`, rAF-batches, writes `--keyboard-height` / `--viewport-height`, sets `isVirtualKeyboardOpen` when kb>100px.
- `TerminalOutput.tsx:1169-1185`: `visualViewport` `resize` -> if `isFittingRef` skip; else `setTimeout(fit, isMobile ? 400 : 300)`, flag cleared one rAF after fit. Issues visible in code: (a) trailing-edge only, fixed delay, not re-armed - resize events arriving during the 400ms are dropped by the `isFittingRef` guard, so a final viewport size after the animation may never be fitted (candidate for a stale size/blank terminal); (b) no `refresh()`/`clearTextureAtlas()` after `fit()`; (c) the `scroll` event is not subscribed here; (d) effect re-subscribes when `isMobile` changes.
- `TerminalOutput.tsx:111+` ResizeObserver tracks container size; `XtermTerminal.tsx:~1015-1137` has a ResizeObserver + dead-band/debounce and fit at `:1052`; there is a zero-size guard that skips `fit()` (`:~1234` comment in TerminalOutput) - a container transiently 0px high during keyboard transition would skip fit and then never retry if no later observer callback fires.
- Android Chrome (KNOWLEDGE): default behavior is `interactive-widget=resizes-visual` (Chrome 108+) - the keyboard shrinks the *visual* viewport only; layout viewport / `100dvh` / `window.innerHeight` do NOT change, and only `visualViewport.resize` fires (not `window.resize`, no ResizeObserver callback on layout-sized containers). So any layout that depends on ResizeObserver of a `100%` container won't see the keyboard unless CSS uses `--viewport-height` (which this app does). `interactive-widget=resizes-content` in the `<meta viewport>` makes the layout viewport shrink (ResizeObserver then fires, `dvh` updates). VERIFIED by grep: no `interactive-widget` anywhere in web-app/src, so the default applies.
- `navigator.virtualKeyboard` (Chrome 94+, Android): `overlaysContent = true` switches to manual handling; `geometrychange` event + CSS `env(keyboard-inset-height)`; gives a reliable "keyboard geometry settled" signal and is Chromium-only (no iOS). Candidate replacement for the 400ms timer; `visualViewport` resize events fire many times through the ~250ms animation, so "settled" must be detected by debounce (trailing) or rAF-stable-height checks, not a fixed delay on first event.
- WebGL on Android: context loss / transient 0-size canvas during resize can leave a blank canvas until the next render; mitigations: `terminal.refresh(0, rows-1)` after `fit()`, listen for `webglcontextlost` via addon's `onContextLoss` (WebglAddon exposes `onContextLoss`), `clearTextureAtlas()`. The repo's webgl->canvas fallback is mismatch-count-based (`XtermTerminal.tsx:526-534`), not context-loss-based - confirm whether `onContextLoss` is wired (grep found no hit in the sampled lines).
- Existing refresh calls are only on theme change (`XtermTerminal.tsx:1199, 1214`); none follows a viewport-driven `fit()`.

## 6. Suggested instrumentation before fixing the blank-terminal bug
