## Concerns

- [ ] **Success Metric #2 ("reduced steady-state call volume") is not actually delivered by anything this plan ships at merge time, and plan.md never says so explicitly.** Tracing every lever requirements.md names for this metric: (1) GraphQL batching is deferred entirely (ADR-001: "Call-count-per-tick is unchanged by this project — it was never the lever"); (2) conditional-requests-by-default infrastructure (Phase 2) is scoped, by the plan's own text, to *future* call sites only ("infrastructure, not a one-time migration of existing call sites"), so it does not reduce volume on any call site that exists today; (3) the fallback-ticker widening that Scope item 4 names as the actual volume-reduction mechanism of webhook invalidation is explicitly *not* shipped — Risk Control keeps it "at today's 60s for the initial ship regardless of webhook activity," and no task in Phase 5 (or anywhere else) ever changes the ticker interval (confirmed by grep — the only ticker-related text is about *not* changing it); (4) both flags default OFF, so even the GraphQL migration's cost/shape win doesn't take effect until Tyler manually flips it. Net effect: at merge time, steady-state call volume is expected to be **unchanged**, and any future reduction is entirely gated on manual flag flips and a follow-on ticker-widening change this plan doesn't contain. This is a defensible, honestly-reasoned deferral (ADR-001 and the Open Questions section lay out the reasoning), but it's scattered across three documents and plan.md itself never states it plainly — a reviewer reading only plan.md's "Cross-cutting acceptance" section would not learn that Success Metric #2 shows no movement until further, currently-unscoped work happens. **Recommendation**: add a short "Success Metrics Traceability" note to plan.md stating explicitly that Metric #2 is infrastructure-only at this plan's completion, and enumerate what follow-on actions (flag flips + a ticker-widening change) are required to actually move the number — so this is a stated deferral, not an implicit one.

- [ ] **`AdmitOrigin`'s behavior on a never-yet-published (zero-value) `RateLimiterSnapshot` is untested and its safety is asserted, not verified.** Task 3.1.1c returns a zero-value `RateLimiterSnapshot{}` (`Remaining: 0, Limit: 0`) when `Snapshot()` is called before any `Update()` has run (fresh process start, before the first native HTTP response). `AdmitOrigin`'s rejection condition (Story 3.2.1) is `Snapshot().Remaining < Snapshot().Limit * backgroundHeadroomPercent / 100`, which evaluates to `0 < 0` → `false` on a zero-value snapshot — background origins are *admitted*, not rejected, at cold start. This happens to be a benign outcome (fail-open when there's no data yet is arguably correct), but Story 3.2.3's claim that the cold-start risk is "closed by construction" only actually addresses a *different* scenario (`research/pitfalls.md` §3a's mid-session flag-flip-while-`IsLimited()`-is-true case, which the `IsLimited()`-precedes-`AdmitOrigin` ordering genuinely does close). No unit test in Story 3.1.1/3.2.1 exercises the literal zero-value-snapshot path, so the "closed by construction" claim overreaches for the specific fresh-process-start case. **Recommendation**: add an explicit test asserting `AdmitOrigin`'s behavior when `Snapshot()` has never been published, and narrow Story 3.2.3's claim to the mid-session-flip risk it actually closes.

- [ ] **No test exercises the compound Success-Metric-#1 claim end-to-end.** Requirements' Success Metric #1 is a two-origin interaction claim: a background-origin call causes exhaustion, and a subsequent interactive-origin call *still succeeds*. Every test in Phase 3 (Task 3.2.1b, 3.2.2's ACs, Task 3.3.1a) either exercises `AdmitOrigin` in isolation against a fabricated `Snapshot()` value, or exercises a single origin's path through `rateLimitTransport` at a time. None drives a real background-origin response through `RateLimiter.Update()` to a low-remaining state and then asserts a subsequent interactive-origin `ghHTTPClient.Do` call succeeds through the same shared `rateLimitTransport`/`AdmitOrigin` pipeline. This is exactly the "unit-level only" gap the review brief flagged. **Recommendation**: add one integration-style test in `github/http_client_test.go` that drives the full two-origin interaction through `rateLimitTransport.RoundTrip`, not just `AdmitOrigin` called directly.

- [ ] **ADR-002's fail-closed default has no enforcement beyond developer discipline and after-the-fact metrics.** The ADR itself acknowledges this ("a `go vet`-style static check... was considered but not built in this project") — so this isn't an undisclosed gap, but it is a real one worth surfacing: any *future* call site (or a helper nested several layers inside an already-tagged call chain that constructs a fresh, untagged `context.Background()`/`context.TODO()` instead of propagating the caller's `ctx`) silently gets background-tier treatment with no compile-time, lint-time, or test-time signal — only a post-hoc metrics anomaly (`origin="poller"` volume that should be interactive) might reveal it, and only if someone is looking. Given `norawghrequest` (Phase 2) sets a precedent in this exact project for catching a structurally similar class of "someone forgot the wrapper" bug via a custom linter, the asymmetry is notable: raw-HTTP-request omissions get a linter, origin-tagging omissions get only a metric. **Recommendation**: at minimum, note this explicitly as accepted residual risk in plan.md (not just the ADR), and consider whether a cheap version of the `norawghrequest` technique (flag a `context.Background()`/`context.TODO()` call inside `github/`, `session/`, or the poller/backlog-sync files as a smell) is proportionate — even as a follow-up, not blocking this plan.

- [ ] **The 2-3 PR parity-fixture matrix (Task 4.1.2a) under-covers `PRInfo`'s actual field-value space relative to the risk it's meant to guard against.** `DerivePRPriority` (`github/priority.go:21-60`, read directly) branches on at least: `State` ("merged"/"closed" vs. other), `IsDraft`, `ChangesRequestedCount > 0`, `CheckConclusion` ∈ {`"failure"`, `"action_required"`, `"success"`, `""`, `"pending"`}, `ApprovedCount > 0`, and `CheckStatus == "in_progress"` — at least 5 distinct `CheckConclusion`-relevant branches alone, plus GraphQL's `Mergeable` enum (`MERGEABLE`/`CONFLICTING`/`UNKNOWN`) and `ReviewDecision`'s 4 values. Task 4.1.2a's stated coverage — "draft/approved/CI-failing states" — plausibly hits `IsDraft=true`, one `CheckConclusion` failure value, and `ApprovedCount>0` with passing CI, but has no explicit fixture for `CheckConclusion="pending"`/`"neutral"`, `ChangesRequestedCount>0`, terminal `State` (`merged`/`closed`), or `Mergeable`'s `CONFLICTING`/`UNKNOWN` values — exactly the field-mapping risk `research/pitfalls.md` §3b calls out by name (a silently-wrong `CheckConclusion` casing "would silently misclassify PR priority... with no error surfaced anywhere"). **Recommendation**: expand Task 4.1.2a's fixture set (or supplement with synthetic/hand-constructed GraphQL response fixtures, not just live-recorded PRs, for states that are inconvenient to find live — e.g. `CONFLICTING`/`UNKNOWN` mergeable, `pending`/`neutral` check conclusions) so the parity test actually exercises every branch `DerivePRPriority` takes, not just 3 real PRs' worth of whatever state they happened to be in.

## Minors

- `backgroundHeadroomPercent` is a hardcoded Go constant, not a config value — the Constraints section requires the *on/off* admission-control behavior to be live-flippable (satisfied), but tuning the reserved-headroom percentage itself still requires a code change + redeploy if the chosen default proves miscalibrated in practice. Not a violation of the stated constraint, but worth a one-line note that "misbehaves" mitigation is binary (fully disable) rather than tunable.
- Task 4.1.1a (GraphQL schema introspection) has no stated contingency if the live schema differs materially from the assumed shape beyond "record findings as a comment" — low risk since Phase 4 ships flag-off, but the plan could say explicitly what triggers a re-scope (e.g., a union type requiring more than a straightforward inline fragment) rather than leaving it fully to implementer judgment.
- `research/architecture.md`'s own sketch code (§3) uses a default of `OriginInteractive` for the untagged-context case, which ADR-002 correctly overrides to `OriginPRStatusPoller` in the final decision — the research doc is superseded here and could confuse a future reader who opens architecture.md instead of ADR-002; consider a one-line "superseded, see ADR-002" pointer in architecture.md itself (not required, since the plan.md and ADR are internally consistent and are the documents of record).
