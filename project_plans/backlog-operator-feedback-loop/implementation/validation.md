# Validation Plan: backlog-operator-feedback-loop

**Date**: 2026-08-12

## Happy Path Scenario

Given a `ready`-status backlog item whose latest `TriageResult` contains a clarifying
question (`{text: "Should retries be per-workflow or global?", rationale: "question"}`) and
whose plan is `pending_review` (has `planArtifactsPath` set, `planApproved=false`,
`planRejectionReason=""`), when the operator opens the item detail view and, without leaving
it, (a) answers that specific question inline and submits — triggering a re-triage via the
existing `triggerTriage(id, feedback)` path — then (b) clicks "Request Changes" on the plan and
submits a non-empty reason, then (c) opens the Steer control on the item's linked work session
and sends a steering message, then the item detail view reflects all three operator actions in
place: the question shows "✓ Answered", the plan status card reads "Revisions requested" with
the reason visible and a "Regenerate Plan with This Feedback" button present, and a success
toast confirms the steering message was sent — all without the operator retyping context or
navigating to another view.

## Test Stack

- **Unit**: Go `testing` package (table-driven where applicable) for backend handlers/predicates; Jest for pure TypeScript functions (`composeQuestionAnswerFeedback`, `derivePlanReviewStatus`, `isSteerable`) and React Testing Library for component-level behavior (`TriageDiffSection`, `PlanVerdictBox`, `SessionsSection` in isolation with mocked props/callbacks).
- **Integration**: Go tests that exercise a real (or fake-backed) ent-storage / `Instance` layer through the actual ConnectRPC handler (`backlog_service_test.go`, `session_service_test.go` — these already spin up real storage per this repo's existing test harness, not mocks); React Testing Library tests that render `BacklogItemDetail` end-to-end with the real hook wiring (`useBacklogService`, `useSessionService`) and only mock the outermost RPC client, proving the UI reaches the correct RPC call rather than testing composer/predicate logic in isolation.
- **E2E / UX**: Playwright against a real running instance (per `tests/e2e/global-setup.ts`'s isolated per-run server), following `.claude/rules/e2e-test-conventions.md` — `@feature` header, no `waitForTimeout`, `data-testid`/ARIA locators only, new page helpers under `tests/e2e/pages/` if any of the three specs accumulate repeated navigation logic.

## Coverage Targets and How to Measure

| Stack | Coverage command | Target |
|---|---|---|
| Go | `go test ./... -coverprofile=coverage.out && go tool cover -func=coverage.out` | ≥80% line |
| TypeScript/Jest | `npx jest --coverage --coverageThreshold='{"global":{"lines":80}}'` | ≥80% line |

- All public service methods: happy path + error paths covered (`RejectPlan`, widened `UpdateSession` steer branch, `ApprovePlan`/`TriggerTriage` symmetry writes).
- All external integrations: unit mocked + at least one integration test (ent-backed `RejectPlan`/`ApprovePlan` round trip; `Instance.SendKeys` via a real/fake `Instance`).
- UX acceptance criteria: each criterion has a corresponding Playwright test or, for the touch-target/keyboard-nav additions, a documented manual-verification step if not automated in the initial pass.
