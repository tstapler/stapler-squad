# Pre-mortem: backlog-operator-feedback-loop
**Date**: 2026-08-12

Assumes the project has shipped and failed. These are failure modes distinct
from plan.md's own Risk Control table (approve/reject symmetry, empty-reason
validation, the two-tab race, the `changes_requested` naming collision, the
in-flight-triage error UX) and Unresolved Questions section — those are
already known and accepted/mitigated by the plan. The five below were not
found there.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The "✓ Answered" marker is pure ephemeral `useState` in `TriageDiffSection`, not persisted anywhere; a re-triage triggered by an answer can take up to 30 minutes (`triageCallBudget`), and any refresh/navigation during that window silently discards the marker while the still-current `TriageResult` iteration re-renders the same question as unanswered. | Operator refreshes the item page (or tabs away and back) between submitting an answer and the retriage completing; the question they just answered shows up unanswered again, they answer it a second time, and the second `triggerTriage` call is rejected by the `alreadyInFlight` guard with a confusing generic error for a click they believe was their first attempt. | Persist the answered marker (localStorage keyed by `item.id` + `triageResult.iteration` + question text/hash) so it survives a remount within the same iteration, or surface an explicit "re-triage in progress" banner derived from server-visible in-flight state rather than relying solely on component-local memory. Add a component test that unmounts/remounts `TriageDiffSection` mid-submission and asserts the marker (or an equivalent in-flight indicator) still reflects the true state. | P2 |
| 2 | Task 2.2.2c's Send button `disabled` condition (`steeringSessionId === s.sessionId \|\| !steerDraft.trim()`) never re-checks `isSteerable(s)`. `isSteerable` is only consulted when the Steer toggle is first rendered/clicked to open the composer — if the session ends while the composer is open, nothing disables Send. | Operator opens the inline steer composer on a live work session, the session finishes/exits while they're mid-typing, and clicking Send still fires `updateSession(...)` against the now-ended session — producing either a late, confusing `FailedPrecondition` toast for a session they've mentally moved past, or (if the stale `Instance` reference's `SendKeys` doesn't detect the dead process) a false "Steering message sent" success toast for a message nobody will ever read. | Add `!isSteerable(s)` (re-derived from the latest fetched `LinkedSession`, not the value closed over when the composer opened) to the Send button's `disabled` condition, and have `handleSteerSubmit` re-check session liveness immediately before calling `onSteerSession`. Add a test: open the composer, mutate the session to `endedAt` set, assert Send becomes disabled without requiring the composer to be closed/reopened. | P2 |
| 3 | §0's scope trim defers `GetPlanArtifactContent` — the item detail view still only shows `<code>{item.planArtifactsPath}</code>`, a raw path string, never the plan's actual content. Gap 3 ships a fully functional Approve/Request-Changes UI (status card, required-reason form, buttons) with nothing in the flow that depends on, or even hints at, whether the operator has actually read the plan. | An operator clicks Approve or fills out Request Changes within seconds of a plan finishing generation — clearly before there was time to open a terminal/editor at the shown path and read it — because the new UI *feels* like a structured review workflow even though nothing about how plan content reaches the operator changed from before this project. The feature satisfies AC3/4/5 literally while not solving the problem statement's actual goal (a human correcting the agent based on what the agent proposed). | At minimum, make the plan path a real "Open to review" affordance with an explicit prompt, and get an explicit product decision recorded (not silently implied by §0's YAGNI framing) that "structured review" and "content the operator has actually seen" are being intentionally decoupled for v1 — add this as an explicit line in Unresolved Questions rather than leaving it implied only by the scope-trim rationale in §0. | P1 |
| 4 | Task 3.2.1a hardcodes `plan_rejection_reason = 33` / `plan_rejected_at = 34` based on `main`'s field numbering "verified... at implementation-plan time" (2026-08-12), not at actual implementation time. This repo runs many concurrent SDD worktrees/agents against the same files. | A second, unrelated in-flight branch also appends a new `BacklogItem` field claiming 33 (or 34) before this project's Phase 3 lands; whichever PR merges second either conflicts in git on `backlog.proto` (best case) or, if the two additions land in non-overlapping hunks of the same message, merges cleanly with a duplicate field number that `buf`/`protoc` only catches on the *next* `make proto-gen`/CI run — a generation failure discovered well after the PR looked green. | Don't treat 33/34 as a value to type verbatim from the plan doc — re-derive "current highest field number + 1" from `main` immediately before editing at implementation time (a one-line grep/sort check), and rely on the existing `buf lint`/`buf generate` CI gate (already wired per the `buf-setup-action` fix in this repo's recent history) as the actual source of truth, not the plan's recorded numbers. | P2 |
| 5 | Pattern Decision P2 chose per-question submission (one `triggerTriage` call per answered question) specifically to avoid "lose your other answers on one failed submit," but didn't examine what happens when a triage round asks more than one question — the common case for a "clarifying questions" feature — against the `triageInFlight` guard's up-to-30-minute exclusivity window. | A real triage run asks 2+ clarifying questions; the operator answers the first (firing a `triggerTriage` call that can run up to 30 minutes), then immediately tries to answer the second — which fails against the `alreadyInFlight` guard, and will keep failing for the full duration of the first retriage. For any triage round with more than one open question, the feature degrades to "one question answerable per ~30-minute cycle," which does not meaningfully close the feedback loop faster than the manual baseline for the multi-question case the feature was meant to fix. | Before implementation, check whether multi-question triage rounds are actually common (grep recent `submit_triage_result` question counts, or ask the triage-prompt author). If common, revisit P2: compose all currently-open answered questions from one render into a single multi-Q/A feedback string on one `triggerTriage` call (still the existing field/RPC — no scope violation), or at minimum make the second+ "Answer" toggle show "queued — will apply once the current re-triage finishes" instead of a hard failure. | P2 |

## P1 Items (address before implementation)
- [x] Failure #3 — Get an explicit product decision on whether shipping Approve/Request-Changes without in-browser plan content (or even a clear "go read this" affordance) is an acceptable v1 trade-off, and record it as a stated line in plan.md's Unresolved Questions rather than leaving it implicit in §0's YAGNI scope-trim rationale. **Resolved**: recorded as Unresolved Question 7 in `implementation/plan.md` — decision made explicit: accepted as a v1 trade-off, no content-viewed gate added (no AC requires it), revisit only if operators are observed approving/rejecting implausibly fast.
