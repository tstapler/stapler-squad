# Pre-mortem: pr-event-webhooks
**Date**: 2026-08-24

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Operator enables `pr_event_webhooks` for a repo without a matching `github_push`-type `Workflow` row (the only secret source the signature-verification loop checks), so every delivery for that repo fails HMAC verification and is rejected before ever reaching the fix-trigger logic — the operational prerequisite the plan's own Unresolved Questions flags but doesn't gate. | `TriggerFireEvent` rows for that repo accumulate with `outcome: "rejected"` (signature failure), while the operator sees zero new PR-fix reconciliations and has no signal tying the silence back to "missing Workflow row" rather than "nothing needed fixing." | Add a startup/on-flag-enable check that cross-references tracked `pr_pending` items' repos against `WorkflowRepository.ListByTriggerType("github_push")` and logs a loud warning for any repo with an active `pr_pending` item but no matching Workflow row. | P1 |
| 2 | The public-reachability story (Epic 3.2) is documentation only, with no code-level verification that GitHub can actually reach `/webhooks/github` — an operator who flips `pr_event_webhooks` on without completing the tunnel/nginx setup gets a fully-wired, all-green feature that never receives a single real GitHub delivery. | Zero `TriggerFireEvent` rows of any outcome ever appear for the new event types — indistinguishable from "no CI failures happened," since the poller keeps quietly catching everything on its normal cadence and masks the total absence of webhook traffic. | Add a reachability self-check step to the new doc (e.g., GitHub's "Recent Deliveries" panel or a ping API call performed right after setup) and log a distinguishing `InfoLog` line on the first successful delivery of each new event type, so an operator can `grep` for "has this ever actually fired" instead of relying on row *absence*, which looks identical to "healthy." | P1 |
| 3 | ADR-001's self-login filter fails open when `github.GetCurrentUserLogin` errors — exactly the condition (GitHub API outage/rate-limiting) most likely to coincide with the bot's own `/github:pr-ship` status comments landing unfiltered, letting the bot's own comments re-trigger `TriggerPRFixForEvent` and potentially re-spawn fix sessions that post further comments. | A burst of `fired_success` `TriggerFireEvent` rows for the same `(repo, prNumber)` in rapid succession, correlated with repeated "self-login cache refresh failed" Warn log lines and a rework-cap counter climbing unexpectedly fast on one item. | After N consecutive `GetCurrentUserLogin` cache-refresh failures, fail *closed* (treat `issue_comment`/`pull_request_review` events as non-actionable) instead of open, and log a distinct "self-filter degraded" line separate from a normal cache miss. | P3 |
| 4 | The pinned `action`/`conclusion`/`state` consts reflect GitHub's docs as researched, but GitHub has added enum values without a breaking-change notice before (noted in the plan's own Unresolved Questions), and `check_run.pull_requests` is empty for fork-sourced PRs (also called out) — both cases make an extractor return `actionable=false` for events that genuinely warrant a fix-loop trigger. | A specific, reproducible class of real CI failures (all fork-PR check runs, or any new GitHub conclusion value) never produces webhook-sourced `fired_success` outcomes, but the poller quietly picks up the same PRs 60s later — the feature appears to work in aggregate while silently under-covering a whole delivery class, discoverable only by manually diffing webhook- vs poller-triggered timestamps. | Add a periodic audit comparing webhook-sourced `TriggerFireEvent` outcomes against poller-triggered reconciliations for the same items, flagging any item the poller had to catch despite a webhook delivery existing for it that resulted in `no_match`/`rejected`. | P2 |
| 5 | The plan explicitly rejects an in-process debounce beyond `RemediationDue`'s CAS gate on the grounds duplicate *spawns* are already prevented — but a matrix CI build can fire dozens of `check_run`/`workflow_run` deliveries for one PR within seconds, and each still triggers a full `reconcilePRPendingItem` → `GetPRStatus` API call before the backoff gate short-circuits the spawn, burning GitHub API quota once per delivery instead of once per PR-transition. | GitHub API rate-limit-remaining drops sharply during matrix-build completions, and the sibling `push`-triggered session-creation feature — sharing the same token/quota — starts intermittently throttling with rate-limit errors that have no apparent connection to PR-fix webhooks. | Promote the short-TTL in-process debounce keyed by `(repoFullName, prNumber)` — which the Pattern Decisions table explicitly deferred as "a possible future optimization" — from optional to required before shipping, short-circuiting duplicate deliveries within a small window (10-30s) before they reach `GetPRStatus`, not just before they reach `AutoReopenForPRFix`. | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — Addressed in `plan.md`'s Risk Control section: `TriggerPRFixForEvent` (Task 1.2.2a) now logs a `WarningLog` the first time it resolves an item whose repo has no `github_push`-type Workflow row, closing the "operator has no signal" gap.
- [x] Failure #2 — Addressed in `plan.md`'s Risk Control section: `handlePRFixEvent` (Task 2.3.2b) now logs one `InfoLog` per event type on its first successfully-verified delivery, and Story 3.2.1's doc (Task 3.2.1a) gained a "verify reachability" step (re-deliver a past event, confirm the log line appears).
