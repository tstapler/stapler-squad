# Pre-mortem: web-transport-architecture-review
**Date**: 2026-08-22

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | A future TLS-terminating reverse proxy in front of `:8543` (the pattern already documented in `.claude/docs/slack-phase2-public-reachability.md`) forwards `WatchSessions`/`WatchReviewQueue`; `opt.baseUrl.startsWith("https://")` reads `https:` from `window.location`, native transport is selected, but the Go process behind the proxy still speaks HTTP/1.1 to it, reintroducing the long-lived-`fetch()`-holds-a-connection-slot regression the guard exists to prevent. | Other tabs/requests on the proxied origin start stalling or timing out under load (browser's ~6-connection-per-origin cap exhausted); no explicit error, just intermittent app-wide slowness for users behind that proxy. | Strengthen the guard beyond a client-observed URL-scheme string — e.g. have the server advertise its own negotiated protocol (a response header/probe) rather than trusting `location.protocol` — and correct the plan's Unresolved Question, which currently claims "no such deployment exists today" when the precedent already exists in-repo. | P2 |
| 2 | The `useSessionService.ts` reconnect state machine (`watchSessions`'s `startStream`, `useSessionService.ts:1004-1019`) decides whether to give up or keep retrying by reading a `ws-close-code` header that only `fromWebSocket()` (`watch-ws-transport.ts:53`) ever sets. Native `createConnectTransport` errors never carry that header, so `getWsCloseCode(err)` is always `null` on the native path and the "non-retriable close code, stop reconnecting" branch never fires — every failure, including ones that should stop retrying, falls through to indefinite exponential backoff. | The mobile app (`https://onyx.staplerhome.internal:8444`, the one real consumer of the TLS listener per project memory) gets stuck in a silent infinite reconnect loop after a hard failure (e.g. auth/protocol error) instead of surfacing a clear disconnected state — appears as "session list won't load" with no actionable error. | Add a task to Epic 1.3/1.4 that exercises a non-retriable server error over the native transport and asserts the reconnect state machine still stops retrying — not just that the transport-selection branch is called (Task 1.3.1c only spies on which constructor runs). Behavior parity of `getWsCloseCode`/`isRetriableCloseCode` across both transports is untested today. | P1 |
| 3 | No e2e/TLS-listener test harness exists (`tests/e2e/helpers/test-server.ts` has no `StartRemote` support, already flagged in adversarial review), so every future change to the transport-selection code — including a fix for #2 — reaches production via the manual, single-operator trial only, with zero CI regression protection on the one path that actually matters (remote-access/mobile). | A regression on the native path (e.g. a reintroduction of #2, or a new one) first surfaces against the mobile app after a routine PR that passed all automated checks. | Extend the e2e harness with a self-signed `StartRemote` instance (Playwright can be configured to ignore the cert) before Story 1.4.2's "default the flag to true" follow-up ships, or explicitly require a fresh manual re-trial on every subsequent change to `watch-ws-transport.ts`/`useSessionService.ts`, not just the initial rollout. | P2 |
| 4 | The "`StreamingWSBridge.Handler()` forwards non-upgrade requests transparently" claim (verified by reading `ws_stream_bridge.go:44-62`) has only ever been exercised by short unary requests in practice — a multi-minute, multi-event native HTTP/2 stream through the `r.Clone`-and-URL-rewrite fallback branch is new live traffic under this plan. If any layer between the mux and the Connect handler (e.g. the `otelhttp.NewHandler` wrapper) buffers rather than flushes per-message on this specific code path, events would arrive delayed/bursty instead of erroring outright. | Session-list/review-queue updates on the native (mobile) path "feel laggy" — minutes-old data rather than real-time — with no error logged anywhere, making it hard to distinguish from normal network latency. | Task 1.1.1a only hits `/health`; add a task that streams several `WatchSessions`/`WatchReviewQueue` events through the actual bridge fallback branch and asserts per-event delivery latency, not just eventual correctness of a single response. | P2 |
| 5 | `web-app/public/cache-sw.js` is a cache-first service worker for all GET requests (confirmed: `caches.match` returns a cached response before ever hitting the network, `cache-sw.js:34-48`), and the mobile app is installed as a PWA (`manifest.json` present). Once installed, it will keep serving the pre-change JS bundle — with `createSessionWatchTransport` absent or the flag effectively baked in as off — until `CACHE_VERSION` in `cache-sw.js` is bumped on deploy. The plan's rollout steps (Epic 1.4) never mention this. | The flag is flipped on / the frontend is rebuilt and redeployed, but the mobile app (the only real target of this change) shows no behavior change at all — because it's still running service-worker-cached JS from before the change. | Add a one-line rollout step to Epic 1.4 / Risk Control: bump `CACHE_VERSION` in `web-app/public/cache-sw.js` as part of any deploy that changes transport-selection code, so the PWA-installed mobile client actually picks up the new bundle instead of serving a stale cached one indefinitely. | P1 |

## P1 Items (address before implementation)
- [x] #2 — Add a reconnect-parity test (or code fix) so `getWsCloseCode`/`isRetriableCloseCode`-driven non-retriable-error handling in `useSessionService.ts:1004-1019` behaves correctly over the native `createConnectTransport` path, not just the WS-bridge path; extend Task 1.3.1c's scope or add a new task under Epic 1.3. **Resolved**: added as Task 1.3.1d in `implementation/plan.md`.
- [x] #5 — Add an explicit rollout step to Epic 1.4 (or the Risk Control section) requiring a `CACHE_VERSION` bump in `web-app/public/cache-sw.js` whenever transport-selection code changes, so the PWA-cache-first mobile client actually receives the updated bundle. **Resolved**: added as Task 1.4.1b in `implementation/plan.md`.
