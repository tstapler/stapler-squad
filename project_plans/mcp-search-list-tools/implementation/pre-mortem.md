# Pre-mortem: mcp-search-list-tools
**Date**: 2026-08-13

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `search_claude_history` wraps `SearchClaudeHistory`, which runs `SearchEngine.IncrementalSync` (`session/search/engine.go:399-479`) synchronously on *every* call — a full exclusive-lock (`e.mu.Lock()`) directory scan + possible index re-save that also blocks all concurrent `Search()` readers (`RLock` queues behind a pending `Lock`). Current plan.md's Risk Control section (lines 80-83) covers only feature-flag scope, rollback, and staged rollout — it contains zero mention of `IncrementalSync`, rate limiting, debouncing, or lock contention, even though this exact risk was already raised as a Concern in `implementation/adversarial-review.md` line 14 and was the sole P1 in the prior pre-mortem revision. The plan regressed/never incorporated the fix across its rewrite to 31 tasks. | Latency spikes or apparent hangs on the deployed `stapler-squad` instance whenever an LLM/agent loop calls `search_claude_history` repeatedly (retries, multi-session polling) — other RPCs sharing the process (session creation, tmux control-mode reads) stall behind the same lock, surfacing as general app unresponsiveness rather than something traced back to this tool. | Add a per-key rate limit before implementation, reusing the existing `tokenBucket`/`writeLim` pattern already used for `write_to_session` (`server/mcp/tools_terminal.go:48,277`) and `create_session` (`server/mcp/tools_lifecycle.go:94`) — both established precedents in this exact package. At minimum, add an explicit sentence to plan.md's Risk Control section naming this as an accepted risk and a duration metric/log line on the `IncrementalSync` span so the cost is visible if it bites, matching how the feature-flag asymmetry *was* written up as an explicit accepted-risk decision two paragraphs above where this one is silent. | P1 |
| 2 | Task 1.4.1a's stated safety net, `TestToolRegistrationCount`, only greps `s.AddTool(` in 5 hardcoded files (`server.go`, `tools_discovery.go`, `tools_lifecycle.go`, `tools_terminal.go`, `tools_vcs.go` — `server/mcp/server_test.go:22-45`). All 3 new tools register in files outside that list (`tools_backlog.go`, `tools_notifications.go`, `tools_history.go`), so a dropped `s.AddTool(...)` call, or a forgotten `registerNotificationTools(...)`/`registerHistoryTools(...)` invocation in `server.go`'s shared `if svc != nil` block (the exact spot Tasks 1.2.1e/1.3.1e both edit sequentially per the dependency diagram), would pass this test with a straight face. Already flagged in `adversarial-review.md` line 16 with a concrete fix (assert against the live `MCPServer`'s `ListTools`); plan.md's Epic 1.4 still names only the file-grep test as the check. | CI is green, the PR merges, but `search_claude_history`/`get_notification_history`/`list_backlog_items` don't actually appear when an MCP client calls `tools/list` — discovered only when someone (or an LLM client) tries to invoke the tool by name and gets "unknown tool," well after merge. | Before implementation, change Task 1.4.1a (or add a new task) to assert tool count via the live `MCPServer.ListTools()` (or equivalent) rather than relying solely on the known-incomplete file-grep test — a one-line addition to Epic 1.4, not a new epic. | P2 |
| 3 | `list_backlog_items` (Pattern A, Pattern Decisions row 2) calls the full `ListBacklogItems` RPC — including its per-item `buildCostLookup()` proto-conversion work — for the entire matching set, then truncates to `limit` client-side in the MCP handler. Cost scales with total matching items, not the ≤50 actually returned. Bounded today by the backend's `defaultSafetyLimit` (1000 rows, cited in Pattern Decisions row 60), but plan.md's Risk Control section doesn't acknowledge this inherited cost at all — the only pagination discussion is about correctness (offset/limit shape), not the wasted-work cost of computing then discarding rows 11-1000. | As the backlog grows toward the 1000-row cap, broad/unfiltered `list_backlog_items` calls (easy for an LLM client to issue, unlike the web UI's paginated, human-driven browsing) show gradually increasing latency, eventually contributing to a slow-request incident that's hard to attribute back to this specific new caller pattern months later. | Add a one-line acknowledgment to plan.md's Risk Control section (mirroring the treatment already given to the feature-flag asymmetry) naming this as an accepted, bounded cost at current scale — cheap to write now, and it's the difference between "known tradeoff" and "surprise" when it's eventually noticed in a profile. | P3 |
| 4 | `SearchClaudeHistoryResult.TotalMatches` (plan.md line 42) is a differently-named field for the same "how many results exist beyond what's returned" concept that `ListBacklogItemsResult.TotalCount` (line 40) and `GetNotificationHistoryResult.TotalCount` (line 41) both use. All three of these new tools are the same shape — list/search results with a page + a total — and this is exactly the kind of cross-tool consistency an LLM client benefits from being able to assume once it's learned one of the three schemas. | An LLM client (or a human skimming 3 tool schemas back to back) that assumes `TotalCount` is the universal field name for "total available" writes code/prompts against `search_claude_history`'s result that silently reads a missing field, falling back to treating `TotalMatches` as absent/zero and mis-reporting result counts — a quiet correctness bug in downstream consumers, not a crash in this codebase. | Rename `TotalMatches` to `TotalCount` in Task 1.3.1b before implementation, unless there's a deliberate reason (there's none stated in the plan) to distinguish "matches" semantics from "count" semantics across the 3 tools — a two-word field rename is free right now and expensive once an MCP client has been written against it. | P3 |
| 5 | This plan is the first to route real historical content — Claude conversation snippets (`search_claude_history`) and notification message bodies (`get_notification_history`) — through MCP, not just session metadata. Both tools register unconditionally whenever `svc != nil` (Risk Control section, lines 81-83), the same ungated exposure as low-sensitivity tools like `list_workflows`. Risk Control explicitly calls out and justifies the *feature-flag* asymmetry but is silent on the *content-sensitivity* asymmetry — a different concern adversarial-review.md raised separately (line 19) that the plan's flag-focused writeup doesn't cover. This matters more than it would in a narrower deployment because this repo supports a documented `--remote-access` mode (`CLAUDE.md`'s manual-test-instance section), meaning the MCP surface is not axiomatically localhost-only. | Not a runtime symptom — this is a silent scope decision that would only surface if/when someone audits what an MCP client (or a compromised/misconfigured remote-access endpoint) can read, and finds full conversation history searchable with no access-control layer beyond "the service is running," well after this and other tools have normalized that posture. | Add one sentence to plan.md's Risk Control section stating this is a deliberate, accepted decision (matching existing precedent for other content-bearing tools) rather than an omission — the cheapest possible fix, and it converts an implicit inheritance into a reviewable, explicit call, consistent with how the plan already treats the feature-flag gap. | P2 |
