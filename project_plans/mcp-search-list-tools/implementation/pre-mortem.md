# Pre-mortem: mcp-search-list-tools
**Date**: 2026-08-12

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `search_claude_history` triggers a full FTS `IncrementalSync` rebuild on every call with no rate limit, so an LLM client that calls it repeatedly (agentic retry loop, several concurrent sessions) causes repeated full-history reindexing with no backpressure. | Server latency/CPU spikes correlated with `search_claude_history` calls; other RPCs slow down during bursts of history-search activity. | Add a lightweight rate limit using the package's existing `writeLim`/token-bucket pattern, or add an explicit "accepted risk, here's why" sentence to plan.md's Risk Control section (adversarial-review.md already flags this gap — plan currently says nothing). | P2 |
| 2 | Task 1.3.1f's stated fallback (test argument-parsing only, against an empty index) is taken instead of the real on-disk FTS fixture, so the handler's own snippet-mapping/sanitization code — the part of Epic 1.3 actually being added — ships with zero coverage against a real match. | A real query against `search_claude_history` returns empty, malformed, or wrongly-truncated snippets despite the underlying `SearchEngine` genuinely having a match (bug only visible in the MCP-layer mapping code, not in `session/search`'s existing engine-level tests). | In plan.md Task 1.3.1f, make the on-disk fixture the required path and the argument-only test purely additive (not an either/or), matching adversarial-review.md's recommendation. | P2 |
| 3 | `priority` filter on `list_backlog_items` has no server-side range validation (unlike `status`, which Story 1.1.1's own AC exists to guard), so a typo'd or out-of-range priority (e.g. `0` or `6`) silently matches zero rows instead of returning a helpful error. | User/LLM passes an invalid `priority` value, gets back `Items: []` with no error, and reasonably concludes "no matching items" rather than "bad input" — may retry with different filters instead of fixing the value. | Add the same `1 <= p <= 5` range check used for `status`, returning `ErrInvalidArgument` with a remediation hint, in Task 1.1.1b. | P3 |
| 4 | `list_backlog_items` inherits `BacklogService.ListBacklogItems`'s fully unbounded, no-server-pagination fetch — the MCP handler truncates only after the entire matching set is already materialized in memory, up to the storage layer's ~1000-item safety cap. | As the backlog table grows, `list_backlog_items` calls (especially unfiltered ones) get progressively slower/more memory-heavy, with no visible warning sign until it's already a noticeable RPC latency outlier. | Add a one-line acknowledgment to plan.md's Risk Control section (pre-existing RPC behavior, but this plan is what makes it LLM-triggerable for the first time) so it's tracked rather than rediscovered cold in production. | P3 |
| 5 | `workflowServiceErrResult`'s hardcoded fallback text (`"workflow operation failed: %v"`) is now reused by 3 more unrelated domains (backlog listing, notification history, Claude search), so any Internal-error path in these new tools produces a misleading message naming the wrong subsystem. | A debugging session (human or LLM) sees `INTERNAL_ERROR: workflow operation failed: failed to list backlog items: ...` in an MCP transcript and initially investigates the wrong subsystem. | Note the now-5-domain reuse explicitly in plan.md, or thread a domain-specific op-name string into the existing helper (small, non-blocking refactor) rather than leaving it as an unremarked pre-existing wart. | P3 |
