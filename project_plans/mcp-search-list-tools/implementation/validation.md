# Validation Plan: mcp-search-list-tools

**Date**: 2026-08-12

## Happy Path Scenario

Given an existing backlog item `bi-002` in status `in_progress` (among other items in other statuses), when an LLM client calls the `list_backlog_items` MCP tool with `status: ["in_progress"]`, then it receives a `ListBacklogItemsResult` whose `Items` contains exactly `BacklogItemBrief{ID: "bi-002", ...}` — proving an LLM can filter backlog items through MCP without a raw RPC/curl call, the core gap this feature closes.

## UX Acceptance Tests

N/A — pure infrastructure, no user-facing surface. This is a backend-only MCP tool-wiring task with no `design/ux.md` and no `web-app/` changes; the "UX" here is the MCP tool schema/description text itself, which is covered by the schema-registration assertions embedded in the integration tests above (e.g. `TestToolRegistrationCount`), not a separate UX test category.

## Test Stack

- **Unit**: Go `testing` package + table-driven tests (this repo's convention — see `server/mcp/*_test.go`). Handler-level tests that exercise argument parsing/validation and reject-before-RPC-call behavior, typically with a `nil` or minimally-constructed dependency to prove validation short-circuits before any backend call.
- **Integration**: Go `testing`, real in-process service/storage construction (no mocks) — this package's existing tests construct real `*services.BacklogService`/`*services.SessionService` against `t.TempDir()`-backed storage (`newTestBacklogStorage`, `notifications.NewNotificationHistoryStore`, `services.NewSessionServiceWithSearchEngine`). Used wherever a test needs to prove behavior through the real backing RPC/service/storage layer (pagination truncation, store-global unread counts, real FTS matching), not just handler-level argument mapping.
- **E2E / UX**: N/A — no web-app surface; MCP tool behavior is fully covered by the unit/integration tiers above.

| Stack | Coverage command | Target |
|---|---|---|

- All public service methods: happy path + error paths covered — `listBacklogItems`, `getNotificationHistory`, `searchClaudeHistory` each have ≥1 happy-path and ≥1 error-path test above, plus the priority-validation gap fill.
- All external integrations: unit mocked (validation-only paths) + at least one integration test — each of the three tools has a real-service/storage integration test (limit clamping for backlog, default-limit + store-global unread count for notifications, real FTS match + limit clamp for search).

- Regression guard for AC4: `TestGetBacklogItem_ErrorHintReferencesListBacklogItems_When_InvalidUUIDGiven` plus the unmodified `TestToolRegistrationCount` together prove the dangling reference is resolved *and* stays resolved, without relying solely on a one-time manual `grep` checkpoint.

## Notes for Implementation

- Run `make build && go test ./server/mcp/... ./server/services/...` and `make lint` as the final gate (Epic 1.4/Task 1.4.1a), confirming `TestToolRegistrationCount` passes unmodified and no new lint findings appear in `tools_notifications.go`/`tools_search.go`.
- Two review docs (`adversarial-review.md`, `architecture-review.md`) surfaced concerns this validation plan directly accounts for: the `priority` validation gap (new required test above), the `search_claude_history` FTS-fixture test being promoted from "acceptable fallback" to "required path" (per adversarial-review.md's explicit recommendation), and the `validBacklogStatuses` literal-vs-derived-from-constants concern (architecture-review.md) — that last one is an implementation-detail fix to Task 1.1.1a itself (source the list from `session/domain.BacklogStatus*` constants rather than a hand-typed literal) and doesn't change this validation plan's test surface, since both forms produce the same list today; no additional test is needed to catch future drift beyond what `TestListBacklogItems_RejectsInvalidStatus_When_UnknownValueGiven` already exercises against whichever list ships.
- `search_claude_history`'s per-call `IncrementalSync` cost (flagged by adversarial-review.md as unaddressed in Risk Control) is a performance/rate-limiting concern, not a correctness one — no test is added for it here since no rate-limiting behavior is in scope for this plan; if a rate limit is added later, its test would belong in a follow-up validation pass, not retrofitted into this one.
