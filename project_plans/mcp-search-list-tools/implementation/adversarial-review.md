# Adversarial Review: mcp-search-list-tools

**Date**: 2026-08-13
**Verdict**: CONCERNS (blocker below resolved post-review — see strikethrough note)

## Blockers
- [x] ~~**ADR-002's justification for requiring `backlogSvc` doesn't match the response shape the plan actually chose.**~~ **RESOLVED 2026-08-13**: ADR-002's Context/Alternatives-Considered sections were corrected to cite the actual reason (reusing `BacklogService.ListBacklogItems`'s status-override-exclusion filter-translation business rule, not cost-annotated proto conversion — `BacklogItemSummaryResult` never used cost data). Original finding preserved below for record. ADR-002 says `list_backlog_items` must hard-fail (`ErrInternalError`) when `h.backlogSvc == nil` because reproducing `BacklogService.ListBacklogItems`'s cost-annotated proto conversion (`buildCostLookup`/`backlogItemSummaryToProto`, both unexported) outside `server/services` isn't feasible. But Task 1.1.1b's own `BacklogItemSummaryResult` type is `{ID, Title, Status, Priority, CreatedAt}` — no cost field at all — and every one of those fields already exists directly on `session.BacklogItemSummary` (`session/repository.go:516-533`), which `storage.ListBacklogItemSummaries(ctx, filter)` returns with no proto conversion or cost lookup involved. `storage` is always non-nil whenever backlog tools register at all (`storage != nil && ...` gate in `server/mcp/server.go:63`), so Pattern B (rejected by ADR-002) would make the tool universally available — including on the Phase-1 stdio path, where ADR-002 currently concedes it's unavailable. Either (a) `storage.ListBacklogItemSummaries` genuinely doesn't need `backlogSvc` and ADR-002/Task 1.1.1c should switch to it (removing the Phase-1 stdio gap for free), or (b) there's a different, real reason to keep Pattern A (e.g. reusing `BacklogService`'s status/priority-filter translation into `BacklogItemFilter` instead of duplicating it in `server/mcp`) — but that is a materially smaller, different justification than "cost annotation requires it," and ADR-002 should say so accurately before Task 1.1.1c is implemented against the current (inaccurate) rationale. — **Recommendation**: resolve which pattern is actually correct and update ADR-002's Context/Decision before writing `listBacklogItems`; don't let the implementer follow a nil-check-and-fail design whose stated reason doesn't hold for the fields actually being returned.

## Concerns
- [ ] **Risk Control section doesn't mention `search_claude_history`'s per-call `IncrementalSync` cost, and Pattern Decisions overstates how well-guarded it is.** Verified in `session/search/engine.go` and `server/services/search_service.go`: `SearchClaudeHistory` calls `ss.searchEngine.IncrementalSync(hist)` unconditionally on **every** invocation (`search_service.go:481`), not gated by the `getOrRefreshHistoryCache` TTL/singleflight — that guard (`search_service.go:169-231`, confirmed as genuinely lock-free-fast-path + singleflight-coalesced) only covers the disk-scan that builds `hist`; it does not skip `IncrementalSync` itself. `IncrementalSync` (`engine.go:399-496`) takes a full write lock (`e.mu.Lock()`) for its entire duration and always walks `computeChangesLocked` (`engine.go:500-533`, O(number of Claude-history sessions) diff) even when nothing changed — `ShouldRebuildLocked` (`engine.go:594-603`) only short-circuits into a *full* rebuild path, it doesn't skip the diff walk on a no-op sync. `Search()` (`engine.go:191-195`) takes a read lock, so it contends with this write lock on every call. This is pre-existing RPC behavior, not introduced by this plan, and the per-call cost is likely cheap in absolute terms for a single-operator tool — so it's not a correctness bug, just a latency/contention risk. But the Pattern Decisions table's phrasing ("`SearchClaudeHistory` owns a singleflight-guarded cache + inverted-index sync") reads as if the index sync itself is also cheaply guarded, when only the history-cache fetch is — and MCP callers (LLM agents looping/retrying) can plausibly call a tool far more frequently than the existing human-driven web UI caller of the same RPC. — **Recommendation**: add a sentence to Risk Control acknowledging this inherited per-call sync cost (even if judged acceptable), and correct the Pattern Decisions wording so a future reader doesn't over-trust the "guarded" framing.
- [ ] **No test task validates `list_backlog_items`'s new offset/limit slicing end-to-end.** The schema (Task 1.1.1d) and handler (Task 1.1.1c) do now correctly add an `offset` parameter and slice by `limit` **and** `offset` (confirmed — this is a genuine fix vs. an earlier version that apparently only used `limit`). But unlike `get_notification_history`/`search_claude_history` (which pass `offset` straight through to already-tested RPCs), `list_backlog_items`'s offset/limit slicing is new code written entirely in the MCP handler (`ListBacklogItemsRequest`/`Response` have no offset/limit fields on the wire at all — verified in `proto/session/v1/backlog.proto:336-354`), with no existing RPC-level test protecting it. Story 1.1.2's tasks (1.1.2a–e) cover filtering, validation, feature-gating, and "default limit applies" — none explicitly cover calling twice with different `offset` values and asserting the second page returns the next slice (not an overlapping/duplicate/empty one), or an `offset` past the end of the result set. — **Recommendation**: add `TestListBacklogItems_OffsetPagesPastFirstLimit` (or fold into 1.1.2d) to Story 1.1.2.
- [ ] **No test task covers `get_notification_history`'s inherited nil-store degrade path.** Pattern Decisions claims "`GetNotificationHistory`'s nil-store degrade-gracefully guard is inherited for free via Pattern A" (verified true in code — `notification_service.go:141-145` returns an empty, non-error response when `notificationStore == nil`) but Story 1.2.2's four tasks (1.2.2a–d) don't include a case exercising it through the new MCP wrapper. Low risk since the behavior is inherited unmodified, but the plan explicitly leans on this inherited behavior as a design justification without a test asserting it actually surfaces correctly as `okResult` (not an error) through `getNotificationHistory`.
- [ ] **Handler tasks (1.1.1c/1.2.1c/1.3.1c) don't explicitly call out RPC-error → `errResult(ErrInternalError, ...)` mapping.** The established convention throughout `tools_backlog.go` (verified — every existing handler wraps a service/RPC error as `errResult(ErrInternalError, fmt.Sprintf("...: %v", err), "")` rather than returning the raw Go error) is asserted generically in the Domain Glossary ("errResult/okResult ... Universal across all 3 new tools") but each of the three handler-implementation tasks' own text jumps straight from "call the RPC" to "map response" / "return `okResult(...)`" without mentioning the failure branch. Almost certainly what an implementer will do anyway given the file's existing pattern density, but worth being explicit in the task text so it isn't the one branch that gets skipped under time pressure.

## Minors
- AC5 (requirements.md) and Risk Control (plan.md) cite different existing-tool precedents for "ungated by design" — `create_workflow`/`list_approval_rules` vs. `search_sessions`/`list_sessions`. Both independently verified true against `server/mcp/server.go` (`registerWorkflowTools`/`registerRulesTools` inside `if svc != nil {}` with no additional flag check; `registerDiscoveryTools` registered fully unconditionally) — not a contradiction, just each doc reaching for a different (both valid) example.
- Pattern Decisions' "backend's 500" framing for `get_notification_history` is imprecise. Verified: `MaxNotifications = 500` (`server/notifications/store.go:17`) is the notification history store's total retention ceiling (how many records the store ever keeps, pruned via retention), not an enforced per-request `Limit` clamp — `GetNotificationHistory` passes `msg.Limit` straight through with no max clamp (`notification_service.go:150-151`). Functionally harmless either way (the MCP-layer max-50 cap is what actually matters, and store size naturally bounds the worst case), but "backend's 500 cap" reads like a formal API limit that doesn't exist as stated.
- The Unresolved Question about `mcpgo.WithArray(...)`'s per-element `Enum()`/`Min()`/`Max()` support can be answered now rather than left for the implementer: verified directly from `$(go env GOMODCACHE)/github.com/mark3labs/mcp-go@v0.48.0/mcp/tools.go` that `Enum`/`Min`/`Max` write straight into whatever schema map they're passed into (lines 1023-1081), so passing them directly as `WithArray` args would incorrectly constrain the array *value* as a whole rather than each element — per-element constraints require nesting inside `Items(map[string]any{...})` instead (confirmed via `Items`'s doc comment/signature at line 1290-1308, which accepts an arbitrary nested schema). Task 1.1.1d's own pseudocode already routes through `mcpgo.Items(...)` rather than passing `Enum()` straight to `WithArray`, so the plan appears to have anticipated this correctly — just tighten the Unresolved Question's wording now that it's directly confirmed rather than deferred.
- Second Unresolved Question (does `Search()` degrade gracefully for an out-of-range offset) is also answerable now: verified at `engine.go:224-229` — `Search()` explicitly handles `opts.Offset >= len(scoredDocs)` by setting `scoredDocs = nil` (empty result, no panic/error). No action needed beyond noting this in the plan so Task 1.3.1c's implementer doesn't need to re-derive it.
