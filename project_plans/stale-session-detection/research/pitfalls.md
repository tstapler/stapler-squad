# Pitfalls Research: stale-session-detection

**Date**: 2026-08-06
**Agent**: Phase 2 Research, Agent 4 (Pitfalls)

## 1. Threshold proliferation — this would be the fourth independently-tuned "is this session stale" number

Confirmed current state on `main` (requirements.md's "2-5min" framing is now stale — recheck):

| Threshold | Value | Location | Purpose |
|---|---|---|---|
| `ReviewQueuePollerConfig.StalenessThreshold` | **5 min** (recalibrated from 2 min by `review-gate-stale-session-rework` ADR-001, 2026-07-24) | `session/review_queue_poller.go:49` | Review Queue "Stale" badge (informational) |
| `maxReworkBlockStaleness` | 15 min | `server/services/backlog_service_triage.go` (per ADR-001) | Gates `notifyIfActiveWorkSessionStale` / `AutoReopenAfterFailedReview` |
| `maxWorkSessionStaleness` | 2 hr | `session/backlog_lifecycle.go:2098` | `StuckReasonStaleWork` durable stuck-item detector |
| *(proposed, review-queue-state-detection FR-3)* | 5 min | not yet confirmed shipped — Phase 2 stack/architecture research should verify | `session.state.stuck` event |

`review-gate-stale-session-rework`'s own pitfalls.md (§1) already flagged this exact risk before this project existed: "three different subsystems independently reaching for three different numbers... without an explicit decision about which is canonical for which purpose, this fix risks becoming a fourth uncoordinated number." This project now adds **two more consumers** (main-list card indicator, `session_age_minutes` approval condition) on top of that already-crowded set.

- **The risk is concrete, not hypothetical**: the 37/41 false-positive incident happened because a threshold tuned for one purpose (rework-block gate) was reused for a structurally different purpose (general badge) without recalibration. A card-indicator threshold that's too aggressive will reproduce that same UX complaint at a third surface; an approval-rule threshold that's miscalibrated has a **worse** blast radius than either (see §5).
- **Recommendation**: don't invent a 5th unnamed number. Either (a) explicitly reuse one of the three already-decided thresholds for the card indicator/approval condition with a documented rationale for why that one transfers, or (b) add exactly one new named, config-driven constant with the same ADR-001-style rationale table, and cross-reference it against the existing three so a future reader sees all four in one place. The requirements.md's own success metric #4 ("No duplicate threshold/detector is introduced") is the right bar — Phase 3 planning should hold itself to producing a rationale table, not just a number.
- **Config-shape trap**: requirements.md's Open Questions already flags "one threshold with per-context overrides vs. fully independent keys" as unresolved. Picking independent keys without a shared default risks each consumer's config defaulting independently and drifting again the moment someone tunes one without realizing three others exist — the same failure mode as the undocumented 2026-10-22 commit that silently dropped the shared value from 5min to 2min (cited in ADR-001) with no changelog rationale. Whatever shape is chosen, the default values must be set explicitly in code (matching each existing hardcoded default), not left to zero-value config surprises (see §4).

## 2. Notification spam / flapping — the existing notify-once primitive is backlog-item-scoped, not session-scoped

`MarkStuck`/`MarkStuckNotified` (`session/ent_repository_backlog.go:1199,1294`) already implements exactly the "notify-once-until-resolved" pattern this feature needs:

- A durable `BacklogStuckState` row keyed on `(item_id, reason)`, upserted idempotently.
- An **open** row only refreshes `last_checked_at`/`context` — `notified_at` is left alone, so repeated ticks don't re-notify.
- A **resolved** row is reopened in place (`ClearResolvedAt()`, `ClearNotifiedAt()`, reset `first_detected_at`) rather than creating a second row — so going stale → un-stale → stale again correctly re-arms notification exactly once per new stale episode, not once ever and not once per tick.

**The gap**: this mechanism is keyed on `itemID` (a `BacklogItem` UUID) and `domain.StuckReason`. The new main-session-list card indicator and its optional notification (`stale_notify`) are scoped to *sessions*, not backlog items — and per requirements.md's own framing, this is explicitly "a distinct, narrower UI surface... independent of backlog stuck-state." Many sessions in the main list (manually created directory sessions, one-off sessions) have **no backing `BacklogItem` at all**, so `MarkStuck` literally cannot be called for them (`current.Status != string(expectedStatus)` precondition assumes a backlog item's status column exists).

- **Consequence if this is missed**: an implementation that reaches for the existing notify-once pattern by default will either (a) silently fail to notify for non-backlog sessions, or (b) be forced to synthesize a fake backlog item / expand `BacklogStuckState`'s schema to cover session-only rows — a bigger schema change than this feature's "Complexity: 2 — no new data model required" framing assumes. Flag this explicitly in planning: the notification-on-state-change requirement needs its **own** lightweight dedup (e.g. an in-memory per-session "last notified stale episode" marker, following the same open/resolved-reopen shape but scoped by session title/ID, not a DB table) — reusing `MarkStuck` as-is only covers the subset of sessions that happen to have a backlog item.
- **Flapping mitigation absent by default**: nothing in `ReviewState` currently debounces a session hovering exactly at the threshold (produces output, goes idle past threshold, produces output again, repeat). The review queue side has a related but distinct mechanism — `LastAddedToQueue`/`IsAcknowledgedAfterOutput`/`LastOutputSignature` (`session/contexts.go:159-163`) — built to suppress *re-adding to the queue*, not specifically to suppress *repeated notifications*. Don't assume that mechanism transfers to the new stale-notification path without checking; it was validated for a different consumer (`review-queue-event-driven`'s R5.1/R5.2 tests target `ReactiveQueueManager`, not a notification-bus emitter).
- **Recommendation**: design the state-change notification as edge-triggered (fire once on the idle→stale transition, once on stale→active if you want a "recovered" notification) with an explicit re-arm-on-resolve step mirroring `MarkStuck`'s reopen semantics, rather than level-triggered (fire whenever `time.Since(lastOutput) > threshold` is evaluated, which is what a naive poller-tick implementation would do and is exactly what produces spam on a hovering session).

## 3. Clock/timer correctness

- **Monotonic reading loss on persistence**: `LastMeaningfulOutput`/`LastTerminalUpdate` are plain `time.Time` (`session/review_state.go:51,55`). Go's `time.Now()` normally carries a monotonic reading that makes `time.Since`/`Sub` immune to wall-clock adjustments (NTP steps, manual clock changes) — but that monotonic component is **stripped** whenever a `time.Time` is marshaled (JSON, proto `Timestamp`, DB row) and reconstructed. Since these timestamps are wire-exposed (proto `types.proto:41,44`) and DB-persisted (session storage), any staleness computation done against a *reloaded* value (e.g. after a service restart, or read from a different process via RPC) loses monotonic protection and is exposed to wall-clock jumps. This is a real, if narrow, risk on a self-hosted single-instance box (NTP corrections, suspend/resume clock skew on a laptop) — worth a one-line doc comment on whichever function does the new comparison, not a redesign.
- **Poll-interval vs. threshold headroom**: `ReviewQueuePollerConfig.PollInterval` is 2s (fast path) / 8s (slow path), comfortably below the 5min `StalenessThreshold` — but this project should not assume a *new* threshold automatically has the same headroom. `review-gate-stale-session-rework`'s pitfalls.md §5 explicitly calls out: pick the polling cadence and the staleness threshold together, verify threshold ≥ 3-5x the polling interval, or a session that's actually fine can flap across the boundary purely from poll-tick granularity/jitter.
- **Polling vs. event-driven status is largely settled, don't re-litigate it**: `project_plans/review-queue-event-driven/` (per its `implementation/validation.md`, R1-R5) already replaced the primary status-detection path with event-driven `ClaudeController` status-change callbacks; the poller is retained only for periodic reconciliation (30s) and non-controller sessions. Phase 2/3 should confirm this is actually merged to `main` (requirements.md's own constraint says to re-confirm, don't assume) before deciding whether the new card indicator computes staleness by polling `LastMeaningfulOutput` on a timer (simplest, matches requirements' framing as "config-driven threshold read by existing detectors") or subscribes to a state-change event. Given the existing detectors (poller, backlog reconciliation) are themselves poll-based already, a poll-based card indicator computed at render/fetch time (not a new background timer) is almost certainly sufficient and avoids adding a fifth timing mechanism to reason about.

## 4. Config validation — the codebase's own established pattern is a `> 0` guard, not a hard validation error

This repo already has a directly analogous precedent: `HibernationSweeper.sweep()` (`session/hibernation_sweeper.go:222-223`) computes `idleTimeout := time.Duration(cfg.Hibernation.IdleTimeoutMinutes) * time.Minute` and then gates the entire hibernation pass behind `if idleTimeout > 0`. A zero or negative `IdleTimeoutMinutes` doesn't hard-fail — it silently and safely disables that pass. `config/types.go`'s other duration/threshold fields (`ContextWindowWarnPct`, `PollIntervalSeconds`, `RateLimitWarnRemaining`, etc.) follow the same `*OrDefault()` pattern: `if out.X <= 0 { out.X = <default> }`.

- **The trap to avoid**: a naive implementation that does `time.Since(lastOutput) > threshold` directly without first checking `threshold > 0` will, for a misconfigured `stale_session_threshold_minutes: 0` (or unset, defaulting to Go's zero value if the config loader doesn't backfill it), mark **every session as stale immediately and continuously** — the worst possible failure mode for exactly the notification-spam concern in §2, and it fires silently (no error, no log) unless someone specifically checks for it.
- **Negative values**: same risk in the other direction if compared carelessly, though `time.Duration(negative_int) * time.Minute` naturally produces a negative duration that a bare `> 0` guard correctly treats as "disabled" — follow the `HibernationSweeper` pattern exactly (guard, don't validate-and-error) for consistency with the rest of `config/`.
- **Recommendation**: add a `*OrDefault()`-style accessor for the new config struct (matching `CapacityConfigOrDefault()`'s shape) that backfills non-positive values to the existing hardcoded default (5min/15min/2hr, whichever this consolidates to per §1) rather than to zero, and gate any consumer's comparison behind the same `> 0` check `HibernationSweeper` uses so a misconfiguration degrades to "feature disabled," not "feature always firing."

## 5. Approval-rule `session_age_minutes` condition — miscalibration here blocks/allows real automated actions, not just a UI badge

This is the same class of bug as the 37/41 false-positive incident, but the blast radius is categorically worse: a badge misfire is visual noise; an approval-rule misfire either **silently auto-approves** something that should have been escalated, or **silently blocks** an approval that should have gone through — in a single-user, no-human-in-the-loop-by-design automation context.

Good news: there's a directly applicable, already-shipped precedent for how to add this safely — `RequireCIPassing` (`pkg/classifier/classifier.go:365-367,735-737`, added by the `ci-status-diff-viewer` project, ADR-001 "AC5 and AC6 are two independent gates"):

- It's a plain field on `ClassificationContext` (`CIStatus string`, `pkg/classifier/classifier.go:75`) — a value the **caller** (`server/services/approval_handler.go`) computes and passes in, not something the classifier package reaches out and fetches itself. `pkg/classifier` does not import `session/`. `session_age_minutes` should follow the identical shape: a plain `SessionAgeMinutes` (or similar) field on `ClassificationContext`, computed by `ApprovalHandler` from `ReviewState`/`Instance` data at classify time — not a new import edge from `pkg/classifier` into `session`, which would be exactly the kind of interface/layering violation `.claude/rules/interface-pollution-checklist.md` and the event-driven project's `R1.4`/`R4.1` "no circular imports" tests exist to prevent.
- It's **ANDed**, matching `matchesRule`'s existing all-conditions-must-pass structure (`command_pattern`, `file_pattern`, `require_ci_passing` all compose the same way) — a `session_age_minutes` condition should slot in the same way, not introduce special-cased OR/priority logic.
- **The critical fail-safe precedent to replicate**: `ApprovalHandler` already has a documented "staleness guard" for `CIStatus` — `classCtx.CIStatus = ""` when the underlying GitHub check data is itself stale (`server/services/approval_handler.go:321-323`, comment: "auto-approve (RequireCIPassing) on stale data" is explicitly what's being prevented). `""` doesn't match `ciConclusionSuccess`, so `matchesRule` returns `false`, the rule doesn't fire, and evaluation falls through to the next-priority rule (ultimately the escalate catch-all at priority 50) — **unknown/unavailable data fails closed (escalate), not open (auto-approve)**.
  - `session_age_minutes` needs the identical discipline: if the session isn't currently tracked live (the existing `notifyIfActiveWorkSessionStale`'s `ok == false` case from `TimeSinceLastMeaningfulOutput`, per the prior pitfalls doc §6) or its `ReviewState` is otherwise unavailable at classify time, the condition must be computed as "does not match" (fail closed to escalate), never silently treated as "0 minutes stale" (which would make an `age > 60min` deny-rule fail to fire and could let something through) or "infinitely stale" (which would make an age-based deny-rule fire unconditionally and block everything). Get this decided explicitly in planning — don't let it inherit whatever a zero-value `time.Duration` happens to compare as.
- **Performance constraint carried over**: `matchesRule` runs per-tool-call under a read lock (`RuleBasedClassifier.mu.RLock`, `pkg/classifier/classifier.go:381`) — it must stay a cheap in-memory comparison, not a DB lookup or RPC. Since `LastMeaningfulOutput` is already an in-memory field on `Instance`/`ReviewState`, computing the age at `BuildContext`/classify time is consistent with this constraint, but any implementation that reaches for a DB-backed `BacklogStuckState`-style lookup here (tempting after §2's discussion) would violate it — keep the approval-rule condition and the notification-dedup mechanism (§2) architecturally separate, they have different freshness/cost requirements.
- **Semantics open question carried from requirements.md**: "time since session created" vs. "time since last output" for `session_age_minutes` changes the blast radius differently — a long-lived-but-active session (creation-time semantics) would wrongly trip an age-based deny rule despite being clearly alive, which is a more surprising and harder-to-debug false positive than the last-output-time interpretation requirements.md already leans toward. Resolve explicitly in Phase 3, and name-check this reasoning in whatever ADR documents the choice — don't let "age" default to whichever field was easiest to plumb through first.

## Summary of concrete recommendations for Phase 3 planning

1. Produce an ADR-001-style rationale table that accounts for **all** staleness-related thresholds in the codebase after this feature ships (existing 3 + whatever this project adds), explicitly justifying any new number rather than adding a fourth/fifth silently.
2. Design the stale-notification dedup as its own lightweight, session-scoped mechanism (edge-triggered, resolve/reopen-aware) — do not assume `MarkStuck`/`MarkStuckNotified` covers it; that pattern is backlog-item-scoped and many main-list sessions have no backing item.
3. Follow `HibernationSweeper`'s `> 0` guard + `config/`'s `*OrDefault()` pattern for the new config surface; a 0/negative threshold must degrade to "disabled" or "default," never to "everything is stale."
4. Add `session_age_minutes` to `ClassificationContext` as a plain value computed by the caller (mirroring `CIStatus`), AND-composed in `matchesRule` (mirroring `RequireCIPassing`), and fail-closed (condition does not match) whenever the underlying session-liveness data is unavailable or stale — mirroring `ApprovalHandler`'s existing CI-staleness guard exactly.
5. Resolve "creation time vs. last-output time" for `session_age_minutes` explicitly and document the choice; default to last-output per requirements.md unless research finds a specific reason approval rules need creation-time.
