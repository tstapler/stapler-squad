# Pre-mortem: stale-session-detection
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The 30-minute default threshold (ADR-001's own "best-effort estimate," no empirical basis) doesn't match Tyler's real workflow — either long "thinking"/compile turns on legitimately-active sessions get flagged Stale (noise), or a threshold that's actually about right for compute-heavy sessions is too slow to catch a genuinely crashed process the user cares about. | Within days, several concurrently-running `ACTIVE` sessions doing long agentic turns show the "Stale" badge while clearly alive; the badge starts being mentally filtered out ("that always shows up, ignore it") the same way the review-queue's pre-recalibration threshold produced the 37/41 false-positive incident this project's own ADR-001 cites. | Before Phase 4 ships, run the notifier against a real multi-session working day (not just the single-session smoke test in Task 4.2.1b) and record the false-positive/false-negative rate at 30min; add that as a one-line empirical note to ADR-001 alongside the existing "best-effort estimate" caveat, and lower/raise the default if the smoke data disagrees with 30min before merging Phase 4. |
| 2 | This feature formally documents a **fourth** independently-tuned staleness number (30min) alongside the three that already exist (5min Review Queue, 15min rework-block, 2hr stuck-detector) for the *same underlying signal* (`LastMeaningfulOutput`), with no shared surface in the UI explaining why a session shows "Stale" in the main list but not yet in the Review Queue, or vice versa — the "uncoordinated threshold proliferation" risk pitfalls.md named as the top risk, now shipped in a new form rather than avoided. | A user (or the developer 3 months from now) files a bug report or asks "why does this session say Stale here but not there" for the same session, treating four independently-correct-by-design numbers as an inconsistency bug. | Add a single cross-reference (e.g. a tooltip on the badge, or a line in Settings near the threshold input) stating "Review Queue and the stuck-item detector use their own separate thresholds (5min / 2hr) tuned for different purposes" so the multiplicity is visible/intentional rather than silently discoverable only by reading four different source files. |
| 3 | Notification fatigue: even with correct edge-triggered dedup (one fire per stale episode), a user running 5-10 parallel sessions with a threshold that's on the aggressive side for some of them (per Failure #1) receives enough stale notifications in a normal day that they get dismissed reflexively or `notify_enabled` gets flipped to `false` within the first week — silently defeating the exact goal Story 4.1.1 states ("so that I find out without having to keep checking manually"). | `notify_enabled: false` appears in `config.json` within the first 1-2 weeks of use, or multiple stale notifications are dismissed from `NotificationPanel` without the corresponding session ever being opened. | Track (even informally, via existing structured logs) how many distinct sessions notify per day during the Phase 4 smoke-test period; if it's more than ~1-2/day at the default threshold, treat that as a signal the default is miscalibrated (feeds back into Failure #1's fix) rather than shipping and waiting for the user to self-report fatigue. |
| 4 | The frontend's 60s re-render tick (`SessionList.tsx`, Task 2.3.1b) and the backend's independent 60s `StaleSessionNotifier` tick (Task 4.1.1b) are two uncoordinated clocks re-evaluating the same "did this session cross the threshold" event — architecture-review.md flagged this as a Concern and assessed it as "not a correctness bug" but it was left unaddressed by design. In production this reads as flakiness: a push notification can arrive up to ~60s before or after the badge appears on an already-open tab. | A user notices a stale-session push notification while the corresponding `SessionCard` in an already-open browser tab still shows no badge (or the reverse), and reports it as the feature being unreliable, when both clocks are independently correct and will converge within a minute. | Add the one-line note architecture-review.md already recommended — either in the Observability Plan or ADR-001 — stating the two ticks are intentionally uncoordinated and may disagree for up to ~60s, so a future bug report citing this exact symptom can be triaged as expected behavior in under a minute instead of re-investigated as a new bug. |
| 5 | `MinSessionIdleMinutes` crosses 4+ independently hand-edited, non-exhaustive conversion hops (`ApprovalRuleData` → ent row → `RuleSpec` (3 call sites) → `pkg/classifier.Rule` (4 call sites)) with no compiler-enforced completeness check — unlike the exhaustive-switch pattern this repo uses elsewhere (e.g. `dispatch.ts`'s `OmnibarAction` union) to catch exactly this class of silent field-drop. Because the field fails closed (`0` = "condition not applied"), a future unrelated refactor that touches one of these five files and misses re-threading the field compiles cleanly and silently stops applying the idle-time gate on every rule that sets it — in a no-human-in-the-loop automation context where pitfalls.md itself flags this exact condition as having a "worse blast radius than a UI badge." | Not a build/CI failure — the first visible signal is a stale session's tool-use action getting auto-approved (or a deny-rule silently failing to fire) that a `min_session_idle_minutes` rule should have blocked, discovered only when reviewing after the fact why an action wasn't gated as configured. | Task 5.2.1e currently says "extend whichever existing test file covers the round trip" — make this concrete: add one dedicated round-trip regression test asserting `MinSessionIdleMinutes` specifically (not folded into a general `RequireCIPassing`-pattern test) survives proto→ent→`RuleSpec`→`classifier.Rule` end to end, so a future refactor that drops it at any hop fails CI instead of failing silently in production. |
