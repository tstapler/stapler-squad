# Pre-mortem: session-retry-backoff
**Date**: 2026-08-29

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Default policy (`InitialDelaySeconds: 0`, preserved for AC7 backward-compat) means jitter/backoff only ever applies once `attempt ≥ 1` with a nonzero delay — a shared-cause failure hitting many sessions at once (network blip, expired 1Password/SSH creds, tmux server OOM-killed hours after boot, outside the narrow `serverStartTime`-anchored restart-grace window) triggers `attempt 0`'s zero-delay, un-jittered restart for every affected session simultaneously. This app has already had two real OOM incidents traced to session/worktree churn (see MEMORY `project_2026_07_29_oom_session_leak_fix.md`, `feedback_backlog_wip_limit.md`); a synchronous mass-restart of 5-10 worktree-backed sessions is exactly the load pattern that caused those. | System-wide slowdown or a second OOM within seconds of the first failure signal; `stapler-squad.log` shows a burst of `handleDriverFailure`/`restartForRetry` calls with near-identical timestamps across unrelated sessions, not spread out. | Apply a minimum floor to `InitialDelaySeconds` even at "attempt 0" (e.g. always add jitter on top of 0, not `0 * (1±jitter) = 0`), or explicitly widen the restart-grace mechanism to cover *any* failure reason detected within a short window of a shared trigger (not just `tmux_exited` near `serverStartTime`) — e.g. detect N sessions failing within the same few-second bucket and stagger their restarts server-side regardless of individual `NextRetryAt` math. Add a load test (Task 6.1.x) that fails 5+ sessions simultaneously and asserts restarts are staggered, not synchronous. | P1 |
| 2 | Round-2's fix for Blocker 4 (Task 2.1.1d) extends `isOneShot()` to exclude `backlog:work`-tagged sessions from driver-level auto-retry entirely, on the assumption `BacklogLifecycleListener`'s remediation gate (`backlog_lifecycle.go`, `backlog_remediation.go`) is the sole authority for that session type. Reading `backlog_remediation.go`/`backlog_lifecycle.go` shows its remediation rows (`OpenStuckStateData`, `evaluateRemediation`) key off backlog-item-level stuck states (push failed, orphaned triage) — there is no evidence it detects "the underlying tmux/agent process for a `backlog:work` session crashed or lost its pane." Today, *before* this feature, `backlog:work` sessions are NOT in `isOneShot()`'s exclusion list (confirmed: `session/session_driver_test.go:274` asserts `isOneShot(work-tagged) == false`) and therefore DO get the existing hardcoded single-retry via `handleDriverFailure`. Task 2.1.1d silently removes that coverage for the app's primary automation mode (Tyler's 5-10 parallel `backlog:work` sessions per requirements.md) without confirming an equivalent replacement exists — this is a regression against AC7 introduced by the blocker-4 fix itself, not resolved by it. | A `backlog:work` session's tmux pane dies (crash/OOM/sleep) and the session just sits `Stopped`/gone with no retry and no `PermanentlyFailed` notification — silently worse than pre-feature behavior, discovered only when the user notices a backlog item stalled with no session activity for hours. | Before merging Task 2.1.1d, verify concretely (not by assumption) that `BacklogLifecycleListener`'s remediation gate actually restarts a `backlog:work` session whose tmux/process died — trace `evaluateRemediation`'s trigger conditions against a real "process crashed" scenario, not just backlog-item automation-step failures. If no such path exists, either (a) give `backlog:work` sessions their own retry policy resolved through this feature's `RetryState`/`RetryPolicyConfig` machinery (not excluded via `isOneShot`), coordinating via the CAS guard instead of blanket exclusion, or (b) extend `backlog_lifecycle.go`'s remediation to explicitly cover process-liveness, and add a regression test proving a crashed `backlog:work` session gets restarted by *some* mechanism end-to-end. | P1 |
| 3 | **Superseded by the architecture-review.md round-2 fix (2026-08-29)** — original text described a `retryInFlight` leak in a per-call-site CAS design (Task 2.3.3b claiming the guard directly). That design was independently replaced: `retryInFlight`'s CAS + `defer`-release now live exclusively inside `restartForRetry` (the single choke point, Task 2.3.4a per architecture-review.md Blocker 2), so no per-call-site task can omit the release — it isn't each caller's responsibility anymore. Original failure mode no longer applies to the current plan text; retained here for audit trail rather than deleted. | N/A — closed by a structural fix, not a targeted patch to this specific task. | N/A | ~~P2~~ Resolved |
| 4 | The `tmux_exited` restart-grace exemption is anchored to `serverStartTime` (process boot, captured once at package init per Task 2.2.2a) — it has no concept of laptop sleep/suspend. A machine sleeping for hours with several sessions mid-backoff wakes up with every pending `NextRetryAt` already in the past; the poll loop's tick-check (Task 2.3.3a) fires all of them as soon as the process resumes scheduling, but since this isn't a process restart, the grace exemption never applies — each of those wake-triggered restarts is treated as a *real* failure occurrence and consumes an attempt from `MaxAttempts`, silently burning down every affected session's retry budget while the user was away from the keyboard, and restarting several worktrees at once on wake (same synchronized-restart risk as #1, via a different trigger). | User opens their laptop after sleep to find several sessions already at `PermanentlyFailed` (attempts exhausted) that were healthy pre-sleep, with retry-history timestamps clustered at the exact wake moment. | Detect a wall-clock discontinuity (e.g. compare a monotonic-clock-based expected tick interval against the wall-clock gap since the last tick) and treat any failure/backoff-expiry observed within a short window of a detected large clock jump the same as `restartGrace` — don't consume attempt budget for it. Add a test that simulates a large `time.Now()` jump between two poll ticks and asserts pending retries are granted grace, not treated as real failures. | P2 |
| 5 | `StaleTriggersRetry *bool` (Task 1.2.1a) ships now as a real, user-settable `config.json` field and is documented in this feature's requirements (FR9), but its actual behavior (Task 5.1.1b) is conditional on the sibling `stale-session-detection` project shipping first with a config shape this plan can only guess at today (`grep -rn "StaleSessionConfig" config/` → confirmed absent). If the sibling ships with a different field/threshold shape than guessed, or nobody circles back to implement Task 5.1.1b at all, the config field is silently inert forever — a user sets `stale_triggers_retry: true`, sees no behavior change, and has no signal (no error, no log, no lint) that the feature they configured doesn't exist yet. | User reports "I turned on stale-triggers-retry and nothing happens" weeks/months later; nothing in logs or UI indicates the setting is a stub. | Either gate the config field's exposure behind a build/UI flag until Task 5.1.1b actually lands (don't surface `stale_triggers_retry` in the UI/API response until it does something), or have `LoadConfigFromPath`/startup logging emit a one-time warning when `StaleTriggersRetry == true` but the sibling's consumer wiring isn't present, so the gap is at least observable instead of silent. | P3 |

## P1 Items (address before implementation)
- [x] Failure #1 — **Patched into plan.md** (Tasks 2.2.2c/2.2.2d, 2026-08-29): a fixed jitter/floor
  delay at `attempt 0` plus a Phase 6 load test asserting 5+ simultaneous failures restart
  staggered, not synchronously. Not yet verified by running code (no implementation exists at this
  phase) — re-check against real behavior during `sdd:5-implement`/`sdd:6-verify`.
- [x] Failure #2 — **Patched into plan.md** (Task 2.1.1d revised, 2026-08-29): `backlog:work` is no
  longer blanket-excluded via `isOneShot()`; it uses the standard `RetryState` machinery for
  process-crash coverage, coordinated with `BacklogLifecycleListener`'s remediation gate via the
  shared `retryInFlight` CAS instead of exclusion. Also promoted to `requirements.md` AC8 so it's
  independently traceable. Same caveat as above — plan-level fix, not yet implementation-verified.
