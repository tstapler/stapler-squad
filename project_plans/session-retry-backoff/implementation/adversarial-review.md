**Date**: 2026-08-06

## Blockers

- [x] **RESOLVED (see Round 2 addendum below).** **`server/adapters/instance_adapter.go`'s `StatusToProto`/`ProtoToStatus`/`StatusStringToProto` are missing from the plan entirely, and they are the wire boundary for the whole feature.** These three switch statements (lines 293-310, 319-334, 353-377) convert `session.Status` ↔ `sessionv1.SessionStatus` and a `ReviewItem`'s string status ↔ proto. None has a `case session.PermanentlyFailed:` / `case sessionv1.SessionStatus_SESSION_STATUS_PERMANENTLY_FAILED:` / `case "PermanentlyFailed":` planned. ADR-001's verification grep (`grep -rn "case Stopped:" session/ server/`) produced a false negative here because code outside the `session` package must qualify the enum (`case session.Stopped:`), which the literal string `"case Stopped:"` does not match — confirmed by re-running the grep with the qualified pattern, which finds exactly these 3 additional sites, none currently tasked. Impact if shipped as-is: `StatusToProto`'s `default:` returns `SESSION_STATUS_UNSPECIFIED`, so `PermanentlyFailed` sessions render as unspecified/blank status over the wire — including in the `RetrySession` RPC's own response — breaking every frontend consumer regardless of how correctly Phase 4 is built. `ProtoToStatus`'s `default:` is worse: it returns `session.Creating`, so any code path that round-trips the enum (e.g. a stale client echoing the field back) would silently reopen a permanently-failed session as "Creating." — Add the three missing cases to `server/adapters/instance_adapter.go` as an explicit task in Epic 2.5, and correct ADR-001's stated verification method (it should grep for `case (session\.)?Stopped\b` / `case (sessionv1\.SessionStatus_)?SESSION_STATUS_STOPPED\b` or equivalent, not the unqualified literal) so this class of miss doesn't recur for the next enum value added after this one.

- [x] **RESOLVED (see Round 2 addendum below).** **Frontend blast-radius sweep (Epic 2.5.3) only tasks 2 of at least 7 files that branch on `SessionStatus` and will silently mishandle `PERMANENTLY_FAILED` via a `default`/fallback branch.** Confirmed by reading each file's switch/comparison: `web-app/src/lib/grouping/strategies.ts:208-219`'s `getStatusDisplayName` (named explicitly in ADR-001's own "need review" list, but never converted into a plan task) falls to `"Unknown"` — a permanently-failed session grouped by the "Status" grouping strategy shows under an "Unknown" bucket; `SessionRow.tsx:71-90`'s `getStatusDotValue` defaults unhandled statuses to `"idle"` — a permanently-failed session's status dot renders identically to a healthy idle one; `SessionDetailView.tsx:86-89`'s `isSessionTerminal` checks only `=== STOPPED`, so the Summary tab (gated on this helper) never unlocks for a permanently-failed session, and its `getStatusLabel` defaults to `"Unknown"`; `HistoryEntryCard.tsx:19-38`'s `hasLiveStatus` (`!== SessionStatus.STOPPED`) treats a permanently-failed history entry as still "live"; `WorkspacePeersPanel.tsx:36`'s `peer.status === SessionStatus.STOPPED` check means a permanently-failed peer never registers as `"gone"`. None of these five files appear anywhere in Phase 2/4's task list. — Add each to Epic 2.5.3 with the same "treat as terminal-like" rule ADR-001 already states for the two files it did cover, before Phase 4 starts (discovering these during Phase 6 QA means rework, not verification).

- [x] **RESOLVED (see Round 2 addendum below).** **The automated backoff-expiry restart path (Task 2.3.3b / Story 2.3.3) is never specified to claim the `retryInFlight` CAS guard before calling `restartForRetry`.** The domain glossary states `retryInFlight` exists to guard "the automated backoff-expiry path AND a manual Retry now RPC," and pitfalls.md §2 names the exact double-restart race this is meant to close — but Story 2.3.3's acceptance criteria and Task 2.3.3b's text ("On elapsed `NextRetryAt`, invoke `restartForRetry` and clear the timestamp") say nothing about claiming the CAS; only `RetryNow()` (Task 2.4.1a) is explicitly specified to do so, and the only concurrency test planned (Task 2.4.2a) races two calls to `RetryNow()` against each other, not the automated path against a manual one. An implementer following Task 2.3.3b literally reproduces the exact race the design exists to prevent: a manual "Retry now" and the automated tick-check restarting the same worktree concurrently. — Rewrite Task 2.3.3b's AC to require claiming `retryInFlight` via CAS before calling `restartForRetry` (deferring to the next tick on CAS failure, matching `RetryNow()`'s "return without touching state" behavior), and add a concurrency test that races the automated path's tick-check against a manual `RetryNow()` call, not just `RetryNow()` against itself.

- [x] **RESOLVED (see Round 2 addendum below).** **The `backlog:work` double-remediation risk (research/features.md "Unstated needs" #1) is left as an Unresolved Question with no code-level guard, but the risk activates under the feature's own primary use case, not an edge case.** `isOneShot()` (`session/session_driver.go:643-645`, confirmed by reading it) excludes only `backlog:triage`/`backlog:review` tags — `backlog:work` sessions are NOT excluded and are therefore eligible for the new multi-attempt policy as written. The plan's own justification for not blocking on this — "the double-remediation risk only newly appears once someone raises the global `MaxAttempts` above 1, which is a config change, not a code change" — is true but not a mitigation: raising `MaxAttempts` above 1 is the entire premise requirements.md opens with ("a failed session stays failed until manual intervention" / today's hardcoded single retry is the problem this feature exists to fix). Shipping a feature whose intended configuration change silently reintroduces a regression risk the requirements' own NFR says must not overlap with `BacklogLifecycleListener`'s independent remediation gate is not resolved by "owner: Tyler, revisit later." — Resolve before implementation: either extend `isOneShot()` to also exclude `backlog:work`-tagged sessions from driver-level retry (mirroring the existing triage/review carve-out, deferring entirely to `backlog_lifecycle.go`'s remediation gate for that session type), or add an explicit coordination primitive both mechanisms consult before acting on the same session.

## Concerns

- [x] **RESOLVED (see Round 2 addendum below).** **No task specifies what happens when `restartForRetry` itself returns an error during an automated retry (not the CAS-guard path).** Today's code (`session_driver.go:531-556`, confirmed by reading it) explicitly handles this: a failed `inst.Restart()`/`inst.Start()` falls back to `markSessionNeedsAttention("restart error: ...")`, producing a `ReviewQueue` entry rather than leaving the session in limbo. The plan's `restartForRetry` extraction (Epic 2.3.4) and its two call sites (Task 2.3.3b's automated path, Task 2.4.1a's `RetryNow()`) never re-specify this error handling — it's unstated whether a restart failure re-schedules another backoff attempt (consuming budget), jumps straight to `PermanentlyFailed`, or is silently dropped (worse than today, which at least surfaces a review-queue item). `RetrySession`'s handler (Task 3.2.2c) only maps `ErrRetryInFlight` to a connect error code, not a restart error bubbling up from `RetryNow()`. — Add an explicit AC to Story 2.3.4 stating a failed `restartForRetry` call is fed back into `evaluateSessionRetry` as a failure occurrence (consuming an attempt like any other failure reason), for both the automated and manual entry points, and specify the RPC error mapping for a restart failure surfaced through `RetrySession`.

- [x] **RESOLVED (see Round 2 addendum below).** **Worktree deletion/corruption between retry attempts (research/pitfalls.md §4) was dropped, not carried forward.** Pitfalls.md explicitly recommends "at minimum note this as a known limitation" and suggests a one-line, low-cost mitigation (mention "this is retry attempt N; if this looks like the same failure, investigate the worktree directly" in the continuation prompt) — the plan's only reference to "worktree" is one incidental mention about AC3's reuse semantics (plan.md:460); there is no task, no documented decision to defer, and no Unresolved Question entry for it, unlike the other three items pitfalls/research flagged, which all made it into the Unresolved Questions section. — Either fold pitfalls.md's suggested one-line addition into Epic 2.7 (which already edits the exact continuation-prompt code path for the failure-reason prefix), or add it as a fifth Unresolved Question with an owner, consistent with how the plan treated the other flagged risks.

- [x] **RESOLVED (see Round 2 addendum below).** **Jitter has a tested pure-function signature but no task wiring a nonzero value into the real call site.** `backoffDelay`'s `jitterFraction` parameter is added and unit-tested (Task 1.1.1b/1.1.3a), and the Unresolved Questions section recommends shipping `jitterFraction: 0.1` as a hardcoded constant (not config, confirmed absent from both `RetryPolicyConfig`'s Go struct, Task 1.2.1a, and its proto message, Task 3.1.2a) — but no task in Epic 2.2/2.3 (where `evaluateSessionRetry`/`handleDriverFailure` actually call `backoffDelay`) specifies passing a nonzero constant instead of `0`. Since jitter's entire stated purpose (pitfalls.md §3) is preventing a synchronized retry storm after a shared-cause failure (e.g. a service restart), an implementation that leaves the real call site at `jitterFraction: 0` — the value used throughout every specified test case — would compile, pass every AC as written, and ship without the storm mitigation the plan claims credit for. — Add an explicit task specifying a named constant (e.g. `defaultJitterFraction = 0.1`) at the production call site, with a test asserting the computed delay actually varies run-to-run (not just that the pure function's bounds are correct in isolation).

## Minors

- Task 2.5.3b ("Verify `SessionActionsOverflow`'s `isStopped`/`isRunning` booleans handle `PermanentlyFailed` correctly") is phrased as a check rather than a concrete change, and unlike most other frontend tasks in the plan doesn't cite the actual boolean-derivation line numbers — risk of becoming a rubber-stamp "looks fine" pass instead of a real fix if the booleans do need updating.
- ADR-001's "3 exhaustive Go switch statements... confirmed via `grep -rn \"case Stopped:\" session/ server/`" reads as an exhaustive count but is only a same-package count (see Blocker 1) — worth rewording once the adapter fix lands so a future reader doesn't re-trust "3" as the true total for the next status value added after this one.
- `evaluateSessionRetry`'s adoption of the `evaluateRemediation` pure-function pattern (mirroring `session/backlog_remediation.go`) is proportionate, not over-engineered — it replicates an already-proven shape in this codebase for a structurally identical problem (attempt budget + backoff + eligibility + restart-grace) and is directly unit-testable. No action needed; noted only because scope was explicitly in review.
- No new dependencies are introduced, and `cenkalti/backoff/v5` (already an indirect dependency) was explicitly considered and rejected with a specific technical reason (it wraps a synchronous call-retry function, not a delay-computation primitive) rather than reflexively hand-rolling — no technology-bet concern.
