# Adversarial Review: flaky-hook-url-tests
**Date**: 2026-08-01
**Verdict**: CONCERNS

## Blockers
_(none — the plan is small, decoupled, reversible, and its core mechanism claims about `-p 1` and coverage semantics hold up under scrutiny)_

## Concerns

- [ ] **No task actually executes the before/after stress-repro the requirements' own Constraints demand.** requirements.md's Constraints section requires the fix be validated via "a stress-run (`go test -race -count=N`) that demonstrates the marginal timeout and then demonstrates it's resolved" — i.e. capture a *failing* run pre-fix and a *passing* run post-fix. Task 3.1.1 only adds a permanent code comment documenting the repro command for future flake hunts; no task in Epic 1, 2, or 3 actually runs it against the unpatched code to record a baseline failure rate and against the patched code to confirm resolution. Task 2.1.2 measures wall-clock cost, not flake-rate improvement. — Recommendation: add an explicit task (or confirm it is Phase 4/`validation.md`'s job before implementation starts) that runs the documented repro command (and its artificial-load variant) against both baseline and patched code and records pass/fail counts, per the requirements' own verification bar.

- [ ] **ADR-001 rejects Option C without engaging `go tool covdata`, which its own research doc names.** stack.md (§2) explicitly says coverage-profile merging is possible "via `go tool covdata` or simple file concatenation," but ADR-001's rejection of the isolated-invocation option only addresses "no `gocovmerge` dependency exists" and "naive concatenation is fragile" — it never names or dismisses `go tool covdata`, which ships with the Go toolchain and is not a "new external dependency" in the sense requirements.md's constraint is worried about. In practice `go tool covdata` operates on `GOCOVERDIR`-based raw counter data from `-cover`-instrumented binaries, not on classic `-coverprofile` text output — so adopting it would mean restructuring the whole test invocation's coverage mechanism, a legitimately bigger change than the ADR implies by omission. That's a defensible reason to still reject it, but the ADR doesn't make that argument; it just doesn't mention the tool. — Recommendation: add one sentence to ADR-001 naming `go tool covdata` and stating the `GOCOVERDIR`-vs-`-coverprofile` format mismatch as the actual reason it doesn't cleanly apply here, so a future reader doesn't reasonably ask "why not just use the toolchain merge tool" and find the ADR silent on it. (Note: this doesn't change the final decision — three other independent reasons for rejecting Option C in ADR-001 stand on their own.)

- [ ] **The "3-for-3 precedent" central to rejecting CI-topology changes isn't verifiable from this clone's git history.** build-vs-buy.md and ADR-001 both lean heavily (cited 4 times total) on "this exact test pair has been patched three separate times... all via wait-tuning, never CI-topology changes" as the strongest evidence for choosing tuning over isolation. Checking `git log --follow -- server/server_integration_test.go` in this repo shows only 6 commits touching the file, and the one that introduced `waitForLiveInstance`, `waitForPermissionRequestHookCommand`, the current 30s-call-site/60s-comment mismatch, *and* the `testSocketOnce` documentation all landed together in a single squashed `chore: sync upstream → personal fork` commit (`6c195bcaf`) — not as three separately-titled fix commits. This may just be an artifact of fork-sync squashing rather than a false claim, but as written the research treats it as confirmed empirical precedent without being able to point at three distinct commits — and features.md's own §3 recommends checking `git log -p`/`git blame` on exactly this point "before reaching for a heavier isolation-based fix," a check whose outcome isn't shown anywhere in the research docs. — Recommendation: either soften the "3-for-3" framing to "the file's own comments describe three distinct historical fixes" (comment-sourced, not commit-log-verified), or note explicitly that upstream's unsquashed history was checked and confirms it.

- [ ] **Task 1.2.2/1.2.3 touch helpers explicitly stated as "not implicated in the reported flakiness."** Converting `waitForLiveInstance` and `waitForResolvedAddr` to `require.Eventually` is broader than the literal ask ("fix these two flaky tests"), and requirements.md's Out-of-Scope explicitly excludes "fixing unrelated flakiness... file separate items." Verified via `grep` that all four wait helpers (`waitForResolvedAddr`, `waitForLiveInstance`, `waitForPermissionRequestHookCommand`, `waitForTmuxTeardown`) are unexported and called only from the two named test functions in this same file — so the blast radius is fully contained and this is a low-risk, mechanical, zero-behavior-change refactor, not a real risk of breaking other tests. Still worth flagging: it's additional reviewed surface for zero measured benefit toward the stated bug. — Recommendation: either drop Tasks 1.2.2/1.2.3/1.2.4 to keep the diff minimal to the actual bug (stale 30s→60s + Task 1.2.1's conversion of the implicated helper), or keep them but note in the PR description that they're confirmed zero-risk consistency-only changes co-located in the same two tests, so a reviewer doesn't have to independently re-verify the blast radius.

## Minors
- `require.Eventually` spawns an extra goroutine + ticker per call versus the hand-rolled `for`/`time.Sleep` loop it replaces; under `-race`, additional goroutines add (small) TSan bookkeeping overhead — mildly ironic given the plan's core diagnosis is CPU contention under `-race`, though negligible next to a real tmux fork/exec. Worth a one-line acknowledgment in the plan, not a blocker.
- Minor line-reference drift: requirements.md cites `installFakeClaudeBinary` at "lines 36-51" while plan.md's glossary cites "lines 36-60" — both defensible (doc comment vs. whole function), but worth aligning if these docs are cross-referenced later.

## Findings checked and dismissed (no action needed)
- **CI job-level timeout risk from `-p 1`**: confirmed via `grep -n timeout-minutes .github/workflows/build.yml` that the `test` job has no `timeout-minutes` set (GitHub's 360-minute default applies), consistent with the plan's own Risk Control claim — not a real risk given the low-single-digit-minutes delta expected.
- **`-p 1` making `session/...`/`config/...` tests "newly flaky"**: no plausible mechanism found — serializing package binaries gives whichever package is running full access to all 4 vCPUs instead of sharing with up to 3 others, which should reduce (not introduce) contention-driven flakiness for those packages too. `-p 1` also doesn't affect within-package `t.Parallel()` subtest scheduling, only cross-package binary concurrency, so it's orthogonal to any existing within-package contention.
- **Cross-job contention (`prepare`/`build`/`install-check` running alongside `test`)**: these are separate GitHub Actions jobs, each on its own runner VM — no shared CPU across jobs, so this isn't a contributing factor regardless of `-p 1`.
