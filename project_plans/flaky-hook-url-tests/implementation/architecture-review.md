## Concerns

- [ ] **ADR-001, "Why not option 3" section** — The ADR's rejection of a merged-coverage second invocation only weighs `gocovmerge` (external dep, correctly rejected) and naive text-concatenation of two `mode: atomic` profiles (correctly flagged as fragile), but never considers `go tool covdata merge` + `go tool covdata textfmt`, which ships with the Go toolchain itself (not a new external dependency) and is *already in production use in this exact file* — `.github/workflows/build.yml:244-254` ("Integration coverage (advisory)" step) builds with `go build -cover`, collects counters via `GOCOVERDIR=/tmp/covdata`, and converts with `go tool covdata textfmt -i=/tmp/covdata -o integration.out`. Merging two `-race` invocations' coverage via `GOCOVERDIR` + `covdata merge`/`textfmt` (instead of `-coverprofile`) is a real, dependency-free path the ADR doesn't name or reject on its own terms — it only refutes the two options it happened to consider. This doesn't necessarily flip the final decision (ADR reasons 2–4 — job-setup duplication, the 3-for-3 wait-tuning precedent, and the shared-tmux-socket problem persisting regardless — stand independently of the merge-tool question), but the ADR's stated rigor ("no new external dependencies," "correctness is unverified and risky") is incomplete on this specific point and should not claim to have foreclosed option 3 on dependency/tooling grounds without addressing the tool the repo already uses next door.
  - **Remediation**: Add a paragraph to ADR-001's "Why not option 3" section explicitly naming `go tool covdata merge`/`textfmt` as a considered-and-rejected sub-option, rejected on reasons 2–4 (job-setup duplication, precedent, doesn't fix the shared-socket problem) rather than on the false premise that no built-in merge path exists.

- [ ] **Task 1.2.1 (`waitForPermissionRequestHookCommand` → `require.Eventually`)** — Verified via `testify@v1.11.1`'s actual source (`assert/assertions.go:1988-2018`) that `assert.Eventually`'s condition callback runs on a **background goroutine** (`go checkCond()`), not synchronously in the caller — a detail neither the plan nor ADR mentions. The literal approach described ("capture the resolved `hookCmd` string in a closure variable," assign only inside the success branch, `return hookCmd` after `require.Eventually` returns) is race-safe as written: the write to `hookCmd` happens-before the `ch <- condition()` send, which happens-before the corresponding receive completes, which happens-before the caller's `return hookCmd` — a valid Go memory-model chain, so `-race` will not flag it. However, the task description doesn't spell out the one property that makes this safe — *assign to the outer variable only in the success branch, never on a failed/partial-parse attempt* — so an implementer translating the "preserve the exact same JSON-parsing logic" instruction could plausibly write a version that unconditionally reassigns `hookCmd` (e.g. to `""` or a partially-parsed value) on every failed tick, which is still race-safe (same happens-before chain) but reintroduces exactly the "stale/partial value" ambiguity the review was asked to check for, and isn't caught by the plan's Given/When/Then (which only tests the pure-timeout case, not "several failed parses, one of which partially succeeds, before the final success").
  - **Remediation**: Add one sentence to Task 1.2.1: "The closure must assign to `hookCmd` only in the `h.Type == "command" && h.Command != ""` success branch, immediately before `return true`; every other return path (`false`) must leave `hookCmd` untouched." Add a Given/When/Then covering: file exists with `hooks.PermissionRequest` present but no `type=="command"` entry on the first 2 polls, then a valid entry appears on poll 3 — assert the returned `hookCmd` is exactly the poll-3 value, not `""` or a stale intermediate.

- [ ] **Task 2.1.2 (local wall-clock measurement methodology)** — "Run the gating command locally twice — once as-is, once with `-p 1`" is a single-sample-per-condition A/B comparison, which is measurement-noisy for a real go/no-go decision: (a) if the `-p 1` variant is run second, it benefits from a warm Go build cache from the first run (packages already compiled), which would make `-p 1`'s reported cost look artificially *smaller* than the true CI-cold-cache delta; (b) a single run per condition can't distinguish a real effect from ordinary local scheduling/thermal noise. Plan.md's own "Unresolved Questions" section already partially self-mitigates this by saying the local number isn't authoritative and must be corroborated by an actual CI run — but Task 2.1.2 itself, as the thing that produces the number that goes into the PR description, should not rely on a methodology this noisy even for a rough estimate.
  - **Remediation**: Run each variant ≥3 times, alternating order (e.g. before/after/before/after/before/after) to cancel out cache-warming and thermal drift, and report the median delta rather than a single before/after diff. Note in `validation.md` that this is still a local approximation pending the CI-run corroboration already flagged as a follow-up.

## Nitpicks
- Task 1.2.1's phrase "matching the current `t.Fatalf` semantics" for `t.FailNow()` is confirmed accurate against `testify@v1.11.1` source (`require.go:408-416`, `Eventually` calls `t.FailNow()` on timeout) — no correction needed, noted here only because it was a specific claim this review was asked to verify and it holds.
- Task 1.2.4's decision to use `testutil/wait.WaitForCondition` instead of `require.Eventually` for `waitForTmuxTeardown` is correct and well-justified: `WaitForCondition` (`testutil/wait/wait.go:53-75`) runs its condition synchronously in the calling goroutine (no background goroutine, unlike `assert.Eventually`), imports only `context`/`fmt`/`time` (confirmed, no cycle risk with `server`/`session`), and never calls `t.FailNow()` — it returns a plain `error` for the caller to `t.Logf`. This is the right primitive for the deliberately-non-fatal post-cleanup case.
- Plan's claim of touching zero production code is verified: Epic 1/2/3 task file lists are exhaustively `server/server_integration_test.go` and `.github/workflows/build.yml` only; no task references `approval_handler.go`, `session_service.go`, or `session/tmux/tmux.go`.
- The `-p 1` technical claim (identical `-race` scope, identical `-coverprofile`/`-covermode=atomic` semantics) holds up: `-p` controls only *cross-package* test-binary parallelism, not intra-binary `GOMAXPROCS`/race-detector interleaving scope, and `coverage.out` is still produced by one unmodified `-coverprofile` invocation — no subtlety found that would invalidate this claim.
