**Verdict**: BLOCKED

## Blockers

- [ ] **ADR-001 does not deliver AC8 and drops mitigations its own research called for.** AC8 says probing is "only allowed for the command the user is configuring"; ADR-001 accepts any command from any caller on `:8543`, which has no auth (`research/pitfalls.md` section 1; `config/config.go:848` default `localhost:8543`, but `listen_address` is user-configurable, `config.go:212-214`). The ADR's justification ("same caller can already create sessions running arbitrary programs") is not evidenced in the ADR. It also drops three mitigations pitfalls section 1 lists: (a) reject relative paths containing a slash (plan task 1.1.1b lists `./x` as a test input but never says the outcome), (b) audit logging (ADR-002 explicitly gives it up), (c) any DNS-rebinding defence (Host/Origin check; the repo only has CORS allowlisting, `server/server.go:1557`, which does not stop rebinding). Recommendation, all cheap and additive to the hardened runner: (1) `Resolve` must accept only a bare name (PATH lookup) or an absolute path, never a relative path; require regular file, executable, not group/world-writable, and reject `exec.ErrDot`; (2) in the handler, reject requests whose `Host` is not loopback/known hostname, and refuse the RPC entirely when the listener is bound to a non-loopback address without auth; (3) keep the RPC POST-only (do not mark it `NO_SIDE_EFFECTS`/idempotent, which would allow Connect GET and a simple cross-site request); (4) restate AC8 in the plan honestly as "server hardening", and record Tyler's sign-off (plan Unresolved Question 2 says it blocks Story 1.2.2, and ADR-001 status is "reviewer sign-off requested").
- [ ] **Runner tests as specified cannot run: sanitized env vs env-gated helper process (AC3, AC8 proofs).** Task 1.1.2c follows `executor/safeexec/safeexec_sigkill_helper_test.go`, which selects helper mode via an environment variable (`SAFEEXEC_SIGKILL_HELPER`, line 16). But `Run` passes exactly `--help` and an allowlist env (task 1.1.2b), so the re-exec'd test binary never sees the gating variable and would just print Go test usage for `--help`. The `bigout`/`hang`/`printenv` modes are unreachable, and the "env has no `GITHUB_TOKEN`" assertion cannot be tested through the real runner. Recommendation: add an unexported test-only option to `Run`/`Limits` (extra env and args, honored only from `_test.go`-constructed options, never from the RPC path) or generate small compiled/scripted fixtures with a fixed `--help` behavior; state which in 1.1.2c and re-check that AC8's "args are exactly `--help`" is still asserted on the production path (fake `run` in the prober test does this; the runner-level assertion needs the same seam).
- [ ] **PATH mismatch makes the headline "not found" result wrong for the owner's real setup; must be decided before implementation, not defaulted.** The plan defers this to the implementer with a default ("server PATH"). Evidence it is not a corner case: `config/config.go:1283-1297` discovers programs by running the user's shell with `source ~/.zshrc; which <cand>`, i.e. the codebase itself already knows the server process PATH is not the user's shell PATH; and this machine's `claude`, `aider`, `uv`, `agy`, `git` live in `~/.local/bin`, Linuxbrew, or shell aliases. Under systemd/launchd the server PATH commonly lacks those. `exec.LookPath` also cannot see aliases/functions. The result is a false "Not found" badge for the very programs the feature targets, contradicting AC2/AC5's value. Recommendation: pick now, in the plan: either resolve via the same mechanism session launch uses (find out what `session` startup actually does; UNVERIFIED here) or build the probe PATH as server PATH plus the user's login-shell PATH (captured once, cached), and word "not found" as "not found on the server's PATH" only as the fallback. Add a test with a PATH-only-in-shell fixture.

## Concerns

- [ ] **Singleflight leader's context cancels every follower.** Plan 1.1.4a/b keys `singleflight` by cache key and derives the run context from `ctx`. The UI aborts requests on stale probes (task 2.1.1a `AbortController`), so a client abort cancels the shared run and all followers get `TIMEOUT`/`ERROR` (and `ERROR`/`TIMEOUT` is cached 30s). Use `context.WithoutCancel(ctx)` plus the probe timeout for the shared run, and never cache a result produced by cancellation; set `TimedOut` only on `DeadlineExceeded` (plan does) and treat `Canceled` as neither.
- [ ] **Process and pipe handling gaps in the runner (ADR-002/1.1.2b).** (1) `cmd.Cancel` fires only when the context ends; on a normal exit any backgrounded/daemonized grandchild in the group survives and holds the pipe until `WaitDelay` (2s, `safeexec/safeexec.go:26`). Kill the group (`syscall.Kill(-pid, SIGKILL)`, ignoring ESRCH) after `Wait` returns, every time. (2) Worst-case wall time is therefore 3s + 2s `WaitDelay` if a grandchild called `setsid`, exceeding AC3's "hard timeout 3s"; document or set `cmd.WaitDelay` lower after override. (3) Overflow does not stop the child: an infinite writer (`yes`) runs the full 3s burning CPU; kill on cap-exceeded instead of draining to timeout. (4) `Setpgid` without `Setsid` leaves the child on the server's controlling terminal when run from a shell; a `--help` that opens `/dev/tty` can write to it or get SIGTTIN (`safeexec_pg.go:29-31` warns about this). Override `SysProcAttr` with `Setsid: true` for the probe. (5) Passing `cmd.Stdout == cmd.Stderr` shares one writer (correct, and makes the mutex in `capWriter` unnecessary); say so to avoid a needless lock.
- [ ] **`git --help` and startup side effects.** Plan leaves "does `git --help` spawn `man`" unresolved (Unresolved Question 3). With `PAGER=cat` alone `git --help` runs `man git`; `man` inherits the group and env. This is the same class of risk as any probed binary: several CLIs in scope (claude, aider, gemini) may write to `$HOME` (config, update checks, telemetry) on any invocation, and the plan keeps `HOME` in the allowlist. UNVERIFIED; capture fixtures (task 1.1.3a) under `strace`/a temp `HOME` once and record whether `--help` mutates state before deciding whether to point `HOME` at the temp dir as well (then `~` expansion must still use the real home for lookup only).
- [ ] **Wrapper commands produce false unknown-flag warnings.** Flagged Choice 7 probes the first token only, and `web-app/src/lib/constants/programs.ts:16` ships a built-in option whose command begins `env -u CLAUDE_CODE_USE_BEDROCK ANTHROPIC_BASE_URL=... claude`. The badge says "Checked: env", but tasks 4.1.2a/b still validate `cli_flags` against `env`'s flags, so any claude flag shows "not listed in `env --help`". Suppress validation and autocomplete when the checked token is a known wrapper (`env`, `sudo`, `npx`, `uv`, `nice`, `time`, `exec`), or skip past `env` options to the wrapped program. Add a test using the built-in Proxy entry.
- [ ] **`FlagCombobox` swap-in loses focus mid-typing.** Task 3.1.2a "returns a plain input when `flags` is empty" and 3.1.3a replaces the input when the probe resolves. A user who tabs from the command field to `prog-flags-input` and starts typing while the probe is in flight will see the element replaced (focus and caret lost) when the result arrives. Always render the same `<input>`; toggle only the ARIA attributes and the listbox.
- [ ] **Interactive child inside `role="option"` (task 4.2.2a).** A `FlagInfoButton` inside an option row is invalid ARIA (options have presentational children) and axe's `nested-interactive` fires; CI blocks on Axe WCAG AA violations (CLAUDE.md, "UX analysis CI"). The plan leaves the design open ("reachable via Right-arrow, or place inline for the active option"). Decide now: show the active option's description inline in the listbox (no nested button) and put the tap-to-expand disclosure on the warning list and a separate "Available flags" disclosure, or make the info button a sibling of the option, not a child.
- [ ] **AC9's proof is not achievable in jest.** AC9's GWT says "viewport 375x667 with touch emulation"; jsdom has neither. Only the Playwright test (5.1b) can prove it, and that depends on the unresolved 4.2.2a layout. State AC9 as "e2e at 375px with `hasTouch` context" and make the jest test explicitly a unit-level substitute (no `mouseover`), and make 5.1b block AC9's sign-off.
- [ ] **AC4 alias representation is undefined.** The GWT expects `--allowedTools` "(alias `--allowed-tools`)" but `FlagInfo` (task 1.2.1a) has only `name` and `short`. Parser task 1.1.3b says `--[no-]long` "emits both" and "comma aliases" without saying whether long-long aliases become separate entries. `validateFlags`/autocomplete depend on this. Add `repeated string aliases = 5` (additive) or specify separate entries with identical descriptions, and test against the claude fixture.
- [ ] **AC7 is only conditionally met.** Task 4.1.2b validates `extraFlags` "only if already plumbed... otherwise validate `cliFlags` alone and note the gap". Verify before implementation whether the panel receives alias `extraFlags` (`Omnibar.tsx:1485,1507-1508`); if not, either add the prop or update the AC7 interpretation in `requirements.md`; an untracked "note the gap" is how AC gaps ship.
- [ ] **Scope drift.** Not asked for by requirements.md: edit-distance "Did you mean" suggestions (4.2.2), a Check button (2.2.1; defensible for AC9 but not required), per-command in-memory memo plus server cache TTL tiers (10 min/30 s/128 entries), `truncated` and five-value `ProbeStatus` in the proto, `docs/reference/program-probe.md` plus a `CLAUDE.md` index row, and a new e2e spec with its page object and fixture. Cut "Did you mean" and defer the doc/e2e, or explicitly bless them; each adds jscpd surface against a 0.12% threshold whose margin the repo memory says is already 0.10%.
- [ ] **`validation.md` contradicts the plan.** `implementation/validation.md` (committed earlier) plans a "fake `CommandExecutor`" (rejected in Pattern Decisions) and a "sleeping script binary" (rejected by pitfalls section 9 and task 1.1.2c "No `sleep` scripts"). Regenerate it from the plan after fixing the blockers so `sdd:4-validate` does not check the wrong tests.

### Blocker 1 (AC8 on :8543): target rules and guard design are sound, but the wiring point is wrong

- **NEW BLOCKER: one shared mux serves both listeners, so a static `ProbeGuardConfig.Authenticated` cannot be right.** Task 1.2.3a wires `WrapProbeGuard` "around `handler` at `:414`", i.e. at route registration. That mux is reused by `Start()` (`server.go:1372`, no auth in practice: `main.go` never calls `SetupAuth`) and by `StartRemote()` (`server.go:1642-1652`, `middleware.Auth`, Host is the LAN/Tailscale hostname, this is the `:8444` listener the mobile app uses). At registration time `authMiddleware` is not yet set (`SetupAuth` comes later, `server.go:1269`), so the guard is built with `Authenticated=false`: then every `:8444` probe with `Host: onyx.staplerhome.internal` gets 403 (feature dead remotely). If instead built `Authenticated=true`, `:8543` is unguarded and the DNS-rebinding hole returns. Also `srv.SetOrigins` runs after `NewServerWithDeps` (`main.go:438`), so `AllowedOrigins` captured at wiring time is empty. Fix (plan text only): apply the guard per listener chain, in `Start()` around `inner` when `s.authMiddleware == nil` and never in `StartRemote()`; read origins lazily (`s.GetOrigins()` at request time) and also allow `SetHostnames` names if the owner wants LAN access on `:8543`; match the full path `/api/session.v1.SessionService/ProbeProgram` (pre-`StripPrefix` it would be `/session.v1...`, so do not wrap the inner `handler`). Add a test that `StartRemote`'s chain does not contain the guard and that `Start()`'s does.
- Resolved parts (VERIFIED by reading): bare-name/absolute-only, regular/executable/not-world-writable, `ErrDot`, POST-only (no `NO_SIDE_EFFECTS`), Host/Origin loopback check does fit Connect POST (browsers send `Origin` on same-origin POST; Host `localhost:8543` parses with `net.SplitHostPort`, bracketed `[::1]` must be handled, already in the test table), audit line, honest AC8 wording, sign-off recorded PENDING.
- Concern: `listen_address=0.0.0.0:8543` users get the RPC refused entirely (403). Correct security-wise, but the UI must show "Couldn't check" for a Connect `permission_denied`, not "not found"; add one hook test (plan Task 2.1.1b) and one sentence in the copy.

### Blocker 2 (runner tests): RESOLVED

`runWith(runSpec)` with `CLIHELP_TEST_`-prefixed `extraEnv` makes the re-exec helper reachable through the sanitized env (same convention as `safeexec_sigkill_helper_test.go`); production `Run` is `runWith(helpSpec(...))` so `args==["--help"]` is asserted on the real path; `orphan` mode works because Go's `WaitDelay` timer starts at process exit (200ms), then the post-`Wait` group kill runs; `Setsid` gives pgid==pid so `Kill(-pid)` is valid; the smoke test (Go test binary answers `--help` with `-test.run` usage) is plausible. Residual minor: the AC8 `printenv` proof through `runWith` is vacuous unless the parent environ is poisoned (`runWith` calls `os.Environ()`); put the parent environ in `runSpec` (or a `parentEnv` field) so the leak assertion runs through the real runner, not only `probeEnv`.

### Blocker 3 (PATH): RESOLVED, with concerns

Login-shell PATH mirrors the existing mechanism (`config.go:1213-1221, 1288-1296`), script is constant (no user text), derived lazily via `sync.Once` (not at startup, so no startup delay), fallback to server PATH on failure, alias-only -> NOT_FOUND with honest copy. No new blocker, but:
- `deriveLoginPath` uses `safeexec.CommandContext` (no process group, no `Setsid`): a `.zshrc` that spawns background helpers (nvm, ssh-agent, direnv) can leave grandchildren holding the pipe until `WaitDelay` (2s) and survive the timeout kill. Use the same `Setsid`+group-kill shape as the runner (reuse `runWith` machinery) and stdin `/dev/null`.
- `sync.Once` caches a nil result from a transient 2s timeout for the process lifetime; prefer retry-after-N-minutes or cache only success. First probe pays up to 2s inside a request; kick off the derivation in a goroutine from `NewDefaultsService()` instead.
- `source ~/.bashrc` non-interactively often returns early (`[ -z "$PS1" ] && return` on Ubuntu), and `$SHELL` may be unset/`/bin/sh` under systemd, giving `/bin/bash` fallback for a zsh user; both silently degrade to server PATH. State this in the Not-found copy caveat (already partly there) and cover with one test using the stub shell.

### New issues from the fixes checked and found OK
- Setsid vs `CommandContextPG`'s `Setpgid`: overriding `SysProcAttr` wholesale drops `Setpgid` and the Linux `Pdeathsig` helper's preserved fields (`safeexec_pdeathsig_linux.go:21`); harmless here, but note the runner loses parent-death cleanup: if the server is killed mid-probe the child runs to its `--help` end. Accept.
- Host-header breakage for LAN/Tailscale via `:8543`: only affects unauthenticated-listener use by non-loopback hosts, which the plan refuses by design; the `:8444` path is correct once the wiring fix above is applied.

### Blocker verification (VERIFIED against the repo, 2026-09-21)

- **(a) Only the unauthenticated `:8543` chain.** `Start()` builds `inner := http.Handler(s)` then adds `authMiddleware` if non-nil (`server/server.go:1374-1377`); `StartRemote()` builds its own `inner` from the `authMW` argument (`:1643-1646`) and is a separate function, so a guard inserted in `Start()` cannot reach it. `SetupAuth` (`:1269`) has no non-test caller, so `authMiddleware == nil` in production `:8543`; the plan's `if s.authMiddleware == nil` condition therefore installs the guard exactly there. Correct.
- **(b) Path match.** The guard wraps `s`, whose `ServeHTTP` (`:77-83`) passes the unmodified request to `s.mux`; `StripPrefix("/api", handler)` is applied inside the mux (`:427`), after the guard. So `r.URL.Path` at the guard is the full `/api/session.v1.SessionService/ProbeProgram`, matching the plan's `probeProcedurePath`. The only other exact-path mux entries for this service are the two Watch* WS-bridge paths (`:421-424`), which do not expose ProbeProgram. Percent-encoded variants decode into `r.URL.Path`, so they still hit the guard; unclean paths are redirected by `ServeMux`, not served.
- **(c) localhost/127.0.0.1 and LAN/Tailscale.** Default bind is `localhost:8543` (`main.go:303-306`), so browsers send `Host: localhost:8543` or `127.0.0.1:8543` and `Origin: http://localhost:8543` (`main.go:438-439` `SetOrigins`), which pass. `CORSWithOrigins` answers `OPTIONS` with 204 before calling `next` (`server/middleware/cors.go:33-36`), and the guard sits inside it, so its non-POST -> 405 rule cannot break preflight. `:8444` is untouched, so the mobile app (`Host: onyx.staplerhome.internal:8444`, passkey auth) is unaffected. Lazy `AllowedOrigins`/`AllowedHosts` closures fix the stale-capture problem (`SetHostnames`/`SetOrigins` run after `NewServerWithDeps`, `main.go:435-439`).
- **(d) Testable without a port.** Factoring `localChain()` out of `Start()` allows `httptest.NewRecorder` tests; the guard itself is a plain `func(http.Handler) http.Handler`. Task 1.2.3c covers both listeners and the late-`SetOrigins` case.

### Remaining concerns (non-blocking)

1. **`StartRemote` chain has no named helper.** Task 1.2.3a only factors `localChain()`; Task 1.2.3c test (2) says "same helper style" for `StartRemote`. Without a `remoteChain(authMW)` helper, test (2) either duplicates the chain in the test (proves nothing about the real code) or must bind a port. Specify the extraction of both chains, or assert the property through the exported behavior of a shared `buildChain(inner, name)`.
2. **`LoopbackBound` must treat `localhost` as loopback.** `s.httpServer.Addr` is the raw `cfg.ListenAddress` (`server.go:113`), default `"localhost:8543"`, so the check must accept the hostname `localhost` as well as `127.0.0.0/8` and `::1` (mirror `main.go:317-318`, which compares host strings). Unresolved Q #7 (accessor) is still open; add a table test for `localhost:8543`, `127.0.0.1:8543`, `[::1]:8543`, `0.0.0.0:8543`, `:8543`.
3. **Non-loopback bind means the feature is off, by design.** Users who bind `:8543` to `0.0.0.0` without auth get a permanent 403 (plan maps this to "Couldn't check" in the UI, good). State it in ADR-001 consequences so it is not later mistaken for a bug.
4. **Loopback `Origin` on any port passes.** A malicious page served from another local port is still stopped by the CORS preflight failing (JSON content type) but not by the guard. Acceptable; consider requiring `Origin` equal to the request's own Host when Origin is loopback, at negligible cost.
5. **`s.origins` is a plain field** (`server.go:1558-1564`), so a lazy read from request goroutines is race-free only because `SetOrigins` runs before `Start()`. Say so in the closure's comment, or the race detector will flag any test that calls `SetOrigins` concurrently with requests.
6. **IPv6 Host parsing:** use `net.SplitHostPort` and strip brackets, fall back to the raw string when no port; the plan lists an IPv6 test, keep it.
