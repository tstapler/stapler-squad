## Blockers
- [ ] Story 1.2.3 / 1.4.1 (focus ownership; ghostty and non-gesture paths) — the plan routes only `handle.focus` and `useTerminalGestures` to `controller.focus()`. But (a) `useTerminalGestures` is used only by `XtermTerminal.tsx` (grep: no other renderer), and `GhosttyTerminal.tsx` header says touch gestures are not ported, so on ghostty, the renderer this bug is about, a tap focuses ghostty's own contenteditable container and nothing ever calls `controller.focus()` within a user gesture; the soft keyboard stays on ghostty's input and the fix does not reach the primary symptom; (b) `TerminalOutput.tsx:1518` calls `xtermRef.current.terminal?.focus()` on every visibility change (bypasses the handle), and `useTerminalGestures.ts:640,660` call `t.focus()` on the xterm `Terminal`, not the handle; with the helper textarea set to `inputmode=none, tabindex=-1` (Task 1.4.1b) those calls focus an element that opens no keyboard. — Remediation: add an explicit task that defines a single "focus the terminal" entry used by tap handlers on both renderers: (1) a pointerup/click handler on the renderer container (layer-owned, installed by `attachMobileInput` or `useMobileInput`) that calls `controller.focus()` synchronously for touch pointers, so ghostty needs no gesture hook; (2) replace `terminal?.focus()` at `TerminalOutput.tsx:1518` and the pool dock focus with `handle.focus()`; (3) change `useTerminalGestures` to receive a `focusTerminal` callback instead of calling `t.focus()`. Add an AC: "Given ghostty with the layer active, When a touch tap lands on the canvas, Then `document.activeElement` is `mobile-input-textarea`" (jsdom plus the Story 5.1.1 spec).
- [ ] Story 3.1.4 with ADR-004 / Story 3.1.3 (queue vs diff base) — 3.1.4 resets `sent` to empty on any non-`sent` result, including `queued`. A queued edit WILL be replayed, so resetting loses the base: `Composing{sent:"hel"}`, sink returns `queued` for `"hel"`, region becomes `"help"`, layer emits `{backspaces:0, insert:"help"}`; on reconnect the queue flushes `"hel"` + `"help"` = `"helhelp"`. Reset is only correct for `dropped`. The AC and the queue's own acceptance of `\x7f` (3.1.3 allows `\r`/`\x7f`) contradict the reset rule. — Remediation: split the behavior by result: `sent` and `queued` keep the base (the queue stores atomic edits including their DELs in order); `dropped` resets it. Add the AC "Given `Composing{sent:"hel"}` and sink returns `queued`, When region becomes `"help"`, Then emit `{backspaces:1, insert:"p"}` and the flushed queue content equals `"help"` after applying to the model terminal", plus a replay-harness case with a disconnect/reconnect in the middle.

## Concerns
- [ ] Story 1.4.1c / ADR-006 (ghostty mount point) — ADR-006 and the glossary say the textarea lives "outside ghostty's input subtree", but `attachMobileInput(container, ...)` receives the container that `GhosttyTerminal` passes to `term.open(container)` (`GhosttyTerminal.tsx:183` is the container div), and ghostty-web `:2330` registers the blanket `beforeinput` `preventDefault` and the `:851` keydown handler on that same element. A textarea appended inside it will have its `beforeinput` bubble into ghostty's handler (cancelable `insertText` will be prevented, so `textarea.value` stops updating and `value`-based reducer fields go stale) and its keydowns reach ghostty's InputHandler (double-send). "Stop propagation at layer root" is a one-line hint in a task title, not an AC. — Mount the textarea in a wrapper that is a sibling of the open() element, or stop propagation of all listed event types on the textarea itself in the capture-phase-safe way; add an AC "Given the layer mounted for ghostty, When `insertText` is dispatched on the textarea, Then ghostty's container listeners are not invoked and `event.defaultPrevented` is false", and have Story 0.1.1 record the real listener set in 0.4.0.
- [ ] Story 2.1.2 (`accepted` label) — the helper is called at `connectrpc_websocket.go:3131` before `if writer != nil`, so `accepted=false` can only mean read-only attach. The permission denials (`!instance.Permissions.CanSendCommand` inside both `onInput` closures, e.g. `:1659`) happen after the call and would be counted `accepted=true`. ADR-005 and research/architecture.md claim permission denials are counted `accepted=false`. — Either call `recordTerminalInput` with `accepted` resolved after the permission check (thread the result back from the closures, still one helper), or narrow the label's documented meaning to "writer attached" and add a separate `reason` enum (`read_only|denied|ok`); add the permission-denied case to the Story 2.1.2 ACs (only read-only is covered today).
- [ ] Story 3.1.1 / 3.1.4a (SendResult plumbing) — `sendInput` returns void and its only consumers are `deliverTerminalData` (`TerminalOutput.tsx:1049`) and `handleTerminalData` (`:1069`, which also has read-only handling, page-key estimate invalidation, and returns void), wired to the renderer through `usePooledTerminalCallbacks(... onData: handleTerminalData ...)` (`:1426`). For the layer to see `dropped`/`queued`, `SendResult` must flow through all of `sendInput` -> `deliverTerminalData` -> `handleTerminalData` -> pool callback -> renderer `onDataRef`. Task 3.1.4a lists only `attachMobileInput.ts`, `useMobileInput.ts`, `composition.ts`, and the Tech Debt row says `TerminalOutput` gets "no new logic". Also `readOnlyRef` early return in `sendInput` (`:242`) must return a result (`read_only`). — Add `TerminalOutput.tsx` and the pool callback type to 3.1.4a's files, define the widened `onData: (bytes: string) => SendResult | void` type once in the seam types, and add a unit test that a `dropped` result at `sendInput` is observed by the layer through the real `handleTerminalData` chain.
- [ ] Tech Debt Disposition, `TerminalOutput.tsx` (2,456 lines) — the plan says "isolate via seam, only passes props and callbacks, no new logic", but tasks 1.4.1d, 3.1.2b, 4.1.2b, 4.2.1c add to it: modifier getters, chip mount, queue-flush/reconnect state, diagnostics sheet open state with long-press (800 ms), `?inputdebug=1` parsing, the compose toggle, and `fallbackDetector` wiring (5x keydown-229 counting). That is new state and effects in a God component. — Make the seam concrete: one `useMobileInputChrome(sessionId, flowControlResult)` hook in `lib/terminal/mobileInput/` (or `components/sessions/`) that owns chip/queue/diagnostics/compose/detector state and returns a single JSX fragment plus the callbacks; `TerminalOutput` gets one hook call and one fragment. Add that hook as an explicit task before 3.1.2b.
- [ ] Story 1.3.2b (`flagStore.ts` persistence) — the plan says "one constant, one branch" and only specifies the preload (`true` unless persisted `"0"`). `persistFlags` (`flagStore.ts:60-85`) writes persisted keys only for the WS flags, `window_keep_alive`, and `ghostty_renderer` (and for ghostty it removes the key when OFF). A default-ON kill switch needs the inverse write: store `"0"` when the flag is disabled, else the preload never sees the kill and returns `true` forever. No AC covers this. — Add a second branch in `persistFlags` that writes `"1"/"0"` for `mobile_input_layer`, and the AC "Given the server flag list reports `mobile_input_layer` disabled, When `persistFlags` runs, Then localStorage `ssq:flag:mobile_input_layer` is `"0"` and `preloadFlagValue` returns false". Note per-scope overrides: `flag.enabled` is the global value; confirm (as ghostty already does) that the workspace-scope override is what the client sees.
- [ ] Story 1.2.1 / ADR-003 (`isTouchDevice` definition) — ADR-003 says it matches the existing `isTouchPrimary` semantics, but `XtermTerminal.tsx:749` uses `matchMedia('(pointer: coarse)')` only, while the plan's AC adds `navigator.maxTouchPoints > 0` (hybrid laptops become "touch", the layer attaches on a mouse-and-keyboard machine and `resolveRenderer` forces xterm there when the flag is off). Two definitions would survive because no task migrates `XtermTerminal`'s `isTouchPrimary`. — Pick one definition and justify it (pointer: coarse alone matches today and avoids hybrid laptops), and add a task to replace `isTouchPrimary` at `XtermTerminal.tsx:749` with `isTouchDevice()` so there is one.
- [ ] Story 3.1.3 (queue contents) — ADR-004 says "plain text only, never control sequences", but the queue accepts `\r`. Replaying a queued Enter up to 30 s later submits whatever the prompt then contains (a different agent state, a permission prompt, `y\r` into an unexpected dialog). — Reject any chunk containing `\r`/`\n` from the queue (queue text only up to the first newline, drop the rest with the notice), or hold the flush at the last non-newline boundary; `\x7f` is fine when paired with queued text. Update the AC and ADR-004 wording.
- [ ] Story 1.4.2 (ghostty in jsdom) — the test mounts the real `GhosttyTerminal`, which `import("ghostty-web")` and runs `mod.init()` (WASM) at `GhosttyTerminal.tsx:25-31`; jsdom cannot run that. The plan has no mock strategy for it, while also forbidding duplicated `jest.mock` blocks. — State the seam: mock `ghostty-web` once in the shared setup helper with a fake `Terminal` exposing `open/onData/focus/dispose`, and assert the integration through the seam only; keep fidelity claims to the Playwright spec (Story 5.1.1).
- [ ] Story 4.2.1 (compose bar send path) — `ComposeBar` writes bracketed paste depending on DECSET 2004 readability, an Unresolved Question blocked on Story 0.1.1. The AC fixes the behavior before the spike result; if neither renderer exposes the mode, the AC is unimplementable as written. — Add a fallback AC (send as typed text with newlines converted to `\r`, no wrapping) and mark the bracketed-paste path conditional on 0.1.1.
- [ ] Story 1.1.2 (illegal states) — `MobileInputEvent` is a single record with optional fields (`inputType?`, `data?`, `keyCode?`, `key?`) discriminated only on `kind`; the plan itself notes `tick` events (Story 1.1.2 AC) that are not in the glossary's `kind` list. Optional fields allow `compositionend` without `data` or `blur` with `inputType`. — Make `MobileInputEvent` a true discriminated union per `kind` (including `tick`) so the reducer's exhaustive switch is checked by the compiler, and add `tick` to the glossary.

## New problems introduced by the repair
- [ ] NEW-1 (concern, Story 1.4.1 vs 1.2.3) - Attach lifecycle vs `bindTapTarget`: Story 1.4.1 says the layer "attaches on focus/dock and disposes on blur/undock; only the focused terminal has a layer", but `bindTapTarget` is a method on the controller that only exists after attach, and the tap is what gives focus. A not-yet-focused docked terminal has no controller, so the first tap on ghostty falls through to ghostty's own element. Fix: define attach trigger as "terminal visible/docked and `useMobileInputLayerActive()`", with only the focus (and `inputmode`) state moving on focus change; or have `useMobileInput` install the tap target before attach and call `controller.focus()` lazily after attaching synchronously in the same gesture. Add an AC for first tap on an unfocused docked terminal.
- [ ] NEW-2 (concern, close to blocker; Task 1.3.2c, Story 1.3.2 last AC) - The shared platform gate is Android-only, but `XtermTerminal.tsx:749` `isTouchPrimary` (`pointer: coarse`) also drives the WebLinksAddon tap menu (`:757`), long-press/selection gestures (`:973`) and a further branch at `:1049`. Replacing it with `shouldAttachMobileInput()` silently removes those on iOS/iPadOS and touch laptops, contradicting the plan's own "iOS keeps today's behavior". Two different questions share one name: "attach IME layer" (Android class) vs "touch-primary UI" (any coarse). Fix: keep a separate `isTouchPrimary()` exported from `platform.ts` (coarse only, existing semantics), have `XtermTerminal` import that, and keep `shouldAttachMobileInput` for the layer only; the grep test still holds (all `pointer: coarse` live in `platform.ts`). Add an AC that link menu and long-press behave unchanged on an iPhone UA.
- [ ] NEW-3 (concern, Delivery Slicing PR-B/PR-C/PR-D) - `useMobileInputChrome` is created in Task 3.1.2b (PR-B). PR-C notes the dependency and allows "4.1 creates the hook shell", but PR-D (compose bar 4.2.1c, fallback detector 4.2.2) also edits the hook and lists only "PR-A, Story 0.1.1" as dependencies. Two later PRs each creating the hook shell is a merge conflict and a design fork. Fix: move the hook shell (empty `{fragment, callbacks}` + `TerminalOutput` single call) into PR-A (it is small and is the stated seam), so PR-B/C/D only extend it; update PR-D's and PR-C's dependency column. Related: the multi-line-paste hint (Story 1.1.3) is "surfaced by the chrome hook" but 1.1.3 is PR-A, so PR-A needs the shell anyway.
- [ ] NEW-4 (minor, Story 2.1.2) - `forwarded` threading is specified only for the `:1653`/`:2489` closures; the other three entry sites (capture-pane `:3849`, shell `:265`, stream_terminal `:439`) each record `received` but the plan does not say where they record `forwarded` (or that they do not). Without that, `received - forwarded` mixes "denied" with "that path never records forwarded". State per site, and add a test per site; keep the diagnostic query scoped to `listener="remote"`.
- OK, no problem found: platform gate shared by xterm and ghostty (single `shouldAttachMobileInput`, pure `resolveRenderer`, 8-combination table, hybrid and iOS rows); Delivery Slicing ordering PR-A..PR-E (PR-A depends on nothing; `onData: SendResult | void` from day one removes the PR-A/PR-B signature coupling; flag defaults off at merge; PR-E depends on PR-C corpus, consistent); `stage` metric design (received before permission checks, forwarded after, no content labels).
