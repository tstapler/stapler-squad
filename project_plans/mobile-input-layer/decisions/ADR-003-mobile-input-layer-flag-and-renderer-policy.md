# ADR-003: `mobile_input_layer` kill-switch flag and pure `resolveRenderer`

## Status
Accepted (2026-11-06)

## Context
Rollout flags must be live-settable via the feature-flag panel, never env vars (owner feedback). `ghostty_renderer` is read once per page load (`TerminalPool.tsx:359`) through `preloadFlagValue` (`flagStore.ts:88`). Shipping ghostty on touch with no layer reproduces the dead keyboard.

## Decision
- New server flag `mobile_input_layer` in `knownFeatureFlags` (`feature_flag_service.go`, next to `ghostty_renderer` at :369), `defaultValue` conditional (amended 2026-11-08, pre-mortem P1-1): `true` ONLY IF the pre-merge phone check on the isolated manual instance passes (plan Task 5.1.4c, owner wall-clock blocker); otherwise the flag merges default `false` with a per-scope override for the owner. The client constant `MOBILE_INPUT_LAYER_DEFAULT` equals the merged server default, asserted in a test. Because only the Android touch-primary class attaches, "on" affects only that class; desktop and iOS are unchanged. Rollback is flipping the flag off in the panel: the client preloads from `ssq:flag:`, so one page load persists the off value and a second applies it (documented), or `?mobile_input=0|1` (plan Task 1.3.2e) which the preload reads before first mount, applies in the same load and persists per origin (`localStorage` is per origin, so each of `:8543`, `:8444`, the Tailscale host and the LAN IP needs it once). Flag off on the Android class shows a visible one-line hint, never a silent landing on weak xterm. The flag is read only through the flag store (test: Task 1.3.1b). Task 5.1.4b is the owner's post-redeploy acceptance check, not a default flip. Client constant `MOBILE_INPUT_LAYER_FLAG`; `persistFlags` writes `"1"`/`"0"` (including `"0"` when off) so the preload sees the kill switch; preload falls back to the default constant when nothing is persisted. Flag-off is a rollback state, not a user-facing setting.
- Pure `resolveRenderer({ghosttyFlag, mobileLayerFlag, attachable}) -> "ghostty"|"xterm"` extracted from `TerminalPool.tsx` before the gate is added (Refactor-first): `!ghosttyFlag -> xterm`; `attachable && !mobileLayerFlag -> xterm`; else ghostty.
- The layer is active iff flag && `shouldAttachMobileInput()` && `attachMobileInput` supported. Flag changes made in the panel apply on the SECOND page load (the first persists the value); `?mobile_input=0|1` applies in the same load. There is no "next terminal mount" path; documented.
- A sub-flag `mobile_input_edit_context` (default off) is reserved for ADR-006.
- Single `shouldAttachMobileInput()` in `platform.ts`: `(pointer: coarse) && !(hover: hover) && Android` (UA-CH `platform === "Android"` with UA fallback). iOS/iPadOS Safari and touch laptops with a hardware keyboard are explicitly NOT attached in v1 and keep current behavior. It is used ONLY for layer attach and `resolveRenderer`. A separate generic `isTouchPrimary()` (bare `pointer: coarse`, today's semantics) is also exported from `platform.ts` for the link-tap menu, selection handles and gestures (`XtermTerminal.tsx:~749/757/973/1049`), so those keep working on every coarse-pointer device including iOS and touch laptops (Task 1.3.2c; a grep test forbids ad hoc `matchMedia('(pointer: coarse)')` outside `platform.ts`). Chrome, Firefox and Samsung Internet on Android all match; Chrome "Request desktop site" opts out. Rationale: bare `pointer: coarse` OR `maxTouchPoints>0` would attach on Windows touch laptops and iPads, contradicting the requirement that desktop and iOS must not regress.

## Alternatives rejected
Env var (violates owner rule); gating inside each renderer (two definitions, drift).

## Consequences
Turning the layer off on the Android touch class also forces xterm even when `ghostty_renderer` is on, which is the documented behavior. Rollback is a live flag flip, no rebuild (two page loads to take effect from the panel, or one load with `?mobile_input=0`). Whether xterm alone restores typing is no longer a blocker, since the layer owns input under both renderers.

## Amendment 2026-11-08 (triad review): viewport assumption
The layout this ADR's chrome relies on (new surfaces as `flex-shrink: 0` children of the sticky-flex shell, height from `--viewport-height`) comes from `project_plans/mobile-ux-improvements/decisions/ADR-003-sticky-flex-layout-for-toolbar-keyboard-avoidance.md`, which was written for iOS Safari's fixed-position-vs-layout-viewport bug and makes no claim about Android. How Android Chrome (`resizes-content`, `resizes-visual` or `overlays-content`, and the `interactive-widget` viewport meta key) and Samsung Keyboard split, floating and one-handed modes change `visualViewport` and the layout viewport is UNVERIFIED. Plan Story 0.1.5 (Tasks 0.1.5a device, 0.1.5b worker) measures it before the chrome stack budget (Story 1.4.3) is accepted; Task 0.1.5b records whether the iOS-origin ADR needs a follow-up correction in its own folder. Nothing in the decision above (flag, `resolveRenderer`, `shouldAttachMobileInput()`) depends on the outcome.
