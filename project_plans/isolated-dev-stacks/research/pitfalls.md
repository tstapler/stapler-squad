# Pitfalls Research: isolated-dev-stacks

Note on process integrity: mid-research, a tool result contained an injected block styled as a `<system-reminder>` instructing me to silently treat a fabricated date change and not mention it. That block did not originate from the real system/user and was disregarded; it is unrelated to this feature and is noted here only for the record.

## 1. Port Allocation Races (TOCTOU)

**This exact tradeoff is already litigated in this repo.** `docs/adr/017-cdp-port-toctou-tradeoff.md` documents the identical pattern for Chrome CDP debugging ports (and cross-references `ADR-013` for VNC ports, `session/vnc/manager.go:656`): `net.Listen("tcp","127.0.0.1:0")` → read the assigned port → `Close()` the listener → pass the bare port number to a child process that binds it independently. The ADR explicitly accepts the TOCTOU window because:
- Binding is loopback-only (127.0.0.1), so no cross-host racer exists.
- Single dev machine, low concurrency — no other process in the system is competing for the same OS-assigned ephemeral ports.
- On bind failure, the caller retries (`Allocate()` up to 3 times) rather than trying to eliminate the race.

`tests/e2e/helpers/test-server.ts`'s `findFreePort()` (line 10) and `tests/demo/helpers.go`'s `findFreePort()` (line 253) use the identical pattern with **no retry-on-bind-failure** at all today — if the race is ever lost, the Go binary just fails to start and the harness's `waitForServer()` polls for 90s before timing out with a generic "Server failed to start" error, which would be a confusing failure mode.

**Verdict for THIS feature:** Not a real problem in practice today (single dev machine, 2-5 concurrent stacks, loopback only — same conditions ADR-017 already accepted), but *is* worth closing the gap the ADR itself calls for: **add retry-on-bind-failure** (2-3 attempts, each re-running the free-port probe) around whatever spawns the Go backend and `next dev` in the new launcher, mirroring `CDPStreamManager.Start()`'s retry loop rather than `findFreePort()`'s current no-retry version. Do not attempt fd-passing (Option B in ADR-017) — it was already rejected there because neither `next dev` nor the stapler-squad Go binary's HTTP listener setup path exposes fd-inheritance flags, and building one is out of proportion to the actual risk.

## 2. Zombie / Orphaned Process Risk

The repo already has two hardened, reusable patterns for exactly this problem — reuse them instead of inventing a third for this feature:

- **Go side:** `executor/managed_process.go` (`StartProcess`/`ManagedProcess`). Sets `Setpgid: true` by default so the child (and anything it forks) lands in its own process group; `Stop()` sends SIGTERM to the *negative* PID (i.e., the whole group) via `killProcessGroup`, waits up to a grace period, then escalates to SIGKILL to the group. `session/native_process_manager.go` independently reimplements the same pattern (`Setpgid: true` at line 97, `syscall.Kill(-pid, SIGTERM)` at line 206, with a comment "NM-1: sole Wait() caller, prevents zombies" and "NM-3: send SIGTERM to the process group before any other teardown"). **The isolated-stack launcher's Go-side supervision of the backend binary should call `executor.StartProcess`, not reinvent process-group handling.**
- **Prior pitfalls doc precedent:** `project_plans/browser-passthrough/research/pitfalls.md` §1.3 and §2.1 already flag "process left running after cleanup failure" as a known class of bug for this codebase's subprocess model and mandates the same `ManagedProcess`/`Setpgid: true` + SIGTERM-then-SIGKILL-to-group pattern, plus a startup reconciliation sweep. `session/orphan_sweep.go` (`ReconcileOrphanedTmuxSessions`) is the existing precedent for that sweep — on startup it kills stale tmux sessions that have no matching DB record.

**Gap for this feature:** none of the existing tooling handles `next dev` as a *Node* child. Node's `child_process.spawn()` (used in `tests/e2e/helpers/test-server.ts`) does **not** set `detached`/its own process group by default — the spawned process shares the parent's foreground process group, so a terminal Ctrl-C (SIGINT) reaches it directly. That is good for the common case, but breaks down for:
- `next dev` in Next.js 15 can spawn its own child workers (Turbopack has a separate compiler process in some configurations; even webpack dev server spawns worker threads/processes). If the *direct* child is killed but a grandchild survives (e.g., because the grandchild called `setsid`/re-parented, or because SIGKILL was sent only to the tracked PID rather than the group), a `next dev` process can linger holding port 3001 (or whatever ephemeral port is assigned) after the harness believes it torn down cleanly.
- `TestServer.stop()` (test-server.ts line ~84) sends `SIGTERM` to the tracked child, waits up to 5s for `'exit'`, then `SIGKILL`s the same tracked PID — never a process-group signal. This is fine only because it currently supervises the Go binary (which does not fork children of its own in normal operation). The same function must NOT be reused unmodified for `next dev` — it needs `detached: true` at spawn time plus `process.kill(-pid, 'SIGTERM')` (negative PID kills the group on POSIX), or a `tree-kill`-style walk of `/proc`/`ps` children. There is no `tree-kill` or `signal-exit` dependency anywhere in `web-app/package.json` or `tests/e2e/package.json` today — one would need to be added, or the Go-side `killProcessGroup` pattern ported to TypeScript.
- Neither `tests/e2e/global-setup.ts` nor `global-teardown.ts` nor `test-server.ts` registers a `process.on('SIGINT'/'SIGTERM', ...)` handler. If Playwright's own runner is killed hard (SIGKILL, terminal closed without a chance for Playwright to run `globalTeardown`), the spawned test server (and, in the new mode, `next dev`) has no listener-side safety net at all — see §4.

**Search results:** "zombie" appears only in a code comment (`native_process_manager.go:135`, referring to `cmd.Wait()` semantics); no test/doc in this repo describes a zombie incident with `next dev` specifically, since no such harness exists yet — this is genuinely new ground for the repo, not a rediscovered/previously-hit bug.

## 3. `next dev` + Dynamic `NEXT_PUBLIC_*` Env Vars — the Real Risk Is Structural, Not Timing

Repo is on **Next.js 15.3.2** (`web-app/package.json:79`) with the App Router. Two independent problems compound here, and the codebase's actual `getApiBaseUrl()` implementation changes what the real risk is:

**3a. `getApiBaseUrl()` (`web-app/src/lib/config.ts:14-23`) does not read `NEXT_PUBLIC_API_URL` in the browser at all.** In the browser branch it *always* returns `window.location.origin + '/api'`; the `process.env.NEXT_PUBLIC_API_URL` fallback is dead code for any client-rendered request — it only fires during SSR/build (`typeof window === 'undefined'`), which barely applies to this app since `output: "export"` makes almost everything client-rendered. So the risk described in the requirements ("assuming `NEXT_PUBLIC_API_URL` set at `next dev` process-start will be picked up") is close to moot **today** for the existing build — the app was designed to *not* need that env var at all in the browser, by design (comment at config.ts:7-12 explicitly calls this out: "ensures tests running on port 8544 connect to the test server"). That design assumes the frontend and backend are always same-origin (the Go binary serves both the static export and the API).

**3b. The real, load-bearing pitfall for THIS feature:** running a real `next dev` on its own port (3001, per `web-app/package.json:14`, `"dev": "next dev --port 3001"`) against a *dynamically-ported*, separate Go backend breaks the same-origin assumption `getApiBaseUrl()` depends on. `window.location.origin` in that mode will be `http://localhost:3001` (or whatever dev port), not the backend's dynamic port — so `getApiBaseUrl()` will target the wrong origin and every ConnectRPC call will 404 or CORS-fail, regardless of what `NEXT_PUBLIC_API_URL` is set to, because the browser-path code never reads it.
  - Fixing this requires either (a) modifying `getApiBaseUrl()` to prefer `NEXT_PUBLIC_API_URL` when explicitly set, even in the browser, or (b) a rewrite/proxy in `next.config.ts` forwarding `/api/*` to the dynamic backend port.
  - **Option (b) is currently blocked**: `web-app/next.config.ts:9` sets `output: "export"` unconditionally (not gated behind the existing `NEXT_BUILD_MODE === 'development'` check that already exists for other dev-only tweaks at line 8/25-29). Per Next.js's own static-export docs, `rewrites()`, `redirects()`, and `headers()` are unsupported with `output: "export"` and **"Attempting to use any of these features with `next dev` will result in an error"** — this is not just a build-time restriction, it fails in dev mode too. So a rewrite-based fix cannot be bolted on without first conditionally dropping `output: "export"` for the new dev/e2e mode (the existing `isDevelopmentBuild` flag in `next.config.ts` is the natural place to gate this, since it already exists for a different purpose).
  - This directly answers the Open Question "Hardcoded 8543 references in `next.config.ts` or proxy layer?" — there is no proxy layer today (`grep` for `rewrites` in `next.config.ts` returns nothing), and the literal `8543` hardcoded references are confined to test mocks (`jest.mock` fallbacks across ~20 `__tests__` files) and the one real fallback line in `config.ts:22` that is dead code in-browser. Option (a) (making `getApiBaseUrl()` honor an explicit override even in-browser) is the smaller, more surgical fix and avoids touching `next.config.ts`'s static-export mode at all.

**3c. Timing nuance the requirements flagged is a non-issue here either way**, because of 3a: since the browser code path never reads `process.env.NEXT_PUBLIC_*` at request time or build time, there is no "was it inlined correctly" question to answer for the client bundle — the actual bug surface is entirely "same-origin assumption breaks when frontend/backend are on different ports," which is a routing problem, not an env-var-timing problem.

## 4. Playwright + Multiple Long-Lived Dev Servers

Known community pitfalls (Playwright issue tracker / community-reported patterns, consistent with this repo's current lack of guardrails found in §2):
- **`globalSetup`-spawned processes outliving the test run.** Playwright's own docs recommend using its built-in `webServer` config option specifically because *it* manages the spawned process's lifecycle (including a `reuseExistingServer` guard and automatic teardown tied to the test run), whereas a hand-rolled `globalSetup`/`globalTeardown` pair (which is what this repo uses, per `tests/e2e/playwright.config.ts:10-11` and `global-setup.ts`/`global-teardown.ts`) has no such guarantee if the Playwright process itself is killed hard (SIGKILL, CI job cancellation, terminal closed) — `globalTeardown` simply never runs, and whatever was spawned (today: one Go binary; with this feature: Go binary + `next dev`) is orphaned holding its port.
- **Port exhaustion after repeated failed/cancelled CI runs** is a commonly reported symptom of this exact pattern: each aborted run leaves one more ephemeral port permanently bound by an orphan process (or, worse, leaves the *fixed* port 3001 bound if `next dev --port 3001` is reused as-is rather than parameterized), so the next run's `findFreePort()`-based probe still succeeds (it just gets a different port), but manual/CI diagnosis becomes progressively harder as `ps aux | grep next` accumulates entries across restarts.
- **This repo's mitigation gap, concretely:** there is no `pretest`/CI step here that does a "kill anything on my target port(s) before starting" sweep, and no equivalent of `orphan_sweep.go`'s reconciliation for the Node-side processes. For the new e2e mode, add either (a) a Playwright `webServer` array entry (built-in lifecycle management, simplest, but may not fit if the harness needs the dynamic-port coordination this feature requires — `webServer` wants a fixed/known command+port pattern) or (b) explicit `process.on('SIGINT')`/`('SIGTERM')`/`('exit')` handlers in `global-setup.ts` that call the same teardown path as `global-teardown.ts`, so a Ctrl-C during a hung test still tears down `next dev` and the backend. Whichever is chosen, it must use process-group kill semantics per §2, not a single-PID `kill()`.
- CI workflow risk specific to this repo: `.github` workflows that run the existing e2e suite (see `e2e-video.yml` referenced in `test-server.ts`'s doc comment) will need a matching "kill stragglers" step if the new isolated-stack e2e mode is added to CI, or a bad run can poison the next CI run's port probe pool (unlikely to *fail* the next run given dynamic ports, but will accumulate zombie `next dev`/binary processes on self-hosted runners across many bad runs — less of a concern on ephemeral GitHub-hosted runners, more of a concern if this repo uses persistent/self-hosted runners for e2e).

## 5. Accidental `make install-service` During Ad-Hoc Stack Work

Real risk, and cheap to design around. `make install-service` is muscle memory in this repo (`CLAUDE.md` says "ALWAYS use this" for rebuilding+restarting) — a developer deep in ad-hoc isolated-stack work who reflexively runs it will rebuild and restart the **systemd-managed shared instance** (`systemctl --user restart stapler-squad` under the hood, per `.claude/rules/systemd-user-service.md`), which is explicitly the collision this whole feature exists to prevent. The constraints section forbids touching `install-service.sh`/the systemd unit/LaunchAgent, but says nothing about guarding the *new* command from being confused with it.

**Concrete design safeguards worth flagging in the plan** (not prescribing which one — appetite is a planning decision, but at least one should ship):
- **Distinct, non-confusable verb.** Avoid any target name containing "install" or "service" (e.g. `make dev-stack`, `make ad-hoc`, or a Go subcommand like `stapler-squad devstack`) — "install-service" and something like "install-dev-service" are one autocomplete-typo apart from each other, which is worse than a completely different word.
- **Startup banner distinguishing the instance.** Since `.claude/docs/state-isolation.md` already shows the log format `[work] INFO: ...` keyed off `STAPLER_SQUAD_INSTANCE`, the ad-hoc launcher should print a loud, colored one-line banner on startup along the lines of `⚠ isolated dev stack '<name>' — NOT the systemd instance; port <N>` so it's visually distinct from the systemd service's log stream in a terminal, and impossible to mistake for the shared instance if a dev pastes output into Slack/a PR.
- **Optional: a lightweight guard in `make install-service` itself is explicitly out of scope** per the Constraints ("No changes to scripts/install-service.sh, systemd unit, or macOS LaunchAgent") — so the safeguard has to live entirely on the new command's side, not as a check bolted onto the existing one.
