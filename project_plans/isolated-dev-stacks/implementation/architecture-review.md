## Previously-Blocked Items Re-Reviewed

- [x] Blocker 1 (srv.addr timing) - RESOLVED - Task 1.1.1a (plan.md:132-134) now states explicitly that `s.addr` is reassigned to the real bound address *before* `s.httpServer.Serve(ln)` blocks, and that this is "the ONLY write to `s.addr` after construction," giving every later `GetAddr()` read a correctness guarantee. Task 1.1.1c (plan.md:140-143) changes `SessionService` from a baked `mcpServerURL string` field to a lazily-invoked `mcpServerURLFn func() string`, with `SetMCPServerURL` now taking a function and all 3 read sites (session_service.go ~322-323, ~624, ~1195) calling `s.mcpServerURLFn()`; the `wireDepsIntoServer` call site now passes `func() string { return "http://" + srv.GetAddr() + "/mcp" }` instead of an eager string, so the closure re-reads the real address at session-creation time, not construction time. Epic 1.3 mirrors this exactly rather than reusing the old eager pattern: Task 1.3.1a (plan.md:178-180) explicitly calls out that the old `mcpURL := "http://" + srv.addr + "/mcp"` construction-time pattern is itself the bug and must not be reused for hook URLs; Task 1.3.1b (plan.md:182-184) converts `hookApprovalURL` from a package-level `const` to a `baseURLFn func() string` field read at each of its 3 usage sites; Task 1.3.1c (plan.md:186-188) converts the `hookEndpoint` map into a `hookEndpoints(baseURLFn func() string) map[HookName]string` function rebuilt fresh per call, invoked at hook-injection time (per-session); Task 1.3.1d (plan.md:190-192) wires one shared closure `baseURLFn := func() string { return "http://" + srv.GetAddr() }` into both the approval-handler and hook-injector constructors, explicitly noting it must NOT be computed at construction time. Story 1.3.1 gained a new Given/When/Then AC (plan.md:175) that exercises `PORT=0` + session creation and asserts both the MCP URL and the hook-callback URLs in `.claude/settings.local.json` contain the real OS-assigned port, never `0` — directly naming this as "the regression test for the early-binding bug found in architecture-review.md." The claimed fix is present as concrete task/AC text (not just prose) and it genuinely closes the gap: the lazy accessor is invoked after `Start()` resolves the real port, for both the MCP URL and the hook URLs, via the same shared closure pattern.
  - Minor residual note (not blocking): the new AC at plan.md:175 is a Given/When/Then acceptance criterion, not a coded unit-test task added to Phase 1. There is no dedicated "Task 1.1.1d / 1.3.1e: write regression test for lazy URL resolution" — the AC is expected to be turned into a test during validation/implementation phases per this project's normal SDD flow, so this is not treated as reopening the blocker, but it's worth confirming validation.md actually maps this specific AC to a concrete Go test before implementation starts.

- [x] Blocker 2 (ambient signal handlers) - RESOLVED - Story 3.2.1's AC (plan.md:271) now states `scripts/dev-stack/launch.ts` exports a pure `startDevStack(name?: string)` core with "ZERO ambient `process.on(...)` registrations," plus a thin CLI wrapper (`main()`) that is "the sole place signal handlers are registered," explicitly naming this as closing Architecture Blocker 2. Task 3.2.1a (plan.md:282) implements the split concretely: the pure core has "NO `process.on(...)` calls anywhere," and `main()` "must only run when the file is executed directly (guard e.g. `require.main === module` / the ESM `import.meta.url` equivalent), never as a side effect of `import`" — this is a structural/code-level guard, not just a convention. Task 3.2.1d (plan.md:294) scopes `teardown()` itself to have "no signal-related action and has no ambient side effects — it is just a function the caller can invoke," and states registration of `process.on('SIGINT')`/`process.on('SIGTERM')`/the top-level `finally` "happens ONLY inside `main()` ... never at module scope — so that importing `startDevStack` ... never attaches a signal handler to the importing process." Task 5.1.1a (plan.md:365-367) adds an explicit re-verification requirement: `startDevStack()` and its returned `stop()` closure "MUST have zero ambient global side effects at module-import time, specifically NO `process.on('SIGINT'/'SIGTERM')` registrations outside `main()`," and states that if a bare `import` reaches any ambient `process.on(...)` call, "that is a regression against Task 3.2.1a/d's split and must be fixed before Epic 5.1 proceeds." This directly answers the review question: the run-directly guard on `main()` structurally prevents `startDevStack()` from ever having a module-level `process.on` call reachable via import, not merely by developer discipline.
  - Minor residual note (not blocking): Task 3.2.1h (plan.md:310-314) adds a unit test for `teardown()`'s SIGTERM→SIGKILL sequencing and the orphan-reconciliation sweep, but does not add a coded assertion that importing the module attaches zero `process.on` listeners (e.g. asserting `process.listenerCount('SIGINT')` is unchanged after `import`). Task 5.1.1a's "verify" language reads as a manual-check instruction rather than a CI-enforced test. Given the structural guard (main-only execution behind a run-directly check) is a stronger protection than a listener-count test would add, this is a nitpick-level gap, not a reason to reopen the blocker.
