# Pre-mortem: isolated-dev-stacks
Date: 2026-07-04

## Failure Modes

| # | Failure | First symptom | Prevention | Severity |
|---|---|---|---|---|
| 1 | Real-world cold start (`orphan-reconciliation sweep` → 2× `BindRetry`-guarded `allocatePort()` → Go backend health-poll → `next dev` compile-and-ready poll, each with its own ~90s ceiling per Task 3.2.1b/c) stacks up to 60-120s+ on a typical laptop, so developers quietly revert to the old manual `PORT=...` workflow instead of `make dev-stack`, and the feature ships technically working but practically unused. | A developer runs `make dev-stack demo` for the first time, the terminal sits at "waiting for frontend ready…" for 30-60+ seconds after the backend banner has already printed, and within the first week `stapler-squad list-stacks` shows the same one or two ad-hoc names going STALE and never being re-launched — nobody is running the tool. | Add an explicit cold-start time budget AC to Story 3.2.1 (e.g. "p50 time-to-both-ready ≤ 20s on CI hardware, asserted in Task 3.2.1h") and turn requirements.md's own Feasibility Risk ("may need a 'skip seeding' fast path for the manual-use case") into a concrete Epic 3.2 task instead of leaving it as an unaddressed risk note — the manual CLI path should skip any demo/session seeding the Playwright harness needs, since Story 3.2.1's AC set currently makes no distinction between the two. | P1 |
| 2 | A `NEXT_PUBLIC_API_URL` value left exported in a developer's current shell (from a prior `make dev-stack` invocation) is still present when that same shell later runs `make install-service`, so `next build`'s static export bakes the stale dev-stack backend URL into the production bundle, silently misrouting every ConnectRPC call from the systemd-managed instance's web UI. | The systemd-managed instance's web UI starts failing all API calls (visible in browser devtools as requests to a dev-stack port, e.g. `54211`, that is no longer listening) even though the developer closed their dev-stack session hours ago and never touched the systemd instance's own config. | Task 2.1.1a/2.1.1c's regression tests only cover runtime browser behavior (set vs. unset at request time); add a build-time guard — either `web-app`'s build script asserts/unsets `NEXT_PUBLIC_API_URL` before invoking `next build --output export`, or a new regression test proves the static-export build output does not embed an ambient `NEXT_PUBLIC_API_URL` — before this ships, since none of Epic 2.1's current ACs exercise the build-time (as opposed to runtime) path at all. | P3 |
| 3 | ~~`STAPLER_SQUAD_EXTRA_ORIGINS` set by a developer for one dev-stack session lingers in a shell profile (`.zshrc`/`.bashrc`) and is still present in the environment when `make install-service` restarts the systemd unit, silently widening the production-style instance's CORS trust list — the exact cross-instance bleed this whole feature exists to prevent, just via CORS instead of ports/data-dir.~~ **RESOLVED 2026-07-04** (see resolution note below). | The systemd-managed instance's startup log line `CORS trusted origins` (Task 1.2.1a) unexpectedly lists more than one origin even though no dev-stack was intentionally left running alongside it. | **Resolved 2026-07-04:** this had been flagged twice — architecture-review.md and adversarial-review.md both raised it, and adversarial review iteration 2 explicitly declined to gate it, carrying it forward as an accepted-but-unmitigated concern. A fresh engineering review re-raised it a third time; given the recurrence, the fix is now adopted rather than deferred again. Story 1.2.1/Task 1.2.1a in plan.md now gate `STAPLER_SQUAD_EXTRA_ORIGINS` on `STAPLER_SQUAD_INSTANCE` being explicitly set to a non-empty value — the env var is never even read when `STAPLER_SQUAD_INSTANCE` is unset, so the systemd instance (which never sets a custom instance name) is structurally incapable of picking up a stray value, regardless of what a leftover shell-profile export contains. ADR-001 §2 documents the gate; Story 1.2.1's new AC is the regression test for this exact scenario. | P2 (resolved) |
| 4 | The opt-in Playwright dev-mode harness (`test:e2e:dev-mode`, Epic 5.1/5.2) is slower than the default suite and not wired into `make ci`, so nobody runs it after the initial PR merges; it silently stops proving the dynamic-port wiring works within a month. | `npm run test:e2e:dev-mode` fails or times out when someone finally re-runs it weeks later, and nobody noticed because it isn't part of any CI gate and `backlog.dev-mode.spec.ts` is the only spec exercising it. | Add a low-frequency scheduled job (e.g. a weekly GitHub Actions cron) that runs `test:e2e:dev-mode`, as an explicit Epic 5.1 task — the plan currently only wires the new Jest unit tests (`ports.test.ts`, `launch.test.ts`) into `make ci` via Task 3.2.1h, and leaves the Playwright dev-mode e2e run's CI cadence entirely unaddressed. | P2 |
| 5 | Every `startDevStack()` invocation unconditionally spawns both `BackendChild` and `FrontendChild` — there is no backend-only mode — so a developer who only wants to smoke-test the MCP server or backend logic (a use case requirements.md itself names under Users/Consumers) is forced to pay the Node/`next dev` cold-start and tooling tax (including the still-unresolved `tsx`/`ts-node` presence question in plan.md's Unresolved Questions) for work that never needed a frontend at all. | `make dev-stack foo` hangs or errors on a machine/session where `web-app/node_modules` isn't installed or `tsx`/`ts-node` isn't resolved, blocking a developer whose actual task (MCP-only testing) never required `next dev` to start. | Add a backend-only mode to `StackLauncher` (e.g. a `startBackendOnly()` export or a `--backend-only` CLI flag) so MCP/backend-only testing skips the `FrontendChild` entirely, and resolve the `tsx`/`ts-node` Unresolved Question definitively in plan.md before implementation rather than deferring it to "owner: implementer." | P2 |
