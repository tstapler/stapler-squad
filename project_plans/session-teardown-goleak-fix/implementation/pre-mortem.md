# Pre-mortem: session-teardown-goleak-fix
**Date**: 2026-09-14

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The new `cc.wg.Wait()`/`pc.wg.Wait()` calls are explicitly unbounded ("do not add a `syncutil.WaitWithTimeout` wrapper," Task 1.1.1a) — a new wait in `DeleteSession`'s teardown path that can block forever if `runStatusChangeLoop`/`pollLoop` never observes `ctx.Done()` (e.g. if the `i.mu` re-entrancy risk in Task 1.1.1b ever materializes). This appears to directly conflict with requirements.md's own AC5 ("any new wait has a bounded timeout with a clear test failure message on expiry"); plan.md's Pattern Decisions table narrows AC5 to mean only a "test-side" wait, which is a stretch of the requirement's plain text. | `Instance.Destroy()`/`DeleteSession` for one specific session hangs indefinitely in production while `i.mu` is held; every other RPC touching that same `Instance` (status queries, etc.) also stalls — looks like a generic hang/timeout report, not a goroutine leak, so it won't surface via goleak or CI at all. | Reconcile plan.md's Pattern Decisions row 3 with requirements.md AC5 before implementing: either get explicit sign-off that AC5 doesn't apply to this production-path wait, or wrap `cc.wg.Wait()`/`pc.wg.Wait()` in a bounded `syncutil.WaitWithTimeout` (mirroring `stopJoinTimeout`) that logs loudly on expiry instead of blocking forever. | P1 |
| 2 | `StartController()`/`StopController()` (`session/instance_controller.go:19-159`, `session/controller_manager.go:38-95`) have a pre-existing TOCTOU: the controller is only `Store()`d into `cm.controller` at the very end of `StartController()` (line 102), after `i.mu` is released (line 46) and the slow `controller.Start()` call (line 81, which already does `cc.wg.Add(1)` and launches `runStatusChangeLoop`) has completed. A concurrent `StopController()` running in this window sees `HasController() == false` (`controller_manager.go:38-40`) and returns immediately without ever calling `Stop()` on the controller that is already running. This is upstream of, and untouched by, this plan's fix — `cc.wg.Wait()` never even executes in this interleaving, so the goroutine leaks regardless of the fix. | `TestSessionService_CreateThenImmediateDelete_NoDataRace`-style create-then-immediate-delete tests continue to intermittently leak the exact same goroutines post-fix, at a lower but nonzero rate, because the wg join is correct but sometimes never invoked. | Before Story 1.1.3's verification run, add a targeted stress test (`go test -race -count=100 -run TestSessionService_CreateThenImmediateDelete_NoDataRace`, tight loop) specifically to surface this window, separate from the 10-iteration full-package run. If it reproduces, this needs its own fix (closing the `StartController`/`StopController` registration gap, e.g. registering the controller under `i.mu` before releasing it for the slow `Start()` call, or tracking "controller starting" state `StopController` can see) — file as a new bug per `.claude/rules/fix-flaky-tests-dont-defer.md` rather than folding into this plan's scope if it can't be fixed in the same sitting. | P1 |
| 3 | The plan fixes only 2 of the 6 goroutines requirements.md names as leak sources. The 6th — `session/tmux`'s `RestoreWithWorkDir` diagnostic `os/exec.(*Cmd).Wait` goroutine (`session/tmux/tmux.go:1730`, reaped only via `waitOnce.Do(cmd.Wait())` inside `closePTYTriple`/`KillSession`) — is dismissed in architecture.md as "unrelated ownership... out of scope," but BUG-084's own recurrence log (2026-08-21 entry) shows this exact goroutine present in an actual, confirmed recurrence of this flake, alongside the two goroutines this plan does fix. `waitForTmuxTeardown` only polls `TmuxSessionExists() == false`, which is not the same as "the attach subprocess has been reaped" — there's no guarantee the two conditions coincide. | Task 1.1.3a's `-race -count=10` verification run still intermittently fails, but with a *different* goroutine (`RestoreWithWorkDir`/`os/exec.(*Cmd).Wait`) in the stack trace instead of the two now-fixed ones — easy to misread as "a new, unrelated flake" and re-excuse rather than recognize as the same root cause, partially fixed. | Before declaring Story 1.1.3 complete, explicitly check any residual failure's goroutine stack against BUG-084's recurrence log. If it's the tmux diagnostic goroutine, this plan's scope needs to extend to it (e.g. `waitForTmuxTeardown` also confirming the attach subprocess is reaped, or `KillSession` exposing a join point) rather than treating criterion 2 as met on a false negative. | P1 |
| 4 | Task 1.1.2a instructs placing `pc.wg.Wait()` "outside the locked section" in `PTYConsumer.Stop()`, but the existing code uses `defer pc.mu.Unlock()` (`integration.go:128-141`). A literal, naive edit — appending `pc.wg.Wait()` as the last statement in `Stop()` — actually executes it *before* the deferred `Unlock()` fires, since defers run at function return. `pollLoop` doesn't currently touch `pc.mu`, so this doesn't deadlock today, but it silently defeats the plan's own stated intent and leaves a latent trap: any future change that has `pollLoop` acquire `pc.mu` (plausible, since `Start()`/`Stop()` already do) would deadlock immediately, with no test currently exercising that interleaving. | No CI signal at merge time — the mistake is invisible until a later, unrelated PR adds a `pc.mu.Lock()` inside `pollLoop`, at which point `PTYConsumer.Stop()` (and everything blocked behind it, including `ClaudeController.Stop()` and `i.mu`) hangs. | Make Task 1.1.2a explicit: restructure `Stop()` to call `pc.mu.Unlock()` manually before `pc.wg.Wait()` (not a bare `defer`), and add a one-line comment stating why, so the next reader doesn't reintroduce the same defer-ordering mistake. Add an acceptance-criterion check confirming `pc.mu` is provably released before `pc.wg.Wait()` is entered. | P2 |
| 5 | Task 1.1.1b's `i.mu` re-entrancy check is a one-time, ~5-minute manual grep with no persisted guard (no lint rule, doc-comment invariant at the `StatusChangeListener` type, or regression test). Even if today's grep finds nothing, a future PR registering a new listener that calls back into an `i.mu`-guarded `Instance` method would silently reintroduce a full deadlock — `StopController()` already holds `i.mu` across the entirety of `ClaudeController.Stop()`, now including the new `cc.wg.Wait()` (architecture.md's own flagged risk). | A full-server hang with no goleak signal at all — `Instance.Destroy()`/`DeleteSession` never returns, every other request touching that `Instance` blocks on `i.mu`, and there's nothing in CI pointing at the cause since this isn't a goroutine-count assertion, it's a deadlock. | Turn the one-time grep into a standing invariant: add a comment at `StatusChangeListener`'s type declaration (`session/claude_controller.go`) and at its registration site stating "listener bodies must never acquire `i.mu` — `StopController` holds it across `cc.wg.Wait()`," so the next author has an explicit contract to check against instead of relying on someone re-running the same ad hoc grep. | P3 |

## P1 Items (address before implementation)
- [x] #1 — Resolve the AC5 (bounded-timeout) conflict in plan.md's Pattern Decisions table before writing `cc.wg.Wait()`/`pc.wg.Wait()` as unbounded calls; either get explicit sign-off that AC5 doesn't cover this path or add a bounded wait with loud-failure-on-expiry. **Addressed in plan.md** (Pattern Decisions "Timeout-on-expiry" row, Task 1.1.1a, Task 1.1.2a): both waits now go through `syncutil.WaitWithTimeout(&wg, stopJoinTimeout)` with `log.Error` on expiry, resolving the AC5 conflict without a stretch reading.
- [x] #2 — Add a dedicated tight-loop stress test for `TestSessionService_CreateThenImmediateDelete_NoDataRace` (separate from the 10-iteration full-package run) to check whether the `StartController`/`StopController` registration TOCTOU (`session/instance_controller.go:19-159`) causes `Stop()` to be skipped entirely; if it reproduces, this needs its own fix before the item can close. **Addressed in plan.md**: new Task 1.1.3c (`-race -count=100`, isolated to the one test), explicitly gating Story 1.1.3's completion and requiring a separate bug filing if it reproduces — not folded into Stories 1.1.1/1.1.2's scope.
- [x] #3 — Before Story 1.1.3 declares success, cross-check any residual `-race -count=10` failure's goroutine stack against BUG-084's recurrence log for the `RestoreWithWorkDir`/`os/exec.(*Cmd).Wait` signature; do not treat a differently-attributed failure as "unrelated" without checking. **Addressed in plan.md**: Task 1.1.3a now requires this cross-check explicitly before any residual failure can be dismissed as unrelated.

All three P1 items are addressed by plan.md updates (verification/scope additions, not redesigns of Epic 1.1's core fix). #2 and #3 remain **verification gates**, not closed facts — they may still surface a separate, out-of-scope bug during implementation (Task 1.1.3c / Task 1.1.3a), in which case that follow-up bug — not this plan — absorbs the fix, per `.claude/rules/fix-flaky-tests-dont-defer.md`.
