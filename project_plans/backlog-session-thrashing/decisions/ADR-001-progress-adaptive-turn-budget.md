# ADR-001: Progress-Adaptive Turn Budget Inside AutonomousDriver

**Date**: 2026-07-25
**Status**: Accepted
**Project**: backlog-session-thrashing

## Context

`AutonomousDriver.run()` (`session/autonomous_driver.go:192-278`) stops an autonomous work session after a fixed 20-turn budget (`maxTurns`, defaulting via `NewAutonomousDriver`, `:66-69`) regardless of whether the target session is actively, productively working right up to the cap or has been silently wedged the whole time. `AutonomousDriverOutcome.Stuck` is driver-internal terminology for "exited without a DONE signal" — it does not distinguish these two cases (architecture.md §2). The requirements doc's primary success metric is explicit: "a work session that is making genuine forward progress is not killed or forced to restart purely because it crossed a fixed turn count."

Two candidate designs were considered for "genuine progress shouldn't be killed":

1. **Respawn with a larger budget.** End the turn-capped session, spawn an entirely new session/driver with a bigger `maxTurns`, similar to how `AutoRespawnAutonomousWork` already respawns today. Rejected as the primary mechanism: it requires threading a `maxTurns` override through `SpawnSessionFromItemRequest` (a new proto field) → `spawnSessionAfterGates` → `StartAutonomousDriverForInstance`/`StartAutonomousDriverWithTimeout`, touching proto definitions and three service-layer call sites for something the driver can decide locally. It also always pays the cost of ending a session and losing its conversation/prompt-cache continuity — the opposite of what `AutoReopenAfterFailedReview`'s own doc comment says the codebase prefers when a live session can be reused ("reusing the live session instead keeps its conversation... intact," `backlog_service_triage.go:1141-1144`).
2. **Extend the same driver's budget in place, using a signal the driver already has.** `AutonomousDriver` holds `d.inst *Instance` directly, and `*Instance` already exposes `GetTimeSinceLastMeaningfulOutput() time.Duration` (`session/instance_approval.go:114`) — the exact signal `notifyIfActiveWorkSessionStale` already uses (via the `SessionStopper` interface) to distinguish "alive and working" from "alive but stale" for a *different* gate (`backlog_service_triage.go:964`). No new plumbing, no proto change, no cross-service wiring: the same `AutonomousDriver.run()` loop can check this signal locally at the moment it would otherwise stop.

## Decision

Chose design 2. `AutonomousDriver.run()` tracks an `effectiveMaxTurns` (starts at `d.maxTurns`) separately from a `hardMaxTurns` ceiling (`d.maxTurns * turnBudgetHardCapMultiplier`, multiplier = 3). When the loop's turn counter reaches `effectiveMaxTurns`, instead of unconditionally stopping, the driver checks `d.inst.GetTimeSinceLastMeaningfulOutput() < turnCapProgressWindow` (15 minutes — chosen to match `maxReworkBlockStaleness`, `backlog_service_triage.go:904`, an existing threshold already validated for "is this live session genuinely still working" in `ADR-001-staleness-threshold-recalibration.md` under `project_plans/review-gate-stale-session-rework/decisions/`; not re-derived from scratch, per that ADR's own warning against inventing a fifth uncoordinated staleness number). If recent output exists, `effectiveMaxTurns` is raised by `turnBudgetExtensionIncrement` (10 turns), capped at `hardMaxTurns`, and the loop continues. If not — or if `effectiveMaxTurns` has already reached `hardMaxTurns` — the loop exits with `ExitKind = DriverExitMaxTurns`, exactly as today, and the existing `onAutonomousDriverComplete` / `AutoRespawnAutonomousWork` machinery takes over unchanged.

This makes the turn budget a soft/hard two-tier cap rather than a single fixed number, entirely inside `session/autonomous_driver.go`. `AutonomousDriverOutcome.Turns` now reports the actual `turnCount` reached (fixing a pre-existing bug where it was hardcoded to `d.maxTurns` regardless of how many turns actually ran — see plan Task 2.1.1c), so an item that got a full extended run shows its real turn count in the Unfinished tab and stuck-reason text, not a number that undercounts extensions or overcounts an early break.

## Consequences

- No proto changes, no new request fields, no cross-service config plumbing required for the adaptive behavior itself — confined to `session/autonomous_driver.go`, matching the requirements doc's "fix/hardening project, not a rewrite" constraint.
- A session that is genuinely still producing output gets up to 3x its base budget before the driver gives up — the specific failure mode this project was opened for (realistic tasks getting cut off at 20 turns) is addressed without spawning a second competing session or losing conversation continuity.
- A session that goes quiet stops at exactly the base budget, same as before — this design does not loosen detection of genuinely stuck sessions; it only extends runway for sessions that are still visibly working.
- `turnCapProgressWindow`'s value (15 minutes) is a deliberate reuse of an already-validated number, not a new empirically-derived constant — same caveat `ADR-001-staleness-threshold-recalibration.md` already carries for that value: future recalibration should update both docs' rationale, not silently drift one.
- The "hard cap ... an absolute ceiling" framing above is per-process-lifetime, not truly absolute across an item's full history: `effectiveMaxTurns`/`turnCount` live only in the `AutonomousDriver` goroutine's local variables and are lost on a server restart (no reattach/resume-on-restart mechanism exists for in-flight drivers). A restart mid-run resets the effective turn counter to 0 for whatever driver run comes next on the same item — an accepted, pre-existing characteristic of this architecture (see `.claude/rules/tmux-keep-server-on-restart.md`), not a new gap this ADR introduces, but worth naming explicitly rather than letting "hard cap" read as stronger than it is.
- The base `maxTurns` itself remains configurable per Task 2.4 (a `config.Config.MaxAutonomousTurnsOrDefault()` knob, default still 20) — orthogonal to this decision, since the hard cap and extension increment scale off whatever the base is.
- This does not touch `AutoRespawnAutonomousWork`'s respawn-with-fresh-session behavior at all — that mechanism still exists and still fires for genuinely-stuck items (no recent output at the soft cap, or the hard cap reached). Design 1 (respawn-with-larger-budget) was not implemented, so a future revisit finding the in-place extension insufficient should treat design 1 as the next escalation, not a duplicate of this one.

## Alternatives Considered

- **Respawn with a larger budget** (design 1 above): rejected as primary mechanism for the plumbing-cost and conversation-continuity reasons above; not ruled out as a future addition if in-place extension proves insufficient in practice.
- **Remove the turn cap entirely, rely only on wall-clock/cost limits**: rejected — no wall-clock or cost cap exists today either (stack.md §1, "Not found / unverified"), so this would trade one unbounded-cost risk for another with no replacement guardrail. The hard cap (`turnBudgetHardCapMultiplier`) preserves an absolute ceiling.
- **Make the extension unconditional (always give more turns) rather than progress-gated**: rejected — this would silently disable the turn cap for a session that's genuinely wedged (e.g., stuck in a loop with no real output), reintroducing unbounded-runaway risk for exactly the case the cap exists to catch.
