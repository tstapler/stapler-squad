## Blockers

- [ ] **Story 1.1.2 / 1.1.3 / ADR-001 shadow design (`gate_missing` is unmeetable)** — Shadow compares the Default answer to the raw `ConfiguredWorkflowEngine` answer. The Configured engine has no built-in guards by design (seed writes zero gates; `PendingGates` returns `nil,nil` for an edge with no gates, `configured_workflow_engine.go:171-173`). So every legitimately blocked transition on a seeded config (e.g. `idea->ready` with no AC, `review->done` with no PASS verdict) is classified `gate_missing`. Story 1.1.1 even documents this as the "expected" gap. The soak criterion (`gate_missing=0` under `config=seeded`) and `make workflow-engine-soak-status` exit 1 then fire on normal traffic, so the enforce flip can never be evidenced. The shadow signal measures the thing the design already decided not to ship (raw Configured), not the thing enforce will run. — **Remediation**: define the shadow candidate as the exact enforce path (Configured graph unioned with `SystemRequiredEdges`, guards = Default `TransitionGuard` AND Configured gates, with the same fallback logic), implemented once as a private `enforceAnswer(...)` used by both Enforce and Shadow. Divergence is then Default vs enforce-composed, and `gate_missing` genuinely means a composition defect. Keep the raw-Configured comparison only in the 1.1.1 offline harness. Update AC text in 1.1.1, 1.1.2, 1.1.3 and ADR-001's shadow row accordingly.

- [ ] **Story 1.1.2 (Task 1.1.2a) / Task 0.1.1a / Unresolved Question "override_reason vs Configured gates"** — The question is treated as unknown and as "reproduce what the handler does". The handler always calls `ValidateGates` (`backlog_service_lifecycle.go:933`) and passes `OverrideReason` only inside the input; only `TransitionGuard` (Default) honors it. `ConfiguredWorkflowEngine.ValidateGates` ignores `OverrideReason` entirely (`configured_workflow_engine.go:219-232`). Under Enforce with Default-guards-AND-Configured-gates, an operator override therefore cannot clear an operator gate. Worse, the deleted-stage path returns a synthetic blocking gate whose log says "blocking ... pending manual override" (`:171`, `stageConfigUnresolvableGateStatus`), so an in-flight item on a deleted stage becomes permanently un-movable in Enforce: the documented escape hatch does not exist. No Story 1.1.2 AC covers Enforce + `override_reason`. — **Remediation**: decide now (it is answerable from the code, not a spike): `override_reason` non-empty bypasses Default guards (today's behavior) and Configured operator gates including the synthetic deleted-stage gate, but never the graph check. Add ACs to Story 1.1.2: (a) Enforce + failing human_approval/custom gate + override => succeeds with progress note; (b) Enforce + item on deleted stage + override => succeeds; (c) empty reason => blocked as today. Task 0.1.1a keeps the characterization of Default-mode behavior only. Drop the corresponding Unresolved Question.

- [ ] **Story 1.2.2 / Task 1.2.2a-b (`transitionOrNotify` placement and call sites)** — The helper is planned in `server/services/backlog_transition_notify.go`, but two of the four named adopters are in `session/backlog_lifecycle.go`. `session` cannot import `server/services` (the dependency runs the other way), so as specified the task either creates an import cycle or forces a second copy of the helper. Separately, the site list is stale (see cite table): two of four cites are not transition sites, and the lifecycle/triage sites that remain call `storage.TransitionBacklogItemStatus`, a pure CAS that can never be denied by the graph, so the premise "a stricter graph makes these live" does not hold for them. The real engine-deniable automated callers are `transitionWithGuard` (`backlog_service_triage.go:680`) and its callers `queueBacklogItem` (`:716`) and `claimAndSpawnCandidate` (`:839`), plus `SyncLoop` (`backlog_sync.go:449`, which already degrades by skipping and retrying). — **Remediation**: (1) re-derive the call-site list with `ast-grep`/grep for callers of `transitionWithGuard` and `GuardedTransitionAllowed`, and put exact current lines in the task; (2) place the helper in package `session` behind a small `TransitionDeniedReporter` interface (comment + stuck reason + notify), with the service layer injecting the notifier, or keep it in `server/services` and scope it to service-layer callers only; (3) rewrite the AC to name `claimAndSpawnCandidate` (`queued->in_progress` denied) instead of `TriggerReReview`, which goes through the handler path that already returns an error to the caller.

## Concerns

- [ ] **Story 1.1.3a / ADR-001 "no I/O" claim** — Research and ADR-001 state Configured evaluation is "pure, in-process, no I/O". It is not for stateful gates: `evaluateRecordedGate` calls `gateSatisfactionRepo.GetByItemAndGate(context.Background(), ...)` (`configured_workflow_engine.go:373-375`), a DB read with an uncancellable context, on the transition hot path and on every shadowed `ValidateGates`. Seeded config has no such gates so shadow is cheap today, but an edited config with a human_approval/automated_review gate adds a DB round trip per shadow call, contradicting the NFR. Recommendation: either skip shadow evaluation of stateful gate kinds (count them as `not_compared`) or thread the caller's `ctx` and cap/measure it; say so in ADR-001.
- [ ] **Epic 5 sequencing vs earlier tasks** — Tasks 1.2.4a and 2.1.1b say they register `ConfigSurfaceProof` entries, and the wave plan places them in W2-W4, but the framework (Story 5.1.1) lands in W7. They cannot register into a registry that does not exist; either those tasks silently skip it (and Metric 5 is retrofitted, the exact anti-pattern ADR-006 exists to prevent) or the order is wrong. Recommendation: pull Story 5.1.1 forward to W2 (it needs only the shapes of `QuotaConfig` and the flag registry), or move the entries to 5.1.2 and remove the claim from the earlier tasks.
- [ ] **Serialization claim for `server/dependencies.go`** — The plan says dependencies.go is touched only by Task 1.1.4a. It is also needed for the `RepoSettingsCache`/gateway injection (3.1.2), the nudge-outcome recorder (4.1.2), the quota settings service/closure (2.1.1, registered in `server/server.go` but sharing the cfg closure at `dependencies.go:1429-1436`), and the status-RPC wiring (1.3.1). Concurrent stories (WIP cap 2) will collide. Recommendation: list the dependencies.go touches per story in the "Stories sharing a file serialize" paragraph, or add one wiring task that all of them append to in order.
- [ ] **ADR-002 `SystemRequiredEdges()` derivation rule** — The rule is "literal-status sites that call storage directly". Those sites never consult the engine, so the union protects nothing for them; what the union actually protects are automated callers that go through the engine: `ready->queued` / `queued->in_progress` (dequeue/claim via `transitionWithGuard`), `SyncLoop` backward-sync targets, and `TriggerReReview` (`:1318`). `ready->queued` and `queued->in_progress` are absent from ADR-002's initial list, and Story 1.2.4 uses `ready->queued` as the edge an operator disables. Recommendation: derive the set from both groups (engine-checked automation callers, plus storage-direct ones for honesty in the UI), and pick a different edge for the allow/deny proof or accept that disabling `ready->queued` is a user-facing choice while `queued->in_progress` is system-required.
- [ ] **Bypass inventory task coverage (Tasks 1.2.3b/c)** — The listed files omit many direct-storage writers that the inventory test (1.2.3d) will fail on at first run: `backlog_service_triage.go` (`:1268,:1324,:2041,:2115,:2418,:2471,:2637,:2906,:3348`), `backlog_lifecycle.go` (`:1004,:1866,:1873`), `jules_session_poller.go` (`:432,:518,:533`). Recommendation: generate the inventory first (Task 1.2.3d ahead of 1.2.3b/c) and list every function; decide per entry instrument vs exempt, otherwise the story cannot reach green as written. Rollback sites (`ExpectedStatus` restore) probably want `exempt: rollback`, not a counter.
- [ ] **Hotspot new-code gate on modified functions (Tasks 1.2.2b, 4.1.3a)** — Per project memory the gocognit/gocyclo gate applies to modified existing functions, not only new lines. `claimAndSpawnCandidate` (switch with several cases) and the `backlog_service_triage.go` callers are large; adopting `transitionOrNotify` there can trip the gate even with a net-small diff. Recommendation: add a pre-check step (`make ready-complexity-gate` on the touched functions) to those tasks and allow an Extract Function inside the task.
- [ ] **`RepoSettings` type allows an illegal state (Story 3.1.1/3.1.2)** — `RepoSettings{Status, AllowAutoMerge bool}` and the proto pairing `AutoMergeLookupStatus` + `optional bool allow_auto_merge` both let `AllowAutoMerge=false` coexist with `Status != OK`, the same "not asked vs false" conflation the plan elsewhere rejects. Recommendation: Go side expose `AutoMerge() (allowed bool, ok bool)` or `*bool` populated only when `Status==OK`; proto side set `allow_auto_merge` only for `OK` and add a test asserting it is unset otherwise. A `oneof` is the stronger form if proto churn is acceptable.
- [ ] **Concurrent `config.json` writers (Story 2.1.1)** — `UpdateQuotaConfig` is a read-modify-write via `config.SaveConfig` (`config/config.go:1557`) while `FeatureFlagService` and other settings services also write the same file; the lost-update risk is deferred to spike 0.1.1c with no stated fallback. Recommendation: name the fallback now (a package-level config mutation mutex or a `config.Update(func(*Config))` helper) so Task 2.1.1a is not blocked on the spike's outcome.
- [ ] **Stale "seeded vs edited" fingerprint scope (Story 1.1.1b)** — `SeedFingerprint` hashes only the edge set. An operator who adds a gate or changes liveness without touching edges is still `config=seeded`, so a `gate_extra`/`error_kind` divergence is counted against the alert population. Recommendation: include enabled stage set and gate count per edge in the fingerprint, or restrict the alert to `graph` and `gate_missing` only (as the plan implies) and say so in the actuator text.
- [ ] **Mixed-mode within a request is accepted by ADR-001 but the new `GetWorkflowEngineStatus` banner reads a separately cached mode** — the banner can say Enforced while one in-flight request used Default. Low severity; note the TTL (about 1s) in the banner/runbook.

### Is Epic 1.5 over-built for Metric 1?

Yes, moderately. Metric 1 (strong) needs exactly four things: (a) every status write funnels through one function; (b) that function decides with the engine built from the edited config (graph, gates), including for automation; (c) the raw writers are unreachable so (a) cannot rot; (d) a denial in automation neither disappears nor causes churn. Epic 1.5 is 44 tasks and about 43% of the total; roughly a third of it is risk-management scaffolding around those four, not Metric 1 itself. Its own text concedes the soak thresholds (N=20, floor 100) are unreachable at about 21 live items, so the per-class soak machinery buys little.

**Simplest design that still satisfies strong Metric 1**
1. `Storage.GatedTransition(ctx, req{item, to, class, caller, precondition, beforeCommit})` with `Gated{Archive,Unarchive,SetPRAndTransition}` as thin variants: one decision function = configured engine (graph UNION `SystemRequiredEdges()`, operator gates; Default built-in guards only for `operator`/`agent`); denial for `agent`/`system` calls the reporter inside the gate. Keep: this IS (a) and (b).
2. Unexport the five `EntRepository` writers (genuine compiler guarantee, cheap), rename the `Storage` wrappers `Raw*`, the strict inventory test, and `create` as an exempt class. Keep: this IS (c).
3. One shared `HasOpenTransitionDenied` predicate plus the re-drive sweep, applied only at the points that actually SPAWN or NUDGE (the `remediationActionByReason` actions, `respawnTriage`/`AutoRespawnTriage`, the inline `FindReviewItemsWithoutGate` respawn, `DequeueNextQueuedItems`), not inside all 25 detector bodies; detectors that only `MarkStuck` stay as they are because stuck-row writes are idempotent. Keep, but re-scope to spawn points (INFERRED: that those points are about 8 functions; confirm with the Story 1.5.8 table before committing to the smaller scope). This IS (d).

**What it would delete**
- Per-class enforce flags and the class dimension of `ModeFor`: one `workflow-engine-enforce` flag plus the existing shadow flag (class stays a metric label). Removes 1.5.2b's flag work, the per-class ledger/actuator/soak-status (1.5.2d), and the `recovery`/`reporter` degrade paths and the `recovery_wired` proto field.
- Registry fields `legacy`, `guards`, `forwarding` and the forwarding singleton pin; keep `{caller, class}` plus declared edges only for the non-forwarding agent/system callers (needed for `SystemRequiredEdges()`). The edge audit stays; the legacy-parity machinery (Shadow baseline for `Unchecked` callers, the `guard_new` class, the owner-acknowledgement table, Task 1.5.2c) goes: with one enforce flip the soak is `--config-diff` plus the shadow counters.
- Task 1.5.9d (replay harness against a copy of the live database): a one-shot `--config-diff` over about 21 items already shows the stranded preview.
- Task 1.5.4f (analyzer extension), see C1; replace with the gate-reports-denial unit test.
- Task 1.5.3d microbenchmarks (50 microsecond budget on a path that runs tens of times per day) and the 1.5.3e overrun checkpoint can fold into the story's definition of done.
- Rough size: about 10-14 of the 44 tasks and 1.0-1.5M of the 4.1M raw tokens (INFERRED from task titles, not re-estimated).

What it would NOT delete, and must not: the unexport of the repo writers, the strict guard, operator gates applying to `system`, system-required-edge union with `X->archived`, the `HasOpenTransitionDenied` guards, and the re-drive sweep. Cutting any of those makes Metric 1 untrue or reintroduces the churn the earlier review found. This is a recommendation only: the owner's standing instruction is to pursue full scope, so the current design is acceptable and the list above is what to cut if effort or review risk becomes the constraint.
