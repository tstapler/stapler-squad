## 1. Shared state vocabulary

| Condition | Copy pattern | ARIA |
|---|---|---|
| Loading | "Loading..." / "Checking..." | `aria-busy="true"` on the region, no live announcement |
| Not applicable (no PR repo, no PR yet) | Row omitted | n/a |
| Known | "<value> (as of <ago>)" | static; changes announced via the surface's single status region (live-region policy) |
| Failed | "Couldn't check <thing>: <short reason>. Last tried <ago>." plus a Retry button | `role="status"` if informational, `role="alert"` if it blocks an action |
| Stale | value + "(as of <ago>, may be out of date)" | none |
| Empty (valid, nothing configured) | Plain sentence naming the default ("No overrides set. Defaults apply.") | none |

The bare word "unknown" is retired. Failed states are not muted/italic (contrast must meet 4.5:1 text, 3:1 for icons/borders, in both themes; verify `textMuted` tokens first, `research/ux.md` section 7). Retry buttons are real `<button>`s, at least 44px tall on touch, keep focus after the retry resolves (status text updates in place). Every Failed state has Retry as its exit; every save form has Revert/Cancel.

**Live-region policy (one rule for every surface, round 7).** A persistent state display (banner text, summary line, the quota "Effective now" line, warnings such as "gate on, budget 0") is a static element with no `role`: it is read in DOM order and is NOT announced on first render. Changes are announced through at most ONE `role="status"` element per surface that is mounted empty before the first change (so assistive technology has registered it), and blocking errors through `role="alert"`, one at a time. Quota page: `backlog-quota-status` is the only status region. Stages page: the banner owns the nested live region `engine-mode-banner-live`, `stage-save-status` is the form's own status, and a banner refetch triggered by a save announces only if the mode text actually changed. Features page: only the row confirmation of the row just changed is populated; it carries the new engine count after an engine flag changes. Specs address regions by `data-testid` or scoped to a row, never by an unscoped `getByRole("status")` except on the Quota page, where exactly one exists.

## 2. S1 Stages page: EngineModeBanner (Story 1.3.2)

**Entry:** Settings nav -> Backlog Stages, or the "Edit stages" link from the Features enforce row. **Exit:** "Change in Feature Flags" link (to `/settings/features#flag-row-backlog-workflow-engine-enforce`, or the `-agent`/`-system` row id for the first class not yet enforced; the Features page focuses that row, section 3), nav away; no modal, so no trap.

```
+------------------------------------------------------+
| Backlog Stages                         [ New Stage ] |
| Configure workflow stages ... (mode-neutral copy)    |
| +--------------------------------------------------+ |
| | (!) Shadow: edits are compared against the       | |
| |     built-in rules but are NOT enforced.         | |
| |     3 differences in the last 24h.               | |
| |     [Change in Feature Flags]                    | |
| +--------------------------------------------------+ |
| Stage list ...                                       |
+------------------------------------------------------+
```

Always rendered directly under the h1 and before the stage list in DOM order, `data-testid="engine-mode-banner"`. The container has no `role` and is not announced on first render (live-region policy). It holds the visible text plus one nested live region `data-testid="engine-mode-banner-live"` (`role="status"`) that is mounted empty and receives the new mode sentence only when the mode, or the Unknown or Stale state, changes after the first resolved value, including after Retry or a visibility refetch. The initial Loading, Unknown and Shadow states are read in reading order, not pushed. While loading the container has `aria-busy="true"`.

| Mode | Copy | Style |
|---|---|---|
| Loading | "Checking whether these settings are enforced..." (`aria-busy`); stage list is still shown but the copy never claims enforcement | neutral |
| Enforced (all three caller classes: operators, agents, automation) | "Enforced: edits here change which transitions and gates the backlog allows, for operators, agents and automation. Edges that automation relies on are fixed; their gates are editable." | neutral/success + icon |
| Partly enforced (at least one class enforced, at least one not) | "Partly enforced. Operators (this UI): enforced. Agents: shadow, not enforced. Automation: shadow, not enforced." (each class names its own mode: enforced, shadow or off) | warning + icon |
| Shadow | "Shadow: edits are compared against the built-in rules but are **not enforced**. N differences in the last 24h. Change in Feature Flags." (N = 0 reads "No differences in the last 24h"; N unavailable reads "Difference count unavailable") | warning + icon |
| Off | "Not in use: the built-in 9-stage workflow is active. Edits are saved but have no effect." | warning + icon |
| Unknown (RPC failed, or the status reports `gate_wired=false`) | "Couldn't determine whether these settings are enforced. Treat edits as not applied." + Retry | warning, never the Enforced text |
| Stale (a refetch failed after a good value) | The last value plus "Last checked <ago>; couldn't refresh." + Retry; never promotes the text to Enforced | the last value's style |

**Freshness:** the status is fetched on load, re-fetched once when the tab regains focus or becomes visible (`visibilitychange`/`focus`, at most once per 5 s) and after a successful stage save; there is no polling timer. A flag flipped in another tab or on another device is therefore reflected the next time this tab is looked at, and the mode reader's own cache lag (about 1s) is the only remaining delay. The nested live region announces changes, not the initial render. (Earlier drafts said both "container `role=status`" and "announces changes, not initial render"; those conflict, because a container with `role="status"` and content present at load is announced on load by most screen readers. The nested empty-then-populated region is the one behaviour kept.)

Owner decision 2026-10-17 (option A, plan Unresolved Question 1): "Edges that automation relies on are fixed; their gates are editable" is exactly true only for edges that have a row in the stage tables. Archive from `in_progress`, `review` and `pr_pending`, re-archive (`archived->archived`) and archive from a custom stage have no row, so the editor shows no place to attach a gate to them and the page note reads "Archive from active stages cannot be gated here; gate `done->archived` instead." Virtual editor rows are not built.

**Review-due line (UX-55).** The status carries `review_due_at` and `review_overdue` (Task 1.3.1c; computed by the same ledger evaluator as `make workflow-engine-soak-status`, so the two cannot disagree). Inside the banner container, below the mode text, a static line `data-testid="engine-mode-review"` reads: before the date, "Soak review due <date>."; once the date has passed with no caller class enforced, "Review overdue: the soak review date (<date>) has passed and no caller class is enforced. Review the soak evidence in docs/how-to/flip-workflow-engine-enforcement.md." (warning style, text plus icon); when any class is enforced, a neutral "Soak review date <date>."; when the ledger cannot be read, the line is omitted (it never claims a date). The Features page summary block repeats it (`workflow-engine-review`). This is the in-product forcing function against "the flip never happens"; the CLI `REVIEW OVERDUE` output and the calendar reminder remain. No `notify()` is sent: a periodic notifier needs a scheduler outside this project, and the banner sits on the page the operator opens to edit stages.

Also: replace the page description at `backlog-stages/page.tsx:151-154`, which currently asserts enforcement; save confirmations carry the mode ("Saved. Not enforced yet (shadow)" / "Saved and enforced" / "Saved. Not in use (off)"); at 360px the stage form repeats the mode in one line directly above its Save button because the banner has scrolled out of view by then. It reads the SAME fetched status object as the banner (one fetch through a shared hook, so the two cannot disagree) and has copy for every state: Enforced "Mode: Enforced." / Partly enforced "Mode: Partly enforced. Saved edits apply to operators only; agents and automation are in shadow." (the class list is generated from the status) / Shadow "Mode: Shadow. Saved edits are not enforced yet." / Off "Mode: Off. Edits are saved but have no effect." / Loading "Mode: checking..." (Save stays enabled) / Unknown "Mode: couldn't be determined. Treat saved edits as not applied." / Stale "Mode: <last value> (last checked <ago>; couldn't refresh). Saved edits may not be enforced." The Unknown and Stale lines never use the Enforced-only wording unless the last good value was all-three-enforced, and the reminder never renders as an empty line (UX-52). The save confirmation uses the same states: "Saved. Enforced for operators only; not enforced for agents and automation." (Partly enforced) and "Saved. Couldn't confirm whether it is enforced." (Unknown); if `invalidator_wired=false`, add "Saved, but the running engine was not refreshed." (UI-says-saved, runtime-unchanged case). The control to flip the mode is not on this page; links both ways ("Change in Feature Flags" / "Edit stages"). The System-required edge rejection (Task 1.3.2d) shows the edge name and why ("Automation relies on this transition") with `role="alert"`, keeps the form values, and offers Cancel as the exit. Save failures (network/server; Task 1.3.2e) keep entered values, show "Couldn't save stage: <reason>" `role="alert"` + Retry.

**Responsive:** banner is full-width block, text wraps (no truncation, no horizontal scroll at 360px), link/Retry buttons are at least 44px tall and stack below the text under 640px; at 1280px the link sits inline right.
## 3. S2 Features page (Stories 1.3.3, 4.1.4)

**Entry:** Settings -> Features, or "Change in Feature Flags" link. **Exit:** nav away; the enforce dialog has Cancel/Escape; "Edit stages" link on the enforce row.

```
 Autonomous backlog
 +------------------------------------------------------+
 | Diagnose & Nudge            [ Off |o  ]  Off          |
 |   Default: Off (not set explicitly)                   |
 |   Flip when ... / Rollback ...    Takes effect w/o reload |
 |   +--------------------------------------------------+|
 |   | Stall nudge          [ |o On ]  On (inactive)     ||
 |   | Has no effect until Diagnose & Nudge is On.      ||
 +------------------------------------------------------+
```

- Group "Autonomous backlog": `diagnose_nudge_enabled`, then `autonomous_stall_nudge_enabled` indented beneath it. State "On (inactive)" + "Has no effect until Diagnose & Nudge is On." when the parent is off; the toggle stays operable.
- Every row: Default / Flip when / Rollback line (served from description or `statusDetail`, not JSX), effective value plus source ("Default: Off (not set explicitly)" vs "Set explicitly: On"), `LIVE_FLAG_NOTE`.
- Switch semantics: `role="switch"`, `aria-checked`, stable label (never flips Enable/Disable), `aria-describedby` to description/statusDetail, hit area at least 44x44px (visual may stay 44x24; also satisfies WCAG 2.5.8), visible `:focus-visible` ring not obscured by sticky chrome (2.4.11). Confirmation `role="status"`; failures `role="alert"`; focus is not moved on success; pending uses `aria-disabled` not `disabled` (focus is retained); while a row's change is in flight Space and Enter on its switch are ignored (no second request, nothing queued), the row's "Revert to Off" is `aria-disabled` as well (one in-flight change per flag), and the row's status region announces "Saving <flag>..." once and then the result (UX-48).
- Page states: loading (`aria-busy` skeleton rows, no switches rendered as Off), load failed ("Couldn't load feature flags: <reason>" `role="alert"` + Retry; no switches shown, so a failure never renders as Off), empty group (group header omitted), toggle-failed (switch reverts to the server value, row shows "Couldn't change <flag>: <reason>" + Retry), toggle-pending ("Saving..."), stale (value with "(as of <ago>, may be out of date)" when a refetch fails).
- A group "Workflow engine" holds the shadow flag and three enforce rows, one per caller class: "Enforce for operators (this UI)" (`backlog:workflow-engine-enforce`), "Enforce for agents (MCP tools)" (`-enforce-agent`) and "Enforce for automation (lifecycle, sync, pollers)" (`-enforce-system`), in the recommended flip order. Each row carries its own "Revert to Off" and "Edit stages" controls.
- **Per-class flags are independent on purpose, with the recommended order shown inline (UX-46).** Any class may be enforced in any order (they carry different risk and different soak windows, plan Risk Control), so nothing blocks enforcing agents or automation first. The group intro says so: "These three switches are independent. Recommended order: operators, then agents, then automation." Each enforce row carries its own step line under the label: operators "Step 1 of 3 (recommended first).", agents "Step 2 of 3. Enforce after operators have soaked.", automation "Step 3 of 3. Enforce last; it needs the denied-transition recovery in the deployed binary." When the operator turns on a class whose recommended predecessor is not enforced yet, the confirm dialog adds one non-blocking advisory line (`data-testid="feature-flag-enforce-order-advisory"`, for example "Operators are not enforced yet; the recommended order is operators first."), which needs no acknowledgement. The Stages banner link ("Change in Feature Flags") targets the first class not yet enforced in this same recommended order.
- Enabling any enforce flag is the only action with a confirm dialog. It is a NEW component, `AlertConfirmDialog` (Task 4.1.4e), not `PiDisableWarningDialog`: `role="alertdialog"`, `aria-modal`, `aria-labelledby` heading, `aria-describedby` body, **initial focus on Cancel** (via `useDialogFocusTrap`'s `initialFocusRef`), Tab/Shift+Tab trapped, Escape and overlay click cancel, focus returns to the switch. Buttons "Cancel" / "Enforce" in that DOM and tab order. Body copy: "Stage edits will change which transitions and gates are allowed." for that class; the automation row adds "Blocked automated transitions appear as stuck items (transition_denied) until the gate is satisfied."
- **Who owns what (UX-43).** `useDialogFocusTrap` owns initial focus, the Tab trap, Escape and focus return to the element focused when the dialog first rendered; it has no overlay-click, no inert background and no explicit return target. `AlertConfirmDialog` therefore owns: the portal; `role` and `aria-*`; overlay click = Cancel, only when `e.target === e.currentTarget` (the `HostKeyTrustDialog` precedent, which also focuses Cancel); the button row; and an optional `returnFocusRef` that it focuses after close, because Safari and Firefox on macOS do not focus a button on mouse click, so `document.activeElement` at mount can be `body` and the hook would return focus to nothing. The switch handler also calls `switchRef.current.focus()` before opening. The background is not made `inert` (the hook does not support it); `aria-modal="true"`, the Tab trap and the full-viewport overlay are the containment, a stated limit. After Confirm succeeds, and after Cancel, Escape or overlay click, the same switch element (stable `key`) holds focus.
- **Evidence region states (UX-44).** The evidence block `data-testid="feature-flag-enforce-evidence"` is a single `role="status"` region mounted with the dialog, the only live region in the dialog. Loading: "Checking readiness evidence..." with `aria-busy="true"`; Enforce is `aria-disabled`; the acknowledgement row is not rendered yet; nothing is announced. Resolved clean: `aria-busy` is removed and the three evidence lines appear and are announced once ("Readiness evidence: 0 shadow differences, soak verdict READY, 0 items would lose an exit."); Enforce becomes enabled. Resolved not clean: the same, with the announcement ending "Acknowledgement required.", and the acknowledgement row (`feature-flag-enforce-ack`) appears. Failed: "Couldn't load readiness evidence: <reason>" with a Retry button (`feature-flag-enforce-evidence-retry`) inside the region, the acknowledgement row shown (label unchanged), Enforce `aria-disabled` until it is ticked; never zeros. Retry keeps focus on itself while pending and after a repeat failure; after success it unmounts and focus moves to Cancel, never to `body`.
- **Layout and focus when the acknowledgement appears.** The evidence block reserves the height of its three lines while loading, so numbers arriving cause no jump. The acknowledgement row is inserted between the evidence block and the button row: on desktop the button row moves down one row, at 360px the dialog body scrolls and the buttons stay reachable. Programmatic focus never moves when the row appears (it stays on Cancel or wherever the user put it); tab order becomes acknowledgement, Cancel, Enforce when the row is present. The whole acknowledgement label (checkbox plus text) is the hit area, at least 44px tall and the full dialog content width (UX-54).
- **Why Enforce is disabled.** While `aria-disabled`, Enforce has `aria-describedby` pointing at a visible hint (`data-testid="feature-flag-enforce-hint"`): "Waiting for readiness evidence." while loading, "Tick the acknowledgement above to enable Enforce." when gated; the attribute is removed when Enforce is enabled. Activating an `aria-disabled` Enforce changes nothing and leaves focus where it is.
- **Readiness re-check at confirm (UX-45).** Evidence fetched when the dialog opened can be stale when Enforce is clicked. Clicking an enabled Enforce first re-fetches `GetWorkflowEngineStatus` (the same RPC) and compares `class_readiness[class]` with what the operator was shown. (a) Unchanged, or not worse than what was acknowledged: `UpdateFeatureFlag` is called. (b) Worse (divergence count up, verdict moved away from READY, stranded count up, or a previously clean view now unclean): the flag is NOT changed, the evidence region updates in place and announces "Readiness evidence changed since you opened this dialog: <what changed>. Review it and confirm again.", a ticked acknowledgement is cleared and required, Enforce returns to `aria-disabled`, and focus moves to the acknowledgement checkbox (the next required action). (c) The re-check fails: the flag is NOT changed and a `role="alert"` in the dialog (`feature-flag-enforce-recheck-alert`) reads "Couldn't re-check readiness: <reason>" with Retry; Enforce stays `aria-disabled` until a re-check succeeds. While it runs, Enforce is `aria-disabled` reading "Re-checking readiness..." and the buttons keep their positions. Accepted residual: the check is client-side because `UpdateFeatureFlag` is a bool-only RPC shared with other clients (plan Pattern Decisions, "Mode flags"); the window between the re-check response and the write is one RPC round trip, and the flag write is reverted in one click.
- **Readiness evidence at decision time (UX-35)**, shown inside the dialog body from `GetWorkflowEngineStatus.class_readiness` for the class being enforced:

```
+--------------------------------------------------+
| Enforce for operators (this UI)?                 |
| Stage edits will change which transitions and    |
| gates are allowed.                               |
|  Shadow differences in the last 24h:  0          |
|  Soak verdict:  READY                            |
|  Items that would lose an exit:  0               |
|  Rollout checklist: docs/how-to/flip-workflow-   |
|  engine-enforcement.md                           |
|  [ ] I have reviewed this evidence and the       |
|      rollout checklist   (shown when not clean)  |
|              [ Cancel ]      [ Enforce ]         |
+--------------------------------------------------+
```

  Clean evidence (0 differences, READY, 0 items) leaves Enforce enabled. Differences above 0, a verdict other than READY (including "needs your acknowledgement" for a low-volume class), or evidence that failed to load ("Couldn't load readiness evidence" + Retry, never zeros) disables Enforce (`aria-disabled`) until the acknowledgement box is ticked. The dialog never hides a bad number. If the confirm call itself fails, the dialog closes, the switch stays Off and a `role="alert"` shows the reason + Retry. Rollback ("Revert to Off") is in the same row, no dialog; the row also shows the "Edit stages" link.
- **Dialog on mobile (360px):** full width minus a 16px gutter; buttons stacked full width, 44px tall, Cancel on top and Enforce below with a 16px gap so a thumb mis-tap does not land on Enforce; the evidence block scrolls inside the dialog, the buttons stay reachable. On desktop: centered, max 480px, buttons right-aligned, Cancel then Enforce.
- **Summary line (UX-39):** above the "Workflow engine" rows, `data-testid="workflow-engine-summary"`, static text with no `role` (live-region policy; a change made by toggling is announced by that row's confirmation, which appends the new count, for example "Enforce for operators is On. 1 of 3 caller classes enforced."): "0 of 3 caller classes enforced. Shadow: edits are compared with the built-in rules but not applied." / "1 of 3 caller classes enforced (Partly enforced): operators enforced; agents and automation still in shadow." / "All 3 caller classes enforced." / "Mode unavailable: couldn't read the engine status." Plain definitions: **Shadow** = the engine computes what it would do and records differences, but the built-in rules still decide; **Partly enforced** = at least one caller class (operators, agents, automation) is enforced and at least one is not. The same words appear in the Stages banner. The summary block also carries the review-due line `workflow-engine-review` (UX-55, section 2).
- **Deep link and focus (UX-37, UX-47):** each flag row has `id="flag-row-<flag name with ':' replaced by '-'>"`, `tabIndex={-1}`, `scroll-margin-top: calc(var(--header-height) + 16px)` and `scroll-margin-bottom: calc(var(--bottom-nav-height) + 16px)`. Those are the existing CSS custom properties in `app/globals.css`, so the sticky-chrome offset is a token and not a magic number (the Header is hidden under 900px, where the BottomNav is the obscuring chrome). The page reads `window.location.hash` on mount and again on `hashchange` and `popstate`. Next's client-side navigation from the Stages banner mounts this page fresh, so mount is the case that matters; Next's `pushState`-based same-page hash links fire neither event, and no such link exists today (stated limit). Rules: (1) the effect is keyed on (hash, list state) and runs once per distinct hash value, acting only when the list reaches a terminal state: `loaded` focuses the row if present (an unknown hash is ignored, no error), `failed` does nothing, and after a successful Retry it runs once for the still-present hash; a 10 s ceiling from mount ends the attempt if the list is still loading. (2) It must not steal focus: it is skipped, with no scroll either, if the user has pressed a key or pointer button since mount (a capture-phase listener records it) or `document.activeElement` is anything other than `body` or the page container. (3) When it acts it calls `row.focus({preventScroll: true})` and then `row.scrollIntoView({block: "center"})`, so the row is not under the Header or BottomNav (WCAG 2.4.11). (4) A later refetch that re-renders the list does not move focus again.
- **Staleness (UX-36):** the flag list re-fetches once when the tab regains focus or becomes visible; rows and summary update in place; a failed refetch keeps the last values with "(as of <ago>, may be out of date)". The engine rows' note reads "Takes effect within a few seconds, without reload" (the mode reader caches about 1s) instead of `LIVE_FLAG_NOTE`'s bare "without reload".
- Per-flag extras go through a `flagExtras` registry keyed by flag name rather than another `name ===` branch.
- **Responsive:** single column at 360px (label, switch, description stacked; switch right-aligned on first line, never wrapped under text); at 1280px label/description left and switch right. (Dialog layout: see the dialog bullets above.)

## 4. S3 Quota page: `/settings/backlog-quota` (Story 2.2.1)

**Entry:** a Link entry "Backlog Quota" on the Settings index (a plain `<Link>` like the other `helpLink` entries, not a tile; also registered in `web-app/src/lib/nav-pages.ts`) (`/settings`, `data-testid="settings-backlog-quota-link"`; the Settings layout has no nav list), plus a link from the quota flag row on the Features page. **Exit:** Revert (restores read-back values), nav away; **unsaved edits are guarded (UX-38):** a visible "Unsaved changes" status line (`backlog-quota-status`, announced once per transition) plus Revert, and a leave guard: `beforeunload` while dirty, and an `AlertConfirmDialog` "Discard unsaved changes?" (initial focus "Keep editing", confirm "Discard") for same-origin in-app link clicks and browser Back. Limit: the Next.js app router has no route-change veto, so programmatic `router.push` from other code is not covered. On a phone this stops an accidental back-swipe from losing the edits.

```
+------------------------------------------------------+
| Backlog Quota                                        |
| Effective now: gate On, budget 5,000,000 tokens,     |
|   warn at $5.00                                      |
| (!) Gate is on but no budget is set ... (if budget 0)|
| Quota gate                       [ |o On ]           |
| Assumed window token budget  [ 5000000 ]             |
|   0 = proactive headroom signal disabled             |
| Pause below headroom %   [ 20 ]  Resume margin % [10]|
| Default soft cost budget (USD) [ 5.00 ]  empty = off |
| [ Save ]  [ Revert ]    status / error summary       |
```
