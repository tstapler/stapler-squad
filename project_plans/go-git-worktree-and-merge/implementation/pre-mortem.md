# Pre-mortem: go-git-worktree-and-merge
**Date**: 2026-09-07

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | go-git's pure-Go object/tree walking is slower than the C `git` binary at this host's real scale (50-90+ concurrent worktrees), so flipping the global flag on violates the stated Performance SLO — but nothing in Phase 5 (differential/fuzz/interop, all correctness-only) would catch this before rollout. | p95 session-creation or `MergeMainIntoWorktree` latency in the `implementation="native"` Tempo-span bucket climbs above the `"legacy"` bucket's, first noticed as slow session starts or backlog PR-fix timeouts under real concurrent load, not in CI (which never runs at production concurrency). | Add a Phase 5 load/benchmark epic: `go test -bench` driving N concurrent `Setup`/`MergeMainIntoWorktree` calls against a production-sized repo, comparing native vs. legacy p50/p95/p99 (per `docs/reference/benchmarks.md` conventions), gating the global-default flip alongside the already-required differential/fuzz/interop gates. |
| 2 | The native merge path writes commit/tree/blob objects as loose objects via go-git's object-writing primitives with nothing equivalent to real git's implicit `git gc --auto` trigger, so weeks of backlog-automation merge volume leaves `.git/objects` growing unbounded, degrading *every* git operation against that repo (native and legacy alike, since they share one on-disk repo). | `.git` directory size trending up in disk-usage monitoring, or an unrelated git operation (`git status`, `FetchBranch`) gradually slowing down weeks after the merge flag flips on — not obviously attributable to this project since the slowdown surfaces in code paths it never touched. | Add a loose-object-count metric to the Observability Plan with an alert threshold, and/or a periodic (low-frequency, out-of-hot-path) `git gc --auto` invocation after N native merges — acceptable under the Constraints, which only forbid subprocess use on the worktree/merge hot path, not maintenance. |
| 3 | `materializeConflictOnAbort` writes real stage-1/2/3 index entries and conflict-marker text to the working tree, then immediately reverses via `abortNativeMerge` — but no lock is held across that write-then-abort window against a *concurrent reader* of the same worktree path (UI file-watcher, backlog automation's prompt-builder, a human's IDE), so a reader can observe transient conflict state that's already gone by the time it acts on it. | A backlog fix-agent's prompt describes conflicts that no longer exist when it tries to resolve them (working tree already clean), or the web UI's live diff view briefly flashes conflict markers on a merge that reports `Merged: true` moments later. | Document (and test) that `MergeMainIntoWorktree`'s return value is the sole source of truth for conflict state — no consumer should poll the filesystem mid-call — and/or hold the existing worktree lock across the full materialize-then-abort sequence; add a concurrency test asserting a concurrent read during the merge call sees only pre-merge or fully-persisted-conflict content, never a mid-transition sliver. |
| 4 | The plan's ground truth for worktree admin-file conventions comes from `git/git@master` (Task 1.2.1a) and this one dev environment's `git config` (Task 3.3.1a) — but real git binaries on other developer machines, CI runners, or the production host may be a materially different (often older) version with different admin-file conventions, so native-created worktrees pass this project's own git-version-pinned tests while breaking interop elsewhere. | A user or CI runner on a different git version reports `git worktree list --porcelain` misclassifying, or `git worktree prune` erroring on, a native-created worktree — while this project's own CI (one pinned git version) stays green throughout. | Record the git version this project's tests actually run against, declare an explicit minimum/maximum supported git version (absent from `requirements.md`'s Constraints today), and add at least one interop test run against an older pinned git version via a CI matrix entry rather than trusting a single local check. |
| 5 | Epic 4.4 ships spans, a latency histogram, and merge-outcome/retry counters, but no task defines an alert threshold, a dashboard, or who actually watches them during the canary window before either global default flips — so a subtle correctness regression (e.g., the diff3 library's own maintainer-flagged "currently erroneous" edge case, per the adversarial review) could ship to the global flip with the metrics present but unreviewed. | A merge that should have auto-resolved (or shouldn't have) is discovered only when a user notices a wrong merge result days after the global flag flipped — not from the metrics, which existed the whole time. | Add a concrete canary-observation task to the Migration Plan / Risk Control: a named before/after comparison of the conflict-rate and retry counters over a defined window, with an explicit sign-off step required before flipping either global default — not just "the metrics exist." |

## P1 Items (address before implementation)
- (none) — all five items above are P2/P3: each is individually recoverable via the plan's existing instant-rollback feature flags, and none blocks correct behavior on the common path. They should still be triaged into the plan (most cheaply folded into Phase 5's gate list and the Migration Plan's canary section) before the global-default flip, not before implementation starts.
