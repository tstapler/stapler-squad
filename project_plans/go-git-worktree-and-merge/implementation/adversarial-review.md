# Adversarial Review: go-git-worktree-and-merge

**Date**: 2026-09-07 (re-review iteration 1)
**Verdict**: CONCERNS

## Blockers — Re-Review (iteration 1)

All 4 prior blockers are resolved. Non-blocking items below (Concerns, Minors) still stand — see original review for their text; they were not re-reviewed this pass.

- [x] **PASS — `WorktreeRedirectFile` now uses `AdminFileWriter`.** Task 2.1.1c (`implementation/plan.md` L264-266) writes the redirect file via a second `AdminFileWriter` instance rooted at `worktreePath`, and explicitly states "a bare `os.WriteFile` is **not** acceptable here," citing the same crash-recognizability rationale the original blocker raised (real git's `worktree list --porcelain` inspects the admin-dir side, not this file's content). Root cause addressed, not just annotated around.

- [x] **PASS — race test added and contradiction explicitly resolved; Task 3.4.1b uses the resulting protection.** ADR-001's new "Update: Re-examination of Alternative #2's deferral" section (`decisions/ADR-001-atomic-admin-file-write-protocol.md` L132-164) states the resolution plainly: "`pitfalls.md`'s conclusion governs... `architecture.md`'s contrary claim rested on a test that raced two real `git` processes against each other, never a go-git writer against a real `git` writer, so it does not actually support the claim it makes." It then narrows the deferral per ref-write site rather than leaving a blanket answer. Plan.md's Story 2.5.3 (L466-490) adds the concrete race: Task 2.5.3a (`TestNativeRefWrite_UnprotectedRace_CanCorruptRef`) with acceptance criterion "at least one trial [of 50] produces a ref file that is neither `def456` nor `ghi789` nor a valid prior value"; Task 2.5.3b implements `writeRefWithLockSentinel`; Task 2.5.3c (`TestNativeRefWrite_LockSentinel_NeverCorruptsAgainstRealGit`) with criterion "the ref file always contains exactly one of the two attempted values... the losing writer gets a normal compare-and-swap-style failure." Task 3.4.1b (L699-701) confirms the merge ref-advance calls `writeRefWithLockSentinel`, "**not** go-git's bare `SetReference`," and explicitly contrasts this with Task 2.1.2a's fresh-branch-ref creation, which is unaffected by the resolution and stays on the deferred (unprotected) path for the stated reason (no in-scope real-git subprocess writes a not-yet-existing ref first).

- [x] **PASS — both decisions now explicit table rows, with a pinning test for the rename/modify case.** The Pattern Decisions table (L87-88) has two new rows: "Rename+modify merge collision" (Pattern: treated as independent, uncorrelated Insert/Delete/Modify changes, not detected as a conflict; Source: `features.md` §1; Reason: matches the CI-bot merge-pattern scope-cut used elsewhere in the plan) and "CRLF/line-ending normalization" (Pattern: skipped entirely; Source: `pitfalls.md` §6; Reason: this repo's sessions are Linux/macOS-only, and skipping avoids a documented corruption vector). Both carry rationale and a cited source, not bare mentions. Story 3.2.2's fourth acceptance criterion (L558-559) and Task 3.2.2e (L578-580, `TestThreeWayFileMerger_RenameModifyCollision_TreatedAsIndependentChanges_NotConflict`) pin the rename/modify decision as a passing test, matching the review's recommendation.

- [x] **PASS — gitlink conflict now has a task, acceptance criterion, and test.** Story 3.2.3's third acceptance criterion (L589-590) covers the gitlink case explicitly: a gitlink entry changed on either side must be reported conflicted with reason `"gitlink conflict"`, with neither `lineDiff` nor `renderConflictHunk` ever invoked for it. Task 3.2.3c (L601-603) implements the detection (checks `filemode.Submodule`/`0160000` on either changed side, classifies immediately, skips line/mode/binary diff entirely for that path, run *before* mode/binary detection) and cites why this doesn't contradict `requirements.md`'s "no submodule-aware merging" exclusion. Task 3.2.3d (L605-607) adds `TestThreeWayFileMerger_GitlinkConflict_NeverContentMerged`.

## Concerns

- [ ] **`MergeMainIntoWorktree`'s dispatch-coverage test silently drops one of the three named real call sites.** Story 3.4.2's own prose names all three real call sites (`drift.go`, `backlog_service_triage.go`, `backlog_lifecycle.go`'s `branchReconciler`), matching `architecture.md` §1b's enumeration exactly — but Task 3.4.2c's test only explicitly names two: *"a second test confirms `drift.go`'s `EnsureBranchSyncedWithMain` and `backlog_lifecycle.go`'s `branchReconciler` value both transitively pick up the native path... "* `backlog_service_triage.go`'s `syncPRBranchWithMain` is never mentioned again. Functional risk is low (all three route through the same renamed public function), but this is exactly the kind of silent-drop the review brief asked to check for. **Recommendation**: add `syncPRBranchWithMain` to Task 3.4.2c's test list explicitly.

- [ ] **`SetupLocked()` — one of the 9 real call sites into the Setup group, and structurally distinct because it runs nested inside the caller's own already-held `WithRepoWorktreeLock` (`CreateBacklogWorktree`, per `architecture.md` §1a) — has no dedicated dispatch test anywhere in Epic 2.1 or 2.5.** Only `Setup()`'s dispatch is tested (Task 2.1.3c). If `SetupLocked()` calls the same private `setupNewWorktree()` this is probably fine by composition, but the plan never states or verifies that, and `SetupLocked`'s already-locked calling context is precisely the kind of edge case `architecture.md` flags as needing explicit verification, not assumption. **Recommendation**: add an explicit `TestSetupLocked_NativeFlagOn_DispatchesCorrectly` alongside Task 2.1.3c's tests.

- [ ] **Branch-ref creation during native `Add` (Task 2.1.2a) isn't given the same atomic-write scrutiny as the structurally identical merge-commit ref-advance.** Task 3.4.1b explicitly flags an open verification question for the merge path's ref write — *"still verify in review it isn't one of the non-atomic paths ADR-001 flags... if verification finds a real risk, route this write through `AdminFileWriter`-equivalent handling instead"* — but Task 2.1.2a's structurally identical ref-creation-via-`Checkout` gets no equivalent caveat. **Recommendation**: apply the same "verify, and have a fallback plan" language to Task 2.1.2a.

- [ ] **The shared-`WithRepoWorktreeLock`-registry invariant is established retroactively (Epic 2.5), after four separate epics (2.1–2.4) have each independently done "rename existing body, add dispatch wrapper."** `architecture.md` §2(c) calls getting this wrong "a concrete design constraint... not a hypothetical," yet the plan's only safeguard against one of those four independent renames accidentally narrowing the lock's scope is a single ~3-minute confirm-and-fix task (2.5.1a) at the very end. **Recommendation**: establish and test the "the lock wraps the dispatch point, not either individual branch" shape once, in Epic 2.1 (Story 2.1.3), so Epics 2.2–2.4 have a proven pattern to mechanically copy rather than each independently getting it right and being checked only after the fact.

- [ ] **The cross-implementation interop matrix (Story 5.3.1) only crosses clean, successfully-completed provenance — it never crosses a crashed/interrupted mid-operation state.** The Migration Plan explicitly requires the `locked`/`initializing` marker convention so that whichever implementation next touches an abandoned worktree must treat it as safe to force-remove and retry (`architecture.md` §5) — but no task in Epic 5.3 tests "native `Add` crashes mid-checkout (locked marker left behind) → flag flips to legacy → legacy's `Setup()` recovers it" or the merge-path equivalent ("native merge crashes between `writeConflictedIndex` and `abortNativeMerge` → flag flips → legacy code touches the worktree next"). **Recommendation**: add at least one crashed-state cross-implementation test to Story 5.3.1, not just clean-state crossings.

- [ ] **The diff3 line-level reconciliation is built on the exact library a go-git maintainer is quoted (in this project's own research) calling "currently erroneous" for this purpose, with no dedicated mitigation beyond the general fuzz/differential gate.** Task 3.2.1a builds `lineDiff` on go-git's `utils/diff` package, which wraps `sergi/go-diff`'s `diffmatchpatch` — `pitfalls.md` §1.2 quotes go-git#942's maintainer thread describing `sergi/go-diff` as "currently erroneous" for diff3 use. The plan doesn't investigate what "erroneous" refers to concretely, nor explain why it doesn't apply here, relying entirely on Phase 5's fuzz/differential-testing gate to catch any resulting divergence after the fact. **Recommendation**: at minimum, log this as a named risk with a specific mitigation (e.g., "Phase 5's fuzz corpus must include the shapes the go-git thread's linked discussion identifies as `sergi/go-diff`'s failure modes, not just generic adjacent/same-line/add-add/delete-modify shapes"), since the plan's own cited research raises it and the plan currently doesn't answer it.

## Minors

- `Cleanup()` (= `Remove`+`Prune`, one of the 12 real call sites) has no test of its own composed dispatch — coverage is inherited from `removeLocked`'s and `Prune()`'s individual tests rather than verified end-to-end.
- Task 2.1.2 relies on go-git's `Worktree.Checkout()` for the entire clean-add path against a *linked* worktree — the exact topology `pitfalls.md` §1.5 documents repeated, real bugs in for `Worktree.Status()` (commondir-indirection resolution issues). The plan's interop test (subprocess `git status --porcelain`, not go-git's own `Status()`) is the right mitigation, but a quick check of go-git's issue tracker for `Checkout`-specific (not just `Status`-specific) linked-worktree bugs would cheaply close this out rather than leaving it implicit.
- `useNativeWorktree`/`useNativeMerge` call `config.LoadConfig()` on every dispatch (Task 2.1.3a), on a path this project's own Non-Functional Requirements say must handle 50-90+ concurrent worktrees at or below current subprocess latency. The plan doesn't state whether `LoadConfig()` is cheap/cached (it presumably mirrors `EffectiveStreamHubEnabled`'s already-proven-acceptable pattern, but this isn't confirmed in the plan itself).
