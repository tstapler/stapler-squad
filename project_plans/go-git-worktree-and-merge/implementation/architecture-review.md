## Concerns

- **Story 3.3.2 (`ConflictEntry`/`NewConflictEntries`/`writeConflictedIndex`) — go-git's own `index.Merged` constant is mislabeled and collides with `AncestorMode`; the plan documents the *sort* landmine in this same struct but not this second one — remediation: add an explicit guard/comment.** Verified directly in `plumbing/format/index/index.go:31-39`:
  ```go
  const (
      // Merged is the default stage, fully merged
      Merged       Stage = 1
      // AncestorMode is the base revision
      AncestorMode Stage = 1
      OurMode      Stage = 2
      TheirMode    Stage = 3
  )
  ```
  `index.Merged`'s doc comment claims it means "the default stage, fully merged" — i.e., real git's stage 0, the value every non-conflicted entry carries — but its actual value is `1`, identical to `AncestorMode`. `research/stack.md` §3 already reads this exact const block (it cites `index.Merged/AncestorMode = 1`) and correctly derives the sort-order bug from the encoder, but neither `stack.md`, `architecture.md`, nor `plan.md`'s `ConflictEntry`/`sortConflictEntries`/`writeConflictedIndex` glossary entries name this second landmine: a future maintainer skimming go-git's exported API and reaching for `index.Merged` to represent "this entry has no conflict" (a very natural reading of its doc comment) gets `Stage(1)`, which is indistinguishable from `AncestorMode` once encoded — producing an index real git would decode as a spurious ancestor-stage entry for a path that should show as clean. Task 3.3.2c's own wording ("remove the stage-0 entry for each conflicted path") implicitly gets this right by treating stage 0 as a literal, but says so only implicitly, not as a stated rule the way the sort-bug got `sortConflictEntries` as a named, tested choke point.
  **Remediation**: add one line to `NewConflictEntries`'s or `writeConflictedIndex`'s doc comment (`native_merge_index.go`) stating explicitly: "never use `index.Merged` — it is mislabeled upstream and equals `AncestorMode` (1), not real git's stage 0; unconflicted entries must keep their existing `Stage(0)` value untouched." This is a one-line documentation fix, not a design change — the existing `ConflictEntry` choke-point design (Value Object, single construction point) already structurally prevents the bug as long as the comment exists to stop someone reaching for the wrong constant later.

- **`GitWorktree`'s already-large method surface (47 methods, 3 files >690 lines) grows further with thin dispatch wrappers, and the plan's Tech Debt Disposition doesn't weigh this against the "isolate via seam" choice — it only justifies not introducing an interface.** The chosen seam (Task 2.1.3b, 2.2.2a, 2.4.2a, 2.3.2a: rename body to `legacy*`, add `native*`/dispatch wrapper at the original name) is the right call over a new `WorktreeManager` interface for the reasons `architecture.md` §4 and `plan.md`'s Pattern Decisions table give (single active implementation per call, 21+3 call sites, `interface-pollution-checklist` precedent) — this is not being second-guessed. But the *disposition table itself* only evaluates "refactor vs. interface vs. seam" for the *existing* code; it never states that the seam pattern being reused (`commandRunner`-style branch) is being applied a fifth/sixth time on a receiver that was already at 47 methods before this project started, and that every new `nativeX`/`legacyX`/dispatch trio adds 2-3 more. Per this repo's own `code-architecture-best-practices` skill guidance (a God Object gaining "another method" is called out there as *not* a valid instance of "extend as-is"), the plan should have made this trade-off explicit rather than silent, even though the actual chosen action (thin one-line dispatch, not a home for new logic) means the SRP damage is real but small. Confirmed the new methods are pass-throughs, not logic homes: e.g. `setupNewWorktree`'s post-refactor body is `if useNativeWorktree(...) { return g.nativeSetupNewWorktree() }; return g.legacySetupNewWorktree()` — one branch, no business logic on the receiver itself.
  **Remediation**: no code change needed at plan-approval time; add one sentence to the Tech Debt Disposition table's `worktree_ops.go` row acknowledging the method-count growth is accepted because the added methods are pure dispatch (not a new responsibility), so a future `code-hotspot-analysis`/`quality:reflect-and-fix` pass on this file isn't blindsided by seeing method count jump after this project lands.

- **Epic 2.5 / Story 2.5.1's acceptance criterion for the shared-lock guarantee is under-specified relative to how central `architecture.md` §2c says it is.** `architecture.md` §2(c) and the Migration Plan both call the shared `WithRepoWorktreeLock` critical section "the load-bearing safety net" for the entire flag-flip-mid-burst threat model — every other safety property (no corruption on flip, safe fresh-per-call evaluation) is stated as depending on it. Story 2.5.1's Task 2.5.1a is phrased as a code-reading confirmation ("Read `Setup()`/`removeLocked()`/`Prune()`'s existing bodies to confirm... Adjust wrapping order... if the rename... accidentally moved the lock"), i.e. a manual check with a conditional fix, not a task that *asserts* the invariant as a standing property. Given how much of the plan's safety case rests on this one property, a single race test (Task 2.5.1b) proving it once is good but the task that's supposed to *guarantee* the lock wraps every dispatch point reads as best-effort ("adjust... if... accidentally moved").
  **Remediation**: reword Task 2.5.1a as a hard precondition checked by the test in 2.5.1b for every one of `Setup`/`removeLocked`/`Prune`/`findLiveWorktreeForBranch` individually (four assertions, not one general race test), or add a lightweight static check (e.g. a `go vet`-style grep-based test asserting `WithRepoWorktreeLock(` appears textually before each `useNative*` call in the four dispatch functions) so a future edit that reorders the wrapping is caught mechanically, not only by code review.

## Nitpicks

- The plan never states which package `nativeSetupNewWorktree`/`nativeRemoveWorktree`/etc. live in relative to `GitWorktree`'s receiver methods — Task 2.1.1 through 2.1.2 describe `nativeSetupNewWorktree` as taking plain parameters (`repoPath`, `branchName`, `baseCommitSHA`, `worktreePath`), but Task 2.1.3b's dispatch line calls `g.nativeSetupNewWorktree()` with no arguments (implying a receiver method that reads `g`'s fields). Both shapes appear in the plan for the same function; worth a one-line clarification (is there a receiver-method wrapper *and* a free function, or does the free function's signature get reduced to reading off `g` at the call site) before Epic 2.1 starts, so the implementation subagent doesn't have to guess.
- `Merge` verification for the clean-3-way path (Task 3.4.1b) flags its own uncertainty about whether `SetReference` needs `AdminFileWriter`-equivalent handling ("if verification finds a real risk, route this write through..."). This is appropriately hedged already (Unresolved-Questions-style), not a defect — noting only because it's the one other spot besides the two named Unresolved Questions where a decision is deferred past plan-approval without being listed in the Unresolved Questions section itself.
- `research/architecture.md` §1a's collateral finding (three-plus duplicate `git worktree list --porcelain` parsers) is correctly kept out of scope in the Tech Debt Disposition table with a clear justification — flagging only that this is a well-handled example other rows could match in explicitness.
