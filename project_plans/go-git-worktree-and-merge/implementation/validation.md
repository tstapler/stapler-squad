# Validation Plan: go-git-worktree-and-merge

**Date**: 2026-09-06

## Happy Path Scenario

Given a main repo with `feature-x` behind `origin/main` by non-conflicting commits and both `native_git_worktree`/`native_git_merge` flags forced on for the session, when a caller invokes `GitWorktree.Setup()` to create the linked worktree and then `MergeMainIntoWorktree(worktreePath, "main")` to bring it current, then the resulting worktree's admin files and merge commit are byte-for-byte indistinguishable from what real `git worktree add` + `git merge --no-edit` would have produced — verified by running real `git worktree list --porcelain`, `git status --porcelain`, and `git log -1 --format=%P` as subprocesses against the result — with zero `git worktree`/`git merge`/`git merge --abort` subprocess spawns along the way.

This is the anchor: every other test below is a variation — a different merge outcome (up-to-date/fast-forward/conflict), a different lifecycle op (remove/list/prune), a different flag state (off, or flipped mid-lifecycle), or a failure injected into one step of this same pipeline.

## Migration Reversibility Tests

*(Per Step 5: this project's "migration" is a feature-flag flip over on-disk git plumbing, not a schema migration. The equivalent of a schema up/down test is proving the legacy subprocess implementation still operates correctly on artifacts the native implementation created — including artifacts left in a partially-written state by an interrupted native operation — after the flag is flipped back off.)*

| Requirement | Test File | Test Name | Type | Scenario |
|---|---|---|---|---|
| Flag flip is fully reversible after clean native use (`requirements.md` Migration Plan: "either implementation can create, read, remove, or prune a worktree the other created") | `session/git/native_interop_test.go` | `TestNativeGitRollout_migration_should_BeReversible_When_FlagFlippedOffAfterNativeWorktreeAndMergeExist` | Migration | *Given* both flags forced on, a worktree is created via `nativeSetupNewWorktree` and then merged (including one run that produces a real `Conflicted: true` result, materializing stage-1/2/3 index entries and conflict markers before `abortNativeMerge` cleans them up) — *When* both flags are then flipped off (global default, no override) — *Then* `legacyRemoveWorktree`, `legacyWorktreePrune`, `legacyFindLiveWorktreeForBranch`, and a subsequent `legacyMergeMainIntoWorktree` call against the same worktree all succeed with no error and no on-disk corruption, verified by real `git worktree list --porcelain` / `git status --porcelain` subprocess checks after each step. |
| Flag flip is safe even when native left an interrupted admin-dir (`requirements.md`'s "crashed/interrupted mid-operation states", extending Story 5.3.1's clean-state-only scope) | `session/git/native_interop_test.go` | `TestNativeGitRollout_migration_should_BeReversible_When_FlagFlippedOffAfterInterruptedNativeAdd` | Migration | *Given* a native `Add` interrupted (test-injected failure) between `GitdirFile` and `CommondirFile`, leaving `locked` in place and no working tree populated — *When* the native flag is then flipped off — *Then* `legacyWorktreePrune`/`legacyFindLiveWorktreeForBranch` classify the entry the same way real git's own tooling would (prunable, not corrupt, not silently reused as live) and neither operation errors, panics, or deletes an unrelated live entry. |

**Coverage note**: these two tests subsume Story 5.3.1's three acceptance criteria (already listed individually above under P5) by chaining them into one flag-flip narrative per direction, plus adding the interrupted-state case the individual round-trip tests don't cover. Both directions (old→new, new→old) and the crash case are represented — a same-implementation round trip alone is never accepted as sufficient per the Migration Plan's explicit requirement.

## Test Stack

- **Unit**: Go stdlib `testing` + `testify` (`require`/`assert`) — matches this package's existing convention (`session/git/ops_test.go`, `drift_test.go`). `t.TempDir()`-backed fixtures throughout; no mocking framework — the package already favors real filesystem/git-subprocess fixtures over mocks (`requirements.md`'s "real filesystem-backed tests, not mocks").
- **Integration**: Same `testing`/`testify` stack, distinguished by exercising a real `git` subprocess (`safeexec.CommandContext`, this package's existing test convention) as an oracle/verifier, a real multi-goroutine race under `-race`, or `go test -fuzz`. No separate integration test tag/build constraint exists in this package today — integration tests here live alongside unit tests in the same `_test.go` files, consistent with `ops_test.go`'s current mix of both.
- **Frontend unit**: Jest + React Testing Library, `pnpm` (never `npm`), `--no-coverage` for iteration per `docs/how-to/use-pnpm-in-web-app.md` — mirrors `StreamHubRolloutPanel.test.tsx`/`TymuxRolloutPanel.test.tsx`'s existing structure.
- **E2E / UX**: Playwright + Allure per `tests/e2e/`'s existing conventions (`// @feature` annotation, `data-testid`/ARIA locators only, no `waitForTimeout`), plus this repo's existing Axe Core / Lighthouse CI gate on PRs touching `web-app/src/`.
- **RPC layer**: ConnectRPC handler tests via the existing `server/services/*_test.go` pattern (in-process handler invocation, no network).
