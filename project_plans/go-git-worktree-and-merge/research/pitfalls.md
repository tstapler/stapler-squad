# Research: Pitfalls of reimplementing git worktree/merge plumbing outside real git

Scope: what has gone wrong for other people building the same two subsystems
(linked-worktree lifecycle, three-way merge) on top of go-git, JGit, and
gitoxide — and what that implies for this project's on-disk-interop and
crash-safety requirements. All findings below are sourced from public issue
trackers (`gh issue view` / `gh search issues`, retrieved 2026-09-06) or from
reading the pinned dependency's source directly; each claim below cites where
it came from.

## 1. go-git's own issue tracker: the exact bug classes this project will inherit if it reuses go-git's write paths as-is

### 1.1 HEAD/ref resolution on a linked worktree — this repo's bug is not unique to this repo

- [go-git#1580](https://github.com/go-git/go-git/issues/1580) "`repo.Head()` on a git worktree fails with reference not found" (closed, stale-bot-closed, not actually fixed for all cases): `git worktree add` puts a *symbolic* HEAD in `.git/worktrees/<name>/HEAD` pointing at `refs/heads/<name>`, but the *hash* ref lives in the **main** repo's `refs/heads/<name>`, not under the worktree's admin dir. go-git's resolution didn't join the two until `EnableDotGitCommonDir` was added — a maintainer comment on this exact issue tells the reporter to try `EnableDotGitCommonDir` instead of `DetectDotGit`, which is precisely the flag `session/git/util.go`'s `defaultPlainOpenOptions` already sets (with a comment about a "real-but-wrong result" bug it fixed).
- [go-git#827](https://github.com/go-git/go-git/issues/827) "`go-git` sometimes returns `object not found` when querying for the commit object for the `HEAD`" — open since 2023, unreproducible in isolation, multiple independent reporters ("we have run into the same issue... consistently on our pipelines"). One reporter's fix was `git prune && git gc`, i.e. the underlying object store was in a state go-git's cached view didn't see — same *shape* of bug as this repo's own `getHeadCommitSHA` torn-read/stale-object problem (see §3), but triggered by object-store staleness rather than a ref-file race.
- [go-git#2242](https://github.com/go-git/go-git/issues/2242) "`object not found` when there is a concurrent repacking happening" (open, with a **minimal, runnable Go reproduction** in the issue) — root cause identified precisely: `storage/filesystem/object.go`'s `requireIndex` builds go-git's in-memory pack index **once** and never re-checks it; a concurrent `git repack` (which can be triggered by an ordinary `git gc --auto` after a commit) deletes the old pack files go-git's cached index still points at. Real git's own object-lookup code retries once on a stale index (cited in the issue, linking `git/git`'s `odb.c`); go-git does not. **Direct implication for this project**: `FetchBranch` (per this project's own scope doc) stays subprocess-based and can itself trigger auto-gc/repack in the shared main repo; any long-lived go-git `*Repository` this project holds across a fetch is exposed to this exact staleness class, independent of anything this project's own code writes.

### 1.2 No merge support exists in go-git — and the two attempts at community diff3 both hit real problems

- [go-git#942](https://github.com/go-git/go-git/issues/942) "Add Merge method" — open since 2022, unresolved. Maintainer's own comment: *"Implementing the merge feature in go-git is not an easy task; currently, there is no suitable implementation of the diff3 algorithm in Golang."* The two community diff3 candidates named in the thread each have documented problems: `sergi/go-diff` (which go-git itself already depends on) is described in-thread as "currently erroneous" for this purpose, and `epiclabs-io/diff3` was LGPL-3.0 (a licensing blocker) until a 2024 relicense to MIT. A late 2025 comment on the same thread points at a third-party project (`antgroup/hugescm`) that built a from-scratch pure-Go diff3 + tree-merge implementation "referencing a lot of go-git's code," which is independent confirmation that building this on top of go-git's primitives, rather than finding a reusable off-the-shelf implementation, is genuinely the only path — consistent with this project's own Alternatives-Considered conclusion.
- This confirms the requirements doc's claim (`Repository.Merge()` only implements fast-forward) is not a version-specific gap that will close soon — it is a multi-year-unsolved problem for the whole ecosystem, not just an oversight in this pinned version.

### 1.3 Concurrency: go-git is explicitly documented as not thread-safe, and worktree-mutating operations are named as unfixed

- [go-git#773](https://github.com/go-git/go-git/issues/773) "Concurrency Issues" (open, tracking issue) quotes the maintainers directly: *"`go-git` is not thread-safe. In some cases, concurrent reads may lead to repositories becoming corrupted or actions to yield invalid results (e.g. not finding an existing ref)."* Its checklist explicitly still has `Worktree.Add()` unchecked as of the last update.
- [go-git#1917](https://github.com/go-git/go-git/issues/1917) / [go-git#1978](https://github.com/go-git/go-git/pull/1978): a real data race in `object.(*Tree).FindEntry()`, fixed by adding a mutex — i.e., even *read-only* tree traversal wasn't safe to call from multiple goroutines against the same `*Repository`, let alone safe against a concurrent writer.
- **Implication**: this project's stated risk ("multiple sessions may create/remove worktrees against the same main repo concurrently") is not just about this project's *own* new code racing itself — it inherits go-git's pre-existing lack of internal synchronization for any shared `*Repository`/`*Storer` object this project's worktree/merge code touches concurrently across sessions.

### 1.4 Verified directly from source: go-git's own writes are not crash-safe or interop-safe, right now, at the pinned version

This is the most concrete finding for the "partial-write corruption" question, verified by reading the actual pinned dependency source (`go.mod` pins `github.com/go-git/go-git/v5 v5.19.2`; confirmed against `git show v5.19.2` via `gh api`, not an older cached module version):

- **Index writes are a plain truncating `Create`, not lock-then-rename.** `storage/filesystem/dotgit/dotgit.go`'s `IndexWriter()`:
  ```go
  func (d *DotGit) IndexWriter() (billy.File, error) {
      return d.fs.Create(indexPath)
  }
  ```
  `storage/filesystem/index.go`'s `SetIndex` opens this writer, wraps it in a `bufio.Writer`, and streams the encoded index directly into it. There is **no** `index.lock` file, no write-to-temp, no fsync-then-rename — real git's own index-write protocol (write `index.lock`, fsync, atomically rename onto `index`) is not replicated at all. If the process is killed mid-`Encode`, `index` is left **truncated/corrupt in place** — not "the old index, untouched" (what a crash during real git's lockfile-based write leaves behind).
- **Ref writes use in-process `flock`, not git's lockfile-rename protocol**, and the no-RDWR fallback path has none at all. `storage/filesystem/dotgit/dotgit_setref.go`'s `setRefRwfs` opens the ref file `O_RDWR|O_CREATE` (truncating if `old == nil`), takes an **advisory `flock`** on that same open fd, truncates, and writes in place — never renaming a `.lock` file into place the way real git does. A crash between the truncate and the write leaves a **zero-byte ref file**, not the pre-write state. Worse: because this is an advisory `flock`, not git's file-existence-based `<ref>.lock` sentinel, **a real `git` process operating on the same ref does not see or respect this lock at all** (git checks for the presence of a `.lock` file; it does not flock ref files). The fallback path used on filesystems without read/write capability, `setRefNorwfs`, does no locking whatsoever — a plain read-check-then-`Create`+write, which is a textbook TOCTOU race.
- Contrast: go-git's `packed-refs` rewriter (`dotgit_rewrite_packed_refs.go`) *does* use `d.fs.TempFile(...)` + rename — proving the library's authors know the pattern and apply it selectively, just not to `index` or loose refs.

**Consequence for this project**: this project cannot treat go-git's `Worktree.Add()`/`Commit()`/`Storer.SetReference()` as "the safe primitive" for the conflicted-index write or for finalizing a merge commit's ref update. Those calls bottom out in the non-atomic paths above. The project must write its own temp-file+rename layer (matching real git's own protocol byte-for-byte in *behavior*, not necessarily in on-disk lock-file naming) around any file this project writes that (a) must survive a crash without corruption, or (b) must coexist with a concurrent real `git` CLI process touching the same repo — which per this project's own Users/Consumers section, is guaranteed to happen (`FetchBranch`, `CheckoutBranch`, `gh` CLI all still shell out against these same worktree paths).

### 1.5 Worktree `Status()` is unreliable in exactly the configuration this project cares about

- [go-git#1843](https://github.com/go-git/go-git/issues/1843) "Worktree.Status() returns all files as changed in linked worktree (bare-repo layout)" (open, go-git v6): every tracked file reported modified in a linked worktree even though `git status --porcelain` is clean — root-caused by the status computation not correctly resolving the index/objects through the `commondir` indirection for a *linked* worktree specifically (not a plain repo). The issue's own suggested workaround is "shell out to `git status --porcelain`" — i.e., even go-git's own community doesn't trust go-git for this on a linked worktree.
- [go-git#1896](https://github.com/go-git/go-git/issues/1896) "Worktree.Status() descends into nested git worktree directories, reporting false untracked files" and [go-git#2297](https://github.com/go-git/go-git/issues/2297) "Worktree.Status() initialises registered-but-uncloned submodules on disk — a read operation that writes" (a *read* API silently mutating disk state) round out the pattern: worktree-aware status/read operations in go-git have a track record of both false results and unexpected side effects specifically in linked-worktree/nested-repo topologies, which is exactly this project's target topology (`~/.stapler-squad/worktrees/`, many linked worktrees off one main repo).

### 1.6 Symlink-boundary escape was a real, recently-fixed go-git bug — not a hypothetical

- [go-git#2276](https://github.com/go-git/go-git/pull/2276) "worktree: make the filesystem wrapper a symlink-safe boundary" (merged): *"`worktreeFilesystem` validated path strings but did not account for symlinks already present on disk. As a result a worktree operation on an otherwise valid path could resolve through a symlinked component and act outside the worktree."* The fix explicitly states it "Mirrors upstream Git's `has_symlink_leading_path` in `symlinks.c` and the `check_leading_path`/`unlink-before-write` guards in `entry.c`" — i.e., go-git had to retrofit a defense real git has always had, and until this fix, a maliciously-crafted symlink already on disk (e.g. planted by a prior checkout of attacker-controlled content in the same worktree) could let a worktree write escape the worktree root. [go-git#2108](https://github.com/go-git/go-git/pull/2108) ("allow symlink targets containing `..`") and [go-git#2266](https://github.com/go-git/go-git/pull/2266) ("reject NTFS and HFS disguised `..` in tree and submodule paths") are siblings in the same bug family.
- **Relevant to this project even though it targets Linux/macOS, not Windows**: HFS+/APFS on macOS is case-insensitive (and can be configured normalization-insensitive) by default, so the "disguised .. / disguised path" class of bug in #2266 is not a Windows-only concern for a repo whose CLAUDE.md states macOS is one of two deployment targets. A merge that materializes two tree entries differing only by case or Unicode normalization needs the same defensive handling go-git itself only recently added.

## 2. JGit (Java) — the most directly comparable prior art, and its most telling result: it still doesn't support worktrees

JGit is a ~15-year-old, heavily used, managed-language (JVM) full reimplementation of git — the closest real-world analog to what this project is attempting. Its issue tracker's answer to "how hard is linked-worktree support" is blunt:

- [eclipse-jgit#76](https://github.com/eclipse-jgit/jgit/issues/76) "Support worktrees" and [eclipse-jgit#264](https://github.com/eclipse-jgit/jgit/issues/264) "Feature Request: Git Worktree Support for JGit and EGit" — **both still open**. #264 (filed 2026, explicitly motivated by "AI Agent Orchestration" — the same use case as this project) spells out the actual engineering surface required: *"Updating Repository discovery to handle `$GIT_COMMON_DIR`. Decoupling Index and HEAD management so that JGit can operate on worktree-specific administrative files while sharing the object database."* After 15+ years of development, JGit's maintainers have not implemented this. That is strong outside evidence that "worktree management" is not a small layer on top of a mature git reimplementation's existing primitives — it is a distinct, load-bearing subsystem, matching this project's own Feasibility Risks framing ("go-git has no API at all for multi-worktree management").

Merge-specific findings:

- [eclipse-jgit#39](https://github.com/eclipse-jgit/jgit/issues/39) "JGit's diff3 is a curious mix of git's diff3 and zdiff3 styles" (open) — a concrete, reproducible byte-level divergence: for a specific 3-line conflict, JGit's diff3-style output silently drops the base-revision content real git's diff3 output would show, because JGit's conflict-region computation merges two independent edits into one shown region where real git keeps the base context visible. **This is a mature, actively-maintained reimplementation still not byte-for-byte matching git's own diff3 output after years** — direct evidence for the requirements doc's own "Rabbit Hole" flag on this exact question. It argues for treating "byte-for-byte match" as a real, non-trivial acceptance target requiring a dedicated interop test matrix (see §5), not an assumption that a diff3 port will just line up.
- [eclipse-jgit#43](https://github.com/eclipse-jgit/jgit/issues/43) "Merging does not follow renames" (open) — confirms the requirements doc's "Rabbit Hole" instinct to explicitly scope rename-detection in/out during planning rather than assume it: even JGit, which *does* implement full three-way merge, has an open, unresolved gap here.
- [eclipse-jgit#131](https://github.com/eclipse-jgit/jgit/issues/131) "Repository index corrupted after a cherry pick with .gitattribute text settings" (open, filed against JGit 7.2.0): a genuine index-corruption bug from `ResolveMerger.updateIndex` computing the wrong on-disk length for a CRLF-normalized merged file, leaving the index's recorded file size mismatched with the actual workspace file — `git status` then permanently reports the file dirty, and a subsequent rebase/cherry-pick can be **aborted as FAILED** because of the stale index state. This is a corruption bug that is *specific to CRLF text-attribute handling* — direct evidence supporting the requirements doc's instinct that a Linux/macOS-only project can plausibly skip CRLF normalization entirely, since this whole bug class only exists because of it.
- [eclipse-jgit#57](https://github.com/eclipse-jgit/jgit/issues/57) "Encountering `LockFailedException`: Cannot lock" (open) — a production report from a load test: concurrent `AddCommand` calls across many repos hit JGit's own `DirCache.lock()` (which **does** implement a real `index.lock`-file-based protocol, unlike go-git) failing with a stale/contended lock, with the only remediation being "manually delete the lock file and retry." This is useful even though JGit does the "right" locking: it shows that even a *correct* lockfile implementation still needs an explicit stale-lock-detection/recovery story under real concurrent load — something this project will need for `.git/worktrees/<name>/index` and any lock files it introduces, not just "get the write path atomic and stop."

## 3. gitoxide (Rust) — a second independent-language reimplementation, and the sharpest evidence on partial-write recovery

gitoxide (`gix`) is a newer (memory-safe, non-GC) reimplementation, actively adding worktree and merge support right now, which makes its issue tracker unusually good source material for "what breaks when you build this in a strict, safety-oriented language and still get it wrong":

- [GitoxideLabs/gitoxide#2421](https://github.com/GitoxideLabs/gitoxide/issues/2421) "`index.write()` can cause index corruption if tree extension/tree cache is not taken into account" — **directly answers this project's "Open Question" about whether a from-scratch index writer can faithfully represent state**: gitoxide's index writer updates the index *entries* correctly but does not update the index's `TREE` extension/cache, leaving the on-disk index internally inconsistent. The observed effect is exactly the kind of silent-wrong-result this project must avoid: *"the written index is in an inconsistent state, and external git clients show `git status` as showing no changes on disk (since they query the tree extension) — this can cause files modified to be completely invisible, and commits to commit things that are not in the index entries."* **This is the single most important citation for this project's index-writing work**: it is not enough to write correct stage-1/2/3 entries for a conflict — the index's cache/tree extensions must be kept consistent (or explicitly stripped/invalidated) or `git status`/`git diff` will lie to a human or to the LLM prompt this project feeds conflict state into. Companion PR [#2664](https://github.com/GitoxideLabs/gitoxide/pull/2664) is gitoxide's own maintainers documenting (not yet fully fixing) this gap.
- [GitoxideLabs/gitoxide#2417](https://github.com/GitoxideLabs/gitoxide/issues/2417) "`index.write()` can fail intermittently on windows" — not directly applicable (Windows is out of scope here), but the *shape* of the fix is instructive: gitoxide's rename-into-place *can itself fail transiently* (antivirus/file-watcher holding a handle) and libgit2's answer is a bounded retry-with-backoff around the rename step specifically, not the whole write. If this project's own atomic-write layer's rename step can transiently fail on this host (e.g. a concurrent `find`/inotify watcher, or another one of this repo's own 50-90 concurrent sessions statting the same directory), the same retry-around-rename-only pattern applies even on Linux/macOS.
- [GitoxideLabs/gitoxide#2959](https://github.com/GitoxideLabs/gitoxide/issues/2959) "`gix`: `fetch` fails when a linked worktree admin dir has a `gitdir` file but no `commondir`" — **directly answers this project's partial-write-corruption question with a real git source citation**. The issue reproduces a linked-worktree admin directory left in a half-written state (`gitdir` file present, `commondir` file absent) and states the real-git ground truth explicitly, citing `git/git`'s own `builtin/worktree.c`:
  > *"git creates this state itself: `add_worktree()` in `builtin/worktree.c` writes `gitdir` before `commondir`, so an interrupted `git worktree add` or `remove` leaves it behind until `git worktree prune`."*
  >
  > and demonstrates real git's own recovery model tolerates this state gracefully:
  > ```
  > $ git worktree list
  > /tmp/f/work   cb15777 [main]
  > /tmp/f/ghost  0000000 (detached HEAD) prunable
  > $ git fetch origin && echo $?
  > 0
  > ```
  gitoxide's bug is that it does **not** tolerate this half-written state the way real git does — it aborts an unrelated `fetch` outright instead of treating the incomplete worktree admin dir as ignorable/prunable. This gives two concrete, verified answers this project needs:
  1. **What a crash mid-`git worktree add` actually leaves behind, straight from real git's own source order**: `gitdir` exists, `commondir` does not (if the crash happens between those two writes) — a well-known, well-defined partial state, not an arbitrary one.
  2. **What "recoverable" means in practice**: real git's own model is "tolerate it as an ignorable/prunable worktree, don't hard-fail," not "fully recover it into a working worktree." This project's own worktree-add/remove code must adopt the same write ordering (or another ordering it can prove is equally recoverable) and, just as importantly, every *read* path this project builds (list, prune, and anything that iterates `.git/worktrees/*`) must tolerate an incomplete entry the way real git does, rather than erroring the way gitoxide's `fetch` did here.

## 4. This repo's own prior pain, re-read for this task, plus what else in the same class to watch for

`session/git/util.go`'s `getHeadCommitSHA` (lines ~333-395) documents a real production bug: go-git's direct, unlocked HEAD-ref-file read raced a concurrent writer against the same parent repo and returned a **syntactically-valid SHA that did not correspond to any real object** — confirmed absent from `git cat-file -t`, `git rev-list --all`, `git reflog show --all`, and `git fsck --unreachable`. The fix layers (a) retry with re-open, (b) verify the resolved hash actually exists via `repo.CommitObject()` before trusting it, and (c) fall back to the git CLI (immune to the race because it uses atomic-rename ref updates) after repeated failures. `session/git/util_test.go`'s `breakHeadReference` (lines ~350-360) reproduces the *other* observed failure mode: go-git's `repo.Head()` erroring outright while `repo.References()` still enumerates the real refs fine — this one is deterministic/single-threaded (a gitdir-parsing gap, not a race), which is why `findGitRepoRoot`/`repoHasAnyRef` check the ref store directly instead of trusting a `Head()` error as "unborn repo."

Given §1.4's source-level findings above, the other read-modify-write races in the **same class** this project must watch for, beyond HEAD:

- **Reading `.git/worktrees/<name>/index` while another process (real `git`, or this project's own concurrent code) is mid-write.** Per §1.4, go-git's `SetIndex`/`IndexWriter` do not create an `index.lock` sentinel at all — so there is no signal a concurrent reader (this project's own status/diff code, or a real `git status` in the worktree) could check for "a write is in progress," unlike real git's own protocol where the presence of `index.lock` is itself the signal. Any index read this project's new code performs must assume it can observe a **committed-in-place-but-mid-flight** truncate, not just a stale-but-consistent old version — a strictly worse failure mode than a torn ref read, since a partially-written index isn't just "old data," it can be **structurally invalid** (truncated encoding) rather than merely stale.
- **Reading/writing a ref (e.g. the worktree's branch ref, or `MERGE_HEAD`) concurrently with a real `git` process.** Per §1.4, go-git's ref writes use `flock`, which real git's own lockfile-rename protocol does not participate in at all — so a go-git-based writer and a concurrent real-`git`-CLI writer (this repo's own `FetchBranch`/`CheckoutBranch`, still subprocess per this project's own Scope) have **zero actual mutual exclusion** against each other today, regardless of what this project builds, unless this project's new code independently honors git's `<ref>.lock`-file-presence convention on every ref write (not just relies on go-git's internal flock).
- **Object-store staleness under a concurrent `git gc`/repack** (go-git#2242, §1.1): any long-lived `*git.Repository` this project holds across a `FetchBranch` call (still subprocess, can trigger auto-gc) risks resolving objects against packs that no longer exist on disk. The mitigation go-git lacks and real git has (retry once on a stale pack index) should be added explicitly by this project wherever it holds a `*Repository` across an operation that can trigger repacking, mirroring the retry-then-CLI-fallback shape `getHeadCommitSHA` already uses for the ref race.

## 5. Partial-write corruption risk: concrete answer and required atomic-write pattern

**Question**: if this project's worktree-add or merge-conflict-write logic crashes or is killed partway through, what state does that leave things in, and can real git recover it?

**Answer, split by what's being written:**

- **`.git/worktrees/<name>/` admin files** (`gitdir`, `commondir`, `HEAD`, `index`, `locked`, etc.): real git's own crash-partial-state is well-defined and documented straight from its source (§3, gitoxide#2959) — `gitdir` written before `commondir`, so an interrupted `add` leaves a `gitdir`-only directory. Real git's own tooling (`git worktree list --porcelain`, `git worktree prune`) recognizes this as `prunable` and cleans it up safely; it does not attempt automatic repair. **This project must copy that exact write order** (or another order it explicitly proves is equally safe) so that real git's own `prune`/`list` — which this project's own success metric requires stays interoperable — correctly recognizes and can clean up this project's own crash-partial state, rather than silently ignoring or mishandling a "foreign" partial layout it wasn't written to expect.
- **The index file**, if this project uses go-git's `SetIndex`/`Worktree.Add` as-is (§1.4): a crash mid-write leaves a **truncated, structurally invalid `index` file in place** — not "the old index, intact" and not "a stray lock file next to an untouched index." Real git **cannot safely recover this automatically**: the standard remediation is `rm -f .git/index && git reset` (or `git read-tree HEAD`), which silently discards any staged-but-uncommitted state that existed before the crash. This is strictly worse than real git's own crash-partial state (a stray `.lock` file next to an intact `index`, trivially recoverable by deleting the lock).
- **Required pattern**: this project must not write `index` (or any single administrative file whose current readers — real `git`, `gh`, this repo's own subprocess call sites — cannot tolerate a torn write) via a direct in-place `Create`/truncate. It must write to a temp file in the same directory (same filesystem, so the subsequent rename is atomic) and `rename(2)` it into place only after a successful `fsync` — i.e., re-derive git's own lockfile-rename discipline in this project's own code, rather than delegate to go-git's `SetIndex`/`SetReference`, which (per §1.4, verified against the pinned v5.19.2 source) do not do this today. Where the write is inherently multi-file (e.g. `git worktree add`'s several admin files), this project should additionally match git's own **ordering** of those writes (§3) so that a crash between any two steps lands in a state real git's own recovery tooling already knows how to interpret.

## 6. CGO_ENABLED=0 / pure-Go: behaviors that are fundamentally hard, not just tedious, to replicate exactly

- **Byte-for-byte conflict-marker/diff3 output matching real git.** Per §2 (eclipse-jgit#39), a mature, actively maintained, full reimplementation in a managed language still produces observably different diff3-style output than real git for a simple 3-line conflict, years into development. This is strong evidence that "exact byte-for-byte match," as the requirements doc's own Rabbit Holes section frames it, is a genuinely hard target, not a formality — and it argues for (a) scoping to git's **default** conflict-marker style (`<<<<<<<`/`=======`/`>>>>>>>`, no base context) rather than `diff3`/`zdiff3` unless a concrete consumer needs the base context, since the default style has far less surface for this class of divergence, and (b) building a dedicated interop test matrix early (real `git merge` vs. this project's merge, byte-diffed, across a curated set of conflict shapes — adjacent-edit, same-line, add/add, delete/modify) rather than validating "some" conflict marker output and assuming it generalizes.
- **Index internal-consistency beyond the visible entries** (§3, gitoxide#2421): a from-scratch index writer that gets the stage-1/2/3 entries right but leaves the `TREE` cache extension stale produces an index that is invisibly wrong to `git status`/`git diff` (which trust the cache) while looking correct to anything that only reads entries directly. This project's research/validation phase must explicitly test against `git status`/`git diff` output, not just against go-git's own index reader, or it can ship the same class of bug gitoxide shipped.
- **Symlink-boundary safety** (§1.6): go-git itself needed a dedicated, git-C-code-mirroring fix (`has_symlink_leading_path`-equivalent) as recently as this repo's current dependency lineage to stop a worktree write from escaping through a pre-existing on-disk symlink. This project's own worktree-materialization and merge-conflict-file-writing code inherits this exact risk class (a merge that writes into a path with an attacker- or bug-planted symlink component) and needs the equivalent boundary check — not something to assume go-git's plumbing primitives (as opposed to its higher-level `Worktree` API, which now has the fix) already provide.
- **Filesystem case/normalization handling is not Windows-only for this project.** (§1.6) macOS's default case-insensitive (and optionally normalization-insensitive) APFS/HFS+ means the same "disguised path" class of bug go-git had to patch for NTFS/HFS (#2266) is live on one of this project's two actual deployment platforms, not an irrelevant Windows concern to dismiss alongside the explicit Windows-worktree-support exclusion already in Scope.
- **CRLF/line-ending normalization can plausibly be skipped**, and now with direct supporting evidence rather than just the requirements doc's instinct: eclipse-jgit#131's index-corruption bug (§2) is *specifically* a CRLF-length-accounting bug, i.e. this entire bug class only exists because of CRLF handling — a Linux/macOS-only project genuinely eliminates a whole documented corruption vector, not just a formatting nuance, by skipping it as the requirements doc's Rabbit Holes section already leans toward.
