# Adversarial review: triage-volume-reduction plan

Verdict: **BLOCKED** (3 blockers, 6 concerns). All claims below verified by reading the cited code on this branch.

## BLOCKERS

### B1. AutoRespawnTriage skip breaks the guidance-answer resume path
`server/services/guidance_request_service.go:94-112` (`resumeTriageIfHalted`) writes the answer as an activity note and then calls `AutoRespawnTriage` to resume a triage that deliberately halted to ask. Halted/refine items routinely already have AC (user-supplied) or a prior completed result with an unchanged title/description/AC hash (the answer lives only in an activity note, which the plan's hash excludes by design). Under the plan, `AutoRespawnTriage` returns nil with a "skipped" note, the answer is silently dropped, and the item stays halted. `AutoRespawnTriage` has three callers, not two automatic ones: shutdown respawn (`session/backlog_lifecycle_triage.go:280`), backoff retry (`:426`), and guidance resume. The plan treats it as one "automatic" caller.
Fix: put the skip check in a distinct entry point (or a parameter) used only by the two reconcile callers; the guidance path must bypass it. Alternatively include activity-note count/last-answer in the hash, but that contradicts the "hash excludes notes" pitfall, so bypass is cleaner.

### B2. Skip inside AutoRespawnTriage returning nil makes items stuck-and-spamming forever
Verified loop: `reconcileOrphanedTriageItems` marks `orphaned_triage` stuck when the latest triage session ended without moving the item out of idea (shape 2) or, for queued items, ended with empty TriageResult (shape 3). `reconcileOrphanedTriageRemediation` then calls `retryOrphanedTriageWithBackoffGate` every sweep for each open row; `AutoRespawnTriage` is the remediation. If the item has user AC (shape 2: failed triage on an item that has AC; the measurement shows 6/14 calls fail, so this is common), the plan skips, returns nil, and nothing resolves the stuck row (`selfHealStuck` only clears it when status leaves idea/queued). Consequences: (a) each backoff-due attempt appends another "Triage skipped" note (bounded by `MaxRemediationAttempts` but still spam, contradicting the pitfalls "once per skip decision" claim), (b) it burns remediation attempts until `justParked` fires an urgent "Auto-triage paused ... attempted N times" notification that is false (nothing was attempted), (c) the item with AC but no plan can never reach ready without a human, since only triage writes `PlanArtifactsPath`/ready transition. pitfalls.md asserts "AutoRespawnTriage skip must not loop" but the plan has no mechanism for it.
Fix: before skipping in the respawn path, explicitly resolve the stuck state (or have the skip return a sentinel the remediation gate treats as "park, notify once"), and write the note only if the last note is not already a gate note (idempotency check via `ListActivityNotesForItem`). Better: the AC rule should not apply to respawn after a *failed* triage, since the point of respawn is to recover from failure. Restrict respawn skips to the hash rule (prior completed result unchanged) and leave AC/PlanApproved only on `MaybeTriggerTriage`.

### B3. Skip ordering vs the queued->idea reset in AutoRespawnTriage
`AutoRespawnTriage` (`backlog_service_triage.go:2506-2523`) transitions a `queued` item to `idea` before calling `TriggerTriage`. Plan says only "call it" without placement. If the skip check runs after the switch, a skipped queued item has already been demoted to idea (a silent backward status change, with a note saying "skipped"). If it runs before, it must still evaluate on status. Also the plan's `PlanApproved` rule: a queued item with approved plan is the normal case for "queued" and would be skipped (correct), but an idea item with `PlanApproved` is unreachable anyway. Specify: skip check after the status switch's staleness `default: return nil` but before the queued->idea transition.

## CONCERNS

### C1. Hash instability and the stored-InputHash timing
- Plan says `InputHash` is computed "at trigger time (item loaded in step 1)" and stored in the result. But a successful triage rewrites AC (`applyTriageResultToUpdate`, `backlog_service_trigger_triage.go:814-826`). The stored hash is therefore of the *pre-triage* item (AC empty), while every later comparison hashes the *post-triage* item (AC populated): they can never match when triage emitted AC. The hash rule only fires for results that emitted no AC. In practice the AC rule does the work and the hash rule is nearly dead for AC-emitting runs. Either compute the stored hash from the post-update item (title/description/AC as persisted) or drop AC from the hash.
- "AC JSON" is not stable input: `AcCriterion` carries status/evidence that `report_progress` mutates (the pitfalls doc says "AC text only"; the plan says "AC JSON" and the two disagree). Hash only normalized criterion text, in index order, not the serialized JSON.
- Title is overwritten? `result.Title` is sanitized in the result but the item title is not changed; fine. Description/title edits by humans correctly change the hash.
- Pre-existing results have no `InputHash` (""), so they never match: safe, but say so and test it.
- 16 hex chars truncation is fine. Use length-prefixing or `\x00` as the plan does; add a test that field-boundary shifts (title "a\x00b" vs description) differ is optional.

### C2. Semaphore queue semantics (cap 1)
Verified `triageSem` is acquired inside the goroutine *after* `CreateItemSession` and `triageInFlight` are set (`backlog_service_trigger_triage.go:366-395`). With a small cap, queued items hold an open ItemSession, are `IsTriageLive` (so the stale sweep won't tombstone them, good), and `callBudget` starts after acquisition (good). Gaps the plan does not address: (a) the queue is an unordered channel-send wait, not FIFO, so starvation is possible with cap 1 (Go channel senders are FIFO in practice, but this is not a documented guarantee; do not assert ordering in a test); (b) queued items waiting more than `maxHeadlessTriageSessionStaleness` (3h15m) with a dead process (restart) are respawned as "shutdown" EndReason (fine); (c) the plan's test ("assert second doesn't start CallBlocking until first finishes") needs a blocking fake caller and `testTriageCompleteHook` filtering by item ID; call out the hook's cross-test warning. (d) `triageSem` is also referenced in a test comment only; no test builds `BacklogService{}` literals with a nil `triageSem`, but a nil `cfg` must size 8 (plan says nil-safe, keep that test). (e) Capacity is fixed at construction, so a config change needs a restart; document it (the repo memory prefers live-settable flags for *rollout* flags, but this is a resource cap, so acceptable if stated).

### C3. Model pin: non-claude executor programs and the account-default escape hatches
- `resolveHeadlessCaller` routes a configured non-claude program (e.g. gemini) to `s.headlessCallers[program]`. The plan applies `HeadlessTriageModelOrDefault()` whenever `triageExecModel == ""`, which would pass a Claude model ID to a non-Claude caller. Gate the default on the resolved caller being the claude pool (`triageConfiguredProgram == ""` and program empty or "claude"); fallbacks that returned `s.headlessPool` are claude and may take the default.
- `session.ResolveModel` failure path sets the model to "" (account default). With `headless_triage_model` set to a typo like `family:sonet`, AC4 ("never the account default") is silently violated with only a Warn. Validate at config load or fall back to the built-in default `family:sonnet`, not "". The plan's T3 "bad family falls back to empty" test enshrines the violation; invert it.
- Default `family:sonnet` resolves via `workflows.DefaultModelFamilies()` ("claude-sonnet-4-6") but `s.modelFamilies` can be overridden; if an override file drops `sonnet`, same silent fallback.
- `ExecutorSnapshotHash` interaction: verified `ComputeExecutorHash` hashes raw program|model and the only consumers are persistence (`storage_backlog.go:266`) and proto mapping; keeping the hash on the raw "" value is correct and mode-side comparison stays stable. But the row will now read `ResolvedModel="claude-sonnet-4-6"` with `ExecutorSnapshotHash=hash("","")`, so anything that infers drift as "ResolvedModel != hash input" would false-flag. I found no such reader, but state it explicitly and add a test asserting hash unchanged between pinned/unpinned for the same raw value.
- Cheaper-model quality risk: 12 of 14 triages in the measurement are `sdd`-mode with a 4-subagent research phase; Sonnet is also what those subagents inherit. Not a blocker, but the PR should say so.
- Items with a *pinned* mode keep winning (raw value non-empty): correct per R4.

Also the measurement covers one workspace DB only and its "tokens" claim is not met (cost only); AC1 says "calls/tokens/cost" so the PR must state that tokens are not stored.
- R2 "visible activity note": the plan writes the note via `Storage.AppendActivityNote(ctx, itemID, "", "triage-gate", ...)`. Verified signature exists (`session/storage.go:1538`). Check `mapAppendActivityNoteCreateError` (`session/ent_repository_backlog.go:2512`) for constraints on empty `authorSessionUUID` (guidance path passes "" so it is accepted). OK.
- R3 "excess runs queue": covered. R3 default 8 test needed (nil cfg and zero value).
- R5 `make lint`: new file must carry the `gocognit/funlen` limits, and `MaybeTriggerTriage`/`AutoRespawnTriage` are existing functions that gain branches, so the gocognit new-code gate applies to the modified functions. Extract the skip decision into the new file (plan does) and keep call sites to a 3-line `if reason := ...; reason != ""`.
- Per-repo CLAUDE.md requires `make registry-generate` only for RPC/component changes; not applicable. Config additions need a docs entry if `config/` fields are documented anywhere (grep `headless_triage_max_cost_usd` in docs/ and mirror it); plan mentions none.

### C5. MaybeTriggerTriage needs data it does not currently load
Plan's `triageSkipReason(item, sessions)` requires a `GetBacklogItem` and `ListItemSessions` call in `MaybeTriggerTriage`, which today does neither (it delegates to `TriggerTriage`, which loads both under the 30s sync context). That is two extra reads per creation and a second, racy read of the item versus `TriggerTriage`'s own. For creation, `sessions` is always empty, so skip `ListItemSessions` there and check only AC/PlanApproved from the item (the hash rule cannot apply to a fresh item). Better still, thread `skip` into a shared helper called inside `TriggerTriage`'s step 1/3c with an `automatic bool` flag, avoiding the double load and the TOCTOU between check and trigger; but that changes the RPC handler signature or needs an internal method (`triggerTriage(ctx, req, automatic)`), which also fixes B1 cleanly (guidance path passes `automatic=false`).

### C6. Items skipped on AC stay in `idea` with no plan and no UI affordance
Plan accepts this as "per AC2". Operationally: an item created with AC (e.g. imported GitHub issue with a checklist, or an MCP-created item) will never get `PlanArtifactsPath`, so the "Approve Plan" flow (`ApprovePlan` does `os.Stat` on it) is unreachable unless `SkipPlanning` is set. Verify what `spawnSessionAfterGates` does for an idea item with AC and no plan; if it cannot spawn, the skip note must say exactly "click Trigger Triage or set skip_planning". Note text in the plan is "Triage skipped: <reason>" with no next step; pitfalls.md requires one ("explains set status/approve manually"). Add it.
