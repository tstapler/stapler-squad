## Concerns

- **Task 1.1.2d (denylist guard test) / Pattern Decisions "Coverage-gap guard" row** — The guard test does not actually catch the forward-compat risk it's designed to catch. It asserts `NON_NO_MATCH_ESCALATION_CATEGORIES` (the TS `Set`, defined in `ReviewQueuePanel.tsx`) equals a second hardcoded literal array written by hand in the *same* test file. Both sides live in the frontend, so if `pkg/classifier/escalation.go` gains a 7th `EscalationCategory` constant, **nothing on the TypeScript side changes and this test keeps passing** — it only fails if someone edits the TS `Set` without updating the TS test (a same-file, same-language typo), not if the Go source of truth drifts, which is the actual scenario pitfalls.md #3 is worried about ("a future new `EscalationCategory` constant fails a test instead of silently defaulting to 'show'" — this claim in the Pattern Decisions table is not true of the test as specified). The only real mitigation is the code comment prompting a human to check the other file, which is documentation, not enforcement — and this fix additionally *flips the safe default*: under the old allowlist, an unrecognized category defaulted to hide (safe); under the new denylist, it defaults to show (the exact failure mode this project has already been burned by once per `escalation.go`'s own doc comments on `EscalationUnexpected`). **Remediation**: acceptable to ship as-is given this mirrors an already-accepted pattern elsewhere in the codebase (`ApprovalAnalyticsPanel.tsx`'s `ESCALATION_CATEGORY_LABELS`, per pitfalls.md #3's own admission) and the blast radius is bounded/self-healing per requirements.md's Impact section — but the PR description should say explicitly that this guard test only protects against frontend-side drift, not backend taxonomy growth, so a reviewer doesn't over-trust the "fails loudly" framing in the plan. If stronger enforcement is wanted later, a small script/CI check diffing `escalation.go`'s consts against the TS `Set` (or generating the TS set from the Go consts) would close the gap — out of scope for this complexity-1 fix.

- **Task 1.1.1b / testability (Lens 1, item 4)** — `isCreateRuleEligibleCategory` is never exported or unit-tested in isolation; only `NON_NO_MATCH_ESCALATION_CATEGORIES` (the Set) gets a direct export (Task 1.1.2d), and all coverage of the predicate's actual boolean logic (`category === undefined || !SET.has(category)`) comes from full-component render tests (Tasks 1.1.2a/1.1.2c) via React Testing Library. This works but is heavier than necessary and contradicts Story 1.1.1's own stated goal ("a single named, **testable** predicate"). A logic bug in the predicate (e.g. an inverted `!`) would surface as a failed render assertion requiring a trace back into the component, rather than a direct, fast, precisely-located unit-test failure. **Remediation**: export `isCreateRuleEligibleCategory` alongside the Set and add 2-3 direct unit tests (`undefined → true`, `"no-match" → true`, `"explicit-rule" → false`) in addition to the render-level tests — cheap to add given the function already exists, and it's a stronger testability story than render-only coverage.

- **Pattern Decisions table, "Category taxonomy / new TS union type" row (Lens 2, item 5)** — The plan rejects a TS union type by citing the requirements' non-goal ("Any change to the escalation category taxonomy itself"), but that non-goal targets `pkg/classifier/escalation.go` (the Go source of truth), not a frontend-local literal type used only to typo-check the denylist's own 5 strings. A lightweight `as const` array (`["explicit-rule", "domain-age", ...] as const`) feeding the `Set` would give TypeScript compile-time protection against a typo'd string literal (e.g. `"domain_age"` vs `"domain-age"`) without inventing or exporting any new cross-file taxonomy type, and without touching Go at all — so it doesn't actually conflict with the non-goal as read literally. This isn't a correctness bug in the current plan (the size/membership test at 1.1.2d would still catch a typo at test time), just a strictly-cheaper compile-time alternative that was dismissed on a rationale that doesn't quite hold up under a literal reading of the non-goal. **Remediation**: optional — swap the plain `Set<string>` literal for a `Set` built from an `as const` array for compile-time literal-typo protection; not worth blocking on given the test-level guard already exists.

## Nitpicks

- `ReviewQueuePanel.tsx` is already large (1464 lines per stack.md) and continues to accumulate escalation-category-related lookup tables (`ESCALATION_REASON_EMOJI`, and now `NON_NO_MATCH_ESCALATION_CATEGORIES` + `isCreateRuleEligibleCategory`). Not a concern for this fix's complexity-1 sizing, but if a future change adds a third such table, consider extracting escalation-category helpers into a colocated `reviewQueue/escalationCategories.ts` module rather than growing the component file further.
- Choice of `Set<string>` vs a plain array for 5 fixed string literals is a wash either way (module-scope, allocated once, negligible perf difference at this size) — no change needed, just noting there's no strong technical reason to prefer `Set` over `Array.includes()` here beyond `.has()` reading slightly cleaner; the plan's own rejection of "(a) inline `.includes()` in JSX" is really about avoiding re-creation/inlining in JSX, not about `Set` vs `Array` semantics — both would satisfy that goal equally.
