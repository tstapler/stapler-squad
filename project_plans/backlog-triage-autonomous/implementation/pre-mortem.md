# Pre-mortem: backlog-triage-autonomous
**Date**: 2026-06-22

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `CreateBacklogItem` auto-triage still gates on `s.sessionCreator != nil`, so in a headless-only environment (no tmux/Claude binary at session level) auto-triage is silently skipped even though the headless pool is present | Items created via API arrive in `idea` status and never advance to `ready`; no error, no notification; operator discovers it days later when the backlog stays full of un-triaged ideas | Replace the `s.sessionCreator != nil` guard in `CreateBacklogItem` (line 413) with `s.headlessPool != nil` (or a `s.canTriage()` helper); add an integration test that calls `CreateBacklogItem` with no sessionCreator but a valid headlessPool and asserts auto-triage fires | P1 |
| 2 | `WorkDir + FakeRunner` returns an error immediately (`"CallWithOptions: WorkDir requires a ProcessRunner; got FakeRunner"`), so the integration test for `TriggerTriage` (Task 4.1.2a) always hits the failure branch — the success path is never actually exercised by the test suite | CI is green; manual test on a real item fails; the goroutine body's persist + transition logic is unreachable via any automated test | Either (a) call `pool.CallBlockingWithOptions` with an empty `WorkDir` in tests and pass a dummy `RepoPath` to the item, or (b) extract a `HeadlessPoolClient` interface and use a mock that returns canned JSON — the adversarial review (concern 4) already recommended this; add a test-only interface before writing the goroutine | P1 |
| 3 | Three independent copies of the triage JSON schema (`triageSuggestion`/`triageTask` in `tools_backlog.go`, `triageSuggestionJSON`/`triageTaskJSON` in `backlog_service.go`, and the new `HeadlessTriageResult` fields in `session/backlog_triage.go`) drift out of sync when a field is added to one but not the others — the headless parse succeeds, but the stored JSON is missing the new field, and the UI silently renders incomplete data | A new field (e.g., `priority`) added to tasks appears in the `submit_triage_result` MCP path but is absent from the headless parse path; the bug is invisible until an operator compares two items side-by-side | Consolidate all three definitions in `session/backlog_triage.go` as the plan already directs in Task 1.1.2a; block the PR until `server/mcp/tools_backlog.go` and `backlog_service.go` import `session.TriageSuggestion`/`session.TriageTask` instead of their local copies — add a `grep -r "triageSuggestion\|triageTask" server/` check to CI that fails if local definitions remain | P2 |
| 4 | The in-flight triage goroutine derives its 30-minute timeout from `context.Background()` (not `shutdownCtx`); on server restart the goroutine outlives the process, leaving `ItemSession.ended_at = null` permanently; next `TriggerTriage` on the same item hits the orphan guard and creates a new session, but the old open session blocks re-triggers from the UI | After a deploy, previously-triaged items are stuck in a permanent "triage in progress" spinner in the UI; re-triggering from the detail pane returns a 409 or no-op; only a manual DB update (`UPDATE item_sessions SET ended_at = now()`) clears the block | Add `shutdownCtx context.Context` / `shutdownCancel context.CancelFunc` to `BacklogService` (plan Task 2.1.0a already specifies this — the risk is that it is coded using `context.Background()` instead of `shutdownCtx`); wire `backlogSvc.Shutdown()` into the server teardown path; add the shutdown cancellation integration test (Task 4.1.2c) before merging | P2 |
| 5 | The LLM outputs well-formed JSON but the `summary` field is a multi-page prose dump instead of a one-paragraph summary, and `tasks` contains 0 entries (Claude generated tasks under a different key name such as `"items"` or `"steps"`); `ParseHeadlessTriageResult` succeeds with no error, the item transitions to `ready`, and `planArtifactsPath` is set — but the triage result stored in DB is effectively empty | Item shows `ready` in the UI with a blank triage summary and 0 tasks; operator opens the detail pane, sees no tasks, and cannot distinguish "LLM produced empty output" from "triage is still running" | Add a post-parse validation step: if `result.Summary == ""` or `len(result.Tasks) == 0`, treat it as a parse failure (log warning, keep item at `idea`, mark session ended); add a unit test for the empty-tasks case; add the schema validation to the acceptance criteria in Story 1.1.2 | P2 |

---

## P1 Items (address before implementation)

- [ ] **Failure #1 — auto-triage guard bypasses headless pool** — Update `CreateBacklogItem` (line 413 of `server/services/backlog_service.go`) to gate on `s.headlessPool != nil` instead of (or in addition to) `s.sessionCreator != nil`; introduce a `canTriage() bool` helper used by both `CreateBacklogItem` and `TriggerTriage`.

- [ ] **Failure #2 — FakeRunner + WorkDir always errors, leaving success path untested** — Add a `HeadlessPoolClient` interface (or use empty `WorkDir` in tests) before writing the goroutine; Task 4.1.2a must be written against this interface, not against `FakeRunner` directly. The integration test must reach the persist + status-transition code on the happy path.

---

## P2 Items (fix before first production item is triaged)

- [ ] **Failure #3 — type drift across three schema copies** — Complete Task 1.1.2a fully: import `session.TriageSuggestion`/`session.TriageTask` in `server/mcp/tools_backlog.go` and `server/services/backlog_service.go` before the PR merges; add CI grep to prevent re-introduction of local copies.

- [ ] **Failure #4 — shutdownCtx not threaded into goroutine timeout** — Verify Task 2.1.0a uses `s.shutdownCtx` (not `context.Background()`) as the parent for `context.WithTimeout`; wire `backlogSvc.Shutdown()` in server teardown; Task 4.1.2c (shutdown cancellation test) is a hard prerequisite.

- [ ] **Failure #5 — empty/miskeyed LLM output treated as success** — Add post-parse validation: `result.Summary == ""` or `len(result.Tasks) == 0` is a failure, not a success; add unit test case for this condition in Task 4.1.1a.
