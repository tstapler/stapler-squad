# Adversarial Review: nav-redesign

**Date**: 2026-06-24
**Verdict**: CONCERNS

## Blockers

_(None identified — all critical issues were caught in research and addressed in the plan)_

## Concerns

- [ ] **Header.tsx is a silent non-consumer of the new grouping system** — The plan's "Out of Scope" note says Header.tsx grouped rendering is "not required by requirements," but the architecture research confirms Header.tsx imports and iterates `NAV_PAGES` directly. After Story 1.1.1b removes `mobileNav: false` from 8 items, those 8 items remain in `NAV_PAGES`. Header.tsx renders items that are `headerNav !== false`, so `mobileNav: false` removal does NOT affect Header at all — but the plan says nothing about verifying this. If any of the 8 newly-mobile items also lack `headerNav: false`, they will appear in the desktop header bar as a regression. The plan never audits which items have `headerNav: false` vs. which currently hide from the header via `mobileNav: false`. Recommendation: before implementation, audit every entry to confirm that removing `mobileNav: false` does not cause unintended appearance in Header.tsx's render path.

- [ ] **Story 1.1.3 is a non-story — it contains no testable acceptance criteria of its own** — The story's AC is "Config Files entry no longer exists, so the bug is eliminated by removal." That is a consequence of Story 1.1.2, not a separate deliverable. If Story 1.1.2 is partially completed or the `Settings` active-state regression (`isMoreActive` returning false for `/settings` paths) is not explicitly tested, this story provides no safety net. Recommendation: either merge 1.1.3 into 1.1.2 and require a test assertion on `isMoreActive` returning `true` for `/settings` paths, or delete the story and add a regression test in Story 4.1.1.

- [ ] **`BOTTOM_NAV_MORE` derivation is never explicitly re-verified after removing `mobileNav: false`** — The plan relies on the claim that removing `mobileNav: false` from 8 entries will automatically add them to `BOTTOM_NAV_MORE`. This depends on how `BOTTOM_NAV_MORE` is computed. The architecture research shows `BOTTOM_NAV_MORE` filters on `mobileNav !== false && !bottomNavPrimary`. If the field removal works as expected, this is correct. However, Notifications is a special case: it is `bottomNavPrimary: true` _specifically_ to exclude it from `BOTTOM_NAV_MORE`, and it is rendered custom outside the `primaryPages.map()`. If any of the newly-unlocked items accidentally have `bottomNavPrimary: true` (or gain it in a future edit), they will be excluded from More and silently unreachable. The plan does not include a count-validation assertion (e.g., "after Story 1.1.1b, `BOTTOM_NAV_MORE.length` must equal N"). Recommendation: add an explicit assertion in nav-pages.test.ts that `BOTTOM_NAV_MORE` contains exactly the expected items after consolidation.

- [ ] **The `group` field is made required on `NavPage` (Story 1.1.1a), but `Header.tsx` and `Navigation.tsx` consume `NavPage` items and will fail TypeScript compilation if their local nav items (if any) lack `group`** — Navigation.tsx is confirmed to not use `nav-pages.ts` at all, so it is safe. But `Header.tsx` iterates `NAV_PAGES` which is the same array being updated. The real risk is if any code creates a `NavPage` literal outside `nav-pages.ts` (e.g., in tests, stubs, or a helper). Making `group` required means all such sites fail to compile. The plan says "run `npx tsc --noEmit`" at step 5, which would catch this — but the plan does not call out that test file mocks that construct `NavPage` objects (e.g., in `BottomNav.test.tsx` or future tests) must also be updated. Recommendation: note explicitly that any `NavPage` literal in test mocks must gain a `group` field, and verify the existing `BottomNav.test.tsx` does not construct `NavPage` objects directly.

- [ ] **The More sheet `maxHeight: 70vh` is hardcoded in CSS** — The plan correctly avoids hardcoding `zIndex` values, but `maxHeight: "70vh"` in `moreSheetScrollable` is a magic viewport-relative value with no token backing. On devices with large notches or variable viewport heights (especially iOS Safari with the collapsible address bar where `100vh !== window.innerHeight`), `70vh` may clip content on small screens or leave excessive empty space on large screens. The pitfalls research explicitly called out the `--bottom-nav-height` ResizeObserver interaction but did not flag the `70vh` hardcode. Recommendation: at minimum, add a comment explaining why `70vh` was chosen; consider using `calc(100dvh - var(--bottom-nav-height, 72px))` to align with the existing CSS variable already set by the ResizeObserver.

- [ ] **The plan's CSS for `moreSheetUtilitySection` uses an interpolated `vars.color.borderColor` directly in a `style()` call** — Task 3.1.2c code sample uses `borderTop: \`1px solid ${vars.color.borderColor}\``. The CSS architecture rules state that token references in `.css.ts` files must use `vars.*` references (not interpolated strings), but vanilla-extract's `style()` function does accept template literal interpolations from theme vars. The concern is that Task 3.1.2b (which the plan says to update) still contains an inline `style={{ borderTop: ... }}` — the plan explicitly says to replace it with a class, but marks the task's code sample as still having the inline version. An implementer following the code sample literally will violate the CSS architecture rule. Recommendation: remove the inline `style` from the Task 3.1.2b code sample entirely, not just flag it in a comment.

- [ ] **DrawerNav feature-flag fix (Story 2.1.2) is bundled with visual grouping changes** — The pitfalls research identifies the DrawerNav feature-flag bug (items render regardless of flag) as a pre-existing bug. The plan fixes it in Story 2.1.2 as part of the grouped rendering refactor. This means the bug fix cannot be landed independently without also landing the grouped rendering. If QA catches a visual regression in the grouped rendering, the feature-flag fix is held back too. Recommendation: either make the feature-flag fix a separate task within Phase 1 (so it can be tested before Phase 2), or accept the coupling and note it explicitly as a release dependency.

## Minors

- The plan counts "15 total entries after removal" in Story 1.1.2 AC, but Story 1.1.1a says "14 remaining entries after consolidation" (referring to the group field assignment). The count mismatch (15 vs. 14) is likely a typo or off-by-one in drafting; the test in Story 4.1.3 verifies the real count so this will surface, but reconciling it in the plan avoids implementer confusion.

- The `NAV_GROUP_LABELS` constant in the plan uses `"settings"` group with label `"Settings & Tools"`, but the architecture research proposed a `"system"` group (Logs, Errors, Help) separate from `"settings"` (Settings, Config Files, Features, Files). The plan collapses system and settings into one group. This is a valid design decision but it is not called out as a change from the research recommendation — an implementer reading both documents in sequence will see a discrepancy without explanation. A brief note in the plan ("research proposed a 5-group structure; this plan consolidates to 4") would prevent confusion.

- `sectionHeader` in DrawerNav.css.ts is implemented as a `recipe()` (has variants), but `moreSheetSectionHeader` in BottomNav.css.ts is implemented as a plain `style()` with no `visible` variant. The collapsed-state hiding logic for section headers is correctly in DrawerNav only (BottomNav doesn't collapse), but the asymmetry between `recipe()` and `style()` for similar-purpose styles is worth a brief comment in the code explaining why.

- Story 4.1.2 lists 5 required DrawerNav tests but the test for "active item receives `aria-current=\"page\"`" depends on `NavigationContext` providing a known pathname that matches a real route. The mock provides `isDrawerOpen: true` but the test plan does not specify which pathname mock to use or which route should become active. An implementer will have to invent this detail; a concrete example route in the AC would save time.

- The `moreSheet` backdrop/overlay behavior when the grouped More sheet opens is not addressed anywhere in the plan. The pitfalls research noted `zIndex.bottomNavMoreSheet` and `zIndex.bottomNavMoreBackdrop` already exist. Since the plan only restructures the sheet's content (not the sheet itself), this is genuinely out of scope — but the review notes it for completeness in case a visual QA step is needed.
