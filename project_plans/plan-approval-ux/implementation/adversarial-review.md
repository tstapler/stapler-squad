# Adversarial Review: plan-approval-ux

**Date**: 2026-08-01
**Verdict**: CONCERNS

## Blockers

- [x] **RESOLVED** (verified against plan.md Task 2.4.1): **`plan_rejection_reason` is never cleared by the `TriggerTriage` regeneration completion write — the plan reintroduces, for the new field, the exact bug class Epic 1 exists to fix for `plan_approved`.** The Domain Glossary (plan.md line 46) and ADR-001 ("Consequences") both explicitly promise `plan_rejection_reason` is cleared by four write sites: `RejectPlan` (sets it, doesn't clear), `ApprovePlan` (Task 3.1.4, `server/services/backlog_service_lifecycle.go`), the backward-transition reset block (Task 2.3.1, same file), and "the `TriggerTriage` completion write." Grepping the plan for every `PlanRejectionReason` occurrence (lines 46, 291, 296, 303, 306, 310, 322, 352, 441, 488, 497) shows no task ever adds `PlanRejectionReason: &clearedReason` to Epic 1's Task 1.1.1 edit at `server/services/backlog_service_triage.go:~2080` — that task (written before Epic 2 introduces the field) only resets `PlanApproved`, and no later epic revisits that file/location to add the missing clear. Concretely: user rejects a plan with reason "missing caching plan" → clicks "Regenerate Plan with This Feedback" (ADR-002's two-click flow, which calls `TriggerTriage`) → regeneration completes, `plan_approved` correctly resets to `false` (Epic 1), but `plan_rejection_reason` still holds the stale text. `derivePlanReviewStatus` checks `changes_requested` (driven by `planRejectionReason !== ""`) with higher precedence than `pending_review`, so the freshly-regenerated, never-yet-reviewed plan is mislabeled "Changes requested" with stale feedback text, instead of "Pending review." — **Recommendation**: add a task in Epic 1 (or a new Epic-2-dependent follow-up task, since the field doesn't exist until Epic 2 lands) that extends the same `backlog_service_triage.go` completion-write `session.BacklogItemUpdate` to also set `PlanRejectionReason: &clearedReason`, and add a regression test (`TestTriggerTriage_RefineWithFeedback_ClearsRejectionReason`) alongside `TestTriggerTriage_RefineWithFeedback_ResetsPlanApproved`.

- [x] **RESOLVED** (verified against plan.md Task 3.1.3b): **`checkPlanArtifactFreshness` fails open on `os.Stat` error, silently defeating the optimistic-concurrency guard for exactly the scenario it exists to catch — and `RejectPlan` has no other precondition check that would catch it.** The helper (Task 3.1.3b) returns `nil` ("pass") whenever `os.Stat(filepath.Join(artifactsPath, "plan.md"))` errors, with the comment "missing plan.md is handled by the caller's own precondition check." That claim is false for `RejectPlan` (Task 3.1.3): its only precondition is `item.PlanArtifactsPath == ""` (a DB-field-empty check, not a file-existence check) — there is no `os.Stat` anywhere in `RejectPlan` before `checkPlanArtifactFreshness` is called. (`ApprovePlan` does have a pre-existing `os.Stat(item.PlanArtifactsPath)`, but that stats the *directory*, not `plan.md` specifically, so it doesn't fully cover this either.) Concrete failure: a concurrent `TriggerTriage` regeneration is mid-rewrite of `plan.md` (unlink-then-create, or the file is briefly missing/renamed) at the exact moment the user's `RejectPlan(expected_modified_at_unix_ms: T1)` call runs. `os.Stat` fails transiently → `checkPlanArtifactFreshness` returns `nil` → the rejection is recorded against content the user never actually saw — precisely the scenario the field's own proto comment says it "guards against" (Task 3.1.1: *"guards against rejecting content the user never actually saw (a regeneration raced their open tab)"*). A stat failure must fail **closed** (return the same `FailedPrecondition` as a mismatch, or a distinct "plan artifact unavailable — reload and try again" error), not silently skip the check. — **Recommendation**: change `checkPlanArtifactFreshness` to return an error (not `nil`) when `os.Stat` fails and `expectedModifiedAtUnixMs != 0`; add `TestRejectPlan_PlanFileGoneMidRegeneration_FailsClosed` / equivalent for `ApprovePlan`.

## Concerns

- [ ] **The Should-Have "approval/rejection history visible in the item's status/progress timeline" is claimed as fully delivered in §0 but admitted as deferred in §7 — an internal contradiction, not just a scoping call.** §0's Approach C row claims Approach C "Delivers all four Must-Haves **and both Should-Haves** ... (approval/rejection *visibility* via the durable reason field)." §7 Unresolved Question #1 then states multi-entry rejection history "is served only as *most-recent-reason visibility* in this pass" and that a real timeline entry (mirroring `BacklogProgressNote`) "is deferred to a follow-up." Nothing in the plan adds an entry to the item's actual status/progress timeline UI for approve/reject events — `PlanVerdictBox` only shows the *current* reason on a card, which is a different requirement than "history ... visible in the ... timeline." A reader who only reads §0 (the creative-pass summary most likely to be skimmed) would believe this Should-Have ships in full. — **Recommendation**: reword §0's Approach C row to say "gate legibility (skipped state) and current-reason visibility; full timeline history explicitly deferred, see §7 Q1" so the two sections agree.

- [ ] **`checkPlanArtifactFreshness` is hardcoded to stat `plan.md` regardless of which artifact filename the client actually fetched and is echoing back — a latent correctness trap once other artifacts are wired up.** `GetPlanArtifactContent` is generalized over an allowlist (`plan.md`, `requirements.md`, `validation.md`, `research/*.md`, Task 4.2.1) and requirements.md itself says other artifacts "are the same rendering path and can reuse the new RPC/component if scope allows" — i.e., this is an anticipated near-term extension, not hypothetical. But `checkPlanArtifactFreshness` always stats `plan.md` (Task 3.1.3b), never the filename the token was actually derived from. Today this is masked because Epic 7's only UI call site hardcodes `getPlanArtifactContent(item.id, "plan.md")` (Task 7.1.3) — but the RPC contract doesn't enforce that pairing, so the first follow-up that renders `requirements.md` and wires its mtime into Approve/Reject will silently validate against the wrong file (false "stale" rejections, or false passes). — **Recommendation**: either scope `expected_modified_at_unix_ms` explicitly to `plan.md` only in the proto comment (and reject/ignore tokens sourced from other files), or thread the filename through the freshness check now while the surface area is small.

- [ ] **`reconcilePlanNotApprovedItems`'s widened staleness clock (`item.UpdatedAt` fallback) measures the wrong thing for `ready`-status items.** Task 8.1.1 falls back to `item.UpdatedAt` when `item.QueuedAt` is nil. `UpdatedAt` is a whole-row timestamp bumped by *any* field write — editing the item's title, tags, description, or any other unrelated field resets the staleness clock. A plan that has genuinely sat unreviewed for weeks would never trip `StuckReasonPlanNotApproved` if the user (or automation) touches any other field on the item in the meantime, unlike `QueuedAt`, which is a purpose-built, stable timestamp that only reflects queue entry. This silently weakens the very detection gap Epic 8 exists to close. — **Recommendation**: use the `TriggerTriage` completion timestamp (when `PlanArtifactsPath` was last set) rather than row-wide `UpdatedAt`, or add a dedicated `PlanArtifactsSetAt` field if one doesn't already exist.

- [ ] **Epic 8's widening is scope beyond what requirements.md's Should-Have literally asks for, and isn't flagged as a deliberate scope decision needing sign-off.** Requirements.md's Should-Have #2 is "Making the plan-approval gate apply consistently regardless of queued vs. direct path (**or an explicit documented decision not to**)." Architecture.md (per P8) confirms enforcement is *already* uniform (verified independently in this review: `SpawnSessionFromItem`'s step 3b and `spawnSessionAfterGates`'s step 4b both gate on `!item.SkipPlanning && !item.PlanApproved && !autonomous`). The documented-decision-not-to-change-enforcement option would satisfy the Should-Have as literally worded. Instead, P8 goes further and adds new stuck-item detection/notification behavior for `ready`-status items that never opted into queue semantics — a real, separate feature (new notifications firing for items that previously never triggered them) bundled into what could have been a no-code "already consistent, documented" resolution. Not necessarily wrong, but it's an expansion of behavior that should get an explicit go/no-go rather than being packaged as if it were the natural conclusion of "or an explicit documented decision not to."

- [ ] **No e2e coverage is added for the direct-spawn-path gate check — pitfalls.md's own flagged gap remains a zero-coverage gap after this plan ships.** pitfalls.md §3 explicitly calls out: *"The [existing] spec covers only the `DequeueNextQueuedItems` / queued-item path ... If Success Criterion #2 ('consistent gate') extends gating to other spawn paths, new gate assertions are needed for those paths ... 'consistent gate' work could ship with zero e2e coverage of the parts that are actually new."* Epic 9's Story 9.3 only (a) re-runs `plan-gate.spec.ts` unmodified as a regression check (Task 9.3.1) and (b) adds `plan-review.spec.ts` covering reject/regenerate/content-rendering (Tasks 9.3.2–9.3.3). Nothing exercises `SpawnSessionFromItem`'s direct-call gate (step 3b) end-to-end. Since Epic 8 stops short of changing enforcement (see above), this is defensible if enforcement genuinely isn't "new" — but the plan should say so explicitly rather than leave it implicit, since a future reader diffing requirements.md's Success Criterion #2 against Epic 9's test list would reasonably expect direct-path coverage to appear somewhere.

- [ ] **Two open tabs racing Approve vs. Reject (or Reject vs. Reject) on an unchanged plan is not prevented, only documented as a general limitation — worth an explicit statement that it's accepted, not overlooked.** `expected_modified_at_unix_ms` detects "the underlying plan *content* changed since you fetched it" (file mtime), but neither `ApprovePlan` nor `RejectPlan` do a compare-and-swap on the `BacklogItem` row itself. Two tabs that both fetched the same `plan.md` (same mtime) can race — one submits Approve, the other submits Reject — and since neither of those actions touches `plan.md`'s mtime, both freshness checks pass and the second call silently overwrites the first's outcome with no conflict error to either tab. Requirements.md scopes out "multi-user / concurrent-reviewer approval workflows," but same-user-multiple-tabs is arguably still in scope for a "solo developer" persona (a very plausible browsing pattern: item detail open in two tabs). — **Recommendation**: either explicitly extend the Out-of-Scope note to cover multi-tab-same-user races, or add a lightweight last-write check (e.g., include the item's own `updatedAt` in the token, not just the file mtime).

- [ ] **`PlanVerdictBox` receives a pre-computed `status` prop while `ActionsSection` recomputes `derivePlanReviewStatus(item)` independently — same function, but two different invocation shapes.** Task 6.1.3 computes `derivePlanReviewStatus(item)` once in `BacklogItemDetail` and passes the *result* into `PlanVerdictBox` as a `status` prop; Task 6.1.4 has `ActionsSection` call `derivePlanReviewStatus(item)` itself from its own `item` prop. Both ultimately read from the same `item` object in the same render pass today, so there's no live bug, but the two call sites aren't structurally symmetric — a future edit to either surface (e.g., memoizing `PlanVerdictBox`'s parent computation, or `ActionsSection` sourcing `item` from a different context/selector) can silently break the "one source of truth" property the Risk Control table (§6) claims is guaranteed by "both call the same helper." — **Recommendation**: pick one shape consistently — either both components accept `item` and compute internally, or `BacklogItemDetail` computes once and passes `status` to both.

## Minors

- P5's mtime-collision dismissal ("not a real risk... within the same millisecond") is reasonable given `TriggerTriage` regenerations are LLM-call-gated (minutes apart per ADR-002), but the plan doesn't note that some filesystems/network mounts have only 1-second mtime resolution — low risk for this repo's local-SQLite deployment model, worth a one-line caveat rather than a silent assumption.
- Story 1.1's Given/When/Then only describes the feedback-driven regeneration case, but the actual code change (Task 1.1.1) fires unconditionally on every `TriggerTriage` completion (fresh or feedback-driven) — correct and desirable, but the acceptance criterion undersells what's actually being fixed; worth broadening the criterion's wording for clarity.
- `GetPlanArtifactContent`'s allowlist (`isAllowedPlanArtifactFilename`) accepts any `research/*.md`, which is broader than what Epic 7's UI ever calls (only `plan.md` for v1) — not a security issue (still server-resolved, traversal-checked), just unused surface area shipped ahead of its consumer; fine to leave as-is but note it's speculative relative to this pass's actual UI wiring.
