## Blockers

- [x] **RESOLVED** (verified against plan.md Task 8.1.1): **Epic 8, Task 8.1.1 (`session/backlog_lifecycle.go`) — widened detection is dead code because `MarkStuck`'s hardcoded `expectedStatus` argument never changes.**
  `reconcilePlanNotApprovedItems` (line 2538) calls `er.MarkStuck(ctx, item.ID, domain.StuckReasonPlanNotApproved, BacklogStatusQueued, ...)` with `BacklogStatusQueued` hardcoded as the fourth argument. `MarkStuck`'s own precondition check (`session/ent_repository_backlog.go:1060`) is `if current.Status != string(expectedStatus) { return false, nil }` — a **silent** no-op, not an error, with no log line at the call site (`if !applied { continue }`, line 2544-2546). Task 8.1.1 widens the `Statuses` filter to include `BacklogStatusReady` items and adds a `QueuedAt`-vs-`UpdatedAt` fallback, but never updates the hardcoded `BacklogStatusQueued` passed into `MarkStuck`. Every newly-included `ready`-status item will have `current.Status == "ready" != "queued"`, so `MarkStuck` will always return `applied=false`, and the entire Should-Have (requirements.md Success Criterion 2 / plan.md Epic 8's stated acceptance criterion) silently does nothing for the one status class it was built to newly cover. The task's own acceptance-criterion Given/When/Then ("the item is marked stuck... matching what already happens for queued-status items") will not hold.
  **Remediation**: Task 8.1.1 must also change the `MarkStuck` call to pass the item's actual current status, e.g. `er.MarkStuck(ctx, item.ID, domain.StuckReasonPlanNotApproved, BacklogStatus(item.Status), ...)`, and Task 8.1.3's test must assert this against both a `queued` and a `ready` seed item (the existing test plan only exercises `ready`, missing a regression check that `queued` still works).

- [x] **RESOLVED** (verified against plan.md Task 8.1.1b): **Epic 8 — `selfHealStuck`'s resolve condition for `StuckReasonPlanNotApproved` immediately un-flags any `ready`-status item, defeating detection even if the blocker above is fixed.**
  `session/backlog_lifecycle.go:3052-3053`: `case domain.StuckReasonPlanNotApproved: resolve = row.ItemStatus != BacklogStatusQueued`. This runs every tick via `selfHealStuck` (registered before `reconcilePlanNotApprovedItems` completes a full staleness window). If a `ready`-status item is ever successfully marked stuck (post the fix above), `row.ItemStatus` will be `"ready"`, and `"ready" != "queued"` evaluates `true` — so `selfHealStuck` will resolve/clear the stuck state on its very next run, before a human ever sees the notification persist. Task 8.1.1/8.1.2 as scoped touch only `reconcilePlanNotApprovedItems` (the detector) and never mention this second consumer of the same `StuckReasonPlanNotApproved` reason (the resolver) — the plan's task-scoping (`grep`-style "3-5 files" boxes) missed a call site in the same file that must change in lockstep. This is the shotgun-surgery pattern the plan's own task-sizing discipline is supposed to catch.
  **Remediation**: Extend the resolve condition to account for both anchor statuses, e.g. `resolve = row.ItemStatus != BacklogStatusQueued && row.ItemStatus != BacklogStatusReady`, or — better, since "resolved" really means "the underlying condition cleared," not "the status changed" — resolve based on `SkipPlanning || PlanApproved` directly rather than status-anchoring at all for this specific reason. Add this file/line explicitly to Epic 8's task list (a new Task 8.1.1b) so it isn't missed a second time in implementation.

- [x] **RESOLVED** (verified against plan.md Task 3.1.3 and Task 3.1.7): **Epic 3, Story 3.1 (`RejectPlan` handler) — the "derived, not stored" design has a real, non-defensive window where `plan_approved=true` and `plan_rejection_reason` non-empty coexist, and the backend spawn gate disagrees with the UI.**
  `RejectPlan`'s handler (Task 3.1.3) only sets `PlanRejectionReason`/`PlanRejectedAt` — it never resets `PlanApproved`. `ApprovePlan` (Task 3.1.4) is made symmetric in the other direction (clears `PlanRejectionReason` on approve), but the reverse case is missing. `PlanVerdictBox`'s "Request Changes" toggle (Task 5.2.2/5.2.3) is not gated to only the `pending_review` state — nothing in the plan conditions it out of the `approved` state — so a normal user flow ("I approved this plan, then noticed a problem and want to reject it") produces a **persisted, non-transient** row with `plan_approved=true AND plan_rejection_reason="..."`. Task 5.1.2 frames this combination as a purely defensive/"shouldn't happen" case that "Task 3.1.4 prevents" — that framing is incorrect; Task 3.1.4 only prevents the opposite direction. On the frontend, `derivePlanReviewStatus` correctly prioritizes `changes_requested` over `approved` (masking the inconsistency for `PlanVerdictBox`/`ActionsSection`). But the **backend** spawn gates at `server/services/backlog_service_triage.go:438` (`!isReopen && !item.SkipPlanning && !item.PlanApproved && !req.Msg.Autonomous`) and `:656` (`!item.SkipPlanning && !item.PlanApproved && !autonomous`) check the raw `PlanApproved` bool directly and never consult `PlanRejectionReason`. Concretely: approve a plan → reject it → the UI shows "Changes requested" and blocks the button, but a session can still spawn (or `DequeueNextQueuedItems` can still dequeue) because the actual gate never learned the plan was rejected. This is exactly the kind of "correctly-interpreted-only-by-luck-of-derivation-order" gap the task brief's Lens 2 question flags — and here it's provably not luck, it's a real divergence between two different consumers of the same underlying fields.
  **Remediation**: Make `RejectPlan` symmetric with `ApprovePlan` — add `approvalReset := false; update.PlanApproved = &approvalReset` to Task 3.1.3's handler, so rejecting a plan always clears approval at the single write site, the same way Task 1.1.1 (Epic 1's correctness fix) already resets `PlanApproved` on `TriggerTriage` regeneration. This closes the gap without requiring every gate-check call site to be taught about `PlanRejectionReason`. Add a test mirroring `TestApprovePlan_ClearsExistingRejectionReason` (Task 3.1.6) in the other direction: `TestRejectPlan_ClearsExistingApproval`.

## Concerns

- [ ] **Domain Glossary cites a nonexistent task, and the gap it describes is real.** The Domain Glossary (plan.md §2, `PlanReviewStatus` row) states the derivation is "mirrored as a Go type where the same derivation is needed server-side for MCP prompt injection (`session/backlog_review.go`, Task 5.3.1)." No Story 5.3 or Task 5.3.1 exists anywhere in the 9-epic/51-task breakdown — Epic 5 only contains Stories 5.1 and 5.2 (confirmed via full-text search of plan.md). `session/backlog_review.go` currently reads `item.PlanArtifactsPath` and injects `readPlanFile(item.PlanArtifactsPath)` content directly (lines 249-250, 331-332) with no awareness of `PlanApproved`/`PlanRejectionReason` at all, and nothing in Epics 1-9 changes that file. Either this was scope that got dropped between drafting the glossary and writing the epics, or it's a stale cross-reference. As shipped, an MCP/AI consumer of `backlog_review.go`'s injected context has no way to see "this plan was previously rejected: <reason>" except via whatever ends up in the next `TriggerTriage(feedback)` call — which is a different, narrower channel (one-shot regeneration input, not standing context).
  **Remediation**: Either add a real task (e.g. Task 5.3.1: a Go `PlanReviewStatus` type + `DerivePlanReviewStatus(item) PlanReviewStatus` function in `session/`, consumed by `backlog_review.go`'s prompt-injection path) or strike the glossary's promise and move it to plan.md §7 (Unresolved Questions / explicitly deferred) alongside the other intentionally-cut items, so the plan is internally consistent about what it delivers.

- [ ] **No canonical Go-side `PlanReviewStatus` derivation — this is the root cause of the Epic 3 blocker above, not just a style preference.** Lens 2 Question 5 asks whether the Go-side derivation should also be a typed enum rather than left implicit. The plan's answer (TS union type on the frontend, raw field checks on the backend) is defensible for the UI layer, but the concrete consequence is visible in the Epic 3 blocker: because there is no single authoritative Go function that every backend consumer of "is this plan actually approved" calls, the two raw-field gate checks at `backlog_service_triage.go:438,656` were free to diverge from the newly-introduced `plan_rejection_reason` semantics. A parse-at-boundary discipline (Lens 2 Question 7) that's only enforced on one side of the wire (TS) isn't a parse-at-boundary discipline at all from the backend's perspective — it's still primitive fields checked ad hoc at each call site.
  **Remediation**: Add a Go-side `PlanReviewStatus` type + `DerivePlanReviewStatus(item)` function (mirrors `web-app/src/lib/backlog/planReviewStatus.ts` 1:1, same precedence order) in `session/` or `server/services/`, and refactor the two gate checks at `backlog_service_triage.go:438,656` to call it (e.g. `status := DerivePlanReviewStatus(item); if status != PlanReviewApproved && status != PlanReviewSkipped { ...block... }`) instead of checking `item.PlanApproved`/`item.SkipPlanning` directly. This makes the "derived, not stored" invariant enforced by one function instead of by convention across scattered call sites, and would have made the Epic 3 blocker impossible to introduce (the gate check and the UI status card would share one source of truth). This subsumes the previous concern's remediation — the same type/function serves both `backlog_review.go` and the gate checks.

- [ ] **`BacklogItemDetail.tsx` (already 1263 lines) continues to grow via inline `useCallback` handlers rather than an extracted hook.** Task 6.1.2 adds `handleRejectPlan`/`handleRegeneratePlanWithFeedback` "near `handleGateReopen`" — consistent with the file's existing style, so this isn't a new violation the plan introduces, but it does continue a pre-existing SRP erosion (one component owning fetch state, toast orchestration, and action handlers for every backlog-item sub-feature). Not a blocker for this plan's scope, but worth naming before the next feature adds two more handlers to the same file.
  **Recommendation**: Not required for this plan, but consider a `usePlanReviewActions(item, load, showActionToast)` extraction hook (mirroring whatever pattern, if any, already exists for the gate-review handlers) as a low-priority follow-up once `BacklogItemDetail.tsx` crosses ~1400 lines.

## Nitpicks

- Epic 8's staleness anchor (`since = item.UpdatedAt` when `QueuedAt` is nil) resets on *any* field update to a `ready`-status item, not just plan-related ones — editing an unrelated field (title, tags) on an item with a genuinely stale, unapproved plan would mask the staleness. A plan-specific timestamp (e.g. the time `PlanArtifactsPath` was last set) would be a tighter anchor. Low priority since this is a Should-Have detector, not the enforcement path itself.
- `GetPlanArtifactContent` (Task 4.2.1) reuses `resolveAndValidatePath`/`readFull`/`maxFileSize`/`truncateSize` from `file_service.go` (good — P10 is a sound decision), but the ~15-line stat-size-check-then-truncate-then-read sequence (lines 612-629 in the plan's code block) is copy-pasted near-verbatim from `FileService.GetFileContent` (`file_service.go:390-409`). A shared `readCappedFile(path string) (content string, truncated bool, size int64, err error)` helper in `file_service.go` would remove the duplication; not urgent given both call sites already share the underlying constants and primitives.
- `BacklogItem`'s aggregate keeps accreting loosely-related nullable fields one pair at a time (`plan_approved`/`plan_approved_at`, now `plan_rejection_reason`/`plan_rejected_at`). The plan's decision not to introduce a new aggregate root (ADR-001) is correct and well-justified against the `status_events` FSM invariant — but a `PlanReview{Approved, ApprovedAt, RejectionReason, RejectedAt}` embedded struct (mapped to the same flat ent columns) would group the four related fields at the type level without changing the schema or violating ADR-001, and would give the Go-side `DerivePlanReviewStatus` function (see Concerns) a natural single parameter instead of four loose fields threaded through call sites. Cosmetic; not blocking.
