# Pre-mortem: plan-approval-ux
**Date**: 2026-08-01

Imagining this project shipped and, one month later, isn't actually solving the
problem requirements.md set out to fix (or is quietly breaking). Five failure
modes below, each grounded in specific plan.md tasks and (where applicable) the
prior review findings that already flagged the underlying mechanism.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Two open tabs race Approve vs. Reject on the same item. `expected_modified_at_unix_ms` (Task 3.1.1) only guards against the plan *file* changing — neither `ApprovePlan` nor `RejectPlan` does compare-and-swap on the `BacklogItem` row itself, so a stale second tab's write silently overwrites the first's outcome with no conflict error to either tab (adversarial-review.md Concern, accepted-not-prevented). | Tyler approves in one tab, later discovers a session spawned/queued despite having rejected the same plan minutes earlier in a second stale tab — no error surfaced anywhere, just an unexpected final state. | Extend the token to also cover `BacklogItem.UpdatedAt` (not just the file mtime) so a stale second write returns `FailedPrecondition`; or explicitly move same-user-multiple-tabs into requirements.md's Out-of-Scope section instead of leaving it an implicit, undocumented risk. | P2 |
| 2 | Epic 8's widened stuck-detection for `ready`-status items falls back to `item.UpdatedAt` (Task 8.1.1) when `QueuedAt` is nil. `UpdatedAt` is a whole-row timestamp bumped by *any* field write (title, tags, description) — so a plan that's sat unreviewed for weeks never trips `StuckReasonPlanNotApproved` if any other field on the item is touched in the meantime (flagged as a Concern/Nitpick in both reviews, never remediated in plan.md). | The gate-legibility feature (requirements.md Success Criterion 2 / the project's #2 stated problem) ships, passes CI against a synthetic untouched item, and then never fires in production because real backlog items get edited (tags, comments, triage feedback) far more often than the 5-minute staleness window — Tyler believes visibility is fixed but it silently isn't. | Anchor staleness to a plan-specific timestamp (e.g. when `PlanArtifactsPath` was last set, or a new `PlanArtifactsSetAt` field) instead of row-wide `UpdatedAt`; add a test that edits an unrelated field after plan generation and asserts staleness still trips. | P1 |
| 3 | No canonical Go-side `PlanReviewStatus`/`DerivePlanReviewStatus` function (architecture-review.md Concern, explicitly deferred per plan.md §7 Unresolved Question 5). Today's known gate/UI divergence is patched at individual write sites (Epic 3), but nothing structurally prevents the next new field or gate check from reading `item.PlanApproved` directly and reintroducing the same class of bug the Epic 3 blocker just fixed. | A future, unrelated change adds a gate check or state field that doesn't consult `PlanRejectionReason`, silently letting a session spawn against a plan the UI shows as rejected — discovered only when the mismatch is noticed by accident. | Add the Go-side `DerivePlanReviewStatus(item)` helper now and refactor the two known gate checks (`backlog_service_triage.go:438,656`) to call it, per architecture-review.md's own remediation — treat this as closing the root cause, not just today's symptom. | P2 |
| 4 | ADR-002's two-click reject flow (reject records a reason; a separate, easy-to-miss "Regenerate Plan with This Feedback" button must be clicked to act on it) assumes Tyler returns to a rejected item later — nothing prompts, surfaces, or defaults to that follow-up action. | Weeks after rejecting a plan, the item is still sitting in `changes_requested` with the original reason untouched, never regenerated, competing for attention against every other backlog item with no distinct "needs action" surface. | Add a distinct "needs action" filter/list for `changes_requested` items in the backlog UI so they don't rely on memory; validation.md should include a manual test that simulates "reject and walk away for a week" and checks the item is still discoverable. | P2 |
| 5 | Task 8.1.2's stuck-notification copy is a single fixed string ("Approve the plan or update the item to unblock it.") regardless of whether the item is `pending_review` or `changes_requested` — for a rejected plan the correct next step is "regenerate," not "approve," so the message actively mis-guides. | Tyler gets a stuck-item notification for an item he already rejected, opens it expecting something new, finds only his own stale rejection reason and a nonsensical "approve" prompt — erodes trust and increases the chance future notifications (including genuinely new ones) get dismissed unread. | Branch the notification text on whether `PlanRejectionReason` is non-empty (mirrors `derivePlanReviewStatus`'s `changes_requested` branch) so rejected-plan items get "regenerate or update the item" copy instead; add a test asserting both message variants. | P3 |
