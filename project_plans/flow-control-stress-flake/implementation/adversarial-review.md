## Concerns

- [ ] **Story 1.1.1's AC3 regression example doesn't actually exercise the assertion it cites** — the plan's proof that the test "still fails if the underlying flow-control logic regresses" proposes deleting the `LOW_WATERMARK` check at line 36 (`if (this.watermark < this.LOW_WATERMARK && this.paused) { this.paused = false; ... }`). But `expect(metrics.watermark).toBeLessThan(50000)` (line 290) tests `watermark`, and the watermark decrement two lines above (`this.watermark = Math.max(0, this.watermark - data.length);`) runs unconditionally inside the same `setTimeout` callback, regardless of `paused` or the deleted check. Deleting that check only stops `paused`/`resumeCount` from ever resetting — neither of which `handles alternating text and control codes` asserts. The cited example would not make the test fail. Recommendation: replace the example with one that actually perturbs `watermark`, e.g. deleting the `Math.max(0, this.watermark - data.length)` decrement itself (which would make watermark grow monotonically and trip the `<50000` assertion), before `sdd:4-validate` treats AC3 as proven.

- [ ] **Task 1.1.3c's contention-repro mechanism is not reliably CPU-heavy on repeat runs** — I ran `make proto-gen` live in this worktree to verify the timer API; it took ~6.4s, but only because `node_modules` and the generated proto stamp file didn't exist yet (it did an implicit `pnpm install` + full `buf generate`). The Makefile target (`proto-gen`, `Makefile:397-407`) is stamp-file-guarded: on a second run with no proto source changes, it prints "Checking if proto files need regeneration..." and does nothing. By the time an implementer reaches Task 1.1.3c, `node_modules` will already be installed and protos already generated by earlier steps in the same session, so `make proto-gen` will most likely be a near-instant no-op — undermining the task's stated purpose of "approximating the original repro's `pnpm install` + `make proto-gen` contention." Recommendation: use a synthetic CPU-load generator instead (e.g. `stress-ng --cpu $(nproc) --timeout 30s &` or a handful of `yes > /dev/null &` background processes), or force a real regen by touching a `.proto` file first.

- [ ] **Off-by-one line-range labels in Task 1.1.1c (and cosmetically in 1.1.2b)** — Task 1.1.1c says "Replace lines 283-285" but the quoted/replacement block spans lines 283-286 (comment, `if`, `await`, and the closing `}` on line 286). The same pattern appears in Task 1.1.2b, which says "Replace line 216:" but quotes lines 215-216 (comment + `await`). The quoted code content itself is verified correct in both cases, and `Edit` matches on exact string content rather than line numbers, so this does not block mechanical execution — but the range labels should be corrected before this plan is used as a reference, since AC1/AC2's traceability claims depend on accurate line citations.

- [ ] **`jest.advanceTimersByTimeAsync` (the async variant actually being introduced) has zero prior usage anywhere in this repo** — `grep -rl "advanceTimersByTimeAsync" src/` returns nothing; the 42 files matched by a broader `useFakeTimers`/`advanceTimersByTime` search all use the synchronous `advanceTimersByTime` or `useFakeTimers()` alone. The plan's "already-adopted toolchain, no ADR needed" framing is accurate for fake timers as a general mechanism, but this specific async API is net-new to the codebase (even though now verified to exist and be correctly typed for the pinned `jest@30.2.0`). This raises the importance of actually running Story 1.1.3's verification tasks (not just trusting the type signature) since there's no existing in-repo precedent to fall back on if the runtime behavior surprises.
