# Validation Plan: cold-start-uuid-loss

**Date**: 2026-08-06

## Happy Path Scenario

Given a session whose tmux pane died with no conversation UUID captured in memory but a resumable JSONL still present on disk for its effective root dir, when any of the four launch-command-building call sites (`startLocked`, `start`, `Resume`, `Restart`) runs, then `prepareColdRestore()` recovers the UUID via `recoverConversationUUIDByPath()` before the launch command is built, the resulting `i.LaunchCommand` contains `--resume <recovered-uuid>`, and `i.LastReviveOutcome == ReviveOutcomeResumeRecovered` — so the conversation continues instead of silently starting fresh.

## Migration Note

plan.md's Migration Plan (lines 128-151) is additive-only: four new fields (`startCycleGeneration`, `recoverySuppressedGeneration` — in-memory only, zero-value `0` is correct/safe; `everHadConversationHistory`, `LastReviveOutcome` — persisted with `,omitempty`-style JSON tags, zero-value `false`/`""` is correct/safe) plus one new proto field (`revive_outcome = 72`, proto3 optional-by-default). There is no schema/DB migration script, no backfill, and no reversibility concern to test — a `migration_should_be_reversible` test is intentionally **not** added. An existing session loaded from disk with no `ever_had_conversation_history`/`last_revive_outcome` keys present simply deserializes to the safe zero value, which Task 1.1.1c's mapping-function tests (covered under Story 2.1.1's rows above, transitively — the adapter reads whatever `InstanceSnapshot` provides) already exercise as the default case.
