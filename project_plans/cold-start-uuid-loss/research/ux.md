# UX Research: cold-start-uuid-loss

## 1. Comparable UX patterns in this codebase

The repo already has a full, wired pipeline for surfacing "degraded/unexpected backend state" — this is not a greenfield UX problem, it's a routing problem: pick the right existing mechanism(s) rather than inventing a new one.

**Backend → frontend event pipeline** (the load-bearing mechanism):
- `pkg/events/types.go`'s `NewNotificationEvent(sessionID, sessionName, notificationID, notificationType, priority, title, message, metadata)` (`pkg/events/types.go:222-245`) is the existing constructor for a session-originated notification event (`EventNotification` / `EventType = "session.notification"`).
- `server/services/event_converter.go:52` converts it to `sessionv1.SessionEvent_Notification` on the wire.
- `server/notifications/store.go`'s `NotificationHistoryStore` (`server/notifications/store.go:76-98`) persists it **server-side** to a JSON file (`Append`, `server/notifications/store.go:129-162`), not just client `localStorage` — this is the durable half of the "durable, visible signal" requirement. It dedupes by `(sessionID, notificationType)` for unread records and tracks `OccurrenceCount`.
- Frontend: `NotificationContext.tsx` subscribes to the RPC stream → feeds `NotificationToast.tsx` (`web-app/src/components/ui/NotificationToast.tsx`) for the transient toast and `NotificationPanel.tsx` / `useNotificationHistory.ts` for the persistent history list (`NotificationsPage.tsx` at `/notifications`).
- Proto enum `NotificationType` (`proto/session/v1/types.proto:768-794`) already has `NOTIFICATION_TYPE_WARNING = 8` (High/Urgent priority by default per the comment) — a plausible fit for "started fresh, could not resume" without adding a new enum value. `NOTIFICATION_TYPE_STATUS_CHANGE = 12` is a weaker but adjacent fit.

**Status badges for degraded/attention states** (session-detail / list-level, not toast):
- `StatusBadge.tsx` (`web-app/src/components/sessions/StatusBadge.tsx:15-37`) renders `AttentionReason` (proto enum, `proto/session/v1/types.proto:638-660`) as a small colored/icon badge with `role="status"` and a `title` tooltip — e.g. `ERROR_STATE`, `UNCOMMITTED_CHANGES`, `STALE`. This is the pattern for a **persistent, glanceable per-session indicator** rather than a fire-and-forget toast.
- `SubStatusChip.tsx` (`web-app/src/components/sessions/SubStatusChip.tsx`) is the finer-grained live-activity variant (`PROCESSING`, `RATE_LIMITED`, etc.), also `role="status"`, rendered inline near the session row/header. Both explicitly render `null` for unknown/unspecified values rather than throwing — a forward-compatibility pattern worth replicating for any new enum value.
- `TriageErrorBanner.tsx` (`web-app/src/components/backlog/TriageErrorBanner.tsx:16-40`) is the closest existing analog to an inline, non-dismissible-until-acted-on **banner for a backend error surfaced in a specific view** — `role="alert"`, message + two explicit recovery actions (`Reload item`, `Skip without applying`). No auto-dismiss; the user must choose an action.

None of these three patterns is wrong for this bug — they answer different questions ("is this notable right now" vs "is this session in a degraded state" vs "here's an error, pick a recovery action"). See section 2 for which one(s) fit the cold-start-uuid-loss case.

## 2. User mental model

The event this bug needs to surface is: *"I asked you to resume, and it silently didn't — this is a different, empty conversation."* Framing matters: telling the user "started fresh" without context reads as neutral/expected (like starting a genuinely new session), but the actual user experience is a broken expectation of continuity. The message should say what happened AND why the user should care, e.g.: *"Couldn't resume this session's prior conversation — a new one started instead. Your previous conversation is preserved but not loaded."*

What the user needs, based on the requirements' explicit non-goals and success metrics:
- **Not silently informational-only** — per requirements.md's "Alternatives Considered," a louder log line alone was explicitly rejected as insufficient (`requirements.md:56`). The marker must be inspectable, not just flashed.
- **Should NOT be a blocking modal** — requirements.md explicitly says the fresh-start "never blocks revive indefinitely" (`requirements.md:22`); the UI shouldn't force an interaction gate either, since the fresh session is already usable and the user may want to keep working immediately.
- **Dismissible but not ephemeral-only**: a toast alone is a bad fit here because the user may not be looking at the screen when the revive happens (this triggers on service restarts, hibernation-wake, reboot — precisely the moments a user is *not* watching the UI). If the only signal is a 8-12s auto-closing toast (per `notification-policy.ts:38-42`), it will frequently be missed entirely, defeating the point. This argues for **both**: a toast for the in-the-moment case, AND a persistent, glanceable badge on the session (StatusBadge-style) so the signal survives past the toast's lifetime and is visible whenever the user next opens that session — matching the "durable" requirement in requirements.md's Success Metrics.
- **Actionable**: at minimum a link/button to view the orphaned prior conversation's JSONL history (the repo already has conversation-history browsing per `HistoryDetailPanel.tsx:154`'s "Start a new session resuming this conversation" pattern — reuse that affordance rather than inventing a new JSONL viewer). This turns "your context is gone" into "your context is recoverable, here's how," which directly serves the emotional JTBD in section 5.
- **Should NOT require immediate action** — unlike `TriageErrorBanner`'s forced-choice pattern (reload/skip), there's no live process here to gate; the fresh session already started successfully, so the marker is retrospective, not blocking.

## 3. Accessibility requirements

Per `.claude/rules/css-architecture.md` and observed conventions in the existing components read:
- **New component styling must use vanilla-extract** (`.css.ts` colocated file), importing tokens from `web-app/src/styles/theme.css.ts` — never hardcoded hex or raw `var()` strings in new `.css.ts` files (see the rule's "Never Do" list). If instead extending an existing `.module.css` (e.g. adding a variant to `StatusBadge.css.ts`), only reference tokens already defined in `web-app/src/app/globals.css` (`--warning`, `--warning-bg`, `--warning-text` at lines 54-55, 130 are the fitting triad for a "recoverable but degraded" signal — matches `.alert` conventions at `globals.css:379-394`, which use `--error`/`--error-bg`/`--error-text` for the more severe case).
- **`role="status"` for badges/chips, `role="alert"` for banners/toasts** — every component read (`StatusBadge`, `SubStatusChip`, `TriageErrorBanner`, `NotificationToast`) consistently uses one of these two roles plus `aria-label` mirroring the visible text. `NotificationToast.tsx:166` additionally sets `aria-live="assertive"` for approval-needed (blocking) toasts vs `"polite"` for the rest — a fresh-start notice is not blocking, so `"polite"` is the right level, matching e.g. a warning-severity toast.
- **Icons are `aria-hidden="true"`** with the label text always present as visible text too (not icon-only) — see `StatusBadge.tsx:101` and every `SubStatusChip` case. Do not rely on emoji alone to convey the state.
- **Focus management**: `NotificationToast.tsx:99-103` moves focus to the primary action button on mount for the `"undo"` toast variant (WCAG 2.4.3) — if the fresh-start toast ships with a "View prior conversation" action button, consider whether it warrants the same treatment, though given it's non-blocking/dismissible this is more defensible to skip than for the undo case (undo has a narrow time window; this doesn't).
- **No project-wide documented contrast ratio target found** beyond CI enforcement: project `CLAUDE.md` states "UX analysis CI... Axe Core (blocks on WCAG AA violations)" runs on PRs touching `web-app/src/` — so **WCAG AA is the enforced bar**, checked automatically, not just documented convention. Any new banner/badge/toast variant must pass Axe Core in CI, which will catch contrast issues using the existing `--warning*`/`--error*` tokens (already presumably AA-compliant since they're reused across the app) — but a novel color choice would need manual verification.
- **Lighthouse CI** also runs (warn-only, threshold 70) per `CLAUDE.md` — not a hard gate but worth not regressing.

## 4. Edge cases: session closed/archived after fresh-start

This is a real gap in the current mechanism, not just a hypothetical:
- `NotificationHistoryStore` has **orphan pruning**: `PruneOrphaned` / `pruneOrphanedRecords` (`server/notifications/store.go:363-396`) removes records where `SessionScoped == true` and the session no longer exists, gated by `SetSessionExistenceLookup` and run at most once per minute (`orphanPruneInterval = 1 * time.Minute`, `store.go:96`). **Open question needing Phase 3 research**: does "session no longer exists" mean *deleted*, or does it also cover *archived*? If archival counts as non-existent for this lookup, a fresh-start marker would vanish from notification history the moment the user archives the session — which is exactly the scenario requirements.md's success metric wants to avoid ("started fresh — could not resume prior conversation" marker inspectable via the events/status API, not just log grep). This needs to be checked against whatever `existingSessionIDs()` lookup function server-side wiring uses (likely in `server/server.go` near the `NewNotificationHistoryStore` init at `server.go:196-215`) before deciding where the marker should live.
- There's also a **global retention cap** (`MaxNotifications`, `MaxNotificationAge` constants at `store.go:16-18`) — even without archival, a fresh-start marker is eventually pruned by age/count like any other notification. If "durable" is meant to survive indefinitely (e.g., visible whenever someone later inspects that session's history), a notification-store-only marker is *not* sufficient — it needs to also be a **field on session state itself** (akin to `SubStatus`/`DetectedStatus` on the `Session` proto message, persisted with the session) so it's inspectable via `GetSession`/session status API regardless of notification retention. This matches requirements.md's explicit target: "inspectable via the existing session events/status API, not only journalctl/log grep" (`requirements.md:22`) — "status API" strongly implies session-state-level, not just notification-history-level.
- **Recommendation for Phase 3 planning**: treat this as two coordinated signals, not one — (a) a `NotificationType.WARNING` event through the existing pipeline for the in-the-moment toast/history-panel visibility (cheap, reuses everything), AND (b) a durable field on the session's persisted state (new `AttentionReason`-style value, or a boolean/timestamp field alongside `ConversationUUID` in `session/instance_claude.go`) so `StatusBadge`-style rendering can show it on the session card/detail header for as long as the session itself exists — independent of notification retention or archival-orphan-pruning. This also naturally answers the Rabbit Hole about "ambiguous JSONL selection" (`requirements.md:51`): if recovery picked the *wrong* file, that's a distinct, arguably more severe signal ("resumed but possibly wrong conversation") worth a different variant than "no recovery possible."

## 5. Jobs-to-be-done

- **Functional**: Don't let the user burn time re-deriving context (re-reading code, re-explaining the task) because they didn't realize the agent's memory was reset. The signal must be visible *before* the user sends their next message assuming continuity — a toast the user is scrolled past, or a marker buried in logs, fails this job. This is directly why "durable + glanceable at time-of-next-interaction" beats "loud but transient."
- **Emotional**: Trust that data loss is never silent. This is a solo-operator tool (per requirements.md's Users section) where the operator is also the one who has to notice and manually reconstruct state today — the existing baseline is explicitly described as a trust-eroding experience ("The user only discovers this by noticing the agent 'forgot everything'," `requirements.md:13`). The fix's UX job is to convert an ambush into an disclosed, expected, recoverable event — even when recovery genuinely isn't possible, *knowing that up front* is the trust-preserving outcome, not the recovery itself.
- **Social**: Not applicable — solo-maintainer project, no team/shared-visibility dimension per requirements.md's Constraints ("solo-maintainer project").

## Recommendation summary for Phase 3 (Plan)

1. Reuse the existing `NewNotificationEvent` → `NotificationHistoryStore` → toast/panel pipeline for the "in the moment" signal — no new proto message needed, `NOTIFICATION_TYPE_WARNING` fits.
2. Add a durable, session-state-level marker (new field or `AttentionReason`/`SubStatus`-style enum value) so the signal survives independent of notification retention/pruning and is queryable via the session status API per the explicit success metric — this is the part that needs a small proto change (see session-creation-registry-style touchpoint analysis, though this isn't a new session-creation mode so that specific registry doesn't apply).
3. Render the durable marker via a `StatusBadge`-style component (reuse `role="status"`, icon + visible text, `--warning*` tokens) on the session card/detail header, with a `title`/tooltip explaining what happened and (stretch, if cheap) a link into the existing conversation-history view (`HistoryDetailPanel.tsx` pattern) for the orphaned JSONL.
4. Resolve the orphan-pruning-vs-archival open question (section 4) before finalizing whether the notification-store copy of this event needs special-casing in `PruneOrphaned`, or whether it's fine to let that copy expire since the durable session-state field is the real source of truth.
