# Adversarial Review: prompt-library

**Date**: 2026-08-06
**Verdict**: BLOCKED

## Blockers

- [ ] **`Save` has no collision/overwrite protection.** Neither `promptlibrary.Save` (Epic 1.4) nor `SavePromptTemplate`'s handler (Story 2.2.1) checks whether `<dir>/<slug>.md` already exists before the atomic rename. Two templates that slugify to the same name (a legitimate re-use of a title, or an accidental duplicate) silently clobber each other with zero warning to the user — no AC, task, or test in Phase 1/6 addresses this. For **global**-scope templates this is irrecoverable: requirements.md explicitly puts "template versioning / edit history beyond what git already gives workspace templates" out of scope, so there is no undo path at all for a global-scope overwrite. Recommendation: before writing, check for an existing file at the target slug path; on collision either (a) have `Save`/the RPC return a distinguishable result the frontend turns into an explicit "a template named X already exists — overwrite?" confirm step (mirroring the picker's existing "Replace current draft" pattern from Unresolved Questions §1), or (b) auto-disambiguate the slug and report back the slug actually used. Add an AC and a `TestSave_should_RejectOrWarn_When_SlugAlreadyExists`-style test.

## Concerns

- [ ] **Story 7.1.1's registry file paths don't match this repo's actual `make registry-generate` output.** The plan's AC states the generator will produce flat files (`docs/registry/features/backend/list-prompt-templates.json`, `get-prompt-template.json`, `save-prompt-template.json`). Verified against real precedent in this repo (`docs/registry/features/backend/backlog/list-items.json`, `id: "backlog:list-items"`, generated from the marker `// +api: backlog:list-items` in `server/services/backlog_service_query.go:106`), the tool actually namespaces output into a subdirectory named after the marker's scope: `backend/<scope>/<action>.json`. Given this plan's markers are `// +api: prompts:list` / `prompts:get` / `prompts:save` (Tasks 2.2.1b–d), the real generated paths will be `docs/registry/features/backend/prompts/{list,get,save}.json`, not the paths stated in the AC. Task 7.1.1b already says "run `make registry-generate`, verify diff," so the *process* is fine — just fix the misleading literal paths/ids in Story 7.1.1's acceptance criteria so a reviewer checking off "does this file exist" doesn't go looking in the wrong place.
- [ ] **`GetPromptTemplate` RPC has no consumer anywhere in the plan.** `TemplatePicker` gets full template bodies (including `body`) from `ListPromptTemplates` directly (Story 1.2.1/2.2.1's `List` already returns complete `Template` objects), the CLI's `show` command bypasses RPC entirely and calls `promptlibrary.List` in-process (Phase 3's own stated design — "no RPC round-trip"), and no UI/e2e task ever calls `usePromptService().getTemplate`. This adds a full proto message pair, a handler (Task 2.2.1c), and 1-2 tests that are pure dead surface against the 9 acceptance criteria. Recommend cutting it for v1 (2 RPCs: List, Save) or adding an explicit forward-looking justification to ADR-002 if it's meant to support something not yet built.
- [ ] **Pitfalls.md §8's explicit "confirm before assuming" instruction for `new_worktree`-mode path resolution isn't answered in the plan.** Pitfalls.md says the chicken-and-egg case (picker needs a workspace root before the new worktree exists) must be confirmed against `OmnibarCreationPanel.tsx`'s actual path-resolution flow "before assuming a worktree path is available at picker-render time" — but the plan's Task 5.2.1b just calls `listTemplates(formState.path)` with no such confirmation recorded anywhere (not in Unresolved Questions, not as a spike task). A quick check of `OmnibarCreationPanel.tsx` shows `path` and `branch` are tracked as separate fields for `new_worktree` mode, suggesting `path` already refers to the source repo rather than a not-yet-created worktree — but the plan should state this confirmation explicitly (it was asked for by name in research) rather than leave a prior-flagged open question silently resolved by omission.
- [ ] **No concurrent-write test for `promptlibrary.Save`.** Pitfalls.md calls the "two Save calls racing on the same filename" scenario "a real risk, not hypothetical," and the plan explicitly models `Save` on `writeSettingsAtomic` (`server/services/mcp_injector.go:129`). That precedent's own test suite includes `TestWriteSettingsAtomic_ConcurrentWritesToSameSettingsPath_NeverProduceCorruptJSON` (`server/services/hook_injector_test.go:424`), which `.claude/rules/fix-flaky-tests-dont-defer.md` cites by name as this repo's canonical worked example for testing exactly this bug class. Task 1.4.1d's four `Save` tests are all single-writer/sequential — none exercise actual concurrent goroutines. Recommend adding an equivalent concurrent test before calling Epic 1.4 done.
- [ ] **`useIsMobile()` doesn't exist.** Tasks 5.1.4a and 6.1.1a reference `useIsMobile()` from `ViewportProvider.tsx` as an existing hook to branch on. The actual exported API is `useViewport()` (`web-app/src/components/providers/ViewportProvider.tsx:16`), which returns `{ isMobile: boolean, ... }`. Small fix, but as written it will send an implementing agent looking for a symbol that isn't there.
- [ ] **No timeout/context bound on the filesystem scan in `promptlibrary.List`.** `os.ReadDir`/file reads in `scanDir` (Task 1.2.1a) have no `context.Context` deadline threaded from the ConnectRPC request. A slow or hung mount under `~` (network home directories, more relevant given this repo's Linux/WSL2 target environments) would block `ListPromptTemplates` indefinitely, in direct tension with the non-functional requirement "must not block or slow down session creation." Worth a defensive bound even though local filesystem is the expected case.

## Minors

- `ListPromptTemplatesResponse.skipped_count` (Task 2.1.1b) is fully derivable from `len(skipped_paths)` — redundant wire field with no independent value.
- Cited UI precedent components (`AliasPalette.tsx`, `LevelFilterChips.tsx`, `SlashCommandDropdown.tsx`, `AliasesManager.tsx`) all verified to exist with accurate line-number citations (e.g. `AliasPalette.tsx:63,103` for `aria-activedescendant` is correct), but live outside `web-app/src/components/sessions/` (in `ui/`, `shared/`, `logs/`, `settings/` respectively) — the plan cites bare filenames without paths, costing an implementer a lookup.
- Saving a workspace-scoped template writes into whatever branch is currently checked out in the resolved main-repo worktree, with no UI hint that the file needs to be committed/merged before it becomes visible from other branches/worktrees — pitfalls.md §8 raises this caveat for `List`'s read side but the plan doesn't restate it for `Save`'s write side.
