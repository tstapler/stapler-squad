# Architecture Review: prompt-library
**Date**: 2026-08-06
**Verdict**: BLOCKED (1 blocker, 3 concerns, 3 nitpicks)

## Constitution Violations
- None — `docs/adr/ADR-000-architecture-constitution.md` does not exist in this repo.

## Blockers

- [ ] **`TemplateScope` proto↔domain conversion is unspecified, and the natural int-cast implementation silently swaps Global/Workspace** — `proto/session/v1/prompt_library.proto` (Task 2.1.1a) defines `enum TemplateScope { TEMPLATE_SCOPE_UNSPECIFIED = 0; TEMPLATE_SCOPE_GLOBAL = 1; TEMPLATE_SCOPE_WORKSPACE = 2; }`, while the Go domain sum type (Domain Glossary / Task 1.1.1a) is `type TemplateScope int; const (ScopeGlobal TemplateScope = iota; ScopeWorkspace)` — i.e. `ScopeGlobal = 0`, `ScopeWorkspace = 1`. The two enumerations are **not ordinally aligned**: proto `TEMPLATE_SCOPE_GLOBAL` is `1`, but domain `ScopeGlobal` is `0`. Nowhere in the plan (Tasks 2.2.1b, 2.2.1c, 2.2.1d — the `ListPromptTemplates`/`GetPromptTemplate`/`SavePromptTemplate` handlers) is an explicit `TemplateScope`↔`sessionv1.TemplateScope` mapping function named. A direct `TemplateScope(req.Msg.Template.Scope)` int cast — the shortest path an implementer (human or LLM) would reach for — would silently map wire-level `TEMPLATE_SCOPE_GLOBAL` (1) to domain `ScopeWorkspace` (1) and vice versa. On the `SavePromptTemplate` write path (Task 2.2.1d) this is a silent-corruption bug: a user choosing "Global" in `SaveAsTemplateModal`'s scope radio (Task 6.1.1c) could have their template written into the workspace directory (or fail to resolve a workspace directory and error unexpectedly) instead, with no error surfaced. This is exactly the class of bug type-driven design's "parse at the boundary" technique exists to prevent (see `type-driven-design` skill, Technique 7) — the sum type is well-designed on the Go side, but the RPC boundary has no proven translation step.
  - **Remediation**: Add an explicit named task — e.g. `scopeFromProto(s sessionv1.TemplateScope) (TemplateScope, error)` and `scopeToProto(s TemplateScope) sessionv1.TemplateScope` in `server/services/prompt_library_service.go` — that switches exhaustively over the proto enum, returns `connect.CodeInvalidArgument` for `TEMPLATE_SCOPE_UNSPECIFIED`, and is the *only* place either type is converted. Add unit tests asserting `TEMPLATE_SCOPE_GLOBAL → ScopeGlobal`, `TEMPLATE_SCOPE_WORKSPACE → ScopeWorkspace`, and `TEMPLATE_SCOPE_UNSPECIFIED → error`, and update Task 2.2.1e's test list to include them explicitly (currently it only covers traversal/typo/not-found cases, not scope translation).

## Concerns

- [ ] **Asymmetric size validation between read and write paths** — `Parse` (Task 1.1.1d) enforces `maxTemplateFileBytes` (64 KiB) and an 8 KiB frontmatter cap as defense-in-depth against oversized files (per pitfalls.md), but `Save` (Task 1.4.1c) has no equivalent cap on the incoming `Template.Body`/`Description`/`Tags` before writing. A `SavePromptTemplateRequest` with a very large body would be written to disk successfully by `Save`, then immediately fail to load (skipped with a warning) the next time `List`/`Parse` scans it — a save-then-unreadable footgun, and an easy local disk-fill vector via the unconditionally-registered (no feature flag, per Risk Control) RPC endpoint.
  - **Remediation**: Apply the same `maxTemplateFileBytes` bound in `Save` (or in the `SavePromptTemplate` handler before calling `promptlibrary.Save`), returning `CodeInvalidArgument` on overflow, and add an acceptance criterion + test (`TestSave_should_RejectOversizedBody_When_ExceedsCap`) to Story 1.4.1.

- [ ] **`TemplateSlug` is a named domain concept in the glossary but never implemented as a type, and slug-matching logic is left ambiguous in two of its three call sites** — the Domain Glossary (line "`TemplateSlug`") describes it as "the primary path-traversal defense," but `slugify()` (Task 1.4.1a) returns a bare `string`, not a distinguished type. Two downstream tasks that need to resolve a slug back to a file both leave the strategy as an unresolved "or": `GetPromptTemplate` handler (Task 2.2.1c) — "call `promptlibrary.List` (**or** a targeted single-file `Parse` by reconstructing `<dir>/<slug>.md`)" — and CLI `PromptsShowCmd` (Task 3.1.1b) — "reuse the same `List` call, find the matching template by slug (compute slug the same way `Save` does, **or** match on filename stem)". Left as-is, two different implementers (or two different subagents in the SDD implement phase) could resolve these two "or"s inconsistently, and nothing in the type system stops a raw, un-slugified name from being passed where a slug is expected.
  - **Remediation**: Define `type TemplateSlug string` with a smart constructor `NewTemplateSlug(name string) TemplateSlug` in `promptlibrary/save.go` (matching Technique 1/2 of type-driven design), make it the single slugification entry point, and use `TemplateSlug` as the parameter type anywhere a slug (not an arbitrary name) is expected — `Get`, `GetPromptTemplateRequest.slug`'s Go-side handling, and the CLI's `show <slug>` lookup. This resolves both "or"s by construction rather than leaving them to implementer discretion.

- [ ] **New picker state is added directly to `OmnibarCreationPanel.tsx` rather than following the plan's own hook-extraction discipline** — the plan explicitly creates `usePromptService.ts` as "its own hook, not folded into the already-large `useSessionService.ts`" (Domain Glossary), correctly recognizing that component/hook bloat is worth avoiding in this codebase. But Stories 5.2.1/5.2.2 (Tasks 5.2.1a, 5.2.1b, 5.2.2a, 5.2.2b) add `pickerOpen` state, template-fetch-on-open logic, `vars` derivation, and the `handleTemplateSelect`/`pendingTemplate` overwrite-guard state machine directly inline into `OmnibarCreationPanel.tsx` — the same kind of component the plan just described as one to protect from further bloat, applied inconsistently between the hook layer and the component layer.
  - **Remediation**: Extract a `useTemplateSelection(formState, setFormField)` hook (e.g. `web-app/src/lib/hooks/useTemplateSelection.ts`) encapsulating `pickerOpen`, `pendingTemplate`, `vars` derivation, and `handleTemplateSelect`, so `OmnibarCreationPanel.tsx`'s new surface area is one hook call plus render wiring — consistent with the discipline already applied to `usePromptService`.

## Nitpicks
- Task 2.2.1c (`GetPromptTemplate` handler) leaves its implementation strategy as an unresolved "or" between reusing `List` and a targeted single-file `Parse` — pick one explicitly in the plan (subsumed by the `TemplateSlug` concern above, but worth calling out as its own ambiguity even if that concern is addressed differently).
- `ListPromptTemplatesResponse.skipped_paths` (Task 2.1.1b) returns full absolute server filesystem paths to the frontend, but the UI copy specified in Task 5.1.3b only ever renders a generic "N templates couldn't be loaded" message and never displays the actual paths — consider whether the wire response needs absolute paths at all (vs. filenames only), since this is local-only low risk but still gratuitous absolute-path exposure in browser dev tools/network logs for no consumed benefit.
- Task 1.3.1a's `strings.NewReplacer`-based interpolation is a (better) variant of `research/build-vs-buy.md`'s literally-recommended `strings.ReplaceAll` loop (single-pass vs. repeated-scan) — the improvement is sound, but a one-line note in the plan cross-referencing why the final implementation diverges from the research doc's literal snippet would save a future reader from wondering whether the deviation was noticed or accidental.
