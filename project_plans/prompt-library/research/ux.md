# UX Research: Prompt Template Picker + Save-as-Template

Research Agent 5 (UX) — prompt-library feature. Source requirements:
`project_plans/prompt-library/requirements.md`.

## 1. Comparable UX patterns

| Pattern | Product | What works | Applicability here |
|---|---|---|---|
| Command palette (⌘K) | VS Code, Raycast, Linear | Single text field, fuzzy search-as-you-type, arrow-key nav, Enter to commit, Esc to dismiss. Results ranked by match quality first, recency second. | This repo already has this exact shape twice: `QuickOpenPalette.tsx` (file search) and `GitHubIssuePicker.tsx` (repo→issue two-phase picker). Both debounce input, use `Fuse.js`-style fuzzy match, and manage `activeIndex` with arrow keys. The template picker should be a third instance of the same shape, not a new interaction paradigm. |
| Inline `/`-triggered dropdown | Slack saved replies, this repo's own `SlashCommandDropdown.tsx` | Triggered by typing a sigil inside the field the result will populate (`/`), rather than opening a separate modal. Keeps the user in flow — no context switch. | Directly relevant: the "First Prompt" textarea in `OmnibarCreationPanel.tsx:721-760` already has this exact pattern wired up (`isSlashDropdownVisible`, `SlashCommandDropdown`, `slashSuggestIndex`). A natural, low-cost extension is a second sigil (e.g. a leading `/template` prefix is already taken by slash commands — better to use an explicit **"From template" button/affordance next to the textarea**, per requirement's own wording, rather than overload the `/` trigger and create ambiguity with slash commands). |
| Raycast/Alfred snippet picker | Raycast Snippets, Alfred Snippets | Two-pane or list+preview: selecting a snippet shows expanded/interpolated text before committing, so the user sees variable substitution *before* it lands in the target field. | Directly answers open question in section 2 below — users expect a preview, not a blind apply, especially since this feature does variable interpolation with silent-blank-on-undefined behavior (AC3) that could surprise users. |
| Tag-filter chips | Log level filters (`LevelFilterChips.tsx`), GitHub label filters | Toggle-button row, `role="group"`, `aria-pressed`, multi-select by click, no separate "apply" step. | Exact existing pattern to reuse for the tag filter in AC4 — don't build a new multi-select dropdown (`MultiSelect.tsx` is heavier, meant for a fixed enum list with "select all/clear"); a chip row scales better for a variable, user-authored tag vocabulary and matches this repo's established idiom for the same job (filter-by-facet). |
| IDE live templates (JetBrains, VS Code snippets) | JetBrains "Live Templates", VS Code user snippets | Variables shown as visibly distinct placeholders (tab-stops) inside the inserted text, not silently substituted. | Less directly applicable since this feature substitutes at selection time, not as editable tab-stops (out of scope per requirements — "not a WYSIWYG"). Worth noting as a *non-goal* to avoid scope creep: don't build tab-stop editing, just show the interpolated result as plain editable text (per AC3, "remains user-editable before submit"). |

## 2. User mental models

**"From template" should be an explicit, opt-in affordance — not a passive state change.**

- Requirement AC3 says selecting a template "populates the session's initial prompt field... which remains user-editable before submit." This confirms the correct model: **From template is a one-shot text-insertion action, not a persistent linked/synced state.** Once inserted, the textarea is just a textarea again — editing it does not "break a link" to the template, and there's no re-sync if the user edits the template file later. This must be communicated in the UI: no persistent "linked to template X" badge that implies live sync.
- Users opening a "From template" picker expect it to **replace** the current contents of the First Prompt field, not append. This matches every comparable pattern in section 1 (Raycast snippet expansion replaces the query text; VS Code palette actions replace, they don't append). If the field already has user-typed content, replacing it silently on selection is a data-loss risk — the picker should warn or require confirmation only when the field is non-empty (a lightweight browser `confirm()`-equivalent is overkill; a subtler pattern used elsewhere in comparable tools is: pre-fill only on an empty field automatically, but require an explicit click-to-replace affordance when the field already has content). This is a UX decision worth flagging back to the plan phase since AC3 doesn't specify overwrite-vs-empty-only behavior.
- **Live variable preview is expected, not optional**, given three separate reasons: (a) the Raycast/Alfred precedent (section 1), (b) AC3's explicit interpolation-with-silent-blank behavior, which is a "gotcha" if not surfaced before commit (a user picks an "issue audit" template with `{{issue_title}}` and gets a prompt with an empty gap that reads oddly, with no indication *why*), and (c) the requirement's own text says the picker should show "name and description" — extending that to a live-interpolated body preview (e.g. a hover/expand panel, mirroring `GitHubIssuePicker.tsx`'s `IssueRow` expand-toggle for issue body preview) is a small, idiom-consistent addition, not new UI vocabulary.

## 3. Accessibility (WCAG AA / ARIA — Axe Core gate)

This repo's own components establish a consistent, working ARIA idiom for exactly this widget class (searchable listbox popovers). Mirror it exactly rather than inventing new patterns — Axe Core in CI (per `CLAUDE.md`'s "UX analysis CI" section) will catch drift.

Concrete conventions observed and to reuse, with file:line references:

- **Search input**: plain `<input type="text">`, `aria-label` describing the search scope (e.g. `aria-label="Search templates"`), `autoComplete="off"`. See `QuickOpenPalette.tsx:225-236`, `GitHubIssuePicker.tsx:154-167` (`aria-autocomplete="list"` + `aria-controls="<listbox-id>"` when the input and listbox are structurally separate).
- **Results container**: `role="listbox"` with `aria-label` (e.g. `"Templates"`). See `QuickOpenPalette.tsx:237`, `SlashCommandDropdown.tsx:51-56`.
- **Each result row**: `role="option"`, `aria-selected={i === activeIndex}`. Give each option a stable `id` (`` `template-option-${i}` `` or by template filename) and set `aria-activedescendant` on the input pointing at the active option's id — this repo's `AliasPalette.tsx:63,103` does this (`aria-activedescendant`) while `QuickOpenPalette.tsx` relies on `aria-selected` alone without `aria-activedescendant` on the input; **prefer the `AliasPalette` variant** (input keeps DOM focus + `aria-activedescendant`) since it's the more complete implementation of the ARIA 1.2 combobox/listbox pattern and avoids focus ping-ponging between input and list.
- **Row selection on click**: use `onMouseDown` with `e.preventDefault()` (not `onClick`) when the row lives inside a popover anchored to a focused input — see `SlashCommandDropdown.tsx:67-70` and `GitHubIssuePicker.tsx:189-192`. This prevents the input's `blur` (which would otherwise fire first on `mousedown` and close the popover before the click registers).
- **Keyboard nav**: `ArrowUp`/`ArrowDown` to move `activeIndex` (wrap-around per `QuickOpenPalette.tsx:184-193`, or clamp per `GitHubIssuePicker.tsx:135-141` — either is acceptable, pick one and be consistent), `Enter` to commit, `Escape` to close. Scroll active row into view via `scrollIntoView({ block: "nearest" })` on `activeIndex` change (`QuickOpenPalette.tsx:174-179`).
- **Empty state**: plain text row inside the listbox container (not a separate `role="alert"`), `data-testid` for e2e per this repo's testing convention. See `QuickOpenPalette.tsx:238-242`.
- **Zero-templates-exist state**: use `role="status"` (polite, not assertive — see AliasPalette's `alias-palette-empty` at `AliasPalette.tsx:46`) since this is informational, not an error.
- **Tag filter chips**: `role="group"` with `aria-label`, each chip a `<button aria-pressed={isActive}>` — see `LevelFilterChips.tsx:25-35`. Do not use checkboxes-in-dropdown (`MultiSelect.tsx`) for this; chips are the established idiom for facet filtering in this codebase and read better for AT users than a closed dropdown with nested checkboxes.
- **Save-as-template modal**: use the existing `web-app/src/components/ui/Modal.tsx` (Radix `Dialog` wrapper) rather than a bespoke `createPortal` modal. Radix handles focus trap, `Escape`-to-close, `aria-modal`, and return-focus-on-close for free — every other save/import form in this codebase already uses it (`ImportRulesModal.tsx`, `ResumeSessionModal.tsx`, `WorkspaceSwitchModal.tsx`). Building the save-as-template form as a bespoke modal (like `QuickOpenPalette.tsx` does, which manually saves/restores `document.activeElement`) would be inconsistent and redundant given a working primitive already exists.
- **Locators for e2e**: per `.claude/rules/e2e-test-conventions.md`, every interactive element needs `data-testid` or an ARIA role — the existing components already tag rows with `data-testid="alias-row"` etc.; do the same (`data-testid="template-option"`, `data-testid="template-picker-empty"`).

## 4. Error states

- **AC6 (malformed template silently skipped, logged warning)**: per the "document AI decisions in edge cases" project convention (silent auto-actions should be visible, not silent), a purely silent skip is wrong even though AC6's wording says "skipped... rather than crashing" — silence at the *system* log level is fine, but the *picker UI* should surface a low-key, non-blocking notice when the count of skipped/failed templates is nonzero, e.g. a small dismissible line under the search input: `"2 templates couldn't be loaded — check ~/.stapler-squad/prompts/"`. Keep it **non-modal and non-blocking** — this is a power-user feature most sessions won't touch, so an error banner that steals focus or requires dismissal before proceeding would be disproportionate. Model this on `SlashCommandDropdown.tsx`'s `role="status" aria-live="polite"` empty-state row (informational, not alarming) rather than `AliasPalette.tsx`'s `role="alert" aria-live="assertive"` treatment (reserved for a total config-load failure, not a partial one). A partial failure (N of M loaded) is categorically different from AliasPalette's all-or-nothing config error and should not borrow its assertive treatment.
- **Zero templates exist (non-functional constraint)**: the requirements explicitly say this must not be an error state and must stay fast. Two sub-cases:
  - *Before the picker opens*: if the "From template" affordance is a button, it can still always be rendered (cheap, doesn't require a fetch) — clicking it opens the picker, which then shows the empty state below. Do not conditionally hide the "From template" button based on a pre-fetch just to avoid an empty state; that adds a network round-trip to every session-creation panel render for a rare payoff (avoiding one dead click). This matches `AliasPalette.tsx`'s approach: the palette component always renders, and shows its own empty-state message rather than the *caller* deciding not to render it.
  - *Inside the picker*: reuse the `AliasPalette.tsx:44-54` empty-state shape — a short title ("No templates yet") plus one line of actionable guidance ("Drop a `.md` file in `~/.stapler-squad/prompts/`, or save one from an existing session's prompt.") rather than a bare "No results" — this is a first-run/discovery moment, not a failed search.

## 5. Jobs-to-be-done

- **Functional** — avoid retyping a known-good prompt (dependency audit, code review pass, test generation) from memory or an external notes app, per the requirement's own "Problem" statement. Success = time-to-first-prompt in session creation drops for repeat workflows; this is what the search-as-you-type + tag filter directly optimize for (fast retrieval among N saved templates, not just N ≤ 5 where a flat list would do).
- **Emotional** — confidence that a "known-good" audit/review prompt is being applied *correctly*, not a stale or mis-copied version. This is why the live-interpolation preview (section 2) matters emotionally as well as functionally: seeing `{{repo}}`/`{{branch}}` resolve correctly before submit is a small trust-building confirmation, especially for `{{issue_title}}` which silently blanks when absent (AC3) — an unexplained blank is worse for trust than a visible "(no linked issue)" placeholder would be, worth flagging as a phrasing choice for the interpolation logic itself (fill blank with nothing vs. a visible placeholder) even though AC3 already decided "blank."
- **Social** — templates committed to `.stapler-squad/prompts/` in the repo (requirement's workspace-scope storage) let a tech lead standardize a team's review/audit prompt the same way a `.eslintrc` or PR template standardizes process — discoverable by any teammate who clones the repo and opens session creation, with zero additional onboarding step. This is the strongest differentiator vs. a personal notes app and should be reflected in the picker UI by visually distinguishing workspace templates from global/personal ones (e.g. a small "workspace" vs "personal" tag/badge per result row), so a user understands *why* a template appeared only in this repo's session-creation flow and not another's.

## 6. Mobile

Per this repo's standing UX instinct ("mobile + desktop UX requirement" — always consider both form factors) and the existing `ViewportProvider` / `useIsMobile` hook already used in `CockpitShell.tsx`, `Header.tsx`, `TerminalOutput.tsx`, and `PaneTilingContainer.tsx`:

- **No hover-only affordances.** The "workspace vs global" badge, any "preview on hover" interaction (section 2's live-preview idea), and row-level actions must all be reachable via tap, not `:hover`/`onMouseEnter` alone. `QuickOpenPalette.tsx` and `GitHubIssuePicker.tsx` already set active state via `onMouseEnter` for desktop mouse users but drive selection via keyboard/click — keep click/tap as the primary interaction and treat hover as a pure enhancement, never the only path to an action.
- **Touch targets**: chip buttons (tag filter) and option rows need ≥44×44px tap targets per WCAG 2.5.5/2.5.8 — the existing `LevelFilterChips.tsx` chip sizing and `AliasPalette.tsx` row sizing should be audited for this if the same CSS is reused verbatim, since those were likely tuned for desktop density first.
- **Modal vs inline**: on mobile, prefer a full-screen or bottom-sheet presentation for the template picker rather than a small anchored popover (an anchored dropdown under the First-Prompt textarea, as `SlashCommandDropdown` does, risks being clipped by the mobile keyboard or requiring awkward scroll on a small viewport). Radix `Dialog` (already used for `Modal.tsx`) supports this responsively without a bespoke implementation — reuse it for the picker itself on mobile (not just the save-as-template form), switching from the inline-anchored `SlashCommandDropdown`-style popover on desktop to a `Modal`-based full-screen picker on mobile via `useIsMobile()`, mirroring how `Header.tsx`/`CockpitShell.tsx` already branch layout on that hook.
- **Save-as-template form fields** (name/description/tags/scope): stack vertically (no side-by-side layout) below mobile breakpoint, consistent with `.claude/rules/css-architecture.md`'s page-scroll convention (`height: "100%"` + `overflowY: "auto"` on the modal body) so the form doesn't get clipped when the on-screen keyboard reduces viewport height.
