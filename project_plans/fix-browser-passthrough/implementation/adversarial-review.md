## Concerns

- [ ] **The AC5/AC6 vs AC9 decision table is partly wrong: AC6 does not depend on frames.** plan.md Revision 2 says AC5/AC6 "stay FAIL (unverified/unmet)" under Option A. The backlog AC6 reads "On Linux with Chrome installed: the Browser tab activates when cdpState.status reaches CDP_STATUS_STREAMING, independent of whether xdotool has detected a window". That is satisfied by the frontend change (`SessionDetailView.tsx:605`, `BrowserTab.tsx:78`) and was confirmed live (tab enabled, viewer mounted, per pitfalls.md). Only AC5 ("CDPViewer rendering frames") needs the backend. AC7 and AC8 are also unmet-by-verification (mobile toast, `make lint` not run per the reviewer verdict) and are not in the table at all. Fix: restate the table as AC5 only (frames), AC6 attainable now, and list AC7/AC8 as "needs verification" so the owner is not misled into thinking Option B is needed for AC6. (requirements.md carries the same conflict at SC1 "renders frames" / FR-5 vs FR-7 / SC6.)

- [ ] **Task 4's "attach to a page target" design is under-specified for input, which uses the same broken connection.** `DispatchInput` writes to `m.cdpConn` (`manager.go:327-337`) and the viewer sends `Input.dispatchMouseEvent` / `Input.dispatchKeyEvent` (`CDPViewer.tsx:214,270,308,...`). If only the screencast dial changes, input still goes to the browser endpoint. INFERRED: Chrome's browser target does not serve `Input.dispatchMouseEvent`, so click and keyboard passthrough is likely broken too. The plan's Task 4 steps never mention `DispatchInput`, and its test only asserts `Page.*` routing. Recommend the page-level dial (Option 2a in the plan) over flattened `Target.attachToTarget`. Page-level makes `DispatchInput` work unchanged, needs no `sessionId` injection into client-supplied JSON, and matches the `inspect.go` precedent. If flattened sessions are chosen, `DispatchInput` must inject the envelope `sessionId`, and `cdpMessage` (`manager.go:88-94`) has no such field. Also note the name clash: `screencastFrameParams.SessionID int` (`:549-552`) is the ack id inside `params`, distinct from the envelope string `sessionId`.

- [ ] **Task 4 step 3 ("set STREAMING only after `Page.startScreencast` returns non-error") is not implementable without new plumbing, and still would not mean "frames flowing".** `readLoop` ignores replies (`:534-537`), so this needs a pending-call map keyed by id with a timeout. Even then a non-error reply does not guarantee a frame (background/occluded or zero-page Chrome). Recommend: keep `Waiting` until the first `Page.screencastFrame` is decoded (`handleScreencastFrame`, `:555-578`) and then set `Streaming`. That removes the false positive at its source and needs no reply correlation for the state change (you still want reply logging for diagnosability).

- [ ] **Reconnect and lifecycle gaps in Task 4 step 4 are only gestured at.** `runLoop` calls `pollForChrome`, which only hits `/json/version` (`:404-441`), then `runScreencast` with that browser URL (`:376`). A page-level design must re-resolve the page target on every loop iteration. Cases the plan should name: (a) Chrome up with zero page targets (the loop must not report Streaming; `inspect.go:128` returns "no page target"); (b) "first page" being the wrong target (new tab opened, `about:blank`, devtools); (c) page-target WS closes on navigation to a new renderer or on tab close, which today yields a 500 ms hot reconnect (`:388-393`) while the state stays `Streaming` (no `setState` on failure: `:376-386`); (d) `latestFrame` is never cleared on reconnect or Chrome exit (`:569-571`), so the viewer shows a stale last frame. Add these to Task 4 acceptance tests; the fake CDP server test in step 5 should cover (a) and (c).

- [ ] **Frontend failure mode left unmitigated: STREAMING with no frames is a silent blank canvas.** `BrowserTab.tsx:217-243` mounts `CDPViewer` and hides all placeholders once `isReady`; `CDPViewer.tsx` only reports ws `open`, never "first frame received" (`:80-110`). The plan acknowledges this as R-A ("spinner-less blank viewer") but accepts it. This is the exact state a user hits in Option A, and the Inspect button is enabled in it (`BrowserTab.tsx:177`). A small frontend-only mitigation is compatible with AC9: an `onFirstFrame` callback from `CDPViewer` and a "Waiting for first frame..." overlay in `BrowserTab` (with a timeout message after ~5 s). Recommend adding it as Task 3b, or at minimum stating plainly in the PR body that frames do not render yet, so the PR does not claim to "fix browser passthrough".

- [ ] **Scope mismatch with the original request.** The backlog description says the user is "not sure if we need to make some fundamental architectural changes to make it more generic and usable across all mobile platforms or web". Neither the plan nor requirements.md addresses this question (even to defer it). Option A ships a PR whose title implies the feature works while the user-visible symptom (no browser image) persists. State in the PR and the follow-up backlog item that the feature remains non-functional until Task 4, and create that follow-up item before the PR merges so it is not lost.
