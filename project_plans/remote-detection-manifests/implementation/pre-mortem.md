# Pre-mortem: remote-detection-manifests
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The 90-day demand checkpoint (target ~2026-10-31) has no durable trigger to actually fire — it exists only as prose in `requirements.md`/`plan.md`, which nobody is scheduled to re-read on that date — so it either silently lapses (Phase 2 stays "BLOCKED" forever, never re-evaluated) or gets skipped when someone starts Phase 2 early because they've forgotten the gate's rationale. Plan.md's own Unresolved Question #5 already names this risk without closing it. | It's past 2026-10-31 (or later) and nobody has revisited the checkpoint — or Phase 2 work starts with no comment referencing whether the checkpoint resolved. | Before implementation starts, create an actual scheduled artifact tied to the date — a `schedule`/`loop`-skill cron entry, a calendar reminder, or (cheapest) a `create_backlog_item` due ~2026-10-31 whose description is literally "re-evaluate detector-plugins 90-day demand checkpoint; resolve remote-detection-manifests Phase 2 gate" — not just a markdown paragraph in a plan file that requires someone to remember it exists. | P1 |
| 2 | The checkpoint's chosen demand signal (was a *new agent* onboarded via `.toml` vs. `binaries/*.go`) doesn't measure demand for *remote fetch* at all — it measures demand for local extensibility. The Problem Statement's actual motivating scenario ("Claude Code UI changes breaking idle/busy detection" on an *existing built-in* agent) would never trip this metric even if it happened three times in the 90-day window, because a built-in-agent breakage is fixed by editing the existing `binaries/*.go` file or a local `.toml` override, not by "onboarding a new agent." The checkpoint can resolve "no demand" while the exact pain point Phase 2 exists to solve occurred and was invisible to the metric. | Checkpoint resolves "demand not confirmed" (zero new agents onboarded) shortly after a real production incident where a built-in detector broke and had to wait for a full release — and nobody connects the two because the checkpoint only tracked the wrong axis. | Before the checkpoint date, add a second, independent signal to `detector-plugins/requirements.md`'s checkpoint criteria: "did any built-in detector require an out-of-band `binaries/*.go` hotfix release in the window" — tracked alongside, not instead of, new-agent-onboarding. Both signals should be checked at 2026-10-31, not just the one currently named. | P1 |
| 3 | Phase 1's premise — "the PR #307 closure was simply an error" — rests on git-ancestry/grep checks (Story 1.1) that can only detect *whether the code landed*, not *why a human/agent chose to close it*. If the closer had a substantive but poorly-worded reason (e.g., a second look at ADR-004's trust boundary, a design reservation, an intent to redo it differently) that got compressed into an inaccurate "already shipped" comment, Phase 1 re-lands a design that was in fact deliberately rejected, not merely a victim of a bookkeeping mistake. | A reviewer (human or the same agent that closed it originally) raises the identical objection during Task 1.2.4's PR review that prompted the original closure — after the re-land effort (Epic 1.1 + 1.2, ~30-40 min of work) is already spent. | Add a task to Epic 1.1 that searches for *any* other trace of a substantive objection beyond the closing comment itself — PR review comments/threads on #307, related backlog items, Slack/notes referenced in the ADRs, or a second closed PR/issue touching the same design — before concluding the closure was purely erroneous. If none is found, proceed as planned; if one is found, treat it as a real design question for Epic 1.2, not noise to route around. | P2 |
| 4 | Task 1.2.2's conflict-resolution step ("resolve preserving the reviewed design exactly... every substantive resolution gets a one-line comment") is a soft, self-graded check — `main` has moved a meaningful number of commits since the source branches were authored (merge-bases `14e26b7ba`/`789775f4d` vs. current `8cbddebab`+), so what looks like "mechanical" conflict resolution in `session/detection/detector.go`, `main.go`, or `session/claude_controller.go` may actually require real judgment calls the original 4 ADRs never anticipated. `make ci` passing doesn't catch a resolution that's *behaviorally* different but still compiles and passes existing tests (which were written against the old `main`, not against whatever changed since). | `make ci` and all of Story 1.2's acceptance criteria pass, PR merges cleanly, but a detection regression for an existing built-in agent surfaces days later in production logs (unrelated bug report, not traced back to the re-land conflict resolution until someone git-blames the diff). | Require a second reviewer (not the implementer) to explicitly diff-review every conflict-resolution hunk against the original PR #307 diff before merge, and add one acceptance criterion to Story 1.2 requiring the 4 existing `detector-plugins` ADRs to be re-read against current `main`'s actual code (not just the historical diff) to confirm none of their assumptions were invalidated by intervening changes. | P2 |
| 5 | Phase 2's trust model (ADR-002, provisional) argues pinned-SHA fetch is safe because "the pinned-SHA approach and editing the local `.toml` by hand... share the same actual trust root (Tyler's own GitHub push access)" — but Story 2.5.1 describes bumping the pin as "a documented, single-line config change" with no required content-diff review step before the bump ships. This silently converts "attacker needs physical/SSH access to this machine" into "attacker needs to compromise Tyler's GitHub account (or CI credentials) to get a bad commit merged, then just needs the pin bumped" — a materially different attack surface the ADR's equivalence claim glosses over. A manifest edit that quietly weakens a `needs_approval`/`input_required` pattern (the "Semantic Spoofing" risk the glossary already names) would pass schema validation, pass the Never-Downgrade Rule (it's a legitimate version bump), and reach a running instance with no human ever reviewing the semantic diff. | An autonomous-mode session takes an action that should have required approval, and post-incident review traces it to a detection pattern that was silently narrowed/removed in a manifest update whose content nobody diffed before the pin was bumped. | Add an explicit task to Epic 2.5 requiring a mandatory content-diff review step (even a manual one — "the pin-bumper must diff the new manifest against the previous pinned version and confirm no `needs_approval`/`input_required` pattern was removed or narrowed") as a hard prerequisite for any pin bump, not just a config-key change task. Document this in ADR-002 itself, not left implicit in the glossary's risk note. | P3 |
