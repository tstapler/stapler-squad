# Pre-mortem: alias-settings-manager
**Date**: 2026-06-21

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The plan describes case-insensitive matching in the Go upsert loop (`strings.ToLower(a.Name) == strings.ToLower(alias.Name)`) but then instructs the story-1.2.4c test to verify this — yet the code snippet in Story 1.2.1b already has the case-insensitive version written out. A developer implementing the code block verbatim will get the right behavior, but the test task note says "compare names case-sensitively (`a.Name == alias.Name`)" in the same section, creating a contradiction. One of the two will win; if the test expectation is wrong the test passes on broken behavior. | `TestUpsertAlias_CaseInsensitiveDuplicate` passes while a second alias `"MYPROJ"` silently overwrites `"myproj"` in config or vice-versa, causing silent data loss. | Resolve the contradiction in the plan before implementation: delete the contradictory parenthetical in story 1.2.4c. Enforce one canonical version of the case rule in both code and test. | P1 |
| 2 | The e2e spec (`alias-settings.spec.ts`) uses `SettingsPage` helper methods (`clickNewAlias`, `fillAliasName`, etc.) that do not exist yet — `SettingsPage.ts` is absent from `tests/e2e/pages/` entirely. The plan notes "create it if it does not exist" but treats the missing file as a 3-minute afterthought. In practice, the omnibar test step (`page.keyboard.press("Meta+k")`) uses macOS-only `Meta` (Cmd) whereas the CI runner is Linux where that key sequence does not open the omnibar, silently making the `@alias` detection test a no-op or timing failure. | CI e2e run on Linux passes with incorrect green status because `Meta+k` is silently ignored and the detection badge assertion is either never reached or the test finds no element and exits before the assertion. | Explicitly add a cross-platform keyboard shortcut step (use the omnibar `data-testid` button click as the trigger instead of `Meta+k`), AND add SettingsPage helper creation as a blocking story step, not a footnote. | P1 |
| 3 | The `ALIAS_NAME_RE` constant the plan wants imported from `AliasDetector.ts` does not exist as an export — `AliasDetector.ts` defines the regex inline and never exports it. Story 2.1.3 says "If AliasDetector.ts does not export a constant, export one now" but this is buried in a hint block. If the implementer skips that edit, `AliasesManager.tsx` will define its own copy of the regex, defeating the stated goal of a single source of truth and making the two patterns diverge undetected. | A user types an alias name that passes client-side validation but is rejected by the server (or vice-versa) because the regexes drifted; they see an inexplicable inline error or an opaque RPC error. | Make adding `export const ALIAS_NAME_RE = /^[\w-]+$/` to `AliasDetector.ts` a first-class named task in the file-touch table and give it an acceptance criterion, not just a parenthetical note. | P2 |
| 4 | The plan relies on load-modify-save with no mutex, documented as "accepted tradeoff." But the `config.LoadConfig()` call pattern used in every handler is called from `DefaultsService` methods, and the Go server handles concurrent HTTP requests. Two simultaneous saves (e.g., a user double-clicks Save, or a profile save and alias save race) will produce a last-write-wins result that drops one change silently. The plan says "file a follow-up to add a package-level mutex" but that follow-up has no ticket number, owner, or timeline — it will not be filed. | A user saves an alias and simultaneously edits a profile; one change disappears from `config.json` with no error shown. | Either add the mutex as part of this PR (15-minute change: one `sync.Mutex` on `DefaultsService` wrapping the load-modify-save block), or block the PR on a filed and linked issue. "File a follow-up" without a link is not a control. | P2 |
| 5 | The `alias:list` registry entry is committed with `"tested": false` at the end of Phase 2, with the expectation that Phase 3 e2e will flip it to `true`. If the e2e spec is skipped, blocked by the Linux keyboard issue, or deprioritized, the `coverage-gaps.json` count grows by 1 at merge time. The plan's acceptance criterion for Story 3.2.2 says "coverage gap count has not grown" but this check is only run as part of the manual `make ci` step — if CI passes without running the e2e suite (which is not part of `make ci` per the CLAUDE.md), the gap is invisible. | `make ci` exits 0 but `coverage-gaps.json` now has `alias:list` as an untested entry; this is only discovered on the next `make registry-diff` run, by which point the PR is merged. | Commit `list.json` with `"tested": false` but add a CI check (or PR checklist item) that explicitly gates merge on `"tested": true`. Alternatively, write a minimal Go unit test for `ListAliases` in Phase 1 and set `"tested": true` from the start. | P3 |

## P1 Items (address before implementation)

- [ ] **Failure #1 — Case-sensitivity contradiction** — Remove the parenthetical `"compares names case-sensitively (a.Name == alias.Name)"` from Story 1.2.4c. The code block in Story 1.2.1b already has the correct case-insensitive implementation; the test note must match it exactly.
- [ ] **Failure #2 — e2e Linux keyboard + missing SettingsPage** — Add `tests/e2e/pages/SettingsPage.ts` creation as a blocking story in Phase 3 (not a footnote), and replace `page.keyboard.press("Meta+k")` with a click on the omnibar trigger button identified by `data-testid` so the e2e test is platform-agnostic and actually exercises the alias detection assertion in CI.
