# Implementation Plan: multi-window

**Feature**: A named-window layer above the existing pane-tiling engine — users group panes into independently-persisted windows, switch between them via tab strip/leader-key/swipe, and address a window per-browser-tab via `?window=<id>`.
**Date**: 2026-09-23
**Status**: Ready for implementation
**ADRs**: ADR-001 (per-tab binding via URL, not shared state), ADR-002 (cross-tab revision guard / Optimistic Offline Lock), ADR-003 (new `cockpit.windowLayout` storage key)

**Note on estimates vs. appetite**: the per-task estimates below (~47-48 tasks, 2-10 min each,
summing to roughly 3.5-4 hours) are raw implementation time only — the time to write the code for
each task in isolation. They don't predict wall-clock delivery time against `requirements.md`'s
Large (3-6 week) Appetite, which additionally has to absorb review cycles; the manual
cross-browser/cross-platform spikes (Story 3.3.2's `Alt+W` collision check); real-device mobile
UX validation (touch gesture disambiguation, tab-strip density); iteration on findings from those
reviews and spikes; and a solo maintainer's available hours per week being a fraction of a
full-time week. Task-sum-hours and appetite-weeks are answering different questions, not
contradicting each other.

## Step 0.5 — Alternatives explored

1. **Array of independent `PaneState`s + a windows-array reducer one layer above `paneReducer`** (chosen). Strength: reuses `paneReducer`/`paneTypes`/`paneUtils` completely unmodified (hard constraint in requirements.md), and the array-of-trees shape maps 1:1 onto "a named, ordered collection of independent pane trees" from Scope. Weakness: `usePaneReducer.ts`'s restore/save/re-validate effects are written for exactly one `PaneState` and can't be reused as-is across an array — that logic has to be rewritten (not called) one layer up.
2. **Single reducer merging window-management actions and pane actions into one `WindowAction` union that `paneReducer` itself understands** (rejected). Strength: one dispatch surface, no wrapper `PANE_ACTION` case. Weakness: requires either teaching `paneReducer` about windows (directly violates "reuse the pane engine unmodified") or writing an outer reducer that re-invokes `paneReducer` per action anyway — architecturally identical to option 1 but with two unrelated state machines (window lifecycle vs. pane layout) coupled into one action type, complicating `RESTORE_LAYOUT`'s existing single-tree semantics for no benefit at this scale (low double-digit window counts).
3. **N mounted `<PaneTilingContainer>` instances inside a `WindowContext`, visibility toggled by CSS** (rejected). Strength: zero new persistence/restore code — each instance keeps using `usePaneReducer` as-is. Weakness: `usePaneReducer`'s refs (debounce timer, restored-flag) are per-mount; mounting N containers means N sets of localStorage timers and N `usePaneShortcuts` registrations firing against the shared `registry` as windows are created/closed, N-fold duplication of the mobile-picker/peek-modal local state, and unmounting a backgrounded window to save cost would defeat "restore the exact state" — see `research/architecture.md` for the full breakdown.

Chosen: **Option 1**, exactly as `research/architecture.md` recommends, with one structural revision this plan makes explicit: **there is no shared `activeWindowId`** in the windows reducer or its persisted blob (see ADR-001) — that piece of `research/architecture.md`'s original `WindowState` sketch is superseded by the per-tab URL-binding requirement added after Phase 2 research.

## Domain Glossary

| Term | Definition | Notes |
|------|-----------|-------|
| `WindowId` | String identifier for a window. | Plain string alias (`type WindowId = string`), generated by `generateWindowId()`. Not a branded/opaque newtype — see Pattern Decisions. |
| `NamedWindow` | `{ id: WindowId; name: string; paneState: PaneState }` — one independent pane tree plus its user-facing name. | Deliberately **not** named bare `Window` — that identifier would shadow the global DOM `Window` interface in every file that also calls `window.location`/`window.addEventListener`. |
| `WindowsState` | `{ windows: NamedWindow[] }` — the shared, persisted, reducer-owned state. | No active-window pointer (see ADR-001) — "which window is active" is per-tab, derived from the URL, and lives outside this type. |
| `WindowAction` | Discriminated union: `CREATE_WINDOW`, `CLOSE_WINDOW`, `RENAME_WINDOW`, `PANE_ACTION`, `RESTORE_WINDOWS`. | Sum type, exhaustively handled in `windowReducer`'s switch — mirrors `PaneAction`'s existing convention. |
| `windowReducer` | Pure `(WindowsState, WindowAction) => WindowsState`. | The `PANE_ACTION` case delegates unmodified to the existing `paneReducer` for the one addressed window; never touches `paneReducer.ts`/`paneTypes.ts`/`paneUtils.ts`. |
| `PersistedWindowLayoutV2` | `{ version: 2; revision: number; windows: NamedWindow[] }` — the localStorage v2 schema. | Written to the **new** key `cockpit.windowLayout` (ADR-003); `cockpit.paneLayout` (v1) is read-only input to migration and never written again. |
| `WindowRevision` | Plain `number`; monotonic counter incremented on every successful save. | Backs the Optimistic Offline Lock cross-tab guard (ADR-002). |
| `lastFocusedWindowId` | A single string value in its own localStorage key, `cockpit.lastFocusedWindowId`. | Fallback for "which window to show when a tab has no `?window=` param." Not part of `PersistedWindowLayoutV2`; no revision guard (single scalar, no partial-tree data to lose). |
| `currentWindowId` | The per-tab resolved active `WindowId`: `?window=` URL param → else `lastFocusedWindowId` → else `windows[0].id`. | Never persisted as a single "the" value — recomputed per render from URL + hint + windows list. |
| `useWindowManager` | Hook owning `windowReducer` state, persistence, migration, per-window session revalidation, and cross-tab reconciliation. Takes `sessions`, not `currentWindowId`. | Returns `windows`, `dispatchPane(windowId, action)`, `createWindow`, `closeWindow`, `renameWindow`. Has no notion of "the active window" itself. |
| `useWindowUrlSync` | Hook (used from `page.tsx`) that reads `?window=` via `useSearchParams`, resolves `currentWindowId` against a `windows` list, self-heals an invalid/missing param via `router.replace`, and exposes `switchToWindow(id)`. | `switchToWindow` is URL navigation only — see ADR-001; it never dispatches a `WindowAction`. |
| `WindowTabStrip` | The window-switcher tab-strip component, forked from `MobilePaneTabStrip`. | `role="tablist"`, `aria-label="Window switcher"` — a second, independently-labelled tablist from the existing pane strip's `"Pane switcher"`. |
| `useWindowSwipe` | Hand-rolled `TouchEvent`-based horizontal swipe hook scoped to the `WindowTabStrip` container. | Modeled on `useTerminalGestures`'s state-machine/ADR-012 pattern, not a new dependency. |
| `useWindowShortcuts` | Registers the leader-key (`Alt+W`) window-switching sequence through the existing `ShortcutRegistry`. | Dynamically registers/deregisters follow-up shortcuts while armed; makes zero changes to `shortcutRegistry.ts` itself. |
| `leaderArmed` | Boolean ref tracking whether `useWindowShortcuts`'s leader sequence is awaiting a follow-up key (digit/`n`/`p`/`,`/`Escape`). | Auto-disarms after a bounded timeout (3000ms) so a stray later `1`/`n`/`p` keystroke (e.g. typed into a terminal) is never silently swallowed. |

## Pattern Decisions

| Component | Pattern Chosen | Source | Alternative Rejected | Reason |
|-----------|---------------|--------|---------------------|--------|
| `WindowAction`/`PaneAction` dispatch | Command (each action object encapsulates a request) | GoF | Per-window class with imperative methods (`window.split()`, `window.close()`) | Breaks referential transparency/serializability needed for localStorage persistence and time-travel-style testing; inconsistent with the already-proven `paneReducer` style. |
| `windowReducer`'s `PANE_ACTION` delegation | Composite reuse — outer reducer re-invokes the existing pure `paneReducer` unchanged, once per addressed window | PoEAA-adjacent (Layered state) | Teach `paneReducer` itself to be window-aware | Directly violates the "reuse the pane engine unmodified" constraint in requirements.md. |
| `WindowId`/`PaneId` | Type alias (`type WindowId = string`), not a branded/opaque newtype | type-driven-design (rejected here) | Branded newtype (`type WindowId = string & { __brand: "WindowId" }`) | Inconsistent with the existing, unbranded `PaneId` in the same codebase; the two ID spaces are used in disjoint code paths (never compared to each other), so the confusion branding prevents has low practical probability here — matches the Proportionality principle. |
| `WindowAction`/`PersistedLayout` version discriminant | Sum type with exhaustive switch (Parse, Don't Validate) | type-driven-design | Optional-field duck-typing / if-else pyramid on `parsed.version` | `research/pitfalls.md` explicitly warns a naive `if (v===1) {...}` with no `else` branch silently produces `undefined` for an unrecognized version; an exhaustive switch fails closed instead. |
| v1→v2 migration | Versioned schema evolution, defensive parse, write-once | type-driven-design / PoEAA | In-place version bump on the existing `cockpit.paneLayout` key | See ADR-003 — a new key preserves an untouched backup, satisfying Risk Control's "fallback that preserves the raw old data untouched" more directly. |
| Cross-tab write conflict on the shared `windows` blob | Optimistic Offline Lock (revision-guarded read-check-write) | PoEAA (Fowler) | Pessimistic lock via the Web Locks API (`navigator.locks`) | See ADR-002 — doesn't answer "whose edit wins," adds a browser API this codebase doesn't otherwise depend on, disproportionate to a single-user, no-oncall-alert feature. |
| Per-tab "active window" | URL as source of truth (`?window=` query param), no reducer field | Established in-app precedent (`?session=`/`?tab=` in `page.tsx`) | Shared `activeWindowId` field in `WindowsState` (research/architecture.md's original sketch) | See ADR-001 — a shared field cannot let two tabs independently display different windows, which requirements.md's per-tab addition explicitly requires. |
| New-window/replacement-window id generation | Generated at the hook/effect layer (`useWindowManager`), passed into the action payload | Command pattern variant | Reducer self-generates the id internally (as `paneReducer.ts` already does for `generatePaneId()` in `SPLIT_PANE`) | The caller (`useWindowUrlSync`) needs the new window's id **synchronously**, before React commits the state update, in order to immediately navigate the tab to it (`switchToWindow(newId)`); nothing outside the pane reducer needs a freshly-split pane's id synchronously, so that convention doesn't transfer here. |
| Window tab-strip UI | Fork `MobilePaneTabStrip.tsx` structurally (hand-rolled `role="tablist"`) | build-vs-buy.md | Wrap `@radix-ui/react-tabs` (already a dependency) | Radix's `TabsTrigger` renders a fixed `<button>` with no `asChild` escape hatch for the long-press-to-rename interaction, and has no swipe support at all (confirmed against Radix's own docs) — would still need the same custom code on top, while also fighting its DOM contract. |
| Window-switch swipe gesture | Hand-rolled `TouchEvent` state machine, modeled on `useTerminalGestures` | build-vs-buy.md, ADR-012 precedent | `react-swipeable` / `@use-gesture/react` | New dependency for a single-axis gesture; neither library documents the iOS `pointercancel`-on-scroll quirk this codebase has already solved once; `web-app`'s `size-limit` budget discipline favors zero added bytes for ~30-40 lines of purpose-built code. |
| Leader-key (`Alt+W`) window-switch sequence | State pattern — armed/disarmed states via dynamic `registry.register()`/deregister of follow-up shortcuts | GoF (State) | Extend `shortcutRegistry.ts`'s core `dispatch()` to natively support two-key chords | Bigger blast radius (every existing single-shortcut consumer would need re-verification against new chord-matching logic) for no benefit — dynamic register/deregister from a new consumer achieves the identical behavior with zero changes to the registry itself. |
| Leader key modifier: `Alt` rather than `Ctrl` | Avoid the entire class of tmux-prefix collisions by construction | pre-mortem P1 #1 | A different specific `Ctrl+<letter>` (e.g. `Ctrl+B`, `Ctrl+A`) | `Ctrl+B` is tmux's actual default prefix and `Ctrl+A` is its most common `screen`/remap alternative; since this app's core purpose is displaying live tmux-backed terminal panes, any `Ctrl`-based leader risks colliding with a real tmux prefix a user sends into a pane. `Alt`-based leaders are not part of that convention, sidestepping the collision class rather than trading one specific `Ctrl+<letter>` for another that might also be someone's remap. |

## Migration Plan
*(localStorage schema migration, not a database migration — no SQL, no DB downtime concerns; adapted to this feature's client-side-only constraint.)*

- **Migration logic**: `web-app/src/lib/window/windowPersistence.ts`'s `loadWindowLayout()`. Order of resolution: (1) `cockpit.windowLayout` if present and `version === 2` and shape-valid → use directly; (2) else `cockpit.paneLayout` (existing `loadPaneLayout()`) if it returns a valid `PersistedPaneLayout` → wrap into `{ version: 2, revision: 0, windows: [{ id: generateWindowId(), name: "Window 1", paneState: { root, focusedPaneId, zoomedPaneId } }] }`, write it to `cockpit.windowLayout` immediately so migration runs exactly once; (3) else → `null`, caller falls back to a single fresh window built from `initialPaneState()`.
- **Reversibility**: irreversible forward migration by design, but non-destructive — `cockpit.paneLayout` (v1) is never deleted or overwritten (ADR-003), so the pre-migration data is always recoverable via devtools even though there is no automated "downgrade" path.
- **Zero-downtime strategy**: not applicable in the DB sense (client-side, single-user, no server round-trip) — the equivalent risk is "migration runs correctly on first load post-ship," covered by the fixture test in Story 1.3.2.
- **Rollback procedure**: reverting the shipping PR restores the old single-key `cockpit.paneLayout` code path; because `cockpit.paneLayout` was never touched, users see their pre-migration layout exactly as it was (no data loss from a rollback). Any `cockpit.windowLayout` value written in the interim is simply ignored by the reverted code, not deleted.

## Observability Plan
- **Logs**: `console.error` at every fail-closed branch in `windowPersistence.ts` (unknown/corrupt version, migration parse failure, cross-tab revision conflict) — matches the existing try/catch logging convention in `usePaneLayout.ts`. Each log includes enough context to diagnose without exposing session content (window count, revision numbers, not pane contents).
- **Metrics**: none — this is a purely client-side, no-server-round-trip feature (matches `cockpit-tiling`'s existing precedent); no new dashboard is warranted for a local-storage-only feature per requirements.md's Observability Requirements.
- **Alerts**: no new alerts required — requirements.md explicitly states a migration failure needs client-side error visibility, not a dedicated oncall alert.

## Risk Control
- **Feature flag**: not gated — matches `cockpit-tiling`'s own precedent and requirements.md's explicit "no feature flag" Risk Control posture. Migration risk is mitigated structurally instead (new storage key, exhaustive version switch, fixture test) rather than via staged rollout.
- **Rollback procedure**: standard revert via PR close + revert commit. Safe because `cockpit.paneLayout` (v1) is never mutated (ADR-003) — reverting cannot destroy a user's pre-migration data.
- **Staged rollout**: full rollout on merge (client-side only, no server-side blast radius).

## Phase 1: Domain Model, Reducer, Persistence & Migration

### Epic 1.1: Window domain types
**Goal**: Establish the type vocabulary every later story builds on, with zero behavior yet.

#### Story 1.1.1: Define window domain types
**As a** developer implementing the window layer, **I want** the `WindowId`/`NamedWindow`/`WindowsState`/`WindowAction`/`PersistedWindowLayoutV2` types defined once, **so that** every reducer/persistence/hook file that follows imports a single, consistent vocabulary instead of inventing shapes ad hoc.
**Acceptance Criteria**:
- `windowTypes.ts` exports `WindowId`, `NamedWindow`, `WindowsState`, `WindowAction` (5-case union), `PersistedWindowLayoutV2`, and `WindowRevision`, all compiling with `tsc --noEmit`.
  - *Given* a fresh `windowTypes.ts` file, *When* another file does `import type { NamedWindow } from "@/lib/window/windowTypes"` and constructs `{ id: "win-1", name: "Window 1", paneState: initialPaneState() }`, *Then* TypeScript accepts it with no type error.
- No exported type is named bare `Window`.
  - *Given* `windowTypes.ts`, *When* `grep -n "^export.*\bWindow\b" web-app/src/lib/window/windowTypes.ts` is run, *Then* no line defines a type literally named `Window` (only `WindowId`, `NamedWindow`, `WindowsState`, `WindowAction`, `WindowRevision` appear).
**Files**: `web-app/src/lib/window/windowTypes.ts`

##### Task 1.1.1a: Create `windowTypes.ts` (~4 min)
- Define `type WindowId = string;`.
- Define `interface NamedWindow { id: WindowId; name: string; paneState: PaneState }` (import `PaneState` from `@/lib/pane/paneTypes`).
- Define `interface WindowsState { windows: NamedWindow[] }`.
- Define `type WindowRevision = number;`.
- Define `interface PersistedWindowLayoutV2 { version: 2; revision: WindowRevision; windows: NamedWindow[] }`.
- Define `type WindowAction = { type: "CREATE_WINDOW"; id: WindowId; name: string } | { type: "CLOSE_WINDOW"; id: WindowId; replacement: { id: WindowId; name: string } } | { type: "RENAME_WINDOW"; id: WindowId; name: string } | { type: "PANE_ACTION"; windowId: WindowId; action: PaneAction } | { type: "RESTORE_WINDOWS"; windows: NamedWindow[] };` (import `PaneAction` from `@/lib/pane/paneTypes`). `replacement` is **required**, not optional — every `CLOSE_WINDOW` action carries one regardless of `windows.length`, so an empty `windows` array is unrepresentable by construction (see Task 1.2.1b and Task 1.4.1e).
- Files: `web-app/src/lib/window/windowTypes.ts`

##### Task 1.1.1b: Add `generateWindowId()`/`initialWindowsState()` helpers (~3 min)
- New file `web-app/src/lib/window/windowUtils.ts`.
- `export function generateWindowId(): WindowId { return generateSecureId().slice(0, 8); }` (import `generateSecureId` from `@/lib/pane/paneUtils` — reuse, don't duplicate).
- `export function initialWindowsState(): WindowsState { const id = generateWindowId(); return { windows: [{ id, name: "Window 1", paneState: initialPaneState() }] }; }` (import `initialPaneState` from `@/lib/pane/paneReducer`).
- Files: `web-app/src/lib/window/windowUtils.ts`

### Epic 1.2: Pure `windowReducer`
**Goal**: A pure, fully-tested reducer over `WindowsState`, with zero persistence or React concerns.

#### Story 1.2.1: `windowReducer` handles all 5 `WindowAction` cases
**As a** developer, **I want** a pure `windowReducer(state, action)` mirroring `paneReducer`'s style, **so that** window lifecycle (create/close/rename) and pane-action delegation are both testable without React or localStorage.
**Acceptance Criteria**:
- `CREATE_WINDOW` appends a new `NamedWindow` with `paneState: initialPaneState()` (satisfying the existing `hasListPane` invariant `usePaneReducer.ts` already enforces for restored layouts).
  - *Given* `WindowsState { windows: [{ id: "win-1", name: "Window 1", paneState: P1 }] }`, *When* `windowReducer(state, { type: "CREATE_WINDOW", id: "win-2", name: "Window 2" })` is dispatched, *Then* the result is `{ windows: [{ id: "win-1", ... }, { id: "win-2", name: "Window 2", paneState: initialPaneState() }] }`, and `getAllLeaves(result.windows[1].paneState.root).some(l => l.viewKind === "session-list")` is `true`.
- `CLOSE_WINDOW` removes the named window; if it was the only window, it is replaced (not just emptied) using the `replacement` payload, which is always present — an empty `windows` array is unrepresentable, not just unlikely.
  - *Given* `WindowsState { windows: [{ id: "win-1", ... }, { id: "win-2", ... }] }`, *When* `windowReducer(state, { type: "CLOSE_WINDOW", id: "win-2", replacement: { id: "win-4", name: "Window 3" } })` is dispatched (the caller always supplies `replacement`, even though it goes unused here), *Then* the result is `{ windows: [{ id: "win-1", ... }] }` (length 1, `win-2` gone, `replacement` ignored since another window remained).
  - *Given* `WindowsState { windows: [{ id: "win-1", name: "Window 1", paneState: P1 }] }` (the only window), *When* `windowReducer(state, { type: "CLOSE_WINDOW", id: "win-1", replacement: { id: "win-3", name: "Window 1" } })` is dispatched, *Then* the result is `{ windows: [{ id: "win-3", name: "Window 1", paneState: initialPaneState() }] }` — never an empty `windows` array.
- `RENAME_WINDOW` with an empty string is a no-op (per `ux.md`'s "empty = cancel" recommendation) rather than setting `name: ""`.
  - *Given* `WindowsState { windows: [{ id: "win-1", name: "Debugging session y", paneState: P1 }] }`, *When* `windowReducer(state, { type: "RENAME_WINDOW", id: "win-1", name: "" })` is dispatched, *Then* `result.windows[0].name` is still `"Debugging session y"`, unchanged.
- `PANE_ACTION` delegates unmodified to `paneReducer`, updating only the addressed window's `paneState`.
  - *Given* `WindowsState { windows: [{ id: "win-1", paneState: P1 }, { id: "win-2", paneState: P2 }] }`, *When* `windowReducer(state, { type: "PANE_ACTION", windowId: "win-2", action: { type: "ZOOM_PANE", paneId: P2.focusedPaneId } })` is dispatched, *Then* `result.windows[0].paneState` is referentially equal to `P1` (untouched) and `result.windows[1].paneState` equals `paneReducer(P2, { type: "ZOOM_PANE", paneId: P2.focusedPaneId })`.
- `RESTORE_WINDOWS` replaces the entire `windows` array wholesale (used by both initial-load restore and cross-tab reconciliation).
  - *Given* any `WindowsState`, *When* `windowReducer(state, { type: "RESTORE_WINDOWS", windows: [W1, W2] })` is dispatched, *Then* the result is exactly `{ windows: [W1, W2] }`.
**Files**: `web-app/src/lib/window/windowReducer.ts`, `web-app/src/lib/window/__tests__/windowReducer.test.ts`

##### Task 1.2.1a: Implement `CREATE_WINDOW` + `RENAME_WINDOW` cases (~5 min)
- `windowReducer.ts`: `case "CREATE_WINDOW": return { windows: [...state.windows, { id: action.id, name: action.name, paneState: initialPaneState() }] };`
- `case "RENAME_WINDOW": if (action.name.trim() === "") return state; return { windows: state.windows.map(w => w.id === action.id ? { ...w, name: action.name } : w) };`
- Files: `web-app/src/lib/window/windowReducer.ts`

##### Task 1.2.1b: Implement `CLOSE_WINDOW` incl. last-window auto-recreate (~5 min)
- `case "CLOSE_WINDOW": { const remaining = state.windows.filter(w => w.id !== action.id); if (remaining.length === 0) { return { windows: [{ id: action.replacement.id, name: action.replacement.name, paneState: initialPaneState() }] }; } return { windows: remaining }; }` — no conditional branch on `action.replacement` itself: now that the field is required (Task 1.1.1a), the reducer only branches on `remaining.length === 0`, and `windows.length === 0` is unreachable by construction.

### Epic 3.3: Keyboard shortcuts (leader-key sequence)
**Goal**: A tmux-style leader key, `Alt+W` ("window"), followed by a digit/`n`/`p`/`,`, registered through the existing `ShortcutRegistry` with zero core changes to it. `Alt+W` was chosen — over a bare `Ctrl+<number>` (unusable: browser-chrome tab-switching on Windows/Linux, OS-level Mission Control on macOS, per `research/pitfalls.md` §2) and over any `Ctrl+<letter>` leader — specifically because `Ctrl+B` is tmux's own actual default prefix key and `Ctrl+A` is its most common `screen`/remap alternative: since this app's whole purpose is displaying live tmux-backed terminal sessions in panes, a `Ctrl`-based leader risks arming this app's outer leader mode whenever a user sends a real tmux prefix keystroke into a pane, silently hijacking their very next keystroke before it reaches the terminal (see `pre-mortem.md` P1 #1 / Failure Mode #1). An `Alt`-based leader sidesteps that whole collision class rather than trading one specific `Ctrl+<letter>` for another that might also be someone's tmux remap.

#### Story 3.3.1: `useWindowShortcuts` leader-key state machine
**As a** keyboard-first user, **I want** `Alt+W` then a digit to jump to a specific window (or `n`/`p` to cycle), **so that** I can switch windows without leaving the keyboard, the way tmux users already expect (with a leader key that doesn't collide with tmux's own).
**Acceptance Criteria**:
- Pressing `Alt+W` arms leader mode; pressing `1`-`9` within the armed window jumps to the window at that 1-indexed position and disarms.

- `n`/`p` cycle to next/previous window with wrap-around.
  - *Given* `currentWindowId = win-3.id` (the last window) and `windows = [win-1, win-2, win-3]`, *When* the user presses `Alt+W` then `n`, *Then* `switchToWindow(win-1.id)` is called (wraps around).
