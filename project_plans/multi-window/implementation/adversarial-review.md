# Adversarial Review: multi-window

**Date**: 2026-09-23
**Verdict**: CONCERNS

## Blockers

(none — no issue found rises to "must fix before any code is written"; all items below can be resolved during implementation without invalidating the architecture.)

## Concerns

- [ ] **Cross-tab `storage` event listener can silently discard this tab's own unsaved edits in windows the remote write never touched.** `useWindowManager`'s `storage` handler (Task 1.4.1c) dispatches `RESTORE_WINDOWS` with the *entire* remote `windows` array as soon as it sees a newer revision — this replaces the whole in-memory reducer state, not just the window the other tab edited. If tab A has an uncommitted split/resize in Window 1 (created in the last <300ms, not yet debounce-saved) and tab B saves an unrelated rename to Window 2, tab A's storage listener fires and wipes A's Window 1 edit too, with only a `console.error` as evidence. ADR-002 frames the accepted loss as "a tab whose *save* is skipped loses that specific in-flight edit" — but this path fires independently of whether A ever attempted a save, and the blast radius is "all windows in this tab," not "the one window in conflict." Recommend: gate the storage-listener's `RESTORE_WINDOWS` on there being no pending local debounce-save timer (let an in-flight local edit's own debounce fire and go through the revision-guard's normal ok/conflict path instead of being preempted), or scope the merge to windows this tab hasn't itself modified since its last known revision.
- [ ] **Silent swallow on localStorage quota/private-mode contradicts the plan's own Observability Plan.** Task 1.3.1c's `saveWindowLayoutRaw()` catches quota/private-mode errors with an empty catch block and no logging ("`catch { /* quota/private-mode */ }`"), but the plan's Observability Plan states "`console.error` at every fail-closed branch in `windowPersistence.ts`." A quota exceeded or Safari-private-mode write failure is exactly such a branch (the user's edit is silently lost, indistinguishable from a successful save from the caller's perspective since `saveWindowLayoutRaw` is `void`). Add a `console.error` in that catch, and reconsider whether `saveWindowLayoutRaw` should signal failure back to `useWindowManager` at all — right now a first-migration write failure would make the hook believe migration succeeded.
- [ ] **`loadWindowLayout()`'s `localStorage.getItem` calls aren't shown wrapped in try/catch, only the `JSON.parse` is (Task 1.3.1a).** In a sandboxed iframe or a browser configuration that throws `SecurityError` on `localStorage` access entirely (not just on write), an unguarded `getItem` throws synchronously and crashes the calling render path rather than falling through to the `null`/fresh-user case the rest of the design promises. Confirm the try/catch in the actual implementation wraps the storage access itself, not just the parse.
- [ ] **No user-visible feedback when a save conflicts or an edit is dropped.** Every failure/conflict path in the plan (stale revision, quota, malformed layout, storage-event override) logs to `console.error` only. Requirements.md explicitly upgraded cross-tab conflict from "edge case" to "load-bearing," yet a user who loses a rename or a split to a conflict gets zero in-app signal — they'll only notice when the layout doesn't match what they just did, with no error message to explain why. At minimum, consider a lightweight toast ("window layout was updated in another tab") on the conflict/adopt path, proportional to how routine the plan itself says this conflict now is.
- [ ] **Forking `MobilePaneTabStrip` structurally is likely to trip this repo's own `jscpd` duplication gate.** `MobilePaneTabStrip.tsx` is 61 lines; the plan's own Pattern Decisions table chooses to "fork ... structurally (hand-rolled `role=\"tablist\"`)" rather than extract shared logic, explicitly to avoid a Radix dependency. But `make ready`'s `jscpd` gate (this repo's CLAUDE.md, `web-app/.jscpd.json`, `minLines`/`minTokens` 20/200) is tuned specifically to catch "component forks" as its named example of real, actionable duplication — this plan produces exactly that pattern (tab button JSX, roving-tabindex logic, truncation/title convention, "+"-button pattern all copied) with no shared-extraction task anywhere in Phase 3. Either add a task to extract the genuinely-shared pieces (tab-button rendering, roving tabindex, truncation) into a common hook/component both strips call, or explicitly budget for the jscpd ratchet threshold needing to move and say so, rather than discovering this at `make ready` time on a nearly-finished PR.
- [ ] **`web-app/src/app/page.test.tsx` isn't in Story 2.2.2's file list.** `grep -rln "PaneTilingContainer" web-app/src` shows `page.test.tsx` (in addition to `page.tsx` and the component itself) references `PaneTilingContainer`. `HomeContent` is being restructured to source `paneState`/`dispatch` from `useWindowManager`/`useWindowUrlSync` instead of a direct `usePaneReducer` call, and to render a new `WindowTabStrip` sibling — this will very likely break `page.test.tsx`'s existing mocks/assertions, but no task updates it. Add it to Story 2.2.2's Files list and give it explicit acceptance criteria (or fold it into Task 2.2.2a/b).
- [ ] **Mobile tab-strip density Rabbit Hole is only mitigated by "visually distinguishable," not "both fit."** Requirements.md flags real-estate contention when both the new `WindowTabStrip` and the existing pane tab row are visible on a small viewport as a genuine UX risk, not just a styling question. Story 3.1.1's only AC on this is a code-review-verified CSS token difference (border side/height/background). There's no manual verification task (unlike Story 3.3.2's dedicated `Ctrl+B` platform spike) confirming the combined layout doesn't crowd out pane content on a real small viewport. Add a manual-verification task in Phase 4 alongside 4.1.1a.

## Minors

- `windowReducer`'s `PANE_ACTION`/`RENAME_WINDOW`/`CLOSE_WINDOW` cases silently no-op when `action.windowId`/`id` doesn't match any window (e.g. a stale dispatch racing a close from another tab) — fine functionally, but a `console.warn` would make an already-hard-to-reproduce cross-tab race easier to diagnose in the field.
- `generateWindowId()` truncates `generateSecureId()` to 8 characters with no collision check against existing window ids on `CREATE_WINDOW` — astronomically unlikely at "low double digits" scale, not worth a fix, but worth a one-line comment acknowledging the assumption if collision detection isn't added.
- Task 4.2.1's coverage-parity metric (`windowReducer.ts` line coverage `>=` `paneReducer.ts` line coverage) is comparable in principle but not a strong proxy for "equally well-tested" — a smaller file can trivially hit 100% while missing edge cases a larger, more complex file's lower percentage still covers more meaningfully. Not worth blocking on since it's what requirements.md's Success Metric literally asks for, but don't over-index on the number alone at review time.
- `closeWindow`'s replacement-id computation reads `state.windows.length` at call time inside the hook rather than inside the reducer; under rapid concurrent dispatches this is a minor staleness risk (same class of issue already accepted elsewhere in the plan for `createWindow`'s synchronous id generation) — low practical risk given single-user, low-window-count usage.
