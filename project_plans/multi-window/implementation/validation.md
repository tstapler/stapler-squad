# Validation Plan: multi-window

**Date**: 2026-09-23

## Happy Path Scenario
Given a user on the Baseline single-`PaneState` cockpit (existing `cockpit.paneLayout`, no `cockpit.windowLayout` key yet), when they load the app (triggering the v1→v2 migration into "Window 1"), click `+` to create a second window, build an independent pane layout in it, and switch back to Window 1 via the tab strip, then Window 1 renders with its exact original layout (same splits, sizes, assigned sessions) and Window 2 retains its own independent layout — proving the core value proposition: two work contexts, each preserved, addressable in under 2 seconds of interaction, with zero disruption to the pre-migration layout.

This is the anchor. Every test below is a variation on it: an error path exercises what happens when a step in this flow is interrupted (stale URL, cross-tab conflict, malformed data); an edge case exercises a boundary of it (last window closed, swipe past the end, leader key with no follow-up).

## Migration Test Detail

Per Step 5: this feature's "migration" is the client-side v1 `cockpit.paneLayout` → v2 `cockpit.windowLayout` schema migration (`web-app/src/lib/window/windowPersistence.ts`'s `loadWindowLayout()`/`migrateFromV1()`), not a database migration — there is no schema "down" command to literally invoke, so "up" and "down" are adapted per the plan's own Migration Plan section (irreversible-forward-but-non-destructive, ADR-003):

**`migration_should_be_reversible`** (`web-app/src/lib/window/__tests__/windowPersistence.migration.test.ts`, Type: Migration)
1. **Up**: seed a mocked `localStorage` with the captured `v1-pane-layout.fixture.json` under `cockpit.paneLayout` and no `cockpit.windowLayout` key. Call `loadWindowLayout()`. Assert: the result is a valid `PersistedWindowLayoutV2` (`version: 2`, `revision: 0`, `windows: [{ name: "Window 1", ... }]`), it was written through to `localStorage["cockpit.windowLayout"]`, and `localStorage["cockpit.paneLayout"]` is byte-for-byte unchanged from the original fixture JSON (never deleted or rewritten).
2. **Down**: simulate "reverting the shipping PR" by calling the pre-migration code path directly — `loadPaneLayout()` (the existing, unmodified v1 loader) against that same `localStorage` state. Assert it returns the original v1 `PaneState` unchanged, proving a revert sees the user's pre-migration layout exactly as it was, unaffected by the interim `cockpit.windowLayout` write from step 1.
3. **Fail-closed, no data loss**: seed `cockpit.paneLayout` with a corrupt/malformed v1 blob (`{"version":1,"root":null}`). Call `loadWindowLayout()`. Assert it returns `null` (never throws, never fabricates a partial `NamedWindow`), logs via `console.error`, and — critically — does **not** write anything to `cockpit.windowLayout`, so a later successful migration attempt (e.g. after a bug fix ships) is not blocked by a bad write-through from this failed attempt.

## Test Stack
- **Unit**: Jest (`ts-jest`, `jest-environment-jsdom`, per `web-app/jest.config.js`) + React Testing Library for hook/component tests (`@testing-library/react`'s `renderHook`/`render`), mirroring `usePaneReducer.persistence.test.ts` and `MobilePaneTabStrip.test.tsx`'s existing structure. No new dependency required.
- **Integration**: Same Jest/RTL stack, distinguished from "Unit" only by scope (multiple modules composed — e.g. `useWindowManager` + real vs. mocked `localStorage` + a dispatched `storage` event, or `windowReducer`'s delegation into the real `paneReducer`) rather than a different framework. `windowPersistence`'s round-trip integration test (REQ-7) uses jsdom's real, unmocked `localStorage` rather than a hand-rolled stub, to catch serialization bugs a mock would hide.
- **E2E / UX**: Playwright, following this repo's existing `tests/e2e/` conventions exactly — `@feature` annotation headers referencing `FEATURE_CATALOG` entries (a new `docs/registry/features/frontend/window/` entry set is needed once `make registry-generate` is run against the shipped `// +feature:` markers), no `waitForTimeout` (use `expect(locator).toHaveValue/toBeVisible/toBeHidden(...)`), `data-testid`/ARIA-role locators only, and new page helpers under `tests/e2e/pages/` (a `WindowTabStripPage.ts` following the `SessionsPage.ts`/`ShellTabsPage.ts` pattern) rather than inlining selectors into spec files. `tests/e2e/accessibility.spec.ts` and `tests/e2e/touch-targets.spec.ts` are extended in place rather than duplicated, since they already exist as this repo's dedicated gates for exactly those two concerns.
