# Pre-mortem: multi-window
**Date**: 2026-09-23

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The `Ctrl+B` leader key (Story 3.3.1) is registered with `context: "cockpit"`, and `shortcutRegistry.ts`'s context gate (`web-app/src/lib/shortcuts/shortcutRegistry.ts:100-103`) lets `"cockpit"`-context shortcuts fire even when `document.activeElement` is inside a terminal pane. `Ctrl+B` is tmux's own real default prefix, and this app's whole purpose is displaying live tmux-backed agent sessions — so a user legitimately sending tmux's own `Ctrl+B` into a session pane also arms the *outer* web app's leader mode, and the very next keystroke they send into that same terminal (a digit, `n`, `p`, or `,` — all real tmux commands) gets consumed by the armed follow-up shortcut instead of reaching the pty. | Users running real tmux inside an agent session report that tmux window/pane commands intermittently "eat" a keystroke or do nothing, with no error — indistinguishable from a flaky terminal/PTY bug, so it's likely to get mis-triaged as a websocket or xterm.js issue rather than a shortcut conflict. | Add an explicit AC + test to Story 3.3.1: `Ctrl+B` (and its armed follow-ups) must not arm/act while `document.activeElement` is inside a terminal pane, either by excluding `useWindowShortcuts`'s registrations from the terminal-context passthrough or gating on focus directly. If terminal-focus exclusion isn't feasible, pick a leader key other than tmux's own default. | P1 |
| 2 | Task 1.3.1b/1.3.3a's v1→v2 migration write deliberately skips the revision guard ("no revision guard needed for this first-ever write"). If two tabs both find no `cockpit.windowLayout` key at nearly the same moment (e.g. a user already had 2 tabs open when the client updates, or double-refreshes), both independently run `migrateFromV1()`, each generates its own fresh `WindowId` via `generateWindowId()`, and both call the ungated `saveWindowLayoutRaw()` — last write wins, and the losing tab's in-memory window id never matches what's now persisted. | Right after ship — the highest-visibility moment for this feature's "zero disruption" promise — a user with 2+ tabs open at update time sees the two tabs silently diverge onto different ids for what should be the same migrated "Window 1," and an edit in one tab appears to vanish from the other. | Route the migration write through the same revision-guarded `saveWindowLayout()` path (treating "no key present" as an implicit revision-0 precondition) instead of the unguarded `saveWindowLayoutRaw()`, so a second concurrent migration detects the first tab's write and adopts it instead of forking. | P2 |
| 3 | Every AC for `useWindowUrlSync`/`page.tsx` wiring (Stories 2.2.1, 2.2.2) is a unit test against mocked `useSearchParams`/`router.replace`. Nothing in Phase 4 exercises two real browser tabs against a running Next.js instance — yet independent per-tab window display via the URL (Success Metric #4) is the single most novel, hardest-to-verify-by-inspection requirement in the whole feature, and the only one of the three "resolved" cross-cutting risks that got no dedicated manual/e2e verification task (contrast Story 3.3.2's dedicated `Ctrl+B` platform spike). | The feature passes `make ci` and review cleanly, ships, and the first bug report is exactly the scenario requirements.md named explicitly: switching windows in one tab moves another tab, or `router.replace` doesn't behave the way the jsdom mock assumed (extra scroll, unwanted navigation, stale `searchParams` read). | Add a Phase 4 task or `tests/e2e` Playwright spec that opens two tabs against the same running instance, switches windows independently in each, and asserts neither affects the other — giving this requirement the same real-environment rigor Story 3.3.2 already gives the leader-key collision check. | P1 |
| 4 | `windowReducer`'s `PANE_ACTION` case (Task 1.2.1c) returns a brand-new `windows` array and a brand-new object for the affected window on *every* pane action, and that same full array (including every other window's pane tree) is passed straight into `<WindowTabStrip windows={windows} .../>` (Task 2.2.2b) with no memoization anywhere in Story 3.1.1. | Dragging a pane divider or resizing with several windows open feels janky compared to single-window use — every mousemove re-renders the tab strip and re-arms the 300ms debounce to `JSON.stringify`/`localStorage.setItem` the entire windows array, not just the one that changed — directly contradicting the plan's own "<100ms perceived switch, no visible re-render jank" NFR, and getting worse as a user accumulates the very window counts the feature is meant to encourage. | Memoize `WindowTabStrip` against a derived `{id, name}[]` list rather than the full `NamedWindow[]`, and add an explicit Phase 4 AC (alongside the existing coverage-parity check) that a resize-drag with 5+ open windows doesn't increase the tab strip's re-render count. | P2 |
| 5 | `useWindowSwipe` (Task 3.2.1c) is wired to the identical `forwardRef` container that the tab strip itself uses for `overflowX: auto` horizontal scrolling (Task 3.1.1a). Once a user has enough windows to overflow the visible strip width, the touch gesture needed to scroll the strip to see hidden tabs is indistinguishable from the gesture defined to switch windows — nothing in Epic 3.2 disambiguates "scrolling the list" from "swiping to switch." | A mobile user with more than a handful of windows tries to scroll the strip sideways to find an off-screen tab, and the app instead jumps to the next/previous window on every touch — the feature becomes actively hostile to exactly the "low double digits" window count it's scoped for. | Move the swipe target off the scrollable strip itself (e.g. onto the pane content area, matching where `useTerminalGestures` already listens), or make `useWindowSwipe` scroll-position-aware so a touch that's actually scrolling (non-zero `scrollLeft` delta, content wider than viewport) doesn't also fire `onSwipe`; add a "strip is overflowing/scrolled" test case to Story 3.2.2. | P2 |

## P1 Items (address before implementation)
- [x] #1 — **Resolved.** Leader key changed from `Ctrl+B` to `Alt+W` across plan.md, design/ux.md, requirements.md, and validation.md — eliminates the tmux-prefix collision class by construction (no `Ctrl`-based leader at all) rather than adding a terminal-focus exclusion. State machine (armed/disarmed, 3s auto-disarm) unchanged.
- [x] #3 — **Resolved.** Added Story 2.2.3 + Task 2.2.3a to plan.md's Epic 2.2: a real two-`browser.newPage()`-tab Playwright e2e test in `tests/e2e/multi-window-cross-tab.spec.ts`, asserting independent window display and cross-tab rename propagation via the `storage` listener. Tracked in validation.md's Requirement → Test Mapping under REQ-10.

## P2 Items Resolved in Planning
- [x] #4 — **Resolved.** Added an AC to Story 3.1.1 and new Task 3.1.1e (plan.md): `WindowTabStrip` is exported as `React.memo(..., arePropsEqual)`, where the comparator derives a lightweight `{id, name}[]` list from `windows` (plus `currentWindowId`) instead of comparing the full `NamedWindow[]` (which embeds every window's pane tree) — so a pane action in one window no longer re-renders the tab strip or re-arms the debounced save for unrelated windows. Story 3.1.3/Task 3.1.3a extended with a render-count regression test; validation.md's Requirement → Test Mapping gained a row under REQ-3 (`WindowTabStrip_should_notReRender_When_unrelatedWindowsPaneStateChanges`).
- [x] #5 — **Resolved.** Kept the swipe gesture wired to `WindowTabStrip`'s own container ref (Task 3.2.1c, unchanged) rather than moving it to the pane content area, since moving it would contradict the existing Pattern Decisions entry that already commits to that wiring. Instead made `useWindowSwipe` scroll-position-aware (plan.md Story 3.2.1's new AC + Task 3.2.1a): a touch that changes the overflowing strip's `scrollLeft` during the gesture is classified as scrolling, not swiping, and never fires `onSwipe`; a clean swipe that doesn't move `scrollLeft` still fires normally. Task 3.2.2a extended with the corresponding test case; validation.md's Requirement → Test Mapping gained a row under REQ-6 (`useWindowSwipe_should_notCallOnSwipe_When_stripIsOverflowingAndTouchScrollsIt`).
