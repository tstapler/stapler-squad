# Research: Prior Art for Window Grouping/Switching

## 1. What cockpit-tiling already built (don't re-solve)

Source: `project_plans/cockpit-tiling/requirements.md`, `implementation/plan.md`; code in `web-app/src/lib/pane/` and `web-app/src/components/pane/`.

- **Data model** (`web-app/src/lib/pane/paneTypes.ts`): `PaneState { root: PaneNode, focusedPaneId, zoomedPaneId }`, where `PaneNode` is a `LeafPane | SplitPane` binary tree. This is exactly the "independent pane tree" unit multi-window needs to multiply — the plan doc's own framing ("collection of named `PaneState` trees") is correct and requires no new tree primitive.
- **Reducer** (`paneReducer.ts`): pure, already handles split/close/resize/focus/assign-session/assign-tab/zoom/nudge-resize/reset/restore. Multi-window must not touch this — it needs a *new* reducer one layer up that holds `PaneState[]` + active index, dispatching pane actions to whichever `PaneState` is active.
- **Persistence** (`usePaneLayout.ts`, `usePaneReducer.ts`): localStorage key `cockpit.paneLayout`, `version: 1` schema, `validateAndRepair()` walks the tree nulling out stale `sessionId`s, `loadPaneLayout()`/`savePaneLayout()`/`clearPaneLayout()`. The migration path requirements.md asks for (v1 flat tree → v2 array of named windows) is a direct analog of the `viewKind` backward-compat shim already in `validateAndRepair` (`tree.viewKind ?? "session-detail"`) — same defensive pattern, one version bump up.
- **Stale-session revalidation timing gotcha** (`usePaneReducer.ts` lines 42-103): there's a `sessionsLoadedRef` guard distinguishing "sessions haven't loaded from server yet" ([] before first response) from "user really has zero sessions" ([] genuinely). The restore effect skips `validateAndRepair` entirely until sessions have loaded once, otherwise every saved `sessionId` gets nulled against an empty set on first mount. **This same bug class will hit the window layer**: if the window-level restore path validates each window's tree independently at different times relative to sessions loading, get the "sessions loaded" check right once at the window-manager level and pass it down — don't let each `PaneState` re-derive its own timing.
- **Mobile tab strip precedent** (`MobilePaneTabStrip.tsx`): existing bottom tab row for panes-within-a-window on <768px, `role="tablist"`/`role="tab"`/`aria-selected`. This is the direct visual/accessibility template to reuse for the window tab strip — but see §3 below on stacking two tab rows.
- **Shortcut collision precedent already documented in code**: `usePaneShortcuts.ts` has inline comments about `Ctrl+-` (browser zoom-out on Windows/Linux, safe on macOS since that's Cmd+-) and `Ctrl+W` (browser close-tab, blocked via `preventDefault()` on Chrome/Firefox). This confirms the pattern to follow for `Ctrl+<number>` (see §2) — document the platform caveat inline next to the registration, the way the pane shortcuts already do.

## 2. Ctrl+\<number\> feasibility — a real risk, not hypothetical

Requirements.md flags this as an open question. Finding: **`Ctrl+1`–`Ctrl+8` (and `Ctrl+Tab`) are OS/browser-reserved literal tab-switching shortcuts in Chrome and Firefox on Windows/Linux, and they cannot be intercepted via `preventDefault()`** — unlike `Ctrl+W`, which the existing pane code already successfully `preventDefault()`s. This is a stronger constraint than "might collide with pane shortcuts" — it's "will silently do nothing (or switch the *browser* tab instead) on the majority desktop platform/browser combo." Recommend the plan either:
- Use `Ctrl+Alt+<number>` or `Cmd/Ctrl+Shift+<number>` (Chrome doesn't reserve these), or
- Follow tmux's own binding of `<prefix> <number>` (a leader-key sequence) rather than a bare modifier+digit, which avoids the browser reservation entirely and matches the tmux mental model requirements.md already leans on for the tab-bar visual language.

`Ctrl+n`/`Ctrl+p` for next/prev also has a browser collision on some platforms (`Ctrl+N` = new window in several browsers) worth flag-testing early, same rigor as the numbered case.

## 3. Edge cases and failure modes beyond requirements.md's Rabbit Holes

- **`zoomedPaneId`/focus across window switches**: `PaneState` already carries `focusedPaneId` and `zoomedPaneId` per tree, and since each window keeps its own independent `PaneState`, switching away and back should trivially preserve both (no extra design needed) — *if* the window-level state literally stores one `PaneState` per window rather than resetting on switch. This needs an explicit test: switch away from a zoomed pane, switch back, assert still zoomed. Easy to get right by construction, easy to silently break if the implementation naively re-runs `initialPaneState()` per switch instead of looking up the stored tree.
- **Background-window session deletion**: `usePaneReducer`'s re-validate effect (lines 86-103) only walks `state.root` — the *active* tree. If windows become an array of `PaneState`, a session deleted while its owning window is in the background will not get nulled out until that window becomes active (or never, if it stays backgrounded and the effect isn't re-run per-window). The window-manager-level reducer needs to run `validateAndRepair` over *every* window's tree on the same sessions-changed effect, not just the active one — otherwise switching to a stale background window can show a pane still pointing at a deleted session while an untouched active window looks fine, an inconsistency that would ship silently since the existing single-window code has no test exercising "revalidate a tree that isn't currently mounted."
- **Rename-in-progress + navigate-away**: no existing rename-with-inline-editable-state precedent was found scoped to a tab-bar-like UI in this codebase (session rename appears to be modal/dialog-based, not inline-in-place — see `components/sessions/SessionCard.tsx`/`SessionRow.tsx` double-click references, worth confirming exact UX before copying it). Decide explicitly: does clicking away (blur) commit, cancel, or leave the input focused-but-ignored? Committing on blur is the tmux-like default and least surprising; silently discarding a half-typed rename on blur is the likely bug if this isn't decided up front.
- **Closing the window that owns the currently-dragged resize handle**: not in requirements.md at all — if a window can be closed via keyboard shortcut while a pointer-drag resize is mid-gesture in a *different* window's pane (unlikely but possible with async state), make sure pointer-event cleanup (`ResizeHandle.tsx`) isn't tied to a window index that just shifted after a close reindexes the array.
- **Empty-tab-bar transient state during window creation**: creating a new window needs a defined "empty window" default — does it start with one blank leaf pane, or the session-list pane assignment that `usePaneReducer.ts`'s `hasListPane` check implies is now mandatory for every tree? If the existing single-window persisted-layout code discards any tree lacking a `session-list` leaf (`usePaneReducer.ts` line 60-64), a newly created window must satisfy that same invariant from the start or it will be silently discarded by that exact check on the next reload.

## 4. Likely unstated needs worth flagging (scope-adjacent, not explicitly asked for)

- **Per-window activity indicator**: the codebase already has the exact analog for this. `SessionRow.tsx` has a `statusDot`/`getStatusDotValue(status)` pattern mapping session status to a colored dot, and `NotificationContext.tsx` computes an `unreadCount` from `notificationHistory.filter(n => !n.isRead)`. A window tab showing "something changed in a session inside this backgrounded window" (new output, an approval needed, a session finishing) is a straightforward composition of those two existing primitives — roll up the worst/most-urgent status dot across all panes/sessions in a non-active window's tree and render it on that window's tab. This is genuinely adjacent to Slack/Discord unread-badge UX the user asked about researching, and it's cheap given the pieces already exist — worth flagging to the user as a likely quick follow-up even though requirements.md's Scope section doesn't ask for it (it's explicitly deferred territory, not core MVP, but low-cost given `statusDot` and `unreadCount` are both drop-in).
- **Reduced-motion / instant-switch for the <100ms SLO**: no explicit finding of a `prefers-reduced-motion` check in the pane code searched; if window switching gets any transition animation for polish, make sure it's skippable/instant under reduced-motion and doesn't itself blow the 100ms perceived-switch budget the requirements set.
- **Confirming "last window" wording vs. tmux precedent**: tmux auto-recreates a window when the last one is killed only in specific configs; by default closing the last window ends the tmux session entirely. Since this app has no equivalent to "end the session" (there's always a cockpit to show), the tmux analogy actually argues for auto-recreating a blank Window 1 on last-close, not blocking the close — worth stating this as the recommended default answer to the open question rather than leaving it fully open into Phase 3.

## 5. Existing "workspace"/"window"/"tab group" concepts already in the codebase — naming collision risk

Searched `web-app/src` broadly for `workspace|tabgroup|multiwindow` and for bare `window` usage (excluding DOM `window.*` calls).

- **`WorkspaceSwitcher.tsx` (`web-app/src/components/layout/`) already owns the term "workspace" for something unrelated**: a header dropdown for switching between *workspace databases* — i.e., the state-isolation feature documented in `docs/reference/state-isolation.md` (`STAPLER_SQUAD_WORKSPACE_MODE`, `SwitchDatabase`). It lists "discovered workspaces" and lets a user switch or merge sessions between separate on-disk databases — a server-side, cross-session-storage concept, nothing to do with pane layouts. **Do not name the new window-tab-bar concept "workspace"** anywhere in code, UI copy, or the plan doc — it would directly collide with this existing, shipped feature and confuse users who already know "workspace" means "which database/instance am I pointed at." The requirements.md doc itself avoids this correctly by using "window," not "workspace" — worth keeping consistent through implementation (variable names, CSS class prefixes, localStorage keys) since it would be easy for an implementer to reach for `workspace.css.ts`/`useWorkspace()` naming by habit.
- **No pre-existing "window" or "tab group" concept found** that would collide with the new feature — the only other uses of the bare word "window" in `web-app/src` are either DOM `window.*` global references or unrelated prose (e.g. "coalescing window," "undo window" as in a time-duration sense, not a UI surface). Safe to use "window" as the new concept's name without an existing-code collision, only the WorkspaceSwitcher naming risk above.
- **Notification system (`lib/contexts/NotificationContext.tsx`) is otherwise unrelated to windows** but is the direct implementation precedent for the activity-badge idea in §4 above (grouping, `isRead`, `unreadCount`).
