# UX Research: multi-window

Deepens the tab-strip decision already recorded in `requirements.md` (top on desktop, bottom-docked on mobile, `Ctrl+<number>`/`Ctrl+n`/`Ctrl+p`, rename via double-click/long-press). Covers comparable patterns, mental-model/naming risk, accessibility, error/edge cases, and jobs-to-be-done.

## 1. Comparable UX patterns

| Tool | Grouping model | What works, and why |
|---|---|---|
| **tmux** | Session (persistent, detachable) → Windows (tab-equivalent) → Panes (splits) | Strict three-level hierarchy with the terminology this app borrows its name from. Windows live in the status line, not a separate visual tab bar — cheap on vertical space. Notably, many experienced tmux users skip the windows layer entirely and use only sessions + panes, because "windows can disappear without a trace — it's hard to know how many you have open" without actively checking the status line. That's a direct precedent for this project's tab-strip decision: a visible, persistent tab bar (unlike tmux's easy-to-miss status line) is the right call specifically to avoid this known tmux complaint. |
| **iTerm2** (native tabs, and `-CC` tmux integration) | Window → Tabs → Split panes | iTerm2's tmux integration maps tmux windows to iTerm2 tabs 1:1 — validates "window = tab" as the natural UI translation. Friction reported: tmux enforces uniform pane dimensions across all windows in a session, which iTerm2 inherits and users find surprising; also a startup cost "spawning all the tabs one at a time" with many tmux windows. Relevant caution: don't assume window-switch is free at arbitrary scale — profile actual render cost if a user opens many windows, even though this project's scale is "low double digits at most" per Feasibility Risks. |
| **Windows Terminal** | Window → Tabs → Panes | Same shape as iTerm2, GUI-native, no persistence. No distinguishing pattern beyond confirming the tab-as-window-equivalent convention is now a cross-platform terminal norm, not tmux-specific. |
| **VS Code (editor groups)** | Editor groups (spatial splits) + tabs (documents) within one project/workspace | Content-centric, not context-centric: tabs are files, groups are splits of files — all inside a *single* project's state. This is the wrong model to imitate for multi-window here, because it doesn't isolate separate work contexts from each other (search, focus, etc. stay unified). Telling counter-signal: there's an active, well-argued VS Code feature request (microsoft/vscode#324309) to bolt a Slack/Discord-style "workspace switcher sidebar" onto the editor precisely because editor-groups/tabs don't solve "switch between isolated projects," and the request explicitly wants each entry to preserve full isolation (not merge state) — which is exactly what this project's "independent `PaneState` tree per window" design already does correctly, just via a tab strip instead of a sidebar. |
| **Slack / Discord (workspace switcher)** | Vertical icon rail, far edge, each icon = fully isolated workspace/server | Confirms the value of an *isolated-context* switcher (matches this project's per-window independent pane tree) but uses a different visual placement (vertical icon rail) than the horizontal tab strip this project already chose. The rail works well for Slack/Discord because switches are infrequent (workspace-per-employer, server-per-community) and icons need no text label. This project's switches are more frequent (context-switching within one work session) and windows need short human-chosen names — a horizontal tab strip with text labels (this project's choice) fits that higher-frequency, named-context need better than an icon rail would. |

**Takeaway for this project**: the horizontal tab-strip decision already made in the requirements interview is well supported — it's the terminal-app norm (tmux/iTerm2/Windows Terminal all converge on tabs-as-windows), it avoids tmux's own "windows are invisible" complaint by staying always-visible, and it delivers Slack/Discord's isolated-context benefit without adopting Slack/Discord's lower-frequency icon-rail affordance, which would be a worse fit here.

## 2. User mental models and naming risk

**tmux's own model**, which this app's name deliberately invokes: `Session → Window → Pane`. Users coming from tmux will map:
- app "session" (existing top-level concept — an agent/tmux session backing a pane) ≈ tmux "pane" content, NOT tmux "session"
- proposed "window" (new layer, a named collection of pane trees) ≈ tmux "window" — this one lines up cleanly
- app's existing pane-tiling layer ≈ tmux "pane" — also lines up

**The collision risk is one level up, not at "window."** This app already uses "session" as its top-level, most-important noun (a running AI agent in a tmux session — see `session/` package, `Session` proto type, `SessionDetailView`). In tmux's own vocabulary, "session" is the *outermost* container (the thing that survives detach/reattach) and "window" sits *below* it. This project's proposed hierarchy is the reverse: `window (new, outer) → pane → session (existing, innermost)`. A user who knows tmux and reads "window" and "session" as coexisting terms in the same app may reflexively expect session to be the outer/persistent concept and window inside it — backwards from what's being built.

Mitigating factors:
- The requirements doc's own framing — "a second axis of organization above panes" — is internally consistent once explained; the risk is purely in the unexplained noun collision for tmux veterans on first encounter, not in the design itself.
- "Window" is *also* the correct, unmarked term for other reference audiences (browser tabs group by "window," VS Code/iTerm2/Windows Terminal all call the outermost native OS container a "window") — so non-tmux users, likely the majority, will read "window" exactly as intended.
- `grep -ril "window" web-app/src` turns up only the browser global (`window.location`, etc.) — no prior *domain-level* UI concept named "window" — so this is a clean namespace to introduce.

**Recommendation**: keep "window" (matches the existing requirements decision and the non-tmux-user majority's expectation) but add a one-line explanatory affordance for the minority audience who will map it onto tmux — e.g. a tooltip or first-run hint on the window tab strip ("Group related panes into a window — like a tmux window, but sessions here are your agent panes, not tmux sessions"). This is a documentation/onboarding mitigation, not a renaming one — renaming risks breaking the "matches tmux vocabulary" benefit for the audience it helps most.

## 3. Accessibility: ARIA and touch target sizing

The codebase already has a working precedent to extend, not invent from scratch: `web-app/src/components/pane/MobilePaneTabStrip.tsx` uses `role="tablist"` on the container, `role="tab"` + `aria-selected` on each button, and `aria-label="Pane switcher"` on the list. The window tab strip should mirror this exactly (e.g. `aria-label="Window switcher"`), which also directly answers the "keep the two navigation layers visually *and* semantically distinguishable" rabbit hole from requirements — they should be two independent `tablist` regions with distinct labels, not nested or merged.

**Required ARIA structure** (WAI-ARIA Tabs Pattern):
- Container: `role="tablist"`, labelled via `aria-label` or `aria-labelledby`.
- Each tab: `role="tab"`, `aria-selected` (exactly one `true` at a time), `aria-controls` pointing at its panel's id, `tabindex="0"` on the active tab and `tabindex="-1"` on all others (roving tabindex — not each individually focusable, so the strip is a single stop in page Tab order).
- Panel: `role="tabpanel"`, `aria-labelledby` pointing back at its tab, and inactive panels get the `hidden` attribute (removed from the accessibility tree, not just visually hidden).
- Keyboard: Left/Right arrow moves focus among tabs (Home/End jump to first/last); moving focus should also activate the tab immediately ("automatic activation") since switching windows here is instant, local state — no network/expensive load that would justify manual activation (Enter/Space to confirm). This matches the project's own <100ms perceived-switch-time NFR.
- Screen reader announcement on switch: covered by `aria-selected` state change plus the panel's `hidden` toggle — assistive tech announces the newly revealed panel's content once it's unhidden and, if the panel itself receives programmatic focus (`tabindex="-1"` + `.focus()`) or the tab's accessible name changes state, that's sufficient without a separate live region. Do not also add an `aria-live` announcement — VS Code and other tools that do this alongside standard tab semantics tend to double-announce and irritate screen reader users.

**Touch target sizing** (WCAG 2.2, Level AA, Success Criterion 2.5.8 Target Size Minimum, published 2023 and still current as of this research): minimum **24×24 CSS pixels**, measured as the largest unobscured touch-activation area. This is the *accessibility floor*, not the practical target — platform guidance sets a higher practical bar: iOS 44×44pt, Android 48×48dp, Microsoft 44×44px. Given the mobile tab strip already exists (`mobileTabButton` in `MobilePaneTabStrip.tsx`) and this project explicitly reuses that visual language, the window tab strip's tap targets should match whatever size that component already uses (check `mobilePaneTabStrip.css.ts` at implementation time) rather than independently re-deriving a size — consistency between the two stacked tab rows matters more here than picking an ideal number in isolation, and both should clear the 44px practical floor, not just the 24px legal minimum, given they'll sit close together on a small viewport (the "mobile tab-strip density" rabbit hole).

## 4. Error states and edge cases

| Case | Recommended handling | Rationale / precedent |
|---|---|---|
| Rename to empty string | Treat as cancel, not error — revert to previous name, no validation message shown. | Common pattern across inline-rename implementations (pgAdmin, others): empty commit = no-op cancel, since forcing the user to re-type a name they were trying to remove is worse UX than silently keeping the old one. |
| Rename to a duplicate name | Allow it — do not block. Windows are addressed by position/id internally (tabs, `Ctrl+<number>`, order), never by name, so a duplicate name is a cosmetic ambiguity, not a functional collision. Blocking it adds friction (an inline error state, extra validation code) for a case with no real downside. | Contrast with the *bad* pattern found in research: several tools validate too late (after a dialog already closed) or not at all, producing silent no-op renames — the fix here is to validate the one thing that matters (empty) inline and *before* commit, not to over-validate a case (duplicates) that isn't actually harmful. |
| Closing the last remaining window | Per the still-open question in requirements.md: recommend **auto-recreate a fresh blank window** rather than blocking the action. Blocking requires an interruptive dialog for a plausible action (a user closing everything to start fresh); auto-recreating matches the zero-disruption guarantee already promised for migrated v1 users (their layout becomes "Window 1" — closing it should degrade to the same empty state a first-run user would see, not an error). | Consistent with requirements' own migration philosophy: no window state should ever be an invalid/unrepresentable state requiring a blocking dialog. |
| Window whose panes all reference deleted sessions | Treat as a normal empty/broken pane state, unrelated to the window layer — the existing pane engine already needs to handle deleted-session leaf panes when their target session vanishes (a `PaneState` concern independent of windows). The window layer itself should not special-case this; the window tab should still show its name and switch normally, with the empty-state handling happening entirely inside `PaneSplitRenderer`. | This falls squarely in "no change to the pane-tiling engine's own behavior" from Scope > Out of Scope — the window layer must not grow special logic to compensate for a pane-level state it doesn't own. |
| Long window name overflowing a tab | Truncate with CSS `text-overflow: ellipsis` in a fixed-max-width tab, full name available via the `title` attribute (matches the existing `MobilePaneTabStrip` pattern, which already sets `title={label}` on each tab button) and/or on focus/hover as a tooltip. | Directly reuses an existing, already-implemented convention in this codebase rather than inventing a new one. |
| Long-press-to-rename vs. swipe-to-switch gesture conflict (mobile) | Distinguish by movement, not just duration: a touch that moves past a small threshold (a few px) before the long-press timer fires should cancel the rename affordance and fall through to swipe handling; a touch that stays stationary past the long-press threshold (e.g. 500ms) enters rename mode and should suppress any subsequent swipe on that same touch sequence. This is the standard mobile disambiguation pattern (long-press = stationary hold, swipe = directional movement) and keeps the two gestures mutually exclusive per touch sequence rather than racing. | Matches the general mobile UX precedent of keeping long-press (mode-switching / entering an edit or selection mode) and swipe (direct, immediate action) as gesture-exclusive within a single interaction, found consistently across mobile rename/delete pattern research. |

## 5. Jobs-to-be-done

**Functional job**: let a user park an entire multi-pane work context (splits, sizes, assigned sessions) and restore it exactly, instantly, without manually rebuilding it — the literal problem statement in requirements.md. The research on tab/context management (Tabs.do academic study, browser "workspace" features) converges on the same insight: the real friction isn't *volume* of open contexts, it's that ad hoc arrangements (nested pane splits reused across contexts) don't preserve a coherent, resumable "mental model" of the task — recovery time after a context switch is dominated by reconstructing that mental model, and an instantly-restorable saved arrangement collapses that recovery time from minutes to seconds. Windows are this project's answer to "give the mental model a container that survives being set aside."

**Emotional job**: a feeling of control and order over what would otherwise be an unbounded, ever-cramping pane tree — directly named in the problem statement ("panes very small once more than 2-3 are open"). Being able to name a window (`"reviewing PR #x"`) converts an anonymous pile of panes into a labeled, intentional workspace, which research on tab overload frames as the difference between tabs as "a mix of everything you've ever been working on" (anxiety-inducing) versus tabs that "represent coherent contexts" (calming, because the user can trust the container to hold its shape).

**Social/professional job**: the ability to "put away" a work context signals — to the user's own future self, primarily, since this is a single-user local tool — that a task is genuinely paused rather than abandoned or lost. This maps to the "black hole" failure mode identified in the Tabs.do research: users who close tabs to declutter often lose the *reminding* function those tabs served, so they end up either never closing anything (leading to the cramped-pane problem this project targets) or closing things and forgetting them. A named, switchable window is deliberately designed to avoid that failure mode: closing is not required to declutter, because switching away is just as available and just as recoverable as switching back.

## Summary of actionable recommendations

1. Ship "window" as the term (per existing requirements decision) but add a lightweight one-line onboarding hint for tmux-literate users, since the risk is a vocabulary-inversion (window nests inside session in tmux; here window sits above the app's own "session" concept) rather than an unfamiliar-word problem.
2. Reuse `MobilePaneTabStrip.tsx`'s existing `role="tablist"`/`role="tab"`/`aria-selected`/`title` conventions verbatim for the new window tab strip, as two independently-labelled `tablist` regions (`aria-label="Window switcher"` vs. the existing `"Pane switcher"`) — this satisfies both the ARIA requirement and the "keep the two tab rows distinguishable" rabbit hole in one move.
3. Use automatic tab activation (arrow-key focus = immediate switch) given the <100ms instant-switch NFR; match tap-target sizing to whatever the existing `mobileTabButton` already uses rather than deriving a new number, and verify it clears 44px (not just WCAG's 24px legal floor) given two stacked tab rows on a small viewport.
4. Resolve the "last window" open question as auto-recreate-blank rather than block, for consistency with the zero-disruption migration guarantee.
5. Validate renames by treating empty as cancel; allow duplicate names without a validation error, since windows are addressed by id/position, not name.
6. Disambiguate long-press-rename vs. swipe-switch by touch movement threshold, not timing alone.
