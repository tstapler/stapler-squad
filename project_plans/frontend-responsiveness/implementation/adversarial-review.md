Evidence labels: VERIFIED = file opened or command run in this worktree; INFERRED = reasoned.

## Blockers

- [ ] **B1. Epic 5 can spend the largest epic on a non-cause, and its success test cannot prove otherwise (Stories 5.1.1, 5.2.1, 5.5.1, 5.5.2, 1.1.4).** Requirements say the slot holder is unknown (only ~3 unary in flight while 160+ queued). The HAR shows 20 open `101` sockets, which suggests open WebSockets do not occupy the 6 slots. Three problems follow.
  1. Nothing gates 5.2/5.3/5.4 on the 1.1.4 finding. The dependency graph runs 1.1/1.2 -> 2.1 -> 5.1 and never branches on the slot-holder result.
  2. Story 5.5.1's AC ("flag ON ... `queuedOver1s` is 0 and status-0 is 0") also passes if Epic 2's volume cuts alone fixed the stall. It does not isolate WS as the cause. The flag-OFF run happens after Epic 2, but the plan compares OFF vs ON only, with no baseline from before Epic 2.
  3. Bootstrap hole (INFERRED): `/ws/unary` is an HTTP/1.1 upgrade that needs a free slot. During a stall the socket cannot open. The 250 ms budget then falls back to the same saturated HTTP pool. The `unary_over_ws` flag itself arrives via `GetFeatureFlags` over HTTP, one of the stalled calls.
  - Fix: add a go/no-go checkpoint after Story 2.1.x and 1.1.4. If E2 alone reaches `queuedOver1s == 0` on the fixture, Epic 5 is re-scoped or deferred, and the owner is asked once. Record the three-arm comparison (baseline, E2, E2+WS) in 5.5.1. State how the socket opens under saturation, for example by pre-opening it before the first RPC burst or with a test that opens it while 6 HTTP calls are pending. Remove the claim in the Epic 5 Goal that WS "removes the ~30 s stalls" until 1.1.4 supports it.

- [ ] **B3. `unary_over_ws_methods` cannot be delivered by the existing flag system, so the "reads-first" staged rollout has no implementation path (Story 5.4.1, Risk Control).** `FeatureFlagsContext.tsx` builds `Record<string, boolean>` (VERIFIED). ## Concerns

- [ ] **Metric definition `queuedOver1s` is not measurable as specified (Task 1.1.2a, Success Metric 1).** "`requestStart - startTime` proxy via `performance.now()` around the awaited fetch" measures total latency, not browser queue time. Blocked time is the Resource Timing delta `requestStart - fetchStart` (or `startTime`). Use `PerformanceObserver('resource')` entries, which also expose status-0 and failed entries by absence. A custom `fetch` wrapper alone cannot see queue time. A production-build absence guard (AC "`typeof window.__ssqPerf` is `"undefined"`") also conflicts with the e2e suite running against the embedded production build (INFERRED, since `tests/e2e/global-setup.ts` starts the real binary). Specify a runtime opt-in (URL param or localStorage key) that the e2e fixture sets, and drop the "absent in production" AC or scope it to "absent unless opted in".
- [ ] **Coalescing can return a pre-mutation read (Story 2.1.2).** A caller issuing `getVCSStatus`/`listFiles` after a write (commit, save, file-op) can join an in-flight read that started before the write completed and receive stale data. Add a rule that a read does not join a flight that started before the latest mutation for that session (epoch or generation counter), and add a test for it. Per ADR-002, `IdempotentMethodSet` is also the replay set, so any over-inclusion is also replayed.
- [ ] **`idempotency_level` does not exist in the proto (VERIFIED, `grep -c idempotency_level proto/session/v1/session.proto` returns 0).** Task 2.1.2a ("from proto idempotency_level where annotated") and ADR-002 ("unit-tested against the proto idempotency_level") are vacuous. Either add `option idempotency_level = NO_SIDE_EFFECTS` to the listed RPCs (a proto change, so `make proto-gen` and a registry touch) or drop the claim and keep an explicit table with a test that every listed method exists in the generated service descriptor.
- [ ] **Bounding the `fromWebSocket` queue risks regressing terminal streaming (Task 5.3.1d, Constraint "streaming must not regress").** The AC fails a stream with `ResourceExhausted` at a cap when the consumer stalls. Story 4.1.3 deliberately keeps hidden terminals' streams open for K windows. A backgrounded tab throttles consumers, so legitimate output bursts can end live terminals. This is also scope drift from Epic 5's unary goal. Make it a separate flagged change with a cap sized from measured burst data, or defer it. Nothing in the plan reconciles it with 4.1.3.
- [ ] **Task ordering conflict on the shared vectors/test file (Waves C, Tasks 5.2.1a / 5.3.1a).** `ws_unary_frame_test.go` is created in 5.2.1a and edited in 5.3.1a, yet the plan runs 5.2.1 and 5.3.1 "in parallel". Create the vectors JSON and the Go/TS test stubs first in one task, or sequence 5.3.1a after 5.2.1a. `lib/api/transport.ts` is also touched by 1.1.2a, 2.1.1a, 2.1.2b and 5.4.1b without a named serialization, unlike `SessionDetailView.tsx`.
- [ ] **Window-switch metric holds only inside the keep-alive set (Story 4.1.2/4.1.4, Success Metric 3).** K=3, so the first visit to each window and any window evicted by the LRU still remount at 0.6-1.8 s. The requirements say "3+ windows". The AC and `4.1.4b` only measure a 3-window fixture after warm visits, and the end mark is "double-rAF after commit", which is not "interactive" (fit, focus, first terminal paint). Add a cold-switch scenario with a stated target or an explicit "cold switch is out of metric" statement, and define the end mark to include fit/focus. Also state the throttle used for the baseline versus the 150 ms target (baseline 0.6-1.8 s was unthrottled on empty windows; the spec uses 4x throttle on 20 sessions).
- [ ] **No numeric acceptance for two success metrics (Stories 2.1.3, 2.1.5, 1.1.3).** `LogClientEvents` "56 per 16 s toward 1 per flush interval" and `ListProgramsConfig` "batched/deduped" are covered by Jest call-count tests but not by the e2e spec or the 7.1.3 blocking subset. Add per-method request-count assertions to the perf spec, for example `ListProgramsConfig <= 1` and `LogClientEvents <= ceil(duration/5 s) + 1`.
- [ ] **Hard-load metric can be inflated by the new cache (Story 6.1.2, Success Metric 5).** The `sessionStorage` snapshot survives a same-tab hard reload, so a "hard load" measurement could pass on cache while the genuine cold load stays at 3.4 s. State that the perf spec clears storage for the cold scenario and report cold and warm separately. A cold-load long-task total under 1 s depends on progressive render, which Epic 6 describes only as "deferred off-screen cards".
- [ ] **Duplication gates for the Go bridge (Story 5.2.1).** `ws_unary_bridge.go` will resemble `ws_stream_bridge.go` (upgrade, read loop, `CheckOrigin`). The `dupl` gate is blocking on new code. Plan an extracted shared upgrader/read-loop helper in 5.2.1b rather than copying. For jscpd, `web-app/.jscpd.json` has a 0.14% threshold and the plan adds many heavily-mocked test files (transport, policy, fan-out). Add `make ready-duplication-gate-web` as a step in the epic exit criteria, not only in 6.1.1.
- [ ] **Kill-switch latency claim is overstated (Risk Control).** "Effective on the next call" conflicts with ADR-002's own "flags are re-read every 30 s". State "within one flag refresh (<= 30 s) or immediately via the circuit breaker/force-HTTP debug switch", and name where the immediate local override lives (localStorage override read by `WsUnaryPolicy`).
- [ ] **Task granularity.** Task 4.1.3c touches five unrelated files (two polling hooks, `XtermTerminal`, `webglBudget`) and carries three ACs (polling gating, WebGL eviction, refit). Split into polling gating vs terminal/WebGL. Tasks 2.1.1b and 2.1.1c migrate ~37 files in two "M" tasks. The second has no file list ("remaining grep output"), so it is not verifiable until the grep is run. Pin the file list into the plan or require the codemod as a first task with a dry-run count.
- [ ] **Prefetch under the dual build (Task 6.1.3a).** `lib/nav/prefetch.ts` "requests the route chunk" but the facade design exists because the build is moving off Next. Specify how `prefetch` maps in `impl.next` vs `impl.memory`/bun builds (and that it is a no-op where chunks are not split), otherwise the Next-only path leaks past `@/lib/nav`.
- [ ] **Estimate table sum does not match its stated total.** Recounted from the 29 story rows: 8.91M CU (not "about 8.5M"), x1.5 = about 13.4M (not 12.8M). Still inside the Large 3-15M band, but the overrun checkpoint ("25% over table value") is anchored on the wrong total. Estimates are correctly expressed in token/CU classes and agent waves with named wall-clock blockers; no hours or days appear (VERIFIED by reading).
