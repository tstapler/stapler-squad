# Adversarial Review (round 2): frontend-responsiveness

**Date**: 2026-10-26
**Verdict**: BLOCKED (3 blockers, 10 concerns, 6 minors)

Method: read `plan.md`, `requirements.md`, ADR-001..003 only (no prior review files). Cross-references checked by script/Read against the worktree. The owner decision to build unary-over-WebSocket is respected; nothing below recommends dropping it.

## Blockers

- [ ] **B1. Story 5.2.1 oversize-frame AC is unimplementable as written.** AC: "Given a 300 KiB REQUEST frame ... the socket answers `resource_exhausted` and stays open", enforced by `conn.SetReadLimit` (also ADR-001). In the repo's gorilla/websocket (`v1.5.4-0.20250319132907-e064f32e3674`, `conn.go:933-935`) exceeding the read limit sends close 1009 and returns `ErrReadLimit`; the connection is dead afterwards. No `SetReadLimit` is used anywhere in `server/` today, so there is no precedent to lean on. Fix: either a hard `SetReadLimit` slightly above 256 KiB that closes 1009 (client policy guarantees it is never hit; AC becomes "closes 1009"), or a soft per-message size check after read with a much higher hard limit, answered `resource_exhausted` while the socket stays open. Amend ADR-001 and the AC/test accordingly.

- [ ] **B2. Feature flags are not defined where the plan says; three new flags have no registration task.** Plan (Risk Control, Task 5.4.1b, Task 4.1.2b, Story 2.1.2) says each flag is "added in `lib/features/features/*`". That directory is the RPC-to-feature registry (`web-app/src/lib/features/features/flags.ts` holds the `get-feature-flags` / `update-feature-flag` RPC rows, not flag definitions). Flags are server-defined in `knownFeatureFlags` (`server/services/feature_flag_service.go:207-214`, each with `defaultValue`/description), and `server/services/config_surface_helpers_test.go:63-64` iterates every entry (a new flag needs the proof/reader that harness expects). Consequences: (a) `request_coalescing` (default ON), `unary_over_ws`, `window_keep_alive` cannot exist or have the stated defaults until a Go task adds them; no story lists `feature_flag_service.go`; Story 2.1.2 has no flag task at all; (b) three stories (2.1.2b, 4.1.2b, 5.4.1b) would edit the same Go file in different waves; (c) the pre-load-default and "flip the default" steps (Story 5.5.2) have no file to change. Fix: add one early task (before Wave B) registering all three flags with defaults, update every story's Files line, and make Story 5.5.2 list the Go default change.

- [ ] **B3. Default-on criterion 3 (head-of-line) cannot be executed, and criteria 4-5 have no measurement mechanism (Story 5.5.1, Task 5.5.1c, Task 2.1.2a).** Criterion 3 requires "a 5 MiB `GetFileContent` in flight" over WS. `GetFileContent` is not in the `coalescible` list (Task 2.1.2a), `wsEligible` is defined as a subset of `coalescible`, and the plan never enumerates `wsEligible` or the Go `wsUnaryAllowed` contents at all (only examples: `GetVCSStatus`, `getSessionDiff`). So no large-response method rides the socket and the probe either cannot run or passes vacuously; ADR-003 option C would never be triggered by evidence. Criterion 5 ("terminal stream message latency p95 within +10% of B") has no instrumented source, clock, or story that builds it; Task 5.5.1c is a one-line `(S)`. Criterion 4's denominator ("eligible calls") is undefined for calls skipped by the 250 ms open rule or breaker at boot. Fix: enumerate the `wsEligible`/`wsUnaryAllowed` set in Task 2.1.2a and the shared JSON fixture; include one genuinely large read (for example `GetFileContent` with a size cap, or `GetSessionDiff` on a large diff) or define the HOL probe on `ListFiles`/`GetSessionDiff`; specify how terminal latency is measured (for example an echo-marker round trip timed in the page) and the fallback-rate denominator, with a minimum sample size.

## Concerns

- [ ] **C1. Wave A is not executable as written.** Story 1.1.3 (spec asserts `ssq:window-switch`, `peakInFlight`, `queuedOver1s`, sets the `ssq:perf` opt-in), Story 1.1.4 (extends the spec, uses the gauge) and Task 1.1.1b (capture needs the `__ssqPerf` opt-in) all depend on Story 1.1.2, but none has a `Depends on` line and Wave A runs them in parallel. The Wave A note names the wrong conflict ("1.1.3 and 1.1.2 share `lib/perf/`"); the real shared-file pair is 1.1.1a and 1.1.2a, both creating/editing `lib/perf/perfDebug.ts`. Add `Depends on: 1.1.2` to 1.1.3/1.1.4 and serialize 1.1.1a before 1.1.2a (or split the file).
- [ ] **C2. Other parallel/prerequisite gaps.** (a) `components/sessions/TerminalOutput.tsx` is in the pinned batch c (Task 2.1.1d) and in Task 2.1.3b, both Wave B parallel. (b) Task 2.1.2b needs the flag read path from Task 2.1.4a (`flagStore`) for `request_coalescing` but Wave B runs 2.1.2 || 2.1.4. (c) Story 4.1.4 says "independent of 4.1.2" yet Task 4.1.4b edits `WindowKeepAliveHost.tsx`, which Task 4.1.2a creates, and Wave D runs them in parallel. (d) Story 6.1.3b calls `announce()` (new in Task 4.1.4a) with no dependency. (e) Story 4.1.5 needs the 4.1.3 gating (its AC says polling/keys are off on `/backlog`) but declares only 4.1.2/1.1.3. (f) Task 4.1.3c edits `useSessionVcs`/`useVcsStatus`/`useWorkflows`/`useBufferFreshness` but depends only on 2.1.6c, not 2.1.6a/d. (g) `app/layout.tsx`/`RootShell` is claimed by Task 5.4.1c, 4.1.5a and 6.1.3b across parallel waves with "(or RootShell)" hedging.
- [ ] **C3. Go test placement cannot reach the things under test.** `localChain()`, `remoteChain()` and `guardedProcedures` are unexported in `package server` (`server/guarded_procedures.go`, `server/server.go:1941`); the cited precedent `server/streaming_chain_test.go` is also `package server`. Tasks 5.1.1a, 5.2.1d and 5.5.1a put the spike, the "no `guardedProcedures` key in `wsUnaryAllowed`" test and the chain-parity tests under `server/services/`, which cannot call them. Move those tests to `server/` (with the bridge taking an injected `http.Handler` dispatcher so `services` tests use a fake). Also Task 5.2.1b's Files omit `server/guarded_procedures.go`, where `localChain` must be split to expose the "minus Compress/Logging" handler (today it returns the fully wrapped chain, `guarded_procedures.go:97-117`).
- [ ] **C4. Decision gate serializes an unconditional build behind an owner wall-clock blocker.** Story 5.1.2 declares that no row cancels or descopes Epic 5, yet 5.2.1/5.3.1 sit after it, and it needs Task 1.1.4b (owner DevTools-closed re-capture). The gate only changes default/priority-socket/early-open timing. Let 5.2.1, 5.3.1 and 5.4.1a start after 5.1.1b; gate only Task 5.4.1c ordering, 5.5.1 and the default flip on 5.1.2.
- [ ] **C5. Success-metric coverage gaps.** (a) Metric 1 ("zero unary requests blocked > 1 s, no status-0") has no standing numeric assertion in Epic 2: Story 1.1.3 asserts only per-method counts; `queuedOver1s`/status-0 appear numerically only in the 5.1.2 table, 5.5.1 criterion 1 (arm C) and the HAR in 7.1.4; Story 7.1.3's blocking subset lists `queuedOver1s` with no threshold. If arm C fails criterion 1 the flag stays OFF and the metric has no remediation story. (b) Metric 3 (switch < 150 ms, long tasks < 50 ms) is met only with `window_keep_alive` ON (default OFF), and no story defines criteria or a task to flip it (Story 5.5.2 covers only `unary_over_ws`); Story 7.1.4 does not state flag states for the final capture. (c) Task 4.1.4c measures retained switches at 4x CPU throttle (stricter than the unthrottled requirement) and explicitly excludes cold switches, so "no task > 100 ms during switching" is unasserted for cold. State the flag states, add a `window_keep_alive` flip story with numbers, and add a numeric `queuedOver1s == 0`/status-0 `== 0` assertion to the spec after Epic 2.
- [ ] **C6. Coalescer can return a pre-write read for non-session reads.** The write-generation guard is per `sessionId` only (Story 2.1.2). `GetFeatureFlags`, `ListProgramsConfig`, `ListWorkflows`, `ListShells` carry no session id, so `UpdateFeatureFlag` followed by an in-flight-joining `getFeatureFlags` can return the stale value, contradicting Story 2.1.4's AC ("`setFlag` then read-back returns `true` immediately"; the existing provider also ignores responses older than a write via `minAcceptable`, `FeatureFlagsContext.tsx:100-110`). Add a global/method-family generation or let `setFlag` bypass coalescing.
- [ ] **C7. Interceptor/timeout placement for the WS path is unspecified.** Auth interceptor, `defaultTimeoutMs: 30_000` and rpcTiming live inside `createConnectTransport` (`lib/api/transport.ts:32-39`); a policy transport routing to `UnaryWsTransport` bypasses them. Story 5.4.1 covers auth redirect and rpcTiming only. State that coalescer, auth, rpcTiming and default timeout wrap the policy transport (outermost), and add an AC that WS calls carry the 30 s default deadline and are coalesced.
- [ ] **C8. Flag persistence edge cases.** (a) Story 2.1.4 persists last-known `request_coalescing`, but Risk Control fixes its pre-load default at ON; pick one. (b) `ssq:flag:unary_over_ws` is written "on every successful load" but not cleared if the flag disappears from the response, so a removed flag leaves the boot-time open permanently armed. (c) Boot-time open runs before login on an auth-protected listener; 401 upgrades count toward the 3-failure breaker (Task 5.4.1c item 4 covers timeouts only). Specify clearing and 401 handling.
- [ ] **C9. Three-arm comparability.** Arm A is a baseline committed before Epic 2; arms B/C run later, possibly on a different machine/CI runner or spec version. Re-run arm A from tag `perf-baseline` in the same session as B/C, and define a noise rule for criterion 2's 20% threshold (for example require the 20% to exceed the run-to-run MAD of the ≥ 5 kept runs).
- [ ] **C10. `perf` Playwright project needs more than `testMatch`.** `tests/e2e/playwright.config.ts` sets global `timeout: 30000` (line ~47). A 5-run, 4x-throttled, 16 s-load spec will exceed it; the project also needs `workers: 1` and single-project execution for stable timings. Also, `testIgnore` is needed only on `chromium` and `chromium-dom` (every other project already has a narrow `testMatch`, verified), so Task 1.1.3d's "every other project" is over-specified. Seeding "20 sessions" with real tmux in CI is an unpriced feasibility risk.
- [ ] **C11. Story 4.1.4 "ships unflagged" contradicts Story 4.1.2.** The `tabpanel` wrappers live in `WindowKeepAliveHost`, and Story 4.1.2 says flag OFF "renders exactly the current single container (behavior unchanged)". With the flag OFF no `tabpanel` exists, so `aria-controls` (4.1.4 AC) points nowhere. Put the tabpanel wrapper in `app/page.tsx` outside the flag, or scope the AC to flag ON.

## Minors

- Wrong line cites: `lib/hooks/useWatchBacklogItems.ts:56` is an import line (the hook is at `:128`); `useWindowUrlSync.ts:56-57` is a `useEffect` (the `currentWindowId` resolution is at `:55`).
- `web-app/src/lib/api/transport.test.ts` does not exist; Task 2.1.1a lists it as if it did (Task 1.1.2a does not create it either).
- Frame-size boundary: the client sends over WS when the serialized body is ≤ 256 KiB, but the server limit applies to the whole frame (body + method + meta header), so a body just under 256 KiB overflows; threshold on frame size.
- Story 5.2.1 AC "RESPONSE bytes equal the HTTP call's": the shared HTTP transport is JSON by default (no `useBinaryFormat`, `transport.ts:32-39`) while the WS path is raw proto; the comparison must use a proto-format HTTP call.
- ADRs are all "Proposed" while the plan header says "Ready for implementation"; acceptable if the 5.1.1 spike gate is respected, but say so.
- Perf target at 4x throttle for the 150 ms switch is stricter than the requirement and may be unattainable on shared CI; keep advisory as stated.
