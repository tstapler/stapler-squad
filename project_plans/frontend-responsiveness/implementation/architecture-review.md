## Blockers

- [ ] **Story 5.2.1 / 5.4.1 / ADR-002 §5 (unary-over-WS skips per-procedure guards)** — VERIFIED: `HostGuard` does wrap WS upgrades on the local chain (`server/guarded_procedures.go:91-113`, `server/middleware/hostguard.go:25`), which answers unresolved question "does HostGuard wrap WS routes" (plan Unresolved Q5 / Story 5.1.1) — yes, for `:8543`; the remote chain has no HostGuard (`server/server.go:1941-1950`, auth is its boundary). But host/origin parity at upgrade is only half the security surface. On `:8543` the second layer is `LocalWriteGuard(guardedProcedures)` (`guarded_procedures.go:111`), keyed by the **request path** of each procedure (`probeProcedurePath`, `writeFileProcedurePath`, prune, `UpdateFeatureFlag`, `ReplyToPendingQuestion`, the Backlog stage/gate writes; map at `:42-70`). A WS upgrade to `/ws/unary` has one path, so none of those guards would ever fire for a call multiplexed inside it. The same holds for `withFileBodyLimits` (`server/server.go:515`, per-procedure body caps; WriteFile cap 1.5 MiB vs the ADR's 256 KiB max frame) and the per-call `Origin` CSRF check in auth (`server/auth/handlers.go:407-420`, which only sees the GET upgrade). The existing `StreamingWSBridge` does not set a precedent here: it builds a fresh `http.NewRequestWithContext("POST", rpcPath, ...)` and copies only `Authorization`, `Cookie`, `Connect-Protocol-Version` (`ws_stream_bridge.go:78-92`), so the synthesized request has empty `Host`, `Origin`, `RemoteAddr`; `services.WithRequestHost` (`server/server.go:514`, `capture_tap_service.go:34`) and the request-record middleware (`capture_tap_service.go:62-76`, reads `r.Host` and `Origin`) and any in-handler local-caller check would see empty values. ADR-002 §5 ("same middleware function the HTTP mux uses") and Story 5.2.1's "Host/Origin matrix" test do not cover this. **Remediation (change plan and ADR-002 before 5.2.1 starts):**
  1. Bridge dispatches by re-entering the **listener's outer handler** (the handler returned by `localChain()` / `remoteChain()` minus Compress/Logging, i.e. stamp -> HostGuard -> auth|LocalWriteGuard -> mux), not the mux or an individual service handler. The bridge is registered on the shared mux, so inject the per-listener dispatcher lazily in `Start()`/`StartRemote()` and select it from `RequestRecordFrom(ctx).Listener`.
  2. Synthesize each request with the **upgrade request's** `Host`, `RemoteAddr`, `Origin`, `Cookie`, `Authorization`, `User-Agent`, `X-Forwarded-*`/proxy headers (so `HasProxyHeader` and rebinding verdicts agree), `Content-Type: application/proto`, `Accept-Encoding: identity`, `Connect-Timeout-Ms` from meta, and path `/api/<pkg.Service>/<Method>`.
  3. Add a server-side **deny set**: until a method is explicitly listed in a Go-side `wsUnaryAllowed` table (reads only, mirrors `IdempotentMethodSet`), the bridge answers ERROR `permission_denied`. Never trust the client-delivered `unary_over_ws_methods` flag as the only gate. Add a test that every key of `guardedProcedures` is rejected over WS (or provably guarded) and one that fails if a new `guardedProcedures` entry appears in `wsUnaryAllowed`.
  4. Tests in 5.2.1d must run the bridge over a real `localChain()`/`remoteChain()` (as `server/streaming_chain_test.go:161` already does for streams), covering: foreign Host -> 403, loopback Origin on another port -> 403, a guarded procedure -> same verdict as HTTP, `/ws/unary` unauthenticated on remote chain -> 401 at upgrade and per-request after cookie expiry.
  Note: per-request re-validation of expiry (ADR-002 §5) comes for free with this design, because each REQUEST traverses the auth wrapper; without it the plan has no concrete mechanism for it.

- [ ] **Story 6.1.1 / 6.1.2 / 6.1.3 (Backlog refactor boundary ignores the real data layer)** — VERIFIED: `/backlog` does not issue a `listBacklog` unary RPC for its list. It subscribes via `useWatchBacklogItems()` (`app/backlog/page.tsx:273`), which streams `WatchBacklogItems` over the WS watch transport (`lib/hooks/useWatchBacklogItems.ts:56`, `getWatchTransport()`) into a **global Redux store** (`lib/store/backlogItemsSlice.ts`, `upsertItem(item, isSnapshot)`), keeping `BacklogItem` proto-shaped and mapping to the domain shape in the hook (file header note 3). `listBacklogItems` exists only as a REST-fallback / refetch path (`useBacklogService.ts`). The plan's `useBacklogData()` with "each backlog RPC issued once", a new `CachedListSnapshot` in `sessionStorage` rendering "before any RPC completes and a revalidation `listBacklog` starts", and a nav-hover "snapshot warm-up RPC" would add a **second, parallel data layer** next to the watch stream and store: two sources of truth, a mapped-vs-proto shape mismatch the hook header already documents as a past blocker, and a warm-up RPC that the stream makes redundant. It also does not establish what the 3.4 s hard-load long-task cost is made of (render of N cards vs mapping vs effects); no story measures it before 6.1.2 commits to a fix. **Remediation:**
  1. Add a measurement task to Epic 1 (or first task of 6.1.1): CPU-profile `/backlog` hard load and a `/` -> `/backlog` -> `/` return, split into store-hydration, mapping, render, and the ~20 effects. Decide 6.1.2's scope from that.
  2. Reword 6.1.1: `useBacklogData` wraps `useWatchBacklogItems` + selectors (list, filters, selection, connection state); it does **not** own a fetch. Classify the ~20 effects as stated, but the "each RPC once" assertion applies to `WatchBacklogItems` subscribe count and the REST fallback, not a new RPC.
  3. Reword 6.1.2: persistence is a **hydration of `backlogItemsSlice`** (serialize proto items with `toBinary`/`toJson`, versioned key, load into the slice with `isSnapshot=false`), and the stream's snapshot event is the revalidation. "Refreshing/out-of-date" derive from the existing `BacklogConnectionState` (`connecting|live|reconnecting|polling|stale`), not a new flag. State explicitly that return navigation already hits a warm global store (INFERRED; verify in the new measurement) so the snapshot helps hard load only.
  4. Reword 6.1.3: warm-up = ensure the watch subscription/store hydration starts on hover, exported from `lib/` (not from `app/backlog/`; see Concern C7), no extra unary call.
  5. Keep ordering: 2.1.1b edits `page.tsx:356-362` (the `rawClientRef` transport effect) in Wave B; 6.1.1a must not start until 2.1.1b is merged (plan already says this; make it a stated `Depends on`).

## Concerns

- [ ] **C1. Story 4.1.3 / Glossary `WindowActive` — `isActive` is "focused pane", not "visible"; gating polling on `isActive && windowActive` regresses visible unfocused panes.** VERIFIED: `SessionDetailView.isActive` doc is "Whether this is the focused pane" (`SessionDetailView.tsx:325-326`), `PaneSplitRenderer.tsx:395` passes `isActive={isFocused}`, and `useSessionVcs` already treats it as **cadence** (`ACTIVE_STATUS_POLL_MS` vs `INACTIVE_STATUS_POLL_MS`, `useSessionVcs.ts:186`), not on/off. The 4.1.3 AC "poll only when `isActive && windowActive`" would stop VCS/workflows/freshness polling for unfocused panes in the visible window. Recommendation: introduce two distinct props, `isFocused` (existing, cadence/keys) and `windowActive` (visibility; on/off for polling, observers, rAF, keydown). Polling = `windowActive ? (isFocused ? fast : slow) : off`. Keydown/shortcuts = `windowActive && isFocused`. Fix the glossary line and the 4.1.3 and 3.1.1 ACs accordingly. The same applies to Story 3.1.1b's "gate on `isActive`": `usePublishStackTopOffset` has an `enabled` param (`usePublishStackTopOffset.ts:14`) that should be fed `windowActive`, not focus, or the toast dock will track only the focused pane within a window (a behavior change nobody asked for).

- [ ] **C2. Ordering conflicts on `SessionDetailView.tsx` (1977 lines) — five stories edit it with no seam.** VERIFIED touch points: `:463-465` (`usePublishStackTopOffset`, 3.1.1b), `:493-495` hash-seeded `filesSelection` and `:1213` `FilesTab` (2.1.6c), `:665-676` window keydown (4.1.3b/d), `:634` `useShortcut(..., isActive)` (4.1.3d), plus `windowActive` prop plumbing (4.1.3b) and `useWorkflows`/VCS wiring (2.1.6a/d, 4.1.3c). Tech Debt Disposition says "Isolate via seam" but no seam task exists; per lens 4/item 13 a named seam must be a concrete task. Recommendation: (a) add **Task 2.1.0 (S)**, before any other SessionDetailView edit: add the optional `windowActive?: boolean` (default `true`) prop through `PaneSplitRenderer -> SessionDetail -> SessionDetailView` as a no-op, and extract `useSessionDetailActivity({isFocused, windowActive})` returning `{ pollMode, keysEnabled, measureEnabled }` in a new file; (b) fixed order: 2.1.0 -> 2.1.6c (FilesTab/hash) -> 3.1.1b (measurer, uses `measureEnabled`) -> 4.1.3b/c/d (flip the plumbed value, gate keydown, add tests); (c) move the `:665-676` keydown into a small `useReviewNavKeys(keysEnabled, ...)` hook in the same task so 4.1.3d is a test-only story. This also removes the plan's own "serialize against 3.1.1b and 4.1.3b" hand-wave.

- [ ] **C3. ADR-001 framing is inconsistent with how unary Connect handlers are invoked, and chunking is under-specified.** VERIFIED: the streaming bridge sets `Content-Type: application/connect+proto` and feeds envelope bytes (`ws_stream_bridge.go:94-98`), which is correct for **streaming** handlers. Unary Connect uses `application/proto` with a raw body (no 5-byte envelope), and errors come back as an HTTP status plus JSON body. ADR-001 puts a Connect envelope in the REQUEST/RESPONSE for unary and does not say the bridge must unwrap it and set `application/proto`. The spike (5.1.1) should decide; remediation is to drop the envelope for unary frames entirely (REQUEST body = method + meta + raw proto; RESPONSE = raw proto; ERROR = JSON from the recorder's status/body). Separately, the frame table has no continuation/FIN marker, yet the decision text says responses over 256 KiB "split into continuation envelopes... client reassembles" and 5.2.1 tests chunk interleaving. Add a `CHUNK` type (or a `more` flag byte) and a total-length field, add them to the shared conformance vectors (5.3.1a), and set `conn.SetReadLimit` on the server. Also state that requests larger than 256 KiB (WriteFile up to 1.5 MiB, `withFileBodyLimits`) are HTTP-only by policy (consistent with the read-only allowlist in Blocker 1). `ResponseRecorder`-style buffering means the full response is in memory before chunking; acceptable, but say so so nobody expects streaming semantics.

- [ ] **C4. Story 5.2.1 route and dispatch details.** Register at `/api/ws/unary`, not `/ws/unary`: `getApiBaseUrl()`-derived URLs, any dev proxy, and reverse proxies already special-case `/api` (the streaming bridges are all `/api/...`), and the SPA catch-all `/` (`server/server.go:1475`) means a mistyped path silently serves HTML. The bridge should also derive the `Connect-Timeout-Ms` header from meta and let connect-go apply the deadline, instead of a second `context.WithTimeout` (ADR-002 §4) that could disagree. Per-request contexts must derive from the upgrade `r.Context()` so shutdown (`connCtx`) cancels in-flight calls. The per-socket write path is correct as designed (single writer, gorilla requires it); add a ping/pong deadline so a dead tab does not hold 32 in-flight slots.

- [ ] **C5. Epic 4 does not survive Sessions <-> Backlog navigation.** VERIFIED: `WindowKeepAliveHost` is inserted at `app/page.tsx:633` inside `HomeContent`; a route change to `/backlog` unmounts `app/page.tsx` and every retained window with it. Requirements scope "faster Sessions<->Backlog return" and the problem statement ties window-switch and Backlog navigation together, and `/` load is the 15 s long-task case. The plan has no story that hoists the host/window state above the route boundary (root layout or AppShell) or otherwise makes return to `/` cheap (the terminal pool is already module-level, `TerminalPool.tsx`, so remount cost may be smaller than assumed; INFERRED, unmeasured). Recommendation: add to Story 1.1.3's scenarios a `/` -> `/backlog` -> `/` timing, and add a decision story in Epic 4: either hoist the host to the layout (then `app/page.tsx` renders null and `sessionDetailRef` focus handling at `page.tsx:107,531` must move), or explicitly accept and document that keep-alive covers intra-`/` window switches only and mark the requirement partially met.

- [ ] **C6. `app/page.tsx` seam is thinner than stated.** `sessionDetailRef` (`page.tsx:78,107,531,626`) is a single ref focused from several effects, `paneDispatch` is bound to `currentWindow.id` (`:164-166`), `paneSessions` and `externalAssignSession` are single-window values. Rendering up to 3 containers needs per-window `paneState`, a per-window dispatch (`dispatchPane(windowId, action)` already exists), per-window refs, and the external-assign counter delivered only to the active container (or hidden containers consume it on a stale pane and steal assignments). Story 4.1.2 names only `app/page.tsx:633`; list these and make "externalAssign only to active" an AC, otherwise 4.1.3a's gating will mask but not fix it. Also `usePaneShortcuts(state, dispatch, containerRef)` (`PaneTilingContainer.tsx:143`) is a second ungated per-container hook not named in the plan (only the picker keydown at `:188` is); `ShortcutRegistry.register` overwrites on duplicate id and the first unmount's cleanup **deletes the surviving registration** (`shortcutRegistry.ts:95-100`), so two windows registering the same id with `enabled=windowActive` will lose the active window's shortcut when a hidden one unmounts or re-registers. Add this to 4.1.3d as a bug to fix (id namespacing or ref-counted/owner-token cleanup), not just a test.

- [ ] **C7. Layering: nav prefetch must not import from `app/backlog/`.** Story 6.1.3 puts the warm-up in `lib/nav/prefetch.ts` and the data hook in `app/backlog/useBacklogData.ts`. Dependency must point from `app/` to `lib/`. Put the store hydration/warm function in `lib/backlog/` (next to `sortGroup`, `status`) and have both import it.

- [ ] **C8. Coalescing/caching shares one `IdempotentMethodSet` for three purposes with different safety bars (Domain Glossary, ADR-002 §3).** Coalescing identical in-flight reads and replaying once over HTTP are safe for read RPCs; **TTL caching** of `GetVCSStatus`/`ListFiles` results is not (file edits, git ops). The plan caches only flags, programs, and capabilities, which is fine, but a shared table invites someone to enable caching by adding a method. Split into `coalescible`, `replayable`, `cacheable` columns with tests. `session.proto:653` already shows an RPC deliberately not `NO_SIDE_EFFECTS` even though it looks read-like, so deriving from `idempotency_level` alone is not sufficient; keep the explicit list authoritative and test it against the proto annotations only as a subset check.

- [ ] **C9. Story 2.1.1 is a 37-file mechanical migration with behavioral options.** The codemod must handle callers that pass a custom `baseUrl`, `useBinaryFormat`, interceptors, or fetch (e.g. `useShells` builds a watch transport for unary, plan AC 3). `getConnectTransport({timeoutMs})` memoized by options is fine; add an AC that no caller loses its `rpcTiming` interceptor, and that the ESLint rule (7.1.1) lands in the **same PR** as the last migration batch to stop regrowth between waves, not in Wave E.

- [ ] **C10. Observability: `ws_unary_fallback_total{reason}` is client-originated and the plan gives no server transport for it.** 5.2.1d says "from a client-reported header or log line". A server cannot see calls that never reached it (the common fallback reason: socket not OPEN in 250 ms). Either expose the counter client-side only via the existing analytics `performance` events, or drop it from `/actuator` and say so.

- [ ] **C11. Unresolved-question ownership.** Unresolved Q5 (HostGuard wrapping WS) is answerable now (see Blocker 1) and should be closed in the plan; Q1 (14 identical `GetFeatureFlags`) blocks 2.1.4 but 2.1.2's coalescing would mask a duplicate-provider cause: have 1.1.1's findings gate **removal** of the cause, with the coalescer treated as defense in depth, not the fix (the plan's AC says this; keep it).
