# ADR-002: Dispatch, fallback, retry, replay and auth semantics for unary-over-WebSocket

**Status**: Accepted 2026-10-26 by the Story 5.1.1 spike (`research/ws-unary-seams.md`, `server/ws_unary_spike_test.go`; no amendment). Prior history: Proposed (amended in repairs 2026-10-26 pass 1, pass 2, the Phase 4 patch and the remote-listener owner decision reversal, which replaces the remote 403 refusal in items 4 and 7 and adds item 11; the Story 5.1.1 spike records Accepted)
**Date**: 2026-10-26
**Decider**: tstapler

## Context
Over HTTP, connect-go gives timeouts, cancellation, status codes and `createAuthInterceptor` 401 handling for free (`web-app/src/lib/api/transport.ts`). A WebSocket has no per-call HTTP status, auth is checked once at upgrade, and an unbounded reader queue exists today (`fromWebSocket`, `watch-ws-transport.ts`; instrumented, not bounded, in Story 5.3.2).

Security surface on `:8543` has two layers (VERIFIED): HostGuard, which covers every route including WebSocket upgrades (`server/guarded_procedures.go:91-113`), and `LocalWriteGuard(guardedProcedures)` (installed when no auth middleware is configured; with auth, auth is the boundary, `server/guarded_procedures.go:103-113`), keyed by each procedure's **request path** (`guarded_procedures.go:42-70`; probe, write-file, prune, `UpdateFeatureFlag`, `ReplyToPendingQuestion`, Backlog stage/gate writes), plus per-procedure body caps (`withFileBodyLimits`, `server/server.go:515`) and the per-call `Origin` check in auth (`server/auth/handlers.go:407-420`). A single upgrade path would bypass every path-keyed guard. The existing streaming bridge is not a precedent: it builds a fresh `POST` request and copies only `Authorization`, `Cookie`, `Connect-Protocol-Version` (`ws_stream_bridge.go:78-92`), leaving `Host`, `Origin` and `RemoteAddr` empty. The remote chain has no HostGuard (`server/server.go:1941`); auth is its boundary, and the unary route is served there too (item 7).

## Decision
1. **Dispatch by chain re-entry.** The bridge at `/api/ws/unary` dispatches each REQUEST by re-entering the **listener's outer handler** (`localChain()`/`remoteChain()` minus Compress/Logging/CORS: stamp -> HostGuard -> auth|`LocalWriteGuard` -> mux), injected lazily in `Start()`/`StartRemote()` and selected via `RequestRecordFrom(ctx).Listener`. Each synthesized request carries the **upgrade request's** `Host`, `RemoteAddr`, `Origin`, `Cookie`, `Authorization`, `User-Agent` and `X-Forwarded-*`/proxy headers, `Content-Type: application/proto`, `Accept-Encoding: identity`, `Connect-Timeout-Ms` from meta, and path `/api/<pkg.Service>/<Method>`. Per-request auth expiry, guards and body limits therefore come for free because every REQUEST traverses the same wrappers. **Header provenance**: `Host`, `RemoteAddr`, `Origin`, `Cookie`, `Authorization`, `User-Agent`, `Forwarded`, `X-Forwarded-*` are copied from the upgrade request only; REQUEST `meta.headers` is restricted to the ADR-001 allowlist and can never set or override any of them (a parity test sends meta carrying `Origin: http://evil.example` and expects ERROR `invalid_argument`). **Plumbing**: `localChainWith`/`remoteChain` (`package server`) are split so the stamp -> (HostGuard) -> (auth | `LocalWriteGuard`) -> mux composition is exposed as a per-listener dispatcher (Compress, Logging and CORS stay only on the HTTP outer chain); `Start()`/`StartRemote()` register the dispatcher by listener name; an unset dispatcher fails closed (ERROR `unavailable`), never falls back to the raw mux.
2. **Server deny-by-default allowlist.** The Go-side compiled `wsUnaryAllowed` table (reads only) is the authority; any other method gets ERROR `permission_denied` (`ws_method_not_allowed`). Tests: every key of `guardedProcedures` is rejected over WS, and the build fails if a `guardedProcedures` key appears in `wsUnaryAllowed`. A client-delivered setting is never the only gate.
3. **Flag and method eligibility.** Feature flags are `Record<string, boolean>` (`FeatureFlagsContext.tsx`), so a per-method flag (`unary_over_ws_methods`) cannot exist. The design is: one master boolean `unary_over_ws` (default OFF; plus the remote-origin sub-flag `unary_over_ws_remote`, item 11) + the static client `wsEligible` column of `IdempotentMethodTable` (a subset of `wsUnaryAllowed`, enforced by a shared JSON fixture and tests in both languages) + a per-session denylist populated when the server answers `ws_method_not_allowed`. Widening eligibility is a code PR. Pre-load behavior: `unary_over_ws` = persisted last-known value else OFF; `request_coalescing` default ON. `GetFeatureFlags` is never `wsEligible`, so the flag fetch does not depend on the socket.
4. **Fallback to HTTP.** The 250 ms rule is decided **once per connect attempt**, not per call: while the socket has been CONNECTING for more than 250 ms every call goes to HTTP immediately until the socket is OPEN (no call pays 250 ms twice); calls arriving in the first 250 ms wait at most the remainder of that window. After 3 consecutive socket failures the transport enters HTTP-only mode for 60 s (circuit breaker), then probes once. Bodies over 256 KiB always use HTTP. The remote origin (`https:`, already HTTP/2) is **not** excluded (owner decision 2026-10-26); it is gated per origin by the `unary_over_ws_remote` sub-flag (item 11).
5. **Retry/replay.** In-flight calls on a dropped socket fail with `Code.Unavailable`. A call is replayed once over HTTP only if its method's `replayable` column is true. The table is an **explicit, hand-maintained list**; `idempotency_level` is absent from `proto/session/v1/session.proto` (VERIFIED, `grep -c idempotency_level` = 0), so it cannot be derived from the proto. A test asserts every listed method exists in the generated service descriptor and that `replayable`/`wsEligible` are subsets of `coalescible`. `coalescible`, `replayable`, `wsEligible` and the TTL `cacheable` list are separate columns so adding a method to one purpose never enables another. Mutations are never replayed automatically.
6. **Deadlines.** `timeoutMs` travels in REQUEST meta and becomes `Connect-Timeout-Ms`; connect-go applies the deadline (no second `context.WithTimeout`). The client also enforces locally and sends CANCEL on abort/timeout. Per-request contexts derive from the upgrade `r.Context()` so shutdown cancels in-flight calls.
7. **Auth and origin.** On the local listener `CheckOrigin` is `isAllowedOrigin` (`server/services/connectrpc_websocket.go:104-120`), which accepts any HTTPS origin and any loopback origin. On `:8543` that leniency is covered because HostGuard (`server/middleware/hostguard.go:37-42`) rejects any Origin that is not loopback, allow-listed or same-origin with Host before the upgrade handler runs (VERIFIED). The remote chain has no HostGuard (`server/server.go:1941-1948`), and the owner decided on 2026-10-26 that the remote listener is served in the first release (this **reverses** the earlier refusal with 403 `ws_unary_remote_disabled`; that marker no longer exists). The unary route therefore does **not** rely on `isAllowedOrigin` on remote. The origin check is per listener (`wsUnaryOriginPolicy`, selected from `RequestRecordFrom(ctx).Listener`): **local** keeps HostGuard plus the loopback rule; **remote** requires all of (a) an `Origin` header (a missing Origin is accepted only for a non-browser client presenting `Authorization: Bearer` and no `Cookie`), (b) scheme `https`, (c) the origin equals, case-insensitively with the default port normalized, an entry of the configured set `GetOrigins()` (remote startup adds `https://<rpID>:<port>`, `https://<hostname>:<port>` and `https://localhost:<port>`, `main.go:1604-1626`) **or** the request's own `Host` with `Host`'s hostname in `GetHostnames()` (same-origin, minus DNS-rebound names), (d) no wildcard or suffix matching. The cookie is `Secure; SameSite=Strict` (`server/auth/handlers.go:290-291`), which stops a cross-site handshake but is site-scoped, so a same-site origin on another port or sibling host still sends it (INFERRED from the SameSite definition); the Origin rule is the primary CSWSH control. **Authentication before any dispatch**: `middleware.Auth` answers 401 to an unauthenticated upgrade before the bridge runs (`server/middleware/auth.go:80-92`), the bridge additionally refuses the remote upgrade unless `RequestRecordFrom(ctx).AuthMode == AuthModeRequired` (403 `ws_unary_auth_required`; this closes the nil-`authMW` posture, `server/server.go:1938-1940`), and **every REQUEST re-runs auth** through the remote dispatcher with the upgrade request's credentials, so an expired or revoked session (`ValidateAuthSession` deletes expired tokens on each call, `server/auth/session.go:195-208`) yields ERROR `unauthenticated` for that request while the socket stays open; this is not a socket failure and never counts toward the breaker. **No credential in the URL**: the route accepts no query string (400 `ws_unary_query_forbidden`), the client builds the URL without query or fragment, no `Sec-WebSocket-Protocol` is accepted, and a token in the query never authenticates (the auth middleware does not read it). Tests: T-CSWSH-1..4, T-TOKEN-1, T-AUTH-1, T-EXP-1 (plan Task 5.2.1g). Auth sessions have a fixed TTL: `SetCookie` appears only in the login handlers (`server/auth/handlers.go:284,378`, `server/auth/localtoken.go:136`), not in the auth middleware (grep, VERIFIED), so dropping `Set-Cookie` from synthesized responses loses no sliding refresh. The Host/Origin matrix test runs over a real `localChain()` and `remoteChain()` (as `server/streaming_chain_test.go:161` does for streams). A new client stage maps ERROR `unauthenticated` to the same login redirect as `createAuthInterceptor`. A browser `WebSocket` exposes no HTTP status for a rejected handshake (INFERRED from the WHATWG API), so the client cannot read a 401 or a 403 off the upgrade: expiry after the socket opened arrives as ERROR `unauthenticated` (redirect, no breaker count, park WS), and a pre-login boot-time open that fails while an HTTP 401 has been seen in the page life does not count toward the breaker (plan Story 5.4.1). **Client interceptor placement**: `UnaryWsTransport.unary` runs through `runUnaryCall` from `@connectrpc/connect/protocol` (exported in the installed `@connectrpc/connect` 2.1.1, `dist/esm/protocol/index.d.ts:7`), called with an **empty** interceptor list (it supplies deadline derivation, abort/CANCEL wiring and error normalization only). The auth interceptor, the 30 s `DEFAULT_RPC_TIMEOUT_MS`, the rpc timing interceptor, the priority interceptor and the coalescing interceptor all wrap the policy transport **once, outermost**, and the inner HTTP `createConnectTransport` carries none of them, so no call is double-instrumented or double-authenticated (test: `rpc:<Method>` is emitted once per call on each path). (Today `getConnectTransport()` carries only auth and `defaultTimeoutMs`, `web-app/src/lib/api/transport.ts:32-39`; rpcTiming is wired only in `useShells.ts:59` and `useImportSessionService.ts:57`.)
8. **Backpressure and liveness.** Client send queue bounded (64 pending frames / 1 MiB); overflow fails fast with `ResourceExhausted`. The in-flight cap per socket defaults to **6** (constant `wsUnaryMaxInFlight`, mirrored as `maxInFlight` in the shared fixture; the client keeps at most that many REQUESTs outstanding and the server answers `ResourceExhausted` beyond it). It starts at 6, not 32, because the ~30 s stalls may be server-side contention (`ListShells` runs a full session-list read per call, `session_service_shells.go:62-73`; server handler waits are not yet measured, Task 1.1.4c): multiplexing 6 browser slots into 32 concurrent handlers could make the server worse. Raising it needs Story 5.5.1 evidence that server handler p95 does not grow with the cap. **Liveness is symmetric**: the server enforces a ping/pong deadline so a dead tab does not hold slots, and the client sends PING every 10 s while any call is in flight (and on `visibilitychange`/`online`/wake) and treats a missing PONG within 5 s as a socket failure (close, reject in-flight `Unavailable`, replay `replayable` reads over HTTP, count toward the circuit breaker), so a half-open socket after laptop sleep or a VPN drop does not recreate the 30 s stall on the new transport. A `replayable` read with no WS reply within `WS_CALL_TIMEOUT_MS = 8000` is cancelled and replayed once over HTTP (the 8 s value is INFERRED from the slowest HAR read of 4-6 s and is recalibrated from arm C); late replies for a replayed or settled id are dropped.
9. **Kill switch.** `unary_over_ws` OFF takes effect within one flag refresh (<= 30 s, the `flagStore` TTL), or immediately through the circuit breaker or the local override `localStorage["ssq:ws-unary:force-http"]`, which `WsUnaryPolicy` reads on every call.
10. **Observability.** `ws_unary_fallback_total{reason}` is a **client-side** counter (analytics `performance` event, `window.__ssqPerf`); a server cannot observe calls that never reached it. Server `/actuator` counters are `ws_unary_calls_total`, `ws_unary_inflight`, `ws_unary_denied_total`.

11. **Per-origin enablement (remote listener).** The client classifies its page origin by protocol, never by port: `https:` = `remote`, otherwise `local`. `local` uses WS when `unary_over_ws` is ON; `remote` uses WS only when `unary_over_ws` **and** the sub-flag `unary_over_ws_remote` (default OFF, server-defined in `knownFeatureFlags`, a plain boolean like every flag) are ON. Choice and reason: both listeners share one server-wide flag value, so a single boolean cannot be ON for local and OFF for remote; the sub-flag is the smallest change that can (the alternative, a hard-coded origin rule, could not be flipped without a code change). `unary_over_ws` OFF remains the kill switch for both origins; the remote value is persisted per origin (`localStorage` is per origin) with the same remove-when-absent rule. `unary_over_ws_remote` flips to default ON only after the remote/h2 arms R1-R5 of plan Story 5.5.1 pass (h2 already multiplexes unary calls, so WS is justified on remote only by a measured gain; a measured loss is recorded as "WS hurts on h2"). Reverse proxies that strip `Upgrade`, buffer or enforce an idle timeout below the PING cadence cause failed handshakes that open the breaker (3 failures, HTTP-only 60 s) and are listed as required proxy settings in the flip guide.

## Consequences
- Rollout is reads-first by construction; mutations stay on HTTP unless a later PR adds them to both tables.
- The HTTP path stays fully supported and is the permanent fallback.
- The bridge shares an extracted upgrader/read-loop helper with `ws_stream_bridge.go` to avoid duplicated code under the blocking `dupl` gate.
