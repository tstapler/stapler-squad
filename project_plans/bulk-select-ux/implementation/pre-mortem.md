# Pre-mortem: bulk-select-ux
**Date**: 2026-06-23

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Space bar does not toggle checkboxes because `onChange={() => {}}` suppresses the synthetic change event — keyboard users cannot select sessions without a mouse | Accessibility audit flags the checkbox as non-interactive; screen reader users report that Space does nothing on focused checkbox | Replace `onChange={() => {}}` with `onChange={(e) => { e.stopPropagation(); onToggleSelect?.(e as unknown as React.MouseEvent); }}` OR switch to an `onClick`-only native button (`role="checkbox"`) so Space and Enter trigger `onClick` naturally; add an explicit keyboard test in `dispatch.test.ts` for Space-key selection | P1 |
| 2 | Concurrent bulk deletes corrupt the undo window: a second bulk delete while the first undo window is active flushes the first batch (fires RPCs), but `pendingDeleteIds` state is cleared by `flushPendingDeletes` before the second batch's `setPendingDeleteIds` call has been batched by React — result is sessions from batch one briefly reappear in the list then vanish again, and the undo toast shows stale session count | Users report sessions "flickering" back after a second bulk delete; undo button on second toast says "Undo 3 sessions" but restores 0 | In `handleConfirmBulkDelete`, call `flushPendingDeletes()` synchronously, then set new `pendingDeleteIds` in the same React state batch using `flushSync` or restructure to set new pending state before clearing old; add a specific Jest test: "second bulk delete before first undo window expires — no session reappearance and correct undo count" | P1 |
| 3 | Stale session IDs accumulate in `selectedSessions` when sessions are deleted externally (e.g., another browser tab, a CLI command, or the session crashing): the `Set<string>` grows unboundedly and `activeSelection` includes IDs that no longer exist in `filteredSessions` — bulk operations silently call `DeleteSession` on non-existent IDs, generating server errors | Server logs show `DeleteSession` returning NOT_FOUND for IDs; `BulkActions` count flickers briefly showing stale counts after an external delete | Add a `useEffect` that subscribes to the session list SSE/polling feed and removes externally-deleted IDs from `selectedSessions`; OR add a pre-flight filter in `handleDeleteSelected` that intersects `activeSelection` with the current server session list before issuing RPCs; add a test: "session deleted externally while selected — bulk delete skips deleted ID" | P2 |
| 4 | `filteredSessions` memo does not list `pendingDeleteIds` in its dependency array — React's linter allows this because `pendingDeleteIds` is a `Set` object (reference stable only if re-created), meaning optimistically-removed sessions reappear whenever any other dep changes (filter state, sort order, new session arriving from SSE) and the user sees sessions flash back into the list during the undo window | QA notices that actively chatting sessions (which update frequently via SSE) reappear in the list immediately after bulk delete | Explicitly add `pendingDeleteIds` as a dep of the `filteredSessions` useMemo; enable `exhaustive-deps` ESLint rule for this memo; add an integration test: "SSE session update arrives during undo window — pending sessions do not reappear" | P1 |
| 5 | `useEffect(() => () => flushPendingDeletes(), [])` captures a stale closure of `flushPendingDeletes` from the initial render — if `deleteSessionRpc` or `removeNotification` are recreated on a later render (e.g., context re-mount, auth token refresh), the cleanup calls the stale version that closes over stale references, silently dropping the delete RPCs | Sessions appear deleted in the UI but persist on the server; users discover phantom sessions on next page load or from another device | Stabilize `flushPendingDeletes` with `useCallback` whose deps include only stable refs (`useRef`-backed values), and store it in a ref (`flushRef.current = flushPendingDeletes`) so the `useEffect` cleanup reads the latest version via `flushRef.current()` rather than closing over the initial function; add a test: "flushPendingDeletes called after deleteSessionRpc is recreated — still fires RPCs correctly" | P2 |

## P1 Items (address before implementation)

- [ ] **Failure #1** — Add an explicit Space/Enter keyboard test for checkbox toggle before writing any checkbox DOM; change `onChange={() => {}}` to a handler that calls `onToggleSelect` or use a `role="checkbox"` button pattern; verify with NVDA/VoiceOver that Space selects the row (WCAG 2.1 SC 4.1.2)
- [ ] **Failure #2** — Specify the exact sequencing contract for "second bulk delete while first undo window is active" in Task 3.2.1-C; add a test case to the acceptance criteria that asserts no session reappearance and correct undo count for the second window; guard `flushPendingDeletes` + `setPendingDeleteIds` sequencing with `flushSync` or an explicit ordering note
- [ ] **Failure #4** — Add `pendingDeleteIds` to the `filteredSessions` useMemo dependency array explicitly in Task 4.1.1-A, and add an acceptance criterion: "Given a session update arrives via SSE during the undo window, the pending sessions do not reappear in the list"
