# Pre-mortem: client-reconnect
**Date**: 2026-06-23

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The `visibilitychange` handler fires on every tab switch (not just after a dropped stream), calling `watchSessions()` unnecessarily and creating duplicate concurrent streams because the `isConnectedRef` check uses a stale value that React hasn't synced yet via `useEffect` | Users see session list flicker or duplicate RPC calls in the network tab whenever they alt-tab back to the app | Add a unit test that asserts `watchSessions` is NOT called when `isConnectedRef.current` is already `true` and `lastEventTimeRef` is recent; also add the `isConnectedRef.current = true` direct-ref sync after first event in `startStream` (mirroring the terminal's task 0 pattern) | P1 |
| 2 | Terminal reconnect after laptop sleep replays the full scrollback buffer on top of existing output, showing every line twice, because `requestScrollback()` is always called post-reconnect with no check for whether the terminal already has content | Users see duplicated terminal output every time the terminal reconnects after sleep; confusing for long-running AI sessions | Resolve the open question in plan.md before Story 3.1.2 ships: either clear the xterm buffer before scrollback replay, or skip `requestScrollback()` if `terminal.buffer.active.length > 0`; add a Jest test for both the "empty buffer" and "non-empty buffer" reconnect paths | P1 |
| 3 | The `shouldReconnectRef.current = false` guard in `disconnect()` has a TOCTOU race with the `setTimeout` callback in the terminal `finally` block: `disconnect()` sets the flag to `false`, but a `setTimeout` already queued by the previous `finally` fires 800ms later, sees an old captured copy of `shouldReconnectRef` if the closure was formed before the flag flip, and calls `connect()` anyway | Terminal appears to reconnect after the user explicitly navigates away from a session; AI agent receives unexpected input or output | In Story 3.1.2 task 1, verify the `setTimeout` callback reads `shouldReconnectRef.current` at callback time (not at schedule time) — the plan's code snippet already does this correctly, but add a specific test case that calls `disconnect()` 100ms after scheduling the timer and asserts `connect()` is never called | P2 |
| 4 | The feature ships with `NEXT_PUBLIC_RECONNECT_V2` defaulting to absent (commented out in `.env.example`), so the feature never actually activates in any deployed environment; the primary user pain (stale sessions after laptop sleep) is not solved, and the feature sits dormant until someone manually sets the env var | After shipping, users still report stale session lists and the "reconnect" PR is considered a failure; no one notices because the `ConnectionIndicator` still shows "Stale" and the fallback behavior is identical to pre-feature | Explicitly decide and document in Story 4.2.1 whether the flag defaults to `true` in the committed `.env` or `.env.example`; the unresolved question is blocking and must be answered before Phase 4; consider defaulting to `true` since the flag exists for rollback, not for opt-in | P1 |
| 5 | The seq backwards-jump detection in Story 2.2.2 uses `event.seq < lastSeqRef.current` but `event.seq` and `lastSeqRef` are `bigint`; if a server restart causes `seq=0` and the client's `lastSeqRef` is `0n` (initial state), the condition is never true, the snapshot path is skipped, and the client silently diverges from server state without any visible error | After a server restart (e.g. `make install-service`), the session list becomes stale or shows phantom sessions from before the restart; no error is shown | Add a test case for the edge case where `lastSeqRef.current === 0n` and `event.seq === 1n` (first event after server restart from empty state); also test `event.seq === 0n` (server sends 0, which the current condition ignores because `0n < 0n` is false) | P2 |

## P1 Items (address before implementation)

- [x] Failure #1 (visibilitychange fires on healthy stream) — RESOLVED: Story 2.1.2 Task 3 now adds `isConnectedRef.current = true` direct ref sync alongside `setConnectionState("connected")` on first event. Story 4.2.2 test cases explicitly cover the "no extra watchSessions call when stream is live" path.
- [x] Failure #2 (scrollback duplication on terminal reconnect) — RESOLVED: Open question resolved in plan.md "Resolved: Terminal scrollback policy after reconnect" section. Policy: skip `requestScrollback()` if `terminal.buffer.active.length > 0` (reconnect path); only call it on empty buffer (initial connect). Added as Task 4 in Story 3.1.2.
- [x] Failure #4 (feature flag defaults to off, never activates) — RESOLVED: Story 4.2.1 Task 1 now sets `NEXT_PUBLIC_RECONNECT_V2=true` in `.env.local` (on by default). Rollback procedure: set to `false` and rebuild.
