# Pre-mortem: session-pinning
**Date**: 2026-08-21

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `PinSession`'s archived-guard reads `inst.ArchivedAt != nil` outside the actor lock and then calls `inst.SetPinned(true)` as a *separate* actor command — a concurrent `ArchiveSession` landing between the check and the mutation produces the illegal state `Pinned=true && ArchivedAt != nil` (concretizes architecture-review Concern 1). | An archived session shows up in the Pinned section (or the DB row has `pinned=1` with non-null `archived_at`) after rapid pin/archive actions on the same session, e.g. from two tabs/devices or a fast double-click. | Move the archived-check inside `setPinnedLocked` itself so the check and the mutation share one actor-serialized critical section; change `SetPinned` to return an error (`ErrCannotPinArchivedSession`) and have the RPC handler translate it — exactly architecture-review's own remediation, but currently only listed as a "Concern," not a plan.md task. | P2 |
| 2 | Task 2.4.3a's Pinned-section render block is a second, independently maintained JSX call site that must replicate every handler prop passed to `SessionCard`/`SessionRowWrapper` in the grouped-list render — the task text says only "wire every other handler prop... identically" with no enumerated list (architecture-review Concern 2). | A pinned session's card silently lacks functionality every other card has — e.g. click-to-open, delete, or rename no-ops — while the same session outside the Pinned section works, with no compiler error since the props are optional. | Extract a shared `renderSessionEntry(session)` helper/component used by both the Pinned section and the grouped-list loop, as architecture-review already recommends; add it as an explicit Epic 2.4 task instead of leaving it as prose guidance to hand-copy props. | P2 |
| 3 | The main list is virtualized (`useVirtualizer` for row mode, `GroupedVirtuoso` for card mode — confirmed in `web-app/src/components/sessions/SessionList.tsx`), but the plan's Pinned section (Task 2.4.3a) is a plain `.map()` outside that virtualizer, combined with the plan's explicit "no cap" decision on pin count (Pattern Decisions: "Pin cap — No cap"). | The list becomes visibly janky / scroll-stutters after a user accumulates dozens of pins over weeks of normal use (a per-session, per-repo tool with an uncapped, unbounded, always-fully-rendered top section), while the rest of the list stays smooth. | Fold the Pinned section into the existing virtualizer's flat item list as a synthetic leading group (matching how `groupSessions()`'s output is already combined), or add a soft cap / "show more" affordance to the Pinned section — decide and encode explicitly in plan.md rather than leaving virtualization scope entirely to the non-pinned path. | P2 |
| 4 | `pinSession`/`unpinSession`'s optimistic-update + rollback logic (Epic 2.1) has zero direct test coverage — Epic 3.3's tests only exercise the `onTogglePinned` prop and section rendering, both of which stub the hook (architecture-review Concern 3). | After a transient RPC failure (server restart, network blip), a pin toggle appears stuck in the wrong state — UI shows pinned, a reload shows unpinned (or vice versa) — with no visible error, and it's hard to reproduce since it depends on failure timing. | Add the test architecture-review specifies: mock `clientRef.current.pinSession` to reject, call `pinSession(id)`, assert the dispatched session reverts to its pre-optimistic value and `setError` fires. Add as an explicit task in Epic 2.1 or 3.3, not left as an acknowledged gap. | P2 |
| 5 | Task 1.2.1a instructs adding `bool pinned = 72;` on the claim that the highest field in use is `workspace_key = 71`. **Verified against the live file**: `proto/session/v1/types.proto`'s `Session` message already has `exit_reason = 72`, `note = 73`, `auto_approve = 74`, `subagent_count = 75` — field 72 is taken and the true next-free number is 76. The plan's field-number research (dated 2026-08-06) has gone stale relative to the current repo. | `make proto-gen` fails immediately with a duplicate-field-number error the moment Task 1.2.1a is applied literally — or, worse, if fixed ad hoc without updating the plan, the other two field-72 references in plan.md (Domain Glossary line 36, Story 1.2.1 AC line 195) drift out of sync with what actually shipped. | Before implementation, re-verify the current highest in-use field number in `Session` (currently `subagent_count = 75`, confirmed via `awk '/^message Session {/,/^}/' proto/session/v1/types.proto \| grep -E '= [0-9]+;'`) and correct all three field-72 references in plan.md to 76. Note in plan.md that proto field numbers must be re-verified at implementation time regardless of what planning recorded, since this file changes independently of this project's timeline. | P1 |
