# Validation Plan: session-pinning

**Date**: 2026-08-21

## Happy Path Scenario

Given a live, non-archived session that is not currently pinned, when the user opens its "···" menu and clicks "Pin," then the session immediately moves into a dedicated "Pinned" region at the top of the session list (optimistically, before the RPC resolves), the RPC persists `pinned=true` to the ent-backed `Session` entity, and the pinned state survives a page reload and a server restart.

## Migration Test Status

`migration_should_be_reversible` — **N/A for this feature.** Per plan.md's Migration Plan, this repo has no hand-written `.sql` up/down migration files; ent's `client.Schema.Create(ctx)` auto-migrates the new `pinned` column additively on startup (`ALTER TABLE sessions ADD COLUMN pinned BOOL DEFAULT 0`), exactly how `hidden` was added. There is no automated down-migration to test — plan.md states explicitly that "a rollback leaves the unused `pinned` column in place, which is harmless" (older binary code simply never reads/writes it), so a reversibility test would have nothing to assert against. REQ-2's integration test (`TestEntRepository_should_RoundTripPinnedTrue_When_ReloadedFromFreshClient`) is the closest applicable coverage — it confirms the additive column round-trips correctly across a fresh client, which is the only migration-adjacent behavior this feature introduces.
