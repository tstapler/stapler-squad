# Architecture Review: session-pinning
**Date**: 2026-08-06
**Verdict**: CONCERNS

## Constitution Violations
- None — no `docs/adr/ADR-000-architecture-constitution.md` file found in this repository (checked at review time).

## Blockers
None. The plan follows five existing, proven identical field-shapes (`hidden`/`auto_yes`/`is_expanded`/etc.) end-to-end and introduces no speculative abstractions, no layer-crossing dependencies, and no library/pattern mismatch. The items below are real but none corrupt correctness as specified — they are forward-looking risks and structural erosions worth fixing while cheap.

## Concerns

- [ ] **Story 1.4.1/1.7.1 — archived-guard invariant lives only at the RPC boundary, not the domain layer** — `PinSession`'s handler (`server/services/session_service.go`) checks `inst.ArchivedAt != nil` and rejects with `CodeFailedPrecondition` before calling `inst.SetPinned(true)`. But `SetPinned`/`setPinnedLocked` (`session/instance_actor_setters.go`) itself performs no such check — it unconditionally sets `Pinned = v`. This is asymmetric with the *reverse* invariant (archiving auto-unpins), which the plan correctly places inside `setArchivedAtLocked` — the one choke point every archive path funnels through — specifically to prevent invariant drift across call sites (Pattern Decisions table, "Archived+pinned interaction" row). The "cannot pin an archived session" half of the same invariant gets no equivalent protection: any future caller of `inst.SetPinned(true)` that doesn't go through the `PinSession` RPC handler (a bulk operation, a workflow action, a test helper, a future admin tool) can produce the illegal state `Pinned=true && ArchivedAt != nil` with no guard at all. DDD's rule that an aggregate root enforces its own invariants (not each caller individually) is violated for this one direction only.
  **Remediation**: move the check into the domain layer. `sendSyncErr`'s closure already supports returning an error — change `SetPinned` to `SetPinned(v bool) error`, check `s.inst.ArchivedAt != nil` inside `setPinnedLocked` (or a wrapping closure) when `v == true`, and return a sentinel error (e.g. `ErrCannotPinArchivedSession`). Have `PinSession`'s handler translate that error to `connect.CodeFailedPrecondition` instead of duplicating the nil-check itself. This mirrors exactly the discipline already correctly applied to the reverse direction.

- [ ] **Task 2.4.3a — pinned-section render block duplicates full handler-prop wiring instead of sharing one render path** — the task's own text instructs: *"Wire every other handler prop — `onSessionClick`, `onDeleteSession`, etc. — identically to how the grouped-list render passes them."* This creates two independently-maintained JSX call sites (`SessionList.tsx`'s new Pinned-section block and the existing grouped-list render block) that must both invoke `<SessionCard>`/`<SessionRowWrapper>` with the same growing prop list. This is an Open/Closed and DRY violation: every future handler prop addition to `SessionList` risks being wired into one render path and silently forgotten in the other, with no compiler error to catch the omission (props are optional, so a missing one just silently no-ops).
  **Remediation**: extract a small `renderSessionEntry(session: Session)` helper (function or `<SessionEntry>` component) inside `SessionList.tsx` that both the Pinned section (`pinnedSessions.map(...)`) and the grouped-list loop call, so handler-prop wiring exists in exactly one place. Both call sites already pass an identical prop set per the plan text, so this is a pure extraction with zero behavior change.

- [ ] **Epic 2.1 vs Epic 3.3 — optimistic-update/rollback logic has no direct test coverage** — `pinSession`/`unpinSession` (`useSessionService.ts`) introduce genuinely non-trivial state-management logic: dispatch an optimistic `upsertSession` before the RPC resolves, then dispatch a rollback to the *previous* session object if the RPC throws (Story 2.1.1). But the plan's only frontend tests (Epic 3.3, Stories 3.3.1/3.3.2) test `SessionActionsOverflow` calling the `onTogglePinned` *prop* and `SessionList`'s rendering — both mock/stub the handler rather than exercising the real hook. Requirements' AC ("Frontend pin toggle... covered by a Jest/RTL test") is technically satisfied, but the code most likely to have a bug — the rollback path on RPC failure — has zero coverage anywhere in the plan.
  **Remediation**: add a test case (in `useSessionService.test.ts` if one exists, else a new small spec) that mocks `clientRef.current.pinSession` to reject, calls `pinSession(id)`, and asserts the dispatched session reverts to its pre-optimistic value and `setError` fires. Cheap to add now; expensive to debug later without it since the failure mode (stuck-optimistic UI state) is not visually obvious in manual testing.

## Nitpicks
- `Instance`/`InstanceSnapshot`/`InstanceData`/proto `Session`/frontend `Session` each gain a 6th near-identical boolean field (`Pinned`, alongside `Hidden`/`AutoYes`/`IsExpanded`/etc.), continuing an existing "shotgun surgery" shape where every new session-level flag requires touching 5+ files in lockstep. Pre-existing architecture, not introduced by this plan — not asking this plan to fix it, but if a 7th flag is ever proposed, that's the trigger to consider collapsing these into a single `SessionFlags` value object.
- `CockpitActions`, `SessionCardProps`, `SessionRowProps`, `SessionListProps`, and `SessionRowHandlers` all grow by one more individual handler prop (`onTogglePinned`) rather than being grouped into a single `SessionActionHandlers` object passed as one prop — continues pre-existing Interface Segregation erosion across an already-large set of interfaces. Every other toggle in the codebase already does this, so it's consistent, just worth a heads-up if these interfaces are ever revisited.
- `inst.ArchivedAt != nil` continues to be used as an implicit "is archived" boolean discriminant via ad hoc nil-comparison rather than an `IsArchived() bool` method on `Instance`. Pre-existing pattern; the new `PinSession` handler is one more call site propagating it (and is also the site of the Concern above, where a proper `IsArchived()`-style domain method would have made the missing domain-layer guard more visible).
- `groupedSessions` and `pinnedSessions` (`SessionList.tsx`) each independently `.filter()` over the same `sortedSessions` array (two full passes) rather than a single partition pass. Negligible at this data scale — pure style nitpick, not worth blocking on.
