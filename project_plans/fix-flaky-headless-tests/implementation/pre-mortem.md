# Pre-mortem: fix-flaky-headless-tests
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The original bug report describes clusters 1+2 as **flaky** (intermittent), but the interpreter-invocation fix targets a **deterministic** OS-refusal hypothesis (Gatekeeper/TCC/EDR blocking every exec of a fresh script on an affected machine). A transient AV/EDR scan-lock race on freshly-written temp files would also produce intermittent failures, and `sh <path>` still has to open/read that same file within the same race window — the fix may not close that window at all, just move which syscall (`open`/`read` inside `sh` instead of `execve`) hits the lock. | A maintainer runs Story 5.1.1's macOS verification 5x, gets 5/5 passes (or 4/5), and can't actually distinguish "fixed" from "got lucky within a narrower window" — the flake reappears weeks later under different system load. | Before treating Phase 5 as closing the loop, run the macOS verification with a much higher count (`-count=20+`) run under background system load (e.g. a Spotlight reindex or an active EDR scan), and capture the exact error text of any failure — a *different* error string than the original `fork/exec ... operation not permitted` would falsify the current root-cause hypothesis outright. |
| 2 | Nothing in this plan or repo automation actually gates the backlog item's resolution on a human running Story 5.1.1 on macOS — it is PR-description prose only. This repo's own reconciliation automation (see `.claude/rules/fix-flaky-tests-dont-defer.md` and the memory note on backlog stuck-review) has repeatedly closed/auto-merged items without a human following up on a documented "needs external verification" caveat. | The backlog item (`04e6841f-ff53-44bb-b737-04e8b52fe1c3`) shows status `resolved`/`done` shortly after the PR merges, with no linked follow-up item, and no macOS confirmation ever recorded anywhere queryable. | Before merge, create a second, explicitly-linked backlog item (via `mcp__stapler-squad__create_backlog_item`) titled something like "Confirm clusters 1+2 fix on macOS" and leave it `in_progress`/blocked; do not let the *parent* item's resolution depend on PR-body text no automation reads. |
| 3 | `interpreter` is an exported, always-compiled field/constructor on the production `ProcessRunner` type with no type-level or lint-level guard against production use; `WithWorkDir`/`WithToolAccess` silently propagate it through every derived runner. A future engineer building a legitimate production feature (e.g. "invoke claude through a sandboxing wrapper script") has an existing, discoverable seam sitting right there and may wire a real interpreter value onto a production-constructed `ProcessRunner` instead of adding a proper reviewed path. | Weeks/months later, real session claude invocations behave subtly differently (working-directory resolution, signal propagation, or environment differences between direct exec and shell-wrapped exec) in a way that's hard to trace back to `interpreter` being set, since nothing flags the assignment as unusual. | Add a cheap enforcement: either a repo-style grep-based CI check (this repo already leans on grep-based checks elsewhere) asserting `interpreter:` / `.interpreter =` is only assigned from `_test.go` files, or move the field behind a `_test.go`-only helper type so the compiler — not convention — enforces it. Record this as a follow-up in ADR-001 rather than the current "cannot leak by accident" claim (already flagged as inaccurate in `architecture-review.md`; this finding proposes the concrete mechanism, not just the naming fix). |
| 4 | `isExpectedFaultSignal` is not directly unit-tested (already flagged in `architecture-review.md`) — but the deeper risk is that it can produce a **false negative on a genuine SIGBUS/SIGSEGV**: `safeexec.CommandContext`'s `WaitDelay` watchdog can race the crash signal (killing a slow-draining crashed process before/instead of a clean signal-terminated wait status being observed), and macOS's own crash-reporter (`ReportCrash`) is known to intercept fatal signals in ways that can alter what the parent process observes via `Wait()`. Either would make `isExpectedFaultSignal` return `(false, "not confirmed")` for a real fault. | The test still passes (log-only change, so no CI signal), but on macOS the log permanently shows "signal not confirmed as SIGBUS/SIGSEGV" even when real crashes are occurring — silently defeating the entire diagnostic purpose Phase 3 exists to add, and nobody notices because nothing fails. | Add the direct unit test architecture-review already recommends, but specifically construct it via `safeexec.CommandContext` (not bare `exec.Command`) so it exercises the exact `WaitDelay` code path production/test code actually uses, and add one `t.Logf` in the real test asserting whether `isExpectedFaultSignal` matched on at least one of the 5 repeated runs — a false-negative streak would then be visible in CI output instead of silently absorbed. |
| 5 | `NewShellWrappedProcessRunnerForTesting` hardcodes the interpreter to `"sh"` and, unlike the kernel's own shebang-driven direct exec it replaces, **ignores whatever shebang line the fixture script itself declares**. All 6 current call sites already use `#!/bin/sh` (confirmed via `grep -n '#!/'`), so this doesn't bite today — but the constructor becomes the copy-paste template for every future fake-claude fixture, and nothing stops a future script from using `#!/bin/bash` + bash-only syntax (arrays, `[[ ]]`) while still being run through this helper, silently forcing it through plain `sh` (which is `dash`, not bash, on Debian/Ubuntu). | A test added after this PR ships fails with a shell syntax error that looks exactly like the original Gatekeeper symptom (a broken fake-claude invocation), and gets misdiagnosed as a regression of the bug this plan just "fixed," burning investigation time re-deriving a root cause that's actually a portability footgun in the fix itself. | Add one sentence to `NewShellWrappedProcessRunnerForTesting`'s doc comment: fixture scripts must be POSIX-`sh`-compatible, not bash-specific, because the shebang line is overridden by the explicit `"sh"` interpreter this constructor always uses. |
