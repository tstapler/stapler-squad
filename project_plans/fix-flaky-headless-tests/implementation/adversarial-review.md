None found. The interpreter-invocation fix was traced end-to-end (`runner.go`'s
`Run`, both copy constructors `WithWorkDir`/`WithToolAccess` used via
`caller.go:448-450`'s `pr.WithWorkDir(...).WithToolAccess(...)` chain, and all

and `runner_test.go` (arg-formatting unit tests that never call `Run`,

## Concerns

- [ ] **ADR-001 overstates the production-isolation guarantee of the interpreter field** — the ADR claims the `interpreter` field "cannot leak into production wiring by accident without a deliberate, reviewable code change to `runner.go` itself," but `session/headless/fake_runner.go` (which will host the new `NewShellWrappedProcessRunnerForTesting` constructor) is a plain, always-compiled file with no `_test.go` suffix or build tag — confirmed by `head -15 session/headless/fake_runner.go` (no `//go:build`) and by the fact that `server/services/headless_service_test.go`, a *different package*, already imports `headless.NewFakeRunner` from it (Go `_test.go` files are never importable cross-package, which is exactly why this file has to be a regular `.go` file). That means the new constructor is an **exported, package-external, always-compiled symbol** — any future production code anywhere in the module (e.g. a new file under `server/services/`) can call `headless.NewShellWrappedProcessRunnerForTesting(...)` directly, with zero review of `runner.go` required, contrary to what the ADR states. The consequence is mild in practice — if this were called against the real `claude` binary, `sh <compiled-binary-path>` would fail loudly (a shell-syntax error), not silently misbehave — but the ADR's stated safety property doesn't hold as written, and the "ForTesting" name is a convention, not an enforced boundary. **Recommendation**: either fix the ADR's claim to say "convention-enforced, not compiler-enforced" or reduce the actual risk (e.g. move the constructor + `interpreter`-aware branch behind a `_test.go`-only helper in each consuming package, or add a lint rule / comment making the non-enforcement explicit).

- [ ] **Story 3.1.1's Windows-CI justification is inaccurate, making the new build-tag scaffolding solve a problem CI doesn't actually have** — AC3 cites "`linux`, `darwin`, `windows` — confirmed via `.github/workflows/build.yml` matrix" as the reason a portable/gated helper is needed. Verified directly: `build.yml`'s `goos: [linux, darwin, windows]` matrix (lines 276-310) runs `go build -v ... .` against the **root main package only** — `go build` never compiles `_test.go` files, and `gogitstore`'s only production consumer (`session/unfinished/gogit_vcs_reader.go`) doesn't touch the new test files either. Separately, `go test -race ./...` (`build.yml:155-157`) and the `golangci-lint` job (`lint.yml:35`) both run exclusively on `runs-on: ubuntu-latest` — confirmed via `grep -rn "runs-on" .github/workflows/*.yml` (28 hits, all `ubuntu-latest`/`ubuntu-22.04`, zero `windows-latest`/`macos-latest`). **No CI job in this repo will ever compile, vet, or run `trunc_fault_signal_windows_test.go`.** The Pattern Decisions table's own footnote half-acknowledges this ("CI never cross-compiles this test file for Windows today, but a native Windows contributor running `go vet ./...` ... would break") — but that's a materially weaker justification than AC3's framing, and the scenario it defends against (a contributor building natively on Windows) isn't otherwise evidenced: this repo's own `CLAUDE.md` documents Manjaro/Ubuntu Linux, macOS, and WSL2 as the supported dev platforms, not native Windows. This is defensible as cheap, low-risk, precedent-following scaffolding (mirrors `zombie_reaper.go`/`zombie_reaper_windows.go`), so not a blocker — but the plan should either correct the citation or drop the windows stub as unnecessary for a repo with no native-Windows contributors and no CI leg that would ever catch its absence.

- [ ] **The mandatory post-merge macOS verification (AC6/Story 5.1.1) is tracked only as PR-description text, not a durable, trackable artifact** — nothing in Phase 5 creates a backlog item, GitHub issue, or other mechanism that outlives the PR itself. Once the PR merges (test-only change, no rollout gate per the plan's own Risk Control section), the only record of "clusters 1+2 are hardened but unverified" is prose in a merged PR's description, which is easy to lose track of — especially since this same repeated-failure-to-follow-through pattern is exactly what `.claude/rules/fix-flaky-tests-dont-defer.md` was written to stop (the rule's own preamble cites this codebase's history of "known pre-existing flake, unrelated" being re-excused release after release without follow-through). **Recommendation**: file a linked backlog item (this repo already has `mcp__stapler-squad__create_backlog_item`) or GitHub issue for the macOS confirmation step at merge time, not just a PR-body checklist item, so it surfaces in normal triage instead of depending on someone re-reading a closed PR.

## Minors

- Bare `"sh"` (PATH-resolved) rather than an absolute path like `/bin/sh` is used for the interpreter (`ADR-001`, Task 2.1.1c). Traced the resolution path: `safeexec.CommandContext` → `exec.CommandContext(ctx, "sh", ...)` resolves `"sh"` via `LookPath` against the **host test-runner process's** `PATH` at `Cmd` construction time (not the filtered child env applied later via `WithProcessReplaceEnv`), so this is safe in practice on any standard Linux/macOS/CI box. It's a new, undocumented assumption, though, and would fail via a different, clearer error (`exec: "sh": executable file not found in $PATH`) than the original Gatekeeper EPERM if it were ever wrong — low risk, no action strictly required, but worth a one-line comment noting the PATH dependency is intentional if a future reader wonders why it isn't `/bin/sh`.
- `pool_test.go:690`'s fixture script uses `$(pwd)` — confirmed this is a shell builtin unaffected by direct-exec vs. `sh <path>` invocation, no behavior change.
- The plan's own scope self-audits (doc-rot cleanup at `capability_check_test.go:19`, the "no caching bug" finding, the `dccee742a` precedent for cluster 3) were all independently re-verified against the actual code/git history in this review and check out — these are correctly not flagged as issues.
