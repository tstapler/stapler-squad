## Concerns

- [ ] **Story 3.1.1/3.1.2 (`isExpectedFaultSignal`) — helper has no direct unit test, only indirect coverage through a platform-dependent test.**
  AC3's own Given/When/Then reads like a unit-test spec ("Given an `*exec.ExitError` from a process killed by SIGBUS on Linux, When `isExpectedFaultSignal(err)` is called, Then it returns `(true, "bus error")`"), but no task in Story 3.1.1 or 3.1.2 adds a `func Test...` that calls `isExpectedFaultSignal` directly with a synthetic/constructed error. The only exercise path is transitively through `TestMmapIndexHandle_TruncateWhileMapped_CrashesWithoutProtection`, which is itself the platform/kernel-dependent test this whole project exists to make more trustworthy — on a run where the kernel happens not to fault (the tolerant `NO_FAULT_OCCURRED` branch), `isExpectedFaultSignal` never executes at all, and on a non-SIGBUS/SIGSEGV failure the "false" branch is likewise untested by anything the plan adds. This is a real testability gap given the requirements doc's own AC0/AC4 discipline ("no fix without root cause," "no change silently loosens a guarantee") — a helper whose correctness can't be independently verified is exactly the kind of change that discipline is meant to catch.
  **Remediation**: add a small direct test (e.g. spawn `sh -c 'kill -SIGBUS $$'` via `exec.Command` and assert `isExpectedFaultSignal` returns `(true, "bus error")`; spawn a normal non-zero exit like `sh -c 'exit 1'` and assert it returns `(false, ...)`) in `trunc_fault_signal_test.go` itself. This is portable across the `!windows` platforms this repo's CI actually runs and doesn't depend on the mmap fault reproducing.

- [ ] **Story 2.1.2 / AC1 — plan silently narrows scope from what AC1 itself states, without recording why.**
  `requirements.md`'s AC1 explicitly names three files as sharing "the same pattern": "Cluster 1 (`capability_check_test.go`) and cluster 2 (`pool_test.go`, **and the same pattern in `caller_test.go`**)." The plan's Story 2.1.2 (Files: `capability_check_test.go`, `pool_test.go`) never migrates or even mentions `caller_test.go`, and no other section of the plan documents why it's excluded. Investigation for this review (`grep -n "WriteFile\|ProcessRunner{" session/headless/caller_test.go` + reading the file) shows `caller_test.go`'s `TestFindClaudeBinary_*` tests write scripts to disk purely to exercise `findClaudeBinary`'s executable-bit discovery logic (`os.Stat`) — none of them ever fork/exec the written file, so they cannot hit the Gatekeeper/TCC exec-refusal this plan targets. The exclusion is almost certainly *correct*, but the plan doesn't say so anywhere, which leaves a real traceability gap: AC1's own wording is broader than what the plan implements, and a future reviewer checking "no outlier bypasses it" against `caller_test.go` has to independently re-derive the same reasoning this review just did, or risk flagging a false gap (or, worse, "fixing" a call site that was never actually exec'ing anything).
  **Remediation**: add one sentence to the plan's Domain Glossary or Story 2.1.2 stating explicitly that `caller_test.go`'s script-writing tests only exercise `findClaudeBinary`'s stat-based discovery and never exec the file, so they're outside AC1's actual failure mode despite the requirements doc's "same pattern" phrasing — closing the loop AC0 itself demands.

- [ ] **Lens 1.2 (layer coupling) — the underlying reason `ProcessRunner` (not an interface implementation) must be touched at all is a pre-existing DIP/LSP smell this plan works around rather than names.**
  Per the plan's own Domain Glossary: `NewProcessRunnerForTesting` exists because "`Pool.CallWithOptions`'s WorkDir one-shot path type-asserts on the concrete `*ProcessRunner`" — i.e., a `FakeRunner` that correctly implements the `ClaudeRunner` interface is rejected by a concrete-type assertion, forcing tests needing WorkDir coverage to construct a real `*ProcessRunner` instead of programming to the interface. That pre-existing design choice is why this fix has to add a field and branch to a production type at all, rather than being expressible as a `ClaudeRunner` decorator/wrapper that lives entirely in test code. This isn't a defect introduced by this plan — it's inherited, and the plan correctly declines to fix it (out of scope for a complexity-1 bugfix) — but the plan doesn't name it as a "why this touches production code" explanation anywhere, which is exactly the kind of layer-coupling question this review's brief asked to check. Recommend acknowledging it explicitly (one sentence) rather than leaving a future reader to wonder why the fix wasn't scoped as a pure test-double.
  **Recommendation**: not required for this PR to merge, but worth a one-line note in ADR-001's Context section acknowledging the `Pool.CallWithOptions` type-assertion as the structural reason a test-only concern has to touch `runner.go`, and optionally filing a follow-up item (per `fix-flaky-tests-dont-defer.md`'s spirit of naming rather than re-excusing structural debt) to make `Pool.CallWithOptions`'s WorkDir path accept the `ClaudeRunner` interface instead of type-asserting on `*ProcessRunner`.

## Nitpicks

- **`interpreter string` is more general than any call site uses.** Only one value (`"sh"`) is ever assigned to it, by exactly one constructor. A `shWrapped bool` would express the actual invariant more precisely and make "no other interpreter is supported" visible in the type instead of only in the doc comment. Not worth blocking on — `string` costs nothing here and leaves room if a second interpreter is ever genuinely needed — but flagging per the primitive-obsession lens since the plan explicitly asked for this judgment call.
- **`fake_runner.go` is a plain, non-`_test.go`, non-build-tagged file — verified.** `NewShellWrappedProcessRunnerForTesting` (like the pre-existing `NewProcessRunnerForTesting` right above it) is compiled into every production binary despite the "ForTesting" name; it is not gated by `_test.go` suffix or a `//go:build` tag. Verified via `grep -rln "NewProcessRunnerForTesting\|NewShellWrappedProcessRunnerForTesting" --include="*.go" . | grep -v _test.go` → only `fake_runner.go` itself, confirming no non-test caller exists anywhere in the repo today. This is genuinely production-compiled code, not "inert" in the sense of being excluded from the binary — but it's an established, pre-existing pattern in this exact file (`NewProcessRunnerForTesting` already does the same thing), not a new risk this plan introduces. ADR-001's "test-only" language is accurate in *practice* (unexported field, only reachable through these two constructors, zero production callers) but could be slightly more precise that "test-only" means "by convention and by the field being unexported," not "excluded from the production binary."
- **Sequencing detail, not a defect**: Task 2.1.1b's interpreter branch is described as going "after `args = append(args, r.toolAccessArgs()...)`" (line 116) "and before calling `executor.StartProcess`" (line 129) — there are ~13 unrelated lines of `opts` construction in between where the actual insertion point isn't pinned down further. Functionally inert either way (no intervening code reads `args`/`name`), just worth the implementer picking one spot rather than splitting the diff across the gap.
- Lens items marked N/A by the task brief and confirmed genuinely inapplicable on inspection: DDD aggregate boundaries (Lens 1.3), parse-at-boundary (Lens 2.7), PoEAA pattern fit (Lens 3.8), build-vs-buy consistency (Lens 3.11).
- Lens 3.9 (GoF pattern rejection) and Lens 3.10 (constructor API stability): reviewed and **agreed** — a Strategy/Decorator here would be over-engineering for a 6-line opt-in branch, and the two `*ForTesting` constructors are adequately distinguished by co-located, cross-referencing doc comments (confirmed by reading both in `fake_runner.go`); no discoverability fix needed.
