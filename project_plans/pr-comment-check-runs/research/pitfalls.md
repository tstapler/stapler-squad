# Pitfalls Research: Reduce PR/Issue Comment Noise, Prefer Check Runs

Agent 4 (Pitfalls) — SDD research phase for `project_plans/pr-comment-check-runs/`.

## 1. GitHub Checks API pitfalls

### 1a. Auth: the Checks API write endpoints are GitHub-App-only — this repo has no GitHub App today (BLOCKING)

VERIFIED via [GitHub REST API docs — Checks: runs](https://docs.github.com/en/rest/checks/runs) (fetched 2026-08-12):

> "Write permission for the REST API to interact with checks is only available to GitHub Apps. OAuth apps and authenticated users can view check runs and check suites, but they are not able to create them."
> "To create a check run, you must use a GitHub App."

This is corroborated by community reports that the "Checks" permission is not selectable at all when creating a fine-grained PAT ([community discussion #179545](https://github.com/orgs/community/discussions/179545), [#129512](https://github.com/orgs/community/discussions/129512)) — GitHub shipped fine-grained-PAT support for it briefly, then disabled it. So neither a classic PAT, a fine-grained PAT, nor an OAuth-app user token (which is what `gh auth token` returns) can call `POST /repos/{owner}/{repo}/check-runs`.

**This repo's entire GitHub auth stack is PAT/OAuth-token based, not a GitHub App:**
- `session/backlog_plugin_github_prs.go:78,94,174` — sets `Authorization: token <cfg.Token>` (classic PAT header format), sourced from `github.GetKeychainTokenForHost`.
- `github/keychain.go` — stores/retrieves tokens keyed by host/account; no App/installation-token concept anywhere in `github/`.
- `github/cli_import.go:74` (`GetCLIToken`) — shells out to `gh auth token --hostname <host>`, i.e. the `gh` CLI's own OAuth user token.
- No `github/app.go`, no JWT-signing code, no `X-GitHub-Api-Version` installation-token exchange anywhere in the repo (confirmed via `grep -rn "GITHUB_APP\|installation.*token\|App.*Private.*Key" server/services github/` — zero hits).

**Consequence for this feature**: "prefer check runs over comments" as literally specified (create/update check runs via the REST Checks API) is not achievable with the app's current credential model without first standing up a GitHub App (registering it, installing it on the target repos, handling JWT→installation-token exchange, storing the private key securely — a materially bigger scope than this ticket's stated intent). This should be surfaced as a **scope decision for Phase 3 (plan)**, not silently discovered mid-implementation. Options to resolve, roughly in ascending cost:
  1. Narrow "check run" to what a plain token *can* do — the classic **Statuses API** (`POST /repos/{owner}/{repo}/statuses/{sha}`, `repo:status` scope on a classic PAT) instead of Checks. Statuses are a strict subset (single state, no summary markdown, no annotations, shown as "Commit Status" not "Check"), but they render in the same PR merge-status area and are creatable with the existing token.
  2. Stand up a minimal GitHub App scoped only to `checks:write`, used solely for this feature, alongside the existing PAT-based auth for everything else — real but bounded new infra.
  3. Defer Checks-API-backed status entirely and re-scope the ticket to "reduce comment volume" only, revisit check-run/status output as a follow-up once auth is solved.

  This must be verified against GitHub Enterprise Server too if this repo talks to a GHE host (`github/keychain.go`'s per-host token support implies multi-host is already a concern) — GHE permission tables can lag or diverge from github.com's.

### 1b. Rate limits
Checks/Statuses writes count against the same primary rate limit as any other REST call from that token (5,000/hr for a PAT, higher for GitHub Apps on a per-installation basis). Not a first-order risk for typical PR volume, but worth noting if a "recreate check run on every push" implementation polls/re-posts more than once per event — batch or debounce rather than firing on every intermediate CI step.

### 1c. Visibility: Checks tab vs Conversation tab
Check runs (and legacy commit statuses) surface in the PR's **Checks** tab and as a compact rollup on the **Conversation** tab's merge-box, but they are *not* visible in a PR's activity/comment timeline the way a comment is — someone scanning only the comment thread (e.g. via email digest, or a client that doesn't render the merge-box prominently) can miss them entirely. Acceptance criterion 4 ("user can glance at checks + comment count and know if PR needs anything") implicitly assumes the user's PR-viewing habit already includes checking the Checks tab/merge-box — worth confirming that's true for how this user (and any skill-driven automation reading PR state back, e.g. `session/backlog_plugin_github_prs.go`'s existing check-run reader) actually consumes it, rather than assuming.

### 1d. Check runs are commit-SHA-scoped — stale runs after force-push/rebase
Both check runs and commit statuses attach to a specific `commit_sha`, not to the PR as a whole. A force-push or rebase changes every SHA on the branch, so:
- Old check runs remain visible in the Checks tab's history for the old SHA but are **not** shown against the PR's current head — GitHub's UI naturally hides them once the head SHA changes, so this mostly self-heals visually.
- But any code that *reads back* check-run state (this repo already does — `session/backlog_plugin_github_prs.go:169`, `repos/%s/%s/commits/%s/check-runs`) must re-fetch for the **current** head SHA after every push, not cache against a SHA that may already be stale. If this feature adds *writing* check runs keyed off a SHA captured earlier in a skill's run (e.g. captured at PR-open time, written after a later `git commit --amend`/rebase happened), the write will land on a SHA nobody is looking at anymore, functionally silently dropping the "check" the automation intended to convey — a subtler version of the exact noise problem this ticket is trying to fix, just moved from "annoying comment" to "invisible no-op write."

## 2. Behavior-change rollout risk (partial migration / silent reversion)

**Partial migration**: The requirements doc's own "Context Already Established" section names four independent call sites for PR/issue posting behavior — `github:pr-ship`, `github:pr-refine`, `code:review`, and backlog-driven autonomous shepherding (which itself routes through multiple RPCs: `report_progress`, `submit_review_verdict`, `report_pr_created`, per the MCP tool list). `PostPRComment`/`Instance.PostComment` (`session/pr_tracking.go:71`, `server/services/github_service.go:137`) are undifferentiated primitives — nothing in the type signature or the RPC distinguishes "this is an action item" from "this is a status ping." That means:
- Updating the convention requires editing **prose in N separate skill files** (`~/dotfiles/.claude/skills/github/skills/pr-ship/SKILL.md`, `pr-refine/SKILL.md`, `code/skills/review/SKILL.md` or equivalent, plus whatever backlog-shepherding skill/prompt calls `report_progress`) — there is no single call site to change. Missing one skill leaves that skill silently comment-heavy while others quiet down, and a PR shepherded partly by pr-ship and partly by backlog automation would show inconsistent noise depending on which skill touched it last.
- **No compiler/type-level guard exists.** Contrast with this repo's own established pattern for catching recurring *code* smells — `.claude/rules/interface-pollution-checklist.md`, `.claude/rules/primitive-obsession-checklist.md` — both of which work because the smell lives in Go source that `go build`/review can inspect. A skill's decision "should I comment or should I emit a check run here" is a runtime LLM judgment call with no artifact a linter can statically verify. This is a materially different pitfall class from the existing rules-file precedent, not a smaller version of it.
- **Silent reversion risk over time**: even a fully-migrated skill can drift back to old behavior in a later edit (a future session tweaking `pr-ship` for an unrelated reason re-adds a "post a status comment" step because that's what training-data-shaped defaults look like, per this repo's own stated rationale for `interface-pollution-checklist.md` — "LLMs default to Java/Spring-shaped abstractions" is the same category of claim as "LLMs default to comment-heavy status narration"). Nothing currently re-checks this after the initial migration.

## 3. Convention-enforcement mechanisms available in this repo

Confirmed via file search (`~/dotfiles/.claude/skills/`) that this repo's ecosystem already has two shapes of standing "audit skill behavior over time" pattern, neither of which is a perfect fit as-is:

- **`quality:reflect-and-fix`** (`~/dotfiles/.claude/skills/quality/skills/reflect-and-fix/SKILL.md`) — "Post-mortem cycle that turns fixed **bugs** into structural enforcement... classifies root cause, finds the earliest possible detection point on the enforcement ladder (compile → lint → test → checklist)." This is explicitly bug→code-fix shaped; its enforcement ladder bottoms out at "checklist" (i.e. a `.claude/rules/*.md` file), which is exactly the mechanism the research question flags as *not* sufficient for runtime skill behavior — a checklist file is read-and-followed by a fresh agent each time, not compiled or linted against.
- **`code:is-it-ready`** — shipping-readiness gate across plan compliance/architecture/quality/tests/security/product/ops. Point-in-time, per-PR, not a recurring cross-time audit of "did comment volume trend down."
- **`backlog-feature-improvement`** (`.claude/skills/backlog-feature-improvement/SKILL.md`, this repo) — **this is the closest existing precedent**, and it already exists in this exact repo. Per its own description: "Audit the stapler-squad backlog automation/reconciliation feature... using ux:review, quality:architecture-review, code:review, and code:is-it-ready... **Use for periodic health checks**." It's explicitly designed as a recurring, whole-feature audit that spans both code and behavior/policy gaps, then routes findings through `sdd:fix-bug`/`sdd:quick`/`sdd:full`. It is feature-scoped to backlog automation today, not comment-vs-check-run policy — but the same shape (a periodic audit skill that greps recent PR activity for stale comment-heavy behavior, flags which skill produced it, and files a fix) is a plausible, low-net-new-infra answer to "what re-audits this over time," rather than inventing a new mechanism from scratch.
- **No skill in this repo's `.claude/skills/` or the shared `~/dotfiles/.claude/skills/` currently audits *prompt-text conformance to a stated convention* as its primary job** — closest is `meta:context-audit` and `meta:refine`, both generic prompt-quality tools, not convention-specific. If the plan phase wants a hard guarantee (not just a periodic nudge), the realistic options are: (a) a recurring `backlog-feature-improvement`-shaped audit skill scoped to this convention, run periodically (matches the "no compiler exists" reality — accept it's advisory, not enforced), or (b) narrow the RPC surface itself (e.g. split `PostPRComment` into an "actionable" vs "status" variant with different logging/telemetry, so at least *volume by type* is measurable even though nothing blocks a skill from misusing either) — a code-level partial mitigation for a policy-level problem.

## 4. Measurement pitfall (acceptance criterion 2: "comment volume drops measurably")

**What's actually measurable, cheaply**: `gh api repos/{owner}/{repo}/issues/{pr}/comments` and `.../pulls/{pr}/reviews` counts (or the `comments` field already returned by `gh pr view --json comments`, which `pr-refine/SKILL.md:40` already uses) give a per-PR comment count with no new instrumentation. A before/after comparison could aggregate this across a fixed window of merged PRs (e.g. `gh pr list --state merged --search "created:<range>"` fanned out to per-PR comment counts).

**What can go wrong with a naive before/after**:
- **Survivorship/selection bias**: PRs that get fewer automated status comments may *also* look cleaner because they had fewer problems to begin with (less CI churn, no rebase conflicts needing multiple "still working on it" updates) — comparing raw average comment count before vs. after conflates "the convention worked" with "the PRs in the after-window happened to need less back-and-forth." Need to normalize by something like PR size, number of CI runs, or number of review rounds, or bucket by whether a PR needed *any* remediation cycles at all.
- **Denominator drift / seasonality**: PR volume and type mix isn't stable — a sprint with more one-line doc PRs (near-zero comments either way) dilutes a comparison against a sprint with more complex multi-round PRs. A raw "total comments this month vs last month" figure moves with volume, not with the policy change. Needs at minimum comments-per-PR (not just total), and ideally restricted to PRs that went through the automation this ticket touches (backlog-shepherded / pr-ship-shepherded), since human-only PRs are an unrelated population the convention doesn't affect at all.
- **Attribution**: the repo already distinguishes `forwardSyncCloseComment` (`server/services/backlog_github_forward_sync.go:32`) as one deliberate, out-of-scope comment source — any measurement needs to exclude it (and any other human/bot comment sources like Copilot review comments, which `pr-ship/SKILL.md:159-165` already special-cases) from the "automation noise" count, or the before/after will be measuring a mix that this feature can't move.
- **What "requires attention" (criterion 2's second clause) can't be measured by count alone**: a lower comment count could just mean automation posts less *and* still posts non-actionable status noise — the acceptance criterion bundles "volume drops" with "remaining comments require attention," but only the first half is a number GitHub's API can give you directly. The second half needs either manual/LLM-graded sampling of remaining comments post-migration, or a proxy signal (e.g. tag automated comments with a marker distinguishing action-item vs status at post time, per the point-3 RPC-split idea, so "action item %" becomes a derivable metric instead of a manually-judged one).

## Summary of blocking/high-priority findings for Phase 3 (plan)

1. **Checks API write access is unavailable to this app's current PAT/OAuth-token auth model** — this is the single biggest scope risk in the whole ticket and should be resolved as an explicit decision (Statuses API fallback vs. new GitHub App vs. defer) before implementation, not discovered mid-build.
2. The convention has no code-level enforcement point available (unlike the interface-pollution/primitive-obsession precedents) — plan for a recurring audit skill (extending or paralleling `backlog-feature-improvement`) as the realistic enforcement mechanism, and set expectations that it's advisory, not compiler-guaranteed.
3. Before claiming "comment volume dropped," define the metric (comments-per-shepherded-PR, excluding `forwardSyncCloseComment` and human/bot comments) up front, not after the fact — otherwise acceptance criterion 2 is unfalsifiable.
