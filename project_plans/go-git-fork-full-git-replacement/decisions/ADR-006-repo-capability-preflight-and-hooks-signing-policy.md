# ADR-006: Repo-capability preflight routes unsupported repos to the CLI; hooks and signing policy

**Status**: Proposed, NEEDS USER DECISION on hooks/signing (open decision O-2)
**Date**: 2026-10-08

## Context
go-git does not run hooks, does not honour `commit.gpgsign`/`gpg.format=ssh`/`gpg.program`, does not apply clean/smudge filters (LFS), does not model sparse checkout in status, does not handle a split index (`link` extension returns `ErrUnknownExtension`, `plumbing/format/index/decoder.go:308`), and has shallow-repo bugs (#2409), CRLF/attribute status divergence (#436). (research/pitfalls.md 2.1.) Correction: research/pitfalls.md 2.1 says go-git supports index v2 only; go-git v5.19.2 decodes v2 to v4 (`decoder.go:19`) and encodes v2 to v4 (`encoder.go:17,144`) and models `SkipWorktree` and `IntentToAdd` (`index.go:150-153`). Optional extensions (UNTR, FSMN, REUC) are dropped on write, which is harmless. Task 0.2.3b round-trips real v3/v4 indexes to confirm; index version alone is not a CLI route.

## Decision
- **Config comes from our own resolver, not go-git's.** go-git's `config.LoadConfig` returns after the first existing global file (`config/config.go:183-194`), so on the maintainer's machine, where `~/.gitconfig` exists, `~/.config/git/config` is never read; it knows only `/etc/gitconfig` as the system file (the macOS Command Line Tools file is `/Library/Developer/CommandLineTools/usr/share/git-core/gitconfig`); and it follows no `include`/`includeIf` and no `GIT_CONFIG_*` variable. A `session/git/native/gitconfig` resolver reads system (union of candidate files, lowest precedence), XDG, `~/.gitconfig`, repo config, `config.worktree` (when `extensions.worktreeConfig` is set) and `GIT_CONFIG_COUNT/KEY/VALUE`, honours `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM`, and expands `include`/`includeIf` (`gitdir:`, `gitdir/i:`, `onbranch:`, `hasconfig:remote.*.url:`) to depth 10, at the position of the directive, returning the include closure for cache keys. Its output is checked against `git config --list --show-origin --show-scope --includes -z` over a fixture matrix (oracle test); disagreement is a failing test. **It does not use go-git's `plumbing/format/config` decoder** (revision 4, adversarial N4; reproduced against v5.19.2): the decoder merges repeated sections so an `[include]` between two `[core]` blocks loses its position, and it decodes a bare `gpgsign` and `gpgsign =` both to the empty string while git reads true and false. The resolver has its own tokenizer (`parse.go`), enforced by a depguard deny rule on go-git's two config packages for `gitconfig` and the capability detectors.
- **`hasconfig:remote.*.url:<glob>` is implemented, not feared** (revision 4, adversarial N3; reproduced against git 2.50.1). Git evaluates it after the remote URLs of the whole scope sequence are known: a lazy first pass walks every file and the command scope with every `hasconfig` condition treated as true and collects `remote.<name>.url` values (not `pushurl`, not `insteadOf`); the main pass then includes the target iff any URL matches the glob under `wildmatch` with `WM_PATHNAME` (`*` stops at `/`, `**` is special only as a whole path component, case-sensitive). Git **dies** (and so does the resolver, which routes to the CLI) if a file read through any true `includeIf` defines a remote URL, and git 2.50.1 **segfaults** on a bare `remote.<n>.url` key while this pass runs, which the resolver also treats as fail-closed. Any other `hasconfig:<key>:` is false. A glob containing `[` or a backslash is not ported and fails closed. The maintainer's config (10 `hasconfig` includes reached through an unconditional include) resolves normally.
- **`includeIf "gitdir:"`** matches the per-worktree git dir, `<CommonDir>/worktrees/<name>` for a linked worktree (VERIFIED), and for symlinked parents git's answer depends on `$PWD` (VERIFIED), so the resolver evaluates a logical and a real candidate and fails closed if the two resolutions differ.
- **Hooks and signing are never cached.** They are re-evaluated on every mutating operation: all of them, not only `Commit`/`Push`/checkout/`Merge` (`post-index-change` and `reference-transaction` can fire on `Add`, `Remove`, `Restore`, `BranchRename`, `BranchDelete`, `SetUpstream`). Resolution: read the `.git` file for linked worktrees to find `GitDir` and `CommonDir`; the effective hooks directory is `core.hooksPath` from the resolved config if set, else `<CommonDir>/hooks`; **a repo has hooks iff that directory holds any executable regular file (or symlink to one) whose name does not end in `.sample`**, and any `hook.*` config key also counts. No hook-name list is kept (git's list is long, includes `post-rewrite`, `post-index-change`, `pre-merge-commit`, `pre-rebase`, `post-update`, `push-to-checkout`, and grows). Signing: `commit.gpgsign` (plus `tag.gpgsign`, `push.gpgSign` for push), `gpg.format`, `gpg.program`, `user.signingkey` from the resolved config, with git's boolean parsing (a bare key is true). This costs microseconds and has no invalidation problem. (The previous design invalidated on `.git/hooks` directory mtime; that is wrong for linked worktrees where `.git` is a file, does not change on `chmod +x` or hook edits, and ignores `core.hooksPath`, `init.templateDir` and global/system config. Adversarial B1.)
- **Only expensive facts are cached**: filter drivers such as LFS, index extensions (split index), sparse checkout, shallow, submodules, SSH `ProxyCommand`/`ProxyJump`/`Match` for the remote host. A filter counts only when an attribute source assigns `filter=<name>` **and** the resolved config defines `filter.<name>.clean|smudge|process` (a global `git lfs install` defines `filter.lfs.*` for every repo, so config alone must not route). Attribute sources: every tracked `.gitattributes` (nested ones included), `<CommonDir>/info/attributes`, `core.attributesFile` (default XDG path), system `gitattributes`. Cache key: resolved `CommonDir` plus content hashes of every file in the config include closure and of each attribute source, never a directory mtime.
- **Fail closed, but only where justified** (exact list for the full resolver v2, plan Story 1.3.4 (c) FC1 to FC11; the `FC` prefix keeps these distinct from fork patches F0 to F5. Revision 6: only the conservative **resolver v1** is in the first appetite: it reads every `include`/`includeIf` target regardless of condition and routes on key presence anywhere in the closure, so it over-detects and errs toward the CLI, because the literal "any include routes to the CLI" rule would route every repo on the maintainer's machine): an include target that exists but cannot be read; a tokenizer parse error (git dies with `bad config line`); include depth over 10 or a cycle; an `includeIf` keyword other than `gitdir:`, `gitdir/i:`, `onbranch:`, `hasconfig:`; a `hasconfig` glob with `[` or a backslash; a remote URL inside a true-`includeIf` file, or a bare remote URL key, while the `hasconfig` pass runs; a symlink-ambiguous `gitdir:` resolution; a `~user/` or command-scope relative include path; an unresolvable `commondir`; and any of `GIT_DIR`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_WORK_TREE`, `GIT_CONFIG_PARAMETERS` set in the server's environment (go-git ignores them, the CLI honours them). Each returns reason `capability_detect_error` with a closed sub-reason and routes the operation to the CLI. A missing include target is skipped, as git skips it; a `hasconfig` include whose condition does not match, or whose target defines no remote URL, is not an error. A ceiling (1% of `Capabilities` calls on the maintainer's instance, checked after the first 24 h, in the soak and at the 14-day flip) on `detect_error` stops fail-closed from silently turning a cohort into a no-op.
- **`capability_local_transport` uses the same resolver, not go-git's `insteadOf`** (Re-review 3 R3-4; VERIFIED v5.19.2): go-git applies `url.<base>.insteadOf` only from the repo's own `Storer.Config()` (`config/config.go:373-376`), so a global or included rewrite into a path would reach go-git unrewritten while git would use the path. The preflight applies the resolver to the URL the backend will actually pass to go-git and checks `transport.NewEndpoint(...).Protocol == "file"` for **both the fetch URL and the push URL** (`RemoteConfig.URLs` is `url` entries then `pushurl` entries, `config.go:666`; fetch uses `URLs[0]`, push the last element, `remote.go:84-86,113-114,416`), plus any direct `RemoteURL` option. The `file` protocol tripwire remains the backstop that keeps a miss a routing-quality issue, not a correctness one.
- A repo with any flagged capability routes the affected cohort (the one that would silently differ) to the CLI, emits `git_backend_fallback_total{reason="capability_<name>"}`, and appears in a "CLI-routed repos" debug view. This is permanent behaviour, not a rollout aid, and is an ADR-003 carve-out.
- Default hooks policy (recommended): in-process mutating operations run only when no hook (any executable non-`.sample` file in the effective hooks dir) is present and signing is off. Otherwise CLI. We do not re-implement hook execution in-process.
- Superseded: the earlier "known limit" (includes are not followed, so fail closed whenever any `include`/`includeIf` key exists) is withdrawn. Both of the maintainer's config files contain includes (`~/.gitconfig:4`; `~/.config/git/config:63,74`, VERIFIED by `grep -n include`), so that rule would have routed every operation on the dogfood machine to the CLI with reason `capability_detect_error` at 100%, making the zero-spawn metric and the soak unreachable. Includes are resolved (see above) instead.
- Known limits that remain: system scope is a union of candidate files because we do not spawn `git` to ask which one it reads; the resolver assumes git 2.36 or newer (the first release with `hasconfig`; an older CLI ignores such includes, so the resolver can only add keys, which errs toward the CLI route); the oracle matrix runs on the maintainer's macOS and on CI Linux, and results on other git versions are not verified; `init.templateDir` is not read (templates are copied into `<CommonDir>/hooks` at init, where the hook scan sees them).

## Consequences
- Behaviour never silently weakens for hooked, signed or LFS repos; those repos keep needing a git binary.
- The zero-spawn metric will not be zero on such repos; the gate allow-lists them by capability reason.
- User decision needed: accept this routing (default), or require in-process hook execution (large, not planned).

## Alternatives rejected
- **Run hooks from Go**: re-implements hook environment and semantics; high risk, no stated demand.
- **Ignore the capabilities**: silently skips pre-commit/gpg, a user-visible behaviour change forbidden by requirements (out of scope: "Changing user-visible session behaviour").
