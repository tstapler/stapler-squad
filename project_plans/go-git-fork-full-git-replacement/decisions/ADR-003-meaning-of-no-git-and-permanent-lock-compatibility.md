# ADR-003: What "no git binary at runtime" means, and permanent CLI-compatible locking

**Status**: ACCEPTED for the meaning of "no git" (O-1, user 2026-10-08: "no git means in the stapler-squad server, we don't shell out to git"; agents, `gh`, IDEs and remote hosts running git in their own processes are out of scope). The tier 3 carve-out list below is **under review** (open decision O-14): the user's wording means the server should not spawn `git` at all, and some carve-outs do.
**Date**: 2026-10-08

## Context
Requirements say "runtime works on a machine with no `git` binary installed". But:
- Agent programs (Claude Code, Aider, etc.) run `git` themselves, as separate processes, inside the same worktrees stapler-squad creates. Every session therefore needs a git binary on the machine (research/architecture.md 3.6, INFERRED; confirmed by product purpose).
- `gh`, users' IDEs and shells also run real git against the same worktrees.
- Remote-host worktrees (`session/git/remote_worktree.go:86,103`, `session_service_create.go:372`) run git on a remote machine over SSH; that cannot be in-process.
- Credential helpers are third-party binaries (`git-credential-osxkeychain`, `gh auth git-credential`); spawning them is not spawning `git`, but a Go-native client still execs them.
- go-git writes the index by truncation with no `index.lock` (`storage/filesystem/index.go`, `dotgit.go:237` `IndexWriter` is `fs.Create`), and refs with in-process advisory locks (`dotgit_setref.go`); a concurrent CLI writer can lose a write, and a CLI reader can see a partially written index (research/pitfalls.md section 0; adversarial review B3).
- go-git's `Worktree.Add`/`Commit` call `Storer.Index()` and `Storer.SetIndex()` as separate calls (`worktree_status.go:134,390`, `worktree_commit.go:62,125`), so a `Storer` decorator cannot see the read-modify-write window.

## Decision (recommended default)
Define three tiers:
1. **Server-process scope (the target)**: the stapler-squad server/daemon process spawns **no `git` subprocess** for its own operations on local repositories. Measured by the zero-spawn gate (plan Story 5.3.1) at the `safeexec` seam.
2. **Agent/tool scope (out of scope, permanent)**: agent, `gh`, IDE and user `git` invocations in the same worktrees are not controlled. A git binary remains a prerequisite for the product as a whole. The "no git binary installed" verification is done in a container that runs the server and non-git-using sessions only; it proves tier 1, not that the product is useful without git.
3. **Carve-outs (CLI stays; Revision 7 marks which conflict with "the server does not shell out to git" and so need an O-14 answer: CONFLICT = the server itself spawns `git` locally; NO LITERAL CONFLICT = the server spawns no `git`)**: remote-host worktrees; repos failing the capability preflight (LFS, filters, hooks, gpgsign, split index; not index v3/v4, which go-git v5.19.2 supports); **local-path and `file://` remotes** (`capability_local_transport`: go-git's `file` transport execs `git-upload-pack`/`git-receive-pack`, `plumbing/transport/file/client.go:39-99`, so those clone/fetch/push/pull operations stay on the CLI and the transport is tripwired); operations that write worktree files and are not yet promoted (`unsafe_worktree_write`); third-party credential-helper binaries (exec'd directly, not via `git credential`); the `torn_read`/`object_missing` route unless spike S7 removes the cause; and **`gh`** (`gh pr create`, `session/git/worktree_git.go:581`), which runs git internally and is invisible to every in-process counter (tier 2 `agent_tool`; open decision O-10: keep as carve-out, or replace with the GitHub REST API).

**Carve-out conflict map (Revision 7, for O-14)**. CONFLICT: capability-preflight routing of hooked, gpgsign, LFS, filter and split-index repos (ADR-006 `FC*`); local-path and `file://` remotes (`capability_local_transport`); `unsafe_worktree_write` operations (`Checkout`, `Reset(Hard|Merge)`, `Restore(Worktree)`, `Remove`, `RemoveGlob`, `Move`); the `torn_read`/`object_missing` route; `Commit(Amend)`/`BranchRename`/ref deletes held on the CLI for reflog parity. NO LITERAL CONFLICT: remote-host worktrees over SSH (the runner spawns `ssh`, git runs on the remote host); `gh pr create` (the server spawns `gh`; open as O-10); third-party credential-helper binaries. Nothing is dropped from the list until Tyler answers O-14 per item; the plan keeps the CONFLICT items as counted, ratcheted-down allow-list entries.

**Permanent constraint**: every in-process write the server makes to a repo (index, refs, HEAD, packed-refs, admin files, config) must use the same lock files and atomic-rename protocol the CLI honours (`index.lock`, `<ref>.lock`, `HEAD.lock`, `config.lock`, `worktrees/<n>/...`). This applies after the CLI fallback is removed, because tier 2 processes are always CLI writers. In-process writers are never allowed to "own" a worktree exclusively.

**Mechanism (amended)**: the lock is **operation-scoped**, not a `Storer` hook. A mutating operation (`Add`, `Commit`, `Restore`, ...) runs inside `WithIndexLock(repo, fn)`: (1) create `<GitDir>/index.lock` with `O_EXCL` **before** reading the index (`GitDir` is the per-worktree dir resolved from the `.git` file/`commondir`, not a literal `.git`); contention returns `ErrLocked`, and a pre-existing lock is never auto-deleted, only reported, mirroring git; (2) `fn` reads the real index and its `SetIndex` writes to the held lock file, never to `index` in place; (3) commit by atomic rename of the lock file over `index`; on any error or panic remove only a lock this operation created. Refs: create `<ref>.lock` O_EXCL, write the new value, rename (go-git's in-place inode lock does not exclude the CLI's rename). Read-only operations take no lock. Lock order: `repoWorktreeLock` (ssq-internal mutex plus flock, `session/git/worktree_lock.go`) first, then the CLI-compatible lock. A fork patch (F1) is justified only if spike S4 shows the go-git write path cannot be reached from public API, and then F1 means an operation-level lock API, not a `SetIndex` hook. Verification (S4/Story 2.3.1): lost-update race, a CLI `status`/`add` loop that must never see a corrupt or partial index, error-path lock cleanup.

**Mechanism, second amendment (adversarial re-review N2; all points VERIFIED against go-git v5.19.2 source unless marked)**:
1. **Read-your-writes.** Inside a scope the storer serves `Index()` by decoding the pending lock file once `SetIndex()` has been called. Needed because `Commit(All)` runs `autoAddModifiedAndDeleted` (ends in `SetIndex`, `worktree_commit.go:109-125`) and only then reads `Index()` at `:62`; a stale read commits a tree missing the auto-added changes and returns success. The full `Index()`/`SetIndex()` call-site census is in plan Story 0.2.4 and is pinned by a census test so an upgrade that adds a call site fails CI.
2. **No CLI fallback while a lock is held.** A spawned `git` would meet our own `index.lock` and fail. Routing, capability, hook, signing, reflog-parity and object-existence decisions are made before the scope opens. A fallback-eligible error inside a scope aborts the scope (lock released or removed) and the router may then run the CLI only if the call reports that no irreversible step happened. `Wrote()` is set **before** the first commit-phase rename is attempted (a failed rename is ambiguous), is aggregated over every scope and worktree write of one backend call, and written objects are inert. After an irreversible step the error is returned, never retried. (Revision 4, adversarial C-a.)
   - **Refs are buffered with the index.** The scoped storer holds `<ref>.lock` files and serves ref reads from the pending content, then commits in a fixed order: index rename, then refs (reflog line appended before each rename, `HEAD` last, `packed-refs.lock` last for deletes). An error before the first rename discards ref and index together, so HEAD, refs and index stay mutually consistent. "Atomic" here covers refs and index only, never worktree files.
   - **This order deliberately differs from git's** (Re-review 3 R3-1, VERIFIED with a `reference-transaction` hook on `git commit -a`, git 2.50.1: at `prepared` and `committed` `index.lock` still exists and the index is still the old one, so git moves the ref first and renames the index last). **Transient**: between our index rename and our HEAD/ref rename a reader (a CLI `git status`, the shadow-compare `diffstatus` reader) sees the new index with the old HEAD, i.e. the commit's changes as staged. Acceptable because it is the same state `git add` produces and the state a crash leaves, whereas git's order would leave HEAD-new with the old index, presenting the commit's own changes as staged reversions. No deadlock: ref locks are held across the index rename, so a CLI commit that wins `index.lock` in the gap fails on the ref lock or the old-value check, as in the CLI's own race. Mitigation is a test, not code: a CLI `git commit` started in the gap fails cleanly and leaves no lock; shadow-compare treats a gap observation as a retry, not a mismatch. Stock go-git does the opposite (`Checkout` and `Reset` write HEAD first, `worktree.go:187-196,299-320`, and `Checkout` moves HEAD before `Reset`'s unstaged-changes check), which is why a bare abort would leave HEAD moved and the index old.
   - **Operations that write worktree files stay on the CLI.** `Checkout`, `Reset(Hard|Merge)`, `Restore(Worktree)`, `Remove`, `RemoveGlob` and `Move` cannot be buffered (`Remove` and `Move` delete or rename the worktree file before `SetIndex`, VERIFIED go-git v5.19.2 `worktree_status.go:584-604,651-657,713-742`, so an abort would discard the index change after the file is gone); they are allow-listed `(operation, unsafe_worktree_write)` until a fault-injection test (a write error at every Nth worktree file) shows HEAD, index and worktree always equal the pre-state or the CLI's post-state.
3. **Refs.** `<ref>.lock` (O_EXCL) first, expected old value checked under the lock, then `packed-refs.lock` for deletion, in git's order; go-git's `RemoveRef` unlinks without a ref lock and rewrites `packed-refs` under an inode flock plus temp-and-rename with no `packed-refs.lock` (`dotgit.go:859-1010`), and the CLI's `pack-refs`/`gc`/`branch -d` use `packed-refs.lock`, so the two do not exclude each other unless our writer takes it. go-git's `RemoveReference`, `CheckAndSetReference` and `PackRefs` are not called directly.
4. **Stale locks after a kill.** Agents are the victims of a lock we leave behind, and "never delete" would need a human. Policy (revised, adversarial C-b; inode identity withdrawn because inode numbers can be reused after delete and re-create, so a CLI-created lock could inherit a journaled identity): the process holds a per-instance `flock` for its lifetime (liveness without PID reuse), and for every lock it creates writes an intent record to a journal before `O_EXCL`-creating the file (failure to journal aborts before any lock exists), then creates a temp file carrying a random 128-bit token in its extended attribute and `link()`s it to the lock name (`EEXIST` as with `O_EXCL`, so the token exists from the instant the lock does), and (Revision 6, pre-mortem P1#2(d)) appends the released record **after** it renames or unlinks, so there is no crash window in which a lock is neither recovered nor reported; recovery still deletes only a lock carrying our token, so a CLI lock created in the gap is reported, never removed; a failed creation appends an abandoned record. A lock whose newest record is released or abandoned is never reported at startup. **At startup only** (never on contention) a lock is auto-removed only if all of these hold: the owner's flock is free; the file carries the recorded token; its mtime is at least 60 s old; the server's session registry shows no running session in that repository; and the filesystem supports the attribute. Anything else, however old, is reported with its age and the failed condition and never deleted (git's own rule). Startup scans every journal directory (default, `instances/*`, `workspaces/*`), so a changed `STAPLER_SQUAD_INSTANCE` does not orphan a journal; a missing journal leaves locks reported, listed once in a startup WARN. A crash between the temp-file create and the `link()` leaves a `*.lock.<rand>` temp name, which the scan reports.
5. **Reflog.** go-git writes none (`grep -ril reflog` over non-test source matches only `internal/revision/parser.go`), while the CLI writes `logs/HEAD` and `logs/refs/heads/*` under the default `core.logAllRefUpdates`. Decision: the ref writer appends the reflog line inside the locked ref update (honouring `core.logAllRefUpdates` from the resolved config), and an operation that changes a ref (`Commit(Amend)`, `Reset`, `BranchRename`, ...) stays on the CLI until its reflog parity test against the CLI is green. Losing `git reflog` recovery after an amend is therefore never a silent regression.

**Scope cost for the O-1 decision (R3-6)**: keeping `Checkout`, `Reset(Hard|Merge)`, `Restore(Worktree)`, `Remove`, `RemoveGlob` and `Move` on the CLI narrows the no-git end state. A no-git container can never run the resume and review flows that call `session/vcs/git.go:243-310` (`checkout -b`, `checkout`, `stash pop`, `checkout .`, VERIFIED by reading); `docs/explanation/what-no-git-means.md` must name these as tier-3 carve-outs. (Revision 6 correction: the earlier citation of `session/vc/git_provider.go:563,568` was wrong; those lines are `restore --staged` and `reset HEAD`, index-only operations that are promotable.) This is the conservative direction, and Tyler decides O-1 with that cost visible.

**Revision 6 scope and trust rules (pre-mortem P1#1 to P1#3)**: the in-process write path (`localwrite`, this ADR's locking mechanism) is **stretch**, outside the 3 to 6 week appetite, entered only at plan gate GL. When built it is opt-in per repository (default off, never default-flipped in the first release) and applies only where the session registry shows no running session in that repository (`live_session`), because an agent is always a concurrent CLI writer the server cannot control. In the MVP (reads) the equivalent safety rule is asymmetric trust: a go-git "clean" answer that gates a destructive decision is confirmed by the CLI (`destructive_confirm`).

## Consequences
- The success metric is re-stated with a scope qualifier; plan tasks measure it that way.
- If the user wants tier 2 to be in scope (bundle a git binary, or restrict sessions to non-git agents), this ADR must be reopened; the plan does not cover it.
- Locking work (spike S4, Story 2.3.1) is not optional migration scaffolding; it stays in the codebase.
- `gh` is named as tier 2, so the zero-spawn gate allow-lists it by operation and reason; the no-git container removes `gh` as well and does not exercise PR creation.

## Alternatives
- **Tier 1 plus bundled git binary** (as tmux is bundled): satisfies "no git installed" literally; large artifact, CGO-free release complications, CVE burden (research/build-vs-buy.md option 4). Not planned.
- **Treat the whole machine as in scope**: unachievable while agents call git.
