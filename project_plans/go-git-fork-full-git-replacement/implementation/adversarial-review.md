## Blockers

- [ ] **B1. The hooks and signing preflight can silently skip hooks, which changes user-visible behaviour.** Story 1.3.4 invalidates the capability cache on a `.git/hooks` mtime change. (a) In a linked worktree `.git` is a file and hooks live under `<CommonDir>/hooks`. (b) A directory mtime changes only when a hook is added or removed. It does not change on `chmod +x` or on editing a hook's contents. (c) The detector list omits `core.hooksPath`, `init.templateDir` and global or system config. (d) It also omits hooks that fire on in-process-equivalent operations: `post-commit`, `post-checkout`, `post-merge`, `reference-transaction`, `prepare-commit-msg`. (e) A stale "no hooks" answer routes a commit to go-git and skips a pre-commit secret scanner. The requirements forbid exactly this ("Changing user-visible session behaviour" is out of scope). — Do not cache the hooks and gpgsign decision. Re-stat the resolved hooks dir (`core.hooksPath` via `ConfigScoped(System/Global/Local)`, else `<CommonDir>/hooks`) on every write, which is microseconds. Cache only expensive facts such as LFS and index version. Add acceptance tests for the chmod, `hooksPath` and global-config cases. Fail closed: on any detector error, route to the CLI.

- [ ] **B2. The `refs` cohort is first to flip and rests on an unexplained, documented go-git failure on linked worktrees.** `session/git/util.go:333-345` records two failures: `repo.Head()` erroring right after a CLI `worktree add`, and, in production, go-git returning a syntactically valid SHA that has no object. Failure (2) returns no error. The plan's "named failure mode" error-class fallback (`reason=torn_read`, Story 2.1.2a, "3 x 20 ms") cannot detect it, and no spike reproduces or root-causes it. Epic 6.2 then deletes the CLI fallback, and the Story 5.3.1 allow-list has no `torn_read` entry, so the mitigation that currently protects production is removed. This violates the repo rule "no fix without root cause". — Add spike S7 before Epic 2.1. Reproduce (1) and (2) with a CLI `worktree add` or `update-ref` racing go-git reads on a linked worktree, and identify the cause. Gate G8: the `refs` cohort may not leave `shadow` until S7 has a root cause and either a fix or a detection predicate (for example, verify the object exists before returning a SHA). Keep `torn_read` as a permanent CLI route, allow-listed in the zero-spawn gate and excluded from Epic 6.2 deletion, unless S7 fixes the cause.

- [ ] **B3. The CLI-compatible locking design, which ADR-003 makes a permanent constraint, cannot deliver the property it claims.** Plan section 0.3, Story 0.2.4b, Story 2.3.1 and F1 describe a `Storer` decorator, or a fork patch, that "takes `index.lock`, writes a temp file, renames". go-git's `Worktree.Add` and commit call `Index()`, mutate in memory, then call `SetIndex()` (`storage/filesystem/index.go`). A lock taken only inside `SetIndex` makes the replace atomic but does not stop the lost update. The CLI can take the lock, write and rename between go-git's read and its write, and go-git then renames its stale copy over the CLI's entry. A lock taken in `Index()` and released in `SetIndex()` leaks on every read-only `Status`. Both branches of G4 (in-repo wrapper or fork patch F1) describe the same incomplete mechanism, so the gate decides between two flawed options. The S4 acceptance test only checks lost entries. It never checks a CLI reader seeing a partially written index, which is what happens if the decorator holds the lock but lets go-git write in place. Refs have the same shape: `setRefRwfs` locks the ref inode in place, while the CLI replaces the file by rename. — Specify the design before G4. Use an operation-scoped lock: acquire `index.lock` (O_EXCL) before the read, write the new index to the lock file, then rename, with `ErrLocked` on contention. For ref updates take `<ref>.lock`, write the new value, then rename. Extend the S4 criteria with (a) a CLI `git status` and `git add` loop that must never see a corrupt or partial index while go-git writes, and (b) crash-leftover `index.lock` handling that mirrors git's behaviour (never auto-delete a fresh lock; report it). State that F1 means "an operation-level lock API", not just a `SetIndex` hook.

- [ ] **B4. The zero-spawn gate cannot see all of the spawns the requirements' headline metrics count.** Requirements metric 1 says "measured with a PATH shim counting `git` execs". The plan uses the shim only for the baseline. The gate (Stories 1.3.2 and 5.3.1) counts only at `safeexec.CommandContext(..., "git", ...)`. Gaps found in the repo: (a) tests spawn git outside `safeexec` (10 `exec.Command("git"` sites in `*_test.go`, plus helpers), so "zero spawns in the `session` test package" can pass while tests still spawn git. (b) `gh` is a child process of the server and runs git internally. `session/git/worktree_git.go:581` runs `gh pr create`, and gh's own git calls are invisible to `safeexec`. They also fail in the no-git container, and ADR-003 does not carve `gh` out. (c) `session/vcs/detect.go:123` calls `exec.LookPath("git")` and returns "git not available" without a binary, so VCS detection fails in the Story 5.3.2 container before any backend routing runs. (d) Remote-host runs go through `r.runner.Run(...)`, not `safeexec`, so the "remote_host allow-list" in Story 4.1.3 is vacuous. — Make the gate two-layered. First, run the suite under a PATH where `git` is a recording shim that exits non-zero (or no git at all), and assert zero shim hits outside the allow-list. This is the requirement's own definition. Second, keep the `safeexec` counter for per-callsite attribution. Add `gh` as a named carve-out to ADR-003 and decide whether `gh pr create` stays. Add a Story 5.3.2 task to remove or replace the `LookPath("git")` pre-check in `vcs/detect.go`. Add a test that runs the whole `session` package with `PATH` containing no git.

## Concerns

- [ ] **C1. Gates and the fork-only test are close to unfalsifiable in the "needs a fork" direction.** An operation-scoped lock (B3) and `Reindex()` (verified public) are both in-repo solutions, so G4 and G6 will almost always return "wrapper works". Claim 9 removes F3, and F4 depends only on benchmarks. Net: the fork ends as F0, an empty pinned fork. The plan admits this ("possibly empty on day one"), but the user explicitly chose a 3 to 6 week fork, and the plan pushes the cancel-or-keep question (O-6) to after the spikes. G0 and G2 also cannot fail by construction (G2's "default stays v5" holds unless several conditions all hold). — Put O-6 and the "fork is likely empty" finding in front of Tyler before Phase 1 (G7 currently allows Epics 1.1 and 1.3 to start earlier, which is acceptable). Record up front what evidence would justify a fork patch, so a no-patch result is not read as a failed plan.
- [ ] **C2. The F3 / `capability_index_v3` premise contradicts the v5.19.2 source (claim 9).** The research table says "v2 only; v3 unsupported". The code decodes and encodes v2 to v4 and models skip-worktree and intent-to-add. Fix `research/pitfalls.md` 2.1, ADR-006 and the plan's FallbackReason enum, or add a spike probe in Task 0.2.3b that round-trips a real v3 and v4 index (sparse checkout, `git add -N`). Route to the CLI only for the real gap, which is probably sparse-aware status (#2460). The encoder drops optional extensions (UNTR, FSMN, REUC), which is harmless but should be stated. Unknown mandatory extensions such as a split index (`link`) return `ErrUnknownExtension` (`decoder.go:308`), a safe failure, and that error should map to a CLI fallback reason.
- [ ] **C3. Fork rollback is only proven for an unpatched fork.** Story 1.2.3 deletes the `replace` and runs `make ci` against stock v5.19.3. Once F1 or F2 land with new exported API called from `session/git/backend/gogit`, deleting the line no longer compiles. — Require fork patches to be behaviour-only (no new exported symbols the app calls), or isolate app use behind a build tag with a stock fallback, and add the rollback test to each fork tag's acceptance criteria. Also note that a private fork needs `GOPRIVATE` and a token, and GitHub Actions secrets are not exposed to PRs from forks, so external-contributor CI and Dependabot break. That is another reason to prefer a public fork (O-4).
- [ ] **C4. `shadow` zero-mismatch gate is racy.** The gate (Stories 2.1.3, 6.1.1) requires 7 days with zero `shadow_mismatch_total` on a live instance where agents mutate worktrees. CLI and go-git reads happen at different instants, so some mismatches are inevitable and the clock never completes, or the gate gets waved through. — Compare against a pinned snapshot (for example, resolve both against the same HEAD SHA and index mtime) or re-read-and-retry once before counting a mismatch, and classify mismatches as `racy` or `real`.
- [ ] **C5. Stale repository handles and thread safety are not designed for.** go-git caches the pack index forever per `ObjectStorage` (`object.go:53-71`), and upstream documents the library as not thread-safe (#773). The plan adds a soak (Epic 5.2) but no rule on handle lifetime. — State that the `gogit` backend opens a fresh `*git.Repository` per call (via `OpenRepo`), never caches one across calls, and serialises per repo where go-git requires it. This also interacts with the existing `repoWorktreeLock` (`session/git/worktree_lock.go`, mutex plus flock), which the plan never reconciles with the CLI-compatible lock story.
- [ ] **C6. No week budget or cut line against the stated appetite.** The requirements say "if the scope does not fit, cut scope, do not move the deadline." The plan has about 60 stories (including a 223-site test migration, a credential client, diff and status parity, soak, and rollout stages with 7 to 14 day dogfood windows plus a one-release retirement wait) with 3 to 5 minute task estimates. Dogfood windows alone exceed 6 weeks if sequential. — Add a calendar view, a marked MVP cut (for example refs plus diffstatus plus fixtures), and the order in which scope is dropped. State which windows run in parallel.
- [ ] **C7. Epic 6.2 "CLI retirement" conflicts with ADR-003 and ADR-006 permanent CLI routes.** Hooked, signed, LFS and remote-host repos keep needing the CLI implementation, so most of `session/git/backend/cli` cannot be deleted, and "norawgitcli baseline 0 for that cohort" has an unclear meaning. The same ADR-003 text says the target excludes tier 2. — Reword Epic 6.2 as "remove the cohort flag and the non-capability fallback", keep the CLI backend as a permanent implementation, and correct the "no git binary" wording in Story 5.3.2 accordingly.
- [ ] **C8. Metric and audit details are out of date with the repo.** The existing histogram name differs (claim 4). O-8 is already answered (claim 8), and the unresolved list should be pruned. `git_cli_spawn_total{callsite}` as "bounded by about 62 sites" will drift. Use a function name or allow-list key rather than `file:line`.

### N1. BLOCKER (residual B1): the preflight's config reader is not git's config resolver, and the include rule is wrong for the maintainer's own machine
Per-operation re-evaluation, fail-closed and the linked-worktree `GitDir`/`CommonDir` resolution are sound. The remaining defects are in the inputs the detector trusts (`ConfigScoped`, ADR-006 / Story 1.3.4 (b)):
- `config.LoadConfig` returns after the **first existing** global file (`config/config.go:183-194`, `return ReadConfig(f)` inside the loop). `Paths` yields `$XDG_CONFIG_HOME/git/config`, `~/.gitconfig`, `~/.config/git/config`. Git merges them all. Maintainer's machine (VERIFIED by `grep`): `~/.gitconfig` exists, so go-git never reads `~/.config/git/config`, which holds `init.templatedir`, `[includeIf "gitdir:~/WorkProjects/"]` and `[include]`. A `core.hooksPath` or `commit.gpgsign` there is invisible, and the preflight reports "no hooks, no signing". Only `/etc/gitconfig` is read as system scope, so Homebrew (`/opt/homebrew/etc/gitconfig`) and Apple CLT system configs are missed.
- `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_COUNT/KEY_n/VALUE_n`, `GIT_CONFIG_PARAMETERS`, `GIT_DIR`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR` are not consulted anywhere in go-git (grep of non-test source: no hits). The server's env can carry them, and the CLI path honours them.
- Per-worktree config (`extensions.worktreeConfig`, `<GitDir>/config.worktree`) is accepted as an extension (`repository_extensions.go:52`) but never read, and can set `core.hooksPath` for one worktree only.
- The "any `include`/`includeIf` key means fail closed" mitigation (ADR-006 last bullet) makes every operation on the maintainer's machine route to the CLI, because his `~/.config/git/config` and `~/.gitconfig` both contain includes (VERIFIED: `grep -n include`; `git config --global --list --show-origin` shows `include.path=~/.gitconfig-proxy`). The zero-spawn metric and the soak are then unreachable on the one machine the plan dogfoods on, and the failure is silent (reason `capability_detect_error` at 100%).
- The hook name list is incomplete: `post-rewrite` (amend), `post-index-change` (fires on every index write, so on `Add`), `pre-merge-commit`, `pre-rebase`, `post-update`, `push-to-checkout`. And the "mutating operation" list (Commit, Push, checkout, Merge) omits `Add`, `Remove`, `Restore`, `BranchRename`, `BranchDelete`, `SetUpstream`, all of which can fire `post-index-change` or `reference-transaction`.
- LFS detection scans only `.gitattributes`; git also reads nested `.gitattributes`, `$GIT_DIR/info/attributes`, `core.attributesFile`, and `$XDG_CONFIG_HOME/git/attributes`.

**Recommendation**: do not use `ConfigScoped` for routing decisions. Specify a small own resolver in Story 1.3.4: read all of system (`GIT_CONFIG_SYSTEM`, `/etc/gitconfig`, Homebrew prefix), XDG, `~/.gitconfig`, repo local, and `config.worktree`, in git's precedence order; expand `include.path` and `includeIf` (`gitdir:`, `gitdir/i:`, `onbranch:`; any unrecognized condition kind fails closed) with a depth limit of 10; fail closed if any of `GIT_CONFIG_*`, `GIT_DIR`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_WORK_TREE` is set in the environment. Replace the hook-name list with "any executable non-`.sample` regular file in the effective hooks dir" for any mutating op. Cache keys must include every file in the include closure. Add an acceptance test using the maintainer's real shape: a fixture `HOME` where `~/.gitconfig` exists **and** `~/.config/git/config` sets `core.hooksPath` through an `includeIf`, expecting `capability_hooks`. Add a soak assertion that `capability_detect_error` is below a stated ceiling (for example 1%) on the maintainer's instance, otherwise the cohort is effectively still CLI.

### N2. BLOCKER (residual B3): the operation-scoped lock design breaks go-git's read-after-write inside one operation, and a mid-operation CLI fallback self-deadlocks
The overall design (take `index.lock` with O_EXCL before the read, write to the lock file, rename) does interoperate with git's own protocol: git also creates `index.lock` O_EXCL, writes, and renames over `index`, and a rename is atomic to a CLI reader. With `EnableDotGitCommonDir` the index resolves to the per-worktree dir (`repository_filesystem.go`: `index` and `HEAD` fall through to `dotGitFs`; `refs`, `packed-refs`, `config`, `logs`, `objects` go to the common dir), matching the plan's `GitDir` rule. The decorator is reachable from public API (`git.Open(storer, fs)` with a `Storage` wrapper), so F1 should not be needed. But:
1. **Read-your-writes is broken (VERIFIED in source).** `Worktree.Commit` with `All: true` calls `autoAddModifiedAndDeleted` (`worktree_commit.go:109-125`, ends in `SetIndex`) and **then** reads `w.r.Storer.Index()` again at `worktree_commit.go:62` to build the tree. The plan's `SetIndex()` writes only to the lock file, and its `Index()` "reads the real index". The commit would be built from the stale index and silently omit the auto-added modifications, with a successful return. The same shape (several `Index()` and `SetIndex()` pairs per operation) exists in `worktree.go:375-484`, and `worktree_status.go:134-741`. S4's acceptance tests exercise only `Add`, so they would not catch this. **Recommendation**: specify that after `SetIndex` the decorator's `Index()` returns the pending lock-file content (decode it, or cache the in-memory value), and add S4 criteria for `Commit(All)`, `Commit(Amend)`, `Remove` then `Status` inside one lock scope, comparing the resulting tree with `git commit -a`.
2. **CLI fallback inside the lock deadlocks against ourselves.** If any in-lock step falls back to the CLI (the `torn_read` or `object_missing` retry, a capability error found late), the spawned `git` sees our `index.lock` and fails with "index.lock exists". **Recommendation**: state that routing and capability decisions are made before the lock is taken, and that a mid-operation fallback is allowed only after releasing the lock and only if no write happened; add a test that injects `object_missing` mid-`Commit`.
3. **Refs: delete and packed-refs are not covered.** `RemoveRef` unlinks the loose file with no `<ref>.lock` and rewrites `packed-refs` under an inode flock plus temp-and-rename, with no `packed-refs.lock` (`dotgit.go:859-876, 952-1010`). The CLI (`pack-refs`, `gc`, branch delete) uses `packed-refs.lock`. The plan's mechanism text and S4 mention `<ref>.lock` for set only. **Recommendation**: the decorator must also wrap `RemoveReference`, `CheckAndSetReference` (compare under the lock, not before), and `packed-refs` rewrites, with `<ref>.lock` then `packed-refs.lock` in git's order; add a CLI `pack-refs --all` and `branch -d` racing test.
4. **A killed server leaves a lock that blocks every agent in that worktree.** The repo's own docs describe service restarts killing processes (`make install-service`). Git behaves the same on a killed CLI, but here agents (the permanent tier 2 CLI writers) are the victims, and "never auto-delete" means a human has to remove it. **Recommendation**: keep a small journal (`~/.stapler-squad`) of locks the server created (path plus inode); on startup remove only those whose inode still matches, and report any other lock. This keeps the "never delete a lock we did not create" rule.
5. go-git writes **no reflog** at all (`grep -ril reflog` in non-test source matches only `internal/revision/parser.go`). In-process `Commit`/`BranchRename` therefore skip `logs/HEAD` entries that the CLI writes under the default `core.logAllRefUpdates`. `git reflog` recovery after an amend or reset is lost, and unreachable-object pruning loses its safety net. Add this as a preflight/behaviour-parity item in Story 2.3.2 (either write the reflog line in the locked ref update or route `Commit --amend`, `Reset` to the CLI).

### R2. CONCERN (was B2): S7/G8 is now a sound shape; three gaps to close
Spike S7, the object-exists predicate and the permanent `torn_read`/`object_missing` route do answer the original block. Remaining:
- G8 requires "a root cause and either a fix or a predicate" but Story 0.2.8 allows "if (2) cannot be reproduced the record says so". That outcome cannot satisfy G8 as worded, so the `refs` cohort is either stuck forever or waved through. State the third outcome explicitly: not reproducible then predicate plus permanent CLI route plus a soak ceiling on `object_missing`, and G8 is passed on that basis.
- The documented symptom is a SHA absent from `cat-file`, `rev-list --all`, the reflog and `fsck` in git itself, so the value did not come from any object store. The predicate detects absence only; a stale-but-existing SHA (loose ref deleted by a concurrent `pack-refs --prune`, then read from an old `packed-refs`) passes it. Shadow mode (class `real`) is the only defense for staleness, so keep the shadow gate for `refs` mandatory even when the predicate exists.
- `torn_read` is an error-class mapping and is allow-listed in the zero-spawn gate by (operation, reason). A broad mapping lets any go-git read error be relabelled and escape the gate. Narrow it to typed errors, and fail the soak if `torn_read + object_missing` exceeds a stated fraction of `refs` calls.

### R4. CONCERN (was B4): the two-layer gate is the right shape but still bypassable in the repo as it exists
- **Tests replace `PATH`.** `server/port_owner_test.go:20,39` and `server/services/hook_status_service_test.go:57` do `t.Setenv("PATH", <dir>)` with no original PATH, so a shim on PATH is dropped for those tests (VERIFIED by `grep`). `executor/circuit_breaker_test.go:141` uses an absolute `/usr/bin/git`, which no PATH shim can see. **Recommendation**: add a `norawgitpath`-style check in the gate (grep or analyzer) that fails on `Setenv("PATH"` without preserving the shim directory and on literal git paths.
- **Skip-if-no-git makes the no-git PATH run vacuous.** `session/mcp_integration_test.go:33,149` gate on `exec.LookPath("git")`; with no git they skip and "pass". Story 5.3.1's no-git run must also assert a ceiling on skipped tests (compare the skip count with a committed baseline), or it proves nothing.
- **`go test` result caching** replays a cached pass without running the test, so no shim hit is recorded. Require `-count=1` (and no `-run` filter narrowing) in the gate target.
- **Scope**: the story runs `./session ./server/...` only. Spawns also live in `github/`, `executor/`, `testutil/` and other packages. Run the shim over `./...` and report per package.
- **"records `(argv0, cwd, test name)`" is not achievable**: a child process cannot learn the Go test name. Have `TestMain` or a helper export `SSQ_CURRENT_TEST` per test, or accept attribution by package plus cwd and say so.
- **Allow-list laundering**: the `gitoracle` build tag and "capability fixtures that explicitly require git" are an unbounded exclusion. Keep the allow-list in one file under CODEOWNERS with a ratchet (count may only fall).

### N4. BLOCKER: the public `plumbing/format/config` decoder cannot implement the specified resolver (it loses include position and conflates a bare key with `key =`)

### C-b. CONCERN: the stale-lock journal can delete a live agent's lock through inode reuse, and can leave a blocking one in two more cases

**R3-1. CONCERN: the commit-phase order (index rename, then refs) is the opposite of the CLI's, and the plan does not say so.** VERIFIED with a `reference-transaction` hook on `git commit -a`: at `prepared` and `committed` the `index.lock` still exists and the index content is still the old one, so the CLI moves the ref first and renames the index last. - Release order is "append released record, then rename".
