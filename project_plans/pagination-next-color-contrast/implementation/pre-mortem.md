# Pre-mortem: pagination-next-color-contrast
**Date**: 2026-08-21

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `make build`'s frontend step (Next.js static export → `server/web/dist`) reuses a cached build output that predates the `theme.css.ts` edit, so IT-5.1 reports 0 failed against a binary that never actually contains `#5457ef`, giving a false green. | Accessibility spec passes, but a manual browser check (or a user report) shows the Next button still visibly the old `#6366f1` shade in the deployed app. | Add an explicit content check to Story 1.2.1/Task 1.2.1a — `grep -r "5457ef" server/web/dist` (or the built JS/CSS chunk) — as a hard gate before running the spec, not just an mtime comparison, which only proves *a* rebuild happened, not that it embedded the new value. | P1 |
| 2 | `ReviewQueuePanel.css.ts`'s accentBg-composited border regression (3.50:1 → 2.97:1, WCAG 1.4.11) is documented only in plan.md and a PR description, with no tracked backlog item and no inline code comment — so it ships as invisible debt, and gets independently "discovered" and filed as a fresh bug weeks later by someone running a border/non-text contrast audit, duplicating investigation effort the plan already did. | A future bug report or accessibility audit flags `ReviewQueuePanel.css.ts` tag/banner borders as low-contrast, with no link back to this PR's known-debt callout. | Before merging, file the "recommended follow-up backlog item" Task 1.1.2b only recommends — turn the recommendation into an actual tracked item (`mcp__stapler-squad__create_backlog_item` or equivalent) referencing `ReviewQueuePanel.css.ts:287,429,493` and the 2.97:1 figure, and add a one-line code comment at `theme.css.ts:654` (`accentBg`) noting it's hardcoded independently of `primary` and known to be under the 3:1 floor as composited elsewhere. | P1 |
| 3 | `--update-snapshots` blindly accepts whatever the fresh build renders for `session-list-empty.png`/`omnibar-open.png`, so if any unrelated visual drift (font load timing, an unrelated pending CSS change, a flaky layout shift) is baked into the same screenshot pass, it's silently absorbed into the new baseline instead of flagged. | A later, unrelated PR's visual-regression diff looks unexpectedly large (or unexpectedly clean) because the baseline it's compared against already contains an undetected shift from this PR. | Before staging (Task 1.3.1a), run an actual pixel-diff tool (e.g. `magick compare` or Playwright's own diff output) between the old and new PNGs and confirm the diff region is confined to the button/CTA area — not just an eyeball pass — and note the diff bounding box in the PR body. | P2 |
| 4 | `borderHover`/`accentText` (theme.css.ts:631,657) and `globals.css`'s legacy `--primary` (line 46, consumed by ~9 `.btn-primary` components) stay on the old `#6366f1`, so the app now visibly renders two different indigo shades side by side for the first time — and because that fact lives only in PR-description prose, a designer or user reports it as a fresh "inconsistent button color" regression, unaware it's known, scoped-out debt. | A screenshot-based bug report or design review comment flags two different button/border shades on the same page. | Add the same one-line pointer used for accentBg (item 2) as inline comments at `theme.css.ts:631,657` and `globals.css:46` referencing this PR and the divergence, so grep/blame surfaces the context instead of only the merged PR body. | P2 |
| 5 | The plan's mitigation strategy for every named regression is "call it out in the PR description" — a dense, four-bullet addition to what looks like a one-line CSS fix — so a reviewer skims past it, approves without registering the accentBg/hue-divergence tradeoffs, and no one outside the plan's author actually signs off on shipping the known debt. | Reviewer approval comment/PR history shows no acknowledgment of the callout bullets; the debt is "documented" but never actually reviewed. | Require the reviewer to explicitly ack the callout bullets (e.g. a review checklist item or a required PR template section "known debt shipped — reviewer initials"), rather than relying on prose density alone to carry the disclosure. | P2 |
