# Implementation Plan: insights-session-visibility

**Feature**: Add token-type composition visuals, tag filtering, persistent session-role
attribution, and missing metric tooltips to the Insights dashboard (`SessionTokenSummary`
+ `SessionsTable.tsx` + `SessionDetailContent.tsx`).
**Date**: 2026-09-12
**Status**: Ready for implementation
**ADRs**: [ADR-029: session_role is sourced from a batched snapshot, not a live join](../decisions/ADR-029-session-role-batched-snapshot-not-live-join.md)
**PR split recommendation**: **2 PRs** — PR1 (backend: proto + Go), PR2 (frontend: React/TS), stacked (PR2 branches from PR1).

## PR split reasoning

The four bundled requirements decompose cleanly along the Go/TypeScript boundary that
already exists in this codebase (research/architecture.md §5: "no shared mapper... each
consuming component reads the generated type directly"):

- **PR1 (backend)** touches only `.proto`, `session/tokens/association.go`,
  `session/storage.go`, `session/ent_repository_backlog.go`,
  `server/services/insights_service.go`, `server/dependencies.go`, and their Go tests.
  It is independently buildable, testable (`go test ./server/services/... ./session/...`),
  and reviewable — a reviewer can verify the two new proto fields are populated
  correctly with `ListSessionTokens`/`curl` alone, with no frontend to click through.
- **PR2 (frontend)** touches only `web-app/src/app/insights/*`, depends on PR1's
  generated TS types (`tags: string[]`, `sessionRole: string` on `SessionTokenSummary`)
  already existing on `main`, and is reviewable purely as a UI/UX diff (screenshots,
  Playwright/jest runs) without re-litigating the Go data-sourcing design.
- Splitting avoids a single PR that mixes an ent-query correctness fix (ADR-029's
  ordering collateral fix), a new cross-package Go interface, **and** four
  independent frontend UI additions (chart, chips, role display, tooltips) — each of
  which benefits from being reviewable/revertable on its own. Frontend PR2 cannot
  merge before PR1 (compile dependency on the generated types), so PR1 ships and
  merges first; PR2 branches from `main` after PR1 merges (not from PR1's branch),
  per this repo's flat single-remote (`origin`) convention.
- Both PRs open ready-for-review (not draft) per this repo's override in `CLAUDE.md`.

##### Task 1.3.3a: Add the `sessionRolesForSessions` helper (~4 min)
- In `server/services/insights_service.go`, add (near `buildSessionSummary`):
  ```go
  // sessionRolesForSessions builds a sessionUUID→role map from one unfiltered
  // GetAllItemSessionsWithBacklogInfo scan, keeping the first (most-recently-created,
  // per that query's explicit Order(Desc(CreatedAt))) role seen per UUID (ADR-029).
  func (s *InsightsService) sessionRolesForSessions(ctx context.Context) map[string]string {
  	if s.backlogReader == nil {
  		return nil
  	}
  	entries, err := s.backlogReader.GetAllItemSessionsWithBacklogInfo(ctx)
  	if err != nil {
  		log.Warn("failed to fetch session roles for insights", "err", err)
  		return nil
  	}
  	roles := make(map[string]string, len(entries))
  	for _, e := range entries {
  		if _, exists := roles[e.SessionUUID]; !exists {
  			roles[e.SessionUUID] = e.SessionRole
  		}
  	}
  	return roles
  }
  ```

### Epic 2.2: Tag data + filter UI
**Goal**: Sessions are searchable/filterable by tag, using `Instance.Tags` via the new
`SessionTokenSummary.tags` field.
**Target PR**: PR2

**Design decisions (per research/features.md §2, no existing codebase precedent to copy)**:
- **Multi-select chips, OR semantics** (any selected tag matches) — chosen over a
  single-select dropdown because the requirements doc explicitly calls for
  "chips/multi-select," and OR is the more intuitive default for a table filter
  (research/features.md §2 recommendation). State this decision inline in code via a
  one-line comment at the filter-predicate call site, not a chip-selection ambiguity a
  future reader has to reverse-engineer.
- Chip *toggle* styling is visually similar to but behaviorally distinct from
  `TagEditor.tsx`'s add/remove chips — reuse its `tagItem` CSS class as a base but add a
