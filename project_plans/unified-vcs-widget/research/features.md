# Research: Feature Landscape — unified-vcs-widget

Agent: Research Agent 2 (Features) — SDD Phase 2

## 1. Existing "one component, multiple density modes" conventions in this codebase

The codebase already has an established, working convention for this — **do not invent a new pattern, extend the existing one**:

- **`GitHubBadge`** (`web-app/src/components/sessions/GitHubBadge.tsx`) is the clearest precedent. Single component, `compact?: boolean` prop (default `false`), same data props in both modes. Compact mode is applied via a CSS class swap (`compact` from `GitHubBadge.css.ts`) plus a content change (`repo` vs `${owner}/${repo}` label at line 172) — not a different component tree. It is reused as-is by both:
  - `SessionCard.tsx` (list card, `compact={true}` at two call sites lines 482/488) and again `compact={false}` in an expanded/detail context (line 656)
  - `SessionRow.tsx` (dense table row, `compact={true}` line 272)

  This is the strongest evidence for how the new shared VCS widget should expose its density: **a `compact`/`density` prop on one component, not `VcsWidgetCompact` + `VcsWidgetFull` as separate components.**

- **`VcsStatusDisplay`** (`web-app/src/components/shared/VcsStatusDisplay.tsx`) is already a shared, dumb, presentation-only component reused by both `VcsPanel.tsx` (session VCS tab) and `BacklogItemDetail.tsx` (Version Control section) — see its own doc comment: "Used by both the history detail panel ... and the session VCS tab ... Keep data-fetching out of this component." This is the precedent for the requirement's success metric ("no data-fetching in the shared widget; caller wires status in"). It currently has **no compact mode** — same rendering in both contexts, since both current call sites are already "full detail" contexts. The new unified widget's compact variant is a net-new density tier, not a variant that already exists on this component.

- **`ShipStatusDisplay`** (`web-app/src/components/backlog/ShipStatusDisplay.tsx`) is the fallback sibling to `VcsStatusDisplay`, selected by `BacklogItemDetail.tsx` based on data availability (`vcsStatus ?? shipStatus`), not by an explicit mode prop — this fallback-by-data-presence pattern (rather than a boolean flag) is itself worth carrying into the new widget's "worktree gone, use durable ship status" behavior.

- Other `compact` props in the codebase (`FilesTab.tsx` file-tree row badges, `ReviewQueueBadge.tsx`, `TokenBadge.tsx` "compact cost pill") confirm `compact: boolean` is the house convention over a `size: "sm"|"md"|"lg"` enum or separate component names.

**Recommendation for Phase 3 (plan)**: model the new shared widget as one component (e.g. `VcsWidget`) with a `density: "full" | "compact"` (or reuse `compact?: boolean` to match existing convention) prop, composing the already-shared `VcsStatusDisplay` internally rather than re-implementing branch/clean/ahead-behind rendering, and extending `GitHubBadge`-style compactness to the new GitHub PR/CI section that currently only exists inline in `VcsPanel.tsx`'s `GitHubSection`.

## 3. Edge cases and failure modes

1. **Multiple concurrently-active work sessions for one backlog item.** Current code (`BacklogItemDetail.tsx` line 186): `[...(item?.linkedSessions ?? [])].reverse().find((s) => s.role === "work")` — picks the *last* work-role session in list order, with no concept of "which one is actually running." If two work sessions are simultaneously active (e.g. a retry/rework spawned a second session before the first was stopped), the widget silently shows only one's VCS state and gives no indication a second exists. `UnfinishedItemDetail.tsx` shows a related but different pattern — it lists `worktree.sessionIds` (plural) with a picker UI when `> 1` (lines 128-152) for "which session to reattach," which is a good precedent for surfacing multiplicity, but that's a *reattach* picker, not a *"which VCS state am I looking at"* indicator. **This design must decide**: show a selector, show the union/most-recently-updated, or explicitly flag "N sessions active, showing most recent" — silently picking one (today's behavior) will look like a bug during Phase 3 review.

2. **PR closed without merging.** Confirmed in `github/priority.go`'s `DerivePRPriority` (lines 29-31): `state == "merged" || state == "closed"` both map to `PRPriorityComplete`, and `GitHubBadge.tsx`'s `priorityLabel()` (line 57) renders `PRPriorityComplete` as **"Merged"** unconditionally. **This is an existing bug the new widget must not inherit**: a PR closed-without-merge currently displays as "✓ Merged," which is false. The durable `BacklogItemShipStatus` proto (`proto/session/v1/backlog.proto` line 213, `shipped_via`) is derived independently via `IsCommitOnMain` git ancestry, not GitHub PR state, so it does NOT have this bug — but the *live* session-side GitHub badge does. The new widget combining both should either fix `DerivePRPriority`/`priorityLabel` to distinguish `closed` from `merged`, or make sure the durable ship-status ("Not yet on main") wins visually whenever it disagrees with a stale "Merged" PR badge.

3. **Force-push / rebase after last snapshot.** No existing staleness indicator anywhere in the three surfaces — `VCSStatus` (live, polled) is always assumed current; `BacklogItemShipStatus` (durable) has no "as of" timestamp exposed in the UI (though `last_commit_at` exists in the proto, line 226, it's not rendered by `ShipStatusDisplay.tsx`). If per-file diff stats are persisted durably per this project's scope, they will go stale the moment someone force-pushes or rebases after worktree cleanup with no live session to re-snapshot. **Recommend**: surface the snapshot timestamp (`last_commit_at`) in the widget, and treat "durable per-file diff stats" as inherently a point-in-time snapshot, not a live value — label it accordingly (e.g., "as of {commit_sha} / {date}") so users don't mistake it for live state.

4. **Jujutsu vs Git — does JJ have a "PR" concept?** No, not natively — Jujutsu operates on top of a Git backend and pushes to the same Git remotes, so GitHub PRs are a **remote-and-hosting-service concept, orthogonal to local VCS type**. `VCSType.VCS_TYPE_JUJUTSU` (referenced in `VcsPanel.tsx`, `VcsStatusDisplay.tsx`, `HistoryDetailPanel.tsx`, `WorkspaceSwitchModal.tsx`) only changes how *local* working-copy status is computed (git status vs `jj status`-equivalent) — it does not gate whether GitHub PR/CI data applies. **Confirm in plan.md**: GitHub PR/CI badges should key off "does this session/backlog item have a GitHub remote + PR number," completely independent of `VCSType`. A JJ-backed session pushing to a GitHub-hosted repo should show PR/CI badges exactly like a Git-backed one; the only VCS-type-conditional part of the widget is the local status section (branch/clean/file lists), which `VcsStatusDisplay` already handles correctly via its `vcsTypeName()` switch.

5. **Merged PR with deleted branch.** Already partially handled: `ShipStatusDisplay.tsx` lines 66-75 render `(deleted — already merged)` when `status.branchExists === false`, and suppress the ahead/behind stats in that case. The new widget should preserve this exact fallback text/logic rather than re-deriving it — it's the one edge case among the three source components that's already correctly handled and just needs porting forward.

6. **Compact-context file lists with limited space.** None of the three existing surfaces currently render file lists in a genuinely compact/list-row context — `VcsPanel.tsx`'s categorized file lists (conflicts/staged/unstaged/untracked, each with per-file stats) are always full-width panel content. `UnfinishedItemDetail.tsx`'s compact-adjacent view collapses this entirely into an aggregate: `{changedFiles} files changed +X -Y` (lines 96-109) plus a flat list of *commit messages* (not per-file changes) — no per-file breakdown at all in compact mode. **This is the actual precedent for compact mode's file section**: aggregate count + aggregate +/- only, no per-file rows, with the categorized clickable file list reserved for full/detail density. Plan should treat "show every file with its stat" as full-density-only, and compact mode should show `N files changed, +X/-Y` (already proven in `UnfinishedItemDetail`) with conflicts called out as a count/badge only if `hasConflicts`.

## 4. Unstated needs beyond the explicit three surfaces

The requirements name three surfaces explicitly (Backlog item detail, Session detail, Unfinished item detail), but code inspection surfaces two more candidates that already have a "compact card/row" slot with **zero VCS status today**, which is inconsistent with the stated goal of parity:

- **`BacklogItemCard.tsx`** (the Backlog board/list card, `web-app/src/components/backlog/BacklogItemCard.tsx`) — grepped for `dirty|isClean|hasUncommitted|git|branch`: **zero matches**. The card shows title, status-driven action button, priority, and (for `in_progress` items) a `TriageLoadingIndicator`, but nothing about the underlying git/PR state even though `item.linkedSessions` (used elsewhere in `BacklogItemDetail.tsx`) is presumably available on the same `BacklogItem` type. A user scanning the Backlog board today gets no at-a-glance signal that a card's work has a failing CI check or has been sitting dirty/unpushed — this is a strong candidate for the compact variant even though the requirements doc doesn't name the board card explicitly.

- **`SessionCard.tsx` / `SessionRow.tsx`** (Sessions list, both the card and dense table-row variants) — already show `GitHubBadge` (PR number + priority) via the exact `compact` convention recommended in section 1, but grepped for `dirty|isClean|hasUncommitted|worktreeBranch|vcsStatus`: **zero matches**. Branch name, dirty/clean state, and ahead/behind are entirely absent from the Sessions list — a user has to open a session's VCS tab to learn "is this dirty," even though the PR badge is already inline. Since these components already import and compose `GitHubBadge` in compact mode, wiring in a compact `VcsWidget` alongside it is a natural, low-risk extension of an existing integration point rather than a new one.

**Recommendation**: flag both to the user/PM during Phase 3 planning as optional stretch scope — same shared component, same compact mode already being built for the three named surfaces, wired into two more existing card/row components. This should be called out explicitly rather than silently added, since it wasn't in the requirements' "In Scope" list and could affect the Large-appetite estimate.
