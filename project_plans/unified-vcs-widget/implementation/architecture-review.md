## Concerns

- [ ] **New/residual — Concern #2's fix lacks a parse/narrowing step at the adapter boundary, risking either a compile failure or an unsafe escape-hatch cast that reintroduces the exact bug class the fix targets.** `GithubSummary.prState`/`checkConclusion` are now closed literal unions (Story 1.1.1/Task 1.1.1b, plan.md:183-186) — confirmed correctly declared. But the actual proto source fields they're populated from are plain, unconstrained `string`: `proto/session/v1/types.proto:112` (`string github_pr_state = 33`), `:127` (`string github_check_conclusion = 38`), `:1357` (`string github_pr_state = 23`). Task 1.1.2b ("reads `session.github*` fields into `GithubSummary`") and Task 1.1.4c (owner/repo parsed from a URL, but `checkConclusion`/`prState` sourced similarly) both describe this as a direct read/map with no mention of a validating parse step. As literally specified, `session.githubCheckConclusion` (typed `string` in the generated TS bindings) assigned into a field typed `"success" | "failure" | "pending" | ""` will not type-check under `npx tsc --noEmit` — the same compiler gate Story 1.1.1's own acceptance criteria rely on to prove the union is enforced. An implementer hitting this will most likely reach for an `as PrState`/`as CheckConclusion` assertion to make it compile, which is precisely the "unexpected GitHub API value silently fails to match instead of being caught" risk the original concern's remediation was written to close (a cast doesn't validate — it just silences the compiler).
  **Recommendation**: add a task alongside 1.1.2b (and 1.1.4c) for a small parse/normalize helper — e.g. `function toPrState(s: string): PrState { return s === "open" || s === "closed" || s === "merged" ? s : "open"; }` (or a documented fallback) and its `CheckConclusion` counterpart — so the adapters *parse* the raw proto string into the union (type-driven-design Technique 7, "parse at the boundary"), rather than relying on an implicit or unchecked cast at 3 call sites (`fromSessionVcs`, `fromUnfinishedWorktree`, and Phase 4's `fromShipStatus` extension).

- [ ] **Concern #1 (discriminated union) — RESOLVED**, with one traceability nitpick (see Nitpicks). The `kind: "live" | "historical"` union (Story 1.1.1, plan.md:170-172, 179-180) makes the previously-representable illegal state (`isLive: true` with a non-null `snapshotAt`) a genuine compile error, verified by an explicit acceptance-criteria test asserting a `kind: "live"` value with a `snapshotAt` property fails `tsc --noEmit` — not just documented-by-convention as before. `snapshotCaptureFailed` is correctly scoped inside the `"historical"` branch only.

- [ ] **Concern #3 (aggregate-stats field explosion) — substantially RESOLVED, no regression found.** `aggregateStats?: { filesChanged, additions, deletions }` (Task 1.1.4a, plan.md:240-242) replaces the 3 flat optionals as claimed, and no new flat per-source optional was added anywhere in Phase 3/4's extension of the adapters (Story 4.1.1 populates `github`/`fileChanges`/`snapshotAt`/`snapshotCaptureFailed`, all of which are either pre-existing common fields or already scoped inside the `"historical"` branch — no new top-level optional). The original concern's secondary ask — an explicit pre-Phase-4 audit checkpoint, or a `source` discriminant — was not added as its own task, but the risk it was guarding against is now substantially mitigated structurally: the discriminated union (Concern #1's fix) already scopes `snapshotAt`/`snapshotCaptureFailed` to one branch, so the remaining common-field surface (`loadError?`, `shipped`, `aggregateStats?`) is small and each field's justification is traceable to a specific story. Not a blocker; worth a one-line note in the Domain Glossary if a 4th data source is ever added, but no action required now.

The plan avoids introducing speculative `GitClient`/`GitHubClient` interfaces (which the original remediation's suggested signature had included) by taking the already-fetched `*git.PRStatus` as a parameter and calling `git.FileStatsBetween` as a plain package function — consistent with `.claude/rules/prefer-go-git-over-subshells.md` and the interface-pollution-checklist's "use the concrete type until a second implementation exists" guidance. No interface pollution reintroduced.
