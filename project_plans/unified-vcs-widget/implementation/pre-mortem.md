# Pre-mortem: unified-vcs-widget
**Date**: 2026-07-18

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Epic 3.0's spike verifies go-git `Patch().Stats()` against static, already-existing repo history (a rename + a binary-file commit pair), but never exercises the actual production call shape: `FileStatsBetween(item.RepoPath, wt.BaseCommitSHA, lastWork.LastCommitSha)` invoked synchronously at merge-detection time, using SHAs sourced from a just-torn-down (or about-to-be-torn-down) worktree/branch. If either SHA is unreachable at the moment of capture — e.g. the session branch was deleted (`gh pr merge --squash --delete-branch`, the project's own documented merge convention) before or racing with `CaptureShipSnapshot`, or the local repo never had that commit as a reachable ref — `git.CommitObject()` fails and the file-stats group silently degrades to `snapshot_unavailable` for real merged PRs, not just edge cases. | For most/all newly-"done" backlog items, `ShippedFileStats` stays empty and the widget shows "Couldn't fully capture PR status at ship time" even though nothing is actually wrong with the PR — the core "durable per-file diff stats survive worktree cleanup" success metric silently fails to materialize for the common case, not the exceptional one, while unit tests (built against the spike's static history) keep passing. | Extend Epic 3.0's spike to run `FileStatsBetween` against a *live* worktree branch this project creates and then deletes via the actual `--squash --delete-branch` flow (or the closest available reproduction), asserting SHA resolvability survives the real cleanup ordering — not just rename/binary correctness on pre-existing commits. Add this as an explicit acceptance criterion to Story 3.0.1/3.2.1 before Epic 3.1 schema work is considered validated. | P1 |
| 2 | Synchronous `CaptureShipSnapshot` inside `ReconcilePRPending`'s merge branch adds an unbounded git-repo-open + `Patch().Stats()` + `UpdateBacklogItem` call to every item transitioning to `done`, with no per-item timeout. go-git's typed diff computation is documented to be substantially slower than native `git diff --numstat` on large diffs/history, and the plan never benchmarks this against a realistically-sized diff before committing to the synchronous, no-timeout design. | The reconciler tick visibly slows down after a large PR merges — other unrelated `pr_pending` items in the same tick take longer to reconcile, or (if the reconciler has any overall tick deadline/context) some items are skipped entirely mid-tick, showing up as `~/.stapler-squad/logs/stapler-squad.log` gaps or delayed `pr_pending → done` transitions with no error logged. | Add a wall-clock timing assertion to Epic 3.0's spike (not just correctness) against a realistically large diff in this repo's own history, and wrap `CaptureShipSnapshot`'s `FileStatsBetween` call in a bounded `context.WithTimeout` so a pathologically large diff degrades to `snapshot_unavailable` (already a defined state) instead of stalling the tick indefinitely. | P2 |
| 3 | `VcsWidget`'s compact mode (Task 2.2.1b) intentionally omits `VcsWidgetGithubRow`, on the stated assumption that "PR badge already lives in `GitHubBadge` at compact call sites." Story 2.2.4 (wiring into `UnfinishedItemDetail`) never verifies this assumption for that specific call site or adds a task to render `GitHubBadge` there — yet `fromUnfinishedWorktree` (Task 1.1.4c) does compute `github` data from `wt.githubPrNumber`/`githubPrUrl`/`githubPrState`. If `UnfinishedItemDetail` doesn't already render `GitHubBadge` today, GitHub PR/CI state becomes silently unreachable on that surface post-refactor — a direct violation of requirements.md's explicit "no loss of any feature currently present in any of the three surfaces" success metric. | QA or a user notices the Unfinished-work dashboard card that used to (or was expected to) show PR/CI state no longer does, with no error — it just quietly isn't there, and nothing in the test suite catches it since `VcsWidget`'s own tests correctly assert compact mode omits the GitHub row by design. | Extend Task 2.2.3d's "feature-parity checklist gate" (currently scoped only to `BacklogItemDetail`'s deletions) to cover Story 2.2.4/`UnfinishedItemDetail` as well: explicitly confirm whether `GitHubBadge` is already rendered at that call site today, and if not, add a task to render it alongside `VcsWidget mode="compact"` so the newly-computed `github` data in `fromUnfinishedWorktree` has somewhere to land. | P2 |
| 4 | The Large-appetite (3–6 week) scope is deliberately split into two independently-mergeable PRs (Phase 1+2 frontend, Phase 3+4 backend) specifically so a problem in one doesn't block the other — but that same independence means Phase 3 can stall indefinitely (compounded by failure #1) while Phase 1+2 ships on schedule. Because the widget is designed to "degrade gracefully" to `snapshotAt: null` / "No history captured," a stalled Phase 3 produces no error, no alert, and no visible signal that the project's core promise (historical richness for done items) was never delivered. | The unified `VcsWidget` ships and looks complete/polished across all three surfaces, but weeks later every "done" backlog item still shows "No history captured for this item" — indistinguishable from Phase 3 simply not having shipped yet, with no tracking mechanism surfacing how many done items lack a snapshot. | Add an observability signal (even just a periodic log line or an ad hoc query, since requirements.md explicitly rules out new metrics infrastructure) counting `BacklogItem`s with `status=done AND ShippedSnapshotAt IS NULL`, so a stalled or broken Phase 3 is visible in logs rather than silently indistinguishable from "not built yet." Treat Phase 3's completion as a tracked milestone against the requirements' success metric, not just "independently mergeable." | P2 |
| 5 | Epic 5.2's e2e coverage for the durable-snapshot path (Story 5.2.1) depends on "a seeded `done` backlog item that has a captured snapshot (`ShippedSnapshotAt` non-nil, via a test fixture/seed)" — the plan never specifies how that seed is produced. If it's seeded by writing directly to the DB/ent layer (the easy path) rather than by exercising the real `ReconcilePRPending → CaptureShipSnapshot` code path against an actual merged PR, the e2e suite proves the read/render path works but never exercises the exact SHA-resolution risk in failure #1 — giving false confidence that the feature works end-to-end when only the happy-path read side was ever tested. | The e2e suite is green, `make ci` passes, the feature ships — and failure #1 (or a variant of it) still reaches production undetected, because no automated test ever ran the real capture path against a real squash-merged branch. | Specify in Story 5.2.1 (or Story 3.3.1e) at least one test — Go integration test or e2e — that exercises `CaptureShipSnapshot` against a real `ReconcilePRPending` invocation with an actual merged-and-cleaned-up branch/worktree, not a hand-seeded DB row, so the SHA-resolution risk from failure #1 has a real chance of being caught before merge. | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — **RESOLVED in plan.md.** Story 3.0.1 was extended with a new "Production-shape verification" acceptance criterion and Task 3.0.1d: the spike now additionally resolves a real merged-and-branch-deleted PR's squash-commit SHA pair against the canonical repo path and cross-checks against `gh pr diff --stat`, specifically testing whether commit objects remain resolvable after this project's real `--squash --delete-branch` cleanup — not just static pre-existing history. Task 3.0.1c now updates Story 3.2.1 *and* Story 3.3.1 if the assumption doesn't hold.

## P2 Items (addressed opportunistically, not gating)
- [x] Failure #3 — **RESOLVED in plan.md.** Added Task 2.2.4d to Story 2.2.4 (`UnfinishedItemDetail` wiring): explicitly verifies whether `GitHubBadge` is already rendered at that call site, and adds it if not, so `fromUnfinishedWorktree`'s computed `github` data has somewhere to land in compact mode.
- [ ] Failure #2 (reconciler-tick latency, no timeout) — not patched into plan.md; a reasonable follow-up for implementation time rather than a plan-level gap (Task 3.3.1a already documents that `CaptureShipSnapshot` makes no new GitHub call; a bounded `context.WithTimeout` around `FileStatsBetween` is a one-line addition an implementer should make while writing Task 3.3.1b — noted here so it isn't lost).
- [ ] Failure #4 (silent Phase 3 stall, no observability signal) — not patched into plan.md; the project's Observability Plan already covers structured logging on capture failure, and requirements.md explicitly scopes out new metrics infrastructure. Worth a lightweight log-line count of `done AND ShippedSnapshotAt IS NULL` items if Phase 3 ships noticeably later than Phase 1+2, but not worth gating the plan on now.
- [ ] Failure #5 (e2e seed data bypasses the real capture path) — not patched into plan.md as a new story; validation.md's e2e test design should be checked against this concern at Phase 4/5 boundary (seed via the real `ReconcilePRPending` path where feasible, not a hand-written DB row) rather than adding scope here.
