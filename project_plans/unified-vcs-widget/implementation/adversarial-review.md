# Adversarial Review: unified-vcs-widget

**Date**: 2026-07-18
**Verdict**: CONCERNS

**Addendum (post-fix, same date)**: a fix pass has since resolved 8 of the 9 Concerns below directly in `plan.md`/`decisions/`: duplicate ADR files were deleted (only the canonical `ADR-001-no-new-diff-rendering-library.md`/`ADR-002-ship-snapshot-fields-on-backlog-item.md`/`ADR-003-mergeability-state-synthesis.md` set survives, matching what plan.md actually implements); the failure-sentinel conflation was replaced with a dedicated `ShippedSnapshotCaptureFailed` field plus per-source independent-failure handling (verified independently by the architecture re-review); a go-git spike (Epic 3.0/Story 3.0.1) now runs before Epic 3.1's schema work; a multi-session indicator task was added (2.1.2f/2.2.3f); a feature-parity checklist task was added before the legacy-deletion task (2.2.3d); a 44×44px touch-target acceptance criterion was added (2.2.1i); ADRs were promoted to `docs/adr/ADR-024/025/026-*.md`; and the rate-limiter reuse is now explicitly confirmed in Task 3.3.1a (no new GitHub HTTP call is made by `CaptureShipSnapshot` itself). The remaining item — flagging `MergeabilityState`/`MergeabilityPill` as added scope beyond requirements.md's literal In Scope bullets — is a judgment call for the user, not a plan defect; it's called out in the Phase 3 completion summary rather than stripped from the plan, since it fixes an independently-verified bug (`github/priority.go`'s closed/merged conflation) and was UX research's top recommendation.

## Blockers

None. The two items that came closest to blocker-severity (the duplicate ADR files and the failure-sentinel field conflation) are both cheap, localized fixes that don't require re-architecting anything already built — moved to Concerns with a strong recommendation to resolve before Phase 3 starts, since they affect a schema decision that's expensive to change once shipped.

## Concerns

- [ ] **Duplicate, conflicting ADR files under the same numbers.** `project_plans/unified-vcs-widget/decisions/` contains *two* files each for ADR-001, ADR-002, and ADR-003, covering different decisions (or, for 001/003, near-duplicate coverage of the same "no inline diff" decision). Critically, the two ADR-002 files propose **different schemas**: `ADR-002-durable-ship-snapshot-schema.md` adds a dedicated `shipped_snapshot_status` field (`"" | "captured" | "failed"`), while `ADR-002-ship-snapshot-fields-on-backlog-item.md` (the one plan.md's header cites) has no such field and instead overloads `shipped_check_conclusion` with the sentinel value `"failed"` (see Task 3.1.2a, 3.3.1c). An implementer following "ADR-002" without checking which file plan.md means could build either schema. Consolidate to one canonical ADR-001/002/003 before Phase 3.1 starts, and don't let the "insert fields exactly as specified in ADR-002" instruction in Task 3.1.2a survive with two candidate specs on disk.
- [ ] **Failure-sentinel field conflation has no defined partial-failure behavior.** Task 3.3.1c sets `ShippedCheckConclusion: ptr("failed")` when *either* `GetPRStatus` or `FileStatsBetween` errors, wrapping "both...in error handling." But `GetPRStatus` and `FileStatsBetween` are independent calls — if `GetPRStatus` succeeds (yielding real `ApprovedCount`/`ChangesReqCount`) and only `FileStatsBetween` fails (e.g. a pruned `baseSHA`), the plan doesn't say whether the legitimately-fetched review counts are still written or discarded, nor does it distinguish "capture totally failed" from "PR data captured fine, file stats didn't." Reusing `shipped_check_conclusion` (a real GitHub CI-conclusion field) as a magic-string failure marker for the whole snapshot is exactly the "companion boolean smuggled into a string field" smell the project's own type-driven-design conventions elsewhere warn against (see the plan's own `snapshotAt: Date | null` nullable-as-witness reasoning at Pattern Decisions, last row). Adopt the other ADR-002 draft's dedicated `shipped_snapshot_status` field and specify per-source (PR-status vs. file-stats) failure handling explicitly.
- [ ] **`FileStatsBetween`'s go-git dependency (`object.Patch().Stats()`) is an unverified assumption, not a spiked fact.** `research/build-vs-buy.md` §5 recommends it based on the documented API surface ("returns `[]FileStat` with `Name`, `Addition`, `Deletion` fields natively") but the research explicitly frames the open question as "the correctness risk is in *how* it's built" — i.e., acknowledges risk without resolving it. Story 3.2.1's rename/binary-file test cases (Task 3.2.1c) are the *first* place this gets exercised against real data, after Phase 3.1's proto+ent schema work is already built on top of the assumption. Recommend a throwaway spike (run `object.Patch().Stats()` against a real rename and a real binary-file commit in this repo) before Phase 3.1, so a go-git limitation surfaces before schema work is sunk, not after.
- [ ] **Multi-concurrent-session ambiguity is silently carried forward, not decided.** `research/features.md` §3 edge case 1 explicitly flags `BacklogItemDetail.tsx:186`'s `[...linkedSessions].reverse().find(s => s.role === "work")` — picks the last work session with no indication a second one exists — and says "this design must decide" or "it will look like a bug during Phase 3 review." Plan.md's "Unresolved Questions" section claims all three requirements.md Open Questions are resolved, but never mentions this edge case at all — it isn't listed as deferred, isn't given a comment, and Task 2.2.3b threads `latestWorkSession.worktreePath` straight into `VcsWidgetHeader` using the same unexamined selection. Either add an explicit decision (surface a "N sessions active" indicator, matching `UnfinishedItemDetail`'s existing multi-session picker precedent) or explicitly defer it with a one-line note — don't let it pass through unaddressed.
- [ ] **No feature-parity audit gate before the legacy components are deleted.** Requirements.md's top Success Metric is "no loss of any feature currently present in any of the three surfaces," but the only gate before `VcsStatusDisplay.tsx`/`ShipStatusDisplay.tsx` are deleted (Task 2.2.3d) is a `grep` for remaining imports (Task 2.2.3c) — not a verified field-by-field parity check. Story 2.2.2's acceptance criteria describes a parity comparison in prose ("diffed against the requirements' In Scope feature list") but there's no concrete task/checklist artifact that enumerates every field each of the 4 legacy components renders and confirms where it lands in `VcsWidget`. Add an explicit parity-checklist task (even a short markdown table) as a gate before Task 2.2.3d's deletion, not an assumption baked into acceptance-criteria prose.
- [ ] **Touch-target sizing (44px minimum) has no task or acceptance criteria anywhere**, despite `research/pitfalls.md` §5 naming it explicitly as "a common regression when a 'compact' variant shrinks padding/font-size without separately checking the tappable hit area." Compact mode's commit-row expand button, "View Diff"-adjacent affordances, and the refresh button are all candidates. No CSS task (2.1.4c, 2.2.1f, etc.) mentions a minimum hit-area requirement.
- [ ] **`MergeabilityState`/`MergeabilityPill` is unrequested net-new UI scope, not named in requirements.md.** It originates entirely from UX research's opinion ("the single highest-value new UX element") and ADR-003, not from requirements.md's In Scope bullets, which only ask to *combine* existing data from the three surfaces. It does fix a real, independently-verified bug (closed/merged conflation in `github/priority.go`), which is good justification — but it also adds a new 9-member union type, a new sub-component, a new CSS recipe with 9 variants, and ~9+1 dedicated tests (Stories 1.1.5 + 2.1.1) to an already-Large-appetite project whose own requirements doc says "cut breadth rather than slip the timeline." Flag this to the user/PM explicitly as added scope (same treatment the plan already correctly gives `BacklogItemCard.tsx`/`SessionCard.tsx` in Epic 6.3) rather than silently building it as if it were always in scope.
- [ ] **ADRs were never promoted to `docs/adr/` in the target repo**, despite the project's own MDD workflow (CLAUDE.md's phase table) routing Phase 3 ADRs there. Combined with the duplicate-numbering issue above, there's no task anywhere in plan.md to reconcile/renumber/commit these ADRs to the canonical location. (Lower severity than it would otherwise be — `docs/adr/` already tolerates duplicate numbers today, e.g. two `013-*` and three `020-*` files — but still worth a cleanup task before shipping.)
- [ ] **Rate-limiter integration for `CaptureShipSnapshot` is asserted, not wired into a task.** `research/pitfalls.md` §3 explicitly says "any new snapshot-fetch code path must go through the same transport (or at least check `DefaultRateLimiter.IsLimited()` before firing a burst of ship-time snapshot calls)." Plan.md's Risk Control section only mentions rate-limit pressure as a *rollback trigger* ("if... proves risky in practice... it can be disabled"), never as a design requirement inside Tasks 3.3.1a–e. It's likely inherited for free if `GetPRStatus` reuses the existing GitHub HTTP transport — but the plan never confirms this explicitly, and the plan does correctly rule out the bulk-backfill risk (no automatic backfill of pre-existing done items), which was the sharper edge of this pitfall.

## Minors

- Domain Glossary's `CaptureShipSnapshot` entry is self-contradictory ("no new GitHub call is needed... a fresh `GetPRStatus` call captures...") even though Task 3.3.1a's actual function signature (`CaptureShipSnapshot(ctx, item, prStatus, lastWork, wt)`) correctly takes the already-fetched `PRStatus` as a parameter, meaning no redundant call is made. Clean up the wording so an implementer doesn't add a second GitHub call by mistake.
- No explicit confirmation that a synchronous `CaptureShipSnapshot` GitHub call inside `ReconcilePRPending` has a bounded timeout — if GitHub hangs (vs. errors/rate-limits), could it stall the whole reconciler tick for other `pr_pending` items? Likely a pre-existing property of `GetPRStatus`/`IsPRMerged` already, not new risk, but worth a one-line confirmation in the plan.
- `ADR-001-no-new-diff-rendering-library.md` and `ADR-003-diff-viewing-stays-in-existing-modals.md` cover essentially the same decision under two different numbers — same root cause as the duplicate-ADR concern above, called out separately since it's the clearest case of redundant content (not just a numbering collision).
- The God Component risk pitfalls research flagged for `VcsWidget` itself is well-mitigated by the explicit 5-sub-component decomposition (Epic 2.1) with data-acquisition hooks kept out of the presentation layer (Task 2.2.2a) — worth calling out as a genuine strength, not just an absence of a problem.
- The "6th/7th snapshot field" / "snapshot history vs. latest-only" extensibility question for putting fields directly on `BacklogItem` (ADR-002) is already adequately pre-answered in the ADR's Consequences section ("if a future requirement needs multiple historical snapshots... this decision must be revisited") — no action needed, noted as resolved.
