## 1. Comparable engineering orgs / OSS patterns

Sources: [OneUptime — Configure GitHub Actions for Monorepos](https://oneuptime.com/blog/post/2026-02-02-github-actions-monorepos/view), [Khalid Abuhakmeh — Building Mono-Repositories With GitHub Actions](https://khalidabuhakmeh.com/building-mono-repositories-with-github-actions), [github/awesome-copilot GitHub Actions CI/CD best practices](https://github.com/github/awesome-copilot/blob/main/instructions/github-actions-ci-cd-best-practices.instructions.md), [Lukas Joswiak — GitHub Actions + Protobuf](https://lukasjoswiak.com/github-actions-protobuf/), [Currents.dev — How To Speed Up Playwright Tests](https://currents.dev/posts/how-to-speed-up-playwright-tests), [Currents.dev — Playwright Sharding vs. Workers](https://currents.dev/posts/optimizing-test-runtime-playwright-sharding-vs-workers), [Mindbowser — Playwright Sharding Guide](https://www.mindbowser.com/playwright-sharding-guide/).

Consistent patterns across Go+JS/TS monorepo CI setups:

- **Build once, fan out via artifacts, not via re-running the pipeline.** The standard shape is a single `prepare`/`build` job that does codegen + compile once, uploads the result as an `actions/upload-artifact`, and every downstream job (test, lint, e2e) does `actions/download-artifact` instead of re-running `pnpm install` / codegen / compile. This repo already implements this *inside* `build.yml` (the `prepare` job, `.github/workflows/build.yml:75-107`) — but only inside that one workflow. It is not applied across the other 6 workflows that need the same generated code (see §2).
- **Protobuf codegen is treated as a cacheable, single-source artifact**, not something every job regenerates — either build once and share, or cache keyed on `.proto` file hashes so a no-op regen is a cache hit, not a redundant `buf generate` invocation.
- **Test sharding + intra-shard parallel workers are used together, not as alternatives.** For suites in the 100s-of-tests range, the standard tuning is "N shards × M workers per shard," each shard on its own runner. Rule of thumb from the Playwright ecosystem write-ups: start with roughly 1 shard per 2–3 minutes of current sequential wall-clock, and start workers at ~half the runner's vCPU count, then benchmark from there — adding a worker that doesn't cut total time by at least ~10% means the ceiling's been hit.
- **PR-vs-main differentiated pipelines**: fast, narrow checks (compile, lint, unit tests) gate the PR; the full/slow suite (e2e video capture, full benchmark, cross-browser matrix) either only runs post-merge or is triggered selectively via a changed-files gate. This repo already does a version of this — `build.yml` and `mcp-integration.yml` both compute a `detect-changes`/path-relevance gate as a job (not a trigger-level `paths:` filter) specifically so a skip still posts a required-check status (see build.yml:21-34's comment referencing PR #618/#619) — a pattern other orgs solve the same way when required status checks and path-filtered triggers interact badly.
- **Fail fast before expensive stages.** Lint/vet/typecheck should be the cheapest, fastest-reporting stage, run before (or fully decoupled from and faster than) e2e/build stages, so a broken PR gets red feedback in minutes, not tens of minutes.

## 2. Concrete redundant work in THIS repo's workflows

### The "prepare" step (protobuf codegen + ent codegen + `next build` web UI) is duplicated across 7+ workflows

`buf generate` + `go run entgo.io/ent/cmd/ent generate` + `pnpm run build` (the full Next.js static export, including a `retry-with-backoff.sh` around it for `fonts.gstatic.com` — `.github/actions/prepare/action.yml:36-77`) is invoked independently, from a cold job, in:

| Workflow | How it invokes prepare | Redundant with |
|---|---|---|
| `build.yml` | `prepare` job runs it **once**, uploads `gen/`, `session/ent/`, `server/web/dist/` as `generated-files`; `test`, `pty-race-regression`, `integration-coverage`, `build` (6-way matrix), `install-check`, `benchmark-gate` all `download-artifact` instead of re-running it | — (this is the model to replicate) |
| `demo-publish.yml:34-37` | calls `./.github/actions/prepare` composite directly | build.yml's `prepare` |
| `ux-analysis.yml` | calls `./.github/actions/prepare` composite directly | build.yml's `prepare` |
| `e2e-video.yml:91-94` | calls `./.github/actions/prepare` composite directly, **per shard** (2 shards × full prepare) | build.yml's `prepare`, and itself (2x) |
| `goreleaser-check.yml` | calls `./.github/actions/prepare` composite directly | build.yml's `prepare` |
| `mcp-integration.yml:75-78` | calls `./.github/actions/prepare` composite directly | build.yml's `prepare` |
| `registry-validation.yml` | calls `./.github/actions/prepare` composite directly | build.yml's `prepare` |
| `lint.yml:99-103` | runs `buf generate proto` + `ent generate` inline (skips the `next build` — see below) | build.yml's `prepare` |
| `benchmark.yml` | runs `buf generate proto` inline **4 separate times** across 4 different jobs (lines 260, 320, 506, 581), plus `ent generate` once (line 584) | build.yml's `prepare`, and itself (4x) |

Net effect: on a single PR that touches both Go and web-app source, the exact same protobuf/ent codegen work happens roughly **9–12 times** across the workflow suite (once genuinely shared inside build.yml, once each in demo-publish/ux-analysis/goreleaser-check/mcp-integration/registry-validation, 2x in e2e-video's two shards, once in lint.yml, and 4x inside benchmark.yml alone), because GitHub Actions artifacts are scoped to a single workflow run and cannot be shared *across* separate top-level workflow files without an explicit hand-off (`workflow_run` trigger, a shared upstream job via `workflow_call`, or a cross-workflow cache key). Each of those repeats also re-pays `pnpm install --frozen-lockfile` and, where the full composite is used, the Next.js `next build` — the single most expensive step in `prepare` (network font fetch + retry, full static export).

**Root cause**: the repo has *not yet generalized* the build-once pattern it already invented for `build.yml`'s internal jobs to the workflow level. There's no shared "prepare once, every workflow downloads" mechanism across files — each workflow independently re-derives the same generated code.

**Concrete lever**: convert `.github/actions/prepare` (or a subset of it) into a reusable workflow (`workflow_call`) invoked once, with its outputs consumed via `download-artifact` by every other workflow that currently calls the composite action cold — mirroring exactly what `build.yml`'s own `prepare`/`test`/`build` jobs already do internally. A simpler intermediate step: workflows that only need Go to compile (not a real UI) — e.g. `mcp-integration.yml`, `goreleaser-check.yml` — could skip the expensive `next build` entirely and substitute lint.yml's existing "web dist stub" trick (`lint.yml:109-112`, a one-line `index.html` stub satisfying `go:embed`) since they never exercise the actual UI.

### The bundled-tmux native build is cached, but only inside `build.yml`

`grep` confirms `build-tmux.sh` / the `tmux-3.4-` cache key appears **only** in `build.yml` (4 of its jobs: `test`, `pty-race-regression`, `integration-coverage`, `benchmark-gate` — each with its own independent `actions/cache` step keyed `tmux-3.4-${{ runner.os }}-v1`, `build.yml:238-247` etc.). Any other workflow that needs a working tmux binary (none of the read files here do directly) would rebuild it uncached from `third_party/tmux` — a native C autotools build, non-trivial wall-clock. Within `build.yml` itself, the tmux build+cache logic (checkout submodules → install `automake libevent-dev libncurses-dev pkg-config` → cache `bin/tmux` → conditionally rebuild) is copy-pasted near-verbatim across 4 jobs rather than factored into a composite action the way `prepare` is — the *cache* prevents redundant rebuild work on a cache hit, but every job still repeats the `apt-get install` and cache-lookup steps.

### `lint.yml` is one large serial job, not parallelized internally

Unlike `build.yml` (job-per-concern, run in parallel), `lint.yml`'s single `golangci` job runs ShellCheck → Go setup → pnpm/node setup → buf install → pnpm install → proto gen → ent gen → Jest → web-dist-stub → golangci-lint (main) → golangci-lint (complexity/dupl gate, a **second full golangci-lint invocation**) → jscpd → import-cycle check → ESLint → CSS lint → gofmt check → feature-catalog validation, all sequentially in one job. Two separate `golangci-lint-action` invocations in the same job (`lint.yml:114-120` and `144-150`) each pay their own tool-cache/lint-cache overhead and re-walk the same source tree — that's a second lever independent of the cross-workflow "prepare" issue: this job's internal steps are mostly parallelizable (Jest vs. golangci-lint vs. jscpd vs. ESLint vs. CSS lint touch disjoint toolchains) but are currently forced serial by being one job.

### No `concurrency:` cancellation on `build.yml`, `lint.yml`, `mcp-integration.yml`

`grep` for `^concurrency:` finds it only in `benchmark.yml`, `e2e-video.yml`, `ux-analysis.yml`. `build.yml` and `lint.yml` (the two most expensive per-PR workflows, ~18m/~12m avg) have no concurrency group — a rapid sequence of pushes to the same PR lets multiple full runs of these queue and execute (or contend for shared runner capacity) rather than the superseded run being cancelled. `build.yml`'s own comment (lines 375-390) shows the author is already aware of this class of problem (guards a PR-comment *mutation* against out-of-order runs by re-checking `pr.data.head.sha`), but that's a narrower fix than cancelling the whole superseded run the way `e2e-video.yml` does (`concurrency: group: e2e-video-${{ github.event.pull_request.number }}, cancel-in-progress: true`).

### `demo-publish.yml` — root-caused, not just "an outlier"

Confirmed root cause for its ~136m average / 202m max, distinct from the other findings above:

1. **Trigger is `workflow_dispatch` only** (`demo-publish.yml:7-8`) — despite the file's header comment claiming "Runs after PRs merge to main," there is no `push`/`schedule` trigger in the file. It does not run automatically per merge today; whatever is invoking it does so manually or via an external scheduler not visible in this file. This is a documentation/behavior mismatch worth flagging regardless of the CI-speed work.
2. **It runs the entire Playwright suite with no spec filter and no sharding**: `npx playwright test --reporter=list` (`demo-publish.yml:70`) — no `FEATURE_SPECS` allowlist (unlike `e2e-video.yml:127`'s 5-spec curated list) and no `--shard=`. That's all 102 spec files (`find tests/e2e -name '*.spec.ts' | wc -l` → 102, including 5 visual-regression-per-theme variants and 5 terminal-stress files) run as a single sequential job.
3. **`playwright.config.ts` sets `fullyParallel: false` and `workers: 1`** globally (`tests/e2e/playwright.config.ts:24-29`) — every one of those 102 spec files' tests runs one at a time, in one process, repo-wide, for every workflow that invokes Playwright (including `e2e-video.yml` and `ux-analysis.yml`, not just `demo-publish.yml`). Combined with #2, `demo-publish.yml` is the only workflow that pays the full cost of this setting across the *whole* suite instead of a curated subset or a matrix-sharded subset.
4. Uses plain `npm install` (`demo-publish.yml:45`) rather than `pnpm install --frozen-lockfile` used elsewhere — inconsistent with the rest of the repo's pinned/frozen dependency-install convention and slower/less deterministic.

This is **consistent with** (not yet fully proven to be *solely caused by*) compute-bound serial test execution rather than non-billable approval/wait time — the workflow has no `environment:` block or manual-approval gate visible in the file, so there's no structural wait-for-human-approval step to point to; the 136m is very plausibly ~100 sequential Playwright tests × single-worker × video-recording-on overhead. A follow-up (out of scope for this research doc) would be pulling one actual `gh run view` timing breakdown for this workflow to confirm step-level duration, since this doc's baseline table only has wall-clock aggregates.

## 3. Unstated needs (beyond "make it faster")

- **Fail-fast ordering for both humans and the backlog/session-worker agents**: `CLAUDE.md`'s own Users/Consumers context (backlog automation opens PRs and waits on CI) means a slow, undifferentiated "everything runs, nothing prioritized" pipeline costs agent wall-clock too, not just human attention. Cheap/fast signals (lint, vet, unit tests) finishing well before expensive signals (e2e video, benchmark) lets an agent get "your change is fundamentally broken" feedback in minutes and either self-fix or bail before burning 15-40 more minutes of e2e/benchmark compute on a doomed PR. Today `lint.yml` and `build.yml`'s `test` job are independent workflows with no ordering relationship to the expensive workflows (`e2e-video.yml`, `benchmark.yml`) — nothing gates the expensive workflows on the cheap ones passing first.
- **Per-step timing visibility ("why was this run slow")**: none of the workflows currently emit a timing breakdown to `GITHUB_STEP_SUMMARY` or similar — the baseline table in `requirements.md` had to be reconstructed externally via `gh run list`/`gh run view` because there's no first-class "here's where the minutes went" artifact per run. A CI-duration budget/gate (called for explicitly in Success Metrics) needs this kind of structured, machine-readable timing data to alert on regressions before they compound, not just a single pass/fail threshold on total wall-clock.
- **Partial re-run of only failed work**: GitHub Actions natively supports "re-run failed jobs" at the job level already, but this repo's monolithic `lint.yml` job (see §2) means a single failing step (say, ESLint) forces a full re-run of ShellCheck, Jest, both golangci-lint passes, jscpd, etc. — splitting `lint.yml` into parallel jobs would also make failed-job reruns cheaper, which matters more for an agent that's iterating against CI feedback in a loop than for a human glancing at a PR once.
- **Stable required-check names through restructuring**: `build.yml` and `mcp-integration.yml`'s `detect-changes`-as-a-job (not a trigger `paths:` filter) pattern exists specifically to keep branch-protection required-check names always-reporting (build.yml:21-34, referencing PR #618/#619). Any consolidation/restructuring work in this project must preserve that same property — a job rename or a workflow split changes the required-check name GitHub tracks, and a naive split-for-speed refactor could silently reproduce the exact "expected, never reported" deadlock those comments already document a fix for.

## 4. Test sharding/splitting feasibility

| Suite | Count | Current parallelism | Sharding feasibility |
|---|---|---|---|
| Go (`go test ./...`) | 108 packages containing non-test `.go` files (`find . -name '*.go' -not -path './third_party/*' -not -name '*_test.go' \| xargs dirname \| sort -u \| wc -l`); 626 `_test.go` files | `build.yml`'s `test` job already manually shards into 2 groups — `TMUX_TEST_PKGS` (`./session ./session/mux ./session/tmux`, run without `-p 1` per a documented flake-fix) and `REST_TEST_PKGS` (everything else) — run as two sequential `go test` invocations *within one job* (`build.yml:279-289`), plus 2 more fully separate jobs (`pty-race-regression`, `integration-coverage`) already split out to run in parallel *across* jobs | Already partially sharded at the job level; the two `go test` invocations inside the `test` job itself are sequential in the same job rather than parallel jobs — an easy further win is splitting `TMUX_TEST_PKGS` vs. `REST_TEST_PKGS` into 2 parallel jobs (mirroring how `pty-race-regression`/`integration-coverage` were already split out) instead of running back-to-back in one job. `go test`'s own `-p` flag already parallelizes across packages within a single invocation, limited by runner CPU count (`ubuntu-latest` = 4 vCPU) — the ceiling here is more likely CPU-bound than structurally unsplit. |
| Jest (web-app) | 367 `*.test.ts*` files under `web-app/src/` | `lint.yml` runs `npx jest --ci --maxWorkers=4` (`lint.yml:107`) — already worker-parallel within one job | Reasonably well-optimized already; a shard-across-runners split would only help if `--maxWorkers=4` is CPU-starved on `ubuntu-latest`'s 4 vCPUs (i.e., workers ≈ core count already) — worth profiling before adding sharding here, since Jest's already using all available cores per job. |
| Playwright (`tests/e2e/`) | **102** `*.spec.ts` files (`find tests/e2e -name '*.spec.ts' \| wc -l`) — includes 5 near-duplicate `visual-regression.spec.ts` copies (one per theme snapshot dir) and a `terminal-stress/` subdir of 5 stress specs | `playwright.config.ts` sets `fullyParallel: false` and **`workers: 1`** repo-wide (`tests/e2e/playwright.config.ts:24-29`) — every spec's tests run one at a time in a single process. The `workers: 1` setting looks intentional (comment: "Run tests sequentially") — almost certainly because many specs share one live `stapler-squad --test-mode` server instance and would otherwise race on session/tmux state; validating whether that's a hard requirement for *all* 102 specs or only a subset (e.g. specs sharing global backlog/session state vs. isolated component-level ones) is a research question for the architecture-planning phase, not something this doc can resolve from static reading alone. |
