## Concerns

- [ ] **Epic 3.1 (Stories 3.1.1–3.1.5), Epic 3.3, Epic 3.4 — artifact name is a hardcoded string with no single source of truth** — `_prepare.yml` (Task 3.1.1a) uploads an artifact literally named `generated-files`, and every one of the 7 consumer stories (3.1.2–3.1.5) independently re-types that same literal in a separate `actions/download-artifact@v4` step in a different file, as does Epic 3.4's `e2e-video-binary` and Epic 3.3's differently-named `lint-generated-files` (a near-duplicate artifact serving the same purpose under a different name). This is exactly the "hardcoded artifact names/paths duplicated across files with no single source of truth" risk the review brief calls out for the prepare/consume boundary — a future rename of the artifact (e.g. splitting `gen/` and `server/web/dist/` into separate artifacts) requires a coordinated edit across 7+ files with nothing catching a missed one at authoring time (only a runtime "artifact not found" failure in whichever consumer wasn't updated). **Remediation**: declare the artifact name as a `workflow_call.outputs` value on `_prepare.yml` (e.g. `outputs: artifact-name: {value: generated-files}`) and have every consumer reference `${{ needs.prepare.outputs.artifact-name }}` instead of a repeated literal — single source of truth, and a rename becomes a one-file edit.

- [ ] **Epic 4.2, Task 4.2.1d/4.2.1e — `CI-BUDGET-EXCEEDED` is a bare string literal, not a named constant, despite this exact file's own established convention** — `server/services/github_webhook_pr_fix.go` already defines every other action/conclusion string it compares against as a named `const` (`ghActionCompleted`, `ghConclusionFailure`, etc., lines 27–39) and groups the failure-shaped conclusions into a package-level map (`failureShapedConclusions`, line 45). The plan's Task 4.2.1d instead proposes inlining `outputTitle != "CI-BUDGET-EXCEEDED"` directly, with the same literal separately typed into the `build.yml` github-script step (Task 4.2.1c) and the test table (Task 4.2.1e) — a stringly-typed contract crossing the YAML/Go boundary with no compiler check that all three copies stay in sync, and no comment in either file pointing at the other. This is the specific risk the review brief asked to check for. **Remediation**: add `const ciBudgetExceededMarker = "CI-BUDGET-EXCEEDED"` next to the existing `ghConclusion*` constants, use it in the extractor and the test, and add a one-line comment in `build.yml`'s github-script step ("keep this string in sync with `ciBudgetExceededMarker` in server/services/github_webhook_pr_fix.go") so a future rename on either side is at least discoverable by grep.

- [ ] **Epic 4.2, Task 4.2.1c — the job-to-check-run matching logic as specified will not find the check run it's looking for.** The task says to filter `checks.listForRef()`'s results to the entry whose `name` matches `context.job`. `context.job` (`github.job` in Actions expressions) is documented to return the job's **id** (its YAML key, e.g. `test`), not its display `name:` field. `build.yml`'s `test` job (the one Story 4.2.1 targets) is declared `name: Test` (verified: `.github/workflows/build.yml:191-192`) — a check run's `name` is populated from the display name, not the id, so `context.job` (`"test"`) will not case-sensitively match the check run's `name` (`"Test"`). As written this silently fails to find a match, meaning the whole marker-setting step no-ops and Epic 4.2's entire disambiguation mechanism never actually fires — every `timed_out` conclusion on this job keeps triggering the auto-fix webhook exactly as before, defeating the epic's purpose without any visible error (the `github-script` step would just find zero matching check runs). The plan already flags this as something to "verify... before merging," but the review confirms it's not a hypothetical — it's a real string mismatch given `test`'s current `name: Test` override. **Remediation**: either (a) use `github.event.workflow_job.name`/re-derive the display name the same way GitHub does, (b) cross-reference via `actions.listJobsForWorkflowRun` (which maps job ids to their run-time names) before calling `checks.update()`, or (c) drop the custom `name:` overrides on budget-marker-eligible jobs so id and display name are identical, removing the mismatch entirely. Whichever is chosen, add an explicit assertion/test (or a first `workflow_dispatch` dry run that deliberately fails the budget) before relying on this for production traffic.

- [ ] **Epic 4.1 vs. Epic 4.2 — the budget-marker disambiguation covers 1 job while `timeout-minutes:` (a new `timed_out`-conclusion source) rolls out to ~30+ jobs across 14 files.** Story 4.2.1 explicitly scopes the check-run marker to "a small initial set of jobs" (in practice, just `build.yml`'s `test` job per the acceptance criteria). Epic 4.1, in the same plan, adds `timeout-minutes:` to essentially every job that lacks one today — which directly increases the population of jobs that can newly produce a `timed_out` conclusion (already in `failureShapedConclusions`, so already `actionable=true`) as a result of *this plan's own change*, not a pre-existing risk. A job that simply runs a bit slower than its assigned budget on one run (e.g. `pty-race-regression`, `integration-coverage`, any of `lint.yml`'s post-split jobs, both `e2e-video.yml` shards) will still spuriously trigger the auto-fix webhook exactly as before, just now with more jobs capable of tripping it. Compounding this, Story 4.1.2's task list for `mcp-integration.yml` (Task 4.1.2b: `detect-changes: 5`, `mcp-integration: 30`) omits a `timeout-minutes:` for that workflow's own new `prepare` job (added by Story 3.1.3, calling `_prepare.yml`) — inconsistent with Task 4.1.2c, which does budget `e2e-video.yml`'s equivalent `prepare` caller job at `15`. **Remediation**: either extend Epic 4.2's marker mechanism to cover every job Epic 4.1 newly bounds (at minimum the ones most prone to legitimate duration variance — Playwright/e2e jobs), or explicitly record the interim risk (spurious auto-fix triggers on non-`test` timeouts) as an Unresolved Question the way the plan already does for the Aggregate Check and regex-list consolidation, rather than leaving it implicit. Separately, add the missing `timeout-minutes:` to `mcp-integration.yml`'s new `prepare` job in Task 4.1.2b.

- [ ] **Epic 3.2 (Stories 3.2.1, 3.2.2) and Epic 3.3 (Story 3.3.1) — the buf+ent+stub sequence is copy-pasted into 3 separate jobs instead of extracted into a composite action, inconsistent with the plan's own Epic 2.5 precedent.** `lint.yml:83-112`'s 4-step sequence (install buf, `buf generate proto`, ent generate, create `server/web/dist` stub) is ~15 lines. The plan's Task 3.2.1a (`mcp-integration.yml`), Task 3.2.2a (`goreleaser-check.yml`'s `build-smoke-test`), and Task 3.3.1a (`lint.yml`'s own new `lint-prepare` job) each independently re-authors this same sequence inline. This is the identical shape of duplication Epic 2.5 explicitly targets for the tmux build+cache block ("This repo already establishes composite actions as the idiom... a second one collapses 4 near-identical blocks to one definition" — Pattern Decisions table), applied at 3 call sites instead of 4, yet the plan doesn't apply the same fix here. **Remediation**: extract a `.github/actions/prepare-stub/action.yml` (or fold the stub path into the existing `.github/actions/prepare` composite action as an optional `full-build: false` input) so all 3 call sites collapse to one definition, matching the precedent the plan itself sets and cites for tmux.

## Nitpicks

- Epic 3.3's `lint-generated-files` artifact and Epic 3.1's `generated-files` artifact serve functionally equivalent content (buf/ent codegen, one with a full `next build`, one with a stub) under two unrelated names with no naming convention tying them together — worth a one-line note in the Domain Glossary distinguishing them, since a future reader will otherwise reasonably assume they're interchangeable.
- Lens 3, item 9 (embed-stub substitution risking a silent coverage gap vs. `build.yml`'s real build): reviewed and found consciously scoped — `build.yml`'s and `lint.yml`'s own jobs still run a real `next build` on every PR that touches `web-app/` (via `detect-changes`), so `mcp-integration.yml`/`goreleaser-check.yml` switching to the stub doesn't create an actual UI-build blind spot; no finding needed here.
- Lens 3, item 11 (build-vs-buy consistency): plan matches `research/build-vs-buy.md` on every point checked (native `timeout-minutes:` not a custom script or marketplace action, `go-version-file` over pinned versions, build-once/artifact-reuse over Turborepo/Bazel, no Bazel/bzlmod work in any phase) — no deviation found.
