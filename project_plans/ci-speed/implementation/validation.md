# Validation Plan: ci-speed

**Date**: 2026-08-28

## Happy Path Scenario
Given the pre-fix Baseline (requirements.md: `build.yml` ~18m avg/81.5m max, `lint.yml` ~12m avg, 9+ independent Go cache scopes, no `timeout-minutes:` on 11/14 workflow files, and `benchmark.yml`'s `go-tier1` job silently passing while 4/9 target packages fail to compile), when a PR author pushes a commit to an open PR branch, then every workflow the push triggers (`build.yml`, `lint.yml`, `mcp-integration.yml`, etc.) reaches a terminal status faster in aggregate than before — `build.yml`'s `test`/`integration-coverage`/`pty-race-regression` download one shared `generated-files` artifact instead of each regenerating it, superseded in-flight runs for the old commit are cancelled instead of finishing, every job has a bounded `timeout-minutes:` ceiling instead of GitHub's 6-hour default, and `benchmark.yml`'s `go-tier1` job now genuinely fails (not silently passes) if a targeted package doesn't compile — and this observable improvement is what Epic 5.1's post-ship measurement quantifies against Epic 1.2's recorded baseline.

## Before/After Measurement Test

**`ci_speed_improvement_should_be_measurable_and_meet_target`** (equivalent to a migration-reversibility test — this project's analogous "before/after must be measured and compared" gate, since there is no schema migration to reverse)

- **Given**: Epic 1.2 (Task 1.2.1a–c) has recorded a pre-fix baseline in `docs/ci/baseline-time-to-green.md` — median and p90 aggregate per-PR time-to-green, computed as `max(updated_at across a PR's triggered workflow runs) − min(created_at across those runs)`, sampled from the last 15–20 merged PRs as of 2026-08-27, drawn only from a window where every triggered workflow's `on:` config was already stable (avoiding the stale-trigger-config pitfall research/pitfalls.md §0 flagged in `demo-publish.yml`'s own history).
- **When**: Phases 2–4 ship and accumulate a handful of real merged PRs, then Epic 5.1 (Task 5.1.1a–c) re-runs the *identical* `gh pr list --state merged --limit 20 --json number,mergedAt,headRefOid,createdAt` + `gh run list --json databaseId,name,event,createdAt,updatedAt,headSha` methodology against a new sample of ~15–20 PRs merged only after every relevant structural change (Epic 3.1's reusable-workflow migration, Epic 3.3's lint split, Epic 4.1's timeout ceilings) is live, computing a new median/p90 with the same formula.
- **Then**:
  1. The percentage reduction is computed as `(baseline_median − post_ship_median) / baseline_median` and recorded alongside both raw numbers.
  2. Tail latency is re-measured the same way for `build.yml` (baseline 81.5m max / 18m avg) and `mcp-integration.yml` (baseline 46.8m max / 13m avg) and compared against their requirements.md baseline figures — the secondary success signal requirements.md names explicitly.
  3. **Pass**: the percentage reduction is ≥~50% (requirements.md's Success Metric) — result recorded as met, with both numbers and the sample PR list linked in the writeup.
  4. **Fail**: the percentage reduction is <~50% — the writeup does not stop at a bare number. It names which specific phase/epic's expected win did not materialize (e.g. "Epic 3.1 shipped but `mcp-integration.yml`'s queueing time, not compute time, dominates — see requirements.md's Unresolved Question on the 20-concurrent-job limit"), cross-referencing the specific epic responsible, per Story 5.1.1's acceptance criteria.
  5. Either outcome is written to `docs/ci/baseline-time-to-green.md` (or a new `docs/ci/post-ship-measurement.md`) — this task is not complete merely because Phases 2–4's code merged; it requires this measurement to actually run and report a number, matching this repo's "no completion claim without proof" standard (plan.md's own framing of Phase 5's purpose).
- **Distinct from** Epic 4.3's `ci-duration-trend.yml`: that workflow tracks a rolling *per-workflow* average on an ongoing weekly cadence (a different quantity, a regression detector); this test is the one-time *aggregate per-PR* before/after comparison against requirements.md's actual stated success metric — the gap the adversarial review's Blocker 2 identified between the two.

## Test Stack

- **Go unit**: standard `go test`, table-driven style matching this file's existing convention (`TestExtractCheckRunEvent_should_HandleAllActionabilityCases`, `server/services/github_webhook_pr_fix_test.go:57`). New tests live in the same file, use a fake/mock annotations-fetcher (no real HTTP call — see Epic 4.2 Story 4.2.1's acceptance criteria: "since a real HTTP call can't fit that existing pure-function table"). No new test framework or dependency introduced.
- **Static verification**: `actionlint` for new/changed workflow YAML syntax (Task 3.1.1b); `grep`-based guards for the artifact-name literal drift check (Task 3.1.1c) and the dead-workflow reference check (Task 2.7.1a); `go build ./...` / `go vet` as a compile gate for the one Go change.
- **Workflow/integration verification**: for every YAML-only change, the concrete method is "trigger the named workflow (via `pull_request`, `push`, or `workflow_dispatch` as appropriate) and observe the named job/step's behavior in the Actions UI or via `gh run view --log`" — there is no framework here beyond GitHub Actions itself; each row in the Requirement → Test Mapping table above names the exact workflow file, job, and observable signal (cache-hit log line, artifact count in the run graph, annotation text, conclusion value, overlapping timeline windows). Every such verification should be performed at least once on a real triggered run before the corresponding story is merged, per this plan's own `.claude/rules/fix-flaky-tests-dont-defer.md`-adjacent "no completion claim without proof" discipline — a code review of the YAML alone is not sufficient evidence that a cache actually hits or a job actually parallelizes.
- **Measurement tooling**: `gh pr list` / `gh run list` / `gh api` (no new dependency) for Epic 1.2 and Epic 5.1's before/after methodology, and for Epic 4.3's weekly trend script.
