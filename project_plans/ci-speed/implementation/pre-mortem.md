# Pre-mortem: ci-speed
**Date**: 2026-08-28

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Per-PR time-to-green is dominated by GitHub-side queueing/scheduling latency (multiple of the repo's up-to-10-workflows-per-PR, or concurrent PRs from the repo's own backlog automation, contending for the free-tier 20-concurrent-job ceiling), not by any single workflow's compute time — so Phases 2–4's per-job/per-workflow speedups don't move the aggregate metric requirements.md actually asks for. | Epic 5.1's post-ship measurement (or Epic 4.3's rolling per-workflow averages, sooner) shows individual workflows meaningfully faster while aggregate time-to-green barely moves — a divergence between the (compute-only) trend numbers and the (queue+compute) time-to-green number. | Promote requirements.md's Unresolved Question ("does the 20-concurrent-job limit cause queueing delays") from an implementer-discretion note to a blocking Phase 1/2 gate: pull `created_at`→`run_started_at` queue-time delta for a sample of recent runs *before* Phase 2 work starts, and if queueing is a non-trivial fraction of wall-clock, add a concurrency-budget story (fewer workflows triggered per PR via path-filtering consolidation, or a lower per-PR fan-out) to Phase 2/3 scope rather than only compute fixes. | P1 |
| 2 | The 17-epic/87-task scope (Large, 3–6 weeks) stalls after Phase 2's cheap wins ship, leaving Phase 3 (the highest-value redundant-codegen fix), Phase 4 (the CI-duration budget/gate requirements.md calls a hard deliverable), and Phase 5 (the only validation of the 50% target) unstarted or half-done past the appetite window. | Weeks after the appetite window closes, PR history shows only Phase 1–2 epics merged; no PR references Epic 3.1/4.1 and Epic 5.1's measurement never runs, so the project's actual outcome against its own success metric is never known. | Add an explicit mid-project checkpoint (e.g. after Phase 2 ships) that forces a go/reduce-scope call with a stated cut line — name which remaining epic is must-ship regardless of time pressure (Epic 4.1's `timeout-minutes:` backstop, since it's requirements.md's explicit guardrail ask) vs. deferrable (Phase 3's structural consolidation), so a stall degrades to a known partial state instead of an open-ended one. | P2 |
| 3 | The new `_prepare.yml` reusable workflow (Epic 3.1) and its underlying `.github/actions/prepare` composite action become a shared dependency for `build.yml`, `e2e-video.yml`, `registry-validation.yml`, and `ux-analysis.yml` — so one transient failure inside it (a `buf`/`next build`/npm-registry flake) now fails 4+ previously-independent workflows in the same PR run simultaneously, contradicting requirements.md's own stated Risk Control principle ("a regression in one workflow doesn't block all CI"). | A single PR run shows `build.yml`, `e2e-video.yml`, `registry-validation.yml`, and `ux-analysis.yml` all fail at the same `prepare`/`_prepare.yml` step in the same few minutes, where previously only one workflow's own inline step would have hit the flake. | Add retry logic to `_prepare.yml`/`.github/actions/prepare`'s flakiest steps (buf CLI download, `next build`) proportional to its new 4-5x blast radius, and track `_prepare.yml`'s own failure rate as a distinct line in Epic 4.3's trend/annotation output so a rise here is visibly attributed to the consolidation, not misread as 4 unrelated workflow regressions. | P2 |
| 4 | Nothing in the plan stops the same anti-patterns (hardcoded `go-version:` literal, an inline `buf generate`/`next build` sequence outside `_prepare.yml`/`prepare-stub`, a new cache scope) from being reintroduced by a workflow file added or edited after this project ships — Epic 4.3's trend workflow only flags *rolling-average regression on existing files*, so a brand-new workflow with no history gets zero signal even if it fully duplicates the pre-fix pattern. | 3–6 months post-ship, a newly added `.github/workflows/*.yml` uses `go-version: '1.25.0'` and its own copy-pasted `buf generate`/`next build` sequence; Epic 4.3's trend script has no prior baseline for that file so it never warns, and the drift is found only by a manual audit. | Add a lightweight PR-time lint (same shape as Task 3.1.1c's grep guard) that fails when any `.github/workflows/*.yml` file contains a literal `go-version:` key (instead of `go-version-file:`) or an inline `buf generate proto`/`next build` sequence outside `_prepare.yml`/`prepare-stub`, catching a reintroduced anti-pattern at review time instead of via a future audit. | P2 |
| 5 | **[Addressed in plan.md]** The Epic 4.2 Soft-Timeout Wrapper only bounds its own step's duration, not the wrapped job's cumulative time — if a job's un-wrapped preamble (checkout, setup-go, artifact download, tmux build) grows slow, the job can hit its hard `timeout-minutes:` ceiling before the soft wrapper's own threshold is ever reached, reproducing the exact undiagnosable `timed_out`-with-no-marker case Epic 4.2 exists to eliminate. Separately, Epic 4.3's `gh api`-driven trend script could stop appending to `docs/ci/duration-history.jsonl` for weeks while still reporting a green run, with no distinction from the expected "no eligible runs" case. | A `check_run` webhook fires with `conclusion: timed_out` and no `CI-BUDGET-EXCEEDED:` annotation on a wrapper-eligible job, and the auto-fix webhook fires exactly as it did before Epic 4.2 shipped; or, `git log -- docs/ci/duration-history.jsonl` shows no new commits for multiple scheduled runs even though `ci-duration-trend.yml`'s own run history is all green. | **Both halves now in plan.md**: Task 4.2.1b requires measuring each of the 7 wrapper-eligible jobs' real preamble time and verifying `preamble + soft budget ≤ hard ceiling − 3m` before finalizing budgets (raising the hard ceiling, not shrinking the soft budget, if the margin isn't there); Task 4.3.1b requires the trend script to emit a distinct `::error::` on an actual `gh api` fetch/parse failure, not just silently skip the same as the expected stale-trigger-config case. This item was independently corroborated by both the Engineering and UX legs of the Phase 4 Product Triad Review. | P2 |
