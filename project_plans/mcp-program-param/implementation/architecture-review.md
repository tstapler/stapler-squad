## Concerns

- [ ] **Tasks 1.2.1a/1.3.1a — the new `ProgramWarning` check logic is duplicated inline in both `tools_lifecycle.go` and `tools_github.go`, instead of being added to the shared `tools_program_common.go` helper file this same plan created to eliminate exactly this duplication shape.** Both tasks show the identical block verbatim (`plan.md:174-182` and `plan.md:230-238`): same `if lh.svc != nil { if known := programIDs(lh.svc); ... }` / `if gh.svc != nil { if known := programIDs(gh.svc); ... }` structure, same `fmt.Sprintf` message text, differing only in the receiver variable name. This is the same two-file-drift shape the plan's own Tech Debt Disposition table calls out as the reason `programSchemaOptions` had to be extracted in the first place ("Recreates the exact two-file-drift bug this backlog item exists to fix," `plan.md:31`) — the fix for the typo-warning concern reintroduces the pattern the fix for the enum-duplication concern just eliminated. Low risk today (both copies are short and were written together, so they can't have already drifted), but it is exactly the kind of hand-synced duplication this plan otherwise treats as a defect class worth a dedicated helper.
  **Recommendation**: extract a `programWarningFor(svc *services.SessionService, program string) string` (or similar) into `tools_program_common.go` alongside `programIDs`/`programSchemaOptions`, and have both `Task 1.2.1a` and `1.3.1a` call it. Small change, keeps the plan internally consistent with its own stated rationale.

- [ ] **Tech Debt Disposition table's `tools_backlog.go` follow-up is documented but not tracked.** The row now correctly states the gap is "confirmed already broken, not just a theoretical drift risk" and names the exact missing enum values (`plan.md:42`), which resolves the concern's core ask (stop treating a live bug as hypothetical). But the remediation text says a backlog item "should be filed" / "not filed as part of this plan" — no backlog item ID or issue link is actually referenced. This satisfies the weaker of the two remediation options offered in the prior review ("or explicitly note... that this review found a live instance and one is being filed") but leaves the follow-up as a note in a planning doc that, per this project's own convention, won't be re-read later. Not a blocker for this plan, but worth closing the loop before Phase 1 ships.
  **Recommendation**: file the backlog item now and drop its ID into this row, rather than leaving "should be filed" as the final state.

## Nitpicks

- The `ProgramWarning` addition is proportional to the concern it fixes (new AC bullets with Given-When-Then, ADR-001 addendum, Domain Glossary entry — `plan.md:21`, ADR lines 84-98) and correctly preserves warn-not-reject semantics: every AC and task explicitly keeps `success == true` on a warned request and only sets the warning on the non-error `okResult` call sites (`plan.md:147-148, 185, 201, 240`). This is consistent with the plan's own "registration-time snapshot, custom programs added later must still work" principle — a custom program added after server start still succeeds with no warning once it's in `programIDs(svc)`'s live-refreshed list, and an unrecognized name only ever warns, never blocks.
- Adding `ProgramWarning string \`json:"program_warning,omitempty"\`` to `CreateSessionResult`/`CreateSessionForPRResult` is low-risk for existing consumers: `CreateSessionResult` already grew an `omitempty` field once before (`StillCreating`, `server/mcp/tools_lifecycle.go:41-50`) with no apparent breakage, and no test in `server/mcp/*_test.go` was found asserting full-map/struct equality on these result types (`tools_github_test.go:251` only does `m := parseResult(t, res)` followed by targeted key lookups, not a `reflect.DeepEqual` on the whole map). `omitempty` also means the field is absent from the JSON entirely on the non-warning path, so it can't perturb any golden-output test that doesn't already know about it.
- The "Isolate via seam" → "Refactor-first" relabeling is corrected in the Tech Debt Disposition table (`plan.md:41`) and the stated reasoning ("no legacy mess is left wrapped behind an adapter") matches what Epic 1.1 actually does.
