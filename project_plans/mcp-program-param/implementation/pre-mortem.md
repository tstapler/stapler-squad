# Pre-mortem: mcp-program-param
**Date**: 2026-09-24

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Phase 2 (`list_programs`) ships later than Phase 1 or never — the Verification Checklist already marks AC4 "satisfied" by Phase 1 alone, so nothing forces Phase 2 to land in the same PR/release — leaving `ProgramWarning`'s hardcoded text ("Call list_programs for the live list") pointing at a tool that doesn't exist yet in that deployment, and leaving the original backlog complaint (custom program effectively unusable right after registration) unresolved for the exact user who triggers the warning. | An agent receiving `ProgramWarning` calls `list_programs` per its own instruction and gets an "unknown tool" error back; separately, a new backlog item gets filed reporting the original bug again ("my custom program still doesn't work smoothly") because the only live-discovery path was deferred. | Ship Phase 1 and Phase 2 atomically in the same PR/release, and change plan.md's Verification Checklist AC4 row from "satisfied by Phase 1" to "satisfied by Phase 1 + Phase 2" so a partial ship is a visible plan violation, not a silent option. If Phase 2 must ship later anyway, make the warning text generic (name the mitigation as "ask a maintainer to verify the program is registered," not a specific tool name) until Phase 2 is confirmed live. | P1 |
| 2 | `ProgramWarning` is a `json:"program_warning,omitempty"` field on a `success:true` result with no accompanying instruction anywhere (tool description, `programDescription`, or elsewhere) telling the calling model that this field is actionable — an LLM client optimizing for "task succeeded, move on" has no signal to specifically inspect this field, especially when a larger multi-tool-call session compresses/summarizes prior tool output. | A session is created with a typo'd program (e.g. `"clade"`), the tool call reports success, and the agent proceeds as if the session is running normally; the user only discovers the failure later by reading tmux output, exactly the pre-fix failure mode `research/pitfalls.md` §2 already flagged — now merely bounded by a warning nobody consumed. | Add one explicit sentence to `create_session`/`create_session_for_pr`'s `WithDescription` (not just the `program` property's description): "If the result includes `program_warning`, the session was still created but the program value may be invalid — verify before assuming success." Optionally add a validation.md test asserting the warning text is distinguishable/greppable in the raw JSON result a client would see, not just present in the Go struct. | P2 |
| 3 | The Observability Plan's justification for adding no logging ("`config.LoadConfig()` doesn't return an error... the two loops can't fail") is true only in the narrow sense that no error return exists — `config.LoadConfig()` (`config/config.go:1203-1221`, verified by reading it) silently swallows a `GetConfigDir()` failure or an unreadable/corrupt config file and falls back to `DefaultConfig()` (empty `SessionDefaults.Programs`) with only an internal `log.Warn`/`log.Error` that never surfaces to `ListProgramsConfig`'s caller. `programIDs(svc)` inherits this: a transient config-read failure makes every registered custom program vanish from both the enum and the request-time warning check simultaneously, producing spurious "program not recognized" warnings for programs that are, in fact, registered. | A user/agent sees `ProgramWarning` fire for a custom program that worked yesterday and is still visible in the Program Configurations UI; nothing in an MCP-tagged log line explains why — the only trace is a generically-worded `log.Warn`/`log.Error` deep inside `config.LoadConfig`, uncorrelated with the specific request. | Revise the Observability Plan: the risk isn't "`ListProgramsConfig` returns an error" (it can't), it's "`ListProgramsConfig` can silently return a degraded result." Add a `log.Debug`/`log.Warn` at the `programIDs`/`programSchemaOptions` call site logging the returned program count (or specifically warn when it's suspiciously low, e.g. builtins-only when a custom program was previously known), so a config-load degradation leaves a trace at the MCP layer, not only inside `config.LoadConfig`'s own unrelated log line. | P2 |
| 4 | The rate-limiter test-isolation fix (`resetCreateSessionLimiterForTest`, called manually as the first line of each new rate-limited test) is a convention enforced only by code review, not by the compiler, a linter, or `TestMain`. Verified today it's sufficient (only `tools_github_test.go` calls `createSession`/`createSessionForPR`, it's already non-parallel, and Go's test runner defers all `t.Parallel()` tests as a group until non-parallel tests finish, so no race with the parallel tests in `tools_terminal_test.go`/`tools_guidance_test.go`/`tools_backlog_test.go` — none of which call these functions). But nothing stops a future, unrelated PR from adding a 6th rate-limited test in `server/mcp` without the reset call. | An unrelated future PR's new `server/mcp` test starts intermittently failing in CI with `ErrRateLimitExceeded`, reproduces only in full-package runs (not standalone), and nobody connects it to this plan's package-global `createSessionLimiter` convention. | Prefer a structural fix over a remembered convention: give each rate-limited test a fresh limiter via `t.Cleanup`-scoped injection (e.g., make `createSessionLimiter` a field the handler struct holds, defaulting to the package var in production, swappable in tests) or add a `TestMain`/shared `t.Cleanup` that resets it automatically. At minimum, add a one-line note to this repo's Go test-writing guidance (or a lint rule) that any test calling `createSession`/`createSessionForPR` must reset the limiter first, so a reviewer — not CI flakiness weeks later — catches an omission. | P2 |
| 5 | `svc` may legitimately be `nil` in some "test/fallback-transport constructions" (`research/stack.md`, citing `githubHandlers.svc`'s doc comment and `tools_github_test.go:241`), and both the dynamic enum (`programSchemaOptions`) and the `ProgramWarning` safety net are independently gated on `svc != nil` — meaning in that mode, AC4's two named mitigations (schema enum, non-fatal warning) both silently no-op at the same time, and nothing in the plan documents or tests this compound interaction. AC4 in that mode is satisfied only by the static `programDescription` text listing built-ins by name. | If a fallback-transport deployment is ever hit with a typo'd `program`, there is no warning and no enum-level hint at all — the pre-fix failure mode (silent tmux-output-only failure) recurs in full, in a mode the plan's own research flags as real but doesn't explicitly test. | Add a test explicitly exercising the `svc == nil` path end-to-end (not just `programSchemaOptions(nil)`'s schema-shape assertion already planned in Task 1.1.1b): call `createSession`/`createSessionForPR` with a nil `svc` and a typo'd program, and assert the result — even without a warning — still carries the static description's built-in list, so a reviewer explicitly confirms what AC4 degrades to in that mode rather than leaving it implicit. | P3 |

## P1 Items (address before implementation)
- [x] #1 — **Resolved in plan.md** (2026-09-24 repair pass, sdd:4-validate): `programDescription` and both `programWarning` messages (Tasks 1.1.1a, 1.2.1a, 1.3.1a) were changed to say "check the Program Configurations UI, or ask whether a list_programs tool is available in this deployment" instead of asserting `list_programs` exists — a Phase-1-only ship no longer points agents at a tool that might not exist. The Verification Checklist's AC4 row and Phase 2's heading now explicitly recommend (not require) shipping Phase 2 alongside Phase 1, with a follow-up note to tighten the wording back to a direct `list_programs` reference once Phase 2 is confirmed live in the same release.
