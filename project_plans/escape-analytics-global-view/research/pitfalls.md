# Research: Pitfalls — GROUP BY Aggregation + Conditional Hook Pausing

## Driver confirmed

This repo uses **SQLite** for the ent analytics client, not Postgres:
- `session/ent_repository.go:26` — `_ "github.com/mattn/go-sqlite3"`
- `session/ent_repository.go:76,89` — `sql.Open("sqlite3", dbPath)`, `entsql.OpenDB(dialect.SQLite, db)`

This matters for the GROUP BY design: SQLite's aggregate SQL dialect differs from Postgres/MySQL in ways that bite ORM escape-hatch code specifically:
- **No native boolean type** — `mangled` is stored as `0`/`1` (ent maps Go `bool` to SQLite `INTEGER`). `SUM(mangled)` works in SQLite (integer sum), but this is dialect-specific — the same raw SQL would need `SUM(CASE WHEN mangled THEN 1 ELSE 0 END)` on Postgres. Since ent's generated `GroupBy`/`Aggregate` builder (confirmed available — see below) abstracts this, prefer it over hand-written SQL strings so a future driver swap doesn't silently break the mangled-count aggregate.
- **No `FILTER (WHERE ...)` clause** support in older SQLite versions bundled via `mattn/go-sqlite3` — don't reach for `COUNT(*) FILTER (WHERE mangled)` syntax; use `SUM(mangled)` or a `CASE` expression instead.
- **Single-writer lock**: SQLite serializes writers; a heavy aggregate `SELECT` can still block behind or be blocked by concurrent event-insert writes if the DB is in rollback-journal mode rather than WAL. Check `session/ent_repository.go`'s `PRAGMA` setup for `journal_mode=WAL` — if absent, a large global aggregate query risks lock contention against live escape-event ingestion from active sessions.

## ent already has a native GroupBy/Aggregate builder — don't assume raw sql.Selector is required

`session/ent/analyticsevent_query.go` and the generated `EscapeEventQuery` (same generator, confirmed pattern at `session/ent/analyticsevent_query.go:259-304`) already expose:
```go
Query().GroupBy(escapeevent.FieldSequenceType, escapeevent.FieldMangled).
    Aggregate(ent.Count()).Scan(ctx, &results)
```
This is real `GROUP BY` SQL (see `sqlScan` building `selector.GroupBy(...)` at line 474), not client-side aggregation — it satisfies the NFR without touching `sql.Selector` directly. **Recommendation for planning: use ent's `GroupBy`/`Aggregate`/`ent.As`/`ent.Sum` builder, reserve `sql.Selector` only if the two-dimensional histogram (`sequence_type` × `mangled` boolean) needs a shape ent's builder can't express in one query** (e.g. combining the sequence-type histogram and the total mangled count in a single round trip may need two separate `GroupBy` calls — `GROUP BY sequence_type` for the histogram, `GROUP BY session_id` for the per-session breakdown — rather than forcing one query to do both, per the Rabbit Hole already flagged in requirements.md).

## GROUP BY / aggregation pitfalls to design against

1. **Division-by-zero on mangle rate per group.** The existing per-session `GetEscapeAnalyticsSummary` (`server/services/analytics_escape_service.go:176-179`) already guards this (`if totalSeq > 0`). The new per-session breakdown list must apply the **same guard per row**, not just once globally — a session with zero rows in the filtered time range must not appear as `mangleRate: NaN` or divide-by-zero (Go doesn't panic on `float64` div-by-zero, it produces `NaN`/`+Inf`, which then serializes through protobuf as a numeric field and can silently corrupt frontend charts/sort order — explicitly branch to `0` when `totalSequences == 0`).
2. **Sessions with zero escape events should not appear in the per-session breakdown at all** (an `INNER JOIN`-shaped `GROUP BY escape_event.session_id` naturally excludes them, since there's no event row to group), but confirm this is the desired product behavior — requirements.md's "spot the outlier session" implies only sessions *with* activity are useful in the breakdown, so this is likely fine, but worth stating explicitly in the plan so it isn't mistaken for a bug.
3. **N+1 risk if per-session breakdown row also needs a histogram-shape join.** If a future iteration wants per-session *and* per-sequence-type breakdown combined, resist looping in Go over `N` sessions each issuing its own `GroupBy` query — that's the N+1 anti-pattern applied to aggregation. The current scope avoids this (per-session breakdown is flat totals only, no per-session histogram), but flag it as an explicit non-goal if a reviewer proposes drilling down.
4. **Time-range filter must apply before the GROUP BY, not after.** Straightforward with ent's `.Where(...).GroupBy(...)` chaining (filter predicates apply as SQL `WHERE`, which runs before `GROUP BY`), but worth a test case: an event just outside `start_time`/`end_time` must not appear in either the histogram or the per-session totals — a single boundary-condition unit test (`WallTimeGTE`/`WallTimeLTE` at exact boundary) is cheap insurance given the per-session summary endpoint doesn't appear to have this edge case tested today (confirm in Phase 5).
5. **`nil` analyticsClient guard already exists** (`s.analyticsClient == nil` check, line 132-134) — replicate this exact guard in the new global handler; it's easy to forget on a new handler copy-pasted from the per-session one, and a nil-pointer panic here would take down the whole ConnectRPC handler goroutine rather than returning a clean `CodeUnavailable`.

## React hook "pause without unmount" pitfalls

The existing hooks (`web-app/src/lib/hooks/useEscapeAnalytics.ts`) reveal two different existing patterns for handling `sessionId` changes — neither is a true pause mechanism, and both have latent issues that the new "All Sessions" toggle will expose more sharply:

1. **`useEscapeAnalyticsSummary` has no request-cancellation guard at all** (lines 44-62). `fetchSummary` checks `if (!clientRef.current || !sessionId) return;` as an early-out, but the `useEffect` that calls it (`useEffect(() => { fetchSummary(); }, [fetchSummary])`) has no cleanup function and no `cancelled` flag. If the user flips to "All Sessions" (which will presumably set `sessionId` to `""` or stop rendering this hook's consumer) while a summary fetch for the old session is still in flight, the response can land **after** the switch and call `setHistogram`/`setTotalSequences` with stale data — a classic "setState after unmount/irrelevant" race. `useEscapeEvents` already has the right pattern (`let cancelled = false; ... return () => { cancelled = true; }`) — the global-view work should either backport that cancellation guard to `useEscapeAnalyticsSummary` or ensure the hook is never invoked at all (not just ignored) when "All Sessions" is active.
2. **Early-return-on-empty-sessionId does not clear existing state.** Both hooks' guards (`if (!sessionId) return`) skip fetching but leave whatever histogram/events were loaded for the *previous* session sitting in state. If the toggle only conditionally renders the *output* of these hooks (per the Rabbit Hole's explicit warning) while the hooks are still mounted with a now-stale/empty `sessionId`, nothing re-fetches or clears — the user could flip back to "Per-Session" and briefly see a phantom previous session's numbers before a real re-fetch resolves. The clean fix per the Rabbit Hole's own framing: don't just hide the output — either (a) unmount the components that call these hooks when "All Sessions" is active (React naturally cancels no in-flight promises on unmount, but the `cancelled` flag pattern above is still needed to avoid the console warning / wasted setState), or (b) pass `sessionId = ""` intentionally as a sentinel and have the hook clear its own state when `sessionId` becomes falsy, not just skip fetching.
3. **Tab switch racing a slow in-flight request.** If the user switches "Per-Session → All Sessions → Per-Session" quickly (e.g. clicking through), two overlapping per-session fetches for two different session IDs could resolve out of order. `useEscapeEvents` guards this per-effect via its own `cancelled` closure var, which is correct — but note the closure captures `sessionId`/`stage`/`sequenceType`/`mangledOnly`/`pageSize` from the effect's own render, so a *stale* fetch resolving late only writes stale values guarded by that same effect's `cancelled` — this pattern must be preserved (not "optimized away") when refactoring these hooks to support pausing, since it's the actual race guard.
4. **Effect cleanup order with a new `enabled`/`paused` param.** The natural fix is to add an `enabled: boolean` parameter to both hooks (default `true`) so the omnibar-style toggle can suspend fetching without unmounting the component tree (useful if "Per-Session" state — selected filters, scroll position — should survive a round-trip through "All Sessions" and back). If doing this: the `enabled` check must guard **both** the initial-fetch effect **and** any `fetchNextPage`/`refresh` callback exposed to consumers, or a stale ref to `refresh()` called from a parent effect after the tab already switched away can still fire a request. Also ensure `enabled` transitioning `true → false` mid-flight still lets the in-flight request's `cancelled` guard suppress the resulting `setState`, rather than only preventing *new* requests.
5. **`clientRef.current` is set in its own effect** (`useEffect(() => { clientRef.current = createClient(...) }, [])`) — this runs once per mount. If the "pause" strategy involves conditionally rendering (mount/unmount) rather than an `enabled` flag, remounting on tab-switch-back re-creates the ConnectRPC client needlessly (cheap here, but worth noting as a reason to prefer the `enabled`-flag approach over full unmount/remount if tab-switching is expected to be frequent).

## Recommendation summary for planning phase

- Use ent's generated `GroupBy`/`Aggregate` builder (already present in this codebase's generated code, e.g. `session/ent/analyticsevent_query.go:259-304`) for the two aggregate queries (sequence-type histogram, per-session breakdown) rather than a raw `sql.Selector` — simpler, and dialect differences (SQLite boolean-as-integer, no `FILTER (WHERE ...)`) are absorbed by ent's query builder instead of hand-written SQL.
- Guard division-by-zero mangle-rate **per breakdown row**, mirroring the existing single-session guard.
- Prefer an explicit `enabled` param on `useEscapeAnalyticsSummary`/`useEscapeEvents` over relying on `sessionId` truthiness or component unmounting alone — and backport the `cancelled`-flag race guard from `useEscapeEvents` into `useEscapeAnalyticsSummary`, which currently lacks it.
