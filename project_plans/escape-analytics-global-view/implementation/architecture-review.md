# Architecture Review: escape-analytics-global-view

**Date**: 2026-08-11
**Verdict**: CONCERNS

Constitution check: `docs/adr/ADR-000-architecture-constitution.md` does not exist in this repo — no automatic-BLOCKER check applies.

## Blockers

None found. The plan's own research/ADR phases already resolved the two structural risks flagged in `requirements.md` (ent aggregation mechanism, per-session pagination), and the chosen design (two independent `GroupBy`/`Aggregate` queries, additive proto messages, sibling handler pattern) introduces no schema migration, no breaking proto change, and no repeat of the in-Go event-scale aggregation anti-pattern the NFR forbids. `research/build-vs-buy.md` §1's verdict (use ent's generated `GroupBy`/`Aggregate`, no raw-SQL escape hatch) is followed through consistently into `plan.md` Step 3a and `ADR-001`.

## Concerns

- [ ] **`escapeMangleRate(total, mangled int64) float64` is a two-same-typed-param function whose arguments are silently swappable** — `plan.md` Task 1.3.5 defines it with two `int64` parameters (`total`, `mangled`) representing distinct, non-interchangeable domain concepts (denominator vs. numerator). Per `.claude/rules/primitive-obsession-checklist.md`, a call-site swap (`escapeMangleRate(mangled, total)`) compiles cleanly and silently produces an inverted rate — exactly the smell the checklist exists to catch, and this function is called from two sites (global total + per-row) where a copy-paste swap is plausible. Remediation: keep the primitive params (a value-object wrapper is overkill for one pure one-line helper), but add a unit test that pins the argument order (e.g. `escapeMangleRate(10, 3)` must equal `0.3`, not `3.33`) so a future swap fails CI instead of shipping silently, and name the params unambiguously in the doc comment (`// escapeMangleRate reports mangled/total, NOT total/mangled`).

- [ ] **`PerSession` row order is unspecified at the query layer** — neither query sketch in `architecture.md` §2 nor `plan.md` Task 1.3.4 applies an `Order(...)` to the per-session `GroupBy(escapeevent.FieldSessionID)` query. The plan relies entirely on the frontend (`SessionEscapeBreakdownTable`, Task 2.4.4) to default-sort by mangle rate descending. This is fine for the UI, but leaves the RPC's own contract order-undefined — a future Go test asserting exact row order, or any non-frontend consumer of this additive/stable proto, inherits SQLite's unspecified `GROUP BY` iteration order. Remediation: add an explicit `Order` (even a cheap tie-breaker like `session_id` ascending, or descending by the aggregated count if ent's `GroupBy` supports ordering by an aliased aggregate column) so the wire contract has a defined, testable order independent of the frontend's client-side sort.

- [ ] **No `start_time <= end_time` validation on the new request, mirroring an existing gap** — like `GetEscapeAnalyticsSummary`, `GetEscapeAnalyticsGlobalSummaryRequest` has no guard against an inverted time range; it will silently return an empty histogram/`per_session` rather than `connect.CodeInvalidArgument`. Requirements explicitly rule out fixing the sibling endpoint's pre-existing issues, so this is not a blocker for scope reasons — but the plan should say explicitly (in `plan.md` or a code comment at Task 1.3.2) that this is a **known, accepted, pre-existing-pattern gap** carried forward intentionally, not an oversight, so a future reviewer doesn't re-discover and re-litigate it. Remediation: one sentence in Task 1.3.2's implementation, or file a small follow-up covering both endpoints together.

## Nitpicks

- `ent.Sum(escapeevent.FieldMangled)`'s correctness depends on SQLite's bool-as-INTEGER storage (correctly identified in `architecture.md` §2's sketch notes and `ADR-001`), but that caveat lives only in the planning docs. Carry a one-line comment at the actual call site in `analytics_escape_service.go` (e.g. `// Sum on a bool field relies on SQLite storing bool as 0/1 — revisit if this DB ever moves off SQLite.`) so the assumption is visible where a future dialect change would actually break it, not just in a planning doc that won't be read at that point.
- The two `GroupBy` queries (histogram, per-session) run sequentially against the same read-only analytics DB; they're independent and could run concurrently (e.g. `errgroup`), though the plan correctly notes this isn't needed at dev-tool QPS. Worth a one-line comment noting the sequential-not-parallel choice was deliberate, so it doesn't read as a missed optimization to a later profiler-driven review.
- Minor cross-document redundancy: `ADR-001`'s Alternatives Considered section and `research/build-vs-buy.md` §4 / `architecture.md` §2 restate largely the same rationale for rejecting the combined-query and fork-existing-handler approaches. Not a code issue — just noting the planning artifacts could cross-reference rather than duplicate prose, for future maintainers reading the ADR in isolation.
