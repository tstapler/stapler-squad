# Pre-mortem: escape-analytics-global-view
**Date**: 2026-08-11

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The two independent `GroupBy` queries (histogram by `sequence_type`, breakdown by `session_id`) run sequentially with no shared transaction/snapshot, so under concurrent escape-event ingestion the two result sets can be read at different points in time — the histogram's `total_sequences`/`total_mangled` no longer equal the sum of the `per_session` rows. | A user or reviewer manually sums the `per_session` breakdown column and gets a different total than the headline mangle-rate summary shown above it, and reports it as a bug. | Wrap both queries in a single read transaction (or, if ent's SQLite driver doesn't cheaply support that, note explicitly in `ADR-001`/plan.md that totals may not reconcile exactly under concurrent writes, and add a unit test asserting the acceptable-skew bound is documented, not silently assumed away). | P2 |
| 2 | `plan.md` Story 3.1 explicitly hedges the time-range filter with "if a UI control exists — else RPC-level only," and no task in Story 2.4 commits to building one. The RPC supports `start_time`/`end_time`, but if no frontend control ships, the "optional time-range filter" capability from requirements.md is functionally dead on arrival — a documented in-scope capability that no user can actually reach. | QA or a user tries to filter the global view by time range in the UI and finds no control to do so, despite the feature description promising it. | Add an explicit task to Story 2.4 (not a conditional) for the time-range UI control, or amend requirements.md/plan.md to explicitly move it to Out of Scope for this iteration so it isn't silently dropped. | P2 |
| 3 | `ent.Sum(escapeevent.FieldMangled)` sums a bool-stored-as-`INTEGER` column; the concrete Go type the SQLite driver returns for a `SUM()` aggregate (often `int64` or `float64` depending on driver/version) may not match the destination struct field's declared type in the `Scan(ctx, &dest)` call, causing either a `reflect`/type-assertion panic at request time or a silently truncated/zero value — a risk independent of any future dialect migration. | The new endpoint returns `connect.CodeInternal` (or a suspiciously-always-zero `mangled_count`) the first time it's hit against real data, even though unit tests with a small fixture happened to pass. | Add a unit test with a mixed true/false `mangled` fixture asserting the exact returned `mangled_count`/`total_mangled` value (not just "some value"), and verify the destination struct's field type against what the driver actually returns before merging — don't only comment on the assumption, test it. | P1 |
| 4 | The shipped "All Sessions" breakdown table has no filter/threshold control (only a default sort) — once the number of sessions with recorded events grows past a screenful (tens, not the "many thousands" bar used to justify skipping pagination), a user is back to visually scanning a long list to "spot the outlier," which is materially the same manual-comparison burden the feature was built to eliminate. | Users continue asking "which session is misbehaving?" in the same way as before, or stop using the "All Sessions" tab because scrolling a sorted table isn't faster than the old per-session click-through for their actual session count. | Add a lightweight client-side filter (e.g. "show only sessions with mangle rate > X%") or a visually distinct top-N callout to the breakdown table now, rather than treating "sorted, unpaginated table" as sufficient to satisfy the success metric — validate against this repo's actual session count before declaring the UX done. | P2 |
| 5 | Neither query has a deterministic tie-breaking sort (the architecture review flagged the missing `Order` on the backend; independently, the frontend's client-side sort by `mangleRate` descending has no secondary key), so sessions tied at `mangle_rate: 0` (the common case — most sessions have no mangled sequences) can silently reorder between successive fetches/refreshes. | The Playwright e2e assertion on "breakdown table default-sorts by mangle rate descending" (Story 3.1) becomes flaky, intermittently failing on row order for tied values; separately, a user tracking a specific session in the table sees it "jump" position between refreshes with no underlying data change. | Add a deterministic secondary sort key (e.g. `session_id` ascending) both in the backend `Order` (already recommended by architecture-review.md) and explicitly in the frontend's client-side sort comparator, and assert exact row order (not just "sorted ascending/descending") in both the Go unit test and the e2e spec. | P2 |

## P1 Items (address before implementation)
- [ ] #3 — Add a Go unit test with a mixed true/false `mangled` fixture that asserts the exact numeric value returned by `ent.Sum(escapeevent.FieldMangled)` through the `Scan(ctx, &dest)` call, confirming the destination struct field's type correctly receives whatever the sqlite3 driver actually returns for a `SUM()` over an INTEGER-stored bool column — treat this as a verification task in Story 1.3/1.5, not an assumption covered only by a code comment.
