# Adversarial Review: escape-analytics-global-view

**Date**: 2026-08-11
**Verdict**: CONCERNS

## Blockers

None found — the core architecture decision (ADR-001's two-`GroupBy` queries) is sound, verified against the actual generated code, and no scope-drift item rises to a hard blocker.

## Concerns

- [ ] **Inverted/malformed time range (`start_time > end_time`) has no explicit handling or test.** Neither `requirements.md`, `plan.md`, nor either ADR mention this case. With `WallTimeGTE(start)` and `WallTimeLTE(end)` both applied as `AND` predicates (same pattern as the existing `GetEscapeAnalyticsSummary`, `server/services/analytics_escape_service.go:139-144`), an inverted range silently produces an empty result set rather than a `CodeInvalidArgument` error — indistinguishable from "no events in range" in the UI. Recommendation: either validate `start_time <= end_time` and return `CodeInvalidArgument`, or explicitly document the silent-empty-result behavior as intentional and add a unit test asserting it (`TestGetEscapeAnalyticsGlobalSummary_should_ReturnEmpty_When_TimeRangeInverted`) so it isn't mistaken for a future bug.

- [ ] **ADR-002's "no pagination for MVP" call is asserted, not confirmed against this repo's own data — and the requirements doc explicitly demanded that confirmation.** `requirements.md`'s Open Questions section says: "confirm against realistic session counts in this repo's own data" (line 69). ADR-002 only argues structurally (row count bounded by distinct-sessions-with-events, precedent from `SessionsTable.tsx`) — it never queries an actual `analytics.db` for a real distinct-session count. I checked: there is no live `~/.stapler-squad/analytics.db` outside test fixture directories on this machine, so the confirmation the requirements doc asked for was never actually possible to perform — but neither `plan.md` nor ADR-002 acknowledges this gap or states "no production data exists yet to check against; revisit once the feature has real usage." The requirements doc's explicit ask was silently downgraded to a structural argument without saying so. Recommendation: add one sentence to ADR-002 acknowledging no live data exists to check against yet, rather than implying the "confirm in this repo's own data" instruction was satisfied.

- [ ] **Rapid tab-switch race (Per-Session → All Sessions → Per-Session) is named in research but has no corresponding test task.** `pitfalls.md` §"React hook" point 3 explicitly flags this scenario ("If the user switches 'Per-Session → All Sessions → Per-Session' quickly... two overlapping... fetches... could resolve out of order") as the actual race the `cancelled`-closure guard exists to close. Story 2.6's Jest tests (Task 2.6.1–2.6.3) only test single-transition cases (`enabled:false` not fetching, stale response ignored on one session change) — none test the double-switch-before-resolution scenario that most directly exercises the interaction between the new `enabled` flag and the `cancelled` guard together. Recommendation: add `EscapeAnalyticsPage_should_RenderCorrectData_When_TabSwitchedTwiceBeforeFetchesResolve` to Story 2.6.

- [ ] **SQLite lock-contention pitfall raised in research is never closed out in the plan.** `pitfalls.md` explicitly instructs: "Check `session/ent_repository.go`'s `PRAGMA` setup for `journal_mode=WAL` — if absent, a large global aggregate query risks lock contention against live escape-event ingestion." Neither `plan.md` nor either ADR mentions WAL, or states this was checked. (I checked it myself: `session/ent_repository.go:75` does set `_journal_mode=WAL`, so the actual risk is mitigated — WAL readers don't block writers and vice versa. But the plan should say this was verified rather than silently dropping an explicitly-flagged research item.) Recommendation: add one line to ADR-001 or the Migration Plan section confirming WAL mode was checked and is enabled.

## Minors

- **Grand-total roll-up from the histogram result (ADR-001) is Go-side aggregation, but it is a defensible, bounded exception, not a smuggled violation of the NFR.** The NFR forbids pulling *event-scale* rows into Go memory; folding `totalSeq`/`totalMangled` from the histogram's already-`GROUP BY sequence_type`-bounded row set (cardinality = distinct sequence types, typically single digits to a few dozen) is a trivial fold over an already-aggregated result, not the anti-pattern the NFR was written against. Worth a one-line note in ADR-001 stating this distinction explicitly (it currently just says "folded in Go... bounded by distinct sequence-type count" without stating why that satisfies the NFR's actual concern), since a future reviewer skimming for "any Go-side aggregation" could flag it incorrectly.

- **`pitfalls.md`'s code citation is off by one entity.** It cites `session/ent/analyticsevent_query.go:259-304` for the `GroupBy`/`Aggregate` builder pattern, but the correct file for this feature is `session/ent/escapeevent_query.go` (verified: `GroupBy` at line 273, `Aggregate` at line 303 — close but not identical to the cited range, and a different generated file than the one cited). Both are generated by the same ent generator and expose an identical pattern, so the substance of the research holds, but `plan.md`'s own citation of `escapeevent_query.go:259-305` (Step 2 domain glossary) is the one actually worth trusting.

- **Story 2.1 modifies an existing per-session hook's behavior (`useEscapeAnalyticsSummary`) under cover of the new feature.** This is a real bug fix (missing cancellation guard) well-justified by the toggle interaction, and is small — but it's technically a change to existing, already-shipped per-session behavior that requirements.md's scope section doesn't explicitly call out as in-scope (only "new endpoint + UI toggle" is named). Not scope drift in the sense the Out-of-Scope list forbids (it doesn't touch the backend in-Go aggregation anti-pattern that section explicitly excludes), but worth a one-line callout in the PR description so a reviewer doesn't mistake it for accidental scope creep.

- **No explicit test for a query error on the second `GroupBy` call after the first succeeds.** Since both queries are read-only with no partial writes, a failure here just propagates as `CodeInternal` with no side effects — low risk — but Story 1.5 has no task covering it, unlike the nil-client and zero-events cases which are covered.
