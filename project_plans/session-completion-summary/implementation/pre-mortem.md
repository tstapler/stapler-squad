# Pre-mortem: session-completion-summary
**Date**: 2026-08-03

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The narrative is grounded only in a (possibly truncated) diff + a decisions-count string (Task 1.4.1a's `GenerateSessionCompletionNarrative(ctx, pool, diff, decisionsSummary string)`), not the "last N tool uses and outputs" the original backlog item described — for exploration-heavy, debugging, or reverted-work sessions with a small/empty diff, the LLM has almost nothing to describe and produces generic, interchangeable prose that adds no value over reading the diff stat directly, defeating the feature's stated purpose of replacing manual scrollback reading. | Users stop opening the Summary tab; feedback that narratives across different sessions "all sound the same" or restate the diff stat in prose. | Before implementation, run a manual eval of `GenerateSessionCompletionNarrative` against 5-10 real historical sessions with varied diff/effort ratios (including near-zero-diff sessions with real work) and confirm the prose adds information beyond the deterministic sections; if it doesn't, widen the input to include a compressed digest of the session's goal/title (`GetSessionGoal`) and/or a short tool-call-type histogram, not diff text alone. | P1 |
| 2 | `GenerateSessionCompletionNarrative` truncates large diffs via the existing `SanitizeDiff`/`MaxDiffSizeReview` helper (Task 1.4.1a), but the deterministic "Changes" section always renders the *full*, untruncated `DiffSnapshot` counts — for large sessions the narrative prose can describe only the files visible in the truncated portion while the numbers above it show a much larger true scope, producing a document that contradicts itself and is misleading if exported verbatim as a PR body. | A user pastes the generated summary as a PR body; a reviewer or the user notices the narrative names only 2-3 files while "Changes" reports 40 files changed. | Pass the true `DiffSnapshot` file/line counts into the narrative prompt alongside the (possibly truncated) diff text, and instruct the prompt to describe scope using those counts when the diff was truncated (e.g., "note: diff truncated, showing N of M files") rather than only from the visible diff; add a unit test with a diff exceeding `MaxDiffSizeReview` asserting the rendered document doesn't understate file count. | P2 |
| 3 | Because the trivial-skip threshold is narrow (`diff.IsEmpty() && decisions.Total()==0 && duration<30s`) and there is no feature flag, config toggle, or per-user cap (Risk Control explicitly says "none required"), essentially every real session — including short, low-value ones that are core to this tool's workflow (spin up, try something, tear down) — triggers a real LLM call through the shared `headless.Pool`, with cost/rate-limit consumption invisible by default (the `AnalyticsEvent` emission is explicitly marked optional/stretch, not required). | Unexpectedly high LLM API spend, or other `headless.Pool` consumers (PR description generation, review-queue triage) experiencing increased latency/semaphore contention that's hard to attribute without the (optional, unimplemented) analytics event. | Make the `AnalyticsEvent` emission (`session_summary` category) a required v1 task, not a stretch task, so cost/volume is observable from day one; add a config-level on/off toggle (`config.json`) so a heavy user can disable automatic generation without a code change, satisfying FR-5's cost-control intent more robustly than the current all-or-nothing design. | P2 |
| 4 | `NotificationHistoryStore.List` "never returns a non-nil error today" because file-corruption/load failures are swallowed silently at load time (explicitly noted in Task 1.3.2a) — if that store fails to load for a session that genuinely had approvals, `BuildDecisionsSnapshot` returns an all-zero `DecisionsSnapshot`, which is byte-for-byte indistinguishable from FR-6's legitimate "no approval requests occurred" empty state, so the summary silently fabricates a false record. | A user who recalls approving several tool calls during a session opens its Summary tab and sees "No approval requests occurred during this session" — files a bug questioning whether approvals are being tracked/audited at all. | Thread a load-health signal out of `NotificationHistoryStore` (or detect it at `BuildDecisionsSnapshot` call time) and add a `DecisionsDataUnavailable bool` to `DecisionsSnapshot`, mirroring the pattern `CostSnapshot.DataUnavailable` already uses to distinguish "genuinely zero" from "data could not be read" — render "Decision data unavailable" instead of the zero-count empty state when detected. | P3 |
| 5 | The FR-7 sequential-duplicate short-circuit (Task 1.5.2b step 1b: "if `reason != manual-regenerate` and row status == `ready`, return immediately with no write") was designed to swallow duplicate/late-arriving triggers for the *same* completion, but it can't distinguish that from a session that was paused and resumed (a supported, common workflow per `resume_session`/`pause_session`) and did substantial new work before exiting a second time — that second, genuinely-new `EventExited`/`EventStopped` is silently discarded because the row is already `READY`, permanently pinning the summary (and its diff/decisions/narrative) to the state at the *first* exit with no error, no staleness indicator, and no automatic path back to accurate — only a user manually clicking Regenerate (which they have no reason to do, since nothing signals staleness) fixes it. | A user resumes a session, does more work, the session exits again, but the Summary tab / exported PR body still reflects the smaller diff from before the resume — noticed only by comparing against the live diff tab or git log by hand. | Key the sequential-duplicate short-circuit off whether *this specific generation's inputs* were already captured (e.g., compare the incoming `diffStats` snapshot or a monotonic resume/generation counter against what's persisted) rather than off row `status` alone, so a resume-then-reexit cycle is treated as a legitimate new trigger; alternatively, have the resume path explicitly reset `SessionSummary.status` to `pending` so the next exit is unambiguously not a duplicate. | P1 |

## P1 Items (address before implementation)
- [x] #1 — Resolved at the planning-doc stage (no manual eval run, since no code exists yet): widened `GenerateSessionCompletionNarrative`'s input to include the session's title and goal (`Instance.GetSessionGoal()`, cheap in-memory read, no I/O) alongside diff+decisions — `plan.md`'s Domain Glossary, Pattern Decisions ("Narrative input scope" row), Task 1.4.1a, Story 1.4.1 AC, and the `summaryGenerator`/`GenerateAndPersist` signatures throughout Epic 1.1/1.5/2.2 were all updated to thread `sessionGoal` through; `requirements.md` FR-2 item 1 was reworded to accurately describe diff+decisions+goal/title grounding (not raw tool-use history) with a one-sentence rationale. A full tool-call-history digest remains the documented fallback if this proves insufficient once real sessions are evaluated post-implementation, not the v1 default.
- [x] #5 — Resolved: `plan.md` Task 1.5.2b step 1b's sequential-duplicate short-circuit now keys off whether *this generation's diff data* has actually changed since the last persisted generation — it compares the incoming `diffStats`' `FilesChanged`/`Added`/`Removed` counts against the persisted row's `diff_files_changed`/`diff_added`/`diff_removed` fields (computed via the already-pure, no-I/O `BuildDiffSnapshot`), rather than off row `status == "ready"` alone. A match short-circuits as a true duplicate; a mismatch (e.g. a resume→re-exit cycle with new work) proceeds with regeneration despite the row already being `READY`. Story 1.5.3's AC-8 and Task 1.5.2d's test list were updated with both the true-duplicate and genuinely-new-data cases; a corresponding row was added to `validation.md`. A residual, explicitly-accepted limitation: if diff content changes while the three counts happen to coincide exactly, this still short-circuits as a false duplicate — a full content-hash comparison would close that gap but wasn't judged worth the added complexity for v1 (per this repo's pragmatic/"ponytail" convention); pre-mortem's own "alternatively... explicit reset" option remains the documented fallback if this proves to matter in practice.

## Summary
5 failure modes identified: 2 P1, 2 P2, 1 P3. Top risk: the sequential-duplicate short-circuit added during the adversarial-review repair pass (designed to fix AC-8's duplicate-trigger requirement) has a blind spot for resumed sessions — a supported core workflow — where it silently pins the summary to a stale, pre-resume diff state with no error and no staleness signal, which is exactly the kind of "two already-fixed pieces interacting badly" risk this pre-mortem was asked to hunt for.
