## Constitution Violations

`docs/adr/ADR-000-architecture-constitution.md` does not exist in this repository — no constitution to check against. Skipped.

## Blockers

None. This plan is unusually disciplined: it explicitly evaluates and rejects a shared `ContentScanner` interface (Step 0.5, option 2; `research/architecture.md` §1) using the exact reasoning `.claude/rules/interface-pollution-checklist.md` prescribes (smell #4 forwarding-only wrapper, smell #1 speculative interface), keeps secret-scan and PII-scan as two independent call sites with genuinely different control flow (return-and-deny vs. fall-through-and-escalate), and matches `research/build-vs-buy.md`'s "Build, hand-rolled regex + inline Luhn" recommendation exactly (no SaaS/library detour). ## Concerns

- [ ] **Task 3.1.1a (`ApprovalHandler` struct)** — Adding `piiConfig config.PIIScanningConfig` and `piiCustomPatterns []namedPattern` as two more raw fields pushes `ApprovalHandler` (`server/services/approval_handler.go:68-83`) past 16 fields (`store`, `storage`, `eventBus`, `queueChecker`, `classifier`, `analyticsStore`, `domainChecker`, `notificationStamper`, `autoApprovalLog`, `timeout`, `headlessPool`, `autonomousChecker`, `pollInterval`, `liveFinder`, plus the two new ones), each wired via its own `SetX` method — a god-object-by-accretion pattern that compounds with every feature added this way. **Remediation**: group the secret-scan and PII-scan runtime state (config + compiled custom patterns for both) into one small collaborator value, e.g. `contentScanState{secretPatterns, piiConfig, piiCustomPatterns}`, held as a single `ApprovalHandler` field and injected via one setter. This is data grouping, not a behavioral interface, so it doesn't reintroduce the `ContentScanner` abstraction the plan correctly rejected — it only caps the struct's field growth.

- [ ] **Task 2.1.1a (`PIIScanningConfig.CustomPatterns []string`) + Task 3.1.1a (`SetPIIScanningConfig`)** — every compiled custom pattern is given the identical `Name: "Custom PII pattern"` (Task 3.1.1a: `namedPattern{Name: "Custom PII pattern", Pattern: compiled}`). If an operator configures more than one custom pattern (e.g. an internal employee-ID format and a case-number format), `FormatPIIEscalationReason`/the review-queue reason text and audit log can never distinguish which one fired — every custom-pattern escalation reads identically. This directly undercuts AC6's compliance/audit intent for the one part of the pattern set operators actually author themselves. **Remediation**: change `CustomPatterns []string` to a named-pattern shape, e.g. `CustomPatterns []NamedPIIPattern{Name, Pattern string}` (or `map[string]string` name→regex) in `config/types.go`, so `SetPIIScanningConfig` can carry the operator-assigned name through to `FormatPIIEscalationReason` instead of a generic label.

- [ ] **Task 2.1.1a (`PIIScanningConfig.OnDetection string` / `OnDetectionOrDefault`)** — the field accepts any string; `OnDetectionOrDefault()` treats anything other than the exact literal `"deny"` as `"escalate"`, silently. An operator in the "stricter environment" the `deny` mode exists for (per ADR-001 and requirements.md Open Question 1) who typos `"Deny"`, `"denied"`, or `"block"` gets silently downgraded to escalate with zero feedback — the one config knob whose entire purpose is tightening behavior fails open without a trace. This is a real illegal-state gap: the type system allows `OnDetection` to hold any of infinite string values when only two are meaningful. **Remediation**: (a) introduce a typed `type PIIOnDetectionMode string` for the field — mirroring `EscalationCategory`'s existing typed-string precedent in this same codebase (`pkg/classifier/escalation.go`) rather than inventing a new idiom — and/or (b) have `SetPIIScanningConfig` `log.Warn` when `cfg.OnDetection` is non-empty and not one of the two recognized literals, so a misconfiguration is observable in logs even though the fail-safe default is preserved.

- [ ] **Task 3.1.3b (PII-scan target loop + `goto createApproval`)** — the loop over scan targets (`command`, then `extractWriteContent`'s result) calls `recordRedactedFinding` for only the *first* target that matches before jumping to `createApproval:`, so only that one field is redacted before analytics persistence. This is safe under today's actual data shapes only because `command` (Bash) and `content`/`new_string` (Write/Edit) are populated by mutually exclusive tool types, per `extractWriteContent`'s switch — but that invariant is never asserted or tested anywhere in the plan (Phase 6 only covers Bash-only and Write-only cases separately, never a hypothetical dual-field payload). If that invariant is ever broken (a future tool call with both `command` and `content` set, or a broadened `extractWriteContent`), the second field's PII would reach the analytics store unredacted — a direct, silent violation of AC8 ("matched PII text is redacted before it is persisted"). **Remediation**: either add an explicit one-line comment (or a defensive assertion) at the target-list construction site in Task 3.1.3b stating the mutual-exclusivity invariant by name, or change the loop to redact *all* matched targets before the single `goto`, not just the first hit.

## Nitpicks

- `RuleIDPIIScan` (Task 4.1.1a) is added as another untyped string constant in the same block as `RuleIDSecretScan`/`RuleIDNewDomainCheck` (`pkg/classifier/escalation.go`). A `type RuleID string` alias would make `CategorizeEscalationRuleID`'s switch exhaustiveness-checkable by `go vet`/linters, but this is a pre-existing pattern across 5 sibling constants that this plan correctly follows rather than unilaterally changes — not worth blocking on.
- Task 3.1.3b's "scan target list" (`command` + `extractWriteContent` result) isn't given an explicit type in the plan text (likely an anonymous `[]struct{field, text string}`); left to implementer discretion with no functional risk either way.
