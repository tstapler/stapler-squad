# UX Research: PII Scanning Review-Queue Surface

Scope: the user-facing surface for `pii-scan` escalations — review queue badge, analytics row, config toggle, and the redaction/display tension unique to PII (vs. secret-scan, which never reaches the UI at all).

## 1. Comparable UX patterns — established visual language

The escalation-reason surface is **one generic system that renders any `EscalationCategory`**, not a set of bespoke widgets per category. New categories plug into existing maps; there is no dedicated "PII tile" component to build.

- **`ESCALATION_REASON_EMOJI`** (`web-app/src/components/sessions/ReviewQueuePanel.tsx:141-147`) — a `Partial<Record<EscalationCategory, string>>`. Rendered at `ReviewQueuePanel.tsx:752` as `` `${emoji ?? ""} ${escalation_reason}`.trim() `` inside a `<p>` with `id`/`data-testid`, **not** as a separate colored badge element. The comment at `:138-140` is explicit: *"Category -> emoji prefix for the escalation reason line (WCAG 1.4.1 — not color-only)."* `secret-scan` deliberately has no entry because it auto-denies before a `ReviewItem` exists.
  - Consistent pattern for PII: add `"pii-scan": "🔒"` to this map. No new component, no new CSS class — it's a text prefix on an existing paragraph.
- **`ESCALATION_CATEGORY_LABELS`** (`web-app/src/components/sessions/ApprovalAnalyticsPanel.tsx:98-105`) — maps category → human-readable label for the "Escalation Reasons" table (`:329-360`). This table is **already generic**: it iterates `escalationReasonRows` (derived from `summary.escalationReasonCounts`, `:143-148`) and renders one row per non-zero category with a label, count, and inline `<Bar>` (`barRule` styling). Adding `"pii-scan": "PII detected in request"` to this map is the entire "analytics tile" requirement — **there is no dedicated stat card for escalation reasons today** (the top-row `cards`/`cardAllow`/`cardDeny`/`cardManual` at `:185-206` are decision-outcome cards — allow/deny/manual/total — not reason-category cards). The requirements doc's "PII detections tile in analytics" (line 31) should be understood as *a new row in the existing Escalation Reasons table*, not a new standalone tile — flag this as a scope-alignment note for planning, since a literal "tile" would be new UI, not reuse.
- **Badge styling precedent** — `categoryBadge` (`ApprovalAnalyticsPanel.css.ts:326-335`) is a neutral pill (`panelBgSecondary` bg, `borderColor` border, `textSecondary` text) used for non-alarming taxonomy labels (tool/category names, `:799,802`). `gapBadgeHigh/Med/Low` (`:364-378`) use semantic color (`warning`/`success` var pairs) *plus* always-visible text content (`"{rounded}% uncovered"`, `"no rule"`) — color reinforces but never substitutes for the label. If a distinct "PII" badge component is added anywhere the plain text-prefix pattern doesn't reach (e.g. a compact table cell), follow this pair-token convention (e.g. `vars.color.warning`/`warningBg`) rather than inventing a new hue — PII is a risk signal, closest existing precedent is `gapBadgeHigh`'s warning styling, not a fresh color.
- All of the above already live in `.css.ts` files using vanilla-extract's `style()` + the shared `vars` token contract (`ApprovalAnalyticsPanel.css.ts` imports `vars` from the theme contract) — this satisfies `.claude/rules/css-architecture.md` already; no raw CSS modules or hardcoded hex values are in play for either target file. Any new PII-specific style additions belong in the existing `.css.ts` file colocated with the consuming component, using `vars.color.*` tokens only.

**Conclusion**: the "new visual language" a PII badge needs is not new — it's two map entries (`ESCALATION_REASON_EMOJI["pii-scan"] = "🔒"`, `ESCALATION_CATEGORY_LABELS["pii-scan"] = "..."`) plus one type-union addition (`web-app/src/lib/sessions/escalationCategory.ts:5-11`, mirroring `pkg/classifier/escalation.go:10-30`). Anything more elaborate (a dedicated stat tile, a colored badge outside the text-prefix pattern) is a deliberate scope expansion beyond what "consistent with existing categories" implies, and should be justified explicitly in planning rather than defaulted into.

## 2. User mental models — "PII detected, escalated" vs. "denied"

Secret-scan's auto-deny is a closed loop: the agent's action is blocked, the developer sees a deny message, and (per `FormatSecretDenyMessage`) presumably retries without the secret. There is no human in the loop and no ambiguity — "you can't do that."

PII escalation is structurally different and the UI needs to carry that difference explicitly, because the existing escalation-reason text pattern (`EscalationReasonText`, `pkg/classifier/escalation.go:83-97`) was designed around *rule-driven* escalations ("no rule matched," "rule X flagged this") where the reviewer's job is roughly "should this rule exist / was this the right call." PII escalation asks a different question: **"does this specific text contain real PII I should be worried about, or is it a legitimate test fixture?"**

Implications for copy and mental model:
- A developer seeing "🔒 PII detected — SSN pattern matched" needs to immediately understand: (a) their agent's action is *paused*, not rejected, (b) a human (possibly them) must look at the actual content and decide, (c) approving is not "overriding a security control" the way overriding a secret-scan deny would feel — PII in test fixtures is often expected, so the framing should be neutral/informational, not alarming, to avoid habituating reviewers to reflexively approve past a real signal (alert fatigue risk — same failure mode as an over-triggering linter).
- The reason text should name *which pattern matched* (email/SSN/credit-card) the same way secret-scan's `FormatSecretDenyMessage` names the pattern, per `EscalationReasonText`'s existing convention of surfacing `result.Reason` verbatim when set — this is a "wire it up" task (set `Reason` when building the PII `ClassificationResult`), not new UI plumbing.
- Distinguish from `no-match` ("❓ no rule matched — could be anything") — PII's `❓`-equivalent (🔒) should read as *targeted and specific*, not "we're not sure, so we're asking." This matters for trust: a vague-sounding escalation reason erodes confidence in every escalation category, so PII's copy quality has knock-on effects on the whole system's credibility.

## 3. Accessibility (WCAG/ARIA) and CSS architecture

- **Not color-only (WCAG 1.4.1)**: already the enforced convention in this codebase — see the explicit comment at `ReviewQueuePanel.tsx:138-140`. The 🔒 emoji + text label pattern automatically satisfies this since it's prefixed to the existing `escalationReasonText` paragraph; no separate work needed as long as the PII entry follows the same map-driven pattern rather than introducing a color-only badge.
- **`data-testid`/ARIA**: the existing reason paragraph already has `id={`escalation-reason-${queueItem.sessionId}`}` and `data-testid={`escalation-reason-${queueItem.sessionId}`}` (`ReviewQueuePanel.tsx:748-749`) — this is generic and needs no per-category change. Per `.claude/rules/e2e-test-conventions.md`, any new e2e test for the PII badge must use this existing `data-testid`, not a CSS selector.
- **CSS architecture** (`.claude/rules/css-architecture.md`): both target files are already vanilla-extract (`ApprovalAnalyticsPanel.css.ts`, and `ReviewQueuePanel.tsx` presumably has a sibling `.css.ts` — confirm at implementation time) using the `vars` token contract. New styles must use `vars.color.*`, never hardcoded hex or bare `var(--x)` strings. No `zIndex`, no `position: fixed`/`absolute` overlay concerns apply to this feature (it's inline table/list content, not a modal).
- **Screen-reader consideration not yet covered by the existing pattern**: emoji prefixes (❓🛑🌐⚙️⚠️, and the proposed 🔒) are read aloud by screen readers with verbose or inconsistent names ("locked" / "closed padlock" / "lock" depending on platform/AT) unless given an `aria-label` or `aria-hidden="true"` + adjacent text alternative. The current code relies on the *label text* being sufficient and lets the emoji be redundant decoration — that already works for accessibility since the text carries the meaning and the emoji is supplemental, not load-bearing. No new work is needed here as long as PII's reason text (e.g. "PII detected — SSN pattern matched") stands on its own without requiring the 🔒 to be parsed. Worth a planning note only if a *bare* badge (emoji with no adjacent text) is introduced somewhere the text-prefix pattern doesn't apply.

## 4. Error/display state — the redaction vs. reviewability tension

This is the most consequential UX finding and does not have a precedent to copy from secret-scan, because secret-scan **never reaches the review queue**.

Trace of what actually happens today, at `server/services/approval_handler.go`:
- **Secret-scan (auto-deny) path** (`:223-251`): on match, the handler writes a `deny` decision and returns immediately (`:248-249`). It never creates a `PendingApproval`, so the raw secret is only ever held in the in-request `payload` — it is explicitly redacted (`sanitizedInput["command"] = redactedSecret`, `:237`, sentinel defined at `server/services/ai_interfaces.go:9-11` as `"[REDACTED: secret detected]"`) before the one place it *is* persisted: analytics (`RecordFromResult`, `:240-246`). No UI ever displays the raw secret.
- **Escalation path** (what PII will use, per requirements item 3): a `PendingApproval` is created and `broadcastApprovalNotification` (`:504-522`) puts `approval.ToolInput["command"]`/`["file_path"]` **verbatim, unredacted** into `metadata["tool_input_command"]`/`["tool_input_file"]`, which the frontend renders raw inside a `<pre className={commandPreview}>` (`ReviewQueuePanel.tsx:755-758`).

**This means: if PII escalates instead of denies, the raw PII text will be displayed in plaintext in the live review queue UI by construction** — and this is not a bug to fix, it's the actual job the reviewer needs done. A human cannot decide "is this a real SSN or fixture data `123-45-6789`" without seeing the text. Acceptance criterion #8 ("matched PII text is redacted before persisted to session history / analytics logs") is correct and achievable using the exact same `sanitizedInput`/sentinel pattern secret-scan uses for analytics recording — but it must apply to **post-decision persistence** (analytics store, session history), not to the ephemeral `PendingApproval`/broadcast payload the reviewer needs to act on. Planning must decide, explicitly, one of:
1. Raw text shown live in the queue (necessary for the reviewer to judge), redacted only in analytics/session-history persistence once a decision is recorded — matches criterion #8's literal wording, and matches how secret-scan already treats "redact before persistence" as distinct from "redact before display" (it just happens that secret-scan never displays at all, collapsing the distinction there).
2. Partial masking even in the live view (e.g. `example@***.com`, `***-**-6789`) — better exposure hygiene (screen-share, browser history, shoulder-surfing) but may block the reviewer's actual judgment call on ambiguous matches, and is new UI/masking logic with no existing precedent in this codebase.
3. A reveal-on-demand pattern (masked by default, click/keyboard-triggered unmask) — the safest middle ground but is a genuinely new interaction requiring its own accessibility treatment (focus management, `aria-expanded`) and is proportionally heavier than anything else this feature needs.

Recommendation for planning: **option 1** is the only one consistent with "no new UI component" scope and the acceptance criteria as written; options 2/3 are legitimate but should be named as explicit scope additions, not assumed. Either way, the requirements doc's phrase "already redacted" (in this research prompt) doesn't match the current architecture — nothing is redacted before the reviewer sees it today, by design, because the reviewer's job requires seeing it. The error/empty state that *does* need a UI decision: if PII is detected in a **file write** whose full content is too large to preview (the existing `commandPreview` has no truncation guard visible in the excerpt reviewed — worth confirming in `research/codebase.md`), decide whether to show a byte-capped excerpt around the match (with position context) rather than either the full file or nothing.

## 5. Job-to-be-done: team lead compliance review vs. individual developer

Two distinct consumers of the same `pii-scan` category, with different jobs:

- **Individual developer approving their own agent's action** (review queue, in the moment): job is *"let my agent keep working without me leaking something."* They need: fast recognition (🔒 + short label, scannable in a list of otherwise-similar rule/no-match items), the actual matched text or surrounding context (to judge fixture-vs-real in seconds), and a low-friction approve path when it's clearly a fixture (test file path, `testdata/`/`fixtures/` directory — open question #2 in requirements about path-based skip logic is directly this job's efficiency need: without it, every fixture-heavy repo trains developers to rubber-stamp PII escalations, defeating the control). This is a **per-item, low-latency decision** — the review queue's existing card-per-item layout already serves it; no new layout needed, just correct signal (badge + reason text).
- **Team lead / compliance reviewer doing periodic audit** (analytics panel, after the fact): job is *"prove to an auditor/manager that PII exposure risk is tracked and bounded, and spot patterns"* — e.g. "we get 40 PII escalations/week, 38 are the same fixture file, 2 are real emails that got approved — who approved them and why." This needs: the aggregate count (satisfied by the generic Escalation Reasons row, `escalationReasonCounts["pii-scan"]`), but **not** satisfied by that row alone — a lead cannot currently drill from "PII detections: 40" to the individual decisions/approvers the way the acceptance criteria's "compliance logging... audit" language (item 6 in Proposed Behavior) implies. The existing `ApprovalAnalyticsPanel` has no per-category drill-down or approver-attribution view for *any* escalation category today (confirmed: `escalationReasonRows` only renders category+count+bar, no link to underlying `ReviewItem`s). This is a real gap between what the requirements imply ("logged separately for audit") and what the existing analytics surface can show — planning should scope explicitly whether "PII detections" in analytics means *just the count* (matches acceptance criterion #6 exactly, zero new UI) or whether compliance review implies a filterable list of past PII decisions (a materially larger UI lift not currently costed).

Net: the count-only interpretation is what criterion #6 asks for and what the codebase already supports for free. The audit/compliance framing in the "Proposed Behavior" section (item 6) reaches further than that and should be reconciled in planning — either descoped to "the existing analytics count satisfies this" or explicitly scoped as new work (filterable review-history view), not left ambiguous.

## Summary for planning

| Surface | What's needed | New UI? |
|---|---|---|
| Review queue badge | `ESCALATION_REASON_EMOJI["pii-scan"] = "🔒"` + `EscalationCategory` union entry | No — reuses existing text-prefix paragraph |
| Analytics "tile" | `ESCALATION_CATEGORY_LABELS["pii-scan"] = "..."` | No — new row in existing generic table, not a dedicated tile |
| Config toggle | `pii_scanning.enabled` in existing JSON config | Backend-only per requirements; no UI toggle specified/scoped yet — confirm whether one is expected |
| Redaction on display | None needed — raw text display in the live queue is required for the reviewer's job | N/A — scope conflict with criterion #8's wording needs planning resolution (persistence-time redaction, not display-time) |
| Compliance drill-down | Not currently supported by any escalation category | Yes, if "audit" requirement is taken literally — needs explicit scope decision |
