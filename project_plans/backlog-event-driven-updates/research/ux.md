# UX Research: Backlog Event-Driven Updates

Agent 5 — Phase 2 research, `backlog-event-driven-updates`

## 0. Grounding: what exists today

- **Fetch-once, no live update.** `/backlog` (`web-app/src/app/backlog/page.tsx`) and `/backlog/board` (`BacklogBoard.tsx`) fetch a list once; `BacklogBoard` just filters the passed-in `items` array by `column.status` client-side (`BacklogBoard.tsx:105`). Nothing re-fetches on a timer or event.
- **`BacklogItemDetail.tsx` polls narrowly** (lines 242–249): a 5s `setInterval` runs only while `triageStatus === "running"`, or `status === "review"` with no/`PENDING` verdict, or `status === "pr_pending"` — and is explicitly suspended `&& !editMode`. Critically, there is **no poll while `in_progress`**, which the requirements doc calls out as the main blind spot, since `in_progress` is where most autonomous wall-clock time is spent.
- **The app already has a proven live-update architecture to mirror**: `WatchSessions` is a ConnectRPC **server-streaming** RPC (`server/services/session_service.go`, wired in `server/server.go`) feeding a Redux slice (`web-app/src/lib/store/sessionsSlice.ts`, `reviewQueueSlice.ts`) via granular `addItem` / `updateItem` / `removeItem` reducers keyed by ID. This is the pattern the requirements doc's success metric ("same latency `WatchSessions` already delivers") explicitly points at — the research question isn't "should we invent something," it's "should backlog items ride the same stream infra or a parallel one."
- **`BacklogItemCard.tsx`** already renders a `VerdictBadge` (lines 63–83) purely from `item.gateVerdict` — no animation, no transition, it's a static conditional render keyed off props. A live-update highlight would be additive here, not a redesign.
- **`GateVerdictBox.tsx`** already has a `readOnly` mode (prop added this session, line 22) that renders verdict + criteria with all action buttons (`Approve`, `Reopen`, `Override`, `Skip Gate`) suppressed — used for showing a past verdict on an item that's since moved to `in_progress`. It's `role="status" aria-live="polite"` at the section root (line 234–236) — **this is already a live region**, just not currently fed live data.
- **`NotificationContext.tsx`** presents live-arriving events two ways: (a) toasts (`addNotification` → rendered via `NotificationToast`, auto-expire after `TOAST_STALE_MS`/`ACTIONABLE_TOAST_STALE_MS`), explicitly capped to **one toast per `sessionId`** (line ~180, replaces rather than stacks — with a carve-out that approval toasts are never displaced by lesser ones), and (b) a badge count off `notificationHistory` unread state (`getUnreadCount`/`groupNotifications`). There's also `addToHistoryOnly` — explicitly "no toast, no sound" for informational events like `task_complete" — the codebase already distinguishes "worth interrupting for" from "worth recording."

This matters for the plan phase: the toast/badge vocabulary is a **notification-of-an-event** pattern for things needing acknowledgment (approvals, questions). Backlog live-updates are a **projection-of-current-state** pattern — closer to how `WatchSessions` silently keeps Redux in sync than to how `NotificationContext` announces things. Recommendation below treats them as architecturally distinct even though both are "live."

## 1. Comparable UX patterns (kanban/PM tools, monitoring dashboards, CI/CD)

**Linear, Jira (real-time boards).** Card and column position update in place via a live sync layer (Linear: custom sync engine; Jira: polling + websocket hybrid depending on plan). The near-universal pattern: **no toast per state change**. A card silently re-renders; a *very* brief background color flash or border pulse (100–300ms) marks "this just changed," then settles to the same visual weight as any other card. The operator is trusted to notice via peripheral vision, not interrupted.

**Trello (Power-Ups / live board sync).** Card moves across columns produce a CSS transition (transform/translate), not a modal or toast. Because both list and board views mutate structurally (item disappears from column A, appears in column B), Trello uses a short "ghost" placeholder in the origin column for ~1s to avoid the item looking like it vanished — directly relevant to the FilteredView disappearance edge case below.

**GitHub Actions / GitLab CI pipeline view.** Job status dots update via websocket/polling with a spinner → checkmark/x transition. No toast for individual job completion; a toast/notification IS used for the terminal state of the whole pipeline (pass/fail) — i.e., toast budget is reserved for the **outcome that ends supervision**, not for intermediate steps. This maps directly onto backlog: a status hop `ready → in_progress` is an intermediate step (no toast); a verdict landing or `review → done`/`review → in_progress` (bounced) is closer to a terminal/actionable outcome for *that phase*.

**Datadog / Grafana dashboards.** Time-series panels auto-refresh silently; the "live" indicator is a small pulsing dot or "Live" badge in the corner, not per-datapoint chrome. This is the right model for a **connection-status affordance** (see §4) — a small persistent indicator that the view is live-synced, separate from per-item change indication.

**Common thread across all four:** the further a view is from "you must act now," the more the UX suppresses interruption and the more it relies on subtle, spatially-anchored change indication (flash/pulse near the exact element that changed) rather than global toasts. Backlog list/board/detail are all "ambient supervision" views — they should follow the Linear/Trello/CI model (silent in-place update + brief flash), not the toast model.

## 2. User mental models and expectations

- **"If it's on my screen, it's true."** This is the single most load-bearing (and most violated) assumption for any dashboard-like view. Users do not model "this fetched once 4 minutes ago" — they model "this is what's happening now." The bug isn't cosmetic; a user approving/reopening/overriding a verdict based on stale card state is a **correctness** hazard, not just a freshness annoyance.
- **Expectation of "it just works" after the first live-updating experience.** Once a user has seen `/sessions` or `WatchSessions`-backed views update live, they generalize that expectation to every other list in the app. Inconsistency (sessions update live, backlog doesn't) reads as a bug even though it's a scoping gap — this is explicitly named in the requirements doc's baseline.
- **Multiple tabs = one source of truth, not N independent views.** The requirements doc calls out "multiple browser tabs/sessions open on the same backlog items concurrently" as a named consumer. Users expect action-in-tab-A to be reflected in tab-B without manual refresh — this is the same expectation NotificationContext's `BroadcastChannel` cross-tab sync already serves for toast dismissal (`createNotificationSyncChannel`, line 13, 309–324) — precedent exists in-repo for exactly this need.
- **Trust calibration for autonomous systems specifically.** This app's whole premise is "autonomous work you supervise without babysitting" (see job-to-be-done below). A live-updating backlog is not a nice-to-have polish item here — it's the mechanism that makes "don't babysit" actually safe. If the screen doesn't update, the *rational* response for a careful operator is to babysit anyway (refresh compulsively), which defeats the product's core value prop.
- **Expectation of graceful degradation, not silent failure.** Users who've used any live-sync tool (Google Docs, Figma, Slack) expect an explicit "reconnecting…" state when the stream drops, not a view that quietly reverts to feeling live while actually being frozen. Silent staleness after a dropped connection is worse than never having had live updates, because it erodes the "if it's on my screen it's true" trust for *every* view, not just the one that broke.

## 3. Accessibility requirements — ARIA live regions specifically

WCAG 4.1.3 (Status Messages, AA) is the controlling criterion: a status change that doesn't shift keyboard focus must still be programmatically announced to assistive tech. Concrete requirements for this feature:

- **Politeness level: `aria-live="polite"` almost everywhere, never `assertive` for routine state.** `assertive` interrupts the screen reader's current speech — appropriate for e.g. an error blocking the user's current action, wildly inappropriate for "item 14 of 40 moved from ready to in_progress" while the user is reading item 3's detail panel. `GateVerdictBox.tsx` already uses `role="status" aria-live="polite"` (line 234–236) correctly — extend this pattern, don't introduce a competing convention.
- **Don't make the whole list/board a single live region.** If `/backlog`'s entire item list is wrapped in one `aria-live` region, every single item mutation (of which there may be dozens per minute under active autonomous reconciliation) gets queued and read aloud sequentially — a screen reader user gets a firehose of "item X changed, item Y changed…" with no way to skip it. Best practice (and what most kanban tools with accessible live regions do): scope `aria-live="polite"` to a **small, dedicated summary region** ("3 items updated") rather than the mutating content itself, OR scope it per-card only for the specific item currently focused/expanded (e.g., the open `BacklogItemDetail` panel, where one status/verdict change is exactly the kind of single discrete announcement `aria-live="polite"` is designed for).
- **`aria-atomic="true"` on any live region whose text is replaced wholesale** (e.g., "Status: In Progress" → "Status: Review") so the screen reader reads the whole updated phrase, not a diff of the DOM text nodes.
- **Never rely on color alone for the "just changed" flash.** If a brief highlight treatment is added to `BacklogItemCard` (per the requirements doc's suggestion), it must not be the sole signal — pair it with the badge/label content itself changing (which it already does: verdict badge text, status label) so colorblind users and non-visual users get the same information via text, and the flash is pure enhancement for sighted users already tracking the screen visually.
- **Keyboard focus must never move involuntarily.** A card re-rendering with new data must not steal focus from whatever the user is currently interacting with (e.g., typing in `BacklogItemForm`'s edit mode, or reading `GateVerdictBox`'s override textarea). React's default reconciliation is safe here as long as updates are prop/state changes to the same DOM node, not remounts (key changes) — worth calling out explicitly in the plan since a naive "flash" implementation via conditional `key={item.updatedAt}` would force a remount and lose focus/scroll position.
- **Respect `prefers-reduced-motion`** for any flash/pulse/transition treatment — a hard requirement given `theme.css.ts`/vanilla-extract is already the CSS system in place; wrap animation keyframes in a `@media (prefers-reduced-motion: no-preference)` guard, falling back to an instant (non-animated) background-color swap that still resets after ~1s for reduced-motion users, rather than removing the change indication entirely.

## 4. Error / edge-case UX

**Stream disconnect / reconnect.** Precedent already exists in-repo for this exact problem: `refreshHistory()` in `NotificationContext.tsx` is explicitly documented as "e.g. after a stream reconnect" (line 61) — i.e., the existing session-notification stream already has a reconnect-triggers-refetch pattern to copy. For backlog:
- Show a small persistent "Live" / "Reconnecting…" indicator (Datadog/Grafana pattern from §1) somewhere globally visible (header or per-view), not a toast, since connection state is ambient, not an event.
- On reconnect, force a full re-fetch of currently-visible items (not just resume streaming from "now") — any mutations during the gap must be reconciled, exactly the same problem `WatchSessions`/session state already solved. Don't invent a new reconciliation strategy; reuse whatever `sessionsSlice`/`useSessionService` does on reconnect.
- If disconnected for longer than some threshold, degrade to the existing 5s-poll fallback already used elsewhere in this codebase (`BacklogItemDetail`'s poll) rather than showing a broken/frozen screen — "live but occasionally choppy" beats "live-looking but silently dead."

**Item changes status while open in edit mode.** `BacklogItemDetail` already has the right instinct here — polling is explicitly suspended `&& !editMode` (line 245) specifically so a background refresh can't clobber unsaved edits. The event-driven version must preserve this: an incoming event for the currently-open item while `editMode` is true should be **queued/buffered**, not applied — and the UI should surface "this item changed elsewhere while you were editing" as a non-blocking banner (reuse `InlineError`'s non-error, informational styling, or add a sibling `InlineNotice`) offering "reload to see latest" rather than silently discarding the incoming update *or* silently overwriting the user's draft. Silent data loss in either direction is the failure mode to design against.

**Item disappears from a filtered view because it no longer matches.** This is the Trello "ghost placeholder" problem from §1. Two sub-cases:
- **List/board views with an active filter** (e.g., "show only `ready`" or a saved Kanban column): when a live event moves an item out of the filter's match set, don't just yank it — a card vanishing mid-glance reads as "did it get deleted?" not "did it move?". Recommended: brief exit transition (fade/slide, respecting reduced-motion) rather than instant removal, so the user's eye tracks *that* the item is gone and can infer why (its status badge was visibly changing right before).
- **The open detail panel for an item that moves outside the currently selected view's scope** (e.g., user has `/backlog/board` filtered to `ready` items open, and the item they're inspecting transitions to `in_progress` via reconciliation): the *detail panel itself* should keep showing the item (per requirements: "session attaching... becomes visible... in `BacklogItemDetail`") even though the underlying list/board would have dropped it — detail is a permalink-style view, keyed by `itemId`, and shouldn't unmount just because a filter elsewhere no longer matches. Confirm this decoupling explicitly in the plan (detail subscribes by ID, list/board subscribe by filter+ID set) since it's an easy thing to get backwards.

**Multiple simultaneous events for the same item (race/ordering).** Autonomous reconciliation can fire several mutations to the same item in quick succession (status change + verdict landing + session attach, near-simultaneously). Whatever event payload shape is chosen (full item snapshot vs. delta), apply a **last-write-wins by server timestamp/version**, not by arrival order, so a client that receives events slightly out of order (plausible over WebSocket/SSE under load) doesn't flicker backward to a stale state. `sessionsSlice`'s `updateItem` reducer pattern (partial merge keyed by ID) is the right shape to copy; just ensure whatever "version"/timestamp field is added to the backlog item is compared, not blindly overwritten.

## 5. Jobs-to-be-done lens

**Functional job:** "Let me know the moment my backlog item's state changes, wherever I'm looking at it, without me having to ask." This is a straightforward correctness/freshness job — the functional job most JTBD analyses would stop at.

**Emotional job — this is the one that matters most for this specific app.** The whole positioning of Stapler Squad is "autonomous AI agents doing real work while a human supervises instead of babysits" (see `feedback_use_agent_tool_not_sessions` and the backlog reconciler/auto-ship/auto-reopen pipeline described in the requirements baseline). The emotional job of live updates here is **anxiety reduction under delegated trust**: an operator who has handed off a body of work to autonomous agents needs the dashboard itself to feel *trustworthy enough that not-refreshing is safe*. Every manual refresh a user performs is a small, measurable vote of "I don't actually trust this screen" — and a system that requires constant manual refreshing to feel safe has functionally failed at delegation, even if the underlying automation is working perfectly. This reframes the priority ordering: `in_progress` (currently the *one* status with zero polling) is disproportionately important to fix first, because it's the longest-duration, most anxiety-prone state — "is my agent still working, stuck, or did something just happen and I don't know yet?"

**Social job:** for an operator who might show this dashion to a colleague/manager as evidence that "the AI backlog pipeline is working," a screen that visibly updates in real time *while they're both looking at it* is a much stronger trust signal / demo moment than a static list that requires an F5 to prove it's alive — directly serves the "software factory" framing this project has (see `backlog-feature-improvement` skill description: "closer to a software factory"). Live-updating UI is itself a piece of evidence for the product's core claim, not just a UX nicety.

**Implication for prioritization/design:** because the emotional job (anxiety reduction / "is it safe not to babysit") outweighs the functional job (freshness) in this specific app's context, the design should bias toward **visible liveness cues** (the small persistent "Live"/connected indicator from §4) even in moments with no data change — a dashboard that's silent for 10 minutes because nothing happened is indistinguishable, from the anxious operator's point of view, from one that's silently broken. This is a case where "just make it accurate" isn't sufficient UX; the system needs to also *prove* it's accurate, ambiently, the same way Slack's "connecting…" pill or Google Docs' "all changes saved" footer do.

## Recommendations summary (for the planning phase)

1. **Architecture**: extend the existing `WatchSessions`-style server-streaming + Redux-slice-with-`add/update/remove`-reducers pattern to backlog items, rather than inventing a parallel mechanism or leaning on toast infrastructure. Backlog live-updates are a state-projection problem, structurally identical to what session state already solved.
2. **No toasts for routine backlog mutations.** Silent in-place update + a brief (reduced-motion-aware) highlight flash on the changed card/row/panel section, mirroring Linear/Trello/CI conventions. Reserve toast-style interruption (if any) for genuinely actionable terminal events already in `NotificationContext`'s domain (e.g., approval needed) — don't duplicate that channel for backlog status noise.
3. **`BacklogItemCard`**: add a brief flash/pulse treatment keyed to a changed-fields diff, not a remount (avoid `key` churn that would break focus/scroll). `VerdictBadge` and status label already change their rendered text/color on data change — the flash is pure enhancement, not new information.
4. **`GateVerdictBox`**: its `role="status" aria-live="polite"` root is already correctly positioned to announce an incoming live verdict change when in `readOnly` mode — no structural change needed there, just feed it live data and confirm `aria-atomic="true"` is added so the whole updated phrase is announced.
5. **Detail panel decoupling**: `BacklogItemDetail` must subscribe by `itemId` regardless of any list/board filter state, and must buffer/queue incoming updates while `editMode` is active (extending the existing poll-suspend precedent) rather than clobbering unsaved edits or dropping the update.
6. **Filtered-list disappearance**: brief exit transition rather than instant removal when an item stops matching the current view's filter, so it reads as "moved" rather than "vanished/deleted."
7. **Connection state affordance**: add a small, persistent, ambient "Live / Reconnecting" indicator (Datadog/Grafana pattern) — this serves the emotional job of proving the screen is trustworthy, not just the functional job of freshness — and fall back to the existing 5s-poll mechanism during extended disconnects rather than freezing silently.
