## Concerns

- [ ] **Task 1.3.1a / Task 1.2.1b — primitive obsession on `OldStatus`/`NewStatus`.** Both new Go structs type `OldStatus, NewStatus` as raw `string`, even though the call site already has a typed value in scope: `EntRepository.TransitionBacklogItemStatus(ctx, id, toStatus BacklogStatus, ...)` (`session/ent_repository_backlog.go:674`) takes a typed `BacklogStatus` parameter (`session/backlog.go:14`, `type BacklogStatus = domain.BacklogStatus`). Unlike the existing `BacklogItem.status` proto field or `BacklogItemData.Status` Go field (both pre-existing raw `string`, which this plan is right not to touch — that's out of scope), `BacklogItemChange` and `BacklogItemEventPayload` are **brand-new types being designed from a blank slate right now**. There's no legacy reason to downcast to `string` here specifically.
  - **Remediation**: Type `OldStatus`/`NewStatus` on both new Go structs as `session.BacklogStatus`, converting to the proto `string` field only at the proto-conversion boundary (`convertEventToBacklogItemEvent`, Task 3.1.1d) — a real parse-at-the-boundary application rather than passing the raw string through every internal layer.

- [ ] **Domain Glossary / Task 1.3.1a — `BacklogItemChange` reproduces the exact "grab-bag struct" anti-pattern the proto oneof was designed to avoid.** Step 0.5 explicitly rejects Option 1 (a single generic event with a flat field list) because "verdict recorded and session attached aren't field diffs... forcing them through a generic field-list either fabricates fake field names or loses information." Correct call at the proto layer. But `BacklogItemChange` (Go, pre-conversion) and `BacklogItemEventPayload` (bus envelope) are exactly that rejected shape one layer down: one flat struct with `Kind` plus `OldStatus`/`NewStatus`/`UpdatedFields`/`SessionID`/`ArchivedAt`/`RemovedReason` (and, per the blocker above, no `Verdict`) where only a handful of fields are meaningful per `Kind` — e.g. `BacklogItemChange{Kind: ChangeVerdictRecorded, OldStatus: "review", NewStatus: "done"}` compiles and constructs cleanly despite being nonsensical for that `Kind`. This is worth noting as a real (if scoped) inconsistency: the plan correctly avoids further bloating the existing flat `events.Event` struct by nesting a new payload field rather than adding 8 more top-level fields (good instinct, better than the existing `Session`-event convention it's extending) — but then repeats the identical illegal-states-representable problem one level inside that new nested struct.
  - **Remediation**: Model `BacklogItemChange` as a Go sum type — either a tagged union via unexported marker methods (`type BacklogItemChange interface { isBacklogItemChange() }` with `StatusTransition{Old, New BacklogStatus}`, `VerdictRecorded{Verdict ReviewVerdictData}`, `SessionAttached{SessionID string}`, `ItemUpdated{Fields []string}`, `ItemArchived{At time.Time}`, `ItemRemoved{Reason string}` as the 6 concrete types), or accept the flat struct as a pragmatic wire-adjacent DTO but add a constructor function per `Kind` (`NewStatusTransitionChange(old, new BacklogStatus) BacklogItemChange`) that only exposes the fields relevant to that kind, so callers can't hand-construct an inconsistent combination. Given this is new code with no existing callers to migrate, the sum-type version is not expensive to do now and directly fixes the class of bug type-driven design targets.

- [ ] **Pattern Decisions table — no evaluated alternative for "publish call embedded directly in 6 `EntRepository` methods" vs. a Decorator wrapping the repository.** The plan's Pattern Decisions table is unusually rigorous about recording rejected alternatives everywhere else (Options 1–3 in Step 0.5, `Notifier`-widening rejected via ADR-001, enumeration-test rejected in favor of repository hooks), but never considers a GoF Decorator — a `PublishingRepository` wrapping the base `EntRepository`/`Repository` interface, intercepting only the 6 mutating methods and delegating everything else — as an alternative to threading `r.itemChangePublisher` nil-checks directly into 6 methods scattered across a 1384-line file (`session/ent_repository_backlog.go`). A Decorator would keep `EntRepository` itself free of any notion of "who is listening" (stronger SRP) and make the base repository trivially testable with zero publisher awareness. The plan's counter-argument likely holds (a Decorator implementing the full `Repository` interface just to intercept 6 of ~30+ methods is itself the "forwarding-only wrapper" smell flagged in `.claude/rules/interface-pollution-checklist.md`'s smell #4) — but the plan never states this reasoning, despite doing so rigorously for every other pattern choice in the same table.
  - **Remediation**: Add one row to the Pattern Decisions table naming this alternative and the forwarding-wrapper-boilerplate reason for rejecting it, for the same completeness/future-proofing reason ADR-001 exists — so a future contributor doesn't "clean this up" into a Decorator without knowing the trade-off was already considered.

- [ ] **Epic 7.2 — the `MergeDatabase` live-leak trace is scoped into Phase 7 (Testing) but may require a Phase 2 code change.** Task 7.2.1a defers discovering *whether* the bulk-copy path loops through the 6 hooked methods (a leak) to implementation time, in Phase 7 — the same kind of "confirm during implementation" deferral flagged as a blocker above for the wiring location. If the trace finds a leak, Task 7.2.1b's fix (adding a `skipEventPublish` bypass parameter to the hooked repository methods) changes the **signature** of methods already implemented and hooked in Phase 2, three phases earlier — meaning Phase 2's work may need revisiting rather than being purely additive, which the Dependency Visualization diagram doesn't currently show as a possible feedback edge.
  - **Remediation**: Move Task 7.2.1a (trace only, no code) into Phase 2 planning/discovery, before Epic 2.1/2.2 are implemented, so the 6 hooked methods are designed with a bypass parameter/flag from the start if needed, rather than retrofitted after the fact. Leave the confirming test (7.2.1b) in Phase 7.

## Nitpicks

- `pkg/events/types.go`'s existing `Event` struct already has top-level `OldStatus session.Status` / `NewStatus session.Status` / `UpdatedFields []string` / `SessionID string` fields (lines 44-47, 42, 40) for **session** events. The new `BacklogItemEventPayload.OldStatus`/`NewStatus`/`UpdatedFields`/`SessionID` fields (nested, but same names) sit right alongside these on the same `Event` value. No Go collision (they're on different structs), but the name reuse across two unrelated domains (session status vs. backlog status) on the same envelope type invites future confusion — consider a naming pass (`BacklogOldStatus` or similar) if this becomes a maintenance pain point, though not worth blocking on.
- The new `old_status`/`new_status` proto fields (Task 1.1.1a) are raw `string`, consistent with the existing (pre-dating this plan) `BacklogItem.status` field (`proto/session/v1/backlog.proto:119`, also raw `string`, unlike `SessionStatus` which is a proper enum). This is defensible as "match existing convention, don't scope-creep a fix into this plan" (and `Out of Scope` explicitly excludes state-machine changes) — flagged only so it's a conscious choice, not an oversight.
- Proto3 cannot statically prevent a `BacklogItemVerdictRecordedEvent` from being constructed with `verdict` unset (message fields are always optional in proto3) — the plan's "illegal states unrepresentable" claim for the oneof is true at the *variant-selection* level but not within a variant's own fields. This is an existing limitation shared by `ReviewQueueEvent` (no worse here), but a constructor helper (`NewVerdictRecordedEvent(itemID, verdict, item)` that errors/panics on a nil verdict) would close the gap cheaply, matching the parse-at-boundary spirit `NewBacklogItemChangedEvent` already partially embraces.
- `Story 1.1.1`'s acceptance-criteria example (`event.GetVerdictRecorded()` returns `nil`) is a good illegal-state-prevention test — worth keeping as a template for the analogous check on all 6 variants, not just the one shown.

## Validated (no finding — confirmed during review)

- **`session.ItemChangePublisher` layer coupling**: confirmed clean. The interface signature (`PublishItemChanged(item *BacklogItemData, change BacklogItemChange)`) references only `session`-package types — no import of `server/services` or `pkg/events`, matching `Notifier`'s existing shape exactly.
- **`ItemChangePublisher` is not a speculative interface** (interface-pollution-checklist smell #1): the `session`→`pkg/events` import cycle is a genuine, mechanical constraint (confirmed: `Notifier`'s own doc comment at `session/backlog_lifecycle.go:22-27` states `pkg/events` imports `session`), not a "might need it later" hedge — same justification already accepted for `Notifier`. No violation.
- **Build-vs-buy override (Synthesis Note) is justified, not cherry-picked.** Independently verified: `proto/session/v1/session.proto:754`'s `WatchReviewQueueRequest` has no `after_seq`-equivalent field, and `server/review_queue_manager.go` has zero references to `AfterSeq`/`Seq`/`EventsSince`. `build-vs-buy.md`'s own Option 4 recommendation (copy `ReactiveQueueManager`) never checks this — it recommends the manager pattern without verifying it meets the requirement's explicit reconnect/replay ask. The plan's override (build transport on `pkg/events.EventBus` directly, borrow only `ReviewQueueEvent`'s proto shape) is the architecturally correct call given `after_seq`/replay is a hard requirement, and `build-vs-buy.md` itself is the weaker analysis here, not the plan.
- **RPC handler testability** (Epic 3.2): hand-rolled fake `connect.ServerStream` avoids the "subscribe to a real bus and assert" antipattern pitfalls.md flags — good design, directly exercises branching logic in isolation.
- **API contract stability** (oneof-of-submessages): additive-safe : new variants can be added without breaking existing clients; matches `ReviewQueueEvent` precedent.
