# Adversarial Review: backlog-event-driven-updates

**Date**: 2026-07-21
**Verdict**: CONCERNS

## Blockers

None. Both prior blockers were re-verified against the current plan.md and are resolved:

- [x] **(Resolved) Epic 3.2's fake `connect.ServerStream[T]` infeasibility.** The plan now splits the handler (Task 3.1.1a): a narrow local interface `type backlogItemEventSender interface { Send(*sessionv1.BacklogItemEvent) error }` is defined in `server/services/backlog_service_events.go`, the registered RPC method (`WatchBacklogItems`) is reduced to a thin wrapper that calls `s.watchBacklogItems(ctx, req.Msg, stream)`, and all snapshot/replay/filter/fan-out logic lives in `watchBacklogItems(ctx, msg, sender backlogItemEventSender)`. Verified independently against the vendored source (`$(go env GOPATH)/pkg/mod/connectrpc.com/connect@v1.19.0/handler_stream.go:117`): `func (s *ServerStream[Res]) Send(msg *Res) error` — this signature satisfies `backlogItemEventSender` structurally with zero adapter code, confirming the plan's claim. Story 3.2.1/Tasks 3.2.1a-d now test `watchBacklogItems` directly via a hand-rolled `fakeBacklogItemEventSender` (Task 3.2.1a) that only implements the narrow interface — no test anywhere constructs or fakes a real `*connect.ServerStream[T]`. This is option (a) from the original recommendation, correctly implemented; the fix does not rename the problem, it actually routes around the unconstructible concrete type.

- [x] **(Resolved) No enforced guarantee that a publish failure/panic cannot affect the underlying mutation.** Task 1.3.2b adds `defer func() { if r := recover(); r != nil { log.WarningLog.Printf(...) } }()` at the top of `BacklogItemEventPublisher.PublishItemChanged` itself (`server/services/backlog_item_event_publisher.go`), before any payload construction or `p.Bus.Publish(...)` call. Reasoned through Go semantics: `PublishItemChanged` is called synchronously (`r.itemChangePublisher.PublishItemChanged(...)` inside `TransitionBacklogItemStatus`, not from a goroutine); a `defer recover()` set up inside a function's own frame runs during stack unwinding *before* a panic in that frame propagates to the caller — recover() stops the unwind at that frame and the function returns normally (here, with no return value, so the caller just continues as if the call had succeeded). Because the recover lives inside `PublishItemChanged`'s own body, not in `TransitionBacklogItemStatus` or in a separate goroutine, the panic never reaches the calling repository method — placement is correct. `PublishItemChanged` deliberately keeps its no-error-return signature (Story 1.3.1) since there is now never an error/panic for a caller to handle. Task 2.1.1d adds the regression test: a `panickingPublisher` wired into `TransitionBacklogItemStatus` via `SetItemChangePublisher`, asserting both (1) the method returns its normal success result and (2) the underlying row was actually updated (re-fetched and checked) — proving containment end-to-end at a real hooked call site, not just at the adapter in isolation.

## Concerns

- [ ] **`after_seq` replay and live fan-out can double-deliver the same event.** Task 3.1.1a mirrors `WatchSessions`'s "subscribe before snapshot/replay" ordering, whose own comment says "snapshot races are resolved by client-side upsert semantics" (`session_service.go:1996-1997`) — but this hand-waves a real duplicate-delivery race: an event published between `Subscribe()` and the `EventsSince(afterSeq)` read (Task 3.1.1c) is already sitting in the ring buffer (so `EventsSince` returns it) *and* was already pushed onto `eventCh` (since the subscription was live at publish time) — so it is sent once via the replay loop and once via the live loop. For `SessionEvent` this is harmless (idempotent overwrite). For this plan specifically it is more exposed: (a) `BacklogItemRemovedEvent` (Task 1.1.1b) triggers `removeItem`, which is idempotent, but (b) Epic 6.1's flash/highlight animation is keyed off `is_snapshot: false` events (Task 6.1.1a) — a duplicated live delivery would double-flash the same card, and neither Task 3.1.1c nor Story 4.2.2 specifies whether replayed events are marked `is_snapshot: true` (to suppress the flash) or retain their original snapshot flag. No task tests or resolves this. — **Recommendation**: either dedup by `Seq` client-side (skip an incoming event whose `Seq` was already applied) or explicitly mark every event sent through the `EventsSince`/replay branch as `is_snapshot: true` regardless of its original flag, and add a test proving no double-flash on reconnect-with-in-flight-event.

- [ ] **Missing explicit regression coverage for the "no regression in triage progress / pr_pending polling" Success Metric.** requirements.md's Success Metrics explicitly names triage progress and `pr_pending` state as existing `shouldPoll`-covered behavior that "must still update at least as promptly under the new mechanism." Neither "triage" nor "pr_pending" appears anywhere in plan.md outside background/glossary references — Story 5.3.1's acceptance criteria only cover the previously-uncovered `in_progress` blind spot and filter-decoupling. There is no task asserting that a triage-in-progress item's live progress updates, or a `pr_pending` item's transition to `done`/`review`, actually reach `BacklogItemDetail` at least as fast as the deleted 5s poll did. — **Recommendation**: add an explicit acceptance criterion/task under Story 5.3.1 (or Phase 7) exercising both named legacy-`shouldPoll` scenarios end-to-end against the new stream.

- [ ] **Forward-gap detection (pitfalls.md #4's headline new feature) is only tested against a synthetic mock, not a real dropped event.** Task 4.2.2d tests by "mock[ing] the stream's async iterable to emit events with a seq gap" — a hand-injected gap, not an actual `EventBus` dropping an event for a slow subscriber under real backpressure. pitfalls.md §4 explicitly argues backlog is at *higher* real-world risk of this than sessions (backgrounded-tab buffer exhaustion). No task exercises the real `EventBus` + real handler + real hook chain under an actual buffer-overflow condition to confirm the self-healing resync fires in practice, only that the hook's own gap-comparison logic works given a hand-fed gap. — **Recommendation**: add one integration-style test that fills a real `*events.EventBus` subscriber channel to overflow (mirroring `pkg/events/bus_test.go`'s existing `TestEventBusBufferOverflow`) while a `WatchBacklogItems` stream is attached, and confirms the client-observable effect (a forced resync) actually happens.

- [ ] **`BacklogItem.updatedAt` is a protobuf `Timestamp` object, not the ISO string the plan's own acceptance criteria model it as — the staleness guard as illustrated would silently never trigger.** Confirmed in generated bindings (`web-app/src/gen/session/v1/backlog_pb.ts:543` etc.): `updatedAt?: Timestamp` (a `{seconds: bigint, nanos: number}` object), identical in shape to `sessionsSlice.upsertSession`'s existing `existing.updatedAt.seconds`/`.nanos` comparison (pitfalls.md's own quoted snippet). Story 4.1.1 and Tasks 4.1.1a/b's acceptance-criteria examples instead write `updatedAt: "2026-07-21T10:00:05Z"` and describe the guard as `incoming.updatedAt < existing.updatedAt` — a plain JS `<` between two proto `Timestamp` objects does not do what's intended: absent a custom `valueOf`/`Symbol.toPrimitive`, `<` coerces both operands via `toString()` to `"[object Object]"` and compares those (always `false`), so the "real" staleness guard this plan exists specifically to add (vs. `upsertSession`'s weaker equal-only check) would silently no-op if implemented literally per the acceptance criteria. — **Recommendation**: make Task 4.1.1b explicit that the comparison must convert both sides to a comparable scalar first (e.g. `Number(seconds) * 1e9 + nanos`, or reuse/extract a `timestampToNanos` helper), and correct the acceptance-criteria examples in Story 4.1.1 to use `Timestamp`-shaped values instead of ISO strings so implementers don't copy the wrong shape.

- [ ] **Redux-slice decision's "alternative rejected" is a strawman; the harder alternative was never named.** The Pattern Decisions table compares "Redux slice" only against "local `useState` per consumer" (today's baseline, which predictably loses on the stated divergent-state-between-list-and-detail argument). It never names or rejects the middle option the task explicitly asks to consider: a backlog-scoped React Context + `useReducer` (same normalized-map/single-subscription benefit, without adding the backlog domain to the global Redux store for the first time). Given today's `/backlog` and `/backlog/board` use local state and Redux is otherwise reserved for sessions/review-queue/bulk-selection, this is worth an on-the-record rejection rather than an implied one. Not necessarily the wrong call (Redux is already a project dependency and the normalized-map shape does mirror `sessionsSlice`), but the "hardest pushback" alternative was skipped in the written analysis. — **Recommendation**: add the Context+useReducer option to the Pattern Decisions table with an explicit rejection reason (e.g. "would still require lifting subscription above both list and detail, at which point it's a bespoke store with none of Redux DevTools/existing selector-memoization tooling `sessionsSlice` already gets for free").

## Minors

- `BacklogItemEventPayload`/`BacklogItemChange` (Go-side, Tasks 1.2.1b/1.3.1a) are grab-bag structs with one field set per `Kind` — a 7th event kind will touch 5-6 layers (proto oneof, `events.go` struct+enum, `session` package struct+enum, adapter switch, RPC handler switch, frontend exhaustive switch). This mirrors the existing `events.Event`/`Session` precedent (not a new liability introduced by this plan), and the proto-layer alternatives were seriously weighed (Step 0.5), but the Go-envelope alternative (a typed `any`/interface payload with type assertions, avoiding further bloating the shared `Event` struct as more domains adopt it) was never named or rejected on the record the way the proto shape was. Consider a one-line note in Pattern Decisions acknowledging this is inherited scope, not a new choice.
- Task 1.3.3a leaves "confirm during implementation which struct [`Storage` or `EntRepository`] the 6 methods are actually defined on" open. If the methods turn out split across both structs, `SetItemChangePublisher` wiring needs to happen in two places instead of one — worth a quick `grep -n "func.*TransitionBacklogItemStatus\|func.*UpdateBacklogItem"` pre-check before Phase 1 starts to remove this ambiguity up front rather than discovering a two-struct split mid-Phase-2.
- Phase 6 (UX Polish, including the ux.md-flagged high-priority Live/Reconnecting `ConnectionIndicator`) is last in the dependency chain (Phase 6 depends on all of Phase 5). Given the "Large" 3-6 week appetite and 8 phases, if the project runs long and phases get trimmed, the specifically-called-out-as-important connection indicator is the first casualty despite the plan correctly including it as a concrete story (Epic 6.2, not just glossary-only as the review question worried). Consider explicitly protecting Epic 6.2 from schedule cuts, or pulling `ConnectionIndicator` earlier (it only depends on `useWatchBacklogItems`'s `connectionState`, which exists after Phase 4).
- Epic 7.2 (`MergeDatabase` leak check) is appropriately actionable (trace-then-fix-or-confirm, Tasks 7.2.1a/b) — flagged here only to note it was checked and found adequate, not a gap.
