| 1 | ~~Server restart/redeploy while operators have tabs open leaves the tab stale forever~~ **[RESOLVED 2026-07-21 — Phase 4 triad-review repair loop]**: backward-seq-jump detection only fires on the *next live event* for that item, and unlike `WatchSessions` (30s/15s idle-staleness backstop, `useSessionService.ts:944-980`), no task in Epic 4.2 adds an equivalent periodic backstop for `useWatchBacklogItems` — so an item that goes quiet after reconnect (e.g. settles in `done`) never self-heals. | An operator runs `make install-service` (routine in this repo per `.claude/rules/tmux-keep-server-on-restart.md`) or any redeploy; their open `/backlog` tab keeps showing pre-restart data with the connection indicator still saying "Live," because no event ever arrived to trip the gap check. | Add a task under Epic 4.2 mirroring `useSessionService.ts`'s time-since-last-event idle timer (15–30s, forces reconnect + full `listBacklogItems` refetch even with zero live events), and a Phase 7 test that simulates a server restart (seq reset) with no organic event and asserts the client still resyncs. **Resolved**: added `plan.md` Epic 4.2 Story 4.2.3 (Tasks 4.2.3a-d), porting `useSessionService.ts:944-997`'s exact 30s periodic backstop + 15s visibility/online staleness check to `useWatchBacklogItems`, plus a fake-timer unit test asserting a refetch fires after simulated silence past the timeout. | P2 |
| 2 | The 6 repository-layer publish hooks are correctly "impossible to miss" only for the 6 methods that exist *today*. Nothing in the plan (no lint rule, no shared choke-point helper, no architecture test) stops a future PR from adding a 7th mutating method (e.g. a new `stuck_reason` field, a bulk-reassign method) that bypasses all 6 hooks entirely — the same "silent missed call site" bug this project exists to eliminate reappears one layer up, just later. | Six months post-ship, a new bulk/administrative backlog mutation ships, passes all tests (there's no structural gate that would fail), and its state changes are invisible in every live view until a manual refresh — indistinguishable from the original bug this project was built to kill. | Add either (a) a single shared `persistBacklogItemMutation`-style helper that all mutating methods (present and future) must route through, so skipping publish requires visibly not calling the helper, or (b) an architecture/lint check (ast-grep or `go/analysis`) that flags any exported `*EntRepository` method performing an ent `Update`/`Save`/`Delete` for `BacklogItem`-adjacent tables without a call to `itemChangePublisher`. Document the chosen guard explicitly in plan.md rather than relying on the current prose claim of structural impossibility, which only holds for today's 6 methods. | P2 |
| 3 | Redux slice is the correct call per the plan's stated reasoning (list+detail mounted simultaneously), but the actual risk of "wrong" isn't architectural failure — it's a well-known normalized-map + `useSelector` footgun: a naive selector like `Object.values(state.backlogItems.items)` creates a new array reference every render, which either (a) triggers full-list re-renders on every unrelated item's event (perf drag, and undermines the "no remount, preserve scroll/focus" goal of Epic 6.1's flash), or (b) if wrapped incorrectly in memoization, drops re-renders that should have fired. Neither Pattern Decisions nor any task calls for a memoized selector (`createSelector`/reselect) as an explicit requirement. | `/backlog` with many items feels janky (every card subtly re-renders, or the "no remount" flash guarantee from Task 6.1.1a silently fails) once real event volume during active reconciler activity is exercised — a perf/trust regression discovered late, likely during Phase 6 UX polish or after ship, not caught by any task in Phase 4 or 7. | Add an explicit acceptance criterion to Story 4.1.1 or Epic 4.2 requiring memoized selectors (reselect `createSelector` or equivalent) for any list-shaped read off `backlogItemsSlice`, plus a test asserting that updating one item's entry does not cause an unrelated `BacklogItemCard`'s render count to increase (a cheap render-count assertion, not a full perf benchmark). | P3 |
| 4 | ~~Adversarial review's CONCERN #1 (double-delivery race between `Subscribe()` and `EventsSince(afterSeq)`)~~ **[RESOLVED 2026-07-21 — Phase 4 triad-review repair loop]**: has a concrete, everyday trigger: any reconnect (laptop sleep/wake, WiFi blip, tab backgrounding) that races a real concurrent mutation delivers the same event via both the replay branch and the live branch. Because Task 3.1.1c doesn't force `is_snapshot: true` on replayed events, this manifests as exactly the two most trust-sensitive UX affordances the plan adds: a double flash/pulse (Epic 6.1) and a double `aria-live` announcement of the same verdict (Epic 6.2) for one transition. | An operator (or, worse, a screen-reader user) sees/hears the same status change announced or flashed twice in a row immediately after reconnecting — precisely the moment they're relying on the UI to tell them accurately what changed while they were away — training them to distrust the "just changed" signal going forward (cry-wolf effect on the exact feature meant to build trust). | Make Task 3.1.1c mark every event sent through the `EventsSince`/replay branch `is_snapshot: true` unconditionally (regardless of the event's original flag), and add a handler test that publishes an event in the race window between `Subscribe()` and the `EventsSince` read and asserts it is delivered exactly once as a snapshot event, never twice. **Resolved**: `plan.md` Task 3.1.1c now explicitly forces `is_snapshot: true` on every replay-branch event before `sender.Send(...)`, and Story 3.1.1 gained a matching Given-When-Then acceptance criterion covering the race-window scenario. | P2 |
| 5 | Requirements.md's Success Metric explicitly demands no regression versus today's `shouldPoll` coverage of **triage progress**, but no task anywhere verifies which repository method(s) triage progress actually writes through. If triage writes via a 7th method not among the 6 hooked ones (plausible — pitfalls.md §3 separately names `backlog_service_triage.go` as one of ~30 independent call sites, and triage's update cadence/shape looks nothing like the title/description/planText/AC-list diff `UpdateBacklogItem`'s hook was scoped for in Task 2.2.1a), the shipped feature doesn't just fail to add live triage updates — it actively regresses today's working 5s poll to zero live updates for that one state, which is worse than baseline for the single most-actively-watched in-flight state. | Within the first weeks post-ship, an operator watching a triage run — the state most likely to be open and watched in real time — sees the detail panel go silent after `shouldPoll`'s polling is removed (Task 5.3.1a), because no event kind was ever wired for triage-progress writes; a bug report lands citing the very regression requirements.md named as a hard non-goal. | Before implementation starts, add a discovery task (grep `backlog_service_triage.go` for exactly which repository method(s) mutate triage-progress fields) and, if it's not one of the 6 hooked methods, add a 7th hook (or fold triage-progress writes into `UpdateBacklogItem`) plus an explicit acceptance criterion/test under Story 5.3.1 exercising a real triage run end-to-end against the new stream, matching or beating the deleted poll's latency. | P1 |
