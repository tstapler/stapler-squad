# Pre-mortem: async-session-creation
**Date**: 2026-08-26

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The 10-minute Stale-Creation Sweeper threshold is empirically wrong for real corp-VPN GHE clone timing variance, so legitimately-slow-but-working `github.netflix.net` clones get flipped to `Failed` mid-clone on bad-VPN days, and users learn to distrust the Failed status and reflexively hit Retry, doubling load on GHE for the same clone. | Users on a flaky VPN/laptop-sleep-wake day report sessions "failing" that used to just take a while; support/Slack complaints cluster around specific hours or a specific office's network; retry-then-succeed becomes a common workflow, meaning the Failed status is now noise rather than signal. | Don't ship a single hard cutoff: require the sweeper to observe staleness across 2+ consecutive ticks (or use a per-phase timeout for the clone phase specifically, since that's the one identified slow phase) rather than a single elapsed-time check. Add the deferred empirical clone-timing instrumentation (Unresolved Questions in plan.md) as a hard prerequisite for picking the final threshold, not a "reasonable default, revisit later." Add a post-merge monitoring step (already flagged as missing in adversarial-review.md) that specifically tracks `outcome=stale` rate for the first 2 weeks. | P2 |
| 2 | The in-memory `TryForceStatusIfEpoch` "win" and the actual `storage.UpdateInstance`/ent-transaction persist are two separate steps, not one durable unit; if the process is killed between them, the Stale-Creation Sweeper (or a user) can see a `Creating` row that actually finished successfully (worktree exists, tmux session is alive) and flip it to `Failed`/retry it — and `cleanupPartialCreation`/Retry then deletes a live, working worktree and kills a live tmux session that may contain in-progress, unsaved agent work. | A user's session that was clearly working (they can see the tmux pane in another terminal, or the branch/commits exist) shows as `Failed` after a service restart, and clicking Retry silently destroys the working directory/session instead of just re-flagging metadata. | **RESOLVED** (plan.md Story 1.2.4, ADR-002 addendum): reversed the ordering — every terminal write now runs a durable, epoch-guarded conditional DB update (`storage.UpdateInstanceIfEpoch`) *first*, and only flips in-memory actor state (`TryForceStatusIfEpoch`) after that persist succeeds, via the new `commitTerminalStatus` orchestrator. A crash after the durable write always leaves the correct terminal state on disk for the next process to reload; the sweeper and Retry only ever act on a row that genuinely still reads `Creating`. The originally-proposed liveness-check-before-delete is kept as a second, independent defense-in-depth layer (plan.md Task 3.1.1d) for the smaller residual window (crash after real side effects exist but before the durable write is even attempted), not as the sole fix. Regression test: Task 1.2.4d (`server/services/session_creation_terminal_write_test.go`) simulates the crash by committing the durable write and then reloading into a fresh registry before any in-memory sync, asserting the reloaded status is correct. | P1 |
| 3 | The RPC becomes fast (meets the <500ms p99 metric), but the *session itself* is no more usable any sooner for a GitHub-URL creation — the user still stares at the same total wall-clock wait before they can type into the terminal, just now with a spinner on a card instead of a blocked dialog. The success metric ("creation appears within ~1s") is satisfied while the actual user complaint ("this feels like a freeze") is not resolved for the case that motivated the project. | Post-ship user feedback says "it still takes forever to actually use the GitHub session, you just changed where the spinner is" — the omnibar closes fast, but the card sits in `Creating` for just as long as the RPC used to block, and users perceive no improvement (or perceive the extra Cancel/Retry UI as new complexity for no payoff) for the one case (GHE clone) the project exists to fix. | Explicitly separate two different success metrics in requirements.md/plan.md: "RPC returns fast" (this project delivers) vs. "time-to-usable-session shrinks" (this project does NOT deliver, and should say so up front) — the actual win is observability/cancelability/non-blocking-UI during the wait, not a shorter wait. Add this framing to the PR description and to Phase 6's manual test so a reviewer checks perceived-improvement expectations against reality, not just the RPC latency number, before anyone claims the user complaint is "fixed." | P2 |
| 4 | Every phase transition now does a synchronous, full-table `ent` transaction (`storage.UpdateInstance`) inline in the pipeline goroutine (per architecture-review.md's write-amplification Concern), and this app's actual primary use case is running many parallel agent sessions at once — so under realistic concurrent session-creation load, sqlite/ent single-writer contention (further contended by the Stale-Creation Sweeper's own periodic scan query) makes the "low-single-digit ms" fast-path acceptance criterion for plain directory sessions empirically false, not just theoretically debatable. | Creating several sessions back-to-back (a normal workflow for this tool — spinning up multiple parallel Claude Code sessions) becomes noticeably slower than before this change, even for plain-directory sessions that do no network I/O, because each one now queues behind DB write contention from the others' phase-transition persists. | Resolve architecture-review.md's write-amplification Concern with a decision now, not "implementer's judgment": either scope per-phase persistence to only the phases that are actually load-bearing for restart survival (skip it for phases with nothing worth surviving a restart for, e.g. plain in-memory phases), or batch/debounce the writes. Add a concurrent-creation load test (N simultaneous `CreateSession` calls, N = realistic max parallel sessions this tool supports) to Epic 6.2, asserting the low-single-digit-ms claim holds under that concurrency, not just in isolation. | P2 |
| 5 | The web UI is used from multiple browser tabs/windows against the same backend (a normal pattern for this tool — multiple monitors/windows watching different session groups). If one tab cancels a `Creating` session (removing the instance) while another tab's view is stale, that second tab's user can click Retry on an instance ID that no longer exists — an interaction not covered by the 7-touchpoint/single-client registry or by single-browser-context Playwright specs. | A user with two windows open sees one window's card disappear (cancel) while the other still shows it `Creating`/`Failed`; clicking Retry/Cancel there either does nothing visible, throws an unhandled RPC error toast, or (worse) silently no-ops leaving the UI in a state inconsistent with the backend until the next `WatchSessions` event reconciles it. | Add an explicit multi-client regression test to Epic 6.1/6.2: two `WatchSessions` subscribers on the same instance, cancel via one, assert the other reconciles via the stream event (not stale local/optimistic state), and assert `RetrySessionCreation`/`CancelSessionCreation` against an already-removed instance ID returns a clean, frontend-handled `NotFound` (toast, not an unhandled exception or silent no-op). | P3 |

## P1 Items (address before implementation)
- [x] Failure #2 — Resolved via plan.md Story 1.2.4 + ADR-002 addendum: durable-first terminal writes (`storage.UpdateInstanceIfEpoch` before in-memory `TryForceStatusIfEpoch`, orchestrated by `commitTerminalStatus`), plus a resource-liveness guard in `cleanupPartialCreation` (plan.md Task 3.1.1d) as defense-in-depth, plus a restart-crash-window regression test (plan.md Task 1.2.4d).
