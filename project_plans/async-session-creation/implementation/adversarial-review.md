# Adversarial Review: async-session-creation

**Date**: 2026-08-26
**Verdict**: CONCERNS

## Blockers

(none — both prior blockers verified resolved, see below)

### Blocker 1 (RESOLVED) — double-click retry spawning two live pipelines sharing one epoch
`TryStartRetry() (newEpoch uint64, started bool)` (Story 1.2.3, ADR-002 addendum) closes this correctly. Walked the actual sequence: `TryStartRetry` is one atomic, actor-routed command (Task 1.2.3a) — "check `Status == Failed`, and if so, bump `creationEpoch`, transition to `Creating`, reset `creation_progress`, all inside one enqueued command." `RetrySessionCreation`'s handler (Task 3.3.1b) calls this as its **first** state-mutating step, and only branches into `cancelFunc()`/`cleanupPartialCreation`/pipeline-spawn if `started == true`. Since the actor mailbox serializes commands one at a time, two concurrent `RetrySessionCreation` calls' `TryStartRetry()` invocations are strictly ordered: whichever's command executes first observes `Status == Failed`, bumps the epoch, and flips to `Creating`; the second's command then observes `Status == Creating` (no longer `Failed`) and returns `(0, false)` — deterministically, before it ever reaches cleanup or spawns a goroutine. This is a genuine fix, not a rewording: the epoch bump and the spawn-eligibility decision are now the same atomic step, not two separate mailbox round-trips as the original design implied. Task 3.3.1d specifies the exact regression test (`-race -count=50`, assert exactly one `started==true`, `goleak`-style check that only one pipeline goroutine ever ran). **VERIFIED.**

### Blocker 2 (RESOLVED) — `CancelSessionCreation` calling a non-restart-surviving `CancelFunc` with no nil guard
Task 3.2.1b now reads: `cancelFunc := instance.CancelFunc(); if cancelFunc != nil { cancelFunc() }`, explicitly documenting `nil` as "no live goroutine to interrupt in this process," not an error — and "Proceed to `cleanupPartialCreation` + removal in **both** branches." Cross-checked against Epic 3.1: `cleanupPartialCreation` is extracted verbatim from `DeleteSession`'s existing cleanup ordering (kill process before delete directory, tolerant of already-absent resources) and is the *same* call in both the live-cancelFunc and nil-cancelFunc paths — the only thing skipped when nil is the (moot) `cancelFunc()` invocation itself, not any cleanup step. So the nil-path cleanup is complete and equivalent to the live path, not a partial substitute. The "still running but CancelFunc lost some other way" ambiguity the review asked about is also closed by construction: Task 2.2.1a specifies the field is "cleared on goroutine exit," and Task 2.2.1b stores it *before* spawning the goroutine — so within one process, `nil` and "no live goroutine" are kept synonymous by the field's own lifecycle; there's no window where a live goroutine exists in-process with a nil `CancelFunc`. Task 3.2.1b-2 adds the exact regression test (construct a `Creating` instance directly via storage, `CancelFunc == nil`, no goroutine ever spawned in-process; assert no panic, epoch bumped, cleanup runs, instance removed). **VERIFIED.**

## Concerns

- [ ] **NEW — `TryStartRetry`'s "reset `creation_progress`" step may not bump `CreationProgressUpdatedAt`, letting a freshly-retried session inherit a stale sweeper-eligible timestamp.** Story 1.1.4 makes `CreationProgressUpdatedAt` (the Stale-Creation Sweeper's actual clock) get bumped only "by the same locked helper `SetCreationProgress` already calls." Task 1.2.3a's spec for `TryStartRetry` says it "bump[s] `creationEpoch`, transition[s] to `Creating`, reset[s] `creation_progress`" but never says this reset goes through that same locked helper (vs. writing the `creationProgress` field directly inside `TryStartRetry`'s own command closure, which is a different code path). If implemented as a direct field write, a session that failed 15 minutes ago (threshold 10) and is then retried would carry forward its old, already-stale `CreationProgressUpdatedAt` — and the Stale-Creation Sweeper's very next tick would immediately flip the freshly-retried `Creating` instance back to `Failed`/`Stale` before its new pipeline gets any chance to run, via the same epoch-matching `TryForceStatusIfEpoch` call the sweeper legitimately owns (this isn't even a race the fencing token is meant to catch — the epoch would correctly match, because the sweeper's check is against real elapsed time from a genuinely stale timestamp, just one that should have been reset and wasn't). This is a plausible new gap introduced by the blocker-1 fix's exact shape, not a rewording of a previously-flagged issue. — **Recommendation**: Task 1.2.3a should explicitly require `TryStartRetry`'s progress reset to route through the same internal locked helper `SetCreationProgress` uses (so `CreationProgressUpdatedAt` is bumped in the same command), and Task 1.2.3b's test suite should add a case asserting `CreationProgressUpdatedAt` is fresh (not the pre-retry value) immediately after a successful `TryStartRetry()`.

- [ ] **The staleness heartbeat is too coarse to tell "hung" from "slow-but-working" for the exact case requirements.md worries about.** Unaffected by the blocker fixes — still stands as originally written. `SetCreationProgress` only fires at phase boundaries (~6 phases total, Story 2.2.2), so a single long-running phase (most plausibly `git clone` against a slow `github.netflix.net`/VPN connection) produces no intermediate timestamp updates, and both backstops (`maxCreationResolutionTimeout`, Stale-Creation Sweeper threshold) default to the same unvalidated 10 minutes. — **Recommendation**: instrument at least the clone phase with periodic heartbeat progress updates before committing to a fixed threshold, or explicitly flag 10 minutes as provisional pending real telemetry.

- [ ] **`context.WithoutCancel(rpcCtx)` propagates every context *value* on the RPC context, not just the trace span ADR-003 wants, into a goroutine that can now outlive the request by up to 10 minutes.** Unaffected by the blocker fixes — still stands. No live bug today (no `context.WithValue` custom keys found in `server/server.go`/`server/services/*.go`), but a standing foot-gun for a future per-request interceptor. — **Recommendation**: add a comment at the `WithoutCancel` call site (and a line in ADR-003) flagging this as a constraint future interceptors must respect.

- [ ] **Fork dispatch's own resolution step (conversation-file copy) is inconsistently scoped.** Unaffected by the blocker fixes — still stands. The Domain Glossary's "synchronous prefix" row (plan.md line 20) still keeps fork dispatch's conversation-file copy fully synchronous and unjustified against the "every potentially-slow resolution step moves to the pipeline" framing. — **Recommendation**: either give an explicit sizing/timing justification for why fork-copy is safe to leave synchronous, or move it into the pipeline.

- [ ] **No staged/soak step despite the repo already documenting the exact mechanism for one.** Unaffected by the blocker fixes — still stands. Risk Control (plan.md lines 121-128) still says "no staged rollout possible" without calling for a manual second-instance dry run (CLAUDE.md's documented `~/.stapler-squad/manual-builds/` procedure, port block 62871-62880) through all 7 modes and a real slow GHE clone before merge. — **Recommendation**: add an explicit Phase 6 task for this.

- [ ] **No post-merge monitoring plan given the no-rollback-except-revert posture.** Unaffected by the blocker fixes — still stands. `session.creation.outcome`/`duration_ms` remain explicitly local-debugging-only with no alerting; combined with "no flag," a field regression has no proactive detection. — **Recommendation**: add a documented "check these metrics/logs daily for N days after deploy" step to Phase 6/shipping.

## Minors

- Task 1.1.3c (now Story 1.1.3, unaffected by the story renumbering from inserted Stories 1.1.4/1.2.3) piggybacks a `.golangci.yml` `exhaustive` linter addition onto the FSM-transitions task. Transparently flagged in the task itself, but call it out separately in the PR description.
- `FailureReason` is still a bare `string` (Task 1.1.2c, unchanged) despite exactly four known values. A typo silently falls through to the generic fallback message with no compiler check. Consider a typed Go string-enum, per `.claude/rules/primitive-obsession-checklist.md`.
- `maxCreationResolutionTimeout` and the sweeper's threshold are still both defaulted to the same 10 minutes "so the two backstops agree" (Unresolved Questions, unchanged) — makes "pipeline self-timed-out" vs. "sweeper caught it" hard to distinguish from logs/metrics after the fact. Consider a modest grace period for the sweeper beyond the pipeline's own timeout.
- **Resolved, dropping from this list**: the previous minor "Epic 6.2's hammer test isn't scoped to the double-click-retry race" is now addressed directly — Task 3.3.1d adds the dedicated concurrent-double-retry regression test called for, rather than relying on the general 50-iteration hammer test to happen to trigger it.

## Overall assessment of the no-feature-flag decision (re-asked per this round's brief)

Both previously-blocking correctness gaps are now closed at the design level with real atomic primitives (`TryStartRetry`, the nil-guarded `CancelFunc` path) and named regression tests, not deferred judgment calls — that's a genuine, verifiable improvement, not just rewording. The new `CreationProgressUpdatedAt`-on-retry gap found in this pass is narrow and mechanically fixable (route the reset through the existing locked helper) rather than structural, so it doesn't by itself argue for reversing the no-flag decision. Combined with the five carried-forward concerns (heartbeat granularity, context-value leakage, fork-copy scoping, no soak step, no post-merge monitoring), Phase 4's pre-mortem should still treat "no flag" as the top adversarial-scrutiny target as the plan itself already directs — the fix quality is now credible enough for that gate to be the load-bearing safety net, provided the new concern above and the five carried-forward ones are explicitly checked off (not just re-read) during Phase 4/6.
