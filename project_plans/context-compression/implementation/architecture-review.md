**Date**: 2026-08-06
**Verdict**: BLOCKED

## Constitution Violations

None — `docs/adr/ADR-000-architecture-constitution.md` does not exist in this repo (`ls docs/adr/` confirms no `ADR-000*`/`*constitution*` file). No constitution check applies.

## Blockers

- [ ] **Epic 3.2 (Story 3.2.1) / Epic 2.3 — `useSessionService.ts` (Touchpoint 7 of `.claude/rules/session-creation-registry.md`) is never updated, so `restartFromSessionId` never reaches the RPC.** `web-app/src/lib/hooks/useSessionService.ts`'s `createSession` (lines 256-281) does not spread its `Partial<CreateSessionRequest>` argument onto the wire call — it constructs an explicit allowlisted object literal (`title`, `path`, `workingDir`, `branch`, ... `cliFlags`) and passes that to `clientRef.current.createSession(...)`. Any field not named in that literal is silently dropped before it ever reaches ConnectRPC. Story 3.2.1's own acceptance criteria assumes the field survives (`createSession({ ..., restartFromSessionId: sessionId })` "calls `createSession` with ... `restartFromSessionId: sessionId`"), and Epic 2.3's entire backend path-derivation/lineage logic (Task 2.3.1a/b) is keyed on `req.Msg.RestartFromSessionId` being non-empty — but no task in Phase 2 or Phase 3 edits `useSessionService.ts` to add `restartFromSessionId: request.restartFromSessionId` to that literal. As planned, every layer's own unit tests would pass in isolation (backend tests set the proto field directly; a frontend component test likely mocks `useSessionService().createSession` and asserts the hook was *called* with the right argument, never that the argument survives *inside* the hook) while the end-to-end feature silently no-ops — every "Restart with summary" session would be created with `RestartFromSessionId == ""`, permanently falling back to whatever `path` default logic exists for a normal directory session, never triggering the path-derivation or `restarted_from_session_id` lineage stamping this plan is built around. **Remediation**: add an explicit task to Epic 3.2 (or 2.3) editing `useSessionService.ts`'s `createSession` call body to include `restartFromSessionId: request.restartFromSessionId`, and add a test (either in `useSessionService.test.ts` or by asserting on the mocked *RPC client* call args, not just the hook wrapper's call args, in `RestartWithSummaryButton.test.tsx`) that would fail today and pass once the field is threaded through — mirroring how the registry's own checklist calls this out as touchpoint 7.

## Concerns

- [ ] **Story 1.5.1 (Task 1.5.1c/1.5.1d) — the transcript-read dependency is hard-wired to the real home directory with no injection seam, undermining the "isolated unit test" the plan itself specifies.** `GenerateAndPersist` calls `session.NewClaudeSessionHistoryFromClaudeDir()` → `GetMessagesFromConversationFile(sessionID, 0)` → `findConversationFilePath(sessionID)` (`session/history.go:346-352`), which calls `os.UserHomeDir()` directly and walks `<home>/.claude/projects/` — there is no constructor parameter or injectable reader that lets a test point this at a temp fixture directory (`NewClaudeSessionHistory(historyPath)`'s `historyPath` only backs the separate `history.jsonl` index, not per-session conversation-file lookup). Task 1.5.1d's stated acceptance test ("Given a source session with a real conversation file ... `FindRowBySessionID` returns a row with `Status == "ready"`") has no established precedent to copy in this codebase: the existing `session/history_messages_test.go` deliberately tests one layer *beneath* `GetMessagesFromConversationFile` (calling `readAllMessagesFromFile`/`readLastNMessagesFromFile` directly against `t.TempDir()` fixtures) specifically to avoid this same hard-coded-home-directory dependency — unlike every other line in this unusually well-sourced plan, this task cites no file:line precedent for how the test achieves isolation. **Recommendation**: either inject a small, consumer-defined interface (e.g. `type TranscriptReader interface { GetMessagesFromConversationFile(sessionID string, limit int) ([]ClaudeConversationMessage, error) }`, defined in the `session` package alongside `HandoffSummaryGenerator`, satisfied structurally by `*ClaudeSessionHistory`) so tests can fake it without touching `$HOME`, or explicitly specify `t.Setenv("HOME", tempDir)` as the intended technique in Task 1.5.1d so the implementer isn't left to discover this friction mid-task.

- [ ] **Story 1.5.1 (Task 1.5.1c) — `config.LoadConfig()` called directly inside domain logic, unlike the sibling generator this plan otherwise mirrors line-for-line.** `GenerateAndPersist` reads `config.LoadConfig().HandoffSummary` inline rather than receiving `HandoffSummaryConfig` (or a budget) via `NewHandoffSummaryGenerator`'s constructor or the method's parameters. This matches an idiom used elsewhere in the `session` package (`instance.go:682`, `instance_hibernate.go:40,133,173`, `instance_program.go:48`), but *not* the specific structural template this plan cites throughout (`SessionSummaryGenerator` takes no config dependency at all — `session/session_summary_service.go` has zero `config.LoadConfig()` calls). Since this is new code with no existing test suite to preserve, prefer passing `HandoffSummaryConfig` into the constructor (or as a `GenerateAndPersist` parameter) so `Story 1.2.1`'s `omitempty`/zero-value ambiguity the plan already flags as a test risk (Task 1.2.1a's note) doesn't also become a hidden global-state dependency in the generator's own tests.

- [ ] **(Minor, inherited) `headless.PoolClient` is defined next to its sole implementation.** `session/headless/client.go` defines `PoolClient` in the same package as `*Pool`, the only type satisfying it (`interface-pollution-checklist.md` item 2: "interface defined next to its implementation, rather than in the package that consumes it"). This is pre-existing debt from `SessionSummaryGenerator`'s design, not introduced by this plan — but `HandoffSummaryGenerator` (Task 1.5.1a) extends the same boundary to a second consumer rather than revisiting it. Not asking for a fix in this plan (disproportionate for the scope), just flagging that it's being propagated, not corrected.

## Nitpicks

- `HandoffSummary.status`/`error_stage` are stringly-typed fields (`"pending"`/`"generating"`/`"ready"`/`"error"`, `"transcript"`/`"generation"`) rather than Go enums, mirroring `SessionSummary`'s existing shape exactly per the plan's own stated rationale ("consistency with the pattern actually being mirrored"). Acceptable given that explicit justification; flagging only for completeness under primitive-obsession review.
- `ActiveTask` extraction (Task 1.5.1c: "substring after the `## Active Task` heading, best-effort, empty string if the heading is missing") is fragile string-boundary parsing of LLM output. Reasonable given the "never error, always degrade" design elsewhere in this plan, but consider a test for a near-miss heading variant (e.g. `##Active Task` with no space, or the literal string `## Active Task` appearing verbatim inside a Head/Tail message that isn't actually the model's own heading) so the "best-effort" extraction has at least one documented failure-mode boundary.
