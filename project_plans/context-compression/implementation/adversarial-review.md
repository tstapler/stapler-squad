# Adversarial Review: context-compression

**Date**: 2026-08-06
**Verdict**: BLOCKED

## Blockers

- [ ] **No timeout on the summarization LLM call** — Task 1.5.1c calls `headless.GenerateHandoffSummary(ctx, g.pool, ...)` with no deadline. `TriggerHandoffSummary` dispatches with `context.Background()` (Task 2.2.1a), so nothing ever cancels it. The plan claims to mirror `SessionSummaryGenerator.GenerateAndPersist` "exactly," but that reference implementation wraps its own LLM call in `context.WithTimeout(ctx, llmNarrativeTimeout)` (60s, `session/session_summary_service.go:31,390`) *specifically* because `research/pitfalls.md` §3 flagged "no explicit LLM timeout" as a gap for this exact call shape. Without it: a hung/slow `headless` CLI subprocess blocks the goroutine forever, the `sync.Map` dedup guard (`release()` deferred to function return) stays held indefinitely — permanently blocking any retry for that session — and the call permanently occupies one of only 5 global concurrency slots (`headless.PoolConfig.MaxConcurrentSessions: 5`, `server/dependencies.go:565-568`) shared with backlog triage, PR-description generation, and session-completion narratives, degrading unrelated features too. — **Recommendation**: add a `handoffSummaryTimeout` const and `context.WithTimeout` wrap in Task 1.5.1c, identical in shape to `llmNarrativeTimeout`.

- [ ] **No UI path for a failed/errored summary — user hits a dead end.** Story 1.5.1's AC (line 334) sends pool failures to a terminal `ERROR` status with no fallback content, diverging from the very pattern it claims to mirror: `SessionSummaryGenerator` degrades gracefully to `READY` with `narrativeFallbackLLMFailure` text (`session/session_summary_service.go:22-25`) rather than dead-ending in `ERROR`. Worse, no frontend task anywhere renders an `ERROR` state at all: `RestartWithSummaryButton` is explicitly speced as a "three-state render (idle → generating → ready-to-restart)" (Task 3.2.1a) — no fourth state — and `HandoffSummarySection`'s ACs (Story 3.3.1) cover only the empty state, list roles, and the `READY`-embeds-button case. The Domain Glossary's claim that "the list shape accommodates retries after an ERROR row" (line 49) is aspirational; no task implements it. Given `research/pitfalls.md` §3 explicitly flags LLM-call failure as a real (not hypothetical) risk for OAuth-only/subscription-only users, this is exactly the failure mode most likely to occur for a nontrivial slice of users, with currently zero recovery surface. — **Recommendation**: either adopt `SessionSummaryGenerator`'s fallback-to-READY-with-degraded-content pattern, or add explicit `ERROR`-state AC/task coverage (message + retry action) to both `RestartWithSummaryButton` and `HandoffSummarySection`.

- [ ] **No stale-`GENERATING` reconciliation.** `SessionSummaryGenerator` has a `staleGenerationTimeout` (5 min) that flips a row stuck in `GENERATING` — e.g. from a server restart mid-generation — back to `ERROR` on next read. Nothing in `GetHandoffSummary` (Task 2.2.1a) mentions an equivalent. Combined with the missing internal timeout above, a server restart during generation (or simply a hung pool call) leaves a row permanently stuck at `GENERATING` with no path back to a usable state short of direct DB surgery — and per the previous finding, no UI even distinguishes a stuck row from one that's still legitimately in flight.

- [ ] **Internal proto field-number inconsistency in the plan itself.** Story 2.1.1's own Acceptance Criteria (plan.md:386) states the new fields are added "at 28 and 72 respectively" — directly contradicting the Migration Plan (line 79), the Task under that same story (2.1.1b, line 397), and the dependency-visualization diagram (line 124), all of which specify `74`, chosen specifically to avoid colliding with `context-health-monitoring`'s already-claimed-but-unshipped fields 72/73. `72` is the exact number the rest of the plan goes out of its way to avoid. Since SDD acceptance criteria are meant to be the machine-checkable spec, an implementer or a spec-compliance reviewer working from the AC rather than the task prose could pick the colliding number. Fix line 386 to say `74` before implementation starts.

## Concerns

- [ ] **"Not more than once per N turns" (thrash prevention) is only half-addressed.** The plan's own "Closing out original ACs" table (line 597) claims Epic 1.5's in-flight dedup guard replaces the original threshold/cooldown requirement. That guard only blocks *concurrent* duplicate calls — it does nothing for *sequential* repeated calls. The exact pattern being mirrored, `SessionSummaryGenerator`, has a **separate** `regenerateCooldown` (30s, `session/session_summary_service.go:41`) specifically for this: rate-limiting repeated non-concurrent triggers independent of the in-flight guard. This plan doesn't adopt it. Two concrete places this bites: (a) repeated manual clicks of "Restart with summary" after a prior READY/ERROR result each dispatch a fresh, uncached LLM call with no cooldown; (b) Phase 4's auto-trigger on RED (once unblocked) re-dispatches `GenerateAndPersist` on every fresh GREEN/AMBER→RED crossing — a session whose `ContextHealth` flaps regenerates the summary from scratch each time with no rate limit. — **Recommendation**: add a cooldown equivalent to `regenerateCooldown` to Epic 1.5.

- [ ] **Declined/deferred restart → staleness.** Phase 4 eagerly generates a summary the moment RED first fires (Task 4.1.1a), but a user who defers acting on it may keep working in the same degrading session afterward. Nothing revisits or regenerates the pre-generated summary before the user eventually clicks "Start new session" — `RestartWithSummaryButton`'s READY branch (Story 3.2.1) uses whatever `data.summaryText` currently holds, which can be stale by the time it's used. The only staleness mitigation the plan has is an automatic re-generation on every fresh RED crossing (health flapping), which doesn't help a session that stays continuously RED while the user keeps working. Not addressed anywhere: what a "decline" even looks like from this plan's side, since Phase 4 doesn't render a dismissible offer itself (that lives on `context-health-monitoring`'s badge, out of this plan's scope) — the interaction between that badge and this plan's eager pre-generation/staleness is unexamined.

- [ ] **Testability gap: `GenerateAndPersist` does its own filesystem I/O.** Task 1.5.1c has the generator call `session.NewClaudeSessionHistoryFromClaudeDir()` + `.GetMessagesFromConversationFile(...)` directly, rather than receiving pre-resolved transcript data as a parameter — unlike `SessionSummaryGenerator.GenerateAndPersist`, whose diff/goal snapshot is fully pre-built by the caller with no I/O inside the generator itself. No existing test in the codebase exercises `GetMessagesFromConversationFile` (verified: zero test references). Task 1.5.1d's test list (`TestGenerateAndPersist_SuccessTransitionsToReadyWithSummaryText`, etc.) doesn't say how transcript content will be supplied to the success-path tests — real JSONL fixtures written to a `~/.claude`-shaped temp dir, or a new test seam on `ClaudeSessionHistory` — either way it's an unaddressed piece of the plan's own detailed task breakdown.

- [ ] **"Cheap auxiliary model" from requirements is silently dropped, without a Pattern Decisions entry.** `GenerateHandoffSummary` calls `pool.CallBlocking(..., CallOptions{})` with no `Model` override (Task 1.4.1b), and the production pool sets no `DefaultModel` (`server/dependencies.go:565-568`) — generation runs on whatever model the user's own `claude` CLI defaults to, not necessarily cheap. This may be the right trade-off (it sidesteps the OAuth-only credential gap flagged for the `anthropic_client.go`/Haiku path in `research/pitfalls.md` §3), but the Pattern Decisions table — which otherwise documents every deliberate substitution with a "rejected alternative + reason" row — has no entry for this one, even though requirements.md explicitly names "a cheap auxiliary model" as a technique to adopt.

- [ ] **`restarted_from_session_id`'s stated purpose is never delivered.** The field's doc comment/glossary entry (line 46) states its purpose is "so the UI can render 'Restarted from: <link>'." The field is added to the proto and populated on the created session (Epic 2.3), but no task in Phase 3 (or elsewhere) renders that link anywhere in the UI. As planned, the field is write-only.

- [ ] **`context-health-monitoring` dependency handling is otherwise honest** (Unresolved Questions, explicit Phase-4 gate, dependency diagram, ACs caveated as "not live until that plan ships") — flagging as a concern only because the one concrete coordination artifact it produced (the field-number choice) is undermined by the Blockers-section inconsistency above, and because the plan has no provision for re-validating Phase 4's *design* assumptions (e.g. whether that project's own level-transition hook still has the shape assumed here) beyond a field-number re-grep, if that project's shipped shape drifts from what's assumed today.

## Minors

- Task 2.2.1a hedges on `context.Background()` vs. request-scoped context for `TriggerHandoffSummary` ("verify... before assuming"), even though the reference (`RegenerateSessionSummary`, `server/services/session_summary_service.go:148-152`) marks this a deliberate `// Critical:`-commented choice already — the plan could just state the answer instead of deferring it to implementation-time verification.
- Story 3.2.1's AC leaves open "whether `HandoffSummaryConfig.Enabled` needs its own read RPC" inside an Acceptance Criterion rather than resolving it or moving it to Unresolved Questions.
- No story addresses what happens to the *source* (degrading) session after a restart — does the user need to manually stop/archive it, or does it keep running and consuming resources alongside the new session?
