# Pre-mortem: context-compression

**Date**: 2026-08-21
**Scenario**: Phases 1-3 (manual-trigger handoff-summary restart) have shipped. Phase 4
(auto-trigger on `ContextHealth` RED) remains blocked. The project has "failed" — it
either doesn't solve the original problem or breaks something within the first month.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Phases 1-3 ship a purely manual button with no proactive signal anywhere in scope — Phase 4's RED trigger is blocked, and the plan's own "Closing out the original ACs" table drops all token-usage-percentage tracking as "superseded, no task re-touches it." A user still only discovers degradation from visible symptoms — the exact silent-failure experience `requirements.md`'s Problem Statement names as the thing to fix. | Button-click telemetry (or anecdote) shows near-zero usage; users keep reporting "the agent got confused" post-hoc, same complaints as before the feature shipped. | Ship an interim, cheap discoverability signal in Phase 1-3 itself — e.g. surface `session/tokens`'s already-computed usage percentage as a plain Info-tab stat (not a new badge) so the manual trigger has *some* prompt to notice before `context-health-monitoring`'s badge exists. At minimum, have `requirements.md`/`plan.md` state explicitly that Phases 1-3 alone do not close the "no warning to the operator" acceptance criterion. | P1 |
| 2 | Task 2.3.1a resolves the restarted session's path as literally the source session's `Path` (confirmed: `session/instance_worktree.go:69-77`'s `setupFirstTimeWorktree` `default` case, which `SessionTypeDirectory` hits, explicitly skips worktree creation — `"directory session, no git worktree"` — and `server/services/session_service.go`'s `CreateSession` passes `resolvedPath` straight through as `instance.Path` with no collision check anywhere in the file). Nothing stops the user from restarting while the degrading source session is still running: two Claude Code CLI subprocesses now write to the identical directory and `.git` index concurrently. | A user who restarts without manually stopping the source session hits a `fatal: Unable to create '.git/index.lock'` error, or finds one session's uncommitted edits clobbered by the other. | Add an explicit guard to Task 2.3.1a: reject or warn-and-require-confirmation on `CreateSession` when `restart_from_session_id` names a still-live instance; and/or fold "stop the source session" into the restart flow itself — this also answers the adversarial-review Minor ("no story addresses what happens to the source session") with a concrete mechanism instead of leaving it open. | P1 |
| 3 | The REFERENCE-ONLY prefix explicitly tells the new session's Claude Code process to treat prior turns as "already addressed" and not re-fulfill them. If `GenerateHandoffSummary`'s LLM call hallucinates or misreads the Tail (e.g. asserts a fix landed when it didn't, names the wrong file), the new session inherits that false premise with an explicit instruction not to double-check it — and no review step is mandatory before restart (`design/ux.md` Surface 4 confirms the preview disclosure is optional/collapsed, not required). | User discovers much later (PR review, a failing test) that the "resumed" session proceeded on a stale or wrong premise the summary had asserted was already done. | Add a `validation.md` scenario using a real multi-turn degraded-session fixture, human-reviewed for factual accuracy, before Phase 1 ships — not just unit tests of head/tail/budget boundary mechanics. Consider softening "already addressed... do NOT answer" to something that invites a quick re-confirm rather than an outright skip. | P2 |
| 4 | This plan's hardcoded field numbers and file:line references decay the longer it sits between validate and implement — confirmed twice now: the field-number pair drifted from `28/72` to `28/74` within the plan's own lifetime (adversarial-review.md), and by 2026-08-21 both `28` and `74` are themselves taken by unrelated shipped fields (`triggered_by_chain_depth`, `auto_approve`; current highs are `CreateSessionRequest=30`, `Session=75`). The plan's only mitigation is one re-grep instruction buried in the Migration Plan section — not a checklist covering every other hardcoded line/field reference in the document (e.g. `server/dependencies.go:588-600`, `session_summary_service.go:159-176`). | `make proto-gen`/`go build` fails immediately at Task 2.1.1b or 1.5.1a with a duplicate-field or line-mismatch surprise; or, worse, an implementer trusts a stale citation and inserts code at the wrong integration point without the build catching it. | Add a mandatory "pre-flight freshness check" task at the start of Phase 1: before writing any code, re-grep and re-verify every hardcoded field number and file:line reference in `plan.md` in one pass, not just the proto pair already flagged. | P2 |
| 5 | Phase 4 depends on `context-health-monitoring`, which has zero implementation today and no scheduled owner. Because the manual button in Phases 1-3 works fine without it (just quietly, per #1), nothing creates urgency to unblock Phase 4 — the dependency is a prose note only a future Phase-4 implementer would find, not a tracked, prioritized item. | Months later, `context-health-monitoring` is still unimplemented and Phase 4 has not been picked up by anyone. | File a tracked backlog item/issue for `context-health-monitoring`'s Phase 1+2 (the concrete unblock condition) at the moment Phases 1-3 ship, explicitly linked as this plan's Phase 4 blocker — don't leave it as plan-doc prose only. | P2 |

## P1 Items (address before implementation)

- [ ] Failure #2 — Add an acceptance criterion + task under Epic 2.3 (`server/services/session_service.go`'s `CreateSession`) that rejects or confirms-before-proceeding when `restart_from_session_id` points at a still-live instance, given confirmed evidence that DIRECTORY sessions share the literal source path with no worktree isolation and no existing path-collision guard exists anywhere in the codebase.
