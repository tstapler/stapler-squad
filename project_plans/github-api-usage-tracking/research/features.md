# Agent 2 — Feature Landscape Research

## 1. `analytics_store.go` is a fully-baked, persisted precedent — reuse the pattern directly

**VERIFIED, refuting the requirements.md open question's cited prior claim ("prior investigation found no disk-write calls in it")**: `AnalyticsStore` **does** persist to disk. Trace:

- `AnalyticsStore.Record()` (`server/services/analytics_store.go:175`) pushes onto a buffered channel (`analyticsBufferSize = 1000`), non-blocking, drops + counts on overflow.
- A background goroutine (`Start()` → `flush()`, `analytics_store.go:551-596`) drains the channel every 5s or on each item, and calls `s.storage.RecordAnalytics(context.Background(), data)` (`analytics_store.go:576`).
- `session.Storage.RecordAnalytics` (`session/storage.go:642`) → `EntRepository.RecordAnalytics` (`session/ent_repository.go:1341`) → writes a `ClassificationAnalytics` ent row.
- The ent client is backed by real SQLite: `session/ent_repository.go:26` imports `github.com/mattn/go-sqlite3`, default path `~/.stapler-squad/sessions.db` (`ent_repository.go:48`, opened via `sql.Open("sqlite3", dbPath)` at `ent_repository.go:76`).

So the async-buffered-channel → background-flush → SQLite-via-ent pattern is real, already production-hardened (drop-counter for overflow, graceful drain on `Stop()`), and directly reusable. This is the strongest existing precedent in the codebase and should be the default answer to requirements.md's "flat JSON file vs. reuse analytics_store.go's pattern" open question — reuse it.

**Query/aggregation layer** (also reusable almost verbatim):
- `ComputeSummary(entries []AnalyticsEntry) AnalyticsSummary` — pure function, no I/O, builds top-N breakdowns + rate percentages from a slice of entries already in memory.
- `ComputeDailyBuckets(entries) []DailyBucket` — pure function, groups by local calendar day for time-series charts.
- `LoadWindow(since time.Time)` / `LoadProgramWindow(ctx, program, since)` — DB-level `WHERE created_at >= ?` (and `WHERE command_program = ?`) queries via ent, not a full-table scan + Go-side filter.
- `GetSubcommandBreakdown` — SQL-level `GROUP BY` via ent's `Aggregate(ent.Count())`.

**RPC layer** (`server/services/rules_service.go`): `GetApprovalAnalytics` (line 160) and `GetProgramAnalytics` (line 206, added later per the `analytics-drill-down` project) are plain request/response ConnectRPC handlers — **pull-based**, not streaming. They take `WindowDays` (clamped 1–90, default 7), compute `since := time.Now().AddDate(0,0,-days)`, call the store, convert to proto. No server push.

**UI layer** (`web-app/src/components/sessions/ApprovalAnalyticsPanel.tsx`, 931 lines): a `useApprovalAnalytics({ windowDays })` hook (line 129) does the RPC fetch; the panel has a `windowDays` `useState` (line 127) with a preset button row (7/30/90-style), a "no data for the last N days" empty state (line 234), and a drill-down sub-panel (`ProgramDetailPanel`, called at line 917) that fetches `GetProgramAnalytics` per-program on click. **No polling/`setInterval`** — refresh is either a manual `refresh()` callback from the hook or implicit on window-selector change. This is a real, load-bearing precedent for the "config-driven poll intervals" work too — if the GitHub UI panel wants live-ish updates without full streaming infrastructure, the existing convention in this codebase is manual/selector-triggered refetch, not a poll loop in the frontend.

## 2. Prior SDD research already extended this exact pattern — don't re-derive

- **`project_plans/analytics-drill-down/research/architecture.md`**: documents the ent schema/query patterns used to add `GetProgramAnalytics` (compound index `("command_program", "created_at")`, ent `Where(...).GroupBy(...).Aggregate(ent.Count()).Scan()`, and the "Go-level daily bucketing after a DB-filtered fetch" tradeoff for trend charts vs. SQL-level date grouping). All of this is **already implemented** (confirmed live in `rules_service.go:206-238`), so it's a working reference implementation of "add a new drill-down dimension to an ent-backed analytics store," directly transferable to "drill down by GitHub API source/resource."
- **`project_plans/token-monitoring/research/stack.md`**: this doc's own claim ("Existing analytics infrastructure... implements *in-memory* analytics") is **stale/wrong** relative to what's actually in the repo today — it predates (or missed) the SQLite persistence confirmed above. Two things from it are still useful: (a) **no charting library exists yet** in `web-app/package.json` (checked at the time; recharts was the recommendation — worth re-verifying `web-app/package.json` before Phase 3 assumes recharts is or isn't present) and (b) `server/services/config_service.go` is cited as the minimal ConnectRPC service template, consistent with `RulesService`'s pattern above.

## 3. Instrumentation hook point is already well-shaped for this feature

`github/rate_limit.go`'s `RateLimiter.Update(resp *http.Response)` (line 49) is called automatically by `rateLimitTransport` on every response and already parses exactly the fields a usage-tracking entry needs: `resource` (`X-RateLimit-Resource` — "core"/"search"/etc.), `remaining`, `limit`, `resetAt` (from `X-RateLimit-Reset`). It currently only logs a WARN (`rateLimitWarnPercent = 10`, hardcoded, line 20) when `remaining < threshold`. This is the natural place to also call something like `usageStore.Record(...)` — the parsing work is done, only the "persist it" step is missing. Confirms the Observability Requirement's framing ("extend, don't duplicate, the existing WARN-at-threshold log line") is achievable with a small diff at this exact call site, not a new parallel instrumentation path for native-HTTP call sites.

The `gh` CLI shell-out call sites (`github/client.go`'s `GetPRInfoCtx`) are **not** covered by this transport at all — they're a separate subprocess, invisible to `RateLimiter.Update`. This matches the Rabbit Hole already flagged in requirements.md; no new finding here beyond confirming the asymmetry is real and structural (subprocess vs. `http.RoundTripper`), not just a missing wrapper call.

## 4. Config hot-reload: confirmed absent

`grep -rl fsnotify config/*.go` returns nothing — `config/` has no file-watcher. Combined with `config/config_test.go`'s `STAPLER_SQUAD_INSTANCE` tests showing config is read at process-start/on-demand via `config.LoadConfig()`, there is no existing hot-reload mechanism to piggyback on. This resolves one of requirements.md's Open Questions: **"config-driven, no rebuild" is achievable, but "no restart" is not** — changing a poll interval will still require at minimum a config write + either a service restart or a bespoke reload path Phase 3 would have to build from scratch (no precedent exists for the latter). Recommend the plan explicitly scope this as "no rebuild, restart still required" per the Feasibility Risk already flagged.

## 5. Edge cases

**Process restart, if storage ends up in-memory-only**: Not applicable if the `analytics_store.go` pattern is reused (it's SQLite-backed and survives restart by construction). Flagging this only because requirements.md's Open Questions leave storage choice open — an in-memory-only design would silently violate the explicit "persisted (survives restart)" scope item the moment the service restarts, which per `.claude/rules/tmux-keep-server-on-restart.md` and `.claude/rules/service-restart-orphan-process.md` happens routinely (both intentional `make install-service` deploys and, on macOS, unintentional orphan-process races). Given restarts are frequent and sometimes silent in this codebase's own operational history, in-memory-only storage should be treated as disqualifying, not a minor tradeoff.

**Multiple concurrent instances sharing one GitHub token**: `STAPLER_SQUAD_INSTANCE=<name>` (documented in CLAUDE.md's "Manual/interactive testing" section and exercised in `config/config_test.go`) gives each instance its **own** state dir under `~/.stapler-squad/instances/<name>/`, which — if the analytics store follows the same per-instance `sessions.db` convention as everything else in `session/storage.go` — means **usage tracking would be per-instance, not per-token**. Since GitHub rate limits are enforced per-token/per-account server-side (not per-process), two concurrently running instances (e.g. the live systemd service at :8543 plus a manual test instance per CLAUDE.md's own documented workflow) sharing the same `github/keychain.go` token would each report a partial, individually-non-exhausting view while the *actual* shared quota could be exhausted by their combined usage — the dashboard would show "fine" in both UIs while the token is actually rate-limited. This is a real gap the Success Metric ("verified using the new tracking data itself... trustworthy enough to attribute cause") is vulnerable to, since Tyler's own documented workflow deliberately runs a second instance for manual testing. Phase 3 should decide explicitly: track globally (keyed by token/keychain identity, shared across instances via a common DB or file — more correct, more plumbing) vs. track per-instance with a UI caveat (cheaper, but silently wrong exactly in the scenario CLAUDE.md tells Tyler to use).

**Empty store (fresh install)**: `ApprovalAnalyticsPanel.tsx` already has a precedent empty state ("No data for the last {windowDays} days," line 234) — reuse this convention rather than inventing a new one. `GetApprovalAnalytics`'s Go handler also degrades gracefully: a `LoadWindow` error becomes a WARN log + an empty summary rather than an RPC error (`rules_service.go:174-177`) — "return empty summary rather than erroring" is an explicit, already-established convention worth carrying over verbatim for the GitHub usage RPC.

**Corrupted store**: No existing precedent handles ent/SQLite corruption specially anywhere in the codebase (not found in `analytics_store.go`, `rules_service.go`, or `ent_repository.go` — `RecordAnalytics` write errors are swallowed with `_ = s.storage.RecordAnalytics(...)` at `analytics_store.go:576`, and read errors degrade to empty-summary-plus-log as above). This is consistent with treating analytics/usage data as best-effort telemetry, not source-of-truth state — reasonable to carry the same posture forward (never let a corrupted usage-tracking DB block startup or break unrelated RPCs), but note it means a corrupted store fails *silently* into "0 requests tracked," which for a rate-limit-avoidance tool risks a false sense of safety at exactly the moment it's most needed. Consider at minimum a distinguishable UI state ("tracking unavailable" vs. "0 requests observed") rather than conflating the two, which the current `AnalyticsSummary`-empty-struct convention does not distinguish.

## 6. Unstated needs: what makes the data *actionable*, not just visible

The stated goal is avoiding rate-limit exhaustion, and the Success Metric is explicit that the tracking data must be "trustworthy enough to attribute cause" — not just present. Gaps between "a dashboard exists" and "a dashboard that tells you which poller to slow down":

- **Rate (req/hour), not raw counts, per source.** A bar chart of total request counts per source over a week answers "who used the most," not "who is currently burning quota fastest." Since `github/rate_limit.go` already resets accounting hourly (GitHub's own `X-RateLimit-Reset` window), a per-source req/hour or req/(reset-window) rate is the metric that actually maps to "which poller should I slow down right now" — raw cumulative counts bury a recent burst inside a long quiet history.
- **Burn-rate / projected-time-to-exhaustion, not just remaining/limit.** `RateLimiter.Update` already has `remaining`, `limit`, and `resetAt` in hand at the exact call site that would record a tracking entry (see §3) — the missing derived metric is "at current rate, remaining hits 0 at T," which is what actually answers "do I need to act now." A static "4200/5000 remaining" gauge doesn't distinguish "fine, resets in 50 minutes anyway" from "critical, will hit 0 in 10 minutes at this burn rate" — the warn-threshold-as-percentage the codebase has today (`rateLimitWarnPercent`) has exactly this blind spot, and the configurable-threshold requirement (scope item) should arguably be paired with (or superseded by) a time-to-exhaustion projection rather than just making the same static-percentage threshold user-tunable.
- **Per-source attribution needs to answer "which poller/RPC do I turn down," which argues for call-site name as the attribution key, not just GitHub resource type.** `resource` (core/search) tells you *what kind* of quota is low; it doesn't tell you *which of the 5 in-scope call sites* (`pr_status_poller`, `worktree_pr_poller`, `GetPRInfoCtx` gh-CLI shellouts, `backlog_plugin_github.go` issue import, on-demand MCP/RPC tools) is driving it. Both dimensions are needed simultaneously — this matches requirements.md's explicit in-scope item ("attributed to originating call site/poller **and** GitHub resource type"), so no new requirement here, just confirming from the `AnalyticsEntry`/`ProgramStat` precedent (§1) that the existing schema already models exactly this two-dimensional shape (`tool_name`-equivalent × `command_program`-equivalent) and it should carry over directly: one dimension = call-site name, one dimension = GitHub resource.
- **Per-worktree-session attribution's value is conditional, not universal.** requirements.md already flags this as a Rabbit Hole requiring a minimum-viable-granularity decision. From a "which poller to slow down" lens: session-level attribution only helps for the on-demand RPC/MCP call sites (where a specific session-triggered action, e.g. "session X imported issue #42," maps to a request) — it adds no signal for the two timer-driven pollers, which are global/singleton, not per-session. Recommend scoping per-session attribution to the on-demand call sites only (where session context is already naturally available in the RPC handler) and treating the pollers as call-site-attributed but not session-attributed, rather than trying to force a synthetic session ID onto background timers.
