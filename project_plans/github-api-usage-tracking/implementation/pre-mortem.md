# Pre-mortem: github-api-usage-tracking
**Date**: 2026-08-11

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `gh`-CLI rows can never trip `ComputeExhaustionEvents` or the `rate_limit.go` WARN, so the Success Metric can read a perfect "0" while the 7 in-scope `gh` call sites are actually being rate-limited. `runGHCommand`'s events always carry `StatusCode: 0` (per plan.md:690-691's own worked example) and never flow through `usageTransport`/`DefaultRateLimiter.Update()`, but `ComputeExhaustionEvents` (Task 3.1.1d, plan.md:1044-1046) filters strictly on `StatusCode ∈ {403,429}` and `Remaining == 0`. | The panel shows `exhaustion_events: 0` and a "0 rate-limit exhaustions" success banner for the full 14-day window, while `gh pr merge`/`gh pr comment` calls are silently failing with GitHub's own rate-limit error text in stderr — a class of failure the feature's own error-string preservation requirement (Story 1.3.2) guarantees stays invisible to structured detection. | Parse `gh`'s stderr/exit output for the known rate-limit phrases (GitHub CLI emits a distinguishable message for both primary and secondary limit hits) inside `runGHCommand`, and either set a synthetic `StatusCode` (403/429) + `Remaining: 0` on that path or add a parallel `gh_cli_exhaustion` detector so `ComputeExhaustionEvents` — or a sibling counter — can actually count it. At minimum, state explicitly in `.claude/docs/github-api-usage-tracking.md` (Story 5.2.3) that the Success Metric's exhaustion counter is native-transport-only and cannot detect `gh`-CLI exhaustion, so "0 exhaustions" is not read as "no exhaustion anywhere." | P1 |
| 2 | The reconciliation residual becomes routine background noise rather than an exceptional signal, because Tyler's own documented workflow (a second manual-test instance, the isolated e2e test server, a separate mobile-app instance — all sharing one token, each with its own per-instance `analytics.db` per the plan's accepted Unresolved Question) will regularly produce a nonzero `unaccounted_requests` residual and trigger `"github usage: reconciliation residual exceeds tolerance"` during ordinary, expected dev activity, not just during a real tracking gap. | The reconciliation WARN fires on most days of the trial regardless of whether tracking is actually complete, so a genuine undercount (e.g. a missed call site, or Failure #1 above) is indistinguishable from "just the usual multi-instance noise" and gets mentally dismissed the same way. | Tag or timestamp known concurrent-instance activity (even coarsely — e.g. record when `claude-manual-test`/e2e/mobile instances were running) so a residual spike during known multi-instance windows can be visually distinguished in the panel from an unexplained residual with no other instance active; failing that, state explicitly in Story 5.2.3's doc that the residual is expected to be routinely nonzero under normal dev workflow and is not itself a trust signal unless it correlates with *no* other known instance running. | P1 |
| 3 | The revived pause-on-limit behavior (dormant for 4 years, now live per Story 1.2.4) silently suppresses exhaustion by starving pollers rather than by actually reducing demand — sessions go stale for the duration of a pause with only an INFO-level skip log and no panel indicator (adversarial-review.md's own carried-forward Concern), so "0 exhaustions in 14 days" can mean "the pause fired constantly and degraded every session's PR status," which is a worse outcome dressed as a metric success. | Users (or Tyler) notice PR status/checks look stale across multiple concurrent worktree sessions with no correlated error, while the usage panel simultaneously reports a clean "0 exhaustions" — the two signals point in opposite directions and nothing in the plan connects them. | Add a `polling_paused_until`/pause-event-count field to `GetGitHubAPIUsageResponse` and require the 14-day verification procedure (Story 5.2.3) to check it alongside `exhaustion_events`/`dropped_events`/residual — a trial with zero exhaustions but frequent/long pauses should not be read as "problem solved." Also bump `session/pr_status_poller.go:198`'s skip log to WARN on the first skip of a given pause window, as adversarial-review.md already recommended but which is not yet a plan task. | P1 |
| 4 | Survivorship bias in the 14-day trial: nothing in the verification procedure (Story 5.2.3) compares trial-period request *volume* against a pre-ship baseline, so a quiet trial (fewer concurrent sessions than usual, a slow week, Tyler working on something else) produces "0 exhaustions" for reasons unrelated to whether the tracking/pacing actually fixed anything. | The panel's volume-over-time section shows a trial window with materially lower total request counts than typical historical load (only detectable by eyeballing the chart — the plan defines no automated check for this), yet the Success Metric is declared satisfied. | Add an explicit baseline-volume check to the Story 5.2.3 verification procedure: record the pre-ship average daily request volume (recoverable retroactively from log line counts or estimated from the requirements' own "hundreds to low thousands/day" baseline) and require the trial window's average daily volume to be at or above that baseline before "0 exhaustions" is accepted as evidence the problem is solved, not just evidence the app was used less. | P2 |
| 5 | Config-driven poll intervals/warn threshold require a service restart to apply (Story 3.3.1), but restarting the live `:8543` service kills every active tmux session (`.claude/rules/tmux-keep-server-on-restart.md`) unless `--tmux-keep-server` is passed — a real, separately-documented operational hazard this plan doesn't address. If a noisy poller is identified mid-trial, actually throttling it costs a disruptive restart, so the one remediation lever the feature adds is practically unusable without risking exactly the kind of live-session disruption Tyler has been burned by before, making it likely the lever goes unused and any real problem discovered mid-trial goes un-remediated until after the trial window closes. | A poll-interval or threshold change is saved in the UI ("Saved. Restart the service to apply.") but the restart is deferred indefinitely because no safe moment presents itself, so the change never actually takes effect during the trial. | Either explicitly document in Story 5.2.3 the exact safe-restart procedure for applying a mid-trial config change (confirm `--tmux-keep-server` is set, check no critical work is mid-flight, restart), or scope a lighter-weight application path (e.g., apply the new interval starting from the *next* natural process restart rather than requiring an ad hoc one) so the remediation lever doesn't carry the same cost as `make install-service`. | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — Resolved by plan.md Story 1.3.2's new acceptance criterion + Tasks 1.3.2d/1.3.2e: `runGHCommand`/`runGHCommandNoOutput` now classify `gh`'s stderr for the primary/secondary rate-limit phrases and synthesize `StatusCode`/`Remaining`/`RateLimitRejected` so the event feeds `ComputeExhaustionEvents` (Task 3.1.1d) instead of always reading `StatusCode: 0`; Story 5.2.3's doc task now states this detection is stderr-pattern-based (hour-bucketed `ResetAt`), not header-exact.
- [x] Failure #2 — Resolved by plan.md Story 5.1.1's strengthened acceptance criterion (the "another instance" clause in the reconciliation copy is now explicitly called load-bearing) plus Story 5.2.3's documentation task, which now states the residual is expected to be routinely nonzero under Tyler's normal multi-instance dev workflow and is not itself a trust signal unless it correlates with a window where no other known instance was running; dynamic per-instance detection is deferred and recorded as a new Unresolved Question (no cross-instance registry exists today — confirmed via `grep -rln STAPLER_SQUAD_INSTANCE --include="*.go"`).
- [x] Failure #3 — Resolved by plan.md Story 1.2.4's new `PauseStats` acceptance criteria + Tasks 1.2.4c/1.2.4d (pause count + cumulative duration tracking) and 1.2.4e (bump the pollers' skip log to WARN on first skip of a pause window); surfaced via new `pause_events`/`total_paused_seconds` fields on `GetGitHubAPIUsageResponse` (Stories 3.2.1/3.2.2) and a new "polling paused" panel stat (Story 4.3.1, Task 4.3.1b); Story 5.2.3's verification-procedure acceptance criterion now requires checking `total_paused_duration` alongside `exhaustion_events`/`dropped_events`/residual.
