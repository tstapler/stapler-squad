# Adversarial Review: github-api-usage-tracking

**Date**: 2026-08-11 (re-review)
**Verdict**: CONCERNS

## Blockers (prior review — re-verified against updated plan.md)

All 3 prior blockers are **RESOLVED**.

- [x] **RESOLVED — `QuotaCharged` formula for rate-limit-rejected responses.** Story 1.2.1's acceptance criteria (plan.md:438-451) now spell out a concrete Given-When-Then: a `403` with `X-RateLimit-Remaining: 0` yields `QuotaCharged: false, RateLimitRejected: true`, and the same rule is stated for `429`. Critically, the plan also adds the negative case — a `403` *without* a zero-remaining header (a permissions-denied 403) must still be `QuotaCharged: true, RateLimitRejected: false` — so the fix is a targeted exclusion, not a blanket "no 403/429 counts" rule that would have introduced a new miscount. Task 1.2.1a's `isQuotaCharged(resp) bool` helper (plan.md:485-490) implements exactly this: `false` for 304, `false`+`RateLimitRejected:true` for 403/429-with-zero-remaining, `true` otherwise. Task 1.2.1c adds dedicated tests for both the rejection case and the not-a-rejection case (`…_MarkQuotaNotChargedAndRejected_When_403WithZeroRemaining`, `…_MarkQuotaCharged_When_403IsNotARateLimitRejection`, plus the 429 equivalent). `APIUsageEvent` (Task 1.1.1b, plan.md:318-330) adds a `RateLimitRejected bool` field with an explicit doc note distinguishing it from the 304 case. This is a real logic change to the counting predicate, not just a new unused field — confirmed by walking the GWT example end to end.

- [x] **RESOLVED — panic-recovery scope.** Task 1.2.1a (plan.md:474-491) now explicitly states the delegation to `t.next.RoundTrip` happens "**outside** any `recover()` scope, and returns `(nil, err)` untouched on error with no event recorded" — then separately: "On a successful round-trip, wrap only the instrumentation portion — `DefaultRateLimiter.Update`, header parsing, `ParseGitHubResource`, `APIUsageEvent` construction, and `recordUsage` — in `defer func() { if r := recover(); ... }`." It explicitly says "The already-obtained `(resp, err)` from `t.next.RoundTrip` is returned to the caller regardless of whether this deferred block panics — never gate the return of `resp`/`err` behind the instrumentation succeeding." This is scoped correctly: it guards only the instrumentation, not the real HTTP call, so genuine transport errors still propagate unmuffled. Story 1.2.1's acceptance criteria add a concrete test scenario (plan.md:461-471): a `UsageRecorder` double that panics on every call, asserting the caller still gets `err == nil, resp.StatusCode == 200`, body intact, plus a WARN log — and Task 1.2.1c adds `TestUsageTransport_should_ReturnResponseNormally_When_InstrumentationPanics` implementing it.

- [x] **RESOLVED — `exhaustion_events` end-to-end implementation.** Task 3.1.1d (plan.md:1043-1056) adds `ComputeExhaustionEvents(rows []UsageRow) int`, filtering `StatusCode == 403 || StatusCode == 429` with `Remaining == 0` (mirroring `rate_limit.go`'s own exhaustion-detection predicate), then deduping by counting distinct `(Resource, ResetAt)` pairs rather than raw matching rows. This dedup logic is sound for the stated purpose: GitHub's `X-RateLimit-Reset` stays fixed for the duration of a single rate-limit window, so repeated retries during one ongoing exhaustion (same resource, same reset time) collapse to one counted incident, while a distinct later exhaustion (different `ResetAt`) correctly counts separately — tests `…_should_DedupeRepeatedRetriesWithinSameResetWindow_When_PollerRetriesDuringExhaustion` and `…_should_CountSeparately_When_ResetAtDiffersAcrossExhaustions` (plan.md:1052-1055) target exactly this. Wiring continues through: Task 3.2.2a's handler explicitly names `exhaustion_events` as populated `from ComputeExhaustionEvents(rows)` rather than left at zero-value default (plan.md:1126-1131, 1144-1146), with a handler test asserting `exhaustion_events == 2` for 2 distinct incidents. Story 4.3.1 / Task 4.3.1a (plan.md:1409-1456) then render it in the panel as a dedicated `data-testid="exhaustion-events-stat"` element, tier-colored by value ("0 rate-limit exhaustions..." in success color, nonzero in critical tier) — closing the gap the prior review found (previously no panel element surfaced this number at all). Detection → aggregation → RPC → UI is now a complete, traceable chain.

## Concerns (carried forward unchanged from prior review — not re-evaluated)

- [ ] **Per-instance storage will make the reconciliation residual routinely noisy, not just "measured."** ADR-028's trust story depends on `unaccounted_requests` reading near-zero so a nonzero residual is a meaningful WARN signal. But this repo's own `CLAUDE.md` documents running a *second*, fully separate `stapler-squad` instance sharing the same token as a routine, encouraged workflow (manual second-instance testing, the isolated e2e test server, a separate mobile-app instance) — each with its own `analytics.db` per the plan's own accepted Unresolved Question. Under that normal workflow, every instance's reconciliation will see the others' consumption as unaccounted, likely triggering `"github usage: reconciliation residual exceeds tolerance"` routinely rather than exceptionally — training the user to ignore exactly the signal the feature is built to make trustworthy. — **Recommendation**: either raise the tolerance/dampen the WARN specifically to account for expected concurrent-instance load, or explicitly document (and accept) that the WARN will fire during normal multi-instance dev sessions and should not be read as an anomaly signal in that case.
- [ ] **`dropped_events` is a process-lifetime cumulative counter exposed through a windowed RPC.** `GitHubUsageRecorder`'s drop counter (Task 2.1.1a) is a plain `atomic.Int64`, not bucketed by time, but Story 3.2.1 exposes `dropped_events` as part of a `window_days`-scoped response alongside window-scoped `exhaustion_events`/`unaccounted_requests`. A drop that happened once, hours after process start, would forever mark every subsequent 1-day-window query as carrying dropped data (or the reverse: a window that genuinely did lose data outside the counter's observation could be misread as clean, depending on how it's ultimately wired — the plan never says). No task reconciles this scoping mismatch. — **Recommendation**: either window-bucket the drop counter or make the response field's semantics ("cumulative since start" vs "in this window") explicit in the proto doc comment and the panel copy.
- [ ] **The revived pause-on-limit behavior has no live "polling is currently paused" indicator anywhere, and the poller's own skip line is INFO, not WARN.** The Risk Control section names this as the single non-additive behavior change in the whole plan, yet: (a) `session/pr_status_poller.go:198`'s `"PR status poller: rate limited, skipping tick"` log is INFO-level, unlikely to surface in typical WARN-focused monitoring; (b) no proto field or panel element surfaces "currently rate-limited / polling paused" as a live state — the panel only shows retrospective quota/volume/source data. A user could go the better part of an hour with stale PR statuses across every session with no visible signal connecting the staleness to rate limiting, discoverable only by already suspecting the cause and checking logs or the new panel's raw quota numbers by hand. The `STAPLER_SQUAD_GITHUB_PAUSE_ON_LIMIT` escape hatch is a valid *undo*, but it doesn't address *visibility* — which is what was asked for. — **Recommendation**: add a `polling_paused_until` (or equivalent) field to the RPC response and a visible banner in the panel, and bump the poller's skip log to WARN on the first skip of a given pause window.
- [ ] **Shipping a 4-year-dormant, never-executed pause path default-ON is a more aggressive rollout than the story's own stated rationale supports.** `DefaultRateLimiter.Update()` currently has zero callers (verified: `grep -rn "RateLimiter.*\.Update("` across the repo returns nothing outside `rate_limit.go` itself), so the pause behavior this feature activates has never run in production. Story 1.2.4 exists specifically because "reviving four-year-dormant code cannot wedge a poller with no way out short of a rollback" — yet the default is pause-enabled, with the escape hatch only useful reactively, after a user has already noticed and diagnosed the problem (compounded by the visibility gap above). — **Recommendation**: consider defaulting `STAPLER_SQUAD_GITHUB_PAUSE_ON_LIMIT=false` for an initial bake-in period (flip to pause-enabled once the behavior has been observed live), or explicitly document why default-on is acceptable given the single-user/local context.
- [ ] **`rate_limit.go`'s existing `setLimitedUntil` computation has a latent bug this plan is the first thing to actually exercise.** Lines 122–130: the doc comment promises "use `X-RateLimit-Reset` for exact resume time rather than a fixed 60s pause," but three lines later `wait` is unconditionally clamped to `maxRetryAfterSleep` (60s) whenever the real time-to-reset exceeds 60s — which, for a primary exhaustion mid-hour, is nearly always. In practice this means the poller will retry (and, per the `QuotaCharged` bug above, get mis-recorded) roughly every 60 seconds for the remainder of the reset window, rather than pausing cleanly until reset. Because `Update()` has never had a caller, this behavior has never been observed. — **Recommendation**: fix or explicitly accept-and-document this pre-existing clamp behavior as part of this feature, since this plan is what makes it live for the first time; don't let it surface as a surprise during the 14-day trial.
- [ ] **`TestClientGo_should_ConstructGHSubprocessInExactlyOnePlace` (Task 1.3.2c) is a source-text-scanning test, not a structural one.** Counting occurrences of the literal substring `safeexec.CommandContext(<ctx>, "gh"` is fragile to routine refactors (argument reformatting, a builder helper, an unrelated `gh --version` diagnostic call) that wouldn't change the counting-site guarantee it's meant to enforce, and could pass or fail for reasons unrelated to the actual invariant. — **Recommendation**: use `ast-grep`/`go/ast` to structurally assert "exactly one `exec.CommandContext` call with `"gh"` as the second argument," consistent with this repo's own stated tool preference for structural over textual code search.
- [ ] **The handler task (3.2.2a) is underspecified about which computed fields are actually wired to which proto fields.** *(Partially addressed: Task 3.2.2a now explicitly names `exhaustion_events` and `dropped_events` as fields the handler must populate from named aggregators rather than leave at zero-value — see resolved Blocker 3 above. Still open below.)* `ComputeBurnRate`/`ComputeTimeToExhaustion` are defined in Task 3.1.1b and required by Story 4.2.1's UI acceptance criteria, but Task 3.2.2a's own description never explicitly enumerates *their* mapping to proto fields the way it now does for `exhaustion_events`/`dropped_events`. The UI story will likely force this to be caught at implementation time (unlike `exhaustion_events`, which had no UI requirement forcing the same catch before this revision), but the handler task itself should still name every field it's responsible for populating, including these two.
- [ ] **The probe-cost contingency (Task 5.1.1a) is underspecified if `/rate_limit` turns out to cost quota.** The task says "raise the default probe interval and set `QuotaCharged: true`" if the empirical check shows the probe consumes quota — but if that's true, the probe becomes a real (if small) consumer competing with the very budget it's meant to measure as ground truth, which has second-order effects on `ComputeReconciliation`'s assumptions that a one-line "raise the interval" doesn't address.
- [ ] **Plan scale vs. stated appetite.** 71 tasks at their own ~3–5 minute estimates sum to roughly half a day of raw execution time, against a requirements.md appetite of "Large (3–6 weeks)." Each individual expansion (reconciliation probe, token-identity check, configurable warn threshold, burn-rate/time-to-exhaustion, four UI states) is independently justified, but nobody in the plan visibly checked whether the sum still fits the stated appetite — exactly the kind of creeping expansion `requirements.md`'s own Rabbit Holes section warned Phase 3 to watch for. Not a request to cut scope, but the estimate mismatch should be reconciled so early "task N/71 done" progress doesn't read as further along than it is.

## Minors

- Story 5.1.2's token-identity check is diagnostic/read-only and doesn't touch credentials, so it stays inside requirements.md's "not about changing token/auth strategy" boundary — but it is new logic in auth-identity-adjacent territory, worth a one-line callout in the PR description so a reviewer doesn't have to work out the distinction themselves.
- The token-identity check (Story 5.1.2) runs once at startup; a token change mid-trial (e.g. re-running `gh auth login`) would go undetected until the next restart. Consistent with this plan's existing restart-required convention elsewhere, but worth stating explicitly in the Story 5.2.3 doc's caveats section since the 14-day trial's validity depends on it.
- ADR-027's acknowledged query-ergonomics cost (JSON `labels` filtering vs. an indexed column) is self-aware and has a named escape hatch already — no action needed, noted only for completeness.
