- [x] **RESOLVED — Blocker 1 (shutdown channel-close race).** Story 2.1.1's acceptance criteria (`plan.md:803-810`) now explicitly require `Stop()` never race a concurrent `RecordAPIUsage` into a "send on closed channel" panic, backed by `TestGitHubUsageRecorder_should_NotPanic_When_RecordAPIUsageRacesStop` run under `-race` for 200+ iterations. Story 2.1.2 (`plan.md:891-899`) adds a second, independent layer: Task 2.1.2b (`plan.md:910-918`) requires `github.SetUsageRecorder(nil)` to be called *before* `rec.Stop()`, with the ordering spelled out explicitly ("Order in code: `githubpkg.SetUsageRecorder(nil)` → `rec.Stop()` → close `deps.AnalyticsEntClient`. Tests are specified by name at both the recorder level (Task 2.1.1c) and are cross-referenced from Story 2.1.2's acceptance criteria.

- [x] **RESOLVED — Blocker 2 (`exhaustion_events` had no implementing task).** Task 3.1.1d (`plan.md:1043-1056`) adds `func ComputeExhaustionEvents(rows []UsageRow) int`, explicitly implementing the same predicate `rate_limit.go` already uses (`StatusCode ∈ {403,429}` and `Remaining == 0`), deduped by `(Resource, ResetAt)` so retries during a single exhaustion window don't inflate the count — with 4 named tests including a zero-rows case. It is wired through the full chain, not left in prose: Task 3.2.2a's handler (`plan.md:1138-1147`) requires `exhaustion_events` be populated "from `ComputeExhaustionEvents(rows)` ... rather than leaving any of them at Go's zero-value default"; Story 3.2.2's acceptance criteria (`plan.md:1126-1131`) test this end-to-end (2 distinct incidents → `GetGitHubAPIUsageResponse.exhaustion_events == 2`); and Story 4.3.1 (`plan.md:1431-1440`) + Task 4.3.1a (`plan.md:1444-1454`) add a dedicated, tier-coloured `data-testid="exhaustion-events-stat"` UI element consuming the field, not just a passthrough proto field nobody reads.

## Concerns

(Carried forward verbatim from the prior review — not re-evaluated this pass.)

- [ ] **Story 5.1.2, `github/token_identity.go` — `CheckTokenIdentityParity` returns two same-typed strings positionally.** `func CheckTokenIdentityParity(ctx) (ghLogin, nativeLogin string, matched bool)` is exactly the primitive-obsession shape `.claude/rules/primitive-obsession-checklist.md` exists to catch — nothing stops a call site (or a future edit to this function's body) from returning/assigning `nativeLogin, ghLogin` swapped, and the compiler accepts it silently. This is the one place in the plan where a swap bug would directly corrupt the exact trust signal the story exists to provide (Task 5.1.2b's mismatch banner: "gh CLI is authenticated as a different user"). Every other cross-source label in this plan (`GitHubResource`, `CallSite`, `Fidelity`) got a newtype for this reason; this pair of returns did not.
  **Remediation**: Return a small value struct, e.g. `type TokenIdentity struct { GHLogin, NativeLogin string; Matched bool }`, or at minimum two distinct newtypes (`GHLogin string`, `NativeLogin string`) so a transposition is a compile error rather than a silent mislabel.

- [ ] **Story 1.1.1 / Story 1.2.2, `github/usage_event.go` + `github/rate_limit.go` — two incompatible representations of "unobserved."** `QuotaSnapshot` (Story 1.2.2) correctly represents "never observed" as map-key absence — the plan explicitly tests this ("the search entry is missing... rendered as '—', not as '0/0'"). But `APIUsageEvent.Remaining`/`Limit` (Story 1.1.1, Task 1.1.1b) use magic sentinels (`-1`/`0`) for the same concept at the per-event level, documented only in a doc comment convention borrowed from `rate_limit.go:53,59`. This is exactly the "illegal state representable" smell type-driven design flags: nothing in the type system stops a future caller from constructing `APIUsageEvent{Remaining: -1}` to mean something other than "unobserved," or from treating a real `Remaining: -1` (impossible in practice, but not impossible in the type) as valid data.
  **Remediation**: Either make `Remaining`/`Limit` `*int` (nil = unobserved) or introduce a small `ObservedQuota` sum type (`Observed{Remaining, Limit int}` / `Unobserved{}`) mirroring the map-absence design already used one layer up in `QuotaSnapshot`, so the two representations of the same domain concept are consistent.

- [ ] **Pattern Decisions table / Stories 4.2.1–4.2.2, `web-app/src/components/sessions/GitHubApiUsagePanel.tsx` — charting choice diverges from `research/build-vs-buy.md` without verifying the cited disqualifier.** `build-vs-buy.md` §3 recommends `recharts` explicitly for this panel ("already a dependency, already used for time-series + breakdown charts... a hand-rolled SVG chart would be reinventing what's already proven"). The plan's Pattern Decisions table instead chooses hand-rolled `Bar`+`<table>`, justified as "a bare SVG chart needs a separate text alternative." That justification is reasonable in the abstract, but the plan never cites having checked whether the existing `recharts` usage in `web-app/src/app/insights/DailySpendChart.tsx` (the very precedent `build-vs-buy.md` points to) already has an accessible fallback — if it does, the stated disqualifier for recharts doesn't hold, and the plan is introducing a second charting convention into the codebase (table-row bars vs. recharts SVG) on an unverified premise. This is not a fabricated rationale, but per this repo's own evidence-and-claims standard ("run it, don't read it" / cite what was actually checked), a research-recommendation override deserves the verification step, not just a plausible-sounding reason.
  **Remediation**: Before or during Story 4.2.1, open `DailySpendChart.tsx`/`ModelBreakdownChart.tsx` and confirm whether they ship any accessible text/table fallback. If they do, either reuse that pattern with recharts (matching the research recommendation) or state explicitly in the Pattern Decisions table why `ApprovalAnalyticsPanel`'s convention still wins even when recharts's accessibility gap is closed elsewhere.

- [ ] **ADR-027 / Epic 2.1 — a second independent async writer added to `analytics.db`'s single-connection pool, contention untested.** ADR-027 correctly identifies that inline writes from `RoundTrip` would contend with `analytics.db`'s `SetMaxOpenConns(1)`, shared with "the escape-event batch writer" (`server/server.go:643`), and solves that by buffering. But the fix adds a *second* independent buffered flush loop (`GitHubUsageRecorder`, 5s ticker) alongside the pre-existing escape-event writer, both ultimately serializing on the same one connection. Functionally safe (the DB layer serializes), but the combined write load of two independent, unsynchronized tickers on one connection is asserted as "negligible" from the feature's own volume estimate, not measured under both writers running together — no story tests or observes flush-loop latency with both writers active simultaneously.
  **Remediation**: Not a blocking concern given the low stated volume, but worth a one-line acceptance criterion in Story 2.1.2 (or the manual-smoke task, 5.2.4b) confirming no elevated `GitHubUsageRecorder` flush latency/drop-count increase is observed with the escape-analytics writer also active, so the "negligible overhead" claim in `requirements.md`'s Non-functional Requirements is checked rather than assumed for the combined case.

## Nitpicks

(Carried forward verbatim from the prior review — not re-evaluated this pass.)

- `web-app/src/components/sessions/GitHubApiUsagePanel.tsx` accumulates quota tiles, volume-over-time, source breakdown, window selector, four empty/stale/unavailable states, and the warn-threshold editor across Stories 4.2.1–4.3.2, all in one file with only `QuotaTile` broken out as a sub-component. This matches the existing `ApprovalAnalyticsPanel.tsx` house convention (not a plan-introduced regression), but the story count (6) suggests the file will be large enough that extracting `VolumeSection`, `SourceBreakdownTable`, and `WarnThresholdEditor` as named subcomponents (even if colocated in the same file) would pay for itself.
- `github/usage_event.go` (Task 1.1.1a/b + Task 1.1.3a) is scoped to hold the three newtypes, `APIUsageEvent`, the `UsageRecorder` interface, `noopUsageRecorder`, and the atomic setter/getter — five distinct concerns in one file. Not a correctness issue (Go doesn't demand one-type-per-file), but worth a mechanical split (`usage_event.go` for the value types, `usage_recorder.go` for the sink) if the file grows past the tasks' rough line estimates.
- `server/analytics/github_usage_query.go`'s `parseUsageRow` (Task 3.1.1a) has no stated behavior for a stored `event_name`/`resource` string that no longer matches any `CallSite`/`GitHubResource` constant (e.g., after a future rename or the kind of dead-code deletion this feature itself does to `IsForkRepo`). Typed-string values degrade gracefully at runtime (no panic), but an explicit test asserting unrecognized historical values surface as an `unknown`-labeled row rather than being silently dropped from aggregation would close the gap cheaply.
