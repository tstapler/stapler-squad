# Architecture Research: Durable Guidance Requests

## 1. Overall server architecture — service boundaries and registration

`server/server.go` (1735 lines) registers one ConnectRPC service per domain concept, each independently mounted on `srv.mux`. Confirmed services (all in `proto/session/v1/*.proto`, one `service` block per file):

- `SessionService` (session.proto) — server/server.go:424
- `BacklogService` (backlog.proto) — server/server.go:593, streaming `WatchBacklogItems` mounted separately at server/server.go:604-605
- `UnfinishedWorkService`, `SessionSummaryService`, `HandoffSummaryService`, `InsightsService`, `GitHubUserService`, `TymuxRolloutService`, `NativeGitRolloutService`, `RemoteService`, `HeadlessService`, `ImportService` — each its own file, each its own `NewXServiceHandler(...)` call (server/server.go:441-675)

There is **no combined "notification service"** — `NotificationService` (server/services/notification_service.go) is itself already a separate, focused service (`GetNotificationHistory`, `MarkNotificationsRead`, `ClearNotificationHistory`) distinct from `BacklogService` and `SessionService`. This is the precedent: the codebase splits by bounded concept, not by "everything backlog-adjacent in one god-service."

**Implication for GuidanceRequest**: the existing pattern strongly favors a new standalone `GuidanceService` (new `proto/session/v1/guidance.proto`), not bolting RPCs onto `BacklogService` or `SessionService`. It would follow the exact same wiring recipe as every other service: define `service GuidanceService` in a new `.proto`, `make proto-gen`, implement a `GuidanceService` struct in `server/services/guidance_service.go`, register in `server/server.go` alongside the others (`sessionv1connect.NewGuidanceServiceHandler(deps.GuidanceService, ConnectOptions(deps.ErrorRegistry)...)`), and wire construction into `server/dependencies.go` (the single place `BacklogService{...}` and friends get built — grep for `BacklogService{` in that file to find the pattern; not present in this exact search but that file is confirmed as the DI point by its role in the codebase's own doc index).

A `GuidanceRequest` is scoped optionally to a backlog item, a session, or standalone per the requirements — that's a genuine new cross-cutting entity, not a natural extension of `BacklogItemData` or `SessionGoal`, reinforcing a dedicated service+entity rather than extension of an existing one.

## 2. Data flow and consistency — the fan-out mechanism

Traced via `server/services/backlog_service_events.go` and `pkg/events/bus.go`.

**Write path** (e.g. a status transition via `post_backlog_update` or `TransitionBacklogItemStatus`):
1. Repository method (`session/storage_backlog.go` et al.) persists the change to the ent/SQLite-backed `Storage`.
2. The repository calls `session.ItemChangePublisher.PublishItemChanged(item, change)` — implemented by the adapter `BacklogItemEventPublisher` (server/services/backlog_item_event_publisher.go:32), which converts the session-package's cycle-avoiding `BacklogChangeKind` into `events.BacklogChangeKind` and calls `p.Bus.Publish(...)`.
3. `EventBus.Publish` (pkg/events/bus.go:72) assigns a monotonically increasing `Seq`, appends to an **in-memory ring buffer** (`eb.buf`), then fans out non-blockingly to every subscriber's channel (drops the event for any subscriber whose channel is full — pkg/events/bus.go:86-93).
4. `BacklogService.WatchBacklogItems` (server/services/backlog_service_events.go:80) is a long-lived ConnectRPC server-stream handler: it subscribes to the bus (`s.eventBus.Subscribe(ctx)`), sends an initial snapshot (fresh connection) or replays `EventsSince(afterSeq)` (reconnect), then forwards live events matching client-side filters until disconnect.
5. MCP's `wait_for_backlog_event` tool (server/mcp/tools_backlog.go:775) does the same subscribe-then-block pattern but as a single blocking RPC call capped at 60 seconds (server/mcp/tools_backlog.go:793-799), with a "already-satisfied" precheck (`currentStateWaitResult`, tools_backlog.go:716) so a caller that missed the event because it wasn't running yet still gets an immediate correct answer from the persisted item state rather than blocking uselessly.

**This is a pure in-memory fan-out pub/sub, NOT a DB-poll-and-diff.** Critically: `pkg/events/bus.go:10-15` — the ring buffer's retention is `eventBufTTL = time.Hour` and `eventBufMaxLen = 10_000`, held entirely in a Go slice in process memory (`eb.buf`, guarded by `eb.bufMu`). **The EventBus does not survive a process restart at all** — on restart, `subscribers` is empty and `buf` is empty; there is no persistence layer under it. It exists solely to (a) push live updates to connected UI/MCP clients and (b) let a client that disconnects for under an hour replay what it missed via `afterSeq`.

**Consequence for GuidanceRequest**: the EventBus fan-out mechanism is perfectly reusable for *live* UI notification (a new `GuidanceRequestEvent` wired the same way `BacklogItemEvent` is, or reuse the existing bus with a new `events.EventType`), but it **cannot** be the durability mechanism the requirements demand ("must survive the asking session being paused/restarted/no-longer-live" — and by extension, must also survive the *server process* restarting, since backlog automation and MCP daemon connectivity already assume that). The durable source of truth must be the ent/SQLite-backed `Storage` (see §5). A resumed/restarted session cannot rely on "I was subscribed and missed it" — it must query persisted state directly on resume (mirroring `currentStateWaitResult`'s precheck-before-blocking pattern), not merely resubscribe to the bus and hope replay covers the gap.

## 3. Integration points for the two producer/consumer types

### Automated triage — `session/backlog_triage.go` + `server/services/backlog_service_triage.go`

`session/backlog_triage.go` itself contains no invocation logic — it's pure prompt-building (`BuildHeadlessTriagePrompt`, `BuildHeadlessRetriagePrompt`) and response parsing (`ParseHeadlessTriageResult`, `extractTopLevelJSONObjects`). The actual orchestration lives in `server/services/backlog_service_triage.go`'s `TriggerTriage` RPC handler (line 2670):

- Validation, status guards, and an atomic in-flight check (`s.triageInFlight.LoadOrStore`, line 2742) all run **synchronously** in the RPC handler.
- At line 2845 (`go func() { ... }()`), the actual headless LLM call (`s.headlessPool` → `CallBlocking`) is dispatched into a **background goroutine** so the RPC returns immediately; the goroutine parses the result and persists it via `applyTriageResultToUpdate`.
- The triage prompt already has a crude, non-durable analog of "asking a question": `TriageSuggestion{Text, Rationale}` where `Rationale == "question"` signals an open question (session/backlog_triage.go:104, :163). These are batched into the final JSON blob, are free text (no structured yes/no/multiple-choice/short-answer schema), are **never blocking** (triage always proceeds to apply whatever it decided), and have no durable answer-delivery mechanism — a human reading the suggestions list has no structured way to "answer" one.

**Where "create a GuidanceRequest and pause/exit early" fits**: inside the line-2845 goroutine, after `ParseHeadlessTriageResult` — instead of (or in addition to) emitting a `rationale:"question"` suggestion, the triage prompt could be extended to emit a distinct `blocking_question` field (or the goroutine could inspect existing suggestions marked as blocking) and, when present, call into the new `GuidanceService`/storage layer to create a durable `GuidanceRequest` scoped to the item, then **skip** `applyTriageResultToUpdate`'s status advance and leave the item in a new "awaiting guidance" sub-state (or reuse `BacklogStatusBlocked`-style semantics — needs an item-status-model decision left to the planning phase) instead of completing triage. The goroutine already has the item ID, artifact path, and iteration count in scope (`itemID`, `itemRepoPath`, `isID`, `iteration` — lines 2840-2843), so wiring in a guidance-creation call requires no new plumbing to reach the item context.

### Autonomous driver — `session/autonomous_driver.go`

`AutonomousDriver.Start` (line 184) launches exactly one long-lived goroutine per session (`run`, line 258) that loops until `directiveDone`/`maxTurns`. Each iteration:
1. Captures pane tail, builds an orchestration prompt (`buildOrchestrationPrompt`), calls the headless LLM (`d.headlessPool.CallBlocking`, line 330).
2. Parses a directive (`parseOrchestrationResponse` → `directiveDone`/`directiveWait`/inject-nudge) from the response (line 336).
3. On a non-WAIT, non-duplicate directive, injects the nudge into the tmux pane via `SubmitDriverContent` (line 394) and waits for the session to go idle again before the next turn (line 416-421).

This loop is exactly the right integration point for "check for an outstanding answered GuidanceRequest and resume/inject it": at the top of each turn (around line 312-322, before `buildOrchestrationPrompt`), the driver could query the guidance store for any `GuidanceRequest` scoped to this session/item that has an `answered_at` timestamp but hasn't yet been delivered, and if found, short-circuit the LLM orchestration call for that turn and inject the answer directly as the next nudge (via the same `SubmitDriverContent` path already used at line 394) — no new delivery mechanism needed, just a new decision point ahead of the existing LLM-orchestrated one. Because this loop already re-polls every turn (bounded by `maxTurns` and idle-settle waits), it naturally satisfies "survive the asking session being paused" for the *autonomous-driver* producer case: even if the driver goroutine itself was killed by a restart, a fresh `AutonomousDriver` constructed on session resume would pick up the same durably-stored, still-unanswered/newly-answered `GuidanceRequest` on its very first turn — provided resume logic queries the DB (not the in-memory EventBus) for outstanding requests, consistent with §2's finding.

## 4. MCP tool surface

MCP tools are defined and registered in `server/mcp/` (confirmed by grep: `server/mcp/tools_backlog.go`, `tools_goal.go`, `tools_notifications.go`, `tools_history.go`, `tools_workflow.go`, `tools_lifecycle.go`, `tools_terminal.go`, `tools_vcs.go`, `tools_github.go`, `tools_rules.go`, `tools_discovery.go`). This is the correct location — not `stapler-scripts/` (that directory holds unrelated standalone tooling and the `llm-sync` config mirror, per this repo's own `CLAUDE.md`).

The established pattern per domain (goal tools are the closest small-scope analog):
- A `*Handlers` struct per domain holding just the dependencies it needs (`goalHandlers{storage, store, eventBus, enabledCheck}`, server/mcp/tools_goal.go:18-23; `backlogHandlers` similarly at tools_backlog.go:320-390-ish).
- A `registerXTools(s *mcpserver.MCPServer, h *xHandlers)` function that calls `s.AddTool(mcpgo.NewTool(...), h.methodName)` per tool (tools_goal.go:26, tools_backlog.go:2880).
- Wired from `server/mcp/server.go`'s `NewCore`/similar constructors (server/mcp/server.go:77-78: `registerBacklogTools(...)`, `registerGoalTools(...)`), which thread through the shared `*events.EventBus` (nil-able — "optional; pass nil to disable... on stdio path", server/mcp/server.go:22,90,119).

**Recommendation**: add a new `server/mcp/tools_guidance.go` with a `guidanceHandlers` struct and `registerGuidanceTools`, exposing at minimum:
- `create_guidance_request` — any LLM session can create one scoped to `item_id` (optional), `session_id` (optional, defaults to caller like `set_session_goal` does — tools_goal.go:31), a `question_type` (yes_no / multiple_choice / short_answer), `question` text, and choices for multiple-choice.
- `get_guidance_request` — read current state/answer by ID, mirroring `get_backlog_item`'s direct-read pattern.
- `wait_for_guidance_answer` — **model directly on `waitForBacklogEvent`** (tools_backlog.go:775): a bounded (≤60s) subscribe-then-block on the EventBus filtered to this guidance request's ID, with a `currentStateWaitResult`-style precheck against persisted state first (so a request answered while the caller was offline doesn't require actually catching a live event — it's returned immediately from storage). This is the same durability-vs-liveness split as §2: EventBus for "wake me up if it happens while I'm here," persisted storage for "tell me if it already happened."

This also directly serves the requirement that "any subscribed LLM/session" (not just internal Go code) can create/read guidance requests — MCP tools are the only surface reachable by an arbitrary Claude Code session, since ConnectRPC endpoints are consumed by the React web UI, not by LLM tool-calling.

## 5. Durability / consistency guarantees

**Database engine**: SQLite, accessed through the `ent` ORM (confirmed: `go.mod:37` `github.com/mattn/go-sqlite3 v1.14.40`, `go.mod:66` `modernc.org/sqlite v1.56.0`; `session/storage_test.go` opens via `sql.Open("sqlite", ...)`). New entities are added as ent schema files under `session/ent/schema/` — e.g. `session_goal.go` is the closest existing analog to a scoped, small, mutable side-entity: it has its own UUID, a `session_uuid` foreign-key-by-convention field, status, optional JSON blob field, and `created_at`/`updated_at` timestamps with a unique index (session/ent/schema/session_goal.go:17-42). A new `GuidanceRequest` schema would follow the same shape: `id`, optional `backlog_item_id`, optional `session_uuid`, `question_type`, `question` text, `choices` (JSON), `status` (pending/answered/expired), `answer` (JSON or text), `answered_by`, `created_at`/`answered_at`, plus indexes on `backlog_item_id`, `session_uuid`, and `status` for the lookups both the autonomous driver's per-turn poll and any dashboard/triage-panel query need.

**Durability is automatic and requires nothing special**: ent/SQLite already gives every write ACID durability via SQLite's WAL/journal — ordinary `Storage` writes (the same path every other entity uses) survive process restart with no extra work, per `docs/reference/state-isolation.md`'s isolation-hierarchy doc: the *file location* of that SQLite DB is what varies (Priority 1 `$STAPLER_SQUAD_TEST_DIR` → Priority 2 `STAPLER_SQUAD_INSTANCE` → Priority 3 test-auto-detect → Priority 4 preferred-workspace → Priority 5 opt-in per-cwd workspace → Priority 6 default `~/.stapler-squad/`), not whether writes persist. A `GuidanceRequest` row written under any of these scopes persists exactly as durably as a `BacklogItem` row in the same scope — no bespoke handling needed, and it automatically respects `--test-dir` isolation since it's the same `Storage`/ent client every other entity shares.

**One thing that is *not* automatic**: cross-restart *notification delivery* to the LLM/session that asked. As established in §2, the EventBus is pure in-memory and gives zero durability across a server-process restart (not just a session restart). The codebase's own precedent for a durable, restart-surviving notification channel is `server/notifications/store.go`'s `NotificationHistoryStore` — but note this is a **separate mechanism from ent/SQLite**: it's a hand-rolled JSON-file-backed store (`loadFromDisk`/`saveToDisk`, server/notifications/store.go:622,650) with its own retention/pruning (`enforceRetention`, `PruneOrphaned`), exposed via `NotificationService`'s `GetNotificationHistory`/`MarkNotificationsRead` RPCs and the existing `mcp__stapler-squad__get_notification_history` tool. A guidance-request answer's delivery should almost certainly go through the **ent/SQLite `GuidanceRequest` row's own `status`/`answer` fields** (queried directly, not via the JSON notification log) as the source of truth an autonomous-driver resume or a `wait_for_guidance_answer` precheck reads — the JSON `NotificationHistoryStore` is a reasonable *supplementary* "hey, you have an answer waiting" ping (reusing `EventBusNotifier`/`Notify(itemID, title, message, notificationType, priority)`, server/services/backlog_notifier.go:17) but should not be relied on as the only place the answer itself lives, since it's designed for lightweight operator-facing alerts, not structured Q&A payloads.

## Summary for coordinator

- **New standalone `GuidanceService`** (proto + `server/services/guidance_service.go`, wired in `server/server.go`/`server/dependencies.go` exactly like `BacklogService`/`NotificationService`) plus a new ent schema entity (`session/ent/schema/guidance_request.go`, modeled on `session_goal.go`) is the right shape — this codebase splits services by bounded concept and already has a precedent (`NotificationService`) for a cross-cutting, non-backlog-owned service, so guidance requests should not be bolted onto `BacklogService`.
- **Durability and liveness are two different, already-separated mechanisms here**: the ent/SQLite `Storage` layer gives free, automatic durability for the `GuidanceRequest` row itself (survives process/session restart, respects `--test-dir`/instance isolation with zero extra code), while `pkg/events.EventBus` (server/services/backlog_service_events.go, server/mcp/tools_backlog.go's `wait_for_backlog_event`) is a **pure in-memory, restart-losing** fan-out that should only be reused for live UI/MCP push notifications — never as the source of truth a resumed session checks. Every consumer (autonomous driver resume, `wait_for_guidance_answer`, triage pause/resume) must precheck persisted DB state first (mirroring `currentStateWaitResult`'s pattern) rather than assuming a missed live event is recoverable.
- **Concrete integration points**: automated triage's async goroutine in `TriggerTriage` (server/services/backlog_service_triage.go:2845) is where "ask instead of guess" would create a `GuidanceRequest` and skip the status-advance; `AutonomousDriver.run`'s per-turn loop (session/autonomous_driver.go:312-421) is where "check for an answered GuidanceRequest and inject it" fits naturally since it already re-polls every turn via the existing `SubmitDriverContent` injection path. New MCP tools (`create_guidance_request`, `get_guidance_request`, `wait_for_guidance_answer`) belong in a new `server/mcp/tools_guidance.go`, modeled directly on `tools_backlog.go`'s `waitForBacklogEvent`/`currentStateWaitResult` pair, so any external LLM session (not just internal Go code) can participate.
