# Pre-mortem: backlog-stuck-item-visibility
**Date**: 2026-07-14

Imagine the feature shipped and failed. The failure that matters most is not a crash —
it is the feature going green in CI, the UI rendering a calm "Nothing stuck — all backlog
items are progressing," and a re-run of the original live investigation *still* finding
silently-stuck items. That is "ship but not solve," and three of the five modes below are
exactly that. Two of the five are more severe than the current adversarial-review "CONCERNS"
verdict admits (see F2 and F3).

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | **The flagship case (PR #148) never surfaces.** `pr_ready_unmerged` is keyed exactly on `github.DerivePRPriority(info) == PRPriorityReady`, and `PRPriorityReady` requires `info.ApprovedCount > 0` (`github/priority.go:50`). On a single-user repo Tyler cannot approve his own PR — GitHub forbids self-approval — so `ApprovedCount` is always 0 and the priority resolves to `PRPriorityPending` forever. The one PR that motivated the whole feature is structurally excluded. | The success-metric re-run finds PR #148 (green, mergeable, 3 days unmerged) is **still not** in the stuck view. Seeded e2e/unit tests pass (they seed `ApprovedCount>0`), so nothing catches it before ship. | Change the `pr_ready_unmerged` readiness signal in Task 2.1.1a: for a single-user self-hosted instance, "ready" must be **`CI passing AND not blocked AND no changes requested AND mergeable`, treating `ApprovedCount==0` as acceptable** (a self-authored PR has no reviewer). Do NOT reuse `PRPriorityReady` verbatim; either add a `PRPriorityReadyNoReview` branch to `DerivePRPriority` or compute readiness for this detector from `CheckConclusion in {success,""} && ChangesRequestedCount==0 && !IsDraft && Mergeable`. Add a unit test asserting an **unapproved** green PR flags `pr_ready_unmerged`. Update plan.md Pattern Decisions row "Green-PR-unmerged signal" — its stated rejection of the raw-boolean path is wrong *for this instance* because the canonical helper is a false-negative here. | **P1** |
| 2 | **The badge lies, so Tyler stops trusting it (adversarial C2, escalated).** `pr_ready_unmerged` and `stale_work` clear *without a status change*: a new commit / re-running CI makes a PR no-longer-ready while it stays `pr_pending`; a stale session resumes while the item stays `in_progress`. Tasks 2.1.1a / 2.1.3b specify only the positive `MarkStuck` branch, and the self-heal sweep is status-based so it *structurally cannot* see a same-status clear. The row stays open. | UI shows "PR ready to merge — stuck 3d" or "work stale" for a condition that already cleared. Tyler clicks in, sees CI running / work active, learns the signal is stale. After 2-3 such incidents he ignores the badge — at which point a *genuinely* stuck item is missed and the feature has failed at its sole purpose. | Give every poll-shaped reconciler an explicit **else-branch**: when the poll shows the condition no longer holds, call the atomic idempotent `ResolveStuck(reason)`. State this in Task 2.1.1a (`pr_ready_unmerged`), Task 2.1.3a (`abandoned_review`), Task 2.1.3b (`stale_work`) as "mark-OR-resolve every tick." This is P1 not "concern": for a single-user trust-based signal, a lying badge is not recoverable — once trust is gone, silently-stuck items return permanently. | **P1** |
| 3 | **The 6 observed review items aren't each proven to map to a reason; zombie-session items fall through every detector.** `abandoned_review` reuses `FindStuckReviewItems`, which **excludes** any review item that still has a work/review session with `EndedAt IS NULL` (`storage_backlog.go:524-527`) — but its own doc comment describes exactly this case (a rolled-back item whose prior work session "never got marked ended"). Such an item is `review` (not `in_progress`, so not `stale_work`), has an "active" session (so not `abandoned_review`), may have <3 cycles (not `bouncing`) and no cap hit (not `rework_cap`). No reason covers it. No story verifies each of the real 6 maps to a reason. | Success-metric re-run: the status-count query still shows 6 items in `review`, but the stuck view shows fewer (e.g. 4). The 1-2 zombie-session items are silently absent, and no test flagged it because tests seed clean sessions. | Add a **live-data verification gate** to validation.md (before Phase 6 sign-off): run the original investigation queries against the shipped data source and assert each of the 6 observed items appears with a reason; any that don't get a documented reason. Add a `stale_review` / zombie-session detector OR broaden `abandoned_review` to also match `review` items whose only "active" session's underlying tmux/CLI session is confirmed dead (reuse the liveness check `reconcileStaleWorkSessions` already relies on). Do not ship until every one of the 6 is accounted for. | **P1** |
| 4 | **Self-heal sweep resolves valid rows on their healthy half-cycle (adversarial C1).** The sweep resolves a row "whose current item status is inconsistent with its reason's expected status," but `bouncing` legitimately spans {`in_progress`,`review`} and the event-shaped `rework_cap`/`push_failed` are written with `expectedStatus=<current>` — they have no single anchor. A naive implementer resolves a valid `bouncing` row the moment the item sits in `in_progress` (its normal half-cycle). | `df0d5872`-style bouncing item flickers in and out of the view every tick; its notification re-fires each time the sweep resolves then the detector re-marks. Notification fatigue; the item may read as "zero stuck" on the exact tick the investigation is re-run. | Add the explicit per-reason expected-status(es) table to Task 2.1.5d: anchored reasons → one status; `bouncing` → set {`in_progress`,`review`}, resolves only on a terminal/`done`/PASS status; `rework_cap`/`push_failed` → **excluded from the status-based sweep**, relying on their event-site `ResolveStuck` (Tasks 2.1.5b/2.1.6a). Decide before Story 2.1.5, as the adversarial review recommends. | **P2** |
| 5 | **A silently-dead detector is indistinguishable from "nothing stuck."** Per-detector `recover()` (Task 2.1.5e) swallows a panic in one detector so the others survive — good for isolation, but on this fast-moving single-user codebase a new code path can nil-deref *every* tick. That reason's rows are never written, and with no metrics/alerts (by design) the UI shows the reassuring empty state for that class. The empty state also can't distinguish "detector ran, found nothing" from "listener `enabled` flag is false" or "detector paniced." | UI: "Nothing stuck — all backlog items are progressing," while a detector has been dead for days. Only a log grep (which this feature exists to replace) reveals it. | (a) In each per-detector `recover()`, log at **WARNING** with the reason name and increment nothing-silent — a panic must be loud even without metrics. (b) Add a per-tick **DEBUG/INFO "self-check"**: log detector-ran counts so a detector that stops running is visible in logs. (c) Consider a lightweight "last successful full sweep at" timestamp surfaced in the UI so the empty state means "checked at HH:MM," not just "empty" (mirrors the `pr_status_unknown` staleness idea, applied to the whole view). | **P3** |

## P1 Items (address before implementation)
- [x] **F1 — `pr_ready_unmerged` must recognize an unapproved green PR.** RESOLVED: introduced the co-located pure predicate `prReadyToMergeSolo(info)` (same blocking-exclusions as `DerivePRPriority` minus the `ApprovedCount>0` gate) and re-keyed Story 2.1.1 / Task 2.1.1a on it (no longer `PRPriorityReady`). Updated plan.md Domain Glossary `pr_ready_unmerged` entry, the "Green-PR-unmerged signal" Pattern Decision, and Story 2.1.0 (predicate + AC). Added the "Single-user readiness" note to ADR-001 explaining Tyler cannot self-approve so `PRPriorityReady` is a permanent false-negative. Flipped validation.md: replaced the old "no false-positive on unapproved PR" test with `TestPrReadyToMergeSolo_should_returnTrue_When_GreenMergeableUnapproved` + `TestReconcilePRPending_should_markStuck_When_PRGreenMergeableUnapproved` (regression guard for PR #148) and fixed the happy-path scenario.
- [x] **F2 — `else ResolveStuck` branch on every poll-shaped reconciler.** RESOLVED: added explicit "mark-OR-resolve every tick" else-branch ACs and task steps to Story 2.1.1 / Task 2.1.1a (`pr_ready_unmerged`), Story 2.1.3 / Task 2.1.3a (`abandoned_review`), and Story 2.1.3 / Task 2.1.3b (`stale_work`) in plan.md — each calls `ResolveStuck` directly when the condition clears without a status change, since the status-anchored self-heal sweep structurally cannot see it. validation.md already carried the C2 regression tests for all three.
- [x] **F3 — live-data verification gate + zombie-session coverage.** RESOLVED: added Task 2.1.3d (zombie-session review detection) + a broadening AC to Story 2.1.3 in plan.md — surfaces `review` items whose only `EndedAt IS NULL` session's underlying process is confirmed dead, reusing the existing `Instance.TmuxSessionExists()`/`TmuxProcessManager.DoesSessionExist()` liveness helper (not a new mechanism) via a `FindZombieReviewItems` query, closing the `FindStuckReviewItems` (`storage_backlog.go:519-527`) exclusion gap. Added validation.md tests (`...OnlyActiveSessionIsDeadZombie` + live-session negative) and a "Live-data verification gate" asserting all 6 observed review items + PR #148 map to a reason before Phase 6 sign-off.

## Notes on the two open adversarial concerns
- **C2 is more severe than "concern" → P1 (F2).** For a single-user, trust-based signal whose entire value proposition is "trustworthy, never a phantom," a persistently-lying badge is not a recoverable annoyance — it is the specific failure that makes Tyler ignore the feature, which re-creates the original problem. The fix is trivial (an else-branch) and must be in the plan before implementation, not discovered in QA.
- **C1 stays P2.** Its worst outcome is flapping/notification-fatigue and a momentary "zero stuck" read, which is visible and self-corrects; it is bounded, unlike F1/F2/F3 which are silent. Still must be specified (the per-reason status table) before Story 2.1.5.
- **A larger risk than either sits outside both concerns: F1.** The canonical-readiness reuse that the plan treats as its safest, most-defensible decision is in fact a structural false-negative on the one instance this ships to. It was not caught by iterations 1-2 because both reasoned about *false positives* (unapproved PR wrongly flagged) and never about the single-user *false negative* (no approver possible).
