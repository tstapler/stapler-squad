# Research: Features & UX Patterns — backlog-stuck-item-visibility

## 1. Industry comparables

| Pattern | What it does well | What's missing that this feature needs |
|---|---|---|
| **GitHub "Ready for review" / merge queue UX** | A PR that's green and approved gets a persistent, always-visible "Merge pull request" button state plus (with auto-merge) a banner: "Auto-merge enabled — will merge when requirements are met." The state is a property of the PR itself, not a transient toast. | GitHub's own UI has no cross-PR dashboard of "PRs that have been mergeable for N days" — that gap is exactly what root cause #1 needs filled at the *repo-owner* level (across many backlog items), which GitHub doesn't natively provide. This project already fetches per-PR check/review state (see §3c) — the missing piece is aggregating "green but unmerged" as its own durable, timestamped condition rather than deriving it live each poll.
| **Dependabot / Renovate "Dependency Dashboard" issue** | Renovate keeps ONE persistent, continuously-edited issue that lists every PR it manages, grouped by state: "Pending", "Rate-Limited", "Errored", "Awaiting Schedule", "Open". Each row has an explicit *reason* string, not just a status. It survives bot restarts because the state lives in the issue body (rendered fresh each run), not in bot memory. | Directly validates the requirements' "durable, queryable, reason-labeled" bar. The key design idea worth borrowing: **one row per item, one explicit reason column, regenerated from source-of-truth state rather than incrementally mutated** — avoids the exact bug class in root cause #3 (in-memory notify-once maps).
| **CI dashboards (CircleCI Insights, Buildkite, GitHub Actions Insights)** | Show duration-in-state ("queued for 4m", "running for 12m") and flag anomalies (flaky, longer than P95). Failures are surfaced as a *persistent row* in a table, not a toast — you only get a toast/notification once, but the dashboard row persists until resolved. | Confirms the "toast vs. row" distinction is an industry-standard pattern: ephemeral notification = "something changed", persistent dashboard row = "current state". This project conflates these today — see §2 on NotificationContext.
| **Project-management "Blocked" swimlane (Jira, Linear, GitHub Projects)** | A card that's flagged blocked shows *why* (linked blocking issue, or free-text reason) directly on the card, in the board itself — not as a separate alert feed. Blocked state has its own visual treatment (red flag icon) distinct from just "in progress". | Suggests the UI for this feature should treat "stuck" as a *badge/attribute on the existing item*, analogous to how `/unfinished` already badges worktrees (dirty/ahead/behind chips) — not a wholly separate feed disconnected from the item's context.
| **Sentry / error-tracking "issue" model** | Groups repeated occurrences of the same underlying problem into one persistent "issue" with first-seen/last-seen timestamps and an occurrence counter, rather than one notification per event. Explicit resolve/ignore/snooze actions per issue. | This repo already has this exact pattern implemented for a *different* subsystem — `session/ent/schema/error_event.go` (fingerprint, occurrence_count, first_seen/last_seen, acknowledged/acknowledged_at) and the notification history store's dedup-by-session-id-and-type logic (`server/notifications/store.go`). That schema is a strong template to reuse/mirror for a `backlog_stuck_state` (or similar) durable table, rather than inventing a new shape from scratch.

## 2. Edge cases and failure modes beyond the 4 listed

1. **Flapping / oscillating items** — an item that repeatedly crosses the stuck threshold and then un-sticks (e.g. CI flakes red then green) will spam notifications on every reconciler tick unless the "already notified" state is itself durable and only cleared on genuine resolution, not on every poll. The current in-memory maps already partially guard this, but a durable version must decide: does re-entering "stuck" after a recovery restart the notification, or only after some cool-down period?
2. **Item resolves out from under the tracker** (PR gets merged manually via `gh pr merge` outside the app, or manually pushed, or force-closed) — the persistent "stuck" record must be actively cleared/reconciled on next tick, not just left stale forever. GitHub's Renovate dashboard model (regenerate from source-of-truth each run) avoids this; a naively-appended log does not.
3. **Multiple simultaneous stuck reasons on one item** — e.g. an item is both rework-cap-parked AND has a stale work session (the last auto-respawned session itself went silent). The data model needs to support >1 concurrent reason per item, not a single enum field, or reasons will silently overwrite each other.
4. **Deleted / archived backlog items** — if an item is archived or deleted while flagged stuck, the stuck record becomes orphaned. Needs a cascade or a join that filters on current item existence (mirrors the `OnDelete(entsql.Cascade)` already used for `status_events` edge in `session/ent/schema/backlog_item.go:82-83`).
5. **Clock/timezone skew and "how long is too long"** — thresholds (e.g. `maxWorkSessionStaleness = 2 * time.Hour` in `session/backlog_lifecycle.go:641`) are wall-clock durations computed from `LastProgressAt`/`CreatedAt`. Server restarts, daylight-saving-adjacent bugs, or a paused/suspended host (laptop sleep) could make an item look "stuck" for an artificially long or short window on next tick — worth clamping/logging rather than trusting raw `time.Since`.
6. **GitHub API failures distinguished from "genuinely nothing wrong"** — `ReconcilePRPending` already treats `GetPRStatus`/`IsPRMerged` errors as skip-and-retry-next-tick (`session/backlog_lifecycle.go:824-828, 840-843`), which is correct, but a persistent stuck-UI must not conflate "PR status unknown because GitHub API/auth is failing" with "PR status is healthy" — those need distinct visual states (e.g. a "last checked" timestamp visible per item so a stale check is itself visible).
7. **Repo without `allow_auto_merge`, and repos WITH it** — root cause #1 is specific to repos with `allow_auto_merge: false`; the design must not assume this is universal across all repos this app manages (per `docs/registry` and multi-repo backlog usage), so the "PR green but unmerged" detector should be a value-add signal for every repo, not conditioned on the auto-merge setting having failed.
8. **Bulk/mass-stuck scenario** (e.g. a GitHub outage or CI provider outage stalls 20 items at once) — needs to avoid a notification storm; grouping/rolling up is likely necessary (the frontend already has `groupNotifications` utility in `web-app/src/lib/utils/notificationGrouping.ts` used by `NotificationContext.tsx:384` — reusable pattern).
9. **Race between reconciler tick and a manual user action** (user clicks "re-review" or merges a PR themselves in the same window the reconciler is mid-scan) — precondition-based transitions already guard this elsewhere (`BacklogItemPrecondition{ExpectedStatus: ...}` pattern used throughout `backlog_lifecycle.go`), and the stuck-tracking write path should follow the same optimistic-precondition discipline to avoid overwriting a resolution with a stale "still stuck" flag.

## 3. Likely unstated user needs

1. **Snooze / dismiss for "intentionally paused"** — the requirements explicitly scope out "one-click remediation" but "visibility only" still needs a way to say "I know, stop reminding me for now" without that being a remediation action. This exact primitive already exists for the analogous `/unfinished` worktree view: `DismissWorktreeRequest` / `SnoozeWorktreeRequest` in `web-app/src/app/unfinished/UnfinishedTab.tsx:9-11, 51-75`. The stuck-item feature should almost certainly reuse this dismiss/snooze RPC shape rather than invent a new one — it is the direct precedent in this exact codebase for "visibility without remediation."
2. **Distinguishing "stuck" from "intentionally slow"** — e.g. a large/complex item genuinely still `in_progress` after 3 hours because it's hard, vs. actually hung. The existing `maxWorkSessionStaleness` threshold-based detection (`session/backlog_lifecycle.go:638-696`) already treats this as "notify but don't force-stop" (comment: "Detection + notification only — a slow-but-alive agent should not be force-stopped"), i.e., the codebase has already made the product decision that visibility ≠ verdict. The stuck-item view should preserve that: label items as "flagged" not "broken," and let the human judge intent.
3. **Historical/trend view** — "how often do items get stuck, and is it getting better or worse" is implied by the Success Metric ("Zero silently-stuck backlog items") needing a way to *measure* zero, i.e. some retrospective count. The append-only `backlog_status_events` table (schema at `session/ent/schema/backlog_status_event.go`) already has `from_status`/`to_status`/`triggered_by`/`note`/`created_at` per item — this is very likely sufficient to compute "time spent in each status" and "how many times item X bounced review↔in_progress" retrospectively via a query, without needing a new event-log table. Worth explicitly validating in the plan phase whether a stuck-state table is even necessary beyond a materialized/derived view over `backlog_status_events` + `item_sessions` + `review_verdict`.
4. **Per-item "why" drill-down, not just a flag** — users will want to click into a stuck badge and see the reasoning (mirrors `reconcileStuckReviewItems`'s existing `outcomeDesc` string built from `GetMostRecentReviewVerdictForItem`, `session/backlog_lifecycle.go:619-634` — that human-readable reason string is already being computed for the notification text and should be persisted/exposed as structured data, not just embedded in a notification message).
5. **Actionable escape hatch even under "visibility only"** — even without remediation *actions*, users will expect at minimum a link straight to the relevant PR/session (as `GitHubPRsSection.tsx` already does via `pr.htmlUrl` and `pr.sessionIds`), so "visibility" in practice means "flag + reason + direct link out", not just a status word.
6. **Confidence in "did this actually get fixed"** — because reasons 1–4 are all detected via best-effort polling with silent failure paths (see edge case 6), users will likely want a per-item "last checked at" timestamp so they can trust that "not flagged" means "checked recently and fine," not "we gave up polling this."

## 4. Codebase findings in detail

### 4a. `/unfinished` page — existing model and delta needed

- `web-app/src/app/unfinished/UnfinishedTab.tsx` renders **worktree-level** git state (`UnfinishedWorktree`: uncommitted/ahead/behind), grouped by repo, with filter chips (All/Uncommitted/Ahead/Behind), plus a separate `GitHubPRsSection` showing the user's live open PRs (CI check chip, review-count chip, draft badge) fetched via `GitHubUserService`.
- It already has the exact interaction primitive this feature needs — dismiss/snooze per worktree (`DismissWorktreeRequestSchema`/`SnoozeWorktreeRequestSchema`, `web-app/src/app/unfinished/UnfinishedTab.tsx:51-75`) — scoped to `(repoPath, branch)`.
- **What's absent**: no concept of *backlog item* at all — it's purely git/GitHub state, unaware of `BacklogItemData.Status`, review verdicts, rework-iteration counts, or "why is this stuck." `GitHubPRsSection` shows CI/review chips per PR but does not flag "green and mergeable but sitting unmerged for N days," has no per-item stuck-duration display, and is not cross-referenced to a backlog item ID.
- **Design implication**: this feature is naturally an *extension* of `/unfinished` (new section or new filter dimension: "Backlog: Stuck") rather than a wholly separate page, reusing its dismiss/snooze RPC pattern, its repo-grouping convention, and its chip-based status vocabulary. A new top-level view is also viable but would duplicate the dismiss/snooze plumbing needlessly.

### 4b. Notification system end-to-end

- Backend origin: `events.NewNotificationEvent(sessionID, sessionName, notificationID, notificationType, priority, title, message, metadata)` (`pkg/events/types.go:151-174`) wraps fields into a generic `Event{Type: EventNotification, ...}`.
- `server/services/backlog_notifier.go`'s `EventBusNotifier.Notify` is the adapter the backlog-lifecycle package (`session/backlog_lifecycle.go`, `Notifier` interface at line 22) calls into — it exists specifically because `session` cannot import `pkg/events` (cycle avoidance), so any new stuck-detection code will need to route through this same `Notifier` interface / `EventBusNotifier` adapter, not a new bespoke path.
- **Durability reality check — important correction to the requirements' framing**: notifications are *not* purely ephemeral today. `server/notifications/store.go`'s `NotificationHistoryStore` is a JSON-file-backed store (`loadFromDisk`/`saveToDisk`) with retention enforcement (`enforceRetention`, trims to a max count) and dedup-by-session+type. The frontend's `NotificationContext.tsx` hydrates a persistent `notificationHistory` panel from this backend store via `useNotificationHistory` (`web-app/src/lib/hooks/useNotificationHistory.ts`) — separate from the transient `notifications` (toast) array, which auto-expires after `TOAST_STALE_MS`/`ACTIONABLE_TOAST_STALE_MS` (`web-app/src/lib/notification-policy.ts`). So there is already a durable, restart-surviving notification *log* with a bell-icon panel (`NotificationsNavBadge`, `NotificationPanel.tsx`) — the toast is genuinely ephemeral (5-6 min), but the history panel is not.
- **What upgrading to "persistent" really requires, then**: not a brand-new persistence layer for notifications (one already exists), but converting an **event log** ("a stuck condition was detected at time T") into **derivable current state** ("this item IS stuck right now, for reason X, since time T, still true as of last check"). A capped, append-only JSON log is fine for "did we ever tell the user" but wrong for "is it still true" — a merged PR's old "PR ready to merge" notification doesn't un-flag itself in that store. This is the crux design decision for Phase 3 planning: the stuck *state* needs a queryable, reconciled table (best derived from `backlog_item` + `backlog_status_events` + `item_sessions`, per §4c), while the existing `NotificationHistoryStore`/`NotificationContext` remains the right mechanism for the *alerting* half (reusing `Notifier`/`EventBusNotifier`, `addNotification` vs. `addToHistoryOnly`, and the existing dedup/grouping utilities).

### 4c. Backlog status model and status_events — can detection be derived rather than newly tracked?

- `session/domain/backlog.go` defines the `BacklogStatus` enum and `validTransitions` state machine (idea → refining → ready → in_progress → review → pr_pending → done/archived, with defined backward transitions) plus `TransitionGuard` business-rule checks (AC required, plan required, PR-before-done, etc.). This is the authoritative state machine; any stuck-detection logic should be defined in terms of *time spent in a status* plus *what's linked to it* (sessions, verdicts), not a parallel state machine.
- `session/ent/schema/backlog_status_event.go` — an append-only `backlog_status_events` table (`item_id`, `from_status`, `to_status`, `triggered_by`, optional `note`, `created_at`, indexed on `(item_id, created_at)`) already gives a full audit trail of every transition, including the human-readable "why" via `note` (e.g. "auto-reopened after FAIL verdict" per the field comment). This is highly reusable: "how long has this item been in review" = time since its most recent `to_status = "review"` event; "does it bounce" (root cause #4) = count of review↔in_progress round trips visible directly in this table's ordered history per item — no new tracking needed for that specific signal.
- Crucially, **the detection logic for 2 of the 4 root causes already exists as derived, non-persisted queries**, proving the "derive rather than track" approach works in this codebase today:
  - `EntRepository.FindStuckReviewItems` (`session/storage_backlog.go:519-534`) — pure ent query: status=review AND has a review-role session AND no session with `EndedAt IS NULL` — no extra bookkeeping table required, fully derived from `backlog_item` + `item_sessions`.
  - `EntRepository.FindPRPendingItems` (`session/storage_backlog.go:538-549`) plus `BackfillMissingPRNumbers` (self-healing repair also purely derived from existing fields, `pr_url`/`pr_number` on `backlog_item`).
  - `ReconcilePRPending` (`session/backlog_lifecycle.go:807-890`) already computes live PR health each tick (`IsPRMerged`, `GetPRStatus` → `CIFailing`/`HasBlockingReviews`/`HasConflicts`/`IsClosed`) — root cause #1's "green but unmerged" is a **one-line addition** to the existing `if !prStatus.CIFailing && !prStatus.HasBlockingReviews && !prStatus.HasConflicts { continue }` branch at line 874: today that branch is a silent no-op ("PR is open and healthy — wait for merge"); it needs a duration check (how long has it been healthy-but-unmerged) and a notify call, exactly parallel to the two `reconcileStuck*` functions already in the same file.
  - The rework cap (root cause #2) is already counted from `item_sessions` (`workCount >= maxAutoReworkIterations` at `server/services/backlog_service_triage.go:421,482`) — again a count over existing session rows, not a new counter field.
- **What genuinely can't be derived and needs new durable state**: the *notify-once* bookkeeping itself (root cause #3) — `staleWorkNotified`/`stuckReviewNotified` in-memory maps (`session/backlog_lifecycle.go:119-133`). This is the one piece that's actually missing durable storage today, and per §4b, the natural home is either (a) a new small ent table (e.g. `backlog_stuck_state` with `item_id`, `reason`, `first_detected_at`, `last_checked_at`, `notified_at`, `resolved_at`) that IS the queryable UI's source of truth and doubles as the durability fix, or (b) piggybacking on the existing `NotificationHistoryStore`'s dedup key if its cap/eviction behavior is judged acceptable — (a) is more aligned with "durable, queryable" per the requirements and with the Renovate-dashboard "regenerate current state" pattern from §1, and additionally solves reasons 1 and 4 uniformly (one state table, populated by a superset of the existing `reconcileStuckReviewItems`/`reconcileStaleWorkSessions`/rework-cap/PR-green-unmerged checks) rather than four bespoke in-memory maps.
