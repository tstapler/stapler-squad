## Concerns

- [ ] **`GateDefinition.Config` is an unvalidated JSON blob, undermining ADR-003's closed-execution-surface guarantee.** Task 2.2.1c defines `transition_gates.config` as a generic JSON field with no schema enforcement anywhere in the plan. ADR-003 bounds the gate's *skill identifier* to a pre-registered allowlist, but no acceptance criterion in Story 2.4.4 asserts that a `GateKindCustom` config containing extra keys (arguments, flags, an alternate command field) is rejected rather than silently passed through to whatever invokes the skill. Given requirements.md calls this "the single largest scope-blowout risk in the whole project," the closed surface should be enforced structurally (a typed config, or explicit key-allowlist validation with a test), not left to an unspecified `~5 min` task. — **Recommendation**: add an AC/test in Story 2.4.4 that a config payload with any key other than the allowlisted skill identifier is rejected at save time, not just at invocation time.
- [ ] **An unresolved design question is folded into a leaf implementation task instead of its own decision point.** Task 2.4.4c says "resolve the open Unresolved Question on `StuckReasonGateTimeout` first" inside a ~5-minute coding task. requirements.md explicitly flags this as still open, and the plan's own Unresolved Questions section gives it a named owner and a default recommendation — but nothing forces that decision to actually get made deliberately before `reconcileCustomGateChecks` is written; it can be decided implicitly by whoever picks up the task. — **Recommendation**: promote this to a short, standalone decision step (or ADR addendum) at the start of Epic 2.4, resolved and recorded before Task 2.4.4c starts.
- [ ] **Uniform ~3-5 minute task estimates don't reflect real complexity variance across a Large (3-6 week) project.** Tasks like "Implement DFS-based reachability check from all `IsEntry` stages" (2.6.1b), "Make the diff/worktree/branch-drift pre-checks conditional on `RequiresDiff`" (2.4.3b — a refactor of existing, presumably load-bearing review-gate logic), and "Build the gate checkbox-group with progressive-disclosure per-kind fields" (2.8.2c) all carry the same ~5-minute figure as trivial CRUD-wiring tasks. This flattens the plan's own risk signal — a reader can't tell from the estimates alone which tasks are actually dangerous. — **Recommendation**: either re-estimate the highest-risk tasks (2.4.3, 2.4.4, 2.6) with realistic ranges, or state explicitly that the "~N min" figures are LLM-agent task-sizing units rather than wall-clock estimates, since the plan never says which.
- [ ] **`InvokeCustomGateCheck` has no acceptance criterion for an immediate (non-timeout) spawn failure.** Story 2.4.4's two ACs cover allowlist rejection and sweep-driven timeout detection, but not a skill invocation that errors out synchronously (crashes, missing runtime dependency, malformed environment) rather than hanging. Given the plan's own fail-closed-for-gates rule, this path needs an explicit "blocks the transition, logs Warn" AC and test, not an implied one.
- [ ] **`session/backlog_lifecycle.go` keeps growing without any consolidation consideration.** The file is already large (bouncing-sweep logic alone spans roughly lines 1539-1909 per current source) and this plan adds to it again: a new field (Task 1.4.1a), a replaced hardcoded status check (Task 2.4.3c), and a brand-new `reconcileCustomGateChecks` function (Task 2.4.4c). No task considers extracting responsibilities from this file, continuing to accrete onto a file this repo's own hotspot-analysis guidance would flag. — **Recommendation**: at minimum, note this as a deliberate deferral in the plan rather than an unconsidered omission; consider carving `reconcileCustomGateChecks` and the gate dispatch logic into a new file from the start (Epic 2.4.4c's own "Files" line already proposes `session/backlog_lifecycle.go` as the destination — redirect it to a new `session/backlog_lifecycle_gates.go` instead).

## Minors

- requirements.md's "Users / Consumers" and Scope sections both explicitly name `web-app/src/lib/hooks/useBacklogService.ts`'s "frontend transition table" as needing updates, but plan.md never mentions this file in any epic/story/task. Source inspection shows the hook already exposes a server-authoritative `allowedTransitions?: string[]` field per item rather than a hardcoded table (`web-app/src/lib/hooks/useBacklogService.ts:195-201`), so the requirement may already be satisfied by prior work — but the plan should say so explicitly rather than silently dropping a named file, so an implementer doesn't assume it was simply missed.
- Epic 2.1's bypass-callsite line numbers (`backlog_service_lifecycle.go:1105`, `backlog_service_sync.go:151`) were verified against the current repo and are accurate, but differ from the line numbers requirements.md cites for the same call sites (`:801`, `:121`). Harmless (source has moved since Phase 2 research), but the plan doesn't note that it re-verified these lines at plan-writing time, leaving a reader to wonder which document is stale.
- Story 1.3.1's cache-fallback acceptance criteria cover a cache miss (no matching row) but not a genuine DB error during `GetByStageAndMode`/cache refresh (e.g., a connectivity outage). The plan says it "mirrors `CachingPipelineEngine` exactly," which likely already handles this, but no explicit AC/test confirms `LivenessEngine` fails closed to `DefaultLivenessEngine` — rather than propagating an error into the periodic sweep — when the DB itself errors as opposed to simply having no matching row.
