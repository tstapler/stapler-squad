# Pre-mortem: backlog-custom-workflow-stages
**Date**: 2026-09-03

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Epic 2.1's "bypass-callsite audit" only re-routes the two already-known `CanTransitionBacklog` call sites, not the other `BacklogStatus`-exhaustive/whitelist sites requirements.md itself names (e.g. `server/mcp/tools_backlog.go`'s "status whitelists") — a custom stage silently breaks or is rejected by every unaudited site once `ConfiguredWorkflowEngine` ships. | An MCP tool call, e2e fixture, or dashboard grouping starts erroring or silently mis-bucketing items the moment the first custom stage is created — not at Phase 2 merge time, but whenever an operator actually uses the new capability. | Turn Epic 2.1 into a repo-wide `grep`/`ast-grep` sweep for `BacklogStatus` literal comparisons/switches (not just the two named call sites) before Epic 2.2 starts, and add its findings as additional blocking tasks in Epic 2.1, not an unscoped "the two known ones." | P1 |
| 2 | The recommended "disable, don't delete" operator workflow (research/ux.md §4, echoed in Story 2.8.1's toggle) lets an operator disable a transition edge with no graph-validator check for whether that edge was the last legal outgoing path for items currently sitting on its source stage — Epic 2.6's reachability validator is only exercised (in its ACs and tests) against stage/transition *creation*, never against disabling an existing edge. | A live item silently stops appearing in `AllowedTransitions` for its current stage with no warning at disable-time; the operator only discovers it when the item stalls and someone manually inspects it. | Add an AC + test to Story 2.6.1/2.7.2 requiring the graph validator to run on `UpdateStageTransition(enabled=false)` too, checking reachability/outgoing-edge-count against the *current live item distribution*, not just the static graph shape. | P1 |
| 3 | `StageConfigSnapshot` (Epic 2.5) only guarantees audit-trail/history-rendering immunity, not gate-evaluation-input immunity — `PendingGates`/`InvokeCustomGateCheck` read live `GateDefinition.Config` at evaluation time, so editing a gate's config (e.g. flipping `RequiresDiff`, swapping a custom-check's skill) while a transition attempt or an in-flight custom check is outstanding changes semantics mid-flight, and `GateSatisfactionRecord` carries no config-version stamp to detect the mismatch. | A previously-recorded human approval or in-flight custom-check verdict is later interpreted against a materially different gate config than the one it was actually satisfied/spawned under, with no log or UI signal that this happened. | Add a `config_version` (or snapshot hash) field to `GateSatisfactionRecord` and an AC requiring `PendingGates` to flag (not silently accept) a satisfaction record whose stamped version doesn't match the gate's current config. | P2 |
| 4 | Three independently hand-copied copy-on-write caches (`pipelineModeCache` → `livenessCache` → `stageConfigCache`, the third explicitly described in Task 2.3.1b as "copy `pipelineModeCache`'s structure *again*") each invalidate independently, but Epic 2.8.2's stage-edit form fires separate RPCs for stage/transition/gate edits in one submit — no task tests the window where one cache has refreshed and a sibling cache hasn't, producing a `PendingGates` read that mixes old and new config. | A gate checklist briefly (or, under load, not-so-briefly) shows a transition as passable under a config combination that never existed as a single consistent save. | Add a cross-cache consistency test exercising a multi-entity edit (stage + its transitions + a gate in one form submit) and assert `PendingGates` never observes a torn read; consider a single invalidation-generation counter shared across all three caches instead of three independent ones. | P3 |
| 5 | Phase 2's `ConfiguredWorkflowEngine` cutover in `server/dependencies.go` is a single one-line, all-items-at-once swap ("full rollout on merge... single-operator tool, no cohorts") validated only by zero-regression tests run against freshly-seeded, clean-room ent test data — never against real production `backlog_items` rows, including the very `orphaned_triage`-stuck items this project exists to fix, which may carry edge-case field combinations the seed migration never exercises. | Every item's transition legality starts failing (or a specific subset with an unusual field combination does) immediately after the Phase 2 deploy, with no canary window to catch it before it's global. | Before flipping `server/dependencies.go`'s construction, run `ConfiguredWorkflowEngine` in shadow mode against a snapshot of real production `backlog_items` (compare its `CanTransition`/`AllowedTransitions` output to `DefaultWorkflowEngine`'s for every live item, not just the 9 synthetic `domain.ValidTransitions()` pairs) as an explicit pre-merge task, not just the existing synthetic-data test. | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — **Resolved in plan.md**: Epic 2.1 renamed to "Repo-wide `BacklogStatus`-literal audit" and rescoped. New Story 2.1.3 consolidates the duplicated terminal-status OR pattern (8 files/12+ call sites) behind one `IsTerminalStatus`-equivalent check; new Story 2.1.4 re-routes `tools_backlog.go`'s `validBacklogStatuses` whitelist through the engine and requires explicit scope-boundary doc comments on the sites confirmed legitimately out of scope.
- [x] Failure #2 — **Resolved in plan.md**: Story 2.6.1 and Story 2.7.2 each gained a new acceptance criterion (with Given-When-Then examples using a `"design-review"` custom stage) plus tasks 2.6.1e/2.6.1f and 2.7.2e/2.7.2f requiring the graph validator to reject disabling a transition edge that would leave a live item's current stage with zero enabled outgoing transitions — not just checked at definition time.
