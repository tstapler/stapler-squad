# Pre-mortem: plan-feedback
**Date**: 2026-09-14

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `triggerTriage` (call 3) internally moves the item `ready→idea` (its own atomic CAS at `backlog_service_trigger_triage.go:249-257`) *before* it can fail on a later step (artifact-dir creation, headless pool unavailable, prior-result lookup) — so on that failure the item lands at status `idea`, not `ready`, and the plan's promised recovery UI ("`PlanVerdictBox` renders `changes_requested` — 'Revisions requested' card with 'Regenerate Plan with This Feedback' as the recoverable retry path", Epic 2.2 AC) never renders, because that card only shows at `ready` with a rejection reason. | Operator submits feedback, gets an error toast, reloads the item detail view, and finds no "Revisions requested" card, no obvious retry button, and a stray artifact-dir/headless-pool error — the item looks stuck at `idea` with no visible next action. | In Epic 2.2's AC and Story 3.1.1, explicitly test a `triggerTriage` failure that occurs *after* its internal ready→idea transition (e.g. mock `headlessPool` as nil, or force `os.MkdirAll` to fail) and assert what the UI actually shows in that branch — not just the currently-tested "transitionStatus/rejectPlan succeeded, triggerTriage rejected" case, which implicitly assumes triggerTriage failed *before* step 3b. | P1 |
| 2 | `stopLiveWorkSessions`'s teardown failure (`StopSessionByUUID` errors) is logged and swallowed, and the transition is *not* rolled back — this is the CONCERN already flagged as open, with zero test coverage. The submit still shows "Feedback sent — retriage started," so the operator has no signal that the old session is still alive and now running concurrently with the new triage/work against a plan that's been superseded. | Two tmux sessions writing to the same worktree/branch at once — conflicting commits, a confused diff, or a second session's output overwriting the first's — discovered only when the operator notices duplicate/conflicting work, not at submit time. | Add the missing test for the `StopSessionByUUID`-errors branch (assert the transition still succeeds per current design, per the observability plan), and additionally surface the teardown failure to the operator — e.g. include it in the success toast or `load()`'s result — rather than only a backend `WarningLog`, so a leftover session is visible in-UI instead of silent. | P1 |
| 3 | The same feedback string is written into three different roles that don't share a grammatical or audience contract: `overrideReason` (an audit-trail justification for bypassing the PASS-verdict guard), `PlanRejectionReason` (rendered as "why this plan was rejected," a retrospective framing), and the `TriggerTriage` prompt (a prospective instruction to the agent). For a `done`-status item — explicitly in scope per `CAN_SEND_BACK_READY` — "Revisions requested" framing is nonsensical for a plan that already shipped, and nothing in the plan addresses what happens to an already-merged PR/branch when a `done` item is forced back through `ready→idea→` a fresh triage run. | An operator uses the box on a `done` item (the UI offers it — same eligibility set as today), gets a "Revisions requested" card for a plan that's already merged, and a new triage run starts with no acknowledgment of the shipped PR — producing a redundant or conflicting plan. | Add an explicit acceptance criterion (and test) for the `done`-source case: either exclude `done` from the new box's `visible` condition (a `CAN_SEND_BACK_READY` narrowing, flagged for product sign-off) or add copy/logic addressing the already-shipped-PR case; at minimum, audit-log the override reason and the retriage instruction as visibly distinct fields rather than reusing the identical string for both. | P2 |
| 4 | `activeWorkSessionCount` is computed once at item load (`BacklogItemDetail.tsx:249`) and passed into `SendBackFeedbackBox` as a static prop — it can go stale between page load and submit in either direction: a session that finished after load still shows the "will stop it" notice (false positive, mildly confusing), or a *new* session spawned after load gets silently killed by `stopLiveWorkSessions` (which re-queries the DB at submit time) with zero warning shown to the operator (false negative — the actual "surprising the operator" failure mode). | An operator, having just restarted a work session moments before submitting feedback (no page reload in between), sees no active-session warning, submits, and the fresh session is torn down without any notice ever appearing — discovered only when they check on the session and find it gone. | Re-derive (or re-fetch) `activeWorkSessionCount` immediately before rendering the notice/enabling submit, or fetch it synchronously as part of opening the form, so the warning reflects server truth at decision time, not page-load time. | P2 |
| 5 | Retrying after a partial failure (transitionStatus succeeded, `rejectPlan` or `triggerTriage` failed) can double-apply the feedback: `handleSendBackWithFeedback` unconditionally calls `rejectPlan(item.id, feedback)` again on retry even if it already succeeded and only `triggerTriage` failed the first time — and `TriggerTriage` itself may now reject the retry outright if a prior partial attempt left `triageInFlight` set or the item at `idea` (mid-transition) rather than `ready`, since `TriggerTriage`'s own status guard only accepts `idea`/`ready` starting statuses and its 3b step requires `ExpectedStatus: ready`. The plan's Story 2.2.1 ACs assume a clean, from-`ready` retry but never test a *second* submit attempt after a first partial failure. | Operator's first submit fails at the `triggerTriage` step; they see "Revisions requested," retype nothing (text is preserved), and click submit again — the retry's `transitionStatus` call now targets an item that's no longer at the CAS-expected status/timestamp (mutated by the first attempt's partial success), or `triggerTriage` returns `CodeAlreadyExists`/`CodeFailedPrecondition` because the in-flight guard or the ready-guard didn't reset cleanly, leaving the operator stuck retrying a call that can never succeed without a full page reload. | Add a test that simulates a failed submit followed by an immediate second submit from the box (without a manual page reload) and asserts it either succeeds or fails with an error the operator can act on — not a confusing precondition/in-flight error; consider having `handleSendBackWithFeedback` re-derive its starting point from a fresh `load()` before each of the three calls, or skip `rejectPlan` if a rejection reason already matches. | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — Resolved in plan.md: `handleSendBackWithFeedback` (Task 2.2.1a) now re-fetches the item via `getBacklogItem` on a `triggerTriage` failure to learn its real post-failure status, tags the error with `itemStatusAfterFailure`, and `SendBackFeedbackBox` (Task 2.1.1b) renders a distinct `idea`-status recovery message instead of assuming `ready`. Story 2.2.1's ACs and `design/ux.md` Surface 7 were updated to cover this case explicitly, with a citation to the exact `ready→idea` CAS (`backlog_service_trigger_triage.go:249-260`).
- [x] Failure #2 — Resolved in plan.md: Task 1.2.1b's `mockSessionStopper` gained a `stopperErr` injection field, and Task 1.2.1c adds `TestTransitionBacklogItemStatus_should_StillTransition_When_LiveSessionTeardownFails`, asserting the transition still completes and the stop is still attempted despite the injected error. The Observability Plan documents an explicit, justified choice to keep the success toast unqualified on a teardown failure (best-effort semantics; `hasActiveWorkSession` makes a leftover session self-limiting/discoverable) rather than the pre-mortem's suggested in-toast surfacing — a reasoned alternative, not an unaddressed gap.

## Summary

5 failure modes: 2 P1, 3 P2, 0 P3.

Top failure mode: `TriggerTriage`'s own internal `ready→idea` transition (a pre-existing, unrelated-to-this-feature CAS at `backlog_service_trigger_triage.go:249-257`) can commit *before* a later step in the same call fails, so a `triggerTriage` failure after that point leaves the item at `idea` rather than `ready` — silently breaking this plan's promised failure-recovery UI ("Revisions requested" card at `ready`), which was only tested for failures that happen *before* that internal transition.
