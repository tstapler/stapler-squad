## Concerns (fix before the task named in "Gate")

- [ ] **N32. The `tmuxInputSender` seam makes check (d) vacuous for the capture-pane site, and the real sender is not exempt.** VERIFIED text, plan.md:1820 and :1849. Task 5.1c-a makes `handleCapturePaneInput` and `handleCapturePaneResize` call `sender.SendInput` / `sender.Resize` obtained through the `TerminalWriter`, and keeps `sendInputToTmuxWithRetry` and `resizeExternalCapturePaneSession` "unchanged" behind one real implementation. Check (d) fires on a function that calls a member of its set. After the change `handleCapturePaneInput` calls no member, so it is no longer checked: a later edit that obtains a sender from `capturePaneStreamParams` directly (not from the writer) and types from a read-only attach passes (a) through (d). The real implementation's method does call the set members, has no `TerminalWriter`, and is not one of "the definitions of those three helpers", the only stated exemption (plan.md:1849), so as written check (d) either fails on the real tree (T-RO-44, the positive control, would be red) or the implementer adds an unlisted exemption. Both are plan-text gaps, not design flaws. — **Recommendation**: add the `tmuxInputSender` methods `SendInput` and `Resize` to check (d)'s set, name the real implementation's two methods as the exempt definitions (by name, pinned like the other by-name exemptions), and add a negative control: a handler that calls `params.sender.SendInput` without referencing a `TerminalWriter` fails R1/R2. Keep T-RO-48 as the behavioral proof. Gate: Task 5.1c-a, Task 5.1d-a.
- [ ] **N33. The plan invents `SSQ_SESSION_UUID`; the repo already injects `STAPLER_SESSION_UUID` into every local tmux session, and that settles the "INFERRED" inheritance question for local sessions.** VERIFIED: `Instance.buildExtraEnv` (`session/instance_tmux.go:693-703`) adds `STAPLER_SESSION_UUID=<uuid>` and `wireTmuxSession` passes it with `SetExtraEnv` (`:759`), i.e. tmux `new-session -e` (`session/tmux/tmux_session_start.go:638-643`); `claudeSettingsEnvOverrideArgs` (`instance_tmux.go:705`) additionally carries the same keys through Claude Code's `--settings` env block. The plan (Story 5.6 hook bullet (a), Task 5.6n, Spike 1.3g h8) says "`SSQ_SESSION_UUID` set when the session's tmux environment is created" and leaves hook-process inheritance INFERRED. A second variable for the same value is a parallel mechanism: two names for one identity, and `tmux_ownership.go:40-48` already parses the first. Reusing the existing one removes a new setting site and a new place for them to diverge. Remote (ssh) sessions get neither, which matches the plan's "remote is not proofed". — **Recommendation**: use `STAPLER_SESSION_UUID` in the command, the T-RP-73 matrix and ADR-010 d4; keep Spike h8 for the one thing still unverified (that a Claude Code hook subprocess sees the pane's environment, not that a variable exists). Gate: Task 5.6n, Spike 1.3g h8.
- [ ] **N34. Three call-site facts the 5.6n signature plan misses, one of which would silently turn Reply off.** (a) VERIFIED at `origin/main`'s caller list and at the checkout: the only production `RemoveHooksConfig` call (`backlog_service_triage.go:1115`) removes only `HookGitDriftCheck`, on every non-autonomous spawn (`inst.UUID` there is the new session). The plan says `RemoveHooksConfig` "deletes that session's proof file when it removes the entry"; implemented per call rather than per hook name, a manual spawn onto a reused worktree deletes the proof file of a session whose `PermissionRequest` entry is untouched, and Reply degrades to `no_proof` with a "restart the session" card that is wrong. The deletion must be keyed to `HookPermissionApproval` being in the removed set. (b) `InjectHooksConfig` has two more production callers that the plan's signature section does not name (`server/mcp/tools_lifecycle.go:243`, `server/mcp/tools_github.go:273`); they run `buildHookCommand` for the same URL entries without a session UUID. Under the new "replace an entry that lacks the proof branch" rule they must produce the same command (the branch reads the environment at run time, so they can) and must not write or delete a proof file. (c) The plan says the proof file is rewritten "at session start or resume" but names only `session_creation_pipeline.go:313`, which runs at creation. Pause/resume and service restart do not pass through it. This is harmless while the secret is stable (the file persists), but it makes the "rotated secret reaches a running session" promise (plan.md:2036 (b)) untrue for any session not re-created; name the resume call site or drop the claim. — **Recommendation**: add one sentence per item to Task 5.6n and a T-RP-73 row for (a). Gate: Task 5.6n.
- [ ] **N35. The "fail-open" hook command is fail-open only when local-token auth is off, and the new replace-in-place rule is silent about the existing `upgradeHookAuth` path.** VERIFIED at `origin/main` (`git show origin/main:server/services/hook_injector.go`, lines ~382-415): `buildHookCommand` appends `hookAuthArg()` (`-H @'<token header file>'`) to the same curl, and `upgradeHookAuth` rewrites an already-injected entry in place to add it. ## Minors

- m20. `flag_change` readers order by `(boot_ts, seq)`. `boot_ts` is wall-clock; a backward clock step across a restart, or two process starts within the timestamp's resolution (a crash loop), misorders boots. A persisted monotonic boot counter (incremented when the sink opens) orders them without trusting the clock; `boot_id` stays as the identity. The residual windows of the old m16 are otherwise accepted as stated (indeterminate, resolved by reading the config).
- m21. Mixed code references. The repair log verifies against `origin/main` `a91e7e46a`; this checkout is older. Line numbers cited for `hook_injector.go` (`:386-409`, `:380`) match neither ref for `buildHookCommand` (the checkout has no `hookAuthArg`; `origin/main` shifts the lines). Task 5.1d-0 and 5.6n should re-derive them at implementation time; the plan already does this for the guard table.
- m22. The probe is allowed to satisfy `failure_delivered_while_on >= 1` alone (carried from pass 6). Acceptable if the Stage 3 text says so; the plan discloses it in the PR text. Confirm Stage 3 says it too, not just the PR body.
- m23. N31's fix keeps 5a behind 2a-2, which gives the lease the gate chain's calendar (R3's first step now waits on the audit sink). Decided in the plan; it is the price of the audited flip. If the lease is wanted earlier, the alternative is the fallback record only until 2a-2 merges, with T-WL-11's audit assertion deferred.

## Attacks that did not produce a finding

- **Positional-parameter form and path injection**: the UUID is read from the environment into a path (`.../hook-proofs/"$VAR"`). A hostile value could traverse, but the only party who controls the pane environment is the agent, who is already inside the stated rail and can read the 0600 file anyway. Not a new hole.
- **Shared-root attribution (N29)**: with the verified UUID as attribution, a stale first-session title in a shared `settings.local.json` cannot mis-attribute a question. A forged proofless request can still supersede (stated, safe direction).
- **`terminal_write_lease` off as an escape hatch**: off removes serialization only; read-only enforcement comes from the capability (`TerminalWriter`/`HeldLease`), not the lease, so turning it off cannot open a hidden session to writes. Reply becomes `NOT_SENT` as stated.
- **PR graph**: acyclic by my edge walk (see the N31 row).
- **Probe reachability**: `shouldNotify` pushes only urgent or approval priority, so a medium-priority probe does not reach push or Slack (VERIFIED in pass 6, unchanged).
