## Blockers

- [ ] **B1. The capture-pane input path types through `sendInputToTmux`, a direct `tmux send-keys -H` subprocess that no remaining check classifies and that the planned per-site test cannot observe.**
  - **Issue**: VERIFIED route. `handleCapturePaneInput` (`server/services/connectrpc_websocket.go:3350-3366`) takes an `Input` frame and calls `sendInputToTmuxWithRetry` -> `sendInputToTmux` (`:3532-3560`), which runs `safeexec.CommandContext(..., tmux.Binary(), "send-keys", "-t", <session>, "-H", <hex bytes>...)`. It calls none of the check (c) primitive set (`SendKeys`, `SendKeysN`, `WriteToPTY`, `TapEnter`, `SubmitDriverContent`, `SubmitContentWithEnter`, `SendKeysWithTimeout`, `SubmitReplyOnce`, `SendCommandImmediate`, `changeDirectory`) and none of check (d)'s UI-stream list (`WriteToPTY`, `SendInputViaControlMode`, `ResizePTY`, `ResizePTYContext`, `SetWindowSize*`, `RequestResize`, `ForwardScroll`). The name `sendInputToTmux` appears nowhere in the plan, the ADRs or `validation.md` (grep over `project_plans/` returns only unrelated "send-keys toolbar" UX text). The route is reachable today for a hidden, managed session whenever `routeMainTerminalStream` picks capture-pane polling, that is with `STAPLER_SQUAD_USE_CONTROL_MODE=false` (documented in the repo `CLAUDE.md` as a supported mode) or `IsManaged == false` (`connectrpc_websocket.go:1031-1049`); the companion-shell path also reaches it (`:1007`). Today there is no guard at all; after the plan it depends on Task 5.1c-a threading `writer` into `capturePaneStreamParams`, and then:
    1. Check (c) cannot see it (not a primitive-set member) and check (d) cannot see it (not a list member, and `handleCapturePaneInput` calls no listed primitive), so deleting or bypassing the gate in that one function, or adding a fifth caller of `sendInputToTmux` in a function with no `TerminalWriter`, passes every remaining check. The other three callers of `sendInputToTmux` (`:1414`, `:2150`, `connectrpc_websocket_shell.go:304`) sit next to a `SendInputViaControlMode` call, so check (d) covers them only by coincidence.
    2. The planned test cannot prove the site. T-RO-01 and Task 5.1a use a "fake tmux target" that "counts bytes and resize calls". `sendInputToTmux` is a package-level function that execs the tmux binary; there is no injection seam (VERIFIED: no test file under `server/` references `sendInputToTmux` or `handleCapturePaneInput`). A fake target that never sees the exec reports 0 bytes whether or not the guard exists, so the `:3337` row of T-RO-01 can pass vacuously.
  - **Recommendation**: (1) add `sendInputToTmux` and `sendInputToTmuxWithRetry` to the check (d) UI-stream primitive list (so every caller needs a `TerminalWriter` presence and use) and to the check (c) primitive set; (2) name the site in Story 5.1, ADR-005 decision 2 and the Story 5.1d table; (3) in Task 5.1c-a, put the exec behind a package-level seam (an injectable `tmuxInputSender` func or interface on `capturePaneStreamParams`) and make T-RO-01's capture-pane row assert 0 calls on that seam for a hidden attach and 1 for a visible one; (4) add a negative control to T-RO-12: a fixture handler that calls `sendInputToTmux` without a writer must fail check (d). Gate: Task 5.1c-a and Task 5.1d-a.

## Concerns (fix before the story named in "Gate")

- [ ] **N29. The hook proof is one file per rootDir for a per-session UUID, so it mis-binds whenever two sessions share a root, which is the normal case for hidden review sessions.** VERIFIED: `SpawnReviewSession` creates a directory session on `item.RepoPath` (`session_service_diagnose.go:53-60`), and `InjectHookConfig(instanceRootDir, title)` writes `<rootDir>/.claude/settings.local.json` (`session_creation_pipeline.go:313`); `hookAlreadyPresent` keeps an existing entry for the same URL (`hook_injector.go:386-409`), so the first session to inject in a directory fixes the `X-CS-Session-ID` title for every later session there, and `RemoveHooksConfig` has one production caller, the drift hook (`backlog_service_triage.go:1115`). Task 5.6n makes the proof file-form entry "untouched" and rewrites the headers file `<rootDir>/.claude/ssq-hook-headers` "on every injection", so after the second session in a directory the file holds the latest session's `<uuid>.<proof>` while every earlier session's hooks still carry their own (or the first session's) title. Effects: (a) a hidden review session's hook sends (stale or first-session title, another session's UUID proof); the rule "resolve by the proof's UUID and require it equal the attributed instance" then fails, so Reply is silently unavailable for exactly the session class it was built for; (b) or, if attribution follows the proof UUID, session A's question registers under session B's UUID and supersedes B's genuine pending question (fail-safe, because the live-fingerprint promotion in Story 5.6 never confirms it on B's pane, but wrong); (c) the closed cause set has no value for a UUID/title mismatch, so it is counted as `bad_proof` and the card tells the operator to "restart the session", which cannot fix it; (d) T-RP-76 ("stays valid after a rename") implies the proof UUID overrides title attribution but the plan never says so, and a rename already breaks the title header today (`SetTitleDirect`, `session_service_update.go:56`); (e) the headers file is a new untracked file in the worktree or repository with a bearer credential in it, and the plan adds no ignore entry for it (INFERRED: Claude Code excludes `settings.local.json`, not other files under `.claude/`), so an agent that runs `git add -A` can commit and push it. — **Recommendation**: key the proof file by session UUID and keep it outside the worktree, for example `<config dir>/hook-proofs/<uuid>` (0600), and have the hook command read the UUID from the session environment (`-H @$HOME/.stapler-squad/hook-proofs/$SSQ_SESSION_UUID`, with the variable set in the tmux session at start); state in Task 5.6n that a valid proof's UUID is the attribution (title is ignored when a proof verifies); add cause `uuid_mismatch` and distinct card copy; add a T-RP row with two sessions sharing one rootDir.
