## Concerns

### Guard set (Story 5.1d, Task 5.0d)
- [ ] **C51 Check (c)'s interface-call rule and the ratelimit row contradict each other, so the positive control would fail on the real tree (Story 5.1d check (c) "Interface calls", pinned table `acquirer` row, T-RO-44).** The text says interface calls are matched by method name and signature against `*Instance`'s method set, and the same table row says the manager's own call `manager.go:284` "goes through the interface and is not a row". `(*Manager).sendRecoveryInput` calls `SessionAccessor.WriteToPTY(data []byte) (int, error)`, which matches `Instance.WriteToPTY`, so under the stated rule it is an unlisted caller of a primitive-set member and T-RO-44 fails on day one (the NB6 failure shape). Fix: either add a row for `(*Manager).sendRecoveryInput` with kind `receiver-via-wrapper` and the reason "the lease is taken by the `session`-package wrapper that implements the interface", or exempt the `ratelimit` package by name; and say which, since the pinned-table-derivation spike (Task 5.1d-0) will hit it either way. Also note that `WriteToPTY` is not a lease-typed primitive (only `SubmitDriverContent`, `SubmitContentWithEnter`, `SendKeysWithTimeout`, `SubmitReplyOnce` and `steerAuthorized` take `*HeldLease`), so the wrapper's acquire-then-write is held in place by the table and `T-RO-45`, not by the compiler; say so in Story 5.0's "type signature makes a missing lease a compile error" sentence.

### Sequencing
- [ ] **C52 PR 5 (the 100%-read-only stream guarantee) is transitively gated on Spike 1.3 through PR 2a-1 (PR table rows 2a-1 and 5, Task 2.6d).** The PR 5 row says "needs only PR 2a-1 ... no Spike 1.3g", but the PR 2a-1 row says "Gates on Spike 1.3", and the only thing PR 5 takes from it is Task 2.6d (the `sinkguard` tag and `make test-delivery-guards` target). So the stream guarantee waits on a spike that has not run and has nothing to do with it, which defeats the point of the C47 split. Move Task 2.6d (Makefile target plus an empty tagged test file) into PR 1c or a tiny PR 1g that depends on nothing, and change PR 5's prerequisite to that; Story 2.6's own tests keep living in 2a-1. Not a blocker: the ordering is satisfiable, it just defers the guarantee.

### Audit ordering (Task 2.8h, Story 2.11)
- [ ] **C53 "True previous value" and rollback-by-delete are specified in two different PRs, and PR 5a ships a default-on flag between them (Task 2.8h in PR 2a-2, Story 2.11 in PR 2e, PR 5a).** VERIFIED `UpdateFeatureFlag` reads `previousEnabled := cfg.GetFeatureFlag(name)` (`feature_flag_service.go:407`), and `GetFeatureFlag` returns `false` for an absent key (`config/config.go:1776-1781`); the rollback at `:428` writes that `false` back as an explicit value. Task 2.8h promises the "true previous value" and the Story 2.11 AC (plan line 1098) fixes the rollback by deleting an absent key, but PR 2e does not gate PR 5a or PR 5u, and `terminal_write_lease` and `hidden_session_readonly_guards` are default **on**. Without the fix a first flip of either flag records `previous=false` (wrong) and a controller failure persists an explicit `false`, i.e. leaves the safety flag off. Fix: put the "previous value from `GetFeatureFlagOverride` plus the registered default, rollback by delete when the key was absent" change in Task 2.8h (PR 2a-2), which PR 5a and PR 2e both already depend on, and have T-RP-79 assert it for a default-on flag.
- [ ] **C54 `boot_ts` is a wall-clock value, so `(boot_ts, seq)` ordering breaks if the clock steps back between restarts (Task 2.8h boot-id bullet, T-RP-79).** Low probability, high confusion in an audit trail. Persist a monotonic boot counter next to the audit file (or in `config.json`) and order by `(boot_counter, seq)`, keeping `boot_ts` as a label. Nit-sized if the operator accepts the clock assumption; say so either way.

### Test seam and hook plumbing (Story 5.1, Task 5.1c-a, Task 5.6n)
- [ ] **C55 The `tmuxInputSender` seam is specified as a params-struct field, but three of the five `sendInputToTmux` callers are not in `capturePaneStreamParams` (Task 5.1c-a, Story 5.1 AC).** VERIFIED `capturePaneStreamParams` (`connectrpc_websocket.go:3226-3237`) holds `stream`, `instance`, `snap`, `cpt`, `streamer`, channels and the scrollback manager, and no sender; `handleCapturePaneInput` and the resize helper take it, but the fallbacks at `:1414`, `:2150` and `connectrpc_websocket_shell.go:304` are inside other functions with other params structs. The AC says the seam covers "the shell and fallback sites" without naming where the field lives for them. State the one place the sender comes from (for example a field on the service that all three params structs copy) and make T-RO-01's per-site rows assert 0 seam calls at each of the five call sites, not only capture-pane. `handleCapturePaneInput` also checks `p.snap.Permissions.CanSendCommand` today; keep that as a separate, additional condition so the hidden-session guard is not conflated with it.
- [ ] **C56 `SSQ_SESSION_UUID` is set "in the session's environment" at creation only, but the session environment is built at several start paths (Task 5.6n, Files list).** VERIFIED the tmux environment is injected through `TmuxSession.ExtraEnv` / `-e` at `new-session` (`session/tmux/tmux_session_start.go:221-226`) and callers append to `sess.ExtraEnv` at several sites in `session/instance.go` (`:1641`, `:1648`, `:1785`, `:1792`, `:1942-1952`: start, resume and restart paths). The plan's file list names `session_creation_pipeline.go` for the env var, so a paused-then-resumed or restarted session can lose it and degrade to `no_proof` for good (fail-open, so only Reply is lost, silently except for the cause label). Set the variable once where the `TmuxSession` is constructed from the `Instance` (one helper used by every `ExtraEnv` site) and add a test that start, resume and restart each produce it. Spike 1.3g h8 already covers hook-process inheritance; this covers the producer side.
- [ ] **C57 Tmux server restarts and `--tmux-keep-server` mean live panes keep their original env, so the proof file rotation story is only half true (Story 5.6 hook bullets (b), (f)).** Bullet (b) says "a rotated secret reaches a running session ... the hook reads the file on each run", which holds only for sessions whose pane already has `SSQ_SESSION_UUID` and whose hook command already has the file form; (f) covers pre-proof sessions. State the third case explicitly (pane has the env var but its settings entry predates the file form: the entry is replaced at the next injection, but a running agent that snapshots hooks at start keeps the old command) so the operator is not told rotation is a revocation tool for every live session. INFERRED: hook snapshot at agent start, as already stated; Spike 1.3g h8 settles it.
