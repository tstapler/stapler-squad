## 1. Existing hidden-session gates (per-channel; this is the bug class)

| Producer / channel | Hidden handling | Evidence |
|---|---|---|
| Review-queue notification (`OnItemAdded`) | Suppresses only `TaskComplete`/`Idle`/`Stale` by **reason**; Error/TestsFailing pass | `server/review_queue_manager.go:442,449` (VERIFIED) |
| Hook path `SendNotification` | Suppresses only `priority == LOW` for hidden; resolves hidden via poller `Snapshot().Hidden`, fallback to stored `d.Hidden` | `server/services/notification_service.go:106,125,138-145` (VERIFIED) |
| Rate-limit detect/recover, cold-restore | Skips all notifications when `inst.Hidden` (raw field read, not `Snapshot()`) | `server/services/session_service_events.go:76,193,234,252` (VERIFIED) |
| Autonomous "complete" notifier | `if !inst.Hidden` | `server/services/autonomous_orchestration_service.go:619` (VERIFIED) |
| **Push subscriber, status-change ("Session Completed")** | **No Hidden check.** Fires for any `FieldStatus` transition to `Stopped` | `server/push/subscriber.go:157-190` (VERIFIED; `grep -c -i hidden` on the other producer files below = 0) |
| Push subscriber, inline `EventNotification` | Only urgent-within-1h or APPROVAL_NEEDED; no Hidden check, event has no hidden info | `server/push/subscriber.go:122-142,193-226` (VERIFIED) |
| History store subscriber (`server/notifications`) | Records every `EventNotification` with an ID; no Hidden check | `server/notifications/subscriber.go:80-90,175-206` (VERIFIED) |
| WatchSessions stream | Drops events where `event.Session != nil && event.Session.Hidden`. **`EventNotification` has `Session == nil`, so notification events for hidden sessions pass through to toasts** | `server/services/session_service_watch.go:38,127`; `pkg/events/types.go:344-362` (NewNotificationEvent sets no Session) (VERIFIED) |
| No Hidden check at all (grep -c = 0) | stale_session_notifier, approval_handler, session_service_update (steer-sent), backlog_service_stuck/verdict_steer/pr_fix_steer, quota_gate, capacity_monitor, memory_pressure_notifier | `grep -c -i hidden` (VERIFIED) |

Structural conclusion (INFERRED, strongly supported): the `events.Event` for notifications carries only `SessionID`/`Context` (name), not a Hidden flag (`pkg/events/types.go:344-362`). A subscriber-side single gate needs a `SessionID -> Hidden` lookup (Snapshot via poller/storage, as `SendNotification` already does at `notification_service.go:98-128`) or producers must stamp the event. Best choke point: gate at EventBus publish (wrapper in front of `Publish` for `EventNotification`/`EventSessionUpdated`) or a shared `isHidden(sessionID)` consulted by the three subscribers (push, history, WatchSessions). Backlog/system producers use non-session IDs (`fork-pressure`, `tmux-server`, item UUIDs) — lookup miss must mean "not hidden / deliver".

## 3. OQ3: is a read-only / hidden-session view already available? (Reuse before build)

Reusable (VERIFIED):
- `GetSession` does not filter on Hidden, and the web app already falls back to it: `web-app/src/app/page.tsx:205-234` (`fetchHiddenSessionFallback`, once per sessionId, then `routeToResolvedSession`). `/?session=<id>` deep links (used by push `buildSessionURL`, `server/push/subscriber.go:302`, and `NotificationsPage.tsx:234`) therefore can open a hidden session in the main page. So "View Session" for hidden sessions is not 0% for deep-link URLs resolved by UUID; the failure is for title-keyed IDs or when the sessions list never contains it (`ListSessions` drops hidden unless `include_hidden`, `server/services/session_service_crud.go:61,101`; proto field `session.proto:679`; web UI never sets it). Verify actual failure mode live before assuming (UNVERIFIED which of: UUID vs title ID, 7-day prune, session already deleted).
- Fallback path loads the session into the **normal interactive** view: `WriteToSession` has no Hidden or read-only guard (`server/services/terminal_service.go:102-125`, only empty-arg and not-found checks) and `StreamTerminal` is bidirectional (`session.proto:49`). So the "read-only" requirement is **not** met by reuse: needs a server-side guard (hidden => reject `WriteToSession`/input frames on `StreamTerminal`, `steer`) plus a client `readOnly` terminal mode. No existing terminal `readOnly` prop was found in `XtermTerminal.tsx`/`TerminalOutput.tsx` (grep readOnly = 0 hits there).
- Existing read-only presentation components are structured-JSON only (no scrollback): `web-app/src/components/backlog/detail/SessionDiagnosticPanel.tsx:25-80` (`TriageReviewPanel readOnly`, `GateVerdictBox readOnly`, `BlockedNotice`) for synthetic `headless-*` rows. Reuse for triage/review verdicts via the backlog item "View in Backlog" link: `NotificationsPage.tsx:377-393` prefers `metadata.item_id`, set by `SessionScopedMetadata` (`events.SessionScopedMetadata(nil, linkedItemID)` seen in `session_service_events.go`, `review_queue_manager.go:458`).
- Other reads that already work for hidden sessions: `GetTerminalSnapshot` (`session.proto:454`), `GetSessionDiff` (`:52`), the standalone summary route `/sessions/summary?sessionId=` (`NotificationsPage.tsx:234-235`, for deleted sessions).
- WatchSessions drops Hidden session *updates* (`session_service_watch.go:38,79,127`), so a Background-activity view cannot be fed from the existing stream; needs a `ListSessions(include_hidden=true)` call (server filter already exists) or a dedicated hidden-only filter field, with polling or an explicit opt-in stream flag.

Recommendation (INFERRED): build = small. (a) reuse `GetSession` + page.tsx fallback; (b) add a read-only flag derived from `session.hidden` that disables input in the terminal and a server guard in `TerminalService.WriteToSession`/`StreamTerminal`; (c) Background activity = `ListSessions{include_hidden:true}` filtered client-side to `hidden`.

## 4. OQ4: "needs-human" for a hidden session -> existing enums (VERIFIED enums)

`NotificationType` (`proto/session/v1/types.proto:992-1016`): APPROVAL_NEEDED=1, INPUT_REQUIRED=2, CONFIRMATION_NEEDED=3, TASK_COMPLETE=4, PROCESS_STARTED=5, PROCESS_FINISHED=6, ERROR=7, WARNING=8, FAILURE=9, INFO=10, DEBUG=11, STATUS_CHANGE=12, AUTO_APPROVED=13. `NotificationPriority` (`:1022-1026`): LOW=1, MEDIUM=2, HIGH=3, URGENT=4; `derivePriority(urgent, important)` maps URGENT/HIGH/MEDIUM/LOW (`server/services/notification_priority.go:11-21`).

Proposed predicate (INFERRED, mapping justified by `mapReviewItemToNotification`, `review_queue_manager.go:948-973`, which already maps reasons to these types):
- Needs-human = type in {APPROVAL_NEEDED, INPUT_REQUIRED, CONFIRMATION_NEEDED} (review reasons ApprovalPending, InputRequired, WaitingForUser).
- Failure = type in {ERROR, FAILURE} (review reasons ErrorState, TestsFailing; hook `--type task_failed`/`error` at `ssq-hook-handler:455,458,528`) plus WARNING only when it is a hard stop (rate-limit-recovery-failed is FAILURE at `session_service_events.go:254`).
- Everything else for hidden (TASK_COMPLETE, INFO, STATUS_CHANGE, WARNING, AUTO_APPROVED, DEBUG, PROCESS_*) = routine -> suppressed.
- Use **type, not priority** as the discriminator. Today's priority-LOW rule (`notification_service.go:143`) misses medium-priority routine hooks (see section 2), and the review-queue reason rule is separate. Hook `--type info` for Claude's `Notification` hook (needs permission/idle) is ambiguous: a hook "waiting for input" is mapped to INFO, so the hook handler (or message) must be reclassified to INPUT_REQUIRED or the gate will drop real needs-human events (gap; verify against Claude Code Notification-hook semantics).
- Approval requests for hidden sessions: `approval_handler.go` has no Hidden check and publishes APPROVAL_NEEDED (`:726,765`) — already passes; push forces `requireInteraction` for type 1 (`push/subscriber.go:206-207`). But auto-approve classifier may handle them first; AUTO_APPROVED (13) should stay suppressed for hidden.
- Stuck (stale) hidden sessions: review queue suppresses STALE for hidden today (`:442`) and `shouldSkipSession` skips hidden entirely (`session/review_queue_poller.go:805-822`), so "stuck hidden session" is currently silent. Requirement says only failures/needs-human notify: decide whether stuck counts (recommend: surface only in the Background activity view, no push).

## 6. Edge cases and failure modes

1. Hidden session deleted/archived before delivery: the push subscriber receives `event.Session` for status events, but for `EventNotification` only an ID. A lookup miss (deleted) must default to **deliver for failure/needs-human, drop routine** — decide by type, not by lookup — otherwise a deleted session's failure is lost. Storage fallback (`ListInstanceData`, `notification_service.go:115-130`) can resolve archived rows. Pruning of orphaned records exists (`store.go:464-505`, `PruneOrphaned`); a retained hidden-failure record will be pruned when the session is gone; "View Session" then needs the summary-route fallback (`NotificationsPage.tsx:85-90,234-235`). Also `ArchivedAt` sessions: `GetSession` still resolves (INFERRED).
2. Hidden -> visible transition: only DB write is create/update from `Hidden` data (`session/ent_repository.go:345,606`); no `.Hidden = false` setter was found in production code (grep of `.Hidden = ` / `SetHidden(` shows only ent). Prior research noted this question (`review-session-notification-cleanup/research/features.md:221-226`). Design: gate reads Hidden at delivery time via Snapshot; history rows already stored while hidden keep their classification; a later un-hide (if added) should not retroactively resurface suppressed routine items.
3. Race in Hidden read: `session_service_events.go` and `autonomous_orchestration_service.go:619` read raw `inst.Hidden` (violates `.claude/rules/instance-lock-free-reads.md`); `event.Session.Hidden` in `session_service_watch.go` likewise. Hidden is effectively set at creation (INFERRED), so low risk, but the new gate must use `Snapshot().Hidden`.
4. Failure for hidden session: must deliver on all channels, be logged (requirements), and be pinned in tray. Note that review sessions' own "failure" overlaps with the backlog item verdict flow (`backlog_notifier.go`, `backlog_service_verdict_steer.go`), which uses item IDs not session IDs; avoid double notification (session failure + item stuck). Dedup key is `(sessionID, type)` for history (`notifications/subscriber.go:206` coalesceKey) and `notification-<id>` tag for push (`push/subscriber.go:200`).
5. Multi-tab: toasts are per-tab (each tab's WatchSessions stream); cross-tab read/dismiss sync exists per requirements (reuse). Web push is deduped by `Tag` (`push/subscriber.go:78-100` dedupTracker + service-worker tag replace). Multiple open tabs each play audio/native notifications unless leader-elected: UNVERIFIED, check `useSessionNotifications.ts` dedup is per-tab only (cache at `:89` is in-memory => per-tab).
6. Push click when app closed: `push-sw.js:64-76` opens `data.url` = `/?session=<id>` (`push/subscriber.go:302`). Cold start loads sessions list then triggers `fetchHiddenSessionFallback` (`page.tsx:241-251`); tray/toast state not restored. A hidden session whose notification URL resolves only after `sessions.length > 0` (`page.tsx:243` early-return when empty) — if the live list is empty the fallback never fires (VERIFIED condition; likely edge). Push for tmux-title-keyed IDs uses `stableID` (`push/subscriber.go:266`).
7. Offline/reconnect replay: WatchSessions replays `EventsSince(afterSeq)` (`session_service_watch.go:35-41`) — missed notification events replay as toasts on reconnect: with the stack cap this could produce bursts; replay must respect gate and demote routine to tray. Sequence gap beyond ring buffer: UNVERIFIED. History store (7-day, 500 cap, `store.go:16-19`) is the durable source for tray after reload.
8. Rate limits: `SendNotification` has a per-session limiter that returns ResourceExhausted (`notification_service.go:147`) — note it runs *after* the hidden suppression, and a failure burst from one hidden session would hit the limiter (INFERRED) and drop distinct failures; coalescing in the history subscriber keeps "latest wins" per (session,type) in the flush window (`notifications/subscriber.go:94`) — a failure followed by an INFO of the same type... different type key so independent (OK).
9. Gate placement drift: ~40 `NewNotificationEvent` call sites (grep) in server/ — adding per-site checks will regrow the bug; one gate with a table-driven test enumerating `NotificationType` constants (compile-time exhaustiveness) is the guard. Add a lint/test asserting every `NewNotificationEvent` call goes through the gated publisher.
10. Toast-stack / bulk-clear safety: `clearAll()` clears everything including approvals; "Dismiss all" must exclude APPROVAL_NEEDED/INPUT_REQUIRED/CONFIRMATION_NEEDED (the never-suppress set at `useSessionNotifications.ts:120-122`) and pinned failures.
11. Mobile: soft keyboard viewport var exists (`--viewport-height`, per requirements); swipe-to-dismiss conflicts with pane swipe (OQ5, not researched here).
12. Slack (`server/services/slack_notifier.go`) is invoked from the review queue manager inside the same `!suppressForHidden` guard (`review_queue_manager.go:449-470`), but other Slack callers (`callback_dispatcher.go`, `session_service_delegates.go`) were not audited (UNVERIFIED).

## 7. Unstated needs

- Observability: counter + slog on every suppression (channel, session id, type, reason) — gate must live in one function that logs; also need an inverse "hidden failure delivered" log (requirements).
- Retroactive cleanup: existing history already holds hidden-session routine rows (7-day retention); one-time prune on rollout or tray will keep showing them. Store has `PruneOrphaned`/`Clear(before)` building blocks (`store.go:419,464`).
- Read/dismiss state: server `MarkRead` (`store.go:370`) vs client `NotificationContext` dismissal — "Dismiss all" in tray should call MarkRead for server-backed rows so the unread badge and other tabs agree.
- Feature flag: live-settable via the feature-flag RPC (no env var), global + scope override; gate must read the flag per event (not at startup).
- Tests: push subscriber has no Hidden test coverage today (`grep -i hidden server/push` = none); add a table test over {hidden, visible} x {each NotificationType} x {each channel}.
- Docs/registry: no existing Diataxis notification doc found under `docs/reference` or `docs/how-to` (the `ls | grep notif|push` returned nothing); new reference page needed, plus `make registry-generate` if RPC/markers change.
