# Pre-mortem: duplicate-backlog-status
**Date**: 2026-07-29

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `mark_duplicate`'s new session-item authorization check (Task 3.1.1a-bis) blocks Phase 7's own backfill: the implementing/operator session performing Epic 7.2 is linked via `ItemSession` only to the source backlog item (`4f03de7b-...`), not to the two non-canonical motivating items (`1dc7ff10-...`, `67de6c7b*`), so both `mark_duplicate` calls in Task 7.2.1b fail with `ErrPermissionDenied` on first attempt | `mark_duplicate({item_id: "1dc7ff10-...", ...})` returns `errResult(ErrPermissionDenied, "this session is not linked to the specified backlog item", "")` when Task 7.2.1b is executed | Add an explicit task to Epic 7.2 (before 7.2.1b) that either (a) spawns/attaches a session to each of the two non-canonical items via the existing `SpawnSessionFromItem`/`AttachSessionToItem` RPCs so a linked `ItemSession` exists before calling `mark_duplicate`, or (b) documents that the backfill must be run from within sessions already attached to those items (e.g. one worker session per item), not from the planning/implementation session. No MCP tool currently exposes attach/spawn, so this is an RPC-only workaround that must be spelled out, not assumed | P1 |
| 2 | Chain-prevention is a read-then-write race one layer above the already-fixed TOCTOU: `DuplicateOfStatus` is resolved via a single `GetBacklogItem(duplicateOfID)` lookup at request time (RPC Task 2.2.4a / MCP Task 3.1.1b), but the atomic write's `StatusEQ(current.Status)` precondition (Task 2.2.3a) only guards the *source* item's status column, never re-checks the *target's* status inside the same write — a concurrent transition that marks the target itself `duplicate` between the lookup and the write still lands, producing a silently-reachable 2-hop chain (A→B→C) that ADR-002/the Non-Goals section explicitly claims can't happen | A backlog item's "Duplicate of:" link resolves to another item whose own status is also `duplicate` — discoverable only by manually following the chain in the UI, no error or log anywhere | Either (a) accept and document the residual race explicitly in Cross-Cutting Notes (parallel to the two carve-outs already there) since duplicate-marking is a low-frequency, human/agent-judgment action, or (b) close it by re-validating target status inside the same transaction/`.Where()` clause used for the source item (e.g. a sub-select or a second `.Where(backlogitem.IDEQ(target) .StatusNEQ(duplicate))`-shaped guard on the write) | P2 |
| 3 | Data-integrity hole in the write path: `TransitionGuard`'s new validation branch is keyed on `to == BacklogStatusDuplicate` (Task 1.1.1e), but the atomic write's `SetDuplicateOfID(...)` (Task 2.2.3a) and the RPC handler's `opts` construction (Task 2.2.4c) are gated only on `opts.DuplicateOfID != ""` / `req.Msg.DuplicateOfId != ""` — with no matching check that `toStatus`/`TargetStatus` is actually `duplicate`. A `TransitionBacklogItemStatusRequest{TargetStatus: "ready", DuplicateOfId: "<anything>"}` bypasses `TransitionGuard`'s duplicate-specific checks entirely (they don't run for `to != duplicate`) yet still persists the unvalidated `duplicate_of_id` — an item can end up `Status: ready` with a garbage/self-referencing/dangling `duplicate_of_id` silently attached | No visible symptom in the shipped UI (which gates the link-resolution render on `item.status === "duplicate"`) — only surfaces via direct API inspection, a future feature reading `duplicateOfId` without also checking `status`, or a `git blame`-triggered incident months later | Add `toStatus == BacklogStatusDuplicate` as an explicit condition alongside `opts.DuplicateOfID != ""` in both Task 2.2.3a's write builder and Task 2.2.4c's `opts` construction, so `duplicate_of_id` can only ever be written when the transition target is actually `duplicate`. Add a regression test transitioning to a non-`duplicate` status with `duplicate_of_id` populated and asserting the column stays empty | P2 |
| 4 | Asymmetric not-found-vs-infra-error test coverage across the two duplicate-target lookups: the MCP `mark_duplicate` path gets a dedicated test proving `duplicate_of_id`-not-found isn't misclassified as an internal error (Task 3.1.3c), but the RPC handler's structurally identical second lookup (Task 2.2.4a) has no equivalent test anywhere in Story 2.2.5 — the underlying `ErrNotFound` translation itself is centralized and reliable (confirmed: `GetBacklogItem` in `ent_repository_backlog.go`/`storage.go` is the single place that wraps `ent.IsNotFound` into `session.ErrNotFound`), so the risk isn't sentinel drift, it's an untested call site that a future refactor of `backlog_service.go`'s error-classification `switch` can silently break | A future PR "cleans up" the RPC handler's error handling, collapses the `switch` into a single `errors.Is` check, and a genuinely-missing `duplicate_of_id` starts returning `CodeInternal` (masking as an outage) instead of `CodeFailedPrecondition`/not-found, with no test catching it | Add a `TestTransitionBacklogItemStatus_DuplicateOfIdNotFound_ReturnsFailedPrecondition_NotInternal` (or equivalent) to Story 2.2.5, mirroring Task 3.1.3c's MCP-side test but exercising the RPC handler's Task 2.2.4a lookup directly | P2 |
| 5 | The 6 WCAG contrast ratios in Task 5.1.2a were hand-computed rather than run through `check-theme-contrast.ts` (option (b) explicitly chosen over extending the script) — independently re-derived all 6 relative-luminance ratios by hand during this review and every one matches the plan's claimed value exactly (7.08, 8.52, 14.23, 7.79, 8.32, 5.92 — all ≥ 4.5:1), so the *initial* values are correct, but choosing not to extend the script means there is zero automated regression guard on this specific triplet going forward | A later, unrelated theme-file edit (rebrand, color-token cleanup) silently drops one of the 6 `duplicate*` pairs below 4.5:1 with no CI signal, since `check-theme-contrast.ts` still doesn't know this triplet exists | Extend `check-theme-contrast.ts`'s pair list to include `{bg: "duplicateBg", fg: "duplicateFg"}` for all 6 themes now, while the values are known-correct and the diff is trivial — deferring it means the gap has to be rediscovered and retrofitted later, likely after a regression has already shipped | P3 |

## P1 Items (address before implementation)

A Given-When-Then on Story 7.2.1's AC now proves the link is established first.

## Summary
1 P1 (resolved), 3 P2 (2 resolved, 1 accepted as documented limitation), 1 P3 (accepted, not blocking).

Top failure mode: Task 3.1.1a-bis's new (and correct) session-item authorization check on `mark_duplicate` has no counterpart step in Phase 7 to actually link the backfill-performing session to the two non-canonical motivating items, so the plan's own adoption-proof step (AC13) will fail with `ErrPermissionDenied` the first time it's run.
