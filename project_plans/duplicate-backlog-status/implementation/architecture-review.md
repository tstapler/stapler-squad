## Concerns

- [ ] **Epic 3.1 / Task 3.1.1c, Pattern Decisions "mark_duplicate MCP handler validation" row** — `mark_duplicate` bypasses the `WorkflowEngine` interface that the RPC path already uses for the identical check. Verified: `server/services/backlog_service.go:640` calls `s.engine.ValidateGates(guardInput, to)` (an injectable interface — `NewBacklogService(storage, creator, cfg, engine)` explicitly takes `engine session.WorkflowEngine` as a constructor param, defaulting to `NewDefaultWorkflowEngine()` only when nil), while `session/workflow_engine.go`'s `DefaultWorkflowEngine.ValidateGates`/`CanTransition` are thin pass-throughs to `session.TransitionGuard`/the `validTransitions` map. The plan's Task 3.1.1c has `mark_duplicate` call `session.CanTransitionBacklog` and `session.TransitionGuard` directly, skipping the `WorkflowEngine` seam entirely. Today this is harmless (no test currently substitutes a non-default engine — confirmed via `grep NewBacklogService(` across `backlog_service_test.go`: every call passes `nil` for engine), but it is a genuine architectural inconsistency: two different invocation styles for the same business-rule check across the RPC and MCP entry points, which is exactly the class of drift ADR-001 argues at length against ("RPC and MCP entry points cannot drift in validation/persistence behavior... one write path, not two"). ADR-001's "one path" argument is made for the *write* path but silently doesn't apply to the *guard* path, even though the same interface (`WorkflowEngine`) already exists specifically to abstract that check. **Remediation**: either thread a `session.WorkflowEngine` into `backlogHandlers` (constructed the same way `NewBacklogService` does) and call `engine.CanTransition`/`engine.ValidateGates` from `mark_duplicate`, or add one sentence to the Pattern Decisions table / ADR-001 explicitly acknowledging that the "one path" principle intentionally stops at the write layer and does not extend to guard invocation, so a future reader doesn't assume it does.

- [ ] **FR2 / Story 1.1.1 Task 1.1.1b + Epic 2.2 Task 2.2.3a** — reopening a duplicate (`duplicate → idea`) does not clear `duplicate_of_id`, leaving a stale canonical-item link on a non-duplicate item. Verified from the plan's own code: the atomic write (Task 2.2.3a) only calls `builder.SetDuplicateOfID(opts.DuplicateOfID)` when `opts != nil && opts.DuplicateOfID != ""`; the reopen transition (any `to` status other than `duplicate`) is one of the 5 call sites that pass `opts = nil` per Task 2.2.4c's `if req.Msg.DuplicateOfId != "" { opts = ... }` gate. So after `duplicate → idea`, the row keeps its old `duplicate_of_id` value even though the item is no longer a duplicate. This is precisely the "illegal state is representable" failure mode type-driven design flags: `(Status: idea, DuplicateOfID: <non-empty>)` becomes a silently reachable, semantically-wrong combination. Impact is contained today — the UI only renders the "Duplicate of:" link when `item.status === "duplicate"` (Task 5.3.2d), and any future re-mark-duplicate call must supply a fresh id from the request rather than reading the stored value (guard input is built from `req.Msg.DuplicateOfId`, not from the current row) — but it is an unaddressed data-hygiene gap with no AC covering it, and a foot-gun for any future feature that reads `duplicate_of_id` without also checking `status` (e.g., a future reverse-lookup query, which is only a Non-Goal *today*). **Remediation**: on the `duplicate → idea` transition specifically (or more generally, whenever `to != BacklogStatusDuplicate`), explicitly clear the column (`builder.ClearDuplicateOfID()` in ent, or `SetDuplicateOfID("")`), and add one test asserting a reopened item has an empty `duplicate_of_id` on re-fetch.

- [ ] **Epic 5.3/5.4, all 3 `STATUS_CLASS`/`STATUS_CSS` maps** (`BacklogItemBadge.tsx:14`, `BacklogItemDetail.tsx:21`, `page.tsx:39`) — the plan's own Domain Glossary correctly identifies these three independent maps as "the single highest-risk silent-failure point in the whole feature," and mitigates the risk only with hand-written Jest coverage (Epic 5.4) asserting `duplicate`'s class differs from `archived`'s. Verified: all three are typed `Record<string, string>` with `getStatusClass = (s: string) => STATUS_CLASS[s] ?? styles.statusArchived` — a missing entry for any status (current or future) doesn't fail to compile, it silently renders that status with `archived`'s styling. A compile-time fix is available at near-zero cost: `KnownBacklogStatus` already exists as a string-literal union (`web-app/src/lib/hooks/useBacklogService.ts:20`, currently 7 values, gaining `"duplicate"` per Task 5.2.2a). Retyping each of the 3 maps as `Record<KnownBacklogStatus, string>` (instead of `Record<string, string>`) would make `tsc` itself reject any of the 3 files if `duplicate` — or any future status — is missing, catching exactly the failure mode the plan is already worried enough about to write a bespoke regression test for, at all 3 sites simultaneously, for free, on every future status addition (not just this one). This is squarely "make illegal states unrepresentable" vs. the plan's chosen "add a test and hope it's kept in sync" — worth at least a deliberate reasoned rejection in the plan if not adopted, given the plan itself flags this as the highest-risk point in the entire feature. **Remediation**: change the 3 map declarations' types (and, if the widened `BacklogItemStatus = KnownBacklogStatus | (string & {})` type is used for the lookup key at the call site, keep the `?? styles.statusArchived` fallback only for that defensive unknown-string case — the map literal itself should still be typed against `KnownBacklogStatus` so a missing key is a compile error at the definition site, not just an untyped object with a runtime fallback).

## Nitpicks

- Task 3.1.1b performs a `GetBacklogItem` lookup on `duplicate_of_id` unconditionally, even in the self-reference case (`item_id == duplicate_of_id`), which is a redundant extra read (the guard's dedicated self-reference check in Task 3.1.1c catches it regardless, so there's no correctness issue) — negligible at this app's single-tenant, low-volume scale; not worth restructuring.
- ADR-002's chain-prevention fold into `ErrDuplicateOfNotFound`: verified the sentinel's actual message (Task 1.1.1d: `"duplicate_of_id does not reference a valid (existing, non-duplicate) backlog item"`) already covers both underlying conditions (genuinely missing, or exists-but-itself-duplicate) in its literal text, so the "confusing error message" risk ADR-002 itself raises and then dismisses is, on inspection, actually addressed by the message wording chosen — no further action needed here, flagging only to confirm this was checked rather than rubber-stamped.
- `mark_duplicate`'s best-effort note append (Task 3.1.1e) reuses `UpdateBacklogItem`, which the plan's own Risk Control section documents as having a known, pre-existing, explicitly-out-of-scope read-then-blind-write race. That's accepted debt already, not something this feature introduces — but `mark_duplicate` is a new, likely-higher-frequency caller of that racy path than existed before, so the probability of the pre-existing gap actually being hit goes up somewhat with adoption. No action required for this feature; worth keeping in mind as an argument for prioritizing the already-flagged future `UpdateBacklogItem` TOCTOU fix.

## Verified as sound (not rubber-stamped)

- **ADR-001 (TransitionOptions parameter object over a forked method)**: independently re-derived the call-site count via `grep -n "TransitionBacklogItemStatus(ctx" server/services/backlog_service.go server/mcp/tools_backlog.go` — confirms exactly the 6 call sites (1 RPC handler + 4 other-status transitions in `backlog_service.go` + 1 in `tools_backlog.go`) and 3 signature declarations (`session/repository.go:167`, `session/storage.go:528`, `session/ent_repository_backlog.go:274`) the ADR claims. Agree with the decision: a forked method would create exactly the double-write-path risk the requirements explicitly want to avoid, and the struct costs nothing over a bare positional parameter while being more extensible.
- **Transaction-Script-shaped `TransitionGuard` (flat switch, no Chain-of-Responsibility)**: read the current function — 4 cases + default today, growing to 5 cases with this feature (~55 lines total). Agree this is still well within "a flat switch is the right shape" territory; a pluggable-validator pipeline would be premature generalization for one more case with no second consumer in sight.
- **`duplicate_of_id` as a plain string, not a newtype**: the obvious type-driven-design instinct is "two different backlog-item IDs being compared (`item.DuplicateOfID == item.ID`) is exactly what phantom-typed IDs prevent." On inspection this doesn't actually apply here — both IDs are the *same* entity type (`BacklogItem`), unlike the classic `UserID`/`OrderID` cross-entity-mixup case phantom types solve. A `BacklogItemID` newtype would not prevent self-vs-target confusion (both fields would carry the identical phantom type), so the runtime equality check in the guard is the correct place for this rule, not a type-system fix. Verdict: keep as plain string — this is a case where the "primitive obsession" smell doesn't actually diagnose a real gap, not just "matches existing convention so it's fine."
- **`BacklogStatus` remaining a string-backed pseudo-enum**: converting to a proper sum type (sealed interface / `iota`) would be a repo-wide refactor touching all 7 existing statuses, ent's plain-string column, and every consumer — far outside this feature's blast radius for a benefit (compile-time exhaustiveness on the Go side) that the existing `validTransitions` map + `CanTransitionBacklog` + this plan's own table-driven tests already substantially cover at the Go layer. Agree with not doing it here. (Contrast with the frontend `STATUS_CLASS` maps above, where the equivalent type-safety win — `Record<KnownBacklogStatus, string>` instead of `Record<string,string>` — costs three one-line type annotation changes, not a refactor, which is why that one is flagged as a Concern and this one isn't.)
- **Build-vs-buy adherence** (`research/build-vs-buy.md`): plan matches all four recommendations — no FSM library, no self-referential ent edge, reuses ent's generated `UpdateOneID(...).Where(...)` precondition machinery (confirmed `backlogitem.StatusEQ`/`UpdatedAtEQ` are the same generated-predicate family already used for `StatusIn`/`StatusNotIn` elsewhere in `ent_repository_backlog.go`), and models tightly on `archived`'s existing footprint rather than the heavier 7-touchpoint session-creation-mode registry.
- **API contract (`duplicate_of_id` as field 6 on `TransitionBacklogItemStatusRequest`, present-but-usually-empty on every transition)**: consistent with the existing `override_reason` field 5 on the same message, which is already sometimes-set/usually-empty in the same way. Not a new pattern this feature introduces.
