# Pre-mortem: modal-focus-trap
**Date**: 2026-08-30

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Requirements/plan scope the audit to `web-app/src/components/{backlog,unfinished}/` only, so the WCAG keyboard-trap violation persists app-wide. `grep -rln 'aria-modal="true"' web-app/src` (run during this pre-mortem) finds 14 additional `aria-modal="true"` components outside those two directories and outside the 5 known `useFocusTrap` adopters — e.g. `HistoryMessagesModal.tsx`, `SessionPeekModal.tsx`, `NewShellDialog.tsx`, `NotificationPanel.tsx`, `ReviewQueuePanel.tsx`, `Omnibar.tsx`, `KeyboardShortcutOverlay.tsx`, `TemplateLibrary.tsx`, `PaneTilingContainer.tsx`, two `ShortcutHelpOverlay.tsx` files, `app/page.tsx`, `app/history/page.tsx`, `app/review-queue/page.tsx`, `insights/SessionDetailDrawer.tsx` — none of which are touched by this plan. | An a11y audit, Axe scan of a non-backlog page, or a screen-reader user report finds the identical Tab-escape bug on `NotificationPanel` or `SessionPeekModal` weeks after this ships as "done." | Add an explicit "Known Out-of-Scope Modals" section to plan.md/requirements.md listing the 14 files found above (from this exact grep), and file a follow-up backlog item enumerating them now — so "modal-focus-trap" is understood as closing the backlog/unfinished slice, not the WCAG issue app-wide. | P2 |
| 2 | The flagged `GateVerdictBox` behavior change — focus now auto-restores to `skipLinkRef` on Cancel/Confirm, not just Escape — was reasoned about but not verified against what happens to `skipLinkRef.current` when Confirm fires: if confirming "Skip Gate" causes the same render pass to unmount or hide the skip-link button (plausible, since skipping transitions the gate to a terminal state), `triggerEl?.focus()` in the hook's cleanup either no-ops (element detached) or throws, leaving focus on `document.body` with no visible indicator. | Manual QA or a keyboard-only user reports "after confirming skip, my next Tab press starts from the top of the page" instead of a graceful restore, or a console error on the confirm path. | Add a test case (Task 3.1.2b) specifically for the Confirm-click path where `skipLinkRef`'s DOM node is removed/hidden by the same state update, asserting the hook's cleanup neither throws nor leaves focus silently on `<body>` — not just the Escape/Cancel paths where the trigger stays mounted. | P2 |
| 3 | Story 4.1.2 (sibling-modal reachability) is deliberately verification-only with "no code change unless a gap is found" and is checked once, manually, per Task 4.1.2a. There is no automated test locking this behavior in, so a later change to the backdrop's CSS/z-index or a new modal added to `BacklogItemDetail.tsx` could silently reopen a click-through/double-trap hazard with zero CI signal. | A user reports being able to click a background trigger through an open modal's backdrop, discovered in production rather than CI, likely much later than this project's ship date. | Convert Task 4.1.2a into an automated Playwright assertion (attempt to activate the sibling trigger while a modal's backdrop covers it; assert no second dialog opens) instead of a manual-only, unrepeated check — bring it under the same AC5 CI gate as the other Tab-loop tests. | P2 |
| 4 | The hook's `focusable.length === 0` branch (`useFocusTrap.ts:38-41`) calls `e.preventDefault()` and returns, so Tab becomes a permanent no-op with no fallback focus target — `BacklogQueueSection`'s plan text calls this "theoretical only ... confirmed by inspection" for `GitHubIssuePicker`, an inspection that has no test backing it and can silently go stale if `GitHubIssuePicker` grows a loading state that renders zero focusable elements. | A keyboard user opens the import dialog during a slow GitHub API response, presses Tab, and nothing happens — no visible focus indicator anywhere, effectively a dead keyboard until the picker finishes loading. | Add a hook-level unit test for `focusable.length === 0` (not a per-component inspection claim) that asserts a defined, intentional behavior — e.g. focus falls back to the container itself — so the "theoretical only" claim is enforced by a test rather than a comment. | P3 |
| 5 | The two new Tab-loop e2e tests (Task 4.1.1a/b) are added to `tests/e2e/accessibility.spec.ts`, the same file requirements.md names as home to "the unrelated flaky `accessibility.spec.ts` test (#424)." A future flaky-test cleanup that quarantines or skips that file's known-flaky test could sweep up these new regression-detection tests too, silently defeating the CI gate AC5 exists to guarantee. | The new Tab-wrap tests start showing up in a "skipped tests" report or get wrapped in a shared `test.skip`/retry block alongside #424 during an unrelated cleanup, and nobody notices the coverage gap until a real focus-trap regression ships unflagged. | Name the relationship to #424 explicitly in plan.md/validation.md: confirm the new tests use isolated fixtures with no shared flaky setup, and add a one-line comment above each new test noting it must not be swept into any #424 quarantine without individual re-justification. | P3 |

## P1 Items (address before implementation)

None. This is a client-side accessibility fix with no data, security, or production-outage blast radius — every failure mode above degrades to either a documented scope gap or a UX regression catchable by manual QA or a future audit, not a catastrophic or irreversible outcome.
