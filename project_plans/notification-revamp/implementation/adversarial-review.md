## Concerns

- [ ] **The arbitration mechanism narrows the human-vs-automation race window but does not close it entirely, contrary to its own doc comment's claim.** Verified against the plan's own pseudocode (Task 2.1.1c, `plan.md:726-756`): `resolveApproval`'s reconciliation branch checks `IsHumanResolving(approvalID)` exactly **once**, at function entry, immediately after argument validation — then falls through to the *same* "unchanged: sessionID lookup, CI-red guard..., approvalStore.Resolve" block the doc comment identifies as the original vulnerability window (`approval_service.go:93-115` today). The check is never repeated immediately before the mutation. Concretely: if a human's RPC calls `MarkHumanResolving` *after* reconciliation's single check has already passed (but before reconciliation reaches `approvalStore.Resolve()` — i.e., during reconciliation's own pass through the CI-red-guard lookup, which for an `"allow"` decision calls `as.liveFinder.FindLiveInstance(sessionID)` and reads `inst.Snapshot()`), reconciliation still proceeds to delete the entry, and the human's later `Resolve()` call loses — exactly the class of bug this fix exists to close, just now bounded to a narrower window (in-process lookup latency, not full-RPC-duration latency). The doc comment's claim — "This closes the CI-guard-lookup window entirely... leaving only an unavoidable, symmetric race no backend design can close (the network transport time for the human's click to reach the server)" — overstates this: the residual window is *not* purely network-transit time, it is (network-transit time) **OR** (reconciliation's own check-to-resolve latency), and only the first of those two is genuinely unavoidable. The second is closeable, e.g. by re-checking `IsHumanResolving` a second time immediately before `approvalStore.Resolve()`, or — more robustly — by having `ApprovalStore.Resolve()` itself take the `humanResolving` check under the *same* `s.mu.Lock()` critical section as the delete (making claim-check-and-mutate atomic for the reconciliation path), rather than checking in a separate, earlier function call in `approval_service.go`. This is a materially smaller window than iteration 2's finding (in-process microseconds vs. full network+handler duration), so it does not rise to blocker severity for a single-operator tool per ADR-004's own risk-acceptance framing, but the plan's rationale should not claim the race is closed "entirely" when it isn't — either tighten the implementation (re-check-immediately-before-mutate, or fold the check into `Resolve()` under one lock) or correct the doc comment to state the residual window's true shape. — **Recommendation**: add a second `IsHumanResolving` check inside `ApprovalStore.Resolve()` (or a new `ResolveIfNotHumanClaimed`-style variant) under the same lock as the delete, called only from the reconciliation path, so the check and the mutation are atomic; alternatively, explicitly narrow the doc comment's claim and accept the residual window in the ADR text rather than asserting closure.
- [ ] **Panic-recovery counters: verified sound, no data race, but worth double-checking `counts` isn't captured by more than one in-flight pass sharing state.** `reconcileCounts` is allocated fresh (`counts := &reconcileCounts{}`) inside each call to `reconcilePendingApprovalsSafe`, so concurrent passes (ADR-004 permits them) never share a `*reconcileCounts` instance, and within one pass `reconcilePendingApprovals(counts)` is called synchronously (not from a further goroutine) — so the loop's increments and the deferred summary-log read are strictly sequential on one goroutine, even across a panic unwind. This is genuinely race-free and correctly fixes iteration 2's finding (the summary log now reads real partial counts on the panic path, since `counts` lives in the outer frame). Downgraded from iteration 2's Concern to noted-and-closed — listed here only because the instructions asked to scrutinize for a race and none was found.
- [ ] **CI-guard vs. concurrent-pass disambiguation via `IsApprovalPending` has a narrow residual TOCTOU of its own, but it is bounded to a logging mislabel, not a correctness bug.** `IsApprovalPending` is called in `reconcilePendingApprovals`'s error-handling switch *after* `ResolveApprovalReconciled` has already returned `CodeFailedPrecondition` — there is a small gap between that return and the `IsApprovalPending` check during which some other actor (a human, or a different concurrent reconciliation pass) could resolve a genuinely-CI-guard-declined item, making it register as `lostToConcurrentPass` instead of `declinedByGuard`. This is strictly narrower than iteration 2's finding (previously: 100% conflation whenever a concurrent pass was involved at all; now: only mislabeled if a *second* event lands in the brief window between the error return and the disambiguation check) and — as the plan's own text already acknowledges — affects only an aggregate log counter's classification, never which approvals get resolved or how. No action required beyond what's already noted in-plan; not escalating past what iteration 2 already filed.

## Minors

- Task 2.2.2c's concurrent test synchronizes at the `ApprovalStore` primitive level (`MarkHumanResolving`/`Resolve` called directly, not via the full `ResolveApproval` RPC handler) rather than literally racing two goroutines through `ResolveApproval`/`ResolveApprovalReconciled` end-to-end as iteration 2's blocker recommendation literally described. This is arguably a *better* test — it pins the exact arbitration boundary deterministically via channel synchronization (`<-humanClaimed`) rather than hoping two RPC-level goroutines interleave usefully — but it means a bug in the *shared* unchanged logic (sessionID lookup, CI-guard, stamping) between the human and reconciliation paths isn't exercised concurrently by this specific test. Acceptable given other tests cover that shared logic sequentially; noting only for completeness. The test as specified is deterministic and non-flaky as designed (real channel-based happens-before, not a sleep).
- Task 2.1.1b's stateful `spyNotificationStore.GetByID` design leaves it slightly ambiguous whether the existing `SetMetadata` stub (`approval_service_test.go:453-456`, currently just appends to `callLog`) needs to be modified to also populate the new `records` map, or whether that's a separate addition — the task text says "or a small settable records map... updated from the existing SetMetadata stub" without spelling out that the stub itself must change. Low risk (an implementer will need to make this decision anyway to satisfy Task 2.1.1d's `TestResolveApproval_AfterReconciled_ReturnsFailedPrecondition`, and doing so is backward-compatible with existing `callLog`-based assertions like `TestResolveApproval_MarksNotificationRead`), but worth a one-line clarification.
- Carried forward, unchanged, low-stakes (see Iteration-1/2 Item Disposition): pitfalls.md's reconciliation-context-staleness caveat (resolved via `title` tooltip) and the pass-can-straddle-two-rule-generations accepted limitation (now explicitly documented in-plan) remain resolved/accepted as before.

## Iteration-2 Item Disposition

1. **Blocker — human-vs-automation race unarbitrated**: SUBSTANTIALLY RESOLVED. A real mechanism now exists (`ApprovalStore.humanResolving` + `MarkHumanResolving`/`ClearHumanResolving`/`IsHumanResolving`, checked as the first step of a shared `resolveApproval` core) and a genuinely concurrent, channel-synchronized test (`TestReconcilePendingApprovals_HumanWinsRace`, Task 2.2.2c) pins the mechanism's observable behavior via the actual `decisionCh` payload, not just an error code. Re-filed above as a Concern only because the mechanism narrows rather than eliminates the race window, and the plan's own doc comment overstates closure — not because the mandate is unimplemented. `ClearHumanResolving` reliably fires on every exit path via Go's `defer` semantics (verified: `defer as.approvalStore.ClearHumanResolving(approvalID)` registers immediately after a call that cannot itself panic under normal map/mutex operation), closing sub-question (b) outright. Sub-question (c) (test flakiness) is closed — the test uses explicit channel handoffs (`<-humanClaimed`), not sleeps.
2. **Concern — panic-recovery summary log doc/code mismatch**: RESOLVED. Verified: `reconcileCounts` now lives in `reconcilePendingApprovalsSafe`'s frame and is passed by pointer into `reconcilePendingApprovals`, with the summary log moved into the same `defer`. No data race introduced — each pass owns its own `*reconcileCounts`, and access within one pass is strictly sequential on one goroutine.
3. **Concern — CI-guard vs. concurrent-pass conflation**: RESOLVED for the case that matters (a `IsApprovalPending` check disambiguates the two in the overwhelmingly common case). Re-filed above as a narrower residual TOCTOU, bounded to a rare logging mislabel with no resolution-correctness impact — not escalated further.
4. **From architecture review — Task 2.1.1b `GetByID` stubs**: CONFIRMED. Verified against current source: `spyStamper` (`approval_handler_integration_test.go:631-644`) and `spyNotificationStore` (`approval_service_test.go:449-463`) both currently lack `GetByID` (neither does `approvalNotificationStamper`, `approval_handler.go:52-55`, nor `NotificationHistoryStore`, confirmed via `grep` — no `GetByID`/`IsReconciled` method exists in `server/notifications/store.go` today). Task 2.1.1b's plan text correctly specifies both need the addition, with `spyNotificationStore`'s being stateful (needed for Task 2.1.1d's reconciled-branch test) and `spyStamper`'s being a fixed stub (`ApprovalHandler` never calls `GetByID` itself). Accurate and buildable as specified, modulo the Minor above.
