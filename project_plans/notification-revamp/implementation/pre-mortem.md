# Pre-mortem: notification-revamp
**Date**: 2026-09-04

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `notificationTypeFilter`'s allow-list fix (Task 3.1.1a) is built on top of `mapNotificationType`, whose own `default: return "info"` (`notificationMapping.ts:39-40`) is the *first* place a proto `NotificationType` value gets bucketed — any backend enum value without an explicit `case` here (a future type, or an existing one the switch never listed) silently becomes UI type `"info"` before `isActionableNotification`/`ACTIONABLE_TYPES` ever sees it. The project fixed the second-stage exclusion-list drift but reproduced the identical class of bug one stage earlier. | A newly-added `NotificationType` proto value (or an existing one nobody thought to add a case for) that is clearly "needs a decision" never appears in `NeedsDecisionSection` — it sits, unread, inside the collapsed informational tier, indistinguishable from "Claude turn complete" noise. | Make `mapNotificationType`'s default fail loud instead of quiet: log a one-time warning (or route unmapped proto values to a distinct UI type, e.g. `"unknown"`, that `isActionableNotification` treats as actionable-by-default rather than informational-by-default) so an unmapped type surfaces for triage instead of disappearing. Add a test iterating the full backend `NotificationType` proto enum (not just the 13-member `UIType` union already tested by Task 3.1.1b) asserting every value has an explicit `mapNotificationType` case. | P1 |
| 2 | Rule-reconciliation only fires from `UpsertApprovalRule`/`DeleteApprovalRule`/`BulkUpsertRules` (user-rule CRUD) and `ClaudeSettingsWatcher`'s reload of the **server process's own cwd** settings files (`session_service.go`'s own comment: "Global-only for v1 — this is always the server's own cwd, never a per-session git worktree path"). A rule added via a session's per-worktree `.claude/settings.json`/`.claude/settings.local.json` — a routine occurrence in this worktree-heavy repo — never triggers `ClaudeSettingsWatcher`, so it never triggers reconciliation, even though the success metric promises "adding or editing an approval rule auto-resolves any currently-pending escalated approval." | The user (or Claude Code itself, via an in-session "always allow" click that writes a project-level settings file inside a worktree) adds a rule that should cover a pending approval for that exact session; the approval sits unresolved, while the identical rule added through the Rules UI would have cleared it — an inconsistency that looks like the feature is flaky rather than scoped. | State the scope limit explicitly in requirements.md/validation.md ("reconciliation covers Rules-UI edits and the server's own cwd settings files only — not per-worktree project settings"), and add a test asserting a worktree-scoped settings change does *not* trigger reconciliation (documents the gap instead of leaving it to be discovered in production). If worktree coverage turns out to matter in practice, file it as an explicit follow-up rather than silently accepting the gap. | P2 |
| 3 | Epic 1.2's `suppressedByAck` extends `IsAcknowledgedAfterOutput`'s indefinite, no-TTL suppression (already latent for `ReasonStale`) to `ReasonIdle` for the first time, and Story 3.2.2 simultaneously removes all idle-reason items from the Review Queue UI regardless of priority. Combined, a session that is skipped once while genuinely idle, then later goes truly stuck (tmux pane dies, a call hangs, zero further terminal output — but no explicit `StatusError`/`StatusTestsFailing` transition ever fires) is suppressed forever with no re-escalation path; the only remaining signal is the passive "Idle" `SubStatusChip` on the Sessions list (Task 3.2.2b), which nobody is nudged to look at. | A session skipped as "idle, ready for next task" days ago is discovered, much later, to have actually died/hung the whole time — it never reappeared in the review queue, and the only trace was an easy-to-miss idle chip on the Sessions list. | Add a maximum suppression duration or a distinct "idle far longer than normal, re-check" threshold that bypasses `suppressedByAck` after N hours with zero output (mirroring how `ReasonStale`'s own threshold works, but making the ack a snooze rather than a permanent dismissal) — or, at minimum, explicitly document this as an accepted trade-off in validation.md and confirm the Sessions-list chip is deliberately the sole compensating control. | P2 |
| 4 | Epic 1.3's `waitingForAgentStuckThreshold` (30-minute grace period) is keyed on `inst.UpdatedAt`, a general-purpose "this instance record changed" timestamp bumped by many actions unrelated to agent activity — renaming a session (`session/instance_terminal.go:99`), saving a note (`session/instance_actor_setters.go:397`, whose own comment says it bumps `UpdatedAt` specifically so the note "doesn't otherwise" go unnoticed), workspace/tag changes (`session/instance_workspace.go:368`), and several other `touchUpdatedAt()` call sites in `session/instance_state.go`. Any of these resets the 30-minute grace window even though no agent progress occurred. | A session genuinely hung in "Waiting for agent" for hours — but which the user renamed, tagged, or left a note on while investigating — never falls through to idle/stale detection and never appears in the review queue, despite being visibly broken on manual inspection. | Key the grace period off a narrower, activity-specific signal (`LastMeaningfulOutput` or a new dedicated `LastAgentActivityAt`) instead of `UpdatedAt`. Add a regression test asserting an unrelated mutation (e.g. `Rename()`) does not reset the `StatusWaitingForAgent` grace window. | P2 |
| 5 | `maxReconcileAutoResolvesPerPass = 50` caps each reconciliation pass, but `ApprovalStore.pending` is a `map[string]*PendingApproval` and `ListAll()`/`ListPendingApprovalsInternal()` iterate it directly (`for _, a := range s.pending`) — Go's randomized map iteration means *which* 50 of a >50-item backlog get resolved is arbitrary and different on every pass/restart, with no age-based ordering and no scheduled catch-up for the remainder. This is not a hypothetical: the incident that triggered this whole project was a 107-item backlog. | After adding a rule expected to "clear the backlog," some pending approvals resolve and others don't, with no visible pattern and no indication a cap was even hit unless the operator reads the structured log line — undermining the exact trust this project exists to rebuild. | Sort `ListPendingApprovalsInternal()`'s result deterministically (oldest-escalated-first) before applying the cap, so repeated passes make monotonic progress instead of touching a random 50 each time; consider auto-scheduling a follow-up pass when `capped` is true so a large backlog fully drains within a few triggers instead of only on the next unrelated rule edit. | P2 |

## P1 Items (address before implementation)
- [x] Failure #1 — Before shipping the `ACTIONABLE_TYPES`/`isActionableNotification` allow-list (Task 3.1.1a), also close the upstream gap in `mapNotificationType`'s `default: return "info"` case: either make unmapped proto values fail loud (log warning / distinct `"unknown"` UI type treated as actionable-by-default) or add a test enumerating the full backend `NotificationType` proto enum and asserting every value has an explicit case, so the exclusion-list-drift bug this project set out to eliminate cannot simply reappear one layer higher in the pipeline. **Resolved in plan.md Task 3.1.1c**: default case now logs a warning and returns `"warning"` (actionable) instead of `"info"`, plus a test-time exhaustiveness check over the real generated `NotificationType` proto enum.
