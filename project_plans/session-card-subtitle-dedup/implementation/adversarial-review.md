# Adversarial Review: session-card-subtitle-dedup

**Date**: 2026-08-06
**Verdict**: CONCERNS

## Blockers
None — see the AC3 reversal item below, which was seriously considered for BLOCKER status but is downgraded to CONCERN given `requirements.md`'s own "(initial — refined further in plan.md)" caveat and the fact that the reversal is structurally load-bearing (see Concern 1), not arbitrary. It is listed first because it is the closest call in this review and should be resolved with an explicit human/backlog checkpoint before Epic 1.2 ships, not silently treated as closed.

## Concerns

- [ ] **AC3 (Program dedup) is fully reversed, not refined, from an explicit numbered criterion sourced from a human-filed GitHub issue, and the plan declares it resolved without ever routing it back for confirmation.** Original `requirements.md` AC3: "Given `session.title` equals `session.program`, the `Program:` row is not rendered." The plan's "Refined Acceptance Criteria" AC3 flips this 180°: "Program row is explicitly excluded from dedup... Program is intentionally out of scope for v1 dedup." `requirements.md`'s "(initial — refined further in plan.md)" line reasonably authorizes *sharpening* ambiguous criteria (e.g., AC2's "row hidden vs. value suppressed" choice, which the plan resolves well via ADR-001) — it's a weaker basis for authorizing a directional reversal of a criterion that was already unambiguous and testable as written. The plan's own "Unresolved Questions" section buries this by lumping it in with three genuinely-open items ("all... resolved above") rather than flagging it as requiring sign-off, even though `AskUserQuestion` is an available tool at this SDD phase. That said, the reversal is not arbitrary: because Program is left permanently unconditional, it structurally guarantees the `info` block can never render fully empty (see next item) — a real, useful side effect, not just a excuse. **Recommendation**: before Epic 1.2 starts, surface this specific reversal back to the user or the source GitHub issue/backlog item for an explicit "yes, drop Program from v1 scope" confirmation — a one-question check, not a re-plan. If confirmed, this concern is fully closed; if not, Program needs its own guard (`session.program && !isRedundantWithTitle(...)`) and the all-fields-redundant fallback (see next item) needs a different anchor row.

- [ ] **The plan's mitigation for the "all-fields-redundant" edge case (ux.md) — "rely on Program always rendering" — is never actually verified by a test, despite ux.md explicitly asking for one.** ux.md's edge-case #4 recommendation says in full: "flag for implementation to add a test fixture exercising the all-fields-redundant case specifically (not just the single-field cases AC1-3 already specify)." The plan's "Unresolved Questions" section downgrades this to "optional, non-blocking... not required to ship, since the CSS collapse behavior is independently verified from source" — but that source-read only proves an *empty* `info` div collapses to zero height; it says nothing about whether Program actually stays present when every other field simultaneously matches the title. That guarantee currently holds only because Program's guard was never added (previous item) — a structural fact, not a tested one. If a future PR "completes" AC3 by adding a Program guard (a natural-looking follow-up given the row is otherwise identical to its 5 siblings), the empty-info-block bug ux.md warned about would silently reappear with nothing to catch it. **Recommendation**: add one render test with `title` matching `branch`, `path`-basename, `workingDir`-basename, `clonedRepoPath`-basename, and `goal.goalText` simultaneously, asserting all 5 rows are absent AND the Program row is still present/non-empty. This also covers features.md's separately-flagged "title matches multiple fields simultaneously" idempotency case (no test currently proves the 5 guards are independent rather than "first match wins") — one fixture covers both.

- [ ] **No test exercises the actual JSX wiring at any of the 5 call sites — only the underlying `isRedundantWithTitle`/`basenameOf` predicates are unit-tested in isolation.** The plan's own Alternatives Considered table (Option B) names this exact risk: "touches 5 separate call sites instead of one central function, so slightly more surface area for a copy-paste mistake — mitigated by table-driven unit tests on the shared predicate." That mitigation doesn't actually cover the risk: a wiring bug (e.g., Task 1.2.2a passing `session.path` instead of `basenameOf(session.path)`, or Task 1.2.4a's guard accidentally comparing against the wrong field) would compile cleanly, pass the isolated predicate unit tests (which call the functions correctly, by construction), and pass every existing `SessionCard` test (none of which assert on row label/value text, per pitfalls.md's own grep). Nothing in Epic 1.2 or 1.3 would catch it. AC1/AC2/AC3/AC4/AC8 all specify rendered-DOM outcomes ("the `Branch:` row is not rendered") that the plan's chosen test strategy never actually checks end-to-end. **Recommendation**: add at least one lightweight full-render RTL test per suppressed row (or one parameterized test over the 5 fields), reusing the render harness already established in `SessionCard.click.test.tsx`/`SessionCard.pending-program.test.tsx` — this is a small addition, not a reversal of the "no full-render tests" architecture decision, since it only needs to assert row presence/absence, not re-test the predicate logic itself.

- [ ] **`basenameOf`'s trailing-slash quirk is knowingly propagated into brand-new code rather than fixed or tracked.** Task 1.1.2a documents and tests the quirk (`basenameOf("/home/user/worktrees/fix-auth/")` returns the *whole* trimmed path, not `"fix-auth"`, because `.split("/").pop()` on a trailing-slash string yields `""`, which is falsy and falls through to the `|| trimmed` branch) as an accepted, "documented inherited quirk," matching 4 pre-existing ad hoc duplicates elsewhere in the codebase. Practical risk is low — no evidence any code path in this app produces a trailing-slash session/worktree path — and this is handled better than any of the 4 existing duplicates (transparently documented and unit-tested here, vs. silent elsewhere). But it's still a known bug shipped fresh with no follow-up filed, which sits awkwardly next to this repo's own "fix collateral debt" convention. **Recommendation**: file a quick follow-up backlog item to consolidate the now-5 duplicate basename implementations into one correctly-handling shared helper (build-vs-buy.md already flags this as "viable... nice-to-have" — just needs an actual tracking item so it doesn't get lost).

## Minors

- `isRedundantWithTitle(value: string | undefined | null, title: string)`'s parameter type is wider than any real caller's domain — every `Session` string field used here is a non-optional protobuf-generated string (defaults to `""`, never `undefined`/`null`). Harmless defensive typing, but slightly overstates the function's actual input contract; a plain `string` signature (relying on the existing `session.branch &&`-style truthiness guards already present at each call site) would more accurately reflect the domain.
- The plan doesn't mention `.claude/rules/feature-registry.md` or `.claude/rules/e2e-test-conventions.md` at all. Likely genuinely N/A — `SessionCard.tsx` carries no existing `// +feature:` marker, and this change adds no new page/component/RPC — but the codebase's own precedent (`hasPendingProgramChange`, an analogously-scoped small SessionCard display feature, has e2e coverage via `tests/e2e/session-program-change.spec.ts`) means "just a display tweak" isn't automatically exempt in this repo. A one-line confirmation in the plan (or during `sdd:6-verify`) that no registry/e2e updates are needed would close this out rather than leaving it silent.
- `features.md` separately flags `session.category` and `session.tags` (header area, outside the 700–778 info-row block) as plausible title-duplication targets, but `requirements.md`'s own AC list never included them (its Problem section explicitly scopes to the 8 named info rows). The plan doesn't restate this exclusion explicitly — worth one line noting category/tags were considered and are out of scope, so a future reader doesn't wonder whether they were simply missed.
- architecture.md frames Program as "cheap to include for consistency" while the plan's Pattern Decisions table frames excluding it as avoiding "a materially larger behavior change" — both are reasonable, but the plan doesn't directly address architecture.md's specific "cheap" framing when explaining the opposite conclusion. Not a real gap (the plan's reasoning stands on its own), just a citation-continuity nit.

## Verified, not a concern

- **"Path row guard changes behavior for ALL sessions, not just duplicates" (explicitly stress-tested per review brief)**: confirmed false. `!isRedundantWithTitle(basenameOf(session.path), session.title)` evaluates `true` (row renders) for every non-duplicate session, identical to today's unconditional render. The new conditional only ever suppresses the row in the specific duplicate case AC2 targets. AC4's "no visual regression for the common case" holds structurally, not just by claim.
- Every line number cited in the plan/ADR/research (`SessionCard.tsx:22-30` for `hasPendingProgramChange`, `:454` for title, `:700-778` for info rows, `:705/:711/:717/:757/:765` for the five guarded rows) was checked directly against the current file and matches exactly — no drift between plan and source.
