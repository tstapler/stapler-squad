## Nitpicks
- `isRedundantWithTitle(value: string | undefined | null, title: string)` (Task 1.1.1a) accepts a wider input type than any real caller can produce. Every field it's called with (`session.branch`, `session.title`, `basenameOf(session.path)`, `basenameOf(session.workingDir)`, `basenameOf(session.clonedRepoPath)`, `session.goal.goalText`) is typed as plain non-optional `string` in `web-app/src/gen/session/v1/types_pb.ts` — proto3 scalars default to `""`, never `null`/`undefined`. The `| undefined | null` union is dead code for every in-scope caller. Harmless (defensive, and the function may gain other callers later), but per type-driven-design's "let the type reflect only what can occur," a plain `string` parameter would more accurately document the actual contract; only widen it if/when a real nullable caller appears.
- `isRedundantWithTitle` intentionally does *not* mirror `hasPendingProgramChange`'s `Pick<Session, "...">` parameter style (raw strings vs. a session slice) — this is flagged only because build-vs-buy.md's "Recommended approach" suggested typing "on a `Pick<...>` of the fields it needs." The plan's actual choice (plain strings) is the more correct design here: 3 of 5 call sites pass a *derived* value (`basenameOf(...)` output) that isn't a real `Session` field, so a `Pick<Session,...>`-shaped signature couldn't express those call sites at all. No action needed — noting only so the build-vs-buy deviation is traceable, not silently inconsistent.
- build-vs-buy.md's "Recommended approach" summary line also mentions "case-insensitive match" as part of the comparison logic; plan.md's Pattern Decisions table correctly overrides this to case-sensitive-only, citing requirements.md AC1 as authoritative over the earlier research suggestion. Already resolved with explicit rationale — flagged only for completeness, not as an open gap.

## Lens-by-Lens Notes (supporting detail)

**Lens 1 — Structural integrity**: No SOLID violations. `isRedundantWithTitle`/`basenameOf` are single-purpose, stateless, decoupled from `Session` (better ISP than a `Pick<Session,...>` signature would give, since 3 callers pass derived strings). No layer coupling introduced — this is pure client-side display logic with zero new dependencies, consistent with the existing file's shape. DDD aggregate boundaries: N/A, correctly self-identified in the plan (no aggregates in a display component). Testability: both new functions are directly importable and unit-testable with zero mocks/render (Story 1.1.2), matching the `hasPendingProgramChange` precedent's test style (`SessionCard.pending-program.test.tsx`).

**Lens 2 — Type-level design**: Primitive obsession assessed and correctly judged not applicable — two deterministic string operations (exact-trim-match, path-basename) have no domain meaning worth encoding as a Value Object at this scope; a `RedundancyCheck` type would be needless ceremony over a boolean predicate. No illegal states are reachable: the `!value` early return in `isRedundantWithTitle` prevents false-positive suppression when a basename or title is empty, and every row's suppression guard composes with the row's existing presence guard (`session.branch && ...`) rather than replacing it, so "row hidden because of a bug in dedup logic" fails closed (row renders) per the plan's own Risk Control section. Parse-at-boundary: N/A, correctly noted — this operates on an already-hydrated, already-typed `Session` proto object; there is no raw/untrusted input crossing a boundary here.

**Lens 3 — Pattern selection**: PoEAA Transaction Script (plain colocated functions) is the right fit — no persistence, no multi-step orchestration, no cross-entity business rules; a Domain Model or Service Layer would be pure ceremony for two pure string predicates. No GoF pattern is warranted or was added — Strategy/Visitor/Chain-of-Responsibility would all be overkill for 5 independent boolean guards, and the plan correctly resists reaching for one. API contracts are stable and consistent: `isRedundantWithTitle(value, title)` keeps the same `(value, title)` argument order across all 5 call sites; `basenameOf(pathValue)` is called only where the caller has already confirmed non-emptiness (guarded by `&&` or by path always being present), so no runtime type mismatch. Plan.md matches build-vs-buy.md's recommendation on every load-bearing point (colocate in `SessionCard.tsx`, no new dependency, reuse the `.split("/").pop()` idiom already shipped 4x elsewhere in the codebase) — the two deviations noted above (case-sensitivity, parameter shape) are both explicitly justified overrides, not oversights.
