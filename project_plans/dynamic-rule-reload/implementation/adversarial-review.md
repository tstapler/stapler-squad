# Adversarial Review: dynamic-rule-reload

**Date**: 2026-08-06
**Verdict**: BLOCKED

## Blockers

- [ ] **`ClaudeSettingsWatcher.lastGood` map is written from two concurrent goroutines with no synchronization.** The struct declares a `mu sync.Mutex` field (Task 4.1.1a) but no task in Phase 4/5 ever calls `w.mu.Lock()` around `Reload()`'s body. `Reload()` (Task 4.1.1b) reads and writes `w.lastGood[path]` (a plain Go map), and is invoked from two independent goroutines: (1) the debounce-timer callback inside `Start()`'s event loop (Task 4.1.1c), and (2) `RulesService.ReloadClaudeSettingsRules`'s RPC handler calling `rs.claudeSettingsWatcher.Reload(ctx)` directly (Task 5.1.1d) — itself reachable concurrently from multiple simultaneous ConnectRPC requests (two people/scripts clicking "Reload rules" near-simultaneously is enough, no fsnotify event required). Two goroutines racing on a `map[string][]classifier.Rule` is a `fatal error: concurrent map read and map write` crash, not a logic bug, and `RulesService.rebuildMu` (ADR-002) does not help — it only guards the *classifier* mutation inside `rebuildClaudeSettingsRules`, which runs strictly after `Reload()` has already touched `lastGood`. Task 4.1.1e's test list (debounce, last-known-good, graceful degradation) never exercises concurrent `Reload()` calls, so `go test -race` as currently scoped would not catch this. — **Recommendation**: hold `w.mu` for `Reload()`'s full body (or at minimum around every `w.lastGood` access), and add `TestClaudeSettingsWatcher_ConcurrentReloadCalls_NoRace` exercising RPC-triggered and fsnotify-triggered reload simultaneously under `-race`.

- [ ] **On the actual deployed configuration, "project" scope collapses onto "global" scope, producing duplicate rules and a misleading `origin=mixed` security tag.** Verified directly: `systemctl --user show stapler-squad -p WorkingDirectory` on this machine returns `WorkingDirectory=/home/tstapler`, i.e. the live service's `os.Getwd()` equals `$HOME` exactly (the systemd unit's `WorkingDirectory=$HOME` line in `scripts/install-service.sh:181`, not a repo checkout path). `LoadClaudeSettingsRulesDetailed(cwd)` builds project-level paths as `filepath.Join(cwd, ".claude", "settings.json")` and global paths as `filepath.Join(home, ".claude", "settings.json")` where `home := os.UserHomeDir()` — also `/home/tstapler`. So on the real deployed instance, the "project" (priority 170/180, `Label: "project"/"project-local"`) and "global" (150/160, `Label: "global"/"global-local"`) entries in the path list resolve to the **same file** (`/home/tstapler/.claude/settings.json`, confirmed present, 3121 bytes). `LoadClaudeSettingsRulesDetailed` parses it twice under two different priority/label pairs, and `claudeAllowsToRules` builds two distinct `Rule` slices from the identical `permissions.allow` content — genuinely duplicated `classifier.Rule` objects, not deduplicated by anything downstream (`filterRulesBySource` only filters by `Source`, and both copies have `Source == "claude-settings"`). Consequences: (a) `ListApprovalRules`/`ApprovalRulesPanel`'s "Claude Settings" tab shows every allow pattern twice; (b) Task 4.2.1a's origin computation — the one mechanism ADR-003 relies on to flag a project/branch-sourced auto-allow expansion as distinct from the operator's own global edit — sees one changed path labeled `"global"` and one labeled `"project"` from the *same edit*, and reports `origin=mixed` for what is actually a purely benign self-edit of `~/.claude/settings.json`. This actively undermines the one security-visibility control this project adds, training the operator to see "project"/"mixed" tags as routine noise rather than a real signal. None of the plan's Given/When/Then acceptance criteria (Story 1.1.1, 4.2.1) exercise `cwd == home` — every example uses a distinct hypothetical `<projectDir>`. — **Recommendation**: dedupe resolved (post-`EvalSymlinks`) paths before building the path list — when the project-level path for `cwd` resolves to the same file as a global path, drop the duplicate project entries instead of loading/watching/tagging them a second time. Add a regression test using `cwd == home` explicitly (mirrors the deployed config, not just a "manual dev instance run from repo root" scenario).

## Concerns

- [ ] **Redundant double-load of claude-settings rules at every startup.** Task 2.1.1b does an additive `classifierObj.AddRules(...)` from a synchronous `LoadClaudeSettingsRulesDetailed(cwd)` call inside `NewSessionService`; separately, Task 4.1.1c's `Start()` does its own synchronous initial `Reload()` (which fully replaces claude-settings rules via `rebuildClaudeSettingsRules`) before entering the event loop. Both read the same files from disk independently, and correctness depends on nothing editing settings.json in the narrow window between the two — if something does, the Task 2.1.1b state is invisibly clobbered before any request or toast ever observes it. — **Recommendation**: make the watcher's own initial `Reload()` the single source of truth for the startup load; drop the separate `AddRules` call in Task 2.1.1b (or have it call through the same `Reload()` path).

- [ ] **No first-activation signal for the behavior change this ships.** ADR-003 and pitfalls.md §6 thoroughly cover the *ongoing* risk (a PR branch rewriting project settings while a session is live) but not the *one-time* risk requirements.md's own framing implies: the moment this merges, every `permissions.allow` entry a user already has in `~/.claude/settings.json` — very likely configured for the standalone Claude Code CLI, not written with "this also silently drives stapler-squad's own auto-approval classifier" in mind — becomes a live auto-approval rule with no opt-in step and no reload event (since `AddRules` at construction isn't routed through the toast/log pipeline Phase 4 builds for later reloads). Risk Control's "not gated, full rollout on merge" is a defensible call, but it leaves the single biggest one-time expansion of auto-allow surface less visible than every subsequent routine edit will be. — **Recommendation**: fire the same `EventNotification`/log line once for the initial startup load (Task 2.1.1b), not only for later reloads, so "N claude-settings rules now active" is visible the first time it happens.

- [ ] **Setter-injection safety isn't signposted for future refactors.** `NewSessionService`'s own header comment (`server/services/session_service.go` ~lines 230-246) already documents several deps (`SetWorkflowService`, `SetTokenStoreReader`, etc.) that *must* use setter injection because of circular or delayed-availability construction constraints — i.e., this file already has real construction-order fragility. The plan wires `ClaudeSettingsWatcher` via the same same-function pattern (safe today, since `rulesSvc` and `eventBus` are both already resolved at Task 4.3.1a's insertion point) but doesn't add a line to that existing decision table. A future contributor splitting `NewSessionService` into smaller functions (plausible — it's already ~250 lines with a comment justifying why it isn't split further) has no signpost that the watcher's `onReload` closure requires `rulesSvc`/`eventBus` pre-resolved. — **Recommendation**: add one line to the existing comment table noting `ClaudeSettingsWatcher`'s same-function constraint.

- [ ] **No test for two settings files changing within the same debounce window.** Task 4.1.1e/4.2.1b's tests only cover single-path scenarios (one malformed path, one changed path per origin test). Given Blocker 2 shows an *unintentional* `origin=mixed` case already exists, there's no test distinguishing it from the *intentional* mixed case (a genuinely distinct global edit and project edit landing in the same 250ms window) — worth a deliberate test once the path-dedup fix from Blocker 2 lands, so "mixed" reliably means "two different files really did both change."

## Minors

- `RuleSource = string` is a type alias, not a distinct defined type — it buys naming/readability only, not compile-time enforcement (a raw string literal like `Rule{Source: "typo-source"}` still compiles and is assignable). The plan's Pattern Decisions table scopes this correctly as a small, non-blocking convenience; just don't rely on it to catch source-string typos.
- pitfalls.md §5 explicitly floats a periodic reconciliation fallback ("insurance against missed fsnotify events... even this codebase's own maintainers don't fully trust fsnotify alone") citing `WatchDirWatcher`'s 60s re-walk as precedent. The plan implements zero backstop and never explicitly states why it's declining that mitigation for this narrower (2-4 path) case — a one-line rationale in the plan or an ADR would close the loop on a concern its own research doc raised.
- The event_converter.go verification claim in Pattern Decisions ("grepped `web-app/src` for `backlog_item_changed` — zero matches... `EventNotification` is converted... at `event_converter.go:51`") checks out against the actual source (`case events.EventNotification:` at line 51, mapping to `SessionEvent_Notification`) — confirmed correct, not just asserted.
