# Pre-mortem: dynamic-rule-reload
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `ClaudeSettingsWatcher.lastGood` map is read/written from two unsynchronized goroutines (fsnotify debounce callback and every concurrent `ReloadClaudeSettingsRules` RPC call), so a near-simultaneous auto-reload and manual reload crash the whole process with `fatal error: concurrent map read and map write`, killing every live tmux session with it (same blast radius as the documented `--tmux-keep-server` incident). | `journalctl --user -u stapler-squad` shows a `fatal error: concurrent map...` panic and a systemd auto-restart timestamp; all in-flight sessions silently rebuilt from scratch. | Hold `w.mu` for the full body of `Reload()` (every `lastGood` read/write), not just a declared-but-unused field; add `TestClaudeSettingsWatcher_ConcurrentReloadCalls_NoRace` (fsnotify-triggered + RPC-triggered reload concurrently, `go test -race`) as a required gate before Phase 5 builds the RPC on top of Phase 4. | P1 |
| 2 | On the actual deployed config (`systemctl --user show stapler-squad -p WorkingDirectory` = `$HOME`), the "project" and "global" settings paths resolve to the same file, so rules load doubled and every self-edit is tagged `origin=mixed` — defeating the one security-visibility signal (ADR-003) this project exists to add, on day one, not as an edge case. | `ApprovalRulesPanel`'s "Claude Settings" tab shows every allow pattern twice; a benign edit to `~/.claude/settings.json` alone logs/toasts `origin=mixed`, training the operator to ignore that tag as noise. | Dedupe resolved (post-`EvalSymlinks`) paths before building the path list in `LoadClaudeSettingsRulesDetailed`; add a regression test with `cwd == home` (mirrors the real systemd config) as a required Phase 1/4 test, and verify against the live unit's actual `WorkingDirectory` before Phase 7 sign-off. | P1 |
| 3 | Every existing `permissions.allow` entry in a user's `~/.claude/settings.json` — almost always configured for the interactive Claude Code CLI, where a human watches and can interrupt — becomes a live, unattended stapler-squad auto-approval rule the instant this merges, with no opt-in step and no confirmation, only a log line buried in Phase 2's startup wiring. | No visible symptom at ship time; discovered later when an unattended worktree session auto-executes a command the operator never intended to trust without supervision, surfaced only via incident review or a "why did it just run X" surprise. | Require an explicit one-time opt-in/confirmation surface on first activation (e.g. blocking startup toast: "N claude-settings rules found — activate as stapler-squad auto-approval rules?") instead of silently merging via `AddRules` at construction; promote adversarial-review's "no first-activation signal" Concern from a suggestion to a plan requirement with a loud, non-dismissable-by-default first-run surface, not just a log line. | P1 |
| 4 | The reload notification ID (`fmt.Sprintf("claude-settings-reload-%d", time.Now().Unix())`) truncates to whole-second granularity; `NotificationContext.tsx` silently drops any notification whose ID collides with one already present, so an auto-reload (fired ~250-500ms after an edit) followed immediately by the manual "Reload rules" click — the exact workflow Story 5.1.1 is written to encourage — loses one of the two toasts. | User clicks "Reload rules" right after an editor autosave; only one toast appears, and the shown rule count may look stale, even though both reloads actually ran. | Generate the ID via `uuid.New().String()` (matching `notification_service.go:104`'s precedent, not `capacity_monitor.go:291`'s collision-prone one); extract the callback's event-construction logic out of the `NewSessionService` closure into a named, unit-tested method per architecture-review's remediation. | P2 |
| 5 | fsnotify reliability is unverified outside this one Linux dev machine's config: macOS (a supported stapler-squad deploy target per `make setup-codesign`) has different watcher-backend quirks, and Linux installs can silently hit `fs.inotify.max_user_watches`; either failure degrades to `log.Warn` + graceful no-op with zero ongoing signal, and the plan explicitly declines the periodic-reconciliation backstop (`WatchDirWatcher`'s 60s re-walk) that pitfalls.md itself raised. | On an affected machine, edits to `~/.claude/settings.json` never take effect without a restart — indistinguishable from the pre-project bug this feature was built to fix — traceable only to a single easy-to-miss startup-time log line. | Add a macOS test/verification pass before shipping (tests so far only cover this Linux config); add the scoped-down periodic reconciliation backstop pitfalls.md §5 flagged, so a missed/failed fsnotify event self-heals within a bounded window instead of silently requiring a restart again. | P2 |

## P1 Items (address before implementation)
- [ ] #1 — Add a `w.mu`-guarded critical section covering all of `Reload()`'s `lastGood` map access (Task 4.1.1b), plus a required `-race` concurrent-reload test gating Phase 5.
- [ ] #2 — Add path dedup logic to `LoadClaudeSettingsRulesDetailed`/the path-listing helper before Phase 4 wires the watcher, plus a `cwd == home` regression test matching the real deployed config.
- [ ] #3 — Add a blocking first-activation opt-in/confirmation step to Phase 2's startup wiring (Task 2.1.1b), not a bare log line, before this ships to any real user.
