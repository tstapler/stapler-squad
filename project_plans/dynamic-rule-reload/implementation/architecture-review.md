# Architecture Review: dynamic-rule-reload
**Date**: 2026-08-06
**Verdict**: CONCERNS

## Constitution Violations
- N/A — `docs/adr/ADR-000-architecture-constitution.md` does not exist in this repository (confirmed: `docs/adr/` contains ADR-001 through ADR-026 plus numbered pre-ADR files, no ADR-000). No hard-constraint check was possible; all findings below are scored purely against the three lenses.

## Blockers

- [ ] **Task 4.3.1a (Epic 4.3, wired from Story 4.1.1/Requirement 5)** — The `onReload` callback's notification ID, `fmt.Sprintf("claude-settings-reload-%d", time.Now().Unix())`, truncates to whole-second granularity. `NotificationContext.tsx` silently drops any notification whose `id` collides with one already present (`if (prev.some((n) => n.id === id)) return prev;` — `web-app/src/lib/contexts/NotificationContext.tsx:194,206`). The realistic collision path is exactly the workflow Story 5.1.1 is written to encourage — "I want to trigger a reload immediately instead of waiting for the debounce window" — i.e., an auto-reload (fired ~250-500ms after the edit, per the debounce window) and an immediately-following manual-RPC reload landing in the same wall-clock second. When that happens, one of the two reload toasts is silently swallowed, directly undermining Requirement 5 ("reload events... are visible"), and it happens with zero test coverage: the callback's message/ID-formatting logic lives inline in `NewSessionService` (`server/services/session_service.go`) rather than in a named, testable unit, and Task 4.3.1f's planned test only asserts `GetClaudeSettingsWatcher() != nil` plus start/stop lifecycle — it never exercises this logic.
  This is also not a novel pattern being introduced — the codebase has both a correct precedent and a buggy one for this exact problem: `server/services/notification_service.go:104` generates `notificationID := uuid.New().String()` (collision-safe), while `server/services/capacity_monitor.go:291` uses the same collision-prone shape the plan's spec mirrors (`fmt.Sprintf("cap-%d", time.Now().Unix())`). The plan is following the bad precedent.
  **Remediation**: (1) generate the ID via `uuid.New().String()` per the `notification_service.go:104` precedent, not the `capacity_monitor.go:291` one; (2) extract the callback's event-construction/message-formatting logic out of the `NewSessionService` closure into a named method (e.g. `func (rs *RulesService) onClaudeSettingsReload(rules []classifier.Rule, origin string)`) that Task 4.3.1f's test suite can call directly and assert against, rather than leaving business logic buried in a DI-wiring closure inside an already-4525-line file.

## Concerns

- [ ] **Epic 3.1/4.3/5.1 (RulesService responsibilities)** — `RulesService` already owns rule CRUD, analytics, and AI-suggestion generation (`server/services/rules_service.go`, 6-field struct). This plan adds `rebuildMu sync.Mutex`, a `claudeSettingsWatcher *ClaudeSettingsWatcher` field + setter, `rebuildClaudeSettingsRules()`, and the `ReloadClaudeSettingsRules` RPC handler directly onto it. Each addition is individually justified (the mutex genuinely needs to guard both rebuild call sites; the watcher handle is needed for the manual-reload RPC), and the plan's own "Option A" analysis correctly keeps the fsnotify I/O loop itself out of `RulesService` — so this is a trend, not a single bad decision. **Recommendation**: no change required now; if a third rebuild trigger or another config-reload source appears later (which ADR-002 itself anticipates as a risk — "a third or fourth rebuild path added later... must remember to also acquire `rebuildMu`"), extract a dedicated type (e.g. `ClassifierComposer`) owning `rebuildMu` plus all rebuild functions, leaving `RulesService` purely CRUD-facing. Flagging now so it isn't a surprise refactor later.

- [ ] **Task 3.1.1a/3.1.1b (`RuleSource` constants)** — `type RuleSource = string` is a **type alias** (note the `=`), not a distinct defined type, so it provides zero compiler-enforced safety: any raw string — including a typo — remains assignable everywhere `RuleSource` is used. `filterRulesBySource(rules []classifier.Rule, allowed ...string)` (Task 3.1.1b) also takes `...string` rather than `...RuleSource`, so the new constants add no protection at their own primary call site either. The Pattern Decisions table frames this as a scoped type-driven-design compromise, but as specified it isn't type-driven at all — it's named string constants that the compiler treats identically to bare strings.
  **Remediation**: declare `type RuleSource string` (a defined type, dropping the `=`) and change `filterRulesBySource`'s signature to `allowed ...RuleSource`, converting to `string` only where it's compared against `Rule.Source` (which correctly stays `string`, per the plan's explicit and reasonable decision not to migrate that field repo-wide). This gets real compile-time protection at the two call sites this project actually touches — `rebuildClassifier()`'s and `rebuildClaudeSettingsRules()`'s allow-lists — at zero blast radius, which is what the Pattern Decisions table already claims to deliver but the `=` alias doesn't.

## Nitpicks

- Task 4.1.1c: `Reload` fires unconditionally on any fsnotify `Write|Create|Rename` event once the debounce timer elapses, without diffing the newly-parsed rules against the previous successfully-parsed content. A no-op save (editor rewrite with identical content, whitespace-only reformat) still produces a log line and — via the Task 4.3.1a callback — a toast. Since Requirement 5 frames the signal as meaningful ("reload events... are visible"), consider comparing the merged rule set against the prior one before calling `onReload`, to avoid toast noise on saves that don't change effective rules.
- Task 4.1.1b: `lastGood map[string][]classifier.Rule` can't distinguish "this path parsed successfully to zero rules" from "this path has never parsed successfully" — both read back as an empty/nil slice. Purely cosmetic (both cases behave identically — no rules contributed), but slightly muddies what `failedPaths` is reporting if a legitimately-empty-but-valid settings file is ever mistaken for a parse failure during debugging.
- Message wording drifts between the auto-reload toast (Task 4.3.1a: `"%d claude-settings rule(s) reloaded (%s)"`) and the manual-RPC toast (Task 5.1.1d / 6.1.1c: `"Reloaded N claude-settings rule(s)."`) for what is, from the operator's point of view, the same event. Minor voice inconsistency, not a correctness issue — worth aligning during implementation if convenient.

## Positive notes (verified, not findings)

- ADR-002's choice of a plain `RulesService`-level `sync.Mutex` over classifier-level locking or a Unit-of-Work abstraction is consistent with this repo's own `docs/adr/011-prefer-lock-free-concurrency.md`, whose guideline table explicitly recommends `sync.Mutex` (not lock-free/CAS) for "Complex State Transitions" — the read-filter-replace rebuild sequence is exactly that shape, so ADR-002 isn't in tension with ADR-011 despite the latter's general lock-free preference.
- `fsnotify` is already a repo dependency (`go.mod:16`), and the plan's watcher shape (struct + `Start(ctx)`/`Stopped()` + parent-dir watch + debounce) matches existing precedents almost exactly (`session/history_watcher.go`'s `HistoryFileWatcher`, `session/unfinished/watcher.go`'s `WatchDirWatcher`) — no new dependency, no reinvention, consistent with build-vs-buy.md's "fsnotify direct, no viper" recommendation.
- `ClaudeSettingsWatcher` is callback-injected rather than taking a concrete `*RulesService` or a premature interface — this is the correct pattern per `.claude/rules/interface-pollution-checklist.md` (concrete type, no speculative interface, consumer-side inversion via a plain func value).
- The `ClaudeSettingsPathResult`/`LoadClaudeSettingsRulesDetailed` split is a clean parse-at-boundary: raw JSON is converted into `classifier.Rule` domain values inside the parser file, with per-path success/failure carried as data rather than swallowed — verified against the existing `LoadClaudeSettingsRules` call site (`server/services/claude_settings_parser.go`), confirmed to have zero existing callers via the plan's own cited `git log -S` search, matching requirements.md's premise.
