# Research: Feature Landscape & Edge Cases — dynamic-rule-reload

## 1. What `LoadClaudeSettingsRules()` actually parses

`server/services/claude_settings_parser.go` (147 lines, small — read in full).

- **Paths searched, in order** (`LoadClaudeSettingsRules(projectDir string)`):
  1. `~/.claude/settings.json` (priority 150, label `global`)
  2. `~/.claude/settings.local.json` (priority 160, label `global-local`)
  3. `<projectDir>/.claude/settings.json` (priority 170, label `project`) — only if `projectDir != ""`
  4. `<projectDir>/.claude/settings.local.json` (priority 180, label `project-local`)
  - Higher priority = evaluated first by `RuleBasedClassifier`, so project rules beat global rules, and `.local.json` beats the non-local file at the same scope.
- **Parsing**: reads each file with `os.ReadFile`, unmarshals only the top-level `permissions.allow` array (`ClaudePermissions.Allow`); `permissions.deny` is parsed into the struct but **never converted to rules** — deny entries are silently dropped (pre-existing gap, not in scope per requirements but worth flagging).
- **Missing file**: `os.IsNotExist` → `ErrSettingsNotFound`, function just `continue`s (logs a `Warn`, not an error). Any other read error (permission denied, etc.) also just logs+continues — the loop never returns an error, so a partially-broken settings tree degrades to "fewer rules," not a crash.
- **Glob→regex**: `globToRegex()` only supports `*` (via `regexp.QuoteMeta` + replacing escaped `\*` with `.*`, anchored with `^`). No `**`, `?`, or brace expansion support — matches Claude Code's own settings.json glob dialect only partially.
- **Rule IDs**: deterministic, index-based — `claude-settings-<label>-<i>` (e.g. `claude-settings-project-0`). Re-running `LoadClaudeSettingsRules` with the same file contents produces the same IDs, which matters for a reload path that needs to diff/replace rather than duplicate.
- **Malformed JSON**: `json.Unmarshal` error is wrapped and returned from `ParseClaudeSettings`, which `LoadClaudeSettingsRules` treats the same as "not found" — logs and skips that one file, does **not** abort the whole load. This is reload-safe by construction: a bad edit to one of the 4 files can't wipe rules loaded from the other 3, *provided the reload path also preserves previously-loaded rules from files that transiently fail to parse* (see §4).
- **No caching/mtime tracking inside the parser** — every call does a fresh `os.ReadFile` + `json.Unmarshal` for all (up to 4) paths. Cheap enough to call on every fsnotify event without needing a separate diff step.

## 2. History of the missing call site — confirmed dead code, not a regression

Contrary to the requirements.md framing ("regression"), the call site was **never wired**, not removed:

- `git log --all -S"LoadClaudeSettingsRules" -- server/services/session_service.go` returns **zero commits** — the string has never appeared in that file at any point in reachable history.
- `git log --all -S"LoadClaudeSettingsRules"` (repo-wide) shows exactly one hit: commit `1c31f024d` ("feat: add auto-approval rules engine with analytics and workspace switcher", 2026-03-26), which is the commit that *defines* the function in `claude_settings_parser.go`. Its diff of `session_service.go` (`git show --stat 1c31f024d -- server/services/session_service.go` → 110 insertions, 0 deletions) never references Claude settings at all.
- The archived doc `docs/archive/tasks/completed/permissions-analysis-auto-approvals.md` (ADR-022, same-era doc) **claims** "Claude settings are read at server startup only (when `LoadClaudeSettingsRules()` is called from `NewSessionService()`)" — this claim is false against the actual code; it appears to be aspirational documentation written for a design that was never implemented, not documentation of a real, later-removed behavior.
- Current `NewSessionService()` (`server/services/session_service.go:252-311`) builds the classifier via `classifier.NewRuleBasedClassifier()` (seed rules only) then merges only `rulesStore.ToRules()` (DB-backed user rules) at line 304-308. No `claude-settings` source rules are ever added at startup today — `pkg/classifier`'s `SeedRules()` + `rulesStore` output is the entire startup rule set.
- **However**, downstream code already assumes claude-settings rules *can* exist in the classifier and is written to coexist with them correctly:
  - `RulesService.allRuleSpecs()` (`server/services/rules_service.go:410-429`) explicitly filters `rs.classifier.Rules()` for `Source == "claude-settings"` when building the list for the UI.
  - `RulesService.rebuildClassifier()` (`rules_service.go:431-443`) partitions existing classifier rules into `Source != "user"` (kept) vs `user` (replaced), so calling `ReplaceRules` for a DB-rule reload will **not** clobber claude-settings rules once they exist — this path is safe to build on.
  - Conclusion for planning: the "re-wire" step is additive (call `LoadClaudeSettingsRules` once at startup and `AddRules`/merge into the classifier), not a fix to broken plumbing — the plumbing around it was already built for this source and never exercised.

## 3. Global classifier vs. per-session/per-worktree scoping — real design tension

- There is exactly **one** `*classifier.RuleBasedClassifier` per server process, constructed once in `NewSessionService()` and returned via `SessionService.GetClassifier()` (`session_service.go:663`). `ApprovalHandler` holds a single `h.classifier` (`approval_handler.go`) shared across every concurrent session/tmux pane/worktree.
- `pkg/classifier.Rule` (`classifier.go:347-377`) has **no project/path-scoping field** — nothing like `ProjectPath` or `AppliesToWorktree`. A rule loaded via `LoadClaudeSettingsRules(projectDir)` is, once merged into the shared classifier, evaluated against *every* session's requests regardless of which worktree they're running in.
- `LoadClaudeSettingsRules(projectDir string)` takes a single `projectDir` — there is no historical or current call site to check for how this was intended to be invoked with a real path, since it's never been called. There is no existing convention to follow here.
- Per-request context **does** carry the right information to scope correctly at classify time instead: `ApprovalHandler` builds `classCtx := h.classifier.BuildContext(payload.Cwd)` per request (`approval_handler.go` ~line 309), and `ClassificationContext` (`classifier.go:61-76`) already includes `Cwd`, `IsGitRepo`, `RepoRoot`, `IsWorktree`. `Classify(payload, ctx)` sees the requesting session's actual working directory on every call.
- **This is the key open design question for the planning phase**: naively calling `LoadClaudeSettingsRules(oneArbitraryProjectDir)` once at startup only correctly reflects *one* worktree's project-level settings for the whole server — wrong for every other concurrently open session in a different repo/worktree. Two shapes to weigh in `/sdd:3-plan`:
  1. **Global-only reload (matches original ask's scope)**: call `LoadClaudeSettingsRules("")` (global paths only, `projectDir=""` skips paths 3-4) at startup + on watch events; explicitly punt project-level `.claude/settings.json` overlay per-worktree as future work. Simplest, matches "in scope" item 1's literal ask (re-wire + watch), avoids the multi-tenancy question entirely.
  2. **Per-request project overlay**: don't bake project rules into the shared classifier at all; instead evaluate `<RepoRoot from classCtx>/.claude/settings.json` at classify time (already have `RepoRoot`/`Cwd` available) with its own small cache+watch keyed by resolved repo root. More correct for multi-worktree but a materially bigger change than "add a watcher to the existing single-classifier design," and the requirements.md scope reads as expecting the smaller change (reuses "the existing ReplaceRules() atomic-swap path").
  - Flagging this now because requirements.md item 3 in scope says "fsnotify watch on the resolved settings.json path(s) (global + project)" as if there's one project path — there isn't, structurally, given N concurrent worktree sessions. The plan phase needs to pick one of the above (or explicitly scope project-level watching to "the server's own repo checkout" / a configured single directory) rather than silently defaulting to whichever worktree happens to start the server.

## 4. Edge cases

| Edge case | Current behavior if naively implemented | Notes |
|---|---|---|
| Malformed JSON during reload | `ParseClaudeSettings` returns wrapped error; `LoadClaudeSettingsRules` logs+skips that file only (see §1) — **safe by construction** at the parser level. Risk is at the *call site*: if the reload handler does `classifier.ReplaceRules(LoadClaudeSettingsRules(...))` wholesale, a bad edit to `settings.json` doesn't crash but silently drops rules from that file until fixed — verify the reload path preserves the last-known-good rules for a file that fails to parse, not just "don't crash." |
| File deleted then recreated | fsnotify emits `Remove` then (on recreate) `Create`. Existing idiom in `session/history_watcher.go`'s `handleEvent` treats `Create\|Rename\|Write` as the trigger set and ignores `Remove`/`Chmod` — a straight port would silently stop watching after a `Remove` unless the watch is re-armed. `HistoryFileWatcher` watches a *directory* (`w.watchDir`), not the file itself, which survives delete+recreate of children automatically — the same "watch the parent dir" idiom (also documented for the retired `RulesStore.WatchAndReload`, see §5) should be used here rather than watching the settings.json file paths directly, since `fsnotify.Watcher.Add` on a single file breaks permanently once that inode is removed. |
| Symlinked settings files | This repo's own dotfiles convention (per `~/dotfiles` cfgcaddy symlinking, referenced in global CLAUDE.md) means `~/.claude/settings.json` is commonly a symlink into a dotfiles repo. `fsnotify` on Linux (inotify) watches the *target* path as resolved at `Add()` time; if the symlink itself is atomically replaced (`ln -sfn`) fsnotify does **not** follow the new target automatically — this matches the existing `filepath.EvalSymlinks` idiom used elsewhere in this codebase (`config/defaults.go:129`, `server/services/slash_command_service.go:61,76`, `session/history_detector.go:75`, `session/history_transfer.go:33`) specifically to resolve symlinks before doing path-sensitive work. The new watcher should resolve symlinks with `filepath.EvalSymlinks` before calling `watcher.Add`, and re-resolve+re-add on watch-directory events in case the symlink target changes. |
| Rapid successive edits (editor autosave / atomic rename) | The retired `RulesStore.WatchAndReload` docstring (`docs/archive/tasks/completed/permissions-analysis-auto-approvals.md:325`) describes "watches the parent directory... debounce timer to coalesce rapid filesystem events" as the established idiom for this exact problem — **but note (§5) this description does not match any code that ever existed in this repo's git history**; treat it as a design note to reapply, not a pattern to copy from real code. The closest *actually-shipped* debounce/coalescing reference is worth checking in `session/unfinished/scanner.go` / `watcher.go` (`periodicReWalk`) though that solves a different problem (periodic re-scan, not edit-debounce). A reload handler should still debounce (e.g. 100-300ms) before calling `LoadClaudeSettingsRules` + `ReplaceRules`, since editors doing atomic-rename saves emit multiple events (`Remove`+`Create` or `Rename`+`Create`) per logical save. |
| Multiple worktree sessions wanting different project-level rules from one shared classifier | See §3 — no existing scoping mechanism; this is a design decision for the plan phase, not an implementation detail. |

## 5. Existing "watch a config file / hot-reload" idioms in this codebase

Repo-wide `fsnotify` usage (from `grep -rl fsnotify --include='*.go' .`):

| File | Purpose | Relevant pattern |
|---|---|---|
| `session/history_watcher.go` (`HistoryFileWatcher`) | Watches `~/.claude/projects/` for new `.jsonl` transcript files | **Closest usable template.** Watches the directory (not individual files) + all existing subdirs found via `filepath.WalkDir`; degrades gracefully (`Start()` returns nil, not error, if the dir doesn't exist — "polling fallback still works" per comment) instead of failing hard; `handleEvent` filters on `event.Op&(Create\|Rename\|Write)` and does cheap suffix/prefix checks before invoking the callback; exposes `Stopped() <-chan struct{}` for shutdown sync. No debounce currently, but structurally the best starting point given it already handles "directory may not exist," "watch subdirs too," and clean goroutine shutdown via `ctx`. |
| `session/unfinished/watcher.go` (`WatchDirWatcher`) | Watches configured directories + pinned repos for `.git/` changes to trigger unfinished-work scans | Adds a **fallback-to-polling** pattern: `fsnotify.NewWatcher()` failure just sets `w.watcher = nil` and logs a warning rather than failing `NewWatchDirWatcher`; combines the fsnotify loop with `periodicReWalk(ctx)` running concurrently as a safety net against missed events. Worth reusing the "always keep a periodic reconciliation pass in addition to fsnotify" belt-and-suspenders idea for settings.json, since a missed inotify event (e.g. from watch-descriptor exhaustion) would otherwise silently leave stale project rules with no self-healing. |
| `session/unfinished/gogitstore/mmapwatch.go`, `registry.go` | fsnotify on git index/mmap files for the unfinished-work git store | Narrower/lower-level use (mmap invalidation), less directly analogous — skim only if the plan needs mmap-adjacent detail, otherwise skip. |
| `server/services/rules_store.go` `WatchAndReload()` | **Currently a no-op** (`// WatchAndReload is now a no-op as we use shared DB.`) | Do **not** treat the surrounding ADR-022 doc prose (parent-dir watch + debounce timer) as "this used to be real code" — confirmed via `git log --all -S"fsnotify" -- server/services/rules_store.go` (zero hits) and `git log --all -S"WatchAndReload"` (single hit, the commit that added the current no-op form) that no fsnotify implementation has ever existed in this file's reachable history. The doc description is a design note/aspiration from the same era as the false "called from NewSessionService()" claim (§2), not a real prior implementation to diff against or resurrect. |
| `daemon/daemon.go`, `main.go`, `server/auth/setup.go`, `session/mux/autodiscover.go`, `session/tokens/store.go` | Various other fsnotify consumers | Not directly relevant to config-file hot-reload; skipped for this research pass (grep hit only, not read in full). |

**Established idiom to follow**: watch the parent directory (survives delete+recreate and atomic-rename saves), filter events by suffix/basename before reacting, degrade gracefully rather than erroring hard when a watched path doesn't exist yet, and pair fsnotify with a periodic reconciliation fallback. `HistoryFileWatcher` is the best structural template to adapt; add debounce (not present in any existing watcher — new work) and `filepath.EvalSymlinks` resolution (present elsewhere in the codebase, not in any watcher — also new work) on top of it.

## Summary of implications for planning

1. Re-wiring `LoadClaudeSettingsRules()` into `NewSessionService()` is additive and low-risk — downstream code (`rebuildClassifier`, `allRuleSpecs`) already tolerates `claude-settings`-sourced rules correctly.
2. The "project-level settings" scope needs an explicit decision in `/sdd:3-plan`: global-only watching (simplest, matches literal requirements text) vs. per-worktree overlay evaluated at classify-time using the `RepoRoot`/`Cwd` already present in `ClassificationContext` (more correct, bigger change). Recommend flagging this ambiguity to the user/plan phase rather than assuming.
3. `HistoryFileWatcher` (`session/history_watcher.go`) is the right template to adapt for the new settings watcher; layer in debounce and `filepath.EvalSymlinks` resolution, neither of which exists in any current watcher in this repo.
4. The archived ADR-022 doc (`docs/archive/tasks/completed/permissions-analysis-auto-approvals.md`) contains at least two claims that don't match git history (the `NewSessionService()` call site, and a "prior fsnotify-based WatchAndReload") — treat it as directional design notes, not as ground truth about what was ever actually built.
