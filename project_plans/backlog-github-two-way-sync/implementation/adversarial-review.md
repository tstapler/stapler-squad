# Adversarial Review: backlog-github-two-way-sync

**Date**: 2026-08-03
**Verdict**: CONCERNS (repaired 2026-08-03 — both blockers resolved and independently re-verified; 5 CONCERNS remain, not blocking)

## Blockers (resolved)

- [x] **RESOLVED 2026-08-03** — plan.md patched: `handleForwardSyncClose` now calls the pre-existing `storage.CreateSourceSyncEvent` (verified real, `session/storage.go:904` / `session/ent_repository_backlog.go:1514`, same method `SyncOne`'s Fetch-failure path already uses) on both `CloseIssue` and `PostIssueComment` failure, giving Story 4.3.2's row-level warning real data. Unresolved Question #1 rewritten to match. Independently re-verified — not an invented API.
- [x] **RESOLVED 2026-08-03** — plan.md patched: `CloseIssue`'s signature changed to `(time.Time, error)`, returning the PATCH response's own `updated_at`; the forward-sync subscriber advances `GitHubSyncedIssueUpdatedAt` from that value, falling back to `time.Now().UTC()` only when the timestamp is genuinely unavailable (matches ADR-003's own stated design verbatim). Independently re-verified consistent across Domain Glossary, `externalIssueCloser`, Epic 1.1, and Epic 1.2 — no remaining wall-clock-only path.

## Blockers (original findings, now resolved above)

- [ ] **Forward-sync write failures have no durable, queryable record, so Unresolved Question #1's deferral rests on a safety net that doesn't exist.** `handleForwardSyncClose` (plan.md Task 1.2.1b) only calls `log.WarningLog.Printf` on a failed `CloseIssue`/`PostIssueComment` — nothing is written to `SourceSyncEvent`/sync history or any other DB-backed table. Story 4.3.2's "persistent row-level warning" reads `historyBySource`, which is populated exclusively by `SyncOne`'s Fetch-cycle path (`CreateSourceSyncEvent`/`FinishSourceSync`), not by the forward-sync subscriber. Unresolved Question #1 explicitly leans on "failed-write visibility (Phase 4's persistent row-level warning)" to justify not building a retry queue — but that warning can never fire for a forward-sync failure, since the two mechanisms don't share a data path. A permanently-failing forward sync (write-scope token revoked while read-scope still works, a persistent rate limit, a transferred/deleted issue) is invisible to the user forever. — **Recommendation**: give forward-sync outcomes a persisted, queryable record (e.g. reuse `SourceSyncEvent`, or add `ForwardSyncLastError`/`ForwardSyncFailedAt` to `ItemSource`/`BacklogItem`) before treating "Phase 4 covers it" as true, or explicitly narrow Story 4.3.2's scope and re-open Unresolved Question #1 as a real gap.

- [ ] **The loop-prevention watermark is written from local wall-clock time, not GitHub's own timestamp, contradicting ADR-003's own rejected-alternative reasoning — and the specified `CloseIssue` signature makes the ADR's preferred approach structurally impossible to implement.** ADR-003 explicitly rejects wall-clock comparison ("local/remote clock skew makes a wall-clock window an unreliable... guard") and mandates storing GitHub's own `issue.updated_at`, "prefer[ring] the API response's own timestamp where GitHub returns one." But `handleForwardSyncClose` (plan.md lines 719-723) sets the watermark with `now := time.Now().UTC()` unconditionally, and `CloseIssue`'s specified signature (`func (p *GitHubIssuesPlugin) CloseIssue(ctx, config, externalID, existingLabels, closeLabel) error` — plan.md line 563) has no return value through which the PATCH response's `updated_at` could ever reach the caller. Every production close is forced onto the "conservative fallback" ADR-003 only meant as a last resort, defeating the reason a GitHub-timestamp watermark was chosen over wall-clock in the first place (build-vs-buy §3, ADR-003 Decision). This is precisely the mechanism AC7 ("no infinite sync loop") depends on. — **Recommendation**: change `CloseIssue` to also return the issue's `updated_at` from the PATCH response body (GitHub's REST API returns the full updated issue object), thread that value into the watermark write, and reserve `time.Now()` for the genuinely-unavailable case ADR-003 anticipated, not the default path.

## Concerns

- [ ] **`state=all` shares an already-unpaginated, fixed 50-item page with closed issues for the first time, silently degrading open-issue coverage on larger repos.** `Fetch` has no `Link`-header pagination (confirmed: `session/backlog_plugin_github.go:16,90` — `per_page=%d` with `githubIssuesPerPage=50`, no page-2+ handling; also flagged pre-existing in `research/features.md` §1). Before this plan, that one page was 100% open issues; after switching to `state=all`, the same fixed page is now split between open and closed issues (GitHub's default sort mixes both), so a repo with more open+closed issues than one page can silently push older open issues out of the observable set — a compounding effect of this plan's core AC0 change that no phase/task revisits. — **Recommendation**: at minimum, flag this as a known limitation (it currently isn't mentioned anywhere in plan.md), or scope a pagination fix into Phase 0 given `state=all` makes the existing gap materially worse, not just pre-existing.

- [ ] **Duplicate `ItemSource`s on the same repo go from harmless to actively cross-talking once forward+backward sync are live, and the plan's "known limitations" section undersells the new failure mode.** Today, two `ItemSource`s pointed at the same repo just independently re-import the same read-only data (annoying, not harmful). Once forward sync writes are added: if item A (under source S1) reaches `done`, forward sync closes the shared GitHub issue; source S2's own, unrelated backlog item for that same issue (`GetBacklogItemByExternalID` is source-scoped, so S1 and S2 hold two independent rows) will then observe that same issue as closed on S2's next tick, and — if `BackwardSyncEnabled` on S2 — get silently archived, even though nobody ever touched S2's copy. This is a new, write-triggered failure mode this plan introduces, not merely an unaddressed pre-existing gap; plan.md's "Known limitations" bullet ("independent, mutually-unaware duplicate imports... No uniqueness constraint or save-time warning is added") doesn't call out this specific cross-source side effect. — **Recommendation**: at minimum add a save-time warning when creating a second `ItemSource` for a repo/owner pair that already has one, given how cheap that check is relative to the blast radius.

- [ ] **Forward sync has no reconciliation/backstop sweep — a missed event is permanently missed.** The mechanism is a pure in-memory `EventBus` subscriber (`pkg/events/bus.go`: `Publish` is non-blocking and drops on a full subscriber buffer; the ring buffer supporting `EventsSince` replay is neither durable across restarts nor consumed by the specified subscriber skeleton, which just calls `bus.Subscribe(ctx)` fresh). A `done` transition that fires during a deploy/restart window, or a startup wiring bug that leaves `bus`/`syncLoop`/`storage` nil (the nil-guard in Task 1.2.1a just logs and returns — the whole feature silently never starts), permanently skips that item's issue close with nothing to catch it later. This was a real tradeoff named in Pattern Decisions ("Option B: a new dedicated poller... rejected: duplicates SyncLoop machinery for no new capability") but the resulting gap — no self-healing at all, unlike the read side which re-observes everything every tick via `Fetch` — isn't discussed anywhere as a residual risk. — **Recommendation**: at minimum, log/monitor whether the subscriber actually started (today a silent no-op), and consider a periodic low-frequency reconciliation check (e.g. as part of `SyncOne` itself) for `done` items whose linked issue is still open and `ForwardSyncEnabled` is true.

- [ ] **Extending an already-unsafe proto3 "always overwrite" settings pattern to 3 more fields multiplies an existing landmine's blast radius instead of fixing it.** Confirmed live: `UpdateItemSource` (`server/services/backlog_service_lifecycle.go:711-712`) does `enabled := req.Msg.Enabled; update.Enabled = &enabled` unconditionally — there's no way to distinguish "the caller didn't intend to touch `enabled`" from "the caller explicitly wants it false" in proto3. Task 4.3.1a acknowledges this exact landmine and works around it by requiring every future toggle call site to echo back all six now-mutable fields (`displayName`, `enabled`, `forwardSyncEnabled`, `backwardSyncEnabled`, `forwardSyncCloseLabel`, `token`) from current state — correct as a workaround, but it's propagating a known-unsafe pattern rather than fixing it (e.g. with `google.protobuf.BoolValue` wrappers or an explicit field mask), so any future call site (including code outside this plan) that forgets to echo one of the six fields will silently clobber it back to zero-value. — **Recommendation**: consider a field mask or wrapper-type fix now, while only one bad precedent (`enabled`) exists, rather than after three more fields depend on the same footgun.

- [ ] **First-enable-of-backward-sync blast radius (Unresolved Question #3) is real and only mitigated by static UI copy.** Enabling `BackwardSyncEnabled` on a source with a backlog of already-imported, already-closed-on-GitHub items will bulk-archive all of them (bounded to `idea`/`refining`/`ready`/`queued` per ADR-002, so non-destructive, but still a surprising background action) on the very next `SyncOne` tick, with no preview, dry-run, or per-item confirmation — just an inline warning shown once, before the fact. The plan is correct that no AC mandates a preview, but given the effect is "silently reclassify N cards while the user isn't looking," a stronger callout (e.g. surfacing a count of affected items before the toggle takes effect) would be proportionate. Flagged as a should-fix, not a hard blocker, since it's already self-identified and bounded to a non-destructive transition.

## Minors

- Task 2.1.1b's closed-issue/reopened-issue block and the field-update (`anyField`) block can both increment `SyncOne`'s `created`/`updated`/`skipped`/`errored` counters for the same item in the same tick; the plan flags this itself ("verify at implementation time that SyncOne's counters aren't double-incremented") but leaves it unresolved rather than specifying the correct accounting.
- The `Labels` `UserModifiedFields` local-wins gate (Epic 2.3) is unreachable dead code on ship day — no UI writes `"labels"` to that set today — which the plan already self-documents in Unresolved Question #4 as intentional forward-compatibility, not a bug.
- Items in `in_progress`/`review`/`pr_pending` whose linked issue closes externally get a log-only no-op with no UI surfacing beyond the process log — a deliberate, well-reasoned (ADR-002) but real, user-invisible product gap; ADR-002 itself flags this as a candidate follow-up ("a card-level indicator") if it proves too silent in practice.
- Task 5.1.1d's e2e coverage for the two new Settings toggles is explicitly called out as optional/non-blocking, consistent with the ACs — noted for completeness, not an issue.
