# Validation Plan: backlog-github-two-way-sync

**Date**: 2026-08-03

## Happy Path Scenario

Given a backlog item imported from a GitHub issue via an `ItemSource` with `ForwardSyncEnabled=true`, when the user transitions that backlog item to `done` in stapler-squad, then `StartBacklogGitHubForwardSyncSubscriber` calls `CloseIssue` on the linked GitHub issue, the issue closes on GitHub with a bot comment, `GitHubSyncedIssueUpdatedAt` is persisted as the loop-prevention watermark, and the backlog item's card/detail view continues to show the "imported from GitHub" badge with the issue's `ExternalURL` and `Labels`.

## Migration Test

`TestSchema_NewColumnsBackwardCompatibleWithPreExistingRows` (`session/ent_repository_backlog_test.go`), type **Migration**: creates a `BacklogItem`/`ItemSource` row using a schema snapshot equivalent to pre-migration (i.e. without setting `labels`, `external_url`, `github_synced_issue_updated_at`, `forward_sync_enabled`, `backward_sync_enabled`, `forward_sync_close_label`), runs `client.Schema.Create(ctx)` (the actual auto-migration entrypoint, `session/ent_repository.go`), then fetches the row back and asserts: no panic, `Labels` reads as `nil`/empty, `ExternalURL` reads as `""`, `GitHubSyncedIssueUpdatedAt` reads as `nil`, and the two new `ItemSource` bools read as their declared defaults (`false`). This project's migration mechanism (ent auto-migration via `client.Schema.Create(ctx)` on every process startup) has **no down-migration by design** — per the Migration Plan's "Reversibility" note and matching ADR-001's precedent from the sibling `backlog-github-issue-link` project — so this test is named for what is actually guaranteed (forward-compatible reads of pre-existing rows against the new schema), not `_should_be_reversible`, which this system does not support and is not expected to.
