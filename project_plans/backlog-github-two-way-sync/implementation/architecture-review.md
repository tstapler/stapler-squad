## Blockers (resolved)

- [x] **RESOLVED 2026-08-03** — plan.md patched: added `Storage.GetItemSourceByID` (Epic 0.5/Task 0.5.3f, renaming the pre-existing in-package `EntRepository.GetItemSourceByID` to `GetItemSourceEntByID` to free the name) and changed `StartBacklogGitHubForwardSyncSubscriber` to take `registry *session.PluginRegistry` directly, mirroring `BacklogService.pluginRegistry`. Independently re-verified against live source (`session/storage.go`, `session/repository.go`, `server/services/backlog_service.go:209`, all call sites of the renamed method) — fix is real, not a relabeling; a wiring gap it surfaced (`PluginRegistry` missing from `RuntimeDeps`/`ServerDependencies`) was also closed in the same patch (Task 1.2.1c).
- [ ] **Epic 1.2 / Task 1.2.1b** (`server/services/backlog_github_forward_sync.go`, new) — `handleForwardSyncClose`'s example code does `entRepo, ok := storage.Repo().(*session.EntRepository)` and `syncLoop.Registry().Get(...)`, but neither accessor exists. Verified: `session/storage.go` exports only `CreateItemSource`/`ListItemSources`/`UpdateItemSource`/`DeleteItemSource` on `*Storage` — no singular `GetItemSourceByID`, and the `repo` field is unexported, type-asserted only from *inside* package `session` today (`session/backlog_sync.go:105`, `sl.storage.repo.(*EntRepository)`). Implemented as literally written, this either fails to compile or forces a new, precedent-breaking hole in `Storage`'s encapsulation (exporting the internal ent-repository type to `server/services`) — no existing cross-package caller does this; `BacklogService` already solves the parallel "get a plugin instance" problem by holding `pluginRegistry *session.PluginRegistry` directly as its own field (`server/services/backlog_service.go:209`, whose `Get(id) (ItemSourcePlugin, bool)` is already public). This is a load-bearing gap for AC3 — without a real accessor, forward sync cannot read `ForwardSyncEnabled`/`ForwardSyncCloseLabel` for a source at all — and Phase 0 (Epics 0.1-0.6) does not list a task to add one.
  **Remediation**: add a Phase 0 prerequisite task exporting `func (s *Storage) GetItemSourceByID(ctx context.Context, id string) (*ItemSourceData, error)` (a thin wrapper the same shape as the existing `ListItemSources`/`UpdateItemSource`), and change `StartBacklogGitHubForwardSyncSubscriber`'s signature to take `registry *session.PluginRegistry` directly as its own parameter (mirroring `BacklogService`'s existing pattern) instead of trying to reach it through `SyncLoop`.

## Concerns

- [ ] **Epics 2.1-2.4, `SyncOne`** (`session/backlog_sync.go`) — SRP/testability: the existing function is already ~131 lines with its own `anyField`/`updated`/`skipped`/`errored` accumulator pattern (verified). This plan adds four more independent inline branches (closed-issue status, reopened log-only, labels backward-sync, `ExternalURL` backfill), each reading/writing the same shared counters and independently calling `TransitionBacklogItemStatus`/`UpdateBacklogItem`. Task 2.1.1b's own note — "verify... counters aren't double-incremented" — treats a structural risk as an afterthought to check at implementation time rather than a guarantee. Every new regression test in Epics 2.1-3.2 exercises the full `SyncOne` loop end-to-end; none of the new backward-sync rules are unit-testable in isolation (only the already-clean `determineBackwardSyncTarget`/`GuardedTransitionAllowed` pure functions are).
  **Recommendation**: extract a single `applyBackwardSync(existing, data, source) backwardSyncResult` function returning one struct (status target + label delta + watermark + which counter bucket to increment), and have `SyncOne` apply that result in one place, rather than four ad hoc inline blocks sharing mutable state.

- [ ] **Epic 0.2 (`State` field) + Epics 2.1/2.2** — primitive obsession / illegal states: `githubIssue.State`/`ExternalItem.State` is a bare `string`, compared via `== "closed"` (Task 2.1.1b) and `== "open"` (Task 2.2.1a) in two separate call sites feeding directly into the safety-critical ADR-002/ADR-003 policies. An unrecognized value (deserialization failure defaulting to `""`, or a future typo) silently falls through both branches as a no-op with no error surfaced, and there is no exhaustive check that would catch a future third value.
  **Recommendation**: parse into a typed enum at the JSON-decode boundary in `backlog_plugin_github.go` (`type GitHubIssueState string; const (GitHubIssueStateOpen = "open", GitHubIssueStateClosed = "closed")`) — parse-don't-validate — and switch exhaustively on it in `SyncOne` so an unrecognized state is a visible, loggable case instead of a silent double-no-op.

- [ ] **Epic 0.5 / Task 4.3.1a** (`UpdateItemSource` RPC contract) — Task 4.3.1a's own comment acknowledges the handler treats `Enabled` (and, per Task 0.5.3c, the new `ForwardSyncEnabled`/`BackwardSyncEnabled`) as unconditionally overwritten by whatever the request carries, forcing each new single-toggle frontend function to manually thread every other current field value through just to avoid clobbering it — the plan explicitly cites this as the same pre-existing bug flagged in Unresolved Question #2 (`CreateItemSource` hardcoding `Enabled: true`). This plan adds three more fields to that same fragile full-replace contract instead of containing the blast radius it already knows about.
  **Recommendation**: use proto3 `optional` on the three new `UpdateItemSourceRequest` fields (generates `*bool`/`*string` wrappers with real field-presence semantics), so a single-toggle call can omit unrelated fields safely instead of extending the "must always pass the whole object" footgun to more fields.

- [ ] **Epics 1.2/2.1/3.x — watermark write is a separate, non-transactional step** — a single `SyncOne` iteration (or the forward-sync subscriber) can perform up to three separate writes to the same `BacklogItem` (field update, `TransitionBacklogItemStatus`, watermark `UpdateBacklogItem`) with no shared transaction. A crash between the status transition and the watermark write happens to be harmless for the specific Risk A/B scenarios ADR-003 targets (because `determineBackwardSyncTarget` already excludes terminal statuses from re-firing), but that safety is incidental to the state machine, not a designed guarantee of the write sequence itself — a future backward-sync branch added without that same structural luck could reintroduce a partial-write hazard, exactly the risk ADR-003's "Consequences" section warns future maintainers about.
  **Recommendation**: add an explicit comment at each such write site cross-referencing ADR-003's invariant, or fold the status transition + watermark write into one `Storage`-level method so the discipline is enforced once rather than repeated by convention at every call site.

## Nitpicks
- Task 1.2.1b's pseudocode is written with the same specificity as the rest of the plan (which elsewhere cites exact line numbers) but is self-admittedly speculative ("verify each against the live code... exact method/field names may need adjusting") — worth an explicit banner at the top of that task pointing implementers to check `Storage`'s and `SyncLoop`'s real exported surface first, given the Blocker above shows the guess was wrong.
- `ExternalURL`, `Labels`, and `GitHubSyncedIssueUpdatedAt` are added as three more flat fields on `BacklogItemData` rather than a grouped `GitHubProvenance`-style value object. This matches the repo's existing all-flat-DTO convention (e.g. `PrFeedbackAddressedAt`), so it's not wrong, but a one-line rationale in the plan would save a future reader from mistaking it for an oversight.
- Epic 0.4.3's `SyncLoop.workflowEngine` silently defaults to `NewDefaultWorkflowEngine()` when the constructor is passed `nil` — a small implicit-default smell on an interface-typed field. Fine as designed, but should be called out in the field's doc comment, not just the constructor body, so a future caller passing an explicit engine isn't surprised by the fallback behavior.
