# Pre-mortem: backlog-github-two-way-sync
**Date**: 2026-08-03

Five most plausible failure modes. Each goes beyond (or directly validates the insufficiency of) what `plan.md`'s own Unresolved Questions / Known Limitations already self-document — findings 1 and 2 were confirmed by reading the actual code paths the plan's tasks touch, not just the plan text.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Forward sync's watermark write (Task 1.2.1b) stamps `GitHubSyncedIssueUpdatedAt` with local `time.Now().UTC()`, not GitHub's real `updated_at` — `CloseIssue`'s signature (Task 1.1.1a) returns only `error`, never the PATCH response's issue object, so the "prefer the API response's own timestamp" branch ADR-003 calls out is unreachable; every forward-sync watermark write silently falls into the "conservative approximation" fallback, reintroducing the clock-skew problem ADR-003's Option B was chosen specifically to avoid. | A backlog item manually reopened shortly after forward-sync auto-closed it gets silently pulled back toward `archived` on the very next `SyncOne` tick — Risk B (the loop AC7 exists to prevent) recurring, because GitHub's real close-time timestamp landed a few seconds after the locally-approximated one. | Change `CloseIssue` to parse and return the PATCH response's `updated_at`; have `handleForwardSyncClose` use that value for the watermark, falling back to local time only if the response is unparseable. Add a test asserting the watermark equals the mocked response's `updated_at`, not the test's wall-clock time. | P1 |
| 2 | Epic 0.3's `UserModifiedFields` write (Task 0.3.2b) is a presence check (`req.Msg.Title != ""`) — but the only frontend path that submits `title` (`BacklogItemDetail.tsx`'s `handleUpdateItem`, the "Edit" form's Save handler, `BacklogItemInput.title` is a required non-optional field) always sends the item's current title verbatim, regardless of which field the user actually changed. Opening "Edit" to change only Priority or RepoPath permanently marks Title/Description/Priority as user-modified. | Backward sync appears to work on never-edited, freshly-imported items, then silently stops updating Title/Description for any item a user has ever opened "Edit" on — no error, indistinguishable from "working as intended." This regresses a dormant pre-existing `SyncOne` gate (`containsField(modifiedFields,"title")`, `backlog_sync.go:265-268`) that Epic 0.3 exists specifically to unlock, and instead re-locks it almost immediately. | Task 0.3.2b must diff against the existing value, not just check presence: `req.Msg.Title != "" && req.Msg.Title != existing.Title` (same for description/priority) before adding to `touchedFields`. Add a test: open Edit changing only Priority, assert Title is NOT added to `UserModifiedFields`. | P1 |
| 3 | Forward-sync close failures (rate limit, auth, network) are logged via `log.WarningLog` only (Task 1.2.1b) — no task writes them to any queryable store. Unresolved Question #1 explicitly claims the mitigation is "Phase 4's persistent row-level warning," but Story 4.3.2's row-level warning only reads existing fetch-side (`Fetch`) sync history — it has no wiring to forward-sync failures at all. | A backlog item sits `done` locally indefinitely while its linked GitHub issue stays open; Settings shows the source as fully healthy (no warning); the only signal is an application log line. | Either have `handleForwardSyncClose` persist a queryable sync-event record on failure (reusing whatever backs `historyBySource`) and extend Story 4.3.2 to read it, or explicitly downgrade Unresolved Question #1's claim — it currently asserts a mitigation that doesn't exist anywhere in the task list. | P1 |
| 4 | `StartBacklogGitHubForwardSyncSubscriber` drains its `EventBus` channel in one serial goroutine doing up-to-30s external HTTP calls per event. The shared production bus (buffer 100, `server/services/session_service.go`) drops events for a full subscriber channel rather than blocking (`pkg/events/bus.go` `Publish`: `select { case ch<-event: default: /* drop */ }`). This subscriber is the only one of the four `Start*Subscriber`s doing slow external I/O, making it uniquely exposed to silent drops under burst load (e.g. an autonomous pipeline or backfill completing >100 items close together). | Some items marked `done` during a burst never get their GitHub issue closed, with zero error — compounds with #3 once it happens (no visibility either way). | Either bound the subscriber with a small worker pool instead of one goroutine, or (more robust) have `SyncOne` periodically reconcile `done` items whose issue was never observed closed, rather than relying solely on best-effort event delivery for a write this consequential. | P2 |
| 5 | `CloseIssue` (Task 1.1.1a) unconditionally PATCHes `state=closed` + posts a bot comment on every `done` transition without checking the issue's current state. For an item that spent time `in_progress`/`review`/`pr_pending` while its issue was closed externally (ADR-002's documented "no valid target, skip" gap) and later completes normally, forward sync re-closes an already-closed issue and posts "Closed automatically — the linked backlog item was marked done" on an issue a maintainer may have already closed for an unrelated reason (wontfix/duplicate/stale). | A misleading bot comment appears on a real GitHub issue already resolved by a human, visible to any repo watcher, asserting an automated close that duplicates/contradicts a manual one. | Have `handleForwardSyncClose` check the already-fetched `ExternalItem.State` before calling `CloseIssue`/`PostIssueComment`; skip both (log "already closed externally, skipping redundant close") when the issue is already closed. | P2 |

## P1 Items (address before implementation)

- [x] #1 — Change `CloseIssue`'s signature to return the PATCH response's `updated_at`; use it (not `time.Now()`) for the forward-sync watermark write in Task 1.2.1b. Add a watermark-source regression test. **Resolved 2026-08-03**: Task 1.1.1a's `CloseIssue` now returns `(time.Time, error)`, parsing the PATCH response's `updated_at` via the existing `githubIssue` struct; Task 1.2.1b uses it for the watermark (falling back to local time only on decode failure); `TestGitHubIssuesPlugin_CloseIssue_ReturnsResponseUpdatedAt` and `TestForwardSyncSubscriber_UsesCloseIssueResponseTimestampForWatermark` added as regression tests.
- [x] #2 — Make Task 0.3.2b's `touchedFields` collection a value-diff against `existing`, not a presence check, before it ships — otherwise backward sync's Title/Description gate is defeated for nearly every actively-managed item almost immediately. **Resolved 2026-08-03**: Task 0.3.2b now diffs `req.Msg.Title != "" && req.Msg.Title != existing.Title` (same for description/priority); `TestUpdateBacklogItem_DoesNotMarkTitleModifiedWhenValueUnchanged` added as regression test.
- [x] #3 — Either wire forward-sync failures into a queryable store Story 4.3.2 actually reads, or correct Unresolved Question #1's claim that Phase 4 already covers this — as written, a real, undetectable-in-the-UI failure mode ships unflagged. **Resolved 2026-08-03**: new `RecordSourceSyncFailure` method (Task 1.2.1b calls it on `CloseIssue` failure) persists into the same store Story 4.3.2's row-level warning reads; Task 4.3.2a now verifies/builds that shared store explicitly; `TestForwardSyncSubscriber_RecordsFailureOnCloseError` and `TestBacklogSourcesSettings_ShowsWarningForForwardSyncFailure` added; Unresolved Question #1's claim corrected to describe the actual mechanism instead of an unwired aspiration.
