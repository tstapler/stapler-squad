# Pitfalls: diff-stats-file-watch-cache

## 1. fsnotify-specific gotchas

**Deleted/renamed watched directory: no leak-free cleanup path exists.**
fsnotify does emit a `Remove` (and `Rename`) event for the directory itself, but:
- [fsnotify#40](https://github.com/fsnotify/fsnotify/issues/40) — once the path is gone, calling `Remove()` on it (to clean up your own bookkeeping) returns a syscall error (`no such file or directory`) on Linux because inotify already auto-removed the underlying watch; the *internal* `w.watches` map entry historically leaked because the code path that finds "syscall error, do nothing" skipped deleting the map entry (partially fixed in newer versions — [PR #73](https://github.com/fsnotify/fsnotify/pull/73), but PR #73 itself introduced a **deadlock risk**: calling `Remove()` from the same goroutine draining `Events` can block waiting for an `IN_IGNORED` event that never arrives if the channel is also full).
- Practical implication for this design: **do not call `watcher.Remove(path)` in reaction to a `Remove`/`Rename` event for that same path** — the OS has already dropped the watch; just delete your own directory-bookkeeping map entry keyed on that path. Only call `Remove()` proactively for paths you're *voluntarily* unwatching (e.g., a directory matched by `.gitignore` after a `.gitignore` edit), not ones the OS already tore down.
- No native "remove all watches under this subtree" call exists ([fsnotify#41](https://github.com/fsnotify/fsnotify/issues/41), [#223](https://github.com/fsnotify/fsnotify/issues/223)) — a whole subtree deleted by `git checkout`/`rm -rf` requires walking your own bookkeeping map by path-prefix and removing each entry individually; this is O(subtree size) on every deletion, not O(1).

**Event-queue overflow is a real, silent-until-you-check failure mode, not a hypothetical.**
- fsnotify surfaces overflow as `ErrEventOverflow` on the **`Errors`** channel, not `Events` — a design that only reads `Events` in its select loop and ignores `Errors` will never even notice an overflow happened.
- On Linux this maps to the kernel's `IN_Q_OVERFLOW` (governed by `fs.inotify.max_queued_events`, default 16384): once the per-instance queue fills, **the kernel drops events silently and appends a single overflow marker** — real filesystem changes are permanently lost, not queued-then-delivered-late ([Loki/Promtail#2134](https://github.com/grafana/loki/issues/2134) hit this at 50k lines/sec even after raising the sysctl to 1M).
- On Windows (`ReadDirectoryChangesW`), the equivalent is a fixed-size buffer (64KB default) — same drop-on-overflow behavior, mitigated by `fsnotify.WithBufferSize()`.
- **Direct consequence for this feature's design**: the requirement's TTL backstop is what turns a dropped event from "one missed refresh, caught next poll" into "stale for up to 5+ minutes." A debounce/coalescing design that assumes "≥1 event survives per real change" is falsified by overflow — the *only* event for a change can be the one that's dropped. This means the watcher must be treated as **advisory, not authoritative**: it should shorten the effective TTL when healthy, but the correctness backstop (a much shorter interval, or a "re-verify on next access if watcher hasn't fired recently" heartbeat) must remain, and `Errors` channel reads must at minimum log+metric on overflow so staleness has a diagnosable signal instead of silently serving 5-minute-old diff stats.

## 2. Resource exhaustion — watch-descriptor budget

Measured against this repo as the stated reference scale:
```
git ls-files | wc -l                        → 6,858 tracked files
git ls-files | xargs -n1 dirname | sort -u | wc -l → 1,300 non-ignored directories
```
So a single worktree's recursive, `.gitignore`-respecting watch needs on the order of **~1,300 watch descriptors** (one `fsnotify.Add()` per directory — fsnotify/inotify has no native recursive watch). At the stated 134-worktree scale, that's **~174,000 watch descriptors for this feature alone**, layered on top of `session/unfinished/watcher.go`'s existing consumer (which only watches `.git/`-adjacent paths at depth ≤5 per repo — a couple orders of magnitude smaller, on the order of hundreds total, not tens/hundreds of thousands).

Compare to the actual Linux ceiling: `fs.inotify.max_user_watches` defaults to **8,192** on stock distros ([Stack Harbor](https://stackharbor.com/en/knowledge-base/inotify-watch-limit-enospc/), [Watchexec docs](https://watchexec.github.io/docs/inotify-limits.html)) — a single worktree at this repo's density (1,300 dirs) already burns 16% of that default per worktree; **the second worktree alone would exceed the default ceiling**, and 134 worktrees would need the sysctl raised roughly **21x** (to ~180K+) just to have headroom, before accounting for the existing `unfinished/watcher.go` consumer or any other process on the box sharing the same per-UID pool. This is a system-wide, per-UID pool, not per-process — any other file watcher running as the same user (an editor, another dev tool) competes for the same budget, and this app cannot know or control that externally.

**Failure mode when the ceiling is hit mid-run**: `fsnotify.Watcher.Add()` returns a normal Go `error` — glibc's `ENOSPC` ("no space left on device", despite having nothing to do with disk space) is returned synchronously from the `Add()` call, not a silent no-op and not a panic. This is actually the *good* case for this design: the requirement's "fall back to pure-TTL for that worktree only" degrade path can and should be implemented as "if `Add()` errors during the initial walk (or new-subdirectory detection), abort watch setup for this worktree and mark it TTL-only" — there is a clean error to branch on. The risk is entirely in **not testing this path**: if the initial walk only checks the *first* `Add()` call's error and ignores errors from the remaining ~1,299 calls (e.g., a range loop that logs-and-continues), a worktree can end up in a **half-watched** state — some subdirectories watched, others silently not — which is worse than the documented "fall back to pure-TTL for that worktree" behavior because staleness would be scoped to specific subdirectories in a way nothing surfaces. The implementation must either watch a worktree fully or fall back to full pure-TTL for it, with no partial-watch state, and the walk should distinguish `ENOSPC`/`EMFILE` (systemic — likely to hit every remaining `Add()` too, so stop the walk and fall back) from a per-path error (e.g., dir removed between walk and `Add()` — safe to skip just that one entry) at that resource scale.

Also relevant: `fs.inotify.max_user_instances` (default commonly 128) caps the number of separate `inotify_add_watch` **file descriptors** (`fsnotify.NewWatcher()` calls), not directories watched — this design's "one goroutine + one `fsnotify.Watcher` per live worktree" pattern means 134 worktrees = 134 inotify instances, which alone is comfortably within a 128-1024 range on typical configs but leaves near-zero headroom if the default is still 128 and any other fsnotify consumer (including `session/unfinished/watcher.go`'s own single shared instance, or an editor) is also running as the same user — worth checking against the deployment host's actual sysctl rather than assuming.

## 3. Concurrency/lifecycle bugs specific to this design

**Teardown races with in-flight events.** A `fsnotify.Watcher`'s `Events`/`Errors` channels keep delivering after the owning `Instance`/`GitWorktreeManager` starts tearing down, unless the watcher goroutine is explicitly stopped and drained first. The invalidation callback this feature wires up will fire with a workdir/path key that may already be gone from whatever cache/registry backs it:
- `vcsStatusCache` is a `sync.Map` keyed by workdir path (`server/services/workspace_service.go:81`, existing pattern at line 431: `ws.vcsStatusCache.Delete(preWorkDir)`) — `sync.Map.Delete` on a missing key is a safe no-op, so this specific cache is naturally race-tolerant for a late invalidation.
- The diff-stats cache (`session/git_worktree_manager.go:36-50`) is a **field on `*GitWorktreeManager`** (`diffStatsAt`), not a map — an invalidation callback that closes over a `*GitWorktreeManager` (or `*Instance`) pointer risks calling back into a struct mid-`Cleanup()`/already-destroyed. Per this repo's own `.claude/rules/instance-lock-free-reads.md`, any such callback must go through the actor's locked setter path or an atomic-published `Snapshot()`, **not** write the field directly from the watcher goroutine — that would reintroduce exactly the class of race that rule exists to prevent. The callback needs to be structured so a "worktree already torn down" case is a safe no-op, not a nil-pointer panic or a race flagged by `go test -race`.

**Goroutine-leak-on-exit-path risk.** With one goroutine per live worktree (134 at target scale), any teardown path that returns early — an error branch in `Cleanup()`, a panic recovered upstream, a pause path that's structurally different from destroy — and skips calling the watcher's `Stop()`/`Close()` leaks both the goroutine and its `fsnotify.Watcher` (and, per the deleted-directory gotcha above, potentially its underlying watch descriptors too, compounding the resource-exhaustion risk in section 2). This needs a `defer`-based guarantee at the single chokepoint where every teardown path converges (not duplicated ad hoc in each of pause/destroy/cleanup), and should be checked with `goleak` in tests per this repo's `golang-testing` conventions — a leaked watcher goroutine from a test that exercises pause/destroy without asserting on goroutine count will not fail visibly until it accumulates in a long-running dev-box process.

**Double-invalidation / debounce-timer races.** A burst (git checkout, build tool writing many files) generates many raw fsnotify events; if the debounce mechanism is "reset a `time.Timer` on each event, invalidate on fire," two events arriving concurrently on the *same* worktree's watcher goroutine are naturally serialized (single reader of one `Events` channel) — but if the debounce timer's fire callback is dispatched onto a separate goroutine (e.g., `time.AfterFunc`) rather than invoked inline in the event loop, two closely-spaced bursts can produce two overlapping `AfterFunc` callbacks both trying to invalidate the same cache entry concurrently. For the `sync.Map`-backed `vcsStatusCache` this is harmless (idempotent `Delete`), but if the diff-stats side's invalidation involves a compare-and-swap on `diffStatsAt`/re-triggering a recompute, concurrent fires could cause two recomputes to race or one stale recompute to overwrite a newer one — worth explicitly using `timer.Stop()`+reset (not a fresh `AfterFunc` each time) to guarantee at most one pending callback per worktree.

## 4. Feature-flag retroactivity pitfall

Read `server/services/feature_flag_service.go`'s `knownFeatureFlags` table and `SetFeatureController` call sites (`server/dependencies.go:1413,1420` — only `"backlog"` and `"handoff-summary"` are wired to a `FeatureController`; every other flag, including all six `terminal:resync-*` flags, is a plain `config.GetFeatureFlagWithDefault` read with no controller). The existing doc comments make the answer explicit and precedented:

> `terminalResyncVisibilityScopeFlagName`: "Applies to newly-focused terminals only — already-open tabs need a reload to pick up the change."
> `terminalResyncCorrelationIDFlagName` / `terminalResyncSkipStaleDimensionSlowpathFlagName`: "Not live-updated on already-open tabs."

This confirms: **flipping a plain (non-`FeatureController`) flag on does nothing for state that already exists** — it's read once at the point something is constructed, not re-evaluated live. For this feature, that means a session/worktree whose watcher was never started (flag was off at worktree-open time) will **not** retroactively get a watcher when the flag flips on; it silently keeps behaving exactly as it did (pure 15s TTL) until that worktree is torn down and a new one is created. This is the same class of limitation as the terminal-resync flags and does **not** need a `FeatureController` wired up to be an acceptable design — it should simply be documented in the flag's own description string (mirroring the terminal-resync precedent verbatim, e.g. "Applies to newly-created worktrees only; already-open sessions keep today's 15s pure-TTL behavior until restarted") so an operator flipping the flag doesn't wrongly expect existing 134 live sessions to instantly pick it up. Only worth escalating to a real `FeatureController` (like `"backlog"`'s) if the requirement explicitly demands live retroactive activation for already-running sessions — nothing in requirements.md asks for that.

## Summary of load-bearing evidence

- `git ls-files | wc -l` = 6,858; `git ls-files | xargs -n1 dirname | sort -u | wc -l` = 1,300 (run in this repo's worktree, 2026-09-10) — basis for the ~174K-descriptor estimate at 134 worktrees.
- `server/services/workspace_service.go:81,431` — `vcsStatusCache` is a `sync.Map` keyed by workdir, already invalidated via idempotent `.Delete()`.
- `session/git_worktree_manager.go:36-50` — diff-stats cache is a struct field (`diffStatsAt`), not a map; needs actor-safe invalidation per `.claude/rules/instance-lock-free-reads.md`.
- `server/services/feature_flag_service.go` lines ~104-186 (terminal:resync-* flag doc comments) — precedent for "not live-updated on already-open [sessions]" being an accepted, documented limitation without a `FeatureController`.
- `server/dependencies.go:1413,1420` — only 2 of ~15 flags have a wired `FeatureController`.
