# Pre-mortem: diff-stats-file-watch-cache
**Date**: 2026-09-10

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Flag-off is not a real incident kill switch: flipping `vcs:worktree-change-detection` to `false` does not stop already-running `WorktreeChangeDetector`s (goroutines/fds keep running until the owning session is torn down), but requirements.md frames "flippable live, no redeploy" specifically as the safety valve for this new-per-session-OS-resource risk — the one scenario where the flag needs to work instantly is the one it doesn't cover. | An operator flips the flag off during a suspected fd/goroutine problem; `CreateDebugSnapshot` still reports the same count of `worktree_git_watch_active: true` sessions minutes later and fd usage keeps climbing. | Add an integration test that asserts (and documents) "flag off does NOT stop existing detectors" as expected behavior, and add a one-line runbook note that the actual incident-response action is restarting affected sessions, not flipping the flag — surface this before an incident, not during one. (Already flagged as a Concern in adversarial-review.md; elevated here because the plan has no test proving the documented-but-unenforced behavior.) | P2 |
| 2 | fd count, not goroutine count, is the real ceiling: two goroutines/worktree × 134 = 268 new goroutines is cheap, but each worktree's `.git` fsnotify watch also costs "~10-20 descriptors" per requirements.md's own estimate — up to ~2,680 fds for this feature alone, stacked on whatever `unfinished.Scanner`, sqlite, tmux PTYs, and log files already hold on the same box, against a macOS default `ulimit -n` as low as 256. | New sessions or unrelated app operations start failing with "too many open files" once N sessions have the flag on — well before all 134 worktrees are enabled — and the failure isn't obviously attributed to this feature. | Before staged rollout, measure actual fd headroom on the dev box (`ulimit -n` and current fd count via `lsof`/`/proc/self/fd` with the flag off), and empirically verify the "~10-20 descriptors" estimate rather than taking it on faith, then record the computed margin against 134× that count in the plan's Risk Control section alongside the CPU metric. | P2 |
| 3 | The periodic 15s stat-walk runs unconditionally per flag-on worktree regardless of whether anything is actually polling that session's diff/status — so a genuinely idle/backgrounded session (the majority case per requirements.md's own 60s→600s unfocused-pane anecdote) now does scheduled work it never did before (no caller previously meant no recompute at all), potentially offsetting or exceeding the very CPU savings this feature exists to deliver. | The plan's own mandated 48-hour post-merge Pyroscope re-measurement shows `GetSessionDiff`/`GetVCSStatus`'s combined CPU share flat or worse, despite cache hit rates improving. | Profile `WorktreeChangeDetector.periodicLoop`/`IsDirtyUncached` as its own line item in the post-enable Pyroscope profile (not folded into the two RPCs' numbers), so a wash is diagnosed correctly; consider skipping a worktree's periodic tick entirely when no cache entry currently exists for it (restoring "no caller, no work" for truly idle sessions) before declaring the feature validated. | P1 |
| 4 | The CPU-share success metric is deferred past merge to a single manual re-measurement with no ticket/reminder and no concrete rollback action tied to a negative result ("re-open Design Pivot assumptions" is not a revert) — so an inconclusive or negative outcome can silently do nothing, leaving the added complexity (new goroutine/fd classes, wider `GitManager` interface, wider caches) in the codebase unproven and possibly never re-checked. | Months later, the flag is still default-off (or was flipped on by someone who never ran the comparison) and nobody can produce the promised before/after CPU delta. | Convert the plan's "Unresolved Questions" follow-up into a tracked, assigned backlog item with the 48h trigger date, and define an explicit rollback action for a negative result (e.g. "if combined CPU share doesn't drop by at least X%, revert the flag default to permanently-off and file a follow-up to remove the feature") instead of an open-ended "re-open assumptions." | P2 |
| 5 | fd/watch exhaustion (#2) degrades individual sessions to periodic-only silently and gradually as more sessions enable the flag; each failure logs once per worktree (per plan design) and shows up only as a per-session `CreateDebugSnapshot` boolean that nobody proactively checks in this no-on-call local dev tool — so there is no fleet-level signal that "N of 134 sessions have lost their .git watch," which is exactly the outcome requirements.md's Observability Requirements said to avoid ("fleet-wide fd problem is visible instead of silently degrading"). | A meaningful fraction of sessions are quietly running periodic-only (15s-latency invalidation instead of near-instant on commits) with nobody aware, discovered only incidentally. | Add a cheap fleet-level rollup — e.g. a single aggregate log line or debug-snapshot summary field ("N/134 sessions have `git_watch_active=false`") — rather than exposing the signal only per-session, since the underlying booleans already exist and this directly satisfies the "fleet-wide visibility" requirement that per-session-only exposure doesn't meet. | P3 |

## P1 Items (address before implementation)
- [ ] #3 — Before treating the 48-hour Pyroscope re-measurement as sufficient validation, add a plan task to separately attribute the periodic-loop's own CPU cost in that profile, and evaluate gating the periodic tick on "does a cache entry currently exist for this worktree" so idle/unpolled sessions don't pay a cost they didn't pay before this feature shipped.
