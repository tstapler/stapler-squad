## Concerns

*(Carried over verbatim from iteration 1 — not re-reviewed this pass.)*

- [ ] Flag-off is not a real kill switch for already-running detectors. requirements.md frames the flag as flippable "live without a redeploy" specifically because this is a *new per-session OS resource at fleet scale* — but per the plan's own documented decision (pitfalls.md §4, plan.md's Risk Control), flipping the flag off leaves every already-started `WorktreeChangeDetector` (and its goroutines/fds) running until that session is torn down. The `terminal:resync-*` precedent cited is for UI-correctness flags, not a resource-exhaustion safety valve — a weaker analogy for this specific risk profile, where the whole point of "flippable live" is presumably incident response to an fd/goroutine problem. Recommend either: (a) state loudly in the flag description that "off" does not free existing detector resources and the escape hatch is restarting affected sessions, or (b) make `stopChangeDetector` reachable from a lightweight poll (e.g., check the flag once per periodic tick and self-stop) so "off" actually degrades running detectors within one interval.
- [ ] `.git` fsnotify watch has no re-arm path if the watched directory disappears and is recreated by something outside `GitWorktreeManager`'s own teardown (e.g., an out-of-band `git worktree remove`+re-add, or another process deleting `.git`). `gitWatchLoop` deliberately never calls `Add()` again per pitfalls.md's PR#73 guidance, which is correct re: avoiding the deadlock — but there's no compensating "watch died, try to re-arm on next periodic tick" logic either. The periodic loop still bounds staleness to 15s, so this isn't a correctness bug, but it's an unannounced, permanent silent regression to periodic-only for that session with no log line distinguishing "never had a git watch" from "git watch died mid-session."
- [ ] `GitWatchActive()` (`WorktreeChangeDetector` and its `GitWorktreeManager` passthrough) can report a false-positive `true` in exactly the above scenario — it only checks `d.gitWatcher != nil`, never whether the watch is actually still receiving events from a live fd. The debug-snapshot observability story (Epic 3.2, satisfying requirements.md's Observability Requirements) can therefore show a session's `.git` watch as healthy when it has silently gone dead — undermining the stated purpose of that field ("fleet-wide fd problem is visible instead of silently degrading").
- [ ] `fsnotify` v1.9.0 → v1.10.1 bump (Epic 3.1) isn't tied to any specific behavior this feature needs. The stated justification ("I want the dependency current," "diff is bugfix/cross-platform-behavior-only") doesn't confirm whether v1.10.1 actually contains a fix for the exact issues the plan's own code comments worry about (fsnotify#40/#73's Remove()-after-external-delete deadlock risk, directly referenced in `gitWatchLoop`'s doc comment). Either cite the specific fixed issue that benefits this design, or drop the bump into an unrelated, separately-reviewable commit — riding it into this feature adds regression surface (a dependency bump touching every existing `session/unfinished` fsnotify consumer) with no benefit stated against this feature's own acceptance criteria.
- [ ] No planned test exercises the detector lifecycle through `Instance.Pause()`/`Instance.Destroy()` directly, though requirements.md explicitly asks for "a test asserting cleanup on Instance pause/destroy." Verified by grep that `Pause()` (`session/instance.go:1938-1940`) and `Destroy()` do funnel through `gitManager.Remove()`/`Cleanup()` (the plan's "6 call sites" claim checks out at the cited line numbers: 1443, 1703, 1940, 2017, 2058, 2133), so the wiring is almost certainly correct — but all planned tests (2.2.1g, 3.3.3a) exercise `GitWorktreeManager` directly, not the `Instance`-level API the requirement names. Add at least one test that calls `Instance.Pause()`/`Instance.Destroy()` on a flag-on worktree instance and asserts the detector stopped.
- [ ] `WorktreeChangeDetector.cancel`/`.stopped` are unguarded by any mutex (unlike `.gitWatcher`, which uses `d.mu`), and there's no documented invariant against concurrent or duplicate `Start()`/`Stop()` calls. It's safe under today's single call pattern (`GitWorktreeManager` only ever constructs-then-immediately-`Start()`s, and only calls `Stop()` once from `stopChangeDetector` under `gm.mu`), but that safety is implicit, not enforced or documented on the type itself — worth a doc comment stating the "construct → Start() once → Stop() once, no concurrent calls" contract explicitly, since nothing in the type would catch a violation.

## Minors

*(Carried over verbatim from iteration 1 — not re-reviewed this pass.)*

- 5-minute TTL and 15s interval are justified by consistency with pre-existing constants (`unfinished.Scanner`'s backstop interval; today's pre-pivot TTL) rather than a first-principles staleness/CPU-cost derivation. Reasonable, but worth noting the "justification" is anchoring, not a computed number.
- `periodicLoop`'s `timer.Reset` fires after tick work completes rather than on a fixed phase, so actual cadence self-drifts by however long `fingerprint()` takes. Harmless at this cost scale, but undocumented.
- `Stop()` (Task 2.1.1e) blocks forever if called on a detector whose `Start()` was never invoked (nil `cancel`, no goroutine ever closes `stopped`). Not reachable via current call sites (`startChangeDetector` always starts before storing), but fragile/undocumented if the type is reused elsewhere later.
