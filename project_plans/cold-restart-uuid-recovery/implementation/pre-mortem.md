# Pre-mortem: cold-restart-uuid-recovery
**Date**: 2026-08-10

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `DetectByPath`'s directory-only, identity-blind "newest JSONL wins" heuristic now directly determines `--resume`, so a reused/recycled worktree path or a directory shared by two sessions silently resumes a stranger's conversation instead of just recording metadata after the fact as it did pre-fix. | A user sees unfamiliar conversation history/context in a session they just (re)created, with no error or log anomaly — only the new DEBUG/INFO recovery lines look "normal." | Add a validation.md test case that creates instance A in dir X, deletes/clears it, then creates fresh instance B in the same dir X, and asserts B does not silently inherit A's JSONL on B's first cold start without an explicit resume choice; if the current design accepts this, say so explicitly as a documented residual risk (like the ADR does for `ClearConversationState`) rather than leaving it implicit in "Existing related work." | P3 |
| 2 | `conversationClearedAt` is in-memory only (ADR-001's own accepted residual risk); a `stapler-squad` process restart (deploy, `make install-service`, crash) between `ClearConversationState()` and the session's next cold restart drops the guard, letting pre-launch recovery resurrect the exact stale-resume conversation the user just cleared. | The health.go dead-pane recovery loop fires immediately post-deploy and the same "No conversation found with session ID" stale-resume error recurs for a session that had just been cleared before the restart. | Add a lightweight on-disk sentinel (a small timestamp file next to the session's worktree/socket state, not a full `session/ent` schema field) that survives a process restart, so the guard isn't lost on every deploy — cheaper than the rejected ent-schema alternative in plan.md's Pattern Decisions; at minimum, add a validation.md test that restarts the process (or re-constructs the `Instance` fresh) between `ClearConversationState()` and cold restore and asserts the current (accepted) resurrection behavior, so regressions are visible. | P2 |
| 3 | The restart-churn window that creates UUID loss in the first place (requirements.md's captured 15:23→17:13 example) is the same window in which the prior `claude` process's JSONL write may not be durable yet when `KillSession()` fires, so `DetectByPath`'s mtime-based pick can select a partially-written/truncated JSONL, or two restarts within the same mtime-granularity second race on "newest." | `claude --resume <uuid>` fails immediately on the freshly-recovered UUID with a parse/format error distinct from the existing "No conversation found" stale-resume path, or the resumed session loads truncated/garbled history. | Add a small debounce in the `DetectByPath` fallback guard (e.g. only trust a candidate whose mtime is more than ~1-2s old, or verify the file is non-empty/well-formed JSON before trusting it) and add a regression test that writes a candidate JSONL with an mtime within milliseconds of the simulated `KillSession()` call to pin down current behavior. | P2 |
| 4 | The pre-launch recovery block is duplicated verbatim at two call sites (`startLocked()` and legacy `start()`); a future PR that touches session-start logic edits only one site (exactly the kind of one-step-late bug this project itself is fixing), silently reintroducing the original bug at the untouched path. | `TestColdRestore_WithoutUUID_RecoversFromJSONL`-equivalent behavior regresses for only one of the two start paths, likely undetected because most manual testing exercises `startLocked()`, not the legacy `start()` path. | Factor the guarded block (`if !firstTimeSetup && !i.pm().IsAlive() && !i.HasClaudeSession() { i.tryExtractConversationUUID() }`) into one small private helper (e.g. `i.recoverConversationBeforeLaunch()`) called from both `startLocked()` and `start()`, instead of literal duplication as Tasks 1.1.1a/1.1.1b currently specify — update plan.md before implementation. | P3 |
| 5 | This plan explicitly defers the actual root cause (`driverInactivityTimeout`'s restart-churn window) and adds no new metric ("no new metrics required" per the Observability Plan), so there is no way to confirm post-ship whether the recovery path is actually firing/succeeding at a meaningful rate — the project could ship, look done, and quietly not move the needle if the churn rate or JSONL-timing assumptions are off. | Nothing observable changes proactively; only a manual `grep` of the new DEBUG/INFO/WARN log lines weeks later would reveal whether `tryextractconversationuuid: found conversation via path fallback` is actually firing in production. | Commit to a specific post-ship check in plan.md's Observability Plan: grep production logs for the new recovery-outcome log lines (used / skipped-by-guard / not-found) ~1 week after deploy and record the counts, so "shipped" isn't the same as "confirmed working." | P2 |
