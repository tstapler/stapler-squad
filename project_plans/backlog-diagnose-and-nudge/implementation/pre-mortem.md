# Pre-mortem: backlog-diagnose-and-nudge
**Date**: 2026-09-27

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The idle-settle-window gate (`isSafeSteerStatus` sustained for `IdleSettleWindowSecondsOrDefault()`, default 60s per AutonomousDriver, with reset-on-leave) is stricter than anything this codebase has shipped before — `safeIdleStatusContexts` only allowlists 3 exact pattern descriptions (`session_service.go:1044`), and the existing precedent for this gate (pr-fix-steering) checks it as a point-in-time snapshot, not a continuously-sustained window. Real Claude Code idle prompts routinely flicker (spinner redraw, a stray status-line repaint, a tool-result banner) in ways that can knock the status context off the 3-entry allowlist for one poll tick and reset the settle timer, so the gate may pass on almost no real stuck sessions. | Diagnose dispatches consistently resolve to `InconclusiveNoteFiled`/never reach the nudge write at all, even for sessions Tyler can see sitting idle for minutes in tmux; `diagnose.nudge.skipped` logs show `NotIdle` far more often than expected. | Before flipping `DiagnoseNudgeExecutionFeatureFlag` on, add a log line on every settle-timer reset (context + how many seconds of progress were lost) and run diagnose-only (flag off) against a handful of known-stuck real sessions to measure how often the window actually completes — this data-gathering step belongs in validation.md, not left to "observe after rollout." If resets are frequent, consider tolerating brief allowlist departures shorter than one poll interval rather than resetting on any single miss. | P1 |
| 2 | `MaxNudgesPerItem=2`/`CooldownSeconds=900` are explicitly acknowledged in the plan's own Unresolved Questions as having "no empirical basis" — either direction of mistuning defeats the feature: too conservative and genuinely-recoverable stuck items degrade to "file a bug" before the target session ever finishes settling (undermining the primary success metric of reducing manual intervention), too permissive and a misbehaving item gets repeatedly, autonomously written into with no human in the loop, echoing the shape (not the exact cause) of the `b28e78fc0` crash-loop incident that motivated ADR-003 in the first place. | Support burden shifts rather than disappears: Tyler still has to manually intervene, but now after the automation has already made 1-2 unhelpful attempts and filed a premature or noisy bug, which is worse than the current baseline of doing nothing automatically. | Both values are live-settable post-ship (ADR-003), which helps, but the plan gives no operational signal for *when* to retune — add one: e.g., track (via the already-planned `DiagnoseDispatch` table, an ad hoc query, no new infra) the ratio of `SkippedSafetyGate(NudgeCapReached)` outcomes to total dispatches over the first two weeks post-flag-on, and treat a high ratio as the trigger to raise the cap, rather than leaving "retune if it feels wrong" undefined. | P2 |
| 3 | Task 4.1.4f reuses `diagnoseNudgeGuardMu` — a single non-reentrant `sync.Mutex` designed and tested (Task 3.3.2b) for exactly one critical section (`CheckAndReserve` on `NudgeCapRecord`, keyed conceptually by item) — for a second, structurally different critical section (`CheckAndSetWriteAttempted` on `DiagnoseDispatch`, keyed by dispatch) invoked from a different point in the same call stack. Task 4.1.4h's race test only mirrors 3.3.2b's same-shape scenario (two calls to the *same* new method); nothing tests the two guarded operations interleaving with each other, and nothing in the plan states "these two operations must never be nested/re-entered from the same goroutine" — an easy invariant for a later refactor to accidentally violate (e.g., folding `CheckAndSetWriteAttempted` into `NudgeGate.Evaluate` for convenience) once both exist and share a name suggesting they're the same mechanism. | A nudge write silently hangs (goroutine deadlocked on `diagnoseNudgeGuardMu.Lock()`), surfacing as a diagnose dispatch that never completes — `Status: Pending` forever, no error logged, contradicting the plan's own "Diagnosing… must survive navigation but ultimately resolve" UX expectation. | Give `CheckAndSetWriteAttempted` its own dedicated mutex (it guards a different row and a different invariant; the "one guard for every nudge-adjacent race" framing in Task 4.1.4f is the kind of forced generalization `interface-pollution-checklist`/type-driven-design guidance elsewhere in this repo warns against) or, if sharing is kept for simplicity, add an explicit doc comment plus a lint/test guard against nested acquisition, and add an interleaving test (concurrent item-A cap-check + dispatch-B write-attempt-check) to Task 4.1.4h rather than only the same-shape duplicate. | P2 |
| 4 | The diagnostic agent's own judgment of "bug filed vs. nudge vs. inconclusive" is exactly the "compounding automation" risk `research/pitfalls.md` §5 names ("scope creep in the diagnostic agent's own judgment... drifting toward optimistic nudging over time as it 'learns' nudging is the cheap option") — but the plan has no mechanism anywhere (confirmed: no "audit"/"sample"/"periodic review" step in plan.md) to detect that drift once shipped. The evidentiary bar for bug-filing is a prose instruction ("same as `ce71ad1a`") baked into a prompt string, not something gradeable at scale, and the stated success metric is explicitly qualitative ("Tyler's own account of 'did I have to do this by hand'") — a signal too slow and too subjective to catch a drift that trades correctness for cheapness one dispatch at a time. | A run of `InconclusiveNoteFiled`/low-effort outcomes on items that a human diagnosis would have nudged or bug-filed decisively — invisible unless Tyler happens to compare the agent's note against what he'd have concluded himself, which is exactly the manual effort this feature exists to remove. | Add a cheap, code-enforced audit trail rather than relying on prompt compliance indefinitely: require the diagnostic agent's `create_backlog_item`/`post_backlog_update` call to cite which specific bundle sections it used as evidence (already-assembled `BundleSection` names), and add a periodic (e.g. every 10th dispatch, or monthly) manual spot-check step to validation.md/Observability Plan — "review N most recent `InconclusiveNoteFiled` outcomes for whether a human would have acted differently" — so drift has a forcing function to surface before it's produced a backlog of bad calls, not just a hope that Tyler notices. | P1 |
| 5 | Two new ent schemas (`NudgeCapRecord`, `DiagnoseDispatch`) are added, and this exact class of pitfall — a freshly created/recreated worktree has no generated `session/ent/*.go` code until `make build`/`make ent-gen` runs, causing `go build`/`go test` to fail with "no required module provides package .../session/ent/<x>" — was confirmed happening in this repo 3 days ago (`instinct_alias_session.md`, 2026-09-24). `plan.md` has zero mention of `make build` as a prerequisite anywhere; Tasks 3.3.1b/5.2.1b only cover regenerating for the *new* schemas, not the baseline "this worktree can't build at all yet" problem every other phase's subagent will hit first if run in a fresh worktree (per SDD's fresh-session-before-implementation convention). | A Phase 1/2 worker subagent (touching `config/config.go`, `session/diagnose/*.go` — no ent involvement) runs `go build ./...`/`go test ./...` and gets confusing "missing package" errors unrelated to its own diff, and either burns a turn misdiagnosing it or — worse — hand-writes a stub package to "fix" the missing generated code. | Add an explicit Phase 0 / setup note at the top of plan.md: "run `make build` once in this worktree before starting any task" — mirroring the repo's own documented gotcha — so every worker subagent (not just the ones touching the new ent schemas) is covered, not only the two tasks that happen to touch ent directly. | P2 |

- [x] #4 (LLM judgment drift toward cheap outcomes) — add an evidence-citation requirement to the diagnostic agent's bug/nudge/note tool calls and a periodic spot-check step to the Observability Plan/validation.md, so drift has a concrete detection mechanism instead of relying solely on Tyler's subjective sense of the qualitative success metric. **Resolved** in plan.md: Story 5.1.2's Tasks 5.1.2e/f (evidence-citation requirement) and a new Observability Plan bullet (periodic spot-check of InconclusiveNoteFiled outcomes).
