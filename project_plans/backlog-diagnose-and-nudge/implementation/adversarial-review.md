## Concerns

- [ ] **Blocker 1 is only half-closed: the code-level backstop against a same-dispatch double-nudge is weaker than the plan's "Verified ordering" note claims.** Story 4.1.4 (plan.md:859-932) does satisfy the literal requirement from `research/pitfalls.md:183-188,261-263` to *distinguish* "tool call failed, no write happened" from "write happened, response lost": Task 4.1.4a adds a real, tested (`4.1.4d`) `"write_outcome_unknown"` classification in all three handlers, with no internal retry loop — that part is genuine, code-enforced, and testable. But the plan's claim that "any subsequent attempt for the same item ... is already counted against the same cap/cooldown window" (plan.md:874-875) overstates what the cap actually prevents. ADR-003 sets the shipped default `MaxNudgesPerItem = 2` (`decisions/ADR-003-nudge-cap-cooldown-shape.md`, "Live-settable limits" section). Read literally: attempt 1 (ambiguous, `write_outcome_unknown`) consumes cap slot 1/2 via `CheckAndReserve` (Task 4.1.1a/4.1.2a/4.1.3a insert `NudgeGate.Evaluate` — which includes the cap-check link, Story 3.3.3 — "at the top of" each handler's write branch, strictly before the write). If the diagnostic agent disobeys the prompt instruction (Task 5.1.2d) and calls the write tool again in the *same dispatch*, `CheckAndReserve` sees `NudgeCount=1 < cap=2` and **succeeds**, consuming slot 2/2 and letting the second write proceed — this is exactly the double-nudge scenario the original blocker described ("an agent retry could deliver two nudges"). The cap only blocks a *third* attempt (same- or next-dispatch); it does not block the single retry that is the realistic failure mode. The plan explicitly acknowledges declining a stronger fix at plan.md:916-919 ("no request-ID/idempotency-key subsystem is added ... letting the already-reserved cap/cooldown do its job for any case where a retry is attempted anyway") — but for the shipped cap=2 default, the cap does *not* do that job for exactly one retry, only for a second one. The remaining backstop is therefore the prompt instruction alone (Task 5.1.2d), which is a soft LLM-compliance constraint, not code-enforced, for precisely the case this story was written to close.
  — **Recommendation**: either (a) add a cheap per-dispatch idempotency guard — the `DiagnoseDispatch` row already exists with a `dispatchID` before any write is attempted (Story 5.1.1's Task 5.1.1d); have the gate check-and-set an atomic "write already attempted this dispatch" flag on that row (or an in-memory `sync.Map[dispatchID]bool` scoped to the dispatcher, cheaper than a full request-ID subsystem) and reject a second write attempt for the same `dispatchID` regardless of remaining cap headroom, or (b) explicitly get Tyler's sign-off that relying on LLM prompt compliance for the single-retry case is an acceptable residual risk for this single-user, low-stakes internal tool (the Tech Debt Disposition table already models this "flag for Tyler" pattern for Concern 1 below — the same treatment should apply here rather than the plan's current wording, which reads as "resolved" when it is actually "reduced and disclosed").
  - This is a downgrade from BLOCKER because real, tested code now exists (classification, no-internal-retry, persisted `WriteAttempted` audit trail) and the residual exposure is bounded (at most 2 real writes ever per item, not unbounded retries) rather than the previous "nothing preventing it" state — but it should not be presented as closed without the caveat above.
  - **Update (2026-09-27, same-day follow-up): RESOLVED by Story 4.1.4's dispatch-level write-attempt guard.** A new `WriteAttemptedAt` field on the `DiagnoseDispatch` row (added alongside, not replacing, the existing `WriteAttempted` audit flag), checked-and-set atomically via `diagnoseNudgeGuardMu` keyed by `dispatchID`, is consulted immediately before each write call and rejects any second write attempt for the same dispatch with a new `SafetyGateReasonDuplicateWriteAttemptForDispatch` — regardless of remaining cap headroom (plan.md Story 4.1.4, Tasks 4.1.4e-h). This closes the exact "one retry, cap still has room" gap identified above structurally rather than relying on the prompt instruction (Task 5.1.2d) alone; the cap/cooldown remains the correct, and now secondary, backstop for a third attempt or a retry from a wholly separate dispatch.
