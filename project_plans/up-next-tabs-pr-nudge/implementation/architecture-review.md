## Blockers
- [ ] Story 1.3.1 / Task 1.3.1a (session-to-PR matching) — The plan's safety model depends on `LinkedSessions` membership ("host+repo+branch"), and it treats the host-collision as a small confirm-and-fix. The actual code is worse than the plan assumes: `RepoRef.BranchKey(branch)` is `r.owner + "/" + branch` (`github/repo_ref.go:51`) and `RepoRef.PRKey(n)` is `r.owner + "/#" + n` (`github/repo_ref.go:55`). Neither includes the **repo name or the host**. Two repos under the same owner with a branch named `fix-ci` (or the same PR number) collide, so a nudge containing repo A's failing checks and thread text can be written into a session working on repo B. Task 1.3.1a only says "if host is not part of the key, include it", and the AC only tests host collision. This is the one-click PTY-write path, so it is a correctness/safety defect. — Remediation: change 1.3.1a to specify the key as `host/owner/repo` + branch (and `host/owner/repo#number`) and add a collision AC for same-owner/different-repo and same-PR-number. Note `BranchKey` is also used for `worktreeByKey` (`user_pr_cache.go:301`), so the change affects worktree linking too; add a regression test there. Both are internal to `github/` (only `user_pr_cache.go` calls them, VERIFIED by grep), so blast radius is small. Make this task a prerequisite of Story 2.3.1, not a Phase 1 detail.
- [ ] Story 2.1.1 Task 2.1.1a (`FetchPRNudgeDetail`) — Plan says `FetchPRNudgeDetail(ctx, PRKey, token)` "using `GetPRInfoGraphQL`". The real signature is `GetPRInfoGraphQL(ctx, ref RepoRef, prNumber int)` (`github/client_graphql.go:205`) with no token parameter, and the viewer cache is multi-account (`collectAllTokens`, `user_pr_cache.go:496`, env tokens, per-host CLI imports). The plan never says which account's token fetches fresh detail for a given PR, nor how `GitHubUserService` learns it (`UserPR` has no account/login field). A wrong or default token on a multi-account/GHE setup returns `PR_NOT_FOUND` or reads the wrong visibility, and this decision shapes the `PRDetailFetcher` port, so it must be settled before implementation. — Remediation: add a task before 2.1.1a that (a) records which token produced each `UserPR` (cache-side field or lookup `TokenForPR(PRKey)` exposed by `UserPRCache`), (b) decides whether to add a token-taking variant of the GraphQL call or write a new query in `pr_nudge_detail.go` using `newGHGraphQLRequestForHostWithToken`. Drop the claim that it reuses `GetPRInfoGraphQL` unless a token variant is added.

## Concerns
- [ ] Task 2.3.1b (handler order) — `IsDuplicate` is checked **before** `Acquire`, a check-then-act race: two concurrent clicks both pass `IsDuplicate`, the first delivers and releases, the second then acquires and delivers a duplicate. — Check `IsDuplicate` after `Acquire` (inside the held lock), or make `guard.TryBegin(id, sig) (release, outcome)` a single atomic operation. Add a concurrency test using the fake clock.
- [ ] Task 2.3.1b / 2.3.1a (two idleness notions) — The plan gates on `session.VerifyNudgeSafeToWrite` (controller status + pane ownership, `session/nudge_gate.go:132`) but delivers via `SessionService.SteerActiveSession` -> `steerInstance`, which re-resolves the instance by title (`session_service.go:1110`) and has a different readiness notion (`IsReadyForSteer`, `statusManager`). The existing auto-steer uses `IsReadyForSteer`. The two can disagree (`CheckNudgeEligible` errors with "no running controller"; autonomous sessions go through `SendCommandImmediate`). Also resolve-then-resolve-again creates a small identity TOCTOU. — Pick one gate for both paths (document why), and prefer a `SteerInstance(ctx, *session.Instance, msg)` port method so the verified instance is the one written to; add `SteerInstance` rather than the title-based call. Test AC for autonomous-mode sessions.
- [ ] Phase 1.2 / Unresolved Q5 (poll query widening) — `userPRGraphQLQuery` is `pullRequests(first: 100)`; adding `reviewThreads(first: 50)` and `contexts(first: 25)` multiplies connection cost per PR on every poll for every account and host, and `mergeable` on 100 PRs forces GitHub to compute mergeability (returns `UNKNOWN` on first read, causing flapping `has_merge_conflict`). The documented fallback ("drop thread counts, fetch lazily") conflicts with the tab badge and with `details_loaded` semantics, since the badge would silently lose thread counts. — Decide before Phase 1 merges: make the cost measurement (1.2.1a) a gate with a concrete threshold already named in the plan, specify the fallback's UI (badge counts only failing CI + conflict; thread chip shows "?" until nudge), and treat `mergeable: UNKNOWN` as "unknown", not `false`, to avoid conflict flapping (AC currently maps UNKNOWN to false).
- [ ] Phase 3 vs Phase 4 sequencing (Tech Debt row 1) — The disposition says the 978-line `GitHubPRsSection.tsx` is isolated via seam and "auth code untouched", but Task 3.3.1b rewrites that file's container (moves filter state out of l.853, adds props, edits its test mocks) **before** Story 4.1.1 extracts `PRCard`/`PRGroupedList` from the same file. The dependency diagram shows 4.1 and 3.x as parallel. — Sequence 4.1.1 (pure move) first, then 3.3.1b, so the state-lift diff lands against the small container; or state explicitly that 3.3.1b is allowed to touch `GitHubPRsSection` container only. Update the dependency diagram.
- [ ] Story 4.3.2 / Task 4.3.2a-b ("+ Session" seeded) — Scope is an open investigation sized at two 5-minute tasks. If an `initial_prompt` field must be added, it widens `CreateSession` (`SessionService` is a 6.8k-line file, `wc -l server/services/session_service.go`) and makes the create path depend on `PRDetailFetcher`/`BuildPRNudgePrompt`, a new coupling from the session-creation service into GitHub PR detail fetching. It also needs the unsupported-program decision (non-Claude) and fork-PR behavior. — Split into its own story with the investigation done up front (move 4.3.2a to Phase 1) and, if it widens `CreateSession`, route through a small `PRFixSeeder` port rather than injecting the fetcher into `SessionService`. Consider descoping to a follow-up since requirements list it but the nudge value is independent.
- [ ] Task 2.1.1c / ADR-002 (shared helpers) — The plan references `maxSteerBytes`, which does not exist under `server/` (grep returned nothing; the real helper is `buildSteerMessage` with an internal budget and `truncateUTF8Bytes`, `backlog_service_pr_fix_steer.go:190,213`). `sanitizeUntrusted` is also a second sanitizer next to MCP `steer_session`'s NUL stripping/`maxInputBytes` in `server/mcp/tools_terminal.go`. — Name the real constant in the AC, and place `sanitizeUntrusted` where both the MCP steer path and this RPC can use it (e.g. `session/` or a small `steertext` helper) so there is one definition of "safe text for a PTY". Not required to refactor the MCP path now, but do not bury it in `pr_nudge_prompt.go`.
- [ ] Task 2.2.1b (guard shared with backlog steer) — `sessionNudgeGuard` is injected into `BacklogService` by a shared pointer constructed in `dependencies.go`, but the plan says "Extend as-is" and calls it a small additive change. `BacklogService` already has six-plus steer-related fields (`backlog_service.go:135-229`) and a `SessionSteerer` interface; adding another untyped dependency continues that growth. — Put the guard behind the existing `SessionSteerer` seam (e.g. have `SessionService.SteerActiveSession` acquire/record the per-session guard) so both callers share it without BacklogService learning a new type. This also guarantees any future caller is covered. If not done, change the disposition wording to acknowledge this is a mild deepening.

## Layering assessment (verified)
- `github/` cannot import `session/` (documented import cycle at `user_pr_cache.go:41-43`), and the plan respects it: `LinkedSession`/`PRAnnotationSession` carry plain data; fetcher lives in `github/` and is consumed through a consumer-side interface in `server/services`. Good.
- `server/services` already imports `session` (`VerifyNudgeSafeToWrite`) so calling the gate from the handler is within existing layering. `PRNudger` as a consumer-side port is the right shape; `*SessionService` already satisfies the methods it lists.
- `server/mcp` is untouched; correct, since `diagnose_nudge_session` is role-gated and the UI RPC must not call it.
- Wiring is feasible: `NewGitHubUserService` is called once (`server/dependencies.go:1248`) after `sessionService` exists, so setter injection (2.3.1a) works; `server/server.go:495-500` registers the handler unchanged.
- Instance reads: plan correctly mandates `Snapshot()` (`.claude/rules/instance-lock-free-reads.md`). `InstanceSnapshot.UpdatedAt` exists (`session/instance_snapshot.go:93`), so the Unresolved Question has a safe fallback.
- `norawghrequest`: plan uses `newGHGraphQLRequestForHostWithToken` (exists, `github/http_client.go:319`); compliant.
