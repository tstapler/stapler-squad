# Adversarial Review: up-next-tabs-pr-nudge

**Date**: 2026-10-05
**Verdict**: CONCERNS (after repair + re-review)

Claims below were checked against the worktree (file:line cited); items marked VERIFIED were confirmed by opening the code.

## Blockers
- [ ] **`UserPR` has no `host` (or account) field, but the plan's identity model needs one.** VERIFIED: `proto/session/v1/types.proto` `UserPR` (fields 1-17) has only `owner`/`repo`/`number`; Go `UserPR` (`github/user_pr_cache.go:22-40`) has no `Host`. The plan adds fields 18-22 without host, yet `PRKey{host,owner,repo,number}`, the AC "client sends `{host:"github.com",...}`" (Story 4.3.1), the cache lookup "find PR by PRKey" (Task 2.3.1b), and the Story 1.3.1 host-collision AC all need it. The viewer poll is multi-account (`connectedAccount`, `user_pr_cache.go:74`), and `GetPRInfoGraphQL` resolves the token by host only (`client_graphql.go:222`, `AccountRef{Host: host}`), so a fresh fetch may use the wrong account's token on a private repo. — Add `host` (and the owning account login) to `UserPR` in Task 1.1.1a, populate it in `fetchUserPRsForToken`, and make `FetchPRNudgeDetail` take the account/token that owns the PR.
- [ ] **Session-to-PR matching key omits the repo name, not just the host; the plan misdescribes the code.** VERIFIED: `RepoRef.BranchKey` is `r.owner + "/" + branch` (`github/repo_ref.go:51`) and `PRKey(n)` is `owner/#n` (`:55`); `Annotate` also hand-builds `pr.Owner+"/"+pr.HeadRef` and `pr.Owner+"/#"+number` (`user_pr_cache.go:~303-306`). So `acme/api` and `acme/web` branches named `fix-ci`, or PR `#42` in two repos, collide today. The plan says "`Repo.BranchKey` carries host... confirm in 1.3.1a" and its AC only tests host. Because the server's `SESSION_NOT_LINKED` check uses this same linked set (Task 2.3.1b), it cannot catch the collision, so one repo's failing-check text could be typed into an unrelated repo's agent session. — Rewrite Task 1.3.1a: key on host+owner+repo(+branch) across all three indexes (sessions, PR-number fallback, worktrees) and the Annotate loop; add a same-owner/different-repo collision AC.

## Concerns
- [ ] **Nudge button vs. server reasons mismatch.** `prAttention` counts `changesRequested` toward `needsAttention` and the button shows when `needsAttention` (Tasks 4.2.1a, 4.3.1c), but `BuildPRNudgePrompt` only has FAILING_CHECKS / UNRESOLVED_THREADS / MERGE_CONFLICT. A PR with "changes requested" and no open threads shows a Nudge button that returns `NOTHING_TO_FIX`. — Gate the button on the three nudgeable reasons, or add a changes-requested reason.
- [ ] **Prompt injection from third-party review comments.** Excerpts of up to 200 bytes of other users' comment text (public-repo contributors, bots) are typed into an agent that has tool permissions, followed by `/github:pr-ship` (`buildSteerMessage` suffix, `backlog_service_pr_fix_steer.go:186-205`). Sanitizing control chars and a "treat as data" frame do not stop semantic injection. — Prefer link + path only (agent reads the thread itself), or restrict excerpts to the viewer's collaborators/reviewers who requested changes.
- [ ] **Reused helper wording and nonexistent symbol.** The plan cites `maxSteerBytes`; the real constant is `session.MaxSteerMessageLength = 10000` (`session/instance.go:200`). `buildSteerMessage` appends the pointer "...[truncated — see item notes for full context]" which is wrong for a PR nudge (no backlog item). — Use the real constant; parameterize or fork the truncation pointer.
- [ ] **Story 4.3.2 ("+ Session" seeded) is an open-ended scope bet.** Task 4.3.2a is investigation with a fallback that adds a new request field and a server-side build path in the create-for-PR handler; no estimate, ACs, or tests for fork PRs. It could grow beyond the 1-2 week appetite. — Timebox with a decision gate, or split to a follow-up and keep plain "+ Session" in this PR.
- [ ] **Query-cost fallback breaks the UI contract.** Unresolved Question 5 says if the poll costs > 50 points, drop thread counts and fetch lazily, but Stories 4.2.1/3.3.1 (badge counts, "N unresolved" chip, `needsAttention`) depend on counts in the poll for every PR. The fallback is undefined for badges. — Define the degraded UI (badge counts failing CI + conflicts only; threads shown "?") before implementation, and measure cost in Task 1.2.1a first (gating, not parallel).
- [ ] **Guard ordering and TOCTOU.** Handler flow checks `IsDuplicate` before `Acquire`, and `VerifyNudgeSafeToWrite` before `SteerActiveSession` (`session/nudge_gate.go:132`; `session_service.go:3783` writes without re-checking). Two clicks can both pass `IsDuplicate`; only `Acquire` serializes. Also `Record` is only on success, so a failed write after a partial PTY send allows an immediate retry duplicate. — Acquire first, then check duplicate inside the lock; document the accepted residual race.
- [ ] **Stuck-tab count source is unknown (Task 3.3.1a).** `StuckItemsSection` is `UnfinishedTab`-rendered with its own data; if it polls internally, lifting changes a component the requirements put out of scope ("Redesigning Stuck internals"). — Resolve before Phase 3 starts; prefer a read-only count hook that shares the existing cache.
- [ ] **Per-session guard keying.** Plan keys on `Instance.GetStableID()` for the manual path but the backlog path has `active.SessionUUID`; confirm they are the same value or the shared guard never matches. — Add a test that both paths resolve to one key.

## Minors

- `FindLiveInstance == nil => PAUSED` conflates "paused" with "not tracked after restart"; the copy "Resume the session first" may be wrong for the latter.

- Observability: no log field for the account/host used on the fresh fetch; add it to the entry/exit log line.
- `research/stack.md` still says "no tabs library" (plan notes it is wrong); fix or delete to avoid misleading implementers.
