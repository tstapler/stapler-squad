# Validation Plan: cross-host-claim-dedup

**Date**: 2026-09-23

## Happy Path Scenario
Given Host A's `Storage.CreateBacklogItem` has already recorded a `ClaimRecord` for `https://github.com/o/r/issues/42` in its local `ClaimIndex` (the always-on Story 1.3.1 choke point — no #475 dependency), when an operator on Host B calls `ImportGitHubIssue` for that same issue URL with `cross_host_claim_dedup` enabled and `override` unset, then the RPC returns a structured `already_claimed_elsewhere` outcome naming Host A's `HostID` and `ItemDeepLink`, creates no new `BacklogItemData` row on Host B, and Host B's UI (`ClaimConflictBanner` / import-result line) surfaces a working "Copy link to hostA's item" action — no second competing item or session is silently created. *(Anchors all test design below: error/indeterminate verdicts, overrides, gossip propagation, and PR provenance are variations on this core "claim exists elsewhere → surfaced, not silently duplicated" flow.)*

## Test Stack
- **Unit**: Go `testing` package + table-driven tests, run via `gotestsum` per `make test`/`make test-race` (repo convention); TypeScript/Jest + React Testing Library for `web-app/` component tests (`cd web-app && npx jest --no-coverage`).
- **Integration**: Go `testing` with `httptest.Server` for gossip/endpoint/peer-fan-out tests; a real ent-backed `Storage` (in-memory/sqlite) for `CreateBacklogItem`/`ImportGitHubIssue`/`DequeueNextQueuedItems` tests; injectable `Clock` fixtures (no wall-clock `time.Sleep`) for TTL/timeout-ordering tests, per `.claude/rules`/`fix-flaky-tests-dont-defer` and `deterministic-fast-tests`; a fake HTTP request-counter server to prove `DequeueNextQueuedItems`'s claim check never issues network I/O under `s.dequeueMu`.
- **E2E / UX**: Playwright against the isolated `tests/e2e/global-setup.ts`-managed instance — `data-testid`/ARIA-role locators only, no `waitForTimeout`, every spec file starts with a `// @feature` header (per `e2e-test-conventions`), one dynamically-assigned port per run; manual checklist items only for the two contrast/screen-reader-pairing criteria genuinely outside Playwright's reach (item 13; screen-reader pairing folded into item 10's automated `aria-live` assertion where feasible, manual otherwise).

## Coverage Targets and How to Measure

| Stack | Coverage command | Target |
|---|---|---|
| Go | `go test ./... -coverprofile=coverage.out && go tool cover -func=coverage.out` (or `make test-coverage`) | ≥80% line, with 100% of `session/claim_index.go` (signing/TOFU-pin/conflict logic — small, high-consequence, security-relevant surface) and `server/services/claim_checker.go`'s `ClaimVerdict` construction paths |
| TypeScript/Jest | `cd web-app && npx jest --coverage --coverageThreshold='{"global":{"lines":80}}'` | ≥80% line, including `ClaimConflictBanner.tsx`, `ClaimChip.tsx`, and the updated `handlePickerSelect`/import-result branch in `page.tsx` |

- All public service methods (`ClaimIndex` incl. `ResolveDispute`, `ClaimGossiper`, `crossHostClaimChecker` implementations, `Storage.CreateBacklogItem`'s claim-recording path, `ImportGitHubIssue`, `CreateBacklogItem`/`CreateBacklogItemFromChat` (NL-create), `SyncOne`, `DequeueNextQueuedItems`, `OverrideClaimBlock`, `check_cross_host_claim`, `PostPRComment`, `reportPRCreated`, `handlePRFixEvent`'s fallback): happy path + error paths covered per the mapping table above.
- All external integrations (claim-gossip HTTP transport, on-demand peer-query fan-out, GitHub PR-comment POST, ent-backed `Storage`): unit-mocked (fake `ClaimRecorder`/`crossHostClaimChecker`) **and** at least one integration test (`httptest.Server` or real ent client) per the table above.
- UX acceptance criteria: all **15** criteria in `design/ux.md`'s "UX Acceptance Criteria (testable)" section map to a Playwright test or a named manual step above — accessibility criteria (8-12, 14) get automated Playwright coverage where DOM/ARIA-inspectable; only pure visual-contrast verification (13) stays manual, per this repo's existing Axe/Lighthouse CI gate on `web-app/src/` PRs. Three supplementary rows beyond the 15 cover the Disputed banner/chip states (CB-2) and Surface 3's override reason-capture form (CC-2), which elaborate existing criteria rather than adding new numbered ones (`design/ux.md`'s own criteria count is unchanged at 15).
- Security-sensitive paths get explicit negative-test coverage beyond the 80% line target: `ClaimRecord.Verify()` tamper rejection, `ClaimIndex.RecordClaim`'s TOFU pin-check forgery rejection, and `PRProvenanceStamp`'s no-leaked-address guarantee are each asserted by a dedicated test, not incidentally covered by a happy-path pass.
