# Pre-mortem: cross-host-claim-dedup
**Date**: 2026-09-23

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Story 1.3.1's single choke point stamps `ClaimingHostID` = local `HostIdentity.ID` on **every** `Storage.CreateBacklogItem` call — including the `ItemSource` forward/backward-sync path, which materializes a local mirror of an item already owned by another host. Ordinary, working cross-host sync (Goal 4 explicitly claims support for it) self-generates a spurious `claim_index.conflict_detected` and eventually a false "already claimed elsewhere" verdict, misattributed to the syncing host rather than the real owner. | Operators running normal multi-host sync see `claim_index.conflict_detected` log lines and/or `ClaimConflictBanner`/`ClaimChip` on items they know are correctly synced; or a later `ImportGitHubIssue`/dequeue on the item's real owning host gets blocked by a claim now pointing at the syncing host. | Before implementing Story 1.3.1, add an explicit AC distinguishing "freshly created" vs. "materialized via `ItemSource` sync" at the `CreateBacklogItem` call site (e.g., only call `RecordClaim` when the row isn't a sync-materialized mirror, or record the sync's *original* origin host instead of the local process's identity). This is a plan.md gap, not an implementation detail to improvise. | P1 |
| 2 | Claims never expire (deliberate — the Tech Debt Disposition table states `ClaimIndex` "does not consult `HostRegistry.Prune()`/TTL for claim expiry"), and `DequeueNextQueuedItems`'s local-only check (Story 2.2.2) skips a blocked candidate with nothing but a log line — Override is wired only into the `ImportGitHubIssue` RPC (Story 2.2.1/4.1.2), not into the dequeue path. A stale claim from an abandoned/crashed host can permanently starve a legitimately-owned local item with zero in-product recourse. | A queued backlog item never gets picked up for work; nothing in the UI explains why; the only signal is a `dequeue.blocked_by_claim` line in `logs/staplersquad.log`. | Give the dequeue-block state an explicit UI surface (reuse `ClaimConflictBanner`/`ClaimChip`, or a distinct "stuck: claim conflict" status) with an override path equivalent to Story 2.2.1's, before Phase 2 ships — or explicitly document in plan.md that log-grepping / manual `claim_index.json` editing is the only remedy, so it's a known limitation instead of a discovered one. | P1 |
| 3 | The plan's own rollout gate ("flip `cross_host_claim_dedup` to default-true once... logs show zero false-block reports over a real multi-host observation window") presumes sustained multi-host traffic to generate that signal. If actual usage is mostly single-host/single-operator, the flag sits at false indefinitely, or gets flipped on once without real concurrent-host exercise — so the parallel peer fan-out, TOFU pin-check, and gossip-conflict paths (and failure #1 above) go untested by real traffic. The first genuine bug surfaces only whenever a second host is later actually stood up against shared repos, which could be many months after merge — well past this pre-mortem's "first month" window, and by then with no one holding fresh context on this subsystem. | No incidents for an extended period, followed by a sudden burst of `claim_index.conflict_detected`/`already_claimed_elsewhere` reports the first time a second real host is used, with the original implementers no longer immediately available. | Add a scripted two-host integration/smoke test (spin up two `session.HostIdentity`s against a shared fixture repo, exercise the full claim/gossip/check loop end-to-end) that runs in CI on every change to this subsystem, so correctness isn't gated solely on organic multi-host adoption ever materializing. | P2 |
| 4 | Unresolved Question #2 (synchronous peer-query latency for bulk import) has no committed resolution — only "a quick timing test... before enabling by default for bulk import," owned informally by "whoever implements Story 2.2.3." If skipped or its result is ignored under time pressure, importing a batch of queued issues spinner-gates on parallel-but-still-bounded-timeout peer queries per item, regressing exactly the interaction `research/ux.md` flagged as unacceptable. | User-reported or observed multi-second-to-tens-of-seconds hang when bulk-importing/triaging issues, worse whenever any peer is unreachable. | Convert the Unresolved Question into a hard AC on Story 2.2.3 before implementation — e.g., bulk import always uses the local-only check (mirroring Story 2.2.2), or an explicit per-batch concurrency/timeout cap — rather than leaving the decision to be made ad hoc during implementation. | P2 |
| 5 | GitHub issue #475 remains open with no committed owner or timeline (confirmed via `gh issue view 475` as of 2026-09-23). This plan correctly routes Phases 0-4 around it using the locally-running process's live `HostIdentity.ID`, but the specific gap Phase 5 exists to close — a `BacklogItemData` row whose creation and claim-recording happen in different processes (replay/restore, or the sync-mirroring case in failure #1) — keeps being misattributed to whichever process's identity happened to run `RecordClaim`. Since Phase 5 can't start until #475 lands, this isn't a temporary rollout gap; it's this project's permanent steady state unless someone external prioritizes #475. | A backlog item's claim/provenance (the claiming host in its deep link) doesn't match what a human would expect from context — e.g., after a disaster-recovery restore or a delayed sync-driven creation — discovered only when someone manually cross-checks a specific item, never via an automated signal. | Record explicitly (e.g., a note in `docs/reference/` or this project's own follow-up tracking) that Phase 5 is indefinitely blocked on an external dependency outside this team's control, with a periodic check on #475's status — so the gap stays a known, tracked limitation rather than quietly becoming permanent by default. | P3 |

## P1 Items (address before implementation)
- [x] Failure #1 — **Resolved, but not as originally prescribed.** The Phase 4 remediation pass verified against the actual code (`session/backlog_sync.go`'s `SyncOne`, `session/ent/schema/item_source.go`) that this failure's premise was wrong: `ItemSource` sync is external-system sync (e.g. GitHub REST polling), not host-to-host DB mirroring — no such mirroring plugin exists, so `RecordClaim` firing unconditionally there is correct, not a bug. Story 1.3.1 carries a revision note documenting this correction. The real gap this failure mode was gesturing at — no pre-creation *check* on the NL-create/`ItemSource`-sync paths — is closed by new **Story 2.2.4**.
- [x] Failure #2 — Resolved: Story 2.2.2 gained new AC + Tasks 2.2.2c/d/e. A dequeue-blocked-by-claim item now gets `MarkStuck(StuckReasonBlockedByClaim)`, surfaced via the existing `ListStuckBacklogItems → /unfinished → StuckItemsSection → BlockerChip` pipeline, plus a reason-gated `OverrideClaimBlock` RPC — no more silent log-only skip.

## Summary
5 failure modes identified: 2 P1, 2 P2, 1 P3. Top failure mode: Story 1.3.1's claim-recording choke point stamps every `CreateBacklogItem` call — including ordinary `ItemSource` cross-host sync — with the local host's own identity, so the feature's intended audience (multi-host operators) can get a false "already claimed elsewhere" the moment normal sync mirrors an item onto a second host.
