# Pre-mortem: review-gate-stale-session-rework

**Date**: 2026-07-24

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Both recalibrated thresholds (5 min badge, 15 min rework-gate) turn out to be wrong in the same direction as the original bug — still too short, or now needlessly too long — because they were chosen by reasoning about plausible turn/tool-call durations rather than measured against this specific instance's actual distribution of LLM turn lengths. | Either the Review Queue badge is still noisy (many false "Stale" flags) after deploy, or a genuinely-stuck session sits unflagged for the full 15 minutes with the user still relying on catching it manually. | ADR-001 already flags both values as best-effort estimates requiring live confirmation (not a silent gap). validation.md's "Live-Data Verification" section makes this a required post-deploy step, not optional. **Additional prevention not yet in the plan**: add a cheap, low-effort logging line at the `notifyIfActiveWorkSessionStale` call site recording the actual `idle` duration whenever it fires (already logged per Task 2.1.1's existing `log.WarningLog` line, which includes `idle.Round(time.Second)`) — confirm during implementation this log line survives unchanged so a few weeks of production logs can retroactively validate or invalidate the 15-minute choice without needing new instrumentation. | P2 |
| 2 | The new `StuckReasonReworkBlockedStale` reason and `StuckReasonStaleWork` end up firing simultaneously and confusingly on the same item in a case not anticipated during planning — e.g., an item bounces from `review` back to `in_progress` (a legitimate, different code path) while still carrying a not-yet-resolved `rework_blocked_stale` row from its time in `review`, producing a UI showing two overlapping "stale" chips that both look like they mean the same thing to the user even though the plan intends them to read as distinct. | User reports the stuck-items list looks duplicated/confusing for a single item, undermining the "durable trace should reduce anxiety" UX goal from research/ux.md. | Task 2.1.1d already adds a coexistence smoke test, but it only checks non-conflicting *storage* behavior, not *UI* legibility when two reasons are open simultaneously for the same item. **Recommendation for implementation**: when Story 2.1.2's resolve pass runs, also explicitly verify (as part of Task 2.1.2c/e's tests) that an item transitioning out of `review` status resolves the `rework_blocked_stale` row via `selfHealStuck` promptly, closing the most likely window for this overlap. This is already covered by design (selfHealStuck is status-anchored) but should be called out and confirmed with a test, not just assumed. | P2 |
| 3 | The layering fix (delegating to `BacklogService` via `ReworkBlockStaleResolver` instead of giving `BacklogLifecycleListener` a direct dependency) is correct in principle but the concrete implementer, working from the plan text alone, reaches for the wrong existing precedent or re-derives a slightly different interface shape than `StaleWorkRemediator`'s, introducing a second, subtly inconsistent delegation pattern into the same file. | Code review flags an interface that doesn't match `StaleWorkRemediator`'s established shape (naming, nil-safety, guard pattern) during Phase 6 verification, requiring rework. | plan.md's Task 2.1.2a already explicitly says "mirroring `StaleWorkRemediator` exactly, including the nil-safe getter pattern the other three `Set*` fields use" — this is about as explicit as prose guidance can be. **Residual risk accepted**: this is inherent to any plan executed by a fresh implementation session without the planner's full context; Phase 6's architecture review layer is the intended backstop for exactly this kind of drift, not something Phase 4 can fully close in advance. | P3 |
| 4 | The proto regeneration (`make proto-gen`, Task 1.3.1b) picks up unrelated drift from other in-flight uncommitted changes in the working tree (this repo's CLAUDE.md flags proto-gen as a known source of noisy diffs / CI rate-limiting issues), and the implementer either commits unrelated regenerated-file changes alongside this feature or, worse, fights the regeneration and hand-edits generated files. | A PR review flags an unexpectedly large diff touching unrelated generated files, or CI fails on a proto/gen mismatch check unrelated to this feature's actual change. | adversarial-review.md already flagged this as a minor process risk with the recommendation "isolate the feature's own diff into its own commit." **Recommendation**: explicitly instruct the Phase 5 implementation to run `make proto-gen` from a clean working tree (verify `git status` shows only the expected proto file changed before running it) rather than after other in-progress edits, to minimize the chance of picking up unrelated drift. | P3 |
| 5 | The fix ships, the immediate false-positive rate drops as intended, but the underlying behavioral root cause the user's *original* mental model was chasing — "why did AC-completion seem to trigger premature review" — was never actually the true root cause (confirmed false in this plan's own requirements.md), and a *different*, still-undiscovered trigger for premature/unwanted review requests exists that this fix does nothing about, resurfacing later as a "the bug is back" report that is actually a different bug wearing the same symptoms. | User reports items going to `review` unexpectedly again, distinct from the "stale-but-alive" symptom this fix addresses, some weeks after this ships. | This is explicitly out of this plan's scope — requirements.md already confirms (from the prior investigation) that `report_progress`/AC-completion does not trigger review transitions, and this plan does not touch that code path at all, so there's nothing in *this* plan to fix for that concern. **Prevention**: none needed within this plan's scope; flagging here only so that if a superficially-similar report recurs post-ship, the response is "investigate as a new/different bug" rather than "assume this fix regressed," since this fix's scope was deliberately narrower than the user's original (and already-disproven) hypothesis. | P3 |

## P1 Items (address before implementation)

None. All five identified failure modes are P2 or P3 — none are both likely and catastrophic. The two P2 items (#1, #2) already have concrete, low-cost mitigations either already present in the plan (ADR-001's best-effort framing, Task 2.1.1d's coexistence test) or added above as implementation-time guidance rather than requiring a plan.md restructure. No blocking changes required before Phase 5.
