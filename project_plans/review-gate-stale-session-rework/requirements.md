# Requirements: review-gate-stale-session-rework

**Date**: 2026-07-24
**Type**: bug fix (backend detection/threshold logic) + small feature addition (durable stuck-state surfacing)
**Complexity**: 2 — localized backend fix + UI surfacing, reusing an established pattern (StuckReason)

## Problem Statement

The mobile Review Queue showed 37 of 41 items flagged "Stale — No activity for Nm — session may be stuck or waiting," and a rework attempt was blocked by a toast: "Rework blocked by a stale-but-alive session." A prior investigation (this session, high confidence, not independently re-verified since) traced this to two compounding issues, not the user's original hypothesis (AC-completion triggering premature review requests — confirmed false; `report_progress` never transitions item status):

1. **Threshold miscalibration.** A single hardcoded 2-minute `StalenessThreshold` (`session/review_queue_poller.go:49`, itself "reduced from 5min" per its own comment) is reused for two different purposes with different tolerances: (a) the general Review Queue "Stale" badge (`session/review_queue_determiner.go:257-278`), and (b) `notifyIfActiveWorkSessionStale` (`server/services/backlog_service_triage.go:882-963`), which gates whether `AutoReopenAfterFailedReview` (`server/services/backlog_service_triage.go:1035-1054`) will refuse to respawn a rework session because the prior one "hasn't produced output" recently. 2 minutes is short enough to misfire on a single slow LLM turn or tool call, producing the observed 37/41 false-positive rate.
2. **No durable, actionable signal when rework is deferred.** When `AutoReopenAfterFailedReview` detects a live session and defers (correctly, by design — force-killing a live session risks double-work/lost state, per the incident referenced at `server/services/backlog_service_triage.go:906-916`), the only surfaced signal today is a single ephemeral toast. There is no persistent item-level state the user can come back to, see why rework is blocked, and act on (e.g., confirm the session is actually stuck and reopen it) — unlike the `StuckReasonPlanNotApproved` pattern already shipped for a structurally similar problem (session/domain/backlog.go, a backlog_lifecycle.go reconcile-detector, and StuckItem.tsx/StuckItemDetail.tsx/StuckItemsSection.tsx UI).

A contributing but lower-priority factor: the task-protocol prompt injected into every agent session (`session/backlog_context.go:106-115`, rule 8) instructs agents to "stay in this session... wait, then run `/backlog/status` again" after requesting review, but gives no concrete polling cadence — a well-behaved, quietly-waiting agent is therefore more likely to look stale than it needs to.

**Correction to the prior investigation, found during this ideation pass (2026-07-24) and requiring Phase 2 re-verification:** the `project_plans/backlog-stuck-item-visibility/` effort has *already shipped* — not just planned — a full durable `StuckReason` mechanism, including a `STALE_WORK` reason with complete UI surfacing (`web-app/src/components/backlog-stuck/{StuckItem,StuckItemDetail,StuckItemsSection,stuckReason}.{ts,tsx}`, label "Stale work session" 🟠) and a backend detector (`session/backlog_lifecycle.go`'s `reconcileStaleWorkSessions`, using a **2-hour** `maxWorkSessionStaleness` threshold and `MarkStuck`/`FindOpenStuckStates`/notify-once bookkeeping). This means the "no durable signal" framing of root cause #2 above is *not quite right*: durable, actionable stuck-item infrastructure already exists for stale work sessions in general.

What's actually missing is narrower: `notifyIfActiveWorkSessionStale` (`server/services/backlog_service_triage.go:882-967`), called specifically from `AutoReopenAfterFailedReview`'s stale-but-alive-session-blocks-rework path, is a **separate, parallel code path** that does not call `MarkStuck` at all — it only publishes a one-shot notification event via `eventBus.Publish`. It uses a different, much shorter threshold (the 2-minute `session.DefaultReviewQueuePollerConfig().StalenessThreshold`, chosen deliberately per its doc comment to reuse the Review Queue's own staleness computation) than the existing durable detector's 2-hour `maxWorkSessionStaleness`. So the actual gap is: **this specific blocked-rework scenario has no durable trace and uses an over-aggressive threshold, while a sibling mechanism for the same underlying problem (stale work session) already has both a well-calibrated threshold and full durable UI surfacing.** The most likely fix shape — to be validated in Phase 2/3, not assumed here — is routing `notifyIfActiveWorkSessionStale`'s scenario through the existing `StuckReasonStaleWork` durable mechanism (or a closely related new reason distinguishing "blocking a rework attempt" from "in_progress and idle") instead of duplicating detection with a second, shorter threshold and a toast-only signal.

This requirements doc treats both the original prior investigation and the correction above as a *starting point*, not gospel — Phase 2 research must re-verify all cited line numbers/behavior against current `main` before the plan relies on them.

## Users / Consumers

Single user (Tyler), via the stapler-squad web UI (desktop and mobile) and the underlying backlog automation/reconciliation loop (`server/dependencies.go` reconcile ticker) that drives it. No other consumers — self-hosted, single-tenant instance.

## Success Metrics

- The Review Queue's false-positive "Stale" rate drops from the observed 37/41 to a small minority reflecting genuinely-idle-or-stuck sessions, verified by re-checking the live Review Queue after the fix ships against the same class of items that triggered the original report.
- When a rework attempt is legitimately deferred because its prior session is stale-but-alive, that state is durable and actionable (visible after the triggering toast has scrolled away/been missed, with a clear path to confirm-and-reopen) rather than depending on the user having seen the one-time toast.
- No regression to the deliberate safety behavior that already exists: a live session must never be force-killed just because output has paused (per the incident this policy already guards against).

## Constraints

- Single-developer, self-hosted instance — no multi-tenant/auth considerations.
- Must not weaken the existing "never force-kill a live session" policy in `AutoReopenAfterFailedReview` — any threshold or UI change must still leave the human (or an explicit, confirmed action) as the one who decides to reopen over a still-running session.
- Existing `docs/registry/` feature-registry rule applies to any new RPC/UI component (`.claude/rules/feature-registry.md`).
- Should reuse the already-shipped `StuckReason` + reconcile-detector + `web-app/src/components/backlog-stuck/*` UI pattern (see `StuckReasonPlanNotApproved` and, especially, the closely related `StuckReasonStaleWork` already covering `reconcileStaleWorkSessions`) rather than inventing a parallel mechanism, unless research finds a concrete reason this case doesn't fit that shape.
- Must not duplicate or conflict with the adjacent, already-planned `project_plans/backlog-stuck-item-visibility/` effort (durable stuck-state storage/detection/UI for 4 *other* stuck-item root causes) or `project_plans/review-queue-state-detection/` (general working/idle/stuck detection for the Review Queue). This plan is scoped specifically to the stale-work-session-blocks-rework bug and its two contributing threshold/UI issues; where those other efforts already cover shared infrastructure (e.g. a `StuckReason` enum, a stuck-items UI section), this plan should extend that infrastructure, not fork it.

## Scope

### In Scope

- **A. Decouple the staleness threshold** used by `notifyIfActiveWorkSessionStale` / `AutoReopenAfterFailedReview` from the general Review Queue "Stale" badge threshold. Concretely: stop reusing `session.DefaultReviewQueuePollerConfig().StalenessThreshold` (2 min) for this gate. Research must determine the right value — either a bespoke, recalibrated duration (prior investigation suggested ~10 min, not to be assumed correct without justification) or, per finding B below, simply reusing the existing `maxWorkSessionStaleness` (2h) that the sibling `reconcileStaleWorkSessions` detector already uses for the same underlying "is this work session actually stuck" question, so the codebase isn't left with a third bespoke threshold. Also assess, independently, whether the general Review Queue "Stale" badge's own 2-minute threshold (the thing actually producing the 37/41 false-positive display) needs recalibrating — it is used for a different purpose (a "might be worth a look" queue signal) and may have a legitimately different correct value than the rework-block gate.
- **B. Give `notifyIfActiveWorkSessionStale`'s scenario a durable, actionable trace**, not just a one-shot toast. The `StuckReason` + reconcile-detector + `backlog-stuck` UI (`StuckItem.tsx`/`StuckItemDetail.tsx`/`StuckItemsSection.tsx`) pattern *already exists and is already wired up* for the closely related `StuckReasonStaleWork` case (`reconcileStaleWorkSessions`, 2-hour threshold, in_progress items). Determine in Phase 2/3 whether the correct fix is (b1) routing the `AutoReopenAfterFailedReview`-blocked scenario through that existing mechanism (e.g., calling `MarkStuck`/reusing `StuckReasonStaleWork` from within or alongside `notifyIfActiveWorkSessionStale`, accounting for the different item status at that point in the flow — review/failed-review, not in_progress), or (b2) a small, distinct addition (e.g. a new `StuckReason` value or a status-precondition change to the existing detector) if the existing detector's `BacklogStatusInProgress` precondition genuinely can't cover this item state. Building new UI components from scratch is explicitly NOT expected to be necessary — the existing `backlog-stuck` components should extend to cover this case with at most incremental changes (new label/icon entry, new action affordance).
- **D. (fold in if cheap)**: give the task-protocol's rule 8 ("stay in this session, wait, then check again") a concrete polling cadence to reduce false-idle appearance from well-behaved agents.
- Feature registry entries for any new RPC/UI component per `.claude/rules/feature-registry.md`.

### Out of Scope

- **C. Auto-escalation past a long grace period** (~30 min) that detaches a stale `ItemSession`'s bookkeeping and proceeds with rework without killing the still-running tmux process. Flagged by the prior investigation as higher-risk (double-work/double-ship risk) and needing its own design — noted as future work, not built or designed in detail here.
- Changing the fundamental policy that live sessions are never force-killed to unblock rework.
- The 4 other stuck-item root causes already covered by `project_plans/backlog-stuck-item-visibility/` (rework-cap silent parking, non-durable notify-once bookkeeping in general, non-converging review cycling, PR-ready-but-unmerged).
- General session working/idle/stuck detection heuristics (spinner/tool-call/prompt pattern matching) — that is `project_plans/review-queue-state-detection/`'s territory; this plan only touches the *threshold values* and *what happens when a session is judged stale in the rework-blocking path specifically*.
- Any change to review-verdict logic or the diff auto-repair mechanism.

## Open Questions

- Exact recalibrated threshold values for (a) the general Stale badge and (b) the rework-block gate — left to Phase 2 research (grounded in realistic Claude Code turn/tool-call durations, and in whether reusing `maxWorkSessionStaleness` outright is preferable to a bespoke value) and Phase 3 planning, not assumed from the prior investigation's suggested "~10 min."
- Whether the general 2-minute Stale badge should change at all, or whether its higher sensitivity is intentional for a different consumer (e.g., a "might be worth a look" signal vs. a "block an automated action" gate) — research question, not pre-decided.
- Whether `notifyIfActiveWorkSessionStale`'s scenario should reuse `StuckReasonStaleWork` verbatim (with the detector's `BacklogStatusInProgress` precondition relaxed or generalized) or needs a distinct `StuckReason` value because the item is in a different status (post-failed-review, not in_progress) at the point `AutoReopenAfterFailedReview` runs — this is the central architectural question for Phase 3 and should be resolved with a concrete look at what backlog status an item is actually in when `notifyIfActiveWorkSessionStale` fires, not assumed.
- Exact reuse boundary with `project_plans/backlog-stuck-item-visibility/`'s (now largely shipped, not just planned) `StuckReason` infrastructure — Phase 2 research must confirm current implementation status against `main`, including whether that project has any of its own still-open follow-up work touching this exact area.
