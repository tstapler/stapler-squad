# Features Research: review-gate-stale-session-rework

**Date**: 2026-07-24

## Comparable features already in the codebase (11 existing `StuckReason` values)

The `session/domain/backlog.go` `StuckReason` catalogue (11 values, see architecture.md for the full list) is the direct, already-shipped analog for everything this feature needs to build. Each existing reason follows the same shape: a detector (periodic reconcile-tick check or an inline call from a triage/lifecycle function), a `MarkStuck` call with an `expectedStatus` precondition, notify-once semantics via `MarkStuckNotified`, and generic UI rendering via the `backlog-stuck` component set. The two most directly relevant precedents:

- **`StuckReasonPlanNotApproved`** — the pattern explicitly cited by the user's own investigation as worth reusing: a periodic gate refusing to proceed (there: `DequeueNextQueuedItems`' planning gate; here: `AutoReopenAfterFailedReview`'s liveness guard) that previously had only an ephemeral log/notification and no durable UI trace, fixed by wiring it into the `StuckReason` system.
- **`StuckReasonStaleWork`** — even closer: the *exact same underlying question* ("has this work session gone stale") already has a mature, tested, durably-marked, remediated implementation — just scoped to `in_progress` items, not `review`-status items whose reopen is blocked. This is this feature's single strongest reuse opportunity (see architecture.md).

## Edge cases and failure modes the design must handle

1. **Item transitions status mid-check.** Between `AutoReopenAfterFailedReview` reading the item's status and any new `MarkStuck` call, the item could have moved (e.g. a human manually clicked "Reopen for Revision" in the same window). `MarkStuck`'s `expectedStatus` precondition already handles this (returns `applied=false` on mismatch, per `TestMarkStuck_should_returnAppliedFalse_When_StatusPreconditionMismatch`) — the new call site must check and handle `applied == false` the same way existing call sites do (skip, don't error).
2. **Session actually finishes between staleness detection and the next tick.** The existing `resolveStuckLogged` pattern (used by `reconcileStaleWorkSessions`' "poll-shaped resolve" pass, `session/backlog_lifecycle.go:2000-2021`) already handles "item was marked stuck, but a later tick finds it's no longer stale" — clear the `BacklogStuckState` row. Any new reason/detector needs the equivalent resolve pass, or (if reusing `StuckReasonStaleWork` verbatim with a widened status filter) gets this for free.
3. **Session ends (work session `EndedAt` gets set) while marked stuck.** `hasActiveWorkSession` becomes false on the next reconcile — the stuck state should resolve automatically rather than staying open forever pointing at a session that no longer exists. Needs explicit handling; not automatically covered by `MarkStuck`'s own logic.
4. **Multiple failed-review cycles on the same item.** `AutoReopenAfterFailedReview` already has a separate circuit-breaker (identical-failure-reason short-circuit, referenced around line 1062-1067) and a rework cap (`StuckReasonReworkCap`). The new stale-session gate must not double-count or conflict with those — e.g., an item that's both rework-cap-hit AND has a stale blocking session should show one coherent state, not two competing/flickering stuck-reason rows. Needs an explicit precedence decision (which condition wins, or can both be shown as separate rows simultaneously — the existing `FindOpenStuckStates` model already supports multiple open reasons per item, per `backlog_service_lifecycle.go:47`'s `[]domain.StuckReason{AbandonedReview, StaleWork}` pattern, so multiple simultaneous reasons is an established, supported shape).
5. **`sessionStopper`/`eventBus` unavailable** (nil, per `notifyIfActiveWorkSessionStale`'s existing guard) — see pitfalls.md #6. Decide explicitly whether the durable-mark path can still fire without a liveness signal, or must skip identically to the notification path today.
6. **The "Reopen for Revision" button's existing behavior when clicked on a session that is, in fact, still legitimately working** — this is a pre-existing UX risk (a human overriding a false "looks stuck" read and yanking a genuinely-productive session), not new to this fix, but worth confirming `GateVerdictBox`'s existing confirmation UX (feedback text field, `handleReopenSubmit`) is adequate friction before this fix starts actively directing more user attention toward that button via a new durable list entry.

## Unstated needs beyond the explicit requirements

- **A way to tell, from the stuck-items list alone, that "stale work session" here specifically means "blocking an automated rework, not just idling"** — implied by requirements.md's emphasis on "actionable," but worth calling out as a concrete need: the label/copy should communicate urgency/actionability, not just "something's stale."
- **Confidence that recalibrating the threshold won't need a second, disruptive round of tuning** — since the original 2-minute value itself carries a comment ("reduced from 5min"), implying it has already been tuned at least once in the wrong direction before. Whatever new value ships should have its rationale documented (see pitfalls.md #1) so a future "it's still too aggressive/too lax" report has something to check against instead of repeating blind trial-and-error.
- **Verification against the *live* instance**, not just unit tests — the original bug report was a live-data observation (37/41 items). Validation.md should include a manual/live-data check step (re-running a query against the live Review Queue after deploy), mirroring how `backlog-stuck-item-visibility`'s own requirements.md defined its success metric via live-data re-verification.
