# Pitfalls Research: review-gate-stale-session-rework

**Date**: 2026-07-24

## 1. Threshold recalibration — picking a wrong value is the highest-likelihood way to reintroduce the exact bug

- **Too short** (anything close to the current 2 min): reproduces the reported 37/41 false-positive rate almost exactly — a single slow LLM turn, a large tool call (e.g. a big `Read`/`Bash` invocation), or a moment of heavy tool-output buffering can easily exceed 2 minutes without the session being remotely stuck.
- **Too long**: defeats the purpose of the gate — a genuinely-hung session (crashed process, deadlocked tool call, runaway loop) stays invisible for the full window, during which the item sits silently un-reworkable with no automated recourse and only the "check it manually" escape hatch (which requires the user to already know to look).
- **Evidence for calibration**: the *existing*, already-battle-tested `maxWorkSessionStaleness` (2 hours, `session/backlog_lifecycle.go:1874`) was explicitly "tuned for interactive/foreground triage sessions where a liveness signal isn't available" per its own doc comment context — i.e., someone already did this calibration work for a structurally similar problem (is a work session that reports progress via `report_progress` actually stuck). Reusing it outright avoids inventing an unvalidated third number, but note it was tuned for `in_progress` items broadly, not specifically for "review just failed, now waiting on the same still-open session" — the shapes are similar but not identical, and Phase 3 should confirm rather than assume the 2h figure transfers unchanged.
- **The review-queue-state-detection project's own FR-3 already proposed a *third* number** — a 5-minute "stuck" threshold for its own `session.state.stuck` event (`project_plans/review-queue-state-detection/requirements.md:60`) — for yet another consumer. Three different subsystems independently reaching for three different numbers (2 min, 5 min proposed, 2 hr) for conceptually related "is this session stuck" questions is itself a pitfall: without an explicit decision about which of these is canonical for which purpose, this fix risks becoming a fourth uncoordinated number instead of consolidating the confusion.
- **Recommendation for Phase 3**: don't silently pick a number and move on — write down explicitly, in the plan or an ADR, *why* the general Review Queue badge's threshold, the rework-block gate's threshold, and `maxWorkSessionStaleness` are allowed to differ (if they are), so a future investigator doesn't rediscover this same confusion.

## 2. Regressing the "never force-kill a live session" safety policy

- `AutoReopenAfterFailedReview`'s `hasActiveWorkSession` guard and `notifyIfActiveWorkSessionStale`'s entire existence trace back to a **documented past incident**: "the stop_session-deletes-branch incident" (referenced at `server/services/backlog_service_triage.go:906-916` and `docs/tasks/backlog-feature-improvement.md`'s `StuckReasonStaleWork` discussion). Any change here must preserve the invariant that a live session is *never* stopped, killed, or bypassed automatically — only observed and (now) durably flagged. This is explicitly called out as a hard constraint in requirements.md; the risk is a well-intentioned "just make item B fully actionable" implementation that adds a one-click "force reopen now" action without the same care `GateVerdictBox`'s existing "Reopen for Revision" flow presumably already has (confirmation step, feedback text field) around a destructive-adjacent action.
- Concretely: reuse the **existing** `onReopen`/"Reopen for Revision" RPC path rather than building a new, less-reviewed reopen action — this both avoids re-implementing a human-confirmation UX pattern and avoids a second, subtly different reopen code path that could diverge in behavior (e.g. different session-cleanup semantics) from the one already exercised in production.

## 3. Detector overlap / double-notification risk if a new StuckReason and the existing StuckReasonStaleWork both fire

- If Phase 3 chooses to widen `reconcileStaleWorkSessions`' status filter (to also cover `BacklogStatusReview`) *and* keep `notifyIfActiveWorkSessionStale`'s separate call site, there's a real risk of **two independent code paths racing to `MarkStuck` the same item** with different `lastProgress` timestamps or slightly different `stuckContext` text, potentially fighting over `NotifiedAt` semantics or producing duplicate/flickering notifications. `MarkStuck`'s own test suite (`TestMarkStuck_should_updateLastCheckedOnly_When_OpenRowExists`) shows it's idempotent-safe for repeat calls with the *same* reason+item, but two different call sites computing overlapping "is this stale" logic independently is a coordination smell worth designing out explicitly (e.g., have one detector own the check, or make the boundary between the two crisp: `reconcileStaleWorkSessions` for `in_progress`, the new/extended path exclusively for `review`).

## 4. UI chip ambiguity if reusing `StuckReasonStaleWork` unchanged

- If the same `STUCK_REASON_STALE_WORK` label ("Stale work session" 🟠) is used for both "an in_progress item that's been silently grinding for 2 hours" and "a review-status item whose reopen is blocked by a stale session," the user loses the ability to distinguish "this needs a look eventually" from "this is actively blocking an automated action right now" at a glance — the two toast messages already use meaningfully different language ("may be hung or working silently" vs. "can't reopen for another rework attempt"). This is a design decision to make deliberately (see architecture.md's open question #2), not a detail to skip.

## 5. Task-protocol cadence fix (item D) interacting with whatever threshold is chosen

- If rule 8's rewrite adds a concrete polling interval (e.g. "wait ~2 minutes, then check again"), that interval must stay comfortably below whatever threshold Phase 3 picks for the rework-block gate — otherwise a *compliant* agent following the new instruction could itself trip the staleness gate purely by waiting exactly as told. Pick the polling cadence and the staleness threshold together, not independently, or verify the chosen threshold has enough headroom above the cadence (e.g. threshold ≥ 3-5x the polling interval to tolerate one or two slow turns).
- This is explicitly a "fold in if cheap" item per requirements.md — if it turns out to need real thought about interaction effects with rule 9's `MaxSameSessionReviewAttempts` cap or token-budget considerations (`BuildTokenBudgetedPrompt`), Phase 3 should feel free to defer it to a follow-up rather than let it block the primary fix.

## 6. Silent-by-design failure modes already present in `notifyIfActiveWorkSessionStale`

- The function already returns silently (no error, no log) if `sessionStopper`/`eventBus` are nil, if no active work session is found, or if the session "isn't currently tracked live" (`ok == false` from `TimeSinceLastMeaningfulOutput`). Any new `MarkStuck` call added to this path should NOT be gated by the same silent-return branches without consideration — e.g., if `sessionStopper == nil` (this repo's own doc comment implies this can happen, "no sessionStopper/eventBus wired"), should the item still get durably marked stuck via a liveness-agnostic path, or is silent skip still correct because there's no way to compute staleness at all in that case? Needs an explicit decision, not inheriting the existing early-returns by default.

## 7. Testing pitfall — time-based logic needs an injectable clock, not `time.Now()` sprinkled through new code

- The existing `staleWork(lastProgress, time.Now())` helper (referenced at `session/backlog_lifecycle.go:1948`) already takes `now` as a parameter specifically to be testable without real sleeps — any new threshold-comparison logic added for this fix should follow the same pattern (injectable/parameterized `now`) rather than calling `time.Now()` directly inline, to keep unit tests fast and deterministic (validation.md should mandate this).
