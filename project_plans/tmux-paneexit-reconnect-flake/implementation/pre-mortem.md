# Pre-mortem: tmux-paneexit-reconnect-flake
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `syncSessionsLocked`'s fetch→diff→swap races with `NotifySessionCreated` (`server_registry.go:151-155`, called from `tmux.go:1070-1071` on every real session creation) — `NotifySessionCreated` bypasses `syncMu` entirely, so a `syncSessionsLocked` call whose `list-sessions` fetch started *before* a session was created can still swap `r.sessions` *after* `NotifySessionCreated` marked it present, silently erasing it. This pre-existed the fix, but fast-recheck adds up to 2 extra `syncSessionsLocked` calls per backoff wait (vs. 1 per full reconnect cycle before), multiplying how often this window opens specifically during the connection instability windows this fix targets. | A session created while control-mode is reconnecting transiently reports `SessionExists() == false` right after creation — the exact flicker `NotifySessionCreated`'s own doc comment says it exists to prevent — surfacing as spurious "session not found" errors or a new flaky test in the session-creation path, not the pane-exit path. | Note the interaction explicitly in plan.md's Unresolved Questions (neither architecture-review nor adversarial-review's iteration-2 passes mention `NotifySessionCreated`), and consider a monotonic sequence/timestamp guard in `syncSessionsLocked`'s swap so a fetch that started before a `NotifySessionCreated` call can never overwrite it — or scope-note it as an explicitly accepted, pre-existing (not introduced) but now more-frequent gap, matching the plan's existing pattern for other accepted gaps. | P2 |
| 2 | The new `log.Debug("[registry] fast-recheck sync failed", ...)` call (Task 1.1.2a) fires on every failed fast-recheck attempt — up to 2×/backoff-wait, continuously for the duration of any real tmux-server outage — which is exactly the hot-poll-logging shape `tools/lint/hotpolllog/analyzer.go` exists to catch (its own doc comment cites two documented production incidents: 26,437 goroutine block events and 155M mutex-contention cycles from `DebugLog.Printf`/`InfoLog.Printf` in hot loops). The call sits between two `select` blocks inside the `for` loop, not textually inside a `CommClause` body, and uses `log.Debug(...)` (a plain function call) rather than the legacy `log.DebugLog.Printf`/`log.InfoLog.Printf` shape the analyzer's AST matcher looks for (`receiverIsHotLog` checks for an identifier/selector literally named `DebugLog`/`InfoLog`) — so `make lint`/`make ci` pass cleanly, but for a reason unrelated to whether the operational risk the linter was built to prevent is actually absent. | Elevated goroutine-block or log-mutex-contention pprof signal correlated with a real tmux-server outage window, discovered only via profiling (`make analyze`/`.claude/docs/profiling.md`) days or weeks after ship, not via CI. | Move the failed-attempt log out of the loop (log once per `waitBackoffWithFastRecheck` call summarizing skip/failure counts, not once per attempt), or explicitly verify with a synthetic outage + `make analyze` / pprof profile before ship that this call site doesn't reproduce the documented incident shape — don't rely on `hotpolllog`'s green result as proof, since its AST pattern doesn't cover this call shape. | P2 |
| 3 | `reconnectLoop`'s `backoff` exists specifically to protect "a possibly-unhealthy tmux server from a reconnect fork-rate explosion" (the plan's own glossary language) — fast-recheck adds up to 2 extra `list-sessions` subprocess forks per backoff wait, independent of whether a connect attempt is even happening, reintroducing a smaller dose of exactly the fork pressure `backoff` exists to prevent, right when the server is least able to absorb it (the unhealthy-server scenario). At scale (many concurrent `TmuxServerRegistry` instances, one per active socket, during a systemic tmux/host issue), those extra forks compound. | During a real tmux-server degradation incident, server recovery is measurably slower or fork/exec error rates climb compared to pre-fix behavior, traceable to `syncSessionsFastRecheck`'s extra `list-sessions` calls layered on top of each `startControlMode` connect-attempt fork. | Have `waitBackoffWithFastRecheck` back off from fast-rechecking after N consecutive failed connect attempts (i.e., once it's clear the server itself, not just control-mode, is unreachable) rather than unconditionally firing `fastRecheckAttempts` every cycle regardless of `backoff`'s cause — or explicitly accept and document this as bounded, small-scale exposure (2 extra 150ms-timeout forks/cycle) rather than leaving it unaddressed in the plan's Non-goals framing ("only detection gets a decoupled fast path" implicitly assumes the fast path is free). | P3 |
| 4 | `waitForReconnectCycles`'s own timing budget (5s `backoffElevationPollTimeout` for 4 pulses, nominal ~1.5s / degraded ~3.1s) is tuned against a clean local run; under `-race` (2-10x slowdown) plus shared-CI-runner tmux-fork contention — the same class of slowdown this file's own `registryPollTimeout` comment and `newSessionWithRetry`'s retry logic already document for *other* tests in this package — actual per-cycle time (dominated by real `attach-session`/`list-sessions` subprocess forks, not just the timer sleeps) can exceed the nominal figures. This risk compounds if adversarial-review's own recommendation (bump `minElevatedBackoffCycles` 4→5, pushing nominal to ~3.1s / degraded to ~4.7s) is applied without widening the 5s ceiling to match. | `TestTmuxServerRegistry_PaneExitDetectedDespiteElevatedBackoff` itself starts failing intermittently in CI (`only observed N/4 reconnect cycles within 5s`) — trading the original flake for a new one in the regression test meant to guard against it. | Before shipping, run the new test under `-race -count=20` on a loaded/shared machine (not just a quiet dev box) to validate the 5s budget has real margin; if adversarial-review's `minElevatedBackoffCycles: 4→5` recommendation is adopted, widen `backoffElevationPollTimeout` proportionally (e.g., to 8-10s) rather than leaving it at 5s. | P2 |
| 5 | The accepted gap "no test exercises the `syncMu` `TryLock`/skip-if-busy path or the lost-update race `syncMu` was built to prevent" (plan.md Unresolved Questions, architecture-review's downgraded Concern) is not merely theoretical coverage debt — Failure Mode #1 above shows a concrete, real interaction (`NotifySessionCreated`) that the accepted-gap reasoning doesn't even mention, let alone test. Because the gap is real and untested, a future refactor (e.g., someone "fixing" `syncSessionsFastRecheck` back to a blocking `Lock()` for perceived correctness, or restructuring `syncSessionsLocked`'s fetch/diff/swap order) can silently reintroduce either the original priority-inversion bug or the `NotifySessionCreated` race, and `make ci` stays green throughout since nothing in the 2-file confinement asserts on either invariant. | A regression reappears in production (detection latency creeping back toward backoff-bound, or session-creation flicker) with no corresponding CI failure anywhere — discovered only via user report or the same backlog-flake-detection process that surfaced the original bug. | Per adversarial-review's own recommendation (already in the plan but not required for this fix): add a black-box, in-scope, probabilistic stress test in `server_registry_integration_test.go` (rapid session create/kill churn racing an intermittent keepalive kill/restore, asserting a once-killed session never transiently reappears and a newly-created session never transiently flickers to "not found") — doesn't need unexported access, fits the 2-file confinement, and would have a real chance of catching both the accepted gap and Failure Mode #1. | P2 |

## P1 Items (address before implementation)
None. Two rounds of architecture-review and adversarial-review already resolved the design's two genuine blockers (the unbounded `syncMu.Lock()` priority-inversion and the static-sleep regression test); the failure modes found here are secondary/operational risks (a pre-existing race made more frequent, a lint-blind-spot in an operational-safety linter, a small fork-rate reintroduction, CI timing tightness, and an untested-but-real coverage gap) — each plausible and worth fixing, but none independently likely *and* catastrophic enough to block shipping the core fix. Recommend addressing #1, #2, #4, and #5 as fast follow-ups (or folding #4's CI-load validation into Story 2.1.1's `-race -count=20` run before merge) rather than blocking this change.
