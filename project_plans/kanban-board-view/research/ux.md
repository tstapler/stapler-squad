# UX Research: Kanban Board View

Research for `project_plans/kanban-board-view/requirements.md`. Scope: interaction patterns, mental model / column ordering, accessibility, error/edge-case UX, and the jobs-to-be-done this feature serves.

## 0. What exists today (grounding for recommendations below)

- `SessionCard.tsx` (`web-app/src/components/sessions/SessionCard.tsx`) is a dense, information-rich card: title (inline-editable), status badge + sub-status chip, review/attention badge, GitHub PR badge, tags with inline editor, task-fraction progress, diff stats (+added/-removed), last-activity timestamp, memory-pressure badge, autonomous/workflow badges, and an expandable terminal-snapshot pane. This is a **list-card**, not a kanban-card — it's too tall/dense to use unmodified as a board card (see §1).
- `SessionStatus` enum (`web-app/src/gen/session/v1/types_pb.ts`): `ACTIVE`/`RUNNING`(alias)=1, `READY`=2 (deprecated), `LOADING`=3 (deprecated), `PAUSED`=4, `NEEDS_APPROVAL`=5 (**deprecated** — moved to sub-status), `CREATING`=6, `STOPPED`=7, `HIBERNATED`=8, `RESTORING`=9.
- `SubStatus` enum (only meaningful when lifecycle status is `ACTIVE`): `IDLE`, `PROCESSING`, `NEEDS_APPROVAL`, `ERROR`, `TESTS_FAILING`, `RATE_LIMITED`, `INPUT_REQUIRED`, `READY`, `SUCCESS`, `WAITING_FOR_AGENT`.
- "Needs Review" is **not** derived client-side from either enum. `ReviewQueueContext`/`useReviewQueue` fetches a server-computed `ReviewItem[]` queue (each with `reason: AttentionReason`, `priority: Priority`) via `GetReviewQueueRequest`/`WatchReviewQueueRequest`. `useApprovalsContext`/`useApprovals` is a **second**, independently 5s-polled list of pending tool-use `PlainApproval` objects. Both are orthogonal to `SessionStatus`/`SubStatus` — a session can be `ACTIVE` *and* have a pending `ReviewItem` *and* have a pending `PlainApproval` simultaneously. **This confirms the requirements doc's flagged ambiguity (line 27, Open Questions line 72) is real**: the board needs one explicit, documented precedence rule for which single column a session lands in when multiple signals are true at once.
- `groupSessions()` / `GroupingStrategy.Status` (`web-app/src/lib/grouping/strategies.ts:179-189`) already defines a status ordering: `Active(0) < Ready(1) < Loading/Creating(2) < Needs Approval(3) < Paused(4) < Stopped(5) < Hibernated(6) < Unknown(7)`. It's keyed off the deprecated top-level `SessionStatus.NEEDS_APPROVAL`, not the live `ReviewItem`/`SubStatus` signal — so it cannot be reused as-is for the board's "Needs Review" column, but its Active-first ordering is a useful precedent (see §2).
- No drag-and-drop library is installed (`grep -i "dnd\|drag" web-app/package.json` → no matches). This is a real build-vs-buy decision for Phase 2/3, not just a UX one.
- `SessionList.tsx` already has a working accessible-announcement pattern worth reusing verbatim: a visually-hidden `role="status" aria-live="polite" aria-atomic="true"` div (`#bulk-feedback-live`, line 1167) that persists across component unmounts specifically so screen-reader announcements survive UI churn. The board's "card moved to X" announcement should use the same pattern, not a new one.
- `.claude/rules/css-architecture.md` requires `createPortal(..., document.body)` for any `position: fixed`/`absolute` overlay, because those break silently under an ancestor `transform`/`filter`/`will-change`. **This applies directly to the drag-ghost/preview element** most DnD libraries render during a drag — if the chosen library's default drag-overlay renders in-place rather than via a portal, it must be re-parented to `document.body` or wrapped in `createPortal`, or the ghost will visually clip/misposition the first time it's dragged from inside any card that has a CSS transform (e.g. a hover-scale effect) applied.

## 1. Comparable UX patterns (Trello / Linear / GitHub Projects)

**Drag handle affordance.** The two viable patterns are (a) whole-card-is-draggable (Trello, GitHub Projects classic) and (b) a dedicated grip handle in a corner (Linear, GitHub Projects new). Whole-card dragging is faster to grab but conflicts with click targets *inside* the card — and `SessionCard.tsx` already has several inline-interactive regions (inline title edit, tag editor, snapshot toggle, overflow menu). A dedicated `::before` grip icon (visible on hover/focus, `cursor: grab`) avoids ambiguity between "click to open session" and "drag to move" — recommend this over whole-card drag given how interactive the existing card already is.

**Drop-zone highlighting.** All three tools highlight the target column (background tint + dashed/solid border) as soon as a drag crosses into it, and show a placeholder/ghost slot indicating exact insertion point within the column. This is table-stakes, not optional — without it, users lose track of which column they're about to drop into, especially with narrow columns on laptop-width screens.

**Card compactness vs. list-card density.** Board columns are narrower than a list row, so kanban cards are conventionally 2-4x denser than list rows: title + 1-2 status indicators + minimal metadata, with secondary detail available on hover/click rather than always-visible. Trying to fit `SessionCard.tsx`'s full field set (diff stats, tags, task fraction, memory badge, timestamps, snapshot toggle) into a board card at column width would either force a very tall card (defeating the "see everything at a glance" goal of the board) or unreadably cramped text. **Recommendation:** a purpose-built condensed `SessionBoardCard` showing title, program/type icon, status/sub-status chip, and at most one "why does this need me" badge (review reason or error), with tags/diff-stats/snapshot deferred to a click-through or hover tooltip — not a CSS-only shrink of `SessionCard`.

**Column WIP badges.** Trello and GitHub Projects show a simple `(N)` count next to the column header; Linear/Kanban-strict tools additionally color the count red when it exceeds a configured WIP limit. Given this board has no user-configurable WIP limits in scope (Out of Scope explicitly excludes new state semantics), a plain `(N)` count per column is sufficient for v1 — it directly serves the stated Success Metric ("identify... how many sessions are in each... without scrolling").

## 2. User mental models: column ordering and what drag-and-drop *means*

**Column order:** the stated default is Running / Needs Review / Paused / Complete — i.e., *not* strict left-to-right urgency. Whether "Needs Review" should be leftmost instead depends on the job-to-be-done (§5): a developer opening this board is scanning for "what needs me," not "what's currently executing." Running sessions require no action; Needs Review sessions block on the user. Putting Needs Review first matches the F-pattern scan users default to (leftmost/topmost = first attention), and matches the existing `ReviewQueuePanel`'s own framing as the thing that needs surfacing. **Recommendation: order columns Needs Review → Running → Paused → Complete**, overriding the literal order given in the requirements doc's Scope section — flag this explicitly as a Phase 3 planning decision rather than silently deviating, since the requirements doc lists that literal order under "In Scope" (line 39) and a reviewer may have intended it as fixed. If Running-first is intentional (e.g., mirroring how Trello's "To Do → In Progress → Done" convention reads left-to-right as a pipeline rather than by urgency), that's a legitimate alternative model — but it should be a stated decision, not a default inherited from the requirements doc's prose order.

**What dragging a card *means* — the biggest UX risk in this feature.** Kanban drag-and-drop, as popularized by Trello, means "move this card along a *workflow pipeline*" — a metaphor of forward progress. This project's "columns" are not pipeline stages; they're *session lifecycle states triggered by real, semi-destructive RPCs* (pause_session, resume_session, stop_session-equivalent). That mismatch creates two specific misreading risks:

1. **Dragging to "Paused" could be misread as "archive/deprioritize"** rather than "actually pause this running agent process, interrupting its work." In Trello, moving a card to a "Blocked" or "Later" column has zero side effects on the underlying work; here it has an immediate, stateful side effect on a live tmux session.
2. **Dragging to "Complete" is ambiguous** — does it mean "stop the session" (a destructive action, per the requirements doc's RPC constraint that Complete likely maps to a stopped/terminal state) or "mark as reviewed/done" (a label with no session-state side effect)? Users accustomed to Trello/GitHub Projects will expect the latter (soft categorization) by default; this board needs the former (hard state transition) per the Constraints section (line 25, reuses `pause_session`/`resume_session`/`stop_session`).

**Mitigation, in priority order:**
- A same-column-as-Trello card should never *look* draggable into a column the RPC can't actually reach in one hop (e.g., if there's no direct "Complete → Running" RPC, that drop target should be visibly disabled/rejected on drag-over, not silently accepted then erroring after drop).
- The drop should require a **confirming visual state**, not just an instant optimistic move: show the RPC verb inline during the drag-over highlight (e.g. the column header text changes to "Drop to pause session" while a card hovers over it), so the destructive framing is explicit *before* the drop commits, not just in a toast afterward.
- Undo affordance (§4) is doing double duty here — it's both an error-recovery mechanism and a "I didn't mean to do that" safety net for a misread drag gesture.

## 3. Accessibility (WCAG / ARIA / keyboard) for drag-and-drop

Native HTML5 drag-and-drop is **not** keyboard- or screen-reader-operable by default — this is a hard WCAG 2.1 SC 2.1.1 (Keyboard) requirement, not a nice-to-have, and it's explicitly called out as a Rabbit Hole risk in the requirements doc only for touch, not keyboard — keyboard accessibility needs equal weight in Phase 3 planning.

- **Keyboard-operable alternative.** The two established patterns (per the "4 Major Patterns for Accessible Drag and Drop" analysis, Salesforce UX/Jesse Hausler) are: (a) focus the card, `Enter`/`Space` to "pick up," arrow keys (or Tab, restricted to valid drop targets) to move between columns, `Enter`/`Space` again to commit, `Escape` to cancel; or (b) a plain context menu / overflow-menu "Move to…" action listing the other columns, invoked via keyboard or the existing `SessionActionsOverflow` component pattern already used on `SessionCard`. **Recommendation: ship (b) as the primary accessible path, not a fallback** — it's simpler to implement correctly, doesn't require simulating a drag state machine via keyboard, and is more discoverable (a visible menu item vs. an implicit "press Enter on a card to enter move-mode" gesture nothing else in this app currently uses). Treat true keyboard-simulated dragging as a stretch goal only if the chosen DnD library provides it for free (`@dnd-kit`'s `KeyboardSensor` does, out of the box, per its docs — Space to pick up, arrow keys to move 25px/step or between droppable regions, Space to drop, Escape to cancel).
- **ARIA live region for card moves.** Every move (drag or menu-triggered) must announce outcome via an `aria-live="polite"` region — e.g. "Session 'fix-login-bug' moved to Paused." Reuse the exact visually-hidden-live-region pattern already in `SessionList.tsx` (`#bulk-feedback-live`) rather than inventing a new one; it already solves the specific problem of surviving component unmount mid-announcement, which a board's column re-render on move will also hit.
- **Focus management after a move.** After a successful move (keyboard or mouse), focus must return to *the moved card in its new column*, not be lost to `document.body` (a common drag-and-drop accessibility regression — the dragged DOM node is often literally removed and reinserted, dropping focus). If the move fails and the card snaps back (§4), focus should return to the card in its **original** column, so a screen-reader user isn't left disoriented about where their selection went.
- **`aria-dropeffect`/`aria-grabbed` deprecation note.** These two ARIA 1.1 properties were the original W3C-recommended way to mark draggable/droppable state but are deprecated in ARIA 1.2+ with no direct replacement yet ratified — don't build new code around them. Modern accessible DnD libraries (dnd-kit, React Aria's drag-and-drop) instead rely on live-region announcements + roving `tabindex` + standard `role="button"`/`aria-roledescription` on the draggable, which is the pattern to follow here.
- **Color must not be the only signal.** Column identity and drop-target-valid/invalid state need a non-color cue too (icon, label text change per §2's "Drop to pause session" recommendation, border style) since several existing status colors (e.g. `statusPaused` vs `statusPausedDistinct` in `SessionCard.css.ts`) are already close enough in hue to risk failing WCAG 1.4.1 (Use of Color) if column identity depended on background color alone.

## 4. Error states and edge cases

- **RPC failure on drop.** Per the requirements doc's explicit Rabbit Hole callout (line 54) and general optimistic-UI practice: **optimistic move + toast-with-rollback is the right default**, not pessimistic (wait-for-RPC-before-moving) — the app already uses optimistic patterns elsewhere (`suppressApprovalSubStatus` prop on `SessionCard` exists specifically to hide a stale badge "during optimistic clear," confirming this codebase's established convention). On failure: animate the card back to its origin column (don't just vanish/reappear — an unannounced silent revert reads as a bug), fire an error toast with the concrete reason if the RPC returns one (e.g., "Couldn't pause session: already stopped"), and re-announce via the live region so screen-reader users aren't left believing the stale "moved" announcement. A one-shot "Retry" action in the toast is worth including given pause/resume/stop RPCs are exactly the transient-failure-prone class (network blip, tmux server restart per `.claude/rules/tmux-keep-server-on-restart.md`) this repo's own docs flag as a real risk in this codebase.
- **Empty column.** Show a minimal empty-state (icon + one line, e.g. "No paused sessions") rather than a bare blank column — a completely blank column is visually indistinguishable from "still loading" or "broken," especially the first time a user opens the board with e.g. zero sessions in Needs Review (the common/good case). Empty columns must still render as valid drop targets (don't collapse their width to zero), or dragging a card into an empty column becomes physically harder to hit than a populated one.
- **1 session vs. 50+ in one column.** The requirements doc already flags virtualization as a Non-Functional Requirement (windowed/virtualized columns) and a Feasibility Risk (combining `react-virtuoso` windowing with drag-and-drop is non-trivial). From a pure UX angle: a column with 50+ cards needs its own internal scroll (not page-level scroll) so column headers with WIP counts stay visible while scrolling one column — losing the header means losing the "how many" at-a-glance value this whole feature exists to provide. A column with exactly 1 card should not visually look "broken" (e.g. don't let a single short card leave a huge empty drop zone below it that reads as an empty column) — pad with the same empty-state affordance area used for zero-card columns, or fix a minimum column height regardless of card count.
- **Simultaneous board updates from another client.** This board reads live session state (same underlying data `SessionList.tsx`/`ReviewQueueContext` already subscribe to). If a session's state changes server-side (e.g., another workspace peer resumes a session, or a webhook auto-completes one) while the user is mid-drag on that same card, the drag should be cancelled gracefully rather than dropping into a column based on stale data — this is an edge case worth an explicit test case in Phase 4 validation, not just an implementation afterthought.

## 5. Jobs-to-be-done

- **Functional job:** "Let me see my whole fleet's workflow state in one screen without reading N individual status badges." The board's entire value proposition, per the requirements doc's own Success Metric #1, is replacing serial scanning (current list view, or toggling into the separate Review Queue panel) with parallel at-a-glance recognition — this is the classic kanban functional job, unchanged from Trello/Jira's original pitch.
- **Emotional job:** reducing "did I miss something" anxiety specific to managing *autonomous* agents — unlike a human task board where nothing happens without you, sessions here keep running, erroring, hitting approval gates, or going idle **without the user watching**. The emotional payload is higher-stakes than a typical kanban tool's "am I behind on my todos" because an agent stuck on `NEEDS_APPROVAL` or `ERROR` is actively burning wall-clock time doing nothing productive until noticed. This is why "Needs Review" as a distinct, prominent column (not buried inside a generic "Active" bucket) matters more here than column-ordering conventions borrowed from human-task kanban tools would suggest on their own (reinforces the leftmost-placement recommendation in §2).
- **Social job:** minimal but not zero — `list_workspace_peers` and the dual-consumer framing ("Existing web-app dashboard users (solo dev + any workspace peers)" per requirements doc's Users section) mean a shared workspace could have more than one person glancing at the same board. The board doesn't need collaboration features (no per-user cursors, no "who moved this card" audit trail is in scope) but should not actively mislead a second viewer — e.g., if peer A's drag briefly shows a card in a new column before the RPC confirms, peer B's simultaneously-loaded board should not show a different (stale) column placement for the same card without eventually reconciling, since a wrong shared read of "is this reviewed yet" is exactly the anxiety this feature is meant to reduce, not add to.

## Open items for Phase 3 planning (flagged, not resolved here)

1. Column order: Needs Review-first (urgency-driven, my recommendation) vs. Running-first (pipeline-driven, the requirements doc's literal order) — needs an explicit decision, not a default.
2. Precedence rule for a session that is simultaneously Running + has a pending `ReviewItem` + has a pending `PlainApproval` — confirmed as a real, unresolved ambiguity in the current data model (§0), not just a hypothetical the requirements doc was being cautious about.
3. Drag-and-drop library choice is a build-vs-buy call for Phase 2 research, not this doc — but whichever is chosen, its default drag-overlay/ghost rendering must be checked against the `createPortal` requirement in `.claude/rules/css-architecture.md` before adoption.
4. Keyboard-accessible move path (recommend: "Move to…" menu, reusing `SessionActionsOverflow`'s existing pattern) should be scoped as core v1, not deferred alongside touch-drag — WCAG keyboard-operability is a harder requirement than touch support, which the requirements doc already correctly treats as a Phase 3 scope decision.
