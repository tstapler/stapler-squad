## 1. General React DnD/kanban pitfalls — how they apply here

| Pitfall | Applies? | Notes |
|---|---|---|
| Mouse-only DnD, no keyboard alternative (WCAG 2.1.1) | **Yes — must mitigate** | No DnD library is currently a dependency (`grep -iE "dnd\|drag\|drop" web-app/package.json` → no hits, only `@tanstack/react-virtual` and `react-virtuoso`). Whichever library Phase 2/3 picks (e.g. `@dnd-kit/core`) must ship with keyboard sensor support (`@dnd-kit/core`'s `KeyboardSensor` is the standard answer) or the board is a WCAG regression vs. today's fully-keyboard-operable action buttons. Requirements' "read-only board, click to open a status-change menu" alternative (line 59) is the accessible fallback if DnD-only ships first — do not ship drag-only with no equivalent affordance. |
| Virtualization + DnD interaction problems | **Yes — flagged as a Rabbit Hole already** (requirements.md line 55) | `SessionList.tsx` uses both `react-virtuoso` and `@tanstack/react-virtual` (`web-app/package.json`). Most DnD libraries measure drop targets via DOM rects; a virtualized column that unmounts off-screen cards breaks (a) drop-target hit testing for cards outside the current window and (b) auto-scroll near column edges during drag. `@dnd-kit` handles this better than `react-beautiful-dnd` (unmaintained, doesn't support virtualization well) — Phase 2 build-vs-buy research should treat "works with virtualized lists" as a hard filter, not a nice-to-have. |
| Stale closures in drag handlers | **Yes** | `useReviewQueue.ts` (`web-app/src/lib/hooks/useReviewQueue.ts:235-272`) shows the codebase's established fix for this class of bug: a ref-backed handler (`handleReviewQueueEventRef`) populated in an effect with only-functional-dispatch-update bodies, specifically to avoid stale-closure reconnect bugs. Any `onDragEnd`/`onDrop` handler holding column membership, selected-session-ids (bulk select), or search-filter state in a closure should follow the same ref pattern rather than closing over React state directly, given DnD libraries typically register handlers once at mount. |
| Drop-target flicker | **Yes, generic risk** | Optimistic reordering during `dragOver` (moving the card in local state before drop) combined with the coming real-time invalidation described in §4 below is exactly the kind of double-update that produces flicker. Recommend: only mutate local "preview" position on `dragOver`; only fire the RPC + let server-driven state settle on `drop`. |
| Touch/scroll gesture conflict | **Explicitly out of scope for v1** per requirements.md Rabbit Holes / Out of Scope — Phase 3 must still explicitly pick desktop-only vs. tap-to-move vs. full touch-drag (not silently default to "drag-only" and break mobile, given `.claude/CLAUDE.md`'s "mobile + desktop UX requirement" memory note applies to all new frontend features). |

## 2. Registry rules — does drag-to-change-state need OmnibarAction/DetectorRegistry registration?

Read `.claude/rules/feature-testing-registry.md` and `.claude/rules/session-creation-registry.md` in full. Explicit conclusion:

- **No touchpoint in either registry applies.** `OmnibarAction` union + `dispatch.ts` covers *user-triggerable omnibar operations* (text-input-driven, dispatched through the omnibar's command surface: navigate, create session, pause, etc. — see the decision tree at the bottom of `feature-testing-registry.md`: "Triggers via a user action... in the omnibar"). A card drag on the board view is a **direct RPC call from board UI** (`pause_session`/`resume_session`/`stop_session` via `useSessionActions.ts`, same as today's per-session action buttons), not routed through the omnibar's action-dispatch pipeline. `DetectorRegistry` only matches typed omnibar *input strings* (URLs, shorthand syntax) — a drag gesture has no text input to detect.
- **`session-creation-registry.md`'s 7 touchpoints do not apply either** — that registry is scoped to *new session creation modes* (a new `SessionType`/enum value). Board view doesn't create sessions or add a session type; requirements.md explicitly puts "new `SessionStatus` enum values" out of scope (line 46).
- **Action needed**: none for these two registries. If the board later grows an omnibar-triggered action (e.g. `>board` command-prefix jump, or a `@board` alias), that specific feature would need registration — but plain drag-and-drop does not. State this explicitly in the plan so a future reviewer doesn't file a false-positive "missing registry entry" blocker.

## 3. CSS architecture pitfalls (`.claude/rules/css-architecture.md`)

Drag ghost/overlay elements are exactly the pattern that rule calls out as commonly hit:

- **`position: fixed`/`absolute` without `createPortal`**: the DnD library's drag overlay (e.g. `@dnd-kit`'s `<DragOverlay>`) must be portaled to `document.body`. `SessionList.tsx`'s ancestor tree likely has `overflow`/layout containers (virtuoso's scroll container, flex panels) — any `transform`/`filter`/`will-change` on an ancestor silently breaks `fixed` positioning per the rule. Existing portal usages to model after: `SessionPeekModal.tsx`, `TerminalContextMenu.tsx`, `QuickOpenPalette.tsx` (all under `web-app/src/components/sessions/`).
- **Hardcoded z-index**: the drag overlay/ghost card needs a new named slot in `zIndex` (`web-app/src/styles/theme-contract.css.ts:195-217`). Current ladder tops out at `tooltip: 1100`; a dragged card should render above board columns but the plan should decide precedence vs. `dropdown: 500`/`modal: 1000` explicitly rather than picking an arbitrary number. No slot for "drag overlay" exists today — must be added.
- **No new CSS Modules** — board/column/card styles must be `.css.ts` (vanilla-extract), colocated (`SessionBoard.css.ts` next to a new `SessionBoard.tsx`, per requirements.md's explicit steer toward a sibling component rather than inlining into the 1601-line `SessionList.tsx`).
- **No inline `flexDirection`/layout inline styles** — a board's column direction must not be set via `style={{flexDirection: ...}}`; use `data-*` + `selectors` in `.css.ts` per the rule, especially relevant if a "swimlane axis" toggle (line 40, reusing `groupSessions()`) changes layout orientation.
- **Dynamic per-column accent colors** (if design uses per-status/per-tag color coding) should go through the CSS-custom-property bridge pattern already documented in the rule, not hardcoded hex.

## 4. Review-queue real-time race condition (drag vs. WebSocket push)

Read `web-app/src/lib/hooks/useReviewQueue.ts` and `web-app/src/lib/contexts/ReviewQueueContext.tsx` in full.

- The review queue is **not a polled snapshot** — `ReviewQueueProvider` (`ReviewQueueContext.tsx:11`) mounts `useReviewQueue({ useWebSocketPush: true, autoRefresh: true })`, which opens a `WatchReviewQueue` stream (`useReviewQueue.ts:291-343`) delivering `itemAdded`/`itemRemoved`/`itemUpdated` events pushed directly into the Redux slice (`reviewQueueSlice.ts` via `addItem`/`removeItem`/`updateItem`).
- **Concrete race**: user starts dragging a card that is currently in the "Needs Review" column (i.e., it's a live item in `reviewQueueItemsWithLiveStatus`). Mid-drag, a server-side event fires — e.g. a teammate/another process acknowledges the same session, or the session's approval resolves on its own — delivering an `itemRemoved` event that pulls the session out of the review-queue slice *while the user's pointer is still over that column*. If the board's column membership is derived reactively from the same Redux selector (as it should be, to avoid a second source of truth), the card can vanish from under the cursor mid-drag, or the column's item list can reindex under a `dragOver` handler that assumed a stable array.
- **Also applies in reverse**: a session could be *added* to "Needs Review" via `itemAdded` while it's simultaneously being dragged out of some other column by the user for an unrelated reason — the same session object briefly has two "true" locations if column state isn't derived from one canonical source per render.
- **Mitigation options to put in front of Phase 3 planning** (do not decide here, this is pitfalls research, not the plan):
  1. Snapshot the drag's source-column item list at `dragStart` and diff against live state only on `drop` (not `dragOver`), so the card doesn't disappear mid-gesture even if the underlying data changes.
  2. On `drop`, re-validate that the session is still in a state consistent with the requested transition before firing the RPC (defense in depth alongside the RPC's own state-transition guard — see §6).
  3. If the target session vanished entirely (session deleted/session ended) mid-drag, cancel the drop with a toast rather than firing an RPC against a nonexistent session.
- This is the same *"acknowledge session with optimistic update, rollback via refetch on failure"* pattern already used in `useReviewQueue.ts:418-444` (`acknowledgeSession`) — reuse that established optimistic-update-then-reconcile shape for drag-triggered transitions rather than inventing a new one.

## 5. Flaky-test patterns this feature's tests might inherit

Per `.claude/rules/fix-flaky-tests-dont-defer.md`, checked for existing flakiness around session status transitions before assuming new board tests are safe:

- **Go**: `session/pause_resume_test.go` has 8 tests (`TestPause_should_NoOpSucceed_When_ActiveInstanceNeverStarted`, `TestResume_should_PerformRealResumeAndMarkStarted_When_PausedInstanceNeverStarted`, `TestPauseResume_should_UseSentinelErrors`, etc.) — no `t.Skip`/flake markers found in a scan of that file. `session/instance_concurrency_test.go` explicitly has **concurrency-race tests for the exact primitive a board's drag-drop would exercise concurrently from the UI**: `TestTransitionTo_ConcurrentPause`, `TestTransitionTo_ConcurrentApprove`, `TestTransitionTo_ConcurrentMixed` (lines 56, 102, 141). These exist because concurrent state transitions on the same session are a known hazard at the backend layer — a board view that lets a user rapid-drag or double-drop a card (or where a drag-drop RPC races the review-queue WebSocket-driven auto-transition from §4) is precisely the client-side trigger for that class of race. Any new backend test added for board-driven transitions should follow this file's existing concurrent-test pattern, not skip concurrency scenarios.
- **No currently-known flaky test names surfaced** in `session/pause_resume_test.go` or `instance_concurrency_test.go` via the recurring-flake grep (`docs/tasks/backlog-feature-improvement.md` names `TestRemoveHooksConfig_should_StripOnlyTheNamedHook_When_MultipleHooksPresent` in `server/services` and two `session/tmux` tests as the repo's known repeat offenders — neither overlaps this feature's likely test surface). `docs/tasks/test-coverage-core-logic.md:739` separately notes `useTerminalStream`'s `requestAnimationFrame`-based batching as a source of frontend flakiness — not directly reused by a board view, but if the board's drag-preview animation also uses rAF-based batching for smoothness, the same class of timing flake is a risk to design against (prefer deterministic state updates over rAF-coalesced ones in tests, or mock rAF explicitly).
- **Action for Phase 4 (validate)**: any new frontend test asserting on drag-and-drop timing must avoid `waitForTimeout` (already banned repo-wide per `.claude/rules/e2e-test-conventions.md`) and any new Go test covering board-triggered transitions should extend `instance_concurrency_test.go`'s existing pattern rather than adding a parallel, differently-shaped concurrency test file.

## 6. RPC failure mid-drag (session already stopped/paused by another process when dropped)

- Requirements.md already flags this as a Rabbit Hole (line 54) needing an explicit Phase 3 decision (snap-back / error toast / optimistic vs. pessimistic). Pitfalls-level findings to feed that decision:
  - The backend already returns **sentinel errors** for invalid transitions — `TestPause_should_ReturnAlreadyPausedError_When_AlreadyPaused` and `TestPause_should_ReturnInvalidTransition_When_NeverStartedFromNonPauseableState` (`session/pause_resume_test.go:66,82`) confirm the state machine rejects a pause/resume that's no longer valid rather than silently no-op'ing (with one documented exception: `TestPause_should_NoOpSucceed_When_ActiveInstanceNeverStarted` is a deliberate no-op success case, not a general precedent). A drag-and-drop board **must not assume the drop always succeeds** — the RPC can and will reject a transition if session state changed between drag-start and drop (e.g. someone else stopped the session via the CLI or another workspace peer's UI mid-drag).
  - `useSessionActions.ts` (`web-app/src/lib/hooks/useSessionActions.ts:24-26`) currently exposes `pause`/`resume` as thin wrappers with **no visible try/catch or error surface at that layer** — error handling for existing pause/resume actions apparently lives further up the call chain (caller-supplied `.catch`), not centralized. Whoever wires the board's drop handler to these RPCs needs to add explicit error handling at the drop-handler boundary (toast on failure + revert the optimistic card position) rather than assuming the existing hook already surfaces failures — this is a "verify the actual behavior, not the shape of the code" item for the implementation phase (per this repo's evidence-only discipline), not something this pitfalls doc can settle with the current audit.
  - Recommended shape (consistent with §4's `acknowledgeSession` reference pattern): optimistic move on drop → fire RPC → on success, leave it; on failure, revert the card to its source column, show a toast with the sentinel error message (state machine errors are already human-readable per the sentinel-error tests), and do not retry automatically (retries on a stale-state error will just fail again).

## Summary of concrete follow-ups for Phase 3 planning

1. Pick a DnD library with first-class keyboard-sensor support and documented virtualization compatibility (e.g. `@dnd-kit/core`) — treat both as hard filters in the build-vs-buy comparison, not nice-to-haves.
2. No OmnibarAction/DetectorRegistry entries needed for drag-to-change-state; state this explicitly in the plan so reviewers don't flag it as a missing touchpoint.
3. Add a new `zIndex` slot for the drag overlay/ghost card in `web-app/src/styles/theme-contract.css.ts`, and portal the overlay via `createPortal` (model: `SessionPeekModal.tsx`, `QuickOpenPalette.tsx`).
4. Derive "Needs Review" column membership from the same Redux-backed `useReviewQueueContext()` selector the rest of the app uses (don't fork a second source of truth), and snapshot drag-start state so a mid-drag WebSocket push doesn't yank the card out from under the pointer; re-validate at drop time before firing the RPC.
5. Extend `session/instance_concurrency_test.go`'s existing `TestTransitionTo_Concurrent*` pattern for any new board-triggered-transition backend test, rather than introducing a parallel concurrency-test shape.
6. Explicit failure-handling contract for drop-triggered RPCs: optimistic move → revert-on-failure + toast, no auto-retry, using the sentinel-error messages the state machine already returns.
