# Build vs. Buy: omnibar workflow color fix

**Verdict: build (direct one-line edit).** No existing tool in this repo would catch or automate this, and standing one up for a single-line swap isn't proportionate — file the detection gap as a follow-up instead.

## Findings

1. **No static linter can flag this class of bug today, and adopting one now isn't proportionate.** `web-app/.stylelintrc.js` only lints via `pnpm lint:css` → `stylelint 'src/**/*.css'` (`web-app/package.json:20`) — vanilla-extract `.css.ts` files are TypeScript object literals evaluated at build time, not `.css` files, so stylelint structurally never sees `AtCommandDropdown.css.ts`. No custom ESLint rule, `@vanilla-extract/recipes` convention, or design-token linter enforces "alpha/overlay token vs. solid text token" in this codebase — `theme.css.ts`'s `accentText: "#003d99"` comment (line 113-116) shows the same class of bug (translucent/hover token misused as text color) was already caught once by axe/manual review and fixed per-token with a hand-written contrast comment, not a rule. Writing a real static check (an ESLint rule walking vanilla-extract `style()` calls to flag known-background tokens used as `color:`) is a legitimate idea but is a multi-hour investment disproportionate to fixing one property value — worth a backlog/follow-up issue, not blocking this fix.

2. **The existing axe-core CI gate doesn't cover this component, and adding coverage isn't warranted for this fix.** `.github/workflows/ux-analysis.yml` runs Axe Core (WCAG 2.1 AA, blocks on critical/serious) and Lighthouse against pages already visited by `tests/e2e/*.spec.ts`. `tests/e2e/accessibility.spec.ts`'s `@feature` list covers backlog/session/notification/review-queue pages, not the omnibar's `@`-command dropdown, and grepping the e2e suite for `AtCommandDropdown` finds no spec that opens it — so axe never renders `slug` in the current CI run. Adding an e2e spec that opens the `@`-command dropdown and asserts axe passes would be reasonable as a follow-up (it would have caught this originally) but is separate work from the fix itself.

3. **No case for a codemod or script.** This is one property value in one `style()` call, already root-caused (`vars.color.accentHover` → `vars.color.accentText`) with a same-file precedent (`vars.color.accentText` used correctly two lines below in `item`'s sibling exports and in `JulesStatusBadge.css.ts:21,26`). A codemod is justified when the same wrong-token pattern repeats across many files; a targeted grep for `color: vars.color.accentHover` across `web-app/src/**/*.css.ts` found no other occurrences, so there's nothing else to sweep. Edit `web-app/src/components/ui/AtCommandDropdown.css.ts` directly.
