## Concerns

- [ ] **Task 3.1.5 (`session/backlog_review.go`, `BuildReviewCallOptions`)** — Growing the signature to `BuildReviewCallOptions(diff, codebaseWorkDir, repoPath string)` adds a third `string` parameter alongside two that are semantically adjacent and easily confused: `codebaseWorkDir` is itself derived from `repoPath` one call frame up (verified: `server/services/backlog_service_triage.go:2619` — `codebaseWorkDir, _ := s.resolveCodebaseWorkDir(ctx, item.RepoPath, mostRecentWorkSession)`), so both are directory-path strings in scope at the call site with no compiler-checked distinction between them. This is exactly the `type-driven-design` anti-pattern "`func f(from, to string)` — easy to swap args": a future edit or copy-paste at the `backlog_service_triage.go:2698` call site (or in the existing test fixtures in `session/backlog_review_test.go`, which currently pass a single `"/some/worktree"` string and will need updating for all 3 tests) could silently transpose `codebaseWorkDir` and `repoPath` and still compile and mostly pass — the resulting bug (wrong `REPO.md` resolved via `config.GetConfigDirForDir`, per ADR-decision "Snapshot loading site") would only surface as stale/wrong-repo memory content, which is already a known-accepted class of gap per Unresolved Question 2, making it easy to misdiagnose as "expected" rather than "we passed the wrong argument."
  **Remediation:** either (a) add a small parameter struct (`type ReviewCallInputs struct { Diff, CodebaseWorkDir, RepoPath string }`) so the two path-like fields are named at every call site instead of positional, or (b) at minimum add a unit test in `session/backlog_review_test.go` that passes visibly distinct `codebaseWorkDir` and `repoPath` values and asserts the memory snapshot was resolved against `repoPath`, not `codebaseWorkDir` — a regression guard for the exact swap this shape invites. Given this is a 3-argument internal function (not a wide public API), a param struct is proportional and cheap; don't over-build a newtype for it.

- [ ] **Task 1.2.1 vs. Domain Glossary (`session/opmemory/opmemory.go`, `readCappedFile`)** — The plan is internally inconsistent about this unexported function's signature. The Domain Glossary (plan.md line 85) specifies `readCappedFile(path string, maxBytes int) (content string, existed bool)`; Task 1.2.1 (plan.md line 193) specifies `readCappedFile(path string, maxBytes int, label string) string` — different arity, different parameter (`label` vs. none), and a dropped return value (`existed bool` vs. single `string`). Tracing forward: `LoadSnapshot` (Task 2.1.1) only needs the trimmed content string (both-empty check is done by string emptiness, not an `existed` flag), and `memory show` (Task 4.1.2) explicitly bypasses `readCappedFile` entirely, calling raw `os.ReadFile` itself specifically to distinguish missing-file from empty-file for CLI display. So no consumer in this plan actually needs `existed bool` — it's a dead/unused design element left over in the glossary entry, and whoever implements from the glossary first (rather than the task list) will build the wrong signature.
  **Remediation:** reconcile before implementation starts — adopt Task 1.2.1's shape (`readCappedFile(path string, maxBytes int, label string) string`, `label` used only in the two log lines) as authoritative, and update the Domain Glossary row to match (drop `existed bool`). Cheap now; confusing mid-implementation.

## Lens Notes (no findings beyond the above)

**Lens 1 — Structural integrity:** No SOLID violations found. Dependency direction is correct and cycle-free: `session/opmemory` → `config` (leaf) only; `server/services` and `session` → `session/opmemory` (verified no reverse edge — the plan explicitly identifies and avoids a `server/services` import-cycle risk for the rejected `ScanForSecrets` reuse). `session/headless/features.go` stays decoupled from `opmemory` entirely — it accepts a plain `memorySnapshot string`, so the prompt-construction layer never depends on the storage/file-I/O layer, only its already-loaded output. No DDD aggregate applies (two flat files, no entity/aggregate model). Testability is good — `STAPLER_SQUAD_TEST_DIR`-based isolation matches the existing `config/config_test.go` convention, and `LoadSnapshot`/`readCappedFile`/`ScanForPromptInjection` are all pure/isolatable functions.

**Lens 2 — Type-level design:** Aside from the `BuildReviewCallOptions` concern above, the plan is appropriately un-typed for its scope — `memorySnapshot` staying a plain `string` that gets tail-appended to another plain `string` (the existing `headlessTriageSystemPrompt` const) matches the codebase's existing convention for prompt text and doesn't need a Value Object; a `MemorySnapshot` newtype wrapping a `string` would add no compiler-checked invariant beyond what the function boundary already provides. "Parse-at-boundary" doesn't cleanly apply here since the output is textual prompt content, not structured domain data consumed downstream — correctly scoped.

**Lens 3 — Pattern selection:** No interface-pollution violations — the plan explicitly considered and rejected a `MemoryStore` interface (single implementation, none imminent), citing `.claude/rules/interface-pollution-checklist.md` by name; this is the correct call. No PoEAA pattern is missing or misapplied (no persistence layer beyond flat-file reads, correctly not wrapped in a Repository). Fully consistent with `research/build-vs-buy.md`'s recommendation: no new dependency, no OSS memory/RAG library, no SaaS API, deterministic denylist scanner (not an LLM classifier) for `ScanForPromptInjection`.
