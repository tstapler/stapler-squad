# Pre-mortem: backlog-session-item-linking
**Date**: 2026-08-16

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The exclusivity precheck in `linkSessionToItem` (Task 1.2.1e: `ListItemSessions` → check → `AttachSessionToItem`) is check-then-act with no lock or transaction around it, and `AttachSessionToItem` itself has no transactional guard either (pitfalls.md §2: `CreateItemSession` + `TransitionBacklogItemStatus` are two separate ent calls). Two sessions calling `link_session_to_item` for the same item within the race window both pass the precheck before either's attach completes, and both end up with live `role=work` rows on the same item. | Two agent sessions both successfully report progress / request review on the same backlog item; a reconciler or human notices duplicate/conflicting PRs or acceptance-criteria updates for one item, with no error ever surfaced to either session. | Wrap the read-check-write sequence (`ListItemSessions` exclusivity check + `GetItemSessionBySessionAndItem` idempotency check + `AttachSessionToItem`'s `CreateItemSession`) in a single `ent.Tx`, or add a DB-level uniqueness/serialization primitive (e.g. a partial unique index on `(item_id)` where `role=work AND ended_at IS NULL`, if the ent/SQLite setup supports it) so the second concurrent caller gets a constraint violation instead of silently succeeding. Add a concurrency test that fires two goroutines at `linkSessionToItem` for the same item and asserts exactly one succeeds. | P2 |
| 2 | The exclusivity check (`activeWorkSessionOwner`, Task 1.2.1a) rejects any relink while the *prior* session's `ItemSession` row still has `EndedAt == nil` — but `EndedAt` is only set by session-exit bookkeeping or a zombie-detector/reconciler sweep (`session/backlog_lifecycle.go`'s `UpdateItemSessionEnded`, `server/services/backlog_service_triage.go:2507`), not synchronously on crash. A session that crashes or is killed (e.g. by `make install-service` restarting tmux per `.claude/rules/tmux-keep-server-on-restart.md`) leaves a live-looking row until the next reconciler pass. A new session trying to pick up that exact in-flight work — the literal scenario this feature was built to unblock (requirements.md's "Gap 1") — gets `CONFLICT`, not success. | An agent calls `link_session_to_item` for an item it was told to pick up (e.g. from a triage handoff) and gets `CONFLICT: item already has a live work session (S_other)` where `S_other` is a session that is provably dead (its tmux session is gone), with no override path (Non-Goals explicitly excludes a "force relink" flag). | Either (a) have the exclusivity check consult session liveness (e.g. the same `SessionLivenessChecker` the zombie detector uses, per `backlog_lifecycle.go:1755`'s comment) instead of trusting `EndedAt` alone, or (b) explicitly document in plan.md that `link_session_to_item` inherits the reconciler's staleness window and is not a substitute for it, with a bounded acceptable delay stated and tested. As written, plan.md's Non-Goals forecloses the "force relink" escape hatch without acknowledging this specific collision with Gap 1's own motivating scenario. | P1 |
| 3 | `SessionAttacher` wiring depends on correctly threading `backlogSvc` through 5 call sites (`NewCore`, `NewHTTPHandler`, `RunServer`, `server/server.go:502`, `main.go:97`) with positional params. A mistake at any site that results in `deps.BacklogService` not actually reaching `NewHTTPHandler` (e.g. wrong parameter position that still compiles, or an initialization-order bug where `deps.BacklogService` is nil at `NewHTTPHandler` construction time) makes `h.attacher == nil` on the **HTTP transport**, indistinguishable at the call site from the intentional stdio-fallback degradation. | Every `link_session_to_item` call over the normal HTTP-connected transport returns `UNAVAILABLE`, and because that is the exact expected response for the *intentional* stdio-fallback case, nobody flags it as a regression — it looks like "working as designed" until an agent stuck on `PERMISSION_DENIED` in a live session (the primary, non-degraded path) escalates to a human. | Story 1.1.2's own acceptance criteria already specify a test that `h.attacher` is non-nil when `deps.BacklogService` is real — make sure that test asserts against the actual `NewHTTPHandler`/`server.go` wiring path (not just `NewCore` called directly with a hand-passed non-nil value), and add a startup-time log line (`InfoLog`) in `NewHTTPHandler` stating whether `attacher` ended up nil, so a misconfigured deploy is visible in logs immediately rather than only when an agent happens to hit it. | P2 |
| 4 | `pruneStaleSlashCommandFiles` (Task 2.1.1a) actively deletes `done-N.md`/`fail-N.md` files from a live worktree's `.claude/commands/backlog/` directory in a loop with no lock, called from `WriteSlashCommands` which is itself non-atomic (pitfalls.md §3). Before this feature, that directory's files were only ever overwritten in place — after this feature, a relink can make a file disappear entirely for a window. A concurrent reader (a human invoking `/backlog:done-3` in an IDE, or another process scanning the directory) can now hit `ENOENT` on a file that existed a moment ago, a failure mode that did not exist pre-feature. | A user (or the harness itself, e.g. `/backlog:help` enumerating available commands) gets a "file not found" error reading a slash-command file immediately after another relink completed, with no correlation shown between the two events in logs. | Note in plan.md/validation.md that this is a new, narrow, non-atomic deletion window (distinct from the pre-existing non-atomic *write* issue that's explicitly deferred) and either accept it explicitly as low-severity, or make the prune+rewrite a single pass over a temp directory + `os.Rename` swap (matching `WriteBacklogContextFile`'s existing atomic pattern, pitfalls.md recommendation #3) rather than delete-then-write in place. | P3 |
| 5 | `get_linked_item`'s reverse lookup (`GetItemSessionBySessionUUID`) only returns a result if an `ItemSession` row already exists for the caller. A session with **zero** rows ever — the literal root-cause scenario named in requirements.md ("the new session's UUID was never written to `item_sessions`") — gets `linked:false` and still has no MCP-native way to discover which `item_id` to pass to `link_session_to_item`. The tool ships, is discoverable via the new actionable-hint text, and works correctly for every session that *does* have SOME prior link — but the hardest instance of the original incident (a session that starts completely cold, with no row at all) is unchanged: it must still fall back to an out-of-band source (task description, PR link, stale slash-command placeholder) that this plan never validates is reliably present. | An agent with a genuinely fresh session (no prior `ItemSession` row) that is not told its `item_id` through any other channel remains stuck exactly as before this feature shipped — `get_linked_item` returns `linked:false` and gives it nothing actionable to call `link_session_to_item` with. | This is already called out in plan.md's Non-Goals cross-reference as an accepted gap ("Sessions that never call `link_session_to_item` are not retroactively fixed") — but that framing describes *not calling the tool*, not *lacking the information to call it correctly*. Add an explicit line to validation.md distinguishing these two gaps, and confirm (e.g. via a quick audit of how a freshly-spawned session actually learns its `item_id` today — slash-command file content, env var, or task prompt) that at least one reliable channel exists independent of `item_sessions`, so the claim "this fixes Gap 1" is scoped accurately rather than assumed. | P2 |

## P2/P3 items addressed during triad review (not required to gate implementation, noted for traceability)
- Failure #5 (P2) — Resolved in plan.md Epic 1.5: reading `session/backlog_context.go` confirmed
  `BuildSessionInitialPrompt` (the normal-mode spawn prompt) never embeds `item.ID`, unlike the
  triage-mode prompt builder (`session/backlog_triage.go`) which already does. Added a one-line
  fix (Task 1.5.1a) plus a test (Task 1.5.1b) so a session's own item_id survives even a total
  loss of its `item_sessions` row — this is the literal mechanism the "had to reconstruct the id
  by hand" symptom in the source incident traces back to.
