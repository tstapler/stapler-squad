# Adversarial Review: detection-architecture-refactors

**Date**: 2026-06-14
**Verdict**: CONCERNS

## Blockers

None. All three mandatory structural risks from the pitfall research are addressed and correctly sequenced in the plan:

1. **LoadPatterns concurrent-mutation hazard** — Addressed. "Critical Pre-Implementation Constraints" item 1 explicitly names the hazard and defers the fix to Epic 4 Story 4.2, which adds a `PatternSet.mu sync.RWMutex` and requires `LoadPatterns` to acquire it before mutating. Story 4.2.2 provides two concrete options (swap under lock; pointer-level atomic swap). The story explicitly calls this out in its acceptance criteria: "LoadPatterns… must acquire a write lock before mutating PatternSet fields." Not blocked.

2. **Ring buffer capacity collapse (500×2 → must be ≥2000)** — Addressed and correctly ordered. Epic 3 Story 3.3 increases `EventRingCap` to 2000 with rationale comment. The dependency graph places Story 3.3 inside Epic 3, and Story 3.2 (wiring the shared instance) follows Story 3.1; the risk register row for this explicitly states "Epic 3 Story 3.3 increases `EventRingCap` to 2000 BEFORE wiring shared instance in Story 3.2." Story ordering within Epic 3 is 3.1 → 3.2 → 3.3 in the document, which is the wrong order for safety (3.3 must precede 3.2 in execution), but the risk register cross-reference makes the intent clear. See Concern #1 below.

3. **Epics 1 and 2 before Epics 3 and 4** — Addressed. Dependency visualization and explicit "Depends On" clauses in Items 3 and 4 enforce this. Epic 3 text states "Requires Epic 2 complete (TerminalDetector interface)." Not blocked.

4. **Injection constructors before IdleDetector struct field changes** — Addressed. Epic 3 Story 3.1 adds `NewIdleDetectorWithDetector` and changes `IdleDetector.statusDetector` field type to `TerminalDetector` (interface), but explicitly holds field renames for Epic 4 via: "Verify all `idle_test.go` tests still compile: `d.now`, `d.lastStateChange`, `d.lastActivity` are NOT moved in this story." Not blocked.

## Concerns

- [ ] **Story 3.3 is sequenced AFTER Story 3.2 in the document** — The plan lists 3.1 → 3.2 → 3.3, but Story 3.2 wires the shared detector into `ClaudeController.Start()` while Story 3.3 increases `EventRingCap`. If an implementer executes them in document order, the shared ring runs at 500 for exactly one story before the cap is raised. The risk register states the cap must be raised BEFORE wiring; the story sequence contradicts this. **Recommendation**: Swap Story 3.3 and Story 3.2 in the document so the ordering is 3.1 → 3.3 → 3.2. Low effort to fix, high value for preventing a latent transient bug.

- [ ] **Missing test task: shared RecentEvents integration test** — Requirements R3.6 mandates: "Tests confirm that events recorded via the injected detector appear in `RecentEvents()` from both the controller and idle detector sides." The plan's Story 3.2 acceptance criteria mention "Events from both call paths appear in `RecentEvents() via the shared ring buffer" but there is no concrete test task written for this. Task 3.2.1 says only "`make test` — confirm existing ClaudeController tests pass." No new test is specified that exercises the cross-component event sharing. Without a new test, R3.6 is unverified at merge time. **Recommendation**: Add a task under Story 3.2: write `TestClaudeController_SharedDetectorEvents` (or similar) that injects `NewIdleDetectorWithDetector`, drives both a controller detect call and an idle detect call, then asserts both events appear in a single `RecentEvents()` call.

- [ ] **`atomic.Pointer[TerminalDetector]` guidance is ambiguous and risks implementation drift** — Story 2.3 note says: "use `atomic.Pointer[detection.StatusDetector]` internally; expose `TerminalDetector` via the accessor method" but also says "OR switch to a `Locked[detection.TerminalDetector]` field" and "Research the actual `atomic.Pointer` constraint." Go's `atomic.Pointer[T]` requires T to be a non-interface type; `atomic.Pointer[TerminalDetector]` where `TerminalDetector` is an interface is invalid. The plan's preferred resolution (keep `atomic.Pointer[StatusDetector]` internally) is correct, but the ambiguous "OR" path pointing to `Locked[TerminalDetector]` could cause an implementer to reach for a wrong, heavier-weight solution. **Recommendation**: Remove the "OR" alternative and the "Research" note. State definitively: "Keep `atomic.Pointer[detection.StatusDetector]` internally; the public accessor returns `detection.TerminalDetector`. Interface-typed `atomic.Pointer` is not valid in Go."

- [ ] **TerminalDetector interface method set in the plan differs from requirements** — Story 2.1 defines the interface with 4 methods: `DetectWithContext`, `DetectWithContextFromLines`, `RecentEvents`, `SetSessionID`. Requirements R2.1 also lists `DetectFromLines(lines []string) DetectedStatus` as a required method. The plan's interface definition omits `DetectFromLines`. If any of the 5 call sites use `DetectFromLines` (which `review_queue_determiner.go` likely does given R2.1 names it), the compile-time check `var _ TerminalDetector = (*StatusDetector)(nil)` will pass but the interface won't cover all actual usages. **Recommendation**: Before Task 2.1.1, add an explicit step: grep all 5 call-site files for all method calls on their `*detection.StatusDetector` field and reconcile against the interface definition. If `DetectFromLines` is used anywhere, add it to the interface.

- [ ] **Epic 4 Story 4.2 LoadPatterns fix uses two incompatible locking strategies without choosing one** — Task 4.2.2 says: "replace `sd.patternSet` under `sd.patternSet.mu.Lock()` OR create a new `PatternSet` and atomically swap — the simplest safe approach is to add a `patternsMu sync.RWMutex` on `StatusDetector` that guards the `patternSet` pointer swap." This presents three options in one sentence. An implementer may combine them inadvertently (nested locks, double-mu). **Recommendation**: Pick one. The cleanest safe approach for `LoadPatterns` is: create a new `PatternSet` (no in-place mutation), then swap the pointer under a short write-lock on a `StatusDetector`-level `sync.RWMutex`. State this explicitly and eliminate the other options.

- [ ] **`getDefaultPatterns` to registry migration (Task 4.2.3) may silently change pattern union semantics** — The task says `getDefaultPatterns()` becomes a "thin wrapper over the registry for the union of all patterns." But `StatusPatterns` has 9 categories; merging across 5 binary detectors by appending slices produces a union where every binary's Ready patterns are concatenated into one slice. The current `getDefaultPatterns()` produces this union manually; the new approach assumes each binary's `Patterns()` returns non-overlapping patterns. If any binary's patterns intentionally override or supersede another's (e.g., a shared "esc to interrupt" Ready pattern appears in both claude.go and gemini.go), the union has duplicates and pattern priority ordering changes. **Recommendation**: Add an explicit acceptance criterion to Task 4.2.3: "Run `TestGeminiPatterns_AgyCoverage` and all `detector_test.go` tests unchanged; assert no duplicate pattern names in the merged union."

## Minors

- Story 1.1 Task 1.1.1 says `DefaultRegistry()` "returns empty registry (populated in 1.2)" but Story 1.2's acceptance criteria require `DefaultRegistry()` to call each constructor and register all 5. The task description is inconsistent with the story AC. Low risk since the AC governs, but a reader could implement 1.1.1 as an empty registry and think they are done.

- The plan introduces a `binaries` sub-package (`session/detection/binaries/`) but does not specify the import path guard or package declaration. If `binaries` imports `session/detection` for `BinaryDetector` and `StatusPatterns`, and `session/detection` imports `session/detection/binaries` in `DefaultRegistry()`, this is a circular import. The risk register flags this as "High if done wrong" and says `binaries` imports only `BinaryDetector` and `StatusPatterns` defined in `detection` — which is correct if `detection` does NOT import `binaries` at init time. Task 1.2.3 imports `session/detection/binaries` from `session/detection/registry.go`, which would create the cycle. The only safe resolution is that `session/detection/registry.go` is part of the `detection` package and imports `session/detection/binaries`; this is only circular if `binaries` imports back into `detection`. Verify the import direction is `detection` → `detection/binaries` (one-way) and not mutual. A build-time `import cycle` error will catch this immediately, so it is minor.

- Story 4.1 Task 4.1.2 says "Update `detectFromLines` to call `detectFromText` directly with pre-normalized string lines — NOT via `DetectWithContext`" but `detectFromText` may be a private method that operates on the current inline regex dispatch logic, not a separately defined function. The plan assumes `detectFromText` exists as a callable entry point without normalization. Verify the actual method exists and has the right signature before Task 4.1.2 or the task will need an extra refactoring step to extract it.

- `DetectionEventSink` in Story 4.3 moves `sessionID` out of `StatusDetector` but `SetSessionID` is in the `TerminalDetector` interface (Story 2.1). If `SetSessionID` delegates to `sink.SetSessionID` in Task 4.3.2, the delegation chain is: interface caller → `StatusDetector.SetSessionID` → `DetectionEventSink.SetSessionID`. This is fine but the ordering dependency (TerminalDetector interface must expose `SetSessionID`; `DetectionEventSink` must implement the same semantics) should be explicit in the Task 4.3.2 acceptance criteria. Currently it is not mentioned.
