# Feature Research: subagent-spawn-tracking

## 1. Existing "count" precedent in this codebase

Three distinct precedents, all worth reusing rather than inventing a new pattern:

- **`github_approved_count` / `github_changes_req_count`** (`proto/session/v1/types.proto:121,124`, both `int32` on the `Session` message) — the closest structural analog to `subagent_count`. `GitHubBadge.tsx` (`web-app/src/components/sessions/GitHubBadge.tsx:81-115`) takes these as optional numeric props and only pushes tooltip/text when `count > 0` (`if (approvedCount && approvedCount > 0) ...`). This is the "badge only when count > 0" pattern the requirements doc asks for (§5).
- **`ReviewQueueNavBadge.tsx`** / **`ApprovalNavBadge.tsx`** — nav-level (not per-session-card) badges computed client-side as `items.length` / `approvals.length` from an already-fetched array, not a server-computed int. These *always* render (even at 0) "for test visibility" per an explicit comment — the opposite of the github-count convention. Not the right precedent for a per-card badge; the github-count pattern is.
- **`review.total_items` / `by_priority` / `by_reason` maps** (`types.proto:741-750`) and **coverage_gap_count** (`types.proto:1124`) — aggregate int32/map counts computed server-side and shipped as static snapshot fields, refreshed on each poll/stream tick rather than incrementally patched. Same shape V1 wants for `subagent_count`.

**Freshness mechanism**: counts ride the existing `WatchSessions` ConnectRPC server-stream (`server/services/session_service.go:2061`), which already pushes `DetectedStatus`/`DetectedContext` per-session on every `EventSessionUpdated` (see `server/services/event_converter.go:20-40`: `sessionUpdatedProto.DetectedStatus = detection.DetectedStatusToProto(...)`, gated on `event.DetectedStatusTyped != detection.StatusUnknown`). This is a genuine push, not polling — confirms §4 below. No separate polling loop needed for the count; it's just one more field alongside `detected_status`/`detected_context` (proto field numbers 68/69 on `Session`, plus a parallel pair at 179/`sub_status` and 621 on other messages) that already flows through this same event path.

## 2. Edge cases specific to this feature

- **Multi-pattern collision / double-counting**: `waiting_for_background_agent`, `shells_still_running`, and `monitors_still_running` are three *separate* `StatusPattern` entries all mapped to the same `StatusWaitingForAgent` status, all at `Priority: 27` (`session/detection/detector.go:571-609`). Detection picks the first/highest-priority match per line (see `pattern_set.go:103`), so today only one pattern's count would ever be captured per detection pass — but if a single terminal snapshot contains multiple lines each matching a different one of the three patterns (e.g. Claude prints "Waiting for 2 background agents" on one line and "1 shell still running" on the next, both real, both currently active), a naive "capture group from the matched pattern" implementation only reports whichever line the detector last matched, silently dropping the other count rather than summing it. The requirements doc's phrasing ("a plain int field") doesn't specify sum-vs-last-match — this is a decision the plan phase needs to make explicit, and it should almost certainly be "last match wins" (matching existing regex-priority semantics) rather than summing, since shells/monitors/background-agents are conceptually different counters and summing them would misrepresent "3 tasks" as one homogeneous pool when it's actually 2 shells + 1 monitor.
- **Scrollback truncation/clearing mid-count**: detection is 100% regex-over-scrollback (no state machine memory of "last known good count" beyond whatever's in the buffer). If the terminal clears (e.g. `clear`, alt-screen switch, or scrollback ring-buffer eviction) while agents are still running, the next detection pass simply won't match any `WaitingForAgent` pattern and status reverts to whatever the next-priority pattern indicates — the count silently drops to 0/absent even though subagents are still live. This is the same class of staleness risk already called out in the requirements doc's "reset to 0 on transition away" rule (item 4) — that reset logic needs to distinguish "genuinely transitioned to a different real status" from "scrollback got clobbered and we lost the evidence," which the current regex-only pipeline cannot do reliably. Worth flagging as a known V1 limitation rather than solving.
- **Reconnect/resume**: Since detection re-runs against replayed scrollback on reconnect (there's no separate persisted "last known subagent count" field independent of the detector's own pattern re-match), the count *is* recoverable as long as the relevant status lines are still in the replayed scrollback window. If the scrollback window is smaller than the time since the last status-line print (e.g. long-running subagents with lots of interleaved output since), the count would read stale/absent (0) even though subagents are still actually running — a "shows 0 tasks but isn't actually idle" false-negative. This matches the requirements doc's own framing of the JSONL-pipeline as future work to solve this properly; V1 inherits the existing detector's replay limitations as-is.
- **Rapid flicker (3→2→3→1)**: No debouncing exists anywhere in the current detection→proto→UI pipeline for *any* status field, including `DetectedStatus` itself — every detection pass pushes straight through `WatchSessions` to the frontend. Nothing in `SessionCard.tsx` or `SubStatusChip.tsx` currently debounces status transitions. Given that precedent, a naive V1 implementation would let the count flicker on the badge in lockstep with however often the poller re-scans scrollback (see `session/instance_status.go` for the poll cadence). Since out-of-order subagent completion is plausible (they don't necessarily finish in launch order), this is a real UX risk worth a plan-phase decision (e.g. minimum-count-hold or only-decrease-after-N-consecutive-reads) — but note it would be a *new* pattern, not reuse of an existing debounce mechanism, since none exists today.

## 3. Unstated user needs beyond "show a badge"

- **Zombie-subagent detection on stuck sessions**: a session showing "3 tasks" for an extended period without any DetectedStatus change is the actual signal users want (a stuck session with orphaned subagents) — the raw count alone doesn't distinguish "3 subagents actively working" from "3 subagents that silently died/hung." V1's scope (regex count only, no JSONL) cannot answer this; it's explicitly named as follow-on work.
- **Background shells vs. Task-tool subagents are conflated** — the requirements doc says so explicitly in the Problem statement, and the pattern set confirms it structurally: `waiting_for_background_agent` (real Task-tool subagents / dynamic workflows) and `shells_still_running`/`monitors_still_running` (backgrounded shell processes, e.g. `run_in_background: true` Bash calls, or CI-watcher monitors) are semantically different things bucketed into one `StatusWaitingForAgent` status and, if summed, one badge count. A user orchestrating 3 real subagents needs a different mental model than a user with 1 subagent that itself kicked off 2 background shells. The badge as scoped ("⊕ 3 tasks") erases this distinction — worth flagging to the requirements/plan phase even though V1 explicitly punts on "distinguishing background shells from actual Task-tool subagents" (also named directly in the Problem statement).
- **"Is it safe to end this session"** — users pausing/stopping/closing a session with active subagents risk orphaning tmux panes or worktree state (see the repo's own `.claude/rules/tmux-keep-server-on-restart.md` and the backlog fix `8be3f242b "kill tmux pane, not just archive, on terminal work/review sessions"` in recent commit history) — a non-zero subagent count is exactly the kind of information that should gate or warn on session-close actions, but nothing in the V1 scope wires the count into any close/pause/stop confirmation flow. Worth a note for the plan phase even if implementing the gate itself is out of scope.

## 4. ConnectRPC streaming already pushes DetectedStatus/SubStatus — confirmed

Yes. `WatchSessions` (`server/services/session_service.go:2061`, a `connect.ServerStream[sessionv1.SessionEvent]`) already streams `DetectedStatus` and `DetectedContext` per session on every update via `EventSessionUpdated` → `event_converter.go`'s `sessionUpdatedProto.DetectedStatus = detection.DetectedStatusToProto(event.DetectedStatusTyped)` / `.DetectedContext = event.DetectedContext`, gated on `event.DetectedStatusTyped != detection.StatusUnknown`. `SubStatus` also exists as its own proto field (`sub_status = 54` on `Session`, `sub_status = 21` elsewhere) fed by the same detection pipeline (`session/detection/proto_mapping.go`'s `DetectedStatusToSubStatus`). A `subagent_count int32` field added next to `detected_status`/`detected_context` in the `Session` and/or `SessionUpdatedEvent` proto messages would ride this exact same already-wired channel — no new streaming plumbing needed, just: (a) the detector capturing the count into the detection result, (b) `Instance`/`event.go` threading it into the emitted event struct alongside `DetectedStatusTyped`/`DetectedContext`, (c) `event_converter.go` copying it into the proto the same way `DetectedContext` is copied, (d) frontend `SessionCard.tsx` reading it off the streamed `Session`/event payload the same way it already reads `detectedStatus`/`detectedContext` (see `SessionCard.tsx:124-126` prop declarations).
