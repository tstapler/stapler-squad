# Pre-mortem: subagent-spawn-tracking
**Date**: 2026-08-01

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | No-debounce decision ships a flickering badge — the plan justifies skipping debounce by claiming "no debounce exists anywhere in this detection→proto→UI pipeline today for any field," but `session/detection/idle.go` already has `DebounceDelay time.Duration // Delay before changing state to prevent flickering` on `IdleStateInfo`, the *same* struct returned alongside the count by `GetStatusAndIdleInfo` — precedent for exactly this problem exists one field over and was overlooked. | Users on multi-agent sessions see the count rapidly cycle (e.g. 2→1→2→0→2) every poll tick during active orchestration; filed within days as "the agent counter is buggy/jumpy." | Before implementation, read `idle.go`'s `DebounceDelay` logic and either (a) explicitly justify in plan.md why count doesn't need the same treatment `IdleStateInfo` gets in the identical call, or (b) reuse the existing debounce primitive for the count field too. Don't ship the "no precedent" claim without checking the neighboring field in the same return tuple. | P1 |
| 2 | "Winning line wins" (not summed) under-reports when multiple `WaitingForAgent` conditions are simultaneously true (e.g. 2 background agents AND 1 shell both matched on different lines) — badge shows the smaller/wrong number instead of any indication multiple things are running. | A user running heavy multi-agent orchestration sees "1 Agent" in the badge while actually observing 3 concurrent tool calls in the terminal; reports the count as "clearly wrong," undermining trust in the whole feature rather than just being incomplete. | Add one explicit product-facing caveat to the badge title/tooltip (e.g. `title="approximate — may not reflect all concurrent background work"`) so the UI doesn't imply false precision; alternatively downgrade badge copy from a bare number to "some agents active" when uncertainty is highest. Flag for product sign-off rather than silently shipping a number that can visibly contradict what's on screen. | P2 |
| 3 | Scrollback truncation causes a false reset to 0 while subagents are genuinely still running (accepted in Risk Control item 3 but not tested or guarded) — the count silently drops out of the visible tail window before the agents finish. | Badge disappears/zeroes mid-session even though the user can see (via other terminal output or session activity) that background work is still in flight; looks like the feature "stopped working" rather than a known scrollback-window limitation. | Add a one-line note to the SubStatusChip or session detail view (or at minimum a code comment + backlog follow-up) distinguishing "0 confirmed" from "0 because it fell out of the detection window," OR widen the reverse-scan window specifically for WaitingForAgent detection so it survives longer than other status transitions. At minimum, make this limitation visible in-product, not just in the plan doc. | P2 |
| 4 | Proto field number 72 collides with a field added by another PR between planning and implementation — the plan verified 72 is free *today* but explicitly notes this repo's SDD workflow frequently splits planning and implementation across sessions/branches, and the adversarial review's recommended re-verification step ("re-run the grep immediately before Task 3.1.1.1") was never folded into the final plan.md task text. | `make proto-gen` fails loudly with a duplicate-field-number error, or (worse) a silent merge where two branches both add field 72 to different fields and one PR's merge silently shifts semantics on a wire message every other in-flight branch also touches. | Add the explicit re-grep instruction (`grep -noE '= [0-9]+;' proto/session/v1/types.proto` scoped to `Session`) as the literal first line of Task 3.1.1.1 in plan.md before the implementer adds the field — this was already recommended by adversarial-review.md and simply wasn't applied to the plan text being executed. | P2 |
| 5 | The `bestCount` threading bug in `detectFromLines`'s two most complex branches (CR-segment loop, `StatusExecuting`-override switch) ships with a subtle miscount despite two rounds of review, because the two new tests (1.3.3.3) cover only one fixture each per branch, while the pre-existing regression tests that gate the PR check `status`/`desc` only and would pass even with `bestCount` silently wrong in an untested sub-case (e.g. a 3-way CR-segment collision, or two consecutive status overrides). | `make test` and `make ci` both go green; the bug surfaces later as a user report that the count is "sometimes right, sometimes not" with no clear reproduction, since it only manifests on multi-line/CR-heavy scrollback patterns not in the fixture set. | During implementation, have the subagent print/assert `bestCount` alongside `bestStatus`/`bestDesc` in *every* existing table-driven case in `detector_test.go`, not just the two new ones — turning the existing regression suite itself into count coverage rather than relying solely on two hand-picked new fixtures. | P3 |
