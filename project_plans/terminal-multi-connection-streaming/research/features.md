# Research: Feature Landscape — Multi-Connection Terminal Streaming

Phase 2 research for `project_plans/terminal-multi-connection-streaming/requirements.md`. Covers industry prior art on shared-PTY resize negotiation, edge cases/failure modes beyond what requirements.md already names, this repo's own directly-relevant prior work, and unstated user needs.

## 1. Industry prior art: resize negotiation for N viewers of one shared PTY

Research method: WebSearch/WebFetch across tmux, mosh, ttyd, GoTTY, Wetty, Zellij, upterm, tty-share, VS Code Live Share. Full per-tool citations preserved below; this directly answers requirements.md's open question ("What resize-negotiation model should the hub use?").

### Per-tool findings

- **tmux (native `tmux attach`, not this repo's control-mode usage)** — Supports N>1 viewers natively, and resize-negotiation is a first-class *configurable policy*, not a fixed architecture: the `window-size` option offers `smallest` (default — shared window shrinks to the smallest attached client; larger clients get padded with `~`), `largest` (grows to fit the biggest client), `latest` (follows whichever client most recently resized — "most-recent-resize-wins"), or `manual` (fixed). A companion `aggressive-resize` option lets background windows resize independently of whether they're the client's active window. Sources: [tmuxai.dev/tmux-window-size](https://tmuxai.dev/tmux-window-size/), [iterm2-discuss thread](https://groups.google.com/g/iterm2-discuss/c/Etfozb_63Pg), [jamesoff.net tmux config](https://jamesoff.net/2017/08/26/tmux-configuration.html).
- **mosh** — No native multi-viewer story; strictly 1:1 UDP state sync. The universal workaround is running tmux underneath and having each mosh client attach to the same tmux session — mosh delegates the entire problem to tmux and contributes no model of its own. Sources: [mosh.org](https://mosh.org/), [hoop.dev](https://hoop.dev/blog/mosh-and-tmux-uninterrupted-remote-terminal-sessions).
- **ttyd** — Spawns an independent process per connection by default (no sharing). The documented pattern for real sharing is `ttyd tmux new -A -s ttyd <cmd>` — again punting resize-negotiation to tmux. ttyd's own contribution is a `-W/--writable` flag (read-only by default) for read-only viewers, but no independent resize logic. Source: [ttyd README](https://github.com/tsl0922/ttyd).
- **GoTTY** — The concrete negative example. [Issue #243](https://github.com/yudai/gotty/issues/243) confirms a second browser client snaps the shared tmux session to a fixed 80×24, and resize from one client doesn't propagate correctly. No sharing by default; even wrapped in tmux, the resize interaction is documented-buggy, not designed. This is the industry cautionary tale for "bolt multi-viewer onto a single-owner design after the fact" — directly relevant since that's the failure mode requirements.md's Baseline section already reproduced live in this repo (2026-08-20).
- **Wetty** — Same class as ttyd/GoTTY (per-connection pty spawn); no independently documented multi-viewer resize model.
- **Zellij** — Same default as tmux (shrinks shared pane grid to smallest attached client), and it's a recurring *unresolved* pain point in Zellij's own issue tracker (a desktop session collapses to phone size when a mobile client attaches). Notably, Zellij's rendering layer already supports per-client customized render output based on that client's terminal size — but the underlying pane-grid *layout* dimensions remain one shared value pinned to the smallest client; true per-client independent viewport sizing is requested but not implemented. Sources: [discussion #5066](https://github.com/zellij-org/zellij/discussions/5066), [issue #1739](https://github.com/zellij-org/zellij/issues/1739), [discussion #3124](https://github.com/zellij-org/zellij/discussions/3124), [DeepWiki client-server model](https://deepwiki.com/zellij-org/zellij/2.1-client-server-model).
- **upterm** — Deliberately avoids resize negotiation of its own; just links stdin/stdout streams. Docs recommend the same tmux-attach escape hatch as mosh/ttyd. Source: [upterm.dev](https://upterm.dev/docs/upterm.html).
- **tty-share** — Same category as ttyd/GoTTY; no distinct model surfaced.
- **VS Code Live Share (shared terminal)** — A genuinely different model: **authoritative-host + permission axis**, not size-based negotiation. Only the host starts a shared terminal; it's shared per-guest as Read-only (default) or Read/write. Resize is host-authoritative, with documented bugs where the host's resize force-resizes the guest's view and guests can't always expand their own window's visible content. Sources: [Microsoft Learn](https://learn.microsoft.com/en-us/visualstudio/liveshare/use/share-server-visual-studio-code), [issue #83161](https://github.com/microsoft/vscode/issues/83161), [live-share issue #3376](https://github.com/microsoft/live-share/issues/3376).

### Synthesis → answer to the open question

Industry practice clusters into two camps:

1. **Shared-logical-size tools** (tmux, Zellij, and everything built atop them — mosh, ttyd, upterm): default to **smallest-common-size**; tmux alone also offers `largest`/`latest`/`manual` as explicit configurable alternatives. Even in modern tools this remains a live UX complaint (Zellij's phone-shrinks-desktop issue is open, not solved).
2. **Permission-first tools** (VS Code Live Share): sidestep symmetric negotiation via one authoritative host + N read-only-by-default guests.

**Recommendation for this repo's design**: stapler-squad's actual topology is one operator with multiple browser tabs/devices plus ssq-mux — not multi-party pair programming with untrusted guests — so the closest fit is **tmux's own default, smallest-common-size**, since every subscriber is the same trust principal and nobody should have their content silently clipped by a larger peer's session. But Zellij's decoupling of "per-client render output" from "one shared logical pane size" is directly reusable: this repo's hub already frames output per-subscriber (via the transport abstraction), so it can send each subscriber output shaped for *their own* viewport while still driving the underlying tmux pane at one negotiated (smallest-common) size — closer to what Zellij's renderer does than to naive tmux. This also cleanly folds in VS Code's read-only-guest idea: a subscriber's capability flags (can-resize / can-write) should gate whether it gets a vote in the size negotiation at all — an audit/recording sink or a future SSE read-only viewer should never be able to shrink the pane for everyone else.

## 2. Edge cases and failure modes beyond what requirements.md already names

- **Stale-size / never-resizing subscriber.** GoTTY's bug is the canonical negative case: a client that never sends a follow-up resize can pin the shared PTY at a stale/default size indefinitely, clipping every other viewer, because there's no distinction between "no size ever reported" and "explicitly reported and unchanged." The hub should default a never-resized subscriber to the *current* negotiated size at attach time (a real vote from that point on), not to some hardcoded 80×24 that then wins a `min()` forever.
- **Disconnect mid-batch-flush.** Not documented by any surveyed terminal-sharing tool (they're all synchronous/immediate-forward, not batched) — this is a risk specific to this design's batching layer. Standard Go mitigation: non-blocking per-subscriber sends (`select { case ch <- msg: default: drop-or-unregister }`), and treating a write error encountered mid-flush as a normal unregister rather than a hub-fatal error.
- **Clock skew / drift between per-connection batching windows.** Not surfaced by any surveyed tool (none of them batch). If each subscriber ran its own independent flush ticker, batches would drift out of phase over a long session, making per-subscriber latency inconsistent and complicating reasoning about ordering. Safer pattern, consistent with this repo's own `terminal-resize-fit-loop` precedent (a single decoupled fixed-cadence sampler owned by one place, not N independent timers — see `project_plans/terminal-resize-fit-loop/decisions/ADR-002-decoupled-sampler-tick-semantics.md`): one shared tick owned by the hub; subscribers read from it, they don't run their own.
- **Backpressure / slow consumer.** Well-documented Go pattern: buffered channel per subscriber + non-blocking `select` with a `default: drop` branch, so one slow reader can't stall broadcast to fast readers. Two refinements worth adopting: (a) emit an observable counter for dropped-due-to-backpressure events (this repo's Observability Requirements section already calls for structured logging at comparable points, so this fits the existing bar); (b) for terminal-output frames specifically, prefer dropping/coalescing *old* frames in favor of the newest over simple queue-full-drop — a viewer cares about "what does the screen look like now," which is exactly the framing this repo's own `terminal-jank` snapshot-cache/quiescence work already established. (c) A *sustained* backpressure condition should escalate to actually disconnecting that subscriber (forcing a clean resync) rather than silently dropping forever — silent partial delivery looks like the exact corruption class `terminal-redraw-corruption` and `terminal-resync-reliability` already fought hard to eliminate.
- **Read-only vs. read-write asymmetry as a first-class subscriber capability**, not just a resize vote: VS Code Live Share's host-authoritative + read-only-guest model suggests the transport interface should carry a per-subscriber capability flag (can-resize / can-write) independent of size. This matters for the two Out-of-Scope-but-named future sinks (audit/recording, SSE read-only viewer) so that adding them later can't accidentally give them a vote in the pane's shared size.
- **A subscriber attaching mid-batching-window during a burst.** Not covered by requirements.md: if a new subscriber attaches while a flush window is mid-accumulation, it needs either (a) to be excluded from the in-flight batch and start clean at the next tick, or (b) to get a synthesized catch-up frame first (mirroring `ExternalStreamer.AddConsumer`'s existing `catchUp` parameter in `session/external_streamer.go:165` — see §3) so it doesn't render a partial mid-batch state as though it were complete.

## 3. This repo's own directly-relevant prior work

Per instructions, summarized in 3 bullets each so this project doesn't re-litigate settled ground.

### `project_plans/terminal-jank` (SHIPPED — commits `29ae24516`/`c66ac2f30`)
- Solved session-switch jank via a **terminal instance pool** (keep-alive across switches) + an **ED3 filter** for xterm.js 6.0.0 to stop Claude's TUI redraws from corrupting cursor/scroll position.
- Introduced **output quiescence detection** to replace a hard-coded 250ms sleep, and a **snapshot cache** so switching to a previously-viewed session doesn't force a full scrollback replay.
- Relevance here: the hub's resize+capture path must preserve this quiescence-detection contract (don't reintroduce a fixed-sleep race), and any new batching must not defeat the snapshot cache's assumption of one coherent capture per session.

### `project_plans/terminal-resize-fit-loop` (SHIPPED via `9651edd5e`)
- Fixed an unbounded `ResizeObserver`→`fit()` feedback loop by **dead-banding** on integer `cols`/`rows` changes (not raw pixel deltas) confirmed across **two consecutive ticks** from a **decoupled fixed-cadence sampler**, not raw `ResizeObserver` firings.
- Added **value-dedup** in `useTerminalFlowControl.resize()` (skip the RPC when `(cols, rows)` is unchanged) layered on top of the existing 200ms time throttle, plus an explicit `force: true` bypass for the two call sites that must always resync (reconnect, manual Fit button).
- Added a one-directional WebGL→canvas renderer fallback when actual-vs-expected px/cell width diverges beyond tolerance. Relevance here: **the decoupled-sampler pattern (ADR-002) is the direct precedent for this project's batching-window design** — a single shared tick, not per-subscriber timers (see Edge Cases §2 above); any resize-negotiation the hub adds must not reintroduce a client-side feedback loop this work already closed.

### `project_plans/terminal-redraw-corruption` (PLANNED THROUGH PHASE 4, NEVER IMPLEMENTED — commits are planning-artifact-only: `36137de26`, `8e2c94259`)
- Diagnosed a **distinct bug class**: stray leading character fragments from a previous, longer status line surviving under a new, shorter redrawn line — an erase-in-line (`\x1b[K`) ANSI handling gap, not an escape-stripping bug.
- Confirmed via screenshot evidence this is *interpretation*, not transport corruption — content already reaching xterm.js correctly, but not being cleared correctly on redraw.
- **Still open** — worth flagging in this project's design so a reviewer doesn't assume it's fixed, but it is out of scope for multi-connection streaming (it's a client-side rendering bug, orthogonal to who owns the resize/capture authority).

### `project_plans/terminal-resync-reliability` (real implementation commits: `543cbf9e2`, `04ec32a92`, `38238c6a3`)
- Diagnosed a **resync storm**: every mounted `TerminalOutput` (kept alive per-session for keep-alive) independently listens to the same document-level `visibilitychange`/`focus` events, so one tab-focus fires a `requestFullResync` burst across *every* mounted terminal at once, not just the visible one.
- Found the resync completion signal had **no correlation ID** — `notifyResyncOutputReceived()` fired on *any* output message, so actively-focused terminals "got lucky" from ambient traffic while backgrounded ones queued past a 4s stall watchdog and got force-disconnected.
- All resyncs also contended for the same shared 8-slot tmux exec-gate (`session/tmux/exec_gate.go`) since virtually all sessions map to the `"default"` gate key. **Directly relevant**: this repo already has multiple keep-alive-mounted terminals per session generating concurrent resize/capture pressure today — the new hub's per-session single-owner model should structurally absorb this class of storm (one hub serializes/coalesces the underlying resize+capture regardless of how many mounted `TerminalOutput`s ask for one), and the correlation-ID gap is a concrete lesson to carry into batching-window flush acknowledgment design.

### `project_plans/terminal-visibility-resync` (feeds into the above — commits `96990ce12`, `9651edd5e`)
- Diagnosed: backgrounding a tab throttles the WebSocket, tmux control-mode deltas coalesce/drop while hidden, and on return xterm.js's buffer silently diverges from the real tmux pane — the underlying session is fine, only the client render desyncs.
- Found the fix primitive (`useTerminalFlowControl.requestFullResync`, sending `CurrentPaneRequest`) **already existed** in the server (`connectrpc_websocket.go`) but was **not wired to any visibility/focus event** — it shipped the wiring, not new server logic.
- This is the feature whose success directly caused `terminal-resync-reliability`'s storm (fixing one bug at single-terminal scale surfaced a new bug at multi-terminal scale) — a cautionary precedent for this project: a hub-level fix that works for one connection must be explicitly load-tested with several kept-alive connections on the same session before being called done.

### `project_plans/new-renderer` (bug fix, root-caused; commits reference upstream sync `85904cd63`/`33de43b09`, fix `dc71b828a`)
- Diagnosed a pipeline-stage escape-code corruption bug introduced when Claude Code's renderer changed, using a prior `terminal-analytics` escape-code analytics system to localize which pipeline stage (PTY reader → Go/ConnectRPC → xterm.js) was mangling bytes.
- Established the general debugging methodology (analytics-first localization across a byte-transport pipeline) rather than guessing — reusable if this project's transport abstraction introduces a new stage where escape sequences could be mishandled.
- Relevance here: any new transport implementation (ssq-mux Unix socket, in-memory test transport) that touches the raw byte stream must be checked against this same class of stage-introduced corruption, especially at batching-window frame boundaries (see requirements.md's own Rabbit Holes: "a batching boundary landing mid-escape-sequence").

### `project_plans/terminal-robustness` (real implementation commits: `fd42c92ea`, `57ae1c16f`, `fe191c283`)
- Fixed resize/reflow corruption from captures racing tmux's reflow-in-progress (adaptive debounce firing before quiescence), scrollback-buffer corruption (xterm.js `scrollback: 0` relying entirely on tmux, but the client never fetched server-side history on scroll-up), and mobile touch select/copy/tap-to-position gaps.
- Root-caused the "current content repeated" scrollback bug to a client-side guard (`handleScrollbackReceived()`) that rejected historical scrollback requests, combined with a too-shallow initial payload (50 lines) against a 10,000-line server-side `ScrollbackManager` buffer that was simply never queried deeper.
- Relevance here: the `ScrollbackManager`'s 10k-line circular buffer is itself a single-owner-per-session broadcast-adjacent component; the new hub design should confirm it composes cleanly with multiple simultaneous subscribers requesting scrollback at different depths, since today it was only exercised by one client's shallow-then-deeper request pattern.

### Prior-art broadcast infrastructure already in this codebase

Two existing multi-consumer broadcast patterns are worth designing *with*, not against:

- **`session/external_streamer.go`'s `ExternalStreamer`** (`AddConsumer`/`RemoveConsumer`/`ConsumerCount`, a `ringBuffer` for catch-up, `broadcast()` fan-out) is *already* a working multi-consumer hub for the ssq-mux side — `AddConsumer(consumer, catchUp bool)` optionally replays buffered recent output to a newly-attached consumer, directly matching Edge Case §2's "subscriber attaching mid-burst" concern above. Its `SendResize(cols, rows uint16)` (line 250), however, does **no negotiation at all** — it blindly forwards whatever the caller passes, i.e. today's ssq-mux path is already exposed to the exact "most-recent-resize-wins, no coordination" race this project is being built to eliminate on the browser side; it has just gone unnoticed because ssq-mux sessions are typically single-IDE-terminal. This is a concrete argument for folding ssq-mux into the same hub (per requirements.md's open question on ssq-mux unification) rather than leaving it as a second, still-unprotected path.
- **`session/mux/multiplexer.go`'s `Multiplexer`** (`broadcastToClients`, `acceptClients`/`handleClient`) is the server-side counterpart inside `ssq-mux` itself — another existing N-client broadcast implementation with its own `SetWindowSize` call, worth auditing during Phase 3 planning for the same blind-forward resize behavior before deciding how ssq-mux folds into the new transport interface.

## 4. Unstated user needs worth surfacing to planning

- **Viewer presence/notification.** Once N connections can genuinely coexist on one session (rather than accidentally racing), the natural next question is whether other viewers should be told someone else is watching — no such presence mechanism exists in this codebase today (confirmed: no "presence"/"who's viewing"/`activeViewers` concept found in `server/`, `session/`, or `web-app/src` beyond unrelated backlog "activity" tracking). Given this repo's single-operator, personal-instance context (not a multi-party pairing tool), this is very likely *not* wanted now — but it's worth naming explicitly as a design non-goal rather than silently absent, since the transport/subscriber-registry work this project is building (a per-session connection registry, per Scope) is the exact plumbing a future presence indicator would need. Recommend: note in the plan as an easy, structurally-free follow-on once the registry exists, not a requirement now.
- **Recording/audit retention & privacy policy.** requirements.md already names a recording/audit sink as an explicit future consumer (Users/Consumers, Scope: Out of Scope) but the requirements doc doesn't address retention or privacy for such a sink once built. Nothing about this needs solving *now* since the sink itself is out of scope — but the transport interface design should not foreclose the option of a sink declining to receive certain subscriber capability classes (e.g. an audit sink is inherently read-only, per the capability-flag idea in §1/§2), and Phase 3 planning should flag "retention policy is undefined" as a known gap for whoever builds that sink later, rather than let it surface as a surprise.
- **Cross-device continuity expectations.** The requester named "additional browser tabs/devices on the same session" as a consumer. An unstated expectation likely to surface once multi-device viewing actually works reliably: does resizing on a phone (tiny viewport) while a desktop tab is also open silently shrink the desktop tab's rendered content (tmux's smallest-common-size default), or does the desktop tab expect to keep its own size? Given the §1 recommendation (shared logical pane at smallest-common-size, but per-subscriber wire framing), this is naturally resolved if the hub frames each subscriber's *display* independently even while the underlying tmux pane is sized conservatively — but it should be called out explicitly as an acceptance-criterion-worthy behavior in Phase 3 planning, since "my phone connecting shouldn't shrink my desktop terminal" is the kind of expectation a user won't articulate until it's violated.
