# Pre-mortem: terminal-multi-connection-streaming
**Date**: 2026-08-20

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The only failure scenario that motivated this project — the mass reconnect after a process restart (`make install-service`/crash) — is never exercised end-to-end against real `*session.Instance`/tmux control-mode; every ownership/race test in the plan (Story 1.4.2's 1000-iteration test, Story 3.1.2's 100-goroutine test) uses a single tmux session and `MemoryTransport`/fake `SessionController`, not N real sessions reconnecting simultaneously against real tmux plumbing. | Right after a routine service restart, a burst of `hub_created`/`StartControlMode` log lines across many sessions in the same second, and — in the worst case — an `OverlapInvariant` panic or a `streamhub_overlap_invariant_violations_total` increment that no unit test ever caught, i.e. the exact corruption symptom the project was built to eliminate, now recurring in a form the test suite never modeled. | Add a Phase 3 test/rehearsal story that boots several real tmux sessions and simulates a restart-then-simultaneous-reconnect storm against real `*session.Instance` control-mode plumbing, not fakes; fold a multi-session (not single disposable session) restart drill into Story 3.3.2 before the global default is ever flipped. | P1 |
| 2 | Smallest-common-size resize negotiation, combined with a reconnect storm leaving stale (not-yet-errored) and freshly-reconnected subscribers for the *same* logical browser tab both voting, causes visible resize thrashing (pane repeatedly shrinking/reflowing) during exactly the restart-reconnect scenario the project targets — trading corruption for a new, more visible flicker bug. | Terminal pane visibly resizes/reflows multiple times in quick succession after a reconnect or when a second tab opens; `resize_negotiated` log lines show `NegotiatedSize` oscillating with `changed=true` several times in a short window. | Require dead/stale-subscriber detection to run fast enough that a reconnecting client's old subscriber is detached before (or atomically with) the new one attaching, or have negotiation ignore votes from subscribers with no recent activity; add a test simulating "same logical tab reconnects while old socket hasn't yet errored" and assert `NegotiatedSize` converges in one settle cycle. | P2 |
| 3 | `BatchWindow`'s single hub-owned accumulation buffer has no documented size bound or backpressure story for sustained high-volume output (e.g. a build log or large scrollback dump) — the 5x-reduction success metric is validated only against a synthetic 50-event/20ms burst, not sustained real throughput, so real load could produce unbounded buffer growth or multi-second flush lag instead of the intended near-instant coalescing. | Terminal output visibly lags several seconds behind the actual process during a large output burst (build, big `cat`, agent dumping scrollback), or memory usage climbs noticeably during that burst — none of which the passing 50-event benchmark would ever surface. | Add a sustained-throughput test (continuous high-rate output for several seconds, not one 50-event burst) and define an explicit max-accumulated-bytes cutoff that forces an early flush regardless of the 20ms ceiling, as a Phase 2 acceptance criterion. | P2 |
| 4 | The rollback rehearsal (Story 3.3.2) and the 14-day trial period are pure process/checklist gates with no code-level enforcement, on a single-operator instance with — per the project's own context — little discipline pressure to run optional steps; combined with the trial's already-flagged "vacuous" exit bar (zero legacy-path WARNs on a path receiving no traffic), the global default is likely to get flipped without the rollback path ever having been proven, leaving the operator's own daily-driver sessions exposed the first time they actually need to roll back. | No visible symptom until an actual incident occurs with the hub path already defaulted on — at which point "flip the flag back" doesn't behave as expected (e.g. an existing hub doesn't tear down cleanly, a live browser tab is left broken), and `validation.md`'s Story 3.3.2 entry is either missing or dated after the default was already flipped. | Turn the rehearsal into a mechanical gate instead of a checklist line — e.g. require a recorded `rollback_rehearsal_completed_at` before the flag's default can be set to `true` in config, and replace the trial's exit criterion with one tied to actual dark-launch traffic volume (hub-path session-hours logged), not just "zero WARNs on an untouched legacy path." | P1 |
| 5 | `StreamOwnershipLock`/`StreamPath` resolution lives only in an in-process `xsync.Map` with no persistence, so every process restart — the same routine event that is this project's own root-cause trigger — silently forgets which sessions were canaried (per-session override) or already resolved, and re-resolves everything fresh from whatever the global flag happens to be at that moment, with no log line distinguishing "fresh resolution" from "lost prior state." | A session the operator had deliberately included in (or excluded from) the canary suddenly behaves under the opposite path immediately after a restart, with no corresponding operator action and no log signal explaining why. | Persist per-session `StreamPath`/override resolution to the existing session state store (or at minimum emit an explicit WARN on every post-restart first-resolution noting "no prior sticky resolution found, resolving fresh"), as an explicit Phase 3 acceptance criterion. | P2 |

## P1 Items (address before implementation)

- [x] Failure #1 — Resolved: added Story 3.3.3 (`plan.md`, Epic 3.3) — a real multi-session restart-then-simultaneous-reconnect storm test against actual `tmux.NewTmuxSessionWithPrefixAndCleanup`-backed sessions (5 real tmux sessions, concurrent mass-detach/reattach under `-race`, asserting `streamhub_overlap_invariant_violations_total == 0`), wired as an explicit prerequisite gate (alongside Story 3.3.2's rollback rehearsal) before the global default flag can ever be flipped to `true`.
- [x] Failure #4 — Resolved: `plan.md`'s Risk Control section now requires a persisted `config.RollbackRehearsalCompletedAt` timestamp (written by Story 3.3.2's Task 3.3.2c) before the global-default resolution code (Story 3.3.1's Task 3.3.1d) will permit `STAPLER_SQUAD_USE_STREAM_HUB`'s default to become `true` — a mechanical gate, not a checklist line; and the 14-day trial's exit criterion now additionally requires at least 20 distinct sessions (or 50 cumulative session-hours) actually served via `PathHubOwned` during that window, not just "zero WARNs on a path that may have received no traffic."
