# Adversarial Review: terminal-multi-connection-streaming

**Date**: 2026-08-20
**Verdict**: CONCERNS

## Blocker Re-Verification (repair pass)

1. **`Transport.Send` error contract undefined — RESOLVED.** The Domain Glossary's `Transport` entry (plan.md:31) now states the contract explicitly: "a non-nil error from `Send` is treated identically to the slow-subscriber-eviction path (Story 1.2.1) — log, evict, close, remove from registry." Story 1.2.1 has a concrete, testable GWT (plan.md:232-233: `MemoryTransport` with `WithErrorSend()`, asserts single detach + logged once + other subscribers unaffected), backed by Task 1.2.1g (plan.md:256). Story 1.4.2 got the matching failure-mode test: AC at plan.md:396-397 plus Task 1.4.2g (plan.md:417), which explicitly consumes Task 1.4.1b's `WithErrorSend` mode. Confirmed against `session/external_streamer.go:20`'s `OutputConsumer func(data []byte)` — no error return exists there, so the plan is right that this is a new contract being defined, and it is now defined concretely rather than left implicit.

2. **No failure mode for the hub's own resize/capture calls erroring — RESOLVED.** Story 1.3.2 gained a sixth AC (plan.md:332-333) with a concrete GWT: a fake `SessionController` whose `SetWindowSize` errors mid-resize causes a stream-ended sentinel broadcast to both subscribers, an error log with `tmux_session`, and "attempts a restart (or clean teardown if restart is not possible) via the same code path Story 1.4.2's hub-crash test exercises," plus explicit handling of stale `ResizeVote`/`NegotiatedSize` state. Task 1.3.2g (plan.md:356) implements it. Story 1.4.2 has the matching test: AC at plan.md:390-391 (`CapturePaneContent` error variant) and Task 1.4.2f (plan.md:414). The restart-or-teardown behavior is pinned to the same code path as the existing `HubCrashed`/`TmuxProcessDied` handling (Task 1.4.2a) rather than left newly vague — that precedent itself only says "attempts a restart... mirrors `controlModeExited`," so the exact mechanics of "restart" inherit whatever `controlModeExited` already does; this is consistent scoping, not a new gap introduced by the fix.

3. **`StreamOwnershipLock` sharing mechanism ambiguous — RESOLVED.** Domain Glossary (plan.md:39) and the Pattern Decisions row (plan.md:56) both now specify one mechanism: a package-level `xsync.Map[string, *StreamOwnershipLock]` in `session/streamhub`, exposed via `streamhub.AcquireOwnershipLock(sessionName string) *StreamOwnershipLock`, with package `session`'s `StartControlMode` importing `session/streamhub` (one-way, non-cyclic). Story 3.1.2 makes this explicit under a header literally reading "**Package boundary (concrete, not "either/or")**" (plan.md:545) and Task 3.1.2a implements exactly this. Grepped the surrounding sections (Epic 3.1, Domain Glossary, Pattern Decisions) for residual "either (a)...or (b)" framing describing this mechanism — none found. (The unrelated "opportunistic-or-ceiling" flush-trigger phrase at plan.md:449 is a different concept — batch flush timing, not lock sharing — and isn't the ambiguity this blocker was about.)

4. **Frame-volume-reduction target never set — RESOLVED.** Story 2.1.1 gained a fourth AC (plan.md:439-440) with a concrete number and a concrete GWT: "≥5x fewer total wire messages than the unbatched baseline" for N≥3 subscribers/50-event burst within one 20ms window, with the GWT computing the exact threshold (`3 × 50 / 5 = 30` vs. baseline `150`). Task 2.1.1e (plan.md:455) is the benchmark/test that asserts it. The Observability Plan's `streamhub_batch_flush_frames_coalesced` entry (plan.md:90) now cross-references this exact target instead of a vague "validates the success metric" statement. Testable as written — the GWT names the transport count, event count, window, and pass/fail threshold.

**All 4 original blockers are resolved with concrete, testable Given-When-Thens**, not prose assertions.

## Concerns (carried forward from original review — none addressed by this repair pass)

- [ ] **The "No regression" success metric is never end-to-end verified for the new path.** requirements.md calls for verification "via the existing Playwright terminal e2e coverage plus `terminal-jank`/`terminal-resize-fit-loop`'s prior test suites." Story 2.2.2 only verifies the *legacy* branch is byte-identical (diff-based). No task runs the existing e2e suite against a `PathHubOwned` single-connection session to confirm latency/redraw parity for the new path itself.

- [ ] **Attach-during-pending-batch ordering is unaddressed.** Story 1.2.1 sends a subscriber's `CatchUpSnapshot` "within the same call" as `AttachSubscriber`. Story 2.1.1 introduces one hub-wide `BatchWindow` buffer that may already hold unflushed output bytes accumulated *before* that subscriber attached. No AC/test covers what a newly-attached subscriber sees when it receives its `CatchUpSnapshot` and then the pending batch flushes moments later — risk of duplicated or stale content immediately after attach. (Story 2.1.2's bypass path covers quiescence/catch-up-snapshot messages skipping the batch buffer, but not this specific new-subscriber-during-accumulation interleaving.)

- [ ] **The 14-day trial-period exit criterion is close to vacuous.** Risk Control requires "zero `420584566` WARNs" during the trial, but the trial condition is "hub path as the effective path for all new sessions" — meaning the legacy path receives no new traffic to ever trigger that WARN, regardless of whether the new design is actually correct. This bar adds no signal beyond `streamhub_overlap_invariant_violations_total == 0`, which is already tracked separately.

- [ ] **`OverlapInvariant`'s "panic in dev builds, slog.Error in prod" has no implementing task, and no dev/prod build-mode distinction exists in this codebase today** (grepped `session/` and `server/` for `DevMode`/`IsDevBuild`-style conventions — none found). As specified in the Domain Glossary, this requires inventing new build-mode infrastructure that no Phase 3 story accounts for.

- [ ] **Story 3.3.2's rollback-rehearsal outcome is recorded in `implementation/validation.md`, described as "created in the SDD validate phase."** SDD's validate phase (Phase 4 of 7) runs *before* implementation (Phase 5) starts, but the rehearsal itself requires the Phase 1-3 code to already exist and be running against a real session. The plan doesn't clarify that this file gets amended post-implementation rather than authored once up front — as written it reads like a phase-ordering conflict.

- [ ] **Scope drift: Phase 4's UI connection-count indicator (Epic 4.2) is not named in requirements.md's In Scope list or Success Metrics.** requirements.md's Appetite explicitly scopes this pass to "the foundational layer" (hub, transport interface, 3 transports, batching); its In Scope bullets list a connection *registry* ("this is also what the requester meant by 'understand multiple connections'") but no UI surface. Shipping a new React component, a proto field change, and feature-registry updates is a larger, separately-reviewable feature than "foundational" — it should be confirmed as in-appetite or split into its own follow-on pass rather than riding along in Phase 4.

## Minors (carried forward — none addressed by this repair pass)

- Story 1.2.1's AC ("evicted once it exceeds the bounded-queue-full threshold") and Task 1.2.1e's "grace period then close+remove" still describe the eviction trigger in two slightly different terms (queue-full-based vs. timer-based); worth reconciling into one precise trigger definition before implementation.
- Task 1.1.2c still hedges with "if not already repo-wide" — `.golangci.yml`'s `exhaustive` linter is confirmed scoped to a specific package allowlist (lines 127-158), not repo-wide, so this task will in fact require adding `session/streamhub` to that list; the "if" undersells that this is very likely required, not optional.
- `MaxBatchWindow = 20ms` is honestly flagged in Unresolved Questions as an unvalidated guess, but is then treated as an authoritative constant throughout Epic 2.1's ACs (including the new §2.1.1 wire-message-reduction target, which is now numerically pinned to this same unvalidated 20ms window) — fine as written, just worth remembering it's a placeholder when reviewing those tests later.
- No story states whether a `Subscriber`'s `SubscriberCapability` is immutable for the subscriber's lifetime; the design implicitly assumes it (capability is set at `AttachSubscriber` time and never revisited), but this invariant is never written down explicitly.
