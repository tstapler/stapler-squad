# Core Domain Decomposition — Requirements

## Project Overview

Decompose the coupling/cohesion problems in this repo's dominant architectural hotspots — `server/services/session_service.go` (4,542 lines, ~140 methods, 19+ distinct responsibility clusters) and the `session.Instance` God Object — applying Go-idiomatic SOLID/Clean-Architecture/DDD/Hexagonal principles (`code-architecture-best-practices` skill), without colliding with the concurrent `instance-actor-concurrency` project's `Registry`/`LiveInstance`/`InstanceSnapshot` redesign.

This is explicitly a **structural decomposition** project — splitting responsibilities into cohesive, independently-testable units — not a concurrency-safety project. Where the two projects touch the same files, this document defers to `instance-actor-concurrency`'s design (see Sequencing below) rather than re-litigating it.

---

## Background

Two audits this session quantified what was previously only suspected:

- **`docs/architecture-audit-temporal-coupling-2026-07-01.md`**: `session_service.go` is the dominant hotspot in the repo by every measure used — highest revision count (70 in ~2 months), highest hotspot score (revisions × lines = 317,940, more than 3x the runner-up), highest project-plan mention count (49 distinct `project_plans/*` directories reference it), and center of nearly every top co-change pair. `session.Instance`'s file-splitting (26 `instance_*.go` files) has spread its coupling across more files without reducing it — 36/1000 commits touch 2+ files in that family together, 42/1000 touch the family AND `session_service.go` together.
- A direct read of `session_service.go`'s method list this session found **~140 methods** clustering into at least 19 distinct responsibility groups: session lifecycle (create/list/get/update/delete/hibernate/rename/restart/archive/fork/batch-create/one-shot), workspace/VCS operations, PR/GitHub integration, approval rules & analytics, autonomous-driver orchestration, terminal streaming, Claude config/history, checkpoints, notifications, projects, workflows, error registry, feature flags, session defaults/directory-rules/aliases, database switching, file browsing, detection events, provider limits, and ~30 dependency-injection-style `Set*`/`Get*` wiring methods. This is a textbook Single Responsibility Principle violation at the file/type level — one struct receiving nearly every RPC handler in the application.
- **A confirmed, previously-undocumented missing abstraction boundary**: `server/services/approval_handler.go` calls `session.Instance.Preview()` (`session/instance_terminal.go:105`), which falls back to `i.pm().CapturePaneContent()` — i.e. raw tmux pane-capture bytes, escape sequences included. This is the actual mechanism behind the audit's finding that `approval_handler.go` co-changes with `session/tmux/tmux.go` (5 shared commits, no static import) despite no direct dependency: when tmux's capture format changes, `Preview()`'s output changes, and `approval_handler.go`'s own classification logic — which does its own parsing of that raw content — has to adapt. `pkg/classifier/classifier.go`'s weaker co-change signal with `tmux.go` (3 shared commits, no direct call site found in this session's read) is noted as a secondary, less certain instance of the same class of issue, not independently confirmed to the same degree.
- Neither `session_service.go` nor `session/instance.go` has a dedicated ADR despite being the two most-referenced files across all of `project_plans/` — a governance gap that has let both files absorb new responsibilities indefinitely with no documented boundary to push back against.

## Sequencing Relationship to `instance-actor-concurrency`

**This project's `Instance` field-decomposition work should NOT happen independently — it should reuse `instance-actor-concurrency`'s `InstanceSnapshot` design as the decomposition boundary, and should land AFTER that project's Epic 1 (additive `InstanceSnapshot` infrastructure) but does not need to wait for that project's full completion.**

Rationale: `instance-actor-concurrency/research/architecture.md` §1.2 already enumerates the full field set that needs a home in `InstanceSnapshot` and explicitly groups fields by sub-concern in its own struct definition (GitHub PR/URL integration block, autonomous-mode block, `ReviewState` embedded value type, etc.) — this is *already* the natural decomposition seam this project would otherwise have to rediscover from scratch. Inventing a second, independent decomposition of `Instance`'s fields while that migration is also touching the same struct would create two competing refactors of the same type, guaranteeing merge conflicts and duplicated design work. Instead:

- This project's `Instance`-decomposition scope is limited to: once `InstanceSnapshot` exists (a struct literal, not yet a set of composed sub-types per its own research), extract its logical field groups (already identified: GitHub/PR block, autonomous-mode block, `ReviewState`) into named, embedded sub-structs (`GitHubIntegration`, `AutonomousModeState`) with their own methods, rather than one flat struct — this is additive polish on top of `InstanceSnapshot`, not a competing design.
- `session_service.go`'s decomposition (the higher-value, lower-conflict-risk half of this project) has **no dependency** on `instance-actor-concurrency` landing first — splitting RPC handlers into focused services is orthogonal to how `Instance`'s internals are synchronized. **This work can start immediately, in parallel.**
- Do not touch `session/instance_workspace.go`'s `SwitchWorkspace` internals or `session/instance_controller.go`'s `StopController` — both are mid-migration in the other project (Item 1 already shipped there; Epic 4 will convert these to actor commands). Any decomposition here should treat those as stable call boundaries, not refactor targets.

## Item 1 — Decompose `session_service.go` by Responsibility Cluster

### Problem — CORRECTED after direct verification against the current code

Initial framing (before verification) assumed `session_service.go` was an undecomposed monolith. **Direct inspection during planning found this is false**: `server/services/` already contains **26 separate, focused service files** (`project_service.go`, `workflow_service.go`, `workspace_service.go`, `approval_service.go`, `github_service.go`, `notification_service.go`, `database_service.go`, `file_service.go`, `defaults_service.go`, `rules_service.go`, `search_service.go`, `path_completion_service.go`, `slash_command_service.go`, `unfinished_work_service.go`, `backlog_service.go`, `review_queue_service.go`, `config_service.go`, `headless_service.go`, `github_user_service.go`, `hook_status_service.go`, `insights_service.go`, `local_file_service.go`, `push_service.go`, `utility_service.go`, `analytics_escape_service.go`), and spot-checking method bodies confirms most `SessionService` RPC methods are already thin (~6-line) delegates to these — e.g. `CreateProject`, `ListProjects` → `s.projectSvc`; `GetPRInfo`, `GetPRComments` → `s.githubSvc`; `SendNotification`, `GetNotificationHistory` → notification service; `ListDatabases`, `SwitchDatabase` → database service. This decomposition has already happened for most clusters.

**What remains genuinely undecomposed** (verified by body-line-count against the actual file): session lifecycle itself (Create/Update/Delete/Hibernate/Resume/Rename/Restart/Archive/Fork/BatchCreate/OneShot/Watch/List/Get — legitimately `SessionService`'s own aggregate-root cluster, not a candidate for further extraction), **checkpoints** (`CreateCheckpoint` 34 lines, `ListCheckpoints` 23 lines, `ClearConversationState`), **autonomous-driver orchestration** (`wireRateLimitCallbacks` 48 lines, `wireAutoArchiveCallback`, `wireSessionExitedPublisher`, `wireStatusChangeCallback`, `wireClaudeSessionIDCallback`, `StartAutonomousDriverForInstance`, `StartAutonomousDriverWithTimeout`, `onAutonomousDriverComplete`, `registerDriver`/`stopAndDeregisterDriver`/`StopDriverForSession` — real logic, not delegates), **`GetProviderLimits`** (76 lines, standalone), **`GetDetectionEvents`** (36 lines), and the ~30 `Set*`/`Get*` dependency-wiring methods (many of these exist because `SessionService`'s own constructor is also the composition root that builds `projectSvc`, `githubSvc`, etc. via `NewProjectService(...)` etc. at construction — late-bound setters exist for dependencies not available at that point).

**Correction (post-adversarial-review)**: an independent first-pass review found this inventory was not exhaustive — it stopped after the two largest clusters instead of sweeping the whole file by line-count. Six additional methods with substantial inline business logic exist that are neither part of the session-lifecycle cluster, the two named extraction targets, nor `GetProviderLimits`/`GetDetectionEvents`/the setter audit: **`ListBranches`** (99 lines — `$HOME` path validation, an in-process TTL branch cache, a `safeexec`-wrapped `git for-each-ref` subprocess call, filtering; sits beside `GetVCSStatus`/`GetWorkspaceInfo`/`ListWorkspaceTargets`/`SwitchWorkspace`, all four of which already delegate to `workspaceSvc` — `ListBranches` is the one exception), **`ArchiveWorkflowSessions`/`DeleteWorkflowFailedSessions`** (55/46 lines — direct `ent` bulk-update queries plus in-memory poller-instance mutation, workflow-scoped but not delegated to `workflowSvc` like their five siblings), **`GetTerminalSnapshot`/`WriteToSession`** (47/48 lines — a shared instance-lookup fallback chain (poller → external discovery), `Preview()`-based read with line-trimming, and a goroutine+`select`/timeout `SendKeys` write, with no existing sibling service to fold into), and **`GetFeatureFlags`/`UpdateFeatureFlag`** (28/62 lines — known-flag validation, `config.LoadConfig()`/`SetFeatureFlag()` persistence, in-process `FeatureController` toggling; `UpdateFeatureFlag` alone already exceeds ADR-001's own 30-line threshold). Requirements R1.9-R1.12 below cover these; see `implementation/plan.md` Epic 1 Stories 1.4-1.6 for the task breakdown.

The file's 4,542-line size is therefore a mix of: (a) irreducible ConnectRPC interface boilerplate (one Go type must implement every RPC method a proto service defines — even a 6-line delegate still needs a full method signature), (b) legitimately-owned session-lifecycle logic, and (c) a genuinely smaller set of not-yet-extracted clusters (now including the four additional clusters found above). This project's real, evidence-backed scope is (c), not a full rewrite of (a)/(b).

### Requirements

- R1.1: Extract **`CheckpointService`** for `CreateCheckpoint`/`ListCheckpoints`/`ClearConversationState` (and `ForkSession` if it shares logic with checkpoint creation — verify during implementation), following the exact pattern already established by `project_service.go`/`github_service.go` (a `NewXService(deps...)` constructor called from `SessionService`'s own constructor, a `xSvc` field, RPC methods reduced to delegates).
- R1.2: Extract **`AutonomousOrchestrationService`** for the driver-lifecycle cluster (`registerDriver`, `stopAndDeregisterDriver`, `StopDriverForSession`, `buildTurnCallback`, `StartAutonomousDriverForInstance`, `StartAutonomousDriverWithTimeout`, `onAutonomousDriverComplete`, and the 5 `wireXCallback` methods) — this cluster has the most inline logic of anything remaining in `session_service.go` and the clearest single responsibility (owning the `AutonomousDriver` lifecycle and its callback wiring into events/notifications/archival). Since `instance-actor-concurrency`'s Epic 5 targets the identical `onAutonomousDriverComplete`/`buildTurnCallback` methods, this extraction carries an explicit phase-check coordination gate — confirm that project's current phase before starting (see `implementation/plan.md` Story 1.2's Coordination gate).
- R1.3: Evaluate `GetProviderLimits` (76 lines) and `GetDetectionEvents` (36 lines) individually during implementation — each may be a one-off that's fine to leave inline (not every long method is a SRP violation; verify against what the method actually does and whether it has a natural service home before extracting for extraction's sake).
- R1.4: Audit the ~30 `Set*`/`Get*` methods: for each, determine whether it exists because (a) the dependency isn't available at `SessionService` construction time (legitimate late-binding — consider whether this repo's existing staged `server/dependencies.go` builder convention, `BuildCoreDeps`→`BuildServiceDeps`→`BuildRuntimeDeps`, could instead supply it at the correct stage, eliminating the setter), or (b) it's a getter exposing an internal dependency to another part of the codebase that could instead depend on that service directly (verify actual callers before assuming either).
- R1.5: No behavior change visible to any RPC client — every extracted method's external contract (request/response shape, error codes) is preserved exactly. This is a structural refactor, not a feature or API change.
- R1.6: New services follow the exact constructor/field/delegate shape already established by `project_service.go`/`github_service.go` — do not invent a new pattern for this codebase; consistency with 24 existing examples matters more than any single "more correct" alternative pattern.
- R1.7: Each extracted service gets its own test file colocated with it, matching the existing `project_service_test.go`/`workflow_service_test.go` convention. This applies to `CheckpointService` **and** `AutonomousOrchestrationService` equally — the existing `autonomous_integration_test.go` must be relocated/renamed or extended to actually cover the new `AutonomousOrchestrationService` type, not left as-is with only an implicit assumption that it already satisfies this requirement.
- R1.8: Governance: this decomposition needs an ADR (see Item 3) recording the established `server/services/`-one-file-per-cluster convention as a standing rule (it already exists as a de facto pattern across 26 files — this ADR makes it explicit so it isn't rediscovered informally again), plus the new services this project adds.
- R1.9: Delegate **`ListBranches`** to `workspaceSvc`, matching the pattern already used by its four sibling VCS/workspace RPC methods — no new service file needed.
- R1.10: Delegate **`ArchiveWorkflowSessions`/`DeleteWorkflowFailedSessions`** to `workflowSvc`, matching the pattern already used by their five sibling workflow RPC methods — no new service file needed.
- R1.11: Extract a new **`TerminalService`** for **`GetTerminalSnapshot`/`WriteToSession`** — unlike R1.9/R1.10, these two have no existing sibling service to fold into; they are cohesive with each other (shared instance-lookup fallback chain) and each individually exceeds ADR-001's 30-line threshold, warranting a new file per that ADR's own rule rather than a fold-in. Evaluate during implementation whether the already-inline `StreamTerminal` RPC shares enough of the same lookup logic to belong in this service too (not committed scope unless verification finds a clean fit).
- R1.12: Extract a new **`FeatureFlagService`** for **`GetFeatureFlags`/`UpdateFeatureFlag`** — no existing service owns feature-flag persistence/toggling, and `UpdateFeatureFlag` alone (62 lines) already exceeds ADR-001's 30-line threshold on its own.

### Out of Scope
- Any change to `session.Instance`'s concurrency model (that is `instance-actor-concurrency`'s scope).
- Any change to RPC/proto contracts.
- Splitting `SessionService` by technical layer (controller/service/repository folders) rather than by business capability — this repo's existing convention (feature-oriented files, not layer-oriented directories) should be preserved; see `code-architecture-best-practices`' Go-native guidance (small consumer-defined interfaces, not a forced `domain/`/`application/`/`infrastructure/` folder structure).

## Item 2 — Explicit Port for Tmux-Derived Terminal Content

### Problem
`server/services/approval_handler.go` (and, more weakly, `pkg/classifier/classifier.go`) consume raw tmux/PTY output (via `Instance.Preview()`) and independently parse/classify it, creating an implicit, unenforced dependency on tmux's output format — confirmed by git co-change history and by tracing both of `Preview()`'s branches: the `CapturePaneContent()` fallback, and the in-memory PTY buffer branch (`ctrl.GetRecentOutput()`) that `approval_handler.go`'s autonomous-mode call path actually exercises. **Correction from initial framing**: the buffer branch is not "already normalized" — `session/response_stream.go` fills that buffer with raw, untransformed PTY bytes (see ADR-003's Amendment). Both branches need normalization, not just the fallback.

### Requirements

- R2.1: Do not introduce a new Go interface at the `Instance.Preview()` boundary — that boundary already exists and is already a reasonable abstraction (`Preview() (string, error)`); the actual missing abstraction is upstream of it: **no normalized/pre-processed representation of terminal content exists, so every consumer (including `session/detection`'s `StatusDetector`, which already does its own ANSI-stripping/CR-collapse per earlier session context) reimplements its own parsing of raw bytes.**
- R2.2: Verify whether `session/detection`'s existing ANSI-stripping/CR-collapse logic (referenced in this session's earlier detection-architecture-refactors context — confirm it still exists at that location) can be extracted into a shared, reusable normalization function that `approval_handler.go` calls before its own classification logic, rather than `approval_handler.go` maintaining independent parsing. This turns an implicit, duplicated normalization step into an explicit, shared one — the actual fix, not a new interface for its own sake. **Corrected scope (post-adversarial-review)**: `Instance.Preview()` has two branches — the in-memory PTY buffer (`ctrl.GetRecentOutput()`) and the `CapturePaneContent()` fallback — and independent verification found **neither** branch normalizes today (the buffer is filled with raw, untransformed bytes by `session/response_stream.go`; see ADR-003's Amendment). `approval_handler.go`'s autonomous-mode approval path exercises the *primary* (buffer) branch, not the fallback, since it only runs for live controller-managed sessions. The fix must normalize both branches at `Preview()`'s single return point, not just the fallback.
- R2.3: Confirm during planning whether `classifier.go`'s weaker co-change signal traces to the same root cause (verify by reading its actual content, not assumed) — if it doesn't, don't force a fix onto a file where the evidence doesn't support one; report it as a non-finding rather than inventing a fix.
- R2.4: No behavior change to approval-rule classification outcomes — this is a refactor of where normalization happens, not a change to what gets normalized or how rules match.

### Out of Scope
- Rewriting the approval-rule classification logic itself (`pkg/classifier`'s rule engine) — only the input-normalization boundary is in scope.
