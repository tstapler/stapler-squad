## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `stopByUserLocked` (Task 0.1.1a) kills the tmux session and removes the git worktree *before* the final `transitionToLocked(s, ctx, Stopped)` legality check — a rejected drag (e.g. a `Restoring` session dropped on "Complete") still destroys runtime/filesystem state even though the RPC returns an error and the UI shows a rejection toast. Architecture-review.md flagged this exact ordering as a "Concern," and the plan's own Task 0.1.1a code block still performs cleanup/removal ahead of the transition check — unchanged from the flagged version. | User sees a "can't move" rejection toast, but the session's tmux pane is gone and its worktree directory no longer exists — uncommitted or just-committed-then-orphaned work is unrecoverable. Surfaces as a backlog/support report: "the board said the move failed but my session disappeared." | Reorder `stopByUserLocked` to check `(i.Status, Stopped)` legality (or call `transitionToLocked` in dry-run/check-only mode) *before* `stopControllerLocked`/`KillSession()`/`gitManager.Remove()`; extend Task 0.1.1a's own "Restoring→Stopped" illegal-transition test to assert the worktree directory still exists and the tmux session is still alive after the rejected call, not just that an error is returned. | P1 |
| 2 | Task 3.2.2a (Story 3.2.2's bucketing-freeze logic) is still written against the singular `inFlightDragSessionId`, even though the Domain Glossary and Tasks 3.1.1b/3.1.1d pluralized this to `inFlightDragSessionIds: ReadonlySet<string>` specifically to close architecture-review.md blocker #2 (multi-select drag race). An implementer following Task 3.2.2a's literal text ("the session matching `inFlightDragSessionId`… a snapshot of *that* session's status") builds a single-value snapshot instead of a per-ID snapshot map, so only the primarily-dragged card is frozen against a racing `watchSessions` push during a multi-select drag — the other N-1 selected sessions have no protection, reintroducing the exact bug the pluralization was meant to fix. | During a multi-card drag, a session that isn't directly under the cursor visibly jumps to a different column (or its optimistic move gets clobbered) whenever any live update lands for it while the bulk drag is still resolving. Only manifests once Phase 6 ships multi-select drag. | Rewrite Task 3.2.2a to explicitly require a `Map<string, Session>` (or equivalent) snapshot keyed by every member of `inFlightDragSessionIds`, not "the session matching" a singular value; add a multi-select-specific freeze test (drag 2 selected sessions, push a live update for the non-primary one, assert its column doesn't change) alongside the existing single-drag Task 3.2.2b test. | P2 |
| 3 | Extracting `SessionList.tsx`'s 4 chained `useMemo` blocks into `useFilteredGroupedSessions` (Task 1.2.1a, explicitly called "the riskiest single step in the whole plan" in Step 0.5) subtly changes memoization boundaries, dependency arrays, or evaluation order in some edge case (stable-sort tie-breaking, `reviewItemBySessionId` staleness, filter/sort interaction) that the pre-existing `SessionList` test suite doesn't happen to cover. Task 1.2.1c's bar is "no changed assertions in the existing suite," which only catches regressions the original tests already exercised — not new ones the refactor introduces in untested corners. | Users notice list view ordering/grouping "looks different" after release (unstable sort order, a session that should be filtered out still showing, or vice versa), with no test failure ever having caught it, silently breaking AC11. | Before refactoring, capture characterization snapshots of `filteredSessions`/`sortedSessions`/`groupedSessions` output against 3-5 fixture datasets exercising sort ties, empty-search-plus-active-filters, and Tag multi-membership; run that snapshot before *and* after the extraction as a dedicated regression gate, not just "pre-existing suite still green." | P2 |
| 4 | Task 6.3.1c fans a multi-select drag into N independent `attemptColumnMove` calls with no aggregation. The `BatchDragOutcome` type is defined in the Domain Glossary (added specifically to address architecture-review.md's "no `BatchDragOutcome` for multi-select drag partial failure" concern) but no task ever constructs or consumes it — Task 6.3.1c's own text never mentions it, and the toast wiring (Task 3.2.1d) is scoped to single-drag `DragOutcome` only. When some of the N RPCs fail (network blip, one session in an illegal state), the user gets no aggregate feedback about which sessions moved and which didn't. | Bug report shape: "I moved 5 sessions to Paused but only 3 actually paused, and I got no error." Silent partial failure is indistinguishable from success unless the user manually re-checks the source column. | Add a task (parallel to 3.2.1d) that aggregates the N `attemptColumnMove` results into the already-specced `BatchDragOutcome` and renders one toast ("4 of 5 sessions moved to Paused — 1 failed: <reason>"); add the mixed-outcome bulk-drag test architecture-review.md already flagged as absent from Task 6.3.1d. | P2 |
| 5 | `BoardColumn`'s scroll container ref is shared via `mergeRefs` between `useVirtualizer`'s scroll ref (Task 2.1.1e) and `useDroppable`'s `setNodeRef` (Task 3.1.1c). dnd-kit's built-in drag-near-edge autoscroll and the virtualizer's own scroll-position-driven re-render both act on `scrollTop` of the same element during an active drag, and no task specifies which behavior takes precedence or verifies they coexist cleanly — a distinct, untested integration risk from the cross-column collision-detection issue pitfalls.md already covers. | Dragging a card near the top/bottom edge of a long (virtualized, 100+ session) column produces janky/stuttering autoscroll, or visible cards jump/reflow mid-drag, making it hard to drop on the intended target. Reported as "the board feels laggy/broken with a lot of sessions." | Add an explicit manual or E2E check (Phase 8) for "drag near a virtualized column's edge with 100+ sessions, confirm autoscroll is smooth"; if a conflict is found, disable dnd-kit's `autoScroll` for board columns in favor of the virtualizer's own scroll handling (or vice versa) rather than leaving the interaction unverified. | P3 |
