# UX Research: Board/Kanban View Toggle for Sessions

Agent 5 (UX) — SDD research phase for `board-kanban-view`. Covers the 5 assigned
questions plus a codebase check of existing mobile/responsive patterns to ground
recommendations in what this repo already does.

## 1. Comparable UX patterns in similar products

**Linear** ([Mobbin: Linear Web Kanban Board](https://mobbin.com/explore/screens/423b83f6-5340-41cd-a537-dd39a0d56ced), [ToolStack](https://toolstackpm.com/tools/linear/features/kanban-boards)) — board is one of several *views* over the same issue data (list, board, calendar), switched via a view selector, not a separate page/route. Columns are workflow states (Backlog/Todo/In Progress/Done); a clear column header with title + count badge is called out as a baseline best practice for "where work lives" scanning. Cards are dense — title, a few metadata chips (assignee avatar, priority icon, label pills) — no card-level buttons visible by default; actions are hover-revealed or via a context menu, keeping resting-state density high.

**Trello** — canonical board/column/card hierarchy; cards drag between columns to change state, and Trello's Butler automation (e.g. "when a card is moved to Done, archive it") demonstrates that drag = a real state transition with side effects, not just visual reordering. Columns are user-defined and unbounded in count, which this project's requirements explicitly reject (status-based, non-goal: custom columns).

**Jira (Kanban board)** — column-to-status mapping is explicit and configurable; a card that has no valid transition into a column simply cannot be dropped there (workflow-enforced), and Atlassian community threads confirm this shows up as a rejected/no-op drop rather than a silent state change. This directly parallels this project's AC5 (invalid transition → card snaps back with visible error).

**GitHub Projects (boards)** — status field-backed columns (no built-in "swimlane by custom field" without opting into a grouping control), single-click "+" quick-add per column, and per-item side-panel for full detail rather than expanding the card in place — a useful precedent for keeping cards lightweight and pushing full detail to the existing session detail view rather than growing the card.

**Vibe-Kanban** (the item's named competitor, per [vibekanban.com](https://vibekanban.com/) and secondary coverage from [VirtusLab](https://virtuslab.com/blog/ai/vibe-kanban) and [Isomoes](https://isomoes.github.io/en/blog/tools/vibe-kanban-intro/)) — closest direct analog: a kanban board specifically for orchestrating AI coding agents. Columns split by lifecycle stage: **planning → in progress → in review → done**, matching this project's proposed Running/Needs Review/Paused/Complete almost one-to-one (their "in review" ≈ this project's "Needs Review", i.e. an agent produced a diff awaiting human approval). Cards show syntax-highlighted diff review inline/on-click before merge — reinforces that "Needs Review" is a first-class, distinct column from "Running," not a sub-state buried in a detail view. No public screenshot/doc surfaced a documented drag-and-drop *rejection* UX for Vibe-Kanban specifically (gap, named explicitly) — Jira's is the best available precedent for that interaction.

**Agent-Kanban** and **Dorothy** — no public screenshots, docs, or UX write-ups were discoverable via WebSearch under those names in this domain (agent-orchestration kanban tools) as of 2026-08. Gap: treat these two as unverified/no-signal for this research pass; don't cite specific interaction claims about them.

**Cross-product synthesis of what works and why:**
- **Column header = title + count badge, always.** Every product surveyed does this; it's the single highest-value scanning aid (matches AC3 directly).
- **Card density stays low in resting state**; secondary actions (pause/stop/open) are hover- or context-menu-revealed, not permanently rendered buttons — avoids visual noise across a full board of cards. This project's existing `SessionCard`/`SessionRow` already carry rich metadata (tags, status chips, sub-status); the board view should show a *reduced* card, not the full row.
- **Column collapse/expand** appears in Jira and some Trello power-ups for columns a user wants to deprioritize (e.g. collapse "Complete" to reclaim horizontal space) — worth considering as a nice-to-have, not a stated AC; flag for planning rather than commit to it here.
- **Quick actions on card** (Jira's card menu, Linear's hover actions) are typically a strict subset of the full row's actions — pause/stop/open, not the entire `SessionRowHandlers` surface — to keep the card compact.

## 2. User mental models and expectations

- **"Toggle" implies same data, same filters, same page.** Because the requirement explicitly frames this as a List/Board *toggle* (not a separate nav item/route), users will expect it to behave like Linear's view switcher: switching preserves the current search query, current filters, and current selection — AC1 ("without... loss of current filters") and AC7/AC8 (search and bulk-select carry over) match this mental model exactly. A user who has just filtered to "my sessions" and toggles to Board will be surprised and frustrated if the filter silently resets — this is the single highest-risk mental-model violation to avoid.
- **Drag = state change, not reorder, when columns are statuses.** Every surveyed status-column board (Jira, Trello, Vibe-Kanban) treats a column-to-column drag as a real transition with a backend write, never a purely cosmetic reorder. Users who have used any of these tools will assume the same here — dragging a session's card into "Complete" should be expected (by the user) to actually change that session's state, which matches AC4. This also means **within-column drag** (reordering cards inside "Running") carries the opposite expectation: users expect that to be either unsupported or purely cosmetic (sort-order only), since no session-status semantic changes. Recommend explicitly deciding (in planning) whether within-column reorder does anything at all — if it's not wired to a real backend concept (session priority/sort order does not currently exist per this scan), the simplest and most expectation-consistent choice is to **not support within-column drag reordering** at all, only cross-column.
- **Swimlane axis reuse changes the mental model subtly**: when swimlane = status (default), columns are the primary axis. When the user picks a *different* grouping strategy (e.g. tag, branch) as requested in AC6, the natural Trello/Jira/Linear precedent is that swimlanes become **horizontal rows within the board**, with status remaining the columns — not that status disappears. The requirements text ("re-groups board columns by that axis instead of status") should be read carefully against this: users coming from Jira/Trello will expect grouping-by-tag to add horizontal swimlanes *crossed with* status columns (a 2D grid), not to replace the columns outright and lose the status view. Flag this as a planning decision point — replacing columns entirely with a non-status axis breaks the "drag = status change" mental model (what does dragging a card between "tag:frontend" and "tag:backend" columns even mean?), so the safer default is swimlane-as-row, status-as-column, consistent with every reference product surveyed.
- **Toggle vs. separate page**: users expect a toggle to be low-friction and reversible (one click / one keystroke, per AC1's `b` shortcut), and to not require a full data refetch — this favors client-side view switching over the same fetched session list, which is also cheaper to implement than a route change.

## 3. Accessibility requirements (WCAG 2.1/2.2, ARIA) for drag-and-drop

- **There is no ARIA APG pattern for drag-and-drop.** Confirmed via direct search of the [W3C ARIA APG index](https://www.w3.org/WAI/ARIA/apg/) and corroborating sources (UXPin, React Aria, SubUX) — drag-and-drop is explicitly *not* one of the documented APG patterns, unlike listbox/menu/dialog/etc. This means there is no single canonical markup to copy; the guidance below is synthesized from WCAG success criteria plus common practice (React Aria's drag-and-drop implementation, which several sources cite as a reference-quality accessible DnD implementation) rather than a ready-made spec.
- **WCAG 2.1 SC 2.5.7 (Dragging Movements, Level AA)** is the specific, binding requirement here: any functionality that uses a dragging movement must also be operable with a single pointer without dragging (e.g. click/tap-based alternative), unless dragging is essential. This directly mandates AC10's "per-card move-to action" fallback — it is not optional polish, it is a Level AA conformance requirement given this project's WCAG posture (see `.claude/rules/css-architecture.md`/UX CI running Axe Core for WCAG AA on `web-app/src/` PRs).
- **Keyboard interaction pattern** (synthesized from React Aria's drag-and-drop guidance and general WAI-ARIA practice, since no formal APG pattern exists): `Tab` to focus a card, `Space`/`Enter` to "pick up" (grab) the card, arrow keys to move focus among valid drop targets (columns), `Space`/`Enter` again to drop, `Escape` to cancel and return the card to its original position. This keyboard path is required regardless of whether a pointer-drag library is used, and should be built as the same code path as the AC10 move-to fallback where possible (a keyboard-operable "move to..." menu satisfies both the SC 2.5.7 requirement and the keyboard-DnD requirement with one implementation, rather than building two separate fallbacks).
- **State communication**: `aria-grabbed` (legacy but still commonly referenced) or a live-region announcement should communicate pick-up, movement across columns, and successful/rejected drop to screen reader users — a rejected drop (AC5) must be announced, not just visually bounced back, since a screen reader user cannot see the bounce animation.
- **Column semantics**: each column should be a labelled region (e.g. `role="list"` with an `aria-label` matching the visible header text, or a `<section aria-labelledby>` pointing at the header) so the count badge and column identity are available to assistive tech, not just sighted users scanning the header visually.
- **Focus management on drop**: after a successful cross-column move, focus should remain on the moved card (now in its new column context) rather than being lost to `document.body` — a common accessibility regression in custom DnD implementations.

## 4. Error states and edge cases

| Case | Recommended UX |
|---|---|
| **Invalid drag target (rejected transition, AC5)** | Card animates back to its origin column (the "5 states" model — resting/grabbed/in-transit/dropped/error — treats this as its own visual state, not a variant of "dropped"). Pair the bounce-back with a toast/inline error naming *why* (e.g. "Can't move a paused session directly to Complete") rather than a bare snap-back, which several sources flag as reading as a silent bug rather than an intentional rejection. Must also fire the screen-reader announcement from §3. |
| **Empty column** | Render a lightweight empty-state message inside the column body (not just a blank column, which reads as broken/loading) — consistent with the existing `SessionListEmptyState.css.ts` precedent already in this codebase for the list view's empty state; reuse that visual language rather than inventing a new one. |
| **Column with 100+ cards** | Requirements' non-goal excludes custom columns but says nothing about column-level pagination/virtualization. Given sessions can accumulate (long-running "Complete" column especially), recommend virtualized scrolling within a column (only render visible cards) rather than capping count — an arbitrary cap would silently hide sessions, which conflicts with the "see the whole workflow at a glance" JTBD in §5. This should be flagged to the architecture/plan phase as a performance requirement, not solved in UX alone. |
| **Network failure during drag-drop mutation** | If AC4's "optimistic vs. confirmed" decision (left open for planning) lands on optimistic: on mutation failure, revert the card to its origin column (same visual treatment as a rejected transition) plus a distinguishable error message ("Couldn't update session — network error" vs. "Can't move to that column" for a rejected transition) so users don't confuse a transient network failure with a permanent business-rule rejection. If confirmed-only (card doesn't move until the RPC succeeds): show an in-flight/pending visual state on the card during the round-trip so the drop doesn't feel unresponsive. |
| **Dragging a card another user/session just changed underneath you** | This is a real risk given this app's multi-workspace, potentially multi-viewer nature (see `list_workspace_peers` MCP tool existing in this repo, implying concurrent viewers are an expected scenario). If the session's status changed server-side between the drag starting and the drop completing, the mutation should fail closed (treat as a rejected transition against current state, not the stale state the drag started from) and the card should re-render in its *actual current* column with a brief highlight/flash, not silently stay wherever the user dropped it. This is the same "return the locally-computed/authoritative value" discipline already codified in `.claude/rules/go-double-checked-locking.md` for backend state — applies equally to reconciling optimistic UI state against server truth. |

## 5. Jobs-to-be-done lens

- **Functional job**: "Let me see, at a glance, where every agent session currently sits in its lifecycle and which ones need my attention *right now*, without reading through a flat list." The board's core functional value over the list is spatial grouping by state — this is well-supported by general kanban literature (Atlassian, KanbanTool) on bottleneck visibility, and matches this project's own stated goal #1 (workflow state at a glance).
- **Emotional job**: "Reduce my anxiety about a stuck or forgotten session." Multiple sources ([KanbanZone](https://kanbanzone.com/2025/kanban-for-harmony-visualizing-work/), general kanban UX literature) directly connect visualized work-in-progress to reduced stress/anxiety versus a flat list a user has to mentally re-scan and re-triage every time. For this project specifically, the "Needs Review" column is the emotional focal point — it is the column a user with review-anxiety will check first, so it deserves the strongest visual prominence (position, color accent) among the four columns, not equal visual weight with "Complete."
- **Social job**: lower-priority for this project than the functional/emotional jobs, since the requirements' non-goals explicitly exclude "cross-workspace board layouts or shared/team board customization" — there's no multi-user shared board here. The residual social job is narrower: a single user showing *their own* board to a teammate (screen share, screenshot) as a quick "here's what I have in flight" status update — this favors keeping the board visually screenshot-friendly (clear column labels + counts) but does not justify building any shared/collaborative board state.

## Codebase check: existing mobile/responsive patterns (AC10 grounding)

- **Breakpoint convention**: `max-width: 768px` is the dominant, repeated breakpoint across the sessions component CSS — found in `web-app/src/components/sessions/SessionList.css.ts:14`, `FileTree.css.ts:67`, `Omnibar.css.ts:33,51,303`, `SessionDetailBar.css.ts:48,80`, `SessionWizard.css.ts:8,21`, `ApprovalCard.css.ts` (8 occurrences), `ApprovalRulesPanel.css.ts` (7 occurrences), `BulkActions.css.ts` (4 occurrences), `FilesTab.css.ts` (6 occurrences), `SessionDetail.css.ts` (11 occurrences), `SubStatusChip.css.ts`, `ReviewQueueBadge.css.ts`, `ReviewQueueNavBadge.css.ts`. Any new board-view CSS should reuse this same `768px` breakpoint rather than introducing a new one, per the existing convention.
- **`SessionList.css.ts:1-18`** shows the concrete pattern to follow: base padding `vars.space["4"]`, reduced to `vars.space["3"]` under `768px` — board view's column padding/gutters should scale down the same way rather than inventing new spacing tokens.
- **No existing horizontal-scroll-columns pattern was found** in the sessions CSS to copy directly — this will be new CSS for the board view, but should still route all spacing/color through `vars.*` tokens per `.claude/rules/css-architecture.md` (no hardcoded hex/px magic numbers), and should decide in planning whether narrow viewports get horizontally-scrollable columns (Trello-mobile-web pattern) or a stacked single-column-at-a-time view (simpler, avoids horizontal scroll-and-drag interaction conflicts on touch, which compounds the AC10 "drag is unreliable on mobile" concern already called out in requirements).
- **Persisted per-workspace view-mode precedent**: no existing "per-workspace" storage key was found verbatim, but the established pattern for this kind of durable UI preference is: (1) a `try { localStorage.getItem/setItem } catch { fall back to default }` wrapper — see `web-app/src/lib/hooks/useSectionExpandState.ts:20-40` (per-item/per-section boolean) and `web-app/src/components/sessions/SessionList.tsx:238-264` (`makeStorageKeys`/`loadFromStorage`/`saveToStorage`, currently keyed by an optional `storageKeyPrefix` prop used today for pane-split instances, e.g. `PaneSplitRenderer.tsx:192`'s `pane-${pane.id}.` prefix — not currently workspace-scoped, but the same prefixing mechanism generalizes directly to a `workspace-${workspaceId}.` prefix for AC9's per-workspace persistence). The workspace id itself is accessible via the same source `WorkspaceSwitcher.tsx` reads (`currentId` from the databases hook, `web-app/src/lib/hooks/useDatabase.ts`) — recommend plumbing that same id into a new `stapler-squad-view-mode` storage key using the existing prefixing convention rather than inventing a new persistence layer.

## Gaps and open items for planning

- Agent-Kanban and Dorothy (the two other named competitors) yielded no usable public UX evidence — do not cite specific claims about them; Vibe-Kanban and Jira/Trello/Linear/GitHub Projects are the load-bearing precedents in this document.
- Whether swimlane-by-non-status axis replaces or crosses with status columns (§2) is a planning decision with real mental-model consequences — flagged, not resolved, here.
- Whether within-column drag (pure reorder) is supported at all is unresolved — recommendation is to *not* support it initially given no backend concept of session ordering was found in this scan.
- Column virtualization for 100+ card columns is a performance requirement this UX research surfaces but does not itself size or design — hand off to architecture/planning.
