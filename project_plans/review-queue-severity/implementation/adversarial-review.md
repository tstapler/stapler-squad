# Adversarial Review: review-queue-severity

**Date**: 2026-08-06
**Verdict**: BLOCKED → **RESOLVED post-validate (2026-08-06)** — both blockers patched into
plan.md during `/sdd:4-validate`; see the "corrected post-validate" annotations on Task
3.1.1, Task 5.2.2, and Task 6.2.1 below.

## Blockers

- [x] **RESOLVED — Task 3.1.1 corrected to scope `riskLevelCounts` to `Decision == "escalate"` only**, matching `escalationReasonCounts`'s existing conditional and eliminating the denominator/empty-state mismatch this blocker describes. Original finding: **Story 3.1/3.2 internal contradiction on what `risk_level_counts` measures, producing incorrect empty-state copy.** Task 3.1.1 aggregates `riskLevelCounts[e.RiskLevel]++` *unconditionally* over every `AnalyticsEntry` (auto_allow, auto_deny, escalate, manual_allow, manual_deny — every classifier decision, verified in `server/services/analytics_store.go`'s `ComputeSummary`). But `escalationReasonCounts` in that same function is conditional — only incremented for `Decision == "escalate"` or the secret-scan `auto_deny` case (`analytics_store.go:414-422`, confirmed by reading the code). Story 3.2's own Given/When/Then assumes the new table shares the old one's scope: "Given a window with zero escalations... the breakdown section shows the same 'No escalations in this window.' empty-state copy" — modeled directly on the Escalation Reasons block, whose empty state is keyed off `escalationReasonRows.length > 0` (`ApprovalAnalyticsPanel.tsx:331`). A realistic window (e.g. 200 auto-allowed low-risk edits, 0 escalations) would have `escalationReasonRows.length === 0` (correctly shows "No escalations") but a non-empty `riskLevelCounts` (`{"low":150,"medium":50}`) — so a "Risk Level Breakdown" table built the same way would show real data, or (if implemented with the *literal* copied condition) show the wrong label for its own non-empty state, or hide non-empty data behind escalation-scoped emptiness. — **Recommendation**: resolve before implementation which scope AC5 actually wants — (a) scope `risk_level_counts` to escalated/reviewed decisions only, matching the sibling table's semantics and AC5's "approval-count breakdown" wording, or (b) keep it decision-wide and give Story 3.2 its own empty-state condition/copy (e.g. "No decisions in this window" keyed off `summary.totalDecisions === 0`), not the reused "No escalations" text.

- [x] **RESOLVED — Task 5.2.2 and Task 6.2.1 both now require an explicit `riskLevel: ""` fixture asserting `riskLevelRank("")` sorts adjacent to/above High**, directly exercising the sort-guarantee function per the recommendation below. Original finding: **Zero test coverage for the one safety-critical guarantee the whole feature exists to provide: unrecorded severity sorts as High, never Low/last.** ADR-001 and the Pattern Decisions table both state this is the fail-safe the feature is *for* ("under-communicating risk is worse than over-communicating it"; Risk Control's top-listed risk is exactly this defeating the feature's purpose). Story 5.2 (`ApprovalDrawer`) and Story 6.2 (`ReviewQueuePanel`) both restate the guarantee in prose ("`""`/unrecorded severity sorts as if High (fail-safe), never last"), but neither paired test task exercises it: Task 5.2.2's fixture is fixed to the given B(critical)→C(medium)→A(low) items only; Story 6.2's example fixtures (`rm -rf`/`npm install`/`git commit`) are all fully-classified too. `SeverityBadge`'s tests (4.3.2) cover *rendering* of the unknown state but that's a different function (`getRiskLevelInfo`) from the one the sort guarantee depends on (`riskLevelRank`). As written, a future edit to `riskLevelRank` that treats `""` as rank 0 (the intuitive-but-wrong reading of an "empty/unknown" value) would silently regress into the exact failure mode ADR-001 was written to prevent, and no test in this plan would catch it. — **Recommendation**: add an explicit test fixture with `riskLevel: ""` to both Task 5.2.2 and Task 6.2.1/6.2.2's test coverage, asserting it sorts adjacent to/above High, before implementation starts.

## Concerns

- [ ] **AC2 (`PendingApprovalProto.risk_level` on the wire) has no paired test task.** Story 2.1's three tasks (2.1.1 proto edit, 2.1.2 handler field, 2.1.3 regen) are implementation-only. The structurally identical Story 2.2 pairs its implementation task with an explicit test task (2.2.2). Verified: no existing test in `server/services/approval_service_test.go` asserts on `risk_level`/`RiskLevel` for a `ListPendingApprovals` response. AC2 is one of the plan's 7 numbered acceptance criteria and, as scoped, could ship with no test proving the RPC actually returns the field. — Add a Task 2.1.4 (or fold into 2.1.2) asserting `resp.Msg.Approvals[i].RiskLevel` on a `ListPendingApprovals` call.

- [ ] **Story 6.2.2's "freeze sort order at snapshot time" is under-specified relative to `ReviewQueuePanel.tsx`'s actual structure.** Verified by reading `ReviewQueuePanel.tsx:330-418`: filtering and sorting for every non-default `sortField` currently live in one `allFilteredItems` `useMemo` that recomputes on every `allItems` change; the stable "items" view is just `allFilteredItems` re-filtered down to snapshot membership — it has no independent order of its own to "move." Splitting sort-order-freezing out from filter-liveness within that shared memo is a bigger change than the plan's one bullet implies, and doesn't address: (a) what happens to the frozen order when the user changes a filter (e.g. toggles the new severity filter chip) mid-session — does the frozen order still apply to the newly-filtered subset, or does filtering re-derive a fresh order; (b) whether the *existing* sort fields (priority/age/diffSize/name) also need freezing for consistency, or if it's acceptable that severity alone behaves differently from every other sort option in the same `<select>`. This freeze mechanism is the explicit justification in the Pattern Decisions table for choosing severity as a *hard default primary* sort key over the safer secondary-tiebreaker alternative that `research/pitfalls.md` §4b recommended — an under-specified implementation risks shipping precisely the reordering-during-interaction bug that mitigation exists to prevent. — Recommend a short design note (in plan.md or as an implementation-time addendum) resolving (a) and (b) before Task 6.2.2 starts.

- [ ] **Dual-frontend-path architecture is scoped as an execution-completeness risk, not evaluated as a standing architectural cost.** The Risk Control table frames "two independent frontend paths" purely as "don't forget to ship both," which the plan's tasks do mitigate. But it never asks whether the underlying pattern — `ReviewQueuePanel` reading approval data through a `map<string,string>` metadata blob populated field-by-field in `review_queue_poller.go`, independently of `ApprovalCard`'s typed proto path — should be consolidated. This is now the *second* field (`escalation_reason`/`escalation_reason_category` was the first) requiring this same double-threading; nothing in the plan records that every future approval-derived field will keep paying this cost, or files it as follow-up debt. Not a blocker for this pass (the requirements doc explicitly rules out inventing new abstractions here, correctly per the interface-pollution checklist), but worth one explicit line — either in Pattern Decisions or as a follow-up backlog item — rather than leaving the recurring cost implicit.

- [ ] **Severity staleness after rule edits isn't named as a tradeoff.** `RiskLevel` is captured once at creation and never re-derived (explicit and correct, per ADR-001/Domain Glossary, mirroring `EscalationReason`/`EscalationCategory`). But if an operator edits an `ApprovalRule.risk_level` via the already-existing rules UI while matching approvals are pending, those pending items keep showing their original, now-stale severity until resolved or expired — this is exactly the "does severity go stale, and is that acceptable" question this review was asked to check, and the plan's Risk Control table doesn't mention it. The design choice is defensible (same precedent as the other metadata fields), but should be a recorded, deliberate tradeoff rather than an implicit consequence a future reader has to re-derive.
