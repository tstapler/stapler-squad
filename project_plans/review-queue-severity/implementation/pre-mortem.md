# Pre-mortem: review-queue-severity
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | ADR-001's `""` "not recorded" sentinel is unreachable from the code path the plan mandates: `riskLevelString()` (`server/services/analytics_store.go:574-587`) has a `switch` covering all 4 enum values plus a `default: return "medium"` — it **never returns `""`** for any input, including the Go zero value (`classifier.RiskLow`). Every freshly-created `PendingApproval.RiskLevel` (via `riskLevelString(escalation.RiskLevel)`) is therefore always `"low"`/`"medium"`/`"high"`/`"critical"`, never `""`; the elaborate fail-safe "unknown → sorts as High" UI machinery only ever fires for pre-feature disk JSON, not for any degraded/zero-value `escalation` at runtime. Task 1.1.3's own claim that the `h.classifier == nil` path "yields `RiskLevel == \"\"` (not `\"low\"`) by construction" is factually wrong against the actual helper. | A future approval-creation path (new session-creation mode, a classifier error/timeout fallback, a refactor that reintroduces the `h.classifier == nil` gap Task 1.1.3 itself calls "currently unreachable... but silent if a future refactor reintroduces it") synthesizes a zero-value `ClassificationResult` and the resulting approval silently displays and sorts as genuinely-computed **"Low"** severity — visually and positionally indistinguishable from a real Low, with no error, log line, or failed test to flag it. A truly dangerous, unclassified action sorts to the bottom of the queue exactly like every other Low item. | Before Epic 1 implementation: either (a) add a dedicated `riskLevelStringOrEmpty(escalation classifier.ClassificationResult, wasClassified bool) string` (or thread a `bool`/pointer signal from the classify call site) instead of reusing `riskLevelString()` for this field, or (b) explicitly test-assert what `riskLevelString(classifier.RiskLevel(0))` and `riskLevelString()`'s `default` branch actually return today, and correct Task 1.1.3 / ADR-001 to state the true behavior (falls back to `"low"`/`"medium"`, not `""`) and pick a fail-safe that isn't `riskLevelString`'s existing zero-value collision. Add a unit test asserting a zero-value/degraded `escalation` produces the intended sentinel, not `"low"`. | P1 |
| 2 | The plan conflates two unrelated, identically-named `PendingApproval` structs. Task 1.1.1/1.1.2 add `RiskLevel` only to `server/services.PendingApproval` (`approval_store.go`), but Task 1.1.2 also lists `session/approval_automation_test.go` as one of "3 known hand-rolled `PendingApproval{...}` test fixtures" to update. That file's literals (`session/approval_automation_test.go:316,416`) construct `session.PendingApproval` — a completely different struct defined in `session/approval_automation.go:33`, part of a legacy `ApprovalAutomation`/`detection` subsystem confirmed (via `grep -rln "ApprovalAutomation"`) to have **zero callers of `NewApprovalAutomation` outside its own file** — i.e., dead code, unrelated to this feature's data flow. | A subagent working Task 1.1.2 either fails to compile after adding `RiskLevel:` to a struct literal that has no such field, or silently "audits" the wrong file and reports "3/3 fixtures updated" in a completion claim when only 2 real ones applied. | Correct plan.md before implementation: drop `session/approval_automation_test.go` from Task 1.1.2's fixture list (or explicitly note the struct-name collision and that it's out of scope/dead code), and replace the hardcoded 3-file list with a verification step (`grep -rn "PendingApproval{" --include="*_test.go" server/services/`) scoped to the correct package, since hardcoded file/line lists drift and don't self-correct. | P2 |
| 3 | Flipping `ReviewQueuePanel`'s default `sortField` from `"default"` to `"severity"` (Task 6.2.1) is treated as purely additive, but AC7's regression-safety analysis only covers backend approve/deny/expiry/auto-approval/secret-scan flows — the plan never audits other existing unit/e2e tests or user workflows elsewhere in the codebase that assume the pre-change (chronological/priority) default order of this widely-used panel. | An existing, unrelated test in `tests/e2e/` or `ReviewQueuePanel.test.tsx` that asserts on first-item/order under default conditions starts failing/flaking shortly after merge; or real users accustomed to chronological order see queue items reorder in a way that reads as random for same-severity items, with no changelog/UI cue explaining the change. | Add a task before Epic 6 ships: grep `tests/e2e/**/*.spec.ts` and the existing (untouched) parts of `ReviewQueuePanel.test.tsx` for order-dependent assertions against the review queue; add a short in-app or changelog note about the default-sort behavior change since none is currently planned. | P2 |
| 4 | Task 6.2.2 freezes sort order at `reviewingIdsSnapshot` capture time, but its test coverage only checks "order stability across a simulated poll that changes underlying data but not snapshot membership" — the compound case of an active severity filter (Story 6.3) plus a new item revealed via the "N new items added" banner is never exercised. Newly-revealed items may simply append rather than insert at their correct severity rank. | A user filtered to "Critical" accepts the "1 new item added" banner and the new Critical item appears at the bottom of the visible list instead of sorted to the top — undermining the exact "glance to find the dangerous one" value proposition for the freshest, most time-sensitive items. | Add an explicit Given/When/Then to Story 6.2 and a test case to Task 6.2.2 covering: severity filter active + new item arrives + banner accepted → new item inserted at correct severity rank, not appended. | P2 |
| 5 | `GetApprovalAnalytics`'s new `risk_level_counts` (Task 3.1.1) increments unconditionally over every `AnalyticsEntry` in the window (`for _, e := range entries { riskLevelCounts[e.RiskLevel]++ }`), which — per `RecordFromResult` (`analytics_store.go:163-203`) — includes **every classified tool call** (auto-allow, auto-deny, manual_deny, escalate). Its sibling `escalationReasonCounts` in the same loop is explicitly conditional (`if e.Decision == "escalate" || ...`, `analytics_store.go:419`). AC5 says "approval-count breakdown by severity level," implying escalations, but the implementation counts the full traffic mix. | The new "Risk Level Breakdown" table, rendered right next to "Escalation Reasons" (which IS escalation-scoped) in `ApprovalAnalyticsPanel`, shows wildly different denominators for the two adjacent tables (e.g., thousands of "Low" from routine auto-approved reads vs. a handful of real escalations) — a reviewer or user reasonably reads them as comparable and draws a wrong conclusion about how much genuinely risky traffic exists. | Before Task 3.1.1: decide and state explicitly whether `risk_level_counts` should filter to `e.Decision == "escalate"` (matching its sibling panel and AC5's "approval-count" wording) or be relabeled/re-positioned as an all-traffic risk distribution, distinct from the escalation-scoped section it currently sits beside. | P2 |
