# Validation Plan: context-compaction-detection

**Date**: 2026-08-06

## Happy Path Scenario

Given a Claude Code session whose PTY output currently shows a generic
"⏳ Thinking…" (`SubStatus.PROCESSING`) badge on its session card, when the
detector observes the compaction-in-progress line (matched by the new
`compacting_conversation` pattern and classified as `StatusCompacting`),
then the session card badge swaps to a single "⟳ Compacting context" pill
(`SubStatus.COMPACTING` → `SubStatusChip`'s new `chipCompacting` case) with
no other card behavior (approve/deny/stop, review-queue membership, working
state filtering) changed as a side effect.

Everything below is a variation on this one flow: proving each hop of
`PTY text → StatusCompacting → SUB_STATUS_COMPACTING → WorkingState → chipCompacting`
individually, and proving the three "additive only" guarantees (AC7) that
protect the pre-existing hops from regressing.

## Test Stack

- **Unit**: Go `testing` package (table-driven, following `detector_test.go`/`proto_mapping_test.go`/`pattern_set_test.go` conventions — `methodName_should_ExpectedBehavior_When_Condition` naming where the file already uses it, plain `TestXxx` matching each file's existing style otherwise); Jest + React Testing Library for TypeScript (`describe`/`it` blocks, `renders <thing> for <SubStatus>` naming matching `SubStatusChip.test.tsx`'s existing style, or `functionName_should_Expected_When_Condition` matching `deriveWorkingState.test.ts`'s existing style).
- **Integration**: Go tests that cross package boundaries on the real runtime path — `binaries.ClaudeDetector.Patterns()` → `pattern_set.go` compilation (AC2), the full `snapshot_test.go` per-fixture harness (AC4), and `server/adapters/{instance_adapter,review_queue_adapter}_test.go` (AC3, the actual RPC-facing adapters, not the unused `proto_mapping.go` functions). Jest/RTL tests that render `SessionCard`/`ReviewQueuePanel` (real component composition, not an isolated unit) count as this project's "integration" tier on the frontend, since there is no separate database or network call in this feature to integration-test against.
- **E2E / UX**: No new Playwright spec in `tests/e2e/` — this feature has no new page, route, or user-triggered flow (per `.claude/rules/e2e-test-conventions.md`'s scope, which targets user-driven journeys); the closest precedent, `SessionCard.approval-suppression.test.tsx`, is itself a Jest/RTL component test, not an e2e spec, confirming this repo already tests session-card badge precedence at the RTL layer. Criteria that are fundamentally non-automatable in jsdom (CSS media-query behavior for #9, real assistive-tech announcement for #5) are covered by a manual browser/AT check against the manual-test instance described in root `CLAUDE.md`'s "Manual/interactive testing" section, not a new e2e spec.

| Stack | Coverage command | Target |

| TypeScript/Jest | `cd web-app && npx jest --coverage --coverageThreshold='{"global":{"lines":80}}' --testPathPatterns="deriveWorkingState|SubStatusChip|StatusBadge|SessionCard|ReviewQueuePanel"` | ≥80% line on touched files |

- All public/adapter functions touched by this plan (`DetectedStatusToProto`, `DetectedStatusToSubStatus`, `toProtoSubStatusFromInfo`, `subStatusFromItem`, `AttentionReasonFromDetected`, `GetStatusIcon`, `GetStatusDescription`, `deriveWorkingState`, `getDetectedStatusInfo`, `SubStatusChip`): happy path + error/negative path covered per the table above.
- No external integrations (no new data store, no new outbound call) — the "integration" tier here is intra-repo package-boundary coverage (detection ↔ adapters ↔ frontend), not a mocked third-party service.
- All 11 UX acceptance criteria in `design/ux.md` have a corresponding automated test or an explicitly named manual step (criteria #5, #8, #9 have a manual component because they test real CSS media-query rendering, code-review-level token discipline, or real assistive-tech behavior that jsdom cannot evaluate).
