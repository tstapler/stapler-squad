# Pre-mortem: context-compaction-detection
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The compacting regex is grounded only in an INFERRED guess (`✻ Compacting conversation… (esc to interrupt)`), never verified against a live Claude Code PTY capture, and the real string differs enough that the regex never matches in production. | `DetectionEvent` ring buffer shows zero `StatusCompacting` events over weeks of real usage; users still report sessions "stuck on Processing" during compaction — the exact bug this feature was meant to fix, now silently unfixed despite the feature shipping and all tests passing. | Make live-capture (Task 1.1.1a) a hard blocking gate before this is called "done" — do not let the INFERRED fallback (1.1.1b) ship to production silently. If no live session is reachable during implementation, require a dedicated follow-up verification PR before closing the parent backlog item, and add a temporary canary: log full raw text on any line matching `(?i)compact` that does NOT classify as `StatusCompacting`, for a bake-in period, to catch a near-miss regex. | P1 |
| 2 | `toProtoSubStatusFromInfo` (`instance_adapter.go`) or `subStatusFromItem` (`review_queue_adapter.go`) is missed during implementation — no `exhaustive` lint covers `server/adapters/` (per `.golangci.yml`'s exclusion), and the plan's own mitigation (Task 2.2.2a) only says to add a test "if one doesn't already exist," leaving it optional. | Backend correctly logs `StatusCompacting` in the `DetectionEvent` ring buffer, but the session card in the browser still shows the generic "Processing"/"Thinking…" chip — a backend/frontend discrepancy that looks like a frontend bug and is easy to misdiagnose, wasting debugging time on the wrong layer. | Make the regression test in Task 2.2.2a mandatory, not conditional. Add a table-driven test that iterates every `detection.DetectedStatus` value and asserts both `toProtoSubStatusFromInfo` and `subStatusFromItem` return a non-default/non-zero `SubStatus` for each — turning "manually remember to update two duplicate switches" into an automated, CI-enforced guarantee before Epic 2.2 is considered complete. | P1 |
| 3 | A future edit to `pattern_set.go`'s `MatchLines` (reordering pattern groups, merging loops for readability, adding a new category) silently moves the `Compacting` check to after `Active`/`Processing`, making it permanently unreachable again — `StatusPattern.Priority` looks like it should prevent this but is confirmed dead/decorative, never read at match time. | Compaction detection regresses after a seemingly-unrelated PR touching `pattern_set.go`, with no compile or lint failure; the existing regression test (Story 1.3.1b) still passes because it only proves the 3 pre-existing "approaching" fixtures don't become `Compacting` — it does not assert the new compacting fixture stays reachable if the chain order changes. | Add an explicit ordering-sensitive test: feed the compacting fixture through `MatchLines` and assert it returns exactly `StatusCompacting` (not `StatusActive`/`StatusExecuting`), and place a loud, hard-to-miss comment directly above the `Active`/`Processing` loops in `pattern_set.go` warning that reordering breaks Compacting reachability — ideally paired with a follow-up lint/structural check (e.g., a `go vet`-style AST check) since no CI mechanism currently enforces switch/chain ordering here. | P2 |
| 4 | The `claude_compacting.txt` fixture (whether from live capture cleaned into a text file, or the INFERRED fallback) doesn't byte-match what the detector actually receives at runtime — e.g., ANSI color/cursor escape codes wrapping the spinner glyph, or carriage-return screen-overwrite sequences (the same class of issue the "screen-overwrite fallback" elsewhere in `MatchLines` exists to handle) that the regex's `^[ \t]*[glyph]?[ \t]*Compacting\b` anchor doesn't account for. | Same end symptom as failure #1 (no badge in production) but harder to catch, because the team believes verification already happened (Task 1.1.1a reported "success"), so nobody re-checks it — this failure mode is more likely to go unnoticed for longer than #1. | When capturing the live fixture (Task 1.1.1a), commit the literal unedited byte output of `tmux capture-pane -p -e` as the fixture — not a human-retyped/cleaned transcription — and run the actual `Detect()`/`DetectWithContext()` call against those exact captured bytes as part of the test, so the test proves the regex works against real terminal bytes, not an idealized string. | P2 |
| 5 | `DetectedStatus.COMPACTING → WorkingState.ACTIVE` and `SubStatus.COMPACTING → WorkingState.PROCESSING` are two different, unreconciled mappings for the same event (per Story 3.1.1); today's precedence rule (`SubStatus` wins whenever non-`UNSPECIFIED`) keeps only `PROCESSING` observable, but the `ACTIVE` mapping is latent, untested-for-consistency dead code that a future refactor could surface. | A user filtering the review queue or session board by working state sees compacting sessions inconsistently bucketed as "Active" in one UI surface and "Processing" in another, after an unrelated refactor changes `deriveWorkingState.ts`'s switch precedence or a new call site reads `DetectedStatus` directly instead of `SubStatus`. | Add a unit test in `deriveWorkingState.test.ts` that explicitly documents why the two mappings differ (or better, reconcile them to the same `WorkingState` value, removing the discrepancy entirely) so a future reviewer doesn't "fix" only one side and unknowingly change production behavior for what is currently a dead fallback path. | P3 |
