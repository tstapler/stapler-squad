**Key correction to the requirements doc's framing**: the visible session-card badge
(acceptance criterion 6) is driven by `session.subStatus` in `SubStatusChip.tsx`, not
by `detectedStatus`/`WorkingState` directly. `deriveWorkingState.ts` only produces the
coarse `WorkingState` bucket (4 values: UNSPECIFIED/ACTIVE/PROCESSING/IDLE/WAITING),
which is a *different* consumer, not the chip. To get a visually distinct
"⟳ Compacting context" badge (not just a generic "Thinking…" chip), the plan needs a
**new `SubStatus` proto value** (e.g. `SUB_STATUS_COMPACTING`), not just a new
`DetectedStatus` value. `DetectedStatus` is still needed too (it's the fallback signal
`deriveWorkingState.ts` uses when `subStatus` is UNSPECIFIED, and it's what
`session/detection/proto_mapping.go` and the detector layer produce natively), but on
its own it is insufficient to produce the distinct chip.

## 2. Integration points and ordering constraints

### a. Proto enum backward-compatibility (append-only)

Both enums in `proto/session/v1/types.proto` are numbered sequentially with no gaps
and no reordering history visible in the current file:

```
types.proto:381-392  enum DetectedStatus { ...UNSPECIFIED=0 ... WAITING_FOR_AGENT=11 }
types.proto:412-433  enum SubStatus      { ...UNSPECIFIED=0 ... WAITING_FOR_AGENT=10 }
```

New values (`DETECTED_STATUS_COMPACTING = 12`, `SUB_STATUS_COMPACTING = 11`) **must be
appended at the end** — proto3 enum wire values are the field numbers, and existing
deployed clients/servers depend on the current numbering being stable. Inserting a
value in the middle would silently reassign every subsequent status's wire number.
This is standard protobuf discipline, not something enforced by tooling here (no
buf breaking-change lint config was found under `proto/`) — just get it right by hand
and cite the append-only convention already followed by the existing 11/10 entries.

### b. `dtypes.StatusPatterns` needs a new field

`session/detection/dtypes/dtypes.go:15-26` — `StatusPatterns` is a plain struct with
one `[]StatusPattern` slice per category (`Ready`, `Processing`, ..., `WaitingForAgent`),
each yaml-tagged. A new `Compacting []StatusPattern \`yaml:"compacting"\`` field is
needed here. **Nothing validates the struct is "fully populated"** — there's no
reflection-based completeness check. The only place that would break if this field
is added but never wired up is `pattern_set.go`'s `compile()` `groups` slice
(`pattern_set.go:36-52`), which must add a `{"compacting", ps.patterns.Compacting,
&ps.compactingRegexes}` entry, and `MatchLines()` (`pattern_set.go:69-141`), which
must add a priority-ordered check. **If the field is added to the struct but never
added to `compile()`/`MatchLines()`, it silently compiles and silently never matches**
— this is a plain Go struct, not caught by any linter or test unless a new fixture
test explicitly asserts the new status is returned (acceptance criterion 4 already
requires this).

### c. Priority-chain placement matters

`pattern_set.go:69-141` `MatchLines()` is a fixed, hand-ordered priority chain
(Error → TestsFailing → NeedsApproval → InputRequired → readline-typing →
WaitingForAgent → Success → Active → Processing → screen-overwrite fallback → Idle →
Ready-catch-all). Where "compacting" is inserted in this chain determines precedence
against ambiguous output. Per the requirements' Non-Goal ("session is not blocked,
not idle — it's self-managing"), compacting should likely sit at a priority similar to
`WaitingForAgent`/`Active` (i.e., checked before `Success`/`Processing` so a stray
completion-looking line during compaction doesn't misclassify it), but this is a
planning-phase decision, not something confirmed by this research pass — the string
itself is still unconfirmed per requirements.md's Open Question.

### d. Duplicated DetectedStatus→SubStatus mapping — 3 sites, 1 lint-enforced

This is the most important consistency finding. There are **three** independent
switch statements that map `detection.DetectedStatus` → `sessionv1.SubStatus`, doing
nearly identical work, only one of which is compile/lint-enforced to stay exhaustive:

| Site | File:line | Used by | Exhaustive-lint covered? |
|---|---|---|---|
| `DetectedStatusToSubStatus` | `session/detection/proto_mapping.go:44` | Not called by either adapter below (currently dead code on the RPC path — grep found no callers outside its own package/tests) | **Yes** — under `session/detection/`, matches the golangci `exhaustive` allow-list |
| `toProtoSubStatusFromInfo` | `server/adapters/instance_adapter.go:240` | **Main session list/watch RPC** — the actual path feeding `SessionCard`/`SubStatusChip` | No — `server/` is lint-excluded |
| `subStatusFromItem` | `server/adapters/review_queue_adapter.go:12` | Review-queue RPC (`ReviewQueuePanel.tsx`) | No — `server/` is lint-excluded |

All three switches currently list the same 10 `DetectedStatus` cases (they're
consistent today), but **only the first would fail `make lint` if a new
`DetectedStatus` case were forgotten**. The other two return
`SubStatus_SUB_STATUS_UNSPECIFIED` after the switch with no `default:` and no
compile/lint guard — a missed case there fails silently at runtime (the badge just
doesn't show; nothing crashes, nothing warns). This is exactly the "silent
fallthrough enum" case research question 4 asked about. **All three must be updated
by hand**; the plan should call this out explicitly as three touchpoints, and
consider (as an optional but low-risk simplification within this change, or as a
follow-up) collapsing `toProtoSubStatusFromInfo`/`subStatusFromItem` to call
`detection.DetectedStatusToSubStatus()` directly instead of re-implementing the
switch, which would reduce this to one enforced site. That refactor is out of scope
to require, but worth flagging since it directly serves acceptance criterion 7
("additive only, no side effects" — duplicated logic is exactly what causes drift).

### e. `session/detection/dtypes/dtypes.go` yaml round-trip

`ExportPatterns`/`LoadPatterns` (`detector.go:70-115`, `674-690`) marshal/unmarshal
`StatusPatterns` via `yaml.v3` for the pattern-override file mechanism. The new
`Compacting` field automatically round-trips once added to the struct (no separate
registration needed there) — confirmed by reading `NewStatusDetectorFromFile`/
`LoadPatterns`, which just unmarshal into `StatusPatterns` generically.

## 3. CRUD vs. Event-Command-Policy

Confirmed: this is a **simple additive state-machine extension**, not a multi-actor
business process. There is exactly one producer (the regex pattern matcher reading
PTY bytes) and the "state" is a single derived enum value flowing one-directional
through typed converters to a UI badge — no commands, no cross-actor policy, no
persisted event log driving the transition (the `DetectionEvent` ring buffer in
`session/detection/events.go` is a debug/observability trail, not a sourced event
store). Skipping the EventStorming table, per the requirements doc's own read, is
correct.

## 4. Consistency requirements — compile-time vs. silent-fallthrough enums

This is the central finding for planning risk allocation. There are **two different
enforcement mechanisms in play**, and they don't cover all the switches:

### Compile/lint-enforced (safe — will fail the build if a case is missing)

1. **Go `exhaustive` linter**, scoped to `session/detection/` only
   (`.golangci.yml:8-114`, `exhaustive` enabled with
   `default-signifies-exhaustive: false`, and an elaborate set of path exclusions
   that net out to "only files under `session/detection/` are checked" — confirmed
   by reading the `^session/[^d]`, `^session/d[^e]`, ... `^session/dete[^c]` exclusion
   chain, which excludes everything except the `session/detec*` prefix). Because
   `default-signifies-exhaustive: false`, having a `default:` clause does **not**
   exempt a switch — every enum value still needs an explicit `case`. Verified
   exhaustive today (all list the current 11 `DetectedStatus` values): `StatusString`
   (`detector.go:646`), `GetPatternNames` (`detector.go:696`), `categoryName`
   (`events.go:65`), `mapStatusToIdleState` (`idle.go:185`),
   `DetectedStatusToProto` (`proto_mapping.go:8`), `DetectedStatusToSubStatus`
   (`proto_mapping.go:44`). **`make lint`/`make quick-check`/`make ci` will fail**
   until `StatusCompacting` gets an explicit case in all six.
2. **TypeScript `never`-exhaustiveness** in two frontend files:
   - `deriveWorkingState.ts:64-65` — `default: return assertNever(session.detectedStatus)`
     on the `DetectedStatus` fallback switch. Adding `DETECTED_STATUS_COMPACTING` to
     the proto **without** adding a case here breaks the TS build (not just a lint
     warning — `assertNever`'s parameter type is `never`, so the compiler rejects it).
   - `SubStatusChip.tsx:157-167` — `const _exhaustive: never = subStatus;` in the
     `default:` branch, deliberately non-throwing at runtime (proto forward-compat: an
     older client shouldn't crash on an unknown value from a newer server) but still a
     **compile-time** guard. Adding `SUB_STATUS_COMPACTING` without a case here breaks
     the TS build.

### NOT enforced (silent-fallthrough — needs a pitfall guard / explicit test)

1. `server/adapters/instance_adapter.go:248` `toProtoSubStatusFromInfo` — the
   **primary session-list RPC path**, unguarded (see §2d). This is the single highest-
   risk site: forgetting this case means the compacting badge silently never appears
   on the main session board even though everything else (detector, proto, frontend
   exhaustiveness checks) is correctly wired — because SubStatus would resolve to
   UNSPECIFIED and the frontend `deriveWorkingState`'s SubStatus-branch has no
   exhaustiveness check either (see below) before ever consulting `detectedStatus`.
   Actually — cross-checked: `deriveWorkingState.ts`'s SubStatus switch (lines 27-43)
   has no `default`/assertNever, so on an unhandled `SubStatus` value it just falls out
   of the switch to the `detectedStatus` fallback, which *would* still resolve to a
   sane `WorkingState` via the (enforced) `DetectedStatus` branch — but `SubStatusChip`
   would still render nothing distinct, because the actual chip switches on `subStatus`
   directly, not on `WorkingState`. Net effect if `toProtoSubStatusFromInfo` is missed:
   no visible regression (no crash, no wrong badge on other states) but acceptance
   criterion 6 silently fails.
2. `server/adapters/review_queue_adapter.go:13` `subStatusFromItem` — same shape, same
   risk, scoped to the review-queue panel instead of the main board.
3. `web-app/src/lib/utils/deriveWorkingState.ts:27-43` — the primary `SubStatus`
   switch has no exhaustiveness guard (unlike the `detectedStatus` fallback switch
   right below it in the same file). Adding `SubStatus.COMPACTING` without a case here
   doesn't break the build; it just falls through to the (correctly-typed) fallback,
   producing a coarser `WorkingState` than intended. Low risk but worth an explicit
   test per acceptance criterion 5.
4. `web-app/src/components/sessions/SessionRow.tsx:196-199` — the `rowActive` CSS
   highlight condition checks `subStatus === PROCESSING || subStatus === WAITING_FOR_AGENT`
   explicitly; a new `COMPACTING` value won't get the row-highlight treatment unless
   added here. Cosmetic, additive-safe either way (existing states unaffected), but a
   planning-phase decision.
5. `session/status_mapping.go:17-37` `AttentionReasonFromDetected` — outside
   `session/detection/`, so not lint-enforced. Explicitly groups
   `StatusExecuting, StatusProcessing, StatusWaitingForAgent, StatusReady, StatusUnknown`
   together as "no attention needed" (line 32); compacting should almost certainly
   join that group (it's self-managing per the requirements' non-goals) but the case
   needs to be added by hand — falling through to the `default: return ""` a few
   lines down happens to produce the same (correct) result today, but that's
   incidental, not guaranteed, and worth an explicit test.
