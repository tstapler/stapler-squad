# Pre-mortem: import-external-session
**Date**: 2026-07-16

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The `SIGSTOP` applied to the original process at commit time (Task 1.2.1e) has no durable record; if the stapler-squad server restarts or crashes while a row is `imported`/`kill-pending` (original process stopped, awaiting confirm-kill or cancel), the in-memory row state that would trigger `ResumeOriginalProcess` is gone and the PID stays `SIGSTOP`'d forever. | A user reports their IDE terminal / Claude CLI pane is frozen (process shows state `T` in `ps`) with no in-app affordance to fix it, especially right after a `make install-service` restart mid-import. | Persist the suspended-PID set (PID, `create_time_ms`, candidate ref) to durable state before sending `SIGSTOP`, and add a server-startup reconciliation pass that `SIGCONT`s any PID left suspended from a prior process incarnation whose row was never confirmed killed. Add this as an explicit acceptance criterion on Story 1.2.1e / Risk Control. | P1 |
| 2 | `HistoryFileDetector`'s PID/path correlation — the entire preview/commit pipeline's foundation — has never been validated against *unmanaged* external processes (requirements.md's own Feasibility Risks section flags this as unproven), so in practice most previews resolve `Ambiguous`/`NotFound` instead of `Resolved`, and the "one-click import" value proposition never materializes. | During Phase 1 soak, testers/early users report the import panel "can't find the right conversation" for sessions that obviously have a matching JSONL; disambiguation dialogs appear far more often than the plan's happy-path examples assume. | Before writing Story 1.1.3's RPC (or even finishing Story 1.1.2), run the correlation-feasibility spike as a go/no-go gate for the whole feature: measure the real resolve rate against a sample of genuinely unmanaged processes (not already-managed ones `HistoryLinker` already tracks), and only proceed with the current design if it clears a stated threshold; otherwise redesign correlation before building RPCs on top of it. | P1 |
| 3 | Story 1.3.3's "cancel/abandon kill" path only `SIGCONT`s the original process — but the managed `Instance` from commit is already alive and writing the same JSONL. Resuming the original re-creates the exact dual-writer hazard that `SIGSTOP` (Task 1.2.1e) was built specifically to prevent, this time with no automatic remediation, because commit already succeeded. | A user who clicks "Keep original session running" after import sees both the original terminal and the new managed session producing responses concurrently; the conversation JSONL shows interleaved/corrupted turns, and a later `claude --resume` on either side errors or shows garbled history. | Redefine "abandon kill" as "abandon the entire import": cancelling must delete the just-created managed `Instance`/DB row (reusing Story 1.2.3's compensating-delete path) before resuming the original, not merely `SIGCONT` the original while leaving the new instance alive. Update Story 1.3.3's acceptance criteria accordingly. | P1 |
| 4 | `KillPlainTmuxPane` (Story 2.2.1) kills at the tmux *session* level, not the pane level, per its stated rationale of matching `KillExternalSession`'s precedent — but a plain-tmux pane the user wants to import may share its tmux session with unrelated panes/windows the user is still using. | A user imports one pane from a multi-pane tmux session, confirms kill, and all sibling panes in that session close at once — losing unrelated terminal work/scrollback with no warning that the blast radius was the whole session. | Default to pane-level termination (`tmux kill-pane`) and only fall back to session-level kill when `tmux list-panes` for that session returns exactly one pane; make the confirm-kill dialog text (Story 1.4.3) explicitly state whether a whole session (and how many other panes) will be destroyed vs. just the one pane. | P2 |
| 5 | The TOCTOU mitigation (`procinfo.ProcessInspector.IsAlive`/`CreateTimeMs` re-check before suspend/kill) assumes create-time has enough resolution to distinguish a reused PID from the original; if the OS/platform's create-time granularity is coarser than the interval between original-exit and PID-reuse (plausible on any host with fast process churn), the re-check can falsely confirm identity and the code proceeds to suspend or kill an unrelated process. | An unrelated, unrelated-to-Claude process on the user's machine suddenly stops responding or exits right after a confirm-kill click, with logs showing `ConfirmKillExternalSession` reporting `Status: Killed` against a PID the user didn't intend to touch. | Add an explicit minimum-resolution/fail-closed requirement to `procinfo.ProcessInspector`: if create-time cannot be read with sufficient precision to distinguish processes, treat the identity check as inconclusive and refuse to act (return `Failed`, never assume alive-match). Add a test exercising this fail-closed path as a required acceptance criterion on Tasks 1.2.1e/1.3.1b/2.2.1a. | P3 |

## P1 Items (address before implementation)
- [ ] Failure #1 — Add durable persistence of suspended-PID state plus a startup reconciliation pass that resumes orphaned `SIGSTOP`'d PIDs; make this an explicit acceptance criterion of Story 1.2.1e and the Risk Control / Rollback procedure section.
- [ ] Failure #2 — Insert a correlation-feasibility go/no-go spike (measuring real resolve rate against genuinely unmanaged processes) ahead of Story 1.1.3, gating whether the current `CorrelateCandidate` design proceeds unchanged.
- [ ] Failure #3 — Rewrite Story 1.3.3 so "abandon kill" triggers a full compensating delete of the committed `Instance` (reusing Story 1.2.3's mechanism) before resuming the original process, rather than resuming the original while the new instance stays alive.
