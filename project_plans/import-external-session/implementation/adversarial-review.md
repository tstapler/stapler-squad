# Adversarial Review: import-external-session

**Date**: 2026-07-16
**Verdict**: CONCERNS (Iteration 1 repair-verification pass — all 3 original blockers resolved; one new non-blocking concern found)

## Resolved (Iteration 1)

- [x] **Dual-writer window (was Blocker 1).** RESOLVED. The revised plan adds Story 1.2.0b, a mandatory pre-implementation spike into `claude --resume`'s behavior against a concurrently-live original process (plan.md lines 235-243), and Task 1.2.1e in Story 1.2.1 (lines 267-271), which sends `SIGSTOP` to the original process's PID — after re-verifying liveness/identity via `procinfo.ProcessInspector.IsAlive` — immediately before `session.CreateManagedInstance` starts the resumed process, `SIGCONT`s it back on commit failure, and leaves it suspended (not killed) until `ConfirmKillExternalSession` (Story 1.3.1) or the new cancel-path guard (Story 1.3.3, lines 367-373) resumes it. This closes the dual-writer window structurally (the original process is physically stopped, not merely "hopefully killed soon") rather than relying on the CLI's own locking behavior, which the spike only characterizes as a bonus finding. Verified this is real story/task text, not just the changelog entry.

- [x] **Correlation drift between preview and commit (was Blocker 2).** RESOLVED. `CommitImportExternalSessionRequest` gains an `expected_correlation` input field (Task 1.2.1a, line 254), and Task 1.2.1f (lines 273-276) explicitly compares the commit-time re-correlation's `Kind`+`UUID` against it, aborting with `connect.CodeFailedPrecondition` and the message "the matched conversation changed since preview — please re-preview" before any `Instance` is created if they differ. This is exactly the `CorrelationChanged`-outcome behavior recommended in the original review, just named as a distinct error code/message rather than a dedicated enum value — functionally equivalent and verified against actual task text and a Given/When/Then example (line 275).

- [x] **No worktree/path-collision check before commit (was Blocker 3).** RESOLVED. New Story 1.2.4 (lines 307-324) adds `CheckPathNotAlreadyManaged`, called at the top of `CommitImportExternalSession` (Task 1.2.4b, before both suspension and `CreateManagedInstance`), which checks `candidate.Path` and its resolved worktree root against every existing `Instance`'s `WorkingDirectory()`/worktree path, returning `connect.CodeAlreadyExists` with a message identifying the colliding instance and creating nothing on collision. Acceptance criteria cover both exact-path collision and worktree-subpath collision cases (lines 311-312). Verified against actual story/task text, not just the changelog summary.

## New Concerns (Iteration 1)

- [ ] **No server-side reaper/timeout for a suspended-but-abandoned original process.** Story 1.3.3's resume-on-abandon guard only fires on explicit client-driven paths — "the user dismisses the row / navigates away without confirming kill" or an explicit "Keep original session running" click (line 370) — all of which require a live frontend to send the `CancelPendingKill` call. If the browser tab is simply closed, the machine sleeps, or the network drops after a successful commit (so the original process is `SIGSTOP`'d per Task 1.2.1e) but before the user confirms or cancels the kill, there is no defined mechanism (timeout, heartbeat, or server-side reaper) to `SIGCONT` the original process — it stays frozen indefinitely with no user-visible indication why their original terminal appears hung. This is a distinct failure mode from the original dual-writer blocker (frozen-forever vs. actively-corrupting-data), so it does not reopen Blocker 1, but it is a real gap the repair introduced: the suspension mechanism that fixes the dual-writer problem creates a new "silently frozen process" problem if the client-side confirm/cancel step never happens. — **Recommendation**: add a story for a server-side timeout (e.g., a background sweep that `SIGCONT`s any `SIGSTOP`'d original process whose commit is older than N minutes with no kill-confirm/cancel received) or, at minimum, surface the suspended state on session-list/page-reload (per the existing Minor about in-progress-import display) so the user has a path to discover and resolve an abandoned suspension.

## Concerns

- [ ] **No timeouts around tmux/`ps` subprocess calls in the import path.** `DiscoverPlainTmuxCandidates` (Story 2.1.1), `CorrelateCandidate`'s PID lookups, and the kill primitives (`KillExternalSession`, `KillPlainTmuxPane`) all shell out to `tmux`/`ps`. Pitfalls research explicitly flags "tmux/PTY not responding" as a real failure mode this review was asked to check, and no story anywhere applies a `context.WithTimeout` around these calls — a hung tmux server would hang the RPC (and the UI spinner) indefinitely. — **Recommendation**: add an explicit timeout (e.g., matching whatever `batchPTYInfo` already uses, if it has one) to every subprocess-shelling function introduced or extended by this feature, with tests asserting the RPC returns a `Failed`/error result rather than blocking forever.

- [ ] **Kill-after-confirm race only covers "process exited," not "a second writer appeared."** `PIDIdentity` re-verification at kill time (Story 1.3.1) proves the *original* PID is still the same process, but requirements' Rabbit Holes explicitly also call out "spawn a resumed `--resume` conflict if the user doesn't wait" — i.e., the user manually running `claude --resume <uuid>` in a third terminal between preview and kill-confirm. No story detects or guards against this; the identity check is necessary but not sufficient for the concurrent-writer risk the requirements explicitly named.

- [ ] **Compensating delete (Story 1.2.3) has no failure-of-failure handling.** If `EntRepository.Delete(instanceID)` itself fails after a start failure, the story's acceptance criteria ("never leave an orphaned, half-created session behind") is violated with no defined fallback (retry, loud alert, manual-cleanup marker) — it's simply not addressed.

- [ ] **Feature-flag exposure to the frontend is unspecified.** Story 1.3.2 gates the three RPC handlers server-side, and Risk Control says the flag "gates... the frontend panel's visibility," but no story defines how the frontend learns the flag's runtime value (no config/capability RPC, no story touching whatever mechanism already exposes other feature flags to the client, if one exists). As written the frontend has no way to conditionally render `ImportExternalSessionsPanel`.

- [ ] **Batch import (Phase 3) is a single blocking unary RPC with no progress feedback.** Story 3.1.1 implements `BatchImportExternalSessions` as a sequential loop inside one RPC call, deliberately not parallel (reasonable, avoids racing writers) — but this also means a batch of N candidates blocks the entire call, and thus the UI, until every item finishes, with zero incremental status for items already completed. Given batch import is explicitly in-scope (not a nice-to-have) and one hung tmux call (see timeout concern above) could stall the whole batch, this degrades the UX the requirements were written to fix.

- [ ] **Story 3.2.1's acceptance criteria are internally self-contradictory on Antigravity's on-disk format** — the same sentence describes it as resolving to "Antigravity's sqlite-backed history file (per `history_transfer.go:85`'s `~/.gemini/antigravity-cli/history.jsonl`-style layout...)" — sqlite and `.jsonl`-style are not the same format. If the real layout turns out to be sqlite (not line-oriented JSONL), the shared `ReadCanonicalTurnsFromFile`/trailing-partial-line-tolerance abstraction from Story 1.1.4 — built specifically for JSONL — will not generalize to it, and the detector interface assumed by Story 3.2.1's acceptance criteria may need to be materially different, not just a second implementation of the same shape. The spike (Task 3.2.1a) is scheduled but there's no fallback plan or re-estimation trigger if it finds a fundamentally different storage format.

- [ ] **No post-commit parity verification before the kill option is offered.** The plan asserts "zero conversation data loss" as a success metric, but no story actually verifies parity (e.g., comparing the previewed turn count / last-message excerpt against the newly-resumed managed instance's actual history) before the "End original session" button becomes available. The metric is stated but never mechanically checked anywhere in the flow.

- [ ] **`ConfirmKillExternalSession`'s `Failed` outcome has no retry path.** Story 1.4.3 shows a dismissible error telling the user to close the original manually, but there's no way to re-attempt `ConfirmKillExternalSession` from the UI once it has failed once (e.g., a transient `tmux kill-session` permission blip) — the user's only path is closing it out-of-band.

## Minors

- Story 2.2.2's Unresolved Question (kill the pane's shell vs. the Claude PID specifically) is correctly flagged as blocking and deferred to a spike, but it's worth reiterating that Phase 2's estimate is not trustworthy until that spike resolves — the plan already acknowledges this but it bears repeating given the platform-specific SIGHUP behavior pitfalls research called out.
- `PIDIdentity` staleness is only explicitly re-verified at kill time (Story 1.3.1) and via re-correlation at commit time (Story 1.2.1); there's no story that re-verifies the *candidate's* PID identity specifically (not just re-running correlation) between preview and commit, even though that gap can also be arbitrarily long.
- No story addresses what the discovery panel shows for an in-progress import (`imported` status, pending kill) after a full page reload/navigation — likely inherited from whatever general session-list persistence already exists, but not called out explicitly anywhere in Phase 1.
