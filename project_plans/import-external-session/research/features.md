# Research: Feature Landscape — import-external-session (Agent 2)

## 1. Analogous "adopt existing thing" patterns

### Industry precedents
- **Docker `docker container` has no native "adopt a manually-started process"** — the closest analog is `docker-compose up` reconciling existing containers by label match, or `docker import`/`docker commit` capturing filesystem state into a new manageable image. The pattern that transfers best here is **label/fingerprint-based reconciliation**: don't require the user to manually specify identity; derive it from environment (cwd, PID, socket) the way Compose derives container identity from `com.docker.compose.project` labels.
- **Kubernetes "adopt existing resources"** (`kubectl apply` on an object that already exists out-of-band, or Helm's `helm adopt`/orphan-resource adoption via annotations `meta.helm.sh/release-name`): the controller pattern is "match by identity fields, patch ownership metadata in place, do not recreate the underlying resource." This maps directly to promoting a `DiscoveredSession`/plain-tmux pane into a managed `Instance` — the underlying tmux session/process must NOT be killed or restarted during adoption; only stapler-squad's bookkeeping objects change. Kill only happens as a deliberate, separate, confirmed step afterward (or never, if PTY reattachment is desired instead).
- **IDE "Attach to Process" debug flows** (VS Code `attach` launch config, IntelliJ "Attach to Process"): these enumerate live processes, let the user pick one, and attach a debugger without restarting the target. The key UX lesson: **preview before commit** — IDEs typically show process command line + PID + module list before attaching, and attaching never kills the process. This is the "read-only preview" unstated need described in section 3 below.
- **tmux session takeover** (`tmux attach -d`, i.e. detach-other-client): tmux already solves "one session, multiple potential controllers" — attaching does NOT kill the pane's process, it just changes which client is displaying it. This is directly relevant: the codebase's own `ExternalSessionDiscovery.handleNewSession` (session/external_discovery.go:170-180) already does exactly this — `tmuxSession.AttachToExisting()` — proving live PTY attach without process termination is the established pattern in this repo, not a new capability to build.
- **Git worktree "adopt a branch already checked out elsewhere"**: `git worktree add` refuses if the branch is already checked out; the resolution pattern (force-move vs. detect-and-reuse) is analogous to the "external cwd may not match any known worktree" rabbit hole — this repo's own git worktree code should be consulted for how it disambiguates path collisions.

### In-repo precedent — this is not a greenfield problem
The codebase already contains a **designed-but-unused "adoption" concept**: `session/mux/protocol.go` line ~58 documents `SessionMetadata.TmuxSession` as "Tmux session name (**for stapler-squad adoption**)". This confirms the wire protocol was built anticipating this exact feature — the mux side already ships the tmux session name specifically so a managed `Instance` can attach to it. The gap is entirely on the "promote `DiscoveredSession` → durable `Instance` with worktree/lifecycle/history wiring" side, not on the transport/discovery side.

## 2. Edge cases and failure modes (beyond the stated Rabbit Holes)

Categorized beyond what's already listed (broad scope, UUID/JSONL ambiguity, worktree mismatch, kill races, batch partial-failure):

**Identity / correlation**
- External session's JSONL conversation file doesn't exist yet (process spawned but no turn has completed) — `HistoryFileDetector.Detect`/`DetectByPath` (session/history_detector.go:59,137) can legitimately return nil; import must handle "no history yet" as a valid state, not an error.
- Multiple JSONL files under the same `~/.claude/projects/<encoded-path>/` directory when several Claude processes have run in that directory historically — `DetectByPath`'s "most recently modified" heuristic (referenced in history_linker.go:254-265 comments) is explicitly called out as **wrong** for already-linked paused/hibernated sessions because a newer unrelated JSONL can steal the slot. The same ambiguity applies at import time for plain-tmux sessions with no PID-based fast path available (process may have already exited, or `GetPanePID` may fail).
- `/clear` mid-import: user runs `/clear` in the external Claude session between "preview" and "confirm" steps, changing the ConversationUUID. Import must re-validate the UUID immediately before the point of no return, not trust the value captured at preview time.
- The conversation UUID belongs to a *different* stapler-squad-managed Instance already (e.g., user externally resumed a session stapler-squad already knows about) — need a "already managed" short-circuit rather than creating a duplicate Instance pointing at the same JSONL.

**Process / PTY lifecycle**
- Non-tmux external process (plain terminal, no wrapper) has no PTY that stapler-squad can attach to at all — for these, import can only be metadata+history (this maps to Open Question 3); there is no live pane to reattach, so post-import the user's original terminal and the new managed Instance are two independent front-ends to the same underlying `claude` process until one is killed.
- Kill-after-confirm race: between "user confirms kill" and the kill command executing, the external process may already have exited (user closed the terminal), may be mid-tool-call (writing a file, running a subprocess), or PID may have been reused by an unrelated process (classic PID-reuse TOCTOU) — must verify PID identity (start time / cmdline match) immediately before sending the kill signal, not just trust the PID captured at discovery time.
- If import wires the new Instance to the *same* tmux session (as `ExternalSessionDiscovery` already does for mux sessions), then "killing the original" is nonsensical/dangerous — killing the tmux session kills the newly "imported" session too, since they're the same process. The kill-after-confirm flow is only meaningful for the plain-tmux/no-attach import path (spawn a NEW `--resume` process) — the mux-attach path has nothing to kill because adoption *is* the takeover.
- SIGTERM/SIGKILL to the external `claude` process while it has unflushed JSONL writes in progress could truncate the last turn — history import should read the JSONL *before* any kill is issued, and ideally re-read/diff after kill to confirm no data was lost (ties to the "zero conversation data loss" success metric).

**Worktree / path**
- External cwd is a subdirectory of a known worktree, not the worktree root itself — path-prefix matching, not exact-match, is required against `GetEffectiveRootDir()`-style lookups.
- External cwd is a worktree stapler-squad created but whose `Instance` was later deleted from storage (orphaned worktree) — import should offer "attach to this pre-existing worktree" rather than erroring or creating a colliding second worktree.
- External cwd's git branch has diverged/been deleted since the external session started — worktree state may not correspond to any current branch at import time.

**Batch import**
- Two discovered sessions share the same cwd (multiple terminals open in one directory) — per the existing `generateExternalTitle` PID-disambiguation pattern (session/external_discovery.go:218-234), batch import needs the same PID-based disambiguation, and the user needs per-row disambiguation UI, not just a directory name.
- One session in a batch fails mid-import (e.g., detector times out) — must not roll back already-successful imports in the same batch; partial success needs a per-row status report.

**Program/adapter diversity**
- Non-Claude programs via `HistoryAdapter` (e.g. `AgyAdapter`) have a different on-disk history format and a different "kill" semantics — `PortSessionHistory` (session/history_transfer.go:41-165) already implements cross-adapter Import/Export and is reusable, but it assumes an existing `Instance` already wired to a program; import needs to run adapter selection *before* the Instance exists.

## 3. Unstated user needs

- **Read-only preview before commit.** Given IDE "attach to process" precedent and the explicit non-negotiable "kill only after explicit confirmation AND after import verified successful," users will expect to see: conversation turn count/summary, last few messages, detected worktree/branch, and detected program — *before* anything changes state. This argues for a two-phase RPC (`PreviewImport` returning a dry-run summary, then `ConfirmImport`) rather than a single blocking call.
- **Tags/category pre-population from git branch.** `ExternalSessionDiscovery.handleNewSession` already sets `Category: "External"`, `Tags: []string{"external", "mux"}` (session/external_discovery.go:143-144) as placeholder metadata; users will expect the *imported* Instance to instead get real tags derived from the git branch/repo the same way `SESSION_TYPE_NEW_WORKTREE`/`EXISTING_WORKTREE` sessions do, not the generic "external" placeholder tags that exist purely for pre-import visibility.
- **In-flight tool call handling at kill time.** If the external Claude session is mid-tool-call (e.g., running a long build) when the user confirms kill, users will expect either (a) a warning that a running command will be interrupted, or (b) a "wait for idle" option — silent SIGTERM mid-tool-call could leave the worktree in a half-modified state that the newly-imported Instance then inherits.
- **Distinguishing "attach live" vs. "resume as new process."** For mux-discovered sessions the natural action is takeover-via-tmux-attach (no process restart, no kill needed at all — attaching already IS management). For plain-tmux/no-wrapper sessions the only option is spawning a fresh `claude --resume <uuid>` process, which necessarily leaves the *old* process running until explicitly killed. Users will likely expect the product to make this distinction obvious (different button/label), because the "kill the original" language in the requirements only cleanly applies to the second path.
- **Confidence signal on correlation.** Because JSONL correlation is heuristic (most-recently-modified file in a directory), users will want the UI to show *why* a given conversation was matched (PID-based exact detection vs. path-based best-guess) so they can catch a wrong match before confirming — especially for the plain-tmux ambiguous case flagged as a Rabbit Hole.

## Summary of key citations
- `session/mux/protocol.go` line ~58 — `TmuxSession` field explicitly documented "for stapler-squad adoption," proving this feature was anticipated at the protocol layer.
- `session/external_discovery.go:170-180` — existing live tmux attach-without-kill pattern, the template for the "adopt discovered session" path.
- `session/instance_tmux.go:201` (`KillExternalSession`) — existing kill-the-original primitive, reusable for confirm-then-kill.
- `session/history_detector.go:59,137` and `session/history_linker.go:221,254-265` — existing correlation heuristics and their documented ambiguity/limitations, directly relevant to the JSONL correlation Rabbit Hole.
- `session/history_transfer.go:41-165` — existing cross-adapter (Claude/Antigravity) history import/export logic, reusable for non-Claude `HistoryAdapter` support in scope.
- `session/claude_session_manager.go` — dead/stub code that should NOT be extended; likely predates the JSONL-based architecture.
