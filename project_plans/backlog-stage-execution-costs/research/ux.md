# UX Research: backlog-stage-execution-costs

Agent 5 (UX Research), SDD Phase 2. Grounded in `web-app/src/app/settings/pipeline-modes/{page.tsx,PipelineModeForm.tsx}`, `web-app/src/app/insights/{InsightsDashboard.tsx,ModelBreakdownChart.tsx,ProjectedCostCard.tsx,SessionsTable.tsx}`, and `web-app/src/lib/constants/programs.ts` / `web-app/src/components/workflows/WorkflowForm.tsx` (an existing, closer analog than the target files call out).

## 1. Comparable UX patterns: group-by/drill-into in CI/CD and cloud-cost dashboards

- **AWS Cost Explorer**: single persistent "Group by" dropdown (service, tag, region, etc.) above the chart — changes the chart's series/bars in place, no navigation. Clicking a legend entry or a bar segment cross-filters the same view rather than opening a new page. Filters (date range, linked account, tag) live in a filter bar beside the group-by control, and a drill-in ("view this service's detail") is a URL-addressable state change, not a modal.
- **GitHub Actions usage/billing insights** and **GitLab CI/CD minutes usage**: usage-by-workflow/job is a table with a sort + text filter, not primarily a chart-driven drill-down — closer to this project's existing `SessionsTable.tsx` (search box + model `<select>` + sortable columns) than to a novel chart interaction.
- **Recommended pattern for this project**: don't invent a new grouping widget. `ModelBreakdownChart.tsx` already renders one dimension (model family) as bars with a color-coded legend below. Add "stage/role" as a second, parallel `BarChart` card (same `PALETTE`, same legend-row shape) rather than a generic pivot control — consistent with the requirement's "consistent with the existing global total" and the codebase's established one-chart-per-dimension composition in `InsightsDashboard.tsx`'s `grid2` sections (`DailySpendChart` + `ModelBreakdownChart` side by side).
- **Drill-into-item-name**: reuse `SessionsTable.tsx`'s existing search box (`Fuse.js` on `backlogTitle`), not a new drill-down UI. Make each bar clickable (`onClick` on `Bar`, same interaction style as `SessionsTable`'s clickable rows / `SessionDetailDrawer`) to set `searchText` in a shared filter state and scroll to `SessionsTable`, mirroring how AWS Cost Explorer's bar click cross-filters an already-visible table rather than opening a new screen. This avoids a second, disconnected "drill down" concept.

## 2. Mental model: per-item override vs. per-pipeline-mode template

The requirement (extend `PipelineMode`, not per-item) matches how users already think about this system — validated, not just assumed:

- `PipelineModeForm.tsx`'s existing 9 `CONTENT_FIELDS` (prompts/commands) are **already** per-template, not per-item — a user configuring "triage prompt" today is editing a mode, applied to every backlog item using it. Program+model per stage is the same kind of setting (how a stage behaves), so it belongs next to the fields the user already edits in the same form, not as a new per-item override surface.
- The "cheap model for triage, strong model for review" framing in the requirements is a **role-based policy** ("this kind of work always gets this model"), which is inherently a template concept — a per-item override would force re-deciding it for every backlog item, defeating the stated job of "control spend without micromanaging every session."
- **Information architecture implication**: the existing form appends 9 textareas in a `templateFieldsGrid` (CSS grid, `PipelineModeForm.tsx:219-235`) — one field per row. Program+model needs 2 fields × N stages (triage/review/work, per the requirement's stage list), so a straight repeat of that pattern produces a very tall form. Prefer a compact **table layout** — one row per stage, two columns (Program, Model) using the `WorkflowForm.tsx` pattern (`MODEL_AUTOCOMPLETE_OPTIONS` fuzzy-autocomplete input, not a rigid `<select>`, since model IDs churn — see `CLAUDE_MODELS` in `web-app/src/lib/constants/programs.ts`) — placed as its own labeled subsection ("Stage execution") above or below the existing `templateFieldsGrid`, not interleaved with the 9 content fields, since it's a distinct concern (execution config vs. prompt/command content).
- Reuse `PROGRAMS`/`MODEL_AUTOCOMPLETE_OPTIONS` from `web-app/src/lib/constants/programs.ts` rather than inventing a new constants list — `WorkflowForm.tsx` already establishes this as the project's program/model picker convention.

## 3. Accessibility

**Bar chart (new "Cost by Stage/Role" chart):**
- `ModelBreakdownChart.tsx`'s current `BarChart`/`ResponsiveContainer` has **no `role` or `aria-label`** on the chart itself — screen reader users get nothing (recharts renders as unlabeled SVG by default). The new chart should not just copy this gap: add `role="img"` and a descriptive `aria-label` (e.g. `"Cost by stage: triage $X, review $Y, work $Z"`) on the chart's wrapping `div` (`chartWrap`), since recharts' SVG output isn't independently announced.
- The **legend is not keyboard-interactive** today (`legendRow`/`legendItem` in `ModelBreakdownChart.tsx` are plain `div`s, no `tabIndex`/`role="button"`/`onKeyDown`). If the new chart makes bars/legend entries clickable for drill-down (per §1), give them the same treatment `SessionsTable.tsx` already uses for its clickable rows (`role="button"`, `tabIndex={0}`, `onKeyDown` handling Enter/Space — see `SessionsTable.tsx:233-238,350-361`) — an established, tested pattern in this codebase, not a new one to invent.
- Data table alternative: since `SessionsTable.tsx` already has a `SessionRole` column, a screen-reader user can get the same stage/cost breakdown from the table without needing the chart to be interactive — keep the chart's clickability as a convenience, not the only path to the drill-down.

**Extended settings form:**
- Follow `PipelineModeForm.tsx`'s existing conventions exactly: every field has a `<label htmlFor>` (not placeholder-only labeling), a `data-testid`, and inline `role="alert"` error display (`styles.errorMessage`, line 154-158). The new stage-row table needs the same per-cell labeling — a bare table of inputs without per-input `<label>`/`aria-label` (e.g. `aria-label="Triage stage model"`) fails WCAG 1.3.1 (info and relationships) since column headers alone don't reliably associate with screen-reader-announced inputs in all AT.
- Table vs. repeated subsections (§2): if a `<table>` layout is chosen, use real `<th scope="col">` headers (mirrors `SessionsTable.tsx`'s existing `scope="col"` usage) so AT announces "Program, row Triage" correctly — don't lay it out with CSS grid `div`s styled to look like a table, which loses that semantic association.

## 4. Error / edge-case UX

- **Program not installed/detected**: `PROGRAMS` (`web-app/src/lib/constants/programs.ts`) is a static hardcoded list with no "installed on this machine" detection at all today — selecting `aider` when Aider isn't installed is currently a silent runtime failure at session-launch time, not a form-time warning. This is a gap the new per-stage config inherits unchanged; scope call: **out of scope** to build install detection as part of this project (no existing detection mechanism to hook into), but the settings form should at minimum surface the failure **when a configured stage's program fails to launch** (a toast/banner at pipeline-run time, analogous to `PipelineModeForm.tsx`'s existing `errorMessage()`/inline `role="alert"` pattern) rather than only failing silently mid-run. Flag this as a candidate follow-up, not silently deferred.
- **Zero sessions for a stage in range**: follow `ModelBreakdownChart.tsx`'s existing empty-state exactly — `models.length === 0` renders a `chartCard` with just `"No data"` (`emptyChart` class) instead of an empty/broken chart. The new stage chart should do the same per-stage: if a stage has zero sessions in the selected time range, omit its bar entirely (matches how `ModelBreakdownChart` only renders bars for families present in `models`) rather than showing a zero-height bar that could be misread as "$0 cost incurred," and if *all* stages are empty, show the same "No data" card state.
- **Unpriced/unknown cost (non-Claude program)**: `ModelBreakdownChart.tsx` already has the pattern to mirror exactly — `pricingUnavailable` per data point renders `" (pricing unavailable)"` inline next to that legend entry (`unpricedLabel` span, line 116-118), not a blocking error or an excluded bar. `SessionsTable.tsx` similarly renders an `unpricedBadge` chip inline (`"unpriced"`) next to the cost cell and sorts unpriced rows last in cost/ROI/waste-score columns rather than treating them as zero. The new stage chart should carry `pricingUnavailable`/`unpriced` through the same way: show the bar (using whatever partial cost data exists, e.g. Claude sub-portions of a mixed-program stage) with an inline "(pricing unavailable)" annotation, never hide the stage or block the chart.
- **Soft budget warning surfacing**: `ProjectedCostCard.tsx` already has the exact shape needed — a `threshold` input, a computed `isWarning` boolean, and a non-blocking inline `warningText` span ("Over budget!") plus the page-level `errorBox` banner in `InsightsDashboard.tsx` (lines 155-159, `role="alert"`, styled as an alert but not a modal/blocking dialog). Per requirements' "visibly, not silently" + out-of-scope "no hard enforcement," extend this exact mechanism for stage/item thresholds rather than building a new toast/notification system — e.g. an additional warning row per over-threshold stage in the new chart's legend area (same visual language as `unpricedLabel`) plus a rollup in the existing `errorBox`/`ProjectedCostCard` region so a user doesn't have two disconnected "budget" surfaces on one page.

## 5. Jobs-to-be-done

- **Functional**: "Let me route each pipeline stage to the model/program that's actually good enough for that stage's work, without hand-configuring every session" — triage is cheap classification, review needs judgment, implementation needs a strong coding model; today every stage is forced onto one setting.
- **Functional (secondary)**: "Let me see where my agent spend is actually going, broken down by what kind of work it's doing" — the existing `ModelBreakdownChart` answers "which model costs the most" but not "is my spend concentrated in triage overhead or real implementation work," which is the actual budget-allocation question this project answers.
- **Emotional**: "Catch a runaway-cost mistake before it becomes a surprise bill" — the soft-budget-warning requirement is explicitly about early, visible signal (not blocking), addressing anxiety about an unattended/autonomous pipeline silently accumulating cost.
- **Emotional (secondary)**: "Feel confident delegating triage/review to a cheaper model without feeling like I'm cutting corners" — seeing the stage breakdown and the cost saved reassures the user their configuration choice was a deliberate, visible trade-off rather than an invisible risk.
- **Social/self-image**: "Feel like a disciplined operator of an AI pipeline, not someone who just lets an agent run wild" — the combination of per-stage control + visible cost breakdown + a budget guardrail together perform "I run this responsibly," which matters for a tool whose whole pitch is autonomous multi-session work.

## Summary of concrete recommendations
1. New chart: a second `BarChart` card next to/near `ModelBreakdownChart`, same `PALETTE`/legend/empty-state/unpriced-label conventions, bars clickable to filter `SessionsTable` by item name (no new drill-down UI).
2. Settings form: add a compact **stage × {program, model}** table/subsection to `PipelineModeForm.tsx`, using the `WorkflowForm.tsx`/`programs.ts` autocomplete pattern (not a rigid `<select>`), separate from the existing 9 content-template fields.
3. Budget warning: extend `ProjectedCostCard.tsx`'s existing threshold/warning mechanism per-stage/per-item rather than building a new alert system; keep it visually attached to the existing budget card so the page has one budget concept, not two.
4. Accessibility gap to fix, not copy: add `role="img"`/`aria-label` to the new chart's container and keyboard support to any new clickable bar/legend elements — `ModelBreakdownChart.tsx` currently lacks both.
5. Program-not-installed detection has no existing hook in this codebase (`PROGRAMS` is a static list) — treat surfacing that failure as a candidate follow-up, not a blocking requirement of this project.
