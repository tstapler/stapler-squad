# Pre-mortem: backlog-stage-execution-costs
**Date**: 2026-09-17

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | A cheap/free triage model (e.g. Haiku) produces lower-quality triage classifications, causing more re-triage, more failed reviews, and more rework cycles downstream — the resulting *item-total* cost (triage + review + work) rises even though the isolated triage-stage number the plan measures goes down. Success Metrics only require "that item's triage cost" to fall (requirements.md line 18); nothing computes or displays a per-item *total* cost delta against a same-mode baseline, so the regression is invisible in the shipped UI even when it happens. | Operator sees `StageCostChart`'s triage bar shrink and believes the feature is working, while `rework_count`/re-review frequency and item total cost creep up unnoticed for weeks (no chart correlates the two). | Add one AC to Epic 4.1/5.2: an item-level "total cost across all stages, this run vs. prior mode" comparison (or at minimum, surface rework/re-review count next to `ItemStageCostTable`, per the adversarial review's own Minor about `session_count` never being rendered) so a triage-quality regression shows up as a visible cost or rework signal, not just a smaller triage bar. | P1 |
| 2 | The soft budget warning (`EvaluateBudgetThreshold`, ADR-003) is only invoked from the triage/review `CostSink` closures (Task 4.2.2c) — there is no task anywhere in Epic 4.2 that calls it from the interactive work-stage session's cost accrual, even though ADR-003's own Decision text says it should fire "at the point a work-stage session's cost is periodically re-read." The work stage (an open-ended interactive Claude Code/Aider session) is the stage most likely to run away in cost, and it is exactly the one stage this feature cannot warn about. | A user sets a $5 per-item budget, an implementation session runs for hours and racks up $40, and no `[BudgetWarning]` log or Insights warning ever fires for that item — the threshold silently only ever applied to the two cheapest stages. | Add a task under Epic 4.2 that re-evaluates `EvaluateBudgetThreshold` against the work-stage `ItemSession`'s running cost on the existing periodic cost-refresh path (wherever `ItemSession.Cost` gets updated for an active interactive session today), not only inside the two headless `CostSink` closures. | P1 |
| 3 | `GeminiCaller.Available()` (Task 3.1.1g) is a bare `exec.LookPath` check — it proves the binary exists, not that the configured API key is valid or quota remains. An expired key or exhausted quota makes `Available()` return `true`, so `resolveHeadlessCaller` routes to `GeminiCaller` every time, and every triage/review call for that mode then hard-fails via the `"error"` object path (Task 3.1.1e) with no automatic fallback-and-retry against Claude. Because this is a single-user local tool with "no new oncall alerting" (requirements.md's Observability Requirements), a whole batch of nightly triage runs can fail this way before anyone notices. | Multiple backlog items sit in a stuck/errored triage state; the operator only discovers the cause after opening one item's session log and finding a `"quota exceeded"` error, not from any dashboard signal. | Extend `resolveHeadlessCaller`'s fallback path to also catch a hard `CallBlocking` error from a non-Claude caller and retry once against the Claude pool (mirroring the existing `configured_program`/`executor_fallback_reason` persistence for the availability-based fallback), rather than treating "binary present" and "call actually succeeds" as the same signal. | P2 |
| 4 | `session/tokens/pricing.go`'s new Gemini entries (Task 3.2.1a) are a one-time, manually-verified snapshot of `ai.google.dev`'s pricing page with no mechanism to detect or flag when Google changes Gemini pricing or free-tier limits later. Unlike the multi-provider drift this codebase already got burned by once (BUG-050: two independently-drifting pricing tables), this is a single table silently going stale against the real world outside the codebase entirely. | Insights shows a plausible but wrong per-item Gemini cost for months; nothing in the plan re-verifies the table, and the soft budget warning (item 2) compounds this by comparing spend against a threshold using stale unit prices. | Add a lightweight recurring reminder (a dated comment with a re-check cadence, or a `/insights` footnote showing the pricing table's last-verified date, mirroring the existing dated/sourced comment convention) so a stale entry is at least discoverable rather than indistinguishable from a correct one. | P3 |
| 5 | `ItemSession.executor_snapshot_hash` is persisted (Task 2.1.2b/2.3.2c) specifically so a "what ran" UI could detect a `PipelineMode`'s executor config having changed since a session started (plan.md line 67's stated purpose) — but no task in Epic 5 ever reads or compares this field anywhere in the frontend, unlike `pipeline_mode_snapshot_hash`'s existing content-drift comparison in `BacklogItemDetail.tsx`. The audit trail the research explicitly called out as an "unstated need" ("a user debugging 'why did this item cost $40' needs to see what ran then, not what the mode says now") is collected but inert. | A user investigating an expensive item can query the raw proto field but has no UI affordance telling them the mode's executor config drifted since that session ran — the debugging workflow the field was built for doesn't exist at ship time. | Add one small Epic 5 task pairing `executor_snapshot_hash` with the current mode's computed hash in `BacklogItemDetail.tsx`'s existing "what ran" section, alongside the already-planned `configured_program`/`executor_fallback_reason` badge (Concern already tracked in adversarial-review.md) — same component, same pass. | P3 |

## P1 Items (address before implementation)
- [x] #1 — Add an item-total (not just per-stage) cost view or rework/re-review-count signal to Epic 4.1/5.2 so a cheap-triage-induced rework cascade is visible, not masked by a shrinking triage bar. **Resolved**: `ItemRoleCost.session_count` surfaced in Story 5.2.3 (Tasks 5.2.3d/e), emphasized when >1.
- [x] #2 — Add a work-stage cost-refresh call site for `EvaluateBudgetThreshold` in Epic 4.2, so the soft budget warning actually covers the stage most likely to blow a budget. **Resolved**: new Story 4.2.3 hooks the threshold check into `WatchBacklogItems`/`GetBacklogItem`'s existing recompute-on-read cost path, with a per-process dedup set to avoid log spam.
