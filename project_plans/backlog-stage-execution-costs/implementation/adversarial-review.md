# Adversarial Review: backlog-stage-execution-costs

**Date**: 2026-09-17 (re-review after repair pass)
**Verdict**: CONCERNS

**Scope of this re-review**: targeted verification of the 3 prior BLOCKERS against the updated `implementation/plan.md` (1073 lines) and `decisions/ADR-002-aider-excluded-from-headless-cost-accounting.md`'s new addendum, cross-checked against live code (`server/services/session_service.go:1632-1734`, `server/services/backlog_service_triage.go:979-1004,3042`, `server/services/backlog_service.go:31,35`, `session/instance.go:889-919`, `session/instance_program.go:59`, `session/headless/pool.go:25-97`, `session/headless/caller.go:288,304,686`, `web-app/src/components/backlog/BacklogItemDetail.tsx`, `web-app/src/lib/backlog/pipelineModeDisplay.ts`, `web-app/src/app/insights/SessionDetailContent.tsx`). The rest of the plan was skimmed only for regressions, not re-audited in full.

## Blocker re-verification

### Blocker #1 — work-stage `SwitchProgram` race dropping the kickoff prompt: **RESOLVED**
Verified against live code that `CreateWorktreeSession`/`CreateDirectorySession` (`server/services/session_service.go:1632-1734`) already build `InstanceOptions{..., Program: resolved.Program, ...}` and pass it to `session.NewInstance` *before* calling `instance.Start(true)` — this is the exact existing pattern the repair's Task 2.4.1b extends: a new trailing `programOverride string` parameter overrides `opts.Program` before `NewInstance`/`Start(true)`, never after. `SwitchProgram`/`Restart` (`session/instance_program.go:59`) is not invoked anywhere in this path. The resolution call itself (Task 2.4.1a) is inserted before the two existing call sites in `backlog_service_triage.go` (confirmed at lines 995/998, matching the plan's cited line numbers). The other two call sites of the now-extended interface (`SessionService.SpawnReviewSession` at `session_service.go:1620`, `TriggerReReview`'s spawn at `backlog_service_triage.go:3042`) are explicitly enumerated in Task 2.4.1b and given `""` (no behavior change) — no inconsistent ripple.
Story 2.4.1 now carries a dedicated AC + Given-When-Then (plan.md:552-553) and a dedicated test task (2.4.1f) asserting the kickoff prompt is delivered exactly once and no `Restart`/`KillSession` occurs — this is real behavioral proof, not just a final-string assertion.
No new blocker introduced: the interface signature change is applied consistently across all 4 call sites named.

### Blocker #2 — `GeminiCaller` unbounded concurrency: **RESOLVED**
Design is concrete, not hand-waved: `GeminiCaller` gets its own `concurrencySem chan struct{}` field, a constructor `NewGeminiCaller(binPath string, pricing *tokens.PricingTable, maxConcurrent int)` defaulting to 5 when `<=0` (Task 3.1.1a), and Task 3.1.1b explicitly directs reuse of `Pool.call()`'s `maxQueueWait`/`ErrPoolSaturated` fail-fast discipline. Verified `GeminiCaller` is planned to live in `session/headless/gemini_caller.go` — the same package as `pool.go` (`package headless`, confirmed) — so it can literally reuse the unexported `maxQueueWait` var and `ErrPoolSaturated` sentinel (`session/headless/caller.go:288,304,686`) rather than reinventing them. AC at plan.md:659 gives a concrete Given-When-Then (2 held + a 3rd call, queue-wait elapses, pool-saturation error returned, no unbounded 3rd subprocess). Dedicated unit test tasks (3.1.1f, 3.1.1h) cover both the happy path and the `Available()` TTL cache. `server/dependencies.go` wiring (Task 3.1.2a) passes `maxConcurrent: 5`, matching Claude's `Pool{MaxConcurrentSessions: 5}` literal at the same file's line 741, called out explicitly so both bounds are visible together.

### Blocker #3 — Gemini availability checked only at startup, silent fallback: **PARTIALLY RESOLVED — staleness fixed, "loud" claim not fully substantiated**
The **staleness** half of the original finding is genuinely fixed: `GeminiCaller.Available()` (Task 3.1.1g) is a short-TTL-cached (~30s) `exec.LookPath` re-probe, consulted by `resolveHeadlessCaller` (Task 2.3.1b) on *every* call via a small `availabilityChecker` interface, not only at server startup. The GWT at plan.md:477 is concrete and correctly models the "installed at startup, removed later" failure mode this blocker named.

The **"loud, not silent" surfacing** half is not fully delivered, though. The repair persists `configured_program`/`executor_fallback_reason` onto `ItemSession` and exposes them as proto fields 24-25 (Tasks 2.1.2a/d, 2.3.2c, 2.3.3b) — real progress over a log-only signal, since it's now queryable and durable. But I checked every Epic 5 (frontend) task in the plan and found **no task that renders these two new fields anywhere in the UI**:
- `BacklogItemDetail.tsx`'s existing "what ran" surface (`web-app/src/lib/backlog/pipelineModeDisplay.ts`) only ever consumes `pipelineModeSnapshot`/`pipelineModeSnapshotHash` (content drift) — a different pair of fields; the plan does not extend it to the new executor-fallback fields.
- The one existing per-session detail view that already renders program/model info, `web-app/src/app/insights/SessionDetailContent.tsx` (shows `session.primaryModel` under a "Model" label), is never referenced anywhere in plan.md — no task wires `configured_program`/`executor_fallback_reason` into it.
- Epic 5.2/5.3's new components (`StageCostChart`, `ItemStageCostTable`, `ItemBudgetWarning`) are all cost-shaped, not "what program actually ran"-shaped, and don't carry these fields either.

So as planned, an operator who didn't already suspect a fallback has no passive way to notice one — they'd have to already suspect a problem and query the `ItemSession` proto/API directly, which is the exact "field nobody looks at" shape ADR-002's addendum claims to have fixed. This is a real, if narrower, gap than the original blocker (it's now discoverable via API rather than lost after log rotation), so I'm not re-opening it as a full BLOCKER, but it should not be reported as closed either. Moved to Concerns below with a concrete recommendation.

### Spot-check: did fixing these 3 introduce a new blocker? No.
- The `CostSink` signature change (`func(usd float64)` → `func(usd float64, priced bool)`, Epic 2.5) is the biggest ripple in this repair pass — verified the plan enumerates all 14 existing `.CallBlocking(` call sites by file:line (plan.md:592) and asserts they compile with no behavior change; inline closures becoming `func(usd float64, _ bool) {...}` is mechanical and low-risk.
- The repair pass's own code verification surfaced one *new*, previously-undiscovered correctness gap as a side effect of shipping `GeminiCaller`: a Gemini-priced `ItemSession` writes no `.jsonl` transcript, so it would have been invisible to `GetInsightsSummary`'s entire aggregation pipeline (which only reads transcripts), silently defeating the "cheaper-model triage lowers visible cost" success metric for the one program this project builds an adapter for. This is not one of the 3 named blockers, but the repair pass caught it and added a fully-scoped fix (Story 4.1.4, Tasks 4.1.4a-c) rather than leaving it as a known gap — good discipline, and a real fix, not a hand-wave.
- `resolveHeadlessCaller`'s new 3-tuple return is brand new in this codebase (verified no pre-existing callers to reconcile); both of its 2 call sites (triage Task 2.3.2b, review Task 2.3.3b) destructure it identically. No inconsistent ripple.

## Concerns

- [ ] **`configured_program`/`executor_fallback_reason` are persisted and exposed on the proto, but no frontend task renders them anywhere.** See Blocker #3 analysis above. **Recommendation**: add a small task to Epic 5.1 or a new one wiring these two fields into `BacklogItemDetail.tsx`'s existing "what ran" section (natural pairing with `pipelineModeSnapshot`) and/or `SessionDetailContent.tsx`'s existing "Model" row — a one-line "ran on Claude (gemini unavailable)" badge is enough to make this actually loud.
- [ ] **(Carried forward, NOT addressed by this repair pass) No idle-timeout-equivalent design decision for `GeminiCaller` hangs.** Searched the updated plan.md for "idle timeout"/"heartbeat"/"stall detection" — no match. Epic 3.1's tasks (3.1.1a-h) still only cover struct/subprocess/parsing/error-mapping/concurrency/availability; a hung `gemini -p ... --output-format json` call still has no stall detection short of the caller's outer hard deadline. **Recommendation**: unchanged from the original review — add one sentence to ADR-002 (or a task) explicitly accepting "idle timeout == hard ctx deadline for Gemini in v1," so it isn't rediscovered as a surprise later.
- [ ] **(Carried forward, NOT addressed by this repair pass) A non-Claude work-stage program with a `Model` override is still silently dropped at the resolution layer.** `session.ResolveExecutorProgram("aider", "family:sonnet", families)` still returns `("aider", nil)` unchanged (plan.md:441-442) — the repair pass did label this "a documented limitation" in the plan text (an improvement in plan-readability over the original silent gap), but no save-time rejection and no runtime Warn/UI hint were added for a user who actually configures this combination. **Recommendation**: unchanged from the original review — either reject the combination at save time (Story 1.3.1) or add a Warn log + one-line UI hint.
