## 2. Event-data defects (VERIFIED)

- **Mixed timezone offsets in stored text.** `select substr(created_at,-6),count(*) from backlog_status_events group by 1`: `+00:00` 247,333; `-07:00` 10,654. Same split in `backlog_items.created_at`: `+00:00` 68, `-07:00` 93. Cause: schema defaults use bare `time.Now` (Local) for `backlog_status_event.created_at` (`session/ent/schema/backlog_status_event.go:31-33`) and `backlog_item.created_at` (`session/ent/schema/backlog_item.go:164-165`), whereas `updated_at` was fixed to UTC (`backlog_item.go:167-186`, comment explains Local vs UTC format differences). The DSN has `_timezone=UTC` (`session/ent_repository.go:139-149`) which normalizes on READ through ent, but raw SQL / sqlite3 string comparisons and `ORDER BY created_at` on TEXT compare lexicographically and mis-order a `-07:00` row against a `+00:00` row (same instant is 7h apart as text). Consequence: any hand-written SQL `WHERE created_at >= '...'`, `GROUP BY date(created_at)` (date() converts, substr does not), or window-function ordering by text can misorder events and produce negative dwell. Mitigation: (a) do aggregation through ent/Go (which parses to UTC), or in SQL use `datetime(created_at)`/`julianday(created_at)` which normalize offsets — but then the index on `created_at` cannot be used; (b) order per item by `rowid`/insertion order as tiebreaker; (c) clamp negative dwell to 0 and count them as data-quality warnings; (d) optionally a one-time migration normalizing to UTC (additive, but writes 260k rows under the live service — do not do in the first pass). Do NOT add yet another `time.Now` default for any new table; use `time.Now().UTC()` (precedent: `backlog_item.go:185`).
- **Self-loops exist:** `from_status = to_status` rows: done>done 2, in_progress>in_progress 6, review>review 2 (VERIFIED). Exclude from transitions/funnel counts (they inflate "stage entries" and rework); keep a data-quality counter.
- **Duplicate/near-duplicate events:** `backlog_status_events` has no unique constraint beyond the UUID PK and `(item_id, created_at)` index (non-unique). Same-timestamp ties possible; ordering must use a deterministic tiebreaker. INFERRED (not measured whether exact duplicates exist; add a check query in tests).
- **Stale tail:** latest event `2026-11-06 04:15:15+00:00` (VERIFIED) — i.e., thrash/events are live now; as-of timestamps must be shown (requirements.md:81).
- **Event table is append-only and unbounded** (schema comment `backlog_status_event.go:13`); retention question is open (requirements.md:91). If raw events are ever pruned, rollups must preserve counts or historical dwell silently changes.

## 3. Joins: verdicts and sessions

- `review_verdicts` has no `item_id` column (VERIFIED: `no such column: item_id`); it hangs off `item_sessions` via ent edge (`session/ent/schema/item_session.go:79` `edge.To("review_verdict")`), and `item_sessions` links to `backlog_item` (`item_session.go:75`; `backlog_item.go:193`). So verdict -> item needs verdict -> item_sessions -> backlog_item. 1,401 item_sessions vs 161 items (VERIFIED) — ~9 sessions per item; joining items->sessions->verdicts multiplies rows; any `COUNT(*)` after the join without `COUNT(DISTINCT ...)` over-counts. Aggregate verdicts per session first, then per item (subquery), not a flat join.
- `session_uuid` is a loose FK (no ent edge; `item_session.go:23-24`): sessions may have been deleted while item_sessions remain; do not join to the sessions table for item-level metrics.
- Verdict sequence ordering uses `created_at` of verdicts — same mixed-offset hazard if those rows were written with Local time (INFERRED: `review_verdict` created_at default not checked).
- Session `end_reason`, `last_progress_at`, `commit_count_since_spawn` exist on item_sessions (`item_session.go` fields) and are better "agent believes done" proxies than free-form notes; do not invent capture before checking these (open question 2).

## 4. SQLite performance and write contention

- Live service holds **one** connection: `db.SetMaxOpenConns(1)` (`session/ent_repository.go:164`), WAL on, busy_timeout 5000ms (`ent_repository.go:150-155`). Any analytic query run through the same `*sql.DB`/ent client **serializes against all writers** (the thrash loop included) and blocks the service for its duration; a slow aggregation = UI/orchestrator stalls and `SQLITE_BUSY` risk. Backlog code already warns about re-entrancy: calling back through the repo while a tx is held deadlocks because of the single connection (`session/ent_repository_backlog.go:46`).
- Mitigations: run flow queries on a **separate read-only connection** (`file:...?mode=ro`, WAL permits concurrent readers with a writer; no `SetMaxOpenConns(1)` on that pool, but cap at 2-3) — or keep queries tiny/bounded on the shared connection and measure. Do not run `PRAGMA wal_checkpoint`/`VACUUM`/ANALYZE from the handler. A long read txn on WAL pins the WAL and blocks checkpoint progress (WAL file growth) — set a context timeout and use short, single-statement reads.
- Measured query cost (VERIFIED): count with `created_at >= '2026-10-06'` returned 10,137 in 0.19s total on 258k rows, but `explain query plan ... where created_at>=... group by to_status` shows `SCAN backlog_status_events` + temp B-tree: the only index is `(item_id, created_at)` (`backlog_status_event.go:47-51`), so time-window-only filters do a full scan. At 260k rows this is ~tens of ms, but grows linearly and thrash adds ~thousands/day. Fix options: add `index.Fields("created_at")` (additive; but creating an index on 260k rows under the live single connection blocks writers for the build; test on a copy first, verify via EXPLAIN on the real-size DB — requirements.md:84) or scope scans by item set (use item_id-leading index after selecting items in window).
- Excluding thrash rows in SQL: filter on `note` text (`NOT LIKE 'dequeued:%'`) is a scan; prefer a rollup/materialized episode table or compute in Go from a per-item ordered stream (index-friendly via `(item_id, created_at)`). Note that 238k thrash rows are mostly concentrated in 2 items; per-item streaming with early collapse is cheap if you skip those two items' raw rows via GROUP BY in SQL (`count(*)`, `min/max(created_at)` over runs) rather than loading them.
- Cache staleness: if a rollup/cached summary is added, key by window and invalidate/expire (TTL) — and always return `as_of`. Existing precedent: stuck-state pitfalls research flagged derived state going stale (project_plans/backlog-stuck-item-visibility/research/pitfalls.md §1). Rollup tables written by the live service add write load; prefer compute-on-read with a short TTL cache for the 1s SLO.
- Test DBs: tests that call `NewEntRepository` run `client.Schema.Create` serialized by `EntSchemaCreateMu` (`ent_repository.go:178-185`); use the in-memory DB isolation guidance in `docs/explanation/test-io-storage-isolation.md` and the deterministic-fast-tests skill; don't seed 260k rows in unit tests (seed a few hundred with explicit thrash runs).

## 5. RPC / MCP layer

- **N+1:** per-item drill-downs implemented as `GetBacklogItem` per row (or ent `.QueryStatusEvents()` per item) will issue ~160 queries over one serialized connection. Fetch events/verdicts in bulk with `item_id IN (...)` or one grouped SQL, then assemble in Go. With the single connection each extra round trip also queues behind writers.
- **MCP response size:** existing precedent caps `list_backlog_items` at default limit 10, max 50, offset/hasMore (`server/mcp/tools_backlog.go:217-231`, `:919-947`; description `:2884` "default limit is 10 to avoid filling LLM context"). New tools must follow this: return aggregates + top-N offenders (default ≤10) with `truncated`/`has_more`, never raw per-event lists; per-item timelines return collapsed episodes only and cap (e.g. 50) with a hint to page. Raw 258k events or a naive timeline for a thrash item (87k events/item) would blow context; the existing long-message guard precedent is `maxPostBacklogUpdateMessageLen`/500-char truncation (`tools_backlog.go:2123-2125`). Include an `estimated`/`partial` flag and `as_of` (requirements.md:81).
- MCP handlers are tested via `server/mcp/tools_backlog_test.go` (requirements.md:37); the live MCP endpoint was unreachable in the planning session (requirements.md:76), so verify via unit tests, not the live server.
- Free-form `note` strings returned to an LLM consumer are untrusted text (agents write them); sanitize/truncate to avoid prompt injection into the improvement-loop session. INFERRED.

## 7. Lessons from prior backlog-subsystem work

- **Thrash is a known recurring failure**: `project_plans/backlog-session-thrashing/requirements.md:16-52` (duplicate concurrent sessions per item + turn-budget exhaustion; WIP checks `countLiveBacklogWorkSessions` possibly bypassed). The flow-obs thrash (WIP-slot dequeue/spawn-fail flips, requirements.md:11) is plausibly the same family; surface it as an anomaly and cross-link rather than fix.
- **Check-then-act status transitions are non-atomic** (`session/ent_repository_backlog.go:516`, per stuck-item-visibility pitfalls §1): events written around transitions can be out of order or missing; do not assume every status change has exactly one event and do not assume event `to_status` equals the item's current status — reconcile last event vs `backlog_items.status` and flag mismatches.
- **Notify-once maps reset on restart** and durable `backlog_stuck_states` was introduced to fix that (stuck pitfalls §3). `backlog_stuck_states` is therefore historical-with-resolution, not a clean event log (reasons overlap: `multiple_reasons` 90; sum of reasons > distinct items). Count distinct items, not rows; treat `multiple_reasons` as its own bucket instead of double counting.
- **Reuse existing capture; no parallel store** (requirements.md:68; `analytics.db` `stage_transitions` also exists in the workspace dir). Two sources of truth for dwell (`backlog_status_events` vs `stage_transitions`) will disagree (different clocks, different thrash handling); pick one primary, cross-check the other in a test/data-quality metric.
- **Triad/plan review does not converge** (memory `feedback_triad_review_does_not_converge.md`): cap review loops; spend effort on the diff.
- **Prefer deterministic tests** (memory `feedback_deterministic_fast_tests.md`): inject a clock into the aggregator; never `time.Now()` in window logic (windows like "last 30 days" make tests flaky and cause the before/after window math to drift between calls).
- **Audit all call sites on shared gating** (memory `feedback_audit_all_call_sites_on_shared_gating.md`): if a new Flow tab/route is gated by a prop/flag, check every render site (Board, Analytics, nav).
