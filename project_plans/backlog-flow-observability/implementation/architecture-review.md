## Verified against origin/main (what holds)

- `session/flow` can stay ent-free and proto-free. `session/domain` has no internal imports (pure), `session/` itself imports no proto (`session/backlog_lifecycle.go:28` says so explicitly), and sub-packages such as `session/search` already import `session` while `session` does not import them. Import direction `server/{services,mcp}` -> `session/flow` <- `session` (reader implements `flow.Reader`) -> `session/domain` is acyclic provided `flow` never imports `session`. The plan's own use of `session.SanitizeForAgentContext` (`session/backlog_context.go:17`) is only in the reader/adapters, never in `flow`, which is correct.
- `storage.GetEntClient()` exists (`session/storage.go:312`), so `session.NewEntFlowReader(storage.GetEntClient())` is constructible in `server/dependencies.go` with no new plumbing.
- Seam disposition matches ADR-001. `server/mcp/server.go` is small (233 lines), `registerStuckReportTools` collision claim is consistent with ADR-001.
- `NewCore` has 10 params on main; 1 non-test call site inside `server/mcp/server.go:137` (via `NewHTTPHandler`) and `:178` (via `RunStdio`), plus 7 test call sites. ADR-001's "about 8 tests" is right.

## Blockers

- [ ] **Tech Debt Disposition table, Stories 5.1.2 / 3.1.3 / 3.2.3** — The table omits three hotspots the plan edits: `session/ent_repository_backlog.go` (3,299 lines, 39 commits/90d on origin/main; holds `MarkStuck` at :2332 and `ResolveStuck` at :2403, the Story 5.1.2 hook points), `server/dependencies.go` (2,229 lines, 66 commits/90d) and `server/server.go` (2,271 lines, 89 commits/90d), both edited by Stories 3.1.3 and 3.2.3. Story 5.1.2 also leaves the edit location vague ("the existing mark/resolve file located in Story 0.1.1"); it is `session/ent_repository_backlog.go` and the `Storage.MarkStuck`/`ResolveStuck` wrappers at `session/storage.go:1378/:1384` (1,876 lines, 57 commits/90d). Lens 4 item 12: a known hotspot with no disposition row is a blocker. **Remediation**: add rows for these four files (disposition "Isolate via seam": the episode logic lives in a new `session/ent_repository_stuck_episode.go` with a single exported helper; each hot file gains only the call or one wiring line), name the exact hook functions in Story 5.1.2, and state which layer the hook sits in (see next blocker).

- [ ] **Story 5.1.2 (stuck-episode writer) vs ADR-003** — The acceptance criteria require "already-open episode, `MarkStuck` again -> no new row" and "close the latest open episode only". Implemented as stated that is read-then-write (`SELECT open episode; INSERT if none`). But `EntRepository.MarkStuck` (`session/ent_repository_backlog.go:2325-2332` doc comment) is deliberately a single upsert so that "row-dedup itself — the concurrency-sensitive part" has no read-then-write window. Two concurrent marks (reconcile tick plus PR poller, both real callers) would insert duplicate open episodes and inflate stuck counts. The plan only says "check the single-connection/tx re-entrancy warning". **Remediation**: derive the episode transition from `MarkStuck`'s own result (open a new episode only when the upsert created the row or the conditional reopen UPDATE reported a reopen; `ResolveStuck` already returns `n > 0`), and back it with a partial unique index on `(item_id, reason) WHERE resolved_at IS NULL` (ent `index.Annotation`) so a duplicate is a constraint error that the best-effort helper swallows. Add a concurrent double-mark test to the story. Decide whether the helper runs inside the same tx as the upsert (atomic) or best-effort after it (drift possible, documented); the plan currently asserts best-effort without addressing drift between `backlog_stuck_states` and episodes.

## Concerns

- [ ] **No enforcement of "flow must not import ent/session/server" (Story 1.1.1, 6.1.3)** — The boundary is only prose. `.golangci.yml` on main has `depguard` rules (`no_server_in_core`, a strict allow-list for `pkg/threatscan`), so the mechanism exists. Add a task in Story 1.1.1 for a `depguard` strict allow-list on `**/session/flow/**`: `$gostd`, `session/domain`, `golang.org/x/sync/singleflight`, testify for tests. Use the bare `**/X/**` glob form the file's own comment prescribes. Without it the next contributor adds `session.SanitizeForAgentContext` into `flow` and the cycle only surfaces at compile time.

- [ ] **Duplicate status type; funnel hard-codes a closed stage list (Glossary `Status`, Story 1.2.2, 4.2.1)** — On main `domain.BacklogStatus` is an open type (custom workflow stages are valid values, `session/domain/backlog.go:52-60`) and has 9 built-ins including `refining`; the plan glossary lists 8 and says `flow` "has its own `Status` string type to avoid importing ent". `session/domain` is ent-free, so no new type is needed. Import `domain.BacklogStatus`/`domain.StuckReason`. Make funnel stage order data (default order slice, unknown/custom stages go to an `other` bucket with a count) rather than the fixed `idea>ready>in_progress>review>pr_pending>done`; otherwise `refining` and any configured stage vanish or panic an exhaustive switch.

- [ ] **`Reader` is a 7-method fat interface (Story 1.4.2a, Glossary `Reader`)** — Events, last-event-before, verdicts, progress notes, request-review events, stuck rows, items. This violates ISP and makes every fake implement all seven. Section-level error isolation (an AC) already implies independent sources. Split into role interfaces (`EventSource`, `VerdictSource`, `StuckSource`, `ItemSource`), have `Aggregator` take a small struct of them, and let `EntFlowReader` implement all. Fakes then stay one method each.

- [ ] **Two parallel DTO mappings for one `FlowSummary` (Stories 3.1.2, 3.2.1, 3.2.3)** — The glossary promises "one proto/Go shape for UI and MCP", but the plan builds a proto mapper in `server/services/backlog_flow_mapper.go` and a separate JSON path in `server/mcp/tools_backlog_flow.go`, then patches the risk with a parity test that needs "field-name normalization". `server/mcp/tools_backlog.go` already imports `sessionv1` and calls the service in-process (`h.backlogSvc.ListBacklogItems(...)`, :1076). Make the MCP handlers call the `BacklogFlowService` handler (or the exported mapper) and `protojson`-marshal the response. Parity then holds by construction and the normalization step disappears; the MCP-only parts are paging/clamping and `SanitizeForAgentContext`.

- [ ] **Aggregator wiring is only half specified (Story 3.2.3, ADR-001)** — Adding the parameter to `NewCore` also changes `NewHTTPHandler` and `RunStdio` signatures (`server/mcp/server.go:120-180`), which the story does not list. "One cache shared by both transports" requires the RPC service and the HTTP MCP core to receive the same `*flow.Aggregator` instance from `server/dependencies.go`; the plan never says where it is constructed. The stdio no-daemon fallback (`RunStdio`, `:178`) has no daemon deps, and research said flow tools should still work there while the plan says nil -> `ErrUnavailable`. State: (a) construction site in `dependencies.go`, one instance, (b) fallback builds its own from `storage` or deliberately returns `ErrUnavailable` (pick one and test it). Consider an options struct or setter rather than an 11th positional argument to a function already at 10.

- [ ] **Sanitization placed in the reader (Story 2.1.4)** — `EntFlowReader.Items` passes titles through `session.SanitizeForAgentContext` and truncates. That is an agent-output concern; applying it in the data layer also alters titles the web UI shows, and Story 3.2.1 sanitizes again. Return raw titles from the reader and sanitize once, in the MCP adapter.

- [ ] **`Span` allows illegal states (Glossary `Span`/`SpanKind`)** — One struct with `Kind` plus `Count, FirstAt, LastAt, NetStatus, Cause` lets a `Real` span carry a `Cause`/`Count` and a `Thrash` span omit them. Use a sealed interface (`RealSpan`, `ThrashSpan`) or at least constructor functions `NewRealSpan`/`NewThrashSpan`; the plan already commits to exhaustive switches, which `exhaustive` (enabled in `.golangci.yml`) only enforces for enums, not for a struct's optional fields.

- [ ] **Deviation from build-vs-buy not recorded (Pattern Decisions, Story 2.1.2)** — `research/build-vs-buy.md:54,63` recommends SQL-native counts/group-bys via ent `GroupBy().Aggregate()` plus one small Go collapse function. The plan loads all window events into Go and computes funnel, FPY, and dwell there. That is defensible at about 10k rows (ADR-004) but it is a deliberate departure; add one line to the Pattern Decisions table or ADR-004 saying so and tying it to the revisit trigger, so a reviewer checking consistency does not flag it.

- [ ] **Cache key and bound (Story 1.4.3)** — Key is the canonical `FlowQuery`, which includes arbitrary `Config` overrides and item filters coming from MCP args. An agent looping over thresholds grows the map without limit. Cap entries (small LRU, for example 64) and evict on TTL; add a test.

## Nitpicks

- Glossary says an episode needs "at least `ThrashMinFlips` events"; ADR-002 says "flips (counting events)" and also defines runs of `FlipPair`s. Use one unit ("events") in both, since the boundary tests (5 vs 6) depend on it.
- Story 5.2.2 lists `session/flow_marker.go` / `ent_repository_flow_markers.go` as files although Story 5.2.1 is the spike that decides whether a new store is needed at all. List them as "if the spike selects a new store".
- `DrillKey` is a "closed enum" of strings in Go; state that the completeness test is what closes it.
- The effort table is not an architecture matter, but the 10.2M CU Large-band total versus the requirements' Medium band is already acknowledged in the plan; no action.
- Stories 1.2.1/1.4.2 put `Seq` (rowid) into `Event`; note that this leaks a storage detail into the domain type. Acceptable if documented as "stable tiebreak".

### Blocker 2 (stuck-episode writer) - RESOLVED, with two concerns
Verified on `origin/main`:
- `MarkStuck` (`session/ent_repository_backlog.go:2332`) opens a tx at ~2362, does the upsert, then a conditional reopen UPDATE, then commits; `ResolveStuck` (:2403) is a single non-tx UPDATE returning `n > 0`. The plan's description matches.
- Writer pool is `SetMaxOpenConns(1)` (`session/ent_repository.go:203`; `session/dbpool/open.go:59`) and `recordStatusEvent` documents the self-deadlock for non-tx writes (`ent_repository_backlog.go:60-66`). The plan's tx-only helpers, `markStuckTx`, and the 1-connection-pool test address exactly this.
- Race safety: with one writer connection, in-process marks already serialize, so the 8-goroutine test passes by construction in-process; the partial unique index is the real backstop for multi-process writers and for any future pool change. Same-tx atomicity removes the stuck-state/episode drift window the first review flagged. Reconcile+poller double-mark yields one open episode. Reopen path is correct: `ResolveStuck` closes the episode, so a later `MarkStuck` inserts a new open one.
- ent support: `entsql.IndexWhere` exists in `entgo.io/ent@v0.14.5` (`dialect/entsql/annotation.go:779`; go.mod pins v0.14.5), and the stuck-state schema comment confirms the existing unique index is plain, so a partial unique index on the new table is expressible. The hand-written fallback in Story 5.1.1 is adequate. Note: the plan still lists this as UNVERIFIED in Task 0.1.1a; it can be marked verified for the annotation (SQLite predicate emission still wants one migration test, which Story 5.1.1's "second open row fails" AC already is).

New concerns:
- [ ] **"rows-affected == 1" is not observable through ent's `Create().OnConflict(DoNothing())`** (Story 5.1.2, ADR-003). `ent_repository_backlog.go:634-639` already shows the precedent: an ignored DoNothing insert surfaces as `sql.ErrNoRows` (and constraint errors), not a count. Reword the AC: `EpisodeOpened = (err == nil)`; treat `sql.ErrNoRows` and `ent.IsConstraintError` as "already open"; any other error is the logged non-fatal case. Do not require the `sql/execquery` feature (the generate command is fixed by CLAUDE.md). Task 5.1.2a already offers this fallback; promote it to the primary path.
- [ ] **Swallowing a non-constraint error inside the tx** (Story 5.1.2 "Never blocks the transition"). On SQLite a failed statement does not abort the tx, so continuing works, but the same code on a driver where it does (Postgres) would poison the commit. Add a one-line note, or use a savepoint-free guard: skip the episode write if the table is absent only at startup, not per statement. Low risk today (SQLite only).
