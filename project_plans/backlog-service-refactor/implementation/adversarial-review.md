# Adversarial Review: backlog-service-refactor
**Date**: 2026-07-09
**Verdict**: BLOCKED

---

## Blockers

- [x] **Board view data audit not done — `HasLinkedSession + TriageRunning` is not sufficient** — `mapBacklogItem` in `web-app/src/lib/hooks/useBacklogService.ts` (lines 211–281) derives `triageStatus`, `gateVerdict`, `triageResult`, and `linkedSessions` all from `p.itemSessions` (proto field 18: `repeated ItemSession`). It checks `triageSession.endedAt`, `triageSession.triageResult?.summary`, `mostRecentReviewSession.reviewVerdict.overallOutcome`, and `mostRecentReviewSession.reviewVerdict.perCriterion`. None of these fields survive the compression to two booleans. When `backlogItemSummaryToProto` receives only `HasLinkedSession bool` and `TriageRunning bool`, it cannot reconstruct `triageResult.summary` (needed to distinguish "completed" from "failed") or any `reviewVerdict` (needed for gate verdict display). Board cards would show `triageStatus = undefined` instead of "running" or "completed", and all gateVerdict UI would vanish. The plan's risk table names this risk but its mitigation ("MUST include HasLinkedSession + TriageRunning") fails to audit what the hook actually needs. **Required action**: Audit every field read from `p.itemSessions` in `mapBacklogItem` and `mapItemSession`; either add those fields to `BacklogItemSummary` (expanding the second query) or document which board-card rendering regresses and accept that regression explicitly. ✅ **RESOLVED** (re-review 2026-07-09): Plan now uses `ItemSessions []ItemSessionSummary` (booleans explicitly rejected in Pattern Decisions). Story 5.1.2 second-phase query selects `session_role, status, triage_result_summary, overall_outcome`. Story 5.1.1 struct comment names Role/Status/TriageResultSummary/OverallOutcome. Story 5.1.3 AC #5 specifies `mapBacklogItem` reads `item_sessions_summary` to derive `triageStatus`, `gateVerdict`, and `linkedSessions`. _Residual minor gap_: `ItemSessionSummary` struct definition in Story 4.1.1 omits `Status` and `OverallOutcome` fields while Story 5.1.2 query and Story 5.1.1 comment assume they exist — spec inconsistency that will surface at implementation time but does not revive the original blocker.

- [x] **Proto field mapping for derived booleans is unresolved, not "OR"** — The proto `BacklogItem` message has `repeated ItemSession item_sessions` (field 18) and no `has_linked_session` or `triage_status` fields. Story 5.1.3 AC #3 says "`HasLinkedSession` maps to the proto's `item_sessions` count field OR to a dedicated bool (whichever the proto supports)" — the OR signals the implementer doesn't know which works. Adding a dedicated bool proto field requires a proto change (out of scope per requirements). Using `item_sessions` as the carrier requires `backlogItemSummaryToProto` to synthesize `ItemSession` entries from booleans alone. That synthesized data cannot carry `endedAt` timestamps, `triageResult.summary`, or `reviewVerdict` — which `mapBacklogItem` requires. This is not an implementation detail; it is a design gap that must be resolved before any P4 code is written. **Required action**: Run `go doc github.com/tstapler/stapler-squad/proto/session/v1 BacklogItem` to enumerate proto fields; decide before implementation starts whether P4 adds proto fields (requires updating constraints) or carries enough session data in `BacklogItemSummary` to reconstruct the hook's derivations. ✅ **RESOLVED** (re-review 2026-07-09): Story 5.1.3 AC #2 defines a new `ItemSessionSummaryProto` message in `proto/session/v1/types.proto` with fields `session_id`, `role`, `status`, `triage_result_summary`, `overall_outcome`. AC #3 adds `repeated ItemSessionSummaryProto item_sessions_summary` to `BacklogItem` proto (additive, backward-compatible; existing `item_sessions` retained for `GetBacklogItem`). Task 2 requires `make proto-gen` before any Go or TS changes. AC #5 and Task 5 explicitly update `mapBacklogItem` to read `itemSessionsSummary` for the list view derivation path. The "OR" language is gone; the design is fully specified.

## Concerns

- [ ] **Lint guard CI suppression mechanism is underspecified and the depguard mitigation is wrong** — Story 1.1.1 AC #4 says "CI is still green because violations are pre-existing." Adding the `forbidigo` pattern for `ent\.IsNotFound` without a matching `exclusions.rules` entry for `server/services/backlog_service.go` (text: `ent\.IsNotFound`) will immediately produce 14 violations and break CI (golangci-lint exits 1 on any violation). The existing pattern for this codebase is to add a file-scoped exclusion rule (see the `LoadInstances` entries at lines 129–131 of `.golangci.yml`) that gets removed when the violation is cleaned up. The plan doesn't say to add this temporary exclusion. For `depguard`, Story 1.1.2 says "Add existing violations to the `allowed-modules` list temporarily" — `depguard` does not have an `allowed-modules` mechanism for per-file exception; the correct approach is a `files:` exclusion or `nolint:depguard` on the import line. **Required action**: Specify the exact `.golangci.yml` exclusion entry to add in Phase 1 (and remove in P6); drop the `allowed-modules` language from Story 1.1.2.

- [ ] **`ReviewGateRunner.Run` signature becomes a build failure in P6, but P6 tasks don't cover it** — Story 3.2.1 AC #4 specifies `Run(ctx, item *ent.BacklogItem, is *ent.ItemSession, onPass func(...) error)`. After P6 (Story 4.1.3), `session/backlog_lifecycle.go` must use `ItemSessionSummary` for all ItemSession references. But `backlog_lifecycle.go` calls `l.runner.Run(ctx, item, is, l.pushAndCreatePR)` where `is` will be an `ItemSessionSummary` post-P6 — a type mismatch with `Run`'s `*ent.ItemSession` parameter. Story 4.1.3's task list does not mention updating `ReviewGateRunner.Run`'s signature. The `session/` package can use ent types directly, so the fix options are: keep `Run` taking `*ent.ItemSession` and have the lifecycle re-fetch via ent (extra query), or change `Run` to take `ItemSessionSummary` and have the runner look up the ent entity internally. Neither path is specified. **Required action**: Add a task to P6/Story 4.1.3 to resolve the `ReviewGateRunner.Run` signature against `ItemSessionSummary`, including whether this adds a DB fetch inside `Run`.

- [ ] **Two-query approach for `ListBacklogItemSummaries` lacks a pagination-scope constraint** — Story 5.1.2 specifies a two-phase query: (1) scalar field scan, (2) separate query for session flags. The second query must be `WHERE backlog_item_id IN (<IDs from query 1's page>)` — not `WHERE backlog_item_id IN (<all backlog item IDs>)`. This constraint is not stated, so an implementer could fetch session flags for all items in the table rather than just the current page, degrading to O(all sessions) per list call and producing cross-page pollution. The existing integration test (Story 5.1.2 AC #7) only checks 2 items and would not catch this. **Required action**: Add explicit language to Story 5.1.2 tasks that the IN-list for the second query is built from `ids` returned by query 1, and add a test fixture that inserts 50+ items with a filtered page of 10 and verifies the second query only touches the 10 visible items.

- [ ] **ent `Select().Scan()` into a custom `BacklogItemSummary` struct is assumed, not verified** — Story 5.1.2 AC #2 specifies `ent BacklogItemQuery.Select(fields...).Scan(ctx, &out)` where `out` is `[]BacklogItemSummary`. ent's `Scan` typically targets generated entity types or maps; scanning into an arbitrary custom Go struct may require `sqlgraph`-level raw SQL or `ent`'s `As()` predicate, neither of which is mentioned. Open Question #1 is simultaneously marked unresolved and pre-answered ("Yes — run two queries"). If `Select().Scan()` into custom structs is not supported by the generated ent code for this schema, the entire P4 implementation approach requires raw SQL. **Required action**: Before writing any P4 code, run a spike: write `ListBacklogItemSummaries` with a real `Select().Scan()` call against the test DB and confirm it compiles and scans correctly into `BacklogItemSummary`.

- [ ] **Parallel P1+P3 branches have no rebase coordination protocol** — The plan marks P1 (file split in `server/services/`) and P3 (ReviewGateRunner in `session/`) as parallel. They touch different files, so there are no structural merge conflicts. However, once P1 lands and the split files exist, the P3 PR's integration tests (which test `BacklogLifecycleListener` via `TestBacklogIntegration_IT002` and `IT006`) may fail if those tests import helpers from `backlog_service.go` that have moved. The plan says nothing about how to keep the second branch green after the first merges. **Required action**: State explicitly that the P3 branch must be rebased on top of P1 before PR review, or add a note that the integration tests in P3 do not depend on the split files.

## Minors

- `itemSessionToProto` appears twice in Story 3.1.1's private helpers list — likely a copy-paste error; one entry is probably `statusEventToProto`.

- Story 3.2.1 AC #7 says "cognitive complexity drops to < 40 (from 35 — already close)." If `backlog_lifecycle.go`'s current cognitive complexity is 35, it already passes the <40 target without P3. The requirement's 87 peak is in `submitTriageResult` in `tools_backlog.go`, which is addressed by P2, not P3. Reword the AC to describe what P3 actually achieves (function-level complexity of `spawnReviewGate` extracted into a testable type).

- Requirements number items P1–P6 but the plan resequences them as Phases 1–6 with a different mapping (plan's Phase 4 = req's P6, plan's Phase 5 = req's P4, plan's Phase 6 = req's P5). Anyone cross-referencing the requirements against the plan will misread dependencies. Consider adding a mapping table at the top of the plan.

- The depguard rule `no_ent_in_services` covers `**/server/services/**/*.go`. After P6, `session/backlog_lifecycle.go` is also supposed to have zero ent ItemSession references (Story 4.1.3 AC #2), but that file is not covered by the depguard rule. There is no automated enforcement of this AC — it relies on manual grep. Add a grep check to CI or note this as a manual verification step.

- Story 2.1.2 adds a fuzz test for `MergeAcCriteria`. The requirements specify "≥3 table-driven unit tests" only. Fuzz testing is beyond scope and adds CI time without a requirement mandate. Low risk, but note it.

- The ent boundary cleanup covers only `ent.IsNotFound` → `session.ErrNotFound`. Other ent error types (`*ent.ConstraintError`, `*ent.ValidationError`) may still be type-asserted in `server/services/` after P6. The `forbidigo` rule doesn't cover these. If callers do `var cerr *ent.ConstraintError; errors.As(err, &cerr)`, they pull in an ent type without importing `session/ent` directly via a named import — the depguard rule catches the import, but if the type is reached via a returned error, the depguard rule may not apply. Acknowledge this as a known residual coupling.
