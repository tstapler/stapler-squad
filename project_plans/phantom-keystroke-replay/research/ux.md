# UX Research: Phantom Repeated Keystroke on Session Reconnect

Backlog item `04089969-0f19-499c-be34-2e8bcfc4f13e`. Focus: how to surface "input was dropped because the connection dropped/superseded" without repeating the phantom-replay failure, per Goal 3 / AC3.

## 1. Comparable UX patterns — how other tools signal dropped vs. buffered input

| Tool | Model | Signal to user |
|---|---|---|
| **mosh** | Input is queued client-side and speculatively echoed (predictive local echo) even while the network is down; once reconnected, the *real* queued keystrokes are replayed to the remote in order. Design intent is "never lose a keystroke," backed by a UDP session-continuity protocol that makes replay-on-reconnect provably safe (sequence numbers, single logical connection). | A dim/underlined predictive-echo overlay tells the user "this hasn't been confirmed by the far end yet." No explicit "dropped" state exists because mosh's whole premise is that nothing is ever dropped — a fundamentally different reliability model than a WebSocket-based tmux control-mode bridge that can flap and get superseded by a fresh session. |
| **tmux itself** (local, no network) | N/A — tmux has no concept of a disconconnected client dropping input; a detached client simply isn't attached, so there's no keystroke capture to begin with. Not a direct analog but establishes that "detached ≠ input capture" is the expected mental model even inside the terminal multiplexer this project wraps. |
| **iTerm2 / Windows Terminal (SSH)** | Input during a network blip is buffered by the OS TCP stack, invisibly, at a layer below the terminal application. The terminal app itself has no "your keystrokes are queued" indicator because TCP already guarantees ordered, at-least-once delivery over the *same logical connection* — there's no scenario (barring a full reconnect with a new session) where queued input could be silently discarded or replayed against a stale context. |
| **VS Code Remote - SSH / Remote Tunnels** | Shows a status-bar bolt/spinner ("Reconnecting...") and, distinctly, a modal/toast when the remote connection is lost long enough to require a full session teardown ("Attempting to reconnect" → eventually "Could not reconnect, click to reopen"). Input typed into a disconnected remote terminal is rejected by xterm.js at the UI layer (the pty is gone) rather than queued — VS Code does **not** attempt to buffer-and-replay keystrokes across a dead remote session. |
| **ttyd / gotty** | Bare WebSocket bridges to a pty. On socket close, the xterm.js instance simply stops forwarding — there is no client-side input queue at all in the default implementations, so nothing can be replayed later. Reconnect (if implemented by the wrapper) starts a fresh WebSocket with no memory of buffered input. |
| **Wetty** | Similar to ttyd — socket.io reconnect logic exists, but keystrokes typed while `disconnected` are not queued; the input box (xterm) is simply not wired to anything until `connect` fires again. |
| **Upterm** | Peer-to-peer SSH-relay; same TCP-layer invisibility as iTerm2/Windows Terminal — no application-level "dropped" indicator because the reliable transport is below the UI. |

**Synthesis**: There is **no standard convention** for "explicitly tell the user their terminal input was discarded," because every mainstream tool either (a) guarantees delivery within one logical connection via a reliable transport (SSH/TCP, mosh's UDP protocol), so buffering is invisible and safe, or (b) has no client-side input queue at all, so there's nothing to lose — input typed while disconnected simply never left the browser. **This codebase is in neither camp**: it has a client-side `MessageQueue` (`web-app/src/lib/terminal/MessageQueue.ts`) that can hold pushed input across a `connect()` call that swaps in a *new* `MessageQueue` instance (`web-app/src/lib/hooks/useTerminalStream.ts:176`), which is exactly the hybrid state (queued, but the queue can be superseded/orphaned) that causes silent replay-into-wrong-context bugs. Because no prior art solves this exact shape of problem, the "visible drop-and-signal badge" the requirements call for is a **novel-but-justified** pattern here, not a deviation from convention.

## 2. User mental model: queued (SSH-like) vs. explicit signal

Developers' baseline mental model, trained by SSH/mosh/tmux, is "my terminal is reliable — either my keystrokes land, or the connection visibly drops and I know to retype." They do **not** expect a web terminal to have a semi-durable client-side queue that can silently misfire input against a different (reconnected) shell state than the one they were looking at when they typed.

Given the bug specifically produced **phantom repeated delivery** — the worse of the two possible wrong outcomes — the failure-mode ranking is:

1. **Best**: input delivered correctly, once, to the shell the user is currently looking at.
2. **Acceptable**: input silently dropped when delivery can't be guaranteed correct (matches the SSH/tmux mental model of "nothing happened, I'll notice from the missing echo and retype").
3. **Unacceptable**: input delivered anyway, into a context the user didn't intend (replayed after reconnect, replayed against the wrong shell, or replayed multiple times) — this is what caused the described incident (Claude Code received `1` repeatedly with no prompt to justify it, and could not proceed).

**Argument for visible drop over silent drop specifically in this codebase**: a *pure* silent drop would already be the safer choice over phantom replay, and matches the SSH mental model. But this project's failure mode isn't hypothetical — it already happened once in a way invisible to the user (no error, no explanation, agent just seemed "stuck"), which is what makes it a trust-destroying bug rather than a merely annoying one. The requirement's insistence on an *explicit, visible+audible* signal (not just silent-safe-drop) is the right call specifically because:
- The user had no local echo to notice the discrepancy (unlike mosh's predictive echo, this transport doesn't render unconfirmed input distinctly), so a silent drop here would look identical to "my keystroke just didn't register" — a common, dismissible glitch a user might retry past without investigating.
- A long-running agent session (the core product here) can silently go off the rails from a single dropped keystroke (e.g., dropping part of a slash command or an approval `y`/`n`) in a way an interactive shell session usually can't — so the cost of the user *not* noticing a drop is higher than in a normal terminal.
- Making the drop loud converts "did my keystroke land?" from a recurring background anxiety (function job: know if input landed) into a rare, explained, and momentarily interruptive event — which is a better trade for the emotional job (trust) than a always-silent, always-uncertain baseline.

So: **silent drop is the correct fallback semantics (never replay), but the drop must be visibly/audibly announced** — the requirement's exact framing — because this is the one class of terminal tool where users have no other way to detect a drop happened.

## 3. Accessibility: ARIA live-region pattern

**Recommendation: `role="alert"` (implicit `aria-live="assertive"`, implicit `aria-atomic="true"`)** for the drop notice itself, matching the existing convention in this codebase for time-sensitive user-facing events:

- `web-app/src/components/ui/NotificationToast.tsx:156-157` already uses `role="alert"` + `aria-live={type === "approval_needed" ? "assertive" : "polite"}` — i.e., this project's convention is: **assertive for things that block or change what the user needs to do right now**, polite for passive informational updates. A dropped-keystroke event is squarely in the "assertive" bucket — it just changed what the user needs to do (retype), and delaying the announcement until the screen reader finishes its current polite queue would defeat the purpose (the user could keep typing into a dead session for several more seconds).
- Contrast with `web-app/src/components/layout/ConnectionIndicator.tsx:44` (`aria-live="polite"`) and `web-app/src/components/sessions/TerminalOutput.tsx:1537` (`role="status"`, implicit polite) — both used for continuous/ambient state (connection dot, resizing spinner), not one-shot events. Do **not** reuse `role="status"`/polite for the drop signal; it's a different category of information (a discrete, actionable, time-critical event vs. ambient status).

**Interruption caveat** (the "not so aggressive it interrupts inappropriately" concern in the prompt): `aria-live="assertive"` interrupts whatever the screen reader is currently announcing. This is intentional here — a stale announcement (e.g., "Live — session data is up to date") being cut off in favor of "3 keystrokes were dropped" is the correct trade, because the dropped-input event is strictly higher priority for the user's next action. To avoid *over*-firing:
- Coalesce a burst of drops (e.g., a fast reconnect flap causing 5 keystrokes to be discarded in under a second) into a **single** announcement per "drop episode," not one announcement per dropped character — this needs debouncing at the source (e.g., 300–500ms after the last drop before flushing the announcement), otherwise assertive spam becomes its own accessibility problem (screen reader announcement thrash).
- Keep the live region's DOM node stable and update its text content (matching the existing `LiveRegion` component pattern at `web-app/src/components/ui/LiveRegion.tsx`, which already clears the message after ~1s via `useLiveRegion()`'s `announce()`) rather than mounting/unmounting a new alert element each time, which is more reliable across screen readers (NVDA/JAWS/VoiceOver) than relying on mount-triggered detection.

**Existing systems to extend** (found via search of `web-app/src/components/`):
- `web-app/src/components/ui/LiveRegion.tsx` — a generic `<div role="status" aria-live={politeness}>` + `useLiveRegion()` hook (message + auto-clear-after-1s `announce()`). This can be reused directly for the audible half of the signal by instantiating it with `politeness="assertive"` (currently it defaults to `"polite"` and callers must opt in) — or, better, add a dedicated `role="alert"` variant/prop since `role="status"` and `role="assertive"` live-region semantics are subtly different from `role="alert"` in some AT (JAWS treats `role="alert"` specially even when `aria-live` isn't explicitly assertive).
- `web-app/src/components/ui/NotificationToast.tsx` + `lib/notification-policy.ts` — the full toast system (entrance animation, auto-close, auto-minimize, dedup window) is overkill for this signal (it's session-corner-of-screen, multi-notification-stack UI, not terminal-local), but its **timing policy conventions** (`toastAutoCloseMs`, `toastAutoMinimizeMs` in `web-app/src/lib/notification-policy.ts`) are the right reference values to mirror rather than invent new ones from scratch (see §4).
- `web-app/src/components/sessions/XtermTerminal.tsx:649-654` — the existing `copiedToast` (a floating toast rendered via `createPortal(..., document.body)`, positioned by ref/DOM mutation near the terminal, `aria-live="polite"`, `display: none` by default) is the closest existing **terminal-local, transient, non-toast-stack** precedent for exactly this kind of badge — recommend building the drop-and-signal badge as a sibling to this pattern (portal-rendered, positioned relative to the terminal container) rather than routing it through the global `NotificationToast` stack, since it's about *this terminal instance*, not a cross-session notification.
- `web-app/src/components/sessions/TerminalOutput.tsx:1516-1542` — `loadingOverlay` / `unavailableOverlay` / `resizingOverlay`, all rendered as absolutely-positioned overlays inside `styles.terminal` with `role="status"`/`aria-label`, is the existing convention for terminal-state overlays. The resizingOverlay's `pointer-events: none` styling (mentioned in its adjacent comment) is worth mirroring so the badge never blocks continued typing.

## 4. Badge UX design

**Placement**: Anchor the badge to the terminal's existing connection-status area, not as a new floating element in an arbitrary corner. Concretely: render it adjacent to/replacing the `ConnectionIndicator` (`web-app/src/components/layout/ConnectionIndicator.tsx`) region if that's visible in this view, **and** as a transient overlay inside the terminal container itself (matching `TerminalOutput.tsx`'s `unavailableOverlay`/`resizingOverlay` convention) so it's visible even if the connection-status chip is scrolled out of view or not rendered in this particular embedding of the terminal. The terminal is the surface the user is looking at when they type — the signal needs to appear there, not only in a header far away.

**Persistence / duration**: Model it as a **discrete event toast**, not a persistent state indicator (it is not describing "current connection state," which `ConnectionIndicator` already owns — it's describing "something just happened to input you already typed"). Auto-dismiss rather than requiring acknowledgment:
- Non-actionable, informational — there is nothing for the user to click to "resolve" a drop; the correct next action is just "retype," which they'll naturally do once they see their input isn't landing.
- Mirror this project's existing non-actionable toast timing (`toastAutoCloseMs` default 8000ms in `lib/notification-policy.ts`) rather than inventing a new duration — 8s is enough to read a short message like "3 keystrokes dropped — reconnecting" without lingering after the user has already resumed typing successfully.
- Do **not** use the `approval_needed`-style indefinite/actionable persistence (`ACTIONABLE_TOAST_STALE_MS`) — that pattern exists for things requiring a decision, and a dropped-input notice requires none.

**Count vs. generic notice**: Include a count when more than one keystroke was coalesced into a single drop episode (e.g., "3 keystrokes dropped while reconnecting"), falling back to a generic singular message for exactly one. Reasoning:
- A bare "input dropped" with no count under-communicates when a whole in-progress command/flag sequence was lost — the user needs enough information to know whether to retype one character or re-enter an entire command line.
- This requires the drop-detection logic (wherever the superseding-MessageQueue guard lives) to track a count of discarded `TerminalData` input events per "episode" (bounded by the debounce window from §3) rather than firing one alert per event, which also solves the assertive-spam problem from §3 in one mechanism.

**Auto-dismiss vs. acknowledgment**: Auto-dismiss (as above). Requiring a manual dismiss/acknowledgment click would elevate a routine (if regrettable) reconnect hiccup to the same UX weight as an approval-needed prompt, which overstates its severity and adds friction to a flow that's already been interrupted once by the reconnect itself.

## 5. Job-to-be-done framing

- **Functional job**: "Know whether my input landed or didn't" — today, this codebase's terminal gives no direct confirmation either way beyond the echo the shell itself produces, which is exactly why a silently-dropped (or worse, phantom-replayed) keystroke is invisible until its downstream effects appear (an agent stuck on a stray `1`, a partially-typed command executed early, etc.).
- **Emotional job**: "Trust this tool enough to leave a long-running agent session unattended." Stapler-squad's whole premise is running unattended/semi-attended agent sessions across reconnects (tmux + worktrees + web UI) — trust in "my input reaches the agent exactly once, correctly, or not at all" is foundational, not incidental, to that premise.
- **Why phantom-replay bugs erode trust disproportionately**: an explained failure (even an annoying one — "your keystrokes were dropped, please retype") is legible and recoverable — the user updates their model ("reconnects can eat input, I should watch for the badge") and moves on. A phantom, unexplained failure (agent silently fed garbage input with no on-screen justification) is not legible — the user's takeaway is "I can't tell when this tool is lying to me about what it did with my keystrokes," which generalizes into distrust of *all* interactions with the session, not just the reconnect path. That's why AC3's insistence on an explicit, visible+audible signal — even though it costs a brief interruption — is the right trade: a loud, honest "I dropped that" is strictly better for long-term trust than a quiet failure the user has to reverse-engineer from a confused agent transcript.
