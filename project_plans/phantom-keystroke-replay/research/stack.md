# Stack Research: Phantom Repeated Keystroke Replay

## 1. Client↔server terminal transport

- **ConnectRPC**: `@connectrpc/connect@^2.1.1` + `@connectrpc/connect-web@^2.1.1` (frontend, `web-app/package.json`); Go side uses `connectrpc.com/connect v1.19.0` (`go.mod`). Note: there's also a legacy `github.com/bufbuild/connect-go v1.10.0` still in `go.mod` — worth checking it isn't dual-wired into the same handler path (only the `connectrpc.com/connect` v1.19.0 import matters for the websocket handler under investigation).
- **Protobuf codegen**: `@bufbuild/protobuf@^2.11.0` / `@bufbuild/protoc-gen-es@^2.11.0` (TS), `google.golang.org/protobuf v1.36.10` + `github.com/bufbuild/buf v1.57.2` (Go/codegen). Standard `make generate-proto` regenerates both `session/gen/session/v1/*.go` and `web-app/src/gen/session/v1/*_pb.ts`.
- **Transport is NOT native ConnectRPC-over-WebSocket** — it's a custom shim. `web-app/src/lib/transport/websocket-transport.ts` (416 lines) implements a hand-rolled `Transport` (unary + streaming) over a raw `WebSocket`/envelope protocol (`protocol.ParseEnvelope` on the Go side, `EndStreamFlag`), not gRPC-Web or Connect's built-in streaming transports. This means none of ConnectRPC's built-in retry/backoff/cancellation semantics apply automatically — all reconnect/abort behavior is custom and lives in this file plus `useTerminalStream.ts`.
- Go backend terminal streaming is handled directly in `server/services/connectrpc_websocket.go` (`HandleWebSocket` → `streamTerminal` → `streamViaControlMode` or `streamViaTmuxCapturePane`), which speaks the same custom envelope protocol, not idiomatic Connect streaming handlers.

## 2. Client-side async producer/consumer + "close and replace" boundary

- **`web-app/src/lib/terminal/MessageQueue.ts`** — the outgoing-message queue passed into `client.streamTerminal(queue)`. It is a hand-rolled async-iterable queue (push → resolve-or-buffer, `close()` sets a `closed` flag and unblocks any pending `await` with a sentinel).
  - **Confirmed bug**: `close()` only unblocks a *pending* `await` — it does **not** clear `this.queue`. The iterator's loop condition is `while (!this.closed || this.queue.length > 0)`, so any message that was `push()`-ed onto the buffer *before* `close()` was called (i.e., buffered because nothing was awaiting yet) is still drained and yielded to the (soon-to-be-torn-down) stream consumer after `close()`. This is a direct mechanism for "input typed while disconnected/flapping gets sent anyway" — it's the leading root-cause candidate for goal #3 in requirements.md (drop, don't replay, queued input across a reconnect boundary).
  - Existing test file `MessageQueue.test.ts` only covers: ordering, unblocking a waiting iterator on `close()`, sentinel filtering, and "push after close is a no-op." **No test exists for "message queued before close() is still drained/leaks out" — this is exactly the gap requirements.md goal #4 calls out ("queued-message-drop-on-close interleaving").**
- **`web-app/src/lib/hooks/useTerminalStream.ts`** (420 lines) owns the `AbortController` / `MessageQueue` lifecycle:
  - `connect()` creates a **new** `AbortController` + `MessageQueue` each call, guarded only by `if (isConnectedRef.current || !sessionId) return;` — there is **no epoch/generation counter**. `isConnectedRef` only flips true once the *first* message of the new stream arrives (line ~214), so there's a window during CONNECTING/reconnect where `isConnectedRef.current` is `false` even though an old stream's async consumer loop (the `(async () => { for await (const msg of stream) {...} })()` IIFE at line 209) may still be running and mutating shared React state (`setIsConnected`, `setTerminalState`, calling `flowControl.handle*`) concurrently with a newly-started loop from a second `connect()` call.
  - `disconnect()` calls `messageQueueRef.current.close()` then races a 1s timeout against `abortControllerRef.current.abort()` — but does **not** null out or invalidate the *previous* stream's in-flight async iterator/IIFE by any generation token; it relies solely on the network-level abort to eventually throw inside `for await`.
  - **No existing epoch/generation-guard idiom is used anywhere in this hook or elsewhere in `web-app/src`** for "invalidate a stale async loop when a newer one starts" (grep for `epoch`/`generation` in `web-app/src` only turns up unrelated hits — rule-generation UI, path-completion generation counters for autocomplete debounce, migration/serialization version fields — none is the connection-generation pattern this bug needs). **This will need to be introduced net-new**, e.g., a `connectionEpochRef = useRef(0)` incremented in `connect()`, captured in a local `const myEpoch = ++connectionEpochRef.current` before the async IIFE, and checked (`if (myEpoch !== connectionEpochRef.current) return/break`) at the top of each loop iteration and in `finally`, so a stale loop can detect it's been superseded and stop touching state/queues.
  - `useTerminalFlowControl.ts` (the sub-hook for `sendInput`/`sendInputWithEcho`/resize/flow-control) already guards every send with `if (!pushMessageRef.current || !isConnectedRef.current) return;` — so it *does* stop pushing once disconnected, but this only protects new user keystrokes after `isConnectedRef` flips false; it does nothing for messages already sitting in the `MessageQueue` buffer from before the flip (see bug above), nor does it protect against a stale consumer loop still processing incoming server messages from a superseded stream.

## 3. Go-side concurrency stack (control mode + websocket handler)

- **`session/tmux/control_mode.go`** (682 lines) already uses well-established goroutine-lifecycle idioms in this repo:
  - `doneCh <-chan struct{}` closed by `StopControlMode()` to signal the sender goroutine (`runCMSender`) to exit; `StopControlMode` then **waits** (with a timeout + warning log) for the sender goroutine to actually exit before closing stdin — a synchronous "wait for goroutine exit" pattern, not fire-and-forget.
  - Explicit code comments distinguish "reader-goroutine-only fields (no lock needed)" vs. fields needing synchronization — i.e., single-writer-goroutine-owns-field is an established pattern here, worth following for any new epoch/counter field guarding the read/write goroutines.
  - `SendInputViaControlMode` uses a **buffered(1) result channel** pattern (`resultCh`) so the reader goroutine can deliver an ack without blocking, and the caller has a bounded wait — a channel-based synchronization idiom to reuse for any new coordination.
- **`server/services/connectrpc_websocket.go`** `streamViaControlMode` (function starts ~line 472) spins up 3 goroutines per stream: output-forwarder, resize-coalescer, and WebSocket-reader (input handler, ~line 857-1000), synchronized via `doneChan := make(chan struct{})` (closed once) and `errChan := make(chan error, 2)` (buffered so goroutines never block writing their termination result), then a `select` on `doneChan`/`errChan` to unwind. This is the same `doneChan`/`errChan` idiom reused at line ~1116 in the sibling `streamViaTmuxCapturePane`. Any new dedup/idempotency guard for input should slot into this reader goroutine (~line 899-924) where `input.Data` is received once per message and forwarded via `instance.SendInputViaControlMode` → subprocess `sendInputToTmux` fallback — **this fallback path itself does not loop or retry-duplicate**; it's a single try-then-fallback, so server-side this is not the duplication source per message. The duplication observed in the ticket's logs is consistent with the client re-sending the same logical keystroke as a *new* message across a reconnect, not the Go handler replaying a message it already processed.
  - `github.com/linkdata/deadlock v0.5.5` is a dependency (deadlock-detecting mutex) — useful if new locking is introduced around any counter/guard state.
- **Existing generation-counter precedent to mirror**: `session/session_driver.go` (`StartSessionDriver`) uses `atomic.Bool.CompareAndSwap` as an idempotency guard so a second call is a safe no-op, plus a `retried *atomic.Bool` flag threaded through explicitly "so the retry goroutine does not spawn a third generation" (line ~77). This is the closest existing idiom in the Go codebase to an epoch/generation guard and is a good template: an `atomic.Bool` or `atomic.Uint64` "epoch" counter passed by pointer/closure into goroutines so a stale one can detect supersession, rather than introducing a new synchronization primitive.
- No `goleak` dependency exists in `go.mod` — goroutine-exit assertions in this repo are **hand-rolled via channels + `sync.WaitGroup` + `time.After` timeouts** (see `server/services/connectrpc_websocket_test.go`: `TestWaitForQuiescenceReturnsOnTimeout`, `TestSnapshotCacheConcurrentAccess` use `chan struct{}`/`sync.WaitGroup` directly). Any new "bounded read-goroutine exit test" (per requirements.md goal #4) should follow this same hand-rolled pattern — close a `chan struct{}`/use a `sync.WaitGroup`, then assert exit within a `time.After` bound — rather than pulling in `goleak`.

## 4. Test tooling

- **Jest**: `web-app/package.json` pins `jest@^30.2.0`; config at `web-app/jest.config.js`. Run subset with `cd web-app && npx jest --no-coverage --testPathPatterns="<pattern>"`.
- **Existing mock-WebSocket / stream patterns**: `useTerminalStream.test.ts` does **not** use real WebSockets or `jest.useFakeTimers()` — it fully mocks out `@connectrpc/connect`'s `createClient`, the websocket transport module, `MessageQueue`, `useTerminalFlowControl`, and `useTerminalMetrics` via `jest.mock(...)`, then drives the mocked async-generator `stream` directly to assert `terminalState` transitions (`describe('useTerminalStream — ResizeQuiescence state machine', ...)`). New tests for "overlapping-connect epoch guard" and "triple-rapid-connect no-throw" should follow this same fully-mocked-stream style (construct a fake async-iterable `stream`, call `connect()` multiple times synchronously/close together, assert only one epoch's state mutations "win" and no unhandled rejection/throw) rather than introducing real timers or real sockets.
- **`MessageQueue.test.ts`** exercises the queue directly (no mocking needed, it's a pure class) — the new "queued-message-drop-on-close interleaving" test belongs here: push a message without an active iterator/awaiter (so it lands in `this.queue`), call `close()`, then start iterating and assert the queued message is **not** yielded (this will currently fail against the existing implementation, proving the bug).
