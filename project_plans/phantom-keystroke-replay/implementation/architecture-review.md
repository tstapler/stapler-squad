## Concerns

- [ ] **Story 3.1.1 / `disconnect()` (`useTerminalStream.ts:371-413`) — epoch guard doesn't cover `disconnect()`'s own async continuation, only `connect()`'s.** The Domain Glossary scopes "Connection epoch" as spanning `connect()`'s "entry to its `finally` block completing" — `disconnect()` is explicitly outside that model. But `disconnect()` has a genuine `await` point (`await new Promise(resolve => setTimeout(...))`, line 392-407) and its post-await code (`setIsConnected(false)`, decoder resets) is not gated by any epoch/generation check. Because refs (`messageQueueRef`, `isConnectedRef`, a future `connectionEpochRef`) persist across the same hook instance regardless of `sessionId`, the `useEffect` at line 416-430 fires `disconnect()` (for an old session) as a cleanup and `connect()` (for a new session, if `autoConnect`) as the new effect body in the same synchronous React commit — so a new `connect()` can complete its synchronous prefix and start reporting `isConnected=true` before the old `disconnect()`'s deferred continuation resumes and calls `setIsConnected(false)`, silently flipping a freshly-connected UI back to "disconnected." This is exactly the "guard every resumption point, not just the happy path" trap the plan itself calls out (Step 0.5 #1) — just applied incompletely, since it stops at `connect()`'s three checkpoints and never extends to `disconnect()`'s one await point, even though Task 4.1.1.1 already modifies `disconnect()` in this same plan (to wire the drop signal). Remediation: capture `connectionEpochRef.current` at `disconnect()`'s entry too, and gate the post-await state mutations (line 409-412) behind an epoch-equality check, or explicitly document in ADR-001 why `disconnect()` is out of scope for this race class if it's judged not to manifest as input replay/loss.

- [ ] **Task 4.1.1.2 (`useTerminalStream.ts`, `onDrop` wiring) — the inline coalescing snippet has a logic bug and duplicates Story 4.2.1's stated ownership.** The plan's own code is `setDroppedInputEvent((prev) => ({ count: (prev?.at === Date.now() ? prev.count : 0) + 1, at: Date.now() }))`. `Date.now()` is called twice, once for the comparison and once for the new `at` — these will essentially never be equal (different millisecond, or even if same ms, comparing a *stale* `prev.at` against a *fresh* `Date.now()` on every subsequent call means the "same episode" branch can basically never take), so every drop resets the running count to `1` instead of accumulating. This also contradicts the Pattern Decisions table's "Coalescing/debounce ownership" row, which explicitly assigns coalescing to `InputDropBadge`'s local state, not to hook-level `setDroppedInputEvent` logic — so this is both a bug and a duplicated-responsibility smell (two places computing overlapping "running total" logic; one of them is wrong). Remediation: drop the accumulation attempt at the hook level entirely — have `onDrop` simply call `setDroppedInputEvent({ count: 1, at: Date.now() })` (or an equivalent single-event shape) and let `InputDropBadge`'s already-planned running-total ref (Story 4.2.1) own all coalescing, matching the ownership the plan already committed to elsewhere.

- [ ] **Lens 2 — Illegal states: `droppedInputEvent: { count: number; at: number } | null` doesn't prevent `count <= 0` at the type level.** Both call sites (Task 4.1.1.1's `if (droppedCount > 0) setDroppedInputEvent(...)` and Task 4.1.1.2's always-positive `+1`) currently only construct valid instances by call-site discipline, not by construction — nothing stops a future edit from calling `setDroppedInputEvent({ count: 0, at: Date.now() })` and rendering a badge that claims "0 keystrokes not sent." Given `InputDropBadge` already renders `null` specially to represent "no event" (Task 4.2.1.1), the `count <= 0` case is genuinely unrepresentable *in the domain* — it just isn't unrepresentable *in the type*. Remediation: a small helper, e.g. `function recordDrop(count: number): DroppedInputEvent | null { return count > 0 ? { count, at: Date.now() } : null; }`, used at both call sites instead of duplicating the `> 0` guard — cheap, and it also would have caught the Task 4.1.1.2 bug above at the point of writing it (a code reviewer skimming a shared helper is far more likely to notice `prev?.at === Date.now()` is wrong than a bespoke inline updater buried in a `useTerminalFlowControl(...)` call's option object).

## Nitpicks

- **`controlModeReadLoop` (Task 5.1.1.1) is declared as a method on `*ConnectRPCWebSocketHandler` but never reads `h`'s fields** (`sessionService`, `scrollbackManager`, `externalDiscovery`, `tmuxStreamerManager`, `snapshotCache`) — everything it needs (`conn`, `sessionID`, `doneChan`, `errChan`, `handleEnvelope`) is a parameter. A free function (`controlModeReadLoop(conn *websocket.Conn, sessionID string, doneChan <-chan struct{}, errChan chan<- error, handleEnvelope func(*protocol.Envelope))`) would be more idiomatic and doesn't need a receiver at all. Low practical cost either way — the existing test suite already constructs `NewConnectRPCWebSocketHandler(nil, nil, nil)` cheaply for similar cases (`connectrpc_websocket_test.go:404` etc.) — so this is a style nit, not a testability blocker.

- **`useTerminalFlowControl.sendInput`'s silent-drop guard (`useTerminalFlowControl.ts:143`) is one of six near-identical `if (!pushMessageRef.current || !isConnectedRef.current) return;` guards in that file** (also at lines 171, 198, 234, 252, 294, 319 per grep). The plan (Task 4.1.1.2, per Unresolved Question 1) wires the drop signal into only the `sendInput` occurrence, which is the right scope for a "phantom keystroke" ticket — resize/scrollback/flow-control drops aren't keystroke loss — but it's worth a one-line note in the task itself (not just the Unresolved Questions section) that the other five call sites were deliberately left unwired, so a future reader doesn't read the fix as incomplete.

- **`MessageQueue.close(): number` return-type widening is unchecked at existing call sites other than the two the plan touches.** A repo-wide grep for other `.close()` callers on a `MessageQueue` instance would be cheap due diligence before Task 2.1.1.1 ships, even though the change is additive (old `void`-style callers remain valid) — not a blocker, just worth a quick confirmation grep during implementation rather than assuming only `useTerminalStream.ts`'s two call sites exist.
