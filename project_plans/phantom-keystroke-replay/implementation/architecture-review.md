**Verdict**: CONCERNS

## Constitution Violations
N/A — no `docs/adr/ADR-000-architecture-constitution.md` in this repository (verified: file does not exist).

## Blockers

None. No plan element rises to "will produce an unrepresentable/incorrect state or an unfixable design mistake if implemented as written." The two closest candidates (Task 3.1.1's missing `sessionID` parameter, Task 2.3.2's `toastAutoCloseMs` type mismatch) are both caught by the plan's own build/test verification steps before merge, and both have a one-line fix — demoted to Concerns below.

## Concerns

- [ ] **Task 3.1.1 (`runInputReadLoop` extraction)** — The proposed standalone-function signature `runInputReadLoop(stream *connectWebSocketStream, doneChan chan struct{}, errChan chan error, onInput func(data []byte), onResize func(cols, rows int))` omits `sessionID`. Verified in the current source (`server/services/connectrpc_websocket.go:857-864`): the WebSocket-read-error log line (`log.Error("[streamViaControlMode] WebSocket read error", "session", sessionID, "err", err)`) sits directly in the loop body, *outside* both the input-handling block (which Task 1.1.1's description folds entirely into the `onInput` callback) and the resize-handling block (`onResize`). `sessionID` is a local var in `streamViaControlMode` (line 473: `sessionID := instance.Title`), not a field on `connectWebSocketStream` (confirmed: the struct at line 402-406 has only `conn`, `requestMsg`, `writeMutex`). If `runInputReadLoop` is truly extracted as a package-level function (not a closure retained via `go func(){...}()`), this reference won't compile with the signature exactly as written. — **Remediation**: add `sessionID string` as an explicit parameter (cheapest fix, preserves log fidelity), or drop the `"session"` tag from that one log line if the implementer decides connection-scoped context is sufficient elsewhere. Either way, update Task 3.1.1's prescribed signature before handing it to an implementation subagent, since the task is written prescriptively enough that a subagent will likely copy it verbatim and then have to self-correct on a compile error. The plan's own verification step (`go test ./server/services` before/after) *does* suffice as a detection mechanism (it fails to compile if this is missed) — this is a spec-completeness gap, not an undetectable risk.

- [ ] **Task 2.3.2 (`InputDropBadge` auto-dismiss timing)** — The plan directs implementers to reuse `toastAutoCloseMs` from `web-app/src/lib/notification-policy.ts` "rather than a new magic number." Verified the actual signature: `toastAutoCloseMs(type: NotificationData["notificationType"]): number` (`notification-policy.ts:38`) — it is parameterized on `NotificationData`'s `notificationType` discriminated-union member (`"approval_needed" | "question" | "error" | "task_failed" | ...`), a domain type describing session-level notifications (approval requests, task completion, errors). "Keystrokes dropped during a reconnect" has no corresponding `notificationType` variant and is a different domain concept entirely (terminal-local transient UI signal, not a session notification). Calling this function for `InputDropBadge` forces the implementer to either (a) pass an unrelated/misleading `notificationType` literal (e.g. `"error"`) purely to extract a millisecond constant, coupling an unrelated UI element's timing to a domain classification it doesn't belong to, or (b) add a new `notificationType` variant just to make the call legal — which is the exact "add a new class to reuse a switch statement" anti-pattern this review is meant to catch (a phantom OCP extension for a type this component isn't actually a member of). — **Remediation**: extract a plain named constant (e.g. `export const DEFAULT_TOAST_MS = 8_000;` next to `toastAutoCloseMs` in `notification-policy.ts`, matching the existing default branch's value) and have both `toastAutoCloseMs`'s default case and `InputDropBadge` reference it, rather than routing `InputDropBadge` through a function whose parameter type it structurally cannot honestly satisfy.

- [ ] **Story 2.3 / Task 2.3.3 (`DropEpisode` coalescing) — testability gap** — The plan's Task 2.3.4 adds Jest tests only for `InputDropBadge.tsx` in isolation (role, singular/plural text, auto-dismiss). The actual coalescing logic — the `dropEpisodeRef`/`useState` pair and `setTimeout` flush that turns N rapid `onInputDropped(count)` calls into one `DropEpisode` within the 400ms window (requirements Goal 3 / AC3's explicit "one coalesced announcement... not one per dropped keystroke") — lives inline in `TerminalOutput.tsx` (Task 2.3.3) and has no assigned test task anywhere in the plan. `TerminalOutput.tsx` is already a large, hard-to-unit-test file (1500+ lines per the plan's own line references). This is the one piece of new behavior in Epic 2 that is *not* extracted into an independently-testable unit (contrast with `answerDialogOnce`, Story 1.2.3, and `runInputReadLoop`, Story 3.1.2, both explicitly pulled out for pure-function/isolated testing) — it is the actual functional requirement AC3 cites by name, yet it is the least-tested piece. — **Remediation**: extract the coalescing logic into a small hook (e.g. `useDropEpisodeCoalescer(onFlush, windowMs)`) colocated near `InputDropBadge.tsx` or in `web-app/src/lib/hooks/`, and add a dedicated Jest test (fake timers: assert 3 calls to the coalescer within 400ms produce exactly one flush with count 3; a call after the window produces a second flush) before wiring it into `TerminalOutput.tsx`.

- [ ] **Story 2.2 — connection-generation guard has no pure-function extraction, unlike its two sibling fixes** — `answerDialogOnce` (Go) and `runInputReadLoop` (Go) are both explicitly extracted so they can be unit-tested without a live tmux session / live WebSocket. The connection-generation guard's actual decision logic (`if (myGeneration !== connectionGenerationRef.current) break;` plus the teardown-old-generation block in Task 2.2.2) stays inline inside `connect()`'s closure and the message-processing IIFE, tested only through full-hook integration tests (Tasks 2.2.5/2.2.6) against mocked streams. This matches the existing repo idiom (`usePathCompletions.ts` also keeps its generation guard inline, per the plan's own Pattern Decisions rationale in Step 3), so it is consistent with prior art rather than a novel omission — demoted from Blocker to Concern on that basis. — **Recommendation**: no code change required; note in ADR-001 or the PR description that this asymmetry (2 of 3 guards get isolated unit coverage, 1 gets integration-only coverage) is an intentional consistency choice with `usePathCompletions.ts`, not an oversight, so a future reviewer doesn't flag it as newly-introduced inconsistency.

- [ ] **Story 1.1 / ADR-001 — `dialogContentHash` zero-value edge case** — `dialogAnswerState`'s zero value (`hash: 0, status: dialogUnanswered, attempts: 0`, assuming `dialogUnanswered` is `iota` value 0) is used as the latch's initial state before any dialog is seen. `hashString` is FNV-64a (`claude_controller.go:621-625`), whose output for any real input (including the empty string, which hashes to the FNV offset basis, not 0) is essentially never exactly `0`. This makes the "hash != state.hash" reset-on-first-tick comparison correct in practice, but it is an implicit invariant (uint64 zero doubling as "no hash seen yet" sentinel) rather than an explicit one. Not worth a dedicated wrapper type for an astronomically unlikely FNV-64a-produces-exactly-0 collision — flagged here only so the implementer doesn't need to re-derive this reasoning, and so ADR-001's "Consequences" section could note it took this into account (it does not currently mention the zero-value case).

## Nitpicks

- `dialogAnswerState.hash uint64` is a bare primitive reused only for equality comparison within `session_driver.go`. A `type dialogContentHash uint64` newtype (per `type-driven-design`'s newtype technique) would cost nothing and would prevent an accidental future comparison against an unrelated `uint64` in the same file, but at 1 call site today this is genuinely optional — do not block on it.
- `dialogLatchStatus`'s 3-state enum is the right choice (Lens 3, GoF): a State-pattern interface with polymorphic types would be pure ceremony for a single transition function with no per-state behavior beyond "send or don't." Go's plain `iota` enum + `switch` is correct here, but note Go gives no compiler-enforced exhaustiveness (unlike the frontend's `OmnibarAction` discriminated union + exhaustive `switch` pattern this repo already relies on elsewhere, per `.claude/rules/feature-testing-registry.md`). Consider a `default: panic(...)` arm in the switch (matching the Go sum-type idiom from the `type-driven-design` skill) so a future 4th status added without updating every switch fails loudly instead of silently no-opping.
- `answerDialogOnce(state *dialogAnswerState, output string, send func() error, sessionTitle, logContext string)` — the two trailing string params exist purely for logging. Stable enough for the two known call sites (Tasks 1.1.3/1.1.4), but if a third call site or richer log context is ever needed, consider bundling into a small `dialogLogContext{title, context string}` struct rather than growing the positional-string-parameter list further.
- Task 1.1.4 (second `SendKeys("1\n")` site, `NeedsApproval`/`shouldApprovePrompt` branch) correctly gives the approval latch its own independently-scoped `var approvalLatch dialogAnswerState` rather than sharing state with `startupLatch` — verified this is consistent with the existing code structure (the two branches are mutually exclusive within a single tick via the startup-dialog branch's `continue`, but independent across ticks/session lifetime), so no aggregate-boundary or shared-mutable-state issue here.
- Epic 1 correctly keeps both latches as local variables in `runSessionDriverWithPrompt`, not new `Instance` fields — verified `sentInitial`/`initialPromptSentAt` are already declared as locals immediately above the same `for range ticker.C` loop (`session_driver.go:94-96`), and `StartSessionDriver`'s `driverRunning.CompareAndSwap` (`session_driver.go:56`) does guarantee single-goroutine sequential ownership for the life of one driver run — the plan's Step 3 reasoning holds up under inspection, this is not a case of avoiding a Repository/Unit-of-Work pattern where a local variable happens to also suffice; a local variable is the objectively correct answer here.
- Server-side connection-registry/refcounting gap (`research/architecture.md` §2, `StartControlMode`/`StopControlMode` unreferenced-counted) is correctly scoped out per the plan's own Unresolved Questions §3 and requirements.md's Non-Goals — the client-side epoch guard alone does not fully close hop 6/7 of the traced re-emission chain (two independent server-side `streamViaControlMode` goroutine sets could still both be alive briefly), but the plan is explicit and honest that this is accepted residual risk with a flagged follow-up ticket, not a silently-dropped gap — no action needed here beyond what's already documented.
