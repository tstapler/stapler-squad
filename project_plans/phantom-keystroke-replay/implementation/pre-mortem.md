# Pre-mortem: phantom-keystroke-replay
**Date**: 2026-07-27

Verified from plan.md's Plan Revision Log: the two blockers from the first adversarial-review round were genuinely addressed, not just re-labeled —
1. **Control-flow starvation** (Blocker 1): Task 1.1.3 now branches on `answerDialogOnce`'s returned status; only `dialogUnanswered` keeps the `continue`, while `dialogAwaitingDismissal`/`dialogGaveUp` fall through to the rest of the tick. Confirmed present in the current plan text (ADR-001 "Control flow" section, plan.md Task 1.1.3).
2. **Content-hash jitter fragility** (Blocker 2): Task 1.1.2 now normalizes via `strings.Join(strings.Fields(output), " ")` before hashing, with a dedicated test case (1.2.3(e)) for whitespace/line-wrap jitter. Confirmed present.

Both are real fixes for the specific jitter class they name (whitespace/line-wrap). However, direct reading of `session/instance_terminal.go` (`Preview()`, lines 105-125), `session/claude_controller.go` (`GetRecentOutput`, lines 628-646), `session/pty_access.go`, and `session/circular_buffer.go` — none of which the plan's authors appear to have traced this deeply — surfaces a **third, unaddressed jitter source** that is more severe than the one Blocker 2 closed: see Failure Mode 1 below. This was not raised in either prior review round and is not covered by the Plan Revision Log.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `Preview()` → `GetRecentOutput(0)` returns the **entire accumulated PTY ring buffer** (raw ANSI included, append-only, up to the 10MB `CircularBuffer` cap — confirmed via `pty_access.go`/`circular_buffer.go`/`response_stream.go`), not a tailed "current screen" snapshot the way `GetCurrentStatus` already tail-slices (`claude_controller.go:528` `tailContent(content, statusDetectionTailBytes)`). Task 1.1.2's normalization only collapses whitespace — it never bounds the input. Once the trust-dialog text has ever appeared, `isStartupDialog`'s `strings.Contains` keeps matching it as a substring for as long as it survives inside the 10MB window (most of an ordinary session), and any new legitimate output Claude produces afterward changes the hash of the whole buffer — which the design explicitly treats as "content changed → new dialog → reset to `dialogUnanswered`." The fix's own re-arm rule then fires another real `SendKeys("1\n")` into an already-working session, reproducing the unbounded-resend bug in the **ordinary, non-flapping** case the fix isn't even meant to guard against — the opposite of what Blocker 2's fix was believed to close. | The phantom "1" reappears in the live pane shortly after Claude produces its first chunk of output *after* the trust dialog is answered — in a completely normal session, not one that ever flapped. Task 1.2.2/1.2.3's tests won't catch this because the fake `ProcessManager` is deliberately built to return byte-**identical** content every tick (the opposite of a growing buffer), so the plan's own test suite structurally cannot exercise this path. | Tail-slice `output` (reuse `tailContent`/a bounded window, mirroring `GetCurrentStatus`'s existing `statusDetectionTailBytes` precedent) before both the `isStartupDialog`/`shouldApprovePrompt` match *and* the hash — not just normalize whitespace. Add a test where the fake `ProcessManager`'s buffer **grows** each tick (new, unrelated Claude output appended after a byte-identical dialog region) and assert the latch still recognizes "same dialog, unrelated new output" as unchanged and does not resend. | P1 |
| 2 | The Blocker-1 fall-through fix means once the dialog latch reaches `dialogAwaitingDismissal` or `dialogGaveUp` (as fast as one successful send, or 3 failed attempts at 2s intervals — ≤6s either way), the tick now reaches the `!sentInitial` block, whose `timedOut := time.Now().After(readyDeadline)` (30s) fires well after any latch resolution. That block unconditionally sends the real initial task prompt and sets `sentInitial = true` / `initialPromptSentAt = time.Now()` **regardless of whether `SendKeys` itself errors** — collapsing the AwaitingDismissal-vs-GaveUp distinction the plan's "falls through to the existing escalation machinery" argument relies on, and silently converting a genuinely-still-stuck (`GaveUp`) session into "initial prompt believed sent," deferring any further signal to the coarse 10-minute inactivity timeout instead of something faster or more specific. Neither plan.md's Task 1.1.3 nor ADR-001's "Control flow" section trace this specific interaction — both mention "Ready-detection" and "inactivity-timeout escalation" as the things restored by falling through, but not that the *same* block also fires the real task prompt unconditionally on a 30s wall-clock timeout. | A session that hit `dialogGaveUp` shows no distinctive log signal beyond the existing dialogGaveUp Warn; the next observable event is either nothing for up to 10 minutes, or a `SendKeys(initialPrompt...)` failure that is logged at Warn but still marks `sentInitial = true`, so operators reviewing logs see "sent initial prompt" and reasonably (but wrongly) assume the session actually progressed. | In plan.md Task 1.1.3 / ADR-001, explicitly trace what the `!sentInitial` block does when reached via `dialogGaveUp` fall-through, and consider gating the initial-prompt send on latch status (skip/delay it while status is `dialogGaveUp`), or at minimum log distinctly when the initial prompt fires immediately after a `dialogGaveUp` fall-through so the two events are correlatable. | P2 |
| 3 | `maxDialogAnswerAttempts`'s bounded-retry framing (and ADR-001's "may be too tight for real flap durations" caveat) only bounds the `SendKeys`-**failure** counting path. Phase 0's own reproduced evidence shows all 3 recorded `SendKeys` calls returning **success** (the `"SessionDriver: answered startup dialog"` log line is the success branch) — i.e. the actually-observed real-world scenario latches to `dialogAwaitingDismissal` after a single successful-looking send and never retries again, with zero dedicated observability (the plan's Observability Plan only logs at Warn on the `dialogGaveUp` transition). The fix silently trusts that one Go-level `SendKeys` success actually reached a possibly-still-flapping/detached pty — the exact assumption the ticket's own root cause (a stale buffer during a flap) calls into question. | A session shows exactly one "answered startup dialog" success log line during a flap, then goes quiet — the trust dialog was never actually dismissed, but nothing distinguishes this from a normal single-answer session until the unrelated 10-minute inactivity timeout eventually notices. | Add an observability line when the driver later confirms (or fails to confirm) that the dialog actually cleared after a successful send — e.g., verify `isStartupDialog(output)` is false on a subsequent tick before fully trusting `dialogAwaitingDismissal`, rather than latching purely on `SendKeys` returning no error. | P2 |
| 4 | The plan validates both independent fixes (Go dialog latch, client `MessageQueue`/generation guard) together in a single AC5 manual-repro pass (Task 4.1.1) with no isolated/bisected variant of the procedure. If the repro still shows a residual phantom-keystroke or input-drop issue, the plan has no prescribed way to attribute it to one fix versus the other beyond ad hoc investigation, despite the dependency graph explicitly calling the two epics "independent." | AC5's manual verification (Task 4.1.1) comes back with a mixed or ambiguous result (e.g., no more repeated "1" but the drop badge never appeared, or vice versa), and there's no documented next step for isolating which fix path is responsible. | Add an explicit bisection step to Task 4.1.1: run the repro once against Epic 1 alone (client-side generation guard/MessageQueue fix reverted or feature-flagged off) before running it against the combined build, so a failure is attributable to a specific epic. | P2 |
| 5 | `InputDropBadge` only fires on the narrow intersection of "user is actively typing" and "an overlapping-generation reconnect/close event is happening at that exact moment" — a window real users rarely hit. This code path (the 400ms coalescing window, the nonce/live-region dedup fix, badge mount/dismiss timing) may go essentially unexercised in production for a long time after ship, risking an unnoticed defect in the one mechanism that fulfills AC3's "user must be clearly told" requirement, precisely when it's needed most. | Weeks or months pass with zero production occurrences of the badge firing (no telemetry proposed for it beyond a `console.warn` per plan.md's Observability Plan), so a latent bug in the coalescer or live-region nonce logic ships invisibly until the next real user report of "my keystrokes vanished with no warning." | Add a lightweight counter/log line (server- or client-side) for "input dropped" episodes distinct from the existing `console.warn`, so real-world firing frequency is observable post-ship rather than assumed; consider a one-time synthetic/manual trigger path (e.g., a dev-only button) to keep the component exercised between real occurrences. | P3 |

## P1 Items (address before implementation)
- [x] Failure #1 — Tail-slice `Preview()`'s output (or a copy of it used for dialog detection) to a bounded recent window before both `isStartupDialog`/`shouldApprovePrompt` matching and hashing, mirroring `GetCurrentStatus`'s existing `tailContent`/`statusDetectionTailBytes` precedent; add a growing-buffer test case to Task 1.2.3 proving the latch does not resend when unrelated new output is appended after an unchanged dialog region. Without this, the fix as currently specified (whitespace-normalization-only) is very likely to still exhibit the ticket's exact symptom in ordinary, non-flapping sessions — a materially different and larger regression surface than what Blocker 2 closed.
