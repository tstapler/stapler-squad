# Pre-mortem: phantom-keystroke-replay
**Date**: 2026-08-02

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Task 3.1.1.1 places `const epoch = ++connectionEpochRef.current;` *before* `connect()`'s pre-existing entry guard (`if (isConnectedRef.current \|\| isConnectingRef.current \|\| !sessionId) return;`, `useTerminalStream.ts:163`). Since that guard is what currently prevents a second real `connect()` from running while one is already CONNECTING/CONNECTED, any guard-blocked call still bumps the epoch and orphans the real in-flight attempt — its `firstMessage`/`catch`/`finally` state mutations now see `epoch !== connectionEpochRef.current` and silently no-op forever, with no second real attempt ever running to complete the handoff. This is exactly the rapid-reconnect flapping scenario (visibility+online listeners firing close together) the ticket is about. | A session intermittently gets stuck showing the "CONNECTING" spinner (or silently reverts to disconnected) after a reconnect flap, with no console error — reproducible by calling `connect()` twice in immediate succession while the first call is still pre-`firstMessage`, which the Jest tests in Story 3.2.1 may not actually exercise if their `mockStreamTerminal` stub doesn't interact with `isConnectingRef`/`isConnectedRef` the same way production code does (in which case the test's "call `connect()` twice synchronously" setup silently never invokes the second mock at all, and the assertion passes for the wrong reason). | Before implementing Task 3.1.1.1, add a test that calls `connect()` a second time while `isConnectingRef.current` is deliberately still `true` (simulating a guard-blocked call) and asserts (a) the still-in-flight first attempt's later `firstMessage`/`finally` handlers are *not* orphaned, and (b) `mockStreamTerminal` was invoked exactly once, not twice. If the guard blocks the second call, move the epoch increment to *after* the entry guard, not before it — the "increment before any await" rule from `pitfalls.md` still holds, but "before the early-return guard" is a stronger and incorrect claim the plan conflates with it. | P1 |
| 2 | AC5's scripted repro (Story 6.1.1) still cannot exercise the actual client-side race: a single sequential agent cannot literally type into the browser terminal *while simultaneously* calling `pause_session` — it can only do them in sequence — and the plan never names the concrete mechanism for "typing into the terminal" (browser automation? `write_to_session`? `send_control`?). If typing is done via an MCP/server-side path that bypasses the browser's WebSocket/`MessageQueue`/epoch-guard entirely, the repro proves tmux/`pause_session` behavior, not that the shipped client fix (Phases 2-4) does anything — the identical failure class already documented for two prior unmerged branches on this exact ticket. | AC5 gets marked done (`report_progress` `criteria_index=4` status=done) with a clean transcript, but no artifact in the report actually shows the browser's `InputDropBadge`/assertive announcement firing during a real overlapping type+pause — the "record whether the badge fired" step is optional/observational rather than an asserted pass/fail gate. | Before Phase 6 executes, pin down the exact typing mechanism in Task 6.1.1.1 as browser automation (Playwright/`claude-in-chrome`) driving real keystrokes into the live DOM terminal — not an MCP tool that writes to the pty directly — and make "InputDropBadge or assertive announcement observably fired for at least one cycle where timing was tight" a required, checked pass/fail assertion in the recorded outcome, not an optional note. | P1 |
| 3 | `InputDropBadge`'s coalescing relies on React re-rendering once per distinct `droppedInputEvent` prop value, but the hook's three independent drop-reporting call sites (Task 3.1.1.2's reconnect close, `disconnect()`'s close, Task 4.1.1.2's `onDrop`) each call `setDroppedInputEvent` independently; if two fire within the same React batch (plausible during rapid reconnect churn, since React 18 batches all synchronous `setState` calls including those outside event handlers), only the last value survives to the next render and the earlier occurrence's count/announcement is silently lost — undercounting the running total the coalescing tests (Task 4.2.3.2) don't reproduce, since those tests drive prop updates via sequential controlled re-renders, not two same-tick `setState` calls from the real hook. | The badge's displayed running total is lower than the actual number of drop occurrences during a fast flap (e.g., shows "2 keystrokes" when 3 were actually dropped across two call sites in one tick), with no error — only detectable by comparing hook-internal call counts against rendered badge text, which none of the planned tests do. | Add a Jest test to Story 3.2.1 or 4.2.3 that triggers two of the hook's drop call sites synchronously within the same `act()` block (not two separate `renderHook` re-renders) and asserts the badge's rendered total reflects both occurrences, not just the last. | P2 |
| 4 | `streamShellViaControlMode` and `streamViaTmuxCapturePane` (Unresolved Question 2) are structurally duplicated goroutine-coordination code with the same `doneChan`/`ReadMessage()` shape as the handler this plan fixes, and are explicitly left untouched. This codebase has direct precedent for this exact failure shape: `c0e6c4ce6` had to *generalize* an initially-narrow latch fix from one dialog type to a second dialog type after the first commit missed it. A recurrence of an input-relay or goroutine-leak issue via one of these two sibling handlers within the first month would look like this same bug reopening, undermining confidence in the fix even though it's technically a different code path. | A new bug report describing "stuck"/replayed input on a session using the shell or tmux-capture-pane control path specifically (not the main `streamViaControlMode` path this plan covers), within weeks of shipping. | Requirements/plan already flag this as a named follow-up (Unresolved Question 2) — strengthen it by filing the follow-up ticket now (not just noting it in prose) so it has a tracking ID before this ticket closes, and add a one-line grep-based CI check (or code comment cross-reference) at the two duplicated handlers pointing back to this backlog item, so a future editor of either handler sees the connection immediately. | P3 |
| 5 | Task 1.1.2.1's new AC2 regression test reimplements `session_driver.go:447`'s state-threading rule (`approvalAwaitingClear = approvalAwaitingClear && approvalVisible`) *inline in the test* rather than driving the real polling loop/method that does this threading in production. This is the same "tests the pattern, not the production code path" gap the plan's own Pattern Decisions table explicitly rejects for Phase 5's Go read-loop test (and the precise failure mode — AC3 marked done against code that didn't do what was claimed — that already happened once on this exact ticket) — but the same discipline wasn't applied when writing Task 1.1.2.1 itself. | The test keeps passing after a future refactor of `session_driver.go`'s actual polling-loop threading logic that introduces a real regression, because the test's hand-copied threading rule silently drifts out of sync with production and no longer reflects what the loop actually does. | Change Task 1.1.2.1 to drive the real driver-loop method that threads `approvalAwaitingClear` across ticks (not a hand-copied inline re-implementation of the threading rule), the same way Phase 5's extraction makes `controlModeReadLoop` directly callable — if no such directly-testable method exists yet, extract one first, mirroring the Phase 5 precedent already in this same plan. | P2 |
