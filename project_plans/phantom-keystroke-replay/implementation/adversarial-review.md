## Blockers

- [ ] **The assertive announcement does not coalesce across multiple drop episodes in one flapping session, directly contradicting `research/ux.md` §4's explicit "coalesce, don't spam" requirement — and Task 4.2.3.2 locks in the spam behavior as the tested-correct outcome.** Task 4.1.1.1 sets `droppedInputEvent` to a brand-new `{ count: droppedCount, at: Date.now() }` on *every* `close()` call (each reconnect supersession, each explicit disconnect, each flow-control-layer drop via Task 4.1.1.2) — there is no windowing/accumulation at the hook level; `count` is always just that single close's own drop count, never a running total across a short window. Task 4.2.2.2 then fires `announce(...)` from a `useEffect` keyed on `droppedInputEvent?.at` — since `at` is a fresh timestamp on every single drop event, every reconnect-triggered drop produces its own separate `announce()` call. During the ticket's own flapping scenario (multiple connect→drop→reconnect cycles in quick succession), this fires one assertive interruption per cycle — exactly the failure mode ux.md §4 names by example ("announce once with a count... rather than firing the live region three times") and explicitly warns is a known screen-reader UX failure ("each one cuts off the previous, and users lose the ability to follow the terminal output entirely"). Task 4.2.1.1's `InputDropBadge` *does* implement visual coalescing (an internal running-total ref, reset only when the dwell window has fully elapsed) — but that coalesced total lives only inside the badge component and is never used by the `TerminalOutput.tsx` announcement wiring, which reads `droppedInputEvent.count` (the single latest event) directly. Two consequences: (1) the announcement spams during exactly the scenario this feature exists to handle, and (2) the spoken count and the displayed badge count can diverge (badge shows an accumulated total, announcement speaks only the latest event's smaller count). Task 4.2.3.2, as scoped, tests that "a second `droppedInputEvent` with a new `at`... still produces a new announcement" — i.e. it asserts the spam behavior is correct rather than testing that rapid-fire drops coalesce into one announcement. **Recommendation**: move the debounce/accumulation up to the hook (or a shared point both the badge and the announcement effect read from) so `droppedInputEvent.count` itself is a windowed running total, and gate `announce()` on a "window closed" signal (timer or reconnect-success) rather than on every individual `at` change, per ux.md §4's literal recommendation to reuse the `NotificationToast` reset-timer idiom for both the visual and the audible signal, not just the visual one.

## Concerns

- [ ] **`disconnect()` is not epoch-gated, and ADR-001 only analyzes connect()-vs-connect() re-entrancy, never disconnect()-vs-connect() interleaving — a gap already flagged, and left unresolved, in this exact codebase's own prior (unmerged) adversarial review pass.** Read `useTerminalStream.ts:371-410` directly: `disconnect()` mutates the same shared `messageQueueRef`/`abortControllerRef` state as `connect()` but never reads or increments `connectionEpochRef`. ADR-001's "Why watchSessions() needs two increments and connect() doesn't" section frames the only two re-entrancy surfaces as "external multi-call" and "internal self-recursion" of `connect()` itself; it never considers `disconnect()` as a second caller that can race with a `connect()` attempt already in flight (e.g., a component-unmount `disconnect()` interleaving with an in-flight internal reconnect timer's `connect()`, or a caller invoking `disconnect()` then `connect()` again before the superseded attempt's `finally` has actually run). The prior unmerged branch's own adversarial-review pass (`backlog/stapler-squad-phantom-keystroke-replay`, `implementation/adversarial-review.md`) raised this identical concern against an earlier version of this same hook ("neither `connect()` nor `disconnect()` check a generation token... whichever runs last wins") and it was never marked resolved in that branch's re-review (only the two blockers were). This plan makes the same architectural choice again without acknowledging or re-litigating that prior finding. **Recommendation**: either have ADR-001 explicitly address why disconnect()-vs-connect() interleaving is safe as designed (e.g., because `shouldReconnectRef` being set `false` first in `disconnect()` is sufficient — plausible, but not currently argued anywhere), or add the epoch check to `disconnect()`'s mutation of shared refs, and add a Jest test for disconnect-interleaved-with-reconnect (not just connect-vs-connect, which is all Story 3.2.1 covers).

- [ ] **AC5's manual repro doesn't script an explicit "type input during the flap window" step, so it may not actually exercise the epoch-guard/MessageQueue-drop mechanism this session's Phase 2-4 work delivers.** Story 6.1.1's Given-When-Then treats input-in-flight as a hypothetical aside — "(if any input was in flight during a pause boundary) the browser shows the InputDropBadge..." — rather than a required, scripted action. Since AC1/AC2's SessionDriver mechanism is already fixed and verified by Phase 1's isolated regression test (not by this live repro), the only mechanism this manual pass can meaningfully add live evidence for is the client-side drop/replay guard — which requires someone to actually type into the terminal at the moment `pause_session` fires. As written, a run where the tester never types during the pause window would trivially "pass" (no phantom keystrokes observed) without ever exercising the fix. **Recommendation**: make Task 6.1.1.1 an explicit script: type a distinguishable string (e.g. a counted sequence) into the terminal immediately before/during each `pause_session` call in the 5-10 cycle alternation, and confirm via `read_session_output` that the string never appears duplicated/replayed, and that the `InputDropBadge`/announcement fired for the cycles where a `pause_session` landed while a keystroke was mid-flight.

- [ ] **Task 4.1.1.2 (wiring `useTerminalFlowControl.sendInput`'s silent drop into the same signal) is implemented as a normal task, not gated behind the stakeholder confirmation the plan itself says it needs.** The plan's own Unresolved Question 1 states this file/line isn't named in requirements.md's "Remaining confirmed gap" section and asks to "confirm with the backlog item's stakeholder that this is in-scope... since requirements.md's own... section does not name this specific file/line" — yet Epic 4.1's task list includes it as a committed, unconditional implementation step, not a follow-up contingent on that confirmation. This is scope drift the plan is self-aware of but doesn't actually gate. **Recommendation**: either get the confirmation before Phase 4 starts and drop the caveat, or make Task 4.1.1.2 conditional/deferred pending that answer rather than bundling it into the same phase as the requirements-scoped work.

- [ ] **requirements.md misdescribes the already-merged fix's actual mechanism as a time-based "cooldown" (`shouldApprovePromptWithCooldown`, `lastApprovalAnsweredAt`, `withinCooldown`/"cooldown timestamps"), and plan.md's new test name (`TestApprovalCooldownLatch_PreventsPhantomReplayAcrossReconnectChurn`) propagates the same incorrect terminology.** Grepped `session/session_driver.go` directly: none of `withinCooldown`, `lastApprovalAnsweredAt`, or `shouldApprovePromptWithCooldown` exist anywhere in the file. The real mechanism (`shouldSendOnce`, used by both `shouldAnswerStartupDialog` and `shouldApprovePromptOnce`) is an edge-triggered latch keyed on `awaitingClear` — the code's own doc comment explicitly disclaims a cooldown: *"A fixed time-based cooldown is deliberately not used here."* The plan's actual Given-When-Then for Task 1.1.2.1 correctly describes the real `approvalAwaitingClear` state-threading behavior, so the underlying test logic is sound — this is a naming/terminology inaccuracy inherited uncritically from requirements.md's Root Cause section, not a logic error, but it will confuse future readers who go looking for a `Cooldown`-named function/field that doesn't exist. **Recommendation**: rename the new test to something like `TestApprovalAwaitingClearLatch_PreventsPhantomReplayAcrossReconnectChurn` and correct requirements.md's Root Cause section's function-name citations before this ships.

- [ ] **Phase 7 (AC6) has zero active verification step — it is pure assertion, not a check, echoing the review task's own suspicion.** "No action" / "Already satisfied; no code or doc change required" is the entire content of Epic 7.1. ## Minors

- The Dependency Visualization's claim that "Phase 3 depends on Phase 2" is accurate for the production code (epoch guard's close-before-install calls the fixed `close()`), but Story 3.2.1's Jest tests mock `MessageQueue` entirely (Task 3.2.1.1: "Enhance the module-level `MessageQueue` mock... to track `close` calls") — so Phase 3's *tests* don't actually exercise Phase 2's real `close()` fix at all, only a mock's `.close()` call count. This is fine (unit-test isolation is reasonable), but the dependency diagram's phrasing ("Phase 3's Jest tests assert on the fixed drop semantics") slightly overstates what those specific tests verify versus what Phase 2's own tests verify.
- Task 5.1.1.1's proposed `controlModeReadLoop` signature takes `conn *websocket.Conn` while the call site passes `stream.conn` — correct and consistent with the actual codebase (`stream *connectWebSocketStream` wraps a `*websocket.Conn`), but the doc comment's claim that "no new param threading needed" for `stream`/`snap`/`tmuxSessionName`/`resizeCh` relies on the `handleEnvelope` closure being defined at the original call site (not inside the extracted function) — worth being explicit about in the task text so an implementer doesn't try to thread those through `controlModeReadLoop`'s signature by mistake.
- ADR-001's reasoning for a single-increment epoch (vs. `useSessionService.ts`'s double-increment) is well-argued and, on direct inspection of both hooks' entry guards, correct for the connect()-vs-connect() case specifically — no issue with the ADR's core claim, only with its scope (see the disconnect()-vs-connect() Concern above).
- Phase 6's chosen repro mechanism (pause_session/resume_session MCP tools driving `instance_tmux.go:471-472` directly) is a genuine improvement over the two prior branches' repro procedures — it correctly avoids the documented wrong-session-creation-path mistake (`dca931a04`: omnibar-created sessions never attach a `SessionDriver`) by using `mcp__stapler-squad__create_session`, which does attach one, and it also sidesteps the prior branches' separate `/tmp`-pre-trust dead end (`~/.claude.json` global trust cache defeating the dialog trigger) since this repro doesn't depend on the trust dialog firing at all. Worth stating explicitly in Task 6.1.1.1 that this is a deliberate improvement over the prior branches' approach, for a future reader's benefit.
