# Adversarial Review: phantom-keystroke-replay

**Date**: 2026-07-27
**Verdict**: BLOCKED (original pass) → **RESOLVED** (see "Re-Review" section at
the end of this file — both blockers confirmed fixed against the revised
plan.md, no new blocking issue introduced)

## Blockers

- [x] **RESOLVED — see Re-Review section.** `dialogGaveUp` (and `dialogAwaitingDismissal`) silently starve the entire driver loop, not just the dialog-answer path. Confirmed by reading `session/session_driver.go:148-165`: the existing (and, per plan Task 1.1.3, still-implied) control flow is `if isStartupDialog(output) { SendKeys...; continue }` — the `continue` skips *every* other check in the tick: `sentInitial`/Ready-detection, the 10-minute `driverInactivityTimeout` → `handleDriverFailure` → `ReviewQueue` escalation path, and the `NeedsApproval` branch. This `continue` fires whenever `isStartupDialog(output)` is true, **regardless of the latch's internal status**. Task 1.1.3 says only "replace the body with a call to `answerDialogOnce(...)`" — it never specifies whether the post-fix code still unconditionally `continue`s once the latch reaches `dialogGaveUp`. If implemented the most literal way (preserve the existing `continue` shape, just wrap the `SendKeys` call), a session whose stale `Preview()` buffer keeps matching `isStartupDialog` forever will, after ~6 seconds (3 failed attempts), permanently stop trying — but will *also* never fall through to the inactivity timeout, never call `handleDriverFailure`, and never reach `markSessionNeedsAttention`. The only remaining exit is the bare `if time.Now().After(totalDeadline) { return }` at ~25 minutes (`driverTotalTimeout`), which returns silently with **zero** operator notification (it doesn't call `handleDriverFailure`). Net effect: this trades "phantom keystrokes forever" (annoying but the driver stays alive and eventually recovers if the real session does) for "the entire session driver silently wedges for up to 25 minutes with one stale Warn log line, then vanishes with no escalation" — worse for the subset of sessions that are genuinely, not just cosmetically, stuck. **Recommendation**: the plan must explicitly specify that once the latch reaches `dialogGaveUp` (or even `dialogAwaitingDismissal`, once the send succeeded), the tick should fall through to the Ready/inactivity/NeedsApproval checks instead of unconditionally `continue`-ing — this also makes Unresolved Question #1 ("should GaveUp escalate to ReviewQueue?") resolve itself for free, via the existing `handleDriverFailure`/inactivity-timeout machinery, rather than needing new wiring.

- [x] **RESOLVED — see Re-Review section.** The content-hash latch can be defeated by non-byte-identical-but-logically-same dialog re-renders, reproducing the original unbounded-resend bug through a different path than the one Phase 0 proved.** `DialogContentHash` is a straight FNV-64a hash of the raw `Preview()` string; any incidental difference between ticks (terminal width change altering line-wrapping, trailing whitespace, cursor-position artifacts) resets the latch to `Unanswered` and re-fires `SendKeys("1\n")`. Requirements.md and this plan explicitly cross-reference bug #164 ("infinite resize loop") as sharing a "reconnect-instability root" with this ticket — meaning resize churn during exactly the flapping window this fix targets is a known, adjacent, real phenomenon in this codebase, not a hypothetical. Task 1.2.2/1.2.3's tests only exercise a fake `ProcessManager` returning **byte-identical** stale text every tick — the easy case. No test exercises "same logical dialog, jittering incidental formatting" — the scenario that would actually defeat this specific design. **Recommendation**: either normalize (trim/collapse whitespace, or hash a stable substring/fingerprint) before hashing, or add a test fixture where content varies slightly-but-immaterially tick-to-tick and confirm the latch still holds; otherwise this fix has an unverified escape hatch back into the exact bug it's meant to close.

## Concerns

- [ ] **Task 2.2.2 changes `connect()` but not `disconnect()`, and the Risk Control table's narrative doesn't match the Task list.** The Risk Control table states the change is "Making `useTerminalStream.disconnect()` unconditionally abort the previous generation (removing the `isConnectedRef.current` gate)" — but Task 2.2.2's actual code change is entirely inside `connect()`; `disconnect()` is untouched. Reading `useTerminalStream.ts:352-387` directly: `disconnect()`'s own `isConnectedRef.current`-gated branch (lines 378-382) resolves the teardown promise **without ever calling `abortControllerRef.current.abort()`** when not connected — a pre-existing latent bug the plan neither fixes nor acknowledges touching, despite the risk table implying it does. Separately, neither `connect()` nor `disconnect()` check a generation token before mutating the shared `messageQueueRef`/`abortControllerRef`, so if `disconnect()` (e.g., component-unmount cleanup) and a concurrent `connect()` (e.g., an auto-reconnect timer in `TerminalOutput.tsx` that isn't guaranteed to be cancelled on unmount) interleave, whichever runs last wins — a legitimate new generation's queue/controller could be torn down by a disconnect() call that thought it was cleaning up the old one. Tasks 2.2.5/2.2.6 only test connect()-vs-connect() overlap, not disconnect()-vs-connect(). **Recommendation**: reconcile the Risk Control table with the actual task list, and either add a generation check to `disconnect()` or add a test proving unmount-racing-reconnect is safe.

- [ ] **Task 1.1.4 (approval-prompt latch) is applied by analogy, not by the same runtime-evidence rigor Phase 0 required for the primary fix.** AC1 explicitly states "source-level research alone does not satisfy" root-cause claims, yet the `NeedsApproval`/`shouldApprovePrompt` branch is fixed purely because it's "the identical defect class" — no live-executing test analogous to `TestSessionDriver_StuckDialogAnswersBoundedNotUnbounded` (Task 1.2.2) exists for this second call site; only the shared `answerDialogOnce` unit tests (1.2.3) cover it, which prove the helper function works, not that the branch's own wiring (`mgr.GetStatus` gating, independent `approvalLatch`) behaves correctly under a stuck buffer. Reasonable to fix opportunistically, but should either get equivalent integration coverage or be explicitly labeled "fixed by inspection, not by reproduced evidence" rather than silently riding on AC2's coverage summary.

- [ ] **No test in the plan actually asserts "forwarded to tmux exactly once" end-to-end, despite AC4's literal wording.** Every concrete test task is single-layer: 1.2.2 counts `SendKeys` calls against a fake `ProcessManager`; 3.1.2 counts `onInput` callback invocations against a fake WebSocket pair (no real tmux); 2.1.2/2.2.5/2.2.6 assert `MessageQueue`/hook-internal call counts and state. `research/pitfalls.md` §5 already flagged this exact risk ("a frontend-only test... would give false confidence... needs to be paired with a Go test") — the plan satisfies "paired" but the two suites test *different scenarios* (client epoch guard vs. server read-loop shutdown), not a single reconnect-during-send trace through both layers into one sink. **Recommendation**: either narrow AC4's wording to match what's actually tested (two independent regression suites, not one end-to-end guarantee), or add one true integration test that drives a reconnect around an input send through a real/faked WebSocket into a real/faked tmux backend and asserts exactly one delivery.

- [ ] **`InputDropBadge`'s live-region announcement will silently fail to re-announce for back-to-back drop episodes with an identical message string.** Verified by reading `web-app/src/components/ui/LiveRegion.tsx`: its `useEffect` only calls `setCurrentMessage(message)` when `message` is truthy (`if (message) { ... }`), so a cleared ("") message is never actually committed to the DOM — `currentMessage` never resets between announcements. Task 2.3.2 composes `<LiveRegion role="alert" politeness="assertive" message={...} />` directly with no nonce/counter and no use of the existing clear-then-set `useLiveRegion` hook. Consequence: two consecutive drop episodes that both drop the same count (e.g., "1 keystroke dropped — reconnecting" twice in a row) render identical DOM text; React bails on the redundant state update, the DOM text never changes, and most screen readers will not re-announce an `aria-live` region whose content is unchanged. This directly undercuts AC3's requirement that an announcement fire "exactly once per coalesced drop episode" — as specified it only reliably fires once per *distinct* message. **Recommendation**: append a monotonic nonce/timestamp to the announced string, or fix `LiveRegion`'s clear-to-empty path so it actually reaches the DOM.

- [ ] **Task 3.1.1's proposed `runInputReadLoop` signature omits `sessionID`, which the extracted loop body still needs.** Reading `connectrpc_websocket.go:856-924` directly: the WS-read-error log at line 868 (`log.Error("[streamViaControlMode] WebSocket read error", "session", sessionID, "err", err)`) is part of the core read loop, not delegated to either the `onInput` or `onResize` callback, yet the proposed signature (`stream, doneChan, errChan, onInput, onResize`) has no `sessionID` parameter. As specified this either won't compile or will silently drop session context from that log line — the "pure move, no behavior change" claim isn't quite accurate as written.

- [ ] **`maxDialogAnswerAttempts = 3` (~6 seconds of polling) may be too tight relative to the ticket's own flapping duration**, and the Risk Control table's "does not regress" claim assumes the flap resolves within that window. Phase 0's own evidence only ran 3 ticks (~6.5s); nothing in the research bounds how long a real "session not started or paused" flap can last in production. If a genuine (not just visually-stale) `SendKeys` failure needs more than 3 ticks to clear, the fix converts "eventually succeeds, if noisily" into "gives up permanently" — compounded by Blocker #1's control-flow gap, this could leave the session wedged rather than merely quiet.

- [ ] **Manual repro (Task 4.1.1) step 5's pass criterion is a weak signal in isolation.** "SessionDriver: answered startup dialog" appearing "at most 3 times total" is also exactly what the log shows in the normal, non-buggy, single-dialog case — the count check alone can't distinguish "the fix correctly bounded a real resend storm" from "the flap was never actually triggered and the dialog was just answered once, normally." Step 4 already asks the verifier to reproduce the specific flap condition, but step 5 doesn't instruct correlating *timestamps* between the "session not started or paused" log lines and the "answered startup dialog" lines to confirm the (bounded) resends actually happened during the induced flap window.

## Minors

- Panic-safety of the `send func() error` closure passed to `answerDialogOnce` is unchanged from today (same top-level `recover()`, same blast radius — a panic there still kills the whole driver goroutine, not just the dialog check). Not a new risk, but also not improved by this plan.
- `isStartupDialog`'s three trigger phrases ("trust this folder", "is this a project you created", "quick safety check") are all assumed answerable with the same literal `"1"` — a pre-existing, unvalidated assumption this plan doesn't re-examine; no test exercises a hash-change transition between two genuinely different real dialog variants (Task 1.2.3's (b) case uses a synthetic content change, not a second real dialog fixture).
- `role="alert"` + `politeness="assertive"` on the same `LiveRegion` instance (Task 2.3.2) is mildly redundant (`role="alert"` already implies assertive live-region semantics) — cosmetic only.
- `InputDropBadge`'s scope (new component + CSS + portal + feature-registry entry) is proportionate, not scope creep — AC3's literal text already mandates a "badge + assertive announcement," and `research/ux.md` already ruled out routing through the cheaper `NotificationToast` stack.

## Re-Review (blocker verification pass)
**Date**: 2026-07-27
**Verdict**: RESOLVED

- Blocker 1 (control-flow starvation): RESOLVED — Task 1.1.3 now explicitly branches on `answerDialogOnce`'s returned `dialogLatchStatus`: "`dialogUnanswered` (this tick just attempted a send, whether it succeeded or is retrying after a failure): `continue`... `dialogAwaitingDismissal` or `dialogGaveUp`: do **not** `continue`. Fall through to the rest of the loop body exactly as if `isStartupDialog(output)` had been false for this tick... only the `dialogUnanswered`-this-tick case returns/continues early; the other two statuses let the tick proceed downward." This is concrete enough that a verbatim implementation is unambiguous — it's phrased as an if/else over the three-value enum, not left to inference, and ADR-001 duplicates the same rule in its new "Control flow: latch status must not starve the rest of the tick" section. Cross-checked against the actual pre-fix code (`session/session_driver.go:148-165`): today's block is exactly `if isStartupDialog(output) { SendKeys...; continue }`, confirming the plan's line citations and problem description are accurate, and Task 1.1.4's claim that the `NeedsApproval` branch (lines 206-219, confirmed) has no `continue` today and therefore needs no analogous fix is also accurate by inspection. Unresolved Question #1 is correctly marked resolved without new escalation wiring.
- Blocker 2 (content-hash jitter): RESOLVED — Task 1.1.2 now specifies normalizing before hashing: "Normalize before hashing using `strings.Join(strings.Fields(output), " ")` (collapse all runs of whitespace, including newlines from line-wrap shifts, to single spaces) and hash the normalized string instead of `output` directly." Task 1.2.3 gained case (e), a whitespace/line-wrap-jitter table row asserting `sendCallCount` stays at 1 across two calls with the same words but different wrapping/whitespace. The claimed `claude_controller.go` precedent checks out: `GetCurrentStatus` (confirmed at lines 500-553, `hashString` confirmed at lines 621-625 exactly as cited) does hash a reduced form of the buffer (tail-sliced via `tailContent` + `filterTmuxMetadata`-stripped) rather than the raw `Preview()` output, for the same stated reason (avoid false-different comparisons against incidental buffer noise) — this is a real, not fabricated, citation. The plan and ADR are appropriately careful to note the *specific* technique differs (tail-slice + tmux-line-filtering vs. whitespace-collapse) and that `filterTmuxMetadata` itself doesn't apply here; only the general "normalize before hash" idiom is claimed as reusable, which holds up.
- New issues introduced by the fixes: One minor, non-blocking structural note. Falling through past the startup-dialog check (Blocker 1's fix) does not cause double-processing within the `!sentInitial`/Ready-detection block or the inactivity-timeout block — both are single, mutually-exclusive-by-construction blocks reached the same way a non-dialog tick reaches them (confirmed by re-reading `session_driver.go:90-220`). However, the fall-through does create one new same-tick reachability path that did not exist pre-fix: once the startup-dialog latch reaches `dialogAwaitingDismissal`/`dialogGaveUp` (no longer continuing), the tick can now reach the `NeedsApproval`/`shouldApprovePrompt` block (lines 208-219) later in the *same* tick using the *same* `output`. Pre-fix, the unconditional `continue` at line 163 made these two branches strictly mutually exclusive within one tick; post-fix they are not. If a single buffer snapshot were ever classified `true` by both `isStartupDialog` (matches "trust this folder" / "is this a project you created" / "quick safety check") and `shouldApprovePrompt`+`StatusNeedsApproval` (matches "allow reading/writing/executing" / "do you want to proceed"), the independently-scoped `approvalLatch` (fresh, `dialogUnanswered`) would fire its own `SendKeys("1\n")` in the same tick the startup latch already considers answered/abandoned. In practice this is very unlikely — the two detectors key on disjoint phrase sets describing genuinely different dialogs — and is bounded (each latch independently caps at 3 attempts, so this cannot reproduce the original *unbounded*-resend bug), making it the same risk class as the FNV-collision risk the plan already accepts elsewhere. It is not currently called out in the plan's Risk Control table or ADR-001's Consequences section; worth a one-line addition there for completeness, but not a blocker.
