# Adversarial Review: webhook-triggers
**Date**: 2026-08-06
**Verdict**: BLOCKED

## Blockers

- [ ] **Delivery-ID dedup is check-then-insert with no uniqueness guarantee — the exact race pitfalls.md §2.2 named is not actually closed.** Task 1.2.1a adds `index.Fields("delivery_id")` (a lookup index, not a `.Unique()` constraint or unique composite index), and `ExistsByDeliveryID` (Task 1.2.1c) is a plain read-only check called before firing. Two near-simultaneous requests with the same `X-GitHub-Delivery` (a real GitHub retry storm, or a captured-and-replayed request arriving in parallel) can both pass the existence check before either has written its `TriggerFireEvent` row, and both fire — double-creating a session. Pitfalls §2.2 explicitly calls for "check-and-set this **before** doing any session-creation work... so a retry that arrives while the first request is still in flight doesn't race past the check," which requires either a DB-level unique constraint on `delivery_id` with insert-time conflict handling, or an application-level lock/singleflight keyed on delivery ID — neither is in the plan. **Recommendation**: add `.Unique()` (scoped appropriately, e.g. per-workflow or global) to `delivery_id`, and make the dedup check-and-record a single atomic insert (treat a unique-constraint violation as "already processed, return 200") rather than a separate read then a later write.

- [ ] **No SSRF validation anywhere for outbound callback URLs, despite pitfalls §5 requiring it explicitly.** Task 5.1.1a-d (`CallbackConfig`) and Task 5.2.1a (`CallbackDispatcher`) never validate the operator-configured URL's scheme or resolved address before POSTing. Pitfalls §5 spells out the exact requirement: "validate the configured callback URL is `http`/`https`, resolve and reject link-local/loopback/private-range targets **at send time** (not just save time — DNS can change between config-save and each future callback fire)." As written, a callback URL of `http://169.254.169.254/...` or `http://localhost:<internal-port>/` would be dispatched to on every session completion/stale/queue-created event. **Recommendation**: add a URL-validation step (scheme allowlist + resolve-and-reject-private-ranges) inside `CallbackDispatcher.Dispatch`, called on every attempt, not just at config-save time.

- [ ] **FR6/AC7 ("enable/disable without redeploy") has no concrete field for the new trigger types, and the plan's own UI task flags this as still unresolved.** Task 1.1.1a's field list for `ent.Workflow` (`trigger_type`, `github_repo`, `github_branch`, `webhook_slug`, `webhook_secret_encrypted`, `event_filter`, `label_filter`, `prompt_template`, `last_fired_at`) never adds a generic `enabled` bool — only the pre-existing, cron-specific `CronEnabled` exists. Story 7.1.1's own acceptance criterion writes the toggle action as `UpdateWorkflow{CronEnabled: false}`-**equivalent (or a new generic `Enabled` field if `trigger_type != cron`)** — i.e. Phase 7 is still guessing at Phase 1's schema six phases later. Meanwhile, neither webhook handler task (2.2.1b's repo/branch candidate matching, 2.3.1a's slug lookup) checks any enabled/disabled state before matching and firing. As scoped, a "disabled" `webhook`/`github_push` trigger has no field to check and would keep firing. **Recommendation**: add a generic `enabled` bool to Task 1.1.1a's field list now, and make both webhook handlers check it before matching, closing this before Phase 7 rather than leaving it as an open bracket in the UI task.

- [ ] **Epic 6.2's chain-fire call likely creates a circular import between `session` and `server/workflows`.** Story 6.2.1's acceptance criterion states the chained session "is created via `FireTrigger`" — i.e. code living in `session/ent_repository_backlog.go`/`session/backlog_lifecycle.go` (Task 6.2.1a/6.2.1b's listed files) calling `server/workflows.Scheduler.FireTrigger` directly. `server/workflows` already depends on `session` (the ent client and repositories `Scheduler` reads/writes through) — for `session` to also import `server/workflows` for the chain-fire call is a cycle Go will refuse to compile, regardless of which specific file in `session` makes the call. The plan never surfaces this as a risk or names a resolution. **Recommendation**: define a narrow consumer-side interface in `session` (e.g. `type ChainFirer interface { FireTrigger(ctx, wf *ent.Workflow, prompt, deliveryID string) (string, error) }`) that `Scheduler` satisfies, and inject it into whatever `session`-package code performs the chain-fire — this is precisely the pattern `.claude/rules/interface-pollution-checklist.md` calls for ("define interfaces where consumed"), and it needs to be decided before Epic 6.2 starts, not discovered mid-implementation.

## Concerns

- [ ] **Webhook HTTP handlers appear to call `FireTrigger`/`CreateSession` synchronously inside the request/response cycle**, unlike `CallbackDispatcher`, which is explicitly dispatched via `go func()`. `CreateSession` spins up a tmux session and git worktree — pitfalls §2.3 itself calls these "expensive operations." GitHub times out and treats a delivery as failed (triggering a retry) if the receiver doesn't respond within roughly 10 seconds. A slow `CreateSession` could cause GitHub to see a failure and retry a request that actually succeeded — the dedup check would correctly no-op the retry, but the operator would see a spurious "failed delivery" in GitHub's own UI for real, successful fires. No task addresses returning 200 promptly and decoupling the actual fire.
- [ ] **No validation prevents cross-type field pollution on the now-wide `Workflow` entity** (e.g. a `cron`-type row with `webhook_secret_encrypted` also populated). ADR-001's stated mitigation — "only trigger-type-relevant fields are surfaced/validated per `trigger_type`" — isn't matched by any task; Task 3.1.1b only validates that `prompt_template` parses, not that a row's field set is consistent with its `trigger_type`.
- [ ] **FR9's "logged/surfaced, not silently dropped" is applied asymmetrically.** Inbound trigger evaluations get a full durable, queryable audit trail (`TriggerFireEvent` + `ListTriggerFireEvents` RPC + `TriggerExecutionHistory.tsx`). Outbound callback delivery failures — which FR9 covers just as explicitly — get only a `log.Warn` line (Task 5.2.1a/Observability Plan); no durable row, no RPC, no UI surface for "did my `on_session_complete` callback actually deliver." Given how carefully the plan built the inbound side, the outbound side reads under-built by comparison.
- [ ] **`CallbackDispatcher.Dispatch` spawns an unbounded goroutine per event with no worker pool, no ceiling, and no shutdown coordination.** Each goroutine can live up to ~15s (3 attempts × 5s timeout) against a dead endpoint; a burst of simultaneous lifecycle transitions (many stale-crossings at once, for instance) has no cap on concurrent in-flight dispatchers, and goroutines started just before process shutdown aren't drained/cancelled. Worth at least a bounded worker pool given this repo's 2026-07-12 OOM history with uncapped concurrency.
- [ ] **`maxChainDepth`'s default and configurability are left as an "Unresolved Question... owner: implementer"** rather than decided at plan time, despite being the primary independent backstop against runaway chained-session loops (pitfalls §3). A safety-critical parameter like this should be fixed before implementation starts, not decided ad hoc mid-coding.
- [ ] **No task confirms `webhook_secret_encrypted` is excluded from `WorkflowProto`'s list/get responses.** `CallbackConfigProto` is explicitly designed as booleans-only (Task 5.1.1b) to avoid ever echoing a secret; no equivalent task exists for the `Workflow` proto that will carry the new webhook fields. It's ciphertext rather than plaintext, but pitfalls §1.5 says "never return the raw secret value in any RPC response used to display trigger config" — worth an explicit masking task rather than relying on it working out by default.

## Minors

- Secret rotation (pitfalls §1.5's "trigger can hold two valid secrets during a cutover window") isn't addressed anywhere in the plan — reasonable to defer for this pass, but should be named as a follow-up rather than silently dropped.
- Task 2.2.1f's GitHub-handler test list ("valid, invalid sig, no-match, replay") omits an explicit malformed-JSON case that the generic handler's tests do cover (Task 2.3.1b/2.3.1f) — AC8 applies to both handlers equally.
- Epic 7.2's "Send test event" dry-run action (`TestTrigger` RPC) isn't required by any FR/AC — a reasonable UX addition sourced from research/ux.md, but it is scope beyond the stated acceptance criteria and could be deferred if time is tight.
- The per-`Workflow` `rate.Limiter` map (Task 2.4.2a) has no eviction path when a `Workflow` row is deleted — a slow, bounded memory leak over long uptimes with high trigger churn.
- No static/config-time cycle detection for pipeline chains (e.g. warning if a chain of `next_workflow_id`s could loop back within N hops) — relies solely on the runtime depth cap. Consistent with pitfalls' own framing of the depth cap as an independent backstop, but worth naming as a natural follow-up rather than a silent gap.
