# Pre-mortem: webhook-triggers
**Date**: 2026-08-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The review-repair fix for Blocker #4 (Epic 6.2) makes `session.ChainFirer.FireTrigger` a **synchronous** call inside `TransitionBacklogItemStatus` (Task 6.2.1a: "attempt the chain fire synchronously... same request"), unlike the sibling fix for the same import-cycle problem (`session.EventDispatcher`, Task 5.2.1a) which is explicitly `go`-launched. A chained fire means a full `CreateSession` (tmux session + git worktree) runs to completion before the persistence-layer status-transition method returns, for every caller of `TransitionBacklogItemStatus` on a chained item. | `done`-transition latency spikes (seconds, not milliseconds) or DB lock/transaction contention correlating exactly with chained items completing; possibly reports of the backlog UI "hanging" briefly after marking an item done. | Make chain-fire async-and-reconciler-driven only (drop the "same request" synchronous attempt from Task 6.2.1a, rely solely on `TriggerChainReconciler`'s 60s tick — which the plan already builds for the crash-recovery case, so it can be the *only* path), or explicitly document/measure that `TransitionBacklogItemStatus`'s transaction is committed and released *before* the chain-fire attempt runs (i.e. chain-fire happens after commit, not inside it) and add a task asserting this via a test that holds a slow chain-fire and confirms no lock/transaction is held during it. | P1 |
| 2 | Adversarial-review's Concern (not a Blocker, so the Review Repair Log's claimed fixes don't touch it) stands: both webhook handlers call `FireTrigger`→`CreateSession` synchronously inside the HTTP request/response cycle, while GitHub times out and retries a delivery after ~10s. `CreateSession`'s tmux+git-worktree cost can exceed that window. | GitHub's own webhook delivery UI shows "failed"/timed-out deliveries with automatic retries for triggers that actually fired successfully; operators lose trust in delivery status shown by GitHub even though the delivery-ID dedup (Task 2.2.1c) prevents an actual double-fire. | Add a task (Phase 2 or 3) to make the handler ack fast: claim the delivery ID and return HTTP 200 immediately, then dispatch `RenderTriggerPrompt`+`FireTrigger` via `go func()` (same async pattern already used for `CallbackDispatcher`), persisting the `TriggerFireEvent` outcome after the async fire completes rather than before responding. | P2 |
| 3 | Adversarial-review's Concern about `CallbackDispatcher.Dispatch` spawning an unbounded goroutine per event (no worker pool, no ceiling, no shutdown coordination) is also untouched by the repair log — it only added SSRF validation and dedup, not concurrency bounding. This repo has a **documented** 2026-07-12 OOM incident (`feedback_backlog_wip_limit` memory) caused by exactly this class of bug (uncapped concurrency), and the repair's own new WIP admission gate (Epic 1.3) protects session *creation* but has no equivalent for callback *dispatch* goroutines. | Memory growth / OOM correlating with a burst of simultaneous lifecycle transitions (e.g. many stale-crossings detected in the same reconcile tick) hitting a slow or dead callback endpoint — each holding a goroutine open up to ~15s (3 attempts × 5s timeout). | Add a bounded worker pool or a semaphore (`chan struct{}` sized N) that `Dispatch` acquires before launching each goroutine, with dispatch attempts beyond the cap either queued with a max queue depth or dropped-and-logged (still satisfying FR9's "not silently dropped" if the drop is logged) — same shape as the admission gate already built for session creation. | P1 |
| 4 | The `session.EventDispatcher`/`session.ChainFirer` setter-injection fix (mirroring `AdmissionGate`) guards every call site with `if r.eventDispatcher != nil { ... }` / `if r.chainFirer != nil { ... }` as a "safe no-op." Per Task 5.2.1a/6.2.1a0, wiring happens via 4 separate setter calls in `server/dependencies.go` (`SetEventDispatcher` × 2, `SetChainFirer` × 2) after construction. If any one is missed, wired in the wrong order, or the feature flag is off, the corresponding callback/chain silently never fires — with no log line, since a nil-guard "safe no-op" by design doesn't log. This directly contradicts FR9 ("failed callback deliveries are logged/surfaced, not silently dropped"), which the rest of the plan otherwise takes seriously (SSRF rejections, dedup rejections, and rate-limit rejections all log). | An operator configures `on_session_complete_url`/a chain, sessions complete normally, but the callback/chained session never appears — and there is nothing in the logs to explain why, making it look like a config bug on the operator's end rather than a wiring gap. | Log at `log.Warn` (once, or rate-limited) whenever `Dispatch`/`FireTrigger` is attempted through a nil `eventDispatcher`/`chainFirer` field, distinguishing "not wired" from "feature flag off" if possible, so FR9's visibility guarantee actually covers this path too. | P2 |
| 5 | The Unresolved Question on `on_queue_item_created`'s exact event source (review-queue `ReactiveQueueManager.OnItemAdded` vs. backlog-item creation — no `BacklogChangeItemCreated` kind exists today) is still open in plan.md, yet Task 5.2.1b already wires the callback to a specific call site (`ReactiveQueueManager.OnItemAdded`) "pending resolution." If that guess is wrong, the feature ships implementing the wrong semantics for FR7's third callback — passing its own AC4 test (a POST fires on *some* event) while not matching what users who asked for "queue item created" actually meant. | Users who configure `on_queue_item_created` expecting a POST when a new backlog item is created instead get one when a review-queue item is added (or never get one for actual backlog-item creation) — discovered only when someone manually correlates callback payloads against actual backlog activity, likely weeks after ship. | Resolve the question explicitly before Task 5.2.1b is implemented (not "pending resolution") — read `session/backlog_item_change.go`'s existing `BacklogChangeKind` values, decide with the requirements owner which "queue item" FR7 means, and if it's backlog-item creation, add the missing `BacklogChangeItemCreated` kind rather than repurposing `ReactiveQueueManager.OnItemAdded`. | P2 |
