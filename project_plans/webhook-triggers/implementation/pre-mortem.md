# Pre-mortem: webhook-triggers
**Date**: 2026-08-06

Assumes the project has shipped and failed. Findings below are specific to
`implementation/plan.md`'s task-level choices, not restatements of
`research/pitfalls.md` (SSRF, dedup TOCTOU, chaining loops, prompt injection are
already covered there and largely mitigated in the plan via AC9-AC12).

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The `delivery_id` unique index (Task 1.2.1a) is global, not scoped per-`workflow_id`, so when two *different* `Workflow` rows legitimately match the same inbound delivery (e.g. two `github_push` triggers both watching `main`, or two generic-webhook slugs fed the same payload), only the first `Create` wins the constraint and the second trigger is silently treated as "already processed" and never fires — the opposite of AC12's intent, and undetectable from the UI since it looks identical to a real dedup hit. | An operator with two triggers configured against the same repo/branch (or the same forwarded payload) reports "trigger B never fires," while its `TriggerFireEvent` history shows nothing at all for it — the row was claimed under trigger A's evaluation. | Change the unique index to a composite `(workflow_id, delivery_id)` (Task 1.2.1a), and for generic webhooks compute the delivery-ID digest over `slug + raw body` (or route the `Create` call per-workflow, matching how the candidate loop already iterates per-workflow in Task 2.2.1b) rather than raw body alone, so identical payloads delivered to different slugs don't collide. | P1 |
| 2 | Nothing in the plan adds a `trigger_type`-aware guard to `Scheduler.Reload`/`Start`'s existing cron-registration gate (`server/workflows/scheduler.go:105`, `if !wf.CronEnabled`), and no task validates that a `Workflow`'s populated fields match its declared `trigger_type` at save time. A row created with `trigger_type: "webhook"` that also has (or later gets) `cron_enabled: true` — via a stale form default, a copy-pasted `UpdateWorkflow` call, or a Phase 7 UI edit flow that doesn't clear the other type's fields on type switch (Task 7.1.1a doesn't mention this) — gets registered as *both* a cron entry and a webhook route, firing twice through two independent mechanisms for what the operator believes is one trigger. | Duplicate sessions/backlog items appear for a single logical trigger, each stamped with the same `WorkflowId` but different `TriggerFireOutcome`/`delivery_id` (one `"cron"`-path fire with no `delivery_id`, one `"webhook"`-path fire with one) — confusing and easy to misdiagnose as the chain-depth or WIP-gate bug instead. | Add a save-time validation in `WorkflowService.CreateWorkflow`/`UpdateWorkflow` (same place as Task 3.1.1b's template-parse check) rejecting any request where populated fields don't match `trigger_type` (e.g. `trigger_type != "cron"` but `cron_enabled: true`, or `trigger_type != "webhook"` but `webhook_slug` set). Also change `scheduler.go:105`'s gate to `if !wf.CronEnabled \|\| wf.TriggerType != "cron"` so a mismatched row can never double-register even if validation is bypassed via direct DB write. | P1 |
| 3 | The Risk Control section claims Phase 1 ships "zero user-visible change" for existing cron-workflow users, but Epic 1.3's own acceptance criteria describes exactly a user-visible behavior change: a cron fire that previously always succeeded now gets rejected once `MaxConcurrentBacklogWorkItems` is saturated. Existing MCP-tool-driven cron-workflow users (the only consumers of this feature pre-Phase-7) have no UI to see `TriggerFireEvent{outcome:"fired_failed"}` rows — `TriggersPanel` doesn't ship until Phase 7 — so between Phase 1 and Phase 7 shipping, a saturated WIP cap causes scheduled cron jobs (e.g. "nightly audit") to silently stop firing with the only trace being a `log.Warn` line no one is watching. | A user who has relied on a cron `Workflow` for weeks notices (days later, by absence) that a nightly job didn't run, with no notification and no queryable record short of grepping the service log for `"[WorkflowScheduler]"` / `"fired_failed"`. | Either (a) sequence Phase 1's admission-gate fix to ship together with (or after) a minimal query surface for `TriggerFireEvent` — even a `stapler-squad` MCP tool or CLI flag, not the full Phase 7 UI — so existing cron users have *some* way to see rejections before the behavior change goes live, or (b) correct the Staged Rollout section's "zero user-visible change" claim to explicitly flag this as an intentional, communicated behavior change (e.g. a changelog/release note) rather than implying it's inert. | P1 |
| 4 | Feature-flag gating is boot-time-only for route registration (`server.go`), but nothing logs or surfaces *that fact* to the operator. An operator who flips `webhook_triggers` to `true` via config/RPC and expects `/webhooks/*` to work immediately gets silent 404s from `http.NotFound` at the mux level — which happens *before* any handler code runs, so **no `TriggerFireEvent` row is ever created for these requests**, unlike every other rejection path in the plan (which the Observability Plan otherwise takes care to make visible). If the external sender (e.g. GitHub) gives up retrying before the operator notices and restarts, the event is permanently and invisibly lost. | GitHub's webhook delivery UI shows repeated 404s (visible only outside stapler-squad, in GitHub's own delivery log) while stapler-squad's own logs, `TriggerFireEvent` table, and UI show nothing at all — an operator debugging from inside the app has zero signal. | Log a line at boot (`log.Info`/`log.Warn`) stating whether `/webhooks/*` routes were registered based on the flag's value at that boot, so `journalctl` at least shows the discrepancy; optionally surface "flag changed, restart required for webhook routes" in the flag-toggle RPC response or the future Triggers UI settings panel. | P2 |
| 5 | The WIP-gate (global concurrency cap) and the chain-depth cap (per-lineage hop limit) are independent and each individually satisfied, but their *combination* has no bound on wait time: a `ChainFirer.FireTrigger` rejected by the admission gate leaves `chain_fired=false` and is retried indefinitely by `TriggerChainReconciler` every 60s (per Task 6.2.1a/6.2.1b) with no expiry, backoff cap, or priority distinction between trigger-spawned and user-initiated demand for the same WIP slots. Under sustained load (the WIP cap is small — the same cap that exists *because of* the 2026-07-12 OOM incident, so saturation is the expected steady state, not an edge case), completed items with a pending chain accumulate without bound, the reconciler's per-tick `ListBacklogItems` scan grows linearly with that backlog, and a chained pipeline (e.g. plan→implement→review→merge) can stall indefinitely at any hop with no signal distinguishing "stuck forever" from "will fire eventually." | Reconciler tick duration creeps up over weeks of uptime; a chained pipeline that used to complete in minutes silently takes hours-to-never during busy periods, with `chain_fired=false` rows accumulating and no per-item staleness alert (Phase 7's UX research explicitly deferred alerting as a "candidate follow-up, not blocking" — this is the scenario that makes it not-optional). | Add a max-wait/expiry on pending chain-fires (e.g. after N reconciler ticks or a wall-clock ceiling, mark `chain_fired=true` with `TriggerFireEvent{outcome:"fired_failed", error_message:"chain expired waiting for WIP capacity"}` rather than retrying forever), and/or give trigger-spawned admission requests a distinct (lower) priority than user-initiated ones so automated chains can't indefinitely starve — or be starved by — manual work sharing the same cap. |  P2 |

## P1 Items (address before implementation)
- [x] #1 — Resolved in `implementation/plan.md`: Task 1.2.1a's index changed to composite `index.Fields("workflow_id", "delivery_id").Unique()`; Task 2.2.1d restructured to dedup per matched candidate (a push can match >1 `github_push` workflow) instead of a single upfront check; Task 2.3.1b's note explains the composite index already scopes generic-webhook dedup per-slug without needing to fold the slug into the digest.
- [x] #2 — Resolved: new Task 1.1.1e adds save-time `trigger_type`-vs-populated-fields validation and tightens `scheduler.go:105`'s cron-registration gate to `!wf.CronEnabled || wf.TriggerType != "cron"`; new Task 1.1.1f adds the corresponding tests.
- [x] #3 — Resolved: Staged Rollout section corrected to no longer claim "zero user-visible change" for Phase 1, and explicitly documents it as a communicated behavior change. New Task 1.2.1d pulls a minimal `ListTriggerFireEvents` RPC (query-only, no UI) forward from Phase 7 into Phase 1 so existing cron-workflow users have observability into admission-gate rejections immediately, not just once the Phase 7 panel ships; Task 7.2.1a updated to reflect the RPC already exists by then.

## P2 Items (also addressed, not blocking but cheap to fix now)
- [x] #4 — Task 8.2.1a now logs the route-registration decision at boot (`/webhooks/*` registered vs. not, and why) so the boot-time-only nature of the feature flag is visible in `journalctl` instead of manifesting as silent, unauditable 404s.
- [x] #5 — Task 6.2.1b now includes a bounded retry ceiling (`maxChainWaitDuration`) so a chain stuck behind a saturated WIP gate eventually gives up (`ChainFired=true`, logged `fired_failed`) instead of retrying every reconciler tick forever and growing the per-tick scan unboundedly.
