# Validation Plan: webhook-triggers

**Date**: 2026-08-06

## Happy Path Scenario

Given an enabled `Workflow{TriggerType: "webhook", WebhookSlug: "jira-ticket", EventFilter: "issue_created", LabelFilter: "urgent", PromptTemplate: "Triage {{.issue.key}}: {{.issue.summary}}"}`, when a `POST /webhooks/jira-ticket` request arrives with a valid HMAC signature and a payload matching `event`/`label_filter`, then `GenericWebhookHandler` claims the `DeliveryID`, `RenderTriggerPrompt` renders the template, `Scheduler.FireTrigger` passes the admission gate and creates a new session tagged with the originating `WorkflowId`, and a `TriggerFireEvent{Outcome: "fired_success"}` row is persisted.

### `migration_should_be_reversible` — detail

Given a pre-feature sqlite ent database seeded with `Workflow` rows in the *old* shape (only `cron_enabled`/`cron_expression` populated, no `trigger_type`/`trigger_enabled`/`webhook_slug`/etc. columns read by new code):

1. **Additive/optional, safe defaults**: run ent's schema-diff auto-migration (`client.Schema.Create(ctx)`) against the seeded DB. Assert every new column (`trigger_type`, `trigger_enabled`, `webhook_slug`, `webhook_secret_encrypted`, `event_filter`, `label_filter`, `prompt_template`, `last_fired_at`, `next_workflow_id`, `chain_fired`, `chained_at`, `triggered_by_chain_depth`) exists post-migration and that a row **not yet touched by the backfill step** reads back its documented zero-value default (`trigger_type=""`/`trigger_enabled=true` per the field default, `chain_fired=false`, nullable fields nil) rather than erroring.
2. **Backfill correctness (Task 1.1.1d)**: seed three pre-existing rows — (a) `cron_enabled=true`, (b) `cron_enabled=false`, (c) a row that already has `trigger_type` set (simulating a row created after a partial rollout) — run the one-time backfill function. Assert: (a) → `trigger_type="cron"`, `trigger_enabled=true`; (b) → `trigger_type="manual"`, `trigger_enabled=false`; (c) is left untouched (backfill only targets `trigger_type == ""`, not overwritten). Assert the backfill is idempotent — running it a second time produces no further writes (verified via a row-touched/updated-at counter or mock `repo.Update` call count staying at the first-run total).
3. **Rollback inertness**: after migration + backfill, simulate an old-binary read by constructing an ent client using only the *old* generated code's field set (or, if regenerating an old client is impractical, directly query the DB via `database/sql` selecting only the pre-feature column list) against the now-migrated schema. Assert the query succeeds and returns the original `cron_enabled`/`cron_expression` values unchanged — the extra columns are present but inert to a reader that never selects them, per the plan's "old binary tolerates extra unknown columns" rollback claim. Also assert that toggling the feature flag off (`cfg.SetFeatureFlag("webhook_triggers", false)`) after migration leaves existing cron-workflow fire behavior (`Scheduler.FireTrigger` via the cron path) unchanged — same session created, same `last_fired_at` update — proving the migration itself introduces no behavior change for existing users independent of the flag.
