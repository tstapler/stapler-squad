# Validation Plan: webhook-triggers

**Date**: 2026-08-06

## Happy Path Scenario

Given an enabled `Workflow` row with `TriggerType: "webhook"`, a `WebhookSlug`, an `EventFilter`/`LabelFilter`, and a valid `PromptTemplate`, when a `POST /webhooks/{slug}` request arrives with a valid HMAC signature and a JSON payload matching the event/label filter, then `GenericWebhookHandler` verifies the signature, matches the trigger, renders the prompt via `RenderTriggerPrompt`, calls `Scheduler.FireTrigger` (which admits the request through the WIP gate, creates a session via `CreateSession` tagged with the originating `WorkflowId`), and persists a `TriggerFireEvent{Outcome: "fired_success"}` — proving an external event can create a visibly-attributed session with zero human interaction.

### Migration Test

| Requirement | Test File | Test Name | Type | Scenario |
|-------------|-----------|-----------|------|----------|
| Migration Plan: additive schema change + one-time backfill (Task 1.1.1d) | `server/workflows/scheduler_test.go` (or `session/ent_repository_workflow_test.go`) | `TestWorkflowTriggerTypeBackfill_should_SetCronOrManual_When_ExistingRowsHaveNoTriggerType` | Integration | ent test-client: seed pre-migration-shaped `Workflow` rows (`trigger_type=""`, some with `CronEnabled=true`, some `false`) directly via the repository, run the boot-time backfill function, assert `trigger_type` becomes `"cron"` for the `CronEnabled=true` rows and `"manual"` for the rest; run the backfill a second time and assert it is a no-op (idempotent — no rows re-touched, backfilled-count logged as 0) |

**No reverse-migration test**: per plan.md's Migration Plan section, this repo has no down-migration mechanism — ent's schema-diff auto-migration is additive-only, all new columns are `.Optional()` with safe zero-value defaults, and rollback is via the `webhook_triggers` feature flag (gating new routes/dispatch/reconciler) rather than a schema down-migration. There is deliberately no test exercising a reverse migration; inventing one would test a mechanism this codebase does not have.

## Coverage Targets and How to Measure

| Stack | Coverage command | Target |
|---|---|---|
| Go | `go test ./... -coverprofile=coverage.out && go tool cover -func=coverage.out` | ≥80% line |

- All public service methods (`CallbackDispatcher`, `Scheduler.FireTrigger`, `GitHubWebhookHandler`, `GenericWebhookHandler`, `ChainFirer`, `TriggerChainReconciler`, `WorkflowRepository`, `TriggerFireEventRepository`): happy path + error paths covered.
- All external integrations (GitHub webhook POST, generic webhook POST, outbound callback POST): unit mocked + at least one integration test per direction (inbound HTTP→session, outbound session-event→HTTP).
- Concurrency-sensitive paths (AC9, AC10, AC12): each has at least one test that exercises real goroutine concurrency via `sync.WaitGroup` + a shared start channel/gate, not just sequential calls — see the "Concurrency-aware" rows above. AC11's TOCTOU concern is time-sequenced (save-time vs. send-time), not goroutine-concurrent, and is covered by a two-attempt DNS-change test instead.
- Run `make build && make test` before considering any task in Phases 1-6 complete; `cd web-app && npx jest --no-coverage` for Phase 7 once it begins.
