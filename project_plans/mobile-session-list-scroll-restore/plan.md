# Plan: Mobile Session List Scroll Position Restore

## Approach

Implement a `useScrollRestore` hook that saves the `scrollTop` of the session-list scroll container to a module-level `Map` on unmount and restores it synchronously on mount. Wire it into `SessionListPaneBody` via the existing `pane.id` stable key.

## File Changelist

### New: `web-app/src/lib/hooks/useScrollRestore.ts`

A reusable hook. Signature:
```ts
function useScrollRestore(
  ref: React.RefObject<HTMLElement | null>,
  key: string,
): void
```

Implementation:
- Module-level `const scrollPositions = new Map<string, number>();`
- `useLayoutEffect` (runs before paint): reads `scrollPositions.get(key)` and sets `ref.current.scrollTop` if a saved value exists.
- `useEffect` cleanup: saves `ref.current?.scrollTop ?? 0` to `scrollPositions.set(key, ...)`.
- Optional: attach a `scroll` handler that keeps the map updated on every scroll event (debounced ~100ms) so the map is current even if unmount doesn't fire cleanly (e.g. fast pane switches).

Why `useLayoutEffect` for restore: applying `scrollTop` after layout but before paint avoids a visible flash of the list at position 0.

### Modified: `web-app/src/components/pane/PaneSplitRenderer.tsx`

In `SessionListPaneBody`:
1. Add a `useRef<HTMLDivElement>(null)` for the scroll container.
2. Call `useScrollRestore(scrollRef, \`session-list-scroll-${pane.id}\`)`.
3. Attach `ref={scrollRef}` to the `<div className={sessionListScroll} data-testid="session-list-scroll">`.

`pane` is already in scope in `SessionListPaneBody` (it receives `{ pane, dispatch }`).

## Adversarial Review

**Risk 1: Race — pane remounts before `useLayoutEffect` fires**
`useLayoutEffect` runs synchronously after DOM insertion but before the browser paints — this is the correct hook for DOM mutations. No race.

**Risk 2: Key collision between multiple windows**
`key = \`session-list-scroll-${pane.id}\``. Pane IDs are generated by `paneReducer` and are UUID-based (confirmed by tracing `paneTypes`). Each window has its own pane tree with its own IDs. No collision.

**Risk 3: Stale scroll position after session list re-filter**
If the user filters the list, the number of rendered items changes and the old scroll position may be past the end. The browser clamps `scrollTop` to `scrollHeight - clientHeight`, so worst case the user is at the bottom — acceptable. The requirement says "reset to 0 if re-filtered" but the browser's clamp is the right behavior (still near the last-seen position).

**Risk 4: Board view vs list view**
Both views render inside the same `sessionListScroll` container. Switching between list and board view at a given scroll position is fine — the container scroll is restored regardless of which child is rendered. If the user wants different scroll positions for list vs board, a separate key `\`session-list-scroll-${pane.id}-${viewMode}\`` could be used, but that adds complexity for an edge case. Start with a single key.

**Risk 5: Test reliability (jsdom scrollTop)**
jsdom does not implement `scrollTop` as a writable layout property, so `element.scrollTop = 200` followed by `element.scrollTop` reads 0. The hook test must either mock the property or test behavior indirectly (verify `scrollPositions` map is populated). Use a module-level `Map` export (`export const _scrollPositions` for tests only) or spy on the element.

**Risk 6: Memory leak**
The module-level `Map` lives for the page lifetime. Pane IDs are created when panes are opened and freed when closed. A closed pane never re-uses its ID. Map entries for closed panes accumulate. In practice, a user opens at most a few dozen panes per session — negligible. Can add `delete scrollPositions[key]` in a `CLOSE_PANE` event listener if needed later.
