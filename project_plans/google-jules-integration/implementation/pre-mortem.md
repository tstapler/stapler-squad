# Pre-mortem: google-jules-integration
**Date**: 2026-09-01

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The Migration Plan re-checked only the two `IsTmuxBackedSessionRole` callers, but a separate, broader family of "does this item have an active session" predicates is hardcoded to `SessionRoleWork`/`SessionRoleReview` and never sees `jules_work`: `hasActiveSession` (`session/backlog_lifecycle.go:2037-2044`, used by the review-reopen gate at `session/backlog_lifecycle_review.go:778` and the PR-reopen gates at `session/backlog_lifecycle_pr.go:269,824`) and `hasActiveWorkSession`/`findActiveWorkSession` (`server/services/backlog_service_triage.go:1255-1271`, guarding `spawnSessionAfterGates`' 8b check and reachable from `AutoRespawnAutonomousWork`, `server/services/autonomous_orchestration_service.go:31,398`, itself driven by the default-on `autoSpawnReadyItemsEnabled` sweep, `server/services/backlog_service.go:370-372`). An item with only an open `jules_work` session reads as having **no** active session to every one of these, so the autonomous driver or a manual respawn can start a *local* Claude Code session on the same branch Jules is already working. | Two `ItemSession` rows open on the same item at once (`work` and `jules_work`), or two competing commits/PRs on what should be one branch — discovered only when reviewing a conflicted diff or a duplicate PR. | Add a new story (not folded into 2.1.1) auditing every caller of `hasActiveSession`/`hasActiveWorkSession`/`findActiveWorkSession`, not just the two `IsTmuxBackedSessionRole` sites the plan already re-read, and add an open `jules_work` row as a blocking condition everywhere they're used to gate spawning or reopening local work. | P1 |
| 2 | Requirements.md's success metric is literally "a Jules session appears in `list_sessions`/backlog UI," but `SessionService.ListSessions` (`server/services/session_service.go:1697-1710`, the RPC behind both the web UI's session list and the `mcp__stapler-squad__list_sessions` MCP tool) is built entirely from `[]*session.Instance` returned by `reviewQueuePoller.GetInstances()`/`loadInstancesWithWiring()` — never from `ItemSession` rows. ADR-001's whole design deliberately never creates a `session.Instance` for `jules_work` (that's the point — no tmux, no PTY), so a Jules session structurally **cannot** ever appear in `list_sessions` output. This is a verifiable contradiction between the requirements doc's own acceptance wording and the chosen architecture, not a hypothetical gap. | Anyone or anything that calls `list_sessions` (including an AI agent using this repo's own MCP tool to check "what's running") sees zero Jules sessions while one is actively billing and running — only `BacklogItemDetail`'s `SessionsSection` shows it. | Before implementation, either narrow requirements.md's success metric explicitly to "backlog UI (item detail page)" with a one-line note on why `list_sessions`/MCP is out of reach for this architecture, or add a task to Epic 3.3/2.4 that surfaces `jules_work` rows through `ListSessions` as a synthetic, non-`Instance`-backed entry so the literal metric holds. Don't let this surface for the first time at Phase 6 review. | P1 |
| 3 | `EgressAcknowledged` is a plain boolean on the `DispatchToJules` request that the service trusts unconditionally and permanently persists into `EgressAcknowledgedRepos` the moment it is `true` (Task 2.2.3a) — nothing distinguishes "a human just checked the box in `JulesDispatchDialog`" from "a caller passed `true` in the request body." Story 2.4.2's own rationale names this RPC as the entry point for "the web UI (and later an MCP tool)" (plan.md:815-818); once any programmatic caller — a future MCP tool, a script, an autonomous backlog driver acting "on the user's behalf" — reaches this RPC, it can silently grant and durably persist real cloud-egress consent for a proprietary repo with one boolean. This defeats the exact NFR (data residency, opt-in-not-silent) the whole design exists to satisfy, and it's the one place in the plan where "the code leaves the machine only with explicit consent" is enforced by a client-supplied flag rather than a server-side fact. | A repo shows up in `EgressAcknowledgedRepos` — and its source has already left the machine — that the user never consciously confirmed through the dialog. | Make the persisted consent artifact something only the UI path can produce: either a short-lived, dialog-issued confirmation token that `DispatchToJules` must present (not accept a bare bool), or split first-time acknowledgement into its own `ConfirmEgressConsent` RPC called only from the checkbox handler, with `DispatchToJules` itself never able to set the flag from `false`→`true`. | P1 |
| 4 | `jules/keychain.go` is explicitly modeled on `session/sshremote/keystore.go` "including its 5s D-Bus timeout guard" (Task 1.2.1a) — but that guard only unblocks the *caller*; the raced goroutine and the D-Bus/Secret Service call it's making are never cancelled, and (per `keystore.go`'s own locking) the goroutine holds the package's keyring mutex until the real op finally returns, if it ever does. `sshremote` tolerates this because SSH identity reads are rare/one-off; the Jules credential is instead re-resolved on every HTTP request (`newRequest`, Task 1.1.2a) — including once per open session per 60s poller tick. On a genuinely wedged headless keychain (a real scenario on the Linux boxes this repo targets, per the existing `keystore.go` timeout guard's own justification), every tick leaks another goroutine blocked forever on a permanently-held mutex, and every keychain call thereafter serializes behind it and times out too — a single hang permanently and invisibly disables both dispatch and polling until process restart. | Dispatch and poll both start failing with 5s timeout errors simultaneously, with no config change, no key rotation, and no user-visible cause; goroutine count climbs steadily but only shows up in a `--profile`/goroutine dump, not in normal logs. | Before Task 1.2.1a copies the pattern verbatim: don't serialize periodic reads behind one intra-package mutex a single hang can hold forever (allow independent, independently-timing-out reads), and/or cache the resolved key for a short TTL so a wedged keychain is hit once per TTL window rather than once per poll tick per open session. Add a bounded-retry/circuit-breaker acceptance criterion to Story 1.2.1 so a hung Secret Service degrades to "feature paused, log once" rather than a creeping goroutine leak. | P1 |
| 5 | `CountJulesItemSessionsSince` (Task 2.1.2a) counts every `jules_work` `ItemSession` row **created** in the last 24h, with no acceptance criterion distinguishing a row that reached a real `jules-sessions/{id}` from one that failed at `CreateSession` and ended `dispatch_failed` (Task 2.2.1b). A bad/expired key or a Jules-side outage — exactly the alpha-API instability the plan already treats as a live risk — means every dispatch attempt that day still consumes one unit of `MaxJulesSessionsPerDay` (default 15) even though nothing was billed. | Every dispatch that day returns "daily limit reached" while the settings panel shows `dispatched` and `failed` climbing in lockstep and zero real sessions ever completed — the cap message reads as a usage limit when it's actually reporting failures. | Scope `CountJulesItemSessionsSince`'s WHERE clause to exclude rows still carrying `julesPendingUUIDPrefix` or ended with `dispatch_failed`, so the daily cap tracks confirmed billed creations, not failed attempts. Add this explicitly as an acceptance criterion on Story 2.1.2/2.2.2 rather than leaving the exact query scope to implementer discretion. | P2 |

## P1 Items (address before implementation)
- [x] #1 — Resolved: new Story 2.1.3 added (Epic 2.1) widening `hasActiveSession` at its 3 call sites and adding a new `session.HasActiveJulesSession` predicate used alongside `findActiveWorkSession` at the spawn/respawn-blocking gates, with a documented guard at the one steering call site (`AutoReopenForPRFix`) left intentionally unwidened. See plan.md Story 2.1.3 and its Migration Plan cross-reference.
- [x] #2 — Resolved via option (a): requirements.md's Success Metrics narrowed to the backlog item detail page, with `list_sessions`/MCP visibility recorded as an accepted architectural tradeoff (not a gap). ADR-001 carries a short addendum note explaining the resolution.
- [x] #3 — Resolved: `EgressAcknowledged` removed from `DispatchToJules`'s request entirely. New Story 2.4.2 (`ConfirmEgressConsent` RPC) is the sole write path to `EgressAcknowledgedRepos`, callable only from `JulesDispatchDialog`'s checkbox handler; `DispatchToJules` (renumbered Story 2.4.3) can only read/check membership, never set the flag.
- [x] #4 — Resolved: Task 1.2.1a redesigned with a short-TTL cache plus a single-in-flight-probe circuit breaker (`ErrJulesKeychainPaused` sentinel) instead of copying `session/sshremote/keystore.go`'s per-call mutex-hold pattern verbatim — bounds a wedged Secret Service call to at most one blocked goroutine for the process lifetime instead of one per poll tick per open session.

## P2 Items
- [x] #5 — Resolved: Task 2.1.2a's `CountJulesItemSessionsSince` now excludes rows still in `julesPendingUUIDPrefix` reservation or ended `dispatch_failed`, so the daily cap tracks confirmed billed creations, not failed attempts.
