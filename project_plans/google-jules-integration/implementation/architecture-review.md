## Blockers

None open.

- [x] **RESOLVED — Story 2.2.1 / Task 2.2.1a vs Task 2.2.1c — `JulesDispatchService` depended on a concrete `*jules.Client`.** Task 2.2.1a (plan.md:593-597) now declares a narrow, locally-declared `julesSessionCreator interface { CreateSession(ctx context.Context, req jules.CreateSessionRequest) (jules.JulesSession, error) }`, satisfied structurally by `*jules.Client`, and states `JulesDispatchService` holds `client julesSessionCreator` — "the interface, **not** the concrete `*jules.Client` — mirrors `JulesSessionPoller`'s `julesStatusClient` pattern from Task 2.3.1a, which is exactly what lets Task 2.2.1c inject a fake." Task 2.2.1c (plan.md:604-606) confirms the test fake "implementing `julesSessionCreator`... satisfies the interface directly — no `*jules.Client` or `httptest.Server` is needed for these tests." The Domain Glossary (plan.md:48) also documents `julesSessionCreator` as its own entry with the same rationale. This matches the exact remediation this review previously requested.

- [x] **RESOLVED — Epic 2.2 / Epic 2.3 — `julesPendingUUIDPrefix`/`julesSessionUUIDPrefix` import-cycle risk between `server/services` and `session/`.** Task 2.2.1a (plan.md:596) now explicitly states: "Declare `julesSessionUUIDPrefix = "jules-"` and `julesPendingUUIDPrefix = "jules-pending-"` as local constants in this file. **Do not import them from `session/`**... This duplicates the codebase's existing precedent for `headlessTriageUUIDPrefix` (`server/services/backlog_service_triage.go:423`, re-declared as `headlessTriageSessionUUIDPrefix` for the read side at `session/backlog_lifecycle_triage.go:43-50`...)." Task 2.3.1a (plan.md:695) mirrors this on the `session/` side with the identical citation and an instruction to keep both copies byte-identical with cross-pointing comments. Verified directly against the cited source: `headlessTriageUUIDPrefix` is declared at `server/services/backlog_service_triage.go:423` (`grep -n` confirms line 423 exactly), and `session/backlog_lifecycle_triage.go:42-50` carries the comment "`headlessTriageSessionUUIDPrefix` mirrors `server/services/backlog_service_triage.go`'s `headlessTriageUUIDPrefix` constant (duplicated here rather than imported: `server/services` imports this package, so the reverse import would cycle)" with the constant declared at line 50 — both citations and the quoted rationale check out against the actual files. The Domain Glossary (plan.md:44-45) also carries matching entries for both constants. This matches the remediation this review previously requested (the "duplicate explicitly" option; the plan did not take the alternative shared-leaf-package option, which is fine — duplication-with-cross-reference is the codebase's established pattern).

## Concerns

- [ ] **Task 2.2.1a — offering `singleflight.Group`-or-`sync.Map`-of-item-mutexes as interchangeable options for the double-click guard is incorrect; only the mutex shape satisfies the story's own acceptance criteria.** Story 2.2.1's third acceptance criterion requires that of two concurrent `DispatchToJules` calls for the same item, "exactly one succeeds, the other returns `ErrJulesDispatchInFlight`." `singleflight.Group` collapses concurrent identical calls into one execution and returns the *same result* to every caller — the second caller would get the *first caller's success*, not `ErrJulesDispatchInFlight`. Only a per-item mutex (second caller blocks until the first finishes, then re-runs the in-flight check and sees the reservation) produces the specified behavior. **Remediation**: drop the singleflight option from Task 2.2.1a; specify a per-item lock (e.g. `sync.Map` of `*sync.Mutex` keyed by item ID) explicitly.

- [ ] **ADR-001 / Epic 2.2 & 2.3 — `ItemSession.session_uuid` is overloaded to encode three distinct states (plain tmux UUID / `jules-pending-<uuid>` reservation / `jules-sessions/{id}` confirmed) via ad hoc `strings.HasPrefix` checks scattered across Task 2.2.1b (write) and Task 2.3.3b (read), instead of a single parsed type — a primitive-obsession / illegal-states-representable gap on the one column this design deliberately reuses to avoid a migration.** Nothing at the type level stops a `jules_work` row from having a `session_uuid` matching neither prefix, or a `work` row acquiring a `jules-`-prefixed value by a future copy-paste bug (the exact class of error `type-driven-design` targets). This is a deliberate, ADR-recorded tradeoff to avoid a schema migration, so it is not a blocker — but the parsing should be centralized. **Remediation**: add one `ParseItemSessionUUID(s string) (kind ItemSessionUUIDKind, name jules.JulesSessionName, err error)` (or equivalent smart constructor) in `session/`, used by both the poller's reservation sweep and the dispatch service's confirm-swap, rather than repeating `strings.HasPrefix(sessionUUID, julesPendingUUIDPrefix)` inline in two places.

- [ ] **Task 2.2.3a — the dispatch service mutates `JulesConfig.EgressAcknowledgedRepos` directly ("append and persist the repo path") instead of through an owned `Config` method, breaking the aggregate's own encapsulation.** The plan does this correctly for the numeric caps (`MaxConcurrentJulesSessionsOrDefault()`/`MaxJulesSessionsPerDayOrDefault()`, clamped accessors per Task 2.2.2a) but not for the repo allowlist, where a service two layers away reaches in and appends to a slice field directly — a Tell-Don't-Ask / DDD aggregate-boundary violation (`config.Config` should own the invariant "a repo is acknowledged at most once", not the caller). **Remediation**: add `Config.AcknowledgeJulesEgressRepo(repoPath string) (added bool)` (idempotent, dedups) to Task 2.2.3a, called from the dispatch service rather than a raw slice append.

- [ ] **Epic 2.2 / Epic 2.4 — `server/services/jules_dispatch_service.go` is scoped (across Stories 2.2.1, 2.2.2, 2.2.3, and 2.4.2) to hold the interface, the value-object constructor, the full guard sequence, the reservation/dispatch orchestration, *and* the Connect RPC handler with its error-code mapping — mixing Service Layer and Interface Adapter responsibilities in one file.** Task 2.4.2b does note this "matches how `TriggerShipPR` sits in `backlog_service_ship.go`," so it is consistent with an existing repo convention rather than a novel mistake, but that file is exactly the kind of hotspot `code-hotspot-analysis` warns about accumulating unrelated concerns. **Remediation**: split the Connect handler (request/response mapping, `connect.Code*` translation) into its own file (e.g. `jules_dispatch_handler.go`), leaving `jules_dispatch_service.go` to the guard sequence and dispatch orchestration only — cheap now, harder once four stories' worth of code already share the file.

## Nitpicks

- Task 2.2.1a's `NewJulesDispatchRequest(itemID, branch, prompt string, egressAck bool)` takes `branch` as a raw `string`, but the glossary types `JulesDispatchRequest.Branch` as `GitHubBranchRef`. The task should say explicitly that the constructor calls `jules.ParseGitHubBranchRef` internally and stores the parsed type (parse-at-boundary) — as written, an implementer could store the raw string and never construct the newtype, silently defeating its purpose.
- `session/ent/schema/item_session.go`'s `session_role` field comment currently reads `"One of: work, triage, review"` (verified) and will go stale once `jules_work` lands; no task updates it. Worth folding into Task 2.1.1a alongside the `IsTmuxBackedSessionRole` doc-comment fix it already calls for.
- The repo already has a proper value type for backlog item identity (`session.BacklogItemID`, `session/backlog_item_id.go`), but `JulesDispatchRequest.ItemID` (and the rest of the plan) uses a raw `string`. This matches the codebase's pervasive existing convention (`SessionCreator`, `AutoReopenAfterFailedReview(ctx, itemID string)`, etc. are all raw strings too), so it's not a new violation introduced by this plan — just noted for the type-driven-design lens.
- `JulesDispatcher`'s declaring package is never named. The glossary calls it a "consumer-defined interface," but Task 2.4.2b's RPC handler and the `JulesDispatchService` that would satisfy the interface appear to live in the same file/package, which makes the indirection read as a test seam rather than a real ISP boundary. Worth one sentence naming which package declares it and why.
