# Adversarial Review: backlog-self-resolve
**Date**: 2026-08-02
**Verdict**: BLOCKED

## Blockers

- [ ] **FR10's claimed stuck-item surfacing mechanism does not cover FR10's actual scenario.** The plan's Observability Plan and pitfalls.md §6 both assert FR10 is "satisfied entirely by the pre-existing `pr_pending_no_pr` detector" (`reconcilePRPendingWithoutPRItems`, `session/backlog_lifecycle.go:2543-2565`). Read directly: that function's loop is gated `if item.PrNumber != 0 { continue }` (line 2553) — it **only** flags `pr_pending` items with **no** PR reference at all. FR10's actual described failure shape is the opposite: an item that reached `pr_pending` via a successful `report_pr_created` (so `PrNumber` is already set, nonzero — this is the literal premise of the requirements.md worked example, item `da58b867-...` with its own PR #281 open) and then got stuck because a *subsequent* `report_duplicate` verification call failed. That item has `PrNumber != 0`, so `pr_pending_no_pr` will `continue`-skip it forever — it is structurally invisible to this detector. The other `pr_pending`-scoped detector, `ReconcilePRPending`/`pr_ready_unmerged` (`backlog_lifecycle.go:3850+`), only fires incidentally if the item's own PR happens to be green/mergeable-but-unmerged — not guaranteed, and nothing in the plan documents or relies on that path. This claim is inherited uncritically from pitfalls.md §6 (same wrong claim) into the plan without independent verification against the actual detector code — exactly the kind of "claims to address vs. actually addresses" gap this review was asked to check. As written, FR10 (an explicit, numbered acceptance criterion) has **no working implementation path** for its "eventually surfaces through the existing stuck-item notification path(s)" half. **Recommendation**: either (a) extend `reconcilePRPendingWithoutPRItems`'s scope (or add a new, narrowly-targeted stuck reason, e.g. "pr_pending item with a logged report_duplicate verification failure") to also catch this shape — likely requiring a way to track "verification failed" state (a `BacklogStuckState`-style marker, not necessarily a schema change), or (b) explicitly narrow FR10's acceptance criterion / get owner sign-off that this gap is acceptable for v1, the way UQ-1/UQ-2 were resolved. Either way this needs a decision and a task before implementation starts, not a Phase 5 surprise.

## Concerns

- [ ] **`verifyGitHubRefExists`'s documented signature contradicts its own code sketch, and the "same 3-way contract as `verifyPR`" claim is inaccurate.** The Domain Glossary (plan.md line 52) and Pattern Decisions table (line 64) both state `verifyGitHubRefExists(ctx, ref) (bool, error)` and describe it as returning "the same 3-way contract `verifyPR`/`VerifyPRMatchesBranch` already use." But ADR-002's actual code block and Task 3.2.2a both define it as `func (h *backlogHandlers) verifyGitHubRefExists(ctx context.Context, ref *githubpkg.ParsedGitHubRef) error` — a single-return-value signature. The shapes are also *genuinely different*, not just a documentation typo: `verifyPR` keeps "definitively doesn't match" (`false, nil`) structurally separate from "transient failure" (`false, err`) in two different return values, while `verifyGitHubRefExists` folds every outcome — including "definitively doesn't exist" — into the single `error` return, disambiguated only via `errors.Is`. Confirmed against actual source: `h.verifyPR` at `server/mcp/tools_backlog.go:605` returns `(bool, error)` for real. Fix the glossary/pattern-decisions rows before implementation so an implementer skimming the summary tables doesn't build to the wrong signature — the task-level instructions (which are self-consistent) are the ones to trust.
- [ ] **ADR-003 and ADR-004 are still `Status: Proposed`, not `Accepted`**, unlike ADR-001/ADR-002/ADR-005 (all "Accepted", two explicitly "ratified by item owner"). The plan treats all five ADRs' decisions as settled ("Status: Ready for implementation"), but two of the five never went through the same explicit ratification step the plan itself uses as the bar for the other three — and ADR-003 in particular documents a real downstream-consumer risk ("any existing dashboard/query filtering `TriggeredBy == 'system'`... Grep check before merging") that seems to warrant the same sign-off ADR-002/005 got. Close this formal gap (ratify or explicitly defer) before coding starts.
- [ ] **Story 3.1.2 adds a 4th, un-enumerated refusal condition to `report_duplicate`, in tension with ADR-005's own reasoning.** ADR-005 rejects an active-reviewer refusal for `report_duplicate` on the grounds that "FR6 enumerates exactly three refusal conditions... no fourth condition appears" and treats that enumeration as the authoritative, complete list. But Task 3.1.2b then adds a *different* fourth, un-enumerated refusal ("item is at status %q — report_duplicate only allowed from in_progress or pr_pending") that also doesn't appear in FR6's literal three-item list — justified instead by the FR1/CAS-trap logic from pitfalls.md §0 ("same trap applies verbatim to report_duplicate"). The source-status whitelist is very likely still correct and necessary (skipping it would reopen the CAS-trap bug for `report_duplicate`), so this is not asking to remove it — but ADR-005's argument-by-textual-completeness is self-undermining given the plan's own Story 3.1.2 doesn't apply that same literalism. Tighten ADR-005 to explicitly carve out the source-status check as "not one of FR6's three, but independently required by FR1/FR3's CAS-safety logic" rather than leaning on "FR6's list is complete" as if it settles both questions.
- [ ] **Task 4.2.1a and Task 1.2.3b send the implementer to nonexistent files for the test-injection pattern.** Both tasks say to check `github/repos_test.go` or `github/client_test.go` for "the exact test-server-injection pattern... this repo already has one, don't invent a second." Neither file exists (confirmed: `ls github/*_test.go` → only `keychain_test.go`, `url_parser_test.go`, `user_pr_cache_test.go`; no `GetIssue` test exists anywhere today). The real, working precedent — a `resetGhBaseURL(ts *httptest.Server) func()` helper that mutates the global `github.GhBaseURL` var with a deferred restore, no `t.Parallel()` — lives in `server/services/backlog_github_rpc_test.go`. The seam itself (`github.GhBaseURL`, documented in `github/http_client.go:15-17` as test-overridable) is real and usable, so this isn't a design gap, but the plan's own citation is wrong and will send Phase 4 implementers on a dead-end search — worth noting the research phase (pitfalls.md/architecture.md) apparently didn't find the actual precedent either, since Task 4.2.1a hedges with "if none exists, add the httptest.Server approach" as if it might not.
- [ ] **Task 4.2.6a's "concurrency regression test" doesn't test what Story 4.2.6 promises.** Story 4.2.6's acceptance criteria: "`report_duplicate` racing `report_pr_created` on the same item results in exactly one status-event row and a non-retryable message **for the loser**." Task 4.2.6a's actual (garbled) construction never calls `reportPRCreated` as a racing party at all — it calls `reportDuplicate` once (which succeeds), then directly calls `storage.TransitionBacklogItemStatus` a second time with the original precondition to force a raw `ErrPreconditionFailed` at the repository layer, and asserts on `BacklogStatusEvent` row count. This never exercises `reportPRCreated`'s (or `reportDuplicate`'s) own handler-level error-message code — it can't demonstrate "a non-retryable message for the loser" because no losing *handler call* ever happens in the test as described. Rewrite this task before implementation: it needs two actual tool calls (`reportPRCreated` then `reportDuplicate`, or vice versa, on the same item) with an assertion on the second call's returned error text.
- [ ] **Task 4.1.5a's hedge offers a fallback that isn't buildable given the rest of the plan.** "...prefer testing via `requestReview` if a clean setup exists... but fall back to directly unit-testing the branch logic if not." Task 2.1.2a inlines the `errors.Is(transErr, session.ErrPreconditionFailed)` branch directly at the `TransitionBacklogItemStatus` call site inside `requestReview` — no task anywhere extracts this into a separately-callable function. "Directly unit-testing the branch logic" as a fallback therefore has nothing to call; either commit to the "seed at in_progress, race a second write" construction as the actual plan, or add a task extracting the classification logic into a testable helper (e.g. `classifyTransitionError(err) (code, message)`) if isolated unit-testing is genuinely wanted as a fallback.
- [ ] **FR2's active-reviewer guard silently disables itself on a `ListItemSessions` error, and that fallback path is untested.** Task 2.2.1b: `if lsErr == nil && hasActiveReviewSession(itemSessions) { refuse }` — else falls through and attempts the transition as if no active reviewer existed. A transient DB error during exactly the check FR2 exists to enforce produces exactly the outcome FR2 is meant to prevent (re-routing a `pr_pending` item out from under a running reviewer). This is documented only in a task-level code comment ("best-effort... CAS remains the actual safety net") and isn't obviously wrong as a design choice, but no test in Epic 4.1 (4.1.4a/4.1.4b) exercises the `ListItemSessions`-error branch — add one, or explicitly accept the gap in writing.
- [ ] **`GetPR` is real, disclosed scope growth beyond FR3/FR4's literal text** — a full new GitHub REST call, struct (`PRResult`), and two test files, where a stricter "only what FR3/FR4 literally ask for" reading could have reused the existing `GetPRInfoCtx` (gh-CLI-subprocess) path instead. ADR-002's auth-consistency argument (mixing `gh`-CLI auth with HTTP-token auth across the 3 ref kinds would produce host-dependent, inconsistent failures for functionally-identical calls) is sound and consistent with this repo's `prefer-go-git-over-subshells.md` native-over-subshell preference, and the competing draft ADR's rejection is explicitly argued through in ADR-002's "Resolution" section — this is not undisclosed gold-plating. Flagging for visibility/sign-off, not as a defect: an implementer or reviewer who only reads FR3/FR4 (not ADR-002) could reasonably ask "why did this PR add a whole new GitHub API call" without the ADR's context in front of them.
- [ ] **`allowedSelfResolveSourceStatuses` is a mutable package-level `var` (Go maps can't be `const`), shared verbatim by `request_review` and `report_duplicate`.** Nothing in the type system prevents accidental mutation (e.g., a future test doing `allowedSelfResolveSourceStatuses[x] = true` to force a code path, then forgetting to undo it). No test today exercises `t.Parallel()` in `tools_backlog_test.go`, so there's no live cross-test-pollution risk *yet*, but this is an implicit "don't mutate" invariant enforced only by convention/doc-comment, not by the compiler. Low-cost mitigation: note explicitly in the doc comment that this map must never be written to outside its declaration, or construct it via a small function (`allowedSelfResolveSourceStatuses()`) returning a fresh map if the test suite ever adopts parallelism.

## Minors

- `Note` field population is added to `request_review`'s existing precondition-building code (Task 2.1.1b, previously always empty) and to the new `report_duplicate` call (Task 3.3.1a) on the strength of ux.md's opinion, not any literal FR — FR7 only mandates `VerificationNotes` persistence, not `BacklogItemPrecondition.Note` text. Confirmed low-risk (no existing test in `tools_backlog_test.go` asserts on `Note` content, so this doesn't jeopardize FR9), but it is a behavior change to an existing, already-shipped code path motivated by a research doc rather than an acceptance criterion — worth a one-line callout for reviewer awareness rather than folding it silently into "FR1's generalization."
- Malformed/truncated JSON bodies and unrecognized GitHub status codes fall into the generic retryable `ErrInternalError` bucket for `GetIssue`/`GetPR`/`GetCommit` alike — a reasonable default (matches `report_pr_created`'s existing template) but not flagged/tested anywhere in Story 4.2.3's four tasks, and not a perfect fit for a systemic cause (e.g. an API version/shape mismatch) that "retry" framing wouldn't actually resolve.
- `github/rate_limit.go`'s `DefaultRateLimiter`/`RateLimiter.Update` is effectively dead code today: `ghHTTPClient` (`github/http_client.go:13`) is a bare `&http.Client{Timeout: 30*time.Second}` with no custom `Transport`, and grepping the whole repo finds `RateLimiter.Update` is never called from production code despite doc comments claiming "updated automatically by rateLimitTransport on every response." This is a pre-existing gap the plan doesn't introduce, but the plan adds two more callers (`GetPR`, `GetCommit`) that — like `GetIssue` today — will silently never feed `DefaultRateLimiter`, so `session/pr_status_poller.go`/`worktree_pr_poller.go`'s `IsLimited()` pre-checks stay blind to rate-limit pressure this feature's own calls generate. Worth a one-line note in the Observability Plan; not a blocker for this feature (consistent with `GetIssue`'s existing, unaddressed behavior).
- GitHub API redirects, deprecation, and version-mismatch responses aren't discussed anywhere in the plan or research docs. Low real-world likelihood for single-resource existence-check GETs against stable REST endpoints; not worth a dedicated task, but worth a one-line acknowledgment rather than silence.
- `hasActiveReviewSession` becomes a 4th independent copy of the same one-line predicate across the codebase (`server/services` x2, `session` x1, now `server/mcp`). Already self-acknowledged in the plan as consistent with existing precedent (no legal cross-package import path exists to consolidate it), so not a new problem — noted for completeness only.
