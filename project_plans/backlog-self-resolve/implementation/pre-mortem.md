# Pre-mortem: backlog-self-resolve
**Date**: 2026-08-02

Imagine `report_duplicate` + the `request_review` CAS generalization shipped a month ago.
architecture-review.md and adversarial-review.md already found and closed two real blockers
(the `strings.Contains` idempotency false-positive, and the FR10 stuck-item detector
mis-citation) — this pre-mortem does not re-litigate those. It asks: assuming those fixes are
in, what still causes this to ship without solving the origin problem (PR #281 superseded by
PR #272, item stuck at `pr_pending` with no way out), or to break quietly in the first month?
The sharpest finding (F1) is that the fix and its own safety net use two auth mechanisms that
don't overlap — so the exact failure this feature exists to prevent can recur *inside the fix
itself*, invisibly.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | **`report_duplicate` is silently and permanently broken on `gh auth login`–only hosts, and FR10's own designated safety net can't see why.** `report_duplicate`'s new `GetPR`/`GetIssue`/`GetCommit` resolve auth via `getGHToken()` — `GITHUB_TOKEN`/`GH_TOKEN` env or this app's own keychain-stored account (`github/http_client.go:29-51`) — while `ReconcilePRPending`, the exact detector the Observability Plan (plan.md:83) cites as FR10's stuck-item safety net, checks the item's own PR health via `GetPRStatus`/`IsPRMerged`, which shell out to `gh pr view` under `checkGHCLI()` (`session/git/worktree_git.go:528-544,685-698`) — a completely separate, non-overlapping auth path. A session configured only via `gh auth login` (the setup this app's own `GetPRInfoCtx` already depends on elsewhere, `github/client.go:247-263`) has `report_duplicate` fail every single call while `ReconcilePRPending` keeps functioning normally, classifying the item purely by its PR's own GitHub state with no idea `report_duplicate` ever ran. | `report_duplicate` returns `ErrInternalError` ("could not verify ... — retry") on every call from that session; retries never succeed because the missing credential never appears. `get_backlog_item` shows the item stuck at `pr_pending` labeled `StuckReasonPRReadyUnmerged`/`PRNeedsFix` — indistinguishable in the UI from an ordinary "PR needs attention" case. Nothing indicates `report_duplicate` ever ran or why it keeps failing. | Add a Phase 1/Epic 1.2 task that returns a distinct, non-generic error when `getGHToken()` yields empty — "this session has no GITHUB_TOKEN/GH_TOKEN/connected GitHub account; report_duplicate cannot verify GitHub refs here; flag for an operator" — instead of folding it into the same `ErrGitHubAccessDenied`/transient bucket a real 401/403/network blip uses. Cross-link this deliberate auth-path split in ADR-002's Consequences. Cap or name this unrecoverable case in FR10's tool-description retry guidance (Task 3.4.1a) so an agent doesn't loop identical retries against a token that will never appear. | **P1** |
| 2 | **`duplicate_ref` only proves existence, not relevance — the tool is exploitable as a generic "escape the stuck item" lever.** `verifyGitHubRefExists` (Task 3.2.2a) checks only that the cited PR/issue/commit returns 200 from GitHub. The adversarial-review-driven cross-repo decision (plan.md:479-480, "cross-repo duplicate_ref is intentionally allowed") widens this further: any real, existing GitHub PR/issue/commit in *any* repo plus arbitrary free-text `reason` is sufficient to route any `in_progress`/`pr_pending` item straight to `review`. Nothing checks the cited work actually relates to the item's own diff, branch, or description. | A reviewer opens an item routed via `report_duplicate` and finds the cited ref unrelated to the item's actual work — caught late because `BuildReviewPrompt` renders the citation once at spawn as presented fact (per FR5's own reasoning), and a reviewer (especially an AI review session skimming the prompt) may act on it without independently re-diffing the original work. | Add a validation.md acceptance criterion documenting a mismatched-but-existing `duplicate_ref` as an *accepted trust boundary*, not an oversight, and strengthen Task 3.4.1a's tool description with an explicit line that this is existence-only verification and relevance is the calling agent's own responsibility — so the tool's name ("report_duplicate") doesn't overpromise a check it doesn't perform. | **P2** |
| 3 | **FR2's active-reviewer guard and FR5's message-accuracy guarantee both fail open on a `ListItemSessions` storage error — still true in the current plan text, not a stale finding.** Task 2.2.1b (plan.md:251): `itemSessions, lsErr := h.storage.ListItemSessions(ctx, itemID); if lsErr == nil && services.HasActiveReviewSession(itemSessions) { refuse }` — on a storage error the guard is skipped and the call proceeds as if no reviewer were active, contradicting FR2's unconditional "must refuse." Task 3.3.3a (plan.md:361) has the identical shape (`itemSessions, _ := h.storage.ListItemSessions(...)`) — on the same error, FR5 emits the optimistic "Reviewer notified" text, the literal outcome FR5 says must never happen, with zero evidence either way. adversarial-review.md flagged both as CONCERNS with concrete fixes; neither has been applied to plan.md as of this pre-mortem. | During a transient DB blip, a `pr_pending` item with a live reviewer gets silently re-routed via `report_duplicate` (a second review-trigger call, or reviewer confusion), or a success message wrongly claims "Reviewer notified" while nothing is watching — surfaced only by a confused reviewer or a stray duplicate trigger in logs, since no test exists for this branch. | Apply adversarial-review.md's own recommendations before implementation: fail closed on a `ListItemSessions` error for FR2 (`ErrInternalError`, "could not verify active-reviewer state — retry"), default to the conservative "next review pass" message for FR5 on the same error, and add the two tests the review specifies (inject a storage error, assert refusal / conservative message). | **P2** |
| 4 | **`VerificationNotes` becomes an unbounded, undifferentiated append-only log across rework cycles, with no "which claim is current" marker.** Task 3.3.2a appends `oldNotes + "\n\n---\n\n" + newEntry` instead of overwriting (correctly, to avoid losing prior evidence) but nothing labels which block is the *live* claim after 2+ `report_duplicate`/rework cycles on the same `ItemSession` (duplicate claimed → reviewer bounces it back as wrong → reworked → a second, different `duplicate_ref` cited). Task 3.1.2b's own idempotency check depends on a clean per-line scan of this same growing block staying exactly delimited as expected. | A month in, an item with 3+ rework cycles renders a `VerificationNotes` wall of several `duplicate_ref=...` blocks in the once-at-spawn review-gate prompt; a reviewer (especially an AI review session skimming it) references or acts on a stale, already-rejected `duplicate_ref` instead of the newest one, since nothing marks which is authoritative. | Add a Story 3.3.2 acceptance criterion for the multi-cycle case (not just the single-append case already covered): either prefix each new entry with a marker (timestamp + "CURRENT") and demote prior entries on write, or store only the latest claim as "live" with history in a clearly-labeled section — still within FR8's no-schema-change, single free-text field. Add a test seeding two `report_duplicate`/rework cycles and asserting the rendered notes/prompt make the current entry unambiguous. | **P3** |
| 5 | **Full rollout on merge, zero staged observation window — for the one tool an unattended session reaches for exactly when something is already going wrong.** plan.md's Risk Control section (plan.md:85-88) states "not gated," "no new flag needed," "full rollout on merge... no cohort/percentage rollout mechanism exists for MCP tools" — `report_duplicate` goes from merged to available to every work session in one step. This project's own requirements.md was itself produced by "an unattended session" with "no interactive ideation interview" (requirements.md:5) — the same operating mode as the sessions that will call this tool, and the same mode whose failure to escalate is this feature's entire premise. Duplicate detection is inherently infrequent, so a defect surfaces slowly by volume alone, and the agents most likely to hit it first have no demonstrated track record of escalating "this tool behaved strangely" rather than retrying or silently giving up. | Weeks after merge, a work session hits an unexpected `report_duplicate` result (F1-F4 above, or an unknown edge case) and, absent any instruction to escalate, either retries into the same failure, abandons the item silently, or falls back to `request_review` in a state that doesn't fit — discovered only when a human happens to audit stuck/duplicate items directly, mirroring the multi-week discovery gap of the original #281/#272 incident. | Add a lightweight, no-new-infra observation step: a one-time follow-up backlog item to grep `report_duplicate` logs weekly for the first month, plus one sentence in the tool description telling a calling agent what to do if a result looks wrong ("do not retry indefinitely — leave the item and note the anomaly in your summary for human review"), so the escalation path this feature builds for backlog items also covers the tool itself. | **P2** |

## P1 Items (address before implementation)
- [x] **F1 — auth-mechanism split between `report_duplicate`'s verification path (`getGHToken()`: env/keychain) and FR10's safety net `ReconcilePRPending` (`gh` CLI via `checkGHCLI()`).** These are two genuinely independent credential stores, not the same mechanism accessed two ways — confirmed by reading both call chains directly (`github/http_client.go:29-51` vs `session/git/worktree_git.go:528-544,685-698`). A host with only `gh auth login` configured — a normal, already-supported setup elsewhere in this codebase — silently and permanently breaks `report_duplicate` while its designated safety net keeps reporting the item as a routine stuck PR. **Resolved (2026-08-02)**: the underlying auth-mechanism split is not eliminated (unifying it is out of scope for this feature — see ADR-002's Consequences), but Task 3.2.2b now classifies a missing-credential failure (the existing `ErrNotAuthenticated` sentinel) with a distinct, explicit non-retry message instead of the generic transient-retry bucket, Task 3.4.1a's tool description carries the same guidance, and ADR-002's Consequences cross-links the risk. This makes the failure legible to the calling agent and an operator instead of an infinite silent retry loop — the practical mitigation this pre-mortem asked for ("an explicit decision... before implementation, not a Phase 5 surprise").

## Notes
- F3 (fail-open on `ListItemSessions` errors) is not a new finding — it restated two adversarial-review.md CONCERNS verbatim, which were unfixed in plan.md at the moment this pre-mortem was written. **Update (resolved same day)**: both are now fixed in plan.md — Task 2.2.1b fails closed (`ErrInternalError`) and Task 3.3.3a defaults to the conservative "next review pass" message on a `ListItemSessions` error, each with a tracked Phase 4 test (`Task 4.1.4c`, `Task 4.2.5b`). This note is left in place (not deleted) as the historical record of the finding; treat it as resolved, not open.
- F2's cross-repo allowance (plan.md:479-480) and existence-only verification are *documented, deliberate* decisions, not oversights — F2 is not asking to reverse them, only to make the resulting trust boundary explicit in the tool description so a calling agent (and a future maintainer) doesn't assume "duplicate" implies a relevance check that was never built.
- Not counted as a new failure mode: the substring-match idempotency bug and the FR10 detector mis-citation are the two already-RESOLVED blockers from architecture-review.md/adversarial-review.md and are out of scope per this review's brief.
