# Pre-mortem: backlog-self-resolve
**Date**: 2026-08-02

Re-run against the **current** `plan.md` (post iteration-2 adversarial review; the
`ListItemSessions` fail-open bugs, the FR10 detector mis-citation, the substring-match
idempotency bug, and the prior pre-mortem pass's own F1 auth-split finding are all confirmed
fixed in the current text — see `Task 2.2.1b`/`Task 3.3.3a`/`Task 3.1.2b`/`Task 3.4.1a` and
the Observability Plan). This pass does not re-litigate those. It looks specifically for
what's *different*: assumptions about real GitHub/runner behavior that the plan states as
fact but that source-reading contradicts, and rollout/sequencing risk. The sharpest finding
(F1) is that ADR-005's entire justification for *not* refusing `report_duplicate` when a
reviewer is already active — "`TriggerReviewForSession`'s own idempotency" — was verified
directly against `session/review_gate.go` and does not exist; the function unconditionally
spawns a second review session.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | **ADR-005 relies on `TriggerReviewForSession` being idempotent when a review session is already active; it isn't — it unconditionally spawns a second, concurrent reviewer.** `ReviewGateRunner.Run` (`session/review_gate.go:77-352`) has no check anywhere for an existing active review-role `ItemSession` before it calls `sessionCreator.SpawnReviewSession(...)` (`:340`) and `storage.CreateItemSession(...)` (`:348`); `TriggerReviewForSession`/`spawnReviewGate` (`session/backlog_lifecycle.go:1114-1210`) likewise have no such guard. Task 3.3.3b's own text asserts the opposite ("`TriggerReviewForSession`'s own internal idempotency... is what makes this safe when a review session is already active") — this is the plan's stated justification for *not* giving `report_duplicate` an FR2-style refusal (ADR-005), and it was accepted at face value by both adversarial-review rounds rather than checked against `review_gate.go` directly. | The exact scenario FR5/ADR-005 describe as expected — `report_duplicate` succeeding while a review-role session is already active for the item — spawns a real second tmux review session and a second `ItemSession` row for the same item. Two reviewer instances now run concurrently against the same backlog item; both can reach `submit_review_verdict`, racing `applyVerdictsToACs`'s status-field writes and doubling review compute for no benefit. Visible as duplicate review sessions in the UI for one item, or a verdict that appears to flip/overwrite unexpectedly. | Before implementation: either (a) add a real dedup check inside `spawnReviewGate`/`Run` (skip spawning if `services.HasActiveReviewSession` is already true for the item) so the idempotency ADR-005 assumes actually exists, or (b) reverse ADR-005 and give `report_duplicate` the same FR2-style active-reviewer refusal `request_review`'s `pr_pending` path has, changing FR5's example from "next review pass" wording to a hard refusal. Either way, update ADR-005's Consequences section to stop citing an idempotency guarantee that isn't in the code, and add a test that actually exercises this path (seed an active review session, call `reportDuplicate`, assert only one review-role `ItemSession` exists afterward) rather than trusting the prose. | **P1** |
| 2 | **`report_duplicate`'s GitHub verification is hardcoded to github.com even though this codebase already has full GitHub Enterprise Server plumbing, used by a sibling feature, that this plan never wires in.** Task 3.2.1a calls plain `githubpkg.ParseGitHubRef(duplicateRef)`, which is `ParseGitHubRefWithHosts(input, nil)` — github.com-only regex patterns (`github/url_parser.go:282`) — instead of the host-aware `ParseGitHubRefWithHosts(input, enterpriseHosts)` that `server/services/backlog_service_sync.go:204` already calls with `s.enterpriseHosts()` sourced from `cfg.GetGitHubEnterpriseHosts()` (`config/config.go:365-376`). Separately and more fundamentally, `GetIssue`/`GetPR`/`GetCommit` all build requests via `newGHRequest` (`github/http_client.go:53-55`), which always passes `host=""` to `newGHRequestForHostWithToken` — i.e. always `https://api.github.com/` — never `ref.Host`, even though that host-parameterized function already exists and is used elsewhere in this package. No ADR, research doc, or plan section mentions GHES; this reads as an unnoticed scope gap, not a considered exclusion. | In a deployment with `GitHubEnterpriseHosts` configured, a `duplicate_ref` pointing at that GHES instance fails to parse at all — `report_duplicate` returns "not a recognizable GitHub PR/issue/commit URL" for a link that is obviously valid on the configured GHES host, indistinguishable from a parser bug. The tool is silently unusable for that class of duplicate — regressing exactly to the "no way to self-resolve" state the feature exists to fix, just for a different subset of items. (Fails closed/loud at the parse step, not silently-wrong-host — no data-corruption risk, but a real functionality gap.) | Either explicitly scope this out ("`report_duplicate` supports github.com only for v1; GHES support is a follow-up") in an ADR and the tool description, or thread `cfg.GetGitHubEnterpriseHosts()` through to `ParseGitHubRefWithHosts` at the Task 3.2.1a call site and extend `GetPR`/`GetIssue`/`GetCommit` to accept and use `ref.Host` via the already-existing `newGHRequestForHostWithToken`, matching `backlog_service_sync.go`'s own pattern. Either is a small, bounded decision — right now it's neither decided nor documented. | **P2** |
| 3 | **The idempotency no-op check is scoped to the calling session's own `ItemSession` row, not the backlog item as a whole — a rework cycle that relinks a new work-session UUID to the same item breaks the "friendly retry" path.** Task 3.1.2b's exact-retry check reads `itemSession.VerificationNotes` from the same `GetItemSessionBySessionAndItem(ctx, callerUUID, itemID)` lookup `reportPRCreated` uses today (`server/mcp/tools_backlog.go:662`) — i.e. keyed on `(session, item)`, not `item` alone. `CreateItemSession` is called fresh for each new role-episode elsewhere in this codebase (`session/review_gate.go:348` for review spawns, `server/services/backlog_service_triage.go:798/1871/2450` for rework/re-triage flows), consistent with a rework cycle handing the item to a new work-session UUID rather than reusing the original one. | An agent (or an operator re-running the same logical duplicate report from a fresh session after a restart/rework) re-issues `report_duplicate` with the identical `duplicate_ref` on an item already at `review`, expecting the documented "no-op, already recorded" success text — instead gets the generic whitelist-rejection `ErrInvalidArgument` ("item is at status \"review\"...") because the new session's own `ItemSession.VerificationNotes` is empty. Confusing, not corrupting: item state is still correct, but the tool's own documented idempotency guarantee (Task 3.1.2b's third GWT) silently doesn't hold across a session-UUID change. | Add a Story 3.1.2 acceptance criterion and test for the cross-session case: seed the idempotent marker on a *different* `ItemSession` for the same item (not the caller's), and assert whether the current design intentionally refuses (documenting that idempotency is per-session, not per-item) or should look the marker up item-wide instead. Right now this is unspecified, not decided. | **P2** |
| 4 | **All new-behavior test coverage is batched into a single terminal Phase 4, after ~30 production-code tasks across Phases 1–3 land — if the implementation pipeline stops or is reviewed for merge before Phase 4 completes, `go build`/`make ci` stay green with zero regression coverage for the exact CAS/idempotency/refusal-ordering invariants both adversarial-review rounds spent most of their effort on.** Phases 1–3 (Epics 1.1 through 3.4) are pure production code; Phase 4 (Epics 4.1–4.4) is where every new test — including the two `ListItemSessions`-fail-closed tests, the ordering-safeguard stub, and the idempotency tests — actually gets written. Nothing in the plan's Dependency Visualization or task structure makes Phase 4 a hard gate on "PR-mergeable"; it's just the last phase in task order. | A PR opened after Phase 3 (or a `sdd:5-implement` run that pauses/context-exhausts there) shows a complete-looking `report_duplicate` implementation with passing `make ci` (the *existing* suite, untouched, still passes) and no visible signal that the new code's own safety properties are unverified — discoverable only by a reviewer noticing the task/story list isn't fully checked off, not by any automated gate. | Interleave each Epic's tests with its own implementation tasks (or at minimum make `sdd:6-verify`/`sdd:7-ship` refuse to proceed unless every Phase 4 task is checked off, not just "tests exist somewhere") rather than batching all coverage into one terminal phase — the epics in Phases 2–3 already group by feature area, so a same-epic test story is a small reorganization, not a re-plan. | **P2** |
| 5 | **Existence-only, cross-repo-permitted verification means "duplicate" is unfalsifiable by the tool itself — the mitigation an earlier pre-mortem pass recommended (disclose this as an explicit trust boundary in the tool description) was never actually added to the shipped description text.** `verifyGitHubRefExists` only checks that the cited PR/issue/commit returns 200; nothing checks it relates to the item's own diff/branch/description, and cross-repo refs are explicitly allowed (Task 4.2.2f). Task 3.4.1a's registered tool description (plan.md's 7 enumerated points) covers role, preconditions, consequence, idempotency, and FR10 retry guidance — but no point states that verification is existence-only and relevance is the calling agent's responsibility. | A reviewer (human or AI, skimming `VerificationNotes` rendered once at review-gate spawn per FR5) encounters an item routed via `report_duplicate` where the cited ref is real but unrelated to the item's actual work — caught late, and nothing in the tool's own description warned the calling agent this check doesn't happen, so neither side had reason to double-check. | Add the disclosure line to Task 3.4.1a's description (e.g. "This only confirms duplicate_ref exists on GitHub — it does not verify relevance to this item's work; that judgment is yours.") — a one-line, zero-risk addition that closes a gap already identified once and dropped before reaching plan.md. | **P3** |

## P1 Items (address before implementation)
- [x] **F1 — RESOLVED (2026-08-02).** Verified directly against `session/review_gate.go:77-354` (full function body, every `CreateItemSession`/`CreateItemSessionWithVerdict`/`SpawnReviewSession` call site) — confirmed no active-reviewer dedup exists anywhere in the spawn path. Chose a third option, narrower than either alternative this row originally proposed: rather than (a) adding a dedup check inside the shared `spawnReviewGate`/`ReviewGateRunner.Run` infrastructure (broader blast radius — used by every review-gate spawn path in the codebase, not just this feature) or (b) reversing ADR-005 to add a hard refusal (would make FR5's literal text permanently unreachable, reopening the exact tension ADR-005 resolved), the fix is scoped entirely to this feature's own code: Task 3.3.3b now makes the `TriggerReviewForSession` call **conditional** on the same `activeReview` boolean Task 3.3.3a already computes for message branching (`if h.reviewTrigger != nil && !activeReview { ... }`) — `report_duplicate` still succeeds and transitions the item while a reviewer is active (FR5's premise intact), it just skips redundantly triggering a second spawn since one is already running. ADR-005 itself never cited the false idempotency claim (that assumption lived only in Task 3.3.3b's now-corrected prose) — no ADR edit was needed. Task 4.2.5a extended with a regression test asserting the trigger is *not* called in the active-reviewer branch and *is* called in the normal branch.
