## Blockers

- [ ] **B1. BUILD files placed inside the tmux git submodule and in a `.bazelignore`d path.** Tasks 0.7a/0.7b/3.3a and Story 0.7 AC put `third_party/tmux/BUILD.bazel` and target `//third_party/tmux:tmux_bin`, but `third_party/tmux` is a gitlink (`git ls-tree HEAD third_party/tmux` -> `160000 commit 7f2a35ad...`; `git check-ignore -v third_party/tmux/BUILD.bazel` -> "Pathspec ... is in submodule"), so the file cannot be committed, and Task 0.2a also puts `third_party/tmux` in `.bazelignore`, which makes the package invisible to Bazel anyway. Every tmux task, Story 4.5's `TMUX_BIN`, and the P5 embed checksums depend on that label. Recommendation: put the tmux rules in a tracked directory that is not the submodule (for example `third_party/tmux_bazel/` or `tools/bzl/tmux/`), keep the submodule path in `.bazelignore`, and rewrite all labels and verify commands. Also decide in Task 0.7c whether the tarball replaces the submodule (the gitlink is a commit on branch `3.8` per `.gitmodules`, not necessarily the release tarball, so `check-tymux-pin.sh` equality needs a stated rule).

- [ ] **B2. `//build:embed_tmux`, `//build:embed_tymux` and `build/windows/BUILD.bazel` live in a directory that is gitignored and `.bazelignore`d.** `.gitignore:99` contains `build/` (output dir; `build/windows_amd64` exists locally) and Task 0.2a lists `build` in `.bazelignore`. Tasks 0.8b, 3.3c, 6.1a and Story 6.1's target `//build/windows:stapler-squad_windows_amd64` would be untracked and unloadable. This fails Spike S7 for a reason unrelated to the spike question, and then breaks Epics 3 and 6. Recommendation: move flags to a tracked package such as `//bazel/flags` and `//bazel/windows` (or `//tools/bzl/...`), and add a check in Task 0.2a that every BUILD location named in the plan passes `git check-ignore` and is not in `.bazelignore`.

- [ ] **B3. ADR-004's "PR jobs are read-only" is a client-side flag, not a control, and the credential path is unspecified/likely wrong.** (a) `--noremote_upload_local_results` is set in `.bazelrc`/workflow files that a same-repo PR branch controls, so any PR branch (agents open many) running with the onyx credential can write. bazel-remote's htpasswd auth has no read-only role: [buchgr/bazel-remote#628](https://github.com/buchgr/bazel-remote/issues/628) (open feature request; the suggested workaround is a read-only proxy; I could not confirm it was resolved). `--allow_unauthenticated_reads` is the only read/write split. Same for the Tailscale key: a PR-modified workflow can use it. (b) Task 7.4a says credentials via `--remote_header` "from env"; `.bazelrc` is not an env-expanding file (not confirmed in docs here, UNVERIFIED but I know of no expansion), so the likely implementation is `--remote_header=Authorization=Basic <secret>` on the command line, which lands in process args, `--build_event_json_file` (`bep.json` is uploaded as a public artifact by Task 1.3b on a public repo) and `--profile`. Whether Bazel redacts it is UNVERIFIED. Bazel has a purpose-built mechanism: [credential helpers](https://www.github.com/bazelbuild/proposals/blob/main/designs/2022-06-07-bazel-credential-helpers.md), recommended over static headers ([EngFlow](https://blog.engflow.com/2023/10/09/configuring-bazels-credential-helper/)). Recommendation: amend ADR-004 and Story 0.12/7.4 to (1) enforce read-only server-side (reverse proxy permitting only GET/HEAD for the PR credential, or `--allow_unauthenticated_reads` over the tailnet only with a write credential reachable solely from `push: main` via a GitHub environment with branch protection); (2) use `--credential_helper` reading an env var, never a header on the command line; (3) add an AC that `bep.json`/`profile.gz` are grepped for the secret and the upload step fails if found; (4) Tailscale tag ACL limited to onyx:port. Must be settled before the owner deploys and credentials onyx (Task 0.12b).

## Concerns

- [ ] **C1. Ordering error: P9 needs Epic 9's script before the parity gate can pass.** Story 7.5 row P9 uses `scripts/bazel-manual-instance.sh` (Task 9.1c), but Epic 9 is sequenced after Epic 8 and 7.6a/8.6 require `PARITY: PASS`. Move Task 9.1c into Epic 7 (or before 7.5) and update the wave list (W10 does not mention it). Similarly the `owner-attestations.yaml` rows for P8/P9 are needed by 7.5c.

- [ ] **C2. The make fallback rots exactly when it matters.** (a) Task 7.6a keeps `legacy-*` jobs but Task 7.6d deletes `detect-feature-changes.sh` and the regex blocks those jobs rely on, so after 7.6d no PR-time job exercises the make path. (b) The weekly canary (Task 8.5a) runs only `BUILD_SYSTEM=make make build` plus "the short test set": no lint/ready, no e2e on the make binary, no install path. (c) Task 10.1a's check ("fails any PR that edits a file only to satisfy Bazel layout, via a `bazel-only` label") is not mechanically decidable. Recommendation: canary runs `make ready` and one e2e shard on the make binary; run it on every PR touching `Makefile`, `go.mod`, `proto/**`, `session/ent/schema/**`; replace 10.1a with a decidable rule (for example: the canary job is required on PRs for the retention window, and it is the guard).

- [ ] **C3. Several spike pass criteria cannot fail.** Task 0.3b ("exits 0, or the diff is pasted and explained"), 0.6b ("equals 0 or lists each path with a fix"), 0.2c ("or record failing fixtures"), 0.9a (table has 10 rows is a format check, not an outcome), 0.10a ("or recorded as a failed pass criterion with the fallback applied"), Story 0.6 AC ("equal or each delta explained"). Spike protocol caps runs but the verdict assignment is judgment. Recommendation: define in each spike a numeric/boolean line `PASS iff ...` and a rule that any "explained delta" maps to `FallbackWorkaround` unless the delta list is on a pre-approved allow-list (for example minifier banner only).

- [ ] **C4. Fallbacks that share the failed dependency.** S1's TS half and Story 2.2 depend on `protoc-gen-es` from the Bun install (ADR-003), so an S4 failure (hermetic Bun repository rule: network, postinstall scripts, platform binaries) also fails S1's TS acceptance, and S4's fork path costs L+L+M+S. S5's final fallback (genrule with host cc) removes hermeticity, a co-equal driver, for the tmux artifact that the embed config and P5 checksums depend on. S10's fallback `actions/cache` disk cache is "zero infra" but cannot give the cross-worktree sharing the worktree-cost driver wants (this is local disk cache, fine) and gives weak CI win, with P10 still required to pass. Recommendation: add to the fallback matrix an explicit "if S4 Fail" column listing the S1/S3/Story 2.2 consequences, and an owner decision pre-registered for "hermeticity downgraded for tmux" before 0.14 so the gate is not a surprise.

- [ ] **C5. S1 offline proto generation: unaddressed BSR dependency.** `proto/buf.yaml`... (root `buf.yaml`) declares `deps: buf.build/googleapis/googleapis` and no `buf.lock` exists (`ls proto/buf.lock buf.lock` -> both missing); `git grep googleapis -- proto` finds no use. A `buf generate`/`buf_lint_test` action in a sandbox with `--sandbox_default_allow_network=false` (Story 0.4 AC and S1 "no network") will try to resolve the dep. How `make proto-gen` currently resolves it is not in the plan. Recommendation: Task 0.3 must establish whether the dep is used; if unused, remove it in an inert PR before Epic 0 ends; otherwise vendor via `buf.lock` and rules_buf `buf_dependencies`.

- [ ] **C6. ent output is many Go packages, not one.** Story 0.4/Task 0.4b treat the tree as feeding "`//session/ent`", but ent generates `session/ent` plus subpackages (`migrate`, `predicate`, one per entity). A single tree-output rule cannot yield several `go_library`s with distinct importpaths without a package list that changes with the schema. S2's pass criterion (`UpsertRule` symbol present, build hash-equal) does not test that every importer package resolves. Add to the S2 criterion: `bazel build //server/... //session/...` resolves all importers of every ent subpackage, and state in the plan how the package list is derived (macro reading a checked-in list guarded by a freshness test, or one rule emitting several `GoInfo` providers).

- [ ] **C7. Baselines are narrower or noisier than the claims built on them.** (a) Task 0.1a measures `build.yml` only; `lint.yml`, `mcp-integration.yml` and e2e workflows also gate merge, so "time-to-green" is the max of required workflows, not one run. (b) P10 "p50 not worse than baseline" has no tolerance for GitHub runner variance, so it can fail or pass by noise. (c) Cold-build/disk baselines (Task 0.1b) are timed on a shared host (free -g: 61 GB total, 39 GB used at review time) that also runs agent sessions; "run it alone" is not enforceable. (d) The two "30%" criteria differ: Story 0.10 compares second Bazel worktree to first Bazel worktree; P10 compares to the make baseline median. (e) `ci-time-to-green.sh` filters `event=pull_request` success runs, which excludes the skipped/short paths and biases the baseline. Recommendation: define time-to-green as last-required-check-completion minus first-start for the same head SHA, add a tolerance (for example +10% p50 and a minimum n), record host load next to each timing, and unify the 30% definition.

- [ ] **C8. `exclusive` tags and `-p 1` mapping.** Task 4.5a maps make's `-p 1 ./session ./session/mux ./session/tmux ./testutil` to `tags = ["exclusive"]`. `exclusive` makes each such test run alone in the whole invocation, serialising CI and hurting P10, while the real need (Makefile:693-702, 802) is isolation from each other, which per-test private sockets (Task 4.1b/4.5) would remove. Recommendation: first make them parallel-safe with unique `STAPLER_SQUAD_TMUX_SOCKET` (per Story 4.5 already) and use `exclusive` only for tests that still fail the `--runs_per_test=3 --jobs` stress; measure the impact in 7.5d.

- [ ] **C9. Soak criterion and flakes.** "N consecutive green PR runs" (default 30) is unmet by construction while BUG-087..090 flakes exist, and Task 4.9b fixes only flakes Bazel exposes. The resolution of N is listed as an owner question that blocks 7.6a but the proposal text is two incompatible rules ("30 PRs or every PR for the same period of 10 main merges, whichever is later"). Recommendation: define soak as green-rate over a window with failures attributed (flake vs real) and a max count of unattributed failures; owner fixes N before Epic 7 starts, not at 7.6a.

- [ ] **C10. Owner-attestation file is agent-writable and CODEOWNERS does not exist.** P8/P9 and the flip/retention gates read `project_plans/.../owner-attestations.yaml`, and `.github/CODEOWNERS` does not exist (`ls` -> No such file), created only in Story 11.6 (late). An agent PR can satisfy the gate by editing the yaml. ### Adversarial questions answered

- **Can a PR obtain the write credential?** Not by editing a workflow: the write password and `TS_AUTHKEY_MAIN` live only in environment `bazel-cache-write` restricted to branch `main`; a PR-branch job asking for that environment is rejected by GitHub. Auth keys (not OAuth clients) are pre-tagged, so a PR cannot choose `tag:ci-main` on its own key. Fork PRs get no secrets. Edits to `credential-helper.sh` in a PR only matter in a job that holds a secret, and PR jobs hold only the read key.
- **Can a PR reach `:9093`?** Only through the ACL (`tag:ci-pr` -> `:9092`); Tailscale default-deny makes that a real control provided the ACL has no broader grant (N5). The S10 check "tag:ci-pr reaching :9093 is refused" is a real network test and can fail.
- **Does `--credential_helper` keep the secret out of BEP/profile/execution log?** The helper moves the secret off the command line, which removes the one place it was certain to be copied (command line goes into BEP options and the profile). The Bazel proposal ([credential helpers](https://www.github.com/bazelbuild/proposals/blob/main/designs/2022-06-07-bazel-credential-helpers.md)) and [EngFlow](https://blog.engflow.com/2023/10/09/configuring-bazels-credential-helper/) recommend it for that reason, but I found no Bazel doc that guarantees the header value is never logged (UNVERIFIED). The plan correctly treats it as unverified and tests it.
- **Is the S10-redaction spike falsifiable?** Yes: `grep -c` sum must be 0, and nonzero maps to `FallbackWorkaround`. Gaps in N3.
- **Spike `PASS iff` spot check** (S1, S2, S5, S6, S10, S11, Story 0.6, 0.3 verify): all are boolean or numeric, with "unevaluable = Fail" and an allow-list; the earlier C3 is fixed. S2 now includes importer resolution (C6 fixed). C1 ordering fixed (P9 script moved to Task 7.5e, Task 9.1c reduced to docs). C10 CODEOWNERS now in Story 0.2.

### New concerns

- [ ] **N1. gRPC cannot pass through a GET/HEAD-only listener.** Task 7.4a and the black-hole test use `grpcs://<onyx>:9092`, but gRPC requests are HTTP/2 POST; the read-only proxy rule "reject every method except GET/HEAD on `/cas/` and `/ac/`" would break Bazel, and the opposite fix (allow POST) reopens writes (gRPC `UpdateActionResult`/`BatchUpdateBlobs`). The S10 probe uses a blob GET, so it would pass while the real Bazel config never works. Fix: use the HTTP cache protocol (`https://onyx:9092`, Bazel GET/PUT on `/ac/` `/cas/`) for both listeners, and make the S10 read test a real `bazel build` with remote cache hits greater than 0 through `:9092`.
- [ ] **N2. Unauthenticated reads vs htpasswd is unspecified.** Task 0.12a configures bazel-remote with `--htpasswd_file` for the write user. Reads proxied through `:9092` then need either `--allow_unauthenticated_reads` on bazel-remote (fine since it is loopback-only behind the proxy) or a proxy-injected credential. State which one; otherwise `:9092` returns 401 and the probe fails for a non-spike reason.
- [ ] **N3. Redaction test coverage is narrower than the leak surface.** (a) The helper emits `Authorization: Basic base64(user:pass)`; the canary grep must cover both the raw password and the base64 string. (b) Add `--remote_grpc_log`/`--remote_http_verbose` outputs (if used), `--remote_cache` failure paths (run once with a deliberately wrong credential so 401 messages are exercised), and the `bazel-out`/`command.log` to the grep set. (c) The `Authorization` grep in the secret-scan step can match benign text; define the allowed exceptions or it will be disabled the first time it false-positives.
- [ ] **N4. Writes are gated by the `main` ref, but `main` is unprotected.** D-PROTECT leaves `main` without a ruleset, so any holder of a push token (including agent tokens) can push directly to `main` and thereby run the write job with the cache credential, or edit `credential-helper.sh`/`bazel.yml` there. ADR-004 calls this "the owner's own trust boundary", but agent sessions here do hold repo push rights. Make a `main` ruleset (no direct push except owner) a prerequisite of Task 0.12b rather than a Story 7.6 decision, or record it as an explicit accepted risk in ADR-004.
- [ ] **N5. Tailscale details not pinned.** (a) The ACL must be default-deny with no `autogroup:member`/`*:*` grant that also covers `tag:ci-pr`, and `tagOwners` must restrict who can create each key; add a check that dumps the ACL JSON and asserts it. (b) `TS_AUTHKEY_PR` is a repo secret any same-repo PR can echo to an artifact or external host; the stated residual risk covers repo writers, but a leaked reusable key is usable off-GitHub until expiry. Require ephemeral, pre-approved, short-expiry keys with rotation, and pin the `tailscale/github-action` SHA. (c) State that no workflow uses `pull_request_target` or `workflow_run` that checks out PR code with secrets (grep returns no mention in the plan; add an actionlint/grep rule to Task 7.4b).
- [ ] **N6. The write path is verified only once.** After the S10 spike, `ci-cache-write` runs only on push to `main`; add the secret-scan and a periodic canary (hit rate drop to 0 or PUT 4xx on `:9093` from `main`) so a silently broken write credential does not erode cache hits unnoticed. Minor.
