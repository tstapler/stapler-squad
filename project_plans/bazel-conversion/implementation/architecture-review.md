# Architecture Review: bazel-conversion
**Date**: 2026-11-01
**Verdict**: BLOCKED

Scope: `implementation/plan.md` (all 1674 lines), `requirements.md`, ADR-001..008, with `research/architecture.md` and `research/pitfalls.md` consulted. Plan claims were checked against the repo with commands; each finding says VERIFIED (command run) or INFERRED.

**Constitution check**: `docs/adr/ADR-000-architecture-constitution.md` does not exist (`ls docs/adr | grep 000` is empty). No constitution violations.

**kibitzer**: on `PATH`, but `.claude/inspect.json` configures only `go-primitive-obsession`, with no layering, coupling or component-deps checks. It adds nothing to Lens 1/4, so the review rests on plan text plus `go list` and `git ls-files`.

## Blockers

- [ ] **B1. Stories 0.7, 3.3, 4.5 (Tasks 0.7a, 0.7b, 3.3a, 3.3c, 3.3d); Task 0.2a `.bazelignore`** — The plan puts `third_party/tmux/BUILD.bazel` (target `//third_party/tmux:tmux_bin`) inside a git submodule path and also lists `third_party/tmux` in `.bazelignore`. Both are impossible. VERIFIED: `.gitmodules` declares `third_party/tmux` as a submodule, so the superproject cannot track a file under it (the path is a gitlink). A `.bazelignore`d directory is invisible to Bazel, so a BUILD file there would not load even if it existed. The plan's own `third_party/tmux_bin` label, the `TMUX_BIN` test wiring (4.3c, 4.5), and the Epic 3 fresh-worktree AC all depend on this label. The S5 spike would pass in a working tree where the file was never committed, and then Story 3.3 would fail on a clean clone.
  **Remediation**: Move every tmux Bazel target outside the submodule path, for example `//tools/bzl/tmux:tmux_bin` or `//third_party/tmux_build:tmux_bin`. Source it from the pinned release tarball via `http_archive` (the plan already prefers the tarball) and never from the submodule checkout. Keep `third_party/tmux` in `.bazelignore` and `gazelle:exclude` and say so in 0.7. Rewrite the labels in 0.7, 3.3, 4.3c and 4.5, and in `docs/reference/bazel-targets-and-configs.md`. Add an AC to 0.7: "`git ls-files third_party/tmux` shows only the gitlink; `bazel build <tmux label>` passes on a clean clone".

- [ ] **B2. Task 0.2a `.bazelignore`; Tasks 0.8b, 3.3c (`//build:embed_tmux`, `build/BUILD.bazel`), Story 6.1 (`build/windows/BUILD.bazel`), Story 1.4** — `build` is listed in `.bazelignore`, and it is also the home of the `TagConfig` bool flags and the Windows cross-compile target. VERIFIED: `.gitignore:99` contains `build/` (the only exception is `!/web-app/build/`), and `git check-ignore -v build/x` matches. So the files `build/BUILD.bazel` and `build/windows/BUILD.bazel` would (a) be gitignored and never committed, and (b) be invisible to Bazel because of the ignore entry. This breaks the `select()` that wires every embed (ADR-007), `--config=embed_tmux`/`embed_tymux`, the release config, and the `windows_amd64` artifact. It would also pass locally in the spike worktree and fail on a clean clone.
  **Remediation**: Rename the Bazel-owned package to a tracked, non-ignored path, for example `//tools/bzl/flags:embed_tmux` and `//tools/bzl/windows:stapler-squad_windows_amd64`. Keep `build` in `.bazelignore` as the make output directory. Update 0.8b, 1.4, 3.3c, 6.1 and the Glossary. Add a verify step: `git check-ignore <every planned BUILD.bazel path>` must print nothing.

- [ ] **B3. Task 4.1a (`testutil/repo_root.go`) and every Epic 4 consumer (4.3b, 4.4b, 4.6a-c, 4.7a)** — `RepoRoot()` is placed in the existing `testutil` package, and the plan states "no import of rules_go packages" but does not check what `testutil` itself imports. VERIFIED: `go list` shows `testutil` imports `executor`, `executor/safeexec`, `session` and `session/tmux`, and `go list -deps ./testutil` includes `stapler-squad/config`. `config` tests are `package config` with no `testutil` import today, and `session` imports `config`. A `package config` or `package session` test importing `testutil` is an import cycle (`import cycle not allowed in test`). Tasks 4.6a (config) and 4.4b (session) would hit it on the first compile. The Epic 4 remediation of the six worst packages depends on this helper, so the failure would surface only after Epic 4 starts.
  **Remediation**: Make the helper a leaf package with only stdlib imports, for example `testutil/repo` (`package repo`, `repo.Root()`), or `internal/testenv`. Add a Tech Debt Disposition row: "`testutil` is a fat, session-aware package (Isolate via seam: new leaf package)". Change the 4.1 AC to "`go list -deps ./testutil/repo` contains no `stapler-squad/` package". Add the same leaf-package rule to the env-default helpers (`t.Setenv HOME` helpers) in 4.3c and 4.6a, which have the same cycle risk.

## Concerns

- [ ] **C1. Story 1.1 (Task 1.1a) vs Stories 2.1b, 2.3b — Gazelle resolve lines land after the BUILD files they affect.** Story 1.1 commits BUILD files for all ~3,373 tracked-`.go`-file packages and requires a clean Gazelle diff. At that point `gen/proto/go/...` and `session/ent` imports are unresolved, because `gazelle:resolve` is added later in 2.1b/2.3b. The committed deps for every importer would be wrong labels, then rewritten wholesale in Epic 2: large generated churn, and a gate that passes with wrong content. The labels are fixed strings that are known before codegen exists. *Recommendation*: land the `# gazelle:resolve` / `gazelle:exclude` lines for `gen/` and `session/ent` in Task 1.1a (labels can point at targets that do not exist yet), using the S11 verdict. Epic 2 then only adds the targets. Also state in 0.11b that the exclusion pattern for `session/ent/*` generated entity directories must spare the tracked `session/ent/schema` (VERIFIED: the only tracked files under `session/ent` are `schema/*`; 47 files).

- [ ] **C2. Task 1.1c / Story 1.4 / P2 — `--config=race` vs `build:linux --...:pure`.** Linux is set to pure Go, and `race` is a TagConfig that needs cgo. INFERRED (rules_go treats race and pure as mutually exclusive; not run). The text says race "needs a host C compiler" but does not turn pure off. *Recommendation*: add `build:race --@io_bazel_rules_go//go/config:pure=false --@io_bazel_rules_go//go/config:race`, and add to spike S7 (Task 0.8a) the criterion "`--config=linux --config=race` builds". Also note that the race and non-race configs produce different action keys, so the two P1/P2 runs do not share cache.

- [ ] **C3. Task 1.4b vs Tasks 3.5a / 11.3b — sealed set checked against a doc that does not exist yet.** `check-configs.sh` compares `.bazelrc` configs with `docs/reference/bazel-targets-and-configs.md`. That page is first created in Story 3.5, with its full content in Story 11.3, so the Epic 1 verify command has nothing to compare against. *Recommendation*: make a machine-readable list the source of truth (`tools/bzl/configs.txt`, created in 1.4a) and have the doc page checked against it later.

- [ ] **C4. Story 2.4 (Task 2.4b) vs Story 8.1 — `BUILD_SYSTEM` used before it is defined.** 2.4b makes `make sync` "honour `BUILD_SYSTEM`" and adds `gen-freshness` to `make ready`, but `make/bazel.mk` and the validation come in 8.1. Under the default `BUILD_SYSTEM=make`, adding `gen-freshness` to `make ready` makes the make path require Bazel (it hashes against `bazel-bin`), which breaks the fallback-independence the plan promises, and the weekly `FallbackCanary` (8.5) would be forced to install Bazel. *Recommendation*: create the `BUILD_SYSTEM` skeleton and validation (a small `make/bazel.mk`) in Epic 1 or at the start of Epic 2. Add `gen-freshness` to `ready` only when `BUILD_SYSTEM=bazel` or when `bazel` is on `PATH` and `.bazelversion` exists. State explicitly that `FallbackCanary` runs with no Bazel installed.

- [ ] **C5. Story 7.6 and the Unresolved Questions — there is no branch protection to rename.** VERIFIED: `gh api repos/tstapler/stapler-squad/branches/main/protection` returns 404 "Branch not protected", `rulesets` has length 0, and `mcp-integration.yml` comments that main has no required checks. Task 7.6b/the "required-check renames" question and the 7.6 AC (reading protection) are written for a state that does not exist, and "blocking" means nothing without protection. *Recommendation*: replace with "owner decides whether to enable branch protection and which jobs to require at the flip" and make the flip a protection-creation step (owner action) or define "blocking" as the job without `continue-on-error`. Remove the rename blocker from the wall-clock list.

- [ ] **C6. Story 7.3 / Task 7.6d / Tech Debt row "Three hand-maintained regex lists" — the premise is partly wrong.** VERIFIED: `mcp-integration.yml` uses native `paths:` filters (0 `grep -E` lines), `tools/ci/detect-feature-changes.sh` has 0 `grep -E` matches, and `build.yml` has 1. The plan's "delete the `grep -qE` blocks in `mcp-integration.yml`" (7.6d) targets code that does not exist, and Task 7.3c's "replay the three regex lists" needs per-list replay logic for three different mechanisms. *Recommendation*: Task 7.3c should first inventory the actual selection mechanisms (`paths:` filters, `detect-feature-changes.sh`, the `build.yml` regex) and name the retained non-Bazel path filters (`tests/e2e/**`, `docs/registry/**`, `website/**`, `.github/**`, Playwright and jscpd inputs, none of which are Bazel targets) in `tools/bzl/global-inputs.txt` or a sibling list. Also specify handling of deleted and renamed files in `rdeps(//..., set(files))` (a file removed by the PR is not in the graph and the query errors) and of files in `.bazelignore`d dirs.

- [ ] **C7. Task 0.3c vs Story 0.6 and the wave plan — spike dependency inversion.** 0.3c (TS generation) needs `protoc-gen-es` "from the web install", which is the Bun repository rule built in 0.6a, but W2 schedules 0.3 before 0.6 (W3). Likewise 2.2a already notes that it depends on 3.1a. *Recommendation*: split TS into its own spike step placed after 0.6a, or have 0.3c use a pinned `protoc-gen-es` fetched by `http_archive`/`npm` tarball and then reconcile in 2.2. Reflect it in the wave list.

- [ ] **C8. Task 3.1a / ADR-003 / ADR-004 — `no-remote-cache` applied to a repository rule.** Tags such as `no-remote-cache` apply to targets and actions, not to repository rules; `bun install` inside a repository rule is not remote-cached anyway. INFERRED. The real exposure is the actions that consume the node_modules repo (the `dist` action, Jest, `protoc-gen-es`): their input digest changes if the install is not byte-reproducible, which causes cache misses, not poisoning, but the plan frames it as a poisoning guard. A second, unaddressed cost is the input-set size: tens of thousands of files in node_modules staged into every sandboxed web action. *Recommendation*: apply `no-remote-cache`/`no-sandbox` tags on the consuming web actions, and add a measurement to S4 (Task 0.6b) for sandbox setup time with the real `node_modules`. Reword Story 7.7 accordingly.

- [ ] **C9. Task 0.2a `.bazelignore` — entries are exact paths, not patterns.** `node_modules` ignores only the root-level directory. VERIFIED nested trees exist (for example `web-app/node_modules`, which the plan lists, plus `tests/e2e`, `website` and others). Gazelle also needs matching `gazelle:exclude` entries (it does not read `.bazelignore`). *Recommendation*: enumerate every nested `node_modules` path via `find . -name node_modules -prune`, and add `# gazelle:exclude **/node_modules` in the root BUILD. Add a check to Task 0.2a ("`bazel query //...` and `gazelle -mode=diff` touch no path under a `node_modules`").

- [ ] **C10. Story 0.14 / Spike protocol — `SpikeVerdict` is a sum type in name only.** Verification is `grep -cE 'Pass|FallbackWorkaround|FallbackFork|Fail' spike-results.md` at least 12, which also matches the word "Fail" in prose and does not tie verdicts to spike ids. *Recommendation*: make the verdict a machine-readable table (`spike-results.yaml`: `{spike, verdict, path, cost}`) validated by a 10-line script that rejects unknown values and missing spikes. This also gives Story 0.14 a gate that downstream tasks (for example Task 8.4's "skipped if S12 is Fail") can read.

- [ ] **C11. Epic 4 packaging (Tasks 4.3, 4.4, 4.6, 4.7) — batching by package rather than by `SandboxClass`.** The Glossary and 0.9 say fixes are batched by class and "fix once at the source", but Epic 4 stories are one-per-package (4.3 `server/services`, 4.4 `session`, ...). Classes like `cwd` and `home` recur across all of them, so the same helper/refactor is rediscovered four times. *Recommendation*: reorder Epic 4 so per-class sweeps (cwd/`runtime.Caller`, HOME, tmux socket, git env, fixed ports) come first, using the S8/S9 census, with per-package stories as the residual tail. This also lowers the chance that the six worst packages absorb the shared-helper design work.

- [ ] **C12. Tech Debt Disposition table — missing entries.** Needed rows: (a) `testutil` fat package (B3); (b) the `session/ent/generate.go` reference: `CLAUDE.md` says it is hand-written and tracked, but VERIFIED `git ls-files | grep ent/generate` is empty and `ls session/ent/generate.go` fails, so the ent generate recipe lives only in the `Makefile`. Record where the canonical `--feature sql/upsert` command lives in Task 0.4a so the Bazel action and `make ent-gen` cannot diverge (single source for the flag); (c) `go.mod` carries 4 stray modules under `project_plans/**/spikes/*` plus `tools/lint`, `tools/scanner`, `tuitest` (VERIFIED 8 tracked `go.mod` files); the plan covers the stray ones but should also note how `go_deps` isolated usage handles `tools/lint`'s `x/tools` version versus `golang.org/x/tools` in the main module.

- [ ] **C13. Story 7.6 soak and Epic 8 ordering — `P1` baseline is a static file.** `baseline-test-set.json` is recorded once in Task 0.1e and is stale by cutover (hundreds of tests are added per month). Story 4.8's script aligns a live `gotestsum` run, which is correct; the stale file is only useful for flake accounting. *Recommendation*: say explicitly that P1 compares the live `go test` run and the live Bazel run on the same commit, and treat `baseline-test-set.json` as the Epic 0 reference only. Regenerate the flake list at the gate.

- [ ] **C14. Observability Plan / Story 7.4 — the cache-credential model gives main-branch CI write access to a home service.** ADR-004 limits uploads to `main` pushes, which is right, but the plan does not say who can trigger a `main`-context run (any workflow with write access, `workflow_dispatch`, and the `bazel-cache-probe.yml` of Task 0.12b). *Recommendation*: use separate htpasswd users for read and write, store the write credential only in an environment-scoped secret restricted to the `main` branch, and add a line to ADR-004 stating this.

## Nitpicks

- ADRs are numbered ADR-001..008 under `project_plans/bazel-conversion/decisions/`, while `docs/adr/` has its own sequence (ADR-033 exists). Precedent is the ci-speed ADR in `project_plans/`, but promote with unique numbers if these move to `docs/adr/`.
- Task 0.14a's second verify (`grep -L Proposed ... | wc -l` equals 3) passes when a file never contained "Proposed"; check the `Status:` line explicitly.
- Task 6.1b's verify counts the word "windows" in build output; use `bazel cquery`/`aquery` for incompatible targets instead.
- The Effort estimate states "no L tasks were needed", but several M tasks (3.1a, 0.6d, 4.7a/b) cover work that ADR-008's own matrix costs at L for the fork path; the overrun checkpoint covers this, but note which tasks are most likely to move.
- Layering and patterns otherwise hold up: Strangler Fig, Facade over `BUILD_SYSTEM`, Adapter for `sync-gen` and embed staging, and a capped Starlark surface are well matched to the problem. Primitive-obsession/illegal-state concerns reduce to the sealed config and verdict sets (C3, C10).
