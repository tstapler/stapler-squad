# ADR-004: Remote cache is self-hosted `bazel-remote` on `onyx`; read-only is enforced by the server; shared local caches for worktrees

**Date**: 2026-11-01 (revised after review iterations 1 and 2)
**Status**: Accepted (owner decision, requirements.md). Reachability mechanism, server-side read-only enforcement and secret redaction remain **Proposed** (not finalised at Task 0.14d): spikes S10 (Story 0.12) and S10-redaction (Task 0.12d) have no verdict and are **WAIVED**, not passed, in `implementation/owner-attestations.yaml` `spike_waivers` (owner decision 2026-11-03, `remote_cache_s10`: start with disk cache only, defer the onyx remote cache; waiver granted 2026-11-06, expires 2027-02-04, `needs-owner-reconfirm`). The local disk-cache tier and the failure policy (owner-confirmed: timeout, retries, circuit breaker; `adr_004_failure_policy`) are not S10-dependent. The remote tier needs its own S10 and S10-redaction spikes before it is enabled; until then EG1/EG2 are measured against the local disk cache only.
**Context**: Free GitHub-hosted runners have no persistent disk and cannot reach a home LAN. No remote execution. The first draft said "PR jobs use `--noremote_upload_local_results`", which is a client-side flag in files a same-repo PR branch controls, and `bazel-remote`'s htpasswd authentication has no read-only role ([buchgr/bazel-remote#628](https://github.com/buchgr/bazel-remote/issues/628), VERIFIED open, last updated 2023-01-13, so not a control). `main` also has no branch protection (VERIFIED), so nothing server-side on GitHub stops a PR branch from editing a workflow.

## Decision

- **Local tier (all worktrees, zero infra)**: committed `.bazelrc` sets `common --disk_cache=~/.cache/stapler-squad-bazel/disk` and `--repository_cache=~/.cache/stapler-squad-bazel/repo`, disk-cache GC flags (names verified on 9.3.1 in Epic 0: `--experimental_disk_cache_gc_max_size=100G`, `_max_age=30d`, `_idle_delay=10s`, the delay kept below the shortest `max_idle_secs` because GC runs in the idle server), and `--repo_contents_cache=~/.cache/stapler-squad-bazel/repo/contents` set beside the repository cache (both are already shared per user by default; the committed paths only fix the location). Disk cache and output bases must share a filesystem (reflink hits on btrfs). Identical sources at different worktree paths share entries (VERIFIED by run for genrules; rules_go path independence is checked by E1-E4, Task 0.10e). `--config=ci` overrides paths.
- **Remote tier topology (HTTP cache protocol, not gRPC)**: `bazel-remote` on `onyx` serves HTTP on loopback only (`--http_address 127.0.0.1:<port>`, gRPC disabled with `--grpc_address none`; bazel-remote's own default gRPC port 9092 is therefore unused, the proxy owns `:9092`/`:9093`). gRPC is HTTP/2 `POST`, so a GET/HEAD-only listener cannot carry it and allowing POST would reopen writes (`UpdateActionResult`, `BatchUpdateBlobs`); Bazel's HTTP cache client uses `GET`/`HEAD`/`PUT` on `/ac/<hash>` and `/cas/<hash>`, which a method filter can split cleanly. A reverse proxy exposes two listeners: `:9092` is read-only (allows `GET`/`HEAD` on `/cas/` and `/ac/` and rejects every other method), `:9093` proxies everything and relies on the htpasswd write user. Bazel uses `--remote_cache=https://onyx:9092` (read) and `https://onyx:9093` (write). bazel-remote documents `--remote_cache=http(s)://host:port` and the `--http_address`/`--grpc_address` flags ([README](https://github.com/buchgr/bazel-remote/blob/master/README.md), VERIFIED by reading it 2026-11-01); that Bazel's HTTP client sends the credential-helper `Authorization` header over `https` to the proxy and that the TLS certificate (Tailscale cert or private CA) is trusted by the runner is UNVERIFIED and tested by S10. Tailscale ACL tags enforce who can reach which: `tag:ci-pr` reaches `onyx:9092` only; `tag:ci-main` reaches `onyx:9093`; nothing else reaches either.
- **Reads authenticate by being unauthenticated on loopback**: bazel-remote runs with `--htpasswd_file` (write user only) and `--allow_unauthenticated_reads` ("If authentication is enabled (--htpasswd_file or --tls_ca_file), allow unauthenticated clients read access", README, VERIFIED). It is safe because bazel-remote is bound to loopback and the only paths to it are the two proxy listeners, each ACL-restricted; the `:9092` proxy additionally rejects every non-GET/HEAD method, so a `PUT`, `DELETE` or `POST` from `tag:ci-pr` never reaches bazel-remote. Writes through `:9093` still need the htpasswd user because `--allow_unauthenticated_reads` covers reads only (README wording; S10 asserts an unauthenticated PUT to `:9093` returns 401). The same flag is not exposed beyond the tailnet, so the earlier objection in Alternatives (reads exposed to anything reaching the port) is bounded by the Tailscale ACL.
- **Read-only is a server property**: PR jobs hold only the `tag:ci-pr` ephemeral key and the read endpoint, so a PR that deletes `--noremote_upload_local_results` gets HTTP 4xx on any PUT and cannot reach `:9093`. Fork PRs receive no secrets (GitHub default) and use the disk cache only.
- **Write credential**: stored only in the GitHub environment `bazel-cache-write`, whose deployment branch rule is `main` only (the rule is independent of branch protection), with its own Tailscale key `tag:ci-main` and its own htpasswd user (separate from any read user). The write job runs only on `push` to `main`; `workflow_dispatch` and the probe workflow can reach it only from `main`. Credentials are in 1Password locally.
- **Credential transport**: Bazel's `--credential_helper` (a script that reads an environment variable and prints the JSON headers), never `--remote_header=Authorization=...`, which would put the secret in process arguments and possibly in the build event JSON and profile. Whether Bazel redacts credential material is **UNVERIFIED**; spike S10-redaction greps both the raw canary and its base64 form (the helper emits `Authorization: Basic base64(user:pass)`) out of `bep.json`, the gunzipped profile, the execution log, `command.log`, stdout/stderr and the HTTP verbose/debug output, on a successful run and on a run with a deliberately wrong credential (failed-auth path, so 401 messages are exercised), and passes only on 0 matches. The `main` write job uploads no raw BEP, profile or execution log, only the scrubbed trend JSON, and every workflow has a secret-scan step that fails if the credential, its base64 form or an `Authorization` header (outside an explicit allow-list file `tools/bzl/secret-scan-allow.txt`, so benign text does not get the scan disabled) appears in any file about to be uploaded.
- **Write-job trigger surface (D-PROTECT-WRITE, owner decision; the separate merge-gate decision at the Story 7.6 flip is D-PROTECT-MERGE)**: `main` has no protection or ruleset (VERIFIED), so any holder of a push token, including agent tokens, can push to `main` and thereby run the write job or edit `credential-helper.sh`/`bazel.yml` there. Before the write credential is created (Task 0.12e), the owner chooses (a) a `main` ruleset (no direct push except the owner, PRs required) plus the `bazel-cache-write` environment's deployment-branch rule and a required-reviewer (owner approval) gate on that environment, or (b) at minimum the environment's deployment-branch rule `main` only AND the required-reviewer approval gate, recording the direct-push exposure as an accepted risk. Without either (a) or (b) the write credential is not created. The approval gate means a direct push to `main` still cannot use the credential without the owner approving the deployment.
- **Tailscale hygiene**: the ACL is default-deny with no `autogroup:member` or `*:*` grant covering `tag:ci-pr` or `tag:ci-main`; `tagOwners` restricts who may create each tag; auth keys are ephemeral, pre-approved, tag-scoped, short-expiry (rotated), and the `tailscale/github-action` is pinned by SHA. A check (Task 7.4b) dumps the ACL JSON and asserts these. No cache-touching workflow uses `pull_request_target`, or `workflow_run` that checks out PR code with secrets; a workflow lint check fails the build if either appears in a workflow that references the cache secrets.
- **Write-path monitoring**: `ci-cache-write` on `main` records the upload outcome; an alert (workflow failure plus a notification) fires after 3 consecutive `main` runs with PUT 4xx/5xx or a hit rate of 0 on the next PR build, so a silently broken write credential does not erode hits.
- **CI reachability** (pick by S10): (1) Tailscale GitHub Action with ephemeral, tag-scoped keys as above; (2) a public TLS endpoint with the same two-listener split and an allow-list. Whichever is chosen is recorded in Story 0.12 results.
- **Non-hermetic actions**: tmux with host cc, and the web actions that consume the Bun install, carry `no-remote-cache` until the determinism job passes; host-cc actions (tmux) are also protected against the local disk cache serving a result built by an older host toolchain after an OS upgrade (`no-cache`, or the host cc version declared as an input; Task 0.7b). (A repository rule such as the Bun install cannot carry an action tag and is never remote-cached; the tag belongs on the consuming actions.)
- **Failure policy**: unreachable cache must never fail a build or slow it materially. Flags (`--remote_timeout=3s`, `--remote_retries=1`, and the circuit breaker, which is off until `--experimental_circuit_breaker_strategy=failure` is set, with `--experimental_remote_failure_rate_threshold=10` and `--experimental_remote_failure_window_interval=60s`) are spike-verified names (Task 0.2b), not assumed. `--remote_local_fallback` is not used: it does not apply to `--remote_cache` unless `--incompatible_remote_local_fallback_for_remote_cache` is also set, and the docs say a cacheable local build does not fail when it cannot cache; Task 0.12c measures the fallback variant and keeps it only if it helps. CI cache configs also set `--remote_cache_compression` (bazel-remote serves zstd over HTTP). Story 0.12 tests real failure shapes, not a refused connection: a DROP-ed address, `tc netem` delay with loss, and a listener that accepts then never responds, each at most 10 seconds slower than no cache (Task 0.12c). CI also runs a pre-flight (`curl --max-time 3` of `/status` after the Tailscale join) and, on failure, drops the remote cache and falls back to `actions/cache` for the disk cache automatically (Task 7.4b), making that fallback a standing second tier.
- **Download and storage policy**: CI uses `--remote_download_toplevel` (already the 9.3.1 default, kept explicit; `minimal` for test-only jobs; names verified in Task 0.2b) so intermediates are not pulled over a residential uplink; `bazel-remote` is capped at `--max_size` 100 GB on a quota'd path so it cannot fill the root filesystem that also holds the live service's SQLite state, and the disk cache has a verified GC size cap.

**Changelog**: 2026-11-01 docs-derived revision (`research/bazel-docs-best-practices.md`): failure policy no longer relies on `--remote_local_fallback`; circuit-breaker strategy flag, compression, GC idle delay and repo contents cache added; local-cache protection for host-cc actions. ADR-008 (fork policy) is unaffected.

## Residual risk (accepted)

Anyone with write access to the repo can open a same-repo PR that reads the `tag:ci-pr` key and so can read cache contents (never write them). This is accepted because the cache holds build outputs of a public repository.

## Consequences

- A new always-on service the owner operates (wall-clock blocker: owner deploys the proxy listeners and Tailscale ACL, creates the `bazel-cache-write` environment, supplies credentials).
- Cache poisoning needs a push to `main`, which is the owner's own trust boundary.
- If neither reachability option is acceptable the fallback is `actions/cache` for `--disk_cache` via setup-bazel (zero infra, coarser; the local shared disk cache across worktrees is unaffected, but the CI speedup is weaker and P10 still has to pass its thresholds). BuildBuddy free tier is the next alternative but was not chosen by the owner and needs an explicit owner decision to adopt.

## Alternatives considered

BuildBuddy cloud, Depot, EngFlow, Buildless: see `research/build-vs-buy.md` section 2. Not chosen by the owner. `--allow_unauthenticated_reads` on bazel-remote was considered instead of the proxy; on its own it gives a read/write split but exposes reads to anything that reaches the port. It is now used, but only behind loopback and the two ACL-restricted proxy listeners (see Decision).
