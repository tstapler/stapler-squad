## 2. Go: rules_go + Gazelle

**MODULE.bazel skeleton** (VERIFIED structure for go_sdk/go_deps in spike; `use_repo` list is produced by `bazel mod tidy`):
```
bazel_dep(name = "rules_go", version = "0.65.0")
bazel_dep(name = "gazelle", version = "0.54.0")
go_sdk = use_extension("@rules_go//go:extensions.bzl", "go_sdk")
go_sdk.from_file(go_mod = "//:go.mod")          # go 1.26.6 from go.mod
go_deps = use_extension("@gazelle//:extensions.bzl", "go_deps")
go_deps.from_file(go_mod = "//:go.mod")
```
- **Go SDK**: `go_sdk.from_file` reads `go 1.26.6`. A BCR/Go download of 1.26.6 must exist on go.dev at implementation time (UNVERIFIED). Keeps one pinned Go for Linux, macOS and CI.
- **`replace` (go-git fork)**: VERIFIED working through `from_file` (section 0). The Gazelle docs ([extensions.md](https://github.com/bazel-contrib/bazel-gazelle/blob/master/extensions.md)) say `replace` directives are effective only in the root Bazel module, which is our case. `use_repo` still names `com_github_go_git_go_git_v5`.
- **Multiple go.mod files**: root, `tuitest` (go 1.21), `tools/scanner` (go 1.21), `tools/lint` (go 1.26.3). Options:
  - (a) `go.work` + `go_deps.from_file(go_work=...)`: supported only in the root module; every direct dependency of every listed go.mod must be listed in `use_repo`; indirect deps depending on workspace modules can diverge from `go.work` ([rules_go bzlmod.md](https://github.com/bazel-contrib/rules_go/blob/master/docs/go/core/bzlmod.md), gazelle issue 1797). The repo has no `go.work` today (none found).
  - (b) Per-module `go_deps.from_file` in the same extension — MVS merges one dependency universe; fine unless the nested modules need conflicting versions (UNVERIFIED; `tools/lint` is a separate module likely to pin golang.org/x/tools differently).
  - (c) Isolated extension usage for `tools/lint` and `tools/scanner` (`use_extension(..., isolate = True)`, needs `common --experimental_isolated_extension_usages`): keeps tool deps out of the main graph. Recommended for `tools/lint` (analyzer binaries should not bump app dependency versions). `tuitest` is a test-helper module and probably joins the main universe (check who imports it).
  - Gazelle must be told each nested go.mod is a module boundary; it handles nested modules automatically (a directory with its own go.mod is excluded from the parent walk), and Gazelle runs once per module root with `# gazelle:prefix` set per module.
- **Gazelle directives** (root `BUILD.bazel`): `# gazelle:prefix github.com/tstapler/stapler-squad`, `# gazelle:go_naming_convention import_alias`, `# gazelle:exclude third_party`, `# gazelle:exclude web-app`, `# gazelle:exclude .claude`, `# gazelle:exclude worktrees`, `# gazelle:exclude project_plans` (the last holds Go spike modules, VERIFIED present). Worktree directories under `.claude/worktrees` contain full copies of the repo including go.mod; they must be excluded or `.bazelignore`d (VERIFIED they exist in-tree).
- **Build tags**: `embed_tmux`, `embed_tymux`, `sinkguard`, `gitoracle`, `integration`, `otelcauto`, `race`. Counts of `//go:build` lines: windows 23, linux 16, gitoracle 15, integration 12, darwin 11, sinkguard 7, `darwin && cgo` 4 (VERIFIED by grep, excluding worktrees). Gazelle emits `select()` on GOOS/GOARCH constraints for OS tags automatically. Custom tags are not understood by Gazelle for generation; it keeps the files in `srcs` and the compiler applies tags at build time via `--@io_bazel_rules_go//go/config:tags=embed_tmux,embed_tymux` (rules_go `string_list_flag`), exposed as `.bazelrc` configs (`--config=embed`, `--config=sinkguard`). `race` maps to `--@io_bazel_rules_go//go/config:race`. Files excluded by default tags (e.g. `ignore`, `otelcauto`) still appear in `srcs`; confirm Gazelle `# gazelle:build_tags` is needed for them (UNVERIFIED).
- **Embeds**: `go_library(embedsrcs = [...])`. Gazelle does generate `embedsrcs` for static `//go:embed` patterns (it globs the files it finds on disk). Gitignored or generated embed inputs (`server/web/dist`, `session/tmux/embed/tmux`, `session/tymux/embed/tymuxd`) are not visible on a clean checkout, so Gazelle will omit or mis-glob them; plan to set them by hand with `# keep` comments or `# gazelle:ignore` on those packages. Specifics in section 7.
- **`gazelle_binary` with custom extensions**: `gazelle_binary(name = "gazelle_ssq", languages = ["@gazelle//language/go", "@gazelle//language/proto", "//tools/gazelle/ent"], visibility = ...)`, run via `gazelle(name = "gazelle", gazelle = ":gazelle_ssq")`. Extensions are Go packages implementing `language.Language`. Candidate custom extensions: (1) ent (section 4 of codegen below), (2) feature-registry markers, (3) embed-input generated-file handling. Each needs a Go module context: put the extension in the main module so it shares `go_deps`.

## 3. Proto and buf

Existing: `buf.yaml`, `buf.gen.yaml` (remote plugins `buf.build/protocolbuffers/go`, `buf.build/connectrpc/go:v1.20.0`, local `web-app/node_modules/.bin/protoc-gen-es` with `target=ts`), `buf.gen.go-only.yaml`; managed mode sets `go_package_prefix github.com/tstapler/stapler-squad/gen/proto/go`; `tools.go` pins `buf`, `protoc-gen-connect-go`, `protoc-gen-go` as Go deps.

Bazel options:
1. **Gazelle proto mode + rules_go `go_proto_library` with a custom `go_proto_compiler` for connect-go** (recommended for Go). rules_go ships the grpc compiler, not connect; add a `go_proto_compiler` target wrapping `protoc-gen-connect-go` built from the `connectrpc.com/connect` module in `go_deps` (the plugin `connectrpc.com/connect/cmd/protoc-gen-connect-go`; note the repo's existing pin to `v1.20.0` because the unpinned plugin began emitting `connectrpc.com/connect/v2` imports, per the comment in `buf.gen.yaml`). Gazelle directive `# gazelle:proto package` / `# gazelle:go_proto_compilers @io_bazel_rules_go//proto:go_proto,//tools/proto:go_connect` (directive exists in Gazelle proto language; custom-compiler wiring UNVERIFIED on this repo).
2. **`buf generate` as a Bazel action** (`genrule`/`run_binary`): hermetic if buf is pinned as a Go binary from `go_deps` (`github.com/bufbuild/buf/cmd/buf` is already in `tools.go`) and plugins are local (not `remote:`), because remote BSR plugins need network and are not hermetic (a `remote:` plugin in `buf.gen.yaml` would fail in a sandbox). Requires a `buf.gen.bazel.yaml` with `local:` plugins. Output tree is declared per-file, so the generated `*.pb.go`/`*_connect.pb.go` list must be known; Gazelle derives it from `.proto` names (`<name>.pb.go`, `<name>connect/<name>.connect.go`). Simpler to maintain parity with `make proto-gen` byte-for-byte.
3. `rules_buf 0.5.4` for **lint/breaking/format tests only** (`buf_lint_test`, `buf_breaking_test`), replacing `make proto-lint proto-breaking`.

Recommendation: Go generation via option 1 (idiomatic, Gazelle-managed, cached per proto_library), TS generation via an action running `protoc-gen-es` from the web-app's node_modules (section 5) through protoc from the `protobuf` module; keep option 2 as a parity oracle during the strangler phase (compare Bazel output with `make proto-gen` output). TS output path `web-app/src/gen/` becomes a Bazel-output directory consumed by the web target, no longer a source-tree write. Managed-mode semantics (`go_package_prefix` overrides) must be reproduced by `go_package` options or `M` flags; with option 1 Gazelle sets `importpath` from `go_package` and the `managed` override means the `.proto` files may lack `go_package` — INFERRED to need `# gazelle:proto_import_prefix`/`importpath` overrides or adding `go_package` options. This is the single highest-risk proto detail; spike it.

## 4. ent codegen and cgo

**ent**: `session/ent/generate.go` command is `go run -mod=mod entgo.io/ent/cmd/ent generate --feature sql/upsert ./session/ent/schema`. As a Bazel action:
- Build the ent CLI via `go_binary` from the `entgo.io/ent/cmd/ent` package in `go_deps` (needs `entgo.io/ent` direct dep and its `cmd/ent` transitive deps, e.g. `golang.org/x/tools`, `github.com/olekukonko/tablewriter`).
- ent loads the schema with `golang.org/x/tools/go/packages` and compiles it, which shells out to the `go` tool and needs module resolution; this does not work inside a Bazel sandbox without a Go SDK and module cache. Two workable shapes: (a) a small Go program `//session/ent:entc` that imports the schema package as a normal Bazel dependency and calls `entc.Generate("./schema", &gen.Config{Features: []gen.Feature{gen.FeatureUpsert}})` — still invokes `packages.Load`; (b) run the `ent` binary in a `genrule` with `local = 1`/no-sandbox plus a vendored module cache. Option (a) with the real `go` binary from the rules_go SDK and `GOFLAGS=-mod=mod GOPATH` pointed at a Bazel-provided module cache is the typical workaround (UNVERIFIED; hardest codegen item, give it a spike). The alternative is a `go_library`-adjacent `run_binary` where `ent` reads schema via `entc` `LoadGraph` with source parsing only (not available in public API; INFERRED).
- Declared outputs: ent emits hundreds of files (`session/ent/*.go` plus subdirectories per entity). Use a tree artifact (`declare_directory`) and feed it as `srcs` to a `go_library` in the generated package; rules_go supports directory-type `srcs`? It does not reliably (rules_go wants individual `.go` files). Practical approach: a custom Starlark rule that runs ent into a directory and then a second action that lists files into a declared set (needs the list at analysis time) — so the file set must be committed to a manifest or derived by a Gazelle extension scanning `session/ent/schema/*.go` (entity names map to a deterministic file set; INFERRED, plausible but real work). This is the "custom Gazelle extension" in requirements.md's rabbit hole.
- **How Gazelle sees gitignored generated Go**: it does not (the files do not exist on a clean checkout, and `.gitignore` excludes `session/ent/*.go` and subdirs, VERIFIED by CLAUDE.md and `ls`). Gazelle will generate nothing for `//session/ent` and will mis-resolve imports like `.../session/ent/...` in dependents as external or unresolved. Needs `# gazelle:resolve go github.com/tstapler/stapler-squad/session/ent //session/ent:ent` (and for each subpackage: `ent/enttest`, `ent/migrate`, `ent/predicate`, `ent/<entity>`) in the root BUILD file, `# gazelle:exclude session/ent` (so a developer's local `make ent-gen` output is not indexed), and the hand-written `session/ent/BUILD.bazel` + `schema/BUILD.bazel` (schema is committed, so Gazelle covers `session/ent/schema`). Same pattern for `gen/proto/go` if option 2 is used.

**cgo and sqlite** (facts in section 0.2):
- Recommended: move the two `mattn/go-sqlite3` tests to `modernc.org/sqlite` and drop `mattn/go-sqlite3` from `go.mod`; then Linux builds use `pure = on` (no C compiler involved) and the go.mod `godebug netdns=go` setting stays valid. The tests mention behavior of `ALTER TABLE ... DROP COLUMN` in SQLite; modernc embeds SQLite and supports it (version of embedded SQLite in modernc v1.56.0 to be checked).
- If mattn must stay: `pure = off` plus a C toolchain. Options: host toolchain (non-hermetic, simplest, drifts) or `toolchains_llvm 1.12.0` (needs sysroots; macOS cross-compilation also needs an Apple SDK, which toolchains_llvm cannot download for you — you provide a SDK tarball or use host Xcode via `apple_support`). A new alternative `hermeticbuild/hermetic-llvm` (zero-sysroot) says vanilla Go needs patches for cgo before Go 1.27 ([README](https://github.com/hermeticbuild/hermetic-llvm)), so not suitable for Go 1.26.6 yet. rules_go itself documents cross-compiling cgo as "possible, but not fully supported" ([rules_go cross-compilation docs via search](https://github.com/bazel-contrib/rules_go/blob/master/go/toolchains.rst)).
- **darwin cgo files** (3 `import "C"` files; four files tagged `darwin && cgo`) are built natively on macOS with the host Xcode toolchain; macOS CI runs on macOS runners anyway. Link flag `-sectcreate __TEXT __info_plist macos/Info.plist` (currently `CGO_LDFLAGS`, Makefile lines ~207, 435, 451) maps to `go_binary(cgo_ldflags/gc_linkopts)` or `x_defs`-adjacent `--linkopt` in a `config_setting` for darwin; the Info.plist file becomes a `data`/linkopt input via `$(location)` (UNVERIFIED).
- Windows: 23 `windows`-tagged files and `build/windows_amd64`. rules_go supports Windows in its CI, but the repo's agent/tmux runtime is Unix (tmux does not run natively on Windows). Recommendation for the Phase 3 decision: keep Windows out of the Bazel `//...` default (`--build_tag_filters` / `target_compatible_with` on windows-only packages), compile-check via `--platforms=@rules_go//go/toolchain:windows_amd64` as a non-test target (cross-compile pure Go works) so the `build/windows_amd64` artifact keeps building.

## 5. web-app: rules_js, TypeScript, bun, jest

Facts: `web-app/package.json` pins `packageManager: bun@1.4.3`, has a `preinstall` guard rejecting non-Bun package managers, `bun.lock` at `web-app/`, `trustedDependencies` (`@swc/core`, `esbuild`, `@ast-grep/cli`), `overrides` (`eval 0.1.8`), a `patches/` directory, and two build paths: `build:next` (Next export) and `build:bun` (`bun build/build.ts`, a custom Bun build with `build/plugins`, `build/stages`). Tests: `jest` (config in `jest.config.js`), Playwright e2e (outside Bazel scope for the build; uses the built binary).

- `aspect_rules_js 3.5.2` needs `pnpm-lock.yaml`. It can generate one by running `pnpm import`/`pnpm install --lockfile-only` through `npm_translate_lock(update_pnpm_lock=True, data=[package.json, pnpm-workspace.yaml])`, but that makes pnpm a second package-manager lockfile alongside `bun.lock`, which conflicts with the "Bun only" repo rule (`docs/how-to/use-bun-in-web-app.md`) and doubles the drift surface. Bun overrides map to `pnpm.overrides`, `patches/` to `pnpm.patchedDependencies`. Hoisting: rules_js models pnpm's strict `node_modules`; Bun's flat layout can hide phantom dependencies that break under rules_js (expect fixes in `package.json`).
- Third-party Bun-lockfile rulesets exist but are immature: `parkrevil/rules_bun` (PR "npm dependencies from bun.lock, Bun 1.4.4"), `curlewlabs-com/rules_bun` (Bazel 9.2.0 / Bun 1.3.10 dev pins; "frozen Bun workspace acquisition"; later versions fetch tarballs via Bazel downloader with lock integrity), `tomato-bazel/rules_bun`. All 0 stars, created 2026-05 to 2026-10, not in the BCR (VERIFIED via GitHub API and BCR 404). Treat as a bet on one maintainer.
- **Options, ranked**:
  1. **Bun-owned install wrapped in a hermetic-enough repository rule or genrule** (recommended starting point): fetch a pinned `bun` binary via `http_archive` (sha256, per OS/arch) and run `bun install --frozen-lockfile` in a repository rule keyed on `bun.lock` + `package.json`, then run `bun build/build.ts` as an action to produce `dist/`. Not fully hermetic (install network access in a repo rule; integrity comes from the lock), but retains one lockfile and the existing build script, and the rule's output cache is keyed by lockfile hash. This is exactly what the curlewlabs ruleset formalizes; copying its approach into repo-local Starlark avoids the dependency.
  2. Adopt `curlewlabs-com/rules_bun` or `parkrevil/rules_bun` (young; pin by commit + `archive_override`/`git_override` since not in BCR).
  3. `aspect_rules_js` + pnpm lockfile maintained by CI check (`pnpm import` from `bun.lock`? no such converter exists; the lockfile must be generated from `package.json` with pnpm, which can resolve different versions than `bun.lock` — a correctness risk).
  4. Keep web-app outside Bazel (`genrule` calling `bun` on the host); contradicts the hermeticity driver.
- **TypeScript/jest**: type-check and jest do not need rules_ts if run through Bun/jest as actions/tests in option 1 (`sh_test` or `genrule` per jest project, with `node_modules` as input). `aspect_rules_ts 3.10.1` (`ts_project`) adds incremental, cacheable type-checks but requires the rules_js `node_modules` model (options 3 only). Jest tests under Bazel need `testing.TEST_TMPDIR`-aware config and the whole `node_modules` as runfiles — large; shard by test file group.
- **Proto TS**: `@bufbuild/protoc-gen-es ^2.11.0` runs from the same install's `node_modules/.bin/protoc-gen-es`; generation depends on the web install target, so proto-TS generation lives in the web package's BUILD (cross-language edge: web deps on proto; Go server deps on web dist).
- UNVERIFIED: whether `build/build.ts` reads files outside `web-app/` (e.g. `../docs` or `../proto`), network access during build, or writes into the source tree.

## 6. tmux (third_party/tmux submodule) and tymuxd

Facts: `.gitmodules` `third_party/tmux` -> `https://github.com/tmux/tmux.git` branch 3.8, pinned to SHA `7f2a35ad` (VERIFIED `git submodule status`). ## 8. Cache options (remote/disk)

- **Disk cache + repository cache**: `common --disk_cache=~/.cache/bazel-disk --repository_cache=~/.cache/bazel-repo` shared by all worktrees fixes the "N worktrees x cold build" cost for action outputs (but each worktree still has its own output base and repo-rule fetches; `--repository_cache` shares downloaded archives). Disk cache has no size cap by default; use `bazel clean`-free GC: Bazel 9 supports `--experimental_disk_cache_gc_max_size` / `--experimental_disk_cache_gc_idle_delay` (INFERRED present in 9.x; check `bazel help build`). Concurrent-writer safety of disk cache is by atomic rename (documented).
- **Output-base cost per worktree**: Bazel server per output base, memory per server; WIP cap of 2 concurrent backlog sessions plus agent worktrees means set `--max_idle_secs` low and consider `bazel shutdown` hooks; this should be measured in Phase 2 baseline work, not assumed.
- **Remote cache**: BuildBuddy cloud: the pricing page lists a free tier with 100 GB cache transfer ([pricing](https://www.buildbuddy.io/pricing/)); docs say free for individuals and open source, README says individuals/OSS/teams up to 3 — wording conflicts, check the current terms before depending on it. `bazel-remote` (self-hosted, e.g. on the home server) speaks the REAPI HTTP/gRPC cache protocol and is also usable behind BuildBuddy's UI. GHA-cache shims are weaker (GitHub's cache service has per-repo 10 GB cap and eviction; the earlier ci-speed analysis already notes this). Secrets via GitHub secrets/1Password only. `--remote_upload_local_results` only on main CI jobs; PR jobs read-only to avoid cache poisoning.
- GHA: [`bazel-contrib/setup-bazel`](https://github.com/bazel-contrib/setup-bazel) action caches disk cache/repository cache/bazelisk (INFERRED existence and features from memory; not re-verified this session).

## 9. macOS codesign and TCC

Makefile `_codesign-binary` (target in `.PHONY` list, used at lines ~535, ~551) signs the Go output after `go build`; TCC grant persistence needs a stable signing identity from a local self-signed cert (`make setup-codesign`). Bazel outputs are read-only files in `bazel-out` and signing is an environment-dependent step (needs keychain access, not available to sandboxed actions) so signing stays **outside** Bazel: `make install-service` (thin wrapper) runs `bazel build //:stapler-squad --config=release` and then `codesign` on a copied binary, exactly as `scripts/install-service.sh` would. Info.plist embedding via `-sectcreate` is link-time and fits inside Bazel (section 4). Whether a Bazel-built binary yields a byte-identical code directory hash so existing TCC grants survive is UNVERIFIED and listed as device-verification by requirements.md (stable Designated Requirement is based on the signing identity, not binary hash, for a self-signed cert with `-i` identifier, so grants should persist; confirm on a device).

## 10. Tests that break in the sandbox (stack-relevant only)

Bazel `go_test` runs in the package directory inside runfiles, not the repo root; tests that read repo-relative paths, `$HOME`, real tmux, real git, or network need `data = [...]`, `tags = ["no-sandbox", "requires-network", "local", "manual"]` or `--test_env`. `rules_go` sets `TEST_TMPDIR`; tests using `os.Getwd()`-relative paths to `../..` break. The `mattn`-test cgo dependency disappears via section 4. Count and classification of such tests is a Phase 2 pitfalls item, not stack.
