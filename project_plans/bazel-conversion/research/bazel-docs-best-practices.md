# Bazel docs best practices for one box, many worktrees

**Date**: 2026-11-01. **Bazel**: 9.3.1 (installed, `bazel --version`). **Host**: `onyx`, 24 cores, 61 GB, `/home` is **btrfs** (`findmnt -T ~` prints `btrfs rw,relatime,ssd,discard=async,space_cache=v2,subvol=/@home`), `/tmp` is tmpfs.
**Labels**: `[DOC]` = VERIFIED-IN-DOCS (sentence quoted, URL given). `[RUN]` = VERIFIED-BY-RUN (`bazel help ... --long` or a tiny experiment on 9.3.1 in the session scratchpad, `--nohome_rc --host_jvm_args=-Xmx2g --max_idle_secs=30`, one invocation at a time, all scratch output bases expunged afterwards). `[INF]` = INFERRED.
**Scope note**: experiments used built-in `genrule`s only (no network, no rules_go). Anything that depends on rules_go/Go compile actions is `[INF]` and has an experiment in section 5.

## 1. Summary: the 10 highest-value findings

1. **`startup:<config>` lines are ignored, so plan Task 0.2f's "`--config=agent` gains `startup --max_idle_secs=30`" cannot work.** `[DOC]` "Setting `startup:config-name --some_startup_option` in the .bazelrc will be ignored." (https://bazel.build/run/bazelrc, section `--config`). `[RUN]` `.bazelrc` with `startup:agent --max_idle_secs=777`, `startup:linux --max_idle_secs=555`, run `bazel build --config=agent`: server `/proc/<pid>/cmdline` showed `--max_idle_secs=555` (the `:linux` line applied, the `:agent` line did not). Also `build --config=agent` fails with "Config value 'agent' is not defined" if `agent` only has a `startup:` line. Fix: put `startup --max_idle_secs=...` unconditionally, or have the `tools/bazel` wrapper pass the startup flag on the command line. `[DOC]` platform configs do apply to startup (`startup:linux`).
2. **Disk-cache GC is built in, and with our planned `--max_idle_secs=30` it would never run.** `[DOC]` "Starting with Bazel 7.4, you can use `--experimental_disk_cache_gc_max_size` and `--experimental_disk_cache_gc_max_age` ... Bazel will automatically garbage collect the disk cache while idling between builds; the idle timer ... `--experimental_disk_cache_gc_idle_delay` (defaulting to 5 minutes)" (https://bazel.build/remote/caching#disk-cache). `[RUN]` all three flag names exist on 9.3.1 (`help build --long`); idle delay default `5m`; with `max_size=5M --experimental_disk_cache_gc_idle_delay=2s` a 20 MB cache shrank to 8 KB after 8 s idle. `[INF]` GC runs in the Bazel server, and the server exits after `max_idle_secs` (30 s in our wrapper config), so the default 5 m delay never elapses. Set `--experimental_disk_cache_gc_idle_delay=10s` (below `max_idle_secs`) or run the standalone tool on a timer (https://github.com/bazelbuild/bazel/tree/master/src/tools/diskcache, `bazel run //src/tools/diskcache:gc -- --disk_cache=... --max_age=7d --max_size=2G`).
3. **Identical sources in different worktree paths DO share disk-cache entries.** `[RUN]` two copies of a workspace at `.../exp/wtA` and `.../exp/other/deep/wtB`, different output bases, shared `--disk_cache`: B's second build reported `2 disk cache hit` for two genrules; a `--execution_log_json_file` shows `runner: disk cache hit, cacheHit: true`. Client `PATH`, `FOO`, `LANG`, `TMPDIR`, `USER`, `HOME` differing between the two invocations still hit (`incompatible_strict_action_env` default `true` on 9.3.1, `help build --long`). The docs say the same: the disk cache "is useful for sharing build artifacts when switching branches and/or working on multiple workspaces of the same project, such as multiple checkouts" (https://bazel.build/remote/caching#disk-cache).
4. **Cache hits can import another worktree's absolute path (poisoning shape).** `[RUN]` a genrule doing `pwd > $@` produced `.../_bazel_tstapler/<outputbase-of-A>/sandbox/linux-sandbox/3/execroot/_main` in A; B received the **same bytes** from the cache (so B's output names A's output-base hash). The action key does not include the cwd; the content does. Any real action that writes `$PWD`/execroot into an output is a cross-worktree leak and a determinism failure, and it is exactly what the `no-remote-cache` tag plan for tmux/Bun is for. Detection: `[DOC]` compare execution logs; for content leaks, diff output hashes across worktrees (Experiment E4).
5. **Repository downloads are already shared per user, and 9.x also shares the *extracted* repos.** `[RUN]` `bazel info repository_cache` prints `~/.cache/bazel/_bazel_$USER/cache/repos/v1` (default is per-user, not per-workspace). `help build --long`: "`--repo_contents_cache` ... contains fetched repo directories shareable across workspaces ... default of `{--repository_cache}/contents`"; `--repo_contents_cache_gc_max_age` default `14d`. `[RUN]` two workspaces fetching the same `http_archive` with a shared `--repository_cache`: both `$(bazel info output_base)/external/+http_archive+pk` were **symlinks to the same directory** under `<repository_cache>/contents/<hash>/<uuid>/`. Consequence: the Go SDK and toolchain repos are extracted once, not once per worktree; the committed `--repository_cache=~/.cache/stapler-squad-bazel/repo` is optional (default is already shared) but must be kept consistent with `--repo_contents_cache`. Whether module-extension repos (`go_deps`, the Bun repository rule) are admitted to the contents cache is `[INF]` (Experiment E6).
6. **On this btrfs `/home`, disk-cache hits cost no extra disk: outputs are reflinked.** `[RUN]` after a hit, `filefrag -v` of the output and of the CAS blob showed the identical physical extent `1437295266..1437300148` flagged `shared`; `nlink=1` on both (so a reflink/clone, not a hardlink); `du` of cache stayed 20 MB for a 20 MB output present in the cache plus two worktrees' outputs. This only holds when disk cache and output base are on the same btrfs filesystem. Do not put the disk cache on `/tmp` (tmpfs) or another filesystem (copy instead, `[INF]`). Docs describe no reflink behaviour: this finding is `[RUN]` only.
7. **Concurrent servers sharing one disk cache did not corrupt it.** `[RUN]` three worktrees built a 20 MB genrule and a small one at the same moment into a fresh `--disk_cache`: all three executed (no cross-server in-flight dedup, 3x CPU for a cold concurrent start), identical sha256 for all outputs, no `corrupt|mismatch` in any log, and a 4th clean build hit 100%. GC keeps a `gc/lock` file in the cache dir (`ls dc/` shows `ac cas gc tmp`, `gc/lock`), `[INF]` coordinating collectors across servers. The docs make no explicit multi-server safety statement for the disk cache; Task 0.10c stays necessary at larger scale.
8. **Bazel documents the exact multi-workspace-on-one-machine memory problem and the knobs.** `[DOC]` "Managing memory pressure across multiple workspaces": "`startup --shutdown_on_low_sys_mem` ... servers idle for more than 5 minutes to exit when host RAM becomes critically low", "Lower `startup --max_idle_secs=1800`", "Run `bazel shutdown`" (https://bazel.build/run/client-server). Servers are one per output base and one invocation per server (`--block_for_lock`, same page). Sharing one server across workspaces is not possible: the client finds the server by output base, "which by default is determined by the path of the base workspace directory and your userid" (same page; https://bazel.build/remote/output-directories: output base = MD5 of workspace path).
9. **Built-in resource-containment startup flags make part of the wrapper's `nice`/`ionice`/cgroup work declarative.** `[RUN]` (`help startup_options --long`) `--io_nice_level` (0-7, Linux), `--batch_cpu_scheduling`, `--experimental_cgroup_parent`, `--experimental_run_in_user_cgroup` ("the Bazel server will be run with systemd-run, and the user will own the cgroup"), `--shutdown_on_low_sys_mem`, `--[no]idle_server_tasks` ("Run System.gc() when the server is idle"), `--[no]preemptible`, `--[no]block_for_lock`. `--batch` is "deprecated and will be removed, please prefer shutting down the server explicitly". The `--local_ram_resources` / `--local_cpu_resources` flags **do not exist** on 9.3.1 (0 matches in `help build --long`); use `--local_resources=cpu=N` and `--local_resources=memory=M`.
10. **Lockfile: Bazel ships a documented merge driver; the plan's custom driver may be unnecessary.** `[DOC]` "Bazel provides a custom git merge driver to help resolve these conflicts automatically ... adding this line to a `.gitattributes`" and each developer registers it once (needs `jq` 1.5+); manual path: restore lock, resolve `MODULE.bazel`, run `bazel mod deps` (https://bazel.build/external/lockfile#merge-conflicts). The code blocks were stripped by the page extractor, so the exact `.gitattributes`/`git config` text is UNVERIFIED here (read the page in a browser during Task 0.10b). Also `[DOC]` "Include the lockfile in version control" and use Bazelisk with `.bazelversion`; "the lockfile is specific to the Bazel version".

## 2. Per-topic findings

### 2.1 Disk cache
- `[DOC]` Semantics: "Bazel can use a directory on the file system as a remote cache ... multiple checkouts"; `--disk_cache` with no value uses `<outputUserRoot>/cache/disk`; `--nodisk_cache` disables; `~` is expanded (https://bazel.build/remote/caching#disk-cache). `[RUN]` `help build --long` for `--disk_cache`: "A path to a directory where Bazel can read and write actions and action outputs. If the directory does not exist, it will be created."
- `[RUN]` Layout on disk: `ac/`, `cas/`, `gc/lock`, `tmp/` (listing of the scratch cache).
- GC flags `[RUN]` on 9.3.1: `--experimental_disk_cache_gc_max_size` (default `0`, "size in bytes, optionally followed by K, M, G or T"), `--experimental_disk_cache_gc_max_age` (default `0`), `--experimental_disk_cache_gc_idle_delay` (default `5m`). "If set in conjunction with ... max_age, both criteria are applied. Garbage collection occurs in the background once the server has become idle." Names are still `experimental_`.
- `[RUN]` GC deleted the largest/oldest blob first in my test (20 MB -> 8 KB with a 5 MB cap): cap is enforced down to well under the limit in one pass, not trimmed to just under it. Plan for headroom: effective steady-state is below `max_size`.
- `[INF]` GC deleting a blob while another server's build is about to read it is handled by re-execution (Bazel treats a missing CAS entry as a miss); not documented, add to Experiment E3.
- Absolute paths: `[DOC]` "An action definition contains environment variables. This can be a problem for sharing remote cache hits across machines ... Only environment variables explicitly whitelisted via `--action_env` are included"; "Bazel does not track tools outside a workspace" (https://bazel.build/remote/caching#known-issues). `[RUN]` `--action_env=PATH` changed the key (a build with `--action_env=PATH` missed an entry written without it); without it, differing client `PATH`/`HOME`/`USER`/`LANG`/`TMPDIR` did not.
- `[RUN]` `--experimental_output_paths=strip` is accepted on 9.3.1 (values `off|strip`; Starlark actions must set `supports-path-mapping`); help calls it "highly experimental" for multi-platform/config builds. Not needed for the single-config worktree case: output-tree path differences between worktrees are not in the key, as the run in finding 3 shows. `[RUN]` `--experimental_remote_scrubbing_config` exists (cache-key scrubbing for cross-platform sharing; "extreme care").
- Digest function: `[RUN]` `--digest_function` is a **startup** option ("hash function; default: see description", tags `loses_incremental_state`). All sharers must use the same one; leave default (SHA-256). `[INF]` changing it invalidates the shared cache.
- Hardlink vs copy: see finding 6. `[RUN]` `--experimental_repository_cache_hardlinks` default `false` ("hardlink the file in case of a cache hit, rather than copying") applies to the repository cache only.
- Size planning `[INF]`: outputs are reflinks into the cache on btrfs, so output bases cost near zero extra for cache-restored files, but files that Bazel executes locally exist twice (once in the execroot, once in the cache, also shared extents after the upload clone if the filesystem clones on upload: finding 6 showed the uploaded blob and the output sharing an extent).

### 2.2 Repository cache, distdir, vendoring, lockfile
- `[RUN]` `--repository_cache`: default `{--output_user_root}/cache/repos/v1`; empty string disables; `--distdir` "Additional places to search for archives before accessing the network"; `--repository_disable_download`; `--http_max_parallel_downloads` default 8.
- `[RUN]` `--repo_contents_cache` (+ `_gc_idle_delay` 5m, `_gc_max_age` 14d). Default location `<repository_cache>/contents`; GC lock file `contents/gc_lock`; `_trash/`. Setting `--repository_cache=` (empty) disables it unless `--repo_contents_cache` is set.
- `[RUN]` Output base `external/<repo>` is a symlink into the contents cache (finding 5). `[INF]` `bazel clean --expunge` of one worktree removes only symlinks; the shared extracted tree survives. `[INF]` the 14 d GC of the contents cache must not remove a repo still symlinked by a live output base; Bazel owns that logic but it is undocumented here (E6).
- `[RUN]` startup `--experimental_remote_repo_contents_cache` (default false): stores reproducible repo-rule results in the *remote* cache. Not recommended (experimental, no gain on one box).
- `[DOC]` `bazel vendor`: "Vendor mode is a feature that lets you create a local copy of external dependencies ... useful for offline builds" (https://bazel.build/external/vendor); "Fetching all repos ... can be time-consuming", "The vendor directory can become very large", so vendor for specific targets. `[DOC]` `--lockfile_deps` vendors what `bazel mod tidy`/`deps` needs. `[INF]` for this plan vendoring is not worth it: committing a large vendor dir to a repo with ~100 worktrees multiplies it. Keep the shared repository cache instead. `VENDOR.bazel` supports `ignore()`/`pin()`.
- `[DOC]` Lockfile modes `update` (default), `refresh`, `error`, `off`; `error` "never changes the lockfile or performs network requests during resolution" (https://bazel.build/external/lockfile). `[DOC]` hidden second lockfile at `$(bazel info output_base)/MODULE.bazel.lock` is a performance optimization. `[RUN]` default `--lockfile_mode` `update`; `--vendor_dir`, `--registry` exist.
- `[DOC]` Best practices: run `bazel mod tidy`; commit the lock; "Use bazelisk ... include a `.bazelversion`". Module extensions can opt out of the lockfile by returning `reproducible = True`.
- Bazelisk cache: `[RUN]` `~/.cache/bazelisk/downloads` exists on this box (the Bazel binary is downloaded once per version, shared by all worktrees). `[INF]` `.bazelversion` in the repo pins 9.3.1 for every worktree.

### 2.3 Output bases, servers, memory, CPU
- `[DOC]` Layout (https://bazel.build/remote/output-directories): outputRoot `~/.cache/bazel` (Linux, overridden by `$XDG_CACHE_HOME/bazel`); `outputUserRoot = outputRoot/_bazel_$USER`; `outputBase = MD5(workspace path)`; `install/<md5 of install manifest>`; override with `--output_base` or `--output_user_root`. "`bazel clean` clears the on-disk action cache and then removes the entire `execroot` ... The `--expunge` option will clean the entire outputBase." The convenience symlinks `bazel-bin` etc. are only for the user.
- `[RUN]` An output base contains `DO_NOT_BUILD_HERE` whose content is the workspace path (no trailing newline) - the orphan test of Task 11.4a is valid; also `action_cache/`, `execroot/`, `external/`, `server/server.pid.txt`, `command-<id>.profile.gz` (5 retained), `MODULE.bazel.lock`, `lock`, `sandbox/`, `java.log.*`.
- `[RUN]` `--experimental_install_base_gc_max_age` default `30d` (GCs old install bases under `_bazel_$USER/install/`). Today `~/.cache/bazel` is 25 GB with 26 entries under `_bazel_tstapler` (other workers' bases), measured with `du -sh` and `ls | wc -l`.
- `[RUN]` `%workspace%` is **not** expanded in startup flags: `startup --output_base=%workspace%/.bzl-ob` created a literal directory named `%workspace%/` and the build failed. A per-worktree in-tree output base needs the wrapper to pass `--output_base="$PWD/<dir>"`, and `[RUN]` that tree must be in `.bazelignore` or `//...` fails with "infinite symlink expansion detected ... .bzl-ob/external/_main"; with `.bazelignore` containing the dir the build succeeded. `[INF]` benefit: `git worktree remove` deletes the output base too (orphans impossible); cost: the server's `execroot` and outputs sit inside the worktree dir that other tools (rg, the cleanup skill's `du`) scan, and `$PWD` length enters the unix-socket/path-length problems noted in `instinct_full_disk_tmp_gotmpdir_socket_path`.
- `[RUN]` server RSS: an idle server for a trivial workspace with `-Xmx2g` had `VmRSS` 364 MB; two other existing servers on this host totalled 1.23 GB. Trivial workspace, so no data for the real repo (Task 0.10a measures).
- `[DOC]` Memory flags (https://bazel.build/advanced/performance/memory): `--host_jvm_args=-Xmx2g`; to trade incremental speed for memory pass `--discard_analysis_cache`, `--nokeep_state_after_build`, `--notrack_incremental_state`. `[RUN]` all exist (`keep_state_after_build` default true, `track_incremental_state` default true, `discard_analysis_cache` default false). `[RUN]` `--gc_thrashing_limits` default `1s:2,20s:3,1m:5` triggers an intentional OOM; `--heap_dump_on_oom` writes `<output_base>/<invocation_id>.heapdump.hprof` (large; leave off).
- Servers and flags: `[DOC]` "the analysis cache ... is invalidated very easily: ... many flags cause the cache to be discarded ... changing startup options" restarts the server; mixing `-c opt` build with `cquery` discards each other's analysis cache; `--noallow_analysis_cache_discard` makes it an error (https://bazel.build/advanced/performance/iteration-speed). `[INF]` therefore `--config=agent`, `--config=ci` etc. must differ **only** in presentation flags (color, curses, progress, test output) so an agent and a human sharing a worktree do not thrash analysis; flags like `--disk_cache` do not invalidate analysis (`[INF]`).
- Resource limits `[RUN]`: `--jobs` default `auto`, accepts `HOST_CPUS*.5`; `--loading_phase_threads` default `auto`; `--local_resources=cpu=..|memory=..` ("Bazel will limit concurrently running actions based on the available resources"); `--[no]allow_one_action_on_resource_unavailable` default true. `[RUN]` `--experimental_sandbox_limits` and `--experimental_sandbox_memory_limit_mb` exist (per-sandbox cgroup limits, require cgroups permissions).
- Ctrl-C: `[DOC]` "the Bazel server is killed if you press Ctrl-C repeatedly" (iteration-speed page): relevant for agents that interrupt builds.
- `[INF]` A 24-core host with N servers each defaulting to `--jobs=auto` (about 24 actions each) oversubscribes the CPU N-fold; the wrapper's slot count (N=2) handles that, but `--local_resources=cpu=HOST_CPUS*.5` in `.bazelrc` makes each server self-limit when the wrapper is bypassed.

### 2.4 Remote cache
- `[DOC]` Protocols: HTTP/1.1 `PUT`/`GET` on `/ac/<hash>` (action result) and `/cas/<hash>`; `grpc`, `grpcs`, `http`, `https`; unix sockets for HTTP; "Take care in who has the ability to write to the remote cache. You may want only your CI system to be able to write"; `no-remote-cache` tag; deleting content is server administration (https://bazel.build/remote/caching). bazel-remote: "provides garbage collection to enforce an upper storage limit", "Both the REST and gRPC remote cache APIs are supported", the Bazel project provides no support for it (same page).
- `[DOC]` bazel-remote README: `--dir` (required), `--max_size` GiB (required), `--config_file`; zstd on HTTP via `Accept-Encoding`/`Content-Encoding: zstd` + `X-Digest-SizeBytes` (https://github.com/buchgr/bazel-remote/blob/master/README.md).
- `[RUN]` Flags on 9.3.1 with defaults: `--remote_timeout` 60s (REST: connect and read), `--remote_retries` 5, `--remote_retry_max_delay` 5s, `--remote_upload_local_results` true, `--remote_accept_cached` true, `--remote_cache_async` true (uploads in background), `--remote_cache_compression` false (zstd, threshold `--experimental_remote_cache_compression_threshold` 100), `--remote_instance_name` "", `--remote_max_connections` 100, `--remote_verify_downloads` true, `--remote_cache_header`, `--remote_download_outputs` default **`toplevel`** (so `--remote_download_toplevel` is already the default; `minimal`/`all` are the alternatives), `--experimental_remote_cache_eviction_retries` 5 ("transient remote cache error ... for example when artifacts are evicted ... A new invocation id will be generated for each attempt"), `--experimental_remote_cache_ttl` 3h, `--experimental_remote_cache_lease_extension` false, `--experimental_remote_cache_chunking` false.
- `[RUN]` Circuit breaker: `--experimental_circuit_breaker_strategy` accepts only `failure` and is **unset by default** (default "see description"); `--experimental_remote_failure_rate_threshold` default 10 (percent, 0 = no limit); `--experimental_remote_failure_window_interval` default 60s. So the breaker is off until the strategy flag is set.
- `[RUN]` `--remote_local_fallback` default false; its help: "fall back to standalone local execution strategy if remote execution fails". `--incompatible_remote_local_fallback_for_remote_cache` (default false): "Whether --remote_local_fallback applies to --remote_cache." `[DOC]` "a cacheable local build would not fail if it cannot cache" (https://bazel.build/remote/cache-local). Net: for a cache-only setup `--remote_local_fallback` is a no-op unless the incompatible flag is on; the real failure policy is timeout + retries + circuit breaker.
- Auth: `[RUN]` `--credential_helper` (scoped `host=path`, `%workspace%`-relative allowed), `--credential_helper_cache_duration` 30m, `--credential_helper_timeout` 10s. `[DOC]` URL-embedded basic auth works but "transmits username and password in plaintext" without HTTPS.
- Disk + remote layering: `[RUN]` `--disk_cache` and `--remote_cache` can be set together; the local disk cache is consulted first and a remote hit is populated into it `[INF]` (not tested here; no remote server was available; E8). `[DOC]` lookup order at https://bazel.build/remote/caching: local outputs, then cache, then execute, then upload.
- Hit-rate debugging `[DOC]` (https://bazel.build/remote/cache-remote, https://bazel.build/remote/cache-local): read the `INFO: N processes: X remote cache hit, Y linux-sandbox` line; run, `bazel clean`, rerun; capture execution logs on both runs and diff; check `cacheable`; check `--noremote_accept_cached` in the canonical command line from BEP (`--build_event_text_file`, `structured_command_line` with `command_line_label: "canonical"`). "The compact format is recommended, as it produces much smaller files with very little runtime overhead." The 9.x tool: `--execution_log_compact_file` (zstd-compressed `ExecLogEntry` protos); converting/parsing needs `//src/tools/execlog:parser` or `:converter` built from the Bazel source tree (https://github.com/bazelbuild/bazel). `[RUN]` `--execution_log_json_file` writes human-readable JSON with `runner`, `cacheHit`, `cacheable`, `targetLabel`, `mnemonic` per spawn and needs no tool, but is large (help text: prefer compact). For our hit-ratio experiments use JSON on the small spike builds and compact + parser on `//...`.
- `[DOC]` Known issues: file modification during a build can upload wrong results; `--experimental_guard_against_concurrent_changes` is named in the doc, but **`[RUN]` it does not appear in `help build --long` on 9.3.1** (grep returned nothing), so do not put it in `.bazelrc`; a stale `/etc/bazel.bazelrc` whitelisting `PATH` can cut hits (check `ls -l /etc/bazel.bazelrc`; INF it is absent on Manjaro).

### 2.5 Performance and sandboxing
- `[DOC]` JSON trace profile: written by default into the output base as `command-$INVOCATION_ID.profile.gz` plus `command.profile.gz` symlink; "Bazel keeps the last 5 profiles (`--profiles_to_retain`)"; "Explicitly passing a profile path with `--profile` disables automatic garbage collection" (https://bazel.build/advanced/performance/json-trace-profile). Consequence for the plan: `--profile=<path>` in CI/agent configs removes automatic profile GC, so the wrapper/CI must prune. `[DOC]` the EngFlow Bazel Invocation Analyzer consumes profiles. `[RUN]` `--[no]slim_profile` default true, `--profiles_to_retain` default 5.
- `[DOC]` Build performance metrics page (https://bazel.build/advanced/performance/build-performance-metrics) is for BEP-based timing; BEP: `--build_event_json_file`, `--build_event_text_file`, `--build_event_binary_file` all exist `[RUN]`.
- Sandbox `[DOC]` (https://bazel.build/docs/sandboxing): `linux-sandbox` needs user namespaces; "For Linux, sandboxed builds are rarely more than a few percent slower. Setting `--reuse_sandbox_directories` can mitigate the setup and teardown cost"; sandboxing disables tool-internal caches; `--spawn_strategy=sandboxed,local` is best effort; `--sandbox_debug` "fills up your disk over time". `[RUN]` `--reuse_sandbox_directories` default **true** on 9.3.1; `--experimental_inmemory_sandbox_stashes` default false ("may use a significant amount of additional memory"); `--sandbox_base` ("Specify a path on tmpfs (like /run/shm) to possibly improve performance a lot when your build / tests have many input files. Note: You need enough RAM and free space on the tmpfs"), `--experimental_sandbox_async_tree_delete_idle_threads` (async sandbox delete; "A server shutdown blocks on any pending asynchronous deletions"), `--experimental_use_hermetic_linux_sandbox` (hardlinks inputs; copies if on a different filesystem). `--incompatible_sandbox_hermetic_tmp` is **not present** on 9.3.1 (`help build --long`, 0 matches), so drop it from any plan text.
- `[INF]` for this box: sandbox directories live under the output base on btrfs by default (observed `.../execroot/_main/..` path in `pwd`); putting `--sandbox_base=/dev/shm/...` would spend RAM that the live service shares; `[RUN]` the run above shows sandboxes sit at `<output_base>/sandbox/linux-sandbox/N/execroot/_main`. Leave default unless profiling shows setup time dominating.
- Persistent workers `[DOC]` (https://bazel.build/remote/persistent): long-running tool processes started by the server; run in a generic sandbox only with `--worker_sandboxing`. `[RUN]` `--worker_max_instances`, `--worker_quit_after_build`, `--experimental_worker_memory_limit_mb` exist. `[INF]` rules_go compiles without persistent workers (not verified), so workers matter mostly for any JVM-based rules (none in plan).
- Tests `[RUN]` (`help test --long`): `--test_output` default `summary` (values `summary|errors|all|streamed`), `--test_summary` default `short`, `--cache_test_results` default `auto`, `--flaky_test_attempts` ("Tests that required more than one attempt to pass are marked as 'FLAKY'"), `--runs_per_test` (disables result caching: `auto` reruns "Multiple test runs were requested with `--runs_per_test`"), `--test_timeout`, `--test_tmpdir`, `--runs_per_test_detects_flakes`, `--test_timeout_filters`. ### 2.6 Best practices pages, bazelrc layering, bzlmod, rules_go
- `[DOC]` rc order (https://bazel.build/run/bazelrc): system `/etc/bazel.bazelrc`, workspace `.bazelrc`, home `$HOME/.bazelrc`, `$BAZELRC`, then `--bazelrc=`; later overrides earlier; `--nosystem_rc/--noworkspace_rc/--nohome_rc/--ignore_all_rc_files` are startup options. `[DOC]` `common` applies to all commands that support the option; `always` fails on unsupported; `build` lines apply to `test/run/clean/info/cquery/aquery/...`; `coverage, fetch, vendor` inherit from `test`; "start with `common` options at the top, and end with the most-specific commands at the bottom". `[DOC]` configs: `command:name` expands in place when `--config=name`; personal configs should start with `_`; `try-import %workspace%/user.bazelrc` (`import`, `try-import`, `try-import-if-bazel-version`); `--enable_platform_specific_config` enables `build:linux`/`startup:linux`. `[RUN]` the `~/.bazelrc` on this box produces "rc files are no longer being read" warnings when `--nohome_rc` is passed (expected) and it sets an 8g heap by the owner's note: the committed `startup --host_jvm_args=-Xmx2g` is overridden by `$HOME/.bazelrc` (later wins), which is exactly the 8g case. `[INF]` the wrapper should pass `--host_jvm_args=-Xmx2g` on the command line (highest precedence) or the owner removes the home setting; otherwise N servers x 8g defeats the 14 GB scope cap. Note `--host_jvm_args` "may be used multiple times" (appends), so both values reach the JVM and the last `-Xmx` wins (`[INF]`).
- `[DOC]` best practices (https://bazel.build/configure/best-practices): fine-grained dependencies for parallelism and incrementality, keep dependencies encapsulated. `[INF]` minimal bearing on caching beyond that.
- Gazelle/rules_go bzlmod page (https://github.com/bazelbuild/rules_go/blob/master/docs/go/core/bzlmod.md): "rules_go automatically downloads and registers a recent Go SDK"; `go_sdk.download(version = ...)`; `nogo` is "run as part of compilation" and registered via the `go_sdk` extension, so nogo findings are part of the compile action and cached. `[INF]` rules_go passes trimmed paths to the compiler, so Go compile actions should be path-independent across worktrees; this is the central unverified assumption (E3). `[INF]` `--stamp` plus `--workspace_status_command` changes stamped actions; `[RUN]` `--[no]stamp` default false, `--workspace_status_command` (path) exists. `[RUN]` a `genrule(stamp = 1)` re-executed (runner `linux-sandbox`, `cacheHit false`, `cacheable true`) in the second worktree and again after a clean in the first, while neighbours hit: it is in the action key via the volatile status. Stamp only the final binary (matches pitfalls R11).
- Hermeticity of the sandbox `[DOC]` "Sandboxing doesn't hide the host environment in any way. Processes can freely access all files on the file system" - so host `cc`, `/usr/bin` tools are untracked inputs ("Bazel does not track tools outside a workspace", caching page). Backs ADR-004's `no-remote-cache` tag for tmux/host-cc/Bun consumers; the local disk cache has the same hole across **different toolchains on the same host** only if the host toolchain changes between builds (system upgrade), so `bazel clean`-free cache poisoning after an `pacman -Syu` is a risk: add the host cc version to `--repo_env` or the action key via a toolchain repo (`[INF]`).

### 2.7 Hit-rate collapse causes and detection
Observed or documented, in order of likelihood for this repo:
1. `--action_env` / `--repo_env` PATH or other env (documented; `[RUN]` `--action_env=PATH` changed the key). Rule: never `--action_env=PATH` in a committed rc; keep strict env (default true).
2. Outputs that embed paths/time/user (`[RUN]` `pwd` genrule). Detect: build the same target in two worktrees, compare output sha256 (E4).
3. `stamp = 1` / `--stamp` (`[RUN]` stamped genrule missed).
4. Differing flags between worktrees' invocations (agent vs human config) that are part of the action key, notably `-c opt` vs fastbuild, `--features`, Go `--@io_bazel_rules_go//go/config:race|pure|tags` ([INF], R14 in pitfalls); each variant is a separate cache population.
5. `--remote_header`/`--remote_instance_name` mismatch or `--noremote_accept_cached` somewhere in an rc file (`[DOC]` BEP canonical command line check).
6. Host tool drift (`[DOC]` untracked tools).
7. Non-deterministic generators (protoc/buf versions, `ent` codegen reading the network, Bun install): each shows up as the same action key with differing output digests, therefore *downstream* actions miss. Detect via two clean builds and output digest diff (E4).
Measuring: `INFO: N processes:` line; `--execution_log_json_file`/compact + parser; BEP `--build_event_json_file` (look for `ActionExecuted` and `remote_cache_hit`); JSON profile (`--profile`). `bazel aquery` shows the command line and env of an action (`[INF]`, it is the action key's visible half); `--explain=<file>` + `--verbose_explanations` explains why a local action re-ran (`[INF]`; not verified: confirm with `bazel help build --long | grep explain` during E1).

### 2.8 Maintenance and operations
- `[DOC]` Orphan servers: "if you're running scripts that perform a lot of automated builds in different directories, it's important to ensure that you don't accumulate a lot of idle servers; ... explicitly shutting them down ... or specifying a short timeout" (client-server page). Server process title is `bazel(<workspace dirname>)` in `ps` (same page).
- `[RUN]` `DO_NOT_BUILD_HERE` records the workspace path (orphan test). `[RUN]` `server/server.pid.txt` gives the server pid for RSS sampling. `bazel shutdown` per orphan base needs the workspace dir: for a deleted worktree use `kill $(cat <base>/server/server.pid.txt)` after confirming the process cmdline contains that `--output_base` (`[INF]`).
- Cache cleaning cron: `[DOC]` the built-in GC + the standalone `diskcache:gc` tool (needs Bazel source to build, or one `bazel run` from a pinned checkout). `[INF]` simplest durable form: built-in GC flags with `idle_delay=10s` in `.bazelrc` (GC is performed by the last-idle server) and a daily `du` alarm; the standalone tool is the fallback if GC proves not to run (E5).
- `[INF]` `du` budgeting for this host (600 GB free, 100 worktrees): disk cache 100 GB cap (`max_size`), repository cache + contents (Go SDK ~0.5 GB, toolchains) < 5 GB, output bases ~ (per worktree) x (live worktrees with a base); Story 0.10 measures that; the 148-worktree/178 GB incident means the per-worktree output base is the term to police.

## 6. Experiments to add to Story 0.10 (each with a falsifiable pass criterion)

Common harness: `--execution_log_json_file=<f>` on each build; hit ratio = (spawns with `runner == "disk cache hit"` or `cacheHit == true`) / (spawns with `cacheable == true`, excluding mnemonics of internal symlink actions). The scratch scripts used here (`parse.py`) are a template.

- **E1 Cross-path hit ratio (the core proof).** Worktree A at `/home/x/wt/a`, worktree B at a *different* path and different depth, same commit, empty shared disk cache, `--config=ci`-free. Build `//:stapler-squad` in A (cold), then `bazel clean` in B's fresh base and build the same target in B. PASS iff B's execution log has >= 95% of cacheable spawns as disk-cache hits and the non-hit spawns are all on a pre-declared allow-list (tmux, Bun consumers); FAIL otherwise, and list the first 5 non-hit actions with `aquery` command lines.
- **E2 Zero-rebuild second worktree.** After E1, a third worktree C: PASS iff `INFO: N processes:` shows 0 `linux-sandbox`/`worker` spawns excluding allow-listed ones and wall time <= 30% of A (matches S6).
- **E3 Go compile path-independence (the rules_go `[INF]`).** For three Go library targets of different sizes, compare action key inputs: the `Command line` of `bazel aquery 'mnemonic("GoCompile", //pkg:lib)' --output=text` in A and B, with the workspace-root prefix and output-base hash substituted. PASS iff the two outputs are byte-identical after normalizing nothing; FAIL if any absolute path remains (then evaluate `--experimental_output_paths=strip`, `-trimpath` equivalents). Add: concurrent `GC` while a 4th worktree builds (`--experimental_disk_cache_gc_max_size=1G` with a 3 GB populated cache) must produce zero build failures and a hit-ratio that degrades gracefully (PASS: zero `ERROR:` lines, outputs identical to a no-cache build).
- **E4 Output-digest determinism across worktrees.** Build everything cache-disabled in A and B (`--nodisk_cache`), sha256 all `bazel-bin` regular files by relative path. PASS iff the two sorted lists are identical; every differing file is a determinism bug (stamps, `$PWD`, timestamps) and goes on the `no-remote-cache` list. Control: include the known-bad `pwd` genrule and require E4 to flag it (positive control, `[RUN]` shape above).
- **E5 GC actually runs under the wrapper's idle timeout.** With `max_idle_secs=30`, populate a 300 MB cache, set `--experimental_disk_cache_gc_max_size=100M --experimental_disk_cache_gc_idle_delay=10s`, run one tiny build, sleep 20 s, `du -sm`. PASS iff size <= 100 MB; also run with the default `5m` delay and PASS iff size is unchanged after the server exits (proves finding 2 and keeps the explicit delay justified).
- **E6 Repo contents cache coverage.** In A run `bazel build @rules_go//go` and the `go_deps`/Bun fetch; in B (fresh base) repeat with network blocked (`unshare -rn` or `--repository_disable_download`). PASS iff B succeeds and `ls -l $(bazel info output_base)/external | grep -c -- '-> .*/contents/'` equals the number of repos A fetched, and `du -sL`-of-new-bytes per worktree for external repos is < 50 MB. List repos that were *not* symlinked (module-extension repos) as per-worktree cost.
- **E7 Containment alternatives.** Compare wrapper `systemd-run --scope -p MemoryMax=14G` against `--experimental_run_in_user_cgroup` (+ `--io_nice_level`): PASS iff a deliberately memory-hungry action is killed/limited without the live service's unit being touched, and `systemctl --user show` reports the limit.
- **E8 Disk + remote layering.** With bazel-remote on loopback: A uploads, B (empty disk cache) builds with both flags: PASS iff B's hits are remote hits, and a repeat in C with the remote killed mid-build still completes with <= 10 s added versus no remote (this is Task 0.12c's pass bar); also confirm B's disk cache now contains the blobs (`du` grew).
- **E9 rc-file semantics guard.** Unit-test `check-bazelrc.sh` against the finding-1 case: a fixture `.bazelrc` with `startup:agent --max_idle_secs=30` must fail the check; a `startup:linux` line must pass.
- **E10 Btrfs reflink precondition.** For the shared cache dir and an output base: `filefrag -v` of an output restored from a hit shares an extent with its CAS blob (`shared` flag). PASS iff `shared` appears; otherwise measure the 5-worktree disk term without it (Task 0.10a's improvement clause 0.80x would then need a copy-based budget).
- **E11 Concurrent cold starts (cost of not queuing).** 3 servers start the same cold build at once vs 3 serialized through the wrapper: PASS iff serialized total CPU-seconds (from profile `CPU usage`) <= 60% of concurrent (expected, since the 2nd and 3rd serialized builds hit). Result feeds the N=2 decision.
