# Adversarial Review: backlog-triage-e2e-hardening

**Date**: 2026-06-23
**Verdict**: BLOCKED

## Blockers

- [ ] **E2e test creates item via wrong path, making the guard unreachable** — The e2e test in Task 3.1.2a calls `backlogPage.fillNewItemForm(...)` which uses the `+ New Item` modal (`BacklogItemForm.tsx`). That modal **already requires** `repoPath` (line 51 of `BacklogItemForm.tsx`: `if (!initialValues?.id && !repoPath.trim()) { errs.repoPath = "..." }`). An item created through that modal will always have a non-empty `repoPath`, meaning the Trigger Triage button will never be disabled, and `expect(triggerBtn).toBeDisabled()` will **always fail**. The root-cause path is the `BacklogEmptyState` inline form (`BacklogEmptyState.tsx`), which collects only title + priority (no repoPath) and calls `onCreateItem({ title, priority })` — it is the only creation path that produces an item with `repoPath = ""`. The test must use the empty-state form path (`[data-testid="backlog-empty-cta-button"]` → `[data-testid="backlog-empty-form"]`) to create a no-repoPath item, but the plan does not account for this. **Recommendation**: Replace the test's item-creation step with the empty-state inline form flow. If the test environment may already have items (non-empty backlog), add a `BacklogPage.createItemViaEmptyStateForm(title)` helper and guard the test with a precondition check (or a dedicated isolated test instance). Alternatively, create the item directly via the RPC with an empty repoPath.

- [ ] **Test cleanup uses `DeleteBacklogItem` RPC which does not exist** — Task 3.1.2a's `test.afterEach` cleanup calls `request.post('.../SessionService/DeleteBacklogItem', ...)`. The generated proto bindings (`web-app/src/gen/session/v1/backlog_pb.ts`) expose only `ArchiveBacklogItem`, not `DeleteBacklogItem`. The cleanup will silently 404 on every test run (the `try/catch` swallows the error), leaving orphan items in the test database that will corrupt subsequent empty-state tests. **Recommendation**: Replace with `ArchiveBacklogItem` (which does exist), or add explicit test isolation (a dedicated `STAPLER_SQUAD_INSTANCE` per test run). The plan's comment "Adjust the endpoint path to match the actual DeleteBacklogItem RPC" acknowledges this uncertainty but does not resolve it.

## Concerns

- [ ] **Brace-scan breaks on JSON embedded in research content** — The proposed brace-scan implementation uses `strings.Index(raw, "{")` (first brace) and `strings.LastIndex(raw, "}")` (last brace). The triage prompt explicitly asks subagents to write markdown files containing freeform text including `{` and `}` characters (e.g., code blocks in `architecture.md`, `pitfalls.md`). If any of that research content is echoed back into the final LLM output (which multi-step prompts sometimes do for synthesis context), the "first `{`" may fall inside an intermediate research block while the "last `}`" falls in the real JSON — the extracted substring `raw[start:end+1]` will span both blocks and fail to unmarshal. The `ParseHeadlessVerdictResult` pattern being copied was designed for single-step review calls; multi-step triage with embedded sub-content is a harder case. **Recommendation**: At minimum, document this limitation in the function comment. Consider a secondary fallback that tries the last well-formed JSON object if the `start..end` extraction fails to unmarshal. The unit test `TestParseHeadlessTriageResult_IntermediateJSONIgnored` covers adjacent JSON objects, not nested or interleaved content — add a test case where intermediate content contains `{code: "example"}` prose.

- [ ] **Missing `aria-disabled` attribute on the `BacklogItemCard` button** — Story 1.2.3 only adds `disabled: !item.repoPath` to `getActionSpec`'s `"ready"` case. The card renders the button as `disabled={actionSpec.disabled || isTriageRunning}` (line 125 of `BacklogItemCard.tsx`) but never sets `aria-disabled`. The "Mark Ready" guard in `BacklogItemCard` (the "idea" case, line 27) already has this gap — but the plan is adding a new guard and should add `aria-disabled` for it. Without `aria-disabled`, screen readers do not announce the disabled state. The acceptance criteria in Story 1.2.3 do not mention `aria-disabled`, yet Stories 1.2.1 and 1.2.2 do. This inconsistency should be harmonized. **Recommendation**: Add `aria-disabled` to the `ActionSpec` interface (optional bool) and thread it through to the card button, or add `aria-disabled={!!actionSpec.disabled}` unconditionally on the card button.

- [ ] **Requirements Success Metric #3 is entirely unaddressed** — Requirements §Success Metrics item 3 states: *"An e2e test exercises: create item → set repo_path → trigger triage → verify loading indicator → verify item transitions to 'ready'."* The plan implements only the negative gate check (button disabled, metric #1). The happy-path test (metric #3) is absent from the plan. The requirements also mention `triggerTriage` and `waitForTriageComplete` helpers in `BacklogPage.ts` scope (§Scope / In Scope). Those helpers are not planned anywhere. **Recommendation**: Either explicitly descope metric #3 in the plan (noting that the mock-triage concern from Open Question #1 is unresolved) or add a story for it. As written, the plan claims "Ready for implementation" while leaving a stated success metric uncovered.

The plan should verify this pattern actually registers in `FEATURE_CATALOG` before the registry entry is created, since `make registry-generate` scans source markers, not the array const.

This is correct as written and needs no change; noted for clarity.
