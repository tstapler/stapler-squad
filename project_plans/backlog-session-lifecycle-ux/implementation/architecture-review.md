## Concerns

- [ ] **Story 4.4.2 (`AutoRespawnReview`) + Story 4.4.3 (`AutoRespawnTriage`) — duplicated "extract SessionUuid → call CreateRespawnEvent" logic, DRY/SRP inconsistently applied** — Story 4.4.1 (Task 4.4.1b) correctly extracts a shared `autoRespawnAutonomousWork(ctx, itemID, reason, triggeringSessionUUID)` helper used by both `AutoRespawnAutonomousWork` and `RemediateStaleWorkSession`, avoiding duplication between those two call sites. But Stories 4.4.2 and 4.4.3 do not receive the same treatment: each independently inlines "guard nil `ItemSession`, extract `.GetSessionUuid()`, call `s.storage.CreateRespawnEvent(...)`" — structurally identical logic, written twice. This is the same class of duplication Story 4.4.1 explicitly fixed for the other two call sites, just left unfixed here. **Remediation**: extract a small shared helper, e.g. `func respawnResultUUID(is *sessionv1.ItemSession) string { if is == nil { return "" }; return is.GetSessionUuid() }`, used by both Task 4.4.2b and Task 4.4.3b, so a future 5th respawn-triggering call site has one obvious pattern to follow instead of two independently-evolved copies.

- [ ] **Story 4.2.1 (`CreateRespawnEvent` signature) — `triggeringSessionUUID, resultingSessionUUID string` are same-typed, adjacent, and easily transposed** — `func CreateRespawnEvent(ctx context.Context, itemID, reason, triggeringSessionUUID, resultingSessionUUID string) error` is exactly the primitive-obsession anti-pattern the `type-driven-design` skill calls out by name (`func transfer(from, to string)` — "easy to swap"). This function is called from 4 different call sites (Stories 4.4.1–4.4.3), each computing a UUID pair independently; nothing in the signature stops a future call site (or a copy-paste slip in one of these very 4 sites) from swapping the two arguments — both are optional/nillable strings that both frequently hold real-looking UUID values, so a swap would not fail any validation and would silently produce a backwards audit row (making a respawn look like it triggered the session that actually triggered it). The acceptance criteria in Stories 4.4.1–4.4.3 do specify exact expected values per field, which would catch a swap *if* a test asserts on both fields precisely — but the type system offers no static protection, only test discipline. **Remediation**: at minimum, define `type RespawnEventParams struct { TriggeringSessionUUID, ResultingSessionUUID string }` (or a positional struct with named fields) so call sites must name which is which; a full `type SessionUUID string` newtype is optional and probably not worth it at this call-site count, but a named-field struct is a near-zero-cost fix for a real transposition risk.

## Nitpicks

- **`RespawnReason` untyped-string justification is thinner than it could be**: the plan cites `SessionRoleWork` (an untyped string const) as the matching precedent, but `session/backlog.go` also contains `BacklogStatus`/`BacklogCategory` — type aliases with an `IsValid()` method — a *stronger* idiom for string-vocabulary domain concepts in the same file. The distinguishing factor the plan doesn't state explicitly: `BacklogStatus`/`BacklogCategory` cross a validation boundary (user-facing selection, proto/external input), while `RespawnReason` (like `SessionRoleWork`) is only ever produced internally from 4 known Go constants, never parsed from untrusted input — so untyped-string is actually the right call, just for a sharper reason than "matches `SessionRoleWork`." No action needed; worth a one-line addition to the Pattern Decisions justification if the plan is revised.

- **`BacklogItem`'s embedded-child-collection count keeps growing**: this is the 4th eagerly-loaded child collection on `GetBacklogItem` (`item_sessions`, `status_events`, `progress_notes`, now `respawn_events`), each added by a separate project. Individually justified at "tens of items/events" scale (per requirements' Non-functional Requirements and the plan's own 50-row cap), but worth a forward-looking note: if a 5th/6th collection is added by a future project, revisit whether `GetBacklogItem` should return summary counts by default with detail sections fetched on expand, rather than continuing to grow the eager-load set. Not this plan's problem to solve.

- **`formatEndReason`'s unrecognized-value fallback is silent**: `formatEndReason`'s `default` case returns `{label: "", severity: "none"}` (Task 1.2.2a) — a future backend `end_reason` value added without updating this switch silently renders no chip rather than surfacing as "unknown reason." This matches the existing `formatPauseReason` convention in this codebase (not a regression introduced by this plan), just noting it as an inherited, not new, gap.

- **`session.Storage.CreateRespawnEvent`'s type-assertion-to-concrete-type pattern** (`s.repo.(*EntRepository)`, Task 4.2.1d) is pre-existing codebase debt (already used by `UpdateItemSessionEnded`, `ListItemSessions`, etc.) — the `Storage.repo` field is nominally an interface but effectively has one real implementation reached via a downcast escape hatch at every non-trivial call. The plan correctly matches this existing (if imperfect) convention rather than inventing a new one; redesigning `Storage`'s abstraction boundary is out of scope for this project and would be disproportionate scope creep here. Flagging only so it's on record as a candidate for a future dedicated cleanup, not something this plan should fix.
