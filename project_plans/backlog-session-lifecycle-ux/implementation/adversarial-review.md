Re-verified live (2026-08-01): the check is correctly wired (dynamically resolves the current commit via `git log`, not a hardcoded SHA), and it's a real hard-stop gate — Task 0.1.1a explicitly says "this is a hard stop, not a soft note" and requires either (a) merging the prerequisite commits to both remotes first, or (b) proceeding only if implementation stays in the same local branch that already has them, with a mandatory PR-description disclosure. ## Concerns

- [ ] **Unresolved Question #1 understates a real, documented contradiction between two of this project's own research docs.** ux.md §4 explicitly recommends: *"Avoid an 'empty state' UI... for a case that will be the majority case (most items never need remediation)... omit the section rather than showing an empty state."* features.md explicitly recommends the opposite: always render `RespawnHistorySection` with an explicit empty state, citing `WorkflowHistorySection`'s precedent. The plan's Story 4.5.2 adopts features.md's answer and cites it as justification without acknowledging or reconciling ux.md's directly opposing, equally explicit recommendation — then labels the whole thing "a 1-line judgment call for whoever implements Story 4.5.2." It isn't a copy-wording call; it's an unresolved disagreement about whether the section is a common-case noise source or a discoverability aid. Resolve explicitly (a one-paragraph note is enough) before implementing 4.5.2, rather than deferring silently.

- [ ] **`BlockerChip`'s new `×N` accessible name is likely to be swallowed by its own parent's `aria-label`, undermining ux.md §3's explicit accessibility requirement.** Task 3.1.1a nests a second `aria-label`-bearing span (`aria-label="Respawned 3 times"`) inside the chip's existing outer span, which already carries `aria-label={label}`. `aria-label` on a plain, non-widget `<span>` (role=`generic`) is inconsistently honored by assistive tech in the first place, and nesting an independently-labelled child inside an already-labelled container is a known way for the inner label to never be announced — worse, if this codebase's own "role=`img`" chip-labeling convention (used elsewhere for the pause-reason tooltip, per ux.md §3) is ever applied to `BlockerChip`'s outer span, children — including the inner `aria-label` — would be excluded from the accessibility tree entirely. The safer fix: compose one full sentence at the outer chip's `aria-label` (e.g. `"${label}. Respawned 3 times."`) rather than relying on a nested label, matching the "full-sentence formatPauseReason-style aria-label" pattern this same plan uses correctly elsewhere (Task 1.2.2a/1.2.3a).

- [ ] **No retention/pruning story for `respawn_events`, and the "tens of events" scale estimate is contradicted by this project's own research.** pitfalls.md §4 cites concrete incident data (15+ restarts/day, 6 items respawned in a single BUG-053 sweep) suggesting a chronically-flapping item can accumulate hundreds of rows, not tens — data gathered from *this same codebase's* operational history, not a hypothetical. The plan's mitigation (Task 4.2.2b's `LIMIT 50` read cap) correctly bounds the actual failure mode the ADR calls out (large RPC payload / slow render), but there is no write-side cap or periodic prune anywhere in the plan, so both a single item's full row count and the table's total size grow unbounded indefinitely. For a long-lived single-user SQLite instance this is low-urgency, but it should be a stated, deliberate deferral (as ADR-001's Consequences section does gesture at — "if respawn volume... exceeds..., revisit") rather than an unstated gap; consider a follow-up backlog item for a delete-oldest-beyond-N trigger now that real volume data exists.

- [ ] **Mobile-layout verification is inconsistent across the three UI phases, despite a standing project-wide constraint.** requirements.md states "Must work on both mobile and desktop (touch targets, responsive layout)" as a hard constraint, and Phase 2 (Task 2.1.1b) includes an explicit "verify no layout regression on mobile width" step for `SessionCard.tsx`. Phase 3's `BlockerChip` ×N suffix (rendered directly on the board card, which pitfalls.md §6 explicitly flags as layout-budget-constrained on mobile widths) and Phase 4.5's `RespawnHistorySection` have no equivalent check. Add the same narrow-viewport spot-check Phase 2 got, at minimum for the board-card change (Phase 3), since that's the surface pitfalls.md specifically warned about.

- [ ] **The `resultingSessionUuid === ""` empty-state text collapses two operationally distinct situations into one ambiguous string.** Task 4.5.2b's copy — `"(no session — spawn was queued or failed)"` — doesn't distinguish "hit the concurrency cap and is waiting to retry" from "the spawn attempt itself failed," even though the `SpawnSessionFromItemResponse.queued` boolean that would disambiguate this is already available at the write call site (confirmed: `proto/session/v1/backlog.proto:412-419` documents `queued` precisely for this case). This directly undercuts one of requirements.md's own Success Metrics — distinguishing "actively being retried, backing off" from "stalled with no further automatic action" — at exactly the per-event granularity this feature exists to add. Recommend either storing the queued/failed distinction in the `reason` field or a small boolean, and rendering two distinct empty-state strings.

## Minors

- `RespawnReason` vocabulary is duplicated by hand between the Go constants (`session/backlog.go`) and the frontend `formatRespawnReason.ts` switch statement, with no shared codegen and no test asserting the frontend map covers every backend constant. Matches this repo's existing idiom for `SessionRoleWork`-style vocab (intentional, per Pattern Decisions), but a future 5th call site with a new reason string could silently render as the frontend's `default → raw string` fallback with nobody noticing. Low priority given only 4 values exist today.
- No acceptance criterion in Epic 4.1 exercises the new `respawn_events` cascade-delete behavior (deleting a `BacklogItem` should delete its `RespawnEvent` rows) with an actual test, unlike the implied expectation elsewhere that this mirrors `status_events`/`progress_notes`. Low risk since it's copying an already-shipped, presumably-tested pattern verbatim, but worth one assertion for parity.
- Story 5.1.1's "no net-new coverage gap" claim depends on `testIds` actually being backfilled into the 5 new per-feature registry JSON files during Phase 1–4's own test-writing tasks, but no task explicitly cross-references "go add the testIds now" — worth double-checking at Phase 5 that the registry's `tested`/`testIds` fields reflect what Phases 1–4 actually wrote, not just that the JSON shape is present.
