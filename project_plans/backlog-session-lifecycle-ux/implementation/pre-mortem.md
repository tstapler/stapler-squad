# Pre-mortem: backlog-session-lifecycle-ux
**Date**: 2026-08-01

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The 4 respawn call sites this plan instruments (`AutoRespawnAutonomousWork`, `RemediateStaleWorkSession`, `AutoRespawnReview`, `AutoRespawnTriage`) have a *documented, recent* history of firing more than once for one logical decision — commit `0ac676001` ("stop orphaned-triage recovery from over-penalizing shutdown kills and duplicating live calls") fixed exactly this class of bug in this exact subsystem. `CreateRespawnEvent` is called with no idempotency guard (no dedupe key, no "already recorded this trigger in the last N seconds" check), so any resurfaced or partially-covered race double-records a respawn. | `RespawnHistorySection` shows two back-to-back rows with the same `reason` and near-identical timestamps (and the same `triggering_session_uuid`) for an item that only respawned once — an obviously-wrong count visible to the user on first use of the exact feature meant to build trust in "what was actually tried." | Add a uniqueness guard before insert (e.g. skip-if-exists on `(item_id, triggering_session_uuid, reason)` within a short window), and add an explicit acceptance-criterion test in Story 4.4.1/4.4.3 that replays the reconciliation-sweep-fires-twice scenario `0ac676001` demonstrates is real in this code path, not hypothetical. | P1 |
| 2 | Two different "how many times has this been retried" counters ship in the same PR and will structurally diverge: `BlockerChip`'s `×N` reads `BacklogStuckState.remediation_attempts`, which is explicitly resolve-in-place (requirements.md's Rabbit Holes) and almost certainly resets/changes when a stuck episode resolves; `RespawnHistorySection`'s count is append-only `RespawnEvent` rows that never reset across episodes. An item that cycles stuck→resolved→stuck several times will show a small `×N` badge on the board card next to a much larger respawn-history list in the detail panel for the same item. | A user opens an item's detail panel, sees "×2" on the board-card chip, expands Respawn History, and counts 7 rows — no explanation for the mismatch anywhere in the UI. | Add one sentence to the Pattern Decisions / RespawnHistorySection copy clarifying the two counters measure different things ("current stuck episode" vs. "all-time"), or compute `BlockerChip`'s `×N` from a windowed `RespawnEvent` count instead of `remediation_attempts` so both surfaces agree by construction. | P1 |
| 3 | `CreateRespawnEvent` is best-effort (log-and-swallow on failure, per Pattern Decisions), and the Observability Plan explicitly declines any metrics/alerts ("single-user internal tool, no oncall"). A DB write failure — lock timeout, disk pressure, a schema-drift edge case — silently produces a gap in the "durable, queryable" audit trail with no signal anywhere except an unmonitored log line in `~/.stapler-squad/logs/stapler-squad.log`. | Weeks after shipping, investigating a specific incident, the user notices `RespawnHistorySection` is missing an event they know happened (e.g. cross-referenced against a log line or the `BlockerChip` count from failure #2) — discovered by accident, not by any system signal. | At minimum, promote `CreateRespawnEvent` write failures to something more visible than `log.ErrorLog.Printf` (e.g. increment a small in-memory counter surfaced on a diagnostics page), or add a periodic sanity check comparing `BacklogStuckState.remediation_attempts` deltas against `RespawnEvent` insert counts and logging a loud warning on mismatch. | P2 |
| 4 | `formatEndReason`'s fallback for any `end_reason` value not in its 5-case switch (Task 1.2.2a) returns `{ label: "", severity: "none" }` — identical to the genuine "clean success" case (`""`/`shutdown`). If a future headless-call failure mode is added to the Go backend without updating this switch, the newest/least-understood failure — exactly the one a user most needs visibility into — renders **no chip at all**, indistinguishable from success. This inverts the feature's purpose for precisely the case it matters most. | A headless triage/review call fails with a new, unclassified `end_reason` string; `SessionsSection.tsx` shows the session as if it ended cleanly, and the user has no reason to investigate. | Change the default case to a distinct `"warning"`-severity "Unrecognized end reason: {reason}" chip instead of silently mapping to `"none"` — only `""` and `"shutdown"` should map to no-chip; everything else, known or not, should render something. | P2 |
| 5 | `GetBacklogItem` gains a 4th eagerly-loaded child collection (`item_sessions`, `status_events`, `progress_notes`, now `respawn_events`), queried on every poll for every item regardless of whether that item has any respawn events. pitfalls.md's own research cites 15+ restarts/day and 6 items respawned in a single BUG-053 sweep — meaning at least one real item can accumulate hundreds of `RespawnEvent` rows, not the "tens" the plan's scale estimate assumes. On SQLite (single-writer), a chronically-flapping item's frequent writes plus its own detail-panel polling reads can compound exactly during the window the feature exists to make visible. | The board or item-detail panel becomes noticeably slower to refresh specifically while a flapping item is actively respawning — a self-inflicted latency spike correlated with the exact scenario this feature was built to surface. | Verify the `(item_id, created_at)` index is actually used by SQLite's query planner (`EXPLAIN QUERY PLAN`) before shipping, and benchmark `GetBacklogItem` latency with a seeded 500+-row `respawn_events` table for one item, not just the "tens of events" happy path. | P3 |

## P1 Items (address before implementation)
- [ ] Failure #1 — Add an idempotency/dedupe guard to `CreateRespawnEvent` (or a pre-write existence check) before Task 4.4.1b/4.4.2b/4.4.3b are implemented, and add a test replaying the double-invocation scenario `0ac676001` fixed, so the new audit trail doesn't inherit the exact duplicate-call bug class this subsystem was just patched for.
- [ ] Failure #2 — Before implementing Story 3.1.1 and Story 4.5.2 together, add an explicit note (Pattern Decisions or inline UI copy) reconciling why `BlockerChip`'s `×N` (episode-scoped, resets on resolve) and `RespawnHistorySection`'s count (all-time, append-only) will show different numbers for the same item — or change `BlockerChip` to derive its count from `RespawnEvent` so the two surfaces agree by construction.

## Summary
5 failure modes identified: 2 P1, 2 P2, 1 P3. Top failure mode: the plan instruments 4 respawn call sites with no idempotency guard even though this exact subsystem was patched weeks ago (`0ac676001`) for firing duplicate live calls from the same reconciliation sweeps — without a dedupe check, the new "durable, queryable" respawn audit trail is likely to inherit that duplicate-call bug and double-record respawns, undermining the feature's core credibility on first real-world use.
