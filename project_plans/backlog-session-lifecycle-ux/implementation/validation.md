# Validation Plan: backlog-session-lifecycle-ux

**Date**: 2026-08-01

## Happy Path Scenario

Given a backlog item that has been auto-remediated 3 times (Baseline: an item stuck with `BacklogStuckState.remediation_attempts = 3`, at least one `ItemSession` with a non-empty `end_reason`, and at least one recorded `RespawnEvent` row), when the user opens the board page and then clicks into that item's detail panel, then they see — without opening `/unfinished` or reading logs — the `×3` remediation-count suffix on the board card's `BlockerChip`, the specific session's end-of-call reason chip in the Sessions section, and the full respawn timeline (reason, timestamp, triggering/resulting session) after expanding the "Respawn History" section.

### `migration_should_be_reversible` — scenario and what "reversible" means here

This plan's migration is **additive-only via ent auto-migration** — there is no hand-written up/down SQL script (per the plan's own Migration Plan section: "No manual SQL migration file exists elsewhere in `session/ent/schema/*.go` siblings, so none is added here"). "Reversible" in this context does **not** mean a scripted down-migration; it means: **a plain code revert leaves the database in a safe, non-broken state**, because the migration only ever adds a new table and never drops/renames/alters an existing column.

Test design:
1. **Given** a fresh test-scoped SQLite DB, **when** `ent generate`'s auto-migrate-on-boot path runs against the schema *before* `RespawnEvent` is added (simulate by running migration with the schema as of the parent commit, or equivalently assert against a DB that never had the table), **then** all pre-existing tables (`backlog_items`, `backlog_status_events`, `backlog_progress_notes`, `item_sessions`, etc.) are present and queryable with their pre-existing columns intact — establishes the "before" baseline.
2. **Given** that same DB, **when** the post-change schema (including `RespawnEvent` + the `respawn_events` edge on `BacklogItem`) auto-migrates on next boot, **then**: (a) the new `respawn_events` table exists with the expected columns (`id`, `item_id`, `reason`, `triggering_session_uuid`, `resulting_session_uuid`, `created_at`) and an index on `(item_id, created_at)`; (b) every pre-existing table/column from step 1 is unchanged (same column set, same data still readable) — asserts additive-only, no destructive `ALTER`.
3. **Given** the post-change DB from step 2 with at least one `RespawnEvent` row written, **when** the code is reverted (simulate by exercising only the pre-change code paths against this DB — i.e. confirm `GetBacklogItem` and every other pre-existing query still succeeds and returns correct data when the new `WithRespawnEvents` eager-load call is simply not invoked), **then** all pre-existing functionality works identically to step 1's baseline — the orphaned `respawn_events` table is inert (unreferenced, causes no errors, matches the plan's "Reverting the code revert is sufficient; the orphaned table is inert" rollback posture) and requires no manual cleanup for correctness (only for tidiness, which is out of scope).

Name: `migration_should_be_reversible`. Type: Migration. This is a single test function with 3 sequential phases (pre-migration baseline → post-migration additive check → simulated-revert compatibility check) run against one temp-file SQLite DB per Go subtest (`t.Run`), not three independent tests, since the phases build on the same DB state.
