# Adversarial Review: session-classifier-pipeline

**Date**: 2026-09-11
**Verdict**: CONCERNS

## Blockers

None. All three prior blockers are resolved:

1. **`ApplyLLMTagResult` suppression filtering — RESOLVED.** Task 4.3.2a routes candidate tags through `filterSuppressedTags(tags, i.SuppressedRuleTags)` — the plan states explicitly this is "the exact same package-level helper `reclassifyTagsLocked` calls... do not write a second, separately-maintained suppression check here" (plan.md:678), and the Domain Glossary entry for `filterSuppressedTags` (plan.md:33) confirms it's one function called from both `reclassifyTagsLocked` and `ApplyLLMTagResult`, defined once in `session/instance_actor_setters.go`. Story 4.3.2's third acceptance criterion (plan.md:673-674) is a concrete "poller tries to re-apply a suppressed tag" test case — `SuppressedRuleTags = {"Feature": true}`, poll tick returns `["Feature"]` again, asserts it is not re-added — implemented by Task 4.3.2c.
2. **`SetTags` provenance/suppression bookkeeping — RESOLVED.** ADR-002 (lines 95-103) now explicitly identifies `SetTags` as "the path the shipped Tag Editor Modal's save button actually calls," and Story 3.2.1 (plan.md:447-463) gives it real diff-based logic: Task 3.2.1d computes `removed`/`added` sets against current `i.Tags` and applies the same suppress/clear bookkeeping as `RemoveTag`/`AddTag`, via two shared unlocked helpers (`suppressIfProvenanced`/`clearSuppression`) called from all three mutation methods so they can't drift. Concrete acceptance criteria and Given/When/Then cases cover removal-via-edit, re-add-via-edit, and no-dangling-provenance-entry scenarios (plan.md:457-460), with tests in Task 3.2.1e.
3. **Exhaustive setter list + structural safeguard — RESOLVED.** Task 3.3.1d (plan.md:513-515) requires the grep-derived enumeration to happen "before Task 3.3.1e, not during it," and names the exact grep pattern and scope (including explicitly carving out `instance_worktree.go`'s unlocked path to Story 3.3.2 rather than leaving it ambiguous). Task 3.3.1f (plan.md:521-523) is a concrete, named test (`TestAllTagRelevantSettersCallReclassify`) that re-runs the same grep/AST pattern at test time and asserts every matching `xxxLocked` function's body calls `reclassifyTagsLocked`, with a named fallback mechanism (chokepoint refactor + ast-grep lint pattern) if the grep-based test proves brittle. This is a real, specific mechanism — not "add a test" — and it does name which setters must be covered (whatever Task 3.3.1d's enumeration produces) and how a future omission would be caught (grep-based CI-time assertion, or an ast-grep-checked chokepoint).

## Concerns

- [ ] **Concurrent `TaggingRule` CRUD write conflicts remain unaddressed** (carried over from the prior review, still open — not silently dropped). No task in Epic 2.1/2.3.2 verifies a unique index/constraint on `rule_id` or confirms `ApprovalRule`'s existing CRUD path is actually safe under concurrent `Upsert` calls; the plan still only says "mirror `ApprovalRule`'s ent CRUD" without a task to *confirm* that precedent is safe. — Add a task to Epic 2.1 or 2.2 verifying `ApprovalRule`'s unique-constraint/upsert semantics under concurrent writes before assuming `TaggingRule` inherits the same guarantee.
- [ ] **`SessionTagVocabulary` live-update staleness remains an open question, not resolved** (carried over — still tracked, not dropped, per Unresolved Questions plan.md:107). The plan still frames "derive from `TaggingEngine.Rules()`'s `OutputTag`s... so the vocabulary never drifts" only as a recommendation for the implementer to pick, not a decided, task-level acceptance criterion tied to Task 4.3.1a's `engine` field. If the vocabulary is actually computed once at poller construction (as Task 4.3.1a's field list suggests: `engine *classifier.TaggingEngine` stored once, not re-queried per tick), a user-added `TaggingRule` with a new `OutputTag` won't reach the LLM's vocabulary until restart. — Resolve this at plan level (not implementer-discretion) before Phase 4 implementation: compute vocabulary from `engine.Rules()` per poll tick, not once at construction.
- [ ] **Story 3.3.2's fresh-lock reclassification doesn't address the pre-existing unsynchronized write to `i.Branch` inside `setupFirstTimeWorktree()`.** The plan (plan.md:536, 543-544) correctly avoids a *new* race by acquiring `i.mu.Lock()` itself in `ReclassifyTagsAfterCreate()` rather than reusing an assumed-held lock — reads at lock-acquisition time are always the most recent value under `i.mu`, so `ReclassifyTagsAfterCreate` itself is race-free with respect to other `i.mu`-guarded readers/writers. But `setupFirstTimeWorktree()` itself still writes `i.Branch` with **no synchronization at all** (documented as running under `startMu`, a "structurally different synchronization domain"), so if any other goroutine calls a `Locked` setter that touches `i.Branch` concurrently with `Start()` (e.g., a rename request racing with session creation, or a UI-triggered rename immediately after session-create returns but before this instance is guaranteed idle), that write races unsynchronized against `setupFirstTimeWorktree`'s write. This is a pre-existing gap the plan inherits rather than introduces, and it is explicitly out of scope for this project, but the plan's own `-race` test for Story 3.3.2 (Task 3.3.2c) only exercises `Start()` concurrent with *reads* (`GetTags()`/`Snapshot()`), not `Start()` concurrent with a *write* to `Branch` from another setter — so this specific race shape is not something the new test would catch even if it existed today. Not a blocker (out of scope, pre-existing, not worsened by this change) — flagging so it isn't mistaken for "proven race-free by the new test."
- [ ] **Retraction lookup for a deleted `TaggingRule` is unspecified.** `reclassifyTagsLocked`'s retraction step (plan.md:510) looks up each `RuleTagProvenance` entry's rule "by ID in `engine.Rules()`"; if the owning rule was deleted via CRUD (Epic 2.3/5), that lookup finds nothing, and the plan doesn't say whether the tag is then treated as unretractable (orphaned provenance, tag persists forever) or removed defensively. Low likelihood in practice (seed rules aren't normally deleted), but the behavior is undefined rather than a deliberate choice. — Add one line to Task 3.3.1c specifying the behavior for a provenance entry whose rule ID no longer exists in the engine (recommend: treat as still-owned/non-retractable, since "rule was deleted" is a different event than "condition stopped matching," and a future "clean up orphaned provenance on rule deletion" task can handle that case explicitly if desired).
