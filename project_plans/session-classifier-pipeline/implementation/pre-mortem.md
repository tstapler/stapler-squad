# Pre-mortem: session-classifier-pipeline
**Date**: 2026-09-11

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The sync-fixpoint retraction loop in `reclassifyTagsLocked` (Task 3.3.1c) has no case for `RuleTagProvenance` entries with `ruleID == "llm"` — once Phase 4 ships, looking that ID up in `engine.Rules()` finds nothing, and if "rule not found" is treated the same as "condition no longer matches" (the plan never says otherwise), every LLM-applied tag is silently stripped by the very next sync-triggered mutation (a rename, a program change, any Task 3.3.1e-wired setter). | A session that was correctly LLM-tagged (e.g. `Feature`) loses that tag the moment its name/branch/path is edited again — tags visibly flicker on/appear-then-vanish right after any unrelated session edit, with no error logged (the retraction path already has a log line, so it fires quietly as "expected" retraction). | Add an explicit acceptance criterion/task to Epic 3.3 (before Phase 4 lands, testable now with a synthetic `"llm"`-provenanced entry) stating the retraction loop must skip any entry whose `ruleID == llmSentinelRuleID` — the sync engine has no authority over LLM-owned tags. Add a regression test asserting a synthetic `RuleTagProvenance{"X": "llm"}` entry survives a fixpoint pass where `"X"`'s condition (trivially) doesn't match any sync rule. | P1 |
| 2 | `TaggingRule` CRUD (Epic 2.1/2.3.2) mirrors `ApprovalRule`'s ent CRUD path without ever verifying that path is safe under concurrent `Upsert` — no task confirms a unique constraint on `rule_id` or exercises two simultaneous edits (e.g. two browser tabs, or a user editing while a seed-reconciliation upsert runs). | Two near-simultaneous rule edits — one is silently lost (last-writer-wins with no conflict signal) or a second `Upsert` throws a 500 on a unique-constraint violation that was never handled; user sees their edit "succeed" in the UI but the rule reverts to the old value on next reload. | Add a task to Epic 2.1/2.2 that reads `ApprovalRule`'s actual constraint/upsert semantics (not just "mirror it") and adds a concurrent-`Upsert` integration test for `TaggingRule` before assuming the same guarantee transfers. | P2 |
| 3 | `SessionTagVocabulary` is computed once at `SessionTagClassificationPoller` construction from `engine.Rules()` (Task 4.3.1a stores `engine` but the vocabulary-refresh cadence is left to "implementer discretion" per Unresolved Questions) — a user-added `TaggingRule` with a new `OutputTag` never reaches the LLM's allowed vocabulary until the process restarts, since the closed-vocabulary filter (Task 4.1.1c) rejects anything not in the stale list. | User adds a custom tagging rule/tag via the new CRUD UI, expects the LLM fallback to also be able to apply it to ambiguous sessions, but those sessions keep coming back `Unclassified` (or an old tag) indefinitely — looks like the LLM step is broken rather than running against a stale vocabulary snapshot. | Resolve this at plan level, not implementer discretion: recompute the vocabulary from `engine.Rules()` on every poll tick (cheap — `engine.Rules()` already returns a fresh, mutex-guarded copy), not once at construction. Add a test: adding a rule with a new `OutputTag` after the poller starts changes the very next tick's accepted vocabulary. | P2 |
| 4 | Retraction for a *deleted* `TaggingRule` is unspecified: `reclassifyTagsLocked`'s by-ID lookup in `engine.Rules()` also finds nothing when a rule was removed via CRUD (as opposed to LLM-owned) — behavior (orphaned-forever vs. defensively-stripped) is undefined, so whichever an implementer picks ad hoc becomes silently load-bearing. | An operator deletes/disables a mis-authored rule specifically to stop a bad tag from sticking, but every session already carrying that tag keeps it forever (if "not found" is treated as non-retractable) — or, the opposite implementation choice ships and a legitimate rule edit unexpectedly strips tags users still wanted, with no way to tell the two "not found" cases apart from a log line. | Add one explicit line to Task 3.3.1c's spec: a provenance entry whose rule ID no longer exists in `engine.Rules()` is treated as non-retractable (rule deletion is a different event from "condition stopped matching"); track "clean up orphaned provenance on rule deletion" as an explicit fast-follow task, not silence. Add a test distinguishing "rule ID absent" from "rule present but condition false." | P2 |
| 5 | Story 3.3.2's `ReclassifyTagsAfterCreate()` acquires `i.mu.Lock()` from inside `Start()` right after `setupFirstTimeWorktree()` returns, but the plan never confirms whether `Instance.startMu` is still held at that call site — if it is, this is the first place in the codebase nesting `startMu` → `i.mu`, and any existing or future code path that acquires the same two locks in the opposite order becomes a real deadlock, not just a race. | Under concurrent load (a rename request landing right as a new-worktree session finishes creating), a session actor hangs permanently mid-creation — "Starting…" never resolves — and if the reverse-order path is on a shared code path, other unrelated sessions relying on the same lock/goroutine pool stall too; a goroutine dump shows two goroutines each blocked waiting on the other's mutex. | Add an explicit acceptance criterion to Task 3.3.2b confirming (a) `startMu` is released before `ReclassifyTagsAfterCreate()` acquires `i.mu`, and (b) no other code path acquires `i.mu` before attempting `startMu` (one grep-based check or a one-line comment at the call site pinning the invariant). If `Instance.mu`/`startMu` already use the repo's `deadlock.RWMutex` (cycle-detecting) rather than stdlib `sync.Mutex`, confirm that explicitly too — it converts a silent hang into a loud panic, which is strictly better but still worth stating as a deliberate property, not an accident. | P3 |
