## Concerns

- [ ] **Task 3.3.1c — sync-fixpoint retraction loop has no stated handling for `"llm"`-sentinel provenance entries.** The retraction step iterates `s.inst.RuleTagProvenance` and, for each `(tag, ruleID)`, looks up that exact rule by ID in `engine.Rules()`, removing `tag` if it no longer matches the current context. Once Phase 4 ships, `RuleTagProvenance` can contain entries with `ruleID == "llm"` (`llmSentinelRuleID`, Task 4.3.2a) — but `"llm"` is never a `TaggingRule.ID` in `engine.Rules()`, so this lookup will find no rule for every LLM-derived tag. The plan never states what "rule not found" means for this loop: if it's treated the same as "no longer matches," every sync-triggered actor setter (a rename, a program change, etc. — anything wired in Task 3.3.1e) would silently strip every LLM-applied tag on the very next mutation after Phase 4 ships, which is the identical class of bug (retracting a tag whose "owning rule" wasn't actually re-checked correctly) the original Blocker 1 fix was meant to eliminate — just recurring at the Phase 3/Phase 4 seam instead of within Phase 1's engine. **Recommendation**: add an explicit task/acceptance-criterion stating the retraction loop must skip (never retract) any `RuleTagProvenance` entry whose `ruleID == llmSentinelRuleID`, since the sync engine has no authority over LLM-owned tags — only `ApplyLLMTagResult`'s own suppression/provenance handling governs those. Add a regression test once Phase 4 lands (or as a Phase 3 test using a synthetic `"llm"`-provenanced entry, since the field shape already exists in Phase 3).

- [ ] **Story 3.3.2 / Task 3.3.2b — new `startMu` → `i.mu` acquisition order is asserted safe but never verified against the reverse order.** `ReclassifyTagsAfterCreate()` is called from inside `Start()` "immediately after `setupFirstTimeWorktree()` returns." The plan doesn't state whether `Start()` still holds `Instance.startMu` at that point, or has already released it. If `startMu` is still held when `i.mu.Lock()` is acquired inside `ReclassifyTagsAfterCreate`, this is the first place in the codebase establishing a `startMu` → `i.mu` lock order (per the documented rationale at `session/git_worktree_manager.go:22-26`, the two mutexes were previously used independently, never nested). If any existing or future code path acquires the two locks in the opposite order (`i.mu` then `startMu`), this introduces a real deadlock risk — exactly the kind of hazard the task description flagged as worth watching for in a fix that adds its own locking. **Recommendation**: add an explicit note/acceptance criterion in Task 3.3.2b confirming (a) whether `startMu` is released before `ReclassifyTagsAfterCreate()` is called, and (b) that no other code path acquires `i.mu` before attempting `startMu` — a one-line grep-based check or a comment at the call site would close this out.

- [ ] **Task 3.4.1b / Task 3.3.2a — mildly redundant, ambiguously-specified double call to the drop-`Unclassified` helper.** Task 3.4.1b's heading says to call `dropUnclassifiedIfOtherTagsPresentLocked(s)` "at the end of `reclassifyTagsLocked`," implying it's invoked *inside* that function, but Task 3.3.2a separately says `ReclassifyTagsAfterCreate` "calls `reclassifyTagsLocked(s, i.taggingEngine)` followed by `dropUnclassifiedIfOtherTagsPresentLocked(s)`" as two distinct steps — which would double-call the helper (harmless/idempotent, but signals the plan itself is inconsistent about whether the drop-helper is `reclassifyTagsLocked`'s own last step or a step every caller must remember to add separately). **Recommendation**: pick one — either fold the call into `reclassifyTagsLocked` itself (then Task 3.3.2a shouldn't re-list it), or make every caller (each wired actor setter in Task 3.3.1e, plus `ReclassifyTagsAfterCreate`) responsible for calling it explicitly (then Task 3.3.1e's task text should say so too, since it currently doesn't mention this helper at all).
