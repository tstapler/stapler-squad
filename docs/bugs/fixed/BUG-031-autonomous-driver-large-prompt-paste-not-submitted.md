# BUG-031: AutonomousDriver's Turn-Injection Prompt Can Sit Unsubmitted in the TUI's Paste Buffer [SEVERITY: High]

**Status**: ✅ FIXED (2026-07-22)
**Discovered**: 2026-07-22 — live screenshot from session `stapler-squad-fix-backlog-status-audit-trail-r16` (backlog item `9264efe7-b4c2-455a-9e2a-ab0196a63ecd`, "Backlog History feature Broken")
**Fixed**: 2026-07-22 — `session/autonomous_driver.go`
**Impact**: A large (multi-paragraph) autonomous-driver continuation prompt injected into a session's tmux pane can be interpreted by Claude Code's TUI as an in-progress paste rather than submitted input — the text sits in the input buffer, un-actioned, and the session stalls until some other event (a `/loop` wakeup, a human noticing) intervenes. Burns wall-clock time on an autonomous, unattended session with nothing happening.

## Live Reproduction (2026-07-22)

Screenshot (`uploads/1784740692786-3832009888-1000164806.png`) of session `stapler-squad-fix-backlog-status-audit-trail-r16` (an autonomous, `backlog:revision` session, r16 — its 16th rework round) shows a large multi-paragraph prompt sitting at the input line, ending with `[Pasted text #4 +1 lines]` and no submitted turn following it — the TUI waiting at its prompt (`❯`) with `⏵⏵ auto mode on` showing, not processing anything. A live `tmux capture-pane` on the same session during this investigation reproduced the identical pattern again, at a different point in the same session's lifetime.

## Root Cause

`AutonomousDriver.run` (`session/autonomous_driver.go`) injected each turn's continuation prompt via a single raw PTY write: `d.inst.SendKeys(nextMsg + "\r")`. The existing code comment already documented that the team had fixed one instance of this exact failure class before (switching `"\r\n"` → `"\r"`, since `SendCommandImmediate`'s appended `"\n"` was being absorbed into the TUI's multiline input buffer instead of submitting). The evidence above shows the same *symptom* — text absorbed into the paste buffer instead of submitting — still occurring with a bare `"\r"`, for a sufficiently large prompt.

`TmuxSession.SendKeys` (`session/tmux/tmux.go:1204`) does a single raw `t.ptmx.Write([]byte(keys))` — content and trailing `"\r"` go out together, in one `Write()` call, with no pause and no bracketed-paste markers. Terminal UIs commonly detect "this is a paste, not typed input" heuristically by burstiness (many characters arriving faster than a human could type). The `[Pasted text #4 **+1 lines**]` label is the direct signature of this: the CLI's own paste UI reports one *extra* line beyond the actual prompt content — consistent with the trailing `"\r"` having been folded into the detected paste block as one more line, rather than recognized as a later, separate Enter-to-submit. For a short message the burst is small enough that the paste-detection window has already closed by the time the trailing `"\r"` arrives (matching why the prior `"\r"`-only fix works for `steer_session`'s typically-short messages); for the driver's much longer orchestration prompts, the entire write — content and `"\r"` alike — can land within the same detection window.

**A second, related finding, not folded into this fix's scope**: the exact string `"◉ Claude resuming /loop wakeup"` visible in the screenshot's scrollback is not backend-injected text — `session/session_driver.go:688` recognizes it as one of the Claude Code CLI's own idle-spinner status phrases ("Baked/resumption markers used by `/loop` mode"), confirming this session is *also* self-driving itself via the CLI's own `/loop` skill (`ScheduleWakeup`), independently of the Go-side `AutonomousDriver.run` loop that's also externally polling and injecting turns into the same pane via `SendKeys`. Neither mechanism appears aware of the other. This is plausible as a contributing factor (two independent "keep the session going" writers racing on the same PTY would only widen the paste/submit race this fix narrows) but was not conclusively proven as *the* trigger for this specific incident, and fixing "should an autonomous backlog session be allowed to self-invoke `/loop` while `AutonomousDriver` is also driving it" is a distinct architectural question, not a one-line code fix. Flagged under Related below for separate investigation rather than bundled into this change.

## Fix Applied

`session/autonomous_driver.go`, `AutonomousDriver.run`: content and the submit keystroke are now sent as two **separate** `SendKeys` writes instead of one concatenated write — `d.inst.SendKeys(nextMsg)`, then `waitForPaneSettle(ctx, d.inst)`, then `d.inst.SendKeys("\r")`. `waitForPaneSettle` (new) polls `Instance.HasUpdated()` until the pane reports two consecutive unchanged reads (settled) or a 2-second deadline elapses, whichever comes first — giving the TUI's paste-detection window a chance to close before the submit keystroke arrives as its own write, shrinking the race regardless of what else might be happening on the pane at the same time (including a concurrent `/loop` wakeup, per the finding above). Best-effort: a pane that never settles (e.g. a permanently busy session) is not blocked forever — the deadline elapses and `"\r"` is sent anyway, matching the prior behavior's timing characteristics for that case.

## Files Affected

- `session/autonomous_driver.go` — `AutonomousDriver.run` (turn-injection split into two writes), new `waitForPaneSettle` helper + `paneSettleChecker` interface + `paneSettlePollInterval`/`paneSettleMaxWait` vars

## Verification

- `TestWaitForPaneSettle_should_returnBeforeDeadline_When_PaneStopsChangingEarly` — a fake pane reporting "changing, changing, then stable" returns promptly once settled, not after the full deadline.
- `TestWaitForPaneSettle_should_returnAtDeadline_When_PaneNeverSettles` — a fake pane that never stops changing still returns once the deadline elapses (never blocks the caller forever).
- `TestWaitForPaneSettle_should_returnImmediately_When_ContextCancelled` — a cancelled context stops the poll loop immediately.
- `go test ./session/...` (including `-race` scoped to `TestAutonomousDriver*`/`TestWaitForPaneSettle*`) — full existing suite green, no regressions; confirmed none of the existing `AutonomousDriver` tests exercise a started `Instance` (they all hit the pre-existing `!started` guard on `SendKeys` and never reach `waitForPaneSettle`), so this change is behavior-preserving for every test that predates it.
- `go build ./...` — clean.
- **Scoping note, same honesty standard as BUG-030's**: this is a real-tmux/PTY timing bug that cannot be forced deterministically in a unit test — there is no prior version of `waitForPaneSettle` to run a "fails pre-fix, passes post-fix" regression test against, since the helper (and the two-write split it enables) did not exist before this change. The tests above verify the new helper's own contract in isolation (settle detection, deadline behavior, cancellation) rather than reproducing the exact live PTY race end-to-end. The live incident itself (the screenshot, and a second `tmux capture-pane` reproduction during investigation) is the evidence the bug is real; a full end-to-end repro would require driving a real tmux pane with a large payload and asserting on Claude Code's own paste-detection behavior, which is out of this repo's control to assert against reliably.

## Reflection (Phase D — fix the class, not the instance)

**Classification**: Integration Gap — `AutonomousDriver`'s raw PTY write and Claude Code's TUI paste-detection heuristic are each individually reasonable, but their interaction (single burst write vs. burst-based paste detection) produces a failure mode neither side's own logic anticipates. The prior `\r\n`→`\r` fix addressed one instance of this same seam without closing the general case (message-length-dependent burst timing).

**Earliest achievable enforcement**: A unit test on `waitForPaneSettle`'s own contract is the practical achievable level — genuine PTY/TUI paste-detection timing cannot be expressed as a compile-time or lint-level invariant, and forcing the exact race deterministically in an automated test isn't practical (see scoping note above). No further ladder escalation attempted.

**Recurring shape**: This is at least the fourth bug found today in the same family — "an action is taken (here: a keystroke injection) but its actual effect (submission) is never verified" — alongside BUG-029 (a verdict recorded but never actioned), BUG-030 (a spawn that can fail with the failure swallowed), and this one (a submit keystroke that can silently not submit). All four share the shape: production code assumes a write/call succeeded in its full intended effect, with nothing checking the actual resulting state. The `paneSettleChecker`/`waitForPaneSettle` pattern introduced here (verify the effect before proceeding, rather than fire-and-hope) is a reusable building block if this shape recurs again in another PTY-write call site — flagged, along with BUG-029/030's flag, for the future `quality:architecture-review` pass already recommended against this general area.
