## Concerns

- [ ] **Story 1.1.3 / Task 1.1.3a** — `CLIFlags string` is a primitive that encodes a shell-parsed command fragment. Appending raw user-supplied strings with `" " + i.CLIFlags` is unsafe when the value contains quotes, spaces inside arguments, or shell metacharacters. The caller in `ResolveAlias` also uses string concatenation (`extraFlags`). This is primitive obsession: the field looks like a `string` but carries implicit parse constraints that no type enforces. **Remediation**: at the parse-at-boundary for alias invocation (detector output), split `--extra-flags` into `[]string` and thread a `[]string CLIArgs` field through `InstanceOptions` alongside or instead of the raw string. The tmux launch command builder can then `strings.Join` safely. Alternatively, document and validate that values must be space-separated tokens with no shell quoting — but then validate it at config load time, not silently at launch time.

- [ ] **Story 2.1.2 / Task 2.1.2b** — `expandEnvVars` is specified to silently **omit** keys when the referenced variable is unset. This creates a legal-but-surprising state: an alias author writes `{"ANTHROPIC_API_KEY": "${ANTHROPIC_API_KEY}"}` expecting the key to always reach the session, but if the variable is unset the key is dropped with no feedback. The plan notes this as a flagged risk (item 4) but defers a warning to "non-blocking, informational." A silently incomplete env can cause confusing session failures (wrong model, missing credentials) that are hard to debug after the fact. **Remediation**: emit a `log.Warn` at session-creation time listing every omitted key (already flagged); additionally, surface omitted keys in the `ListAliases` RPC response or in the resolution chip so the user can see at invocation time that a key will not be set. At minimum, the unit test (Task 2.1.2d) must assert the warning path, not just the happy path.

- [ ] **Story 2.1.2 / Task 2.1.2c** — `ResolveAlias` signature is `(cfg *Config, aliasName, branch, label, extraFlags string) (ResolvedDefaults, *AliasConfig, error)`. Returning `*AliasConfig` alongside `ResolvedDefaults` breaks the Single Responsibility of the function: callers receive both the fully-merged result (what to use) and the raw config (the input), creating a temptation to bypass the resolution layers and read alias fields directly. `session_service.go` (Task 5.1.3d) will consume this — if the handler ever reads `alias.Path` or `alias.Program` directly instead of using `resolved.*`, the resolution order (FR-6) is silently violated. **Remediation**: return only `(ResolvedDefaults, error)`. If the handler needs alias metadata (e.g., `alias.Path` to populate `resolvedPath`), promote `resolvedPath` into `ResolvedDefaults` as a `Path string` field. This mirrors how `ResolveDefaults` already computes `MatchedDirectory`. The handler then has one authoritative source of truth.

- [ ] **Story 3.1.3 / Task 3.1.3a** — `AliasDetector` is constructed with an `aliases: AliasEntry[]` snapshot at registration time. `OmnibarContext` re-registers on every reference change of the `aliases` array (Story 3.1.4). However, `useAliases` fetches once on mount with no polling. If config.json is edited while the app is open, the detector's alias list goes stale indefinitely. This is not the same staleness risk as `WorkflowDetector` (workflows are DB-backed and could be refreshed) — it is a config-file-backed list with no invalidation signal. The plan correctly notes "no polling needed" for performance, but the consequence — that detection reflects a stale snapshot until page reload — is not documented. **Remediation**: document the staleness window explicitly in the hook's JSDoc and in the alias palette empty-state copy. Optionally add a manual "Refresh" gesture or detect config changes via a server-sent event. At minimum, the hook should expose a `refresh()` callable so the palette can offer "Reload aliases" as an action.

- [ ] **Story 5.1.3 / Task 5.1.3d** — The handler logic path for `alias_name != ""` in `CreateSession` is designed to call `config.ResolveAlias` and then populate `resolvedPath`, `program`, `instanceOpts.EnvVars`, `instanceOpts.CLIFlags`, and `tags`. However, the existing `ResolveDefaults` block at line 1047–1061 runs unconditionally (when `!req.Msg.SkipDefaults`) before the alias resolution block that the plan inserts. This means for an alias invocation: global + directory + profile defaults are applied first (setting `program`, `autoYes`), then alias resolution re-applies — but the merge order for the alias resolution must now account for partially-populated `instanceOpts`. The plan says "populate ... from resolved result" but does not specify whether the alias resolution result overwrites or merges with the already-applied `ResolveDefaults` output. If `resolveDefaults` sets `program = "aider"` from a directory rule and then alias resolution also sets `program = "claude"`, the alias wins — which is correct per FR-6, but only if the handler explicitly overwrites rather than conditionally sets. **Remediation**: clarify in Task 5.1.3d that when `alias_name` is present, the code should skip the existing `ResolveDefaults` block entirely (or set `SkipDefaults = true` internally) and instead call only `ResolveAlias`, which already calls `ResolveDefaults` internally as layers 1–3. Running both in sequence will double-apply lower layers and could produce incorrect tag unions or overwritten `CLIFlags`.

- [ ] **Story 4.1.1 / Story 4.1.2** — The plan introduces two new hooks (`useAliases`, `useAliasSuggestions`) and a new state field (`aliasSuggestIndex`) all wired directly into `Omnibar.tsx`. `Omnibar.tsx` already orchestrates keyboard navigation, session search results, `AtCommandDropdown`, workflow detection chips, and form state. Adding alias palette keyboard navigation (`aliasSuggestIndex`, ArrowUp/Down/Enter interception) into the same component risks coupling: alias navigation and session-search navigation will compete for the same key events. The plan says "mutually exclusive with `AtCommandDropdown` in alias mode" but does not specify the mutual exclusion contract for session search result navigation (which also uses arrow keys). **Remediation**: before writing Story 4.1.2 code, audit the existing arrow-key and Enter handler(s) in `Omnibar.tsx` and document which state flag gates which handler branch. Add a single `activeDropdown: "none" | "alias" | "workflow" | "search"` discriminated state field to make the exclusion explicit and testable, rather than a boolean per dropdown.

## Nitpicks

- `AliasName` validation (`^[\w-]+$`) is documented in a comment on the struct field (plan line 163) but enforced only at "load time" — the plan does not specify which function validates and where the error surfaces. A config with an invalid alias name should produce a clear error at `LoadConfigFromPath`, not a silent nil return from `FindAlias` later.
- The `@` trigger collision with `PathWithBranchDetector` (which uses `@` as branch separator in `/path@branch`) is handled by the `AliasDetector` requiring a leading `@` before `[\w-]+`. `PathWithBranchDetector` requires the `@` to appear after path characters. The detectors do not conflict, but the placeholder text update (Story 4.1.4) must clearly distinguish `@alias` from `path@branch` — this distinction is noted in UX requirement ALIAS-003 but has no corresponding copy in the plan.
- `GetAliasesByGroup` (Task 2.1.2a) uses key `""` for ungrouped aliases. The frontend must special-case this empty string to suppress the section header. A named sentinel constant (e.g., `AliasGroupUngrouped = ""` in Go, `UNGROUPED_KEY = ""` in TypeScript) would make the contract explicit at both ends.
- `mergeProfileInto` currently overwrites `CLIFlags` with the last non-empty value rather than appending. When `ResolveAlias` calls it with the alias's inline `CLIFlags` on top of a profile's `CLIFlags`, the profile flags are silently dropped. FR-6 and FR-5 imply concatenation semantics for `CLIFlags` (each layer's flags should accumulate). This is an existing behavior in `ResolveDefaults` for the three current layers — the alias layer will inherit the same truncation bug. File a follow-up or fix `mergeProfileInto` before alias support launches.
- The `AliasProto` message in Task 2.1.3a omits `env_vars` and `cli_flags` fields. `ListAliases` will therefore not expose these fields to the frontend, which means the resolution chip cannot show "will inject N env vars" without a separate enrichment call. This is a scope decision but should be explicit — either add the fields to `AliasProto` or document that the chip only shows path/program.
